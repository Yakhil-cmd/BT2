### Title
`DenyReserveTransferToRelayChain` in Asset Hub `Barrier` only inspects the top-level instruction slice and can be bypassed by nesting the denied instructions inside `SetAppendix`/`SetErrorHandler`/`ExecuteWithOrigin` - ([File: system-parachains/asset-hubs/asset-hub-kusama/src/xcm_config.rs](), [File: system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs]())

### Summary
`asset-hub-kusama` and `asset-hub-polkadot` wrap the deny filter as plain `DenyReserveTransferToRelayChain`, while `bridge-hub-polkadot` and `bulletin-polkadot` in the same repository deliberately wrap the identical filter with `DenyRecursively<...>`. This inconsistency means the Asset Hub barrier only scans the top-level instruction list for `InitiateReserveWithdraw`/`DepositReserveAsset`/`TransferReserveAsset` targeting `Parent`, and does not recurse into nested `Xcm` programs carried inside `SetAppendix`, `SetErrorHandler`, or `ExecuteWithOrigin`.

### Finding Description
The Asset Hub `Barrier` type is: [1](#0-0) 

`DenyReserveTransferToRelayChain` (from `xcm-builder`, not vendored in this repo) implements `ShouldExecute` by iterating `message.iter()` over the **top-level** instruction slice, looking for `InitiateReserveWithdraw`, `DepositReserveAsset`, or `TransferReserveAsset` whose `reserve`/`dest` resolves to `Parent`, and denying execution (`ProcessMessageError::Unsupported`) if found. It does not descend into the `Xcm` payloads carried by nesting instructions such as `SetAppendix(Xcm)`, `SetErrorHandler(Xcm)`, or `ExecuteWithOrigin { xcm: Xcm, .. }`.

This is exactly the gap that `DenyRecursively<T>` was introduced to close elsewhere in this same codebase: both `bridge-hub-polkadot` and `bulletin-polkadot` explicitly wrap the deny filter as `DenyRecursively<DenyReserveTransferToRelayChain>` (and, for bridge-hub, also `DenyRecursively<DenyExportMessageFrom<...>>`): [2](#0-1) [3](#0-2) 

However, `asset-hub-kusama`, `asset-hub-polkadot`, and several other system parachains (`coretime-kusama`, `coretime-polkadot`, `collectives-polkadot`, `people-kusama`, `people-polkadot`, `encointer`) still use the bare, non-recursive `DenyReserveTransferToRelayChain`: [4](#0-3) 

Exploit flow: a signed user calls `pallet_xcm::execute` (an unprivileged, permissionless extrinsic) with a top-level XCM whose first instructions satisfy `AllowTopLevelPaidExecutionFrom<Everything>` (e.g. `WithdrawAsset` + `BuyExecution`), so the barrier's fallback tuple lets the message through once `DenyReserveTransferToRelayChain` itself does not trip. The attacker embeds the actually-denied instruction (`DepositReserveAsset`/`InitiateReserveWithdraw`/`TransferReserveAsset` targeting `(1, Here)`) inside `SetAppendix(Xcm(...))` or `SetErrorHandler(Xcm(...))` instead of at the top level. Because `DenyReserveTransferToRelayChain::should_execute` only scans the outer `message` slice, the nested reserve-transfer-to-relay instruction is invisible to it, and the barrier returns `Ok(())` for the whole program. When the executor later runs the appendix/error-handler as part of the same XCVM program, the reserve-transfer instruction executes and dispatches the outbound message to the Relay Chain, unaffected by the deny filter that was supposed to block exactly this pattern.

### Impact Explanation
If the reserve-transferred asset is not one the Relay Chain trusts Asset Hub as a reserve for, the Relay's own XCM barrier/asset-trap logic will not credit the beneficiary, and the assets debited/burned on Asset Hub become trapped (`AssetTrap`) on the Relay Chain, unreachable without a manual claim (and impossible to claim if the asset type/config isn't recognized at all). This matches the scoped impact: cross-chain balance mismatch and loss/stuck assets caused by a filter meant to categorically prevent Asset-Hub-to-Relay reserve transfers of arbitrary/foreign assets.

### Likelihood Explanation
The only precondition is a signed account able to call `pallet_xcm::execute` (or `send`) with a hand-crafted XCM - a completely standard, unprivileged, repeatable action. No governance, proxy escalation, or special origin is needed. The bypass relies purely on the well-known top-level-only scanning behavior of `DenyReserveTransferToRelayChain` combined with the confirmed fact that this repository's own bridge-hub/bulletin runtimes were patched with `DenyRecursively` to close this exact gap, while Asset Hub was not.

### Recommendation
Wrap the deny filter in Asset Hub's `Barrier` (and the other affected system-parachain runtimes: coretime-kusama/polkadot, collectives-polkadot, people-kusama/polkadot, encointer) with `DenyRecursively`, matching bridge-hub-polkadot/bulletin-polkadot:
```rust
pub type Barrier = TrailingSetTopicAsId<
    DenyThenTry<
        DenyRecursively<DenyReserveTransferToRelayChain>,
        ( /* ... */ ),
    >,
>;
```

### Proof of Concept
xcm-emulator integration test on Asset Hub (Kusama or Polkadot):
1. Fund a test account with a non-native/foreign asset and native token for fees on Asset Hub.
2. Craft an XCM: top-level `WithdrawAsset` + `BuyExecution` (to satisfy `AllowTopLevelPaidExecutionFrom`), followed by `SetAppendix(Xcm(vec![DepositReserveAsset { assets: Wild(All), dest: Location::parent(), xcm: Xcm(vec![]) }]))`, then a benign final instruction (e.g. `DepositAsset` back to self).
3. Submit via `PolkadotXcm::execute` from a signed origin.
4. Assert:
   - The call succeeds (barrier does not return `Filtered`/`Unsupported`), proving `DenyReserveTransferToRelayChain` did not detect the nested reserve-transfer.
   - After appendix execution, a message is queued/sent to the Relay Chain performing the reserve transfer.
   - On the Relay Chain side, assert the asset is trapped (`AssetsTrapped` event) or the transfer is otherwise unrecoverable, confirming loss/stuck-asset impact.
5. Repeat the same scenario against `bridge-hub-polkadot` (which uses `DenyRecursively<DenyReserveTransferToRelayChain>`) and assert the call is instead rejected with `ProcessMessageError::Unsupported`/`Filtered`, demonstrating the asymmetry between the protected and unprotected runtimes.
