### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` [1](#0-0) , with no filter on the repository that authenticated the webhook. `Shipit::WebhooksController#verify_signature` only checks that the payload is validly signed for the GitHub organization named in the payload's own `repository.owner.login`/`organization.login` field [2](#0-1) [3](#0-2) ; it never confirms that the payload's repository/SHA corresponds to the specific `Stack`/`Commit` rows that will be mutated. Because `Commit` rows across all stacks are keyed only by `sha` with no per-repository namespace enforced at write time, any commit sharing that SHA in another stack (e.g. a fork/mirror sharing git history with an attacker-owned repo) gets its status set, and `blocked?`/`deployable?` on that unrelated stack can flip as a result.

### Finding Description
The broken binding: the code implicitly assumes `commit.sha == params.sha` implies `commit.stack.repository == webhook.repository`, but nothing enforces that equality.

Path:
1. Attacker owns/pushes to a GitHub repository `R1` that has the Shipit GitHub App installed on its organization, so GitHub will deliver a genuinely signed `status` webhook for events in `R1` (attacker needs no `webhook_secret`; GitHub sends real, correctly-signed events for their own repo activity).
2. `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and validates the signature using that organization's key [4](#0-3) . This passes because the request truly did come from GitHub for `R1`; the check never compares `R1` to the stack(s) that will be looked up later.
3. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to `StatusHandler`, whose `params` schema only requires `sha`/`state`/`context` — no repository identifier is required or checked [5](#0-4) .
4. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) . This query is global across the `commits` table, not scoped to any stack/repository derived from the webhook payload.
5. `Commit#create_status_from_github!` writes into `statuses` for that commit's own `stack_id` [6](#0-5) , and `add_status` recomputes `status`, emits `deployable_status`/`commit_status` hooks, and calls `stack.schedule_merges` on success [7](#0-6) .
6. `Commit#blocked?` walks `stack.commits.reachable...any?(&:blocking?)` and `deployable?` depends on `success? && !blocked?` [8](#0-7) . A forced `success` or a forced blocking-context status therefore directly flips `blocked?`/`deployable?` for whatever stack owns a `Commit` row with the matching SHA — even if that stack tracks a completely different GitHub repository from the one that authenticated the webhook.

Why existing guards fail: `verify_signature` validates *who sent it* (a real GitHub org/app) but not *which stack's data may be touched*; `ExplicitParameters` on `StatusHandler` validates the shape of the payload but has no repository field to check; there is no model validation on `Commit`/`Status` tying the write to `params.dig('repository', ...)`. The precondition needed is that two `Stack`s (potentially tracking a fork, mirror, or otherwise repo with shared git history) contain `Commit` rows with an identical `sha` — a realistic condition since git SHAs are content-derived and identical commits routinely exist across forked/mirrored repositories, and the attacker only needs to control (or trigger status posting on) one such repository.

### Impact Explanation
A successful exploitation lets an attacker who authenticated only for `R1` mutate `Status`/`blocked?`/`deployable?` state on a `Stack` tracking a different repository `R2`, as long as `R1` and `R2` share a commit SHA (fork/mirror scenario). This can force `stack.schedule_merges` to fire on `success`, or set `blocked?` on a `blocking_statuses`-configured stack to `true`, gating or unblocking deploys/merges on a stack the attacker never authenticated for. This matches "a payload for one repository mutating another's stack/commit" — Critical, cross-tenant state manipulation of deploy/merge gating.

### Likelihood Explanation
Requires: (a) the target stack has `blocking_statuses` configured (or otherwise depends on the `ci/test` context) so the flip has observable gating effect; (b) a `Commit` row with an identical SHA exists in both the attacker-reachable repository and the victim stack — realistic for forked/mirrored repos sharing history, less so for unrelated repos (SHA collision is otherwise infeasible). Attacker cost is low: no secrets needed, only ownership of a repo whose GitHub App–signed webhooks reach the same Shipit instance and whose commit history overlaps with the victim's. Repeatable per shared-SHA commit.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers) to the repository identified in the webhook payload — e.g., join through `stack.repository` and filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repo.id })` — instead of a bare `Commit.where(sha: ...)`. This restores the invariant that a status only affects commits belonging to stacks of the repository that authenticated the webhook.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` for repository `attacker/repo` and `stack_b` for repository `victim/repo`, with `stack_b.blocking_statuses = ['ci/test']`.
2. Create `commit_a = stack_a.commits.create!(sha: 'deadbeef...')` and `commit_b = stack_b.commits.create!(sha: 'deadbeef...')` (same SHA, simulating shared history), plus an older deployed commit on `stack_b`.
3. Assert baseline: `commit_b.reload.blocked?` is `false` (or whatever pre-state) and `stack_b.deployable?`/`commit_b.deployable?` unaffected.
4. Build payload `{ sha: 'deadbeef...', context: 'ci/test', state: 'success', repository: { owner: { login: 'attacker' } } }` scoped/signed for `attacker/repo` only, and call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (or `process`) directly, bypassing only the controller's signature check (already proven valid for `attacker/repo`).
5. Assert `commit_b.reload.statuses.last.context == 'ci/test'` and `commit_b.reload.blocked?`/`stack_b.deployable?` changed — i.e., `stack_b`'s state changed from a webhook that only authenticated for `stack_a`'s repository, proving the equality `commit.stack.repository == webhook.repository` does not hold.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
