### Title
Ambiguous, delimiter-less hashing of prosaic/arbiter contract fields allows content-boundary collisions - (File: `prosaic_contract.js`, `arbiter_contract.js`)

### Summary
The external report describes an ERC-712 typehash string that is malformed (extra whitespace between struct members), breaking the canonical, unambiguous encoding that EIP-712 requires and causing signature verification to silently fail. The root cause class is "structured data is serialized into a hash preimage in a way that does not guarantee an unambiguous, collision-free mapping between distinct field values and distinct hash outputs." `ocore` has the same bug class in its bespoke contract-hashing helpers, but instead of merely breaking verification, the ambiguity is exploitable: `prosaic_contract.js`'s `getHash`/`getHashV1` and the legacy branch of `arbiter_contract.js`'s `getHashSrc` concatenate multiple free-text/numeric fields with **no delimiter at all**, so different `(title, text, creation_date, …)` tuples can produce an identical hash.

### Finding Description
`ocore`'s canonical structured-hashing utility, `getSourceString` in `string_utils.js`, is deliberately designed to avoid ambiguity: every field is prefixed with a type tag and fields/keys are separated by an explicit `\x00` join character, and any embedded `\x00` in a string or key throws an error [1](#0-0) . This is the correct analog of "properly delimited EIP-712 struct encoding."

However, the prosaic-contract and arbiter-contract features bypass this safe primitive and instead build the hash preimage via naive string concatenation:

- `prosaic_contract.js` `getHash` and `getHashV1` hash `contract.title + contract.text + contract.creation_date` with **no separator whatsoever**: [2](#0-1) 

- `arbiter_contract.js` `getHashSrc` has two branches: a "new" branch that joins fields with a delimiter (`exports.DELIMITER = "[|#|]"`), and a legacy branch (for contracts created before `NEW_HASH_DATE`) that joins the same free-text fields with `""` (no delimiter): [3](#0-2) 

Because `title` and `text` are attacker/counterparty-controlled free-text strings, an adversarial contract counterparty can choose `title = "AB"`, `text = "C..."` vs. `title = "A"`, `text = "BC..."` (or shift characters across the `title`/`text`/`amount`/`name` boundaries in the legacy arbiter path) such that the concatenated preimage — and therefore the resulting SHA-256/base64 `contract.hash` — is identical for two semantically different contracts. This is exactly the same root-cause class as the report's "extra space" issue: the hash no longer uniquely commits to the intended structured data.

### Impact Explanation
The contract `hash` is the value that is signed, shared with the counterparty, referenced from the on-chain `data` message payload (`contract_text_hash`), and checked for equality when the wallet reconciles a signing unit against a locally-stored contract (`payload.contract_text_hash !== contract.hash`) [4](#0-3) . Since this hash is meant to bind a specific human-readable agreement (title/text/amount/parties) to the cryptographic record that later authorizes fund release via a shared/multisig address, a boundary-shifting collision lets a malicious counterparty (in a private, unprivileged wallet-to-wallet negotiation — no elevated network/hub privileges required) present one version of a contract for review/signature while a colliding, differently-worded version (e.g., different `amount`, `payee_name`, or dispute terms) validates against the very same `contract.hash` that was accepted/signed. In the arbiter-contract flow this hash underlies dispute resolution and fund routing between payer/payee/arbiter, so a collision can be leveraged to misdirect or dispute funds — i.e., counterparty fund loss — which is a concrete impact under the accepted-impact criteria (unauthorized/altered fund disposition between private-payment counterparties).

### Likelihood Explanation
Likelihood is high for anyone acting as a prosaic/arbiter contract counterparty: no cryptographic key compromise, no privileged network position, and no on-chain race condition is required — only the ability to choose the free-text `title`/`text` fields of a contract offer, which is inherent to the feature (both parties are expected to author these strings). Constructing a boundary-shifting collision between two chosen strings that hash to the same value under plain concatenation is trivial (simply re-partitioning characters between adjacent fields yields byte-identical preimages, guaranteeing equal hashes without any cryptographic effort). The legacy arbiter branch is gated only by `creation_date` predating `NEW_HASH_DATE` (`'2026-11-01'`), meaning it remains reachable for contracts dated before that cutoff, while the prosaic-contract `getHash`/`getHashV1` path has no such date gating and is presumably still in active use.

### Recommendation
- Replace the ad hoc concatenation in `prosaic_contract.js`'s `getHash`/`getHashV1` with the project's existing safe, delimiter- and type-tag-based serializer (`string_utils.getSourceString`/`object_hash.getBase64Hash` applied to a structured object `{title, text, creation_date}`) so that field boundaries can never be shifted without changing the hash.
- For `arbiter_contract.js`, drop (or explicitly reject/flag as insecure) the legacy no-delimiter branch of `getHashSrc`, or retroactively re-hash/migrate any contract whose `creation_date` predates `NEW_HASH_DATE` using the delimiter-safe scheme, and ensure the delimiter chosen (`"[|#|]"`) cannot itself appear inside `title`/`text`/`party_name` (otherwise the same class of collision persists for the "new" branch too — this should be explicitly validated/escaped, mirroring `getSourceString`'s `\x00`-in-string rejection).

### Proof of Concept
1. Party A offers a prosaic contract with `title = "AB"`, `text = "Pay 100 USD"`, `creation_date = "2024-01-01 00:00:00"`.
   `hash1 = sha256("AB" + "Pay 100 USD" + "2024-01-01 00:00:00")`.
2. Malicious Party B (or a later re-presentation by A) crafts a semantically different contract with `title = "A"`, `text = "BPay 100 USD"`, same `creation_date`.
   `hash2 = sha256("A" + "BPay 100 USD" + "2024-01-01 00:00:00") = hash1`.
3. Both contracts share `contract.hash`. When `handleReceivedSigningUnit` later checks `payload.contract_text_hash !== contract.hash` [5](#0-4) , either variant of the contract text passes verification against the same on-chain-referenced hash, so the wallet cannot distinguish which agreement text the signing unit actually corresponds to — an attacker-controlled party can substitute contract wording/terms post hoc while keeping the same committed hash.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
