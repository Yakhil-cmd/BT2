## Confirmed root cause

`Handler#stacks` resolves which `Stack`/`Repository` a webhook event acts on purely from the JSON body's `repository.full_name` field: [1](#0-0) 

That lookup is completely independent of which GitHub organization's `webhook_secret` was used to authenticate the request. Authentication happens earlier, in `WebhooksController`, keyed off a *different* field pulled from the same attacker-controlled JSON body: [2](#0-1) [3](#0-2) 

`repository_owner` reads `repository.owner.login` (or falls back to `organization.login`) to pick which org's HMAC secret (`Shipit.github(organization: repository_owner)`) verifies `X-Hub-Signature`. `PushHandler`/`StatusHandler`, however, act on whatever `repository.full_name` says, via `Repository.from_github_repo_name`: [4](#0-3) [5](#0-4) 

Nothing in the request pipeline enforces `repository.owner.login == repository.full_name.split('/').first`. Since GitHub itself always sends consistent values, this divergence is only reachable by a party who can *craft* an arbitrary JSON payload and sign it with a webhook secret Shipit trusts — i.e., a tenant organization that is legitimately registered in Shipit's multi-org `github:` config (see `config/secrets.development.shopify.yml`) but that has no relationship to another tenant's repository.

### Trust equality broken
`repository_owner` (the org whose secret authenticated the payload) is assumed to equal `repository.full_name`'s owner (the repository the handler subsequently writes to). That assumption is never checked.

## Analog validity

This matches the whitelisted pattern "an organization that authenticated versus the repository that is written." A malicious/compromised org admin who owns Org-A (configured in Shipit as one of several GitHub orgs/apps `Shipit.github(organization: ...)` can serve) knows Org-A's `webhook_secret` because it belongs to them (this is not "the app's own secret" — it is the tenant's own credential, so it does not fall under the "requires the app's webhook_secret" exclusion). They forge a POST to `/webhooks` with:
```json
{"repository": {"owner": {"login": "org-a"}, "full_name": "org-b/victim-repo"}, "ref": "refs/heads/main", "after": "<attacker sha>"}
```
and sign it with Org-A's `webhook_secret`. `verify_signature` succeeds (org-a matches), but `PushHandler` calls `stack.sync_github(expected_head_sha: ...)` against a stack that belongs to `org-b/victim-repo`, forcing an unrelated tenant's stack to re-sync against attacker-chosen `expected_head_sha`, and `StatusHandler` lets Org-A forge commit statuses (`Commit.create_status_from_github!`) for any `sha` value regardless of which repo/org it actually belongs to, since `StatusHandler` doesn't even scope by repository at all — it matches on the global `sha` across all commits.

This is a genuine cross-tenant boundary break reachable by any org onboarded into a shared multi-org Shipit instance, without needing another tenant's secret, an `ApiClient` token, or repository write access on GitHub itself.

### Impact
- `StatusHandler` (no repository scoping at all — matches `Commit.where(sha: params.sha)` globally) lets any authenticated org forge a passing/failing CI status on **any commit of any stack in the whole Shipit instance**, which can flip `Commit#deployable?` and enable an unauthorized deploy of another org's stack (a High/Critical-adjacent "unauthorized deploy" primitive, since Shipit gates deploys on commit status).
- `PushHandler` lets Org-A trigger `sync_github` with an `expected_head_sha` against a completely unrelated stack, causing spurious GitHub API calls to a repository Org-A doesn't own/administer using the credentials of whichever org actually owns that stack (cross-repository interaction it should never have access to).

### Title
Webhook handlers resolve target repository/commit from unauthenticated payload fields, decoupled from the organization whose secret verified the signature - (File: `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook using the org derived from `repository.owner.login`/`organization.login`, but the handlers that execute afterward (`Handler#stacks`, `StatusHandler#process`) key off `repository.full_name` or a bare `sha`, with no cross-check that these refer to the same organization/repository that was actually authenticated.

### Finding Description
`Handler#repository_name` reads `payload.dig('repository', 'full_name')` [6](#0-5)  while `WebhooksController#repository_owner` reads `params.dig('repository', 'owner', 'login')` [3](#0-2)  to select which org's `webhook_secret` verifies the HMAC signature. GitHub always keeps these fields consistent, but nothing in Shipit enforces it for a crafted payload signed by a legitimately-configured (but different) tenant org. `StatusHandler` is worse — it never consults `repository` at all, matching purely on `Commit.where(sha: params.sha)` instance-wide [7](#0-6) .

### Impact Explanation
Any org configured as a Shipit "tenant" (multiple orgs are supported by `Shipit.github(organization:)`, each with its own `webhook_secret`) can forge push/status events for stacks belonging to a different org's repositories, causing forged CI statuses that unlock deploys (`Commit#deployable?`) and spurious cross-repository `sync_github` calls — both cross the "cross-repository writes / unauthorized deploy" impact bar.

### Likelihood Explanation
Requires only that the attacker control one legitimately-onboarded GitHub organization/app in a multi-tenant Shipit deployment (a realistic, commonly-documented setup per `config/secrets.development.shopify.yml`), and the ability to send an arbitrary signed HTTP POST — no GitHub write access, no `ApiClient` token, and no Shipit account needed.

### Recommendation
In `Handler#stacks`/`StatusHandler#process` (and any other handler that resolves a `Repository`/`Stack`/`Commit`), verify that the repository/stack's owner matches the organization that was used to validate the webhook signature (pass the verified organization down from `WebhooksController` into the handler and assert equality with `repository.full_name`'s owner before acting).

### Proof of Concept
1. Shipit is configured with two orgs, `org-a` and `org-b`, each with a distinct `webhook_secret` (multi-tenant setup as documented in `config/secrets.development.shopify.yml`).
2. Attacker controls `org-a` and knows `org-a`'s webhook secret.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body `{"repository": {"owner": {"login": "org-a"}}, "sha": "<victim commit sha in org-b's stack>", "state": "success", "context": "ci/attacker"}`, signed with `org-a`'s secret.
4. `verify_signature` succeeds (org-a's secret matches org-a's declared owner).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim commit belonging to `org-b`'s stack regardless of org — and creates a forged successful status on it, potentially satisfying `deployable?` checks and enabling an unauthorized deploy of `org-b`'s stack.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
