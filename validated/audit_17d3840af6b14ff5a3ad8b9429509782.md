### Title
Membership webhook signature check is scoped to attacker-supplied `organization.login`, letting a signer for organization A mutate `Team`/`Membership` rows belonging to organization B via `params.team.id` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to validate against using an attacker-controlled payload field (`organization.login`, since membership events carry no `repository` key), rather than the organization that actually owns the team being mutated. `MembershipHandler#find_or_create_team!` then resolves the target `Team` purely by `params.team.id` (`github_id`), with no check that the found/created team's `organization` matches the organization whose secret validated the signature, so a validly-signed payload from organization A can add or remove members on organization B's `Shipit.github_teams`-authorized team.

### Finding Description
Binding claimed: `params.team.id` resolved via `Team.find_or_create_by!(github_id: params.team.id)` == a team actually owned by the organization whose secret verified `X-Hub-Signature`. This binding is never enforced.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) . Membership events don't carry a `repository` key, so `repository_owner` is exactly the attacker-supplied `organization.login`.
2. It then does `github_app = Shipit.github(organization: repository_owner)` and validates the signature against that org's configured `webhook_secret` [2](#0-1) . In a multi-org config, `Shipit.github_app_config(organization)` looks up a distinct secret per organization key [3](#0-2) , and `verify_webhook_signature` HMACs the raw payload with that specific secret [4](#0-3) . This only proves "whoever sent this knows org A's secret" — it says nothing about which `team.id` is safe to mutate.
3. `MembershipHandler#process` resolves the team purely from `params.team.id`, independent of the verified organization: `Team.find_or_create_by!(github_id: params.team.id) do |team| team.github_team = params.team; team.organization = params.organization.login end` [5](#0-4) . Because `find_or_create_by!`'s block only runs on creation, if a `Team` with that `github_id` already exists (e.g., organization B's team, previously created via `Team.find_or_create_by_handle` for `Shipit.github_teams`), the existing record is returned untouched — the attacker's `organization.login` value in the block is never applied and never checked against it.
4. `process` then executes `team.add_member(member)` or `team.members.delete(member)` on that resolved team [6](#0-5) , mutating organization B's authorization table using a signature that only proved knowledge of organization A's secret.

Exploit flow: In a Shipit deployment configured with multiple GitHub orgs (a documented, supported configuration [7](#0-6) ), an attacker who administers their own tenant organization A's GitHub App (and therefore legitimately knows A's `webhook_secret`, not a secret they had to steal) sends `POST /webhooks` with `X-Github-Event: membership`, `organization.login: "orgA"`, HMAC-signed with A's secret, but `team.id` set to the `github_id` of an existing team belonging to authorized organization B (e.g. one of `Shipit.github_teams`), and `action: "removed"` plus an existing `member.login`. `verify_signature` passes because the signature is validated against org A's own secret for org A's own claimed identity. `MembershipHandler` then deletes that member's `Membership` row for organization B's authorized team — or, with `action: "added"`, silently grants Shipit-authorization-team membership to an arbitrary user, an escalation into `Shipit.github_teams` authorization.

No existing guard prevents this: `drop_unhandled_event` and `ExplicitParameters` schema only validate shape/presence of fields, not organizational ownership; `verify_signature` never re-derives `repository_owner` from the resolved `Team` record; `find_or_create_team!` performs no `organization ==` check against the signed org before mutating membership.

### Impact Explanation
An attacker who controls (administers) any organization configured as a tenant in Shipit's multi-org GitHub App setup — even one deliberately kept out of `Shipit.github_teams` — can write to another organization's `Team`/`Membership` records: removing a legitimate authorized user's Shipit access (denial-of-authorization) or, via the identical `added` branch, granting an arbitrary GitHub login membership in a `Shipit.github_teams`-authorized team. The latter is escalation into `Shipit.github_teams` authorization (High/Critical per the rubric), and it is repeatable against any team `github_id` the attacker can learn (team IDs/slugs are often discoverable), across any number of victim organizations sharing the same Shipit instance.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where the attacker legitimately controls one configured tenant organization's GitHub App/webhook secret — a realistic and documented deployment shape, not a hypothetical. No Shipit session, API token, or stolen secret is needed beyond the attacker's own org's webhook secret, which they configure themselves. The only extra piece of information needed is the target team's `github_id`, which is often discoverable via the GitHub API/UI for the victim org's teams.

### Recommendation
After resolving the `Team` in `MembershipHandler#find_or_create_team!`, verify `team.organization == params.organization.login` (and that this equals the organization actually used to validate the webhook signature); reject the event otherwise. More robustly, `WebhooksController#verify_signature` should not trust `organization.login`/`repository.owner.login` from the payload as the sole key for selecting which secret to validate against without binding that identity to the resource being mutated downstream.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, multi-org secrets stubbed):
1. Configure `Shipit.stubs(:secrets)` (or equivalent) so `secrets.github` has two orgs: `org_a` (attacker-controlled, secret `secretA`, not in `oauth.teams`) and `shopify` (secret `secretB`, in `oauth.teams`).
2. Fixture: `team = shipit_teams(:shopify_developers)` with `organization: 'shopify'`, existing `github_id`; `membership = shipit_memberships(:walrus_shopify_developers)`.
3. Build payload: `{ action: 'removed', team: { id: team.github_id, name: team.name, slug: team.slug, url: team.api_url }, organization: { login: 'org_a' }, member: { login: 'walrus' } }.to_json`.
4. Sign with `secretA` (org A's secret): `sig = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', 'secretA', payload)`.
5. `post :create, body: payload, as: :json` with headers `X-Github-Event: membership`, `X-Hub-Signature: sig`.
6. Assert both sides of the binding: before request, `assert team.organization == 'shopify'`; after request, `assert_response :ok` yet `refute team.members.reload.include?(walrus_user)` should be the failing/vulnerable outcome — i.e. assert the bug by showing `Membership.count` decreased (or `team.reload.members` no longer includes `walrus`) even though the verified signer was `org_a`, not `shopify`. A fixed implementation should instead return `:unprocessable_entity` / leave `Membership` untouched.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

      return true unless webhook_secret

## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
