### Title
Emergency and regular OP-list vote counting are not mutually exclusive, allowing conflicting `system_vars`/`op_list` state to be written for the same subject - (File: main_chain.js, writer.js)

### Summary
`countVotes()` in `main_chain.js` is invoked from two independent code paths that are meant to be mutually exclusive in intent (emergency vote counting is only supposed to kick in when normal consensus is "stuck"), but no mechanism actually prevents both from running and mutating the same `system_vars` / `storage.systemVars.op_list` state for the `op_list` subject. This mirrors the `GenesisGroup.emergencyExit`/`launch` bug class: two state-mutating paths intended to be exclusive remain independently callable, corrupting shared accounting/consensus state.

### Finding Description
`countVotes(conn, mci, subject, is_emergency, emergency_count_command_timestamp)` performs vote tallying and unconditionally writes the result into `system_vars` via `REPLACE`/`INSERT` and unshifts a new entry onto `storage.systemVars.op_list` [1](#0-0) .

It is called from two separate places:

1. **Regular path** - triggered only after an `op_list` `system_vote_count` message becomes *stable* (i.e., after full DAG stabilization/consensus), collected in `voteCountSubjects` and processed once per MCI at the end of `markMcIndexStable` [2](#0-1) .

2. **Emergency path** - triggered immediately when a unit containing a `system_vote_count` message for `op_list` is *written* (before that unit is even stable), via `writer.js`, calling `main_chain.applyEmergencyOpListChange` [3](#0-2) . `applyEmergencyOpListChange` only guards on a timestamp/timeout check against the last stable unit, not on whether the regular path has already run or will run for the same underlying vote [4](#0-3) .

Both paths call the same `countVotes` function for the same `subject = 'op_list'`, and both persist their result with `storage.systemVars.op_list.unshift({ vote_count_mci, value, is_emergency })` and a `system_vars` row keyed by `(subject, vote_count_mci)` [5](#0-4) . There is no check in either path that:
- the emergency path cannot run if a regular vote count for an overlapping/later MCI has already been applied, or
- the regular path cannot run (or must reconcile) if an emergency vote count already applied for that vote.

Because the emergency path executes at unit-write time (deterministic node-local wall-clock/DAG-propagation timing) while the regular path executes only at DAG-stabilization time, the relative ordering of these two mutations is not guaranteed to be identical across all nodes. This is analogous to the reported bug where `launch()` and `emergencyExit()` in `GenesisGroup` could both mutate the same accounting variable (`totalCommittedFGEN`) without excluding each other, corrupting shared state.

### Impact Explanation
`storage.systemVars.op_list` (and the underlying `system_vars` table) determines the current set of Order Providers/witnesses used for majority-witness and stability determination throughout the DAG consensus engine. If the emergency and regular vote-count paths can race or double-apply for the same underlying vote (or apply results in different node-local order), different nodes can end up with divergent `op_list` entries/ordering for a given MCI. Since witness-list determination directly drives stability and validity checks for the entire DAG, this can lead to **node disagreement on validity/stability of units**, which is one of the accepted high-impact outcomes for this class of bug (network unable to reach consistent confirmation of new units).

### Likelihood Explanation
The emergency path is reachable by any unprivileged unit poster who includes a `system_vote_count` message with payload `'op_list'` in a unit — this is a standard message type validated in `validation.js` and not restricted to privileged addresses [6](#0-5) . The `applyEmergencyOpListChange` guard normally prevents premature emergency execution (it requires `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` since the last stable unit), so under normal network conditions this is not exploitable. However, during any genuine period of stalled stabilization (which the emergency mechanism is explicitly designed to handle), an attacker or even ordinary users posting `system_vote_count` messages could trigger the emergency path multiple times/at different real-time moments on different nodes while the regular (stability-driven) path is also pending, producing the described lack of mutual exclusivity. This requires the DAG to actually be near/at a stall condition to be practically triggered, which lowers likelihood somewhat, but the missing mutual-exclusion guard is a genuine structural gap rather than a purely theoretical one.

### Recommendation
- Ensure the emergency `countVotes` path cannot execute if a regular (non-emergency) vote count for `op_list` has already been finalized for a corresponding or later state, and vice versa.
- Ensure the regular vote-counting path checks whether an emergency vote count has already been applied for the same or a later MCI before inserting/replacing `system_vars`, to prevent stale or out-of-order entries in `storage.systemVars.op_list`.
- Consider adding a single, explicit state flag (akin to a `bEmergencyApplied`/lock) that both code paths check before mutating `system_vars`/`storage.systemVars.op_list`, matching the recommendation pattern from the referenced report (mutual guarding + explicit invalidation of the superseded path's effect).

### Proof of Concept
Exact reproduction requires coordinating: (1) posting an `op_list` `system_vote` from enough voting balance to satisfy `SYSTEM_VOTE_MIN_SHARE`, (2) posting a `system_vote_count` unit for `op_list` while the network/local node has not stabilized past `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` since the last stable MC unit (satisfying the guard in `applyEmergencyOpListChange`), triggering the emergency path in `writer.js` at write time [3](#0-2) , and (3) allowing the same or a related `system_vote_count` message to later stabilize and be processed by the regular path in `markMcIndexStable`/`updateMainChain` [2](#0-1) . I was not able to fully trace how `storage.systemVars.op_list` entries are subsequently *consumed* (e.g., the exact `getOpList`/witness-selection lookup function was not located within the indexed context) to confirm the precise downstream consensus divergence mechanics with certainty; a live/local multi-node test harness (not available via static indexing here) would be needed to conclusively demonstrate node divergence. This uncertainty should be resolved with a full Devin session that can run the ocore test suite and multi-node simulation.
