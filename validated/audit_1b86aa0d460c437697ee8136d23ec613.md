### Title
Git credential cache is keyed by host, not full URL — attacker-controlled submodule URLs on the same host can exfiltrate git-sync's stored credentials (File: `main.go`)

### Summary
`git-sync` configures git to cache credentials globally via `credential.helper: cache --timeout 3600` [1](#0-0)  and stores usernames/passwords/tokens with `git credential approve` in `StoreCredentials` [2](#0-1) . Git's credential cache, by default, matches stored credentials by protocol+host (not full URL or path) unless `credential.useHttpPath` is explicitly enabled, which `SetupDefaultGitConfigs` never does. Because `configureWorktree` unconditionally runs `git submodule update --init [--recursive]` against attacker-influenced repo content (submodule URLs come from the synced `.gitmodules`) [3](#0-2) , an attacker who can add/modify a submodule pointing at a different repo path on the *same host* as the legitimate `--repo`/`--credential` URL can trick git into presenting the cached credentials to that attacker-controlled path — leaking the password, token, or GitHub App installation token that git-sync provisioned for the trusted repo.

### Finding Description
This mirrors the `FlywheelCore.setBooster()` pattern where a single shared, globally-scoped resource (there: the booster/flywheel dependency; here: the process-wide git credential cache) is consulted without verifying that the specific caller (there: `user`; here: the exact submodule URL/path) is actually the one entitled to it. Both are "shared custody" bugs: a broadly-scoped grant (unclaimed rewards custodied by `flywheelRewards`; here, a git credential custodied by a host-scoped cache) is handed out to whoever asks next matching a coarse key, rather than the specific entity it was meant for.

Concretely:
- `refreshCreds` iterates `--credential` entries and calls `git.StoreCredentials(ctx, cred.URL, cred.Username, password)`, which runs `git credential approve` with `url=<cred.URL>` [4](#0-3) [2](#0-1) .
- The credential helper is globally configured as `cache --timeout 3600` with no `useHttpPath` setting [5](#0-4) . Git's cache credential helper keys stored entries by `protocol://host` by default; any request for a URL on the same host will be satisfied from the same cache entry regardless of the path.
- When syncing, `configureWorktree` always runs `git submodule update --init [--recursive]` (when submodules aren't disabled) on the checked-out tree [3](#0-2) , and this checked-out tree — including its `.gitmodules` submodule URLs — is fully attacker-controlled content coming from the synced repository/ref.
- The e2e tests explicitly acknowledge and rely on per-URL credential separation for submodules over HTTP/SSH with *different* hosts/ports [6](#0-5) , but nothing in the code path enforces that submodule URLs share a host with an entry approved for a different path — the isolation only works incidentally, per test setup, because each test server uses a distinct IP/port. If a submodule is added under the same host/port as a previously-approved credential's URL but a different path, git will present that credential to the attacker's endpoint.

### Impact Explanation
An attacker who can influence the content of the synced repository (e.g., push access to a branch/ref git-sync tracks, or control of a nested submodule) can add or alter a `.gitmodules` entry to point at an attacker-controlled path on the same host as a trusted, credentialed repo. On the next sync, `git-sync` will fetch that submodule using the cached, previously-approved username/password or GitHub App installation token, disclosing the secret to the attacker's endpoint (via HTTP Basic Auth headers sent to the attacker's server). This is credential/token disclosure, matching the "steal value owed to others via shared custody" class of the reported bug: rather than tokens meant for the legitimate repo, the attacker exfiltrates them by presenting a lookalike endpoint under the same coarse-grained credential scope.

### Likelihood Explanation
Requires: (1) `--submodules` not set to `off` (the default is `recursive`) [7](#0-6) , (2) the operator uses HTTP(S) username/password, `--credential`, `--askpass-url`, or GitHub App auth (all of which route through `StoreCredentials`/`git credential approve`) [8](#0-7) [9](#0-8) , and (3) the attacker controls or can add a submodule URL on the same host as a credentialed repo (plausible for self-hosted git servers or GitHub Enterprise instances hosting both trusted and untrusted repos under one hostname). This does not require a malicious operator or leaked key — only push/edit access to synced repo content, which is the intended untrusted-content threat model for this bug class.

### Recommendation
- Set `credential.useHttpPath=true` (or equivalent path-scoped credential matching) in `SetupDefaultGitConfigs` so cached credentials are matched per full URL/path, not just per host.
- Scope credentials narrowly to the exact repo/submodule URL they are intended for, and avoid a shared global credential cache when `--submodules` is enabled with untrusted content.
- Consider validating/pinning expected submodule hosts, or restricting submodule recursion for repos with third-party contributed content.

### Proof of Concept
1. Configure git-sync with `--repo=https://git.example.com/org/trusted-repo` and `--username=svc --password-file=/creds/token` (or `--credential` for a specific URL on `git.example.com`).
2. In the synced repo (or a nested submodule the attacker can modify), add a submodule entry: `git submodule add https://git.example.com/attacker/evil-repo evil`.
3. On next sync, `configureWorktree` runs `git submodule update --init --recursive` [3](#0-2) ; git resolves credentials for `https://git.example.com/attacker/evil-repo` from the cache helper keyed by `https://git.example.com`, sending the previously-approved `svc`/token as HTTP Basic Auth to the attacker-controlled repo path, disclosing the secret to the attacker's server logs.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}

// SetupDefaultGitConfigs configures the global git environment with some
// default settings that we need.
func (git *repoSync) SetupDefaultGitConfigs(ctx context.Context) error {
	configs := []keyVal{{
		// Never auto-detach GC runs.
		key: "gc.autoDetach",
		val: "false",
	}, {
		// Fairly aggressive GC.
		key: "gc.pruneExpire",
		val: "now",
	}, {
		// How to manage credentials (for those modes that need it).
		key: "credential.helper",
		val: "cache --timeout 3600",
	}, {
		// Never prompt for a password.
		key: "core.askPass",
		val: "true",
	}}

	for _, kv := range configs {
		if _, _, err := git.Run(ctx, "", "config", "--global", kv.key, kv.val); err != nil {
			return fmt.Errorf("error configuring git %q %q: %w", kv.key, kv.val, err)
		}
	}
	return nil
