The vulnerability is confirmed. Two independent, attacker-controlled JSON fields in the unsigned webhook body are used for two different security-relevant purposes with no cross-check between them.

### Title
Webhook signature is verified against `repository.owner.login` while `PullRequest` writes are keyed only on `repository.full_name`, allowing cross-org PullRequest forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to check against using `params.dig('repository', 'owner', 'login')`, but `EditedHandler` (and its sibling PR handlers) locate/mutate the `PullRequest` using `params.repository.full_name` alone, via `Repository.from_github_repo_name`. Because these two payload fields are independently attacker-controlled and nothing enforces they refer to the same repository/org, an attacker who owns a webhook-enabled org can send a signed payload whose `full_name` names a victim org's repository, causing Shipit to update that victim's `PullRequest` row.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`organization_verifying_signature (params.repository.owner.login)` **must equal** `organization_owning_written_repository (owner segment of params.repository.full_name)` — but no code enforces this.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` via `repository_owner` helper: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and uses it to select `Shipit.github(organization: repository_owner)` for HMAC verification [2](#0-1) .
- On success, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw parsed JSON to all `pull_request` handlers, including `EditedHandler` [3](#0-2) [4](#0-3) .
- `EditedHandler`'s `ExplicitParameters` schema only requires `repository.full_name`; it never declares or reads `repository.owner.login` [5](#0-4) .
- `EditedHandler#repository` resolves the target repository purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` [6](#0-5) , and `from_github_repo_name` simply splits that string on `/` and does a `find_by(owner:, name:)` lookup with no relation to the signature's organization [7](#0-6) .
- `process` then finds and updates the matching `PullRequest` by `number` scoped to that resolved repository's stacks: `pull_request.update(github_pull_request: params.pull_request)` [8](#0-7) .

Exploit request: attacker controls `attackerorg`, which has its own configured `webhook_secret` in `Shipit.github(organization: 'attackerorg')`. Attacker POSTs to `/webhooks` with header `X-Github-Event: pull_request`, body:
```json
{
  "action": "edited",
  "number": <victim PR number>,
  "pull_request": { ... arbitrary attacker-chosen title/state/etc ... },
  "repository": { "full_name": "victimorg/repo", "owner": { "login": "attackerorg" } },
  "sender": { "login": "attackerorg-user" }
}
```
signed with `attackerorg`'s real `webhook_secret`. `verify_signature` picks `attackerorg`'s app via `repository_owner` (= `attackerorg`), signature checks out, request proceeds. `EditedHandler` then resolves `Repository.from_github_repo_name("victimorg/repo")`, finds the victim's real repository/PR, and overwrites `github_pull_request` with attacker-supplied JSON — mutating `victimorg`'s `PullRequest` row using only `attackerorg`'s secret.

Why existing guards fail: `drop_unhandled_event` and `check_if_ping` don't inspect repository identity at all; `ExplicitParameters` schema validates types/presence only, not cross-field consistency; `Repository.from_github_repo_name` and the `Repository` model validations (`owner`/`name` format) never compare against the payload's `owner.login`; there is no `force_github_authentication`/team-membership check in this flow since it's a machine-to-machine webhook, not a user session. Nothing in the engine ties the authenticating org to the org embedded in `full_name`.

### Impact Explanation
An attacker who fully controls their own org's Shipit webhook configuration (a legitimate, self-service capability) can write to any tracked `PullRequest` belonging to any other tenant org configured on the same Shipit instance, using only their own org's secret. This is a cross-tenant data-integrity bypass on `PullRequest#github_pull_request`, satisfying "a payload for one repository mutating another's ... task" under the Critical category. It is fully repeatable per victim PR number and is not limited to `EditedHandler` — the same `full_name`-only trust pattern (with no owner-login cross-check) exists in `ClosedHandler`, `ReopenedHandler`, `AssignedHandler`, `LabeledHandler`, `UnlabeledHandler`, and `LabelCapturingHandler`, all of which resolve `repository` the same way, meaning `stack.archive!`/`unarchive!` and label-driven review-stack provisioning can also be triggered cross-org.

### Likelihood Explanation
Preconditions are attacker-cheap: they only need any org onboarded to the Shipit instance with its own `webhook_secret` (a normal, unprivileged tenant setup), and knowledge/guess of a target PR `number` on a victim repo tracked by the same Shipit instance (PR numbers are small sequential integers, easily enumerable). No victim secret, GitHub token, or Shipit session is required. This is a straightforward crafted HTTP POST to `/webhooks` with a correctly-computed HMAC using the attacker's own known secret — trivially repeatable against any tracked repository/stack on the instance.

### Recommendation
In `WebhooksController` or in `Handler#initialize`, after computing the authenticating organization from `repository_owner`/`organization.login`, enforce that it matches the owner segment parsed from `payload.dig('repository', 'full_name')` (case-insensitively) before invoking any handler; reject with `422` on mismatch. Alternatively, have each handler's `repository` resolution validate that `Shipit::Repository#owner` equals the verified `repository_owner` passed down from the controller, rather than trusting `full_name` alone.

### Proof of Concept
minitest (e.g. in `test/controllers/webhooks_controller_test.rb`, no live GitHub — stub `Shipit.github`):
```ruby
test "cross-org pull_request edited payload should not mutate victim org's PullRequest" do
  attacker_secret = 'attacker-secret'
  Shipit.stubs(:github).with(organization: 'attackerorg').returns(
    Shipit::GitHubApp.new('attackerorg', webhook_secret: attacker_secret)
  )

  victim_pr = shipit_pull_requests(:review_stack_review) # belongs to a repo owned by "victimorg"
  original_title = victim_pr.github_pull_request['title']

  payload = payload_parsed(:pull_request_opened)
  payload["action"] = "edited"
  payload["number"] = victim_pr.number
  payload["pull_request"]["title"] = "ATTACKER OVERWRITE"
  payload["repository"]["full_name"] = "victimorg/repo" # matches victim_pr's stack repository
  payload["repository"]["owner"]["login"] = "attackerorg" # divergent, attacker-owned org

  body = payload.to_json
  signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', attacker_secret, body)

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = signature

  # Equality being tested: repository_owner used for signature ('attackerorg')
  # vs owner embedded in full_name used for the write ('victimorg') -- must NOT both succeed.
  assert_no_changes -> { victim_pr.reload.github_pull_request['title'] } do
    post :create, body: body, as: :json
  end
  # Currently this assertion FAILS: title changes to "ATTACKER OVERWRITE",
  # proving verify_signature (attackerorg) authorized a write to victimorg's PullRequest.
end
```
This demonstrates both sides of the claimed equality diverge (`attackerorg` != `victimorg`) while the engine still processes and persists the write, confirming the vulnerability.
