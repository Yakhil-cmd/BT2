### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler resolves the target `Stack` from the unrelated, uncorrelated `repository.full_name` field - allowing cross-organization forged webhooks ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against by reading `params.dig('repository', 'owner', 'login')` (or `organization.login`) out of the raw, attacker-controlled request body itself. [1](#0-0)  Once the signature is accepted, the full unmodified payload is dispatched to handlers, each of which independently determines the `Repository`/`Stack` to mutate using a *different* field of the same body, `repository.full_name`. [2](#0-1)  Nothing binds `repository.owner.login` to `repository.full_name`; they are independent JSON keys within the same attacker-supplied payload.

### Finding Description
The equality that should hold is:
`organization whose webhook_secret authenticated the request == organization that owns the repository being written to`

In `verify_signature`, the org used for HMAC verification is taken from `repository_owner`:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`github_app = Shipit.github(organization: repository_owner)` then checks `request.headers['X-Hub-Signature']` against that org's configured `webhook_secret`. [4](#0-3)  Shipit supports multiple GitHub organizations/Apps, each with its own independent `webhook_secret`, as shown in the multi-org secrets fixtures. [5](#0-4) 

Every event `Handler`, however, resolves the affected `Repository`/`Stack` via a completely separate field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

This same pattern (`params.repository.full_name`) is used across `PushHandler`, and the `pull_request/*` handlers (`opened`, `closed`, `labeled`, `unlabeled`, `assigned`, `edited`, `reopened`) to look up the `Repository` that gets archived/unarchived, synced, or updated. [6](#0-5) [7](#0-6) 

Because GitHub normally guarantees `repository.owner.login` and `repository.full_name` are consistent (`full_name == "owner/name"`), this discrepancy is invisible for genuine GitHub-originated events. But since this is a raw HTTP endpoint accepting an arbitrary attacker-crafted JSON body (`JSON.parse(request.raw_post)`), an entity that knows (or legitimately controls) the `webhook_secret` for *one* configured organization ("Org A") can sign a payload whose `repository.owner.login` is `"OrgA"` (so the correct/known secret is selected and verification passes) while setting `repository.full_name` to `"OrgB/some-other-repo"` - a repository that belongs to a completely different, unrelated organization/GitHub App tracked by the same Shipit instance. `verify_signature` never checks that the two fields agree.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written," matching the allowed impact category of cross-repository writes / unauthorized actions. Concretely, holding only the webhook secret for one organization's GitHub App lets an attacker forge webhook events (`push`, `pull_request`, etc.) that act on `Stack`s/`Repository` records belonging to a different organization entirely:
- `PushHandler` will call `stack.sync_github(expected_head_sha:)` on stacks under the victim org/repo. [8](#0-7) 
- `pull_request` handlers can archive/unarchive review stacks and mutate `PullRequest` records for repositories under a different organization (e.g. `opened_handler`, `labeled_handler`, `unlabeled_handler`). [9](#0-8) [10](#0-9) 

This is a cross-repository/cross-organization write performed without the write-holder's actual GitHub webhook credential for the targeted repository - an unauthorized action on a stack the attacker's credential was never meant to authorize.

### Likelihood Explanation
Exploitability requires the attacker to know (or legitimately hold, as an org admin of one of the multiple configured GitHub Apps) the `webhook_secret` for *any one* organization onboarded to the shared Shipit instance, and to be able to reach the public `/webhooks` endpoint (unauthenticated by design - it's meant to accept GitHub webhooks). Given Shipit explicitly supports and documents multi-organization deployments with per-org secrets, and organization admins of an onboarded org are, by design, less trusted than Shipit's full instance operator, this is a realistic multi-tenant/cross-org confusion once more than one organization is configured. This is not theoretical: `test/dummy/config/secrets_double_github_app.yml` demonstrates the exact multi-org configuration where this cross-organization confusion becomes exploitable. [11](#0-10) 

### Recommendation
In `WebhooksController#verify_signature` (or in the base `Handler`), after resolving the signing organization, validate that the actually-targeted repository's owner (`payload.dig('repository','owner','login')`) matches the organization of the `Repository`/`Stack` resolved from `payload.dig('repository','full_name')`, rejecting the request (422) on mismatch. Alternatively, look up the target `Repository` first, derive its known organization from Shipit's own configuration, and use that organization's `webhook_secret` for verification rather than trusting an attacker-controlled field to choose the verification key.

### Proof of Concept
1. Shipit is configured with two GitHub Apps/organizations, `OrgA` and `OrgB`, each with tracked repositories/stacks (as in `secrets_double_github_app.yml`).
2. An attacker who knows `OrgA`'s `webhook_secret` (e.g., as an admin of `OrgA`'s onboarded GitHub App) crafts a POST body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and send with header `X-Github-Event: push` to `/webhooks`.
4. `verify_signature` selects `Shipit.github(organization: "OrgA")`, verifies successfully using the known `OrgA` secret. [4](#0-3) 
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github` on `OrgB`'s stack - an action the attacker had no legitimate GitHub credential for. [2](#0-1) [8](#0-7)

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )

      ].join(' '))
    end

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
