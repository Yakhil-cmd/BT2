### Title
Same-Block Liquidation Guard Uses a Single-Block Equality Check While Oracle Prices Remain Valid for Up to `max-staleness` Seconds, Letting an Attacker Cross the Block Boundary and Liquidate a Freshly-Borrowed, Legitimately Healthy Position - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate()` blocks liquidation of a borrower only when the borrower's `last-borrow-block` exactly equals the current `stacks-block-height`. This is a single-block "window," not a time-based cooldown. Any liquidator can simply wait for the very next block — crossing that one-block boundary — and liquidate the same position while the price/oracle conditions that made the position momentarily appear unhealthy are still considered "fresh" under the much wider `max-staleness` check (measured in seconds, not blocks). The borrower who just took out a healthy loan is harmed by a liquidator who is unprivileged and only needed to wait for block N+1.

### Finding Description
`liquidate()` computes: [1](#0-0) 

`last-borrow-block` is stamped onto the borrower's obligation the moment they call `borrow`, via `debt-add-scaled` in the vault: [2](#0-1) 

The stated purpose of this guard is to stop "flash-loan based attacks where user borrows + gets liquidated in same block" — i.e. an attacker manipulating price and liquidating within one atomic block. However the check is a strict `is-eq` on `stacks-block-height`, so its protective window is exactly one block. Meanwhile, price freshness is validated against `max-staleness`, a per-asset value expressed in seconds (docs describe values such as 60s for volatile assets and 300s for stable assets): [3](#0-2) 

Because Stacks blocks (post-Nakamoto) can be produced in a few seconds, many blocks can elapse well within a single `max-staleness` window. This means:
1. Attacker pushes a valid-but-adverse price update (still within confidence-ratio and staleness bounds) that temporarily depresses a victim's collateral value or inflates their debt value, in block N. The victim borrows normally in block N (their `last-borrow-block` = N), and the health check at borrow time (`is-healthy-with-mask`) may still pass, or the adverse price only fully manifests moments later.
2. The `same-block-check` in `liquidate()` blocks any liquidation attempt in block N itself.
3. In block N+1 (or any later block, as long as `oracle-timestamp-fresh` still accepts the stale/adverse timestamp under `max-staleness`), the `is-eq last-borrow-block stacks-block-height` check trivially evaluates to `false`, and liquidation proceeds against the same victim using effectively the same manipulated/stale price basis that the guard was designed to exclude.

The victim borrower never gets a chance to react (no time-based grace, no re-evaluation requirement tied to the price's own age relative to the borrow), and an unprivileged liquidator profits from the liquidation penalty at the victim's expense — exactly the "crossing the window bypasses the privileged check" pattern described in the source report, just translated from a UI PIN timer to an on-chain block-height equality guard.

### Impact Explanation
The victim's collateral is seized and a liquidation penalty applied to a position that was healthy under fair pricing, based on a price condition the "same-block" guard was explicitly built to neutralize. This is direct theft of a borrower's collateral (funds at rest) by an unprivileged counterparty exploiting the narrowness of the block-based guard relative to the much larger oracle staleness tolerance — a Critical-class impact (direct theft of user funds).

### Likelihood Explanation
Rated moderate: the attacker needs to be able to push a valid oracle update (within `max-confidence-ratio` and `max-staleness`) that is adverse to a specific borrower, and then simply issue a `liquidate` call one or more blocks later while that price is still "fresh." No privileged access or DAO compromise is required — only ordinary user-facing entry points (`price-feeds` param on `borrow`/`liquidate`, or waiting for a naturally adverse-but-fresh price tick) and patience of one block.

### Recommendation
Replace the block-height equality check with a time-based cooldown consistent with (or larger than) the maximum `max-staleness` configured across assets, e.g. require `stacks-block-time - last-borrow-time >= cooldown-period`, where `cooldown-period` is set at least as large as the largest per-asset `max-staleness`. This closes the gap between the "anti-same-block" guard and the oracle freshness tolerance so that the guard cannot be trivially defeated by waiting one block.

### Proof of Concept
1. Borrower Bob deposits collateral and borrows in block N; `last-borrow-block[Bob] = N`, position healthy at fair price.
2. Attacker submits a Pyth/DIA price update via the `price-feeds` param on any hot-path call that is valid (within `max-confidence-ratio`, within `max-staleness`) but adverse to Bob's collateral/debt valuation.
3. Attacker calls `liquidate(Bob, ...)` in block N — reverts with `ERR-LIQUIDATION-BORROW-SAME-BLOCK` as intended.
4. Attacker waits for block N+1 (only a few seconds later under Nakamoto fast blocks) and calls `liquidate(Bob, ...)` again. `last-borrow-block[Bob] = N ≠ N+1`, so `same-block-check` passes. The previously "adverse" price is still accepted by `oracle-timestamp-fresh` because its timestamp delta is still `<= max-staleness`. Liquidation succeeds, seizing Bob's collateral plus liquidation penalty, even though Bob's borrow and position were legitimate moments earlier. [4](#0-3)
