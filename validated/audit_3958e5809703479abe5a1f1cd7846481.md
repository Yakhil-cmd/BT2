### Title
Excess attached deposit not refunded on successful registration in `AddressRegistrar::register` - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
`AddressRegistrar::register()` only validates that the attached deposit is **at least** the storage cost required to add a new address mapping. It never checks whether the caller attached **more** than necessary. On the success path (vacant entry), the full attached deposit is retained by the contract instead of returning the surplus to the caller, matching the exact bug class described in the report (checking `>=` a minimum without handling the "too much provided" case).

### Finding Description
`register()` computes `required_deposit` from the bytes needed to store the `address -> account_id` mapping and only enforces a lower bound: [1](#0-0) 

If `given_deposit >= required_deposit` it proceeds. In the `Entry::Vacant` (success) branch, the mapping is inserted and the full `given_deposit` (not just `required_deposit`) is retained by the contract — there is no transfer back to `env::predecessor_account_id()` for the surplus: [2](#0-1) 

Notably, the `Entry::Occupied` (failure) branch *does* refund the entire `given_deposit` back to the caller: [3](#0-2) 

This shows the developers were aware refunding is the correct behavior for unused deposit, but only implemented it for the failure path, leaving the success/surplus case unhandled — the same class of oversight as the reported `ARCH` bug (checks the floor, ignores and consumes the excess). This contrasts with how nearcore's own protocol-level refund logic and the sibling `DeterministicStateInitAction` handler correctly compute and refund exactly the unused portion of an attached deposit: [4](#0-3) 

No `withdraw` or owner-recovery method exists in `AddressRegistrar` to later reclaim the stranded surplus.

### Impact Explanation
Any unprivileged account calling `register` via a signed transaction/function call with `#[payable]` can lose the excess NEAR they attach above the storage cost — the tokens become permanently locked in the `AddressRegistrar` contract's balance with no path to recovery. Because `register` is invoked as part of the `near-wallet-contract` EVM-emulation flow (registering an `AccountId` to an address before executing wallet transactions), a caller (or the caller's tooling) that over-estimates the required deposit will have funds silently absorbed by the contract rather than returned, constituting an unauthorized/irrecoverable balance loss for the user.

### Likelihood Explanation
Likelihood is moderate: the deposit is computed as `20 + account_id.len()` bytes × `storage_byte_cost`, a very small, easy-to-overestimate value. Any caller (human or automated tooling, including the wallet-contract's own callers) that attaches a conservative/rounded deposit rather than the exact byte-computed amount will trigger the loss on every successful (non-colliding) registration.

### Recommendation
In the `Entry::Vacant` success branch of `register()`, refund the difference `given_deposit - required_deposit` back to `env::predecessor_account_id()` via a transfer promise, mirroring the logic already used in the `Entry::Occupied` branch and consistent with the refund pattern used elsewhere in the codebase (e.g., `action_deterministic_state_init`).

### Proof of Concept
1. Deploy/observe the existing `AddressRegistrar` contract account.
2. Call `register({"account_id": "alice.near"})` attaching a deposit well above `required_deposit` (e.g., `1 NEAR` when only a few hundred yoctoNEAR-per-byte × ~30 bytes is required).
3. Observe: the call succeeds (`Entry::Vacant` path), the mapping is stored, and the entire `1 NEAR` deposit remains in the contract's account balance — no refund receipt is generated for the caller, unlike the colliding-address case which does refund in full.
