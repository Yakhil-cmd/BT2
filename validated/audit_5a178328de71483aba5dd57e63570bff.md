### Title
Cross-organization webhook spoofing via decoupled signature-verification identity and payload repository identity - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the inbound HMAC against using a field pulled straight out of the untrusted, unauthenticated JSON body (`repository.owner.login`, falling back to `organization.login`). The event handlers, however, locate and mutate the actual `Repository`/`Stack` using a *different* field from the same body: `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name`). Nothing binds these two fields together, so the "org that authenticated" and the "repository that gets written to" are two independent, attacker-influenced values.

### Finding Description
`verify_signature` computes the org used for secret lookup like this: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves the `GithubApp` configuration for that org, and `verify_webhook_signature` is called on it: [3](#0-2) 

Critically, if that org's `webhook_secret` is blank/unset, verification unconditionally returns `true`:
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```
Shipit explicitly supports multi-organization deployments where each org has its own independent `webhook_secret`, as shown in the shipped config template — including orgs configured with no secret at all: [4](#0-3) 

Once `verify_signature` passes (either because the named org has no secret, or an org's secret was otherwise satisfied), `WebhooksController#create` dispatches the **entire raw payload** — including the `repository.full_name` field the signature check never inspected — to the handlers: [5](#0-4) 

Every handler resolves the target `Stack`/`Repository` purely from `repository.full_name`, with no cross-check that this repository belongs to the org that was used to satisfy the signature check: [6](#0-5) 

For example, `PushHandler` uses that repository/stack lookup to trigger a GitHub sync for the target stack, driven entirely by attacker-supplied `ref`/`after`: [7](#0-6) 

**The broken binding, stated as an equality that should hold but doesn't:**
`org(secret used to verify signature) == owner(repository.full_name acted upon by handler)`

Before the attacker's request: for a legitimate GitHub-generated webhook, `repository.owner.login` and `repository.full_name`'s owner segment are always the same object (GitHub itself guarantees this consistency for a given delivery).

After the attacker's request: because the HTTP endpoint accepts an arbitrary, self-constructed JSON body (it is not required to have originated from GitHub at all — it only needs to pass `verify_signature`), an attacker can submit a payload where:
- `repository.owner.login` (or `organization.login`) = an org that has *no* `webhook_secret` configured on this Shipit instance (satisfying `verify_signature` trivially), and
- `repository.full_name` = any other tracked repository/stack in the Shipit instance (e.g., a victim org's repo), which the handler will act on.

### Impact Explanation
This allows an unauthenticated, unprivileged party (no Shipit session, no `ApiClient` token, no `webhook_secret`, no GitHub App key, no repo write access to the victim repo) to forge trusted GitHub events — `push`, `status`, `check_suite`, `pull_request`, `membership` — against any `Stack`/`Repository` tracked by the Shipit instance, as long as at least one configured org lacks a `webhook_secret` (an explicitly supported, documented configuration state, not a hypothetical misuse). Concretely this can:
- Force `GithubSyncJob`/`sync_github` to run against a victim stack with an attacker-chosen `expected_head_sha` (`PushHandler`), corrupting the stack's known commit state.
- Forge commit `status`/`check_suite` results for a victim commit via `StatusHandler`/`CheckSuiteHandler`, which feed into Shipit's CI-gating logic used to permit merges and deploys.
- Manufacture/alter team `Membership` records via `MembershipHandler`.

Because commit statuses/checks are inputs Shipit's merge-queue and deploy-safety logic trusts as coming from GitHub, this can escalate into an unauthorized ship/merge condition — i.e., it crosses the authentication boundary the webhook signature is supposed to enforce, without ever compromising a `webhook_secret`, `api_clients_secret`, or GitHub credential.

### Likelihood Explanation
Likelihood is contingent on deployment configuration: it requires at least one org configured in `Shipit.github` without a `webhook_secret`. This is not a corner case invented for this analysis — the project's own shipped secrets template (`config/secrets.development.shopify.yml`) shows `webhook_secret:` left blank as a normal, valid configuration for an org, and the code path (`return true unless webhook_secret`) treats that as "verified" by design rather than "unconfigured/reject." Any multi-org Shipit deployment where a lower-trust or newly-onboarded org has not yet set a webhook secret is immediately exposed for every other tracked repo/stack in the same instance, with zero credentials required from the attacker.

### Recommendation
Bind the two identities: after determining which org's secret verified the signature, require that `repository.full_name`'s owner (or `organization.login`) actually matches that org before allowing handlers to run, rejecting the request otherwise. Additionally, treat a missing `webhook_secret` as "reject all events for this org" rather than "accept unconditionally," or require an explicit opt-in flag for unsigned webhooks per org.

### Proof of Concept
1. Deploy Shipit with two configured orgs: `victim-org` (repos tracked by Shipit, `webhook_secret` set) and `empty-org` (any org, `webhook_secret` left blank, as the shipped template allows).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "empty-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
No `X-Hub-Signature` header is required to pass `verify_signature`, since `Shipit.github(organization: "empty-org")` has a blank `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb` lines 76-77).
3. `WebhooksController#create` proceeds and calls `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }`.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb` lines 32-38) and calls `stack.sync_github(expected_head_sha: params.after)` on the victim stack — despite the attacker never proving any relationship to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
