### Title
Attacker-controlled PR label name overrides `LD_LIBRARY_PATH` for the `ruby`/`bundle` dependency step spawned by `TaskCommands#install_dependencies`, enabling a relative-path shared-library hijack on the deploy host - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name, upper-cased, into the stack's environment hash with no key allowlist, and that hash is merged unfiltered into `TaskCommands#env`, which is used to build every `install_dependencies` `Command` (including the `bundle install` step). `Command#unbundled_env` merges this attacker-influenced hash *last*, so a label named `ld_library_path` sets `LD_LIBRARY_PATH="true"` on the spawned process, and because `Command#start` runs `PTY.spawn` with `chdir` set to the attacker-controlled checkout directory, `"true"` resolves as a relative sub-directory of that checkout that the dynamic linker will search first for shared objects loaded by the `ruby`/`bundle` process.

### Finding Description
The intended invariant is: *no PR-label-derived key can alter the environment of a `ruby`/`bundle` dependency step in `TaskCommands#install_dependencies`* (`label_key ∉ {LD_LIBRARY_PATH, LD_PRELOAD, RUBYOPT, ...}`). This does not hold.

Path:
1. `LabelCapturingHandler#capture_labels` persists label names straight from the webhook payload with only a `String` type check, no character/name allowlist: [1](#0-0) 
2. `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" }` into the stack env with no key filtering: [2](#0-1) 
3. `TaskCommands#env` merges `@stack.env` (the above) directly, again with no allowlist, before building `install_dependencies` commands: [3](#0-2) 
4. `Command#unbundled_env` merges `@env.stringify_keys` **last**, so it overrides anything `BASE_ENV`/`Bundler.unbundled_env` would otherwise set, and `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`: [4](#0-3) 
5. `chdir` for the dependency step (`steps_directory`) is inside `@task.working_directory`, i.e. the checked-out PR branch content, which the attacker fully controls via their fork: [5](#0-4) [6](#0-5) 

Attack: an attacker opens a PR from a fork whose repo contains a `Gemfile` (so `discover_bundler`/`bundle_install` produces a `bundle install`/`ruby`-invoking dependency step, per `app/models/shipit/deploy_spec/bundler_discovery.rb`), adds a label literally named `ld_library_path` (or `LD_LIBRARY_PATH`) to their own PR, and commits a directory literally named `true` in the repo root containing a malicious shared object matching the soname of a library the spawned `ruby`/`bundle` process will `dlopen` (e.g. a C-extension `.so`). Because `label_name.upcase` produces the exact key `LD_LIBRARY_PATH` with value `"true"`, and that key/value pair flows unfiltered into the environment of the `PTY.spawn`-ed `bundle install` process whose CWD is the same checkout, the dynamic linker resolves the relative `LD_LIBRARY_PATH` entry (`"true"`) against the process CWD and will preferentially load the attacker's shared object, executing attacker code on the Shipit deploy host.

Existing guards do not stop this: `EnvironmentVariables#permit` is a real allowlist mechanism in the codebase (`lib/shipit/environment_variables.rb`) but it is never invoked on `ReviewStack#env` or `TaskCommands#env` — those methods merge label-derived keys with no call to `permit`. `provisioning_behavior_prevent_with_label` only gates whether the *stack* is provisioned/archived; it does not restrict which environment keys a label can inject into subsequent task command executions once the stack exists and is active.

### Impact Explanation
This is Critical — Remote Code Execution on the Shipit deploy host. The attacker's shared object executes with the privileges of the Shipit worker process during the `install_dependencies` step of any task (deploy, restart, review-stack provisioning task) run against the review stack, before any deploy-time secret gating applies. Because the checkout directory and the environment merge are both per-task and per-stack, this is repeatable against any repository/stack that has review stacks enabled and runs a `ruby`/`bundle` dependency step, giving the attacker a foothold on infrastructure shared across all tenants deployed from that Shipit instance (e.g. `GITHUB_TOKEN`, other stacks' secrets reachable from that host).

### Likelihood Explanation
Preconditions: review stacks enabled for the target repository, a `Gemfile` present so a `bundle`/`ruby` dependency step is generated, and the attacker's ability to label their own PR (per the stated threat model) and to commit arbitrary files (the `true/` directory with the malicious `.so`) to their fork branch. All of this is achievable by an unprivileged external contributor with no Shipit credentials, no GitHub App secret, and no maintainer approval, making this highly feasible and fully repeatable per PR/label event.

### Recommendation
Do not merge PR-label-derived keys into process environments without an allowlist. Apply `EnvironmentVariables#permit` (or an equivalent explicit allowlist/denylist) in `ReviewStack#env`/`TaskCommands#env` to reject or drop any label-derived key that collides with loader-sensitive variable names (`LD_LIBRARY_PATH`, `LD_PRELOAD`, `RUBYOPT`, `RUBYLIB`, `GEM_PATH`, `DYLD_*`, etc.), and consider prefixing all label-derived keys (e.g. `SHIPIT_LABEL_<NAME>`) so they can never collide with toolchain-significant variable names regardless of label content.

### Proof of Concept
Add a minitest under `test/lib/shipit/task_commands_test.rb`:
```ruby
test "#install_dependencies does not let a PR label override LD_LIBRARY_PATH" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["ld_library_path"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  commands = Shipit::TaskCommands.new(task).install_dependencies
  command = commands.first

  assert_nil command.env["LD_LIBRARY_PATH"], "expected no loader-sensitive env var to be settable via a PR label"
end
```
Currently this assertion fails because `command.env["LD_LIBRARY_PATH"]` equals `"true"`, proving the label name directly reaches the environment of the `install_dependencies` `Command` object that `Command#start` passes to `PTY.spawn`.

    end
