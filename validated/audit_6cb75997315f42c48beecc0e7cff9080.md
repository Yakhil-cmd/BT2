### Title
First-depositor share-price inflation attack in the Uniswap-like AA template lets an attacker steal a victim's deposit - (File: `test/samples/uniswap_like_market_maker.oscript`)

### Summary
The bundled Uniswap-like market-maker AA template mints its `mm_asset` liquidity-share token using a share/asset ratio (`mm_asset_outstanding` vs. pooled balances) that can be manipulated by a first depositor combined with "silent" balance donations, exactly analogous to the classic ERC4626 first-depositor/inflation attack described in the external report. A single attacker-controlled AA trigger sequence can inflate the price of a `mm_asset` share so that a subsequent depositor's minted-share calculation rounds down to zero, letting the attacker capture the victim's contributed funds.

### Finding Description
The AA issues shares on the first deposit without any protection against under-collateralized share issuance or minimum liquidity locking: [1](#0-0) 

```
{ // invest in MM
  if: `{$mm_asset AND trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] > 0}`,
  init: `{
     $asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
     $bytes_balance = balance[base] - trigger.output[[asset=base]];
     if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
        $issue_amount = balance[base];
        return;
     }
     ...
     $issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
  }`,
```

Crucially, the AA composer's own execution semantics allow any trigger unit whose payload doesn't match any `if` condition in `cases` to be **silently absorbed into the AA's balance** with no state change and no share issuance ("eats the received coins"): [2](#0-1) 

Because the "invest" and "exchange bytes to asset" cases both require `trigger.output[[asset=base]] > 1e5`, any pure-bytes payment of ≤ 100,000 bytes is not matched by any case in the template and is therefore accepted directly into `balance[base]` without touching `var['mm_asset_outstanding']`: [3](#0-2) 

This gives an attacker the same two ingredients required for the ERC4626 inflation attack described in the report:
1. Become the sole/majority holder of `mm_asset` via a minimal first deposit (the "define" + first "invest" cases).
2. Repeatedly "donate" ≤100,000-byte payments that increase `balance[base]` without increasing `mm_asset_outstanding`, inflating the effective price of each `mm_asset` share.

### Impact Explanation
Once the pool's base-asset balance is inflated relative to `mm_asset_outstanding`, a subsequent victim's deposit computes `$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding'])`, which rounds down to 0 for any deposit whose relative share of the inflated `bytes_balance` is small. The victim's payment (base asset + paired custom asset) is nonetheless accepted into the AA's balances as part of the "invest" message flow, but the victim receives 0 `mm_asset` shares in return. The attacker, holding effectively 100% of `mm_asset_outstanding`, can then call "divest" and redeem `var['mm_asset_outstanding']` for a proportional share of `balance[$asset]` and `balance[base]`, which now includes the victim's stolen contribution. This is a direct unauthorized fund loss for the victim and unjust enrichment for the attacker — matching the "AA fund loss" acceptance criterion.

### Likelihood Explanation
Any address can trigger the AA with arbitrary payment amounts (no privilege required). The attack only costs the attacker the bounce fees for however many sub-threshold "donation" units it sends plus its own initial deposit, which is recoverable via divest — this is a realistic, unprivileged, single-poster attack path against a template that is shipped/tested as a reference AA in the ocore repository and likely to be copied by dapp developers as-is.

### Recommendation
- On the very first deposit, permanently lock/burn a minimum number of `mm_asset` shares (do not credit the entire `balance[base]` worth of shares to the first depositor), similar to the standard `MINIMUM_LIQUIDITY` mitigation used by Uniswap V2 and ERC4626 vaults with a virtual/dead share offset.
- Track `mm_asset_outstanding` (and pool reserves) purely through explicit state updates rather than relying on `balance[...]`, and add an explicit "no-op donation" guard/case that either bounces unmatched payments below the 1e5 threshold or accounts for them proportionally in `mm_asset_outstanding` so they cannot be used to skew the price per share without also being reflected in share issuance.
- Reject/bounce deposits whose computed `$issue_amount` would round to 0 rather than silently keeping the incoming funds while minting nothing.

### Proof of Concept
1. Attacker sends `trigger.data.define` to deploy the `mm_asset`.
2. Attacker sends a minimal "invest" trigger (bytes slightly above `1e5` + 1 unit of `$asset`) to become the sole holder of `mm_asset`, with `mm_asset_outstanding` set to that small `balance[base]` value.
3. Attacker repeatedly sends bare-bytes payments of `≤100000` bytes (below the `1e5` threshold used by both "invest" and "exchange" cases) — per [2](#0-1) , since none of the `if` conditions match, the AA "eats" these coins into `balance[base]` with no change to `mm_asset_outstanding`, inflating the effective share price.
4. A victim later sends a proportionally small "invest" payment; `$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding'])` per [4](#0-3)  rounds to 0, so the victim receives 0 `mm_asset` while their funds remain in the pool.
5. Attacker sends a "divest" trigger with its entire `mm_asset` balance and receives its proportional share of `balance[base]` / `balance[$asset]` — which now includes the victim's absorbed contribution — per [5](#0-4) .
