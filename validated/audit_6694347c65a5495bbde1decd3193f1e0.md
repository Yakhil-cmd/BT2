## Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Act On `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate a signature against using `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`). However, every webhook `Handler` (push, status, check_suite, pull_request, membership) determines *which* `Repository`/`Stack` to mutate using a *different* payload field, `repository.full_name`. Because both fields live in the same attacker-controlled JSON body and are never checked for consistency, an attacker who legitimately controls one GitHub organization configured in Shipit (and thus knows that organization's own `webhook_secret`) can produce a validly-signed request whose `repository.owner.login` matches their own org but whose `repository.full_name` names a completely different, victim-controlled repository/stack.

## Finding Description
`Shipit.github(organization: repository_owner)` in `app/controllers/shipit/webhooks_controller.rb` is looked up via `repository_owner`:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

This selects the `GithubApp` instance (and therefore the `webhook_secret`) used by `verify_webhook_signature`, which HMAC-verifies the *entire raw body* against that org's secret: [3](#0-2) 

Shipit explicitly supports per-organization configuration, each with its own independent `webhook_secret`, `app_id`, and `private_key` (documented multi-org config in `docs/setup.md`). The org whose secret is used for verification is therefore *not* necessarily the org whose repository is subsequently acted upon.

Once signature verification passes, `WebhooksController#create` dispatches the *raw, unmodified* JSON payload to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
end
``` [4](#0-3) 

Every handler resolves the target repository/stack independently via `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler` uses this to trigger a GitHub sync against a specific branch: [6](#0-5) 

`StatusHandler` writes CI status directly by SHA lookup regardless of repository owner at all: [7](#0-6) 

`CheckSuiteHandler` similarly resolves stacks by branch/sha across all repositories reachable through `Repository.from_github_repo_name`: [8](#0-7) 

Pull-request handlers (`opened_handler.rb`, `closed_handler.rb`, `reopened_handler.rb`, `label_capturing_handler.rb`, etc.) all resolve `repository` via `params.repository.full_name`, completely decoupled from whatever org's secret verified the signature.

**The binding that should hold:** `repository.owner.login` (the org whose secret authenticated the request) == the owner of `repository.full_name` (the repository the handler writes to). This binding is never enforced anywhere in the request path.

## Impact Explanation
This is a cross-repository/cross-organization write: any actor who is an administrator of an organization onboarded into Shipit (i.e., they created the GitHub App/Organization webhook for their own org and thus legitimately know that org's `webhook_secret` — a routine, unprivileged-relative-to-other-orgs action) can forge a signed webhook whose `repository.owner.login` is their own org (so verification succeeds against their known secret) but whose `repository.full_name` points at an unrelated stack belonging to a different, victim organization also configured in the same Shipit instance. Concretely:
- A forged `push` event triggers `stack.sync_github(expected_head_sha:)` (see `Stack#sync_github` referenced from `app/models/shipit/stack.rb` and `app/jobs/shipit/github_sync_job.rb`) against the victim's stack/branch, causing Shipit to record attacker-chosen commits/refs as reachable for that stack using the app's own `GITHUB_TOKEN`-equivalent credentials for the victim org.
- A forged `status` event can inject an arbitrary CI status (`state`, `context`, `description`, `target_url`) onto any commit SHA in the system via `Commit.create_status_from_github!`, independent of which repository/org actually owns that commit — this can flip a merge-required CI check to `success` for a victim stack, enabling an unauthorized merge/deploy gate bypass.
- Forged `pull_request`/`check_suite` events can archive/unarchive review stacks or trigger check-run refreshes on victim repositories.

This crosses the "cross-repository writes" / "unauthorized deploy" impact bar because the org that cryptographically authenticated the webhook is not the org whose stack state is mutated.

## Likelihood Explanation
Requires only that the attacker control (be an admin of) at least one GitHub organization that is legitimately configured as a Shipit-integrated org in a multi-org deployment — a realistic scenario for any Shipit instance shared across multiple orgs/teams (explicitly supported per `docs/setup.md`'s multi-org config example). No access to the victim org's secret, GitHub App private key, or a Shipit session/API token is needed; the attacker only crafts one HTTP POST to `/github/webhooks` with a valid HMAC computed from their own known secret.

## Recommendation
In `WebhooksController#verify_signature` / `create`, or in `Shipit::Webhooks::Handlers::Handler`, enforce that `repository.owner.login` (or `organization.login`) — the value used to select the verifying `webhook_secret` — equals the owner segment of `repository.full_name` before any handler is invoked. Reject (422) any payload where these disagree.

## Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App/organization webhook and independent `webhook_secret` (per `docs/setup.md` multi-org config).
2. Attacker is an admin of `attacker-org` and therefore knows `attacker-org`'s `webhook_secret` (they configured it themselves).
3. Attacker crafts a JSON body for the `push` event:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org secret, raw_body)>` and POSTs to `/github/webhooks`.
5. `WebhooksController#verify_signature` computes `repository_owner => "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature against the attacker's own secret. [9](#0-8) 
6. `create` dispatches the raw payload to `PushHandler`, whose `repository_name` resolves to `"victim-org/victim-repo"`, and it invokes `sync_github` on the victim's stack — a repository the attacker never authenticated for. [10](#0-9) [6](#0-5) 

Note: I could not fully inspect `Stack#sync_github`'s complete body or `GithubSyncJob`'s downstream effects within the tool budget available, so the exact downstream consequences (e.g., whether it triggers an actual `Deploy` task automatically vs. just updating commit records) should be independently confirmed by a background agent with full file access before finalizing severity, but the core boundary break (verification org ≠ acted-upon repository owner) is confirmed directly from the cited source.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
