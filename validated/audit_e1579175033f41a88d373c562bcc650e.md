### Title
Cross-repository status forgery in `StatusHandler#process` breaks the commit/stack authorization binding, enabling unauthorized `Shipit::Deploy` via `Stack#trigger_continuous_delivery` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `sha`, with no scoping to the repository/organization whose webhook secret actually authorized the request. `WebhooksController#verify_signature` selects the signing secret using an attacker-controlled `repository.owner.login` field from the same payload, so any GitHub org/repo owner with their own valid webhook secret can send a `status` event whose `sha` matches a commit belonging to a *different* stack/tenant, injecting a forged status on that victim commit. If that status satisfies `required_statuses`, the victim commit becomes deployable and `Stack#trigger_continuous_delivery` will deploy it using `Shipit.user`.

### Finding Description
The intended binding is: **the webhook secret that signs a status event must belong to the same repository/organization that owns the commit being updated** — i.e. `signing_org == commit.stack.repository.owner`. The code never enforces this equality.

- `WebhooksController#verify_signature` derives the signing organization entirely from the payload itself: `repository_owner` reads `params.dig('repository', 'owner', 'login')` [1](#0-0)  and then fetches `Shipit.github(organization: repository_owner)` to verify the HMAC signature [2](#0-1) . An attacker who owns/administers any org/repo configured in Shipit (their own fork or any onboarded org) legitimately possesses that org's webhook secret and can produce a validly-signed request — the signature check only proves "this request was signed by *some* org's secret," not "signed by the org that owns the target commit."
- `StatusHandler#process` then applies the status to **every** `Commit` in the database matching the payload's `sha`, with no filter on repository or stack: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . The resulting `Status` is attached with `stack_id` taken from whatever stack the matched commit belongs to (via `commit.create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` in `Commit`) [4](#0-3) , not from the webhook payload's own repository.

**Exploit flow:**
1. Attacker controls/owns a repository (and its GitHub App/webhook config) recognized by Shipit — obtainable simply by onboarding any repo they own, which is a normal, unprivileged workflow.
2. Attacker discovers (via public GitHub) the SHA of a commit already tracked in a victim stack, along with the CI `context` name that stack requires (both are typically public information on GitHub).
3. Attacker POSTs to `/webhooks` a `status` event, HMAC-signed with **their own** repo/org's webhook secret, with `repository.owner.login` set to their own org (so `verify_signature` passes) but `sha` set to the victim commit's SHA and `state: "success"`, `context: "<required-context>"`.
4. `StatusHandler#process` matches the victim `Commit` purely by `sha` and creates a `Status` scoped to the victim's `stack_id`, making the commit `deployable?` if that was the missing required status.
5. Any subsequent trigger of continuous delivery — via `Commit#add_status` → `ProcessMergeRequestsJob`/hooks, or a scheduled/periodic call to `Stack#trigger_continuous_delivery` — calls `next_commit_to_deploy` → `deployable_commits`, which now includes the victim commit [5](#0-4) , and `trigger_deploy(commit, Shipit.user, ...)` builds and enqueues a real `Shipit::Deploy` against the victim repository using `Shipit.user` credentials [6](#0-5) .

None of the existing guards catch this: `verify_signature` validates a signature against a secret chosen from attacker-supplied payload fields (not tied to the commit being modified); `drop_unhandled_event`/`check_if_ping` are irrelevant; the `StatusHandler` `ExplicitParameters` schema only validates types of `sha`/`state`/etc., not the repository binding [7](#0-6) ; there is no `force_github_authentication`/`User#authorized?`/`require_permission!` check on this unauthenticated webhook endpoint at all (by design, since it's supposed to be authenticated purely by HMAC-per-org).

### Impact Explanation
An attacker who owns any repository/org onboarded into a shared Shipit instance can forge deployability status for a commit belonging to an unrelated tenant's stack, and drive that tenant's `Stack#trigger_continuous_delivery` to create and run a `Shipit::Deploy` (using `Shipit.user`) against that victim's infrastructure. This is a cross-tenant authorization break: "a payload for one repository mutating another's stack/commit" leading to "an unauthorized deploy." On multi-tenant Shipit installations (many orgs/repos sharing one instance, which is the common deployment model), this is repeatable against any stack whose commit SHAs and required-status context names are discoverable, and is not limited to a single victim — any tracked stack is a target as long as the attacker knows a commit SHA and context name.

### Likelihood Explanation
Preconditions are low-cost for the stated unprivileged attacker: they need only one legitimate repo/org onboarded into the same Shipit instance (i.e., control of a webhook secret for *some* org, not the victim's), knowledge of a target commit's SHA (usually public on GitHub) and the required status `context` string (often a conventional/discoverable CI check name). No GitHub App private key, no victim webhook secret, no Shipit session or API token is required. The attack is a single crafted HTTP POST to `/webhooks`, fully repeatable.

### Recommendation
Scope status (and check-run) ingestion to the repository that actually sent the webhook: in `StatusHandler#process`, restrict `Commit.where(sha: params.sha)` to commits whose `stack.repository` matches the webhook's `repository.full_name`/owner (as verified during signature validation), e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_from_payload.id })`. More generally, `WebhooksController` should carry the verified repository identity through to every handler and each handler should filter all cross-repository lookups (`Commit`, `PullRequest`, etc.) by that verified repository, not merely by content-derived keys like `sha`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "cross-repo status forgery marks a commit in another stack deployable and triggers a deploy" do
  victim_stack = shipit_stacks(:shipit) # belongs to org "shopify"
  victim_commit = shipit_commits(:second) # tracked, currently NOT deployable (missing required status)
  refute_predicate victim_commit, :deployable?

  # Attacker only has a webhook secret for THEIR OWN org "attacker-org", not for "shopify".
  forged_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => victim_stack.required_statuses.first, # publicly known CI context name
    'repository' => { 'owner' => { 'login' => 'attacker-org' } } # attacker's own org, signs with their own secret
  }

  assert_difference -> { victim_commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.new.call(forged_payload)
  end

  victim_commit.reload
  assert_predicate victim_commit, :deployable?

  assert_difference -> { Shipit::Deploy.count }, 1 do
    victim_stack.trigger_continuous_delivery
  end

  deploy = Shipit::Deploy.last
  assert_equal victim_commit, deploy.until_commit
  assert_equal Shipit.user, deploy.user
end
```
This demonstrates the broken equality: `signing_org` (attacker-org) `!= commit.stack.repository.owner` (shopify), yet the forged status is accepted and used to authorize a real `Deploy` against the victim stack.

      deploy
