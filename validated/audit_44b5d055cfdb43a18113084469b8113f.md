### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the untrusted `repository.full_name` field, allowing any onboarded GitHub organization to forge webhooks for a different repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an incoming webhook against using `repository_owner`, a value read straight out of the untrusted JSON body (`repository.owner.login`, or `organization.login` as a fallback). All webhook handlers, however, resolve the actual `Repository`/`Stack` to operate on using a **different** field of the same untrusted body: `repository.full_name`. Because Shipit never checks that `full_name`'s owner matches the organization whose secret validated the signature, any GitHub organization legitimately onboarded to a multi-tenant Shipit instance (i.e. one entry in `secrets.github`) can forge a webhook that is cryptographically valid for *their own* organization but whose `repository.full_name` points at a completely different, unrelated repository/stack.

### Finding Description
`Shipit.github(organization:)` supports a multi-tenant configuration where several GitHub organizations, each with its own `webhook_secret`, can be configured under `secrets.github` [1](#0-0) . Signature verification picks which organization's secret to use purely from data inside the unauthenticated payload: [2](#0-1) [3](#0-2) 

Once the signature check passes, `create` blindly dispatches the same untrusted body to the event handlers: [4](#0-3) 

Every handler (`PushHandler`, `PullRequest::*Handler`, etc.) resolves the target `Repository`/`Stack` from `repository.full_name`, a field that was never part of the verified binding: [5](#0-4) [6](#0-5) [7](#0-6) 

There is no code anywhere that asserts `repository.full_name.split('/').first == repository.owner.login` (the field used for signature key selection). Consequently, the equality the system implicitly relies on — `organization that authenticated == organization whose repository is acted upon` — is never enforced. Any organization admin who legitimately knows *their own* org's `webhook_secret` (because they configured that GitHub App/webhook themselves, which is normal in this self-service multi-tenant model) can produce a request that is "signed" for their org while acting on any other onboarded repository's `Stack`.

### Impact Explanation
This breaks a genuine authentication-to-authorization binding: an organization can only prove it owns *its own* webhook secret, yet the engine lets that proof authorize state-changing actions against a *different* organization's `Stack`/`Repository`. Concretely:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha:)` on any not-archived stack matching the forged `full_name` and branch, letting an attacker force a sync/rollback of arbitrary already-existing commits on a victim stack they do not own, which for stacks with continuous deployment or lock-triggering commit messages (`yoloshipit!`, etc.) can result in an unauthorized deploy/rollback. [8](#0-7) 
- `PullRequest::ClosedHandler#process` / `ReopenedHandler#process` call `review_stack.archive!` / `unarchive!` on a victim's review stack, allowing an attacker to archive or resurrect review stacks belonging to a repository they don't administer. [9](#0-8) [10](#0-9) 

This is a cross-repository write through a forged organization-authentication binding, matching the "Critical - cross-repository writes / unauthorized deploy or rollback" category.

### Likelihood Explanation
Any tenant of a multi-org Shipit deployment (a normal, documented configuration under `secrets.github`, see `docs/setup.md`) already legitimately possesses their own `webhook_secret` and can send arbitrary requests to `/webhooks` (it is a public, unauthenticated HTTP endpoint by design — that is the entire point of GitHub webhooks). No additional privilege, session, or GitHub write access is required to forge the `repository.full_name` field; it is trivial JSON manipulation plus a correct HMAC computed with a secret the attacker already legitimately owns.

### Recommendation
- Short term: After signature verification, re-derive `repository_owner`/`organization` strictly from `repository.full_name` (or `organization.login`) and reject the webhook (422) if it does not match the organization whose secret validated the signature.
- Long term: Bind the verified organization to the handler dispatch path explicitly (e.g., pass the verified organization into `Handler.call` and have `Handler#stacks`/`#repository` refuse to resolve a `Repository` whose `owner` differs from the verified organization), so no handler can ever act on data outside the organization that cryptographically authenticated the request.

### Proof of Concept
1. Assume a multi-tenant Shipit instance configured with at least two organizations in `secrets.github`: `attacker-org` (secret `S1`, known to the attacker because they administer that org's GitHub App/webhook) and `victim-org` (secret `S2`, unknown to the attacker), each with existing `Stack`s.
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<any sha that already exists in victim-org/victim-repo>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S1, raw_body)>` using their own known secret `S1`, and sends it to `POST /webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and validates the signature successfully against `S1` [2](#0-1) .
5. `create` dispatches to `PushHandler`, which resolves `repository_name = "victim-org/victim-repo"` [11](#0-10)  and calls `stack.sync_github(expected_head_sha:)` on the victim's real stacks, even though the signature was never verified with `victim-org`'s secret `S2`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
