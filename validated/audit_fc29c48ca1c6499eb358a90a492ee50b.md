### Title
Webhook organization used for signature verification is decoupled from the organization acted upon, allowing cross-organization `Shipit.github_teams` escalation - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment, the webhook signature check selects which GitHub App/`webhook_secret` to verify against using the payload's `repository.owner.login` (with a fallback to `organization.login`), while the `membership` event handler acts on a *separate* `organization.login` field to create/attribute `Team` records that drive `Shipit.github_teams` authorization. Because these two fields are never checked for consistency, an attacker who legitimately controls (or has stolen) the webhook secret for one onboarded organization can forge a `membership` webhook that is "signed" for that organization but whose `organization`/`team`/`member` fields target a *different* organization's team, silently adding themselves to a privileged team.

### Finding Description
`WebhooksController#verify_signature` picks the signing GitHub App like this: [1](#0-0) [2](#0-1) 

`repository_owner` is derived as `params.dig('repository','owner','login') || params.dig('organization','login')`. Shipit explicitly supports configuring multiple, independent GitHub Apps (and therefore independent `webhook_secret`s) per organization: [3](#0-2) 

The `membership` webhook handler, however, uses a *different* field — the top-level `organization.login` — to decide which `Team` gets created/modified, completely independent of whatever `repository` object (if any) was used to pick the signing secret: [4](#0-3) 

Real GitHub `membership` events never include a `repository` key (they are org-scoped events), so nothing in the handler or in `verify_signature` enforces that the `organization.login` used to write team membership matches the org whose secret validated the request. An attacker who administers Org A (one legitimate tenant of this multi-org Shipit instance, hence knows Org A's `webhook_secret`) can add a spurious `repository: {owner: {login: "orgA"}}` object to the JSON body purely to steer signature verification to Org A's secret, while setting `organization.login`, `team`, and `member.login` to reference Org B (a different, unrelated tenant) and the attacker's own GitHub login.

Team membership feeds directly into the application-wide authorization check: [5](#0-4) [6](#0-5) 

If Org B's team happens to be part of `Shipit.github_teams` (the whitelist gating login access), the attacker's `User` record becomes a member of it, bypassing the intended organizational boundary and granting them access to the Shipit UI/API for Org B without ever possessing Org B's GitHub App credentials or webhook secret.

**Binding broken (as an equality):** `organization authenticated by verify_signature (repository.owner.login / signing secret)` ≠ `organization.login written by MembershipHandler into Team#organization`.

### Impact Explanation
This directly matches the specified High-impact category "escalation into `Shipit.github_teams` authorization." An attacker with legitimate credentials for one onboarded organization can grant themselves membership in an authorization-relevant team belonging to a completely different organization, gaining unauthorized access to that organization's Shipit stacks (view, and — depending on further `ApiClient`/team-based permission wiring — potentially deploy/lock actions), without compromising the target organization's own GitHub App, webhook secret, or private key.

### Likelihood Explanation
This requires: (1) the deployment be configured with more than one GitHub organization (an explicitly documented and supported configuration), and (2) the attacker to control a valid webhook secret for at least one of the onboarded organizations (e.g., because they administer that org's GitHub App settings). Given that requirement, no other privileged material (session, `ApiClient` token, target org's secret) is needed to forge the cross-org `membership` event, making exploitation straightforward once the multi-org precondition is met.

### Recommendation
- In `MembershipHandler` (and any other org-scoped handlers), require that the `organization.login` used to determine which `Team`/`GithubHook::Organization` record is written matches the organization whose `webhook_secret` verified the request in `WebhooksController#verify_signature`. Pass the verified organization from the controller through to handlers instead of trusting an independent payload field.
- In `WebhooksController#repository_owner`, do not silently fall back between disjoint fields (`repository.owner.login` vs `organization.login`); each event type should assert exactly the field it verifies against and reject payloads where an unexpected extra field (e.g. a `repository` object on a `membership` event) is present.
- Fail closed when the signature-selection field and the field actually processed for privileged effects (team membership) diverge.

### Proof of Concept
Preconditions: Shipit configured with `github: { OrgA: {..., webhook_secret: "secretA"}, OrgB: {..., webhook_secret: "secretB"} }` and OrgB has a `Shipit.github_teams` entry (e.g. `OrgB/admins`) used for login authorization. Attacker is an administrator of OrgA and therefore knows `secretA`.

1. Attacker crafts a JSON body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Admins", "slug": "admins", "url": "https://api.github.com/x" },
  "organization": { "login": "OrgB" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "OrgA" } }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC(secretA, body)` and POSTs to `/webhooks` with `X-Github-Event: membership`.
3. `WebhooksController#verify_signature` computes `repository_owner => "OrgA"` (from the injected `repository` field), fetches OrgA's `GitHubApp`, and validates the signature successfully against `secretA` — which the attacker legitimately possesses.
4. `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler`, which uses `params.organization.login => "OrgB"` to `find_or_create_by!` the `admins` team under OrgB and adds `attacker-github-login` as a member via `team.add_member(member)`.
5. On next login, `User#authorized?` finds the attacker's user record now belongs to a team in `Shipit.github_teams`, granting them access to OrgB's stacks in Shipit despite never having any relationship to OrgB's GitHub organization or App.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```
