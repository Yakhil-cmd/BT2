### Title
`InitializeBuffer` sets an arbitrary, unsigned authority on an uninitialized upgradeable-loader buffer account, allowing front-running/hijacking of the buffer authority - (File: programs/bpf_loader/src/lib.rs)

### Summary
The `bpf_loader_upgradeable` program's `InitializeBuffer` instruction sets the `authority_address` of a Buffer account to whatever pubkey is passed in as instruction account index 1, without requiring that account to be a signer, and without requiring the Buffer account itself to be a signer. This mirrors the reported Solidity `initialize()` pattern where a state-setting "constructor-like" call lacks access control and can be invoked/front-run by anyone before the intended caller's transaction lands.

### Finding Description
In `process_loader_upgradeable_instruction`, the handler for `UpgradeableLoaderInstruction::InitializeBuffer` is: [1](#0-0) 

It only checks that the buffer account's state is `Uninitialized` (i.e., not yet initialized) before writing `authority_address: authority_key` — there is no `is_instruction_account_signer` check on the authority account (index 1), and no signer requirement on the buffer account (index 0) either. Compare this to every other authority-mutating instruction in the same file (`SetAuthority`, `SetAuthorityChecked`, `Write`), which explicitly verify `is_instruction_account_signer` on the current authority before allowing a change: [2](#0-1) [3](#0-2) 

Once a buffer account exists on-chain (owned by `bpf_loader_upgradeable`, created via `system_instruction::create_account` and left `Uninitialized`), the `InitializeBuffer` instruction can be called by any unrelated transaction sender, on any signer set, specifying an arbitrary `authority_address` pubkey of the attacker's choosing. If the account-creation and the intended `InitializeBuffer` call are not guaranteed to land atomically in the very same transaction (e.g., a wallet or tooling flow that creates the account and initializes it in separate transactions/instructions, or any case where the legitimate `InitializeBuffer` transaction is delayed/dropped and resubmitted), an attacker can race ahead and claim buffer authority for themselves.

### Impact Explanation
Whoever becomes the recorded `authority_address` on a Buffer account gains exclusive control comparable to the `SolverVaults.initialize()` front-run scenario: they alone can subsequently `Write` program bytes into the buffer, `Close` the buffer to redirect its lamports to an account they control, or use it as the source buffer in a `Deploy`/`Upgrade` instruction. This is a concrete unauthorized-authority-assignment bug on a builtin program reachable from a single unprivileged transaction — matching the report's core defect class ("anyone can take control of state meant to be set once by the deployer") even though the ultimate blast radius depends on whether callers always bundle `CreateAccount` + `InitializeBuffer` atomically in practice.

### Likelihood Explanation
Exploitation requires only that an `Uninitialized` buffer account (owned by `bpf_loader_upgradeable`, correctly sized) exist on-chain with the legitimate `InitializeBuffer` call not yet having landed — i.e., any window between account creation and buffer initialization. No signatures, no special privileges, and no elevated compute budget are needed; a bare `InitializeBuffer` instruction naming the target buffer and an attacker-chosen authority pubkey suffices.

### Recommendation
Require the authority account (instruction index 1) to be a signer in `InitializeBuffer`, consistent with the signer checks already present in `Write`, `SetAuthority`, and `SetAuthorityChecked`. Alternatively/additionally, require the buffer account itself to be a signer of the `InitializeBuffer` instruction so that only the entity that controls the buffer keypair (i.e., the same entity that created the account) can initialize it, closing the front-running window entirely.

### Proof of Concept
1. Attacker observes (via mempool/gossip or public account state) a freshly created account `B`, owned by `bpf_loader_upgradeable`, sized for `UpgradeableLoaderState::size_of_buffer(N)`, and currently in the `Uninitialized` state (this occurs after `system_instruction::create_account` targeting the loader, before the legitimate `InitializeBuffer` call is confirmed).
2. Attacker submits a transaction invoking `bpf_loader_upgradeable`'s `InitializeBuffer` instruction with:
   - account[0] = `B` (writable, `is_signer: false`)
   - account[1] = attacker's own pubkey (`is_signer: false` is sufficient — no signature required)
3. Per `programs/bpf_loader/src/lib.rs:158-172`, since `B`'s state is `Uninitialized`, the handler sets `B`'s state to `Buffer { authority_address: Some(attacker_pubkey) }` without ever validating a signature from the intended owner.
4. The legitimate owner's later `InitializeBuffer` call for `B` now fails with `InstructionError::AccountAlreadyInitialized` (as demonstrated by the existing test `test_bpf_loader_upgradeable_initialize_buffer`, which shows this exact "already initialized" rejection path), permanently locking the buffer under the attacker's authority. The attacker can then `Write` arbitrary bytecode into `B`, or call `Close`/authority-only paths to control or drain the account. [4](#0-3)

    #[test]
    fn test_bpf_loader_upgradeable_initialize_buffer() {
        let loader_id = bpf_loader_upgradeable::id();
        let buffer_address = Pubkey::new_unique();
        let buffer_account =
            AccountSharedData::new(1, UpgradeableLoaderState::size_of_buffer(9), &loader_id);
        let authority_address = Pubkey::new_unique();
        let authority_account =
            AccountSharedData::new(1, UpgradeableLoaderState::size_of_buffer(9), &loader_id);
        let instruction_data =
            bincode::serialize(&UpgradeableLoaderInstruction::InitializeBuffer).unwrap();
        let instruction_accounts = vec![
            AccountMeta {
                pubkey: buffer_address,
                is_signer: false,
                is_writable: true,
            },
            AccountMeta {
                pubkey: authority_address,
                is_signer: false,
                is_writable: false,
            },
        ];

        // Case: Success
        let accounts = process_instruction(
            &loader_id,
            &instruction_data,
            vec![
                (buffer_address, buffer_account),
                (authority_address, authority_account),
            ],
            instruction_accounts.clone(),
            Ok(()),
        );
        let state: UpgradeableLoaderState = accounts.first().unwrap().state().unwrap();
        assert_eq!(
            state,
            UpgradeableLoaderState::Buffer {
                authority_address: Some(authority_address)
            }
        );

        // Case: Already initialized
        let accounts = process_instruction(
            &loader_id,
            &instruction_data,
            vec![
                (buffer_address, accounts.first().unwrap().clone()),
                (authority_address, accounts.get(1).unwrap().clone()),
            ],
            instruction_accounts,
            Err(InstructionError::AccountAlreadyInitialized),
        );
        let state: UpgradeableLoaderState = accounts.first().unwrap().state().unwrap();
        assert_eq!(
            state,
            UpgradeableLoaderState::Buffer {
                authority_address: Some(authority_address)
            }
        );
    }
