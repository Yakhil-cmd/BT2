### Title
Webhook signature is validated against an organization derived from the payload, while the repository/commit that gets written is looked up from an unrelated payload field, letting one configured (or secret‑less) organization forge CI status/deploy‑sync events for a repository belonging to a different organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GithubApp` (and therefore the HMAC secret) used to authenticate an inbound webhook based on `repository.owner.login`/`organization.login` taken from the JSON body itself. [1](#0-0) [2](#0-1)  The handlers that actually act on the event, however, resolve the target repository/commit from a *different* field of the same body: `payload.dig('repository', 'full_name')` in the generic `Handler#stacks`/`#repository_name` helper, or, for `StatusHandler`, directly from `params.sha` with no repository scoping at all. [3](#0-2) [4](#0-3) 

The binding that should hold is:
`organization whose secret validated the signature == organization that owns the repository/commit being mutated`

Because both sides are independently attacker‑controlled fields inside the same JSON body, and the code never cross‑checks them, an attacker can pick the organization used for signature verification (e.g. one configured in Shipit's multi‑org `github:` config without a `webhook_secret`, which is an explicitly documented, valid configuration — see `secrets.development.example.yml` lines 8‑16) while pointing the actual `repository.full_name` / commit `sha` at a repository belonging to a *different*, "protected" organization.

### Finding Description
- `Shipit.github(organization: repository_owner)` picks a `GitHubApp` instance keyed by the organization named in the payload. [1](#0-0) 
- `GithubApp#verify_webhook_signature` **trivially returns `true` if that organization has no `webhook_secret` configured**: `return true unless webhook_secret`. [5](#0-4) 
- Shipit explicitly supports per-organization GitHub App configuration where each org can independently set (or omit) `webhook_secret`. [6](#0-5) 
- `WebhooksController#create` then dispatches the *entire, unmodified* JSON body to the registered handlers regardless of which organization "verified" it. [7](#0-6) 
- `Handler#stacks` resolves the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` — a field that is never checked against the organization used to select the verification secret. [3](#0-2) 
- `StatusHandler#process` is worse: it doesn't even use the repository field. It looks up `Commit.where(sha: params.sha)` **instance-wide**, across every stack/repository tracked by the Shipit installation, and calls `commit.create_status_from_github!(params)`, writing an attacker-chosen `state`/`description`/`target_url`/`context` for that commit. [4](#0-3) 
- Writing a `Status` record on a commit has direct side effects: `Status#enable_ci_on_stack` flips the stack's CI status and `Status#schedule_continuous_delivery` triggers continuous‑delivery evaluation of the stack. [8](#0-7) 

This is the same class of bug as the reported PublicVault issue: one code path updates/validates state keyed on field A (organization from `repository.owner.login`), while a different code path consumes/mutates state keyed on field B (`repository.full_name` or bare commit `sha`) from the very same message, and the two are never reconciled — exactly the analog category "an organization that authenticated versus the repository that is written."

### Impact Explanation
An attacker who can reach `/webhooks` (no session, no `ApiClient` token, no GitHub credentials required) can, if any organization in a multi-org Shipit deployment has no `webhook_secret` set (a documented, supported configuration), forge a `status` webhook whose `repository.owner.login`/`organization.login` names that secret‑less org (so `verify_webhook_signature` short-circuits to `true`), yet whose `sha` matches a commit belonging to an entirely different, secret-protected organization's stack. This lets the attacker inject a fabricated `success` CI status onto that commit, which can:
- Cause `Stack#schedule_continuous_delivery`/CI-gated automatic deploy logic to treat the commit as deployable, contributing to an **unauthorized deploy** of unreviewed code.
- Poison commit-status-based safety checks (`review.checks`, deployable/merge status) that other parts of the engine rely on to gate merges/deploys.

This satisfies the Critical impact bucket ("an unauthorized deploy") because the write is not scoped to the organization whose credential (or lack thereof) was actually validated.

### Likelihood Explanation
Likelihood is dependent on operational configuration: the flaw is only exploitable when at least one organization tracked by the Shipit instance is configured without a `webhook_secret` (or, in the general case, whenever the attacker can produce a valid signature for *any* onboarded organization — even one unrelated to the target repo). Since the multi-org configuration schema explicitly allows per-org `webhook_secret: # nil`, and the docs present this as a normal setup path, this is a realistic misconfiguration rather than a purely theoretical one. No session, GitHub write access, or privileged account is required — only network access to the public webhook endpoint and knowledge of a target commit SHA (retrievable from public GitHub history).

### Recommendation
Bind the field used to select the verification secret to the field used to identify the write target:
- After selecting `github_app` via `repository_owner`, re-verify that the same value equals the owner embedded in `repository.full_name` (reject on mismatch) before dispatching to handlers.
- In `StatusHandler` (and any other handler that trusts payload identifiers without going through `Handler#stacks`), scope `Commit` lookups to the stack(s) belonging to the repository named in the *verified* payload, not to a global `Commit.where(sha:)` search.
- Consider making `webhook_secret` mandatory (or, in its absence, refusing to accept events that reference repositories under a *different* organization from the one whose config was consulted) rather than silently returning `true` when unset.

### Proof of Concept
Preconditions: Shipit configured with multi-org GitHub config; `OrgA` has no `webhook_secret`; `OrgB` (secret configured) owns a tracked repository `orgb/victim-repo` with a known commit `sha`.

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "orgb/victim-repo" },
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/forged",
  "description": "forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
- `repository_owner` resolves to `"OrgA"` → `Shipit.github(organization: "OrgA")` → `verify_webhook_signature` returns `true` unconditionally because `OrgA.webhook_secret` is blank (no `X-Hub-Signature` header even needed).
- `StatusHandler` ignores `repository.full_name`/`owner` entirely and matches `Commit.where(sha: "<victim-commit-sha>")`, creating a forged `success` `Status` on `orgb/victim-repo`'s commit, triggering `enable_ci_on_stack` / `schedule_continuous_delivery` on that stack — with zero credentials belonging to `OrgB`. # frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
