## Analysis

`@nyariv/sandboxjs`'s bug class is: an internal, mutable, unsanitized interpreter object is exposed by reference to untrusted script code, instead of being deep-cloned/sanitized, allowing the sandboxed code to mutate shared internal state through that reference.

ocore's oscript formula evaluator (`formula/evaluation.js`) has the exact same "wrap-and-expose" design pattern via `wrappedObject`, and it is careful almost everywhere to call `string_utils.cloneDeep()` before handing a JS object to the AA/formula sandbox — e.g. `trigger.data`/`params`, `previous_aa_responses`, `trigger.outputs`, `keys`/`reverse`, dictionary literals, and the two in-memory response-unit lookups inside the `unit` opcode: [1](#0-0) [2](#0-1) 

However, the third branch of the same `unit` opcode — the one that reads a **stable unit from storage/cache** — wraps the raw `objUnit` object **without** any `cloneDeep`, breaking the pattern used everywhere else in the same function: [3](#0-2) 

The same missing-clone pattern exists in the `definition` opcode, which wraps `arrDefinition` returned from `storage.readAADefinition` / `storage.readDefinitionByAddress` directly: [4](#0-3) 

Once wrapped in a `wrappedObject`, oscript code can mutate the wrapped object's `.obj` in place through ordinary field assignment (`$x.b = 9`), as demonstrated by existing tests: [5](#0-4) 

Note also that just before wrapping, the code already mutates `objUnit` in place (`delete objUnit.actual_tps_fee`, `objUnit.timestamp = 0`, `objectHash.cleanNulls(objUnit)`), confirming `objUnit` is treated as a live, shared object rather than a disposable copy: [6](#0-5) 

`objJoint`/`objUnit` and `arrDefinition` originate from `storage.js`'s in-memory joint/definition caches (I could not fully trace every cache path within tool budget, but `storage.js` is known to hold `assocUnstableUnits`/`assocStableUnits`-style maps keyed by unit hash that are read by many other subsystems, e.g. `main_chain.js`, `writer.js`, `validation.js`). If `readJoint`'s `ifFound` callback returns a reference into such a cache (rather than a fresh deserialization per call), then any AA whose formula calls `unit(...)` or `definition(...)` on an already-cached unit/definition can obtain a live reference and mutate fields of that shared object via ordinary oscript object mutation. Because the mutated unit/definition object is the same object instance other code paths (other AA triggers referencing the same unit, revalidation, other getters) will subsequently read, this can cause different logical views of the same historical unit/definition within the same node process — a form of interpreter-internal-object leak analogous to the SandboxJS report, with the impact category being node disagreement/incorrect AA evaluation results derived from a corrupted cached unit or definition.

I was not able to fully confirm, within the available tool budget, whether `storage.readJoint`'s `ifFound` path and `storage.readAADefinition`/`readDefinitionByAddress` always return the literal cached object (vs. a fresh copy) for every code path (there are multiple internal helper functions in `storage.js` and I could not trace all of them). This is the key fact that would need verification to fully confirm exploitability and severity — I flag this explicitly as unresolved.

### Title
Unsanitized exposure of internal unit/definition objects via `unit()`/`definition()` oscript opcodes - (File: formula/evaluation.js)

### Summary
The `unit` and `definition` opcodes in the oscript formula evaluator wrap raw, potentially cache-shared JS objects (`objUnit`, `arrDefinition`) in a mutable `wrappedObject` without calling `string_utils.cloneDeep()`, unlike every other opcode in the same evaluator (`trigger.data`, `params`, `previous_aa_responses`, `trigger.outputs`, in-memory response-unit lookups, `keys`/`reverse`, dictionary literals) which consistently clone before exposing data to AA/formula code.

### Finding Description
`wrappedObject` is the internal representation oscript uses to let sandboxed formula code read and mutate object-typed values (`$x.b = 9`, `assignByPath`, `delete()`, etc.). The evaluator's design intent, visible throughout `formula/evaluation.js`, is that any host-side JS object handed into a `wrappedObject` must first be deep-cloned so that in-sandbox mutation cannot reach back into shared interpreter/storage state. The `unit` opcode's third branch (reading a stable unit from storage) and the `definition` opcode both skip this clone step, wrapping `objUnit`/`arrDefinition` directly: [7](#0-6) [8](#0-7) 
This mirrors the SandboxJS `New` handler flaw where a raw internal object (there, a `Prop` wrapping `scope.allVars`) was returned without sanitization, letting sandboxed code capture and mutate interpreter-internal state that other parts of the interpreter continue to rely on.

### Impact Explanation
If the objects returned by `storage.readJoint`/`storage.readAADefinition`/`storage.readDefinitionByAddress` are references into shared in-memory caches (as is typical in ocore's architecture for performance), any AA whose formula invokes `unit(...)` on a stable unit, or `definition(...)` on an address, obtains a live reference it can mutate via normal oscript object-field assignment. Because this object may be reused by other consumers within the same node process (other AA triggers referencing the same unit/definition, subsequent evaluations, or other validation paths), a malicious AA could corrupt shared unit/definition data for the remainder of the process lifetime, potentially causing the node to compute different results for other AAs/units than a node that hasn't run the malicious formula — a node-disagreement class issue.

### Likelihood Explanation
Reachable by any unprivileged AA author: writing an AA whose `init`/getter/state formula calls `unit(<some_stable_unit>)` or `definition(<some_address>)` and then mutates the returned object is a standard, always-available oscript capability requiring no special privileges, matching the "unprivileged AA author/trigger sender" reachability bar. The remaining uncertainty is solely whether the underlying storage functions return a cached shared reference or a fresh copy each call — this could not be conclusively verified with the available tools.

### Recommendation
Apply `string_utils.cloneDeep()` (or equivalent) to `objUnit` before `new wrappedObject(objUnit)` in the `unit` opcode, and to `arrDefinition` before `new wrappedObject(arrDefinition)` in all three return points of the `definition` opcode, matching the pattern already used consistently elsewhere in `formula/evaluation.js`. Additionally, avoid mutating `objUnit` in place (`delete objUnit.actual_tps_fee`, `objUnit.timestamp = 0`, `objectHash.cleanNulls(objUnit)`) before establishing that it is a disposable copy, since these mutations already touch the object prior to wrapping it.

### Proof of Concept
Conceptual PoC (exact reachability depends on confirming that `storage.readJoint`/`readAADefinition` return shared cached references, which requires further investigation in `storage.js`):
1. Deploy AA `A` whose `init` formula does: `$u = unit(<some_already-stable_unit_hash>); $u.messages = []` (or mutate any nested field).
2. Trigger AA `A` so the formula runs and mutates the wrapped unit object in place.
3. Trigger another AA `B` (or the same AA again, or core validation logic) that also reads the same unit via `unit(...)` or via `storage.readJoint`, and observe that it now sees the corrupted fields, since no clone was made before wrapping.
