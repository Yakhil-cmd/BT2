Confirmed: the `teams` table has a unique index only on `["organization", "slug"]` (`index_teams_on_organization_and_slug`), and no unique index or constraint on `github_id` alone. [1](#0-0) [2](#0-1) 

Now let's check how this affects the specific claimed exploit path. `MembershipHandler#find_or_create_team!` uses `Team.find_or_create_by!(github_id: params.team.id)` keyed purely on `github_id`. [3](#0-2) 

`Team.find_or_create_by_handle` looks up by `organization`+`slug` and, on miss, calls `fetch_and_create_from_github`, which does `create!(github_team:, organization:)` — this would insert a *second* row with the same `github_id` as the attacker's pre-existing row, since there is no unique index on `github_id` to raise `RecordNotUnique`. [4](#0-3) 

So the DB-level claim in the question is correct: `github_id` has no uniqueness constraint, and two `Team` rows with the same `github_id` but different `organization` values could coexist without any exception.

However, the question itself pre-empts the actual exploitability of this specific path: `Shipit.github_teams` membership checks are keyed on the Shipit primary key `id`, not `github_id`. Let's verify this claim to close the loop, since it determines whether the confirmed schema gap has any real impact.
