### Title
CCMenu API client token is not stack-scoped, allowing any stack's deploy/task state to be read through it - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The `Shipit::CCMenuUrlController#fetch` action mints a `read:stack` `ApiClient` token intended to authorize CCMenu polling for a single stack, but that token is created without a `stack_id`, and the `Shipit::Api::CCMenuController` that consumes it never checks that the token's authorized stack matches the stack being requested. The equality that should hold — "the stack a token authorizes == the stack it touches" — is broken, mirroring the `VoteEscrowDelegation` bug class where an authorization check is bound to the wrong context.

### Finding Description
`CCMenuUrlController#client` creates (or reuses) an `ApiClient` scoped only by permission, never by stack: [1](#0-0) 

Because `find_or_create_by!` keys only on `creator` and `name`, the very same token is returned for every stack a given user requests a CCMenu URL for. The `ApiClient` record produced this way has `stack_id == nil`, i.e. it is a globally-scoped `read:stack` client (compare with `ApiClient#belongs_to :stack, optional: true`) [2](#0-1) .

The consuming endpoint, `Shipit::Api::CCMenuController`, authenticates the token and then resolves the stack directly from the request parameter, bypassing the stack-scoping helper (`BaseController#stacks`/`#stack`) that every other API controller relies on: [3](#0-2) 

For contrast, `BaseController` normally restricts the visible stacks to `current_api_client.stack_id` when the client is stack-bound: [4](#0-3) 

`CCMenuController#stack` overrides this entirely with `Stack.from_param!(params[:stack_id])`, so `require_permission :read, :stack` only checks the generic `read:stack` permission string on the token — it never checks *which* stack the token is entitled to see: [5](#0-4) 

The user-facing intent (visible in the UI that generates one "CCMenu URL" per stack, embedding the token as a query-string parameter) is that the resulting URL/token only exposes that one stack's status to an external CI dashboard tool. In reality, the token is a master `read:stack` credential for that user, valid for every stack in the Shipit instance, and the controller performs no per-request check that `params[:stack_id]` matches the stack the URL was generated for.

### Impact Explanation
This is a High-severity issue: unauthenticated/unauthorized read of stack state (deploy status, task/rollback history exposed by the CCMenu XML feed) beyond what the token holder was ever granted. A token that leaks from one CI dashboard (URLs with embedded secrets in query strings are commonly logged, cached by proxies, or stored in third-party tool configs) grants the leaker read access to the deploy/task status of every stack in the Shipit instance, not just the one it was minted for — an unintended cross-stack authorization escalation, matching the "stack a token authorizes vs. stack it touches" binding.

### Likelihood Explanation
Any authenticated Shipit user can trigger `CCMenuUrlController#fetch` for a stack they can view, obtaining a `read:stack` token. No special privilege beyond normal engine usage of the CCMenu feature is required to create the mis-scoped token; exploitation of the leaked token to touch other stacks needs only knowledge of another stack's `stack_id`/param, which is not secret (stack slugs/ids are visible throughout the UI).

### Recommendation
Bind the `ApiClient` created in `CCMenuUrlController#client` to the specific `stack` (pass `stack:` into `create_with`/`find_or_create_by!`, and include the stack id in the `find_or_create_by!` lookup key so distinct stacks get distinct tokens). In `Shipit::Api::CCMenuController`, remove the `stack` override and route resolution through the shared `stacks`/`stack` helpers in `BaseController` so the client's `stack_id` scoping is enforced, consistent with every other stack-scoped API endpoint.

### Proof of Concept
1. As a logged-in Shipit user, visit the CCMenu URL generator for Stack A (`GET /*stack_id/ccmenu_url` equivalent, i.e. `CCMenuUrlController#fetch`). This mints/reuses an `ApiClient` with `permissions: ['read:stack']` and no `stack_id`, and returns `.../api/<stack_A>/ccmenu.xml?token=<T>`.
2. Take token `T` and request `.../api/<stack_B>/ccmenu.xml?token=<T>` for an arbitrary Stack B the same user (or an entity that obtained the leaked token) was never explicitly granted a CCMenu URL for.
3. `CCMenuController#authenticate_api_client` accepts `T` (valid `ApiClient`), and `CCMenuController#stack` resolves Stack B directly via `Stack.from_param!`, with no check that `T`'s (nonexistent) `stack_id` matches B. The XML response for Stack B's latest deploy/rollback status is returned, confirming cross-stack disclosure through a token intended for a single stack.
