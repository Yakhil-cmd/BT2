### Title
Cross-tenant MergeRequest CI-gating via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` writes a GitHub `status` webhook's state to every `Commit` row whose `sha` matches the payload, without restricting the lookup to the repository/stack that the webhook was authenticated for. Because `Commit` uniqueness is scoped to `(sha, stack_id)` rather than globally, and `verify_signature` only proves the payload was signed by *some* organization's webhook secret (the one named inside the attacker-controlled payload), an attacker who legitimately owns a GitHub org/repo can forge a `state: 'failure'` status for a sha that also exists as a `Commit` in a victim's unrelated stack (e.g., a shared/forked commit), causing `Shipit::MergeRequest::StatusChecker` to read the forged failing status and `reject_unless_mergeable!` to reject the victim's merge with `ci_failing`.

### Finding Description
The broken binding: `commit.stack.repository == webhook.repository_owner-authenticated-org` is assumed but never enforced.

- `WebhooksController#verify_signature` computes `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight out of the untrusted JSON payload (`params.dig('repository','owner','login')`), and verifies the HMAC using that organization's `webhook_secret`. [1](#0-0) [2](#0-1) 
  This only proves the request was signed by the org named in the payload — an org the attacker legitimately controls (their own GitHub org/repo with its own registered `webhook_secret`). It says nothing about which `Commit`/`Stack` the `sha` field inside the same payload is allowed to affect.

- `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
  This query is **global** — it is not scoped to the repository the webhook was verified for, unlike the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) used by other handlers (`PushHandler`, `CheckSuiteHandler`), which do scope work to the repository named in the payload. The `Handler` base class even defines a `stacks`/`repository_name` helper for this purpose, but `StatusHandler` bypasses it entirely. [4](#0-3) 

- `commits` are only unique per `(sha, stack_id)`, not globally, so the same `sha` string legitimately exists as separate `Commit` rows across many different stacks/repositories (e.g. a victim repo and any fork/mirror of it that shares git history and is also tracked by Shipit). [5](#0-4) [6](#0-5) 

**Exploit flow**: Attacker owns/administers a GitHub org+repo that Shipit tracks (so they legitimately know that org's `webhook_secret`, or can trigger a real GitHub webhook delivery from their own repo which GitHub will sign correctly). They obtain the victim's open `MergeRequest#head.sha` (public on GitHub). If that sha also exists as a `Commit` row in the victim's stack — plausible whenever the attacker's tracked repo shares history with the victim (fork, mirror, shared upstream commit) — the attacker POSTs `/webhooks` with `X-Github-Event: status`, a body whose `repository.owner.login` is their own org (so `verify_signature` passes using their own real secret) but whose `sha` field is the victim's PR head sha and `state: 'failure'`. `StatusHandler#process` finds the victim's `Commit` row purely by `sha` and writes a failing status onto it via `commit.create_status_from_github!`. Later, `ProcessMergeRequestsJob#perform` → `merge_request.reject_unless_mergeable!` → `any_status_checks_failed?` instantiates `MergeRequest::StatusChecker` over `head.statuses_and_check_runs`, sees the forged failing status, and the victim's otherwise-mergeable `MergeRequest` is rejected with `rejection_reason == 'ci_failing'`, even though the victim's real CI never failed. [7](#0-6) [8](#0-7) [9](#0-8) 

None of the existing guards catch this: `verify_signature` authenticates *the sender's own org*, not *the target commit's owning repository*; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema in `StatusHandler` only validates field types/presence, not ownership; `Repository`/`Stack` model validations never run against the `sha` lookup because `StatusHandler` never consults `Repository.from_github_repo_name` at all.

### Impact Explanation
A payload legitimately authenticated for repository A can mutate/create a `Status` record attached to a `Commit` belonging to repository B's stack, which is exactly the "a payload for one repository mutating another's stack/commit" Critical category. The concrete consequence demonstrated is denial of a legitimate merge (`MergeRequest` forced into `rejected`/`ci_failing`) driven entirely by a payload the victim's tenant never authorized. This is repeatable against any victim commit whose sha is discoverable and also present as a tracked `Commit` row (most plausibly via forks/shared history), and it is not limited to one merge request — every subsequent evaluation while the forged `Status` exists will keep failing the gate until a fresh legitimate status supersedes it.

### Likelihood Explanation
Preconditions: attacker must control a Shipit-tracked GitHub org/repo with a real, working webhook (attainable by any GitHub user who can create a repo/org and register it — no Shipit secrets needed since GitHub itself signs the real webhook, or the attacker's own configured secret is used for a self-sent forged payload); the victim's PR head sha must also be resolvable to an existing `Commit` row in the victim's stack, which happens naturally through common fork/mirror history. Attacker cost is low (a single crafted HTTP POST or a real webhook triggered by pushing to their own repo/fork). Feasibility depends on sha collision existing in practice (fork of the victim's repo, not a raw cryptographic collision), which is a realistic and controllable scenario for an attacker targeting a specific competitor's public repository.

### Recommendation
Scope `StatusHandler#process` (and any other handler performing `Commit`/`Stack` lookups by sha) to the repository authenticated by `verify_signature`, mirroring the base `Handler#stacks` pattern, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or more directly, restrict via `Repository.from_github_repo_name(repository_name)`'s stacks' commit association instead of a bare `Commit.where(sha:)`, ensuring a status webhook can only ever mutate commits belonging to the repository it was cryptographically verified for.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "forged status from attacker's authenticated repo rejects victim's unrelated merge request" do
          victim_stack = shipit_stacks(:shipit)
          victim_head = shipit_commits(:first) # belongs to victim_stack, sha shared via fork history
          merge_request = shipit_merge_requests(:shipit_pending) # pending, otherwise mergeable, head == victim_head

          # Binding under test: commit.stack.repository == webhook-authenticated org  --  should hold but doesn't
          assert_not_equal victim_stack.repository.owner, 'attacker-org'

          forged_payload = {
            'sha' => victim_head.sha,
            'state' => 'failure',
            'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
          }

          # attacker-org's signature verifies successfully (their own real secret), simulating
          # WebhooksController#verify_signature passing before StatusHandler.call is invoked
          StatusHandler.call(forged_payload)

          merge_request.reject_unless_mergeable!

          assert_equal 'ci_failing', merge_request.rejection_reason
        end
      end
    end
  end
end
```
This demonstrates that only a webhook authenticated for `attacker-org` (never touching `shipit`'s webhook secret) is sufficient to flip `merge_request.rejection_reason` to `'ci_failing'` for a `MergeRequest` in an entirely different stack.
