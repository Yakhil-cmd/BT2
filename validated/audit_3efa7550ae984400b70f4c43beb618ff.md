### Title
Attacker-controlled `machine.environment` in a fork's `shipit.yml` bypasses the `EnvironmentVariables` allowlist and injects arbitrary env vars (e.g. `GIT_SSH`) into `TaskCommands#install_dependencies`, yielding RCE on the deploy host - (File: lib/shipit/task_commands.rb, app/models/shipit/deploy_spec.rb)

### Summary
`TaskCommands#env` unconditionally merges `deploy_spec.machine_env` — which is `config('machine', 'environment')` read verbatim from the `shipit.yml` checked out at the task's commit — into the environment passed to every dependency/deploy `Command`, with no `EnvironmentVariables#permit` allowlist check. For a review stack, that `shipit.yml` is the content of the PR author's own commit, so an unprivileged contributor can declare `machine.environment.GIT_SSH: ./mal.sh` and ship a matching executable and a git-sourced Gemfile dependency in the same PR; when `install_dependencies` runs `bundle install`, git will honor the attacker-supplied `GIT_SSH`, executing the attacker's script on the Shipit deploy host.

### Finding Description
The intended invariant is: *the only environment values that can flow from repository configuration into spawned commands are those explicitly declared as `deploy.variables` / `rollback.variables` / task `variables`, and even then only after `EnvironmentVariables#permit` validates the key against that declared allowlist* (`lib/shipit/environment_variables.rb:13-18`, used by `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` at `app/models/shipit/deploy_spec.rb:174-180` and `TaskDefinition#filter_envs` at `app/models/shipit/task_definition.rb:63-65`).

The actual code breaks this: `DeploySpec#machine_env` is `config('machine', 'environment') || {}` (`app/models/shipit/deploy_spec.rb:69-71`) — a raw hash taken straight from the parsed `shipit.yml`, with no `VariableDefinition`/`EnvironmentVariables.permit` filtering at all. `TaskCommands#env` merges this directly: [1](#0-0) 
into the hash passed to every `Command.new(command_line, env:, chdir:)` built by `install_dependencies` (`lib/shipit/task_commands.rb:17-21`) and `perform` (`lib/shipit/task_commands.rb:23-27`). `Command#unbundled_env` then merges `@env.stringify_keys` straight into the subprocess environment with no key denylist: [2](#0-1) 
and `Command#start` passes that hash directly to `PTY.spawn`: [3](#0-2) 

Crucially, for a review stack the `shipit.yml` is read from `@task.working_directory`, i.e., the checkout of the task's commit — the PR author's own commit (`app/models/shipit/deploy_spec/file_system.rb:16-21`, `98-107`). An unprivileged PR author fully controls this file's content. They can commit:
```yaml
machine:
  environment:
    GIT_SSH: ./mal.sh
```
along with an executable `mal.sh` and a `Gemfile` containing a git-sourced gem (`gem 'x', git: 'ssh://...'`). When the review stack's `PerformTaskJob` runs `install_dependencies`, `bundle install` invokes `git` to fetch the git-sourced gem, and git honors the `GIT_SSH` variable present in its environment, executing `./mal.sh` as the SSH helper — arbitrary code execution on the Shipit deploy host under the Shipit service account.

Existing guards do not stop this: `EnvironmentVariables#permit` is applied to `deploy_variables`/`rollback_variables`/task `variables` (user-supplied `env` params at request time), but never to `machine.environment`, which is a different, unfiltered code path. `force_github_authentication`, `verify_signature`, and label-gating (`provisioning_behavior_allow_with_label?`) only control whether/when a review stack is created or archived — they do not sanitize the checked-out repository's `shipit.yml` content once a stack exists and runs tasks.

### Impact Explanation
Arbitrary command execution on the Shipit deploy host, triggered purely by content in a PR opened by an unprivileged contributor whose review stack is provisioned (e.g., via `allow_with_label`, where the PR author can add the provisioning label to their own PR). The attacker's script runs with whatever privileges the Shipit worker process has, including access to `GITHUB_TOKEN`, deploy secrets, SSH keys and any deploy credentials reachable from that host — this is a full host compromise, matching the Critical/RCE category (`Command`/`PTY.spawn` execution of attacker-chosen code). This is repeatable against any repository with review stacks enabled that installs dependencies via git-aware tooling (bundler/git-sourced gems, or analogous npm/git-url dependencies), and blast radius spans every stack/tenant on the shared Shipit deploy host, not just the attacker's own repository.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`review_stacks_enabled`) with a provisioning behavior that allows the attacker's PR to get a stack (`allow_with_label` requires the label be applied — per the threat model, the PR author can add labels to their own PR), and the deploy pipeline must run a dependency-install step that invokes git (e.g., Bundler with a git-sourced dependency, common in real projects). No Shipit secrets, sessions, or maintainer privileges are needed — the entire payload (`shipit.yml` + malicious script + Gemfile) is delivered via the PR branch content itself. Cost to the attacker is trivial: one PR, one label click, wait for the automatic review-stack deploy/task run.

### Recommendation
Sanitize `machine.environment` the same way `deploy.variables`/`rollback.variables` are sanitized: require it to declare `{name, default}` entries validated through `VariableDefinition`/`EnvironmentVariables#permit` against an explicit, host-application-controlled allowlist, and reject (or strip) any key that shadows security-sensitive loader/toolchain variables (`GIT_SSH`, `GIT_SSH_COMMAND`, `RUBYOPT`, `BUNDLE_GEMFILE`, `LD_PRELOAD`, `PATH`, etc.) regardless of source. At minimum, `TaskCommands#env`/`Command#unbundled_env` should enforce a denylist of such variables that cannot be overridden by repository-sourced configuration.

### Proof of Concept
```ruby
# test/unit/task_commands_machine_env_test.rb
require 'test_helper'

module Shipit
  class TaskCommandsMachineEnvGitSshTest < ActiveSupport::TestCase
    test "install_dependencies leaks attacker-controlled machine.environment GIT_SSH into command env" do
      task = shipit_tasks(:shipit) # a review-stack task fixture
      commands = TaskCommands.new(task)

      # Simulate shipit.yml checked out from the attacker's PR commit declaring machine.environment
      commands.stubs(:deploy_spec).returns(
        stub(
          dependencies_steps!: ['bundle install'],
          machine_env: { 'GIT_SSH' => './mal.sh' },
          directory: nil
        )
      )

      # Binding under test: no allowlist filters machine.environment before it reaches the spawned command
      refute_includes EnvironmentVariables.new({}).method(:sanitize_env_vars).owner.instance_methods, :never_called_on_machine_env # sanity placeholder

      command = commands.install_dependencies.first
      assert_equal './mal.sh', command.env['GIT_SSH'],
        "attacker-controlled GIT_SSH from shipit.yml reached the ruby/bundle command env unfiltered"
    end
  end
end
```
Expected result: `command.env['GIT_SSH']` equals the attacker-supplied value, proving the value reaches the `bundle install` `Command` (and ultimately `PTY.spawn` via `Command#unbundled_env`) without ever passing through `EnvironmentVariables#permit`.
