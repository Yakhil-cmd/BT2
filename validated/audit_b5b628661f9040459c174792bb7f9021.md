Based on my investigation, I found a concrete analog in the `system_vote` validation logic in `validation.js`, where the `tps_interval` system parameter has a minimum bound but no maximum bound — the exact bug class described in the report (missing upper-bound check on a fee/parameter value).

### Title
Missing upper bound on `tps_interval` system parameter allows unbounded TPS fee manipulation - (File: `validation.js`)

### Summary
The `system_vote` message handler validates `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` before they can be voted into effect as network-wide fee parameters. `base_tps_fee` and `tps_fee_multiplier` each have both a minimum and a maximum bound, but `tps_interval` only has a minimum bound (`>= 0.1`) and no maximum bound check.

### Finding Description
In the `system_vote` case of `validation.js`, the three TPS-fee-related subjects are checked together: [1](#0-0) 

While `base_tps_fee` is capped at `1e8` and `tps_fee_multiplier` is constrained to the range `[1, 1000]`, `tps_interval` is only required to be `>= 0.1` — there is no corresponding upper-bound check. This mirrors the reported issue exactly: an admin-set (here, network-voted) numeric parameter used directly in fee computation lacks an upper bound, whereas sibling parameters in the same code path do have both bounds, indicating the omission is an oversight rather than an intentional design choice.

`tps_interval` feeds directly into TPS fee computation used by `storage.getLocalTpsFee`/`getCurrentTpsFee`, which are invoked during `validateTpsFee` for every non-AA unit and used to determine the minimum acceptable fee a poster must pay: [2](#0-1) 

`system_vote` units can be posted by any address (not just witnesses/OPs) — the code only blocks AAs from casting `system_vote`, and enforces additional witness-list checks only for the `op_list` subject, not for TPS-fee-related subjects: [3](#0-2) 

Because `tps_interval` scales the effective TPS fee (fees are computed per interval of time), an unbounded value could push the derived TPS fee to be miscalculated in ways that are inconsistent with the bounded `base_tps_fee`/`tps_fee_multiplier` safety design, undermining the very rationale for having those other bounds.

### Impact Explanation
If `tps_interval` is voted to an extreme value (no ceiling enforced), the effective per-unit TPS fee derived from it can become inconsistent across the design assumptions baked into `base_tps_fee` (max `1e8`) and `tps_fee_multiplier` (max `1000`) bounds, since those bounds were clearly chosen assuming `tps_interval` stays within a sane range. This can lead to either an inability of the network to correctly price/confirm new units (fees computed incorrectly relative to actual throughput) or systematically wrong fee charging for all unit posters, which is a network-wide fee-integrity/availability concern rather than a localized one.

### Likelihood Explanation
Reaching this requires a `system_vote_count` to tally enough weighted votes for the change to actually take effect (network consensus via `system_vote`/`system_vote_count`), so it is not a single-poster-triggered bug, but any address can post a `system_vote` for `tps_interval`, and validation itself does not reject an extreme value at the point of casting the vote — the missing bound is purely a validation gap, matching the audit's characterization of "no upper bound" validation missing on a fee-affecting parameter.

### Recommendation
Add an explicit maximum bound check for `tps_interval` in the `system_vote` validation, analogous to the existing bounds for `base_tps_fee` and `tps_fee_multiplier`:
```js
if (payload.subject === "tps_interval" && (payload.value < 0.1 || payload.value > <MAX_TPS_INTERVAL>))
    return callback(payload.subject + " must be between 0.1 and <MAX_TPS_INTERVAL>");
```

### Proof of Concept
1. An address (not necessarily a witness) posts a `system_vote` message with `subject: "tps_interval"` and an extremely large `value` (e.g., `1e15`), which passes validation because only the minimum (`>= 0.1`) is checked: [4](#0-3) .
2. If sufficient `system_vote_count` weight accrues for this value (via the standard voting mechanism), the parameter becomes the active `tps_interval`, feeding into TPS fee computations for all subsequent units network-wide, unlike `base_tps_fee`/`tps_fee_multiplier` which are protected by explicit ceilings from similar extremes.
