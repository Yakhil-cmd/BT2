### Title
Archived supply positions are treated as zero collateral, enabling destructive bad-debt cleanup - (File: contracts/controller/src/storage/account.rs)

### Summary
An absent `SupplyPositions` persistent-map entry is silently converted into an empty map. If that entry expires independently while the account metadata, debt map, and NFT owner entry remain live, `clean_bad_debt` sees an account with debt but no collateral, socializes the debt, deletes the account, and burns the NFT without seizing the archived collateral claim.

### Finding Description
`get_supply_positions` uses `unwrap_or_else(|| Map::new(env))`, so a missing persistent value is indistinguishable from an account that legitimately has no collateral [1](#0-0) . `try_get_account` then constructs the account with that empty supply map while still loading any live debt positions [2](#0-1) .

The unrestricted `clean_bad_debt` endpoint is documented as callable by anyone once debt exceeds collateral and collateral is at most $5 [3](#0-2) . With the supply map missing, risk calculation sees zero collateral, satisfying that condition for any positive debt.

Cleanup iterates only the decoded `account.supply_positions`; because the archived map was replaced by an empty map, it creates no deposit-seizure entry for the pool shares still represented by that map [4](#0-3) . It still seizes/socializes every live debt position and calls the pool [5](#0-4) , then deletes controller state and burns the account NFT [6](#0-5) .

Unlike the PHP bug’s NULL mishandling, this is not merely a crash: the missing-value default causes collateral to be ignored in a destructive accounting transition.

### Impact Explanation
Permanent loss/freezing of user funds and protocol insolvency. The user’s pool supply shares are not transferred or settled during cleanup, while the controller deletes the only account-position entry that can later identify them. The debt is socialized even though collateral existed, harming suppliers; restoring the archived map afterward would leave an orphaned position because the account metadata and NFT were already removed.

### Likelihood Explanation
No privilege is required to call `clean_bad_debt`. The vulnerable state arises from Soroban’s independent persistent-entry TTL lifecycle: `SupplyPositions(account_id)` can expire while `AccountMeta`, `BorrowPositions`, and NFT ownership remain live. Position-map writes do not renew their own TTL, and renewal only extends entries that still exist [7](#0-6) . An attacker can monitor accounts and invoke cleanup once this partial-expiry state occurs.

### Recommendation
Do not default missing `SupplyPositions` to an empty map on destructive or risk-sensitive paths. Introduce `try_get_supply_positions`/`try_get_debt_positions` that distinguish `None` from an explicitly stored empty state, and make `get_account` fail with a recoverable/missing-state error when a required side map is absent. Since empty maps are deleted, consider storing an explicit empty marker or restructuring position storage so collateral cannot be silently interpreted as zero after archival. `clean_bad_debt`, liquidation, withdrawal, and threshold refresh should require the complete account state rather than substitute empty maps.

### Proof of Concept
1. A user supplies collateral and borrows, producing live `AccountMeta`, `SupplyPositions`, `BorrowPositions`, and NFT owner entries.
2. The account remains inactive until `SupplyPositions(account_id)` expires, while at least one debt map and the other account/ownership entries remain live.
3. An attacker calls `clean_bad_debt(attacker, account_id)` after the debt market has been updated.
4. `get_supply_positions` returns an empty map, so calculated collateral is zero and the bad-debt predicate passes.
5. `execute_bad_debt_cleanup` emits only debt-seizure entries, socializes the debt, removes all controller account entries, and burns the NFT.
6. The archived supply map no longer has a valid account owner to reclaim the corresponding pool collateral, while suppliers absorb the debt loss.
