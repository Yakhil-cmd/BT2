### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every handler acts on the repository named by `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC against using a field taken from the *same untrusted payload* it is about to verify: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

In a multi-organization Shipit deployment (documented in `docs/setup.md`, "Using Multiple Github Applications"), each onboarded GitHub organization has its own `webhook_secret` under `secrets.github.<org>`, retrieved via `Shipit.github_app_config` [3](#0-2) . This means the signature check only proves *"this payload was signed with the secret belonging to whatever organization is named in `repository.owner.login`/`organization.login`"* — it does not prove anything about the repository that handlers subsequently operate on.

Every event handler, however, resolves the target `Repository`/`Stack` using a **different field**: `repository.full_name`, via `Handler#repository_name`: [4](#0-3) 

and this is reused identically in `PushHandler`, and the various `PullRequest::*Handler` classes (`OpenedHandler`, `ClosedHandler`, `EditedHandler`, `LabelCapturingHandler`, `UnlabeledHandler`, etc.), all of which call `Repository.from_github_repo_name(params.repository.full_name)` to find the Stack to mutate: [5](#0-4) [6](#0-5) 

The binding that should hold is:
`organization whose secret validated the request == owner of the repository the handler mutates`

but the code only enforces:
`organization named in repository.owner.login == organization whose secret validated the signature`
while separately trusting `repository.full_name` (which can name **any** owner/repo pair) for the actual write.

Because HMAC verification is keyed by an attacker-controlled field within the very payload it authenticates, any actor who legitimately possesses a valid `webhook_secret` for **one** onboarded organization (e.g., they administer that org's own GitHub App installation on a shared/multi-tenant Shipit instance) can craft a payload where:
- `repository.owner.login` = their own organization (so `Shipit.github(organization: ...)` picks their own secret and the signature check passes), while
- `repository.full_name` = a different, victim organization's repository/stack tracked by the same Shipit instance.

The signature check passes (it was computed with the attacker's own known secret over the attacker's own crafted body), yet the handler dispatches actions (e.g. `PushHandler#process` calling `stack.sync_github`, or PR handlers creating/archiving Review Stacks, updating pull request state, or capturing labels) against the victim's stack.

### Impact Explanation
This breaks the "organization authenticated versus the repository that is written" trust binding explicitly called out as in-scope. An attacker who legitimately controls a webhook secret for one onboarded organization can forge state-changing webhook events (push-triggered syncs, PR-driven ReviewStack provisioning/archival, label capture) against a completely different organization's repository/stack tracked by the same Shipit instance — a cross-repository write achieved purely by manipulating which payload field is used for authentication versus which is used for authorization of the target resource.

### Likelihood Explanation
Requires only that the target Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration) and that the attacker is a legitimate administrator/owner of at least one of those organizations (able to see/rotate its own `webhook_secret`) — no special privilege on the victim organization, no `ApiClient` token, and no compromise of Shipit itself is required. Unlike the analog-report's arithmetic clipping bug, this is a straightforward field-substitution attack against publicly documented payload shapes.

### Recommendation
Verify the webhook signature using the app/secret resolved from a trusted, immutable source (e.g., the installation ID from the request context, or by validating the signature against *all* configured organizations' secrets and then cross-checking that the matching organization equals `repository.owner.login` used by the handler), and additionally assert in `Handler#repository_name`/`stacks` that the resolved repository's owner matches the organization whose secret validated the signature before dispatching any handler.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` per `docs/setup.md`'s "Using Multiple Github Applications" section, both tracked by the same Shipit instance (attacker-org is legitimately onboarded and administered by the attacker; victim-org has a Stack the attacker wants to affect).
2. Attacker, knowing `attacker-org`'s `webhook_secret` (they administer that org's GitHub App), builds a `push` payload body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"` [2](#0-1) , fetches `attacker-org`'s app/secret via `Shipit.github(organization: repository_owner)`, and the signature validates successfully.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method resolves the target using `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` [4](#0-3) [7](#0-6) , triggering `stack.sync_github(expected_head_sha: ...)` on the victim's stack — despite the request never being signed by `victim-org`'s secret.

module Shipit
  module Webhooks
    module Handlers

        params do
          requires :ref
          requires :after
        end

            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
