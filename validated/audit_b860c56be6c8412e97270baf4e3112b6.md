### Title
Webhook signature is verified against the payload's `repository.owner`/`organization` field, but every event handler acts on a different, unverified field (`repository.full_name`, or nothing at all for `status` events) — allowing cross-organization forgery of CI status and repo sync events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/`webhook_secret` used to validate the HMAC signature based on `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')`. Every downstream `Webhooks::Handlers::Handler` subclass, however, resolves the actual `Repository`/`Stack` to act on using a completely different, unverified field: `payload.dig('repository','full_name')` (or, in the `StatusHandler` case, no repository scoping at all). This creates a broken equality: `organization authenticated (repository.owner.login) != repository actually written (repository.full_name / matched commit)`.

### Finding Description
The webhook endpoint is a single, unscoped route (`config/routes.rb`) shared by all configured GitHub organizations. Signature verification is implemented as: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` selects one of possibly many configured GitHub App entries (see `config/secrets.development.shopify.yml`, which shows multiple orgs each with their own `webhook_secret`), and `verify_webhook_signature` HMACs the raw body against **that org's** secret: [3](#0-2) 

Once the signature passes, `WebhooksController#create` dispatches the parsed JSON to handlers without re-validating which repository/org the payload's other fields refer to: [4](#0-3) 

Every handler resolves the target repository from `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

`PushHandler` uses this to sync any stack whose repository matches `full_name`: [7](#0-6) 

Worse, `StatusHandler` doesn't even use the repository field — it matches purely on commit SHA across the entire database, with no repository/org scoping whatsoever: [8](#0-7) 

**Attack:** an attacker who legitimately controls/administers an org configured in Shipit (Org B) knows or can derive Org B's `webhook_secret` (it's their own org's GitHub App webhook secret, not a Shipit secret). They can POST directly to Shipit's single public webhook endpoint with:
- `X-Github-Event: status`
- `repository.owner.login: "orgB"` (or `organization.login: "orgB"`) — so `verify_signature` picks Org B's `webhook_secret` and the HMAC they compute with their own secret passes.
- `sha`, `state: "success"`, `context: "<the CI check name required by Org A's stack>"` referencing a commit that belongs to an unrelated repository owned by Org A.

Because `StatusHandler` never checks which repository/org the SHA belongs to, `Commit.where(sha: params.sha)` in Org A's stack will find the matching commit and call `commit.create_status_from_github!(params)`, marking it green for a required CI context — even though Org B has no relationship to that repository at all. The same class of mismatch also lets Org B forge `push` events for Org A's repository (`PushHandler`/`Repository.from_github_repo_name(full_name)`), forcing spurious `sync_github` calls, or pull_request events that create/archive/unarchive Org A's review stacks (`ReviewStackAdapter`, `Repository.from_github_repo_name(params.repository.full_name)`).

### Impact Explanation
Forging a passing CI status for a commit belonging to a repository/org the attacker does not control can satisfy Shipit's `ci.require` gating and enable an **unauthorized deploy** of a commit that never actually passed CI in the real, unrelated organization/repository — this crosses the "unauthorized deploy" / "cross-repository writes" bar explicitly listed as Critical/High impact. It also lets one org's credentials manipulate another, unrelated org's review-stack lifecycle (archive/unarchive/create) and force repository syncs, none of which the attacker's own signing key should authorize.

### Likelihood Explanation
Any entity that legitimately administers one GitHub organization configured in a multi-org Shipit deployment (a completely unprivileged actor with respect to any *other* org's repositories) can compute a valid signature using their own org's `webhook_secret` and simply change the unauthenticated body fields (`repository.full_name`, `sha`) to target a different org. No Shipit session, `ApiClient` token, or privileged account is required — only knowledge of one's own org's webhook secret, which by design that org's admins possess.

### Recommendation
Bind the signature-verifying identity to the identity actually acted upon: after selecting the GitHub App/secret via `repository_owner`, re-validate that `payload.dig('repository','full_name')`'s owner segment (and any SHA/commit lookups) belongs to that same, verified `repository_owner`/organization before dispatching to handlers. `StatusHandler` in particular must scope its `Commit` lookup by the verified repository, not by bare SHA.

### Proof of Concept
1. Shipit is configured with two orgs, `orgB` (attacker-administered) and `orgA` (victim), each with a distinct `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. Attacker builds a `status` event JSON body:
```json
{
  "sha": "<sha of a commit in orgA/some-repo tracked by Shipit>",
  "state": "success",
  "context": "<context required by orgA's stack ci.require>",
  "repository": { "owner": { "login": "orgB" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(orgB_webhook_secret, body)>` using Org B's own known webhook secret and POSTs it to the shared `/webhooks` endpoint (`config/routes.rb`) with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgB"`, fetches Org B's `GithubApp`, and `verify_webhook_signature` succeeds because the attacker signed with the correct (their own) secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no org/repository filter and marks the Org A commit's status green. [8](#0-7) 
6. If Org A's stack required that CI context to deploy, it may now be deployable/mergeable despite never having received a real passing status from Org A's actual CI.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
