### Title
Webhook signature verified against `repository.owner.login`'s org secret while every handler resolves the target Stack from the same body's `repository.full_name`, with no check that they name the same org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives the GitHub App/secret to check the HMAC against solely from `params.dig('repository','owner','login')` (or `organization.login`), while every `Shipit::Webhooks::Handlers::Handler` subclass resolves the actual `Repository`/`Stack` to mutate from `params.dig('repository','full_name')` in the very same JSON body [1](#0-0) . Nothing ties these two fields together, so an attacker who controls a repository under org X (and therefore knows/can compute a valid signature under X's `webhook_secret`) can send a request that authenticates as "org X" but whose `repository.full_name` names a repository owned by unrelated org Y.

### Finding Description
The intended binding is: **organization whose `webhook_secret` validly signed this HTTP body == organization owning the repository the handler subsequently mutates**. The controller only enforces the first half of that binding and never checks the second half against the first.

- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner)` to fetch that org's `GitHubApp`, then calls `verify_webhook_signature(header, raw_post)` [2](#0-1) . `verify_webhook_signature` is a pure HMAC-sha1 check against `webhook_secret` configured for that one org [3](#0-2) . It proves only "whoever sent this raw body knows org X's secret" — it says nothing about which repository's data is embedded in the body.
- `params = JSON.parse(request.raw_post)` in `create` re-parses the exact same raw bytes that were signed, then dispatches to handlers unmodified [4](#0-3) .
- Every handler resolves its target repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, entirely independent of `repository.owner.login`: e.g. `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [5](#0-4) , and the pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `ReopenedHandler`, `AssignedHandler`, `EditedHandler`, `LabelCapturingHandler`) all do `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to find the `Repository`, then act on `review_stacks`/`stacks` derived from that lookup [6](#0-5) [7](#0-6) [8](#0-7) .

Attacker flow: attacker owns/controls org X with a webhook configured pointing at the shared Shipit instance (or simply knows X's `webhook_secret` because it's their own org's app). They craft a JSON body where `repository.owner.login = "X"` (used only for signature-org selection) but `repository.full_name = "Y/victim-repo"` (used by the handler to pick the Stack to mutate), compute `sha1=HMAC(X_secret, raw_body)`, and POST it to `/webhooks` with `X-Github-Event` set to a handled event (e.g. `pull_request`). `verify_signature` selects X's `GitHubApp`, the HMAC matches X's secret over the exact bytes, so verification passes; the handler then loads `Y/victim-repo`'s `Repository`/`Stack`/`PullRequest`/`Team` and archives/unarchives/updates it based on entirely attacker-supplied `pull_request`, `action`, `labels`, `sender` fields.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type exists [9](#0-8) ; `ExplicitParameters` schemas only validate presence/type of fields, not cross-field consistency between `repository.owner.login` and `repository.full_name` (see the identical `requires :repository { requires :full_name, String }` blocks with no owner/org cross-check in every handler above); `Shipit::GithubOrganizationUnknown` only fires when `repository_owner` doesn't match any configured org, which is irrelevant here since X is a legitimately configured org.

### Impact Explanation
An attacker with a legitimately configured (even attacker-owned, small) GitHub org/app in Shipit's multi-org config can forge a cross-tenant, fully-signature-valid write into any other tracked stack: archiving/unarchiving review stacks, mutating `PullRequest` records (`github_pull_request`, `labels`), and triggering downstream provisioning/deprovisioning actions for a repository owned by org Y that they have no relationship with. This matches "a payload for one repository mutating another's stack, commit, task or team" — Critical severity. It is fully repeatable against any tracked repository whose `full_name` the attacker knows (public repo names), and requires no secret leakage, guessing, or GitHub-side action at all — only knowledge of X's own secret and Y's public `owner/repo` string.

### Likelihood Explanation
Preconditions: Shipit must be configured with the multi-organization github schema (`secrets.github` keyed by org, as documented) and the attacker must control (or be the operator of) at least one such org's webhook secret — realistic in any Shipit deployment serving multiple orgs/tenants, which is an explicitly supported and documented configuration [10](#0-9) . No GitHub-side privilege on the victim org/repo is needed; the attacker never touches GitHub at all, they just POST directly to the Shipit `/webhooks` endpoint with a self-crafted, self-signed body. Cost is trivial (compute one HMAC, know target repo's `full_name`), and it is repeatable per request against arbitrary tracked repositories.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after, before dispatch), require that the organization used to verify the signature is the same organization implied by `repository.full_name` (and `organization.login`/`sender.login` where relevant) — e.g. derive the owner from `full_name.split('/').first` and assert it equals `repository_owner` (case-insensitively), rejecting with 422 on mismatch. More robustly, look up the `Shipit::Repository` for `full_name` first and verify the signature using the `GitHubApp`/secret configured for the org owning *that* repository record, not an attacker-chosen owner field, closing off the divergence entirely.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_cross_org_test.rb
require 'test_helper'

module Shipit
  class WebhooksControllerCrossOrgTest < ActionController::TestCase
    tests Shipit::WebhooksController

    setup do
      # org X: attacker-controlled org with a real, known secret
      Shipit.stubs(:github_app_config).with('x-org').returns(webhook_secret: 'x-secret')
      # org Y: victim org/tenant, tracked in Shipit, has its own review-enabled repository + stack
      @victim_repo = shipit_repositories(:shipit) # owned by "Y-org/victim-repo" in fixtures
      @victim_repo.update!(review_stacks_enabled: true, provisioning_behavior: 'allow_all')
    end

    test "signature valid for org X accepted while full_name targets org Y's repository, mutating Y's stack" do
      body = {
        action: 'opened',
        number: 999,
        pull_request: {
          id: 1, number: 999, url: 'x', title: 'x', state: 'open',
          additions: 1, deletions: 0,
          head: { sha: 'deadbeef', ref: 'attacker-branch' },
          user: { login: 'attacker' }, assignees: [], labels: []
        },
        repository: {
          owner: { login: 'x-org' },       # used ONLY for signature org selection
          full_name: 'Y-org/victim-repo'   # used by handler to pick the target Stack/Repository
        },
        sender: { login: 'attacker' }
      }.to_json

      signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'x-secret', body)

      @request.headers['X-Github-Event'] = 'pull_request'
      @request.headers['X-Hub-Signature'] = signature

      assert_difference -> { @victim_repo.review_stacks.count }, 1 do
        post :create, body:, as: :json
      end

      assert_response :ok
      # Binding check: the org that validly signed (x-org) != the org whose Stack was mutated (Y-org)
      assert_equal 'Y-org/victim-repo', @victim_repo.full_name
    end
  end
end
```
This demonstrates: signature verified against `x-org`'s secret (passes, 200 OK), yet the actually-mutated `ReviewStack` belongs to `Y-org/victim-repo`, proving the two sides of the intended binding diverge while the request is still accepted.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
