### Title
Cross-organization Team-membership forgery via `MembershipHandler` grants `Shipit.github_teams` access - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
In a multi-organization Shipit deployment (`secrets.github` keyed by organization, each with its own `webhook_secret`, per `docs/setup.md` "Using Multiple Github Applications"), the webhook signature is verified against the GitHub App belonging to the organization named in the payload itself, but the `membership` event handler resolves the target `Team` record purely by the GitHub-global `team.id`, without ever re-checking that the authenticated organization matches the team's actual `organization`. This lets the holder of *any one* configured org's webhook secret forge a `membership` "added" event naming another organization's team, silently appending an attacker-controlled GitHub login to that team - which can gate access to the entire Shipit instance via `Shipit.github_teams`.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the signature against based solely on data taken from the same untrusted payload: [1](#0-0) [2](#0-1) 

For `membership` events there is no `repository` key, so `repository_owner` falls back to `params.dig('organization', 'login')` — i.e. whichever organization the *attacker's own webhook* declares. `Shipit.github(organization: ...)` looks up per-organization config declared in `secrets.github` (multi-org support): [3](#0-2) 

Once the HMAC check passes (using that organization's *own* legitimately-known `webhook_secret`), the payload is dispatched to `MembershipHandler`: [4](#0-3) 

The team is resolved with:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
```
The lookup key is `github_id` (globally unique across GitHub, not scoped to the authenticated organization). The `organization` assignment only happens inside the creation block — if a `Team` row with that `github_id` already exists (created earlier from a legitimate webhook belonging to a *different* organization), the existing row is returned unchanged, and `team.add_member(member)` / `team.members.delete(member)` mutate that pre-existing, unrelated team's membership.

`Shipit.github_teams` is exactly this same `Team` model, used to gate all authenticated access to the engine: [5](#0-4) [6](#0-5) [7](#0-6) 

**Broken binding:** `authenticated_organization` (the org whose `webhook_secret` validated the HMAC over the current request) should equal `team.organization` (the org whose team membership is being mutated). `MembershipHandler#find_or_create_team!` never re-asserts this equality on the update path — only on first creation.

### Impact Explanation
This directly matches the listed High-severity impact "escalation into `Shipit.github_teams` authorization". An attacker who is the administrator/owner of *any one* GitHub App configured in Shipit's multi-org `secrets.github` (a legitimately onboarded, but untrusted-relative-to-other-orgs, organization) can:
1. Learn the numeric `github_id` of a `Team` belonging to a different, trusted organization (team IDs are visible via GitHub's public/authenticated API, or simply the org/team the attacker is trying to break into).
2. Send (with their own org's genuine `webhook_secret`, which they legitimately possess as the owner of their own GitHub App) a correctly-signed `membership` event body: `{"action":"added","team":{"id":<victim_team_github_id>, ...},"organization":{"login":"<attacker_org>"},"member":{"login":"<attacker_account>"}}`.
3. `MembershipHandler` finds the pre-existing victim `Team` row by `github_id` and calls `team.add_member(member)`, adding the attacker's GitHub account to that team.
4. If that team is listed in `Shipit.github_teams`, the attacker's account is now `authorized?` and gains full authenticated access to the Shipit instance (deploy triggering, stack management, etc.), i.e. an unauthorized access/authorization-bypass across organizational trust boundaries that the multi-org feature was supposed to keep separate.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (a documented, supported configuration) where the attacker controls at least one of the onboarded GitHub Apps/organizations (and hence its `webhook_secret`) but not the target organization. This is a realistic scenario for shared/multi-tenant Shipit instances that onboard several partner or contractor organizations under one instance. No access to the victim's webhook secret, no Shipit session, and no API client token is required — only knowledge of the target team's numeric GitHub `id`, which is not secret.

### Recommendation
Scope the `Team` lookup by both `github_id` **and** the authenticated `organization`, and re-validate on every event (not just at creation) that `team.organization == authenticated_organization` before mutating membership, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |team|
    team.github_team = params.team
  end
  raise ArgumentError, "organization mismatch" unless team.organization == params.organization.login
  team
end
```
Additionally, `WebhooksController#verify_signature` should not trust an organization name taken from the unauthenticated payload without cross-checking it against server-side, already-known associations (e.g. the `stack`/`repository` or previously-registered `Team#organization`) before dispatching to handlers that mutate authorization-relevant state.

### Proof of Concept
Given a multi-org Shipit config with `secrets.github` containing `AttackerOrg` (secret known to attacker) and `VictimOrg` (secret unknown to attacker), and an existing `Team` row `{github_id: 555, organization: "victimorg", slug: "admins"}` already registered in `Shipit.github_teams`:

1. Attacker computes `sha1=HMAC(attacker_org_webhook_secret, body)` for:
```json
{
  "action": "added",
  "team": {"id": 555, "name": "Admins", "slug": "admins", "url": "https://api.github.com/teams/555"},
  "organization": {"login": "AttackerOrg"},
  "member": {"login": "attacker-gh-login"}
}
```
2. POST to `/webhooks` with header `X-Github-Event: membership` and `X-Hub-Signature: sha1=<computed>`.
3. `verify_signature` resolves `repository_owner` → `"AttackerOrg"`, fetches `Shipit.github(organization: "AttackerOrg")`, and validates successfully (attacker's own secret matches).
4. `MembershipHandler#process` runs `find_or_create_team!` → finds existing `Team(github_id: 555)` (`VictimOrg/admins`), then `team.add_member(User.find_or_create_by_login!("attacker-gh-login"))`.
5. Attacker's GitHub account is now a member of `VictimOrg/admins`; on next login, `User#authorized?` returns true via `Shipit.github_teams`, granting full access to the Shipit instance.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
