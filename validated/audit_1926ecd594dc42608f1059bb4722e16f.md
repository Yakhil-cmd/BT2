### Title
`ERC20Transactor` credits XCM holding with the full declared transfer amount instead of the amount actually received, breaking accounting for fee-on-transfer ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` performs an ERC20 `transfer()` call to a "checking account" and then unconditionally credits the XCM holding register with the *requested* `amount`, never verifying how much the checking account actually received. If the wrapped ERC20 contract is a deflationary/fee-on-transfer token (which `pallet-revive` can host arbitrary Solidity contracts), the checking account balance increases by less than `amount`, yet the XCM executor treats `amount` as fully backed and can later `deposit_asset_with_surplus` that same nominal amount to a different beneficiary, transferring more out of the checking account than it ever received for that operation.

### Finding Description
`ERC20Transactor` is a `TransactAsset` implementation used to represent ERC20 tokens (deployed via `pallet-revive`) as XCM-transactable fungible assets [1](#0-0) . It is wired into the Asset Hub Westend XCM configuration [2](#0-1) .

In `withdraw_asset_with_surplus`, the transactor issues an ERC20 `transfer(checking_address, amount)` call from the user's mapped address to a shared checking account, and — if the call does not revert and returns `true` — mints an `Erc20Credit(amount)` into the XCM holding register using the *originally requested* `amount`, not any value read back from the contract (e.g. a balance delta or `Transfer` event value): [3](#0-2) 

The complementary `deposit_asset_with_surplus` similarly moves `amount` out of the checking account to a beneficiary based solely on the value the executor believes it holds: [4](#0-3) 

Standard ERC20 `transfer()` success (`return true`) only guarantees the call succeeded per the ERC20 ABI; it makes no guarantee about the magnitude of the resulting balance change. Fee-on-transfer / deflationary ERC20 contracts (freely deployable by any user via `pallet-revive`) intentionally deliver less to the recipient than the `value` argument. Because the transactor never re-reads `balanceOf(checking_address)` before and after the call (or otherwise validates the amount actually received), the XCM holding register is credited with a phantom surplus each time such a token is withdrawn. This directly mirrors the reported `LToken`/`ERC4626` bug class: a deposit/collection routine trusts the nominal transfer amount instead of verifying tokens actually received.

### Impact Explanation
Every use of a fee-on-transfer ERC20 contract with this transactor inflates the XCM holding register beyond what the checking account actually custodies. Repeated use of such a contract in `ReserveAssetDeposited`/`WithdrawAsset` + `DepositAsset` XCM programs allows the checking account to be drained below the sum of credited amounts, since deposits are honored against nominal (not actual) balances. This is an accounting/backing break in a production, non-mock XCM asset-transactor path (`pallet-asset-conversion`-style TransactAsset used on Asset Hub), potentially leading to under-collateralization of the checking account relative to what the chain believes is held — a form of unbacked issuance/economic loss for whoever ultimately can't redeem their credited holding.

### Likelihood Explanation
Likelihood is constrained by two factors that were not fully verifiable from indexed code alone: (1) whether the concrete `Matcher: MatchesFungibles<H160, u128>` configured for `ERC20Transactor` on Asset Hub Westend restricts which ERC20 contract addresses are matchable (e.g., only a pre-registered allowlist versus arbitrary user-deployed contracts), and (2) whether any additional balance-check wrapper exists elsewhere in the XCM barrier/executor pipeline that was not surfaced by search. If the matcher allows any `pallet-revive`-deployed ERC20 contract address to be used as an XCM-transactable asset (which is the design intent of an "ERC20 Asset Transactor" generic over arbitrary tokens), then any user can deploy a standard fee-on-transfer ERC20 and trigger the mismatch with no privileged access, making likelihood moderate-to-high. This detail (matcher configuration for the deployed instance) could not be confirmed with the available tools and should be validated in a live session.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the checking/beneficiary account's ERC20 `balanceOf` immediately before and after the `transfer` call and use the actual balance delta (not the requested `amount`) both to construct `Erc20Credit` and to determine how much was actually moved. Alternatively, explicitly disallow assets whose registered ERC20 contracts are not verified to be fee-free (e.g., via an allowlist/registration step that simulates a transfer and rejects tokens with non-standard fee behavior).

### Proof of Concept
No executable PoC was run; this analysis is based on static code review of `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` and its wiring in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`. The critical guard that is missing — verifying actual received amount versus nominal transfer amount — was confirmed absent by inspecting the full `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` bodies. Reachability from a real signed extrinsic/XCM message and the exact `Matcher` restrictions for the deployed Asset Hub Westend configuration were not confirmed and require a live Devin session with full repository/runtime access (including `MatchesFungibles` instance and any ERC20 asset-registration allowlist) to build a minimal FRAME/XCM integration test that deploys a fee-on-transfer ERC20 via `pallet-revive`, drives it through `ERC20Transactor::withdraw_asset_with_surplus`, and asserts the holding register value versus the checking account's actual balance delta.
