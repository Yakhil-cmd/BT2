### Title
Webhook signature verification is skipped for organizations with no `webhook_secret`, letting a forged payload write to any other configured organization's repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/secret to validate against using an attacker-controlled field (`repository.owner.login`, falling back to `organization.login`), then delegates the actual HMAC check to `GitHubApp#verify_webhook_signature`, which unconditionally returns `true` when that organization has no `webhook_secret` configured. Every event handler, however, resolves the target `Repository`/`Stack` from a *different*, equally attacker-controlled field of the same unauthenticated JSON body (`repository.full_name`). Nothing ties the two together, so an attacker only needs one configured organization in the Shipit instance to have no `webhook_secret` in order to forge webhook events that are treated as "verified" while acting on repositories that belong to a completely different, secret-protected organization.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-30` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
head(422) unless verified
```
`repository_owner` (line 59-62) is taken straight from the unauthenticated request body:
```ruby
params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
```
This selects a `GitHubApp` instance per organization (`lib/shipit.rb#github`), each with its own optional `webhook_secret`. The actual verification, `GitHubApp#verify_webhook_signature` in `lib/shipit/github_app.rb:76-83`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
returns `true` immediately if that organization has no secret set - which is an explicitly supported configuration (see `webhook_secret: # nil` for `OrgTwo` in `test/dummy/config/secrets_double_github_app.yml`, and `github_app_config`/`github_organizations` in `lib/shipit.rb` which support multiple orgs, each independently configured).

Meanwhile, every `Shipit::Webhooks::Handlers::Handler` subclass resolves the repository/stack to act on from a *different* field of the same body:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
```
(`app/models/shipit/webhooks/handlers/handler.rb:36-38`), used by `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb`) to call `stack.sync_github(expected_head_sha: params.after)`, and independently by `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) to call `commit.create_status_from_github!(params)` for any `Commit` matching `params.sha`, with no organization/owner check at all.

The binding that should hold - "the organization whose signature was verified" == "the organization whose repository is actually written to" - is never enforced. The controller only ever checks `verified` against the org named in `repository.owner.login`; it never checks that `repository.full_name`'s owner segment matches, nor that the resolved `Stack`'s `Repository` belongs to that verified organization. Since `repository.owner.login` and `repository.full_name` are two independent JSON fields under full attacker control (when no secret exists for the org named in the first field), an attacker can set them inconsistently: e.g. `repository.owner.login: "OrgTwo"` (unsecured) but `repository.full_name: "OrgOne/production-app"` (a different, secured organization's tracked stack).

### Impact Explanation
This breaks the "organization that authenticated" vs. "repository that is written" binding called out in scope. Concretely, once one org in a multi-org Shipit deployment has no `webhook_secret` (a supported, non-privileged configuration state, not an attacker precondition like knowing a secret or holding an `ApiClient`/session token):
- An unauthenticated network attacker can send a `push` event naming any tracked `Stack` via `repository.full_name`, causing `PushHandler` to invoke `stack.sync_github(expected_head_sha: ...)` for that stack regardless of which org actually owns it.
- The same gap lets an attacker send a `status` event (`StatusHandler`) that creates a GitHub commit status (`create_status_from_github!`) on any `Commit` row matching an arbitrary `sha`, for any repository tracked by the instance - including repos belonging to a different, secured organization. Because CI-required deploys (`require_ci`) and continuous-deployment stacks key off `Commit`/`Status` state, this can be used to make an attacker-chosen commit appear "deployable" for a stack the attacker was never authorized to touch.
- `membership`/other handlers are reachable the same way, letting the attacker create/modify `Team`/`User` records tied to an org whose signature check was bypassed.

This is a cross-repository/cross-organization write achieved purely by exploiting an inconsistency between which field gates "is this verified" and which field decides "what do I write," with no attacker-held credential of any kind - matching the Critical impact bar ("cross-repository writes").

### Likelihood Explanation
Likelihood depends on deployment configuration: the vulnerability is fully live any time a Shipit instance runs the multi-org GitHub App schema (`Shipit.github_organizations`, `github_app_config`) and at least one configured organization has not set a `webhook_secret` - a state the codebase itself treats as a legitimate, supported combination (it's exactly what the shipped test fixture `secrets_double_github_app.yml` demonstrates, and `verify_webhook_signature` explicitly special-cases it rather than rejecting it). No credentials, sessions, or GitHub push access are required; only network reachability to the `/webhooks` endpoint. The one soft precondition (an org without a secret existing) is common in practice, since `webhook_secret` is documented/implemented as optional per organization and easy to omit by oversight.

### Recommendation
- Do not let `verify_webhook_signature` return `true` when `webhook_secret` is blank; instead, require every configured organization to have a webhook secret (fail closed), or explicitly reject events for organizations without one.
- After selecting the GitHub App/organization used to verify the signature, enforce that the same organization owns the `repository`/`organization` object actually referenced by the payload (e.g., compare `repository_owner` against the owner segment of `repository.full_name`) before dispatching to handlers.
- Consider signing/verifying against the resolved `Stack`'s configured organization/secret rather than trusting an owner value taken from the unauthenticated body to select the verification key.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs, e.g. `OrgOne` (has `webhook_secret: s3cr3t`) and `OrgTwo` (no `webhook_secret`), both with stacks tracked in Shipit (`OrgOne/production-app` and `OrgTwo/whatever`).
2. Attacker (no credentials) sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/production-app"
  }
}
```
3. `verify_signature` computes `repository_owner = "OrgTwo"`, loads `Shipit.github(organization: "OrgTwo")`, and `verify_webhook_signature` returns `true` unconditionally because `OrgTwo` has no `webhook_secret` - regardless of the bogus `X-Hub-Signature`.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgOne/production-app")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgOne`'s stack, even though the signature check was only ever performed (and trivially bypassed) for `OrgTwo`.

Note: I could not fully trace `Stack#sync_github`/`continuous_deployment` auto-deploy triggering logic within the available context to confirm whether this alone can drive an unauthorized deploy end-to-end (that chain, `app/models/shipit/stack.rb` and `app/models/shipit/commit.rb`, was only partially inspected); the `StatusHandler` cross-org status write and `PushHandler` cross-org sync trigger described above are confirmed directly from the cited code.
