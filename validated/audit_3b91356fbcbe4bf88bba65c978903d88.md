Confirmed root cause: `Shipit::WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify the HMAC signature against by reading `repository.owner.login` (falling back to `organization.login`) from the **unverified** JSON body [1](#0-0) , while the actual event handlers (e.g. `PushHandler`) resolve the target `Repository`/`Stack` using a *different* field of that same unverified body — `repository.full_name` — via `Handler#repository_name`/`#stacks` [2](#0-1) .

### Title
Webhook signing-org selection is not bound to the acted-upon repository, allowing cross-organization stack writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports hosting stacks for multiple GitHub organizations, each with its own `webhook_secret` configured per-org [3](#0-2) . `WebhooksController#verify_signature` picks which org's secret to verify the signature with based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), both read straight out of the untrusted, not-yet-verified JSON payload [4](#0-3) . Once the signature checks out for that chosen org, the entire raw `params` hash — including the `repository.full_name` field — is handed unchanged to the event handlers [5](#0-4) . `Handler#stacks`/`#repository_name` then looks up the target `Repository` (and thus `Stack`) purely from `repository.full_name` [2](#0-1) , with no requirement that `full_name`'s owner match the `repository.owner.login`/`organization.login` used to select the verifying secret.

This is the structural analog of the reported Beanstalk bug: two fields that should be bound together by one authoritative check (stem delta vs. BDV scale in Beanstalk; signing-org vs. acted-upon-repo here) are instead computed/read independently, and only one of the two is actually verified.

### Finding Description
The binding that should hold is:
`org authorized by valid HMAC signature == org owning the repository whose Stack is mutated`

Because `repository_owner` (used to pick the HMAC secret) and `repository_name`/`full_name` (used to pick the `Stack`) are two independent keys read from the same attacker-suppliable JSON body, an attacker with push/webhook-delivery capability to *any one* configured organization (org A, with its own `webhook_secret`) can send a payload where:
- `repository.owner.login` == `"org-A"` (so `Shipit.github(organization: "org-A")` is selected and the signature verifies with org A's secret, which the attacker/GitHub legitimately computed for a push to org A), and
- `repository.full_name` == `"org-B/some-repo"` (a repository belonging to a different configured organization, org B).

`Repository.from_github_repo_name` splits `full_name` on `/` and does a straight `find_by(owner:, name:)` lookup with no cross-check against `repository.owner.login` [6](#0-5) . `PushHandler#process` will then run `stack.sync_github(expected_head_sha: params.after)` against org B's stack [7](#0-6) , and other handlers (`status`, `check_suite`, `membership`, `pull_request`) will similarly act on whatever repository `full_name` names, all under a signature that was only proven valid for org A.

### Impact Explanation
This breaks the intended per-organization webhook-secret isolation the engine is designed to provide (the very reason multi-org `webhook_secret` config exists), letting an actor who controls delivery of correctly-signed webhooks for one org (e.g. a legitimate GitHub App installation admin or anyone who can trigger repo events in org A) drive Shipit actions (triggering `GithubSyncJob`, commit-status updates, PR/merge status changes, `RefreshCheckRunsJob`) against a `Stack` belonging to an unrelated organization B whose secret they never possessed. Depending on which handler is invoked this can affect deploy/rollback readiness signals and merge-status computation for org B's stacks — cross-organization interference with deploy/ship state.

### Likelihood Explanation
Requires the operator to have configured Shipit with the multi-organization `github:` secrets schema (documented and supported feature) and requires the attacker to be able to produce a validly-signed webhook payload for at least one configured org (i.e., they have legitimate GitHub App webhook delivery for org A, or repo access in org A that triggers such deliveries) while crafting/relaying a payload whose `repository.full_name` names a stack under org B. This is a realistic multi-tenant misconfiguration-adjacent scenario, not requiring any Shipit credentials, API tokens, or GitHub App private keys — only the ability to have org A emit (or replay) a webhook event.

### Recommendation
Bind the two fields with a single authoritative check: after `verify_signature` succeeds for organization `X`, reject the request (or the specific handler dispatch) unless `repository.full_name`'s owner segment matches `X` (and, symmetrically, if `organization.login` is present it must also match). Concretely, in `WebhooksController`, compute `repository_owner` once, verify the signature against that org, and then also enforce `params.dig('repository', 'full_name')&.split('/')&.first&.casecmp?(repository_owner)` before dispatching to `Shipit::Webhooks.for_event(event)`, returning `422` on mismatch.

### Proof of Concept
1. Configure Shipit with two orgs, each with a distinct `webhook_secret`: `org-A` and `org-B` [3](#0-2) .
2. As an actor with legitimate webhook delivery for `org-A` (e.g., GitHub computes/sends the signature using `org-A`'s secret because the outer event genuinely originates from an org-A repo), craft the JSON body so that:
   - `repository.owner.login` = `"org-A"`, and
   - `repository.full_name` = `"org-B/some-repo"`.
3. POST to `/github/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature` computed over this body with `org-A`'s `webhook_secret`.
4. `verify_signature` calls `Shipit.github(organization: "org-A")` and succeeds [1](#0-0) .
5. `PushHandler.call(params)` resolves `stacks` via `Repository.from_github_repo_name("org-B/some-repo")` [2](#0-1)  and triggers `stack.sync_github` on org B's stack [7](#0-6)  despite the signature only having proven authenticity for org A.
