### Title
Webhook signature is validated against the payload's `repository.owner.login`/`organization.login` while every handler dispatches on the independent `repository.full_name` field, allowing a valid webhook secret for one organization to forge events against stacks belonging to a completely different repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to check against by reading `repository.owner.login` (or `organization.login`) out of the untrusted JSON body, and validates the HMAC over the raw payload with that org's secret [1](#0-0) . Once verification "passes," the full parsed `params` hash is handed unmodified to every registered handler for the event [2](#0-1) . All handlers, however, decide **which stacks to mutate** using a different, unverified field of the same payload: `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [3](#0-2)  and looks up local `Repository`/`Stack` records purely by that string, with no re-check against the org used for signature verification. Since nothing in GitHub's HMAC scheme binds `repository.owner.login` to `repository.full_name` at the Shipit layer (the whole raw body is attacker-controlled once you know any one org's secret), these two fields can be made to disagree.

### Finding Description
The trust boundary that should hold is:

organization whose secret authenticated the request == organization/repository the handler is permitted to write to

Before the attacker's request: a webhook is only accepted after HMAC verification against the secret configured for `Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` [4](#0-3) [5](#0-4) .

After the attacker's request: the same raw body is parsed again and passed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [2](#0-1) . Every default handler (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, the `PullRequest::*` handlers) resolves its target stacks via `Handler#stacks`, which calls `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing re-derives `full_name`'s owner and compares it to `repository_owner` used for signing.

Since Shipit explicitly supports **multiple GitHub organizations, each with its own App/webhook secret** (`config/secrets.development.example.yml` documents a multi-org `github:` map, one secret per org) [6](#0-5) , a party who is a legitimate administrator of *any one* onboarded organization (call it `orgA`, which they legitimately control and for which they legitimately know/can regenerate the webhook secret) can craft an arbitrary JSON body such as:

```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<any sha the attacker wants recorded as pushed>"
}
```

and sign it with `orgA`'s webhook secret. `verify_signature` computes `repository_owner == "orgA"`, fetches `orgA`'s `GitHubApp`, and the HMAC matches because the attacker legitimately possesses that secret. The request is accepted. `PushHandler#process`, however, resolves `stacks` from `full_name == "orgB/victim-repo"` [7](#0-6) , i.e. a stack belonging to a completely different organization that the attacker has no relationship to and whose secret they never possessed.

This breaks exactly the binding class called out in scope: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Once a forged event is accepted for an arbitrary target stack, the impact depends on the handler:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)`, which enqueues `GithubSyncJob` for the victim stack — this causes the victim stack to sync against whatever `expected_head_sha` the attacker names, which can desynchronize the deploy pipeline's notion of head commit and, combined with continuous deployment, cause an unintended/forced deploy path to be considered "ready to ship" for a commit the attacker names, without ever touching the victim's real GitHub repo or credentials.
- `StatusHandler`/`CheckSuiteHandler` let the attacker inject fabricated CI status/check-run state for the victim's commits, which can be used to make an otherwise-blocked commit appear to pass required CI checks (`ci.require`) referenced by `DeploySpec` [8](#0-7) , directly enabling deploys/merges on the victim stack that should have been blocked.

This reaches the "unauthorized deploy" / "cross-repository writes" tier called out as Critical impact in the rules, because a credential legitimately scoped to one organization is used to mutate state belonging to a different, unrelated repository/stack.

### Likelihood Explanation
Requires only: (1) the attacker legitimately administers one org onboarded to a shared/multi-tenant Shipit instance (a supported, documented configuration) and thus knows that org's webhook secret, and (2) the target stack (a different org/repo) also exists in the same Shipit instance. No compromise of the victim's GitHub App, private key, or Shipit session is needed — only crafting a raw HTTP POST with a mismatched `repository.owner.login` vs `repository.full_name`, which the webhooks endpoint accepts unauthenticated by design (`skip_before_action :verify_authenticity_token`) [9](#0-8) .

### Recommendation
In `WebhooksController#verify_signature` / `Handler#repository_name`, derive the org used for signature selection and the org used for stack targeting from the *same* field, and explicitly assert they match (e.g., require `repository.full_name.split('/').first == repository_owner`) before dispatching to handlers; reject the webhook otherwise.

### Proof of Concept
Conceptual PoC (cannot be executed in ask-only mode, but the code paths are exact):
1. Legitimately obtain `orgA`'s webhook secret (e.g., as an org admin who installed the Shipit GitHub App for `orgA`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{"repository":{"owner":{"login":"orgA"},"full_name":"orgB/victim-repo"},"ref":"refs/heads/master","after":"deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"}
```
3. Sign with `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_secret, body)>`.
4. `verify_signature` resolves `Shipit.github(organization: "orgA")` and accepts the signature [4](#0-3) .
5. `PushHandler#process` resolves `stacks` for `"orgB/victim-repo"` and enqueues a sync with the attacker-chosen `expected_head_sha` [10](#0-9) , affecting a stack the attacker has no legitimate relationship to.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
