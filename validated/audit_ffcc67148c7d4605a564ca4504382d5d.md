### Title
Fee-on-transfer/deflationary ERC20 tokens desynchronize `ERC20Transactor` accounting, causing stuck `TransfersCheckingAccount` funds and failed cross-chain transfers - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` move ERC20 tokens by calling the token's `transfer()` function and unconditionally trust the requested `amount` as the amount actually moved, never checking the ERC20 contract's real balance change. Any Solidity contract that implements `transfer()` with a fee/burn (i.e. a legitimate fee-on-transfer/deflationary ERC20, deployable without privilege via `pallet-revive`) breaks this assumption.

### Finding Description
`ERC20Matcher` (`cumulus/parachains/runtimes/assets/common/src/lib.rs:159-160`, backed by `IsLocalAccountKey20`/`AccountKey20ToH160` at lines 134-155) matches **any** local `AccountKey20` XCM asset id to the contract's own address — there is no registration, allow-list, or ownership check. Any user can deploy an arbitrary ERC20-compatible contract via `pallet-revive` (a permitted, unprivileged action) and immediately use it as an XCM asset on Asset Hub Westend, whose `AssetTransactors` includes `ERC20Transactor` (`cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs:221-246`).

`withdraw_asset_with_surplus` (`erc20_transactor.rs:150-216`) transfers `amount` to the `TransfersCheckingAccount` via `IERC20::transferCall` (line 169) and then unconditionally credits the XCM holding register with `Erc20Credit(amount)` (line 198-201) purely based on the `transfer()` return value being `true`, never verifying the checking account's actual received balance.

`deposit_asset_with_surplus` (`erc20_transactor.rs:225-306`) later attempts to move that same recorded `amount` from `TransfersCheckingAccount` to the beneficiary via another `IERC20::transferCall` (line 253), again trusting `amount` as ground truth.

If the underlying ERC20 contract implements a transfer fee/burn (fully legal per ERC20 semantics — nothing in `IERC20`/`ethereum_standards` or the XCM barrier restricts this), then:
- On withdraw, `TransfersCheckingAccount` actually receives `amount - fee`, but the XCM holding register believes it holds the full `amount`.
- On deposit, the transactor tries to push out the full `amount` from `TransfersCheckingAccount`, but the account is short by the accumulated fees from prior withdrawals — the ERC20 `transfer()` call reverts (`did_revert()==true` or returns `false`), and `deposit_asset_with_surplus` returns `Err`.

This is the exact analog of the reported `Depositor` bug: an intermediary contract/account assumes `amount_in == amount_out` across a token transfer, without checking real balances, and a deflationary/fee token breaks that invariant.

### Impact Explanation
Repeated XCM transfers of a fee-on-transfer ERC20 progressively drain `TransfersCheckingAccount`'s real balance below what the runtime's XCM accounting believes it holds. This causes:
- Deterministic failure (`FailedToTransactAsset`) of legitimate subsequent deposits for that asset once the shortfall exceeds available balance — griefing/DoS on the checking account shared by all users of that asset.
- Desynchronization between XCM asset-in-holding bookkeping and actual on-chain ERC20 balances, which can leave assets permanently stuck in `TransfersCheckingAccount` (funds effectively unrecoverable through the normal withdraw/deposit path since the amount recorded no longer matches reality).

This is a Medium-severity issue: no privileged role or governance action is required, and it results in functional breakage/fund lock for a class of user-created ERC20 assets in the newly-added ERC20 XCM feature, but does not directly allow theft of unrelated assets or bypass of consensus-critical guarantees.

### Likelihood Explanation
Likelihood is realistic but bounded: it requires a user to deploy or reference a fee-on-transfer ERC20 contract as an XCM asset (fully permitted, no privilege needed) and then perform withdraw/deposit cycles through the transactor. Because `ERC20Matcher` performs no allow-listing, any attacker can trivially deploy such a token and immediately trigger the divergence; this is not a contrived or config-only scenario.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the actual balance delta of the `TransfersCheckingAccount` (or recipient) before and after the `IERC20::transferCall`, and use that measured amount — not the caller-supplied `amount` — when constructing/consuming the `Erc20Credit` in `AssetsInHolding`. Alternatively, explicitly reject ERC20 contracts whose `transfer()` does not preserve `balanceOf` deltas equal to the requested `value` (e.g. by probing balances during asset registration) before allowing them to be used as `ERC20Matcher`-matched XCM assets.

### Proof of Concept
Not executed against a live network. Conceptually:
1. Deploy an ERC20 contract via `pallet-revive` whose `transfer()` deducts e.g. 1% and burns it (a standard fee-on-transfer pattern, legal per ERC20).
2. Reference this contract's `H160` address as an `AccountKey20` XCM asset id (no registration needed, per `IsLocalAccountKey20`).
3. Submit an XCM program on Asset Hub Westend that withdraws `amount` of this asset from a user account — `withdraw_asset_with_surplus` calls `transfer(checking_account, amount)`; checking account actually receives `0.99 * amount`, but `Erc20Credit(amount)` is recorded in holding.
4. XCM program deposits the asset to a beneficiary — `deposit_asset_with_surplus` calls `transfer(beneficiary, amount)` from `TransfersCheckingAccount`, which only holds `0.99 * amount` (plus whatever residual from prior transfers) — call reverts or returns `false`, yielding `XcmError::FailedToTransactAsset`.
5. Repeating step 3 with other users/amounts compounds the checking account's real-vs-recorded shortfall, eventually causing deposits for *any* holder of that fee-on-transfer asset to fail deterministically.
