### Title
Reentrancy in `requestERC20Transfer` / `requestERC721Transfer` via `requestNonce` Updated After External Token Call — (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`requestERC20Transfer` and `requestERC721Transfer` both invoke an external token contract (`safeTransferFrom` / `transferFrom`) **before** `requestNonce` is incremented. Neither function carries a `nonReentrant` guard. A registered ERC20/ERC721 token with a transfer callback (e.g., an ERC-777 `tokensToSend` hook, or any token whose `transferFrom` reenters the bridge) can cause two `RequestValueTransfer` events to be emitted with **distinct, valid nonces** in a single transaction. Bridge operators on the counterpart chain will process both nonces and release bridged assets twice, while only one deposit (or zero deposits) was actually made.

---

### Finding Description

In `BridgeTransferERC20.sol`, `requestERC20Transfer` is:

```solidity
function requestERC20Transfer(
    address _tokenAddress, address _to,
    uint256 _value, uint256 _feeLimit, bytes memory _extraData
) public {
    IERC20(_tokenAddress).safeTransferFrom(          // ← external call FIRST
        msg.sender, address(this), _value.add(_feeLimit));
    _requestERC20Transfer(                           // ← requestNonce++ happens here, AFTER
        _tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
``` [1](#0-0) 

Inside `_requestERC20Transfer`, `requestNonce` is incremented only at the very end:

```solidity
emit RequestValueTransfer(..., requestNonce, fee, _extraData);
requestNonce++;   // ← updated last
``` [2](#0-1) 

The identical pattern exists in `requestERC721Transfer`:

```solidity
function requestERC721Transfer(...) public {
    IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId); // external call first
    _requestERC721Transfer(...);   // requestNonce++ at end
}
``` [3](#0-2) 

By contrast, `handleKLAYTransfer` — the KLAY-side handler — carries an explicit `nonReentrant` modifier:

```solidity
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
``` [4](#0-3) 

Neither `requestERC20Transfer` nor `requestERC721Transfer` has `nonReentrant`, and `requestNonce` is the only state variable that guards against duplicate bridge requests on the deposit side.

---

### Impact Explanation

When a malicious (or callback-enabled) registered token reenters `requestERC20Transfer` during `safeTransferFrom`:

- **Inner call** completes `_requestERC20Transfer` first, emitting `RequestValueTransfer` with `requestNonce = N` and incrementing to `N+1`.
- **Outer call** then completes `_requestERC20Transfer`, emitting `RequestValueTransfer` with `requestNonce = N+1` and incrementing to `N+2`.

Both nonces are valid and distinct. Bridge operators on the counterpart chain observe two legitimate `RequestValueTransfer` events and call `handleERC20Transfer` for both nonces, releasing bridged assets twice. The attacker deposited tokens for at most one transfer (or zero, if the malicious token's inner `transferFrom` returns `true` without transferring).

This constitutes **unauthorized minting or transfer of bridged assets** — directly within the allowed impact gate.

---

### Likelihood Explanation

The attack requires a registered ERC20/ERC721 token with a transfer callback. Token registration is controlled by the bridge owner, which is a semi-trusted role. However:

- **ERC-777 tokens** are a widely deployed standard whose `tokensToSend` hook fires during `transferFrom`. Any ERC-777 token legitimately registered in the bridge is sufficient.
- **ERC-721 tokens** with `safeTransferFrom` callbacks (`onERC721Received`) are similarly common.
- The attacker does not need to be the bridge owner; they only need to use a registered token that has a callback mechanism.

Likelihood is **medium**: requires a registered callback-capable token, but such tokens are common in production deployments.

---

### Recommendation

1. Add `nonReentrant` to both `requestERC20Transfer` and `requestERC721Transfer` (matching `handleKLAYTransfer`).
2. Follow checks-effects-interactions: increment `requestNonce` **before** the external token call, or move the external call to after all state updates.

```solidity
function requestERC20Transfer(...) public nonReentrant {
    _requestERC20Transfer(...);   // increments requestNonce first
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
}
```

Or equivalently, increment `requestNonce` at the top of `_requestERC20Transfer` before any external call.

### Proof of Concept

```solidity
contract MaliciousERC20 is ERC20 {
    Bridge bridge;
    bool reentered;

    function transferFrom(address from, address to, uint256 amount) public returns (bool) {
        if (!reentered) {
            reentered = true;
            // Reenter: emits RequestValueTransfer with nonce N, requestNonce → N+1
            bridge.requestERC20Transfer(address(this), attacker, amount, 0, "");
            reentered = false;
        }
        // Return true without actually transferring (or transfer a dust amount)
        return true;
    }
}

// Attack:
// 1. Bridge owner registers MaliciousERC20 (or attacker uses a legitimate ERC-777 token).
// 2. Attacker calls bridge.requestERC20Transfer(maliciousToken, attacker, 100e18, 0, "").
// 3. safeTransferFrom → MaliciousERC20.transferFrom → reenters requestERC20Transfer
//      → inner _requestERC20Transfer emits RequestValueTransfer(nonce=0), requestNonce=1
// 4. Outer _requestERC20Transfer emits RequestValueTransfer(nonce=1), requestNonce=2
// 5. Bridge operators call handleERC20Transfer for nonce 0 and nonce 1 on counterpart chain.
// 6. Attacker receives 200e18 bridged tokens having deposited 0 (or dust).
