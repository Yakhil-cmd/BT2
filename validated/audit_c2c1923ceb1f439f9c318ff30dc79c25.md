### Title
Global `Commit.where(sha:)` lookup in `StatusHandler#process` lets a webhook from one tenant mutate commit status for another tenant's identical-SHA commit - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the *entire* `commits` table, with no repository or stack scoping, while the DB only enforces SHA uniqueness per stack (`add_index :commits, %i(sha stack_id), unique: true`). Since git commit SHAs are content-addressed and identical across forks/mirrors of the same repository, an attacker who owns a fork of a victim's public repository (and thus can trigger a legitimately-signed `status` webhook from their own org) can write a `Status` record onto the victim's identically-shaed `Commit` row in a completely different `Repository`/`Stack`.

### Finding Description
Binding claimed to be broken: `Commit.sha` uniqueness scope == per-stack (`add_index :commits, %i(sha stack_id), unique: true`, [1](#0-0) ) vs. `StatusHandler#process`'s query scope == global (`Commit.where(sha: params.sha)`, no `stack_id`/`repository` filter), [2](#0-1) .

Both sides evaluated:
- Schema side: nothing prevents two `Commit` rows in two different stacks/repositories from sharing the same `sha`; the unique index is `(sha, stack_id)`, not `(sha)` alone, and no model validation adds a global uniqueness constraint. Git SHAs are deterministic content hashes, so a fork of any public repository naturally contains commits with byte-identical SHAs to the upstream repository it was forked from.
- Handler side: `StatusHandler#process` never restricts the query by repository/stack, unlike its sibling `CheckSuiteHandler#process`, which correctly scopes through `stacks.where(branch: ...)` derived from `Repository.from_github_repo_name(repository_name)` before touching `stack.commits`, [3](#0-2)  and the base `Handler#stacks` helper, [4](#0-3) .

Existing guards do not close the gap:
- `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, which validates that the request was signed with the webhook secret configured for the *sending* organization, [5](#0-4)  and `GitHubApp#verify_webhook_signature`, [6](#0-5) . This only proves the webhook genuinely originated from the attacker's own onboarded organization/repository — it says nothing about which `Commit` row the payload's `sha` may match once inside `StatusHandler#process`.
- `Handler#process` for `StatusHandler` never calls `stacks` or otherwise derives a `Repository`/`Stack` from `payload.dig('repository','full_name')`, so the repository context that was authenticated by the signature check is discarded before the DB lookup.

Attacker's exact path: attacker forks (or otherwise obtains write access to) a public repository whose history overlaps with a Shipit-tracked victim repository (trivial for any fork, since fork commits share identical SHAs with upstream ancestor commits), configures/owns a Shipit-recognized GitHub org/repo (satisfying `verify_webhook_signature` for their own tenant), and sends a `status` webhook (`POST /webhooks` with `X-Github-Event: status`) whose `sha` matches a commit that also exists, under a different `Repository`/`Stack`, in the victim's Shipit instance. `StatusHandler#process` finds and mutates **every** `Commit` row across all stacks with that `sha`, calling `commit.create_status_from_github!(params)` on each — including the victim's commit in a repository the attacker never authenticated against.

### Impact Explanation
The attacker can write a forged `Status` (arbitrary `state`, `context`, `description`, `target_url`) onto a commit belonging to a repository/stack they do not own or control, purely because that commit's SHA happens to coincide with one in their own (attacker-owned) repository. Statuses feed into `Commit#status`/`stack.branch_status`/`merge_status`, which gate whether a commit is considered deployable/mergeable in Shipit. This is a cross-tenant integrity violation: a payload signed for tenant A's webhook mutates tenant B's commit/stack state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any victim repository whose commit history overlaps with a repository the attacker can push to (most trivially, any fork relationship), and the blast radius spans every stack tracking a commit with the colliding SHA, not just one target.

### Likelihood Explanation
Preconditions: (1) the attacker's own repository/org must be a Shipit-recognized GitHub organization with a working webhook secret (i.e., the attacker is already an onboarded, if unprivileged, Shipit tenant/repo owner who can legitimately emit signed `status` events for their own repo); (2) the victim repository must be tracked as a `Shipit::Repository`/`Stack` and contain at least one commit whose SHA also exists in a repository the attacker can push events for — which is the normal case for any fork of a public open-source repository, since forked commits retain identical SHAs. No GitHub secrets, session tokens, or API client credentials are needed beyond the attacker's own legitimately-configured webhook. This makes the attack cheap and repeatable: one `POST /webhooks` request per forged status, against any commit SHA the attacker can reproduce or already shares via fork ancestry.

### Recommendation
Scope `StatusHandler#process` (and any other handler using a bare `Commit.where(sha:)`/`Commit.by_sha` lookup driven by webhook payload) to the repository that the webhook was verified for, mirroring `CheckSuiteHandler`: derive `stacks` from `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and restrict the query to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalent `stack.commits.where(sha:)` per matched stack), instead of querying the global `commits` table.

### Proof of Concept
Minitest under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (conceptual, not yet written):
```ruby
test "commits with identical sha under different stacks both persist (schema binding)" do
  stack_a = shipit_stacks(:shipit)               # repository/stack A
  stack_b = create_stack_for_different_repository # distinct Repository, different github_id/owner

  sha = "a" * 40
  commit_a = stack_a.commits.create!(sha:, message: "m", author: shipit_users(:walrus), committer: shipit_users(:walrus))
  commit_b = stack_b.commits.create!(sha:, message: "m", author: shipit_users(:walrus), committer: shipit_users(:walrus))

  assert commit_a.persisted?
  assert commit_b.persisted?
  assert_equal commit_a.sha, commit_b.sha
  refute_equal commit_a.stack_id, commit_b.stack_id
end

test "StatusHandler#process mutates commits across unrelated stacks sharing a sha" do
  # ...same two commits as above, from two different Repository owners...
  payload = { "sha" => sha, "state" => "success", "context" => "ci",
              "repository" => { "full_name" => stack_a.repository.full_name, "owner" => { "login" => stack_a.repository.owner } } }

  assert_difference -> { commit_a.statuses.count + commit_b.statuses.count }, 2 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
This demonstrates both halves of the equality: the schema/model side permits two `Commit` rows with identical `sha` under different stacks/repositories, and `StatusHandler#process`'s global query mutates both from a single webhook nominally scoped to only one of them.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
