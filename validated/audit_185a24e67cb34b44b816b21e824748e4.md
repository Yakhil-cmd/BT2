## Analysis

The report's bug class is "an administrative mapping/record is not scoped/cleaned to match the entity actually being acted upon, letting stale/foreign keys be reused against the wrong target." The closest reachable analog in this engine is a **webhook-authentication scope mismatch** in the `status` event handler.

### The binding that should hold
`repository_owner` used to select the `GithubApp`/`webhook_secret` that authenticates a webhook == the `Stack`/repository whose data is mutated by that webhook.

### Where it breaks

`WebhooksController#verify_signature` selects which `GithubApp` (and therefore which `webhook_secret`) to verify the signature against based solely on the org name found in the payload: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple GitHub Apps/orgs, each with its own independent `webhook_secret`, in a single deployment: [3](#0-2) 

Once the signature is verified for *that org's* secret, the payload is dispatched by event type. Every other handler scopes its writes to the repository named in the payload via the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`): [4](#0-3) [5](#0-4) [6](#0-5) 

`StatusHandler`, however, never calls `stacks` — it looks up commits **purely by SHA, globally, with no repository/organization filter at all**: [7](#0-6) 

`create_status_from_github!` then writes the attacker-supplied `state`/`description`/`target_url` onto that commit and recomputes the commit's status, which feeds directly into deploy-gating logic (`deployable?`, `blocked?`, `schedule_merges`): [8](#0-7) [9](#0-8) [10](#0-9) 

### Title
Cross-organization commit-status forgery via unscoped `StatusHandler` lookup enables unauthorized deploy gating bypass - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` solely by `sha`, with no check that the commit belongs to the repository/organization whose `webhook_secret` was used to authenticate the request. In a multi-organization Shipit deployment, an attacker who legitimately controls a GitHub App/webhook installed on **Organization A** can forge a `status` webhook payload, correctly signed with Organization A's secret, that references a commit `sha` belonging to a completely unrelated **Organization B**'s stack, and have Shipit write a fabricated CI status onto that foreign commit.

### Finding Description
`WebhooksController#verify_signature` derives the signing `GithubApp` from `repository.owner.login`/`organization.login` in the payload body (`repository_owner`), i.e., authentication is scoped to "does this payload carry a valid signature for the organization it claims to be from" [1](#0-0) . Nothing ties the verified organization to the specific `repository` field consumed later by the handler, and `StatusHandler` doesn't perform that check itself — unlike `PushHandler`/`CheckSuiteHandler`, which both scope through `Handler#stacks`, which filters by `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [4](#0-3) . `StatusHandler` instead does a bare `Commit.where(sha: params.sha)` [7](#0-6) , so any commit SHA in the entire Shipit instance — belonging to any stack, any repository, any organization — can be targeted as long as the request is signed with *some* configured org's webhook secret, not necessarily the org that owns the commit.

Before vs after the crafted request:
- Before: Commit C in Org B's stack has status derived only from Org B's own GitHub App/CI webhooks (equality: verified-org == commit's-owning-org holds).
- After: attacker sends `X-Github-Event: status` signed with Org A's `webhook_secret`, body `{"sha": "<Org B commit sha>", "state": "success", ...}`. `verify_webhook_signature` succeeds against Org A's secret [11](#0-10) , then `StatusHandler` mutates Commit C's status regardless of which org actually owns it — breaking the equality.

### Impact Explanation
A forged `success` status on a foreign commit changes `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [12](#0-11) , and `blocked?`/merge scheduling logic [13](#0-12)  and [14](#0-13) . A commit forged into "success" can satisfy the `require_ci` gate checked by `DeploysController#create` (`param_error!(:require_ci, ...) if params.require_ci && !commit.deployable?`) [15](#0-14) , letting a subsequent (otherwise legitimate) deploy request bypass its CI requirement — an unauthorized deploy of code that never actually passed CI. It also pollutes commit-status UI/state and can trigger merge-queue scheduling for a repo the attacker does not control.

### Likelihood Explanation
Requires the attacker to hold a valid `webhook_secret` for at least one org configured on the same Shipit instance (a credential they may legitimately possess for their own team/org in a shared multi-tenant Shipit deployment, as explicitly supported by `config/secrets.yml`'s multi-org schema). No Shipit session, `ApiClient` token, or GitHub repository write access to the *target* org/repo is required — only knowledge of any one configured org's webhook secret, satisfying the "unprivileged relative to the victim org" requirement.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup through `stacks` (as `PushHandler`/`CheckSuiteHandler` already do) so the commit must belong to a stack whose repository matches `payload.dig('repository', 'full_name')`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent join, instead of a global `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Attacker legitimately administers a GitHub App/webhook for `org-attacker` on the shared Shipit instance and knows its `webhook_secret`.
2. Attacker identifies a target commit SHA belonging to `org-victim/repo`'s stack (SHAs are visible in Shipit's public-ish task/commit pages or PR history).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body:
```json
{"sha": "<victim commit sha>", "state": "success", "repository": {"owner": {"login": "org-attacker"}}}
```
signed (`X-Hub-Signature`) with `org-attacker`'s `webhook_secret`.
4. `verify_signature` passes because it only checks the signature against `org-attacker`'s secret [1](#0-0) .
5. `StatusHandler#process` finds the victim's `Commit` purely by SHA and applies the forged `success` status [7](#0-6) , changing `deployable?` for that commit in `org-victim`'s unrelated stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
