### Title
Definition-disclosure griefing lets any co-signer/oracle-condition holder permanently DoS a pending multi-party address's first transaction - (File: validation.js)

### Summary
`validateAuthor()`'s `handleDuplicateAddressDefinition()` in `validation.js` unconditionally rejects any unit that explicitly discloses an address `definition` once that `definition_chash` already exists in the `definitions` table, exactly like the referenced report's `checkOrder`/`_useNonce` pattern where any unprivileged caller can "consume" a state slot ahead of the legitimate actor and cause the legitimate action to permanently revert.

### Finding Description
When a unit's author includes an explicit `definition` field (used only on the first spend from that address), `validateDefinition()` looks up the definition via `storage.readDefinitionByAddress()` [1](#0-0) . If the definition_chash is already present (`ifFound`), it calls `handleDuplicateAddressDefinition`, whose active code path is:

```
function handleDuplicateAddressDefinition(arrAddressDefinition){
//	if (!bNonserial || objValidationState.arrAddressesWithForkedPath.indexOf(objAuthor.address) === -1)
		return callback("duplicate definition of address "+objAuthor.address+", bNonserial="+bNonserial);
``` [2](#0-1) 

The guard that would allow a matching re-disclosure is commented out, so **any** unit whose author declares this definition after another unit has already caused it to be inserted into the `definitions` table is rejected outright, regardless of whether the definitions match.

Crucially, the `definitions` table row is written as soon as any unit carrying that definition is *accepted into the DAG* (not necessarily stable/final), in `writer.js`'s `saveJoint`:
```
if (definition){
    definition_chash = objectHash.getChash160(definition);
    conn.addQuery(arrQueries, "INSERT "+conn.getIgnore()+" INTO definitions (definition_chash, definition, has_references) VALUES (?,?,?)", ...);
``` [3](#0-2) 

For addresses defined with an `or`/`r of set` composition (a normal pattern for shared/multi-sig addresses created via `wallet_defined_by_addresses.js`, e.g. `["or", [["address","A"],["address","B"]]]`), any single co-signer who already knows the full definition (it is shared among all members when the shared address is created, see `handleNewSharedAddress`/`addNewSharedAddress`) [4](#0-3)  can unilaterally satisfy just their own branch of the `or` and broadcast a trivial unit (e.g. a zero-value text/data message) that discloses the *identical* definition first. This is the "front-run and consume the one-time state" step analogous to calling `checkOrder`.

The victim's independently composed unit — built by `composeAuthorsForAddresses`, which only omits the `definition` field if a *stable* definition disclosure is already found [5](#0-4)  — will also include the `definition` field if none was stable at composition time. Once the attacker's throwaway unit lands first (even if unstable), the victim's real payment unit hits `ifFound` → `handleDuplicateAddressDefinition` → unconditional `"duplicate definition"` error, permanently invalidating that already-signed unit. The user must recompose and re-sign from scratch, and if the attacker can repeat this before every subsequent attempt (or simply beats it once at a critical moment), the address's first spend can be blocked indefinitely.

### Impact Explanation
This causes an AA fund/asset-holder or shared-address participant's transaction to be permanently rejected by validation ("your unit is unable to confirm"), forcing recomposition; a hostile co-signer of a 2-of-2 or `or`-composed address can weaponize this to block a joint address's very first spend at will, which is a concrete denial of the address's use case (Medium severity — funds/participation blocked, not simply resource-only DoS).

### Likelihood Explanation
Requires the attacker to be a legitimate signer of the `or`/`r of set` branch of a shared address (a normal role for co-signers of these composed addresses) or otherwise possess a satisfying authentifier for one branch of the definition, and to race a throwaway unit into the DAG before the victim's transaction confirms. This is realistic for any multisig/shared address using disjunctive definitions and does not require breaking cryptography.

### Recommendation
Restore/implement the check that only rejects duplicate-definition disclosures when the new definition doesn't match the already-known one (or when it's a genuine fork/conflict scenario), i.e., accept the unit when `objectHash.getChash160(arrAddressDefinition) === objectHash.getChash160(objAuthor.definition)` instead of unconditionally failing, so an honest, matching re-disclosure by any party is not treated as an error.

### Proof of Concept
1. Alice and Bob create a shared address `S = or(A_alice, A_bob)` via `wallet_defined_by_addresses.js`'s shared-address flow, both learning the full `arrDefinition`.
2. Before Alice sends her first real payment from `S` (which must include `definition` since no stable disclosure exists yet), Bob crafts and broadcasts a trivial unit from `S`, satisfying only his own `or` branch, including the identical `definition`. This unit is accepted (not necessarily stable) and `writer.js` inserts the `definition_chash` into the `definitions` table.
3. Alice's pre-signed real unit (already built with `definition` included, per `composer.js`) is then broadcast; `validateAuthor` → `validateDefinition` finds `ifFound`, and `handleDuplicateAddressDefinition` unconditionally returns `"duplicate definition of address S"`, rejecting Alice's unit even though the definitions are byte-identical.
4. Alice must recompose and resend without the `definition` field; Bob can repeat step 2 to block her again, achieving a repeatable griefing DoS on address `S`'s spends.
