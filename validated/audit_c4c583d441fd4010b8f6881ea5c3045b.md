### Title
Webhook signature verification authenticates a claimed organization but writes to a repository chosen from an unrelated payload field, allowing cross-tenant unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/push_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the request against by reading `repository.owner.login` (or `organization.login`) out of the untrusted JSON body itself, then computes the HMAC over the entire raw body [1](#0-0) . Any Shipit tenant that legitimately owns a configured GitHub App/organization (and therefore knows its own `webhook_secret`) can forge an arbitrary webhook payload, sign it correctly with their own secret, set `repository.owner.login` to their own org (so the signature check passes), but set `repository.full_name` to a *different* organization's repository. All webhook handlers resolve the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` [2](#0-1) , which is never cross-checked against the organization that was used to authenticate the request.

### Finding Description
The relevant equality that should hold but doesn't:

`organization used to select/verify the webhook_secret (repository_owner)` == `organization of the repository whose Stacks get mutated (repository.full_name)`

`WebhooksController#verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`GithubApp#verify_webhook_signature` just checks that the HMAC over the raw body matches, using the secret for whichever organization `repository_owner` claims to be:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [4](#0-3) 

Because the attacker controls (and knows the secret for) the organization named in `repository.owner.login`, they can compute a valid signature for *any* body content they choose — including a `repository.full_name` that points at a completely different, victim organization's repository. `Handler#stacks`/`#repository_name` then trust `full_name` unconditionally to look up the target `Repository`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler#process` uses this repository/stack lookup and the attacker-controlled `after` (commit SHA) to drive a sync of the victim's stack to an arbitrary commit:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

`Stack#sync_github` enqueues `GithubSyncJob` with the attacker-chosen `expected_head_sha`, which fetches and appends commits (potentially triggering continuous deployment) for the victim stack: [6](#0-5) [7](#0-6) 

The `StatusHandler` is similarly unscoped: it looks up commits globally by SHA without any repository/organization check at all, `Commit.where(sha: params.sha)`, so a forged, self-signed status event can affect commits belonging to *any* stack in the whole Shipit instance: [8](#0-7) 

### Impact Explanation
This breaks the trust boundary between "who authenticated this webhook" and "whose data gets written." A tenant/organization that only controls its own GitHub App installation on Shipit can forge webhook traffic that mutates another organization's stacks: triggering `GithubSyncJob` against arbitrary commit SHAs (which for stacks with `continuous_deployment: true` can result in an unauthorized deploy of attacker-chosen code), and forging commit statuses for arbitrary stacks via `StatusHandler`. This matches the "unauthorized deploy" / cross-tenant write impact category. It only applies in multi-organization Shipit deployments where more than one org's `webhook_secret` is configured (a normal, documented deployment mode per `docs/setup.md` / `config/secrets.development.shopify.yml`).

### Likelihood Explanation
Likelihood is High for any deployment hosting multiple organizations/tenants: any organization admin who can install/configure their own GitHub App on the shared Shipit instance already knows their own `webhook_secret` and can freely craft and POST a self-signed payload to `/webhooks` with an arbitrary `repository.full_name`/`sha`/`ref`. No privileged Shipit account, session, or API token is required — only a legitimately configured organization's own webhook secret, which is knowledge an unprivileged organization owner is expected to have by design.

### Recommendation
After verifying the HMAC, additionally validate that the repository/organization the payload claims to represent (`repository.full_name` / `repository.owner.login`) actually belongs to the organization whose secret was used to verify the signature, before dispatching to any handler — e.g., reject the webhook if `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner != repository_owner`. Additionally, scope `StatusHandler`'s `Commit.where(sha: ...)` lookup by the verified repository/organization rather than searching globally across all stacks.

### Proof of Concept
1. Attacker operates `org-attacker`, a legitimately configured tenant on the shared Shipit instance, and knows its `webhook_secret` (`SECRET_A`) from `config/secrets.yml`.
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/production-service"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, raw_body)>` themselves, since they know `SECRET_A`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` reads `repository_owner = "org-attacker"`, fetches `Shipit.github(organization: "org-attacker")`, verifies the HMAC against `SECRET_A` — succeeds because the attacker signed it with their own known secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-victim/production-service")` — the victim's real stack — and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, enqueuing `GithubSyncJob` against the victim's production stack with attacker-controlled data.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
