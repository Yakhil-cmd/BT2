## Confirmed Analog Vulnerability

### Title
Webhook signature verification binds to `repository.owner.login` while event handlers dispatch on `repository.full_name`, allowing cross-organization commit-status/push forgery in multi-org deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) used to authenticate an inbound webhook based on `repository.owner.login` taken directly from the attacker-controlled JSON body, while the handlers that actually mutate state (e.g. `StatusHandler`, `PushHandler`) select the *target* repository/commits using an entirely different field of the same body, `repository.full_name`. Nothing ties these two fields together, so a payload can be signed with the secret of organization A yet act on a repository belonging to organization B.

### Finding Description
`verify_signature` resolves the signing key via:
```ruby
github_app = Shipit.github(organization: repository_owner)
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization secrets from `secrets.github`, supporting a multi-org configuration where each organization has its own `webhook_secret`: [3](#0-2) 

After the signature is validated using organization A's secret, the raw JSON is dispatched unmodified to all registered handlers for the event:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

But the base `Handler` class resolves which repository/stack to act on from a *different* payload field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`Repository.from_github_repo_name` looks up by `owner`/`name` independent of any relation to the signing organization: [6](#0-5) 

Concretely, `StatusHandler` does not scope by repository at all — it matches purely on `sha` globally across all commits in the database, and directly creates a `Status` record from attacker-supplied `state`/`context`/`description`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [7](#0-6) 

This is the exact analog to the reported bug class: the value that is cryptographically **authenticated** (`repository.owner.login`, used to pick the verifying secret) is not the value that is actually **acted upon** (`repository.full_name` / bare `sha`, used to pick the target). Just as duplicate Compound proposal actions shared an identifier that didn't uniquely bind to the intended action, here the trust binding "authenticated organization == repository being written" is never enforced, so the two can be made to diverge by an attacker who legitimately controls the webhook secret of *any one* organization configured on the shared Shipit instance.

### Impact Explanation
An operator who administers organization A's GitHub App/webhook configuration (and therefore legitimately knows organization A's `webhook_secret` — not a Shipit credential, session, or API token) can forge a signed webhook where `repository.owner.login = "orgA"` (satisfies signature verification) but `repository.full_name` (for push events) or a bare `sha` (for status events, which isn't even scoped by repository) references a stack belonging to organization B, which they have no access to. This lets them:
- Fabricate a `success` CI status for arbitrary commits belonging to another organization's stack via `StatusHandler`, bypassing the CI-gating safety normally required before a commit is deployable, and potentially triggering `ProcessMergeRequestsJob` / continuous delivery for that stack.
- Trigger `sync_github`/`GithubSyncJob` for another organization's stack via `PushHandler` using a forged `after` SHA.

This constitutes an authorization-boundary bypass ("unauthorized deploy" enablement / cross-repository state corruption) matching the High-impact criteria (escalation across a repository/organization trust boundary without a Shipit session, API token, or `webhook_secret` belonging to the victim org).

### Likelihood Explanation
This requires the Shipit instance to be configured for multiple GitHub organizations (the `secrets.github` multi-org schema) and an attacker to have legitimate control of at least one onboarded organization's webhook secret — a realistic scenario for any shared/centralized Shipit deployment serving multiple business units or external partner orgs, none of which is out of scope per the rules (it does not require a Shipit session, API client token, `api_clients_secret`, or GitHub App private key — only knowledge of one org's own already-configured webhook secret).

### Recommendation
Bind the value used for signature-key selection to the same value used for repository dispatch: after selecting `github_app` by `repository_owner`, re-validate that `repository.full_name`'s owner (and, for `status` events, the resolved commit's stack owner) matches `repository_owner` before invoking any handler; reject the webhook otherwise.

### Proof of Concept
1. Configure Shipit with multi-org secrets (`secrets.github: {orgA: {webhook_secret: ...}, orgB: {webhook_secret: ...}}`).
2. As an administrator of `orgA`'s GitHub App, compute `sha1=HMAC(orgA_webhook_secret, body)` for a `status` event payload where `repository.owner.login = "orgA"` but `sha` corresponds to a commit that belongs to a stack under `orgB`.
3. POST to `/github/webhooks` with header `X-Hub-Signature: sha1=<computed>`. `verify_signature` resolves `Shipit.github(organization: "orgA")` and validates successfully.
4. `StatusHandler#process` matches `Commit.where(sha: params.sha)` — since it performs no organization scoping at all — and calls `create_status_from_github!` on the `orgB` commit, injecting a forged CI status the attacker was never authorized to set.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
