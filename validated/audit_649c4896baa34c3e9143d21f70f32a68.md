### Title
Webhook status/CI signature is verified against the organization derived from `repository.owner.login`, but the commit acted upon is looked up by SHA alone with no repository binding - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the inbound HMAC signature against using `repository_owner`, taken from the JSON body itself (`repository.owner.login` / `organization.login`). Once the signature check passes, `StatusHandler#process` updates commit status by matching `sha` globally across the entire `commits` table, with no check that the commit actually belongs to the repository/organization that produced the authenticated webhook.

### Finding Description
The trust binding that should hold is: *"the organization whose secret authenticated this webhook" == "the repository/commit that the webhook is allowed to mutate."* This engine breaks that binding in two places that compound each other:

1. `WebhooksController#verify_signature` derives the signing organization straight from attacker-controlled JSON, then fetches that organization's `GitHubApp` and validates the signature against it: [1](#0-0) [2](#0-1) 

2. `StatusHandler#process` resolves the target purely from `sha`, with no repository/stack scoping at all: [3](#0-2) 

Compare this with `Handler#stacks`/`repository_name`, which *does* scope other handlers (e.g. `PushHandler`) to the repository named in the payload: [4](#0-3) 

`StatusHandler` does not use `stacks`/`repository_name` at all — it queries `Commit.where(sha: params.sha)` across the whole installation, and any commit record (regardless of which stack/repository it belongs to) whose SHA matches gets its CI status mutated: [5](#0-4) 

Because Git commit SHAs are content-addressed, forks and repos that share history (a very common GitHub pattern) can and do share identical commit SHAs. Shipit only requires the webhook signature to validate against *some* organization it is configured for (from `Shipit.github(organization: repository_owner)` in `lib/shipit/github_app.rb`), not the specific organization that owns the target `Stack`: [6](#0-5) 

### Impact Explanation
If Shipit is configured (as documented) with multiple GitHub Apps/organizations (`docs/setup.md`, "Using Multiple GitHub Applications"), or even with a single org where the attacker legitimately administers one repository whose commit history is shared with a tracked victim stack (e.g. a fork), the attacker can send a validly-signed `status` webhook from their own repository/org for a SHA that is also tracked by a victim `Stack`. The signature check passes because it is verified against the organization that actually signed it, but `StatusHandler` applies the resulting status update to every `Commit` record with that SHA, including the victim's. This can set a commit's CI state to `success`, which feeds directly into `Commit#deployable?` and `Commit#schedule_continuous_delivery`, potentially causing an unauthorized commit to be marked deployable and triggering continuous deployment or unblocking a manual deploy for a stack the attacker does not own or have any GitHub relationship with: [7](#0-6) [8](#0-7) 

This constitutes an unauthorized-deploy path (cross-repository write of trust-critical state) crossing an authentication boundary the signature check was supposed to enforce, matching the "authenticated organization vs. repository/commit written" binding called out in the rules.

### Likelihood Explanation
Requires: (a) Shipit be reachable with a known/guessable webhook endpoint (documented, public), and (b) the attacker control (or be an admin of) at least one GitHub organization/repository that is itself onboarded into the same Shipit instance (single-tenant or multi-org deployments), and (c) a shared commit SHA between the attacker's repository and the victim `Stack`'s repository (trivially achievable via forking a public/tracked repository and pushing the same commit or opening a PR with matching history). No repository write access to the victim repo, no `ApiClient` token, and no privileged Shipit account are needed — only ordinary control of one's own onboarded org/repo, which the rules explicitly treat as unprivileged relative to the victim repository.

### Recommendation
Scope `StatusHandler` (and any other handler resolving records purely by `sha`) to the repository/stacks derived from `repository_name`, exactly as `PushHandler`/`Handler#stacks` do, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`. More generally, ensure `verify_signature`'s chosen signing organization is cross-checked against the repository/stack that the handler subsequently mutates, so a valid signature from organization A can never be used to write state belonging to a stack owned by organization B.

### Proof of Concept
1. Shipit tracks `victim-org/victim-repo` as a `Stack`, and has ingested a commit with SHA `abc123...` (via normal sync).
2. Attacker forks `victim-org/victim-repo` into `attacker-org/attacker-repo` (or otherwise possesses a repository sharing that same commit SHA) and onboards it to the same Shipit instance, or otherwise controls a `webhook_secret`/GitHub App configured for `attacker-org` in `config/secrets.yml`.
3. Attacker sends a `status` event to `POST /webhooks` with body:
   ```json
   { "sha": "abc123...", "state": "success", "context": "ci",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" } }
   ```
   signed with `attacker-org`'s legitimate webhook secret.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC validates successfully.
5. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, matches the victim's commit record (unscoped by repository), and calls `create_status_from_github!`, marking it `success` — potentially unblocking `victim-org/victim-repo`'s deploy pipeline despite the attacker having no access to that org/repo.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
