### Title
Webhook signature is verified against the organization derived from `repository.owner.login`/`organization.login`, but the repository actually acted upon is taken from an independently-controlled `repository.full_name` field in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC against using `repository_owner`, a value read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Every webhook handler, however, resolves the target `Repository`/`Stack` using a completely different payload field, `repository.full_name` (`Handler#repository_name`, and duplicated in `PushHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`). `StatusHandler` goes further and does not scope by repository at all, matching purely on `Commit.where(sha: params.sha)` across the entire installation. Because Shipit supports multi-organization configuration (`config/secrets.yml` keyed by org, `Shipit.github_organizations`), an actor who legitimately possesses the `webhook_secret` for one configured organization can craft a payload whose `repository.owner.login` (used only for signature-org selection) names their own org, while `repository.full_name` (used to pick which `Stack`/`Repository` the handler mutates) names a repository belonging to a *different* configured organization.

### Finding Description
The binding that should hold is: `organization used to verify signature == organization owning the repository the handler mutates`. This is broken:

- `verify_signature` picks the app config via `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

- Once the signature check passes (using org A's secret), `create` dispatches to handlers, passing the parsed JSON body verbatim. [3](#0-2) 

- Every handler resolves its target repository/stack from `payload.dig('repository', 'full_name')`, a separate field from the one used for signature-org selection. [4](#0-3) [5](#0-4) [6](#0-5) 

- `StatusHandler` doesn't even reference the repository at all — it applies the attacker-supplied state to any `Commit` in the entire install matching the given `sha`, across all stacks/organizations. [7](#0-6) 

- `Shipit.github` supports per-organization apps/secrets keyed independently, confirming multiple orgs (hence multiple, mutually-untrusted secret holders) can be configured on one Shipit instance. [8](#0-7) 

Since `/webhooks` is a public, unauthenticated endpoint (only integrity-checked via `verify_signature`, not restricted to actual GitHub IP ranges or any session), any party who legitimately controls org A's `webhook_secret` (e.g., an org admin, or someone who obtained one org's secret through normal, lower-privilege access) can POST a forged payload directly to Shipit, setting `repository.owner.login`/`organization.login` = "orgA" (to pass signature verification against orgA's key) while setting `repository.full_name` = "orgB/some-repo" (a repository belonging to an org they do not control). This lets the attacker:
- Trigger `GithubSyncJob`s / provoke merges and review-stack provisioning on org B's stacks via `push`/`pull_request` handlers.
- Forge CI status/check-run states for org B's commits via `StatusHandler`/`CheckSuiteHandler`, which directly gates the merge queue (`schedule_merges`) and continuous delivery (`schedule_continuous_delivery`) on `Stack`s the attacker does not own. [9](#0-8) 

### Impact Explanation
This breaks the organization-authenticated vs. repository-written binding explicitly called out as in-scope. By forging CI status ("success") for a target commit belonging to a repository/organization the attacker does not control, the attacker can cause Shipit to believe CI has passed, unlocking automatic merges via the merge queue and triggering continuous deployment (`schedule_merges`, `schedule_continuous_delivery`), effectively an unauthorized deploy/merge or a cross-repository write of state that Shipit trusts for deploy/merge decisions. This meets the Critical "unauthorized deploy, rollback, or merge" / "cross-repository writes" bar.

### Likelihood Explanation
Requires the attacker to already legitimately hold a `webhook_secret` for at least one organization configured in the multi-org `secrets.yml` — a credential far weaker than repository write access, a Shipit session, or `GITHUB_TOKEN`. In a multi-tenant Shipit deployment serving several organizations with independently managed webhook secrets, this is a realistic, moderate-likelihood scenario: any org onboarded to the shared Shipit instance can pivot into any other onboarded org's stacks.

### Recommendation
- Verify that the organization used for signature validation (`repository_owner`) matches the organization implied by `repository.full_name` (i.e., `full_name.split('/').first`) before dispatching to handlers; reject the request if they differ.
- Scope `StatusHandler` (and any handler resolving via `Commit.where(sha:)`) to commits/stacks belonging to the verified organization/repository, not a global sha lookup.
- Consider signing/binding the expected repository identity into the verification step itself rather than trusting two independently-read fields from the same untrusted payload.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (multi-org config as documented in `docs/setup.md`). [10](#0-9) 
2. As a holder of `orgA`'s `webhook_secret` (e.g., an admin of an orgA repo), craft a `status` event JSON body:
```json
{
  "sha": "<sha-of-a-commit-belonging-to-orgB/some-repo>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "orgA" } }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, body)>`.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner = "orgA"`, validates successfully against orgA's secret. [1](#0-0) 
6. `StatusHandler#process` matches on `sha` alone (no organization/repository check) and creates a `success` status on the orgB commit, potentially unlocking merge/deploy for a stack the attacker has no access to. [7](#0-6)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
