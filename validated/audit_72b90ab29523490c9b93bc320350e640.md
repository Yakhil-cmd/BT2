## Analog Found

### Title
Missing Network (`alt`) Binding in Signed Messages / `is_valid_signed_package` Enables Cross-Network Signature Replay - (File: `signed_message.js`, `formula/evaluation.js`)

### Summary
The Aptos report flags that transactions lacking a bound `chain_id` can be replayed across networks that share the same signing scheme. Obyte's ocore analog is the `alt` field (mainnet=`'1'`, testnet=`'2'`, devnet=`'3'`) used to separate networks, defined in `constants.js` [1](#0-0) . Regular DAG units are protected: `validation.js` explicitly rejects any unit whose `alt` doesn't match the running network's `constants.alt` [2](#0-1) . However, the **signed-message** subsystem used by wallets, AAs and paired-device messaging never binds this network identifier into what gets signed.

### Finding Description
`signMessage()` builds an `objUnit` containing only `version`, `signed_message`, and `authors` (plus optionally `last_ball_unit`) — there is no `alt`/network field included [3](#0-2) .

`validateSignedMessage()` explicitly whitelists the allowed top-level fields as `["signed_message", "authors", "last_ball_unit", "timestamp", "version"]` — `alt` is not among them, and it is never checked [4](#0-3) . The only network-adjacent check is on `version` (i.e., protocol version string), not the network partition (`alt`).

The hash-to-sign is computed by `objectHash.getSignedPackageHashToSign`, which serializes the object described above — again with no `alt`/chain component — so the resulting signature is bit-for-bit identical regardless of which ocore network (mainnet, testnet, devnet) it is used against, as long as the signing address/definition is the same on both networks (which is common, since `chash160`-derived addresses do not depend on `alt`).

This signed-message construct is directly exposed to arbitrary AA trigger data via the `is_valid_signed_package` oscript operation, which un-marshals attacker/trigger-supplied JSON, only checks `hasFieldsExcept(signedPackage, ['signed_message', 'last_ball_unit', 'authors', 'version'])`, and then calls `signed_message.validateSignedMessage(conn, signedPackage, evaluated_address, mci, ...)` [5](#0-4) . Any signature ever produced by an address's key for a given message (e.g. one produced on testnet or devnet, or produced for one AA's `is_valid_signed_package` check) will validate identically when replayed as trigger data against a different network deployment of the same AA/address, since nothing in the signed payload commits to the network.

### Impact Explanation
An off-chain signed authorization (used by AAs to gate fund releases, oracle-style attestations, or approvals via `is_valid_signed_package`) is not bound to the network it was intended for. If the same address/key material is used across mainnet/testnet/devnet (a realistic scenario for AA authors who test on testnet with identical definitions before deploying to mainnet, or reuse cold-storage keys), a signed message obtained/observed on one network can be replayed as valid trigger data on another network's AA that performs the identical `is_valid_signed_package(signed_package, address)` check. Where such an AA gates a payment or state transition on this check (e.g., "release funds if this address signed order X"), the replay lets an attacker satisfy an authorization check with a signature never intended for that network/AA instance, leading to unauthorized fund release from the AA (fund loss).

### Likelihood Explanation
The bug is systemic to `signed_message.js`/`is_valid_signed_package` (any AA using this construct is affected), and no privileged position is required — an ordinary AA trigger sender can submit the replayed signed package as `data`. The main precondition — an address/definition reused with the same signing key across networks — is a routine practice (developers/users commonly test with the same seed/definition on testnet before mainnet), making exploitation realistic wherever such reuse occurs, though it is not universal (impact depends on a specific AA's use of `is_valid_signed_package` for value-releasing logic).

### Recommendation
Bind the network identifier into the signed payload and its validation: include `constants.alt` (and/or the intended AA/asset context) as a mandatory field of the `signed_message` structure, add it to the `hasFieldsExcept` whitelist, incorporate it into `objectHash.getSignedPackageHashToSign`'s source string, and reject in `validateSignedMessage` (and in the `is_valid_signed_package` oscript handler) any package whose `alt` doesn't match `constants.alt` of the executing network — mirroring the existing `objUnit.alt !== constants.alt` check already enforced for ordinary DAG units in `validation.js`.

### Proof of Concept
1. On network A (e.g. devnet, `alt='3'`), a user signs a message with `signMessage()` for address `ADDR` (definition `["sig",{pubkey:PK}]`), producing `objSignedMessage = {version, signed_message, authors:[{address:ADDR, authentifiers:{r:SIG}}]}` — note: no `alt` field is present.
2. Deploy (or observe) an AA on network B (e.g. mainnet, `alt='1'`) that reuses the same address definition (`ADDR` derived identically since `chash160` is network-independent) and contains oscript logic such as `if (is_valid_signed_package(trigger.data.signed_package, 'ADDR')) { payment... }`.
3. Attacker submits `trigger.data.signed_package = objSignedMessage` (captured from network A) as trigger data to the mainnet AA.
4. `formula/evaluation.js`'s `is_valid_signed_package` case calls `signed_message.validateSignedMessage`, which never checks any network marker, verifies the signature successfully (since the hash-to-sign never included `alt`), and returns `true`, causing the AA to execute its funds-releasing branch despite the signature never having been intended for network B.
