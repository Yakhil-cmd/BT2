### Title
Private-asset payment secrets (blinding factors, amounts, spend proofs) written to plaintext console/disk logs - ([File: indivisible_asset.js])

### Summary
The reported CVE (CVE-2016-9882) is a class of bug where a system logs secret/credential values that should remain confidential, and those logs are persisted to disk and often forwarded to log aggregators, exposing the secrets to anyone with log access. In `ocore`, the analogous defect is in the private (indivisible-asset) payment validation and persistence path in `indivisible_asset.js`, where the confidential elements of a private-payment chain — the output `blinding` factor, `amount`, `address`, and the derived `spend_proof` — are written verbatim to the process logs via `console.log`.

### Finding Description
`validatePrivatePayment` computes a `spend_proof` from the previous hidden output's secret fields and then logs the full plaintext of those fields: [1](#0-0) 

Later, when the whole chain is accepted, `validateAndSavePrivatePaymentChain` logs the entire array of private elements (which contains every output's `address` and `blinding`) and also logs each output object individually: [2](#0-1) [3](#0-2) 

For hidden/private outputs of an indivisible asset, the security model relies on the `blinding` value and `amount` being known only to the payer and payee; the `output_hash` published on-chain is a commitment (`hash(address, amount, blinding)`), and the `spend_proof` is a hash over `{asset, unit, message_index, output_index, address, amount, blinding}` (or `serial_number` for issuance) as seen in the code above. Anyone who learns `address`, `amount`, and `blinding` for an unspent hidden output can recompute the same `spend_proof` and reconstruct a spendable private-payment chain, because these are exactly the fields `validatePrivatePayment` checks against (lines 111-133) and exactly what gets inserted into `outputs`/`inputs` when a payment is accepted.

This validation and logging path is reached whenever any private-payment counterparty (i.e., anyone who receives or sends a private/indivisible-asset payment) sends the private chain for validation, since `validatePrivatePayment` and `validateAndSavePrivatePaymentChain` execute on that data without any special privilege. Anywhere these logs are written to disk (default `console.log`) and later aggregated, shipped, or inadvertently exposed (e.g., crash reports, log shipping, support bundles), the secret blinding factors are disclosed — the same failure mode as CVE-2016-9882, where credentials returned from service brokers ended up in disk logs and syslog aggregators.

### Impact Explanation
Exposure of the `blinding` and `amount` values for a hidden output breaks the confidentiality guarantee of Byteball/Obyte's private (indivisible) asset scheme. Anyone obtaining these logged secrets (through log aggregation, crash reporting, backups, or a compromised log pipeline) gains everything needed to construct a valid `spend_proof` for that output and thus spend it — potentially in parallel with the legitimate holder, resulting in a double-spend of a private-asset output, or unauthorized disclosure/spending of funds that were intended to remain confidential between the payer and payee. This aligns with the "unauthorized spending" / "double-spend of a stable output" impact categories.

### Likelihood Explanation
This is triggered automatically and unconditionally on the normal flow of validating and saving any private-payment chain — no malicious or privileged action is required beyond the ordinary act of sending/receiving a private payment, which is a normal, unprivileged wallet operation. The likelihood of a log line actually leaking depends on deployment/log-handling practices (same caveat as the original CVE, where the risk materializes when logs reach a syslog/log aggregator), but the sensitive data is written to the log stream on every private-payment validation regardless of configuration.

### Recommendation
Remove or redact the `console.log` statements in `indivisible_asset.js` that print `blinding`, `amount`, `address`, and computed `spend_proof` inputs (lines 125-133, 243, and 272). Replace with non-sensitive debug identifiers (e.g., unit hash and message/output index only), and audit other private-payment code paths (e.g., `divisible_asset.js`, `private_profile.js`) for similar logging of secret payment fields.

### Proof of Concept
1. Any two wallets perform a private (indivisible-asset) payment; the private chain (containing `address`, `amount`, `blinding`) is sent to a peer/hub node for validation via `validatePrivatePayment`/`validateAndSavePrivatePaymentChain`.
2. On that node, the process log records the full plaintext secret fields, e.g.:
   `"validation spend proof: "+JSON.stringify({asset, unit, message_index, output_index, address, amount, blinding})`
   and
   `"saving private chain "+JSON.stringify(arrPrivateElements)`.
3. If these logs are persisted to disk and forwarded to any external log aggregation/monitoring system (as is common for production nodes), an operator of that logging infrastructure — who is not a party to the original private payment — can extract `address`, `amount`, and `blinding`, recompute the identical `spend_proof`, and submit a conflicting spend of the same hidden output, causing a double-spend / unauthorized use of funds that were meant to be confidential between the original two parties.
