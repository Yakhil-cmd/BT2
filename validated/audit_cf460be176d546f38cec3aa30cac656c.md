### Title
Fork-controlled `machine.environment.BUNDLE_PATH` in `shipit.yml` overrides Shipit's hardcoded `BUNDLE_PATH` before `bundle install` - (File: lib/shipit/task_commands.rb)

### Summary
`TaskCommands#env` builds the environment hash for every task/deploy command, including the `bundle install` step. It sets a hardcoded, safe `BUNDLE_PATH` early in the chain but then merges `deploy_spec.machine_env` — which is the unfiltered `machine.environment` section of the review stack's `shipit.yml` — afterward, letting a later key win. Since a review stack's branch and `shipit.yml` are fully controlled by the fork PR author, the attacker can set `BUNDLE_PATH` to redirect `bundle install`/`bundle` to a directory they populate with malicious gems that execute on load.

### Finding Description
The broken binding: the code intends `command.env['BUNDLE_PATH'] == Rails.root.join('data', 'bundler').to_s` (the fixed, safe vendor path) for every task, but in reality `command.env['BUNDLE_PATH'] == deploy_spec.machine_env['BUNDLE_PATH']` whenever the fork's `shipit.yml` defines that key, because it is merged after the hardcoded default.

Concretely, in `TaskCommands#env`: [1](#0-0) 
the hash chain is `super.merge(@stack.env).merge({ ..., 'BUNDLE_PATH' => Rails.root.join('data','bundler').to_s, ... }).merge(deploy_spec.machine_env).merge(@task.env)`. Ruby's `Hash#merge` gives precedence to the argument's keys, so `deploy_spec.machine_env`'s `BUNDLE_PATH` — merged in *after* the hardcoded default — silently overrides it.

`DeploySpec#machine_env` is defined as: [2](#0-1) 
which returns `config('machine', 'environment')` verbatim — the raw, unfiltered content of the `machine.environment` key from the checked-out `shipit.yml`, with no whitelist (unlike `filter_deploy_envs`/`filter_rollback_envs`, which do call `EnvironmentVariables#permit` against declared variable definitions). `DeploySpec::FileSystem` does not override `machine_env`; it only overrides `discover_machine_env` (used solely inside `cacheable_config`, a different code path used for spec serialization/caching, not for `TaskCommands#env`): [3](#0-2) 

For a review stack, the branch whose `shipit.yml` is loaded is the fork PR's head ref, entirely attacker-controlled: [4](#0-3) 
and stack creation is triggered by an unauthenticated `pull_request` `opened` webhook (subject only to signature verification and the repo's provisioning policy, not to any authorization of the PR author): [5](#0-4) 

Once the resulting `BUNDLE_PATH` is set in `Command#env`, it flows directly into the spawned subprocess, since `Command#unbundled_env` merges the instance's `@env` last (highest precedence) over `BASE_ENV`: [6](#0-5) 
and `Command#start` passes this merged environment to `PTY.spawn`: [7](#0-6) 

The `bundle install` step itself is generated by `BundlerDiscovery#bundle_install` and run via `TaskCommands#install_dependencies`, which uses the same `env: [8](#0-7) 
so the attacker-controlled `BUNDLE_PATH` is present for the exact `bundle install` subprocess.

No existing guard intercepts this: `filter_deploy_envs`/`filter_rollback_envs`/`EnvironmentVariables#permit` are only applied to deploy/rollback *variables* supplied via the API (`@task.env`), not to `machine.environment` from `shipit.yml`; `machine_env` is documented as intentionally free-form ("machine.environment contains the extra environment variables that you want to provide during task execution").

### Impact Explanation
An attacker who can open a pull request against a repository with review stacks enabled can commit a `shipit.yml` on their fork branch containing:
```yaml
machine:
  environment:
    BUNDLE_PATH: /tmp/evil-bundle
```
along with a vendored gem tree (also committed in the PR branch or fetched by an `extconf.rb`/gem `Rakefile` hook) at that path. When the review stack's dependency step (`bundle install`) runs, `bundle` operates against `BUNDLE_PATH=/tmp/evil-bundle`. Malicious gem install hooks (`extconf.rb`, native extension `Rakefile`) execute arbitrary Ruby/shell code on the Shipit deploy host during `bundle install`, or a poisoned `bundle config`/subsequent `bundle exec` step loads attacker-controlled gem code. This is Remote Code Execution on the deploy host, matching the Critical class (RCE via `Command`/`PTY.spawn`). Because review stacks are created per attacker-controlled PR/branch and the deploy host is typically shared across the org's stacks, this is repeatable against any repository with review stacks enabled and represents full compromise of the deploy host, not limited to a single tenant's stack.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`review_stacks_enabled`) with a provisioning policy that doesn't require a trusted maintainer action (e.g., `allow_all`, or `allow_with_label`/`prevent_with_label` where the attacker can add/omit their own label on their own PR). No Shipit session, API token, or GitHub secret is required — only the ability to open a PR from a fork, which is available to any GitHub user against a public repository with these settings. Cost is a single PR; the exploit is fully repeatable and works against every review-stack-enabled repository sharing this behavior.

### Recommendation
In `TaskCommands#env`, merge `deploy_spec.machine_env` before the hardcoded/security-sensitive keys (or explicitly re-apply `'BUNDLE_PATH' => Rails.root.join('data', 'bundler').to_s` after merging `machine_env`), so untrusted `shipit.yml` content cannot override it. More generally, sanitize `machine_env` through an explicit key denylist/allowlist (at minimum reject `BUNDLE_PATH`, `BUNDLE_GEMFILE`, `GEM_HOME`, `GEM_PATH`, `RUBYOPT`, `LD_PRELOAD`, `PATH`) before merging it into the task's command environment, consistent with how `filter_deploy_envs`/`filter_rollback_envs` sanitize other user-configurable environment sources.

### Proof of Concept
minitest plan (add to `test/lib/shipit/task_commands_test.rb` or `test/unit/deploy_commands_test.rb`):
```ruby
test "#install_dependencies does not allow shipit.yml machine_env to override BUNDLE_PATH" do
  deploy_spec = stub(
    dependencies_steps!: ['bundle install --jobs 4 --retry 2'],
    machine_env: { 'BUNDLE_PATH' => '/tmp/evil-bundle' },
    directory: nil,
    clear_working_directory?: true
  )
  commands = TaskCommands.new(some_task)
  commands.stubs(:deploy_spec).returns(deploy_spec)

  command = commands.install_dependencies.first

  # Binding under test: BUNDLE_PATH must remain Shipit's safe default, not the attacker's value
  assert_equal Rails.root.join('data', 'bundler').to_s, command.env['BUNDLE_PATH']
  refute_equal '/tmp/evil-bundle', command.env['BUNDLE_PATH']

  # Confirm what actually reaches the spawned process via Command#unbundled_env
  assert_equal Rails.root.join('data', 'bundler').to_s, command.unbundled_env['BUNDLE_PATH']
end
```
Running this against current code fails: `command.env['BUNDLE_PATH']` and `command.unbundled_env['BUNDLE_PATH']` equal `'/tmp/evil-bundle'`, confirming the fork-controlled override reaches the `bundle install` subprocess environment.
