## Title
Stack-scoped API token can read any stack's CI status via CCMenu XML endpoint — (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

## Summary
`Shipit::Api::CCMenuController#stack` overrides `BaseController#stack` and resolves the requested stack directly via `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!(params[:stack_id])` used everywhere else. Combined with `require_permission :read, :stack`, which only checks the permission string via `ApiClient#check_permissions!`, a token that is scoped to one stack (`stack_id` column set) can read the CCMenu XML — including latest deploy/rollback status and lock state — for any other stack in the installation.

## Finding Description
The intended binding is: `current_api_client.stack_id == requested_stack.id` whenever `current_api_client.stack_id?` is true. This is enforced in `BaseController#stacks`: [1](#0-0) 

`stacks` restricts the resolvable set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` (the private helper used by `StacksController`, `LocksController`, `HooksController`) calls `stacks.from_param!`, enforcing the binding.

`CCMenuController`, however, defines its own `stack` method that bypasses this scoping entirely: [2](#0-1) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which checks the string `"read:stack"` against `permissions` and has no notion of `stack_id`: [3](#0-2) 

`CCMenuUrlController#fetch` creates exactly this kind of stack-agnostic-permission-but-stack-scoped-by-intent client: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)`, and its token is embedded in the CCMenu URL for a specific stack: [4](#0-3) 

Attack: the attacker legitimately obtains (via UI/`CCMenuUrlController#fetch` for a stack they can access, e.g. stack X) a token with permission `read:stack`. They then send `GET /api/:stack_id/cc.xml?token=<token>` with `stack_id` set to an arbitrary stack Y's param. `authenticate_api_client` (the CCMenu-specific override) authenticates the token successfully via `ApiClient.authenticate`, `require_permission` passes since the token has `read:stack`, and `stack` resolves Y directly with no scoping check, rendering Y's deploy/lock/CI status.

Existing guards do not prevent this: `verify_signature`/webhook checks are irrelevant here (this is a token-authenticated GET, not a webhook), `ExplicitParameters` does not scope `stack_id`, and the only scoping mechanism (`BaseController#stacks`) is explicitly not used by this controller's overridden `stack` method.

Note the test suite includes a directly analogous regression test for `StacksController#index` — "an api client scoped to a stack will only see that one stack" — confirming the scoping is intentional and expected elsewhere, but `CCMenuController` was not written to honor it: [5](#0-4) 

## Impact Explanation
An attacker who holds a legitimately-issued, stack-scoped `read:stack` token (e.g., their own CCMenu URL) can read the CI/deploy status (latest deploy/rollback, running state, lock state) of any other stack in the same Shipit instance by simply changing the `stack_id` route/query parameter — no additional secret or privilege needed for the target stack. This is an unauthenticated-adjacent (cross-tenant) read of stack state, matching the "High" impact category (unauthenticated read of stack state). It is fully repeatable against any stack ID/slug in the instance, for as long as the attacker holds any valid CCMenu token.

## Likelihood Explanation
The attacker only needs one legitimately obtained stack-scoped `read:stack` token (trivially obtainable if they have access to any single stack's Settings page, since `CCMenuUrlController#fetch` requires only `current_user` session, not admin/team elevation) and knowledge/guess of another stack's `to_param` (owner/repo/environment, often discoverable or guessable). No GitHub secrets, no `api_clients_secret`, and no privileged role are required beyond having a valid session to mint the initial token. This is low-cost and fully reproducible.

## Recommendation
Change `CCMenuController#stack` to use the scoped `stacks` helper instead of resolving directly against `Stack`, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, mirroring `BaseController#stack`. This ensures the `current_api_client.stack_id` scoping check is applied for CCMenu access just as it is for `StacksController`, `LocksController`, and `HooksController`.

## Proof of Concept
Minitest plan in `test/controllers/api/ccmenu_controller_test.rb` (existing suite already covers this controller):

```ruby
test "a token scoped to one stack cannot read another stack's cc.xml" do
  other_stack = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')
  scoped_client = ApiClient.create!(
    creator: @user,
    name: 'Scoped CCMenu client',
    stack_id: @stack.id,
    permissions: %w[read:stack]
  )

  get :show, params: { stack_id: other_stack.to_param, token: scoped_client.authentication_token }

  # Binding under test: scoped_client.stack_id (== @stack.id) must equal the stack actually served.
  assert_not_equal scoped_client.stack_id, other_stack.id
  assert_response :forbidden # currently fails: returns :ok with other_stack's XML
end
```
This asserts the `stack_id` binding explicitly and demonstrates that, prior to the fix, the request returns `200 OK` with `other_stack`'s deploy XML instead of being rejected.
