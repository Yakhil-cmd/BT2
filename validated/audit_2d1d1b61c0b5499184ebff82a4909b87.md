## Confirmed vulnerability found

### Title
Webhook signature is verified against the org derived from `repository.owner.login`, while all event handlers act on the repository derived from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/webhook secret to validate a webhook against using `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, then verifies the raw body's HMAC with that org's secret. Once verification passes, every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) determines the *target* repository/stack using a **different** field of the same JSON body: `payload.dig('repository', 'full_name')`. Nothing enforces that `repository.full_name` actually belongs to `repository.owner.login`.

### Finding Description [1](#0-0) 

`verify_signature` resolves the signing organization purely from the JSON body content and uses `Shipit.github(organization: repository_owner)` to obtain that organization's configured `webhook_secret`, then HMAC-verifies the raw POST body against it: [2](#0-1) 

Handlers, however, never look at `repository.owner.login`. They resolve the affected repository/stack from `repository.full_name`: [3](#0-2) [4](#0-3) [5](#0-4) 

The equality that is *implicitly assumed but never enforced* is: `owner used to pick the verifying secret == owner of the repository the handler actually mutates`. Since both `repository.owner.login` and `repository.full_name` are independent strings inside the same attacker-influenced JSON body, an operator of a multi-tenant Shipit instance who legitimately owns/administers one onboarded GitHub organization (and therefore knows or can trigger requests signed with that organization's `webhook_secret`) can submit a webhook whose `repository.owner.login` is their own org (so the correct secret is chosen and verification succeeds) but whose `repository.full_name` names a *different* organization's repository that is also tracked by the same Shipit instance. The signature check only proves body integrity relative to the org named in `repository.owner.login` — it proves nothing about the org named in `repository.full_name`, which is what the handlers actually trust.

This maps to the required binding-break category: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Concretely, `StatusHandler` uses only `sha`/`state`/`branches` and matches by SHA across *all* tracked commits regardless of repository, and `commit.create_status_from_github!` will attach an attacker-controlled CI status (e.g. `state: "success"`) to a commit belonging to a repository/stack owned by a completely different, unrelated organization. If that victim stack has continuous delivery enabled, a forged `success` status can be the trigger that causes Shipit to autonomously deploy a commit — this is an unauthorized deploy of another organization's code path, driven entirely by a payload the attacker forged and self-signed with their own org's webhook secret. `PushHandler` similarly resyncs a victim stack (`stack.sync_github(expected_head_sha: params.after)`) chosen purely from `repository.full_name`, letting one tenant force GitHub-sync/queue activity against another tenant's stack. This satisfies the High/Critical impact bar of "escalation... or an unauthorized deploy" driven by a broken trust binding, not merely a best-practice nit.

### Likelihood Explanation
Likelihood is High in a multi-organization Shipit deployment: any onboarded organization admin (an "unprivileged attacker" relative to other tenants) who knows/controls their own org's webhook delivery (which GitHub signs with the configured secret for their installation) can craft a POST body where `repository.owner.login` names their own org while `repository.full_name` names any other tracked repository, then deliver it (replay or directly, since `/webhooks` is a public unauthenticated endpoint gated only by this signature check). No cross-org secret knowledge, no GitHub App private key, and no Shipit session is required — exactly the credential/repository boundary crossing this scan is scoped to.

### Recommendation
Enforce that the two identity fields agree before dispatching to any handler: after resolving `repository_owner` and verifying the signature, also validate that `payload.dig('repository', 'full_name')` (and/or `organization.login` for org-scoped events) is consistent with `repository_owner`/the app installation that produced the signature, rejecting (422) any webhook where they diverge. Alternatively, resolve the repository/stack to act on using the same authenticated `repository_owner` value (not a second, independently-supplied field) so the value that authorizes the request is the same value that is written.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`, onboarded to a shared/multi-tenant Shipit instance, and can produce (or capture/replay) a webhook POST correctly signed with `attacker-org`'s configured `webhook_secret`.
2. Attacker crafts (or has GitHub deliver, then modifies fields that aren't part of what they need to forge, since they know the secret and can self-sign) a `status` event body:
```json
{
  "sha": "<victim commit sha tracked by Shipit>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_of_attacker-org, body)` and POSTs to `/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` reads `repository_owner = "attacker-org"`, fetches `attacker-org`'s webhook secret, and the HMAC matches → verification passes (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), attaching a forged `success` status to the victim's commit — with no check that the commit belongs to `attacker-org`.
6. If `victim-org/victim-repo`'s stack has continuous delivery enabled, this forged status can trigger an automatic deploy of that commit for an organization the attacker has no access to.
