### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but every event handler acts on the repository named in `repository.full_name` — allowing cross-organization webhook forgery in multi-app deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to check the HMAC against using `repository_owner` (`repository.owner.login` or `organization.login`), while every `Shipit::Webhooks::Handlers::Handler` subclass resolves the repository/stack to act on using a *different* field of the same payload: `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`). Nothing ties these two payload fields together, so the "organization that authenticated" and the "repository that is written" are never checked for consistency.

### Finding Description
`Shipit.github(organization:)` (`lib/shipit.rb:170-181`) supports per-organization GitHub Apps, each with its own independently configured `webhook_secret` (`lib/shipit/github_app.rb:44-57`, illustrated by `test/dummy/config/secrets_double_github_app.yml`). `WebhooksController#verify_signature` does: [1](#0-0) 

using `repository_owner`: [2](#0-1) 

Critically, `GitHubApp#verify_webhook_signature` treats an organization with no configured `webhook_secret` as automatically verified: [3](#0-2) 

Meanwhile, the actual repository acted upon by every handler is derived from a *different* JSON field, `repository.full_name`, with no cross-check against `repository.owner.login`: [4](#0-3) 

In a multi-org install where at least one configured organization has no `webhook_secret` set (this is documented as "optional" in `docs/setup.md`), an attacker can submit an unsigned/arbitrarily-signed webhook with `repository.owner.login` set to that unsecured org while setting `repository.full_name` to any *other* tracked organization/repository's full name. `verify_signature` will select the unsecured org's `GitHubApp`, which short-circuits verification (`return true unless webhook_secret`), and the request passes with a 200. The `PushHandler`, `CheckSuiteHandler`, `MembershipHandler`, and all `PullRequest::*Handler`s then act on the spoofed `repository.full_name`/`organization.login`, e.g. queuing `stack.sync_github`, creating/removing `Team`/`Membership` records, or archiving/unarchiving review stacks for a repository/org that was never the one whose signature was actually checked: [5](#0-4) 

This is the direct analog of the reported bug class: a verification step (the ERC20 boolean-return check / here, the HMAC signature check) is bound to one piece of data (`repository.owner.login`), while the state-changing operation is bound to a different, unchecked piece of data (`repository.full_name`) from the same untrusted input — breaking the equality `verified_org == acted_upon_repo_owner`.

### Impact Explanation
Team/membership webhooks are especially significant: `MembershipHandler` creates `Team` and `Membership` records that directly feed `User#authorized?` (`app/models/shipit/user.rb:80-82`) and `Shipit::Authentication#force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:20-34`), which gate access to the entire application. An attacker who can get *any* unsecured/insecurely-secreted organization accepted by `verify_signature` could forge `membership` events claiming to originate from a *different, trusted* organization's team, adding an arbitrary GitHub login to a privileged team and escalating into `Shipit.github_teams` authorization — matching the High-impact criterion in scope. `push`/`pull_request`/`check_suite` forgery can also trigger unwanted syncs and review-stack lifecycle changes (archive/unarchive) against real, unrelated stacks.

### Likelihood Explanation
Requires: (a) the target Shipit instance to be configured with multiple GitHub Apps/organizations (a documented, supported configuration — `docs/setup.md` "Using Multiple Github Applications"), and (b) at least one configured organization to have no `webhook_secret` set (also explicitly documented as "optional"). Given both are supported, documented configurations rather than misuse of the engine, an unprivileged external attacker (no Shipit session, no API token, no repo write access) can send a single crafted HTTP POST to `/webhooks` to exploit this — satisfying the "unprivileged attacker" and "no credential" requirements.

### Recommendation
After computing `repository_owner`, verify handlers only ever act on repositories whose owner matches the organization the signature was verified against — i.e., cross-check that `payload.dig('repository','full_name')`'s owner segment equals `repository_owner` (and reject if the app is configured without a `webhook_secret` for that org, or require a `webhook_secret` to be mandatory rather than optional in multi-app setups). At minimum, `verify_webhook_signature` should not silently succeed when `webhook_secret` is blank in a multi-organization configuration.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `OrgOne` (has stacks/teams Shipit trusts, `webhook_secret` set) and `OrgTwo` (installed but with `webhook_secret` left blank, as in `test/dummy/config/secrets_double_github_app.yml`).
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "OrgTwo" },
  "team": { "id": <id-of-a-team-belonging-to-OrgOne>, "slug": "developers", "name": "Developers", "url": "https://example.com" },
  "member": { "login": "attacker-controlled-login" },
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/some-repo" }
}
```
No valid `X-Hub-Signature` is required, because `Shipit.github(organization: 'OrgTwo').verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
3. `verify_signature` passes (200/`head(:ok)` path), and `MembershipHandler` processes the event against the `OrgOne` team referenced by `team.id`, adding `attacker-controlled-login` as a member — despite the request never being authenticated by `OrgOne`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
