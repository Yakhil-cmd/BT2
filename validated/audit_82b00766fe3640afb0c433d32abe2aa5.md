## Analog Found

### Title
Unbounded `eventBus` listener/closure leak on queued private payment chains causes wallet memory exhaustion - (File: `wallet.js`)

### Summary
`handlePrivatePaymentChains()` in `wallet.js` registers a one-shot `eventBus` listener for every private-payment element that cannot be immediately validated (the `ifQueued` case), but never removes that listener if the awaited validation event is never emitted. A private-payment counterparty (or any paired device) can repeatedly send private chains that fall into the "queued" branch and are never resolved, causing permanent accumulation of listeners and their captured closures — an unbounded memory leak analogous to the QEMU `serial_exit_core` leak (CVE-2017-5579), where repeated unplug operations leaked memory because cleanup never ran.

### Finding Description
When a device sends private payment chains via `handlePrivatePaymentChains(ws, body, from_address, callbacks)`, each chain element is validated with `network.handleOnlinePrivatePayment`. If the wallet cannot validate immediately (typical for light clients waiting on a dependency), the `ifQueued` callback fires and registers: [1](#0-0) 

```
ifQueued: function(){
    console.log("handleOnlinePrivatePayment queued, will wait for "+key);
    eventBus.once(key, function(bValid){
        if (!bValid)
            return cancelAllKeys();
        assocValidatedByKey[key] = true;
        ...
    });
    cb();
}
```

The `key` is derived from attacker-controlled data (`unit`, `payload_hash`, `output_index`) computed per chain element: [2](#0-1) 

The only cleanup path is `cancelAllKeys()`, which calls `eventBus.removeAllListeners(key)` for every key in `assocValidatedByKey`: [3](#0-2) 

`cancelAllKeys()` is invoked only if the overall chain-validation series errors out, or if the specific `key` event later fires with `bValid === false`. If the referenced unit/dependency is never delivered or validated (e.g. the counterparty never forwards the underlying joint, or crafts chains that reference units that will never resolve), the `key` event is never emitted, `cancelAllKeys` is never called, and the `eventBus.once(key, ...)` listener — along with its closure over `assocValidatedByKey`, `arrChains`, `from_address`, `body`, etc. — stays registered on the shared `eventBus` singleton forever.

Because `key` is generated from attacker-supplied `unit`/`payload_hash`/`output_index` values, an unprivileged private-payment counterparty can generate an unbounded number of distinct, never-resolving keys, each producing a permanent listener + retained closure. This is directly analogous to the QEMU bug class: a normal, repeatable protocol operation (posting private payment chains / device unplug) that should release resources on completion but instead leaks memory when the completion event never arrives, letting a remote peer exhaust the host's memory and crash the process — matching the "device unplug ⇒ memory leak ⇒ host memory consumption and process crash" pattern in the original CVE.

I was not able to fully trace, within the current search budget, every code path that emits the `key` event (`'private_payment_validated-...'`) to confirm there is no other implicit cleanup mechanism (e.g. a timeout elsewhere); this should be verified before treating the analog as fully confirmed.

### Impact Explanation
Each unresolved queued private payment leaves a dangling `eventBus.once` listener with a retained closure (including `assocValidatedByKey`, `arrChains` and other chain data). Repeated posting of such chains by a correspondent/paired device grows Node's `EventEmitter` listener list and retained heap objects without bound, degrading performance and eventually causing an out-of-memory crash of the wallet/hub process — a denial of service against the node handling private payments, consistent with the "memory consumption and process crash" impact described in the CVE.

### Likelihood Explanation
The trigger requires only sending private-payment chain messages (`handlePrivatePaymentChains`) that are validated as *queued* rather than immediately accepted/rejected, and ensuring the awaited unit/dependency never resolves — both achievable by a private-payment counterparty or paired device without needing elevated privileges, node/hub cooperation, or race conditions. Repeating this cheaply (many crafted chains with unique unit/payload_hash/output_index combinations) scales the leak linearly with attacker effort.

### Recommendation
Add a timeout/TTL to each `eventBus.once(key, ...)` registration in `handlePrivatePaymentChains`, removing the listener (and its `assocValidatedByKey` entry) if the corresponding validation event has not fired within a bounded window, mirroring the way `assocUnitsWaitingForPrunedContent` and `handledChainsCache` are periodically purged elsewhere in the codebase (see the `purgeExpiredCachedPrunedJoints` / `handledChainsCache` cleanup patterns in `archiving.js` and `wallet.js`).

### Proof of Concept
1. As a paired device or private-payment counterparty, craft a `private_payments` message with `chains` referencing a `unit` whose dependency will never be delivered/resolved by the receiving wallet (e.g., a unit that is withheld or never broadcast).
2. Send it via `handle_message_from_hub` → `handlePrivatePaymentChains(ws, body, from_address, callbacks)`; the light-client validation path returns `ifQueued`, registering `eventBus.once(key, ...)`.
3. Never deliver the dependency; the `key` event never fires, so `cancelAllKeys()` is never invoked and the listener persists indefinitely.
4. Repeat with new `unit`/`payload_hash`/`output_index` combinations to generate unlimited distinct keys, growing `eventBus`'s listener count and retained closures without bound until the victim process runs out of memory. [4](#0-3)
