### Title
Missing Token Registration/Lock Validity Check in Bridge Handle Functions — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`, `BridgeTransferKLAY.sol`)

---

### Summary

The Kaia service-chain bridge enforces token registration and lock status when a user **requests** a value transfer, but omits those same checks when bridge operators **handle** (complete) the transfer on the counterpart chain. If the bridge owner deregisters or locks a token after a request is emitted but before operators process it, operators can still mint or transfer tokens for the now-invalid token, bypassing the owner's intent and breaking the protocol invariant.

---

### Finding Description

`_requestERC20Transfer` (the user-facing entry point) is guarded by two modifiers from `BridgeTokens`:

```solidity
// BridgeTransferERC20.sol lines 84-86
internal
onlyRegisteredToken(_tokenAddress)
onlyUnlockedToken(_tokenAddress)
```

It also requires `isRunning`. These guards enforce that only registered, unlocked tokens can be bridged while the bridge is active.

`handleERC20Transfer` (the operator-facing completion function) carries **only** `onlyOperators`:

```solidity
// BridgeTransferERC20.sol lines 42-43
public
onlyOperators
```

No `onlyRegisteredToken`, no `onlyUnlockedToken`, no `isRunning` check. The same asymmetry exists in `handleERC721Transfer` (lines 40–41 of `BridgeTransferERC721.sol`) and `handleKLAYTransfer` (lines 71–73 of `BridgeTransferKLAY.sol`, which lacks `unlockedKLAY` and `isRunning`).

The off-chain bridge manager (`node/sc/bridge_manager.go`, `handleRequestValueTransferEvent`) automatically calls `HandleERC20Transfer` / `HandleERC721Transfer` for every pending `RequestValueTransfer` event it observes, without re-checking whether the token is still registered or unlocked on the destination bridge.

**Attack / failure scenario:**

1. User calls `requestERC20Transfer` for token T on chain A. Token T is registered and unlocked — the call succeeds and emits `RequestValueTransfer`.
2. Bridge owner discovers a problem with token T and calls `deregisterToken(T)` (or `lockToken(T)`) on the chain-B bridge to halt further transfers.
3. The automated operator relayer observes the pending event from step 1 and calls `handleERC20Transfer(..., T, ...)` on chain B.
4. Because `handleERC20Transfer` has no `onlyRegisteredToken` guard, the call succeeds.
5. In `modeMintBurn` mode the bridge mints `_value` tokens of T to the recipient — **unauthorized minting of a deregistered bridged asset**. In lock-transfer mode the bridge transfers T from its own reserves — **unauthorized transfer of a deregistered bridged asset**.

---

### Impact Explanation

- **`modeMintBurn = true`**: Operators can mint an arbitrary amount of a deregistered ERC-20 or ERC-721 token, inflating its supply without authorization. This is an unauthorized mint of a bridged asset.
- **`modeMintBurn = false`**: Operators can drain the bridge's token reserves for a deregistered token, transferring assets to recipients the owner intended to block.
- In both cases the bridge owner's explicit deregistration/lock action is silently bypassed, corrupting the protected asset accounting of the bridge.

---

### Likelihood Explanation

The trigger requires the bridge owner to deregister or lock a token while there are in-flight (pending) transfer requests. This is a realistic operational scenario — emergency deregistration due to a token exploit or regulatory action is a common reason to lock a token. The automated operator relayer (`bridge_manager.go`) will unconditionally process all pending events, making the bypass automatic rather than requiring deliberate operator misconduct.

---

### Recommendation

Add the same guards to the handle functions that exist on the request functions:

```solidity
function handleERC20Transfer(...) public onlyOperators onlyRegisteredToken(_tokenAddress) onlyUnlockedToken(_tokenAddress) {
    require(isRunning, "stopped bridge");
    ...
}

function handleERC721Transfer(...) public onlyOperators onlyRegisteredToken(_tokenAddress) onlyUnlockedToken(_tokenAddress) {
    require(isRunning, "stopped bridge");
    ...
}

function handleKLAYTransfer(...) public onlyOperators unlockedKLAY nonReentrant {
    require(isRunning, "stopped bridge");
    ...
}
```

---

### Proof of Concept

1. Deploy bridge on chain A and chain B with `modeMintBurn = true`. Register token T on both bridges.
2. Alice calls `requestERC20Transfer(T, bob, 1000, ...)` on chain A. `RequestValueTransfer` event is emitted with `requestNonce = 0`.
3. Bridge owner calls `deregisterToken(T)` on chain B (emergency halt).
4. Operator calls `handleERC20Transfer(txHash, alice, bob, T, 1000, 0, blockNum, "")` on chain B.
5. The call succeeds (only `onlyOperators` is checked). `ERC20Mintable(T).mint(bob, 1000)` executes, minting 1000 tokens of the deregistered token T to Bob.

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}
