### Title
Cross-organization webhook forgery via secret-selection field not bound to the acted-upon repository field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate a webhook against using a field taken directly from the *unauthenticated* request body (`repository.owner.login`, falling back to `organization.login`), while the handlers that act on the payload (creating statuses, syncing stacks, etc.) resolve the target repository/stack from a *different* payload field, `repository.full_name`. Because both fields live in the same attacker-controlled JSON body, the field used to pick the authenticating secret is not cryptographically bound to the field used to select what gets written to.

### Finding Description
In a multi-organization Shipit deployment (`Shipit.github_organizations` / `github_app_config`, `lib/shipit.rb` lines 190-200), each onboarded GitHub organization has its own `webhook_secret` configured via `Shipit.github(organization: ...)`.

`verify_signature` determines which organization's secret to verify the HMAC against by reading it straight out of the untrusted payload: [1](#0-0) [2](#0-1) 

Meanwhile, every handler (`PushHandler`, `StatusHandler`, etc.) resolves which `Repository`/`Stack` the event applies to from an *independent* payload field, `repository.full_name`, via the shared base class: [3](#0-2) 

The HMAC (`verify_webhook_signature`, `lib/shipit/github_app.rb` lines 76-83) proves only that the byte string was signed with *some* organization's secret — specifically the secret for whatever organization the attacker names in `repository.owner.login`/`organization.login`. It proves nothing about which `repository.full_name` the same payload claims to target. An org owner who has legitimately onboarded their own organization into this same multi-tenant Shipit instance therefore knows their own valid `webhook_secret` and can sign an arbitrary payload with it, while setting `repository.full_name` to any other tracked repository/stack in the instance (e.g. `victim-org/victim-repo`).

This breaks the intended binding:
`organization authenticated (repository.owner.login → webhook_secret) == repository actually acted upon (repository.full_name → Stack)`

### Impact Explanation
The clearest concrete exploitation is via `StatusHandler`: [4](#0-3) 
This writes a `Status` for *any* `Commit` matching an attacker-chosen `sha`, independent of which organization actually owns that commit's stack — the handler never re-derives or checks `repository.full_name`/owner consistency for `StatusHandler` (it only matches by `sha`, which is global across the `commits` table). Since deploy/merge gating in Shipit is driven by required CI statuses (`Stack#required_statuses`/`Commit#deployable?` per `app/models/shipit/stack.rb`, `app/models/shipit/commit.rb`), an attacker who legitimately signs with their own org's webhook secret can inject a forged "success" status for a commit belonging to a *victim* organization's stack, potentially satisfying CI requirements that gate an otherwise-blocked deploy — an unauthorized deploy through data poisoning of a trust signal the deploy pipeline relies on. Other handlers keyed on `repository.full_name` (e.g. `PushHandler`) similarly act on whichever repository/stack the forged field names, regardless of which org's secret validated the request.

This requires a multi-organization Shipit configuration (`github_default_organization` present with multiple `secrets.github` entries); in the common single-org configuration the same secret is used for all webhooks so the cross-org binding does not exist and there is no crossing of a trust boundary.

### Likelihood Explanation
Requires the operator to run Shipit with more than one onboarded GitHub organization (each with a distinct `webhook_secret`) tracking stacks/repos in the same instance — a supported, documented configuration (`lib/shipit.rb` `github_app_config`). The attacker only needs to be able to configure/administer their own already-onboarded organization's GitHub webhook (something a legitimate tenant org owner already can do) — no Shipit session, `ApiClient` token, or repository write access to the victim repo is required, satisfying the unprivileged-attacker requirement.

### Recommendation
Bind the field used to select the verifying secret to the field used to determine the acted-upon repository. Concretely:
- After signature verification, re-derive the organization strictly from `repository.full_name`'s owner (or a repository→organization mapping already known to Shipit) and reject if it does not match the organization whose secret validated the signature.
- Alternatively, verify signatures against the secret owned by the `Repository` record matched by `repository.full_name` (looked up server-side) rather than trusting `repository.owner.login`/`organization.login` from the payload to pick the secret.

### Proof of Concept
1. Shipit instance is configured with two tenant organizations, `attacker-org` and `victim-org`, each with a distinct `webhook_secret` (`github_app_config`).
2. Attacker (owner of `attacker-org`) knows their own webhook secret `S_attacker` (they configured it when installing the GitHub App/webhook for their own org, a supported self-service action).
3. Attacker crafts a JSON body:
```json
{
  "organization": { "login": "attacker-org" },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<sha of a commit in victim-org/victim-repo's tracked stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(S_attacker, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`), which succeeds because it is the attacker's own valid secret — see: [1](#0-0) 
6. `StatusHandler#process` then updates the status for the commit belonging to `victim-org/victim-repo`, unaffected by the mismatched owner, potentially unblocking an unauthorized deploy for that stack: [4](#0-3) 

Note: I could not fully trace, within available tooling limits, the exact call path from a forged `Status` to a completed unauthorized deploy trigger (e.g. auto-deploy-on-green configuration) or confirm whether any additional per-stack repository ownership check exists elsewhere in the deploy-gating code that I did not locate; this should be verified with a running instance/full source before treating the impact as fully confirmed end-to-end.
