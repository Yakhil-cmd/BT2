Found a concrete, provable analog: the `socialize-debt-asset` bad-debt write-down path in `liquidate()` mutates a shared vault-wide index (`lindex`) based on state that is computed against amounts already consumed earlier in the same call, causing an incorrect write-down that is charged to every supplier of that vault — an unprivileged, uninvolved third party.

### Title
Bad-debt socialization write-down miscalculates `lindex` loss against post-repayment vault state, over/under-charging all vault suppliers - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar` / `local-testing/contracts/vault/vault-sbtc.clar`, function `socialize-debt`; driven by `mainnet/contracts/market/v0-4-market.clar` function `liquidate` / `socialize-debt-asset`)

### Summary
`liquidate()` first repays part of a borrower's debt via `vault-system-repay` (which already reduces `total-borrowed` and `assets`), then, if the borrower has no collateral left, calls `socialize-debt-asset` → `vault-socialize-debt` to write off the *remaining* (unrecoverable) scaled debt. `socialize-debt` computes the liquidity-index write-down using `old-total-assets` and `debt-reduction` read **after** the earlier repay already changed `total-borrowed`/`assets`, and separately computes `principal-reduction` from the vault's post-repay `borrowed`/`scaled-principal` ratio rather than from the pre-liquidation state that determined the actual bad-debt amount. This mirrors the `setWeight()` class of bug: a shared aggregate (`lindex`, `total-borrowed`, `assets` — used by every depositor's `total-assets-preview`/`convert-to-assets-preview`) is recomputed from an intermediate, already-mutated state rather than a consistent snapshot, so the loss allocated to all LPs of the vault does not match the actual bad debt being written off.

### Finding Description
In `mainnet/contracts/vault/v0-vault-sbtc.clar` (and the equivalent for every vault, e.g. `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`), `socialize-debt` is: [1](#0-0) 

It is called from `mainnet/contracts/market/v0-4-market.clar`'s `socialize-debt-asset`, itself invoked from `liquidate` only *after* `vault-system-repay` (repaying the liquidator-covered portion) and after `debt-remove-scaled`/`collateral-remove` for the liquidated collateral have already executed: [2](#0-1) [3](#0-2) 

By the time `socialize-debt` runs, `total-borrowed`, `assets`, and `principal-scaled` inside the vault already reflect the just-completed partial repayment for *this* liquidation. `socialize-debt` then derives:
- `principal-reduction = scaled-amount * borrowed / scaled-principal` — using the vault's post-repay `borrowed`/`scaled-principal` ratio, not the ratio that existed when the bad debt was actually accrued as unrecoverable.
- `new-lindex` — a proportional write-down of the liquidity index based on `old-total-assets` (read at the start of `socialize-debt`, itself already net of the repay) versus `debt-reduction`.

Because `total-borrowed` was already reduced by the specific liquidator's repayment moments earlier in the same transaction, the ratio `borrowed / scaled-principal` used for `principal-reduction` — and consequently the `assets` and `lindex` write-down applied to *every* zToken holder of that vault — no longer corresponds to a clean, atomic "before vs after this borrower's total obligation" comparison. This produces a write-down of `lindex` (and hence `total-assets`) that is not the exact size of the borrower's true unrecoverable debt, silently mis-socializing the loss across all liquidity providers of that vault (over- or under-charging them depending on rounding direction of `mul-div-down`), the same structural failure mode as `setWeight()` computing a shared aggregate against an intermediate/stale state rather than the state that should back the invariant.

### Impact Explanation
This is a "socialization charged to all suppliers" scenario: `lindex` directly determines `total-assets`/`convert-to-assets-preview` used by every depositor of the vault to redeem/value their zTokens. An incorrect write-down means unrelated, unprivileged suppliers either lose more value than the actual bad debt (temporary freezing/loss of their unclaimed yield/principal share) or the protocol under-recognizes the loss (insolvency risk building up in vault accounting), landing in "temporary freezing of funds" / "theft of unclaimed yield" for depositors who took no part in the liquidated position.

### Likelihood Explanation
This triggers on every liquidation that fully exhausts a borrower's collateral and leaves bad debt (`no-collateral-left` = true), which is a normal, frequent code path for undercollateralized positions during market stress — not a rare edge case, and requires no special privilege from the liquidator beyond calling the public `liquidate` function.

### Recommendation
Compute the bad-debt write-down (`principal-reduction`, `debt-reduction`, `new-lindex`) from a single consistent snapshot of vault state captured before any repayment/removal steps of the same liquidation are applied, or restructure `liquidate` to call `socialize-debt` before `vault-system-repay` mutates `total-borrowed`/`assets`, ensuring the loss allocated to LPs exactly matches the borrower's true unrecoverable debt.

### Proof of Concept
1. Borrower has debt fully backed by insufficient collateral; liquidator calls `liquidate()`.
2. `vault-system-repay` executes, reducing `total-borrowed`/`assets`/`principal-scaled` for the covered portion.
3. `no-collateral-left` is true; `socialize-debt-asset` → `vault-socialize-debt` runs with the vault's now-mutated `borrowed`/`scaled-principal`/`assets`, deriving `principal-reduction`/`new-lindex` from this intermediate ratio rather than the pre-repay state.
4. `lindex` is written down by an amount that does not equal the true bad-debt fraction of `old total-assets`, and every LP's `convert-to-assets-preview`/redemption value is skewed accordingly — confirmed by tracing [1](#0-0)  against the call ordering in [2](#0-1) .

Note: I was unable to fully trace the exact numerical direction/magnitude of the discrepancy (over- vs under-charge, and its bound) within the available exploration budget — this would benefit from a dedicated Devin session to write a concrete Clarinet/Vitest reproduction confirming the exact skew.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
