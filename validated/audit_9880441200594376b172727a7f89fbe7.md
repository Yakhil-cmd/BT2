### Title
Status webhook handler updates commits across all repositories/stacks by SHA alone, ignoring the webhook's authenticated repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the commit to update purely by matching `sha` against the global `Commit` table, without ever checking that the webhook's `repository` field corresponds to the `Stack`/repository that owns that commit. This breaks the trust binding "organization/repository whose webhook signature was verified" versus "repository whose commit status actually gets written," letting a GitHub `status` event legitimately signed for repository A modify commit-status state for a commit belonging to a completely unrelated `Stack`/repository B, as long as the two repositories happen to share a commit SHA (a routine occurrence for forks, mirrors, or multiple environment stacks tracking shared history).

### Finding Description
`WebhooksController#verify_signature` only proves that the raw JSON body was signed by the GitHub App/organization matching `repository.owner.login` in the payload: [1](#0-0) 

That verification says nothing about which *commit* the handler is allowed to touch — it only proves "this org sent this exact payload." The base `Handler` class does provide repository-scoping helpers (`stacks`, `repository_name`) that other handlers such as `PushHandler` use to scope side effects to the sending repository: [2](#0-1) [3](#0-2) 

`StatusHandler`, however, never uses this scoping. It declares only `sha`/`state` (plus optional description/url/context/branches) as parameters and never even parses `repository`, then looks up commits solely by SHA across the entire `Commit` table: [4](#0-3) 

`Commit#create_status_from_github!` then creates a `Status` and can flip the commit's aggregated state, which can enqueue continuous-delivery/merge processing: [5](#0-4) [6](#0-5) 

So the equality actually enforced is:
`verified_signature_organization == repository.owner.login_in_payload`

while the equality that should hold, but doesn't, is:
`repository_that_authenticated_the_webhook == repository_owning_the_commit_whose_status_is_mutated`

Any commit that shares a SHA with a commit tracked by *any* `Stack` in the Shipit instance — regardless of which repository/organization sent the webhook — will have its CI status mutated.

### Impact Explanation
Shared commit SHAs across repositories are common: forks/mirrors of the same upstream project, multiple `Stack`s tracking the same repository for different environments, or repositories built from shared git history/subtrees. An attacker who can post a real GitHub commit-status update on *any* repo they control or have `repo:status` write access to (a much lower bar than access to the victim repository or a Shipit session/token) can cause that genuinely-signed webhook to flip the CI status of a same-SHA commit belonging to an unrelated victim `Stack`. If that victim stack has continuous delivery enabled and the forged `context`/`state: success` satisfies its `required_statuses`, this can make a commit `deployable?` and trigger an unauthorized automatic deploy in a repository/organization the attacker never authenticated against — satisfying the "unauthorized deploy" impact bar.

### Likelihood Explanation
No Shipit session, `ApiClient` token, `webhook_secret`, or GitHub App private key is required — only ordinary GitHub commit-status write access to some repository whose commit history overlaps (via fork/mirror/shared subtree) with a repository tracked by Shipit. This is a plausible, low-privilege setup that many organizations using forks or multi-environment stacks would have.

### Recommendation
Scope `StatusHandler#process` (and any other handler operating on commits by SHA) to the repository that actually authenticated the webhook, e.g. restrict the `Commit` lookup to `stacks` (as derived from `payload.dig('repository','full_name')`, matching the `Handler#stacks`/`repository_name` helpers already used by `PushHandler`) instead of a global `Commit.where(sha: ...)` scan.

### Proof of Concept
1. Attacker has GitHub commit-status write access (e.g. `repo:status` scope) on `attacker-org/repo-x`, which shares commit history (fork/mirror) with `victim-org/repo-y`, a repository tracked by a Shipit `Stack` with continuous delivery enabled and `ci.require: ["ci/mycontext"]`.
2. Attacker posts a commit status to GitHub for `attacker-org/repo-x` at a SHA that is identical to an undeployed commit in `victim-org/repo-y`'s stack, with `state: success`, `context: "ci/mycontext"`.
3. GitHub delivers a genuinely-signed `status` webhook for `attacker-org/repo-x` to Shipit.
4. `WebhooksController#verify_signature` passes because the signature is valid for `attacker-org`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the matching commit under the victim's stack (not `attacker-org/repo-x`), and calls `create_status_from_github!`, marking it successful.
6. If this satisfies the victim stack's required statuses, `stack.schedule_merges` / continuous delivery proceeds to deploy the commit — an unauthorized deploy triggered from a webhook that never authenticated against `victim-org/repo-y`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
