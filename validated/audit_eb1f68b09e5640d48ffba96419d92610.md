### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup triggers continuous delivery on victim stacks - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `status` webhook handler resolves target commits solely by SHA, with no binding to the repository/organization whose webhook secret actually signed the request. Because git SHA1s are content-addressed and identical across forks/mirrors that share history, an attacker who owns a repository sharing commit history with a victim's tracked repository can forge a `status` webhook for their own org (verified with their own `webhook_secret`) naming a SHA that also exists as a `Commit` row belonging to the victim's `Stack`, causing `Status#schedule_continuous_delivery` to fire against the victim's stack.

### Finding Description
The broken binding, stated explicitly:

`verify_webhook_signature(signature, payload)` proves only that `payload` was signed by `Shipit.github(organization: repository_owner).webhook_secret` where `repository_owner = payload.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . It does **not** prove `payload.sha` belongs to `payload.repository.full_name`, nor that `payload.repository.full_name` equals the repository of any `Commit` row later mutated.

`StatusHandler#process` looks up commits purely by SHA, globally, with no scoping to the repository/org that was actually verified:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

So the intended equality `repository verified by signature == repository owning the mutated Commit/Stack` does not hold: the query is `Commit.where(sha: params.sha)`, unscoped by `stack.repository`. If the attacker's own (attacker-owned, attacker-signed) repository shares a commit SHA with a repository tracked by a victim `Stack` (trivial for forks, mirrors, or any repo with common upstream history — git SHAs are computed from tree/parent content and are identical across such repos), the created `Status` row is attached to the victim's pre-existing `Commit`/`Stack`.

From there, `Status` triggers `after_commit :schedule_continuous_delivery` on create [4](#0-3) , and `schedule_continuous_delivery` delegates unconditionally to `commit.schedule_continuous_delivery`: 
```ruby
def schedule_continuous_delivery
  commit.schedule_continuous_delivery
end
``` [5](#0-4) 
`Commit` also fires `schedule_continuous_delivery` on its own `after_commit :create` hook [6](#0-5) , and this operates on `commit.stack` — the victim's `Stack`, entirely determined by the pre-existing `Commit` row, not by anything the attacker's signature actually verified.

**Exploit flow:**
1. Attacker owns/forks a public repository that shares commit history (and therefore SHAs) with a repository tracked by a victim Shipit `Stack` with `continuous_deployment` enabled.
2. Attacker sends `POST /webhooks` with `X-Github-Event: status`, `repository.owner.login` = attacker's own org, and `sha` = a SHA known to exist in the victim's tracked history, `state: success`, signed with the attacker's own `webhook_secret`.
3. `verify_signature` passes because the signature correctly matches the attacker's own org config [1](#0-0) .
4. `StatusHandler#process` matches the victim's existing `Commit` row purely by SHA (no repo/org filter) and calls `commit.create_status_from_github!(params)` [3](#0-2) .
5. The new `Status` row (`stack_id` = victim's stack) triggers `schedule_continuous_delivery` against the victim's stack [4](#0-3) .

Existing guards do not prevent this: `verify_signature` only checks organization-level HMAC validity, not repository/commit ownership; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema on `StatusHandler` only validates types/presence of `sha`, `state`, etc., not repository ownership [7](#0-6) ; no model validation ties `Status`/`Commit` lookup to the payload's `repository.full_name`.

### Impact Explanation
An attacker with only their own repository and webhook secret can enqueue a continuous-delivery evaluation job against an arbitrary victim `Stack`, without any Shipit credentials, session, or knowledge of the victim's secrets. This is a payload-for-one-repository-mutating-another's-stack/commit scenario, matching the Critical impact category (unauthorized action taken against a stack/commit the attacker never authenticated for). Because continuous delivery evaluation can lead to automatic merges/deploys on the victim stack when a `success` status appears, the practical consequence is an unauthorized deploy trigger on a tenant the attacker does not control, repeatable against any stack whose tracked repository shares commit history with an attacker-controlled repo (e.g., any public repo with forks).

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment` enabled (explicitly stated as given), and the victim's tracked repository shares commit SHAs with an attacker-accessible repository (very common for forks/mirrors of public repos, or private repos an attacker previously had access to and forked before losing access). Attacker cost is minimal: create/own a GitHub App or org with any `webhook_secret`, and send one crafted, self-signed HTTP request to `/webhooks`. No GitHub session, Shipit session, API token, or victim secret is required. This is fully repeatable per target stack as long as a shared SHA can be identified.

### Recommendation
Scope the `status` handler's commit lookup to the repository verified by the signature, not just the SHA. For example, resolve `Stack`/`Commit` via `payload.repository.full_name` (and organization) in addition to `sha`, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_owner: ..., repository_name: ... })`, ensuring the mutated `Commit`/`Stack` belongs to the same repository that was cryptographically verified in `verify_signature`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
    test "a status signed by attacker's org for a shared SHA schedules continuous delivery for a victim stack" do
      victim_stack = shipit_stacks(:shipit) # continuous_deployment enabled fixture
      shared_sha = "deadbeef" * 5
      victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared history commit")

      # Attacker's payload: repository belongs to attacker's own org, but sha collides with victim's commit
      payload = {
        "sha" => shared_sha,
        "state" => "success",
        "repository" => { "full_name" => "attacker/attacker-repo", "owner" => { "login" => "attacker-org" } }
      }

      GithubApp.any_instance.stubs(:verify_webhook_signature).returns(true) # attacker's own secret verified their own payload

      assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_id: victim_stack.id]) do
        Webhooks::Handlers::StatusHandler.call(payload)
      end
    end
  end
end
```
Both sides of the equality to assert: the org verified by `verify_webhook_signature` (`attacker-org`) does **not** equal `victim_stack.repository_owner`, yet the enqueued job's `stack_id` equals `victim_stack.id` — proving the binding claimed by the question is broken.
