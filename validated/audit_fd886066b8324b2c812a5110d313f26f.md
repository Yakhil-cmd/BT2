### Title
Cross-repository CI status forgery via unscoped commit lookup in `StatusHandler` breaks the org‑authenticated‑vs‑commit‑written binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook only against the GitHub App/organization named in the payload's `repository.owner.login` (or `organization.login`), not against the specific repository or commit the event claims to describe. [1](#0-0) 
For the `status` event, `Handlers::StatusHandler#process` never re-checks that binding: it looks up commits purely by SHA across the entire Shipit installation and writes a status derived directly from attacker-controlled fields. [2](#0-1) [3](#0-2) 

### Finding Description
Shipit is multi-tenant: it can hold configuration for multiple GitHub organizations/apps, each with its own `webhook_secret`. [4](#0-3) 
The webhook signature check resolves *which* secret to verify against using `repository_owner`, taken directly from the unauthenticated JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`): [5](#0-4) 
An operator of any organization that Shipit trusts (i.e., an attacker who controls one legitimate, low-privilege GitHub App installation/org configured in the same Shipit instance) can compute a valid `X-Hub-Signature` using their own org's `webhook_secret`.

The binding that should hold is: *organization authenticated by the signature* == *repository/commit the event is allowed to mutate*. This binding is never enforced for the `status` event. `StatusHandler` does not look at `repository.full_name`/`repository.owner` at all when deciding what to update — it queries `Commit.where(sha: params.sha)`, which is a global, cross-stack, cross-repository lookup: [2](#0-1) 
Any commit in any stack (belonging to any organization onboarded to the Shipit instance) whose SHA happens to match `params.sha` gets `commit.create_status_from_github!(params)` called on it, with `state`, `description`, `target_url`, and `context` taken verbatim from the attacker's payload: [6](#0-5) 

Because the check performed in `WebhooksController#verify_signature` only authenticates "this payload came from *an* org we trust," while the mutation performed by `StatusHandler` acts on "whatever commit matches this SHA anywhere in the system," the two sides of the trust equality diverge: `authenticated_org(payload) == org_owning(stack.repository)` is required, but the code only enforces `authenticated_org(payload) == org_named_in(payload)`, an attacker-controlled tautology.

### Impact Explanation
`Commit#deployable?` and the release/merge machinery are directly driven by commit status: `deployable?` requires `success? && !blocked?` [7](#0-6) , and a status update can trigger `stack.schedule_merges` and continuous-delivery scheduling once the state becomes `success`/`pending`. [8](#0-7) 
An attacker who legitimately controls one org/repo hosted on the same Shipit instance can forge a `success` status for a commit belonging to a **different** organization/stack they do not control, provided they can predict or learn that commit's SHA (public repos, PRs, or previously observed SHAs make this trivial). If that victim stack has `continuous_deployment` enabled or relies on CI status gating before deploy, this can drive an unauthorized deploy of a commit that never actually passed CI — meeting the "unauthorized deploy" impact bar.

### Likelihood Explanation
This requires the attacker to already be an authenticated, low-privilege tenant of the Shipit instance (i.e., they control at least one org/app configuration with a valid `webhook_secret`) — which is the "unprivileged attacker" the scoped analog class targets, as opposed to needing an `ApiClient` token, session, or GitHub App private key. The attack payload is trivial to construct (arbitrary JSON body plus a correctly computed HMAC using the attacker's own secret) and needs no interaction with the victim.

### Recommendation
Scope every webhook handler's DB lookups by the authenticated organization, not just by fields taken from the unauthenticated payload. Concretely:
- In `StatusHandler`, restrict `Commit.where(sha: params.sha)` to commits whose `stack.repository` belongs to the organization that was cryptographically verified in `verify_signature` (e.g., join through `Stack`/`Repository` and filter by `repository_owner`).
- More generally, thread the verified `repository_owner`/GitHub App identity from `WebhooksController` into every `Handler`, and assert that `payload.dig('repository','full_name')`'s owner segment matches the organization whose secret validated the signature, rejecting the event otherwise.

### Proof of Concept
1. Attacker owns/administers `attacker-org`, which is a legitimately configured GitHub App/org in the target Shipit instance, so they know `attacker-org`'s `webhook_secret`.
2. Attacker identifies a target commit SHA `S` belonging to a stack under `victim-org/victim-repo` (e.g., from a public commit, PR, or prior observation).
3. Attacker crafts a `status` event payload: `{"sha": "S", "state": "success", "context": "ci/required-check", "repository": {"owner": {"login": "attacker-org"}}}` and signs it with `attacker-org`'s `webhook_secret` to produce a valid `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org`, fetches `Shipit.github(organization: 'attacker-org')`, and the signature verifies successfully. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: 'S')`, finds the victim's commit (regardless of `repository.owner` in the payload), and calls `create_status_from_github!` with the attacker's forged `state: "success"`, updating the victim commit's CI status. [2](#0-1) 
6. If `victim-org`'s stack has continuous deployment enabled or otherwise gates deploys on status, this forged success can trigger an unauthorized deploy of that commit.

Note: I was unable to fully verify (within the index) whether every `Shipit.github(organization:)` deployment configuration in practice hosts more than one distinct, mutually-untrusted organization sharing a single Shipit instance — this is an operational/deployment assumption inherent to Shipit's documented multi-org support, and I could not inspect a live `secrets.yml` to confirm multi-tenancy is actually enabled for a given install.
