### Title
Unauthenticated read of live stack/task/deploy event streams via `/events` mount - ([File: config/routes.rb])

### Summary
`Pubsubstub::StreamAction` is mounted directly as a Rack endpoint at `/events` in `config/routes.rb`, bypassing all Rails controller filters, including `Shipit::Authentication#force_github_authentication`. The only reference to a guard for this endpoint is a comment in `GithubAuthenticationController#callback` claiming a `UserRequiredMiddleware` protects it, but no such middleware is defined or inserted anywhere in this engine's `lib/` or `app/`.

### Finding Description
The broken binding: the comment at `app/controllers/shipit/github_authentication_controller.rb:15-17` asserts `session[:authenticated] = true` is meaningful because "the /events and /sidekiq endpoint... leverage `UserRequiredMiddleware`" — i.e., it claims `middleware_guard(/events) == UserRequiredMiddleware.enforced`. Tracing the actual code shows this equality is false: `UserRequiredMiddleware` does not exist anywhere in the engine (confirmed via full-repo search), is not registered in `lib/shipit/engine.rb`'s `app.middleware.use(...)` calls (only `OmniAuth::Builder` and, conditionally, `Shipit::SameSiteCookieMiddleware` are inserted, per `lib/shipit/engine.rb:46-55`), and `config/routes.rb:9` mounts `Pubsubstub::StreamAction.new` directly (`mount Pubsubstub::StreamAction.new, at: "/events"`), which is a raw Rack app, not an `ActionController` action — it never passes through `ApplicationController`'s `before_action :force_github_authentication` defined in `app/controllers/concerns/shipit/authentication.rb`.

Attacker request: an unauthenticated `GET /events?channels[]=stack.1` (or any channel name) with no session cookie and no `Authorization` header reaches `Pubsubstub::StreamAction#call` with zero engine-side authorization checks, because Rails routes mounted engines to the target Rack app before any engine controller callback chain can run.

### Impact Explanation
The attacker receives a live SSE stream of stack, task, and deploy state for any stack/channel they can guess or enumerate (channel names appear to follow predictable patterns like `stack.<id>`), without any session, GitHub OAuth, API token, or team membership. This is unauthenticated read of stack state and task/deploy streams across all tenants hosted by the Shipit instance — matching the "High" impact category defined in the rules ("unauthenticated read of stack state, task streams or deploy output"). It is fully repeatable against arbitrary stacks by varying the channel parameter, with no rate limiting or session requirement.

### Likelihood Explanation
No special configuration or precondition beyond a stack existing is needed. `Shipit.enable_samesite_middleware?` is irrelevant since that middleware only touches cookie attributes, not authorization, and even if enabled it is inserted after `Rack::Runtime` unconditionally for the whole app but performs no authentication logic (`lib/shipit/engine.rb:53-55`). The attacker cost is a single unauthenticated HTTP GET; feasibility is high, and the issue is deterministic per the current routing/middleware stack.

### Recommendation
Add real authentication/authorization in front of the `/events` mount — e.g., wrap the mount behind a Rack middleware (or a small controller action that streams via `Pubsubstub`) that checks `session[:user_id]`/`current_user.authorized?` (mirroring `Shipit::Authentication#force_github_authentication`) before allowing the SSE connection, and validate that the requested channel corresponds to a stack the authenticated user is permitted to view. Remove or fix the stale comment referencing the non-existent `UserRequiredMiddleware`, and implement the middleware it describes, registering it via `app.config.middleware.insert_before` ahead of the `/events` mount in `lib/shipit/engine.rb`.

```ruby
    # No session cookie, no Authorization header

    # Binding under test: middleware_guard(/events) should equal
    # force_github_authentication-equivalent enforcement.
    # Currently this assertion FAILS because no 401/403/redirect occurs.
    assert_includes [401, 403], response.status
  end

  test "force_github_authentication before_action never runs for /events mount" do
    Shipit::Authentication.any_instance.expects(:force_github_authentication).never

    get "/events", params: { "channels[]" => "stack.1" }
    # Demonstrates the mount bypasses ApplicationController's filter chain entirely.
  end
end
```
Both assertions demonstrate that no engine-side authorization check (`force_github_authentication`, `current_user.authorized?`) is evaluated for `/events`, confirming the binding claimed in the comment (`UserRequiredMiddleware` protecting the mount) does not exist in code.
