### Title
Hookify `RuleEngine._matches_tool` exact tool-name whitelist lets `MultiEdit` bypass rules written for `Edit|Write` - ([File: plugins/hookify/core/rule_engine.py])

### Finding Description
`RuleEngine._rule_matches` gates every rule on `_matches_tool(rule.tool_matcher, tool_name)`, which only supports exact string membership in the `|`-separated matcher list: [1](#0-0) 

Rule authors write matchers as documented (e.g. `tool_matcher: "Edit|Write"`) to catch file-modification tools, per `plugins/hookify/skills/writing-rules/SKILL.md`. However, Claude Code exposes a third, semantically equivalent file-editing tool, `MultiEdit`, which is a distinct `tool_name` string and is never included by these conventional matchers unless the author explicitly adds it. Because `_matches_tool` does a plain `tool_name in patterns` check with no normalization/aliasing of tool families, any rule scoped to `"Edit|Write"` (or just `"Edit"`/`"Write"`) silently does not fire when the same dangerous content is written via `MultiEdit`.

This is compounded by `_extract_field`, which has a separate, narrower field mapping for `MultiEdit` than for `Edit`/`Write`: [2](#0-1) 

Note that for `Edit`/`Write` both `old_text`/`old_string` and `new_text`/`content` are extracted, but for `MultiEdit` only `file_path` and `new_text`/`content` (concatenation of all `edits[].new_string`) are supported — there is no `old_text` extraction for `MultiEdit` at all. So even a rule that does correctly enumerate `tool_matcher: "Edit|Write|MultiEdit"` but conditions on `field: old_text` will never match `MultiEdit` invocations, because `_extract_field` returns `None` for that combination and `_check_condition` treats `None` as "condition unsatisfied."

An attacker who can influence the assistant's tool choice (e.g., via prompt-injection in repository content, issue/PR text, or file contents that Claude reads and acts on) can cause Claude Code to prefer `MultiEdit` for a multi-part edit that a security-conscious repo owner intended to block via a Hookify rule keyed to `Edit|Write` and/or `old_text`/`new_text`. Since `evaluate_rules` only blocks when `_rule_matches` returns `True`, and `_rule_matches` returns `False` whenever the tool matcher or a condition fails to find the field, the dangerous edit is silently allowed through — the "deny" hook output is never produced.

### Impact Explanation
This breaks the core Hookify invariant that a configured `block` rule reliably denies the protected operation. Because the bypass happens purely through Claude Code's own normal tool selection (no admin privilege, no key leakage, no local shell needed beyond ordinary Claude Code usage), an attacker who can steer tool choice (e.g., via injected instructions in a repository/PR that Claude reads) can get dangerous file content written or destructive edits applied that the user explicitly configured Hookify to block, defeating the approval/deny control Hookify is meant to provide. This matches the "Unauthorized local command execution/file mutation that bypasses Claude Code approval or deny controls" impact class, scoped to file-write operations reachable through the `MultiEdit` tool.

### Likelihood Explanation
Feasibility is high and repeatable: it requires no special access — only that a Hookify rule author uses the common (and documented) `Edit|Write` matcher pattern without including `MultiEdit`, and that the assistant is induced (by normal repo content, its own judgment, or prompt injection) to perform the edit via `MultiEdit` instead of `Edit`/`Write`. Since `MultiEdit` is a first-class, frequently-used Claude Code tool for multi-hunk edits, this is not an edge case; it can occur in ordinary usage without any adversarial trigger, and can be deterministically reproduced with a fixed rule set and crafted hook JSON.

### Recommendation
- In `_matches_tool`, normalize/expand tool-family matching so that matchers like `Edit`/`Write` are automatically treated as including `MultiEdit` (or require rule authors to use an explicit alias table maintained by the engine rather than raw string equality), and document this in `writing-rules/SKILL.md`.
- In `_extract_field`, make the `MultiEdit` field extraction symmetric with `Edit`/`Write`: support `old_text`/`old_string` (e.g., concatenating `edits[].old_string`), not just `new_text`/`content`.
- Add an engine-level self-check/lint (e.g., in `config_loader.load_rule_file`) that warns when a rule's `tool_matcher` references `Edit` or `Write` without `MultiEdit`, since these tools address the same class of operation.

### Proof of Concept
Unit test in `plugins/hookify/core/rule_engine.py` test harness (or a new pytest module):
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-secret-write",
    enabled=True,
    event="file",
    action="block",
    tool_matcher="Edit|Write",
    conditions=[Condition(field="new_text", operator="contains", pattern="BEGIN PRIVATE KEY")],
    message="Blocked: writing secret material",
)
engine = RuleEngine()

# 1) Baseline: Write is correctly blocked
write_input = {"tool_name": "Write", "tool_input": {"file_path": "x.pem", "content": "-----BEGIN PRIVATE KEY-----"}}
assert engine.evaluate_rules([rule], write_input).get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

# 2) Equivalent operation via MultiEdit bypasses the same rule
multiedit_input = {
    "tool_name": "MultiEdit",
    "tool_input": {"file_path": "x.pem", "edits": [{"old_string": "", "new_string": "-----BEGIN PRIVATE KEY-----"}]},
}
result = engine.evaluate_rules([rule], multiedit_input)
assert result == {}  # FAILS invariant: dangerous write is allowed, no deny/systemMessage produced
```
Expected: the second assertion demonstrates that an identical dangerous payload delivered via `MultiEdit` is not blocked, confirming the tool-matcher/field-extraction gap.

    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns
