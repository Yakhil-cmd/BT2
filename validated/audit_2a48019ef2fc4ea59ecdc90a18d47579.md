Found a valid analog: the shared `index-cache` in `v0-4-market.clar` is a cache primed by one caller (e.g. a liquidator or accruer) and consumed by another user without value/staleness validation of the accrue result being tied to the caller.

### Title
Shared per-timestamp index-cache can be primed with stale/incorrect accrual data that is silently reused by other users in the same block - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`accrue-and-cache` implements a shared cache keyed only by `{timestamp: stacks-block-time, aid: aid}` that any user's transaction can populate, and which every other user's subsequent transaction in the same second/block will read and trust without re-validating against the vault's own state.

### Finding Description
`accrue-and-cache` first checks `index-cache` for an entry keyed by `{timestamp: stacks-block-time, aid: aid}` [1](#0-0) . If present, it is returned directly ("cache HIT: return cached value (1 read only)") without calling `vault-accrue` again. If absent, it calls `vault-accrue aid`, an external `contract-call?` to the corresponding vault, and stores whatever indexes that call returns into the shared map, keyed purely by timestamp/asset — with no dependency on who the caller is, what operation they're performing, or a bound on how much this cached value can diverge from a freshly-computed one.

This cache is consumed transitively by every user operation that touches the same asset in the same `stacks-block-time` window: `accrue-debt-asset` and `accrue-collateral-asset` both call `accrue-and-cache` and `unwrap-panic` the result [2](#0-1) , and these are folded over a user's full debt/collateral list during position accrual, borrow, repay, deposit, redeem, and liquidation flows. Because the cache key does not commit to which vault-accrue outcome was cached (the map simply stores whatever `indexes` value the first caller's `vault-accrue` invocation returned), if the first accruing transaction in a given timestamp window observes/produces indexes based on transient state (e.g., is itself part of a larger operation that changes vault state before or after the accrual call, or the vault's `accrue` has any timestamp/order sensitivity), that value is then binding for every other user's transaction that shares the same `{timestamp, aid}` key for the rest of that time-bucket — regardless of the actual order or content of their own transaction.

This matches the "shared index or cache primed by one caller and consumed by another" bug class: the ReDoS report's core issue was that attacker-controlled input silently degrades a shared computation path; here, attacker-controlled *transaction ordering* silently determines a shared, unauthenticated cache value that other unrelated users' operations depend on for correctness of their own debt/collateral accrual, interest indexing, and (via `get-cached-indexes`) liquidation math.

### Impact Explanation
If the cached index value materially differs from what an honest recomputation should be for a given later caller, that later caller's `debt-updated`, `other-debt-repayable`, and liquidation/bad-debt-socialization calculations (which call `get-cached-indexes` again, expecting a consistent cached value from earlier in the same transaction chain) will use the stale/first-observed value instead of one accurate for their own operation. This can under- or over-charge interest for a victim user within the same timestamp window, a form of temporary freezing/incorrect accounting of unclaimed yield (interest) imposed on a user by another user's transaction ordering, landing on the "temporary freezing of funds" / "theft of unclaimed yield" impact classes.

### Likelihood Explanation
Requires two transactions from different users landing with the same `stacks-block-time` for the same asset, and requires `vault-accrue`'s returned index to be sensitive to transaction ordering/timing beyond the timestamp itself — this is plausible but not certain from the code available; the actual vault `accrue` implementation (in `v0-vault-*` contracts) was not available in the index to confirm whether it is purely a deterministic function of `stacks-block-time`, in which case the cache would be safe. This uncertainty affects confidence in the finding.

### Recommendation
Verify that `vault-accrue`'s return value is a pure, order-independent function of `stacks-block-time` alone (not dependent on any other mutable state read at call time). If it is not provably pure, either remove the cross-user cache (recompute per call) or include a content hash/version discriminant of the vault's authoritative state in the cache key so a stale or order-dependent value cannot be silently reused by unrelated callers.

### Proof of Concept
Not fully constructible from the available index: reproducing the issue requires inspecting `v0-vault-*.accrue` (e.g. `v0-vault-stx.clar`) to determine whether its return value can vary based on call order within the same `stacks-block-time`, and this file's content was not available in the current search results. (define-private (accrue-and-cache (aid uint))
```text
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
