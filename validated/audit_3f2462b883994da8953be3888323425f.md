### Title
Structural mismatch in manual DER parsing between key validation and signature verification allows secp256k1 PEM signature check to be bypassed - ([File: signature.js])

### Summary
The `BigNumber`-style report flags excessive, error-prone use of low-level, hand-rolled binary parsing in place of clear structural logic. In `ocore`, the analogous pattern is the manual DER (ASN.1) parsing implemented in `signature.js` for PEM public keys used by oscript `sig` definitions with `algo`/PEM support. `validateAndFormatPemPubKey` computes the SubjectPublicKeyInfo structure offsets explicitly (`identifiersStart`, `identifiersLength`) based on the outer SEQUENCE length-tag encoding, while the separate function `verifyMessageWithSecp256k1PemPubKey` locates the public key bytes by *scanning* the same DER buffer for the raw byte pattern `03 42 00` with `Buffer.indexOf`, rather than deriving the offset from the same structural fields. ### Finding Description
`validateAndFormatPemPubKey` is the function responsible for structurally validating a PEM key blob and confirming it encodes an allowed curve/algorithm (`objSafePemTypes`/`objSupportedPemTypes`), based on exact byte offsets computed from the ASN.1 length octets: [3](#0-2) 

By contrast, `verifyMessageWithPemPubKey`/`verifyMessageWithSecp256k1PemPubKey`, used to actually perform the ECDSA signature check for secp256k1 PEM keys, does not reuse those computed offsets. Instead it re-parses the DER independently:
- It computes `algIdStart` using a *different*, simplified length-tag branch (`der[1] <= 0x7F ? 4 : ...`) than `validateAndFormatPemPubKey`'s branches, and only checks that the fixed 17-byte `SECP256K1_ALG_ID` sequence appears at that single offset.
- It then locates the actual public key bytes not from a computed offset at all, but by scanning the *entire* buffer for the literal 3-byte pattern `03 42 00` via `der.indexOf(...)`: [4](#0-3) [5](#0-4) 

Because the BIT STRING pattern is located by scanning rather than by structural offset, and because `verifyMessageWithSecp256k1PemPubKey` is a self-contained function that does not depend on or reuse the validation performed in `validateAndFormatPemPubKey`, the two code paths can disagree about which bytes constitute "the" public key whenever a DER blob is crafted so that the byte sequence `03 42 00 04 <32 bytes> <32 bytes>` appears at a location other than the true SubjectPublicKeyInfo BIT STRING position (e.g., by inserting extra/duplicate structures, altering non-critical DER fields, or embedding the pattern inside otherwise-unused/padding bytes that the length-based validator does not scrutinize byte-for-byte outside of the fields it explicitly checks). If the address/definition binds to the original PEM string (hashed as-is) but `algIdStart`/BIT-STRING scanning extracts a different key than what a strict, canonical DER parser would, this is exactly the "manipulate individual words/buffers instead of clear structured logic" anti-pattern called out in the report: two independent low-level buffer walkers over the same input can diverge on malformed-but-not-rejected input.

### Impact Explanation
If the pubkey extracted by `verifyMessageWithSecp256k1PemPubKey`'s pattern scan can be made to differ from the pubkey that `validateAndFormatPemPubKey` associates with the address/definition (or from the key an honest verifier would extract via canonical DER decoding), an attacker could craft an oscript `sig` (PEM/ECDSA) address definition or AA trigger payload where the effective verification key diverges from the intended one, potentially enabling unauthorized signature acceptance for that authentifier path. Because `sig` with PEM keys is reachable directly from unit authors' address definitions and AA triggers evaluated by every full node, a successful bypass would let an attacker satisfy an address's or AA's ECDSA authentication with an unintended key — a form of unauthorized spending/authorization bypass, which nodes would also disagree on if some validate strictly and others accept the scanned key, causing potential validity/stability disagreement across the network.

### Likelihood Explanation
This is Medium likelihood: exploiting it requires an attacker to hand-craft a DER blob that (a) still passes the coarse checks in `validateAndFormatPemPubKey` (fixed algorithm-identifier length options, hex length check) and (b) contains the `03 42 00 04` marker at an offset different from the canonical BIT STRING location so that a different 65-byte value is extracted by the scan-based verifier. This is plausible given the validator only checks specific length/offset fields and does not perform full DER canonicality/uniqueness checks (e.g., it does not reject duplicate or reordered SEQUENCE/BIT STRING elements, or extra trailing/injected bytes outside the fields it inspects), leaving room for the scan in `verifyMessageWithSecp256k1PemPubKey` to latch onto attacker-controlled bytes. Full confirmation of an exploitable crafted DER requires binary-level experimentation that could not be completed within the scope of this review.

### Recommendation
Refactor the two PEM-parsing code paths so there is a single, canonical, offset-driven DER parser (in the spirit of the bug report's suggestion to isolate low-level buffer/word operations into small primitives and keep all structural/control-flow logic in clear, shared Solidity/JS code). Specifically:
- Have `verifyMessageWithSecp256k1PemPubKey` reuse the exact `identifiersStart`/`identifiersLength` computation (or the resulting validated key bytes) from `validateAndFormatPemPubKey` instead of independently recomputing `algIdStart` and scanning for `03 42 00`.
- Reject any DER blob where the `03 42 00 04` marker used for the BIT STRING is not located at the single offset implied by the previously validated SEQUENCE/algorithm-identifier structure (i.e., disallow scanning; require an exact, structurally-derived offset).
- Add strict DER canonicality checks (no trailing/extra bytes, no duplicate BIT STRING markers) so that both parsers cannot be made to disagree on any crafted input.

### Proof of Concept
Conceptual (not executed, given index-only access):
1. Construct a DER SubjectPublicKeyInfo blob whose outer SEQUENCE/AlgorithmIdentifier fields satisfy `validateAndFormatPemPubKey`'s length checks (`identifiersLength` one of 13/16/19/20, matching `secp256k1` OID) and whose `hex_pub_key_length` check passes for the *intended* 65-byte key K1 placed at the canonical offset.
2. Inject, elsewhere in the same DER buffer (e.g., in unused/padding trailer bytes not covered by the offset-based checks), a second byte sequence `03 42 00 04` followed by a different 65-byte key K2.
3. Call `verifyMessageWithPemPubKey(message, signature, pem_key, true)`; because `der.indexOf(Buffer.from([0x03,0x42,0x00]))` returns the *first* match in the buffer, if K2's marker precedes K1's canonical position (or is the only literal match `indexOf` finds due to subtle byte differences from the canonical structure), `verifyMessageWithSecp256k1PemPubKey` extracts and verifies against K2 rather than the key that `validateAndFormatPemPubKey` associated with the address, while `validateAndFormatPemPubKey` still reports the key as valid for K1's structural fields.
4. This produces a discrepancy between "the key that was validated/bound to the address" and "the key actually used to verify the signature," matching the report's core concern: low-level, hand-rolled buffer scanning substituting for clear, single-source structural parsing, with concrete security consequences (signature/authentication bypass) rather than mere code-quality issues. function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}

function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
	} catch(e) {
		console.log('secp256k1 pem verify exception: ' + e);
		return false;
	}
}

function validateAndFormatPemPubKey(pem_key, algo, handle, bPostPemCurvesFix) {

	if (!ValidationUtils.isNonemptyString(pem_key))
		return handle("pem key should be a non empty string");

	//we remove header and footer if present
	var contentAloneB64 = pem_key.replace("-----BEGIN PUBLIC KEY-----", "").replace("-----END PUBLIC KEY-----", ""); 
	
	//we remove space, tab space or carriage returns
	contentAloneB64 = contentAloneB64.replace(/\s/g, "");

	if (contentAloneB64.length > 736) // largest is RSA 4096 bits
		return handle("pem content is too large");

	if (!ValidationUtils.isValidBase64(contentAloneB64))
		return handle("not valid base64 encoding" + contentAloneB64);

	var contentAloneBuffer = Buffer.from(contentAloneB64, 'base64');

	if (contentAloneBuffer[0] != 0x30)
		return handle("pem key doesn't start with a sequence");

//we determine start and length of algo/curve identifiers
	if (contentAloneBuffer[1] <= 0x7F){
		if (contentAloneBuffer[2] != 0x30)
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 4;
		var identifiersLength = contentAloneBuffer[3];
	} else if (contentAloneBuffer[1] == 0x81){
		if (contentAloneBuffer[3] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 5;
		var identifiersLength = contentAloneBuffer[4];
	} else if (contentAloneBuffer[1] == 0x82){
		if (contentAloneBuffer[4] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 6;
		var identifiersLength = contentAloneBuffer[5];
	} else {
		return handle("wrong length tag");
	}

	//we decode the length of identifiers
	if (identifiersLength != 13 && identifiersLength != 16 && identifiersLength != 19 && identifiersLength != 20)
		return handle("wrong identifiers length" + identifiersLength);

	//we isolate the identifiers
	var contentAloneHex = contentAloneBuffer.toString('hex')
	var typeIdentifiersHex = contentAloneHex.slice(identifiersStart * 2, identifiersStart *2 + identifiersLength *2);

	if (!objSupportedPemTypes[typeIdentifiersHex])
		return handle("unsupported algo or curve in pem key");

	if (bPostPemCurvesFix && !objSafePemTypes.has(typeIdentifiersHex))
		return handle("unsupported curve after pem curves fix MCI");

	if (algo != "any"){
		if (algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "ECDSA")
			return handle("PEM key is not ECDSA type");
		if (algo == "RSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "RSA")
			return handle("PEM key is not RSA type");
	}

	if (objSupportedPemTypes[typeIdentifiersHex].algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].hex_pub_key_length != (contentAloneHex.length - identifiersStart * 2 - identifiersLength *2 - 8))
		return handle("wrong key length");

	//we add back header and footer
	pem_key =	"-----BEGIN PUBLIC KEY-----" + "\n";
	pem_key += contentAloneB64+"\n";
	pem_key += "-----END PUBLIC KEY-----";
	return handle(null,pem_key);
