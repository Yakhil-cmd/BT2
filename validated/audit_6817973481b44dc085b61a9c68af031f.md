### Title
RAY-scaled market value overflows before the index cap and permanently freezes the market - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` converts total scaled supply and debt back into RAY-denominated values before applying interest. [1](#0-0)  These conversions store `scaled_amount * index / RAY` in an `i128`, so an exact result above `i128::MAX` panics with `MathOverflow` even though the intermediate multiplication is widened to `I256`. [2](#0-1) [3](#0-2)  Once this happens, `global_sync` cannot advance `last_timestamp`, causing every later synced market operation to repeat the same overflow. [4](#0-3) 

### Finding Description
The protocol stores positions and market totals as RAY-scaled shares and values them by multiplying those shares by the borrow or supply index. [2](#0-1)  `accrue_step` performs this valuation for both totals before calculating utilization, updating the indexes, or splitting interest. [5](#0-4) 

`update_borrow_index` limits only the index to `MAX_BORROW_INDEX_RAY`; it does not limit the product of outstanding scaled debt and the resulting index. [6](#0-5)  Likewise, interest calculation independently multiplies the scaled debt by both the old and new borrow indexes. [7](#0-6)  Consequently, a sufficiently large market can reach the `i128` value ceiling while its index remains far below the nominal index cap. [8](#0-7) 

The public `update_indexes` path reaches `interest::global_sync` for each submitted market. [9](#0-8)  Ordinary pool actions use the same synchronization path through `synced_market`, and withdrawal and repayment legs reach it through `load_leg`. [10](#0-9) [11](#0-10) [12](#0-11) 

An unprivileged caller can create or rely on a very large supplied balance, maintain high borrowing through `borrow`, and eventually call `update_indexes` on that `HubAssetKey`; once accrual overflows, no accrual-dependent operation on that market can complete. [13](#0-12) [14](#0-13) 

### Impact Explanation
This permanently freezes supplier collateral and prevents borrowers or third parties from repaying or liquidating the market through the normal controller paths. [15](#0-14)  Because the overflow occurs before the accrual timestamp is committed, retrying does not make progress, and every subsequent synchronized operation encounters the same oversized stored share-index product. [16](#0-15) 

The existing regression test demonstrates that the borrow index remains below `MAX_BORROW_INDEX_RAY` when the failure occurs, so the configured index ceiling cannot rescue the market. [17](#0-16)  The test then confirms that both withdrawal and repayment revert with `MathOverflow`, satisfying the permanent-freezing and contract-unable-to-operate impact classes absent a privileged contract upgrade. [15](#0-14) 

### Likelihood Explanation
The attack requires an exceptionally large market and sustained borrowing, but all required actions are unprivileged: supply the asset, provide sufficient collateral, borrow against it, and later invoke `update_indexes`. [13](#0-12) [18](#0-17)  The repository’s own test uses a billion-unit eighteen-decimal market at 98% utilization and advances the ledger until the public index update fails. [19](#0-18) 

The scenario can also arise organically in an already-large market: an attacker does not need to own all affected liquidity and only needs to trigger the next accrual after the stored totals become unsafe. [9](#0-8)  Caps reduce exposure when configured tightly, but the code does not derive a per-market scaled-share ceiling that guarantees `scaled_amount * index` remains representable for every permitted index. [20](#0-19) [21](#0-20) 

### Recommendation
Do not allow accrual to persist an index whose corresponding scaled market value cannot fit in `i128`. [5](#0-4) 

1. Add non-panicking value calculations that detect when `scaled_amount * index / RAY` would exceed `i128::MAX`. [22](#0-21) 
2. Clamp each market’s effective borrow and supply indexes to `floor(i128::MAX * RAY / scaled_amount)`, with additional headroom for protocol-revenue share minting. [6](#0-5) [23](#0-22) 
3. When a market reaches its arithmetic ceiling, stop interest accrual safely while still marking it synchronized, rather than reverting before state commit. [4](#0-3) 
4. Enforce supply and borrow caps that leave representable-value headroom under the configured maximum index and expected revenue-share growth. [20](#0-19) 
5. Retain the existing large-market regression test and add boundary tests for the exact last representable index, the first unsafe index, repayment, withdrawal, liquidation, and `update_indexes`. [24](#0-23) 

### Proof of Concept
The repository already contains an executable reproduction. [25](#0-24) 

```rust
// Supply a very large eighteen-decimal market and borrow at high utilization.
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);

let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

// Repeatedly advance one-year ledger intervals and call the public
// controller index-update route.
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
        break;
    }
}
```

The update eventually reverts with `MathOverflow`, while the stored borrow index is still below `MAX_BORROW_INDEX_RAY`. [26](#0-25)  Subsequent `withdraw` and `repay` calls revert with the same error because both load an interest-synced market before processing their positions. [15](#0-14) [10](#0-9)

/// Converts a Ray-denominated `fee` into scaled supply-index shares
/// (`fee / supply_index`), floor-rounded and saturating on overflow. Caps the
/// result so that adding it to `supplied` cannot overflow `i128::MAX`.
pub fn protocol_fee_shares(env: &Env, fee: Ray, supply_index: Ray, supplied: Ray) -> Ray {
    let raw = fp_core::mul_div_floor_saturating(env, fee.raw(), RAY, supply_index.raw());

    let headroom = i128::MAX.saturating_sub(supplied.raw());
    Ray::from(raw.min(headroom))
}

**File:** docs/reference/formulas.md (L405-417)
```markdown
## Caps, fees, and numeric limits

A cap is in native token units. Entry compares stored scaled usage plus the
new scaled amount with the cap floor-converted at the current index. Zero cap
allows no positive exposure. Exits subtract usage without checking caps;
missing usage rows and zero exit deltas are no-ops. Cap→scaled conversion
saturates at `i128::MAX` (`calculate_scaled_cap`), so the entry check fails
open instead of trapping. A saturated scaled cap does not enforce the
configured asset-unit limit. An admitted cap saturates only at an index below
one RAY. Only a bad-debt write-down moves the supply index below one RAY; at
its floor (`RAY / 1000`), a supply cap above 1/1000 of the admitted maximum
saturates. The borrow index never falls below one RAY, so an admitted borrow
cap cannot saturate. Position conversion still rejects overflow.
```
