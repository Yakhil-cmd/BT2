## Title
`get_reward_distribution_num_blocks` caps the *number* of reward-distribution blocks but not the *per-block workload*, allowing attacker-inflated stake-account counts to blow up per-block work in `store_stake_accounts_in_partition` - ([File: runtime/src/bank/partitioned_epoch_rewards/mod.rs])

## Finding Description
`get_reward_distribution_num_blocks` computes `num_chunks = total_stake_accounts.div_ceil(stake_account_stores_per_block)` and then clamps it to at most `slots_per_epoch / 10`: [1](#0-0) 

This clamp bounds only `num_partitions` (and therefore satisfies the `assert!(self.epoch_schedule.get_slots_in_epoch(...) > partition_rewards.partition_indices.len())` in `distribute_partitioned_epoch_rewards`), but it does **not** bound how many stake rewards end up in each partition: [2](#0-1) 

Partitioning itself is done by `hash_rewards_into_partitions`, which hashes every stake reward's pubkey into one of `num_partitions` buckets, roughly evenly distributing `total_stake_accounts` rewards across the (capped) number of partitions: [3](#0-2) 

Once `num_partitions` saturates at `slots_per_epoch/10`, any further growth in `total_stake_accounts` (i.e., attacker-created stake accounts/delegations) increases the *average bucket size* (`total_stake_accounts / num_partitions`) without bound. Each block, `store_stake_accounts_in_partition` then iterates over the entire bucket for that partition index, building and storing a `StakeReward` per entry via `build_updated_stake_reward` and `self.store_accounts`: [4](#0-3) 

The per-block target of `stake_account_stores_per_block` (baseline `MAX_PARTITIONED_REWARDS_PER_BLOCK = 4096`, scaled by slot time) is only used to *compute* `num_chunks` before the clamp; it is never enforced as a hard per-partition size limit after clamping: [5](#0-4) 

The test `test_get_reward_distribution_num_blocks_cap` explicitly documents this behavior: once `num_stakes` exceeds `3 * stake_account_stores_per_block` in a 32-slot epoch, `num_partitions` stays capped at 3 regardless of how much larger `num_stakes` grows: [6](#0-5) 

An attacker able to create a very large number of minimum-delegation stake accounts (rent-exempt reserve + minimum delegation, which is `1` lamport unless `upgrade_bpf_stake_program_to_v5` is active, in which case it is `1 SOL`) before an epoch boundary increases `total_stake_accounts` unboundedly, while `num_partitions` stays capped at `slots_per_epoch/10`. This causes each of the capped partitions to contain far more entries than the intended `stake_account_stores_per_block` budget, so `store_stake_accounts_in_partition` does proportionally more work per block than the system was designed to bound.

## Impact Explanation
This does not trip the `assert!` (which only bounds `num_partitions < slots_in_epoch`), so it does not cause an unconditional panic/crash across honest nodes. It does, however, defeat the intended per-block work bound (`stake_account_stores_per_block`) that the partitioning scheme is designed to enforce, causing epoch-boundary block processing time to grow linearly with attacker-controlled account count rather than staying capped. Depending on stake_account_stores_per_block: 4096 baseline value and the magnitude of inflation, this could slow down (but not deterministically halt, since Rust vector iteration and account stores complete, just more slowly) processing of the affected blocks, which matches an "availability / DoS via unbounded epoch-boundary work" class issue rather than a fund-theft or misattribution bug.

## Likelihood Explanation
The precondition requires funding and delegating minimum-delegation stake to many stake accounts before an epoch boundary. Feasibility depends heavily on: (1) whether `upgrade_bpf_stake_program_to_v5`/`_v5_1` is active, since post-activation minimum delegation is 1 SOL per account (making mass account creation capital-intensive, though the capital is not burned, only escrowed), and (2) rent-exemption reserve cost per account, which is a real per-account cost that scales attack cost linearly with account count. This bounds the practical scale of the attack economically even though it is not blocked at the protocol/logic level. I could not fully verify from the available index whether there are additional runtime limits (e.g., on `CreateAccount`/`DelegateStake` transaction throughput per block, cost-tracker per-block compute/account limits) that would further throttle how many such accounts an attacker could actually create per epoch — this would need further investigation in a full checkout of the repo (e.g., `cost_tracker.rs`, stake program CPI limits) to establish a hard ceiling on feasible `total_stake_accounts` growth per epoch.

## Recommendation
Enforce `stake_account_stores_per_block` as a true per-block ceiling independent of the `slots_per_epoch/10` cap — e.g., by increasing the number of partitions beyond `slots_per_epoch/10` when necessary (spilling distribution beyond the "typical" epoch-boundary window, with appropriate handling of `distribution_end_exclusive` reaching into the next epoch), or by processing more than one partition's worth of stores per block while still respecting a fixed maximum total accounts processed per block, so total per-block work is provably bounded by a constant regardless of `total_stake_accounts`.

## Proof of Concept
Extend the existing `test_get_reward_distribution_num_blocks_cap` test (`runtime/src/bank/partitioned_epoch_rewards/mod.rs`) into an invariant/fuzz test:
1. Fix `stake_account_stores_per_block` (e.g., 4096) and `slots_per_epoch` (e.g., 432000).
2. For increasing `num_stakes` values (fuzzed upward, e.g., 10x, 100x, 1000x the naturally expected count for `slots_per_epoch/10 * stake_account_stores_per_block`), call `get_reward_distribution_num_blocks` and `hash_rewards_into_partitions`, then assert:
   - `num_partitions == slots_per_epoch/10` (clamp reached), and
   - `max_partition_size = partition_indices.iter().map(|v| v.len()).max()` grows roughly linearly with `num_stakes` (i.e., is NOT bounded near `stake_account_stores_per_block`).
3. Assert that this violates the intended invariant "per-block distributed stake reward count ≤ `stake_account_stores_per_block`", demonstrating the bound is only nominal once the partition-count clamp is reached.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }

    fn store_stake_accounts_in_partition(
        &self,
        partition_rewards: &StartBlockHeightAndPartitionedRewards,
        partition_index: u64,
    ) -> DistributionResults {
        let feature_snapshot = self.feature_set.snapshot();
        // Name intentionally doesn't match -- "adjust delegations for rent" is
        // part of relaxing post-exec min balance checks.
        let adjust_delegations_for_rent = feature_snapshot.relax_post_exec_min_balance_check;
        let use_fixed_point_stake_math = feature_snapshot.upgrade_bpf_stake_program_to_v5_1;

        let mut stake_reward_lamports_minted = 0;
        let mut stake_reward_lamports_burned = 0;
        let mut block_reward_lamports_distributed = 0;
        let mut block_reward_lamports_burned = 0;
        let indices = partition_rewards
            .partition_indices
            .get(partition_index as usize)
            .unwrap_or_else(|| {
                panic!(
                    "partition index out of bound: {partition_index} >= {}",
                    partition_rewards.partition_indices.len()
                )
            });
        let mut updated_stake_rewards = Vec::with_capacity(indices.len());
        let stakes_cache = self.stakes_cache.stakes();
        let stakes_cache_accounts = stakes_cache.stake_delegations();
        let stake_history = stakes_cache.history();
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let rent = &self.rent_collector.rent;
        for index in indices {
            let partitioned_stake_reward = partition_rewards
                .all_stake_rewards
                .get(*index)
                .unwrap_or_else(|| {
                    panic!(
                        "partition reward out of bound: {index} >= {}",
                        partition_rewards.all_stake_rewards.total_len()
                    )
                })
                .as_ref()
                .unwrap_or_else(|| {
                    panic!("partition reward {index} is empty");
                });
            let stake_pubkey = partitioned_stake_reward.stake_pubkey;
            let stake_reward_amount = partitioned_stake_reward.inflation.stake_reward;
            let block_reward_amount = partitioned_stake_reward.block_reward;

            match Self::build_updated_stake_reward(
                self.epoch,
                stake_history,
                new_warmup_cooldown_rate_epoch,
                stakes_cache_accounts,
                partitioned_stake_reward,
                rent,
                adjust_delegations_for_rent,
                use_fixed_point_stake_math,
            ) {
                Ok(stake_reward) => {
                    stake_reward_lamports_minted += stake_reward_amount;
                    block_reward_lamports_distributed += block_reward_amount;
                    updated_stake_rewards.push(stake_reward);
                }
                Err(err) => {
                    error!(
                        "bank::distribution::store_stake_accounts_in_partition() failed for \
                         {stake_pubkey}, {stake_reward_amount} lamports burned: {err:?}"
                    );
                    stake_reward_lamports_burned += stake_reward_amount;
                    block_reward_lamports_burned += block_reward_amount;
                }
            }
        }
        drop(stakes_cache);
        self.store_accounts(
            (self.slot(), &updated_stake_rewards[..]),
            // Reuse the rewards calculation thread pool to parallelize
            // loading the previous versions of the stake accounts.
            Some(crate::bank::rewards_calculation_thread_pool()),
        );

pub(in crate::bank::partitioned_epoch_rewards) fn hash_rewards_into_partitions(
    stake_rewards: &PartitionedStakeRewards,
    parent_blockhash: &Hash,
    num_partitions: usize,
) -> Vec<Vec<usize>> {
    let hasher = EpochRewardsHasher::new(num_partitions, parent_blockhash);
    let mut indices = vec![vec![]; num_partitions];

    for (i, reward) in stake_rewards.enumerated_rewards_iter() {
        // clone here so the hasher's state is reused on each call to `hash_address_to_partition`.
        // This prevents us from re-hashing the seed each time.
        // The clone is explicit (as opposed to an implicit copy) so it is clear this is intended.
        let partition_index = hasher
            .clone()
            .hash_address_to_partition(&reward.stake_pubkey);
        indices[partition_index].push(i);
    }
    indices
}
