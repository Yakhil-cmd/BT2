### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while handlers act on the independent `repository.full_name` field, letting multi-org Shipit deployments accept forged events for repositories in a different, secured organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against solely from `repository.owner.login` (or `organization.login`) in the untrusted JSON body, but every event `Handler` (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the target `Stack`/`Repository` to mutate from the independent `repository.full_name` field in that same body. In a multi-organization Shipit install, these two fields are never cross-checked, so a payload that names an organization with a weak/absent `webhook_secret` in the `owner.login`/`organization.login` sub-object, but a `full_name` pointing at a repository belonging to a different, properly-secured organization, passes signature verification and is then processed against the other org's stack.

### Finding Description
`verify_signature` computes the verifying organization purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization config (`webhook_secret`, keys) that multi-org installs support, as documented and fixture-backed: [3](#0-2) [4](#0-3) 

Both example/documented configs explicitly allow `webhook_secret` to be `nil` per organization, and `verify_webhook_signature` treats a blank secret as automatically verified: [5](#0-4) [6](#0-5) 

Once `verify_signature` passes (or is skipped because the claimed org has no secret), `create` dispatches the *entire raw payload* to every registered handler for the event: [7](#0-6) 

But the handler base class resolves which repository/stack to act on from a *different* payload field, `repository.full_name`, with no relationship enforced back to the `repository.owner.login`/`organization.login` value used for signature verification: [8](#0-7) 

Concrete handlers then act on whatever stacks match that independently-controlled `full_name`, e.g. `PushHandler` triggers a GitHub resync against the resolved stacks: [9](#0-8) 

This is the same class of bug as the reported issue: a verification/authorization step (`delegateToViewImplementation`/signature check) is bound to one thing (the CToken storage layout/the claiming organization), while the actual state-mutating operation runs against a different, unchecked target (the delegate call that updates state/the repository named in `repository.full_name`). Here the equality that should hold — "organization whose secret authenticated this request" == "organization/repository the mutation is applied to" — is never enforced.

### Impact Explanation
In any Shipit deployment configured for multiple GitHub organizations (the documented "Using Multiple GitHub Applications" setup), if even one configured organization has no `webhook_secret` set (shown as the default/example value in the shipped config templates), an attacker can send a crafted, unsigned or arbitrarily-signed webhook body whose `repository.owner.login` (or `organization.login`) names that weakly-configured org, while `repository.full_name` names a stack belonging to a fully-secured organization. The request passes `verify_signature` and is then processed for the targeted repository. Depending on the event type this reaches:
- `PushHandler` → forces `stack.sync_github` against the targeted repo/stack.
- `MembershipHandler` → creates/deletes `Team`/`Membership` records keyed by attacker-controlled `organization.login` and `member.login`, which is used by `User#authorized?` to gate access to the entire Shipit UI/API via `Shipit.github_teams` — see `app/controllers/concerns/shipit/authentication.rb` and `app/models/shipit/user.rb`. Since team membership can be fabricated for teams not actually reviewed by GitHub, this can escalate an attacker-controlled login into `Shipit.github_teams` authorization, matching the explicitly listed High-severity impact ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
This requires the operator to run Shipit against multiple GitHub organizations (a documented, supported configuration) and to leave at least one organization's `webhook_secret` unset — both are explicitly shown as acceptable/default in the shipped example configs (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `docs/setup.md`). No GitHub App private key, ApiClient token, or repository write access is required by the attacker; only the ability to POST an arbitrary JSON body to the public webhook endpoint. This makes the likelihood moderate: it is entirely configuration-dependent, but the vulnerable configuration is exactly what the project's own documentation and templates present as normal/acceptable.

### Recommendation
- After verifying the signature, re-derive the organization strictly from the same `repository.owner.login`/`organization.login` value and require it to match the organization actually owning the `repository.full_name` used by handlers, rejecting mismatches.
- Consider requiring a non-blank `webhook_secret` for every configured organization (fail closed) rather than silently treating a blank secret as "always verified" in `GitHubApp#verify_webhook_signature`.
- In `Shipit::Webhooks::Handlers::Handler`, validate that the resolved `Repository`/`Stack` actually belongs to the organization that was used to authenticate the webhook before processing.

### Proof of Concept
1. Configure Shipit for two organizations, e.g. `OrgA` (no `webhook_secret` configured) and `OrgB` (a properly configured `webhook_secret`), following `docs/setup.md`'s "Using Multiple Github Applications" section.
2. Craft a `membership` (or `push`) webhook JSON body with:
   - `organization.login` (or `repository.owner.login`) = `"OrgA"`
   - `repository.full_name` = `"OrgB/some-secured-repo"` (for `push`) or `team`/`member` fields naming a team/user relevant to `OrgB`'s stacks (for `membership`)
3. POST this body to `/github/webhooks` with `X-Github-Event` set accordingly; the `X-Hub-Signature` can be omitted or arbitrary since `Shipit.github(organization: 'OrgA').verify_webhook_signature` returns `true` unconditionally because `OrgA`'s `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
4. Observe that `WebhooksController#create` dispatches the payload to `Shipit::Webhooks.for_event('membership')` / `'push'`, and the handler resolves and mutates state for `OrgB`'s stack/team based on `repository.full_name`/`team`/`organization.login`, even though the signature check never validated anything about `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
