### Title
Cross-tenant commit-status forgery via `Commit.where(sha:)` lookup with no repository/stack scoping bypasses `MergeRequest#reject_unless_mergeable!` CI-failure check - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook by SHA alone, across the entire database, with no check that the commit belongs to the repository/organization that produced the (correctly signed) webhook [2](#0-1) . An attacker who owns any repository tracked by this Shipit instance can obtain a real, correctly signed GitHub status webhook for a commit SHA that is shared with a victim's PR (e.g., because the victim's PR branch commit also exists, byte-for-byte, in the attacker's fork before any rebase), causing a fabricated `success` `Status` row to be attached to the victim's commit under the victim's own `stack_id` [1](#0-0) .

### Finding Description
The binding the security model relies on is: *the set of `Status` rows used by `MergeRequest#any_status_checks_failed?` for Victim's PR head == statuses that Victim's own repository/CI legitimately reported for that repository*. This binding is broken because status attribution keys purely on `sha`, not on `(sha, repository)`.

Path:
1. `WebhooksController#verify_signature` validates the HMAC using `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the JSON payload's `repository.owner.login` field [3](#0-2) [4](#0-3) . This only proves the payload was signed by the org named in the payload — it says nothing about which `sha`s the payload may reference.
2. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1)  — a global, unscoped lookup across every stack/repository in the Shipit install.
3. `Commit#create_status_from_github!` writes the new `Status` using the found commit's own `stack_id` [1](#0-0) , so the forged status becomes indistinguishable from a status genuinely reported for the victim's stack.
4. `Status::Group.new` computes `visible_statuses = reject_hidden(statuses.to_a.uniq(&:context))` over `statuses` ordered `created_at: :desc` [5](#0-4) [6](#0-5) . `uniq(&:context)` keeps the first (most recent) entry per context, so a forged `success` status with the same context and a newer `created_at` than the victim's real `failure` status masks it.
5. `MergeRequest#any_status_checks_failed?` and `#reject_unless_mergeable!` consume this masked `Status::Group`, incorrectly concluding CI passed [7](#0-6) .

Attacker's exact action: fork or otherwise obtain a repository containing the exact same commit SHA as the victim's PR head (trivial before a rebase/force-push, since Git commit SHAs are content-addressed and identical across forks); have that repository added as a Shipit-tracked stack (or already own a Shipit-tracked repo) so a legitimate webhook secret is configured for their own org; use the GitHub Statuses API on their own repository to post a `success` status for that shared SHA (or replay/forge locally with their own repo's secret) — GitHub (or the attacker with knowledge of only their own org's secret) delivers a validly signed `status` webhook to Shipit. `verify_signature` passes because the signature matches the attacker's own org's secret and the payload's `repository.owner.login` correctly names the attacker's own org. `StatusHandler` then finds and pollutes the victim's commit purely by SHA match.

Existing guards do not stop this: `verify_signature` authenticates *who signed*, not *which commit the payload may write to*; there is no repository/stack ownership check anywhere between signature verification and `Commit.where(sha:)`.

### Impact Explanation
This allows an unauthenticated-relative-to-victim attacker to inject a fabricated passing CI status into any victim repository/stack tracked by the same Shipit instance, suppressing `ci_failing`/`ci_missing` rejection and enabling `ProcessMergeRequestsJob` to merge code that actually failed CI (`merge_request.merge!`) [8](#0-7) . This is an unauthorized-merge class impact (Critical) and is a genuine cross-tenant write: a payload authenticated for one repository (attacker's) mutates another repository's (victim's) status/commit/merge-request state, matching the Critical criteria in the prompt ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Preconditions: the Shipit instance must host more than one repository/stack (multi-tenant install, common for GitHub orgs with many services), and the attacker must have some Shipit-tracked repository under their control with a colliding SHA against the victim's PR head — trivially arranged by forking the victim's repo before the PR branch is rebased or amended, which is the common case for open PRs. No secrets belonging to the victim, no `api_clients_secret`, and no Shipit session are required — only the attacker's own repo's legitimate webhook delivery. This is realistically exploitable and repeatable against any victim stack sharing a SHA on the same instance.

### Recommendation
Scope the `StatusHandler` (and analogous check-run/commit-status handlers) lookup by repository, not just by SHA — e.g. resolve the `Stack`/`Repository` from the webhook's `repository.full_name` (already authenticated by `verify_signature`'s org check, but must also validate repo name, not just org) and restrict `Commit.where(sha: ..., stack: matching_stacks)`. Alternatively, key commits by `(stack_id, sha)` consistently for any webhook-driven writes and always join through the stack that matches the authenticated `repository.full_name` from the payload, rejecting any request where the payload's repository does not match the commit's own stack's configured GitHub repository.

3. Create `attacker_commit` on `attacker_stack` with the **same** `sha = "deadbeef"`.
4. POST to `/webhooks` with `X-Github-Event: status`, a payload naming `repository.owner.login` as the attacker's org and `sha: "deadbeef", state: "success", context: "ci/circle"`, signed with the attacker's org's real secret (as `webhooks_controller_test.rb` does via `Shipit.github(organization: 'attacker').verify_webhook_signature` stubbing/real HMAC).
5. Assert equality violated: before request, `victim_commit.statuses.where(context: 'ci/circle').first.state == 'failure'`; after request, assert a new `success` `Status` row was created with `stack_id == victim_stack.id` (i.e. `victim_commit.statuses.count` increased) even though the signed request only authenticated `attacker_stack`.

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(

        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)

        # branch was already deleted somehow
      end
      complete!
      true

      false

    end
