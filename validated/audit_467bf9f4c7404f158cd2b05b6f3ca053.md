### Title
Missing parentheses in `OpenedHandler#provision?` let `review_stacks_enabled: false` be bypassed for `allow_with_label`/`prevent_with_label` repos - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` combines `repository.review_stacks_enabled` with three provisioning-behavior clauses using `&&`/`||` without parentheses, so `review_stacks_enabled` only gates the `allow_all` branch. Any PR opened against a repository configured with `provisioning_behavior_allow_with_label?` or `provisioning_behavior_prevent_with_label?` will provision a review stack even when `review_stacks_enabled` is `false`. By contrast, `UnlabeledHandler`/`LabeledHandler` correctly AND `review_stacks_enabled` with the entire `archive?`/`unarchive?` disjunction at the `respond_to_label_change?` level, so they are not affected.

### Finding Description
The broken binding: the intended equality is `provision? == (review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)))`, but the actual code in [1](#0-0)  parses (per Ruby operator precedence, `&&` binds tighter than `||`) as:

`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

This means when `review_stacks_enabled == false`, the first disjunct is `false`, but the second and third disjuncts are evaluated independently of `review_stacks_enabled` and can still be `true`.

Attack: for a repository with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (with a configured `provisioning_label_name`), an unprivileged GitHub user opens a pull request and adds the provisioning label to it (or, for `prevent_with_label`, simply opens a PR without the label). The `opened` webhook fires `OpenedHandler#process` → `respond_to_pull_request_opened?` → `provision?` returns `true` despite `review_stacks_enabled` being `false`, and `ReviewStackAdapter#find_or_create!` creates a `Shipit::Stack` for that repository [2](#0-1) .

Contrast/control case: `UnlabeledHandler#respond_to_label_change?` places `repository.review_stacks_enabled` as a top-level `&&` term ANDed against the full `(archive? || unarchive?)` expression [3](#0-2) , so when `review_stacks_enabled` is `false` the whole expression short-circuits regardless of `archive?`/`unarchive?` values — this is the correct pattern and confirms `OpenedHandler#provision?` is a distinct coding defect (missing parentheses), not a documented/shared behavior. `LabeledHandler` follows the identical correct pattern [4](#0-3) .

No existing guard prevents this: `verify_signature`/webhook signature checks only authenticate that GitHub sent the payload, not the semantic content; `drop_unhandled_event` doesn't apply since `opened` is handled; the `ExplicitParameters` schema only validates payload shape; there is no re-check of `review_stacks_enabled` downstream in `ReviewStackAdapter#find_or_create!`.

### Impact Explanation
An attacker who can open a pull request (and, for the `allow_with_label` case, apply a label to their own PR — both within the stated unprivileged capabilities) can cause `Shipit` to create a `Shipit::Stack`/`ReviewStack` record for a repository whose operator explicitly disabled review stacks (`review_stacks_enabled: false`). This is a record written for a repository under conditions the operator's own configuration was meant to prevent, and it seeds downstream provisioning (stack awaiting provision), which can lead to an unauthorized deploy/provision task being queued for that repository. This matches the Critical category "a payload... resulting in an unauthorized deploy" — scoped to repositories that have been configured with `provisioning_behavior: allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is `false`. It is repeatable against any such repository, once per PR/label toggle, but is confined to `OpenedHandler`; `UnlabeledHandler`/`LabeledHandler` are not affected, so the window is limited to the `opened` event.

### Likelihood Explanation
Requires the target repository to have `review_stacks_enabled: false` combined with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a plausible transitional/misconfiguration state, e.g., an operator disabling review stacks without resetting `provisioning_behavior` back to `allow_all`). No secrets or elevated privileges are needed — only the ability to open a PR against the repo (and label it, for the `allow_with_label` case), which matches the stated attacker capabilities.

### Recommendation
Add explicit parentheses in `provision?` so `review_stacks_enabled` gates the entire disjunction:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style:
```ruby
test "does not create stacks for allow_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  # Binding under test: provision? should equal
  # (review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || ...))
  # i.e. false, since review_stacks_enabled is false.
  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end

test "control: UnlabeledHandler does not act when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_unlabeled) # analogous fixture
  assert_no_difference -> { Shipit::Stack.count } do
    UnlabeledHandler.new(payload).process
  end
end
```
The first test currently fails (asserts `assert_no_difference` but a stack is created), proving `OpenedHandler#provision?` bypasses `review_stacks_enabled`; the second test passes, confirming `UnlabeledHandler` correctly enforces the flag.
