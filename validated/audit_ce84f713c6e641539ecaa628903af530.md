## Validate

**Binding claimed:** `repository.review_stacks_enabled` (value read by `ReopenedHandler#unarchive?` at reopen time) == `repository.review_stacks_enabled` (value that should gate `ReviewStackAdapter#unarchive!`'s re-provisioning).

Tracing the code shows the premise in the question is imprecise — `ReviewStackAdapter#unarchive!` itself has no gate, but `ReopenedHandler#process` does call a gate (`respond_to_pull_request_reopened?` → `unarchive?`) before invoking `stack.unarchive!`, analogous to `OpenedHandler#provision?`. So the real defect is not "no gate at all" — it's that the gate is *broken by operator precedence* for two of the three `provisioning_behavior` configurations. [1](#0-0) 

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

`&&` binds tighter than `||` in Ruby, so this parses as:

```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)
```

`review_stacks_enabled` is only ANDed with the first disjunct (`allow_all?`). For `provisioning_behavior == "prevent_with_label"`, the third disjunct fires whenever the PR lacks the preventing label — the **default state of any PR** — completely independent of `review_stacks_enabled`. The same is true for `allow_with_label?` if the label happens to be present.

This is inconsistent with the sibling handler, which correctly gates the whole decision on `review_stacks_enabled`: [2](#0-1) 

For the default configuration (`provisioning_behavior: allow_all`, which is also the DB default), the AND correctly gates the flag, so disabling review stacks does stop reopen re-provisioning — no bug in that specific case, matching test `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb:130-144` and `146-161` (behaviorally exercised, though not with `review_stacks_enabled: false` explicitly). But for `allow_with_label` / `prevent_with_label` configurations, the binding breaks, and the same defect independently exists in `OpenedHandler#provision?` (identical precedence pattern), meaning it isn't limited to reopen/unarchive. [3](#0-2) 

### Title
Operator-precedence bug in `ReopenedHandler#unarchive?` bypasses `review_stacks_enabled` for non-`allow_all` provisioning behaviors - (File: `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`)

### Summary
`ReopenedHandler#unarchive?` intends `repository.review_stacks_enabled` to globally gate re-provisioning on PR reopen, but due to Ruby `&&`/`||` precedence, the flag is only ANDed with the `allow_all` branch. When a repository is configured with `provisioning_behavior: prevent_with_label` (or `allow_with_label` with the label present), disabling `review_stacks_enabled` does not prevent `ReviewStackAdapter#unarchive!` from re-queuing and re-provisioning a previously archived stack.

### Finding Description
The broken binding: `review_stacks_enabled` value consulted for the `allow_all` path == `review_stacks_enabled` value consulted for the `allow_with_label`/`prevent_with_label` paths. This equality fails because of operator precedence in `unarchive?`: [4](#0-3) 

Call path: attacker (owner of the fork/PR) reopens their own previously-archived PR → webhook `pull_request.reopened` → `ReopenedHandler#process` → `respond_to_pull_request_reopened?` → `unarchive?` evaluates true (because `prevent_with_label? && !has_label` is true regardless of `review_stacks_enabled`) → `stack.unarchive!` → `ReviewStackAdapter#unarchive!` re-adds the stack to `ReviewStackProvisioningQueue` and calls `stack.unarchive!`: [5](#0-4) 

This triggers a `GithubSyncJob` and eventual re-provisioning from the current HEAD SHA of the attacker's branch (confirmed by `test/models/shipit/review_stack_test.rb:67-76`), which runs `shipit.yml` provisioning steps. Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) do not address this because the payload is a legitimate, correctly-signed `reopened` event — the defect is purely a logic/precedence error in the authorization predicate, not a signature or schema bypass.

### Impact Explanation
An operator who disables Review Stacks (unchecks `review_stacks_enabled`) on a repository configured with `prevent_with_label` (or `allow_with_label` with an already-applied label) does not actually stop dynamic provisioning for reopened PRs. The attacker (any GitHub user who can open/reopen a PR against the repo) can push new commits to their branch before reopening, and those commits' `shipit.yml` steps get executed on re-provisioning — an unauthorized command execution that should have been blocked by the disabled flag. This is scoped to the specific repository whose `provisioning_behavior` is non-`allow_all`; it does not cross tenant boundaries to other repositories. Matches Critical: a command runs (`shipit.yml` provisioning steps) that should not, driven by attacker-controlled commits.

### Likelihood Explanation
Requires: (1) the repository previously had review stacks enabled and provisioning_behavior set to `prevent_with_label` or `allow_with_label`, (2) an archived `ReviewStack` already exists for the attacker's PR, (3) operator later disables `review_stacks_enabled` without also resetting `provisioning_behavior` to `allow_all`. This is not the default configuration (`allow_all` is the migration default), so likelihood depends on operator's specific settings choice, but is entirely plausible for teams using opt-out labeling. No secrets or privileges are needed by the attacker — only the ability to reopen their own PR.

### Recommendation
Fix operator precedence in both `ReopenedHandler#unarchive?` and the identically-flawed `OpenedHandler#provision?` by parenthesizing `review_stacks_enabled` as a top-level AND over the entire behavior disjunction, mirroring `LabeledHandler#respond_to_label_change?`:
```ruby
def unarchive?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`, add:
```ruby
test "does not unarchive stacks when review_stacks_enabled is false, even with prevent_with_label and no label" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = []

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  assert stack.reload.archived?, "Expected stack to remain archived because review_stacks_enabled is false"
end
```
Given current code, `unarchive?` evaluates to `true` (via the `prevent_with_label? && !has_label` branch) despite `review_stacks_enabled == false`, so `stack.reload.archived?` is `false` and this assertion fails — proving the equality binding breaks for this configuration.
