### Title
Any genuinely-signed org's `membership` webhook can write to arbitrary `Shipit.github_teams` Teams via `MembershipHandler` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::Webhooks.for_event('membership')` unconditionally returns `[MembershipHandler]` for every organization configured in Shipit, and `MembershipHandler#process` resolves the target `Team` purely by `params.team.id` via `Team.find_or_create_by!(github_id: params.team.id)` with no check that `params.organization.login` matches the team's already-stored `organization`. Since `verify_signature` only validates that the payload was signed by *some* configured `Shipit.github(organization: repository_owner)` app - not that that org is the authority backing `Shipit.github_teams` - a legitimately configured but unrelated org can mutate `Membership` rows for a team belonging to a different, authoritative org.

### Finding Description
The binding that should hold is: `params.organization.login == team.organization` for any Team record mutated by a `membership` webhook, or more precisely, `webhook-verified-org ∈ {orgs backing Shipit.github_teams}` before `Membership` is created/deleted. This binding is never checked.

Path: `WebhooksController#create` [1](#0-0)  calls `Shipit::Webhooks.for_event(event)`, which statically returns `[Handlers::MembershipHandler]` for the `'membership'` event regardless of which org signed the request [2](#0-1) . The only gate before dispatch is `verify_signature`, which resolves `Shipit.github(organization: repository_owner)` from the payload's own `repository.owner.login`/`organization.login` and checks the HMAC signature against *that org's* configured `webhook_secret` [3](#0-2) . This only proves "some configured org's app genuinely emitted this payload" - it says nothing about whether that org is authorized to write into `Shipit.github_teams`.

Inside `MembershipHandler#process`, the team is looked up/created solely by `github_id` [4](#0-3) :
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```
`find_or_create_by!` only sets `organization` on *creation*; if a `Team` with that `github_id` already exists (e.g., created earlier from orgA's real membership sync backing `Shipit.github_teams`), the block is skipped and the existing record - regardless of its `organization` column - is returned and mutated via `team.add_member(member)` / `team.members.delete(member)`. Nothing compares `params.organization.login` to the found team's `organization`, and nothing checks that `repository_owner`/`organization.login` from the verified webhook is even a member of `Shipit.github_teams`' backing org(s) (`Shipit.github_teams` is a derived, unrelated attribute of `Shipit` module config, not consulted here at all - see `Shipit.github_teams` at [5](#0-4) ). `User#authorized?` then trusts `teams.where(id: Shipit.github_teams.map(&:id))` [6](#0-5) , so a `Membership` row written by an unrelated org's webhook is indistinguishable from one written by the authoritative org.

Attack: attacker (or any GitHub org admin of orgB, which is configured in Shipit purely for CI push/status webhooks) sends a real `membership` webhook from orgB, naming `team.id` equal to an existing authorization team's `github_id` (these IDs are enumerable/guessable, or discoverable via any public GitHub API team lookup) and `member.login` equal to the attacker's own GitHub login. Since orgB's app is genuinely configured and the signature is valid for orgB's secret, `verify_signature` passes, `for_event('membership')` returns the handler regardless of org, and `find_or_create_team!` finds the existing (orgA-owned) `Team` row and adds the attacker as a member, granting `authorized?` == true.

### Impact Explanation
The attacker gains membership in a `Shipit.github_teams`-backing `Team`, which flips `User#authorized?` to `true` for their account, escalating an unrelated/unprivileged GitHub identity into Shipit's authorization boundary. This is repeatable against any team `github_id` and any `member.login`, and blast radius spans every organization configured in the Shipit deployment for unrelated purposes (any of them can be abused this way), not just the authoritative org. This matches "escalation into `Shipit.github_teams` authorization" (High per the provided severity taxonomy).

### Likelihood Explanation
Preconditions: a multi-org Shipit deployment where `Shipit.github_organizations` includes more than one org (some are legitimate but unrelated to `Shipit.github_teams`), and the attacker (or a party controlling any such secondary org) can send a genuinely GitHub-signed `membership` event - i.e., they administer/own that org's GitHub App installation, or convince/wait for GitHub to fire this event naturally. Attacker cost is low: they need control (as an org admin) of any one configured secondary org and knowledge of a target team's numeric `github_id` (discoverable). No Shipit secrets, sessions, or API tokens are required. Feasible and repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!` / `#process`, verify that `params.organization.login` matches the org(s) actually backing `Shipit.github_teams` (or matches the existing `team.organization` when the team already exists) before creating/mutating memberships; reject/no-op otherwise. More generally, `Webhooks.for_event`/`WebhooksController` should enforce a per-event, per-organization allow-list so that only the org(s) configured as the identity authority can dispatch to `MembershipHandler`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb
test "membership webhook from an unrelated org can mutate a team belonging to another org" do
  # Team already exists, created under orgA (the authoritative org backing Shipit.github_teams)
  team = Team.create!(github_id: 4242, organization: 'orgA', slug: 'authz-team', name: 'Authz Team', api_url: 'https://api.github.com/teams/4242')

  attacker = User.find_or_create_by_login!('attacker-login')
  refute team.members.include?(attacker)

  # Genuinely signed webhook, but from orgB (unrelated org, configured only for push/status events)
  params = ExplicitParameters::Params.new(
    action: 'added',
    team: { id: 4242, name: 'Authz Team', slug: 'authz-team', url: 'https://api.github.com/teams/4242' },
    organization: { login: 'orgB' }, # <-- mismatched org
    member: { login: 'attacker-login' }
  )

  Shipit::Webhooks::Handlers::MembershipHandler.new(params).process

  team.reload
  assert team.members.include?(attacker), "attacker was added to orgA's authorization team via orgB's webhook"
  # Binding params.organization.login == team.organization is violated: 'orgB' != 'orgA', yet mutation succeeded
end
```
This demonstrates the equality `params.organization.login == team.organization` does not hold, yet `Membership` is created regardless, confirming the described authorization gap.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
