## Finding: Confirmed

### Title
`repository.review_stacks_enabled` is not enforced for `allow_with_label` / `prevent_with_label` provisioning due to `&&`/`||` operator-precedence bug - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`provision?` in `OpenedHandler` (and the equivalent `unarchive?` in `ReopenedHandler`) is written as `A && B || C || D`, so Ruby's operator precedence only gates the `allow_all` branch (`B`) with `review_stacks_enabled` (`A`); the `allow_with_label` and `prevent_with_label` branches (`C`, `D`) are evaluated independently of `review_stacks_enabled`. This lets a repository with `review_stacks_enabled == false` still provision review stacks.

### Finding Description
The claimed binding — `pull_request_has_provisioning_label? == true` must not, by itself, substitute for `repository.review_stacks_enabled == true` — is broken. The code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. `review_stacks_enabled` never gates the last two disjuncts. The same flawed pattern exists in `ReopenedHandler#unarchive?` at [2](#0-1) .

This is contrasted by the *correct* pattern used in `LabeledHandler#respond_to_label_change?`, where `review_stacks_enabled` is combined with `&&` across the whole condition, correctly gating every branch: [3](#0-2) .

Exploit flow: a repository owner sets `provisioning_behavior = allow_with_label` but disables review stacks (`review_stacks_enabled = false`), expecting no stacks to ever be created. Any user who can open a pull request against that repository and get the `provisioning_label_name` label applied (self-application possible if the repo grants Triage/label permissions broadly, or the label is added by any automation/bot with less-than-full trust) causes `pull_request_has_provisioning_label?` to be true. `provision?` then evaluates true purely from the second disjunct, bypassing the intended `review_stacks_enabled` kill switch, and `ReviewStackAdapter#find_or_create!` creates and enqueues a real `ReviewStack` for provisioning: [4](#0-3) , [5](#0-4) .

Separately (and more directly reachable without needing any label at all), for `provisioning_behavior = prevent_with_label` and `review_stacks_enabled = false`, simply opening a PR with no labels satisfies `!pull_request_has_provisioning_label?` and again bypasses the `review_stacks_enabled` gate. No signature-verification, `ExplicitParameters` schema, or model validation intercepts this because none of them check the provisioning-behavior logic — that logic error is purely internal to `provision?`.

### Impact Explanation
An unauthorized `Shipit::ReviewStack` (and its provisioning job/queue entry) is created for a repository whose operator explicitly disabled review-stack provisioning. This causes unintended infrastructure/deploy-pipeline actions (stack creation, provisioning queue enqueue, potential downstream task/deploy execution against attacker-controlled branch/environment values from the PR) to run against a repository that never authorized it. This matches "a payload for one repository mutating another's stack" / "unauthorized deploy" category at least at Critical-adjacent severity for stack creation; repeatable against any repository misconfigured this way, once per PR/label event.

### Likelihood Explanation
Requires: `repository.review_stacks_enabled == false` combined with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a plausible/likely real-world configuration for "review stacks temporarily disabled" while keeping the per-label workflow configured). For `prevent_with_label`, exploitation needs nothing beyond opening a PR — zero extra privilege. For `allow_with_label`, exploitation needs the attacker (or any actor) to get the exact label applied, which may require some GitHub-side permission depending on repo settings, but no Shipit-side privilege whatsoever. This is a genuine, signed webhook (GitHub actually sends it because the real event occurred), so `verify_signature`/`GitHubApp#verify_webhook_signature` do not block it.

### Recommendation
Fix the operator precedence in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` so `review_stacks_enabled` gates every branch, matching the pattern already used in `LabeledHandler`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "#process does not provision when review_stacks_enabled is false even with provisioning label present (allow_with_label)" do
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: 'allow_with_label',
    provisioning_label_name: 'deploy-preview'
  )
  params.pull_request.labels = [{ name: 'deploy-preview' }]

  handler = Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params)
  assert_no_difference -> { Shipit::ReviewStack.count } do
    handler.process
  end
end

test "#process does not provision when review_stacks_enabled is false with no label (prevent_with_label)" do
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: 'prevent_with_label',
    provisioning_label_name: 'no-deploy'
  )
  params.pull_request.labels = []

  handler = Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params)
  assert_no_difference -> { Shipit::ReviewStack.count } do
    handler.process
  end
end
```
Both assert `repository.review_stacks_enabled == false` implies `provision?`/stack-creation must be false; under current code both fail (a `ReviewStack` is created), demonstrating the bypass.
