### Title
Direct token transfers to the pool are permanently lost and become withdrawable liquidity for other users - ([File: contracts/pool/src/cache/cash.rs])

### Summary
Tokens sent directly to the liquidity pool are not credited to the sender or to market `cash`, but they remain part of the pool’s single physical token balance and can subsequently be transferred to unrelated borrowers or suppliers. [1](#0-0) [2](#0-1) 

### Finding Description
The pool credits `cash` only through pool operations such as `supply`, where the controller first transfers and measures the received amount. [3](#0-2) [4](#0-3) 

A direct token transfer bypasses this path, so the donated amount does not create supply shares, debt repayment, recapitalization credit, or any sender-owned claim. [5](#0-4) [6](#0-5) 

All pool mutators are owner-only, and the public pool interface contains no permissionless rescue or surplus-balance withdrawal function. [7](#0-6) [8](#0-7) 

Normal withdrawals burn only the claimant’s shares and debit only booked `cash`, but `transfer_out` sends tokens from the pool’s total physical balance without distinguishing donated funds. [9](#0-8) [2](#0-1) 

### Impact Explanation
A user who directly transfers a listed token to the pool permanently loses those funds, while other users can receive the donated balance through ordinary `withdraw` or `borrow` payouts. [2](#0-1) 

This is theft or permanent loss of user funds rather than a mere accounting discrepancy because the donation becomes indistinguishable protocol liquidity and can be consumed by unrelated positions. [10](#0-9) [2](#0-1) 

### Likelihood Explanation
The trigger requires a user to bypass the controller and directly call the token contract’s `transfer` to the pool, rather than using `Controller::supply`, `repay`, or `recapitalize`. [11](#0-10) [12](#0-11) 

The protocol’s measured-payment paths refund overpayments, which reduces accidental occurrences, but the vulnerable direct token call remains available to any unprivileged address. [13](#0-12) [14](#0-13) 

### Recommendation
Track an explicit surplus allowance of `token.balance(pool) - aggregate_booked_cash` and provide a bounded recovery path for accidental senders, or route provable surplus to protocol revenue. [15](#0-14) 

If returning funds to arbitrary historical senders is impractical, at minimum expose an owner-authorized sweep limited to unbooked physical surplus so those funds cannot silently subsidize unrelated withdrawals. [8](#0-7) [2](#0-1) 

### Proof of Concept
1. Bob supplies `100` units of a listed asset through `Controller::supply`, causing the controller to transfer the measured amount to the pool and the pool to credit `cash`. [16](#0-15) [3](#0-2) 

2. Alice directly invokes `token.transfer(Alice, pool, 50)` on the same asset without calling a controller endpoint. [4](#0-3) 

3. The pool’s physical balance becomes `150`, while market `cash` and Bob’s shares still represent only `100`; Alice receives no position or claim. [17](#0-16) [18](#0-17) 

4. Bob calls `Controller::withdraw(caller = Bob, account_id, withdrawals = [(hub_asset, 100)], to = Bob)`. [19](#0-18) 

5. The pool debits `100` of booked cash and executes `token.transfer(pool, Bob, 100)` from the combined physical balance, consuming Alice’s donated `50` along with Bob’s deposit. [10](#0-9) [2](#0-1) 

6. Alice cannot recover the `50` through `Controller::withdraw` because she received no supply shares, and cannot call a pool rescue function because all pool mutators are owner-only and no rescue endpoint exists. [19](#0-18) [7](#0-6)

pub fn transfer_amount_measured(
    env: &Env,
    asset: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
    non_positive_error: GenericError,
) -> i128 {
    assert_with_error!(env, amount > 0, non_positive_error);
    let tok = token::Client::new(env, asset);
    let pre = tok.balance(to);
    tok.transfer(from, to, &amount);
    let post = tok.balance(to);
    post.checked_sub(pre)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::AmountMustBePositive))

/// Enforces reserve, utilization, and solvency guards, then debits cash for
/// the net transfer. Liquidations and footprint-only closes skip utilization.
fn gate_and_debit(env: &Env, cache: &mut Cache, net_transfer: i128, skip_utilization_check: bool) {
    cache.require_reserves(net_transfer);

    if !skip_utilization_check {
        guards::require_utilization_below_max(env, cache);
    }
    guards::require_supply_for_debt(env, cache);
    cache.debit_cash(net_transfer);
}

pub(crate) fn recapitalize(
    env: &Env,
    payer: Address,
    hub_asset: HubAssetKey,

        &pool_addr,
        amount,
        GenericError::AmountMustBePositive,
    );
