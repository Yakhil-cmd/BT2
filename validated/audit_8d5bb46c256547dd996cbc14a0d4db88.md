### Title
`Api::CCMenuController` lets a single "CCMenu Client" token read any stack's deploy/rollback status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController#authenticate_api_client` and `#stack` both bypass `Api::BaseController#stacks`, the only place that enforces `current_api_client.stack_id == requested stack`. Combined with `CCMenuUrlController#fetch` minting an `ApiClient` that is never bound to a particular stack in the first place, any holder of a CCMenu token (which is designed to be handed to unauthenticated CI-badge tools) can request `GET /api/1/stacks/:stack_id/cc.xml?token=<t>` for any `stack_id`, not just the one for which the URL was generated.

### Finding Description
The claimed binding is: `stack resolved for the request` == `current_api_client.stack_id` (when the client is stack-scoped). Tracing the code:

- `Api::BaseController#stacks` is the only method that enforces this binding: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `#stack` calls `stacks.from_param!(params[:stack_id])` [1](#0-0) .
- `Api::CCMenuController` overrides both hooks: `#authenticate_api_client` calls `ApiClient.authenticate(params[:token])` directly, and `#stack` calls `Stack.from_param!(params[:stack_id])` directly, never touching `stacks` [2](#0-1) .
- `ApiClient#check_permissions!` (used by `require_permission :read, :stack`) only checks the permission string `"read:stack"` and never checks `stack_id` at all [3](#0-2) .
- Critically, `CCMenuUrlController#fetch` never sets a `stack` on the client it mints: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — keyed only by `creator` and `name`, so **one client per user is reused across every stack** they've ever fetched a CCMenu URL for [4](#0-3) .

Because `stack_id` is never populated on this `ApiClient`, `current_api_client.stack_id?` is always false, so even the inherited `stacks` scope in `BaseController` would resolve to `Stack.all` for this client — the per-stack binding never existed for CCMenu tokens in the first place. `Api::CCMenuController`'s override is a second, independent bypass of the same missing enforcement, but the root defect is that CCMenu tokens are never bound to a stack at mint time.

Exploit flow: User A (any legitimate Shipit user) opens stack A's settings and clicks "Fetch URL," calling `CCMenuUrlController#fetch`, which returns `.../api/1/stacks/A/cc.xml?token=<t>`. User A pastes this into a public CI badge/README as intended (it's designed for unauthenticated third-party consumption). An attacker who sees that public URL can request `GET /api/1/stacks/B/cc.xml?token=<t>` for any other stack `B` and receive stack B's deploy/rollback XML, because `<t>` authenticates the same client regardless of `stack_id`, and `stack_id` binding is never checked anywhere on this path.

### Impact Explanation
An attacker with no session, no repository permission on stack B, and no knowledge of stack B's own token can read stack B's `deploys_and_rollbacks` state (last build status, label, time, running state) via `Api::CCMenuController#show` rendering `shipit/ccmenu/project` [5](#0-4) . This is repeatable against every stack on the instance using a single leaked token, cross-tenant, matching the "High - unauthenticated read of stack state" impact category.

### Likelihood Explanation
The only precondition is that one legitimate user has ever generated and publicly exposed a CCMenu URL (the documented intended use for CI badges), which is a normal, expected occurrence. No secrets, sessions, or privileged roles are needed by the attacker; they only need to change the `stack_id` path segment of an otherwise-public URL. Cost is a single unauthenticated HTTP request per target stack.

### Recommendation
Bind the `ApiClient` created by `CCMenuUrlController#fetch` to the specific stack (e.g. include `stack:` in the `find_or_create_by!`/`create_with` call, scoped per stack rather than reused per user), and make `Api::CCMenuController` use the inherited `Api::BaseController#stacks`/`#stack` methods (or otherwise verify `current_api_client.stack_id == stack.id`) instead of resolving `Stack.from_param!(params[:stack_id])` directly.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token minted for stack A cannot render stack B's deploy state" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.create!(owner: 'foo', name: 'bar'), branch: 'main')

  session[:user_id] = shipit_users(:walrus).id
  get :fetch, params: { stack_id: stack_a.to_param } # CCMenuUrlController#fetch
  token = Rack::Utils.parse_nested_query(URI(JSON.parse(response.body)['ccmenu_url']).query)['token']

  # Binding under test: stack requested via params[:stack_id] == current_api_client.stack_id
  client = ApiClient.authenticate(token)
  assert_nil client.stack_id # client is not bound to stack_a at all

  get :show, params: { stack_id: stack_b.to_param, token: token } # Api::CCMenuController#show
  assert_response :ok # currently passes -> confirms unauthorized cross-stack read
  assert_payload 'name', stack_b.to_param
end
```
