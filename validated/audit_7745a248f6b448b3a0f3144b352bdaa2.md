### Title
Cross-tenant CI status forgery via `StatusHandler#process` allows a foreign, webhook_secret-verified repository to downgrade a victim commit's CI state from `success` to `error`/`failure`, flipping `Commit#deployable?` to `false` and blocking legitimate continuous deployment - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves commits solely by `sha`, without verifying that the webhook's authenticated `repository_owner`/org actually owns the `stack_id` of the matched `Commit` records. Any repository that can pass `WebhooksController#verify_signature` for its own org (a trivial precondition for its own repo) can push a `status` event with a sha that also exists in a victim's stack (e.g. because the attacker forked the victim repo and both share commit history), causing the victim commit's status - and therefore `Commit#deployable?` - to be corrupted.

### Finding Description
The broken binding is: `commit.stack_id == authenticated_repository.stack_id` should hold before any write is applied by `create_status_from_github!`, but the actual code performs: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` iterates over **every** `Commit` record across **all** stacks that share that sha, with no scoping by `stack_id`, `repository`, or `repository_owner`.

Upstream, `WebhooksController#verify_signature` only proves that the payload's `repository.owner.login` matches an org known to `Shipit.github(organization: repository_owner)` - it verifies the sender is a legitimate GitHub org, not that the sender is authorized to write status for the specific commit/stack referenced by `params.sha`: [2](#0-1) 

So an attacker who owns/administers their own repository (satisfying `verify_signature` for their own org) can send a `status` webhook whose `sha` collides with a commit that also exists in a victim's stack (trivially achievable via a fork sharing history, or any coincidental shared commit sha across stacks). The handler applies the status write to the victim's `Commit` regardless of which org sent it.

The write path is `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb`), which creates a `Status` scoped to the victim's `stack_id` from data supplied entirely by the attacker's request (`state: 'error'`).

`Commit#deployable?` directly depends on the aggregated status: [3](#0-2) 

Given `success? && !blocked?` is required for `true`, injecting an `error` status flips it to `false`, and `status` is memoized via `Status::Group.compact` recomputed after `reload`.

None of the existing guards prevent this: `verify_signature` checks org-level HMAC validity, not per-commit/stack ownership; `ExplicitParameters` (`status_handler.rb:7-18`) only validates payload shape (`sha`, `state`, etc.), not scope; there is no `stacks`/`current_api_client.stack_id` check anywhere in this handler.

### Impact Explanation
A cross-tenant write: a request authenticated only for the attacker's own repository/org mutates a `Status` record (and therefore `Commit#deployable?`) belonging to a victim's `Stack`. This blocks the victim's continuous deployment (`Stack#continuous_deployment?` / `schedule_continuous_delivery`) and can also stall auto-merging (`stack.schedule_merges` is only triggered on `pending?`/`success?`, not `error`), effectively sabotaging the victim's release pipeline. This is repeatable against any sha shared across two stacks (most straightforwardly a fork tracked as its own Shipit stack) and requires no privilege beyond controlling one's own repository's webhook delivery/secret - matching the "payload for one repository mutating another's stack/commit" Critical category.

### Likelihood Explanation
Preconditions: the attacker must control a GitHub repository that is registered as a Shipit stack (or otherwise able to complete `verify_signature` for its own org), and a commit sha that is shared between the attacker's stack and the victim's stack - most realistically achieved by forking the victim repository so that both stacks track overlapping commit history. No Shipit secrets, session, or API token are needed; the attacker only needs their own repo's normal GitHub webhook delivery (or the ability to POST a well-formed status payload with a valid signature for their own configured GitHub App/org). This is a low-cost, repeatable attack limited only by the need for a shared sha between the two stacks.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to only those commits whose `stack`/`repository` matches the authenticated `repository_owner`/`repository.full_name` from the webhook payload (e.g., join through `Stack#repository` and filter `Commit.where(sha: params.sha, stack: Stack.where(repository: matching_repo))`), so a status update can only be applied to commits belonging to the stack corresponding to the org/repo that signed the webhook.

### Proof of Concept
```ruby
test "a foreign, differently-owned stack cannot downgrade another stack's commit status via StatusHandler" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, message: 'victim commit')
  victim_commit.statuses.create!(stack: victim_stack, state: 'success', context: 'ci', description: 'ok')
  assert_equal true, victim_commit.reload.deployable?

  attacker_stack = shipit_stacks(:cyclimse) # unrelated stack/org, verified via its own webhook_secret
  # simulate a sha collision (e.g. shared fork history) and forge a foreign-org status webhook
  Shipit::Webhooks::Handlers::StatusHandler.new(
    sha: victim_commit.sha,
    state: 'error',
    context: 'ci',
    description: 'forged failure'
  ).process

  assert_equal false, victim_commit.reload.deployable?, "victim commit's deployable? should not be flippable by an unrelated, verified-for-its-own-org repository"
end
```
