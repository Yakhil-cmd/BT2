### Title
`StatusHandler#process` updates commit statuses across all stacks by `sha` alone, with no `repository` binding, while `PullRequest` handlers correctly scope to `repository` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target records via `Commit.where(sha: params.sha)` with no reference to the webhook's `repository` field, whereas `PullRequest::OpenedHandler` (and its siblings) explicitly derive `repository` from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` before acting. Because `Commit#stack_id` is not part of the lookup, a validly-signed `status` webhook for repository A can mutate `Commit`/`Status` rows that belong to a `Stack` bound to a different repository B, as long as both stacks happen to contain a commit row with the same `sha`.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`payload.repository.full_name == commit.stack.repository.github_repo_name` is enforced in `PullRequest::OpenedHandler#repository` (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`) via `Shipit::Repository.from_github_repo_name(params.repository.full_name) || Shipit::NullRepository.new`, but is never checked in `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`). [1](#0-0) [2](#0-1) 

`Handler` (the shared base class) already implements the correct binding as a reusable private helper: `repository_name` extracts `payload.dig('repository', 'full_name')` and `stacks` resolves `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`, i.e. the primitive for repository-scoped queries exists in the engine. [3](#0-2) 

`StatusHandler#process` never calls `stacks` or `repository_name`; it looks up `Commit.where(sha: params.sha)` globally and calls `commit.create_status_from_github!(params)` for every match, across all stacks in the installation. [1](#0-0) 
`Commit` belongs to exactly one `stack` (`belongs_to :stack`), and there is no uniqueness constraint or scoping tying `sha` to a particular repository at the query level in this handler. [4](#0-3) 

`create_status_from_github!` writes a new `Status` row (`statuses.replicate_from_github!(stack_id, github_status)`) and recomputes the commit's aggregate status, which can trigger deploy-affecting side effects: `Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges` — i.e. state changes that can influence continuous deployment/merge decisions for the victim stack. [5](#0-4) [6](#0-5) 

Attacker request/path: the attacker owns repository A with a GitHub App/webhook installation pointed at the Shipit host (a legitimate, allowed action per the threat model — "emit webhooks from a repository they own"). `WebhooksController#verify_signature` computes `Shipit.github(organization: repository_owner)` from `params.dig('repository', 'owner', 'login')` and validates HMAC against the real GitHub-computed signature for that org/app installation. [7](#0-6) 
This signature check is *sound* and cannot be forged for a different `repository_owner` without that org's webhook secret — so the attacker cannot literally set `repository.full_name` to `orgB/repo` and get a valid signature. The vulnerability is not signature forgery; it is that `StatusHandler` ignores `repository`/`repository_name` entirely and matches purely on `sha`. If a `sha` value present in the attacker's own repository A's commit history also exists as a `Commit` row belonging to stack for repository B (a realistic scenario for forks/mirrors/shared-history repositories, or simply any commit whose sha the attacker can predict/observe from a public/shared upstream that both A and B track), a `status` event genuinely and validly emitted from GitHub for repository A will update the status of the matching-sha `Commit` row(s) regardless of which stack/repository they belong to.

Contrast with `PullRequest::OpenedHandler`: even though the attacker's PR webhook is validly signed for their own repository A, `respond_to_pull_request_opened?` / `provision?` / `ReviewStackAdapter.new(params, scope: repository.review_stacks)` all operate strictly on `repository` resolved from `params.repository.full_name`, so the created/found stack is always scoped to repository A's own `review_stacks`; it structurally cannot touch stacks belonging to repository B. [8](#0-7) 

No other guard closes this gap: `drop_unhandled_event` and `verify_signature` only gate on event type and signature validity for the *sender's own* org, not on whether the acted-upon record belongs to that org; `ExplicitParameters` schema in `StatusHandler` only validates types/shape of `sha`/`state`, not repository ownership. [9](#0-8) 

### Impact Explanation
A validly-signed webhook from an attacker-owned repository can write `Status` records (and trigger `commit_status`/`deployable_status` hooks and `schedule_merges`) against `Commit` rows belonging to a stack for a repository the attacker does not own and never authenticated against, provided a matching `sha` exists in both. This is a cross-tenant write ("a payload for one repository mutating another's ... commit"), matching the Critical impact category. Blast radius is bounded by the practical likelihood of `sha` collision across independently-tracked stacks, but is fully repeatable/deterministic once such a shared-history commit is identified (e.g., forked/mirrored open-source repositories tracked by two different Shipit stacks, or any scenario where the attacker can learn a sha already present in a victim stack's commit list, e.g. via the public Shipit UI/API for that stack).

### Likelihood Explanation
Preconditions: the attacker must (a) have a Shipit-integrated repository of their own with a working webhook (an explicitly allowed capability), and (b) know or engineer a git commit `sha` that is also recorded as a `Commit` row for a target stack — realistic when repositories share history (forks/mirrors) or when the target stack's commit shas are discoverable (Shipit stack UI is often readable). No secrets, sessions, or privileged roles are required. This is a genuine gap distinct from a general engine invariant, since the sibling `PullRequest` handlers demonstrate the fix pattern is already used elsewhere in the same codebase.

### Recommendation
Scope `StatusHandler#process` by repository, mirroring the pattern already used elsewhere in `Handler`: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` (or equivalent) and constrain the `Commit` lookup to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or `stacks.flat_map(&:commits)...`) instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan (no live GitHub, model/handler-level):
1. Create `stack_a` bound to `Repository` "attacker/repo" and `stack_b` bound to `Repository` "victim/repo".
2. Create `commit_a = Commit.create!(stack: stack_a, sha: "deadbeef...")` and `commit_b = Commit.create!(stack: stack_b, sha: "deadbeef...")` (same sha, different stacks) — asserting up front `commit_a.stack_id != commit_b.stack_id` and `commit_a.sha == commit_b.sha`.
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo"` and `sha = "deadbeef..."`, `state = "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert both `commit_a.statuses.reload` and `commit_b.statuses.reload` now contain a new `success` status — proving the write leaked into `stack_b` despite the payload naming only `attacker/repo`.
6. As the contrasting control, build an `opened` `pull_request` payload with `repository.full_name = "attacker/repo"` targeting a PR whose head matches something relevant to `stack_b`/`victim/repo`, call `PullRequest::OpenedHandler.call(payload)`, and assert no `ReviewStack`/record for `victim/repo`'s repository is created or modified — showing the sibling handler is correctly scoped and the divergence is specific to `StatusHandler`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
