### Title
Webhook signature is verified against a different GitHub organization than the repository the event payload writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to validate the HMAC signature based on `repository_owner`, which is read straight from the attacker-controlled JSON body (`repository.owner.login`, falling back to `organization.login`). The event handlers, however, resolve the `Stack`/`Repository`/`Commit` to act on using a *different* field of the same body — `repository.full_name` — with no check that the two agree. An attacker who legitimately controls the webhook secret for *any* organization onboarded to this Shipit instance can therefore sign a payload as their own org while pointing `repository.full_name` at a completely different, victim-owned stack, and have the handlers (e.g. `StatusHandler`) write state for that victim repository.

### Finding Description
`Shipit.github(organization:)` supports a multi-tenant configuration where each organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which organization's secret to validate against using a value taken from the untrusted payload itself:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once the signature check passes, `Shipit::Webhooks.for_event(event)` dispatches the raw parsed body to handlers [3](#0-2) . The base `Handler` (and e.g. `PushHandler`) resolve the target `Repository`/`Stack` using an *independent* field of the same JSON body:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Nowhere is `repository.owner.login` (used for signature verification / secret selection) cross-checked against `repository.full_name` (used to select the actual database record acted on). Since both values are simple JSON fields inside the same attacker-authored payload, they can be set independently before the payload is signed. This breaks the binding: `organization authenticated == repository written`.

This is directly analogous to the reported Burve bug, where a value used for one purpose (computing the amount of shares) was derived from a mutable/uncontrolled source (`sqrtRatioX96`) instead of the value that was actually verified/committed to — here, the "verified" field (`repository.owner.login`) is not the field the write path actually consumes (`repository.full_name`).

### Impact Explanation
An attacker who is the legitimate owner/admin of any single organization tracked by this Shipit instance (and thus knows/controls that organization's real GitHub App webhook secret, e.g. because they configured the GitHub App webhook on their own org's repos) can forge a signed webhook that is accepted by `verify_signature` for their own org, while `repository.full_name` names a stack that belongs to a completely different, victim organization. Handlers such as `StatusHandler` build `Commit::Status` records straight from attacker-supplied `sha`/`state`/`description`/`context` fields [5](#0-4) , without any GitHub API cross-check. Forged "success" statuses feed directly into `Commit#deployable?` (`success? && !blocked?`) [6](#0-5)  and into required-status gating (`Status::Common#required?`) [7](#0-6) , which is exactly the mechanism `ci.require`/`ci.blocking` rely on to gate deploys [8](#0-7) . This can result in an unauthorized deploy of a commit that never actually passed CI on a repository the attacker does not control — matching the "Critical: unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires only that the attacker be an admin/onboarding org for any organization already configured in this multi-tenant Shipit instance (an unprivileged position relative to the *victim* org/stack) — no Shipit session, API token, or GitHub write access to the victim repository is needed. The only prerequisite is that the instance is running the documented multi-organization `secrets.github` configuration, which is a normal, documented deployment mode [9](#0-8) .

### Recommendation
After signature verification succeeds, verify that `repository.owner.login` (or `organization.login`) actually matches the owner encoded in `repository.full_name` before dispatching to handlers, and reject the webhook (422) on mismatch. More robustly, derive the organization used for secret lookup and the repository used for record lookup from the same, single trusted field, and reject payloads that reference a repository not administratively tied to the authenticated organization.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret `S1`) and `victim-org` (secret `S2`), each tracked with a `Stack`.
2. As the attacker (who legitimately knows `S1`), craft a `status` webhook payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Sign the raw body with `S1` and send `X-Hub-Signature: sha1=<hmac>` and `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against `S1`.
5. `StatusHandler` (via `Handler#repository_name` = `"victim-org/victim-repo"`) creates a `success` `Status` on the victim's commit, satisfying `ci.require`, even though no such status was ever emitted by the real GitHub App/CI for `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

<h3 id="ci">CI</h3>

**<code>ci.require</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want Shipit to disallow deploys if any of them is missing on the commit being deployed.

For example:
```yml
ci:
  require:
    - ci/circleci
```

**<code>ci.hide</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want Shipit to ignore.

For example:
```yml
ci:
  hide:
    - ci/circleci
```

**<code>ci.allow_failures</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want to be visible but not to required for deploy.

For example:
```yml
ci:
  allow_failures:
    - ci/circleci
```

**<code>ci.blocking</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want to disallow deploys if any of them is missing or failing on any of the commits being deployed.

For example:
```yml
ci:
  blocking:
    - soc/compliance
```
