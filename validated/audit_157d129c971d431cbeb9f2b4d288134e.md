### Title
Webhook signature is validated against the organization named in the payload while events are applied to the repository named in the payload, allowing cross-organization event injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` selects which GitHub App/webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the *unauthenticated* JSON body, then, once "verified", every `Handlers::Handler` subclass resolves the target `Repository`/`Stack` using `repository.full_name` — a *different* field of the same unauthenticated body. Nothing ties these two fields together, so a caller who legitimately controls one organization's webhook secret can forge events for repositories belonging to any other configured organization.

### Finding Description
`verify_signature` computes the org used to fetch the webhook secret from the raw request body: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a *per-organization* webhook secret from `secrets.github` when multiple orgs are configured: [3](#0-2) 

Once the signature check passes, every handler resolves what to act on using a *different* field of the same attacker-controlled JSON body — `repository.full_name` — completely independent of `repository.owner.login`: [4](#0-3) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Because the value used to select/verify the HMAC secret (`repository.owner.login`) and the value used to select the write target (`repository.full_name`) are two independent, attacker-supplied fields of the same JSON body, and the signature only proves the payload was signed by *some* org whose secret matches, the equality the app implicitly relies on — `organization that authenticated == owner of repository that is written` — is never checked. A caller who has legitimate GitHub App installation on Org A (and therefore knows/controls a payload correctly HMAC-signed for Org A's webhook secret from a real event on their own repo) can freely set `repository.full_name` to `"OrgB/some-other-repo"` in that same signed body's semantics (or, since the signature is computed over the raw body with Org A's secret, simply generate a payload whose `repository.owner.login == "OrgA"` while `repository.full_name == "OrgB/some-other-repo"`, sign it with Org A's known/leaked secret, and send it). The handler layer (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) will then act on Org B's `Stack`/`Repository`/`Commit`/`Membership` records — e.g. enqueue a `GithubSyncJob` for another org's stack, create bogus commit statuses, or manipulate team memberships — despite never having proven authorization from Org B.

### Impact Explanation
This breaks the deployment-trust binding between "organization that authenticated" and "repository that is written," letting an attacker who only controls one configured GitHub App/organization inject webhook events that are applied to a different organization's `Stack`/`Repository` records. Depending on which handler is targeted, this can enqueue `GithubSyncJob` for a foreign stack (affecting what commits are considered head/deployable), fabricate commit statuses used as deploy gates (`ci.require`), or add/remove `Membership`/`Team` records that back `Shipit.github_teams` authorization — i.e., escalation into authorization state, and manipulation of state that gates unauthorized deploys/rollbacks. This maps to the High-impact category ("escalation into `Shipit.github_teams` authorization" / unauthenticated write influencing deploy gating).

### Likelihood Explanation
Exploitability requires the instance to be configured with multiple GitHub Apps/organizations (the multi-org secrets schema in `lib/shipit.rb#github_app_config`) and requires the attacker to control (or have previously observed) one organization's webhook secret — a scenario explicitly supported by the engine (one GitHub App per org) but never enforced to be scoped only to that org's own repositories. No repository write access, no Shipit session, and no `ApiClient` token are required — only the ability to send an HTTP POST to `/webhooks` with a validly-HMAC'd body for any one of the configured organizations.

### Recommendation
Enforce that the organization used to select the webhook secret and the organization that owns `repository.full_name` (and `organization.login` when present) are the same before processing the event — e.g., re-derive the owning organization strictly from `repository.full_name.split('/').first` for verification, or explicitly compare `repository.owner.login` against the owner segment of `repository.full_name` and `organization.login`, rejecting mismatches with `422` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `orgb`, each with its own GitHub App and `webhook_secret` (per `lib/shipit.rb#github_app_config`).
2. As an attacker who knows/controls `orga`'s webhook secret (e.g., via a legitimate installation on `orga`), craft a `push` event JSON body:
   ```json
   { "repository": { "owner": {"login": "orga"}, "full_name": "orgb/target-repo" }, "after": "<sha>", ... }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orga_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orga")`, computes the HMAC with `orga`'s secret, and it matches → request is accepted.
5. `Handlers::Push#stacks`/`repository_name` resolves `"orgb/target-repo"` via `Repository.from_github_repo_name`, and a `GithubSyncJob` is enqueued for `orgb`'s stack — despite the attacker never being authenticated for `orgb`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
