### Title
Webhook signature check is bound to `repository.owner.login`/organization while the write target is bound to `repository.full_name` - a spoofed/unsecured organization can drive arbitrary-stack webhook events ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization "authenticates" the request using `repository.owner.login` (or `organization.login`) from the JSON body, and validates the HMAC signature against that organization's configured `webhook_secret`. But every webhook `Handler` subclass resolves which `Repository`/`Stack` to act on using a *different* field of the same body — `repository.full_name` — via `Handler#repository_name`/`#stacks`. `GitHubApp#verify_webhook_signature` additionally treats a blank `webhook_secret` as automatically verified (`return true unless webhook_secret`). This breaks the intended binding "organization that authenticated == repository that is written": the signature only proves control over *an* organization entry (possibly one with no secret configured), while the payload's `repository.full_name`, which determines what actually gets mutated, is never covered by that binding.

### Finding Description
- Signature verification selects the app/secret by the *owner* field only: [1](#0-0) 
- `repository_owner` is read straight from the untrusted JSON payload with a fallback to `organization.login`, also attacker controlled: [2](#0-1) 
- `verify_webhook_signature` returns `true` unconditionally whenever the resolved organization's `webhook_secret` is blank, i.e., it is not a signature check at all in that case: [3](#0-2) 
- Every handler ignores the "authenticated" organization entirely and instead resolves the target `Stack`s from a separate field, `repository.full_name`: [4](#0-3) 
- Concrete handlers (e.g. `PushHandler`) then mutate stack state (trigger `sync_github`, and other handlers update commit statuses, PR state, merge status, etc.) based purely on that unauthenticated `full_name`: [5](#0-4) 

So the equality that should hold is: `organization whose secret validated the request == owner of repository.full_name that gets written to`. Because the controller derives the "authenticating organization" from `repository.owner.login`/`organization.login` while the handlers derive the "written repository" from the independent `repository.full_name` field, and because a blank `webhook_secret` short-circuits verification to `true`, an attacker who controls (or names) any organization entry in `Shipit.github_apps` config that has no `webhook_secret` set can send an arbitrary crafted payload whose `repository.owner.login` matches that unsecured organization while `repository.full_name` names a completely different, unrelated (and presumably better-protected) repository/stack. The signature check trivially "passes" (because there is nothing to verify), and the handler dispatch proceeds to operate on the attacker-chosen `full_name` repository/stack.

### Impact Explanation
This is a cross-repository write: an unprivileged network attacker (no Shipit session, no `ApiClient` token, no repo write access to the target repo — only knowledge that some configured organization lacks a `webhook_secret`, e.g., a newly onboarded or misconfigured org) can forge `push`, `status`, `check_suite`, `pull_request`, `deployable_status`, or `merge_status` events against a target stack they do not own. Depending on which handler is invoked, this can:
- Force `Stack#sync_github` / commit ingestion on a target repo's stack, poisoning commit history state used for deploy eligibility.
- Post forged commit statuses/check-runs that mark unreviewed commits as CI-passing, which (combined with `continuous_deployment`) leads to an unauthorized deploy of attacker-influenced code — matching the High/Critical impact bar ("unauthorized deploy").
- Manipulate `pull_request`/`merge_status` webhook-driven state used by merge-queue automation on a stack the attacker doesn't control.

### Likelihood Explanation
Likelihood depends on operational reality: it requires at least one organization entry configured in the Shipit deployment without a `webhook_secret` (the code explicitly supports and tolerates this state via `.presence` handling and `return true unless webhook_secret`), and the fact that handlers never cross-check that the "authenticating" owner matches the "written" repository's owner — this is a structural gap in the engine, not a host-misconfiguration corner case, since the split between `repository_owner` (auth) and `repository.full_name` (target) exists for every event.

### Recommendation
- Remove or gate the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature` (require an explicitly-configured secret, or reject when absent, rather than treating "no secret" as "always verified").
- In `WebhooksController`, verify that `repository.owner.login`/`organization.login` (used to pick the signing secret) is consistent with the owner of `repository.full_name` that the handler will actually act on, rejecting the request otherwise.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs: `victim-org` (proper `webhook_secret`) and `unsecured-org` (no `webhook_secret` set, e.g. left blank during onboarding).
2. Attacker (no relation to either org) POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to exist>",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "unsecured-org")`; since its `webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header — request passes.
4. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack, an action the attacker was never authorized to trigger.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
