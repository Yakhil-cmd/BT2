### Title
Webhook signature validated against `repository.owner.login` but repository/stack mutated using `repository.full_name` allows cross-repository webhook forgery in multi-org configurations - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature using `repository_owner`, which is read from the *unverified* payload (`repository.owner.login`, falling back to `organization.login`). Once the signature check passes, event handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`) locate the actual `Repository`/`Stack` to mutate using a *different* field of the same unverified payload: `repository.full_name`. These two fields are never cross-checked against each other.

### Finding Description
The binding that should hold is: **organization that authenticated == repository owner that is written**. In this engine that equality is broken:

- Signature verification: `verify_signature` picks the app config by `repository_owner`. [1](#0-0) 
- `repository_owner` is read straight from the untrusted JSON payload, with a fallback to `organization.login`. [2](#0-1) 
- After signature verification succeeds, handlers resolve the affected `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — a separate, independently-attacker-controlled field of the same JSON body. [3](#0-2) 
- `PushHandler` (and other handlers) then act on whatever stacks that lookup returns, e.g. triggering a GitHub sync for the branch. [4](#0-3) 

Shipit explicitly supports configuring multiple independent GitHub Apps for different organizations, each with its own `webhook_secret`. [5](#0-4) [6](#0-5) 

In this setup, an attacker who controls (or is an admin of) one configured, low-trust GitHub organization ("OrgB") can send a webhook to the shared `/webhooks` endpoint with a valid HMAC computed using OrgB's own `webhook_secret`, while setting `repository.owner.login`/`organization.login` to `OrgB` (so `verify_signature` picks OrgB's secret and validates), but setting `repository.full_name` to `OrgA/some-repo` — a repository belonging to a completely different, higher-trust organization also hosted by the same Shipit instance. `verify_signature` never checks that `repository.owner.login` matches `repository.full_name`'s owner, so the forged event is accepted and dispatched to handlers that act purely on `full_name`.

### Impact Explanation
This is a cross-repository write: an attacker with legitimate control of one configured org's GitHub App/webhook secret can forge webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`) that are attributed to and cryptographically "authenticated for" their own org, but which are processed against a `Stack`/`Repository` belonging to an unrelated org. For `push`, this triggers `PushHandler#process` → `stack.sync_github(expected_head_sha:)` for the victim repository/branch, which can queue GitHub sync jobs and (depending on stack configuration) feed into continuous delivery/commit tracking for a repository the attacker does not control — an unauthorized cross-repository interaction with Shipit's deploy pipeline, satisfying the "cross-repository writes" criterion for Critical impact.

### Likelihood Explanation
Requires only that the Shipit instance is configured with multiple GitHub Apps for multiple organizations (a documented, supported configuration) and that the attacker administers or has compromised the webhook configuration of at least one of those lower-trust organizations — no privileged Shipit account, `ApiClient` token, or GitHub token for the victim org is needed. Given multi-tenant Shipit deployments hosting several orgs is an explicitly documented use case, likelihood is realistic wherever that feature is used.

### Recommendation
In `WebhooksController#verify_signature`, after selecting the app by `repository_owner`, verify that `repository_owner` matches the owner segment of `repository.full_name` (and `organization.login` when present) before dispatching to handlers. Alternatively, have handlers resolve the repository using the same owner value that was cryptographically verified, rather than trusting `full_name` independently, so that the authenticated organization and the mutated repository are provably the same entity.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who administers `OrgB`'s GitHub App, craft a `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "OrgA/victim-repo", "owner": { "login": "OrgB" } }
}
```
3. Compute `X-Hub-Signature` using `OrgB`'s legitimate `webhook_secret`, and set header `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` calls `Shipit.github(organization: 'OrgB')` (from `repository_owner`) and the signature validates successfully against `OrgB`'s secret.
5. `PushHandler` is dispatched with the full payload; `Handler#repository_name` returns `OrgA/victim-repo`, and `stacks` resolves to `OrgA`'s stack, which is then synced/mutated — despite the request having been authenticated only for `OrgB`.
