### Title
Webhook signature verification is bound to `repository.owner.login`, not to the repository/commit actually written — allows cross-organization forged GitHub events (status, push, check_suite) - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's HMAC secret to check against using a field taken from the untrusted JSON body (`repository.owner.login` or `organization.login`), while the handlers that actually act on the payload (e.g. `StatusHandler`, `PushHandler`, the PR handlers) resolve the target `Commit`/`Repository`/`Stack` using a *different* attacker-controlled field (`sha` globally, or `repository.full_name`). These two values are never required to match, and for orgs with no `webhook_secret` configured (an explicitly supported/default configuration) the signature check is a no-op. This breaks the equality "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly bypasses verification when no secret is configured for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

`webhook_secret` being unset (`nil`) is a documented, supported configuration state, e.g. `webhook_secret: # nil` in `config/secrets.development.example.yml:11` and per-org in the multi-org example `config/secrets.development.shopify.yml`, where every organization has its own independent `webhook_secret`. [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (because the org named in `repository.owner.login`/`organization.login` has no secret, or because the attacker knows/can produce that org's secret), the event is dispatched to handlers that key their side effects off completely different fields of the same JSON body:

- `StatusHandler#process` does **no repository scoping at all** — it matches purely on `sha` across the entire installation:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [6](#0-5) 

- `Handler#stacks` / `Handler#repository_name` (used by `PushHandler`, `CheckSuiteHandler`, PR handlers) resolve the target repository from `payload.dig('repository', 'full_name')`, a field never checked against `repository_owner`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) [8](#0-7) 

So the equality that should hold — "the organization whose secret authenticated this request == the organization/repository whose state is mutated" — does not: an unprivileged attacker only needs to control (or find) one organization entry with no `webhook_secret` configured (or one whose secret they know) to pass `verify_signature`, and can then set `sha`/`repository.full_name` in the body to target commits/stacks belonging to an entirely different, independently secured organization.

### Impact Explanation
Because `StatusHandler` has zero scoping by repository/organization, a forged, "verified" webhook for a permissive org can create a `success` commit-status on any commit `sha` known to the attacker, in any stack, regardless of which organization actually owns that repository. `Commit#deployable?` (`app/models/shipit/commit.rb`) relies on such statuses (`success? && !blocked?`), so this can make an unreviewed/malicious commit appear deployable in stacks with continuous deployment enabled, i.e. it can lead to an **unauthorized deploy** and a **cross-repository write** — both explicitly listed as Critical impact. `PushHandler`/`CheckSuiteHandler` extend the same organization-mismatch primitive to arbitrary `repository.full_name` targets via `Repository.from_github_repo_name`.

### Likelihood Explanation
No session, API token, or GitHub write access is required — only an HTTP POST to the public webhook endpoint. The only precondition is that at least one configured GitHub organization in the installation has no `webhook_secret` (a state the shipped example configs explicitly show as the default/acceptable value) or that the attacker otherwise knows/derives one org's secret; multi-org Shipit deployments (shown in `config/secrets.development.shopify.yml`) are the realistic target since they mix orgs with differing trust levels behind a single endpoint.

### Recommendation
Bind the verified organization to the actual mutated resource: derive the target repository/stack from an already-trusted, request-scoped identity (e.g. require the verified `repository_owner`/`installation` to match `repository.full_name`'s owner before dispatching), and refuse to process any event whose `repository_owner` cannot be resolved to a configured, secret-bearing GitHub App. Additionally, `StatusHandler` (and any other handler with global `Commit`/`Stack` lookups) must scope its queries by the verified organization/repository, not merely by `sha`.

### Proof of Concept
1. Deployment configures two organizations, e.g. `orgA` (no `webhook_secret` set — a supported default) and `orgB` (has `webhook_secret` set, hosts the real target stack/commit).
2. Attacker POSTs to the webhooks endpoint:
   - Header `X-Github-Event: status`
   - Header `X-Hub-Signature: sha1=anything` (irrelevant)
   - Body:
     ```json
     {
       "repository": { "owner": { "login": "orgA" } },
       "sha": "<sha of a real commit in orgB's stack>",
       "state": "success",
       "context": "ci/attacker-forged"
     }
     ```
3. `verify_signature` calls `Shipit.github(organization: "orgA")`; since `orgA.webhook_secret` is `nil`, `verify_webhook_signature` returns `true` unconditionally — the forged request is accepted.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no org/repo filter, finds the real `orgB` commit, and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status into `orgB`'s stack.
5. If `orgB`'s stack has continuous deployment/merge-queue enabled and this was the last blocking status, the commit becomes `deployable?`/mergeable, resulting in an unauthorized deploy or merge of a commit the attacker never had CI or repository access to.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
