### Title
Webhook signature-verification identity is not bound to the repository the handlers act on, permitting cross-repository status/commit forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and its `webhook_secret`) used to validate the HMAC purely from a field inside the untrusted, attacker-supplied JSON body — `repository.owner.login`, falling back to `organization.login` [1](#0-0) [2](#0-1) . The individual event handlers, however, resolve *which repository/stack to mutate* from an entirely different field in the same body: `repository.full_name` [3](#0-2)  (used by `PushHandler`, `StatusHandler`'s underlying commit lookup, and all `PullRequest::*` handlers via `Repository.from_github_repo_name`) [4](#0-3) .

Nothing ties the organization whose secret validated the signature to the owner encoded in `repository.full_name`. Shipit explicitly supports multi-organization deployments where each org has its own (optionally unset) `webhook_secret` [5](#0-4) , and `verify_webhook_signature` trivially returns `true` when no secret is configured for that org [6](#0-5) .

### Finding Description
The binding that should hold is:
`organization whose credentials authenticated the request == owner of the repository the handler subsequently writes to`

In this engine that equality is never enforced:
1. `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and looks up `Shipit.github(organization: repository_owner)` to obtain the `GitHubApp` used only for HMAC verification [1](#0-0) .
2. Handlers never re-read `repository.owner.login`. They independently derive the target `Repository`/`Stack` from `repository.full_name` through `Shipit::Repository.from_github_repo_name` [3](#0-2) .
3. Because the HMAC signs the *entire* raw JSON body, an attacker only needs to know (or have) a valid `webhook_secret` for **any one** onboarded organization — call it Org A — to produce a signature that will pass `verify_signature` for a payload where `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/some-other-repo"`.
4. If Org A additionally has no `webhook_secret` configured — which is explicitly documented as *optional* [7](#0-6)  — `verify_webhook_signature` returns `true` unconditionally, meaning **no secret at all** is required to forge a signed-looking request that targets a *different* organization's repositories.

This is analogous to the Frankencoin H-05 pattern: a value used to gate/authorize an action (`repository_owner` for signature selection) is disjoint from the value the subsequent state-mutating logic actually consumes (`repository.full_name` for target resolution), letting an attacker who controls one side of the equality manipulate the other.

### Impact Explanation
An attacker who can obtain a valid signature for one organization (or who targets an org with no webhook secret configured — a documented, supported configuration) can deliver forged `push`, `status`, `pull_request`, or `check_suite` events that appear valid to `WebhooksController`, but whose `repository.full_name` points at any other organization's stack tracked by the same Shipit instance:
- `StatusHandler` will create arbitrary `Status` rows for any `Commit` matching the attacker-chosen `sha`, regardless of which org's secret was used, directly feeding `Commit#create_status_from_github!` [8](#0-7) . Since successful CI statuses drive `MergeRequest#all_status_checks_passed?` and continuous-deployment triggers [9](#0-8) , this can be used to fake a passing status on someone else's stack and cause `ProcessMergeRequestsJob` to auto-merge a pull request or trigger a continuous deploy that GitHub's real CI never approved — an unauthorized merge/deploy, which is squarely in the defined High/Critical impact set.
- `PushHandler`/`PullRequest::*` handlers can force `stack.sync_github`, archive/unarchive review stacks, or manipulate merge-request state on stacks belonging to organizations the attacker has no relationship with.

### Likelihood Explanation
Exploitability depends on operational configuration that the engine itself documents and supports: multi-org deployments with per-org (optional) webhook secrets [5](#0-4) , and any org onboarded without a webhook secret bypassing verification entirely [6](#0-5) . This is not a hypothetical misconfiguration — the setup docs list the webhook secret as "(optional)" [7](#0-6) , so any instance following the documented setup for at least one org without a secret is exposed to fully unauthenticated cross-repository writes.

### Recommendation
Bind the verified identity to the data the handlers act on: after `verify_signature` succeeds, re-derive `repository_owner` from `repository.full_name` (the same field handlers use) and require it to match the organization whose secret validated the request, rejecting the request otherwise. Alternatively, pass the verified organization into `Shipit::Webhooks.for_event` handlers and have `Handler#stacks`/`#repository_name` enforce that the resolved `Repository#owner` equals the authenticated organization before any mutation.

### Proof of Concept
1. Deploy Shipit configured for two organizations, "OrgA" (no `webhook_secret` set) and "OrgB" (secret configured, private, tracked stacks).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/private-repo" },
  "sha": "<sha of an existing commit on OrgB's tracked stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header [6](#0-5) .
4. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching OrgB's commit — and calls `create_status_from_github!`, inserting a forged "success" status on OrgB's private stack despite the request never being signed by OrgB's secret [8](#0-7) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
