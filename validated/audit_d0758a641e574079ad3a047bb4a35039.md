### Title
Webhook signature verification is keyed by `repository.owner.login`/`organization.login`, but event handlers act on the independent `repository.full_name` field, letting an authenticated multi-tenant org forge cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Shipit supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which org's HMAC secret to check by reading `repository.owner.login` (falling back to `organization.login`) out of the *unverified* JSON body, then verifies the raw body against that org's `webhook_secret` [2](#0-1) . Once the signature check passes, the full (still attacker-controlled) payload is dispatched to handlers, which independently derive the target repository from a *different* field, `payload.dig('repository', 'full_name')` [3](#0-2) , and use it to look up and mutate `Stack`/`Repository`/`PullRequest` records belonging to that org, e.g. `Repository.from_github_repo_name(params.repository.full_name)` in the PR handlers [4](#0-3)  or `stacks` from `repository_name` feeding `PushHandler#process` which triggers `stack.sync_github` [5](#0-4) .

Because `X-Hub-Signature` only proves the request came from the org whose secret matches `repository.owner.login`/`organization.login`, and never binds that HMAC to `repository.full_name`, an org administrator who legitimately controls their own GitHub App/webhook secret in a multi-org Shipit deployment can sign a payload where `repository.owner.login` = their own org (so verification passes) but `repository.full_name` = `"OtherOrg/other-repo"` (so the handler acts on a repository they don't control).

### Finding Description
The equality that should hold but does not is:

`org authenticated via HMAC(webhook_secret[repository.owner.login])` == `repository whose Stack/PullRequest/Commit records are mutated (repository.full_name)`

- `verify_signature` selects the verifying `GitHubApp`/secret using `repository_owner`, computed purely from unauthenticated JSON: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [6](#0-5) .
- `Shipit.github(organization: repository_owner)` resolves to a per-organization config/secret via `github_app_config` [7](#0-6) , confirming each org is isolated by its own `webhook_secret`.
- After the signature is validated against that org's secret, the **entire raw payload**, including a completely independent `repository.full_name` field, is handed to handlers unmodified: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [8](#0-7) .
- Handlers never re-check that `repository.full_name`'s owner matches the org whose secret authenticated the request. They resolve the target strictly through `full_name`: `Repository.from_github_repo_name(repository_name)` / `payload.dig('repository', 'full_name')` [3](#0-2) , and `Repository.from_github_repo_name` simply splits `owner/name` and does a DB lookup with no relation to who signed the request [9](#0-8) .

This is structurally identical to the reported bug class: a value used to gate/verify an action (webhook HMAC keyed on `repository.owner.login`) is decoupled from the value actually acted upon (`repository.full_name`), so a signature that is valid for org A's inputs is accepted for actions targeting org B's data.

### Impact Explanation
An attacker who administers *any* one of the multiple GitHub orgs configured on a shared Shipit instance (a routine, low-privilege scenario explicitly supported by the engine's multi-org secrets schema [1](#0-0) ) can send a signed webhook where `repository.owner.login`/`organization.login` = their own org (to pass HMAC verification) while `repository.full_name` (and, for `check_suite`/`push`, the `stacks` lookup) targets another org's repository. Depending on event type this reaches:
- `PushHandler#process` → enqueues `stack.sync_github(expected_head_sha:)` against another org's stack [5](#0-4) .
- `PullRequest::ClosedHandler#process` → `review_stack.archive!` on another org's review stack [10](#0-9) .
- `PullRequest::OpenedHandler#process` → provisions a new review stack for another org's repository [11](#0-10) .

These are unauthorized cross-repository writes/deploys triggered against a repository the attacker does not own, satisfying the "cross-repository writes" / "unauthorized deploy" critical-impact bar.

### Likelihood Explanation
Requires: (1) the deployment configured with multiple GitHub organizations (documented, supported feature), and (2) attacker administers one of those orgs' GitHub Apps well enough to know/set its `webhook_secret` and send a crafted POST to `/webhooks`. This is a realistic scenario for any Shipit instance shared across several orgs/teams, since organization admins routinely have legitimate access to configure their own org's webhook without any special Shipit privilege — no `ApiClient` token, session, or repository write access on the *target* org is required.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after verifying the HMAC, enforce that the org used to select the verifying secret matches the owner encoded in every repository-bearing field the handlers will use (`repository.full_name`'s owner segment and `organization.login`), rejecting the payload (422) on mismatch instead of passing the full unverified body through to handlers. Handlers should also reject/ignore payloads whose target owner differs from the authenticated organization rather than trusting `repository.full_name` unconditionally.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`, e.g. `orgA` (attacker-administered) and `orgB` (victim), each with distinct `webhook_secret`s, per the supported schema [1](#0-0) .
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(orgA_webhook_secret, raw_body)`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and the HMAC validates successfully [12](#0-11) .
5. `PushHandler` resolves the target stacks via `repository.full_name = "orgB/victim-repo"` [3](#0-2)  and enqueues `GithubSyncJob`/`sync_github` against `orgB`'s stack, despite the request only ever being authenticated as `orgA` [5](#0-4) .

**Note on confidence:** I was not able to fully trace every downstream side effect of `stack.sync_github` or `review_stack.archive!` (their implementations live outside the files indexed here), so the exact blast radius (e.g., whether this can trigger an actual deploy vs. only a metadata sync) could not be independently confirmed within the current index; a Devin session with full repository access would be needed to trace `Stack#sync_github` and `ReviewStack#archive!` end-to-end to confirm deploy-triggering capability.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
