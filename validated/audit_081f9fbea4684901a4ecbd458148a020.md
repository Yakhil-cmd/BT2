### Title
Unbounded, unauthenticated HTTP endpoint enables slowloris-style connection-exhaustion DoS - (File: main.go)

### Summary
`git-sync`'s optional `--http-bind` endpoint (used for liveness probes, `/metrics`, and `/debug/pprof/*`) is started via a bare call to `http.Serve(ln, mux)` with no `http.Server` timeouts configured. Any client able to reach that TCP port can open large numbers of slow/idle HTTP connections and exhaust goroutines/file descriptors in the `git-sync` process, denying service to legitimate liveness/readiness probes and potentially crashing the whole process (which also runs the sync loop), producing persistent sync denial. This directly parallels the Indy CVE-2022-31006 pattern: an unauthenticated network endpoint with no connection/­resource limits that an attacker can max out to deny service.

### Finding Description
At [1](#0-0)  git-sync conditionally starts an HTTP endpoint when `--http-bind`/`GITSYNC_HTTP_BIND` is set:

```go
ln, err := net.Listen("tcp", *flHTTPBind)
...
mux := http.NewServeMux()
mux.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) { ... })
...
go func() {
    err := http.Serve(ln, mux)
    ...
}()
```

`http.Serve` constructs an implicit `&http.Server{}` with all timeout fields at their zero values — no `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, or `IdleTimeout`, and no limit on concurrent connections. A repo-wide search confirms none of these fields are set anywhere in the codebase [1](#0-0) . This is the classic Go "slowloris" footgun: Go's `net/http` server spawns one goroutine per accepted TCP connection and will block that goroutine indefinitely waiting to read request headers/body if the client sends data slowly or not at all, since there is no per-request or per-connection deadline. An attacker who can reach the bound port (e.g., another compromised pod on the cluster network, or an operator who inadvertently binds to a non-loopback address per the documented `--http-bind` examples such as `":1234"`) can open many such connections and hold them open, exhausting the process's goroutines and file descriptors.

This endpoint is unauthenticated by design — it is documented as "suitable for Kubernetes startup and liveness probes" [2](#0-1) , with no auth/ACL mechanism, and additionally exposes `/metrics` and `/debug/pprof/*` (the latter includes `/debug/pprof/profile`, which itself blocks for up to 30s per request by default, amplifying the DoS with fewer connections) when enabled [3](#0-2) .

### Impact Explanation
Exhausting file descriptors/goroutines in the `git-sync` process can:
- Make the liveness/readiness endpoint unresponsive, causing Kubernetes to repeatedly kill/restart the sidecar (persistent sync denial), even though the underlying git repo content is unaffected — mirroring the Indy advisory's framing that "the ledger content will not be impacted... [but] unable to be used for its intended purpose."
- Exhaust process-wide file descriptors shared with the git subprocess execution and worktree/symlink filesystem operations performed by the sync loop [4](#0-3) , causing sync failures or process crash (the goroutine calls `os.Exit(1)` if `http.Serve` itself returns an error, but resource exhaustion can also manifest as failures in the concurrently-running sync loop before that).

This qualifies as "persistent sync denial" under the validation criteria.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where `--http-bind` is reachable from untrusted network peers (e.g., shared cluster network, multi-tenant namespaces, or misconfigured non-loopback bind addresses as shown in the flag's own documented examples). No authentication, TLS, or per-connection limiting exists, and the attack requires only ordinary unprivileged TCP access to the bound port — no git push/commit access, no credentials, and no cooperation from the repo owner or ledger/node operator.

### Recommendation
Configure explicit timeouts and limits on the `http.Server` instead of using the bare `http.Serve` helper, e.g.:
```go
srv := &http.Server{
    Handler:           mux,
    ReadHeaderTimeout: 5 * time.Second,
    ReadTimeout:       10 * time.Second,
    WriteTimeout:      30 * time.Second,
    IdleTimeout:       60 * time.Second,
}
go func() {
    err := srv.Serve(ln)
    ...
}()
```
Additionally consider limiting `MaxHeaderBytes` and documenting that `--http-bind` should always be restricted to `127.0.0.1` (loopback) unless intentionally exposed, and gating `/debug/pprof/*` behind a separate, more restrictive listener since profiling endpoints are especially amenable to resource-exhaustion amplification.

### Proof of Concept
1. Start `git-sync` with `--http-bind=":1234"` (as shown in the flag's own example) and `--http-pprof`.
2. From an attacker-controlled host with network access to port 1234, open many TCP connections (e.g., via `nc` or a slowloris script) and either send headers one byte at a time with long delays, or send valid headers but never complete the request body, keeping each connection open indefinitely.
3. Because no `ReadHeaderTimeout`/`ReadTimeout` is set, each connection consumes a goroutine indefinitely; repeating this at scale exhausts available file descriptors/goroutines.
4. Observe that `curl http://<bind>/` (the liveness endpoint) starts timing out or failing, and — if `/debug/pprof/profile` is enabled — a handful of concurrent requests to it (each holding a connection for ~30s by default) achieve the same effect with far fewer sockets.
