### Title
Uncaught exception / crash from concurrent cache eviction racing with in-flight AA trigger processing — `handlePrimaryAATrigger` reads `storage.assocStableUnits[unit]` after unguarded async gap ([File: aa_composer.js])

### Summary
The QEMU NVMe bug (CVE-2021-3929) is a reentrancy issue: a guest-triggered DMA write reaches the device reset path while a request is still in flight, freeing state structures that the original request later dereferences, causing a use-after-free/crash. The ocore analog is a JS-level equivalent: `handlePrimaryAATrigger()` in `aa_composer.js` holds only the `'aa_triggers'` mutex key while asynchronously executing an attacker-controlled AA trigger, and then, after a long asynchronous gap (arbitrarily long DB/oscript evaluation), unconditionally dereferences a shared in-memory cache entry `storage.assocStableUnits[unit]` and throws if it is gone. That cache is independently mutated/evicted by `storage.shrinkCache()`, which runs on its own timer and takes only the `'write'` mutex key — a different lock key that does not exclude the AA-trigger code path. A single posted unit that triggers a slow/deep AA response chain widens the async window in which the cache entry for its own triggering unit can be evicted by the concurrent, unguarded cache-shrink job, causing an uncaught `throw Error(...)` deep inside an `async function` callback and crashing the node process.

### Finding Description
`handleAATriggers()` acquires the `'aa_triggers'` mutex key and iterates queued triggers, calling `handlePrimaryAATrigger()` for each: [1](#0-0) 

Inside `handlePrimaryAATrigger()`, after the full (potentially very long, oscript-evaluation-heavy, recursively-triggered secondary-AA) `handleTrigger()` call resolves, the code deletes the trigger row and then reads the unit's cached properties directly from `storage.assocStableUnits`: [2](#0-1) 

If `objUnitProps` is not found, it throws unconditionally:
```
if (!objUnitProps)
    throw Error(`handlePrimaryAATrigger: unit ${unit} not found in cache`);
```
This throw happens inside a `conn.query(..., async function(){...})` callback — an unhandled rejection/exception context that is not caught by any try/catch up the AA-trigger execution path, so it propagates out of the event loop and crashes the process.

The relevant cache, `storage.assocStableUnits`, is periodically pruned by `shrinkCache()`, which is scheduled independently every 5 minutes and takes the `'write'` mutex key — not `'aa_triggers'`: [3](#0-2) [4](#0-3) 

Because `mutex.isAnyOfKeysLocked()` only checks for overlapping key strings, and `shrinkCache` locks `'write'` while AA trigger processing locks `'aa_triggers'`, these two paths can run concurrently with no exclusion. `shrinkCache()` deletes `assocStableUnits[unit]` for any unit whose `main_chain_index` is older than `top_mci` — a value computed from `min_retrievable_mci` and `last_stable_mci`, both of which advance as new units stabilize while the AA trigger chain is still executing (each nested/secondary AA call, oscript evaluation, and DB round trip in `handleTrigger()`/`handleSecondaryTriggers()` adds delay): [5](#0-4) 

Additionally, `storage.resetMemory()` — invoked from `writer.js` whenever any unrelated unit write fails and rolls back — wipes `assocStableUnits` entirely and rebuilds it, which is an even more direct source of the same race: [6](#0-5) [7](#0-6) 

This mirrors the DMA-reentrancy/reset pattern in the CVE: a long-running, attacker-influenced operation (deep AA-chain execution, analogous to an in-flight NVMe DMA transfer) races against an independent "reset"/cache-clear path (`shrinkCache`/`resetMemory`, analogous to `nvme_ctrl_reset()`) that is not excluded by the same lock, and the original operation later dereferences state that the reset path already freed/removed.

### Impact Explanation
An unprivileged unit poster who triggers an AA can cause the local full node processing that trigger to crash via an uncaught exception once the outer cache entry for the trigger's own unit is evicted mid-flight. A full-node crash during AA-trigger/unit stabilization halts consensus processing on that node (a node unable to confirm new units), and if reproducible/broadcast widely enough, is a network-wide denial-of-service vector against nodes running AAs — matching the "network unable to confirm new units" impact bar. It is not a straightforward remote-code-execution as in the C/QEMU case, since JS has no raw memory to corrupt, but the reentrant-cache-eviction-during-in-flight-processing pattern is the direct behavioral analog and produces a crash/DoS, the JS-safe equivalent of the CVE's consequence.

### Likelihood Explanation
Reaching the throw requires: (1) posting a unit that triggers an AA with a long enough/deep enough (chain of secondary triggers, expensive oscript) execution time to create a window where MC advances several times, and (2) the 5-minute `shrinkCache` timer or a concurrent write-rollback-triggered `resetMemory()` firing in that window and evicting the specific unit's `assocStableUnits` entry. This is timing-dependent and not deterministically triggerable on demand by an attacker in a single action, which lowers likelihood, but an attacker can amplify the odds by repeatedly posting AA triggers designed for maximal chained execution time, and by inducing failing units elsewhere to force `resetMemory()` more often. The exact reproduction requires careful adversarial timing that cannot be fully confirmed without dynamic testing.

### Recommendation
- Have `handlePrimaryAATrigger` and any other AA-trigger code that reads `storage.assocStableUnits`/`assocUnstableUnits` acquire (or be excluded by) the same `'write'` mutex key used by `shrinkCache`/`resetMemory`, or otherwise coordinate eviction with in-flight AA processing (e.g., pin/refcount units currently being processed so they are skipped by `shrinkCache`).
- Replace the unconditional `throw Error(...)` on missing cache entry with a safe recovery path: re-read the unit's `count_aa_responses` from the database instead of assuming the in-memory cache entry still exists.
- Audit other places that assume `storage.assocStableUnits[unit]`/`assocUnstableUnits[unit]` remain valid across long async gaps for the same racing-eviction issue.

### Proof of Concept
Conceptual reproduction (cannot be executed here, requires a running node/test harness):
1. Deploy an AA whose response triggers a long chain of secondary AA calls (many hops, each doing nontrivial oscript work) so that `handleTrigger()`/`handleSecondaryTriggers()` for a primary trigger takes long enough to span multiple main-chain advances.
2. Post a unit that triggers this AA so it enters `handlePrimaryAATrigger()` and begins the long `handleTrigger()` chain [8](#0-7) .
3. Concurrently, either wait for the 5-minute `shrinkCache()` interval to fire [3](#0-2)  (or induce an unrelated unit write failure to trigger `storage.resetMemory()` [9](#0-8) ) while the trigger unit's stability age crosses the shrink threshold.
4. When `handlePrimaryAATrigger`'s callback resumes and executes `storage.assocStableUnits[unit]`, the entry is gone, and the unconditional `throw Error("handlePrimaryAATrigger: unit ... not found in cache")` fires inside an unguarded async callback, crashing the node process [10](#0-9) .
