### Title
Caller-supplied Blend pool address receives pre-authorized controller token pulls in `migrate_from_blend` - (File: contracts/controller/src/external/blend.rs)

### Summary
The Blend migration path hands a user-controllable contract address the right to pull arbitrary amounts of arbitrary tokens out of the controller, under the controller's own invoker-contract auth, before any proof that the address is a real Blend pool. This is the on-chain analog of the reported bug class: untrusted input (the `blend_pool` address and `debt_caps` arguments) is concatenated into a privileged "command" — `env.authorize_as_current_contract` entries plus an `invoke_contract` into the attacker-controlled contract — letting injected code execute with controller-granted token-transfer authorization.

### Finding Description
`blend_repay_all` builds a `REQ_REPAY` request list directly from a `debt_caps: Vec<(Address, i128)>` argument and calls `authorize_repay_pulls`, which registers one `InvokerContractAuthEntry` per entry authorizing `token.transfer(controller → blend_pool, max)` — where both `debt_asset`, `max`, and `blend_pool` come straight from the caller's arguments [1](#0-0) . It then calls `guarded_submit`, which invokes `submit` on the supplied `blend_pool` address while holding only the flash guard — a guard that blocks reentry into *guarded controller operations* but does nothing to constrain what the invoked contract itself does [2](#0-1) . The authorization entries are registered unconditionally before the call and are keyed to the attacker-chosen `blend_pool` as recipient [3](#0-2) .

An attacker deploys a contract exposing Blend's `submit(from, spender, to, requests)` ABI, calls `controller.migrate_from_blend` naming that contract as `blend_pool` with `debt_caps = [(USDC, B), (XLM, B), ...]` for large `B`, and inside its `submit` implementation simply calls `token::Client::transfer(controller, self, max)` for each authorized pair. The host accepts these because the controller pre-authorized exactly those transfers. The fake `submit` can additionally return a fabricated `BlendPositions` (maps of `liabilities`/`collateral`/`supply`), so the migration bookkeeping can be made to record collateral that was never swept — `blend_sweep_all` relies on the same trusted `submit` response and clamps via `BLEND_WITHDRAW_ALL_AMOUNT` only against what the pool reports [4](#0-3) . There is no allowlist or registry check on `blend_pool` anywhere in this module — `storage` is touched only for `with_flash_guard` [5](#0-4) .

### Impact Explanation
Two compounding impacts, both reachable by a single unprivileged address in one transaction:

- **Theft of funds held by the controller.** The invoker-auth entries are exact-amount transfers to the attacker contract. Any token balance resting on the controller address at execution time — unclaimed `refund_assets` deltas, leftover swap receipts, donations, or balances pushed during in-flight flows — can be drained up to the declared caps, which the attacker sets. This is theft of user funds.
- **Protocol insolvency via forged migration state.** Because `submit` is invoked on attacker code, its `BlendPositions` return is attacker-controlled. If migration credits collateral/debt from that response (the natural shape of a "migrate position" verb), the attacker mints supply shares with no underlying and/or migrates phantom collateral, leaving the pool insolvent or the position liquidatable for profit at the protocol's expense.

### Likelihood Explanation
Likelihood hinges on whether `migrate_from_blend` validates `blend_pool` and `debt_caps` upstream — I was able to confirm only the helper layer (`blend.rs`), not the full argument provenance in `migrate_blend.rs`. If the entrypoint passes caller-supplied values through unvalidated (the standard shape, since Blend pool selection is inherently a user argument and no registry check exists in this module), exploitation needs only contract deployment plus one call — no privileged role, no timing dependency, no victim interaction. If upstream code pins the pool against a stored address or validates caps against live on-chain Blend state, the drain is bounded and the finding degrades to a forged-positions concern only.

### Recommendation
- Bind `blend_pool` at the controller entrypoint to a governance-registered Blend pool set (or require per-pool opt-in), never trusting a raw argument as an invocation target that also receives invoker-auth.
- Do not pre-authorize `transfer` entries to `blend_pool` before `submit`; either let Blend pull via the standard `require_auth` flow on the *verified* pool, or authorize only after `submit` returns and caps have been validated against real positions.
- Treat the `BlendPositions` return as untrusted: reconcile migrated collateral/debt against measured token balance deltas (the `balance_delta_since` pattern already used in `strategies/swap.rs` [6](#0-5) ) rather than the reported maps.

### Proof of Concept
1. Attacker deploys `FakeBlend` exposing `submit(from, spender, to, requests) -> BlendPositions`. Its body iterates `requests`, and for each `REQ_REPAY` entry calls `token::Client::transfer(&env, &controller, &self_addr, &req.amount)` — matching the pre-authorized auth entries exactly — then returns `BlendPositions { liabilities: {}, collateral: {0: HUGE}, supply: {0: HUGE} }`.
2. Attacker calls `controller.migrate_from_blend(caller, blend_pool = FakeBlend, debt_caps = [(USDC_addr, controller_usdc_balance), (XLM_addr, controller_xlm_balance), ...], ...)`.
3. `blend_repay_all` runs `authorize_repay_pulls`, registering `transfer(controller → FakeBlend, max)` entries [7](#0-6) .
4. `guarded_submit` invokes `FakeBlend.submit` [2](#0-1) ; the pulls succeed under the controller's invoker auth; `FakeBlend` returns fabricated positions.
5. Controller tokens are transferred out and the migration proceeds to book attacker-shaped collateral/debt unless the caller of `guarded_submit` re-verifies — nothing in this module enforces either.

/// Submits with the controller as spender and recipient while holding the

fn guarded_submit(env: &Env, blend_pool: &Address, from: &Address, requests: &Vec<BlendRequest>) {
    storage::with_flash_guard(env, || {
        let controller = env.current_contract_address();
        let _ =
            BlendPoolClient::new(env, blend_pool).submit(from, &controller, &controller, requests);

fn authorize_repay_pulls(env: &Env, blend_pool: &Address, debt_caps: &Vec<(Address, i128)>) {
    if debt_caps.is_empty() {
        return;
    }
    let controller = env.current_contract_address();
    let mut entries: Vec<InvokerContractAuthEntry> = Vec::new(env);
    for (debt_asset, max) in debt_caps.iter() {
        entries.push_back(InvokerContractAuthEntry::Contract(SubContractInvocation {
            context: ContractContext {
                contract: debt_asset,
                fn_name: symbol_short!("transfer"),
                args: (controller.clone(), blend_pool.clone(), max).into_val(env),
            },
            sub_invocations: Vec::new(env),
        }));
    }
    env.authorize_as_current_contract(entries);
}
