### Title
Unsigned membership webhook accepted and grants Shipit team membership when an org has no `webhook_secret` configured - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever `webhook_secret` is blank, so `WebhooksController#verify_signature` treats every unsigned request as authenticated for any org configured this way. Because `MembershipHandler#process` trusts the payload's `team.id`/`organization.login`/`member.login` without any further check against `Shipit.github_teams`, an attacker can add an arbitrary GitHub login to any existing team (including oauth-authorization teams) with a single unsigned POST.

### Finding Description
The broken binding: the code treats `verify_webhook_signature(signature, message) == true` as equivalent to "signature cryptographically verified", but in fact:
`verify_webhook_signature(signature, message) == true` when `webhook_secret.blank?`, regardless of `signature` or `message` values — [1](#0-0) .

Path: `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` from the attacker-controlled `repository.owner.login`/`organization.login` field of the raw JSON body, then calls `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)` and only `head(422)` if it returns false [2](#0-1) . If that org's config has no `webhook_secret` — a state explicitly documented and shipped in example configs (`config/secrets.development.example.yml:11`, `docs/setup.md:182-209`, `test/dummy/config/secrets_double_github_app.yml:1-79`) — the check passes for any request with any (or no) `X-Hub-Signature` header.

Once past this gate, `WebhooksController#create` dispatches to `MembershipHandler.call(params)` for `X-Github-Event: membership` [3](#0-2) . `MembershipHandler#process` calls `find_or_create_team!` which does `Team.find_or_create_by!(github_id: params.team.id)`, then does `team.add_member(User.find_or_create_by_login!(params.member.login))` for `action == 'added'` [4](#0-3) . All of `team.id`, `organization.login`, and `member.login` are attacker-supplied fields validated only for type/presence by the `ExplicitParameters` schema, not against any Shipit-side identity or authorization [5](#0-4) .

Attacker request: unsigned (or arbitrarily-signed) `POST /webhooks` with `X-Github-Event: membership`, body `{"action":"added","team":{"id":<github_id of a Shipit.github_teams team>,"name":...,"slug":...,"url":...},"organization":{"login":"<org without webhook_secret>"},"member":{"login":"<attacker-github-login>"},"repository":{"owner":{"login":"<org without webhook_secret>"}}}`.

Existing guards that fail to prevent this: `drop_unhandled_event` only screens unknown event types, not authenticity [6](#0-5) ; `verify_signature` is the only authenticity control and is bypassed by design when `webhook_secret` is unset; `Team.find_or_create_by!(github_id:)` performs no cross-check against `Shipit.github_teams` membership before allowing `add_member`.

### Impact Explanation
An attacker who knows (or brute-forces, since GitHub team IDs are small sequential integers) the `github_id` of a team referenced in `Shipit.github_teams` (`oauth.teams` config) can add an arbitrary GitHub login — including their own — as a member of that team via a single unsigned HTTP POST, for any org onboarded without a `webhook_secret`. Since `Shipit.github_teams` membership gates OAuth login authorization (`lib/shipit.rb:256-258`), this is a direct escalation into `Shipit.github_teams` authorization (matches the High severity category), repeatable against every stack under that org and against every org sharing the same misconfiguration, with no session, token, or GitHub secret required.

### Likelihood Explanation
Preconditions: an org entry in Shipit's `github` secrets config with `webhook_secret` unset/blank — a state the repo's own example and multi-org template files ship with by default (`config/secrets.development.example.yml`, `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`), making it a plausible real-world deployment state rather than a hypothetical. No other secret or privilege is required; the attacker only needs the org login and the numeric GitHub team ID of a target team, both easily discoverable via GitHub's public API. The attack is a single crafted HTTP request, fully repeatable.

### Recommendation
Change `verify_webhook_signature` to fail closed: if `webhook_secret` is blank, return `false` (or raise a configuration error) instead of `true`, and/or enforce at boot/config-validation time that every configured GitHub org must have a non-blank `webhook_secret` before the webhooks endpoint is enabled for that org.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "unsigned membership webhook is accepted and grants team membership when webhook_secret is blank" do
  Shipit.stubs(:github).with(organization: 'shopify').returns(
    Shipit::GitHubApp.new('shopify', webhook_secret: nil)
  )
  target_team = shipit_teams(:shopify_developers) # has a known github_id, referenced by Shipit.github_teams

  @request.headers['X-Github-Event'] = 'membership'
  # no X-Hub-Signature header set at all

  assert_difference -> { target_team.reload.members.count }, 1 do
    post :create, as: :json, body: {
      action: 'added',
      team: { id: target_team.github_id, name: target_team.name, slug: target_team.slug, url: target_team.api_url },
      organization: { login: 'shopify' },
      member: { login: 'attacker' },
      repository: { owner: { login: 'shopify' } }
    }.to_json
  end
  assert_response :ok
end
```
This asserts `verify_webhook_signature(nil, raw_post) == true` (LHS: actual method return; RHS: claimed-equivalent "signature cryptographically verified" — mismatched) and that the unauthenticated request results in a real `Membership` row for an attacker-chosen login on an existing, oauth-relevant team.
