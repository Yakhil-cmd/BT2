### Title
Stack-scoped API tokens can read CI/deploy status of any stack via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via its `stack_id` column, and `Shipit::Api::BaseController#stack` enforces that scope by resolving `params[:stack_id]` against the `stacks` relation, which is filtered to `Stack.where(id: current_api_client.stack_id)` whenever the client is stack-scoped. `Shipit::Api::CCMenuController` bypasses this enforcement by redefining `stack` to call `Stack.from_param!(params[:stack_id])` directly against the global `Stack` model, ignoring `current_api_client.stack_id` entirely.

### Finding Description
The intended binding is: *the set of stacks a token authorizes == the set of stacks the token's requests may touch*. Before the break, a client record such as fixture `here_come_the_walrus` (`stack: shipit`, `permissions: [read:stack]`, `test/fixtures/shipit/api_clients.yml:12-17`) is meant to only ever resolve `stack` to the `shipit` stack, as enforced generically by `BaseController#stacks`/`#stack` (`app/controllers/shipit/api/base_controller.rb:74-80`).

`CCMenuController` only checks the coarse-grained permission string `read:stack` (`require_permission :read, :stack`, `app/controllers/shipit/api/ccmenu_controller.rb:6`), which is present on any client with `read:stack` regardless of `stack_id`, and then resolves the target stack via its own private `stack` method:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This never checks `current_api_client.stack_id`, so any `stack_id` param value is honored — after the break, a token minted with a narrow stack scope can retrieve `#show` data (`app/controllers/shipit/api/ccmenu_controller.rb:22-25`, rendered via `app/views/shipit/ccmenu/project.xml.builder`) for every stack in the Shipit instance, not just the one it was authorized for.

### Impact Explanation
This is an unauthenticated-for-that-resource read of stack state: a token explicitly scoped by an administrator to one stack (e.g. shared with an external CI dashboard) discloses build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, lock status — see `test/controllers/api/ccmenu_controller_test.rb:33-45`) for arbitrary other stacks, including ones the token holder should have no visibility into. This matches the High-impact category of "unauthenticated read of stack state, task streams or deploy output" since the authorization boundary the token was explicitly given (single-stack scope) provides no actual containment for this endpoint.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token (a legitimate, low-privilege credential intentionally restricted to one stack) can trigger this by simply substituting a different `stack_id` in the request path — no additional privilege, secret, or race condition is required. `require_permission :read, :stack` is satisfied by the mere presence of `read:stack` in the client's permission list.

### Recommendation
Change `CCMenuController#stack` to resolve through the scope-aware `stacks` relation (i.e. call `super` or `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so stack-scoped tokens are constrained the same way as every other API endpoint.

### Proof of Concept
1. As an admin, create a stack-scoped `ApiClient` for stack `shipit` with `permissions: ['read:stack']` (mirrors fixture `here_come_the_walrus`, `test/fixtures/shipit/api_clients.yml:12-17`), and note its `authentication_token`.
2. Create or identify a second stack the token was never granted access to, e.g. `some-other-org/other-repo/production`.
3. Request:
   `GET /api/stacks/some-other-org/other-repo/production/ccmenu.xml?token=<the-scoped-token>`
4. `CCMenuController#authenticate_api_client` succeeds (valid token), `require_permission :read, :stack` passes (token has `read:stack`), and `stack` resolves via `Stack.from_param!(params[:stack_id])` to the *other* stack instead of being restricted to `shipit`, returning that stack's build/deploy status in the XML response — despite the token being scoped only to `shipit`. # frozen_string_literal: true

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }

    class << self
      def authenticate(token)
        find_by(id: message_verifier.verify(token).to_i)
      rescue Shipit::SimpleMessageVerifier::InvalidSignature
      end

      def message_verifier
        @message_verifier ||= Shipit::SimpleMessageVerifier.new(Shipit.api_clients_secret)
      end
    end

    def authentication_token
      self.class.message_verifier.generate(id)
    end

    def check_permissions!(operation, scope)
      required_permission = "#{operation}:#{scope}"
      unless permissions.include?(required_permission)
        raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
      end

      true
    end
  end
end
