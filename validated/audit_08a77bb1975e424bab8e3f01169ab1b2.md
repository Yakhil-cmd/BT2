### Title
API client stack-scoping bypass allows unauthorized read of another stack's deploy state - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports being scoped to a single `Stack` via its `stack` association, so a token can be issued with least-privilege access limited to one stack. [1](#0-0)  This scoping is the authorization boundary enforced by `Shipit::Api::BaseController#stacks`/`#stack`, which restricts lookups to the client's own stack when one is set. [2](#0-1)  `Shipit::Api::CCMenuController` overrides `#stack` to resolve directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the `stacks` scoping helper, while still relying on the generic `require_permission :read, :stack` check that only validates the permission string, not which stack it applies to. [3](#0-2) [4](#0-3) 

### Finding Description
The binding that should hold is: **stack a token authorizes == stack the request touches**, i.e. `current_api_client.stack_id` (when set) must equal the `stack_id` resolved and acted upon in every API controller action.

- Every other API controller resolves the target stack through the scoped `stacks` relation: `stacks.from_param!(params[:stack_id])` (e.g. `Api::StacksController#stack`, `Api::HooksController`, `Api::TasksController`, `Api::MergeRequestsController`), which is defined as `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. [2](#0-1) [5](#0-4) 
- `CCMenuController` instead defines its own `#stack` that calls `Stack.from_param!(params[:stack_id])` directly, an *unscoped* class method lookup that ignores `current_api_client.stack_id` entirely. [6](#0-5) 
- The only authorization check applied is `require_permission :read, :stack`, which is implemented as `current_api_client.check_permissions!(operation, scope)` — this only tests whether the string `"read:stack"` is in the client's `permissions` array; it never compares the requested stack against `current_api_client.stack_id`. [7](#0-6) [4](#0-3) 
- The fixture `here_come_the_walrus` demonstrates that a client can legitimately be scoped to a single stack (`stack: shipit`) with only `read:stack` permission, and a dedicated test confirms this scoping is expected to constrain visibility ("an api client scoped to a stack will only see that one stack"). [8](#0-7) [9](#0-8) 

Because `CCMenuController#stack` doesn't go through `stacks.from_param!`, a client scoped to Stack A that only has `read:stack` will still pass `require_permission :read, :stack` for a request naming Stack B, and `Stack.from_param!(params[:stack_id])` will happily resolve and render Stack B's data.

### Impact Explanation
This satisfies the "High" impact bar: **unauthenticated (i.e., un-authorized for that specific resource) read of stack state** — the CCMenu XML response exposes `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` for whatever stack is named in `params[:stack_id]`, not just the stack the token was scoped to. [10](#0-9)  A token that an operator believes is limited to one project's status (e.g., handed to a CI dashboard or third party) can be used to enumerate deploy/lock status of any stack in the Shipit instance, defeating the least-privilege guarantee the `stack_id` scoping is documented and tested to provide.

### Likelihood Explanation
Any holder of a valid, stack-scoped `ApiClient` token with `read:stack` permission can trigger this — no additional privileges, secrets, or session are required beyond the token itself, and the endpoint is reachable with a simple authenticated GET request by only changing the `stack_id` path/query parameter. This is a low-effort, high-reliability bypass since it is a straightforward routing/authorization logic gap, not a race condition or timing issue.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` helper instead of the raw `Stack` model, mirroring every other API controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Additionally, consider adding a defense-in-depth check in `ApiClient#check_permissions!` (or a dedicated method) that verifies `stack_id.nil? || stack_id == requested_stack.id` for any controller performing custom stack resolution, so future controllers cannot reintroduce this bypass by overriding `#stack`.

### Proof of Concept
1. Admin creates (e.g. via console/seed, matching the `here_come_the_walrus` fixture pattern) an `ApiClient` scoped to `stack: <stack_A>` with `permissions: ['read:stack']`, and issues its `authentication_token` to a third party expecting it to only reveal Stack A's status. [8](#0-7) 
2. The token holder authenticates against the CCMenu endpoint with Basic Auth using that token, but sets `stack_id` to `<stack_B>` (a different, unrelated stack) in the request path: `GET /api/<stack_B_owner>/<stack_B_repo>/<stack_B_env>/cc.xml`.
3. `authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])` / Basic Auth. [11](#0-10) 
4. `require_permission :read, :stack` passes because the client's `permissions` array contains `read:stack`, regardless of which stack is requested. [4](#0-3) 
5. `stack` resolves via `Stack.from_param!(params[:stack_id])`, returning Stack B — outside the client's authorized scope — and its deploy/lock status is rendered in the XML response. [12](#0-11)
