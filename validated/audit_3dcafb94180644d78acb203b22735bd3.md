### Title
Env-var whitelist checked against the stack's current HEAD `shipit.yml` while the deploy actually executes the `until_commit`'s `shipit.yml` - permitted key vs. spawned key mismatch (File: `app/models/shipit/stack.rb`, `lib/shipit/task_commands.rb`)

### Summary
`Stack#build_deploy` filters user-supplied deploy environment variables through `filter_deploy_envs`, which is delegated to `cached_deploy_spec` — the deploy spec cached from the stack's **current HEAD** commit. However, the deploy actually checks out and executes `until_commit` (the commit the caller chose to deploy, which can be any older undeployed/reachable commit), and `TaskCommands#env`/`#deploy_spec` reads the **live** `shipit.yml` from that checked-out commit, not the cached HEAD spec. The whitelist ("checkpoint") and the environment actually injected into the spawned process ("transfer") are computed from two different refs.

### Finding Description
`Stack#build_deploy` performs the permission check at deploy-creation time: [1](#0-0) 

`filter_deploy_envs` is delegated straight to `cached_deploy_spec`, which is populated by `CacheDeploySpecJob` from `stack.commits.reachable.last` (effectively HEAD), independently of any particular deploy request: [2](#0-1) [3](#0-2) 

The whitelist itself is derived from `deploy_variables`, i.e. whatever `deploy.variables` names are declared in the shipit.yml at that cached (HEAD) commit: [4](#0-3) [5](#0-4) [6](#0-5) 

But at execution time, `TaskCommands` rebuilds the deploy spec fresh from the actual checked-out working directory of the commit being deployed (`until_commit`), not from `cached_deploy_spec`, and merges its `machine_env` into the process environment used to spawn every step: [7](#0-6) [8](#0-7) 

Deploy requests accept an arbitrary `until_commit_id`/`sha` chosen by the caller from among the stack's reachable commits, independent of which commit is currently at HEAD: [9](#0-8) 

Because the whitelist check ("checkpoint") is evaluated against HEAD's `shipit.yml` while the spawned process's environment and executed steps ("transfer") come from `until_commit`'s `shipit.yml`, the equality the system implicitly assumes — *env-var names permitted at request time == env-var names the executing commit's config expects* — does not hold whenever the two `shipit.yml` deploy-variable declarations diverge. This mirrors the analog bug class: an action (checkpoint) is evaluated on state that is not the state the follow-up mutation (env spawn) will actually observe.

### Impact Explanation
If any commit reachable on the branch (past, future-merged, or a since-reverted one still reachable in history) ever declared a `deploy.variables` entry with a dangerous name — e.g. `LD_PRELOAD`, `BASH_ENV`, `GIT_SSH_COMMAND`, `BUNDLE_GEMFILE`, `PYTHONSTARTUP` — while that commit sits at HEAD (even transiently, before being superseded), any user able to trigger a deploy (`deploy:stack` permission or the `/deploys` UI action) can pass that variable name and have it accepted by `filter_deploy_envs`, then have it injected into the shell environment of the actual commands run for **any other reachable `until_commit`**, including much older, already-reviewed commits whose own `shipit.yml` never declared that variable and whose deploy scripts have no expectation of it being attacker-influenced. Depending on the shell/tooling invoked by the deploy steps, this can lead to arbitrary code execution on the deploy host — meeting the Critical bar (RCE on the deploy host).

### Likelihood Explanation
Requires: (a) a `deploy:stack`-permitted user or UI actor to trigger a deploy against a non-HEAD commit, and (b) the stack's `cached_deploy_spec` (HEAD) to declare, at some point, a deploy variable with a dangerous name, either intentionally by a malicious/compromised contributor or transiently while a since-reverted commit was at HEAD. This is not a zero-privilege exploit — it requires ordinary deploy access, which shipit-engine treats as a normal, low-trust capability for team members — but it breaks the intended invariant that the deploy-variable whitelist reflects the config of the specific commit being deployed, not whatever happens to be at HEAD at request time.

### Recommendation
Compute the deploy-variable whitelist from the `DeploySpec` of the actual `until_commit` being deployed (or re-validate right before execution using the checked-out working directory's spec), rather than from `cached_deploy_spec` (HEAD). Alternatively, reject deploys whose selected commit's `shipit.yml` deploy-variable declarations differ from the cached HEAD spec, or re-run `filter_deploy_envs` against the live `deploy_spec` inside `TaskCommands` before merging `@task.env` into the spawned process environment.

### Proof of Concept
1. Attacker with write access lands a commit `C1` at HEAD whose `shipit.yml` contains:
   ```yaml
   deploy:
     variables:
       - name: LD_PRELOAD
   ```
   `CacheDeploySpecJob` runs and updates `stack.cached_deploy_spec` to include `LD_PRELOAD` in `deploy_variables`.
2. Attacker reverts/removes that declaration in a follow-up commit `C2`, or simply lets the branch continue; `C1` remains a reachable commit in `stack.commits.reachable`, and `stack.cached_deploy_spec` may still reflect `C1`'s config for a window (until the next `CacheDeploySpecJob` run), or an accomplice/compromised token races a deploy during that window.
3. A deploy-permitted user (or the same attacker if they hold `deploy:stack`) issues:
   ```
   POST /stack_id/deploys { until_commit_id: <old_commit_sha>, env: { "LD_PRELOAD": "/tmp/evil.so" } }
   ```
   `Stack#build_deploy` calls `filter_deploy_envs({"LD_PRELOAD" => "/tmp/evil.so"})`, which succeeds because `cached_deploy_spec.deploy_variables` (from `C1`) whitelists `LD_PRELOAD`, even though `until_commit`'s own `shipit.yml` never declared it.
4. At execution time, `Deploy#env`/`Task#env` merges this attacker-supplied `LD_PRELOAD` into `TaskCommands#env`, which is passed to every `Command.new(...)` spawned for `until_commit`'s deploy steps, achieving code execution in the context of whatever binaries those steps invoke.
