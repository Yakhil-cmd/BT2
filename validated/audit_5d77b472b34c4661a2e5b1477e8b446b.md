## Analysis: Analogous Spoofing Bug in Device Pairing Name

The Grafana bug is a **CWE-79 spoofing** issue: an auto-generated trust indicator (`originalUrl`) can be overridden by an unprivileged actor and is later presented to a different user as if it were trustworthy/system-generated data. The closest analog reachable by an unprivileged actor in ocore is the `device_name` field accepted during device pairing in `device.js`, which is stored as the correspondent's identity and surfaced back to the user with only cosmetic sanitization.### Title
Spoofed correspondent display name via pairing message enables device-identity impersonation - (File: device.js)

### Summary
`handlePairingMessage()` in `device.js` accepts an attacker-controlled `device_name` string from a wallet pairing request and, after only stripping HTML tags, stores it as the trusted display name for the new correspondent. This name is later surfaced to the user in the wallet UI to identify who they are chatting with, sharing a shared/multi-sig address with, or receiving text/AA/contract-related messages from — mirroring the Grafana `originalUrl` issue where an unvalidated, attacker-supplied value is displayed to the victim as if it were a trustworthy, automatically-generated field.

### Finding Description
When device A initiates pairing with device B by sending a `pairing` justsaying/message, the body contains `{pairing_secret, device_name, reverse_pairing_secret}` [1](#0-0) . On the receiving side, `handlePairingMessage()` validates only that `pairing_secret` and `device_name` are non-empty strings and that `device_name.length <= 100`; it does not restrict character set, does not check for name collisions with existing correspondents, and does not verify the identity behind the name in any way [2](#0-1) .

The only "sanitization" applied is a naive tag-stripping regex, `body.device_name.replace(/<[^>]*>?/g, '')`, before the value is written into `correspondent_devices.name`, which becomes the confirmed identity of that correspondent going forward [3](#0-2) . This mirrors the class of bug in the advisory: a field meant to represent contextual/trust information (the correspondent's human-readable identity, analogous to `originalUrl`'s implied provenance) is fully attacker-controlled and only cosmetically filtered, yet consumed downstream as authoritative.

This stored `name` is later read back and surfaced through `readCorrespondents()` / `readCorrespondentsByDeviceAddresses()` for building UI lists of correspondents (e.g., wallet cosigners, chat partners) [4](#0-3) .

Because pairing is explicitly reachable by an unpaired/unknown device — `pairing` is one of the whitelisted subjects allowed from non-correspondents both on the hub-message intake path and the wallet message dispatcher — any external party who obtains or brute-forces/guesses a pairing secret (or who is offered one through a legitimately shared "permanent" pairing link, e.g. `pairing_secret IN(?, '*')` matching a wildcard/permanent secret) can pair and choose an arbitrary display name [5](#0-4) [6](#0-5) . This name can be crafted to impersonate a known/trusted correspondent, bot, or arbiter (e.g. naming itself identically to a support bot or a known co-signer), since there is no uniqueness or authenticity check tying the display name to the underlying pubkey/device_address.

### Impact Explanation
A spoofed correspondent name is a social-engineering / identity-spoofing primitive analogous to the Grafana `originalUrl` spoof: it lets an unprivileged, previously-unknown device present itself under a name the victim will trust. In ocore's wallet flows, correspondent identity/name is the primary cue a user relies on when:
- accepting shared/multi-signature wallet cosigners,
- trusting chat messages that reference arbiter/prosaic contracts (`text` messages with `arbiter-contract-offer`/`arbiter-dispute` markers are emitted with the sender's `from_address`, but the human-facing identity is the spoofable `name`) [7](#0-6) ,
- approving payment requests, signing requests, or private-payment counterparties that arrive from a "known" correspondent.

An attacker impersonating a trusted name can more easily social-engineer the victim into approving a malicious shared-wallet definition, signing a request, or accepting a private payment/asset transfer they would otherwise reject, potentially leading to unauthorized spending or loss of funds in multi-device/multi-sig wallets. This matches the severity class of the source advisory (Medium, CWE-79/spoofing), since exploitation requires a follow-on user-interaction step but directly undermines integrity of a trust indicator relied upon for security decisions.

### Likelihood Explanation
Likelihood is moderate: pairing requires either knowledge of a random pairing secret (normally shared out-of-band, e.g. via QR code/link) or use of a "permanent"/wildcard pairing secret path (`pairing_secret IN(?, '*')`), which some deployments (e.g. bots) intentionally publish for easy pairing [8](#0-7) . Any party possessing such a secret — including a legitimate but malicious third party who obtains a publicly shared link — can pair while claiming an arbitrary spoofed name with no additional identity proof, making the attack straightforward to mount but requiring the victim to subsequently misplace trust in the impersonated identity.

### Recommendation
- Do not allow the pairing-provided `device_name` to silently overwrite/establish a trusted display identity; visually flag device_names for unconfirmed/first-time correspondents as "unverified" or prefix them distinctly.
- Reject or flag device names that exactly or confusingly match existing correspondents' names/bots to prevent impersonation.
- Apply stricter sanitization/normalization (not just tag-stripping) and consider disallowing homoglyphs/formatting tricks.
- Require an explicit user confirmation step showing both the claimed name and the underlying device pubkey/address side by side before the correspondent is used in any security-sensitive flow (multi-sig cosigning, signing requests, private payments).

### Proof of Concept
1. Attacker obtains any valid pairing secret for the victim's device (e.g., a permanent/wildcard pairing secret published by the victim for easy pairing, or a leaked one-time secret).
2. Attacker's device sends a `pairing` message to the victim's hub with `body = {pairing_secret: "<secret>", device_name: "Trusted Support Bot"}` — a name matching or impersonating a real trusted correspondent.
3. `handlePairingMessage()` accepts this because it only checks non-emptiness and length ≤ 100, strips angle brackets, and inserts/updates `correspondent_devices.name` = `"Trusted Support Bot"` for the attacker's `device_address` [9](#0-8) .
4. The victim's wallet UI now lists the attacker as "Trusted Support Bot" in correspondent lists, chat, and any multi-device/multi-sig wallet cosigner selection dialogs sourced from `readCorrespondents`/`readCorrespondentsByDeviceAddresses` [4](#0-3) , enabling the attacker to solicit funds, cosigner approval, or private data under a spoofed trusted identity.
