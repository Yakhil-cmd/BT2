### Title
PreToolUse hookify hook fails open on rule-evaluation exceptions, bypassing deny/ask gates for Bash execution - ([File: plugins/hookify/hooks/pretooluse.py])

### Summary
`main()` in `plugins/hookify/hooks/pretooluse.py` wraps `load_rules()` and `RuleEngine.evaluate_rules()` in a bare `try/except Exception`, and unconditionally calls `sys.exit(0)` in a `finally` block regardless of whether rule evaluation succeeded, threw, or the module failed to import. Any exception thrown while parsing a malformed or adversarial `.claude/hookify.*.local.md` rule file causes the hook to print an error message and still exit 0, which Claude Code interprets as "allow" — silently defeating any configured deny/ask rule for that tool call (e.g., a Bash-blocking rule that should have gated `clean_gone.md`'s worktree-removal loop).

### Finding Description
The exact code path is: [1](#0-0) 

1. `main()` reads `tool_input`/`tool_name` JSON from stdin and calls `load_rules(event=event)` followed by `engine.evaluate_rules(rules, input_data)`.
2. If a `.claude/hookify.*.local.md` rule file in the (attacker-controlled/cloned) repo is malformed — e.g., invalid YAML frontmatter, unexpected type, missing field, regex that raises, or any other parsing/evaluation error — `load_rules()` or `evaluate_rules()` raises an exception.
3. The `except Exception as e` branch at lines 61-66 catches it, prints `{"systemMessage": f"Hookify error: {str(e)}"}` to stdout, and does **not** set any `"decision": "deny"` or `"permissionDecision": "ask"` field.
4. The `finally: sys.exit(0)` at lines 68-70 (explicitly commented "ALWAYS exit 0 - never block operations due to hook errors") always runs, causing Claude Code to treat the hook as having passed with no blocking directive — i.e., allow.
5. This also applies to the module-level `ImportError` handler at lines 25-32, which explicitly allows on import failure.

Because the hook has no fallback "deny by default" behavior, any adversarial rule file that is merely malformed enough to throw during parsing/evaluation silently disables the entire hookify enforcement for that tool call, rather than blocking it. A downstream command such as `plugins/commit-commands/commands/clean_gone.md`, whose Step 3 executes an unreviewed Bash loop performing `git worktree remove --force` and `git branch -D` on data derived from `git branch -v`/`git worktree list` output: [2](#0-1) 
would run unguarded if the configured hookify deny/ask rule intended to gate such Bash invocations fails to evaluate due to a malformed rule file.

### Impact Explanation
If a user or agent relies on a hookify Bash-guard rule (deny/ask) to prevent destructive or exfiltration-capable Bash commands from executing automatically, an attacker who can plant or modify a `.claude/hookify.*.local.md` file in a cloned/checked-out repository (e.g., via a malicious PR branch or repo content) can craft it to throw during parsing. This silently disables the enforcement gate for that PreToolUse invocation, allowing unsanctioned Bash execution — matching the "approval/permission bypass leading to unauthorized command execution" bounty impact category. Combined with any Bash-triggering slash command (such as `clean_gone.md`), this could enable destructive git operations or serve as a stepping stone to secret/code exfiltration via subsequent network calls, without the user's configured guard ever firing.

### Likelihood Explanation
Preconditions: (1) the victim has a hookify rule configured to deny/ask on Bash tool calls, and (2) a malformed/adversarial `.claude/hookify.*.local.md` file exists in the working repo (checked into a cloned/untrusted repo, or otherwise attacker-influenced). Given hookify rule files are plain markdown/YAML parsed by `load_rules()`/`RuleEngine`, crafting an input that throws (e.g., invalid regex pattern, unexpected structure) is straightforward and requires no special privilege — only the ability to add a file to the repo tree, which is a normal, low-privilege action (e.g., contributing a branch/PR). The bug is deterministic and fully repeatable: every exception path in `main()` results in exit 0.

### Recommendation
Change the fail-open design to fail-closed (or at minimum "ask") on rule-evaluation errors: in the `except Exception` branch of `main()`, emit a hook output with an explicit deny/ask decision (e.g., `{"decision": "ask", "systemMessage": "Hookify rule evaluation failed: ..."}`) instead of allowing silently, and avoid `sys.exit(0)` masking failures. At minimum, validate/sandbox parsing of `.claude/hookify.*.local.md` files so malformed rule files cannot silently disable the entire guard, and add a "strict mode" that blocks tool execution when hookify itself is broken.

2. Invoke `plugins/hookify/hooks/pretooluse.py` as a subprocess, piping a `tool_name: "Bash"` / `tool_input: {"command": "rm -rf /tmp/x"}` JSON payload on stdin.

Fuzz variant: generate a corpus of malformed `hookify.*.local.md` files (bad YAML, bad regex, wrong types) and assert for each that the hook never emits a deny/ask decision when it should, i.e., that `main()`'s exception path always resolves to allow — proving the invariant "deny means deny" is violated whenever rule evaluation throws.

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
