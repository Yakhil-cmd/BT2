### Title
Scoped API client token bypasses its stack restriction in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack via the `stack_id` column, and `Api::BaseController` is supposed to enforce that scope for every read/write operation. `Api::CCMenuController`, however, overrides the `stack` lookup method with an unscoped query, so a token that GitHub-side authorizes only for stack A can be used to read the deploy status of any other stack B. This breaks the "stack a token authorizes vs. stack it touches" binding explicitly called out as in-scope.

### Finding Description
`Api::BaseController` centralizes stack access control: `stacks` restricts the queryable set to the API client's own stack when one is configured, and `stack` (`stacks.from_param!(...)`) is meant to be the safe accessor every subclass uses. [1](#0-0) 

`Api::CCMenuController` requires only the generic `read:stack` permission and re-defines `stack` to bypass the client-scoped `stacks` collection entirely, looking the stack up directly from `Stack.from_param!(params[:stack_id])`: [2](#0-1) 

The `ApiClient` model only checks permission names, not stack scope, in `check_permissions!`, and stack scoping is entirely the responsibility of controllers correctly using `BaseController#stacks`/`#stack`: [3](#0-2) 

Fixture data confirms scoped clients exist in the codebase (e.g. `here_come_the_walrus`, scoped to the `shipit` stack with only `read:stack`): [4](#0-3) 

And `Api::StacksControllerTest` demonstrates the intended enforcement — a stack-scoped client only sees its own stack when using the correctly-scoped `stacks`/`stack` accessors: [5](#0-4) 

Because `CCMenuController#stack` never consults `current_api_client.stack_id`, any valid token — even one explicitly scoped to a single, low-sensitivity stack — can be replayed against `GET /:stack_id/ccmenu` for an arbitrary other stack and will successfully render that stack's deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, etc.), as shown by the controller test using an arbitrary `stack_id` param with no scope check enforced beyond permission name: [6](#0-5) 

### Impact Explanation
This is an authorization-scope escalation: the equality that should hold is `stack authorized by the ApiClient == stack touched by the request`, but for the CCMenu endpoint the right-hand side is attacker-controlled via `params[:stack_id]` while the left-hand side (the client's `stack_id` restriction) is never consulted. An attacker holding any single stack-scoped, `read:stack`-permissioned token (e.g. leaked from a low-privilege CI dashboard integration, or self-issued via `CCMenuUrlController#client`, which always creates a `read:stack`-scoped client for whichever stack the current user is viewing) can enumerate and read the deploy status of every other stack in the installation, defeating the per-stack API token isolation the engine advertises.

### Likelihood Explanation
Low likelihood of privileged access is required — the attacker only needs one legitimately-scoped, low-privilege API client token (which multiple parts of the app hand out routinely, e.g. `CCMenuUrlController`), and the exploitation itself is a single unauthenticated-parameter-substitution HTTP GET, with `stack_id` values guessable/enumerable from the stack slug format used throughout the app.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` collection from `BaseController` instead of querying `Stack.from_param!` directly, i.e. `@stack ||= stacks.from_param!(params[:stack_id])`, so the client's `stack_id` restriction is enforced identically to every other API controller.

### Proof of Concept
1. Obtain (or self-issue via `CCMenuUrlController`) an `ApiClient` token scoped to `stack_id: <stack-A>` with only `read:stack` permission.
2. Send `GET /api/<stack-B>/ccmenu?token=<token>` where `<stack-B>` is any other stack in the installation.
3. Observe the response renders `stack-B`'s CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`) even though the token is scoped only to `stack-A`, whereas the same token used against `/api/stacks/<stack-B>` (which uses `BaseController#stack`) would correctly be excluded from the client's `stacks` scope.
