### Title
Unfiltered PR label names merged into stack `env` allow `PATH` injection into `dependencies.override` commands - (File: app/models/shipit/review_stack.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly into the environment hash with no key allowlist or denylist, and `DeploySpec#dependencies_steps` (the `dependencies.override` section) is executed with this full, unfiltered env — unlike `deploy_steps`/`rollback_steps`, which are always passed through `filter_deploy_envs`/`filter_rollback_envs`. Because `Command#unbundled_env` merges the caller-supplied `@env` **after** computing the safe `PATH`, a label literally named `path` becomes `env["PATH"]="true"` (or, depending on how commands construct the env hash, an attacker-chosen directory), which can override the process `PATH` used by `PTY.spawn` for the `dependencies.override` steps.

### Finding Description
The broken binding: the code assumes `dependencies_steps` execution env == `filter_deploy_envs(stack.env)` (a whitelisted subset), but in reality `dependencies_steps` execution env == raw `stack.env`, which is `super.merge(pull_request.labels.each_with_object({}){|n,h| h[n.upcase]="true"})` [1](#0-0) .

- `ReviewStack#env` has no allowlist/denylist on label-derived keys, so any label name becomes an env key verbatim (uppercased) [1](#0-0) .
- `DeploySpec#dependencies_steps` reads `config('dependencies', 'override')` with no call to `EnvironmentVariables#permit`, unlike `filter_deploy_envs`/`filter_rollback_envs` which explicitly whitelist against `deploy_variables`/`rollback_variables` [2](#0-1) [3](#0-2) .
- Tests confirm the full stack env (including uppercased labels) reaches `Shipit::DeployCommands#env` unfiltered [4](#0-3) .
- `Command#unbundled_env` computes a safe `PATH` from `Shipit.shell_paths` and `ENV['PATH']`, then merges the caller's `@env` **last**, so any `PATH` key in `@env` wins: `BASE_ENV.merge('PATH' => "...").merge(@env.stringify_keys)` [5](#0-4) .
- `Command#start` spawns the process with this merged env via `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [6](#0-5) .

Attacker flow: on a repository configured with `provisioning_behavior=allow_with_label`, the attacker opens/labels a PR with a label named `path` (any case). The `labeled` webhook is handled by `LabelCapturingHandler#capture_labels`, which persists `params.pull_request.labels.map(&:name)` verbatim with no validation [7](#0-6) . When the review stack's `dependencies.override` step runs (e.g., during CI/deploy), `ReviewStack#env` merges `{"PATH"=>"true"}` into the stack env, this reaches `Command`'s `@env`, and `unbundled_env` places it last in the merge, potentially causing a bare command name in the `shipit.yml` step (e.g., `bundle install`, `npm install`) to resolve against an attacker-influenced `PATH` value rather than the safe, computed one.

Existing guards do not catch this: `filter_deploy_envs`/`filter_rollback_envs` exist for `deploy`/`rollback` sections but are never applied to `dependencies_steps`; `EnvironmentVariables#permit` is not invoked for the dependency-override path at all.

### Impact Explanation
If a bare (non-absolute-path) command is used in a `dependencies.override` step and the injected `PATH` value can be shaped to include an attacker-writable directory ahead of legitimate binary directories, the deploy host would execute an attacker-controlled binary in place of the intended tool, leading to arbitrary command execution on the Shipit deploy host under the Shipit process's privileges — a Critical RCE per the target class. This affects the specific repository/stack whose `provisioning_behavior` is `allow_with_label` and where `dependencies.override` uses a bare command name.

### Likelihood Explanation
Requires: (1) the target repository configured with `review_stacks_enabled` and `provisioning_behavior=allow_with_label`; (2) a `dependencies.override` section defined that invokes a bare command name (not an absolute path) — this is the common/default pattern in `shipit.yml`; (3) the attacker's ability to attach a label named `path` to their PR. Whether an unprivileged fork contributor can add labels to a PR against the base repository is governed by GitHub's own permission model (typically requires triage/write access), which is outside this engine's control — the question's threat model stipulates this capability is available to the attacker, but this is a GitHub-side precondition, not one enforced or bypassed by Shipit's code. Given that precondition, exploitation via the engine's code is straightforward and repeatable per labeled PR/deploy.

### Recommendation
- Add an explicit denylist (or an allowlist as done for `deploy`/`rollback` via `EnvironmentVariables#permit`) to `ReviewStack#env` so that dangerous keys such as `PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `RUBYOPT`, `BUNDLE_GEMFILE`, `GEM_HOME`, etc. can never be set from pull request label names.
- Apply the same `EnvironmentVariables#permit` whitelist mechanism used by `filter_deploy_envs`/`filter_rollback_envs` to `dependencies_steps`' environment before it reaches `Command`.
- In `Command#unbundled_env`, compute the final `PATH` after merging `@env`, or explicitly exclude `PATH` from caller-supplied `@env`, so untrusted env can never override the sanitized `PATH`.

### Proof of Concept
```ruby
# test/lib/shipit/deploy_commands_test.rb (extend)
test "#env with a 'path' label does not leak into dependencies.override PATH" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["path"]
  deploy = stack.trigger_continuous_delivery

  env = Shipit::DeployCommands.new(deploy).env
  assert_equal env["PATH"], "true"   # demonstrates unfiltered label -> env["PATH"]

  command = Shipit::Command.new("some-tool", chdir: Dir.tmpdir, env: env)
  resolved_env = command.unbundled_env
  # BROKEN BINDING: resolved_env["PATH"] should equal the safe computed PATH
  # (Shipit.shell_paths + ENV['PATH']), but instead equals the label-derived value.
  refute_equal resolved_env["PATH"], "true"
end
```
This demonstrates that the env hash used to build `dependencies.override` `Command` instances is not filtered by any whitelist (unlike `deploy`/`rollback`), and that `Command#unbundled_env`'s merge order lets a label-derived `PATH` key override the safe computed `PATH`.
