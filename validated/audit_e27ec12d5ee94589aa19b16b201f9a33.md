### Title
Fork-controlled `machine.environment` entry in `shipit.yml` overrides trusted env vars (including `SSH_ASKPASS`) reaching `PTY.spawn` for review-stack task steps - (File: lib/shipit/task_commands.rb, app/models/shipit/deploy_spec.rb, lib/shipit/command.rb)

### Summary
`DeploySpec#machine_env` returns `config('machine', 'environment')` verbatim from the parsed `shipit.yml`, and `TaskCommands#env` merges this hash last (after `SHIPIT_USER`, `GIT_COMMITTER_*`, etc., but before `@task.env`), so any key the PR author places under `machine.environment` reaches the command's `env` hash unfiltered. `Command#unbundled_env` then merges `@env.stringify_keys` on top of `BASE_ENV`/`PATH`, so this attacker-supplied key is what `PTY.spawn` ultimately receives.

### Finding Description
The claimed broken binding is: `env_passed_to_PTY.spawn['SSH_ASKPASS'] == BASE_ENV['SSH_ASKPASS']` (i.e., only host-controlled environment should reach the spawned child), but in fact `env_passed_to_PTY.spawn['SSH_ASKPASS'] == fork_shipit_yml['machine']['environment']['SSH_ASKPASS']` when the fork sets it.

Trace: for a review-stack task, `TaskCommands#deploy_spec` builds a `DeploySpec::FileSystem` from `@task.working_directory` [1](#0-0) , which is the checkout of the *fork branch* associated with the review stack (this is inherent to how review stacks work — the stack's working directory tracks the PR branch's HEAD, and `shipit.yml` is read from that checked-out tree). `DeploySpec#machine_env` returns `config('machine','environment') || {}` with no key allow-list, unlike `deploy_variables`/`rollback_variables`/task `variables`, which are explicitly filtered via `EnvironmentVariables#permit` (`filter_deploy_envs`, `filter_rollback_envs`, `TaskDefinition#filter_envs`) [2](#0-1) [3](#0-2) [4](#0-3) .

`TaskCommands#env` merges `deploy_spec.machine_env` near the end of the chain, then `@task.env` last, with no filtering applied to `machine_env` at all: [5](#0-4) .

Each step in `perform` builds `Command.new(command_line, env:, chdir: steps_directory)` using this unfiltered `env` [6](#0-5) . `Command#initialize` stores `@env = env.transform_values { |v| v&.to_s }` [7](#0-6) , and `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` where `unbundled_env` is `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [8](#0-7) . Because `@env` is merged **last**, any key the attacker supplies — including `SSH_ASKPASS` — overrides whatever `BASE_ENV` would otherwise contain (which normally has no `SSH_ASKPASS` at all, so the attacker's value is unconditionally injected).

Confirmed by the existing test suite showing `machine_env` is taken from parsed YAML verbatim and merged straight into the command env: `test '#machine_env returns an environment hash'` [9](#0-8) , and `"#perform merges shipit.yml machine_env in ENVIRONMENT"` [10](#0-9) .

Attacker's exact PR: open a pull request from a fork branch whose `shipit.yml` contains:
```yaml
machine:
  environment:
    SSH_ASKPASS: "/tmp/evil.sh"
```
Once the target repository has `provisioning_behavior: allow_all` (a maintainer/operator setting, not attacker-controlled, but it is the documented condition under which the review stack is provisioned and its own branch content — including `shipit.yml` — is used for the stack's `tasks.<name>.steps`/deploy steps), the PR's `ReviewStack` is provisioned using the fork's own `shipit.yml` [11](#0-10) , and no code path filters `machine.environment` before it reaches `PTY.spawn`.

Why existing guards don't help: `EnvironmentVariables#permit`-style filtering is applied only to `deploy_variables`, `rollback_variables`, and task-definition `variables` — never to `machine.environment`. There is no allow-list, denylist, or `SSH_ASKPASS`-specific stripping anywhere in `DeploySpec`, `TaskCommands`, or `Command`.

### Impact Explanation
If an SSH invocation occurs during any step run through `TaskCommands`/`Command` (e.g., `git`, deploy/task steps that call `ssh`/`git+ssh`), the attacker-controlled `SSH_ASKPASS` names an arbitrary executable path that will be invoked by the SSH/git subprocess whenever it needs to prompt for a password/passphrase (glibc/OpenSSH behavior invokes `$SSH_ASKPASS` when there's no controlling TTY, which is exactly the case under `PTY.spawn`-driven automation). That achieves arbitrary code execution on the Shipit deploy host under the Shipit service account, matching the Critical RCE class. This is scoped to the review-stack's task/deploy execution context (the fork PR's own stack), not other tenants' stacks directly, but it is fully repeatable by any unprivileged PR author against any repository whose maintainer enabled `allow_all` (or any behavior which lets an untrusted branch's shipit.yml run).

### Likelihood Explanation
Preconditions: repository must have `provisioning_behavior: allow_all` (or similar), which is a real, documented, and used feature intended to let PR authors control review-stack configuration/tasks — attacker cost is a single PR from their own fork. No secrets, sessions, or privileged roles are required, matching the "unprivileged fork PR" threat model exactly. This is not theoretical; the merge order and lack of filtering are directly demonstrated by existing DeploySpec/Command tests [9](#0-8) .

### Recommendation
Apply a strict allow-list/deny-list to `machine.environment` before merging it into task/deploy env — at minimum strip or reject dangerous keys such as `SSH_ASKPASS`, `LD_PRELOAD`, `BASH_ENV`, `GIT_SSH`, `GIT_SSH_COMMAND`, `PATH`, and any variable that can redirect binary execution — analogous to the existing `EnvironmentVariables#permit` used for `deploy_variables`/`rollback_variables`. Alternatively, ensure `Command#unbundled_env` merges `BASE_ENV` **after** `@env` for a fixed denylist of security-sensitive keys so they cannot be overridden by task/deploy/machine env regardless of source.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (new test)
test "#env allows SSH_ASKPASS injection via machine.environment (unfiltered)" do
  stack = shipit_stacks(:review_stack)
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  deploy_spec = Shipit::DeploySpec.new(
    'machine' => { 'environment' => { 'SSH_ASKPASS' => '/tmp/evil.sh' } }
  )
  Shipit::TaskCommands.any_instance.stubs(:deploy_spec).returns(deploy_spec)

  commands = Shipit::TaskCommands.new(task)
  env = commands.env
  assert_equal '/tmp/evil.sh', env['SSH_ASKPASS']

  command = commands.perform.first
  # Command#unbundled_env merges @env last, so SSH_ASKPASS reaches PTY.spawn
  assert_equal '/tmp/evil.sh', command.send(:unbundled_env)['SSH_ASKPASS']
end
```
Both sides of the binding (`env['SSH_ASKPASS']` and `command.unbundled_env['SSH_ASKPASS']`) equal the attacker's value `/tmp/evil.sh`, proving the fork-controlled `shipit.yml` entry reaches the process environment passed to `PTY.spawn` with no filtering.
