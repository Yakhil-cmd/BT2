### Title
Webhook signature verification is keyed on an unverified `repository.owner.login`/`organization.login` field, letting a payload's HMAC be checked against the wrong GitHub App/organization secret - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization's `webhook_secret` to validate the request against by reading `repository.owner.login` (falling back to `organization.login`) straight out of the **unauthenticated, unverified** JSON body, before the signature check has run. It then verifies the HMAC of the *whole raw body* against that organization's secret, but the handlers that subsequently act on the event trust a **different** field from the very same unverified body — `repository.full_name` — to decide which `Repository`/`Stack` to mutate. Nothing forces the organization used to pick the verification key to match the repository that ends up being written to.

### Finding Description
```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` resolves the per-organization config from `secrets.github` (multi-org schema is documented and supported, e.g. `test/dummy/config/secrets_double_github_app.yml`) and raises `GithubOrganizationUnknown` only if that organization key is entirely missing: [2](#0-1) 

Critically, `GitHubApp#verify_webhook_signature` treats a **missing** `webhook_secret` as automatic success:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

The webhook `secret` is documented as optional per-organization (`webhook_secret: some-secret-value` / `webhook_secret: # nil`), and multi-org installs configure it independently per key: [4](#0-3) [5](#0-4) 

Meanwhile, event handlers ignore `repository.owner.login` entirely and instead resolve the affected `Repository`/`Stack` from `repository.full_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 
`PushHandler#process` then triggers a real GitHub sync (`stack.sync_github`) for whichever stack matches that name: [7](#0-6) 

**The broken binding, stated as an equality that fails to hold:**
`organization whose secret authenticated the signature (repository_owner)` **≠** `repository/organization actually written to by the handler (repository.full_name)`.

Because both fields come from the *same unverified attacker-controlled JSON body*, and because the org used to select the verifier is looked at **before** — and independently of — the org whose repo is acted upon, an attacker can:
1. Pick any organization `X` that is configured in Shipit's multi-org `secrets.github` but has no `webhook_secret` set (or is otherwise weakly configured), and set `repository.owner.login`/`organization.login = X`. `verify_webhook_signature` will then unconditionally `return true` for `X` regardless of the actual `X-Hub-Signature` header (or lack thereof).
2. Simultaneously set `repository.full_name` to any real, secured repository/stack tracked by Shipit (e.g. `victim-org/victim-repo`), which is unrelated to `X`.
3. The signature check passes (because of step 1), and the handler then processes the event against the victim's stack (step 2) — e.g. `push` triggers `GithubSyncJob`/`sync_github`, `check_suite`/`status` mutate commit statuses, `pull_request` events can archive/unarchive review stacks or drive the merge queue's `StatusChecker`, and `membership` events can add arbitrary GitHub users to `Team`s that gate `Shipit.github_teams` authorization (`app/models/shipit/webhooks/handlers/membership_handler.rb`).

This is the direct structural analog of the gnark issue: a single verification step is trusted to bind multiple logically-independent values (here, "which secret authorizes this request" and "which repository this request concerns"), but the underlying data lets an attacker satisfy the check for one value while freely controlling the other, because both are read from the same unauthenticated blob before any cryptographic binding is established.

### Impact Explanation
An unprivileged, unauthenticated network attacker (no session, no `ApiClient` token, no real `webhook_secret`) can forge webhook deliveries against any repository/stack tracked by a Shipit instance that has at least one configured GitHub organization/app without a `webhook_secret` (which the docs explicitly present as an optional, valid configuration), by naming that unsecured organization in `repository.owner.login`/`organization.login` while pointing `repository.full_name` at the target stack. This can drive unauthorized GitHub syncs, status mutations, merge-queue interference, review-stack archiving, and team-membership manipulation (`membership_handler.rb`) that feeds directly into `Shipit.github_teams` authorization — an escalation into authorization state as described in the High-severity criteria.

### Likelihood Explanation
Exploitability requires the deployment to use the documented multi-organization `github:` schema with at least one organization lacking `webhook_secret` — a configuration explicitly presented as valid/optional in `docs/setup.md` and `config/secrets.development.example.yml`. Given that likelihood is conditioned on this common, documented configuration pattern (rather than a misconfiguration outside the engine's control), likelihood is moderate-to-high in multi-org deployments and the endpoint itself (`/webhooks`) requires no credentials to reach.

### Recommendation
- Never let an unverified value read from the same request body select the trust boundary used to verify that body. Determine the organization/app context for signature verification from routing/config that is independent of attacker-controlled JSON (e.g., dedicated per-org webhook endpoints, or verify against *all* configured secrets and require exactly one match), rather than `params.dig('repository','owner','login')`.
- Stop treating an absent `webhook_secret` as an implicit "always verified" bypass (`return true unless webhook_secret`) in multi-org configurations; either require a secret for every configured organization or make it explicit and loud (reject the webhook) rather than silently accepting unsigned payloads.
- After the signature is verified, cross-check that the organization used for verification actually owns the repository referenced by `repository.full_name` in the payload before dispatching to handlers.

### Proof of Concept
Given a Shipit deployment configured like `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`, each independently configured) where `OrgOne` has no `webhook_secret` set and `OrgTwo` is properly secured and hosts a tracked `victim-repo` stack:

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json
# No valid X-Hub-Signature required

{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/victim-repo"
  }
}
```
- `repository_owner` resolves to `"OrgOne"` → `Shipit.github(organization: "OrgOne")` → `verify_webhook_signature` returns `true` unconditionally since `OrgOne` has no `webhook_secret` (`lib/shipit/github_app.rb:76-83`).
- `PushHandler` then resolves the stack via `repository.full_name = "OrgTwo/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and triggers `stack.sync_github(expected_head_sha: ...)` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) on the victim's real, secured stack — despite the attacker never possessing `OrgTwo`'s `webhook_secret`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
