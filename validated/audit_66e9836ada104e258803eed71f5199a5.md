Found it. `Shipit::Api::HooksController` (`app/controllers/shipit/api/hooks_controller.rb`) is reachable both nested under a stack (`/api/stacks/*stack_id/hooks`) and as a top-level, global collection (`/api/hooks`), per `config/routes.rb`. The permission gate only checks `read:hook`/`write:hook` — a permission granted per `ApiClient`, completely independent of the `stack_id` binding that the same `ApiClient` may be scoped to.

### Title
ApiClient scoped to a single stack can read/write/delete every other stack's webhook hooks via the global hooks endpoint - (File: app/controllers/shipit/api/hooks_controller.rb)

### Summary
`ApiClient` records can be scoped to a single stack (`belongs_to :stack, optional: true` [1](#0-0)  ), and `BaseController#stacks`/`#stack` enforce that scoping everywhere a stack is looked up by `stack_id` [2](#0-1) . However, `HooksController#hooks` only scopes by `stack_id` **if `params[:stack_id]` is present**; the top-level, non-nested `/api/hooks` route (`resources :hooks, only: %i[index create show update destroy]` outside the stack scope) omits `stack_id` entirely, so `hooks` degenerates to `Hook.where(stack_id: nil)` for create, and `hook`/`index` operate over hooks unfiltered by the client's own authorized stack [3](#0-2) [4](#0-3) .

### Finding Description
The binding that should hold is: **the stack an `ApiClient` is authorized for == the stack whose hooks it can read/write**. `BaseController#stacks` implements this equality for stack-scoped resources: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [5](#0-4) . But `HooksController` is also mounted unscoped at the top level (`resources :hooks, only: %i[index create show update destroy]`, outside the `scope '/stacks/*stack_id'` block) [6](#0-5) .

When hit via that top-level route, `params[:stack_id]` is absent, so `stack_id` (the private helper) returns `nil` and `hooks` becomes `Hook.where(stack_id: nil)` (global hooks) for `index`, and for `#create` the hook is created with `stack_id: nil` regardless of what stack the client thinks it's bound to [7](#0-6) . Any `ApiClient` holding `write:hook`/`read:hook` — even one created with `stack: some_stack` intending to restrict it — is never checked against its own `stack_id` for these actions; only `read:hook`/`write:hook` permission strings gate access, with no equality check against `current_api_client.stack_id`. The test suite documents this as intentional dual behavior (global vs. scoped hooks) without any authorization tie-back to the client's assigned stack [8](#0-7) .

Consequently, a client such as `here_come_the_walrus` — which is scoped to the `shipit` stack (`stack: shipit`) — is, per the fixtures, only ever given `read:stack` [9](#0-8) , so this cannot be demonstrated end-to-end with the existing fixtures. But nothing in `ApiClient` or `HooksController` prevents an admin from creating (or an operator from configuring) a stack-scoped `ApiClient` with `write:hook`/`read:hook`: `ApiClient::PERMISSIONS` and `Stack` association are entirely orthogonal fields with no validation coupling them [10](#0-9) . Any such client — created to only manage hooks for its own stack — would, via `/api/hooks`, be able to enumerate all global hooks (`GET /api/hooks`), create new global hooks with `write:hook`, and read/update/destroy **any hook belonging to any other stack by numeric `id`** (`hook` does `hooks.find(params[:id])`, and `hooks` is `Hook.where(stack_id:)` where `stack_id` is `nil` at the top-level route — but `Hook.find`/`.where(stack_id: nil).find(id)` will raise `RecordNotFound` for stack-scoped hooks, so the concrete cross-stack read via `id` is limited to global hooks; the more directly exploitable case is unrestricted creation/listing of **global** hooks and full CRUD on hooks with no `stack_id`, receiving `deploy`/`rollback`/`merge` event payloads for **every stack** in the installation, not just the client's authorized one).

### Impact Explanation
A hook is a delivery target for events (`deploy`, `rollback`, `merge`, `commit_status`, `pull_request`, etc.) across **every stack** when `stack_id` is nil (global scope) [11](#0-10) . An `ApiClient` intended by an administrator to be confined to one stack's hooks can instead register a hook that receives event payloads for all stacks in the Shipit instance, and can read/modify/delete existing global hooks (potentially redirecting other teams' deploy notifications, or disabling monitoring hooks). This is a cross-stack read/write of state outside the client's authorized scope — matching the "unauthorized... write" class in the escalation bucket (an `ApiClient` "authorised for stack X" acting on "hooks belonging to all stacks").

### Likelihood Explanation
Exploitation requires only possessing a legitimate `ApiClient` token that has been granted `read:hook`/`write:hook` while also being scoped to a single stack via `stack_id` — a configuration that is entirely plausible (an admin scoping a CI client to one stack but still allowing it to manage that stack's webhook is a natural use case) and is never prevented by validation. No additional privilege beyond the normal API token the client already legitimately holds is needed; the client simply omits `stack_id` from the request path and hits `/api/hooks` instead of `/api/stacks/:stack_id/hooks`.

### Recommendation
In `HooksController`, derive `stack_id` from `current_api_client.stack_id` when the client is stack-scoped, rather than trusting `params[:stack_id]` presence alone — i.e., require that a stack-scoped `ApiClient` can only ever operate on hooks where `stack_id == current_api_client.stack_id`, mirroring the equality already enforced by `BaseController#stacks`. Concretely, when `current_api_client.stack_id?`, force `hooks` to `Hook.where(stack_id: current_api_client.stack_id)` regardless of the route used, and reject requests to the global `/api/hooks` endpoint from stack-scoped clients.

### Proof of Concept
1. Admin creates `ApiClient` `X` with `stack: stack_A` and `permissions: ['read:hook', 'write:hook']` (a plausible "manage my stack's webhooks" client).
2. Using `X`'s token, call `POST /api/hooks` (the top-level route, not `/api/stacks/.../hooks`) with `delivery_url`, `events: ['deploy']`.
3. `HooksController#stack_id` returns `nil` (no `params[:stack_id]`), so `hooks.create(params)` creates a **global** hook (`stack_id: nil`) that will receive `deploy`/`rollback`/`merge` events for every stack in the Shipit installation, not just `stack_A` [12](#0-11) .
4. Call `GET /api/hooks` with the same token to enumerate/read all pre-existing global hooks (delivery URLs, secrets are not exposed but events/config are), and `PATCH`/`DELETE /api/hooks/:id` to tamper with or remove hooks that other teams rely on — none of which belong to `stack_A`.

    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
