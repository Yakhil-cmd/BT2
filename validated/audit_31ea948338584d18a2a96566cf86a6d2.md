### Title
Signature-verification org binding is decoupled from repository resolution in `LabelCapturingHandler#capture_labels`, allowing cross-org label injection - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
In a multi-org Shipit deployment (`config/secrets.yml` with per-org GitHub App entries, as documented in `docs/setup.md` "Using Multiple Github Applications"), `WebhooksController#verify_signature` selects which org's `webhook_secret` to validate against using `params.dig('repository', 'owner', 'login')`, while `LabelCapturingHandler#repository` resolves the actual repository to mutate using the independent field `params.repository.full_name`. Nothing ties these two fields together, so a webhook signed with one org's secret can carry a `repository.full_name` pointing at a repository belonging to a completely different org, letting attacker-controlled label data overwrite a victim `PullRequest` row.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`Shipit.github(organization: repository_owner).webhook_secret` used to accept the request `==` the secret that actually protects the repository named in `params.repository.full_name` — **false** whenever `repository.owner.login` and `repository.full_name`'s owner segment diverge.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and verifies the raw POST body's HMAC against `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [7](#0-6) 
2. In a multi-org configuration, `Shipit.github(organization:)` looks up a distinct config/secret per org key via `github_app_config(organization)`. [5](#0-4) 
3. Once the signature check passes for "attacker-org" (using the secret the attacker themselves chose when they created their own GitHub App, per `docs/setup.md`), the raw JSON body — fully attacker-controlled since this is a direct POST to `/webhooks`, not a real GitHub delivery — is dispatched to `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler`.
4. `LabelCapturingHandler#repository` resolves the target repo solely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`, with no comparison to `repository.owner.login` used in step 1. [8](#0-7) 
5. `stack` is found by `ReviewStackAdapter#stack`, scoped only to that resolved repository's `review_stacks` and keyed by `environment = "pr#{params.number}"` — again no org/owner cross-check. [6](#0-5) 
6. `capture_labels` then runs `stack.pull_request.update!(labels: params.pull_request.labels.map(&:name))`, persisting attacker-chosen strings onto the victim repo's `PullRequest` row. [9](#0-8) 

The `ExplicitParameters` schema only requires `repository.full_name` to be a `String`; it never requires or validates `repository.owner.login` to match, and no code anywhere re-derives `repository_owner` from `full_name` or vice versa for use inside the handler. Existing guards (`drop_unhandled_event`, `check_if_ping`, the params schema, `review_stacks_enabled`, `provisioning_behavior` checks, archived-stack checks) all operate on the attacker-controlled payload fields and do nothing to bind the authenticating org to the target repository.

### Impact Explanation
A repository under one GitHub org (owned/administered by the attacker via a legitimately-configured Shipit GitHub App, per the documented multi-org setup) can have its correctly-signed webhook payload's `repository.full_name` field repointed at an arbitrary victim repository under a different org configured on the same Shipit instance. This lets the attacker overwrite the victim `PullRequest.labels` with arbitrary attacker-chosen values for any existing review-stack PR number in the victim repo. Since labels feed provisioning/archival decisions in `LabeledHandler`, `UnlabeledHandler`, `OpenedHandler`, and `ReopenedHandler` (`provisioning_behavior_allow_with_label?`/`prevent_with_label?`), this is a cross-tenant data-integrity issue that can influence downstream provisioning/merge behavior for a repo the attacker never authenticated for — matching "a payload for one repository mutating another's stack." This is repeatable against any repo/PR-number pair configured with `review_stacks_enabled`, for as many victim orgs as are configured on the shared Shipit instance.

### Likelihood Explanation
Requires: (a) Shipit configured for multiple GitHub orgs (a documented, supported configuration), (b) attacker able to set up their own GitHub App/org entry in that Shipit instance (i.e., they are an onboarded org, but with no elevated privilege over other orgs), (c) victim repo has `review_stacks_enabled` and an existing `PullRequest`/stack for the targeted PR number. Given those preconditions, exploitation costs a single crafted HTTP POST with a valid HMAC computed from the attacker's own known secret — no victim secrets, sessions, or tokens required.

### Recommendation
In `WebhooksController`/handler `repository` resolution, derive and enforce that the org used to verify the signature (`repository_owner`) matches the owner segment of `params.repository.full_name` before dispatching to any handler (e.g., reject the request if `full_name.split('/').first.casecmp(repository_owner) != 0`), or resolve the target `Repository` scoped to the authenticated org rather than trusting `full_name` globally across all configured orgs.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test, multi-org secrets fixture)
test "label capturing handler cannot be repointed to a repository outside the authenticating org" do
  # victim: repo "victim-org/victim-repo" configured under Shipit org "victim-org"
  victim_repo = shipit_repositories(:victim) # owner: "victim-org", name: "victim-repo"
  stack = create_review_stack_for(victim_repo, number: 42)
  stack.pull_request.update!(labels: ["known-good"])

  payload = payload_parsed(:pull_request_labeled)
  payload["repository"]["full_name"] = "victim-org/victim-repo"
  payload["repository"]["owner"]["login"] = "attacker-org" # attacker's own org
  payload["number"] = 42
  payload["pull_request"]["number"] = 42
  payload["pull_request"]["labels"] = [{ "name" => "attacker-injected" }]
  body = payload.to_json

  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] =
    "sha1=#{OpenSSL::HMAC.hexdigest('sha1', ATTACKER_ORG_WEBHOOK_SECRET, body)}"

  post :create, body:, as: :json

  stack.pull_request.reload
  # Binding under test: org that authenticated (attacker-org) == org owning the mutated row (victim-org)
  assert_not_equal "attacker-org", "victim-org" # the two orgs are distinct, i.e. cross-org
  assert_equal ["known-good"], stack.pull_request.labels,
    "victim PullRequest.labels must not change from a payload authenticated under a different org"
end
```
This test signs the body only with the attacker's own org secret and asserts the victim's `PullRequest.labels` remain unchanged; as written today, the code updates them to `["attacker-injected"]`, demonstrating the cross-org write.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
