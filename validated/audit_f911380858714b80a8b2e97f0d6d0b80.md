This confirms the vulnerability chain. Key finding:

- `WebhooksController#verify_signature` selects the HMAC key by calling `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the still-unauthenticated JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) .
- The `Handlers::Handler` base class, used by `StatusHandler`, resolves the target repository from a *different* field of the same untrusted payload: `payload.dig('repository', 'full_name')` [2](#0-1) .
- `StatusHandler#process` then writes a `Status` for **any** commit matching `params.sha` across the whole install, using attacker-supplied `state`, `description`, `target_url`, `context` verbatim: [3](#0-2) .
- `Status#schedule_continuous_delivery` / `Commit#schedule_continuous_delivery` then trigger `ContinuousDeliveryJob`, which will auto-deploy if the commit's cached CI state is `success` and `continuous_deployment?` is enabled [4](#0-3) [5](#0-4) .
- This deployment install supports multiple independent GitHub Apps/orgs with distinct `webhook_secret`s, exactly the scenario documented in `docs/setup.md` "Using Multiple Github Applications" and exercised in `test/dummy/config/secrets_double_github_app.yml` [6](#0-5) .

### Title
Cross-organization webhook forgery lets an attacker's own GitHub App secret authenticate status payloads for a victim organization's stacks, enabling unauthorized deploys - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` derives *which* organization's `webhook_secret` to check the HMAC against from the same untrusted JSON body it is about to trust, and that field (`repository.owner.login`) is never cross-checked against the field the event handlers actually act on (`repository.full_name`). In a multi-organization Shipit deployment, an attacker who legitimately controls (or has compromised) one configured GitHub App/organization can forge a valid signature using their own secret while spoofing the `repository` object to point at a completely different, victim organization's tracked stack, letting them inject arbitrary commit statuses—and, via continuous deployment, unauthorized deploys—for repositories they have no access to.

### Finding Description
The binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository the handler writes to`.

`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [7](#0-6) 

Both `repository_owner` (used to pick the HMAC key) and the value later used by handlers to select which DB rows to mutate (`payload.dig('repository', 'full_name')`, in `Handlers::Handler#repository_name`) come from the **same attacker-controlled JSON body**, and they are never checked for consistency: [2](#0-1) 

`StatusHandler`, however, does not even use `repository_name`/`stacks` scoping — it matches purely by `sha` across the entire install:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

`create_status_from_github!`/`Status.replicate_from_github!`-style write persists the attacker's `state`, `description`, `target_url`, and `context` verbatim [8](#0-7) .

This install supports multiple independent GitHub Apps, one per organization, each with its own `webhook_secret`, which is exactly `Shipit.github(organization:)`'s purpose [9](#0-8) , and is a documented, tested configuration [6](#0-5) .

### Impact Explanation
An attacker who is the legitimate owner/admin of GitHub App/organization "AttackerOrg" (configured on the same shared Shipit instance as victim organizations) knows their own `webhook_secret`. They can POST to `/webhooks` with `X-Github-Event: status` and a body such as:
```json
{
  "repository": { "owner": { "login": "AttackerOrg" } },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
signed with AttackerOrg's own secret. `verify_signature` passes because it only checks against AttackerOrg's key. `StatusHandler` then finds `Commit.where(sha: ...)` regardless of which stack/organization owns it and creates a forged "success" status. If the targeted commit's stack has `continuous_deployment` enabled, this forged status can make the commit satisfy `required_statuses`/`deployable?`, triggering `ContinuousDeliveryJob` and an **unauthorized deploy** of a commit that never passed real CI — a direct violation of collateralization/authorization guarantees analogous to the reported `sUSX` mintCap bypass (verification bound to one entity, enforcement/state-mutation applied to a different one).

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization (a documented, supported feature) and that the attacker controls one of those organizations' GitHub Apps (i.e., is a legitimate but low-privilege tenant on a shared install) — no repository write access, `ApiClient` token, or Shipit account credentials are needed, satisfying the "unprivileged attacker" requirement.

### Recommendation
In `WebhooksController#verify_signature`/`Handlers::Handler`, after selecting the `GitHubApp` by `repository_owner`, verify that the organization used to authenticate the signature matches the owner of the `repository.full_name` actually being acted upon (and reject/424 on mismatch) before dispatching to any handler, especially `StatusHandler`, which currently performs no per-organization/per-stack scoping at all.

### Proof of Concept
1. Configure Shipit with two orgs, `AttackerOrg` and `VictimOrg`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the owner of `AttackerOrg`'s GitHub App, compute a valid HMAC-SHA1 signature over a JSON body using `AttackerOrg`'s `webhook_secret`:
```json
{
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "AttackerOrg/irrelevant" },
  "sha": "<sha of a real commit on a VictimOrg-owned stack with continuous_deployment=true>",
  "state": "success",
  "context": "<VictimOrg stack's required ci context>"
}
```
3. POST to `/webhooks` with `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` succeeds (keyed on `AttackerOrg`); `StatusHandler#process` matches the commit by `sha` alone (ignoring which org it belongs to) and creates the forged `Status`, which can trigger `ContinuousDeliveryJob` and an unauthorized deploy on `VictimOrg`'s stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
