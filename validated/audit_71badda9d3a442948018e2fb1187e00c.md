### Title
`StatusHandler#process` writes commit statuses by bare SHA across all repositories, letting one authenticated repo's `status` webhook mutate another stack's commit and trigger continuous deployment - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)`, with no repository/stack scoping, unlike sibling handlers (`PushHandler`, `CheckSuiteHandler`) which scope through `stacks` (derived from the webhook payload's `repository.full_name`). Since GitHub SHAs are content-addressed and identical across forks/shared history, an attacker who owns a repository sharing a commit with a victim stack can send a validly-signed `status` webhook for their own repo that flips the status of the victim's `Commit` record for that SHA, and if the victim stack has `continuous_deployment` enabled, this can force a ship or block.

### Finding Description
The broken binding: for any commit-status write, the invariant should be `commit.stack.repository == webhook.authenticated_repository`. `StatusHandler` breaks this by querying `Commit.where(sha: params.sha)` [1](#0-0)  with no repository filter, in contrast to `PushHandler#process`, which scopes lookups through `stacks` (built from `Repository.from_github_repo_name(repository_name)`) [2](#0-1)  and `CheckSuiteHandler#process`, which likewise scopes through `stacks.where(branch:)` before touching `stack.commits` [3](#0-2) . The `Handler` base class exposes exactly this scoping helper (`stacks`, derived from `payload.dig('repository', 'full_name')`) [4](#0-3) , but `StatusHandler` does not use it.

`WebhooksController#verify_signature` only proves that the webhook was signed for the `repository_owner`/org named in *this* payload [5](#0-4) ; it says nothing about which `Commit` rows the handler is allowed to touch. Since `Commit` rows belong to a `Stack` (`belongs_to :stack`) and are keyed only by `sha` at the handler-query level [6](#0-5) , any commit sharing the same 40-hex SHA in a different stack/repo (fork, mirrored repo, cherry-picked/shared history) gets its status mutated by `commit.create_status_from_github!(params)` regardless of which repo actually authenticated the webhook.

Exploit flow:
1. Attacker forks or mirrors the victim's repository/history so that a specific commit SHA `S` exists both in a Shipit stack tracking the attacker's own repo (or is otherwise known/predictable) and in the victim's stack.
2. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for their own repo, `context: ci/test`, `state: failure`, `sha: S`.
3. `verify_signature` passes because it validates only against the attacker's own repo/organization.
4. `StatusHandler#process` runs `Commit.where(sha: S)`, which matches the victim stack's `Commit` row for `S` too, and calls `create_status_from_github!` on it.
5. `add_status` recomputes `status`/`blocked?`/`deployable?` for the victim's commit and can call `stack.schedule_merges` or feed `Commit#schedule_continuous_delivery`'s downstream evaluation path, and if the victim stack has `continuous_deployment` enabled, the change in deployability (`Commit#deployable?`, `Commit#blocked?`) is evaluated by `ContinuousDeliveryJob` against `stack.deployable?` [7](#0-6) [8](#0-7) .

No existing guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) checks that the resolved `Commit` rows belong to a stack whose repository matches the authenticated payload's `repository.full_name`.

### Impact Explanation
A payload authenticated for repository A can write a `Status` record onto a `Commit` belonging to a stack for repository B, satisfying the rule's "payload for one repository mutating another's stack/commit". Depending on state (`success`/`failure`) and the victim's blocking/required-status configuration, this can flip `Commit#blocked?`/`Commit#deployable?`, which on a `continuous_deployment`-enabled stack drives `ContinuousDeliveryJob`'s deploy decision — an unauthorized deploy or forced block of a legitimate deploy. This matches the Critical category ("a payload for one repository mutating another's stack, commit ... or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
The precondition is that the same commit SHA exists in both the attacker-controlled repository (which they can validly sign webhooks for) and the victim's tracked stack — realistic for forks, mirrors, or shared upstream history, which is common in the GitHub ecosystem this engine targets. The attacker needs no Shipit credentials, session, or API token — only the ability to own/control a GitHub repository and cause GitHub to emit a `status` event for it (or replicate a valid signature using their own webhook secret for their own repo). The attack is repeatable at will for any SHA the attacker can get to coincide with a victim commit.

### Recommendation
Scope `StatusHandler#process` through the `stacks` helper (as `PushHandler` and `CheckSuiteHandler` do), restricting the lookup to commits belonging to stacks whose repository matches `repository_name`/`payload.dig('repository', 'full_name')`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently iterate `stacks` and query `stack.commits.where(sha: params.sha)`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, new file):
1. Create `repository_a` and `repository_b` (different `full_name`), each with its own `stack` (`stack_a`, `stack_b`), `stack_b.continuous_deployment = true`.
2. Create `commit = Commit.create!(stack: stack_b, sha: 'a' * 40)` representing the victim's tracked commit, with a prior passing `ci/test` status so `commit.deployable?` is `true` before the attack.
3. Build a `status` webhook payload with `repository.full_name = repository_a.full_name`, `sha: 'a' * 40`, `context: 'ci/test'`, `state: 'failure'`.
4. Assert before: `commit.reload.deployable?` is `true` and `commit.stack_id == stack_b.id` while payload's `repository.full_name != stack_b.repository.full_name`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
6. Assert after: `commit.reload.deployable?` is now `false` (or `blocked?` true), even though the authenticated repository for this webhook was `repository_a`, not `repository_b` — demonstrating the cross-repository write and the resulting effect on `stack_b`'s (continuous-deployment-enabled) deployability decision.

      verified = github_app.verify_webhook_signature(

      )
