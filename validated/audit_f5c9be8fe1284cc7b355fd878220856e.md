### Title
Case-collision bypass in `FindNameCollisions` allows silent skill overwrite on case-insensitive filesystems - ([File: internal/skills/discovery/collisions.go])

### Summary
`FindNameCollisions` groups skills by an exact-string map key (`byName[s.Name]`), so two skills whose `Name` values differ only by case (e.g. `Foo` vs `foo`) are treated as distinct and never reported as a collision. Because `installSkill`/`installLocalSkill` in `internal/skills/installer/installer.go` builds the on-disk directory with `filepath.Join(baseDir, skill.Name)` using the raw, case-preserved name, on a case-insensitive filesystem (default macOS/Windows) both skills resolve to the same physical directory, causing the second-installed skill's files (including `SKILL.md`) to silently overwrite the first's.

### Finding Description
`matchSkillConventions` in `internal/skills/discovery/discovery.go` derives `Skill.Name` directly from the directory basename (`path.Base(dir)`) at lines [1](#0-0)  with no case normalization, and `validateName`/`safeNamePattern` explicitly allow any-case letters (`^[a-zA-Z0-9][a-zA-Z0-9._\- ]*$`) at [2](#0-1) . An attacker-controlled repo can therefore contain `skills/Foo/SKILL.md` and `skills/foo/SKILL.md`, both passing discovery and producing `Skill{Name:"Foo"}` and `Skill{Name:"foo"}`.

`FindNameCollisions` keys its grouping map by the exact string `s.Name` with no case folding: [3](#0-2) . `"Foo"` and `"foo"` are different Go map keys, so `len(group) <= 1` for each and no `NameCollision` is produced, meaning `collisionError` in `pkg/cmd/skills/install/install.go` (`discovery.FindNameCollisions(ss)` at [4](#0-3) ) returns `nil` — no error, no warning, installation proceeds for both skills.

During install, `installSkill` computes the target directory purely from `skill.Name` (explicitly *not* `InstallName()`, to force a flat layout): [5](#0-4) . On a case-sensitive filesystem this creates two separate directories (`Foo/` and `foo/`), so there's no clash. But on a case-insensitive filesystem (default HFS+/APFS on macOS, NTFS on Windows), `filepath.Join(baseDir, "Foo")` and `filepath.Join(baseDir, "foo")` resolve to the same physical directory entry. Both `installSkill` invocations `os.MkdirAll` the same directory and `os.WriteFile` their respective files into it (lines [6](#0-5) ), so whichever skill installs second (order is non-deterministic — `Install` uses a worker pool over `opts.Skills` for `--all` with `maxConcurrency` goroutines, lines [7](#0-6) ) silently overwrites files—including `SKILL.md`—of the other, with no error, warning, or collision detection ever surfacing to the user.

### Impact Explanation
This is a file-write-outside-expectation / content-integrity bug: a victim running `gh skill install owner/repo --all` (or selecting both skills interactively) on macOS/Windows ends up with one skill's `SKILL.md` and supporting files silently replaced by attacker content in the merged directory, with the collision-detection safeguard (`collisionError`) never firing to warn them. Since `SKILL.md` content is later parsed and acted upon by AI agents (per the codebase's stated purpose), this enables a supply-chain-style content-injection into what the victim believes is the trusted skill they selected. Matches GitHub bounty impact class of file write outside intended scope / verification-soundness bypass, though the write is confined to the intended skills install directory (not arbitrary path traversal) — the harm is silent overwrite/spoofing rather than out-of-tree write.

### Likelihood Explanation
Requires only an unprivileged attacker publishing a public repo with two SKILL.md directories differing by case, and a victim on a case-insensitive filesystem (default for most macOS and Windows users) running `gh skill install owner/repo --all` or selecting both conflicting skills. No token, MITM, or social engineering needed beyond normal skill install flow; highly repeatable and deterministic in triggering the missing-detection condition (though which skill "wins" on disk is a race depending on goroutine scheduling in the concurrent installer).

### Recommendation
Normalize `Skill.Name` (and any namespace component) with case-folding (e.g. `strings.ToLower`) when building the collision-detection map key in `FindNameCollisions`, or better, always case-fold when computing install-path keys anywhere directory names are derived from repo content, since installer.go writes flat directories keyed by `skill.Name` on filesystems whose case-sensitivity cannot be assumed. Consider using `strings.EqualFold`-based grouping instead of exact map lookup to catch this cross-platform issue independent of the host OS's actual filesystem case sensitivity.

```go
// internal/skills/discovery/collisions_test.go
func TestFindNameCollisions_CaseInsensitiveBypass(t *testing.T) {
    skills := []Skill{
        {Name: "Foo", Path: "skills/Foo"},
        {Name: "foo", Path: "skills/foo"},
    }
    collisions := FindNameCollisions(skills)
    // Current (buggy) behavior: len(collisions) == 0
    // Expected (fixed) behavior: len(collisions) == 1
    if len(collisions) == 0 {
        t.Fatal("case-differing skill names 'Foo'/'foo' not detected as a collision, " +
            "but would clobber each other on a case-insensitive filesystem")
    }
}
```
Companion integration test (`installer_test.go`) would stub `os.MkdirAll`/`os.WriteFile` targets to a lowercase-normalizing path resolver simulating a case-insensitive FS, install both `Foo` and `foo` skills via `Install(&Options{Skills: []discovery.Skill{{Name:"Foo",...},{Name:"foo",...}}, ...})`, and assert that the final directory contains only one skill's `SKILL.md` content (the other having been overwritten) while `collisionError` returned `nil` upstream.
