### Title
XCM `ERC20Transactor` credits the nominal transfer `amount` instead of the actual balance delta, allowing fee-on-transfer/deflationary ERC20 tokens to desync the XCM reserve-checking account balance from recorded holdings - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` move value by calling the target contract's `IERC20::transfer` and interpreting a `true` boolean return as proof that exactly `amount` moved, then crediting the XCM holding register (or asserting the deposit succeeded) with that same nominal `amount` — never comparing pre/post ERC20 `balanceOf` state. Any user can permissionlessly deploy an arbitrary ERC20-like contract via `pallet-revive` and reference it in XCM through `AccountKey20` locations, which `assets_common::ERC20Matcher` accepts unconditionally. This is the FRAME/XCM analog of the reported Morpho `PositionsManager` bug: trusting the caller-specified transfer amount instead of the measured balance change.

### Finding Description
`ERC20Matcher` (`MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`) matches any XCM `Asset` whose location is `{parents:0, X1(AccountKey20{key,..})}` and extracts `key` as the ERC20 contract address to call — no allow-list, no "sufficient"/trusted-asset gate exists at this matcher level [3](#0-2) . This transactor is wired into `AssetTransactors` on Asset Hub Westend as `ERC20Transactor` [2](#0-1) , reachable via signed `pallet_xcm::execute`/`transfer_assets` calls with no privileged origin required.

In `withdraw_asset_with_surplus`, the transactor extracts `(asset_id, amount)` from the caller-specified `Asset`, calls `transfer(checking_address, amount)` on the arbitrary contract, and if the ABI-decoded return value is `true`, unconditionally constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — crediting the XCM holding register with the full requested `amount`, regardless of what the checking account actually received [4](#0-3) . Symmetrically, `deposit_asset_with_surplus` calls `transfer(beneficiary, amount)` from the checking account and treats a `true` return as full success, without verifying the beneficiary's balance actually increased by `amount` [5](#0-4) .

A standard-conforming ERC20 `transfer` returns `true` on success even if the implementation internally burns/redirects a fee portion of `value` (this is exactly the fee-on-transfer pattern USDT/USDC could enable, and any custom Solidity contract deployable via `pallet-revive` can implement deliberately). Since `Erc20Credit(amount)` records the nominal amount rather than the delta actually observed at `checking_address`, the XCM executor's internal accounting of what the shared `ERC20TransfersCheckingAccount` custodies becomes inflated relative to the contract's real `balanceOf(checking_account)`.

### Impact Explanation
The `TransfersCheckingAccount` is a single shared reserve/custody account used across all XCM operations that route ERC20 value through this transactor. If the credited (`Erc20Credit`) amount in the XCM holding register systematically exceeds the real on-chain ERC20 balance held by the checking account, any XCM program that subsequently tries to `DepositAsset`/forward that credited value (e.g., depositing the "withdrawn" amount to a beneficiary, or via `InitiateTransfer` to a remote chain relying on this reserve) will attempt to move more real tokens out of the checking account than it possesses. Depending on the specific fee-on-transfer contract's behavior this either: (a) causes the subsequent `transfer` call from the checking account to revert (fail-closed, denial-of-service for legitimate users of that asset once the reserve is short), or (b) if multiple such operations interleave, allows draining real backing faster than recorded liabilities are decremented, harming later/legitimate holders of that asset's XCM-side representation — a reserve/backing insolvency, not merely a UX bug.

### Likelihood Explanation
Reaching this path requires only: (1) permissionlessly deploying a contract via `pallet-revive` on a chain configured with `ERC20Transactor` (Asset Hub Westend today) — no governance or privileged role; (2) implementing a `transfer` function that returns `true` while moving less than `value` to the recipient (a few lines of Solidity, fully within the attacker's control since they own the contract); (3) submitting a signed `pallet_xcm::execute`/`transfer_assets` extrinsic referencing that contract's address as an `AccountKey20` asset location, which `ERC20Matcher` accepts unconditionally. No malicious peer, validator, or governance action is needed.

### Recommendation
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` should measure the actual balance delta of the relevant account (via `balanceOf` before/after, or requiring the ERC20 implementation to guarantee exact transfer semantics) instead of trusting the caller-declared `amount` combined with a boolean success return, before crediting `Erc20Credit` or considering the deposit complete. Alternatively, restrict `ERC20Matcher` to a curated/registered allow-list of ERC20 contracts vetted to transfer exact amounts, rather than accepting arbitrary `AccountKey20` addresses.

	fn contains(location: &Location) -> bool {

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());

			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};

			Some(inner) => inner,
