### Title
Webhook Signature Verified Against `repository.owner.login`, But Event Processing Trusts Unbound `repository.full_name` — Cross-Organization Webhook Forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and therefore its `webhook_secret`) to validate the HMAC signature using the organization derived from `repository.owner.login` (or the `organization.login` fallback) in the raw JSON payload. Once the signature passes, `Shipit::Webhooks::Handlers::Handler#stacks` resolves the actual repository/stack to act on using a *different* payload field, `repository.full_name`. Because the field used to select the verifying secret and the field used to select the target repository are never checked for consistency, anyone who legitimately knows one organization's `webhook_secret` (e.g. an admin of their own org's installed GitHub App in a multi-tenant Shipit deployment) can forge a signed webhook whose `repository.owner.login` matches their own org (so the signature check passes) while `repository.full_name` points at a stack belonging to a completely different, unrelated organization hosted on the same Shipit instance.

### Finding Description
- Verification side: `verify_signature` computes `repository_owner` and fetches the app/secret for that organization: `github_app = Shipit.github(organization: repository_owner)` then calls `github_app.verify_webhook_signature(...)`. [1](#0-0) 
- `repository_owner` is read straight from the untrusted, attacker-supplied JSON body: [2](#0-1) 
- Processing side: once the signature is accepted, handlers resolve the target stacks from an entirely separate payload field, `repository.full_name`, with no cross-check against the organization that was used to verify the signature: [3](#0-2) 
- This engine explicitly supports hosting multiple GitHub organizations from a single Shipit instance, each with its own `webhook_secret`: [4](#0-3) 
- `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler#process`, which uses `stacks` (built from `repository.full_name`) to trigger `stack.sync_github(...)` — a real, state-changing action (deployable commit ingestion, and with continuous deployment configured, an actual deploy): [5](#0-4) 

Because the equality `organization authenticated by webhook_secret == organization that owns the acted-upon repository` is never enforced, the two can diverge: `repository.owner.login = OrgA` (used to pick and pass the HMAC check with OrgA's secret) while `repository.full_name = "OrgB/private-repo"` (used to find and mutate OrgB's stack).

### Impact Explanation
This breaks the deployment-trust boundary between organizations hosted on the same Shipit instance. An attacker who only controls/administers one organization's GitHub App installation (and thus legitimately knows that org's `webhook_secret`) can forge webhook deliveries that are processed as if they came from a different organization's repository. Depending on the handler and event, this can trigger unauthorized commit ingestion, CI status manipulation, or an actual continuous deployment (`stack.sync_github` → deploy) against a stack/repository the attacker has no legitimate access to — a cross-repository write / unauthorized deploy, which matches the Critical impact bar for this engine.

### Likelihood Explanation
Likelihood is high for any deployment configured with the documented multi-organization `github:` secrets layout: any org-scoped webhook secret holder can compute a valid `X-Hub-Signature` for a payload whose `repository.owner.login` is their own org while freely choosing `repository.full_name` to target a different org's stack, then simply POST it to `/webhooks`. No additional session, GitHub App private key, or victim-org secret is required.

### Recommendation
Enforce that the organization used to verify the signature is the same organization that owns the repository being acted upon. Concretely, derive the target repository strictly from the same trusted owner used for signature selection (e.g., validate `repository.full_name.split('/').first == repository_owner` before dispatching to handlers), or better, have handlers re-derive/validate the owning organization from `repository_owner` (already established during signature verification) instead of independently trusting `repository.full_name`.

### Proof of Concept
1. Assume Shipit is configured with multi-org secrets (`OrgA`, `OrgB`), each with a distinct `webhook_secret`, as documented in `docs/setup.md`.
2. Attacker administers `OrgA`'s installed GitHub App and thus knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha already known to exist in OrgB/private-repo>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/private-repo"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs it to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies successfully against `OrgA`'s secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/private-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on `OrgB`'s stack, even though the request was never authenticated for `OrgB`.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "repository_owner=#{repository_owner}",

    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
