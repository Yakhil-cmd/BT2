This confirms the vulnerability. `StatusHandler#process` does not scope its `Commit.where(sha:)` query by repository at all — unlike other handlers (`ClosedHandler`, `OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler`), which all resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` and scope subsequent operations to that repository's stacks, `StatusHandler` never reads `params.repository.full_name` nor uses the `stacks`/`repository_name` helpers already defined in the base `Handler` class.This confirms `Commit belongs_to :stack` only, with no repository-scoping delegated from `stack.github_repo_name` used anywhere inside `StatusHandler`. The `verify_signature` before_action only checks that the HMAC signature matches the org named in `repository_owner` — it never restricts which `Commit`/`stack` rows the payload's `sha` can touch. `drop_unhandled_event`, `ExplicitParameters` schema (`params do requires :sha ... end`) and `force_github_authentication`/`User#authorized?` are all irrelevant to this path since this is an unauthenticated webhook route scoped only by HMAC signature per-organization, not per-repository content.

### Title
Cross-tenant Status mutation via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by SHA across the entire `commits` table and calls `create_status_from_github!` on every match, without ever checking that the commit's stack corresponds to `payload['repository']['full_name']`. Since GitHub SHAs are content-addressed (git blobs/trees can be identical byte-for-byte, e.g. the empty tree `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or a fork mirrored into multiple Shipit stacks), a single verified webhook for repository A can mutate CI status/state (`Status`, and via `deployable?`/`blocked?`/`enable_ci_on_stack`) for commits belonging to stacks of unrelated repositories B, C, etc.

### Finding Description
Binding claimed: `mutated_stacks(status_webhook_for_repo_A) == {A}`. Actual code: [1](#0-0) 
does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no filter on `commit.stack.repository` or `params.repository`. Contrast with every other handler (`ClosedHandler`, `OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler`, `LabelCapturingHandler`), which all resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` first and scope their side effects to that repository's stacks — a pattern `StatusHandler` skips entirely, and the base `Handler#stacks`/`Handler#repository_name` helpers ( [2](#0-1) ) exist precisely for this purpose but are unused here.

`verify_signature` in `WebhooksController` only checks that the payload's HMAC matches the GitHub App keyed to `repository_owner`'s org ( [3](#0-2) ); it authenticates that *an* org sent the payload, not that the SHA belongs only to that org's commits. `ExplicitParameters` only validates the shape of the JSON (`requires :sha, String`), not cross-tenant scoping. No `require_permission!`/`User#authorized?` check applies since this is an unauthenticated webhook endpoint.

Attack: attacker owns/controls repo A (or any repo whose GitHub App webhook secret they can trigger — note: legitimate GitHub-triggered `status` events for repo A are sufficient, no forgery needed) and pushes/creates a commit whose SHA collides with an existing commit SHA already tracked in stacks for repos B/C (trivially achievable via the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, which is identical across every git repository, or via any repo forked/mirrored into multiple Shipit stacks sharing history). GitHub emits a `status` webhook for repo A with `sha=4b825dc6...`. `StatusHandler#process` finds all `Commit` rows with that SHA — potentially belonging to stacks for completely unrelated repositories B and C — and calls `create_status_from_github!` on each, writing a `Status` row, tripping `enable_ci_on_stack`, `schedule_continuous_delivery`, and altering `deployable?`/`blocked?` for those foreign stacks.

### Impact Explanation
A single verified webhook payload for repository A causes `Shipit::Status` records to be created for commits under repositories B, C, ... — this is exactly the "payload for one repository mutating another's stack/commit" Critical category. Effects per foreign stack: `Status.after_create :enable_ci_on_stack` flips `ignore_ci` state accounting, `schedule_continuous_delivery` may unblock/allow merges (`ProcessMergeRequestsJob`), and `deployable?`/`blocked?` calculations change, potentially permitting or blocking deploys on stacks the attacker does not own. This is repeatable at will using the deterministic empty-tree SHA (or any historically shared commit, e.g. common ancestor commits from forks) against any number of target stacks that happen to share that SHA.

### Likelihood Explanation
Preconditions: attacker needs (a) control of any single repository already wired to Shipit as stack A (trivial — any GitHub user can fork/create a repo and add it as a Shipit stack, or simply cause a legitimate `status` event on a repo already configured), and (b) existence of a `Commit` row with a matching SHA in another tracked stack. The empty-tree SHA is guaranteed to exist in essentially every git repository's history is not guaranteed to be recorded as a Shipit `Commit` row unless it was ever pushed to the tracked branch, so the more practical route is shared history between forks mirrored as separate Shipit stacks (common in monorepo-split or vendored setups) — plausible but requires some victim configuration alignment. No secrets are needed; only a legitimately signed webhook for the attacker's own repo.

### Recommendation
Scope the query by the payload's repository: resolve `repository = Shipit::Repository.from_github_repo_name(params_or_payload.dig('repository','full_name'))` and restrict to `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))` (or join through `stack.repository`), matching the pattern already used by `ClosedHandler`/`OpenedHandler`/etc. and the base `Handler#stacks` helper.

test ":status webhook for repo A mutates commits belonging to unrelated stacks B and C sharing the same SHA" do
  shared_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee4904'

  repo_a = shipit_repositories(:shipit) # or a factory-created Repository for 'org-a/repo'
  stack_b = create_stack_for_repo('org-b/repo')
  stack_c = create_stack_for_repo('org-c/repo')

  commit_a = repo_a.stacks.first.commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...)
  commit_c = stack_c.commits.create!(sha: shared_sha, ...)

  request.headers['X-Github-Event'] = 'status'
  body = {
    sha: shared_sha, state: 'success',
    repository: { full_name: repo_a.github_repo_name, owner: { login: repo_a.owner } }
  }.to_json

  post :create, body:, as: :json

  # Binding under test: only repo A's commit should have gained a status.
  assert_equal 1, commit_a.reload.statuses.count
  assert_equal 0, commit_b.reload.statuses.count, "commit in unrelated stack B was mutated"
  assert_equal 0, commit_c.reload.statuses.count, "commit in unrelated stack C was mutated"
end
