### Title
RAY index-value overflow permanently freezes large lending markets - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` converts the scaled borrow and supply totals into absolute RAY values before selecting the rate and updating indexes. [1](#0-0)  Those conversions use `scaled_to_original`, which performs an `i128`-bounded `scaled * index / RAY` multiplication and reverts with `MathOverflow` when the result is unrepresentable. [2](#0-1) [3](#0-2)  Consequently, sufficiently large markets can hit the aggregate RAY-value ceiling while both indexes remain far below their nominal `10^36` cap. [4](#0-3) 

### Finding Description
Any signed caller can invoke `Controller::update_indexes(caller, assets)`, which forwards the requested `HubAssetKey` list to the pool. [5](#0-4) [6](#0-5)  The pool accrual path loads each market and executes `interest::global_sync`, while ordinary mutation legs also call `global_sync` through `synced_market` before making any state change. [7](#0-6) [8](#0-7) 

`global_sync` chunks elapsed time, but chunking only bounds the exponent passed to `compound_interest`; it does not bound `borrowed * borrow_index` or `supplied * supply_index`. [9](#0-8) [10](#0-9)  Each chunk first calls `scaled_to_original` for both totals, then `update_borrow_index`, `update_supply_index`, and reward accounting all perform additional index-weighted products. [11](#0-10) [12](#0-11) [13](#0-12) [14](#0-13) 

For example, one billion whole tokens at 18 decimals produces `10^36` scaled RAY shares, so the `i128` limit is crossed near a `170x` index multiplier rather than the configured `10^9x` index ceiling. [15](#0-14)  The repository’s regression test drives a valid admitted market to that condition through repeated permissionless `update_indexes` calls and observes `MathOverflow`, after which both withdrawal and repayment also revert. [16](#0-15) 

### Impact Explanation
Once the affected market crosses the representable-value boundary, `update_indexes` cannot commit a new timestamp because accrual panics before `mark_accrued` is reached. [17](#0-16)  Every later operation still has elapsed time and enters the same overflowing step before it can repay debt, withdraw collateral, liquidate positions, socialize bad debt, claim revenue, or add liquidity. [8](#0-7) [18](#0-17)  This permanently freezes market funds and leaves borrowers unable to repay while suppliers cannot exit, which is a permanent freezing-of-funds and protocol-operation failure rather than a temporary fail-closed oracle condition. [19](#0-18) 

### Likelihood Explanation
The trigger does not require an authorization bypass or malformed argument: the caller only submits `update_indexes` for an existing `HubAssetKey`, and the setup consists of normal `supply` and `borrow` positions in a market whose configured caps admit sufficiently large totals. [20](#0-19) [5](#0-4)  The likelihood is bounded by the need for a very large book, suitable caps, and sustained index growth, but those inputs are within the protocol’s explicitly admitted cap and rate domains rather than invalid storage or corrupt parameters. [21](#0-20) [22](#0-21)  The protocol documentation itself recognizes that valid caps and bounded indexes do not guarantee that accrued values remain representable and that repayment or withdrawal can be blocked by the overflow. [23](#0-22) 

### Recommendation
Introduce a share-aware index ceiling before any `scaled * index / RAY` multiplication: `max_borrow_index = min(MAX_BORROW_INDEX_RAY, floor(i128::MAX * RAY / borrowed))` and analogously for `max_supply_index`, using an `I256` intermediate or an existing saturating mul-div helper so the bound itself cannot overflow. [12](#0-11) [24](#0-23)  When an index reaches that market-specific ceiling, accrual should clamp and continue committing `last_timestamp` instead of reverting, preserving repayment and withdrawal paths while stopping further interest growth. [9](#0-8)  The same bound must be used by `accrue_step`, `simulate_update_indexes_body`, `calculate_supplier_rewards`, `update_supply_index`, and `supply_index_reward_shortfall` so view and mutation behavior remain identical. [25](#0-24) [26](#0-25) 

### Proof of Concept
The existing long-horizon test is a direct PoC: it creates a valid 18-decimal market, supplies `1_000_000_000 * 10^18` base units, borrows 98% of it, advances ledger time year by year, and repeats the permissionless controller index update until `MathOverflow` is returned. [27](#0-26)  It then verifies that the borrow index remains below `MAX_BORROW_INDEX_RAY` and that both `withdraw` and `repay` fail with the same error. [28](#0-27) 

```rust
let market = HubAssetKey { hub_id, asset };
let assets = vec![&env, market.clone()];

controller.supply(
    supplier,
    supplier_account_id,
    spoke_id,
    &vec![&env, (market.clone(), 1_000_000_000 * 10i128.pow(18))],
);
controller.borrow(
    borrower,
    borrower_account_id,
    &vec![&env, (market.clone(), 980_000_000 * 10i128.pow(18))],
    None,
);

loop {
    advance_ledger_time();
    match controller.try_update_indexes(any_caller, &assets) {
        Err(_) => break,
        Ok(_) => continue,
    }
}

controller.try_withdraw(supplier, supplier_account_id, &vec![&env, (market.clone(), 1)], None);
controller.try_repay(payer, borrower_account_id, &vec![&env, (market, 1)]);
```

Both final calls panic with `GenericError::MathOverflow` because the pool accrues the stale market before processing either mutation. [8](#0-7) [19](#0-18)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
}

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}
