## Analysis

I've confirmed the key mechanism: `Shipit::WebhooksController#verify_signature` derives the GitHub organization used to select the HMAC secret from the **unauthenticated** request payload itself, before that payload has been verified: [1](#0-0) [2](#0-1) 

Meanwhile, the actual side effects performed in `create` (via handlers like `PushHandler`, `StatusHandler`) resolve the target `Stack`/`Repository` from a *different* field of the same payload — `repository.full_name` — with no cross-check that it matches the organization whose secret validated the signature: [3](#0-2) [4](#0-3) [5](#0-4) 

Multi-tenant configuration is real: `Shipit.github_organizations` / `Shipit.github_app_config` support multiple independent orgs each with their own `webhook_secret`: [6](#0-5) 

This satisfies the rule's named binding category: *"an organization that authenticated versus the repository that is written."*

### Title
Webhook signature is validated against an organization key chosen from unauthenticated payload data, letting any onboarded organization forge events for any other stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which organization's `webhook_secret` to HMAC-verify the request against by reading `repository.owner.login` / `organization.login` straight out of the still-unverified JSON body. The handlers that actually mutate state (`PushHandler`, `StatusHandler`, `MembershipHandler`, etc.) look up the target `Stack`/`Repository` from a *different* payload field, `repository.full_name`, with no requirement that this repository actually belongs to the organization that was used to validate the signature.

### Finding Description
In a multi-org Shipit deployment, `Shipit.github_organizations` lists several independent GitHub organizations, each configured with its own `app_id`/`webhook_secret` under `secrets.github` [6](#0-5) . Any of these organizations' administrators can legitimately install the Shipit GitHub App/webhook for their own org and therefore knows their own org's `webhook_secret` (it's provisioned to them when they configure the integration, and it's used to sign real webhooks that GitHub sends on their behalf — it is not secret from that org's own operators).

`verify_signature` computes `repository_owner` from the raw, unauthenticated JSON payload:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and uses it to select which app/secret to verify against: `Shipit.github(organization: repository_owner)` [1](#0-0) . This binds "which secret is used to authenticate" to attacker-controlled data, not to any GitHub-issued property of the actual HTTP delivery.

Once the signature check passes (because the attacker signed the body with their *own* org's secret and set `repository.owner.login` to match their own org), `create` dispatches to the event handler with the full parsed payload [7](#0-6) . Each `Handler` subclass then resolves the *actual affected repository* via `payload.dig('repository', 'full_name')` [8](#0-7)  — a field independent from `repository.owner.login`. There is no check anywhere that `repository.full_name`'s owner segment matches `repository_owner`/the org whose key validated the HMAC.

Consequently, an operator/member of Organization A (who legitimately knows Org A's webhook secret) can send a forged webhook whose `repository.owner.login` = "org-a" (to pass signature verification against Org A's secret) but whose `repository.full_name` = "org-b/victim-repo" (to target Org B's stack). The `PushHandler` would then call `stack.sync_github(expected_head_sha: params.after)` for Org B's stack [4](#0-3) , and `StatusHandler` would inject arbitrary commit statuses for any commit sha tracked by Org B's stacks [5](#0-4) , entirely bypassing the trust boundary that the per-org webhook secret is supposed to enforce.

### Impact Explanation
This breaks the binding "organization authenticated == repository written." A user who is only an admin/operator of one onboarded organization (not a privileged Shipit user, no `ApiClient` token, no Shipit session) can forge `push`, `status`, `check_suite`, or `membership` events attributed to a completely different organization's stacks. `StatusHandler` writing forged commit statuses can flip `MergeRequest#all_status_checks_passed?` for cross-org merge requests (`StatusChecker` in `merge_request.rb`), and `PushHandler` can trigger `sync_github` on victim stacks, both of which can influence whether a deploy/merge proceeds — i.e., an unauthorized change to deploy/merge state for a repository the attacker has no legitimate access to. This falls under "authentication bypass" / "unauthorized deploy" impact category, since the signature check — the sole authentication mechanism for this endpoint — is defeated for cross-tenant writes.

### Likelihood Explanation
Requires only that Shipit is configured for multiple GitHub organizations (a documented, supported configuration per `secrets.github` schema and `Shipit.github_organizations`) and that the attacker controls/operates one such onboarded organization (thus legitimately possessing that org's webhook secret through normal GitHub App setup) — no repository write access, GitHub App private key, or Shipit account is needed. This is a realistic configuration for any Shipit instance serving several teams/orgs.

### Recommendation
After `verify_webhook_signature` succeeds, enforce that the organization used to select the secret matches the actual owner of `repository.full_name` (and `organization.login` where relevant) in the payload before dispatching to handlers — i.e., re-derive/require consistency between the two fields, or better, always resolve stacks by validating `full_name`'s org segment equals `repository_owner` used for verification.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with a stack and its own `webhook_secret` (multi-tenant setup as supported by `Shipit.github_organizations`).
2. As an operator of `org-a` (who legitimately has `org-a`'s `webhook_secret` from installing the GitHub App), craft a `push` event payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature` using `org-a`'s webhook secret over this exact raw body.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature [1](#0-0) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` [3](#0-2)  and calls `sync_github(expected_head_sha: ...)` on `org-b`'s stack — a write the attacker has no legitimate authority over.
