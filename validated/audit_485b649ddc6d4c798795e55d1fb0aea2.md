### Title
Cross-repository status forgery via unscoped SHA lookup enables blocking_statuses bypass - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and applies the incoming GitHub `status` event to every matching row, without ever checking that the commit's `stack.repository` matches the repository that authenticated the webhook. An attacker who owns (or forks) a repository configured with Shipit can send a legitimately-signed `status` webhook for a commit whose SHA is shared with a victim stack (trivial via `git fork`, since forked history retains identical commit SHAs), forcing a `ci/integration: success` status onto the victim's commit and flipping `blocked?`/`deployable?` for a stack that has `blocking_statuses` configured.

### Finding Description
The broken binding: the code assumes `commit.stack.repository == repository_owner/repo_from_signed_payload`, but no such check exists.

- `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) validates the HMAC signature against the GitHub App/org derived from `repository_owner` (`params.dig('repository', 'owner', 'login')`). This proves the payload came from a real GitHub webhook belonging to that org/app — it does **not** prove that the `sha` field in the payload corresponds to a commit that only exists in that org's repositories. [1](#0-0) 
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a bare, global lookup across the entire `commits` table with **no repository/stack scoping** whatsoever. [2](#0-1) 
- `Commit#create_status_from_github!` → `add_status` recomputes `status`, and if the `simple_state` changes, calls `stack.schedule_merges` and emits `deployable_status` hooks. [3](#0-2) [4](#0-3) 
- `Commit#blocked?` walks `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)` — driven entirely by the `statuses` records just written by the forged webhook. [5](#0-4) 
- `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, so a forged `ci/integration success` status can flip a commit from blocked to deployable (or vice versa if the forged status is a `failure`/`error`). [6](#0-5) 

Exploit flow: Commit SHAs are content-addressed and identical across forks and any repository sharing history with the victim's tracked repo. An attacker forks the victim's (or any) public repository, has their fork configured behind a Shipit-registered GitHub App/org (which they control, satisfying `verify_signature` since it only checks org-level HMAC, not sha ownership), and sends `POST /webhooks` with `X-Github-Event: status`, a validly-signed payload for their own repo, `sha: <shared-sha>`, `context: ci/integration`, `state: success`. `StatusHandler` finds the victim's `Commit` row with the same SHA and writes the status to it, altering `blocked?`/`deployable?` for the victim's stack, regardless of that stack's repository or organization.

Existing guards fail because:
- `verify_signature` authenticates the *sender's own repo/org*, not the *sha's ownership*.
- `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/type of `sha`, `state`, `context`, not repository correlation.
- No model validation in `Commit`, `Status`, or `Stack` ties an incoming status update to the repository that produced the commit.

### Impact Explanation
A payload authenticated for one repository directly mutates commit/status state belonging to a completely different stack/repository/tenant — this is a cross-tenant state write matching the Critical category ("a payload for one repository mutating another's stack, commit, task"). Concretely, it can: (a) force `blocked?` to `false` on a victim stack with `blocking_statuses` configured, allowing an otherwise-blocked commit to become deployable and be auto-merged/deployed via `stack.schedule_merges` / continuous delivery, or (b) force a currently-deployable commit into a blocked state, disrupting the victim's deploy pipeline. This is repeatable against any stack/repository whose tracked commit history overlaps (via fork or shared upstream) with a repository the attacker controls.

### Likelihood Explanation
Preconditions: attacker needs a repository with Shipit's GitHub App/webhook installed for an org they control (their own account/org — trivial to set up if Shipit is multi-tenant, or they simply fork a monitored repo and enable their own webhook), and a victim stack configured with `blocking_statuses` tracking a commit whose SHA the attacker can reproduce (guaranteed for forked history). Attacker cost is a single signed HTTP POST to `/webhooks`; no Shipit credentials, session, or API token are required. Fully repeatable and scriptable against any repository sharing commit history with a Shipit-monitored stack.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers) to only update commits belonging to the stack(s) associated with the repository that authenticated the webhook (i.e., filter `Commit.where(sha: params.sha)` further by joining `stack.repository` matched against `params.dig('repository', 'full_name')`, or by looking up the stack via `repository_owner`/`repository_name` from the payload before touching any commit).

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook does not affect commits belonging to unrelated repositories sharing the same sha" do
  attacker_stack = shipit_stacks(:shipit) # repository X, attacker-controlled
  victim_stack   = shipit_stacks(:cyclimse) # repository Y, blocking_statuses: ['ci/integration']
  shared_sha = "a" * 40

  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "attacker")
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, message: "victim")

  # Precondition: victim commit is currently blocked (before == before)
  assert victim_commit.blocked?, "expected victim commit to be blocked before forged status"

  params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: shared_sha, state: "success", context: "ci/integration"
  )
  # Simulate webhook authenticated ONLY for attacker's repository/org
  Shipit::Webhooks::Handlers::StatusHandler.new.process(params)

  victim_commit.reload
  # Assert the binding: victim_commit.blocked? (after) should still equal victim_commit.blocked? (before)
  assert victim_commit.blocked?, "victim stack's blocked? state was flipped by a status authenticated for a different repository"
end
```
This demonstrates that `StatusHandler#process` mutates `victim_commit`'s status/blocked state purely from a SHA collision, without any repository ownership check.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
