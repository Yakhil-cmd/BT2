### Title
Single reverting secondary-AA call irreversibly bounces an entire multi-AA trigger chain, freezing/losing funds routed to unaffected sub-AAs - (File: `aa_composer.js`)

### Summary
When a primary Autonomous Agent (AA) sends payments to several secondary AAs in one response unit (a "fan-out to multiple strategies" pattern, e.g. a router/aggregator AA that forwards funds to N independent sub-AAs), `handleSecondaryTriggers` processes each secondary AA sequentially with `async.eachSeries` and treats **any single** secondary AA bounce as fatal for the whole chain, unconditionally calling `revert()`, which rolls back all state and balance changes for every AA in the chain — including the ones that executed successfully.

### Finding Description
`handleSecondaryTriggers` iterates over all output addresses that are AAs and invokes `handleTrigger` on each one in series: [1](#0-0) 

If any child AA in that list bounces (returns a `bounce_message`), the `async.eachSeries` callback receives an error and the primary handler does not try any partial-success handling — it calls `revert()` for the whole chain: [2](#0-1) 

`revert()` discards all cached responses, clears all accumulated `stateVars`, and issues a full `ROLLBACK TO SAVEPOINT initial_balances`, before finally bouncing the primary trigger: [3](#0-2) 

This is the AA-execution analog of the reported `MultiStrategyVault` issue: a "multi-strategy" AA that forwards a single trigger's funds/logic to multiple independent secondary AAs ("strategies") has no way to exclude one that is permanently reverting ("paused") from the aggregate operation. Because the fan-out is evaluated eagerly and any one failure reverts the entire batch, a single malfunctioning/permanently-bouncing secondary AA (analogous to a paused third-party pool) makes it impossible to complete the operation for the *other, healthy* secondary AAs as well — the primary AA's payment/state changes to all of them are rolled back every time, and the trigger unit bounces (funds returned minus bounce fee, with any user-intended distribution completely undone).

Unlike Solidity `try/catch`, oscript/AA execution provides no primitive for the primary AA author to "catch" a specific secondary AA's bounce and simply skip/exclude it while still processing the others — the same conceptual gap the C4 report highlights for `MultiStrategyVault`, where a paused strategy cannot be excluded from withdrawal fan-out.

### Impact Explanation
Any wallet/AA design that forwards a single trigger to multiple downstream AAs (a common Obyte pattern for AA-based routers, aggregators, or "vaults" distributing to several strategy AAs) is fully blocked as soon as one target AA starts reverting deterministically (e.g., due to a bug, a permanently failing precondition, or intentional "pause" logic within that AA). Every trigger to the router AA will keep reverting, since `handleSecondaryTriggers` always calls `revert()` on any single secondary failure — funds intended for the working secondary AAs never get delivered, and the router AA itself can become permanently unusable, i.e., AA fund freezing.

### Likelihood Explanation
This requires an unprivileged user only to send a normal trigger unit to a router/multi-target AA that fans out to several secondary AAs — no privileged access or malicious peer/node behavior is needed. The scenario is realistic: any secondary AA a router depends on could contain a bug or deliberate condition that causes it to always bounce (equivalent to "pausing" a third-party pool in the original report), and the router AA author has no oscript-level mechanism to isolate that failure.

### Recommendation
Provide oscript/AA authors a mechanism to treat a secondary AA's bounce as a local, catchable failure rather than an unconditional trigger for `revert()` of the entire chain — for example, an explicit "try remote call, on bounce continue with other targets" primitive, or allow `handleSecondaryTriggers` to optionally continue processing remaining secondary AAs and only roll back the specific failed sub-call plus any of the primary AA's response messages that strictly depended on it, rather than the whole batch.

### Proof of Concept
1. Deploy a primary "router" AA whose response unit sends payments to secondary AAs `A`, `B`, and `C` (analogous to strategies).
2. Deploy `B` such that it deterministically bounces for all triggers (simulating a "paused" strategy/third party).
3. Send a trigger unit to the router AA.
4. Observe in `handleSecondaryTriggers` (`aa_composer.js:1702-1757`) that even though `A` and `C` succeed, `B`'s bounce causes the `async.eachSeries` final callback to invoke `revert()` (`aa_composer.js:1749`), which rolls back state/balances for `A` and `C` too, and the whole trigger bounces.
5. Every subsequent identical trigger to the router AA produces the same result, permanently blocking distribution to the healthy secondary AAs as long as `B` keeps bouncing.
