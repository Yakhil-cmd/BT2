## Analysis

Shipit-engine supports **multi-tenant GitHub App configuration**: multiple organizations can each be configured in `secrets.github` with their own independent `webhook_secret`, selected at verification time by `Shipit.github(organization:)`. [1](#0-0) 

The webhook signature check derives which organization's secret to verify against **from a field inside the untrusted, attacker-supplied payload itself**: [2](#0-1) [3](#0-2) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` and used purely to select **which org's `webhook_secret` to check the HMAC against**. Once that check passes, the actual event handlers determine **which stack/repository to act on** using a *different* field of the same payload: [4](#0-3) 

`repository_name` (`payload.dig('repository', 'full_name')`) is never cross-checked against `repository_owner`. Both fields are attacker-controlled inside a single HTTP body that only needs to be self-signed with a secret the attacker legitimately possesses (their own organization's `webhook_secret`, configured for their own GitHub App installation in a multi-org Shipit deployment). Nothing forces `repository.owner.login == repository.full_name.split('/').first`.

The `status` webhook handler illustrates concretely how attacker-controlled payload fields turn into a database write, confirmed by the controller test: [5](#0-4) 

`state`, `target_url`, `description`, and `context` are copied verbatim from the payload into a `Status` record tied to the commit resolved via `stacks` (i.e., via `repository.full_name`), while the request is authenticated only against the organization named in `repository.owner.login`. Shipit's deploy safety machinery consumes these commit statuses (including "blocking statuses") to decide deployability, so this is a genuine authorization-relevant sink, not a cosmetic log line.

### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the event handlers act on the unrelated `repository.full_name` field, letting an org with its own valid `webhook_secret` inject commit statuses for a different organization's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization secret to validate the `X-Hub-Signature` against using `repository.owner.login` (or `organization.login`) taken from the raw JSON body. Once verified, `Webhooks::Handlers::Handler#stacks`/`#repository_name` independently reads `repository.full_name` from that same body to decide which `Stack`/`Repository` the event applies to. These two payload fields are never checked for consistency, so a payload that is internally self-consistent for signing (repository owner = attacker's own tenant) but names a *different* tenant's repository in `full_name` will pass verification and be dispatched against the victim tenant's stack.

### Finding Description
- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and checks the HMAC against that organization's `webhook_secret`. [6](#0-5) 
- `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — fully attacker-controlled content of the same signed body. [3](#0-2) 
- Handlers resolve the target `Stack`/`Repository` via `payload.dig('repository', 'full_name')`, a separate field from the same body. [7](#0-6) 
- Nothing enforces `repository.owner.login` (used for the trust decision) to be the owner segment of `repository.full_name` (used for the actual write). Real GitHub webhooks always keep these consistent, but an attacker forges the JSON body directly and only needs a valid secret for *some* organization onboarded to the Shipit instance, not for the organization whose repository is actually affected.
- This is the exact "field trusted for the security decision" vs. "field used for the effect" split called out by the report's bug class: the equality that should hold — *organization that authenticated == repository that is written* — is never enforced.

### Impact Explanation
The `status` handler demonstrates a genuine write sink from fully attacker-controlled fields (`state`, `context`, `target_url`, `description`) tied to a commit resolved through the mismatched repository. [5](#0-4)  Because Shipit's deploy-gating logic relies on recorded commit statuses (including configured blocking/required statuses) to decide whether a commit is deployable, an attacker who controls only their own tenant's `webhook_secret` can inject a forged "success" status onto a commit belonging to a completely different organization's repository, without ever having write access, an `ApiClient` token, or a GitHub App private key for the victim org. This crosses the "cross-repository writes / unauthorized deploy" impact bar.

### Likelihood Explanation
Requires the attacker to control at least one organization already configured in the multi-tenant `secrets.github` map (i.e., know/control that organization's own `webhook_secret`, which is normal for a legitimate but untrusted-for-others tenant in a shared Shipit deployment). No access to the victim organization, no Shipit session, and no GitHub App credentials for the victim are needed — only crafting an HTTP POST to `/webhooks` with a self-consistent signature but a spoofed `repository.full_name`.

### Recommendation
After `verify_signature` succeeds, assert that the repository referenced by the payload's `full_name` (or any repository resolved by handlers) belongs to the same organization that was used to select the verifying secret (`repository_owner`). Reject the webhook (422) if `repository.full_name.split('/').first != repository_owner.downcase`. Apply the same cross-check inside `Webhooks::Handlers::Handler` before resolving `stacks`, rather than trusting `full_name` unconditionally.

### Proof of Concept
1. Assume Shipit is configured multi-tenant with organizations `org-a` (victim) and `org-b` (attacker's own onboarded org, e.g. a legitimate customer in a shared instance), each with distinct `webhook_secret`s in `secrets.github`.
2. Attacker crafts a `status` event body:
```json
{
  "sha": "<real sha of a commit in org-a/victim-repo tracked by Shipit>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://attacker.example",
  "repository": { "owner": { "login": "org-b" }, "full_name": "org-a/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-b_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner == "org-b"`, fetches `org-b`'s `webhook_secret`, and the signature matches — verification passes. [6](#0-5) 
5. The status handler resolves `stacks` via `repository.full_name == "org-a/victim-repo"` and writes a forged "success" `Status` on `org-a`'s commit, potentially satisfying a blocking-status deploy gate for a repository the attacker has no access to.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
