### Title
Webhook signature is verified against `repository.owner.login` while the acted-upon repository is taken from `repository.full_name`, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate an inbound webhook's HMAC signature against by reading `repository.owner.login` (or `organization.login`) out of the **unauthenticated JSON body itself**. Every event handler that then acts on the payload (`PushHandler`, `StatusHandler`, `PullRequest::ClosedHandler`, etc.) resolves the target `Repository`/`Stack` using a **different field of the same body**, `repository.full_name`. Because GitHub's HMAC only proves the payload was signed with *some* configured organization's secret, not that the "owner" field and the "full_name" field agree, an attacker who controls (or is invited to) any organization/app installation configured in the same multi-tenant Shipit instance can forge a signature-valid webhook that is attributed to their own org but whose `repository.full_name` points at a completely different, victim organization's repository/stack.

### Finding Description
The binding that should hold is:
`organization authenticated by the webhook signature == organization owning the repository whose Stack is mutated`

In `verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up the `GitHubApp` (and its `webhook_secret`) keyed purely by this attacker-supplied string, with case-insensitive/indifferent matching across all configured organizations [2](#0-1) . The signature check therefore proves only "this payload was HMAC-signed with Organization X's secret" — it does not constrain any other field of the JSON body, because the signature covers the raw bytes but the controller only checks that *a* valid organization's secret matches, and lets the attacker pick which organization's field (`repository.owner.login`) is used to select that secret.

Every downstream handler, however, ignores `repository.owner.login` and instead resolves the target repository via `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` uses this to trigger `stack.sync_github` for every branch-matching stack under that repo [4](#0-3) , and `PullRequest::ClosedHandler` independently re-derives the repository from `params.repository.full_name` to archive review stacks [5](#0-4) . `StatusHandler` looks up commits purely by `sha` with no repository/org scoping at all [6](#0-5) .

Test fixtures confirm this is a genuinely multi-tenant setup where distinct organizations (`shopify`, `cyclimse`, and arbitrary `Repo`/`Organization` hooks) can coexist in one Shipit instance, each with its own secret [7](#0-6) .

**Before the attack:** signature verification is meant to guarantee that only GitHub, on behalf of organization X, can cause mutations to stacks belonging to organization X's repositories.

**After the attack:** an attacker who is a legitimate member/admin of Organization A (with their own GitHub App installation and webhook secret configured on the same Shipit instance as victim Organization B) can send an HTTP POST to `/webhooks` with:
- `X-Github-Event: push` (or `status`, or `pull_request`)
- `X-Hub-Signature` computed with Organization A's `webhook_secret` over the raw body
- Body JSON containing `"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}`

`verify_signature` passes because it validates against OrgA's secret, but the handler resolves and mutates Stacks belonging to `OrgB/victim-repo` — an organization the attacker never authenticated as.

### Impact Explanation
This crosses the "organization authenticated versus repository written" trust boundary explicitly called out as in-scope. Concretely, an attacker with a foothold in one tenant organization can, for a victim organization's stack that is also hosted on the same Shipit instance:
- Force arbitrary `git fetch`/sync cycles via forged `push` events (`stack.sync_github`), influencing which commits/refs Shipit believes are the tip of a branch.
- Inject forged commit statuses (`StatusHandler#process`) with arbitrary `state`/`context`/`target_url` for any commit sha known to the attacker, which can satisfy CI/blocking-status gates used by the merge queue to decide whether a commit is deployable/mergeable.
- Archive or otherwise manipulate victim review stacks via forged `pull_request` `closed` events.

Forged commit statuses that satisfy blocking status checks can allow an attacker to make the merge queue treat unreviewed/unsafe commits as deployable, which can lead to an unauthorized deploy — one of the accepted critical impacts.

### Likelihood Explanation
Requires the attacker to control a legitimate GitHub App installation/organization that is configured in the same multi-tenant Shipit instance as the victim (i.e., being a member of any onboarded organization, not requiring any Shipit session, API token, or the victim's own webhook secret). No specific Shipit privilege is required beyond having a repo/org already registered with the shared Shipit deployment — a realistic scenario for shared/self-hosted internal Shipit installations serving multiple orgs or repos.

### Recommendation
Bind the signature-verification identity to the same field used for repository resolution:
- Verify the signature using the organization derived from `repository.full_name` (or verify against all configured secrets and require the resolved organization to match the actual owning org of the resolved `Repository`).
- Alternatively, after resolving the target `Stack`/`Repository` in each handler, assert that its owning organization equals the organization whose secret validated the signature, rejecting the event otherwise.

### Proof of Concept
1. Attacker is an authorized member of Organization A, which has its own GitHub App/webhook secret configured on the shared Shipit instance (`config/secrets.yml` `github` block, keyed by org) [8](#0-7) .
2. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature [9](#0-8) .
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on OrgB's stack [4](#0-3) , even though the signature only proved authenticity for OrgA.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
