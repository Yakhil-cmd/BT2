This confirms the multi-org GitHub App architecture: `Shipit.github(organization:)` selects a per-organization config keyed by name in `secrets.github`, each with its own independently-optional `webhook_secret` [1](#0-0) , and `GitHubApp#verify_webhook_signature` unconditionally returns `true` whenever that org's `webhook_secret` is blank [2](#0-1) .

The vulnerability is real and maps cleanly onto the reported bug class.

### Title
Webhook signature verification is bound to an attacker-chosen `repository.owner.login` while handlers act on a different, unverified `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to verify the request signature against using `repository_owner`, a value read directly out of the *unauthenticated* request body, before any signature has been validated. The handler that subsequently acts on the payload identifies the target `Repository`/`Stack` using a different, equally unauthenticated field: `repository.full_name`. Because these two fields are never checked for consistency, and because `verify_webhook_signature` treats a blank `webhook_secret` as automatically valid, an attacker can select an organization with no configured (or a known) webhook secret to satisfy signature verification, while pointing `repository.full_name` at a stack belonging to a completely different, protected organization.

### Finding Description
`verify_signature` computes the verifying `GitHubApp` like this: [3](#0-2) 

`repository_owner` is read straight out of the JSON body, prior to any signature check: [4](#0-3) 

`Shipit.github(organization:)` looks up a per-organization config block, each of which independently supplies its own `webhook_secret` (this multi-app schema is explicitly supported/documented, and a `webhook_secret` is explicitly optional per organization): [1](#0-0) [5](#0-4) 

`verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank: [2](#0-1) 

Meanwhile, every webhook handler resolves the actual target `Repository`/`Stack` using an entirely separate field, `repository.full_name`, also taken unverified from the same JSON body: [6](#0-5) [7](#0-6) 

The broken binding is: **organization that authenticated the signature (`repository.owner.login` / `organization.login`) == repository that is actually written to (`repository.full_name`)**. Nothing in `WebhooksController` or `Handler` enforces that these two attacker-supplied strings refer to the same GitHub organization. An attacker who knows (or controls) a configured Shipit organization whose `webhook_secret` is blank can craft a payload with `repository.owner.login` = that unprotected org (satisfying `verify_signature`) and `repository.full_name` = `"<protected-org>/<target-repo>"` (driving `PushHandler`, `StatusHandler`, `MembershipHandler`, `CheckSuiteHandler`, or the `PullRequest` handlers to operate on the protected org's stack). This is the exact analog of the MerkleDB flaw: the verifier reconstructs and checks only a partial/adjacent structure (the organization-to-secret mapping) instead of the actual object being acted upon (the repository), so a value that was never covered by the cryptographic check ends up controlling the write.

### Impact Explanation
This allows an unauthenticated attacker to forge `push`, `status`, `check_suite`, `membership`, or `pull_request` webhook events for a *protected* stack without ever knowing that stack's true webhook secret, as long as any other organization configured in the same Shipit instance has no (or a leaked) secret. Depending on which handler fires, this can trigger an unauthorized deploy-sync (`PushHandler` → `stack.sync_github`, queuing `GithubSyncJob`), fabricate CI/commit statuses (`StatusHandler`), or manipulate PR-driven review-stack provisioning/archival (`OpenedHandler`, `LabeledHandler`, etc.) — i.e., an unauthorized deploy/rollback-adjacent action on a repository the attacker does not control, satisfying the "unauthorized deploy" bar.

### Likelihood Explanation
Exploitability requires only that the target Shipit instance runs the documented multi-organization GitHub App configuration (`app_id`/`installation_id`/`webhook_secret` per org, as shown in `test/dummy/config/secrets_double_github_app.yml` and described in `TOP_LEVEL_GH_KEYS` handling in `lib/shipit.rb`) and that at least one configured organization has `webhook_secret` unset — which the setup documentation explicitly calls "optional." No credentials, session, or API token are required; the attacker only needs to know the name of one lightly-configured organization and the full repository name of the target stack, both of which are typically public information.

### Recommendation
In `WebhooksController#verify_signature`, verify that the organization used to select the signing secret is the same organization referenced by every field the handlers will use to locate the target repository (`repository.full_name`, `organization.login`, etc.) before dispatching to handlers — e.g., reject the request if `repository.full_name.split('/').first.casecmp(repository_owner) != 0`. Additionally, consider disallowing a blank `webhook_secret` from silently passing verification, or require secrets to be configured for every organization in a multi-app deployment.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgUnsecured` (no `webhook_secret`) and `OrgProtected` (with a `webhook_secret` and a real stack for `OrgProtected/target-repo`).
2. Send a `POST /webhooks` request with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgUnsecured" },
    "full_name": "OrgProtected/target-repo"
  }
}
```
No `X-Hub-Signature` header (or an arbitrary one) is required.
3. `verify_signature` resolves `Shipit.github(organization: "OrgUnsecured")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [2](#0-1) .
4. `PushHandler` resolves `Repository.from_github_repo_name("OrgProtected/target-repo")` via `repository_name` [6](#0-5)  and queues `stack.sync_github(expected_head_sha: params.after)` for the protected organization's stack — despite the request never being signed by `OrgProtected`'s secret.

    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end
