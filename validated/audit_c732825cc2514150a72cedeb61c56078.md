### Title
Webhook signature is verified against the organization derived from the payload while the affected Stack/repository is selected from a different, unverified payload field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/secret to validate a webhook delivery against solely from attacker-controlled JSON in the request body: [1](#0-0) [2](#0-1) [3](#0-2) 

`repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) is used to resolve `Shipit.github(organization: repository_owner)`, which loads that organization's own `GitHubApp` instance and its own `webhook_secret`, and the HMAC in `X-Hub-Signature` is checked against that secret: [4](#0-3) 

Once the signature is accepted, the actual handlers never re-use `repository_owner` to decide what gets mutated. Instead, every handler independently resolves its target repository/stack from a completely separate field, `repository.full_name`: [5](#0-4) 

`PushHandler` (and other handlers) then act on whichever `Stack`s match that `full_name`: [6](#0-5) 

`StatusHandler` matches purely on `sha`, with no owner/org check at all, and directly creates a `Status` on any commit sharing that sha across the whole instance: [7](#0-6) 

Because Shipit supports hosting multiple, independent GitHub organizations from a single instance (`Shipit.github(organization:)`, `github_app_config`), each with its own `webhook_secret`: [8](#0-7) 

the equality that should hold is:
`organization whose secret authenticated the request == organization owning the repository/stack that gets written`

This equality is never enforced. An entity that legitimately controls the GitHub App/webhook secret for organization "A" (e.g. an org admin who set up their own GitHub App integration on this shared Shipit instance, per `docs/setup.md`) can sign an arbitrary payload with `repository.owner.login`/`organization.login` = "A" (so `verify_signature` passes using A's own secret) while setting `repository.full_name` (or `sha`, for status events) to reference organization "B"'s repository/stack — an org they have no access to. The forged event is accepted and dispatched to handlers that write to B's data:
- a forged `push` event queues `stack.sync_github` for B's stack,
- a forged `status` event with `state: success` creates a `Status` on B's commit, which can flip `deployable?`/trigger continuous deployment on B's stack: [7](#0-6) 

Additionally, this endpoint requires no Shipit session, no `ApiClient` token, and no GitHub App private key — only possession of one (any) configured organization's own `webhook_secret`, which by the engine's own documentation is treated as an independently-managed, optional per-org secret: [9](#0-8) 

### Impact Explanation
This breaks the trust boundary between tenants on a multi-organization Shipit deployment: an actor authenticated only as organization A can cause writes (sync jobs, CI statuses) against organization B's stacks that they have no GitHub authorization over, and can leverage the `status` handler to move a victim stack toward an unauthorized deploy via `continuous_deployment`. This matches the "cross-repository writes" / "unauthorized deploy" impact tier, since the check that authenticates the request (per-org HMAC) is never bound to the resource the code subsequently mutates (per `full_name`/`sha` from the same unchecked payload).

### Likelihood Explanation
Exploitability requires only legitimate control of any one organization's own webhook secret configured on the shared instance (a routine, unprivileged-relative-to-other-tenants capability for a multi-org Shipit deployment as documented), no interaction with victim credentials, sessions, or GitHub App keys, and a single crafted HTTP POST to the public `/webhooks` endpoint.

### Recommendation
In `WebhooksController#verify_signature`/`create` (and in `Handler#stacks`/`repository_name`), after successfully verifying the signature for organization `repository_owner`, re-derive the target repository strictly from that same verified organization, and reject/ignore any handler resolution (`full_name`, commit `sha` lookups) whose owning organization does not match the organization that authenticated the request.

### Proof of Concept
1. Configure Shipit with two organizations, "org-a" and "org-b", each with its own `webhook_secret` (`docs/setup.md` "Using Multiple Github Applications").
2. As the legitimate owner of org-a's GitHub App, compute a valid `X-Hub-Signature` (`sha1=HMAC-SHA1(org-a-webhook_secret, body)`) for this payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. POST it to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = "org-a", loads org-a's `webhook_secret`, and the signature validates (`lib/shipit/github_app.rb#verify_webhook_signature`).
5. `PushHandler#process` resolves stacks via `repository.full_name` = "org-b/victim-repo" (`Handler#repository_name`) and queues `sync_github` on org-b's stack — an organization the requester never authenticated against.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
