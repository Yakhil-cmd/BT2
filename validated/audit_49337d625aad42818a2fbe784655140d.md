### Title
Webhook signature is verified against the organization identity while target repository is resolved from an unverified field, allowing cross-organization stack takeover - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks which GitHub App (and thus which `webhook_secret`) to validate a webhook against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Every webhook `Handler`, however, resolves the actual `Stack`/`Repository` to act on using a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`. Both fields are attacker-controlled content inside the same HTTP body; only the raw body as a whole is HMAC-signed, so nothing binds "the organization whose secret validated the signature" to "the repository the handler will mutate."

### Finding Description
`verify_signature` selects the verifying `GithubApp` instance by organization: [1](#0-0) [2](#0-1) 

`Shipit::GithubApp#verify_webhook_signature` only checks the HMAC using that organization's own configured `webhook_secret`; it never checks that the payload's `repository.full_name` belongs to that organization: [3](#0-2) [4](#0-3) 

Every handler, on the other hand, resolves the target `Stack` from `repository.full_name`, a sibling field with no relation to `repository.owner.login`: [5](#0-4) 

This is the exact binding break called out in the rules: "an organization that authenticated versus the repository that is written." In Shipit's documented multi-organization configuration, each organization owns an independent GitHub App with its own independent `webhook_secret`: [6](#0-5) 

An attacker who legitimately controls (or has installed) their own GitHub App for organization `attacker-org` inside a shared multi-tenant Shipit instance knows `attacker-org`'s own `webhook_secret`. They can therefore sign an arbitrary HTTP body with that secret and set `repository.owner.login` (or `organization.login`) to `attacker-org` — so `verify_signature` succeeds — while setting `repository.full_name` to `victim-org/some-repo`, a repository/stack that belongs to a completely different, unrelated tenant.

`PushHandler` is the most severe consequence of this: it resolves stacks purely from `repository.full_name` and drives them from attacker-supplied `ref`/`after` fields: [7](#0-6) 

`stack.sync_github(expected_head_sha:)` is the same mechanism that feeds continuous delivery/auto-deploy logic (`Stack#trigger_continuous_delivery`, `next_commit_to_deploy`): [8](#0-7) 

`CheckSuiteHandler` and the `PullRequest::*` handlers exhibit the same pattern — they all key off `repository.full_name` / `Repository.from_github_repo_name`, decoupled from the verified `repository_owner`: [9](#0-8) [10](#0-9) 

### Impact Explanation
In a multi-organization Shipit deployment, a tenant that legitimately controls only their own GitHub App/organization can forge webhooks that are authenticated as "their own org" but are processed against a victim organization's `Stack`. Via `PushHandler`, this can force `sync_github`/continuous-delivery evaluation on a victim stack using attacker-chosen `ref`/`after` values, and via `CheckSuiteHandler`/`PullRequest` handlers it can flip check-run refresh, review-stack archival, or merge-queue state on repositories the attacker does not own. This maps to the "unauthorized deploy, rollback, or merge" / cross-repository-writes impact tier, since a webhook boundary meant to isolate organizations from each other is not actually enforced.

### Likelihood Explanation
Exploitability strictly requires a multi-organization Shipit configuration (`config/secrets.yml` with multiple top-level `github` org keys, as documented) where at least two mutually distrusting organizations' Apps are registered on the same Shipit instance. Given that configuration, exploitation needs no privileged Shipit account, `ApiClient` token, or repository write access — only knowledge of one's own org's `webhook_secret`, which any org that installs its own App into the shared instance inherently possesses. This is squarely an "organization authenticated vs. repository written" binding break as called out in scope.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`/`stacks`), cross-check that `repository_owner` (the organization whose secret validated the signature) matches the owner segment of `repository.full_name` before dispatching to handlers. Reject (422) any webhook where these two fields disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App/`webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. As the owner/admin of `attacker-org`'s own GitHub App, compute `sha1=HMAC(attacker_webhook_secret, body)` for a crafted push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha, e.g. an old/reverted victim commit>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `POST /webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `attacker-org`'s `GithubApp`, and the signature validates successfully (signed with the attacker's own known secret).
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack, despite the request never being validated against `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
