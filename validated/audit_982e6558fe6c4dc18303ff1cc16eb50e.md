### Title
`try!` on sBTC `transfer` result trusts a boolean it never checks - pox-5 can credit sats that were never received (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
The ERC20 "no-revert-on-transfer" bug class is about a caller treating a token-transfer call as successful without verifying that value actually moved. In pox-5, every inbound/outbound sBTC movement is done via `(try! (contract-call? sbtc-token transfer ...))`. `try!` in Clarity only short-circuits on `(err ...)`; if the response is `(ok false)` it simply unwraps to `false` and execution continues normally, exactly like Solidity code that doesn't check an ERC20 `transfer()`'s boolean return value.

### Finding Description
`roll-sbtc`, the function that custodies a staker's sBTC into pox-5 (used by `register-for-bond`, `update-bond-registration`, and bond-to-bond/bond-to-stake roll-overs), pulls funds with: [1](#0-0) 
and refunds with: [2](#0-1) 
Neither branch checks the *value* returned inside the `ok` — it only checks that the call didn't `err`. The same pattern recurs in `unstake-sbtc`'s payout: [3](#0-2) 
and in `transfer-from-reserve` / `transfer-stranded-rewards` and the signer-manager's fee sweep/reward-claim, which follow the identical `try!`-on-`transfer` idiom: [4](#0-3) [5](#0-4) 

In `roll-sbtc`'s deposit path, `total-sbtc-staked` (and the caller's bond/stake accounting via `register-for-bond`) is incremented by `delta` *based purely on the `try!` succeeding*, not on any confirmation that `delta` sats actually left `tx-sender` and landed in `current-contract`. If the configured `sbtc-token` contract ever returns `(ok false)` on a failed transfer (a valid SIP-010 response shape, mirroring the ERC20 tokens like ZRX that return `false` instead of reverting), pox-5 would credit the staker's sats-staked/reward-share bookkeeping and increase `total-sbtc-staked` while zero sats moved into the contract — breaking the equality "locked sBTC in the contract == sum of stakers' credited sats."

### Impact Explanation
This would be unbacked minting of stacking credit: a staker's on-chain sats-staked balance and `total-sbtc-staked` accounting increase without any real sBTC custody increase, letting that staker earn a share of real sBTC rewards paid out to signers/stakers from `roll-sbtc`'s siblings (`unstake-sbtc`, `transfer-from-reserve`, `transfer-stranded-rewards`), which do use a validated balance check elsewhere. That is a "reward paid that was not earned" / "sats credited by proof/registration that were never locked" scenario, i.e. Critical-severity theft/unbacked minting of sBTC rewards, if the deployed sbtc-token can produce this response shape.

### Likelihood Explanation
This is a **conditional/analog** finding: it depends entirely on the sBTC token implementation actually being able to return `(ok false)` for a failed transfer instead of an `err`. The token contract itself is explicitly out of scope per the rules ("the external sbtc-token except where pox-5's own use of it is the flaw"), and I could not locate the real mainnet sbtc-token's `transfer` implementation in this index to confirm whether it ever legitimately returns `(ok false)` — only a test stub was found, which always errs via `ft-transfer?` on insufficient balance: [6](#0-5) 
If the real sbtc-token strictly follows SIP-010 semantics (only ever `(ok true)` on success, `err` on any failure, as Clarity's built-in `ft-transfer?` behaves), this path is unreachable and the flaw is purely defensive/theoretical, not exploitable. This uncertainty means the finding cannot be confirmed as concretely reachable from the code available in this index alone.

### Recommendation
Regardless of the current token's behavior, pox-5 (and the reference signer-manager) should not rely on `try!` alone for asset transfers whose boolean payload matters. Wrap sBTC `transfer` calls with an explicit `(asserts! (is-eq result true) ERR_...)` (or `(unwrap! ...)` requiring literal `true`) before mutating `total-sbtc-staked` / bond membership state, so that any `(ok false)` response aborts the transaction instead of being silently treated as a successful custody event.

### Proof of Concept
Could not be constructed against real on-chain state in this index: the mainnet/testnet sBTC token source that would show whether `transfer` can return `(ok false)` was not found in the indexed files (only the always-`ft-transfer?`-erroring test stub was located). A full PoC would require deploying/mocking an sbtc-token whose `transfer` returns `(ok false)` on failure, then calling `register-for-bond`/`update-bond-registration` to trigger `roll-sbtc`'s deposit branch and observing `total-sbtc-staked` increase with no actual balance change on the token contract — analogous to the Cally `testStealFunds` PoC in the source report. This should be verified with a Devin session that has access to the full sBTC token contract source and can run the Clarinet/vitest suite in `contrib/core-contract-tests`.
