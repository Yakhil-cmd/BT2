### Title
AA definitions fetched by a light client from its vendor are registered into `aa_addresses` without full AA-definition validation - (File: aa_addresses.js)

### Summary
The CVE analog is the tc358743 class of bug: a component is registered (made globally visible/usable) *before* its setup/validation has actually succeeded. In `ocore`, `readAADefinitions()` in `aa_addresses.js` does exactly this for autonomous agents on light clients: when an address is unknown locally, the wallet fetches its definition from the light vendor and, if the returned array's c-hash matches the requested address, immediately calls `storage.insertAADefinitions()` to register it as a live AA — without ever running it through `aa_validation.validateAADefinition()`, the function that normally gatekeeps whether a definition is actually a well-formed, executable AA (checked during normal unit validation in `validation.js`'s `validateInlinePayload` "definition" case).

### Finding Description
For light clients, `readAADefinitions` resolves unknown addresses referenced as payment outputs (used by `checkAAOutputs` to determine bounce-fee requirements) by querying the vendor via `light/get_definition`: [1](#0-0) 

The only check performed on the vendor's response is that `objectHash.getChash160(arrDefinition) === address`, i.e. that the JSON hashes to the requested address. If `arrDefinition[0] === 'autonomous agent'`, the code proceeds straight to `storage.insertAADefinitions(db, [{ address, definition: arrDefinition }], constants.GENESIS_UNIT, 0, 0, false, insert_cb)` — inserting the row into `aa_addresses` — with **no call to `aa_validation.validateAADefinition`** (the function that checks structural correctness, complexity limits, getters, `base_aa` validity, bounce fees, etc.).

Compare this to the authoritative path used when an AA is actually defined on-chain in `validation.js`, where a `definition` message is only accepted after `aa_validation.validateAADefinition(payload.definition, readGetterProps, objValidationState.last_ball_mci, ...)` succeeds: [2](#0-1) 

Because chash-matching only proves internal consistency of the JSON blob (an attacker/vendor can construct arbitrary "autonomous agent" JSON whose hash is self-consistent — the address itself is derived from the same JSON), it does **not** prove the definition is a valid, executable AA. The vendor is the one supplying this address→definition mapping in the first place, so an attacker/vendor can trivially craft a JSON structure that hashes to whatever `address` was requested and is tagged `'autonomous agent'`, yet contains malformed `messages`/`init` code, an invalid `base_aa` reference, missing `bounce_fees` structure, or values that would be rejected by `validateAADefinition`'s complexity/getter checks.

Once inserted, this row lives in `aa_addresses` and is used elsewhere as if it were a fully vetted AA — e.g. `checkAAOutputs` reads `bounce_fees` straight out of `arrDefinition[1].bounce_fees` from this unvalidated row: [3](#0-2) 

This mirrors the tc358743 pattern precisely: the "device" (AA definition) is registered/exposed to the rest of the system for use before the equivalent of a successful "probe"/setup (`validateAADefinition`) has occurred.

### Impact Explanation
A light wallet that composes a payment to an address it believes to be an AA (via this cache) can be misled about bounce-fee requirements, or otherwise have downstream code operate on a definition object that does not conform to the invariants normally guaranteed by `aa_validation.validateAADefinition` (e.g., structurally invalid `bounce_fees`, undefined `base_aa`, or fields that later code paths assume are validated). Because this row is written directly into `aa_addresses` (the same table used by AA execution logic and `getAADefinition`/`readAADefinitions` consumers across the codebase), any other light-client logic that trusts a cache hit here inherits the same unvalidated data, increasing the risk of built-in assumptions being violated (e.g., division by absent fields, incorrect bounce-fee guidance leading a user to under/overpay, or crashes/inconsistent state in dry-run/complexity code paths that assume validated defs).

### Likelihood Explanation
This path is reachable in the ordinary flow of any light wallet composing a payment to an address that is not yet cached locally: it is triggered automatically whenever `checkAAOutputs`/`readAADefinitions` resolves an unknown output address, which is a routine operation for light clients (`conf.bLight` branch), not an edge case. The main external dependency is the response of the wallet's configured light vendor, which is trusted infrastructure but not cryptographically bound to producing *valid* AA definitions — only self-consistent ones.

### Recommendation
Before calling `storage.insertAADefinitions` in `aa_addresses.js`, run the fetched definition through `aa_validation.validateAADefinition` (or equivalent full validation used in `validation.js`'s `definition` message handling), and reject/ignore (treat as "not found") responses that fail validation, mirroring the on-chain path's ordering: validate first, register (make visible) only after successful validation.

### Proof of Concept
1. Run a light wallet (`conf.bLight = true`) connected to an attacker-controlled or compromised light vendor.
2. Wallet composes a payment whose output address `ADDR` is unknown locally; `checkAAOutputs` → `readAADefinitions(['ADDR'], ...)` is invoked.
3. Malicious vendor responds to `light/get_definition` with a crafted JSON array `['autonomous agent', { ... malformed/incomplete fields that would fail aa_validation.validateAADefinition, e.g. invalid base_aa, malformed bounce_fees, or nonsense messages/init code ... }]` such that `objectHash.getChash160(arrDefinition) === 'ADDR'` (trivial since `ADDR` is defined as this hash).
4. `aa_addresses.js:100-104` accepts it purely on the hash-match check and calls `storage.insertAADefinitions(...)`, writing the unvalidated definition into `aa_addresses` — bypassing `aa_validation.validateAADefinition` entirely.
5. Subsequent calls to `checkAAOutputs`/other consumers of this cached row operate on attacker-controlled, unvalidated AA-definition JSON.

Note: This finding centers on light-client trust in vendor-supplied AA definitions; I was not able to fully trace every downstream consumer of the `aa_addresses` cache to enumerate all resulting impacts within the available context, so some secondary consequences (beyond bounce-fee miscalculation) are inferred from code structure rather than directly observed.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
}
