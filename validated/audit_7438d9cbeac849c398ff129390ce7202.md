**Analysis:**

The `aggregate_signatures` function in `bls12381.move` simply calls the native `aggregate_signatures_internal` and wraps the resulting bytes into an `AggrOrMultiSignature` struct — it performs no binding to any particular expected set of signers. [1](#0-0) 

The security property that prevents the described attack lives in `verify_multisignature`, which checks the BLS pairing equation against the caller-supplied `aggr_public_key`. [2](#0-1)  If an attacker aggregates only a strict subset of signature shares (dropping or reordering shares does not matter for BLS since aggregation is a commutative group operation), the resulting aggregate signature corresponds to a smaller effective aggregate public key than the full quorum's `aggregate_pubkeys` output. Per the BLS pairing equation, `e(aggSig, g2) == e(H(m), apk)` will not hold when `apk` includes public keys whose corresponding signature shares are missing from `aggSig`, so `verify_multisignature_internal` cryptographically fails in that case. This exact property is already exercised in the existing test suite, which aggregates increasing partial subsets of signers against the corresponding partial aggregate public key (not the full one) precisely because a mismatch would not verify. [3](#0-2) 

Additionally, this `aptos_std::bls12381` module is a general-purpose Move stdlib cryptography library exposed to Move contracts; it is not part of Aptos's core transaction authenticator/admission path (mempool, vm-validator, or VM signature checks), which uses Ed25519/MultiEd25519/WebAuthn authenticators rather than this BLS module for account-level transaction signing. [4](#0-3)  No unprivileged transaction-admission entrypoint routes through `aggregate_signatures`/`verify_multisignature` in a way that could bind the "wrong" approval set at the sender/authenticator level, so the boundary conditions for this review (transaction admission) are not met even if such a Move contract existed on top of this module.
