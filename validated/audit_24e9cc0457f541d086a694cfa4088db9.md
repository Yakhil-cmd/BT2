### Title
Cross-tenant Status write via unscoped SHA lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the webhook's verified `repository.owner.login`/`full_name` matches the repository that owns the `Commit`/`Stack` being written to. A repository owner who can get GitHub to emit a signed `status` event for a commit whose sha collides with a commit already tracked under a different tenant's stack can write a `Status` row against that other tenant's `Commit`, which flows straight into `Commit#schedule_continuous_delivery` and can trigger an unattended deploy of that tenant's stack.

### Finding Description
The broken binding: the question claims `verified_repository_owner (from params.dig('repository','owner','login'), authenticated only against Shipit.github(organization: attacker).webhook_secret)` should equal `commit.stack.repository_owner` (the tenant actually authorized to mutate that commit's status/stack), but the code never enforces this equality.

Path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves the payload was signed with the webhook secret configured for `repository_owner` (the org named in the *attacker's own payload*, e.g. `attacker`). It never checks that the `sha` in the payload actually belongs to a commit under that org's repositories. [1](#0-0) 
- `StatusHandler#process` then does a global, unscoped lookup:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` across **all stacks/repositories** by `sha` alone — there is no `.where(stack: stack_owned_by(repository_owner))` filter. [2](#0-1) 
- `Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` writes a `Status` row using the **victim commit's own `stack_id`** (from `commit.stack_id`, not anything derived from the attacker's payload), so the new `Status` is legitimately attached to the victim's `Stack`. [3](#0-2) [4](#0-3) 
- `Status` has `after_commit :schedule_continuous_delivery, ... on: :create` which calls `commit.schedule_continuous_delivery`. [5](#0-4) 
- `Commit#schedule_continuous_delivery` checks `deployable? && stack.continuous_deployment? && stack.deployable?` and, if true, enqueues `ContinuousDeliveryJob` for the **victim's stack**. [6](#0-5) 
- `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` — a forged `state: success` status is enough to satisfy this if the commit isn't locked/blocked. [7](#0-6) 

Why existing guards fail: `verify_signature` authenticates *who sent the payload* (an org that legitimately controls the named `repository_owner`) but not *whose data the payload may mutate*. Since `Commit.where(sha:)` is a global table scan with no `stack_id`/repository filter, any correctly-signed status payload from any onboarded organization can target a `Commit` row belonging to a completely different tenant, as long as the `sha` strings match. The `ExplicitParameters` schema for `StatusHandler` only validates types/presence of `sha`, `state`, etc.; it does not perform any repository-ownership check. [8](#0-7) 

The existing test suite for this handler only exercises the case where sha matches a commit under the correct stack (`fixtures.first`), never asserting that a cross-repository sha cannot mutate a different stack's commit — confirming this scoping is untested and unenforced. [9](#0-8) 

### Impact Explanation
This is a payload for one repository (`attacker/evil`) mutating another repository's `Commit`/`Stack` state and potentially triggering an unauthorized deploy — matching the Critical category. The attacker gets a `Status` row (state e.g. `success`) written under the victim's `Stack`, and if the victim stack has `continuous_deployment` enabled and the affected commit is otherwise deployable (not locked/blocked), a `ContinuousDeliveryJob` is queued that deploys the victim commit without any legitimate CI signal from the victim's actual CI provider. This is repeatable against any commit sha the attacker can reproduce in their own repository, and generalizes across all tenants sharing the same Shipit installation/database.

### Likelihood Explanation
Feasibility hinges entirely on the attacker's ability to produce a `Commit` in their own repo whose sha matches a target victim commit's sha. Git commit SHA-1 is computed over author/committer name+email+date, tree hash, parent(s), and message; producing an actual collision against an *arbitrary* existing victim commit generally requires either: (a) the victim commit is a well-known deterministic object (e.g., the canonical empty-tree root commit, or a common boilerplate/license commit that many repos share byte-for-byte), or (b) a real SHA-1 collision attack (expensive but demonstrated feasible, e.g. SHAttered-class techniques). Case (a) is realistic and requires no cryptographic attack at all — many organizations' repos legitimately contain byte-identical commits (fresh `git init` empty commits, generated boilerplate from the same scaffolding tool with fixed timestamps). No Shipit secrets are needed beyond the attacker owning a repo with the Shipit GitHub App installed on their own org, which is a normal, unprivileged setup step.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogous handlers) by the verified repository, not sha alone — e.g. resolve the `Stack`/`Repository` from the verified `repository.full_name` in the payload first, then query `stack.commits.where(sha: params.sha)` (or join through `Repository` to constrain by `full_name`) before calling `create_status_from_github!`. Reject or ignore statuses whose payload repository does not match any commit's owning repository.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":status from an unrelated repository can write a Status onto another tenant's commit" do
  victim_commit = shipit_commits(:cyclimse_first) # belongs to stack `cyclimse`, different repo than `shipit`
  request.headers['X-Github-Event'] = 'status'

  # Attacker's own repo ("shipit" fixture org, signed with its own legit webhook secret)
  # crafts a payload whose sha collides with victim_commit.sha but repository is attacker's own.
  body = {
    sha: victim_commit.sha,
    state: 'success',
    context: 'attacker-ci',
    repository: { full_name: 'attacker/evil', owner: { login: 'shopify' } } # signed org != victim's repo owner
  }.to_json

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body:, as: :json
  end

  # Assert the equality the code should have enforced but doesn't:
  # payload repository ('attacker/evil') != victim_commit.stack.repository ('cyclimse/...')
  refute_equal 'attacker/evil', victim_commit.stack.repo_name

  victim_commit.stack.update!(continuous_deployment: true)
  assert_enqueued_with(job: Shipit::ContinuousDeliveryJob, args: [victim_commit.stack]) do
    victim_commit.reload.schedule_continuous_delivery
  end
end
```
This demonstrates the write succeeds against `victim_commit` despite the signed payload's repository not owning it, and that continuous delivery is scheduled for a stack the attacker's webhook never legitimately authenticated against.
