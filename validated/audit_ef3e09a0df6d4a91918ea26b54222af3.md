The `CCMenuController#stack` method in `app/controllers/shipit/api/ccmenu_controller.rb` overrides `BaseController#stack` and calls `Stack.from_param!(params[:stack_id])` unscoped, bypassing the `current_api_client.stack_id` restriction that `BaseController#stacks`/`#stack` enforces for every other API endpoint.

### Title
Stack-scoped ApiClient token can read CCMenu build status of any stack, bypassing its stack binding - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` scopes stack lookups to the authenticated `ApiClient`'s assigned `stack_id` via `stacks`/`stack`, but `Shipit::Api::CCMenuController` overrides `stack` to bypass that scoping, allowing any valid `ApiClient` token (or CCMenu URL token) to read the build/deploy status of any stack, not just the one it was authorized for.

### Finding Description
`Shipit::Api::BaseController` establishes the trust binding "a stack a token authorises" == "a stack a token can touch": [1](#0-0) 

`current_api_client.stack_id?` restricts `stacks` (and therefore `stack`) to only the single stack an `ApiClient` was created with, when it has one. This is the mechanism the entire API namespace relies on to enforce per-stack authorization for scoped tokens (e.g. tokens minted by `CCMenuUrlController#client`, which creates an `ApiClient` scoped to one stack with `read:stack` permission): [2](#0-1) 

However, `Shipit::Api::CCMenuController` defines its own private `stack` method that calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, completely bypassing the `stacks` scoping defined in `BaseController`: [3](#0-2) 

The `require_permission :read, :stack` before_action only checks that the token has the `read:stack` permission string (`ApiClient#check_permissions!`), not that the specific stack being requested matches `current_api_client.stack_id`: [4](#0-3) 

So a token that is scoped/authorised for stack A but has the generic `read:stack` permission (which every stack-scoped token created via the UI/`CCMenuUrlController` has) can be replayed against `/api/stacks/<any-org>/<any-repo>/<any-env>/ccmenu` to read the deploy status of stack B — an equality that should hold (`token.stack_id == requested_stack.id`) is broken specifically in this controller.

### Impact Explanation
This satisfies the "High" impact bar: "unauthenticated read of stack state, task streams or deploy output" via improper authorization — a token scoped to one stack can read another stack's build state (last build status/label/time, running/sleeping activity) across the whole instance, without any additional credential. Any leaked/observed per-stack CCMenu token (these are embedded in plaintext query strings meant for CI-status-monitor tools, and are also partially/fully disclosed via `ApiClientsHelper#api_client_token` in the UI) becomes a master key for reading every other stack's build status, undermining the intended per-stack isolation of `ApiClient` tokens.

### Likelihood Explanation
Likelihood is high: exploitation requires only a single valid, low-privilege stack-scoped API token (already the intended low-trust credential for this endpoint) and knowledge/guessing of another stack's `owner/repo/environment` identifier, which are not secret (they appear in URLs, `stack.to_param`, GitHub repo names). No privileged account, GitHub App key, or webhook secret is needed.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reuse `BaseController#stacks.from_param!`) so that CCMenu lookups are scoped by `current_api_client.stack_id` exactly like every other API controller, restoring the `token.stack_id == requested_stack.id` binding.

### Proof of Concept
1. As a legitimate user, generate a CCMenu URL for Stack A via `CCMenuUrlController#fetch` (`GET /ccmenu/*stack_id`), obtaining a `token` scoped to Stack A with `read:stack` permission.
2. Send `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<token-for-stack-A>` for an unrelated Stack B.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (`ApiClient.authenticate(params[:token])`), `require_permission :read, :stack` passes because the token has `read:stack`, and `stack` resolves via unscoped `Stack.from_param!` to Stack B.
4. The response renders Stack B's `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `activity`, even though the token was only ever authorized for Stack A.
