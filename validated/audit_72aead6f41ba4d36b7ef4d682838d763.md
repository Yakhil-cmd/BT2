### Title
Cross-repository status webhook bypasses `ci.blocking` deploy gate via unscoped sha lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub status to purely `Commit.where(sha: params.sha)`, with no scoping to the repository that emitted the webhook, unlike `PushHandler` which correctly scopes through `stacks`/`repository_name`. Because `Commit#blocked?` and `Commit#deployable?` are computed from whatever `Status` rows exist for a commit regardless of which repository authored them, an attacker who controls a repository whose commit happens to share a `sha` with a commit in an unrelated, blocking-configured victim stack can flip that victim commit's blocking status to `success`, clearing the `ci.blocking` gate for a stack they have no relationship to.

### Finding Description
The binding the safety gate depends on is:
`(context, state) authorized for victim_stack.github_repo_name at sha == (context, state) supplied in the webhook payload for sha`

In `app/models/shipit/webhooks/handlers/status_handler.rb`: [1](#0-0) 
`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never consults `payload.dig('repository', 'full_name')` or the `stacks` helper that other handlers use (`Handler#stacks`, `Handler#repository_name`) to constrain the update to commits belonging to the repository that sent the webhook: [2](#0-1) 
Compare with `PushHandler#process`, which correctly restricts to `stacks.not_archived.where(branch:)` derived from the payload's own repository: [3](#0-2) 

`Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` persists a `Status` row scoped to that commit's own `stack_id` (taken from the found `Commit`, not from the payload), and recomputes derived state: [4](#0-3) [5](#0-4) 

`Commit#blocked?` walks `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)`, and `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`: [6](#0-5) 

`verify_signature` in `WebhooksController` only authenticates that the payload came from the GitHub org named in `payload['repository']['owner']['login']` (the attacker's own org) — it never checks that the `sha` in the body belongs to that org's repository: [7](#0-6) 

So a legitimately-signed webhook from the attacker's own GitHub org/repo (triggered by pushing a commit and setting a commit status on their own repo, both actions available to any unprivileged GitHub user on their own fork) is authenticated correctly for their own org, but its effect — via `StatusHandler`'s unscoped `Commit.where(sha:)` — is applied to every `Commit` row in the entire Shipit database that happens to share that `sha`, across every stack/org/tenant. Combined with the "cross-repo sha-collision" precondition already established for this payload family, an attacker who can produce a commit whose sha collides with a specific blocking commit in a victim's stack can post `state: success` with the exact `context` string the victim's `ci.blocking` config expects, flipping `blocking?` to false for that commit and thus `blocked?` to false for every later undeployed commit in the victim stack, clearing `Commit#deployable?` for it.

None of the listed guards intervene: `verify_signature` validates org-level HMAC only, not sha-to-repo ownership; the `ExplicitParameters` schema in `StatusHandler` only validates types/presence of `sha`, `state`, `context`, etc., not repository binding; there is no `require_permission!`/`stacks` scoping call in this handler at all.

### Impact Explanation
The attacker can write a `Status` record (and thereby flip `blocked?`/`deployable?`) for a commit belonging to a repository/stack they do not own or control, on an unrelated tenant's Shipit configuration. This is a cross-repository write: a payload authenticated for repository A mutates commit/status state that gates deploys for stack B. It directly clears a "blocking CI" safety gate (`ci.blocking`) that operators rely on to prevent deploys of not-yet-verified changes, enabling an unauthorized/unsafe deploy to proceed on the victim stack. This matches the Critical category: "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy."

### Likelihood Explanation
This finding is entirely gated on the previously-established "cross-repo sha-collision signed status" precondition (a genuine SHA collision or sha reuse across repositories, which the audit series treats as the attacker's starting capability for this class of finding) plus the victim stack having a non-empty `blocking_statuses` (`ci.blocking`) configuration whose expected context string is guessable/known to the attacker (commonly published, e.g. `ci/travis`, a CI vendor's context name). Given that precondition, the attacker cost is a single legitimate webhook delivery from their own repository/org — no Shipit credentials, no privileged role, and it is repeatable against any stack whose blocking context name is known and whose commit sha collides.

### Recommendation
In `StatusHandler#process` (and equivalently for check-run/other sha-keyed handlers), scope the commit lookup to the repository that sent the webhook, mirroring `PushHandler`: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` and restrict `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or iterate `stacks.flat_map(&:commits)` matching the sha) instead of a global `Commit.where(sha:)`. This restores the binding that a status payload can only mutate commits belonging to the repository authenticated by `verify_signature`.

### Proof of Concept
Minitest (`test/models/shipit/webhooks/handlers/status_handler_test.rb` style, but omitted per scope — described here as the plan a background engineer would implement under `test/`):
1. Create two stacks/repositories, `victim_stack` (`repository.full_name = "victim/repo"`) with `cached_deploy_spec` configuring `ci.blocking = ['ci/required']`, and `attacker_stack` (`repository.full_name = "attacker/repo"`).
2. Create `blocking_commit` under `victim_stack` with `sha: "deadbeef..."` and no successful `ci/required` status (so `blocking_commit.blocking?` is true and a later `commit` under `victim_stack` is `blocked?` / not `deployable?`).
3. Create a commit under `attacker_stack` with the **same** `sha: "deadbeef..."` (simulating the cross-repo sha collision precondition).
4. Assert baseline: `assert commit.blocked?` and `refute commit.deployable?` for the victim's later commit.
5. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call('sha' => 'deadbeef...', 'state' => 'success', 'context' => 'ci/required', 'repository' => { 'full_name' => 'attacker/repo' })` — i.e., a payload whose `repository` is the attacker's, not the victim's.
6. Assert both sides of the binding: `assert_equal 'success', blocking_commit.reload.status.state` even though the payload's repository (`attacker/repo`) does not equal `blocking_commit.stack.github_repo_name` (`victim/repo`), and `refute blocking_commit.blocking?`.
7. Assert the safety gate flip: `refute commit.reload.blocked?` and `assert commit.deployable?`, demonstrating the victim stack's `ci.blocking` gate was cleared by a payload authenticated only for the attacker's own repository.
