### Title
Webhook signature is verified against the organization named in `repository.owner.login`/`organization.login`, but event handlers act on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/secret to validate the HMAC signature against using a value read from the untrusted JSON body itself (`repository.owner.login`, falling back to `organization.login`), while the actual event handlers (`Handler#repository_name`, used by `PushHandler`, `CheckSuiteHandler`, `StatusHandler`, PR handlers, etc.) resolve the target `Stack`/`Repository` using a *different* field from the very same body, `repository.full_name`. Because both fields are attacker-controlled inside the same payload, an actor who legitimately knows the webhook secret for one configured GitHub organization (e.g. an org admin who provisioned their own Shipit `github` app entry) can forge a signature that "authenticates" as that organization while making the handler act on a repository belonging to a completely different organization.

### Finding Description
The signature check selects the app config purely from body content: [1](#0-0) [2](#0-1) 

`repository_owner` is derived entirely from the JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`), and this value is used to pick which configured GitHub App's `webhook_secret` to validate the HMAC against via `Shipit.github(organization: repository_owner)` in `lib/shipit/github_app.rb`: [3](#0-2) 

Once the signature is accepted, `create` dispatches the raw parsed body to every registered handler for the event: [4](#0-3) 

But the handlers determine *which* `Stack`/`Repository` to act on from a different field of the same body, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

For example `PushHandler` uses `stacks` (based on `repository_name`) to call `stack.sync_github(expected_head_sha: params.after)`: [6](#0-5) 

Because the HMAC is computed over the entire raw body that the caller fully controls, an attacker who is a legitimate administrator of one Shipit-configured GitHub organization ("OrgA", knowing OrgA's `webhook_secret` because they configured/created it) can build a payload where `repository.owner.login` = `"OrgA"` (so `verify_signature` selects and validates against OrgA's secret, which the attacker knows and can sign correctly) while `repository.full_name` = `"OrgB/victim-repo"` (a repository/stack that belongs to a different organization entirely tracked by the same Shipit instance). The equality that is supposed to hold — *the organization whose secret authenticated the request* == *the organization whose repository is acted on* — is broken: `repository_owner (verified) != repository.full_name.owner (acted upon)`.

### Impact Explanation
This lets an attacker who only controls one tenant organization on a shared/multi-org Shipit deployment (config example in `secrets_double_github_app.yml`, referenced by `Shipit.github(organization:)` supporting multiple orgs) force actions against another organization's stacks without ever compromising that other organization's webhook secret or GitHub credentials:
- Forge `push` events causing `Stack#sync_github(expected_head_sha:)` to run for a victim stack with an attacker-chosen `after` SHA, corrupting the tracked deploy state / triggering unwanted syncs.
- Similarly forge `status`, `check_suite`, `pull_request`, and `membership` events for a repository the attacker does not own, since all handlers derive their target purely from the unauthenticated `repository.full_name` (or team/org fields for membership) rather than from the organization the signature actually verified.
This is a cross-repository/cross-organization write reachable by an unprivileged-relative-to-the-victim attacker, matching the "organization that authenticated versus the repository that is written" trust binding called out in scope.

### Likelihood Explanation
Requires the deployment to host more than one GitHub organization's app config (a documented, supported configuration — see `test/dummy/config/secrets_double_github_app.yml` and `Shipit.github(organization:)`), and requires the attacker to know the `webhook_secret` for at least one of the configured organizations (plausible if they administer that org's GitHub App configuration, since `webhook_secret` is set by whoever installs/configures the app for that org). Given that constraint, forging the cross-repository payload is trivial (a single crafted HTTP POST); no additional privilege or session is needed for the target organization.

### Recommendation
Bind the field used for signature-secret selection and the field used for repository/stack resolution to the same value, and verify they are consistent: after selecting the app by `repository_owner`, re-derive `repository.full_name`'s owner and reject the request (422) if it does not match `repository_owner`. Alternatively, resolve the app/secret from the `Repository`/`Stack` record's own configured organization (looked up via `repository.full_name`) rather than from an attacker-suppliable field, so the same authenticated field is used consistently for both secret selection and event routing.

### Proof of Concept
1. Configure two GitHub orgs in `secrets.yml` under `github`, each with its own `webhook_secret` (as supported by `Shipit.github(organization:)`), e.g. `OrgA` (attacker-administered) and `OrgB` (victim, hosting stack for `OrgB/victim-repo`).
2. As the attacker, who knows OrgA's `webhook_secret`, build a push payload:
```json
{
  "organization": {"login": "OrgA"},
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"},
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, raw_body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches OrgA's app, and the HMAC validates successfully.
5. `PushHandler#repository_name` resolves `"OrgB/victim-repo"` from the same body and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on OrgB's stack — an action the attacker was never authorized to trigger for OrgB.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
