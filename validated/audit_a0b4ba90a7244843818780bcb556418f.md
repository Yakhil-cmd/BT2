### Title
CRLF/newline injection via unescaped GraphQL `viewer.login` into `git credential approve` stdin allows wrong-host credential storage - (File: pkg/cmd/auth/shared/gitcredentials/updater.go)

### Summary
`Updater.Update` builds the `git credential approve`/`reject` stdin protocol stream with `heredoc.Docf` and unescaped `%s` substitution of `hostname`, `username`, and `password`. Because `username` comes directly from the GraphQL `viewer.login` field returned by `GetCurrentLogin` with no character validation, a value containing embedded `\n` can inject extra `key=value` lines (e.g. `host=github.com`) into the credential-store protocol, causing git to persist the entered token under an attacker-chosen host rather than the intended one.

### Finding Description
The call chain is `Login` (`pkg/cmd/auth/shared/login_flow.go:179`) → `GetCurrentLogin` (`pkg/cmd/auth/shared/login_flow.go:253-285`) → `cfg.Login` → `opts.CredentialFlow.Setup` (`login_flow.go:207-212`) → `Updater.Update` (`pkg/cmd/auth/shared/gitcredentials/updater.go:18-55`).

`GetCurrentLogin` issues a raw GraphQL POST to `.../graphql` and decodes `result.Data.Viewer.Login` directly from the JSON body with no validation of its character set: [1](#0-0) 

That `username` string flows unmodified into `Update`, which builds the credential-approve stdin using `heredoc.Docf` with plain `%s` formatting, with no escaping of embedded newlines: [2](#0-1) 

The `git credential approve` helper protocol parses stdin as a sequence of `key=value` lines terminated by a blank line, where a later `key=` line overwrites an earlier one for the same key. If `username` contains `"\nhost=github.com\n"`, the constructed stream becomes:
```
protocol=https
host=<original-hostname>
username=<attacker-chosen-prefix>
host=github.com
password=<token>
```
Git will apply the last `host=` value it parses, storing the victim's real token under `host=github.com` (or any host the attacker chooses) instead of the enterprise hostname the user actually authenticated against.

This requires the attacker to control (or spoof) the response of an enterprise/self-hosted GitHub instance that the victim explicitly points `gh auth login --hostname <attacker-host>` at — this is within the stated threat model ("controls responses from a host the victim points gh at"), and is distinct from MITM of github.com itself. No existing code path validates or sanitizes `viewer.login` for control characters before it is embedded into the credential protocol stream, and `heredoc.Docf` performs no escaping — it's a thin wrapper over dedent + `fmt.Sprintf`.

### Impact Explanation
Successful exploitation causes wrong-host credential routing: the victim's real PAT/OAuth token — entered or generated during login to the attacker's chosen enterprise hostname — becomes stored in the local git-credential-store (or cache) keyed to a different host of the attacker's choosing (e.g., `github.com` or another internal host the victim also uses). Subsequent git operations against that host will silently present this token, which the victim did not intend for that host. This falls under GitHub's "wrong-host / wrong-account request routing" and credential-confinement impact classes. The impact is scoped to the victim's local git credential storage (not remote exfiltration of the token itself unless the injected host is one the attacker's own infrastructure can subsequently interact with via git operations initiated by the victim).

### Likelihood Explanation
Requires the victim to run `gh auth login` against a hostname controlled by (or resolving to) the attacker — a documented, supported gh workflow for GitHub Enterprise Server users, and explicitly in-scope per the threat model. The attacker only needs to control the JSON response to the `UserCurrent` GraphQL query and return a `login` value containing an embedded `\n`, which is straightforward since JSON allows escaped newlines in string values. No client-side validation of the `login` field's charset exists anywhere in this path.

### Recommendation
Sanitize/validate `username` (and `hostname`/`password` defensively) before constructing the credential-protocol stream in `Updater.Update` — reject or strip any embedded `\n`/`\r` (or `\0`) characters, or better, avoid manual `heredoc.Docf` string building entirely and construct the protocol lines programmatically per-field, rejecting any field containing newline bytes. Additionally, validate `viewer.login` in `GetCurrentLogin` against GitHub's known username charset (alphanumeric and hyphens) before use anywhere downstream.

### Proof of Concept
```go
func TestUpdateRejectsNewlineInjectedUsername(t *testing.T) {
    cs, restore := run.Stub()
    defer restore(t)
    // stub git credential approve command, capture stdin
    cs.Register(`git credential reject`, 0, "")
    cs.Register(`git credential approve`, 0, "")

    u := &Updater{GitClient: &git.Client{ /* ... */ }}
    maliciousUsername := "victim\nhost=github.com"
    err := u.Update("enterprise.example.com", maliciousUsername, "real-token-value")
    require.NoError(t, err)

    stdin := cs.Calls[1].Stdin // the "approve" invocation
    // Assert the captured stdin does NOT contain a second "host=" line
    require.Equal(t, 1, strings.Count(stdin, "host="),
        "credential stream must not allow injected extra host= line")
}
```
Expected (current, vulnerable) behavior: the captured stdin contains two `host=` lines and the second overrides the first, demonstrating the injection is unmitigated. After a fix, the test should assert that `Update` returns an error for usernames containing `\n`/`\r`, or that such characters are stripped/escaped so only one `host=` line remains.
