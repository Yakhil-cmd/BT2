### Title
Reward-distribution DoS via unchecked subtraction underflow in `get-rewards` / `calculate-rewards` - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar`'s reward-accounting pipeline computes the contract's distributable sBTC rewards with a raw subtraction that has no underflow guard, structurally analogous to the reported `Treasury._loadSwapState()` bug where `_state.xNav = baseSupplyNav.sub(fSupplyNav).div(xSupply)` reverts once the protocol invariant `baseSupplyNav >= fSupplyNav` is violated. In `pox-5.clar`, `get-rewards` computes `(- current-balance total-staked-sbtc cur-reserve)` [1](#0-0)  and this feeds directly into `get-new-rewards` and `calculate-rewards`, the sole entry point that computes, records, and distributes sBTC bond rewards and STX-staker rewards for a cycle [2](#0-1) .

### Finding Description
Clarity's `-` operator on `uint` traps (aborts the whole transaction) on underflow, exactly like Solidity's `SafeMath.sub` in the reported bug. `get-rewards` assumes the invariant `current-balance >= total-staked-sbtc + cur-reserve` always holds, i.e., that the contract's actual sBTC token balance always at least covers the sum of (a) all sBTC currently credited as "staked" via `get-total-sbtc-staked`, and (b) the internally tracked `reserve-balance`. This is the exact same class of "invariant assumed instead of enforced" bug as the reported `xNav` underflow, where `baseSupplyNav >= fSupplyNav` was silently assumed.

If any code path can cause the tracked accounting values (`total-staked-sbtc`, `reserve-balance`) to exceed the contract's actual live sBTC balance — for example, through partial/failed L1 lockup crediting, a bond/stake unwind that decrements the real balance faster than the internal counters, rounding drift across many `calculate-bond-rewards` folds, or any sBTC withdrawal path that reduces `current-balance` without a matching decrement to `total-staked-sbtc`/`reserve-balance` — `get-rewards` underflows and traps. Because `calculate-rewards` is the single choke point for reward accounting (updating `rewards-per-token-for-cycle`, `reserve-balance`, and `last-accounted-rewards-only`) [3](#0-2) , once this underflow condition is hit, every future call to `calculate-rewards` (and therefore every downstream reward-claim/settlement path that depends on it) permanently reverts. There is no fallback path (unlike the reported fix's `if (_state.xNav == 0) { ... }` branch) that lets the system degrade gracefully instead of trapping.

### Impact Explanation
This maps to a "permanent freezing of reserve or fees" / "temporary freezing of staked funds" class of High-severity impact per the rules: once the underflow condition occurs, sBTC bond rewards and STX-staker rewards for the affected and all subsequent cycles can never be computed or distributed through the normal path, freezing reward flow indefinitely (there being no admin/manager recovery function visible in the reachable pox-5 accounting logic analogous to the reported protocol's redemption-path fix). This does not require any privileged role — any state transition that shifts the balance/accounting relationship (e.g., via legitimate stacking/lockup/reward flows already reachable by ordinary stackers and signers) can trigger it.

### Likelihood Explanation
Medium: I was not able to fully trace every mutator of `total-staked-sbtc` (`get-total-sbtc-staked`) and `reserve-balance` within the available index (searches for `reserve-balance`, `get-total-sbtc-staked`, `slash`, `withdraw-reserve` in `pox-5.clar` returned no additional matches beyond what was already read, likely due to index truncation of this large file). I could not conclusively identify a concrete external call sequence that forces `current-balance < total-staked-sbtc + cur-reserve`. The structural flaw (unchecked, trapping subtraction on an invariant that is merely assumed) is confirmed, but proving the exact triggering path requires reading the full `pox-5.clar` reserve/stake bookkeeping (deposit, withdrawal, and bond-settlement functions) which is not fully visible here.

### Recommendation
Replace the raw subtraction in `get-rewards` with a saturating/checked computation that returns `u0` (or an explicit error) instead of trapping when `total-staked-sbtc + cur-reserve` exceeds `current-balance`, mirroring the reported fix's pattern of branching on the underflow condition (`if (baseSupplyNav <= fSupplyNav) { xNav = 0 } else { ... }`) rather than relying on the arithmetic to fail safe. Concretely:
```clarity
(define-read-only (get-rewards)
    (let (
            (cur-reserve (var-get reserve-balance))
            (total-staked-sbtc (get-total-sbtc-staked))
            (current-balance (unwrap-panic (contract-call? ...sbtc-token get-balance current-contract)))
            (committed (+ total-staked-sbtc cur-reserve))
        )
        (if (>= current-balance committed)
            (- current-balance committed)
            u0)
    )
)
```
Additionally, audit all writers of `reserve-balance` and the stake-accounting maps feeding `get-total-sbtc-staked` to confirm the intended invariant `current-balance >= total-staked-sbtc + cur-reserve` is actually maintained by every code path, not merely assumed.
