### Title
Contract Hash Collision Via Unescaped Delimiter Concatenation in Arbiter Contract Hashing - (File: arbiter_contract.js)

### Summary
`getHashSrc()` in `arbiter_contract.js` builds the source string used to compute an arbiter contract's identifying `hash` by concatenating several attacker/party-controlled, variable-length fields (`title`, `text`, party names, etc.) with a fixed delimiter, and — for contracts with `creation_date <= NEW_HASH_DATE` — with **no delimiter at all**. Because none of the individual field values are forbidden from containing the delimiter string (or, in the legacy branch, any byte sequence), two different sets of field values can produce the exact same concatenated string, and therefore the exact same SHA-256 `hash`. This is the same class of bug as the reported `calcDestinationId` issue: a deterministic hash built from an unescaped concatenation of attacker-influenced inputs, which can be deliberately collided. [1](#0-0) 

### Finding Description
`getHashSrc` is:
```js
function getHashSrc(contract) {
	...
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
``` [2](#0-1) [1](#0-0) 

Unlike `string_utils.getSourceString`, which prefixes every field with a type tag and rejects values containing the join character (`STRING_JOIN_CHAR`), `getHashSrc` never validates that `contract.title`/`contract.text`/party names don't contain `exports.DELIMITER` ("[|#|]"), and the legacy branch (used for any contract whose `creation_date` is not after `NEW_HASH_DATE`) has **no separator whatsoever** between `title`, `text`, `creation_date`, and the party names. [3](#0-2) 

This means a party composing the contract (the "offeror", who freely controls `title` and `text` when calling `createAndSend`) can choose `title`/`text` pairs such that the concatenation `title + text` is byte-identical to a different, more advantageous `title' + text'` pair (e.g., moving a clause from the end of `title` to the start of `text`, or embedding the delimiter/pipe sequence inside a field to reshuffle field boundaries). Both variants hash to the same `contract.hash`.

The resulting `hash` is the authoritative identifier used throughout the arbiter-contract flow: it is stored as primary key, sent to the peer as the contract offer, and — critically — checked against the on-chain signing unit's `data` message field `contract_text_hash` before the contract is marked "signed":
```js
if (payload.arbiter !== contract.arbiter_address || payload.contract_text_hash !== contract.hash || payload.contacts_hash !== contacts_hash)
	return console.log(`data message payload does not match contract ${contract.hash} in purported signing unit ${unit}`);
``` [4](#0-3) 

The equivalent check exists for prosaic contracts as well. [5](#0-4) 

Because the hash-equality check is the only binding between the on-chain signed commitment and the actual contract text shown to the counterparty/arbiter, a hash collision lets a malicious party present one `title`/`text` to the counterparty for review/acceptance while the dispute-resolving arbiter (or a later re-derivation) is shown/reconstructed with a different, colliding `title`/`text`, without invalidating the `contract_text_hash` binding recorded on-chain.

### Impact Explanation
The arbiter contract's `hash` is the sole cryptographic binding between the natural-language contract text (which determines how the arbiter releases escrowed funds) and the on-chain signed unit. If two different contract texts can be crafted to produce the same hash, a malicious payer/payee can exploit the ambiguity during a dispute: the arbiter's decision about fund release is based on `title`/`text`, but the validator only checks the hash, not the content itself. This can result in the arbiter (or counterparty) being shown or later presented a different agreement than what was originally hashed and signed, undermining the integrity of the escrow/arbitration mechanism and enabling fraudulent redirection of escrowed funds — a concrete fund-loss scenario for the deceived party.

### Likelihood Explanation
Reachable by any wallet user without special privileges: the party proposing the contract fully controls `title` and `text` via `createAndSend`, and the legacy (pre-`NEW_HASH_DATE`) hashing path has zero separator between fields, making boundary-shifting collisions trivial to construct (simply move characters between adjacent fields). Even in the delimited branch, since field content isn't restricted from containing the delimiter, an attacker can insert `exports.DELIMITER` into `title` or `text` to fabricate an alternate parse that collides.

### Recommendation
Adopt the same disciplined serialization used elsewhere in the codebase (`string_utils.getSourceString`/`getJsonSourceString`), which prefixes each field with its type/length and explicitly rejects values containing the separator byte, or switch to length-prefixed / JSON-based serialization (as already done for AA-hashing via `getJsonSourceString`) before hashing. Reject `title`/`text`/party name values containing `exports.DELIMITER`, and deprecate the legacy no-delimiter hashing path entirely rather than keeping it reachable for any `creation_date`.

### Proof of Concept
1. Party A calls `createAndSend` with `title = "Pay for goods[|#|]500 USD"` and `text = ""` (post-`NEW_HASH_DATE` contract).
2. Party A crafts an alternate contract with `title = "Pay for goods"` and `text = "500 USD"` (same `creation_date`, addresses, amount, asset).
3. Both produce identical `getHashSrc` output because `title + DELIMITER + text` is identical in both cases (`"Pay for goods[|#|]500 USD" + DELIMITER + ""` vs. `"Pay for goods" + DELIMITER + "500 USD"`), hence identical `contract.hash`.
4. Party A sends the seemingly benign second version to the counterparty for acceptance, while retaining/presenting the first, differently worded version to the arbiter during a later dispute — both validate against the same `contract.hash` and the same on-chain `contract_text_hash`, so the substitution is undetectable by the hash check in `handleReceivedSigningUnit`.
