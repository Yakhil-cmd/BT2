Arbitrary, unvalidated `creator` account in `initialize_with_permission` permanently locks creator fees - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`initialize_with_permission` lets a permissioned pool creator store an arbitrary, completely unconstrained `creator` pubkey as the pool's `pool_creator`. Because `collect_creator_fee` requires that stored address to be a `Signer`, and `collect_creator_fee_permissionless` only relocates the accumulated fees into an associated token account owned by that same address, choosing a `creator` address that has no corresponding keypair (or is a PDA with no spending logic) permanently strands all creator fees accrued by the pool — the exact fund-class bug described in the external report, where tokens are sent to an "owner" that structurally has no way to withdraw them.

### Finding Description
In `InitializeWithPermission`, the `creator` field is declared as a bare `UncheckedAccount<'info>` with no signer requirement and no constraint tying it to `payer` or to any verifiably-controllable key: [1](#0-0) 

That unchecked value is written directly into the pool's persistent state as `pool_creator`: [2](#0-1) 

Later, `collect_creator_fee` requires the `creator` account to be a `Signer` whose address matches `pool_state.pool_creator`: [3](#0-2) 

If `pool_creator` was set (at initialization) to an address for which nobody holds a private key (e.g., a burn address, an unrelated mint, or a PDA of a program with no CPI path to sign this specific instruction), then `collect_creator_fee` can never be called — no signature can ever be produced for that key.

The permissionless fallback avoids the signer requirement but still routes funds to an ATA owned by that same uncontrollable address: [4](#0-3) [5](#0-4) 

Since SPL token transfers out of that ATA require a signature from its `authority` (the unownable `creator` pubkey) or a delegate, and no such signature can ever be produced, the fee tokens sitting in that ATA become permanently unspendable. This is functionally identical to the reported bug class: fees/tokens are sent to an "owner" address that has no mechanism to ever withdraw them, resulting in permanent fund loss. By contrast, the non-permissioned `Initialize` path is safe because its `creator` account is a `Signer`, which necessarily has a controllable key at pool-creation time.

### Impact Explanation
All accumulated `creator_fees_token_0` / `creator_fees_token_1` for the affected pool are permanently and irrecoverably locked once collected via `collect_creator_fee_permissionless`, since no path exists to move tokens out of an ATA whose owner has no available signature. This is a direct, protocol-caused freezing of real fee assets, not merely a user misconfiguration recoverable by the protocol.

### Likelihood Explanation
The `creator` field in `InitializeWithPermission` is fully attacker/caller-controlled with zero validation (no signer check, no relation to `payer`, no PDA ownership check), so any permissioned pool creator can trivially set it to a keyless address in a single `initialize_with_permission` transaction. Once swaps generate creator fees on that pool, calling `collect_creator_fee_permissionless` deterministically strands those fees forever.

### Recommendation
Require `creator` in `InitializeWithPermission` to either be a `Signer` (mirroring the standard `Initialize` path) or explicitly validate that it is a system-owned account capable of signing (e.g., disallow program-owned/PDA addresses, or require an off-curve/PDA `creator` to additionally supply proof of a corresponding withdrawal-authority mechanism). At minimum, add a constraint rejecting known-unspendable addresses and document/enforce that `creator` must be an account able to eventually sign or delegate spending of its ATA.

### Proof of Concept
1. Obtain a `Permission` PDA for `payer` (whatever permission-granting flow the deployment uses).
2. Call `initialize_with_permission` with `creator` set to an arbitrary pubkey with no known private key (e.g., a freshly generated keypair's pubkey that is never used again, or any PDA belonging to a program with no relevant CPI signer path). This succeeds because `creator` is an `UncheckedAccount` with no signer/ownership constraint.
3. Perform swaps on the resulting pool so that `creator_fees_token_0`/`creator_fees_token_1` accumulate in `pool_state`.
4. Call `collect_creator_fee_permissionless`; the fees are transferred into `creator_token_0`/`creator_token_1` ATAs owned by the keyless `creator` address.
5. Attempt to move tokens out of those ATAs: this requires a signature from `creator` (or a delegate), which is impossible to produce, permanently locking the fee tokens — analogous to the referenced `FjordAuction` bug where `auctionToken.transfer(owner, totalTokens)` sends tokens to an `owner` (the factory) with no withdrawal mechanism.
