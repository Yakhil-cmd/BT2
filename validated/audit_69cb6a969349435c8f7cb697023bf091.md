### Title
Security-review coverage cap can be bypassed by donating decoy "risk score" padding to push the real vulnerable file out of the reviewed window - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
The `security-guidance` plugin caps how many changed files it sends to the LLM reviewer (`MAX_DIFF_FILES`, default 30) and, when a diff exceeds that cap, keeps only the top-scoring files as ranked by `_prioritize_diff_files()`. The score is a cheap, fully attacker-observable/attacker-computable heuristic — path substring matches against a fixed token list plus a raw count of `"\n+"` in the diff content. Anyone who can shape the commit/push content (a malicious or prompt-injected subagent, or a user racing the review) can "donate" cheap decoy weight — filenames containing risk tokens (`auth`, `route`, `handler`, …) padded with many trivial `+` lines — to fill every slot in the cap, pushing the file that actually carries the injected vulnerability below the cutoff. The review then silently proceeds without ever showing that file to the LLM, exactly mirroring the reported bug class: inflating a self-controlled, unauthenticated value to bypass a hard-coded exposure/coverage limit without giving up anything of real value.

### Finding Description
`_prioritize_diff_files()` computes, for every changed file, `score = (risk, not low_prio, added)` where `risk` is the count of substring matches against `_SECURITY_RISK_PATH_TOKENS` and `added` is `content.count("\n+")` — a raw, cheap-to-inflate line-count proxy taken directly from the diff text the attacker controls. [1](#0-0) 

This ranking function is the sole gate deciding which files survive the `MAX_DIFF_FILES` cap before being handed to the LLM reviewer, in all three review surfaces: per-commit review, push-sweep, and the Stop hook. [2](#0-1) [3](#0-2) [4](#0-3) 

`MAX_DIFF_FILES` itself is explicitly a hard exposure cap ("Cap on source files sent to the LLM reviewer per Stop fire"). [5](#0-4) 

Because both components of the score are computed purely from attacker-supplied diff text (file path string, and a naive substring count of `+` at line starts), an attacker who authors the commit/push (e.g., a subagent under indirect prompt injection, or the human author racing an automated push-sweep) can trivially "donate" score inflation: create N decoy files whose paths contain risk tokens (`auth/`, `route/`, `handler.py`, etc.) and pad them with junk `+`-heavy diff content, cheaply outscoring the one file that contains the real vulnerability but whose path/content happens not to match the fixed token list. Since the cap is a hard top-K cut (`ranked[:cap]`), the genuinely dangerous file is dropped entirely from `diff_files` before `analyze_code_security`/the agentic reviewer ever sees it — the review pipeline reports "clean" for a commit it never actually reviewed.

### Impact Explanation
This is a direct analog of the reported bug class: the review pipeline enforces a fixed "exposure limit" (`MAX_DIFF_FILES`) using a self-computed value that the attacker fully controls and can inflate for free (padding a decoy file's diff and adding a risk substring to its path costs nothing and doesn't require the attacker to sacrifice anything). The result is that the security-guidance hook — the project's automated safety net against a model/agent smuggling a vulnerability into a commit — can be starved of the one file that matters, and the vulnerable code merges/pushes with no LLM review flag and no visible skip signal to the user (the emitted metric only shows `diff_files_dropped`, a count, not which files were dropped). Per the plugin's own adversarial-verification guidance, this is explicitly NOT a "no privilege boundary" case — the model/subagent is the attacker and the user relying on the automated review is the victim.

### Likelihood Explanation
Feasible for any actor that can shape commit content review passes over: a compromised/prompt-injected subagent doing the actual coding, or an attacker who can influence file paths and diff volume in a PR that later gets auto-reviewed by `push-sweep`/Stop hooks. No credentials or special access are required beyond the ability to author files in the repository, which is the exact same capability the review is meant to gate.

### Recommendation
Do not let the cutoff decision depend on values the diff author fully controls. Concretely:
- Decouple "how many decoy risk-token matches / added-line padding a file has" from whether it gets reviewed — e.g., always include every file whose diff was NOT already reviewed under `previous_findings`/`reviewed_shas`, batching call-outs instead of dropping files outright when the cap is exceeded.
- Replace the raw `content.count("\n+")` proxy with a bounded/normalized signal (e.g., cap per-file "added" contribution so no single or few files can dominate the ranking) and treat `risk` token matches as an OR-inclusion filter (always keep any risk-token match) rather than a magnitude that competes with volume-based padding.
- Emit which specific files were dropped (not just a count) in metrics/telemetry so drops are auditable and detectable.

### Proof of Concept
1. A subagent (or attacker-controlled contribution) crafts a commit touching 40 files (over `MAX_DIFF_FILES=30`): 35 decoy files with paths like `src/auth/decoy_1.py` … `decoy_35.py`, each with a large block of trivial `+` lines (e.g., blank/comment lines) to maximize `added`.
2. One real file, e.g. `utils/formatter.py`, contains the actual injected vulnerability (e.g., `subprocess.run(cmd, shell=True)` built from untrusted input) but its path contains none of `_SECURITY_RISK_PATH_TOKENS`.
3. `_prioritize_diff_files()` ranks by `(risk, not low_prio, added)`; the 35 decoys (risk≥1, large `added`) outrank `utils/formatter.py` (risk=0), so it's dropped from the top-30 slice returned to `analyze_code_security`/agentic review.
4. The commit-review/push-sweep/Stop hook completes with no findings for `utils/formatter.py`; only `diff_files_dropped` (a count) is emitted, giving the user no indication the vulnerable file was excluded from review.

```python
def _prioritize_diff_files(diff_files, cap):
    """When `diff_files` exceeds `cap`, return the top-`cap` by security
    relevance plus the count dropped. Otherwise return (diff_files, 0).

    Score = (risk_tokens_in_path, not_low_priority, added_lines). The
    added-lines proxy is `content.count('\\n+')` which counts diff additions
    cheaply without re-parsing hunks. This is a heuristic, not a guarantee —
    the goal is to review the likely-dangerous subset of an over-cap diff
    instead of reviewing nothing. Diffs that exceed the cap are typically
    large multi-file scaffolds, and the cross-file source→sink vulnerabilities
    in them concentrate in a handful of api/client/route files.
    """
    if len(diff_files) <= cap:
        return diff_files, 0

    def _score(item):
        fp, content = item
        low = fp.lower()
        # Prepend "/" so leading-slash patterns in _LOW_PRIORITY_PATH_TOKENS
        # match top-level dirs (git diff paths are repo-root-relative, e.g.
        # `migrations/001.py` not `/migrations/001.py`). Same trick as
        # _is_reviewable_source.
        low_slashed = "/" + low
        risk = sum(1 for t in _SECURITY_RISK_PATH_TOKENS if t in low)
        low_prio = (
            fp.endswith(_LOW_PRIORITY_SUFFIXES)
            or any(t in low_slashed for t in _LOW_PRIORITY_PATH_TOKENS)
        )
        # added_lines: count('\n+') over-counts by including '+++' header and
        # any literal '+' at line start in context, but it's a consistent
        # ordinal across files in the same diff which is all we need.
        added = content.count("\n+")
        return (risk, not low_prio, added)

    ranked = sorted(diff_files, key=_score, reverse=True)
    return ranked[:cap], len(diff_files) - cap
```
