### Title
Missing contextual upper-bound check on `count_coins` in asset denomination definitions allows unsafe-integer values that break issuance arithmetic - (File: `validation.js`, `aa_validation.js`)

### Summary
When an asset (or an AA-issued asset) defines fixed denominations, each denomination entry's `denomination` field and the overall `cap` are explicitly bounded to `constants.MAX_CAP`, but the paired `count_coins` field — which is multiplied against `denomination` to derive the effective issuance cap — is only checked with `isPositiveInteger()`, which has **no upper bound at all**. This is the same class of bug as the reported OctoRPKI issue: a field (`maxLength`) that passes an isolated syntactic check but is never validated *in context* against the sibling fields/bounds that make the overall record safe.

### Finding Description
In `validation.js`'s `validateAssetDefinition`, `cap` and `denomination` are both bounded: [1](#0-0) [2](#0-1) 

But `count_coins`, used to derive `total_cap_from_denominations`, only gets an `isPositiveInteger` check with no `MAX_CAP` bound: [3](#0-2) 

The same asymmetry exists in the AA-issued asset path (`aa_validation.js`), where `denomInfo.count_coins` is validated with `isPositiveInteger` only, while `cap` and `denomination` have explicit `MAX_CAP` checks: [4](#0-3) [5](#0-4) [6](#0-5) 

`isPositiveInteger`/`isInteger` in `validation_utils.js` never check against `Number.MAX_SAFE_INTEGER` (2^53); they only require `Math.floor(value) === value`, which is trivially true for any IEEE-754 double beyond 2^53 because such doubles have no fractional component representable in binary: [7](#0-6) 

The unchecked `count_coins` is later used in floating-point multiplication both when summing the declared cap (`total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination`) and, at issuance time, in `validateIndivisibleIssue`, where the issue amount is checked with `input.amount !== denomination * denomInfo.count_coins`: [8](#0-7) [9](#0-8) 

Because `count_coins` can be an unsafe (>2^53) double while `denomination`/`amount`/`cap` are constrained to `MAX_CAP` (well below 2^53), and the equality checks that are supposed to bind these values together (`total_cap_from_denominations === payload.cap`, `input.amount === denomination*count_coins`) are all performed in floating-point arithmetic, the multiplication `denomination * count_coins` can silently round to a "convenient" in-range double even though the mathematically exact per-denomination supply is different from what is stored/compared. This is exactly the "contextual out-of-bounds" pattern from the report: `count_coins` is syntactically valid in isolation (positive integer) but is never checked in the context of the bound that its sibling fields (`denomination`, `cap`) are required to respect.

### Impact Explanation
This falls under asset issuance and supply-inflation risk: an asset issuer can craft `denominations` arrays with astronomically large, unsafe `count_coins` values that pass validation on all full nodes identically (since the check is purely a JS floating-point comparison, deterministic across nodes), but where the declared `cap`/per-denomination `count_coins` relationship is not the mathematically exact one an honest reader of the asset definition would assume. Downstream, `asset_denominations.count_coins` (a `BIGINT` column) stores the raw unsafe integer, decoupling the on-disk "capacity" bookkeeping from the actual capped economics implied by `payload.cap`, which is itself bound to `MAX_CAP`. In the worst case this permits a mismatch between the intended cap enforcement and the recorded per-denomination coin count, since the multiplication and equality comparisons used to enforce "capped means capped" are done with a numeric type that cannot faithfully represent the value being checked.

### Likelihood Explanation
Reachable by any unprivileged unit poster defining a fixed-denomination asset (`validateAssetDefinition` in `validation.js`) or any AA whose bytecode issues a new asset (`aa_validation.js`, `case 'asset'`) — no special privileges required, matching the "asset issuer" actor class explicitly in scope. The only requirement is choosing a `count_coins` value above `Number.MAX_SAFE_INTEGER`, which trivially passes `isPositiveInteger`.

### Recommendation
Add an explicit upper bound to `count_coins` (and any other integer amount-like field multiplied against `denomination`/`cap`) equal to `constants.MAX_CAP`, in both `validation.js`'s `validateAssetDefinition` (near line 2776) and `aa_validation.js`'s `validateDenominations` (near line 274), mirroring the existing bound already applied to `denomination` and `cap`. Consider also validating that `denomInfo.count_coins * denomInfo.denomination <= constants.MAX_CAP` explicitly (using BigInt or a safe-integer check) before accumulating `total_cap_from_denominations`, rather than relying on floating-point equality with `payload.cap`.

### Proof of Concept
1. An attacker composes an `asset` definition unit (or an AA `asset` response message) with:
   - `fixed_denominations: true`
   - `denominations: [{ "denomination": 1, "count_coins": 9007199254740993 }]` (2^53 + 1, an unsafe integer that IEEE-754 doubles round to 9007199254740992 or 9007199254740994 depending on operation)
   - `cap` set to the floating-point result of `count_coins * denomination` as computed by the validator (which may not equal the attacker's intended exact integer value).
2. `isPositiveInteger(denomInfo.count_coins)` in both `validation.js` (`validateAssetDefinition`) and `aa_validation.js` (`validateDenominations`) returns `true` because `Math.floor()` of an already-rounded double is a no-op — no `MAX_CAP`-style bound rejects it, unlike `denomination` and `cap`.
3. The definition is accepted deterministically by all full nodes (since the check is pure JS float math and thus consistent), embedding a stored `count_coins` in `asset_denominations` (`BIGINT`) that no longer corresponds exactly to the double used during validation-time arithmetic.
4. At issue time, `validateIndivisibleIssue` performs `input.amount !== denomination * denomInfo.count_coins` — again in floating point — allowing an issue amount to be accepted based on a rounded product rather than the exact stored `BIGINT` value, decoupling the enforced cap from the economically intended one.
