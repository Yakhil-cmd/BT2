Confirmed: `Shipit.github_teams` (`lib/shipit.rb:256-258`) maps `github.oauth.teams` entries to `Team` records via `Team.find_or_create_by_handle`, and `User#authorized?` (`app/models/shipit/user.rb:80-82`) grants access to anyone whose `teams` include one of `Shipit.github_teams`. ### Title
Membership webhook signature only binds to the sending organization, not to the team being modified, allowing cross-organization authorization-team membership forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GithubApp` (and thus the HMAC secret) used to authenticate an incoming webhook based on `params.dig('repository','owner','login') || params.dig('organization','login')` — a field taken from the unauthenticated JSON body itself, before the signature is validated. Once validated, `MembershipHandler#process` looks up the `Team` to mutate by `github_id` alone, never checking that `params.organization.login` matches the organization the `Team` actually belongs to. Any principal capable of generating a validly-signed `membership` webhook for *one* configured GitHub organization (e.g., an admin of a secondary/low-trust org onboarded to the same Shipit instance) can add or remove arbitrary users from a `Team` record belonging to a *different*, higher-trust organization, as long as they know/guess that team's numeric `github_id`. ### Finding Description
The equality that should hold is:
`organization that authenticated the webhook == organization that owns the Team object being mutated`

Instead, the code enforces only:
`organization that authenticated the webhook == params['organization']['login']` (used solely to pick the verifying secret)

and separately:
`Team looked up by params['team']['id']` (no organization check at all)

Because Shipit supports multiple GitHub organizations configured side by side (`docs/setup.md:181-209`, `lib/shipit/github_app.rb:44-57`), each with its own `webhook_secret`, a `membership` event delivered from Org A's installation is authenticated only against Org A's secret via `Shipit.github(organization: repository_owner)` (`app/controllers/shipit/webhooks_controller.rb:25-30`). Once that check passes, `MembershipHandler.find_or_create_team!` resolves the `Team` strictly `Team.find_or_create_by!(github_id: params.team.id)` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-42`), and then adds/removes `params.member.login` from it (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`). There is no assertion that `params.team.id` actually belongs to `params.organization.login`, nor that it belongs to the same org whose secret validated the signature.

An attacker who administers (or otherwise controls the GitHub App/webhook configuration of) any org configured in `Shipit.secrets.github` can therefore forge a `membership` webhook whose `organization.login` is their own org (so the signature check passes with their own secret) but whose `team.id` is the `github_id` of a `Team` that actually belongs to a completely different, unrelated organization — including one used in `Shipit.github_teams` for authorization gating.

### Impact Explanation
`User#authorized?` (`app/models/shipit/user.rb:80-82`) is `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?`, i.e., membership in a `Team` referenced by `Shipit.github_teams` is the sole authorization gate for the entire Shipit UI/API (`app/controllers/concerns/shipit/authentication.rb:20-34`). By forging a `membership` "added" event against that team's `github_id` while authenticating with an unrelated, lower-privileged org's webhook secret, an attacker can insert an arbitrary `User` (including one they control) into that authorization team, escalating into `Shipit.github_teams` authorization and gaining full access to stacks, deploys, rollbacks, and merges — a High severity impact under the given rubric.

### Likelihood Explanation
Exploitation requires: (1) the target Shipit instance be configured with more than one GitHub organization (a documented, supported configuration, `docs/setup.md:181-209`), (2) the attacker controls/administers the GitHub App webhook configuration for at least one of those organizations (so they can deliver arbitrary signed payloads to Shipit's public `/github/webhooks` endpoint), and (3) the attacker knows or can enumerate the target `Team`'s numeric `github_id` (sequential/guessable, or discoverable via other endpoints). This is a realistic scenario for any multi-tenant/multi-org Shipit deployment where organizations have differing trust levels.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the `Team` lookup by both `github_id` and `organization` derived from the verified webhook context (not just `params.team.id`), and reject the event if an existing `Team` with that `github_id` belongs to a different `organization` than `params.organization.login`. More generally, `WebhooksController#verify_signature` should pass the verified organization down to handlers so each handler can assert that every organization-scoped object it mutates (`team.organization`, `repository.owner`, etc.) matches the organization whose secret validated the request.

### Proof of Concept
1. Shipit is configured with two orgs in `secrets.yml`: `trusted-org` (owns `Team` #`shipit_teams(:shopify_developers)`, `github_id: X`, referenced in `oauth.teams` for authorization) and `low-trust-org` (attacker-administered, with its own `webhook_secret`).
2. Attacker computes `sha1=HMAC(low-trust-org.webhook_secret, body)` for:
```json
{
  "action": "added",
  "team": { "id": X, "name": "Developers", "slug": "developers", "url": "..." },
  "organization": { "login": "low-trust-org" },
  "member": { "login": "attacker-controlled-user" },
  "repository": { "owner": { "login": "low-trust-org" } }
}
```
3. POST to `/github/webhooks` with header `X-Github-Event: membership` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `"low-trust-org"`, fetches `low-trust-org`'s `GitHubApp`, and validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `MembershipHandler#process` finds the existing `Team` with `github_id: X` (belonging to `trusted-org`) and calls `team.add_member(User.find_or_create_by_login!('attacker-controlled-user'))` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-42`), granting that user membership in `trusted-org`'s authorization team without ever authenticating as, or being vetted by, `trusted-org`.
