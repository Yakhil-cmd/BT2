### Title
Snowbridge `system-frontend` pallet swaps user tip/fee assets via `swap_exact_tokens_for_tokens` with no slippage protection (`amount_out_min = None`) - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

### Summary
`register_token` and `add_tip` extrinsics let a signed user swap an arbitrary fee/tip asset into Ether through `pallet_asset_conversion`, but the pallet always passes `None` for `amount_out_min`, disabling the underlying AMM's slippage check entirely, unlike the Balancer report where the caller hardcoded `minAmountsOut = [0,0]`.

### Finding Description
`swap_and_burn` invokes: [1](#0-0) 
The `Swap` trait's `swap_exact_tokens_for_tokens` signature explicitly supports an optional minimum-out for slippage control: [2](#0-1) 
and the pallet enforces it only `if let Some(amount_out_min) = amount_out_min`: [3](#0-2) 
Because `swap_and_burn` passes `None`, the `ensure!(amount_out >= amount_out_min, ...)` guard is entirely skipped — the swap always executes at whatever price the pool state yields, regardless of how far it has moved due to prior transactions in the same block/extrinsic ordering. This is called from both public extrinsics:
- `register_token`, reachable by any account whose origin passes `T::RegisterTokenOrigin` (not root-only for non-`Here` origins) via `swap_fee_asset_and_burn` → `swap_and_burn`: [4](#0-3) 
- `add_tip`, reachable by any `ensure_signed` account: [5](#0-4) 

Both paths let an ordinary signed user (attacker has no privileged role) trigger a swap of their fee/tip asset for Ether inside the same pool used by `pallet-asset-conversion`, with zero protection against price movement between transaction submission and inclusion. A block author or any actor able to place transactions before/after this one in the same block (e.g. sandwiching via large swaps in the same pool immediately before this extrinsic executes, then reversing after) can force the swap to execute at an arbitrarily unfavorable price, extracting value from the caller of `register_token`/`add_tip`.

### Impact Explanation
The caller's fee/tip asset is swapped into Ether without any bound; a sandwich attacker can manipulate the pool reserves immediately before this call executes and reverse afterward, capturing the difference between fair price and executed price. This constitutes an attacker capturing value at the direct expense of an unprivileged user through a codepath the target codebase explicitly designed to support (`amount_out_min`) but chose not to use. Impact scales with tip/fee size and pool depth/liquidity; it is not unbounded theft of protocol funds and does not break consensus, placing it below Critical.

### Likelihood Explanation
Likelihood is bounded by the practical difficulty of atomically sandwiching a specific extrinsic in Substrate compared to Ethereum mempool sandwiching — the attacker would need influence over transaction ordering within a block (e.g. being the block author/collator, or exploiting a permissionless ordering assumption) since there is no public mempool with guaranteed pending-tx visibility in the same sense as Ethereum. This significantly lowers likelihood versus the original EVM report, but the missing check itself is unconditionally present in the code for every call to these two extrinsics whenever the fee/tip asset differs from Ether.

### Recommendation
Compute a slippage-bounded minimum via `QuotePrice::quote_price_exact_tokens_for_tokens` (or equivalent) before swapping, and pass `Some(min_out)` to `swap_exact_tokens_for_tokens` in `swap_and_burn`, or expose a `min_ether_out` parameter on `register_token`/`add_tip` that the caller supplies and the pallet enforces.

### Proof of Concept
No executable PoC was run. Static analysis is conclusive: `swap_and_burn` passes the literal `None` for the `amount_out_min` parameter, which — per `do_swap_exact_tokens_for_tokens` — is the sole gate on `amount_out >= amount_out_min`; supplying `None` bypasses that gate entirely (see cited lines above). I did not build a full XCM/multi-block reproduction demonstrating an actual price-manipulation sandwich because that requires modeling block-author transaction-ordering control, which is outside static code inspection; this is noted as an open verification gap. All other AMM entry points I inspected in this codebase (`pallet-asset-conversion` extrinsics, its precompile, `SwapAssetAdapter` for tx-payment fees, and `SingleAssetExchangeAdapter` for XCM asset exchange) correctly compute and pass non-`None`/quoted minimums immediately before consuming them atomically in the same call stack, so they are not vulnerable to this pattern: [6](#0-5) [7](#0-6)
