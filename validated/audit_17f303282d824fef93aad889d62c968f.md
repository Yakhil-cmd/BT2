### Title
Unbounded `machine.environment` merge from PR-controlled `shipit.yml` overrides `GITHUB_TOKEN`/`GIT_ASKPASS` in task command env - (File: lib/shipit/task_commands.rb)

### Summary
`Shipit::TaskCommands#env` merges the trusted `base_env` (which contains `GITHUB_TOKEN` and `GIT_ASKPASS`) first, then layers `deploy_spec.machine_env` — sourced directly from the `machine.environment` key of the `shipit.yml` checked out from the ReviewStack's own branch — on top, with no key allowlist. Because `ReviewStack.branch` is set to `pull_request.head.ref` from the PR-opening webhook, an attacker who opens a PR from their own fork can supply a `shipit.yml` whose `machine.environment` defines `GITHUB_TOKEN` or `GIT_ASKPASS`, and that value silently overwrites the trusted credential in the environment eventually passed to `PTY.spawn` via `Command#unbundled_env`/`Command#start`.

### Finding Description
The broken binding, stated as an equality that must hold but does not: for every key `k` in the env hash reaching `PTY.spawn` in `Command#start` [1](#0-0) , `k ∈ {GITHUB_TOKEN, GIT_ASKPASS}` should imply `value(k) == base_env(k)` (the value injected by `Shipit::Commands#base_env`) regardless of any attacker-controlled `shipit.yml`. This does not hold.

Trace:
1. `Shipit::Commands#base_env` sets the trusted credentials: `'GITHUB_TOKEN' => github.token` and, when `Shipit.use_git_askpass?`, `'GIT_ASKPASS' => .../git-askpass` [2](#0-1) .
2. `TaskCommands#env` starts from `super` (this `base_env`), then merges `@stack.env`, then task metadata, then **`deploy_spec.machine_env`**, then `@task.env`, in that order — later merges win: [3](#0-2) .
3. `deploy_spec.machine_env` is `config('machine', 'environment') || {}` [4](#0-3) , and for `DeploySpec::FileSystem` this config is loaded from the shipit.yml file checked out in the stack's own working directory [5](#0-4) [6](#0-5) . Unlike `deploy_variables`/`rollback_variables`, which are explicitly sanitized through `EnvironmentVariables#permit` with a name allowlist [7](#0-6) [8](#0-7) , `machine_env` has **no such filter** — any key name is accepted verbatim.
4. For a `ReviewStack`, `branch` is set from the PR webhook payload to `params.pull_request.head.ref` — i.e., the attacker's own fork/branch — at stack-creation time: [9](#0-8) . The Task's working directory/checkout used by `DeploySpec::FileSystem` is that same branch's checkout (via `StackCommands#git_clone`/`TaskCommands#clone`/`#checkout`), so the `shipit.yml` read for `machine_env` is the attacker's own file, not one from a trusted/base branch.
5. `Command#unbundled_env` merges `BASE_ENV`, `PATH`, then `@env.stringify_keys` with no allowlist of permitted keys: [10](#0-9) . `Command#start` then calls `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` [11](#0-10) .

Attacker's exact action: open a pull request from a fork whose HEAD branch's `shipit.yml`/`.shipit/shipit.yml` contains:
```yaml
machine:
  environment:
    GITHUB_TOKEN: "attacker-value"
    GIT_ASKPASS: "/tmp/attacker-askpass"
```
Once the ReviewStack is provisioned/deployed (an automatic or one-click action depending on repository provisioning policy, not requiring any elevated GitHub role), `TaskCommands#env`'s merge order causes this attacker value to overwrite the trusted `GITHUB_TOKEN`/`GIT_ASKPASS` for every subsequent `git`/deploy `Command` built from that env (checkout, deploy steps, etc., since `@stack_commands`/`TaskCommands` reuse this merged env for git operations too, e.g. `checkout`, `clone`).

Why existing guards fail: `EnvironmentVariables#permit` is only invoked for `deploy_variables`/`rollback_variables` (user-facing "custom deploy variables"), never for `machine.environment` [4](#0-3) ; `filter_deploy_envs`/`filter_rollback_envs` are unrelated code paths. There is no repository/branch-trust check gating which `shipit.yml` is used to build `machine_env` for a ReviewStack — it is always the PR branch's own file by design (this is a documented, intentional feature: "machine.environment contains extra environment variables... during task execution"), but the implementation does not exclude reserved/sensitive keys like `GITHUB_TOKEN`/`GIT_ASKPASS` from that user-controlled namespace.

### Impact Explanation
An attacker who can only open a pull request (no Shipit session, no elevated GitHub role) can overwrite the `GITHUB_TOKEN` and `GIT_ASKPASS` environment variables used by every `git`/deploy `Command` run for their own ReviewStack's tasks. Because `PTY.spawn` executes on the Shipit deploy host with these environment variables, this is a credential-substitution/RCE-adjacent primitive: the attacker fully controls what value ends up in the process environment under a name that other deploy scripts and git helpers (`git-askpass`) rely on for authentication, and can point `GIT_ASKPASS` to an executable path they also control if writable, or otherwise disrupt/substitute the credential used by git operations for that stack. This matches the "Critical" category for exfiltration/substitution of `GITHUB_TOKEN` and unauthorized command execution reaching `PTY.spawn`. Blast radius is scoped to the attacker's own ReviewStack/task execution context (their fork's deploy environment) rather than other tenants' stacks, since `machine_env` is read from that stack's own checkout.

### Likelihood Explanation
Preconditions: the repository must have ReviewStacks enabled with a provisioning policy that allows PR-based stack creation (e.g., `allow_all` or `allow_with_label` where the attacker can self-apply the label, per the rules' attacker capabilities). No Shipit secrets, sessions, or GitHub App credentials are required. The attacker only needs to push a `shipit.yml` in their own PR branch and trigger a task (deploy/checkout) on the resulting ReviewStack — an action within their control as a PR author when continuous delivery/task triggers execute automatically for review stacks. This is low-cost and repeatable for any repository that enables ReviewStacks with an open provisioning policy.

### Recommendation
In `Shipit::DeploySpec#machine_env` (or where `TaskCommands#env` merges it), reject or filter out reserved/sensitive keys (`GITHUB_TOKEN`, `GIT_ASKPASS`, `GITHUB_DOMAIN`, and any other credential-bearing keys set by `Shipit::Commands#base_env`) before merging, or reorder the merge so `base_env`'s credentials are applied last and cannot be overridden by `deploy_spec.machine_env`/`@task.env`. Additionally consider routing `machine_env` through an explicit allowlist mechanism analogous to `EnvironmentVariables#permit` used for deploy/rollback variables.

### Proof of Concept
Minitest plan (`test/unit/task_commands_test.rb`-style, no live GitHub):
```ruby
test "#env does not allow shipit.yml machine.environment to override GITHUB_TOKEN/GIT_ASKPASS" do
  stack = shipit_stacks(:review_stack)
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  commands = Shipit::TaskCommands.new(task)
  commands.stubs(:deploy_spec).returns(
    stub(machine_env: { 'GITHUB_TOKEN' => 'attacker-value', 'GIT_ASKPASS' => '/tmp/evil' })
  )

  trusted_token = Shipit.github.token
  env = commands.env

  # Binding under test: env['GITHUB_TOKEN'] must equal the trusted base_env value, not the attacker's.
  assert_equal trusted_token, env['GITHUB_TOKEN'], "attacker-controlled shipit.yml overrode GITHUB_TOKEN"
  refute_equal 'attacker-value', env['GITHUB_TOKEN']
end
```
And directly on `Command`:
```ruby
test "Command#unbundled_env does not let arbitrary env override reserved keys" do
  command = Shipit::Command.new('true', chdir: Dir.tmpdir, env: { 'GITHUB_TOKEN' => 'attacker' })
  refute_equal 'attacker', command.unbundled_env['GITHUB_TOKEN']
end
```
As currently written, both assertions fail against the code in `lib/shipit/task_commands.rb` and `lib/shipit/command.rb`, confirming the vulnerability.
