### Title
Webhook organization used for signature verification is decoupled from the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against based on `repository.owner.login` (or `organization.login`) taken from the *unauthenticated JSON body*, while the event handlers that actually act on the payload (e.g. `PushHandler`, `PullRequest::*Handler`) resolve the target `Repository`/`Stack` from a *different* field of the same body: `repository.full_name`. Nothing enforces that the owner encoded in `full_name` matches `repository.owner.login`. In a multi-organization Shipit deployment (`docs/setup.md`, "Using Multiple Github Applications"), this lets a party who legitimately controls the webhook secret of Org A forge a signed payload whose `repository.owner.login` is "OrgA" (so it validates against OrgA's secret) but whose `repository.full_name` points at a repository belonging to OrgB, causing Shipit to sync/act on OrgB's repository using a signature that was never issued by OrgB.

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) 
selecting `github_app = Shipit.github(organization: repository_owner)` where [2](#0-1) 
`repository_owner` is read straight out of the untrusted JSON body (`params.dig('repository', 'owner', 'login')`). The HMAC signature is verified only against the secret configured for *that* organization key.

Separately, every webhook `Handler` resolves which `Repository`/`Stack` to mutate using a **different field of the same body**: [3](#0-2) 
`repository_name` comes from `payload.dig('repository', 'full_name')`, which is then matched via `Repository.from_github_repo_name` (owner/name split) to find the `Stack`, and e.g. `PushHandler#process` calls `stack.sync_github(...)`, enqueuing `GithubSyncJob` which fetches commits and mutates the `Stack`'s state using the GitHub API credentials for the repository's actual owner.

Because Shipit's multi-org configuration (`lib/shipit.rb#github`, `config/secrets.development.shopify.yml`, `docs/setup.md`) allows each organization to have its own independent `webhook_secret`, GitHub App, and installation, the equality that should hold is:

`organization whose secret validated the HMAC signature == organization that owns the repository the handler will act on`

In reality the code only enforces:

`repository.owner.login (used to pick the secret) == repository.owner.login (trivially itself)`

and never checks it against `repository.full_name` (used to pick the target repository). An attacker who controls (or knows) the webhook secret for one org configured on the same Shipit instance can therefore build a raw JSON body where `repository.owner.login` = "OrgA" (to select and pass verification with OrgA's secret) but `repository.full_name` = "OrgB/some-repo", sign it with OrgA's secret, and submit it to `/webhooks`. `verify_signature` passes (OrgA's secret matches), then the handler acts on `OrgB/some-repo` — a repository the attacker was never authorized to affect and for which no valid signature was ever produced by OrgB's GitHub App.

### Impact Explanation
This is a cross-organization/cross-repository write: an actor who is unprivileged with respect to Org B (no GitHub write access to OrgB's repos, no OrgB webhook secret) can forge webhook events that Shipit will treat as authentic for OrgB's stacks. Depending on handler, this can trigger `GithubSyncJob` (ingest arbitrary forged commit metadata into OrgB's stack, potentially unlocking/queueing deploys), `MembershipHandler` (create/delete arbitrary team memberships against OrgB's teams), or `PullRequest` handlers (create/close/label review stacks for OrgB repos), i.e. unauthorized cross-organization mutation of Shipit's deployment state — matching the "cross-repository writes" Critical-tier impact.

### Likelihood Explanation
This requires a Shipit instance configured with the multi-organization `github:` secrets schema (explicitly documented as a supported configuration) and requires the attacker to already control a webhook secret for at least one of the configured organizations — a low bar for an org admin who is not a Shipit or OrgB-privileged user, since webhook secrets are typically set by whoever administers that org's GitHub App, not by Shipit operators. No GitHub credentials, `ApiClient` token, or Shipit login are needed to exploit the mismatch itself; only knowledge of one org's HMAC secret and the ability to POST to the shared `/webhooks` endpoint.

### Recommendation
In `WebhooksController#verify_signature` / handler resolution, cross-validate that the organization used to select the verifying GitHub App (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` used by handlers to resolve the target `Stack`/`Repository` (and any `organization.login` fields used by `MembershipHandler`). Reject the webhook (422) if they diverge, and prefer deriving the target repository from the same field that was used to select the verifying secret.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`, "Using Multiple Github Applications").
2. Attacker knows `OrgA`'s `webhook_secret` (e.g. is the admin of OrgA's GitHub App) but has no access to `OrgB`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "OrgA")` and validates the signature successfully (it was signed with OrgA's real secret).
6. `Shipit::Webhooks::Handlers::PushHandler` resolves `repository_name` = `"OrgB/target-repo"`, finds the `Stack` belonging to OrgB, and enqueues `GithubSyncJob` for it — mutating OrgB's stack state based on a payload never authorized by OrgB. [4](#0-3) [3](#0-2) [5](#0-4)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
