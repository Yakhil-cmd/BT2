### Title
Legacy `pattern:` field silently fails to enforce `block` rules on `Write` tool calls, evading intended file-content blocking - ([File: plugins/hookify/core/config_loader.py])

### Summary
`Rule.from_dict` infers a hard-coded condition field of `new_text` for legacy `pattern:` rules with `event: file`, but `RuleEngine._extract_field` only resolves `new_text`/`new_string` from `tool_input['new_string']`, a key that exists for the `Edit` tool but not for `Write` (which uses `content`). As a result, any legacy-format `action: block` rule targeting `event: file` silently never matches `Write` tool calls, while the same protection expressed via explicit `conditions: [{field: content, ...}]` works correctly.

### Finding Description
`Rule.from_dict` in `plugins/hookify/core/config_loader.py` converts a simple `pattern:` field into a single condition, inferring the field name purely from `event`: [1](#0-0) 
For `event: file` it always picks `field = 'new_text'`, regardless of which file tool (`Write`, `Edit`, `MultiEdit`) will actually trigger the rule.

In `plugins/hookify/core/rule_engine.py`, `_extract_field` resolves this field per tool type: [2](#0-1) 
For `Write`/`Edit`, `field == 'content'` checks `tool_input.get('content') or tool_input.get('new_string', '')` (covering both tool shapes), but `field == 'new_text'`/`'new_string'` only checks `tool_input.get('new_string', '')`. The `Write` tool's `tool_input` only contains a `content` key, not `new_string`, so this lookup always returns `''` (not `None`) for `Write` calls. Since `_check_condition` only short-circuits on `None`, an empty string still proceeds to the regex/contains check, but an empty string can never match a non-empty dangerous pattern — the condition silently evaluates to `False` for every `Write` invocation.

Consequently, a legacy-style rule such as:
```
event: file
action: block
pattern: eval\(
```
which the plugin's own documentation presents as the simple/default rule format [3](#0-2) , will correctly block `Edit` operations but will never fire for `Write` operations (e.g., creation of a new malicious script file), because `RuleEngine.evaluate_rules` requires `_rule_matches` → all conditions match, and the sole inferred condition can never match on `Write`. [4](#0-3) 

The same protective intent expressed via the explicit/advanced format (`conditions: [{field: content, operator: regex_match, pattern: eval\(}]`) as shown in the README/skill examples [5](#0-4)  works correctly for both `Write` and `Edit`, because it uses `field: content` rather than the auto-inferred `new_text`.

This is exactly the invariant violation described: automatic default-field inference for the legacy format silently narrows enforcement scope compared to the explicit condition path, without any warning, error, or documentation of the discrepancy.

### Impact Explanation
A `/hookify rule creation` flow (or a repo-shipped `.claude/hookify.*.local.md` file) that uses the commonly-documented simple/legacy `pattern:` format with `event: file` and `action: block` to stop dangerous file content (e.g. blocking writes containing `eval(`, hard-coded secrets, malicious install scripts, etc.) provides a false sense of enforcement: it fully protects `Edit` calls but is a silent no-op for `Write` calls. Content that should have been blocked from being written to disk via `Write` will be allowed through unblocked. If that written content is subsequently executed (e.g., a written shell script later run via `Bash`, or a written config/hook file that is auto-loaded), this becomes a path to unauthorized local code/command execution that the user believed was covered by their block rule — i.e., the intended enforcement/approval-equivalent control (`permissionDecision: deny` in the PreToolUse hook) never engages for the vulnerable case. [6](#0-5) 

### Likelihood Explanation
High feasibility and fully reproducible: any rule author (the user's own `/hookify:create` flow, Claude-generated rule via `/hookify rule creation`, or a rule file shipped in a repository's `.claude/` directory) that follows the documented simple pattern format for `event: file` triggers this behavior deterministically — no timing, race, or privilege requirements. It requires no admin/maintainer access; it only requires that a `block`-intent rule for file events be authored in the simple/legacy format, which is presented in the plugin's own docs as the default/simplest way to write a rule [7](#0-6) .

### Recommendation
In `Rule.from_dict`, stop hard-coding `new_text` for `event: file`; instead infer `field = 'content'` (which `_extract_field` already resolves correctly for both `Write` and `Edit`/`MultiEdit`), or generate two conditions (`content` OR `new_text`) combined with OR semantics for legacy rules. Additionally, `_extract_field` should treat `new_text`/`new_string` the same as `content` (falling back to `tool_input.get('content')`) so the two code paths cannot diverge in matching behavior. Add a regression test asserting that a legacy `pattern:`/`event: file`/`action: block` rule blocks both `Write` and `Edit` tool_input shapes identically to an equivalent explicit `conditions` rule.

### Proof of Concept
Unit test to add to `plugins/hookify` tests (pseudo-code):
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

frontmatter = {
    "name": "block-eval",
    "enabled": True,
    "event": "file",
    "action": "block",
    "pattern": r"eval\(",
}
rule = Rule.from_dict(frontmatter, "Blocked eval() usage")
engine = RuleEngine()

# Write tool call containing the dangerous pattern
write_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Write",
    "tool_input": {"file_path": "malicious.js", "content": "eval('rm -rf /')"},
}
result = engine.evaluate_rules([rule], write_input)
# BUG: expected permissionDecision == "deny", actual result == {} (rule never matches)
assert result == {}, "demonstrates block rule is bypassed for Write tool"

# Edit tool call with the same dangerous content
edit_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Edit",
    "tool_input": {"file_path": "malicious.js", "old_string": "x", "new_string": "eval('rm -rf /')"},
}
result2 = engine.evaluate_rules([rule], edit_input)
assert result2["hookSpecificOutput"]["permissionDecision"] == "deny"  # works correctly here
```
This demonstrates the differential: identical malicious content is blocked via `Edit` but silently allowed via `Write`, confirming the default field-inference weakens enforcement relative to the explicit-condition path.

```python
    def _rule_matches(self, rule: Rule, input_data: Dict[str, Any]) -> bool:
        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        # Check tool matcher if specified
        if rule.tool_matcher:
            if not self._matches_tool(rule.tool_matcher, tool_name):
                return False

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True
```
