### Title
`StatusHandler#process` writes CI status onto any commit sharing a SHA, across stacks/repositories, unscoped by repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) purely by `Commit.where(sha: params.sha)`, with no filter tying the write back to the repository that authenticated the webhook. If a victim stack's commit table contains a commit with the same SHA as one the attacker can trigger a genuine, signed `status` webhook for (e.g. a shared/forked commit), the attacker's status update is applied to the victim's commit and can flip the victim stack's deployable/blocking state. Separately, `OpenedHandler#provision?` / `ReopenedHandler#unarchive?` contain a Ruby operator-precedence bug that can provision/unarchive a review stack even when `review_stacks_enabled` is `false`, but this is not required for the `StatusHandler` cross-repo write — that bug is independent of `review_stacks_enabled`.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `commit.stack.github_repo_name == webhook.repository.full_name` for every `commit` mutated by `StatusHandler#process`. In reality: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never checks `params.repository` (not even required in the handler's `params` schema) against `commit.stack.github_repo_name`. Any `Commit` row anywhere in the database with a matching `sha` gets a new `Status` record via `create_status_from_github!` → `add_status`, which can flip `deployable_status`/`commit_status` hooks and calls `stack.schedule_merges` on `pending`/`success` transitions. [2](#0-1) [3](#0-2) 

`Webhooks::Handlers::Handler` invokes handlers per event globally; the controller only checks the HMAC signature against the org named in the *incoming* payload's `repository.owner.login`, not against the specific repository the target commit's stack belongs to: [4](#0-3) 

So signature verification proves "this payload came from GitHub for organization X," not "this SHA belongs to a commit that lives in a stack under organization X's repo." Two different Shipit-tracked repositories (e.g. a fork and its upstream, or two forks of the same base) can legitimately contain identical commit SHAs (git SHA1 is content-addressed and identical trees/parents produce identical SHAs), so an attacker who owns or controls any repository that is onboarded into a Shipit-configured GitHub organization can send a real, correctly-signed `status` event for a SHA that also exists on a victim stack, and that event will mutate the victim's `Commit`/`Status` rows and can trigger `stack.schedule_merges` / change `deployable?`.

Regarding the "review_stacks_enabled false" precedent bug referenced in the question: it does exist as a genuine defect in `OpenedHandler#provision?` and `ReopenedHandler#unarchive?`/similar predicates, e.g.: [5](#0-4) 

Due to Ruby `&&`/`||` precedence, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`, so a repo with `review_stacks_enabled = false` but `provisioning_behavior = allow_with_label` and a labeled PR will still provision/unarchive a stack. This is a real bug, but it is orthogonal to `StatusHandler`: the cross-repo status-write vulnerability does not require review stacks to be involved at all — it fires against any pre-existing `Commit` row regardless of how the owning stack was created. The question's framing conflates the two; only the `StatusHandler` scoping gap is load-bearing for the "status flips CI state on the wrong stack" claim.

No existing guard prevents this: `verify_signature` only authenticates the org of the sender, not the target repository of every commit matched by SHA; `ExplicitParameters` on `StatusHandler` only requires `sha`/`state` and doesn't cross-check `repository`; there is no `require_permission!`/stack-scoping check inside `StatusHandler#process` at all.

### Impact Explanation
A `status` webhook authenticated for repository/organization A can write a `Status` row against a `Commit` that belongs to a `Stack` under repository B, provided both repos happen to share that SHA (common with forks/shared history). This can: flip `commit.status`/`deployable?` (via `Status::Group`), trigger `Hook.emit(:deployable_status, ...)`, and call `stack.schedule_merges`, i.e. cause an unauthorized deploy/merge decision on a stack the attacker never authenticated against. This matches the "payload for one repository mutating another's stack/commit" Critical class in the rubric.

### Likelihood Explanation
Requires: (1) attacker has push/webhook-emitting rights on a repository already onboarded to a Shipit-configured GitHub organization (so `verify_signature` succeeds), and (2) a SHA collision — i.e., a commit that is content-identical (same tree/parents/author/committer/timestamps/message) between attacker's repo and the victim stack's repo, most plausible with forks sharing early history or common upstream commits. This is a real but non-trivial precondition (needs a coincidentally/deliberately shared commit, not an arbitrary chosen SHA), and depends on Shipit's org/app configuration allowing the attacker's repo through signature verification. It is repeatable per shared SHA and does not require any secret beyond what GitHub itself issues for legitimate webhook delivery.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository that authenticated the webhook, e.g. join through `stack` and filter `stack.repository.github_repo_name == params.repository.full_name` (require `repository.full_name` in the `params` schema), instead of a bare `Commit.where(sha: params.sha)`. Additionally fix the operator-precedence bugs in `OpenedHandler#provision?`, `ReopenedHandler#unarchive?`, and related predicates by adding explicit parentheses so `review_stacks_enabled` gates every branch: `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — not present today):
```ruby
test "status for one repo's sha must not mutate a commit belonging to another stack" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine"
  shared_sha = "abc123deadbeef"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)

  # attacker's payload authenticates for a DIFFERENT repository
  params = { sha: shared_sha, state: "success", context: "ci/e2e",
             repository: { full_name: "attacker/unrelated-repo" } }

  assert_equal victim_commit.stack.github_repo_name, "shopify/shipit-engine"
  refute_equal victim_commit.stack.github_repo_name, params[:repository][:full_name]

  assert_no_difference "victim_commit.statuses.count" do
    Shipit::Webhooks::Handlers::StatusHandler.new(params).process
  end
end
```
Before the fix, this assertion fails: `victim_commit.statuses.count` increases even though `params[:repository][:full_name]` never equals `victim_commit.stack.github_repo_name`, proving the write crosses the repository boundary.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
