Based on the exchange rate / commission recalculation bug in `OperationalStaking.sol` — where a *rate* is changed but a previously accumulated aggregate is combined with the *new* rate instead of the rate that produced it — the closest reachable analog in `ocore--021` is the `tps_fee` accounting mechanism in `storage.js`, which distributes/reads a per-address running balance (`tps_fees_balance`) using a *per-unit* commission-style share (`earned_headers_commission_share` / `getTpsFeeRecipients`) that can differ from unit to unit.

### Title
TPS-fee balance normalized by the wrong (unit-specific) commission share, causing under/over-estimation of the required `tps_fee` - ([File: storage.js])

### Summary
`tps_fees_balance` is a single running balance per address, but the “share” used both to **credit** it (`updateTpsFees`) and to **read/normalize** it back (`getPaidTpsFee`) is taken from `earned_headers_commission_recipients` of *whichever unit is currently being processed*, not from the historical mix of shares that actually produced the accumulated balance.

### Finding Description
`updateTpsFees` computes, for each stabilized unit, a `total_tps_fees_delta` and splits it among the unit's own recipients according to that unit's own `share` (derived from `assocEarnedHeadersCommissionRecipients`), then adds the per-recipient portion to the address's single, address-wide `tps_fees_balance`: [1](#0-0) 

Because `tps_fees_balance` is keyed only by `(address, mci)` and not by which unit/share produced the contribution, it becomes a mixture of deltas computed under potentially different `share` values across different multi-authored units (e.g., an address might be a 100%-share sole author in one unit and a 30%-share co-author in another).

Later, when a *new* unit is validated, `getPaidTpsFee` reads this same mixed balance and "un-splits" it by dividing by the **current unit's own share** to estimate what fee level it represents: [2](#0-1) 

This mirrors the Sherlock finding's structure exactly: an aggregate (`tps_fees_balance`, analogous to `totalShares`) that was built up using historical, possibly-differing per-unit shares is later recombined using only the *current* transaction's share (analogous to the new `commissionRate`), rather than the share(s) that actually generated each portion of the balance.

The recipient/share mapping is computed the same way in both directions via `getTpsFeeRecipients`, and shares are attacker-controlled per unit through `earned_headers_commission_recipients`, which any multi-authored unit poster can set (validated only for internal consistency, sum=100, sorted) in `validateHeadersCommissionRecipients`: [3](#0-2) 

### Impact Explanation
An attacker who controls a sequence of multi-authored units naming the same address as a recipient with varying `earned_headers_commission_share` values can cause the address's `tps_fees_balance` to be a mix of contributions computed at different shares. By subsequently posting a unit with a favorable share, `getPaidTpsFee` divides the mixed balance by that share and can compute an inflated allowed `tps_fee` credit, letting the attacker under-pay the required `tps_fee` for their unit (`getCurrentTpsFeeToPay`/`getPaidTpsFee` checks feed the TPS-fee-based anti-spam/pricing mechanism used for admission of new units, part of the v4 upgrade). Under-collection of TPS fees weakens the network's ability to price/limit unit throughput — the DAG's core spam/fee-based confirmation mechanism — potentially enabling a poster to push units through without paying the fee the protocol expects, or, in the opposite direction, causing legitimate balances to be under-counted and valid low-fee units to be wrongly rejected.

### Likelihood Explanation
Reachable by any ordinary unit poster who can author multi-author units and set `earned_headers_commission_recipients`/shares (no privileged role required); the code path is exercised for every stable unit after `constants.v4UpgradeMci` via `updateTpsFees`, and on every new-unit validation via `getPaidTpsFee`/`getCurrentTpsFeeToPay`. However, exploitation requires deliberately engineering a sequence of units with specific share splits to skew the address's balance, which raises the practical bar (multiple coordinated units needed) — hence Medium rather than High confidence in real-world exploitability without further modeling of `getTpsFeeRecipients`'s exact semantics, which I was not able to fully inspect due to tool-call limits.

### Recommendation
Track `tps_fees_balance` contributions per `(address, share-context)` or normalize deltas to a share-independent unit before crediting the shared balance (e.g., store `total_tps_fees_delta` un-split, or store per-unit/per-share ledger entries) so that reading the balance back never depends on which unit's share happens to be used at read time. Alternatively, disallow reusing shares from the current unit to interpret historical balance and instead persist the effective 100%-equivalent amount at write time.

### Proof of Concept
1. Address `A` co-authors unit `U1` with `earned_headers_commission_share = 100` (sole recipient) — `updateTpsFees` credits `A`'s `tps_fees_balance` with the full `total_tps_fees_delta` for `U1`.
2. Address `A` later co-authors unit `U2` with another address, `earned_headers_commission_share = 10` for `A` — `updateTpsFees` credits only 10% of `U2`'s delta to the same shared balance bucket for `A`, mixing with the balance from step 1.
3. `A` posts a new unit `U3` naming itself with `share = 10` again; `getPaidTpsFee` divides the *mixed* `tps_fees_balance` by `0.10`, inflating the computed allowed fee credit far beyond what was actually earned at that ratio, letting `U3` be validated with an insufficient declared `tps_fee`. async function getPaidTpsFee(conn, unit) {
	if (unit === constants.GENESIS_UNIT)
		return 0;
	let objUnitProps = assocUnstableUnits[unit] || assocStableUnits[unit];
	if (!objUnitProps) {
		const objJoint = await readJoint(conn, unit);
		const objUnit = objJoint.unit;
		objUnitProps = {
			unit,
			author_addresses: objUnit.authors.map(a => a.address),
			assocEarnedHeadersCommissionRecipients: ehcr2assoc(objUnit.earned_headers_commission_recipients),
			tps_fee: objUnit.tps_fee || 0,
			last_ball_unit: objUnit.last_ball_unit,
		};
	}
	if (!("tps_fee" in objUnitProps))
		throw Error(`no tps_fee in props`);
	const objLastBallUnitProps = await readUnitProps(conn, objUnitProps.last_ball_unit);
	const last_ball_mci = objLastBallUnitProps.main_chain_index;
	const recipients = getTpsFeeRecipients(objUnitProps.assocEarnedHeadersCommissionRecipients, objUnitProps.author_addresses);
	let min_tps_fee = Infinity;
	for (let address in recipients) {
		const share = recipients[address] / 100;
		const [row] = await conn.query("SELECT tps_fees_balance FROM tps_fees_balances WHERE address=? AND mci<=? ORDER BY mci DESC LIMIT 1", [address, last_ball_mci]);
		const tps_fees_balance = row ? row.tps_fees_balance : 0;
		const tps_fee = tps_fees_balance / share + objUnitProps.tps_fee;
		if (tps_fee < min_tps_fee)
			min_tps_fee = tps_fee;
	}
	return min_tps_fee;
}

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
