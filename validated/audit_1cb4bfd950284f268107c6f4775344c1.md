### Title
Skill update re-fetches from previously-trusted `github-repo` coordinates without re-showing the untrusted-source disclaimer or re-verifying repository identity - ([File: pkg/cmd/skills/update/update.go])

### Summary
`gh skill install` requires the user to accept an explicit "not verified by GitHub" disclaimer before it will download and install a third-party skill (`printPreInstallDisclaimer`) [1](#0-0) . This one-time consent is recorded implicitly as metadata (`github-repo`, `github-tree-sha`, `github-path`) embedded in the installed `SKILL.md` frontmatter [2](#0-1) . `gh skill update` subsequently re-fetches content from that same recorded `owner/repo` coordinate indefinitely, on every future invocation, without ever re-displaying the disclaimer or re-confirming that the user still trusts that specific source.

### Finding Description
When a skill is installed remotely, `install.go` shows the "not verified by GitHub"/"malicious" disclaimer once as part of the initial approval flow [3](#0-2) . That trust decision is persisted only as plain metadata inside the skill file (`github-repo`, `github-tree-sha`, `github-path`), not as a scoped, re-checked authorization.

`updateRun` in `update.go` scans installed skills, groups them by `repoKey{host, owner, repo}` taken directly from this stored metadata, and calls `discovery.ResolveRef`/`discovery.DiscoverSkills` against that owner/repo to fetch new content [4](#0-3) . The only user-facing gate before applying updates is a generic confirmation ("Update N skill(s)?") that does not mention the source repository, its owner, or repeat the untrusted-source warning [5](#0-4) . Unlike `install.go`, `update.go` contains no call to the disclaimer-printing logic (`grep_search` for `printPreInstallDisclaimer`/"not verified by GitHub" only matched files under `pkg/cmd/skills/install/`, not `update/`).

This mirrors the structure of the NFT bug class: an approval/trust decision made for one state of an asset (initial repo content, accepted once via disclaimer) is not re-validated or re-confirmed when the underlying resource is fetched again later. If the `owner/repo` referenced in a skill's stored metadata later comes under different, malicious control (e.g., the original repository is deleted and the name is reclaimed by a different party, or a maintainer's account/repo is compromised), `gh skill update --all` (or interactive update) will silently pull and install that new, unverified content into the user's/agent's skill directory using the previously-established trust, without the user ever being shown the original disclaimer or a warning that the "verified" source's identity may have changed.

### Impact Explanation
Skills are consumed by AI coding agents (Copilot, Claude, etc.) and are explicitly called out by `gh`'s own disclaimer as a prompt-injection/malicious-content risk [6](#0-5) . Because `gh skill update` re-trusts the stored `owner/repo` coordinate indefinitely and never re-surfaces that warning, a takeover of the referenced repository (or account) lets an attacker deliver malicious `SKILL.md` content to any user who runs `gh skill update`, which is then fed directly into an agent's instruction/context surface. This is a supply-chain-style repeat-compromise path analogous to repeatedly draining an NFT via a stale approval whenever the underlying asset re-enters the vault.

### Likelihood Explanation
Requires an attacker to gain control of a `owner/repo` name that a victim has previously installed a skill from and left tracked for updates (e.g., via GitHub's repository-name-reuse-after-deletion behavior, or compromising the original maintainer's repo/account) — a remote, unprivileged, attacker-controlled-host scenario reachable through normal `gh skill update` usage, requiring no local access or MITM.

### Recommendation
Re-display the same untrusted-source disclaimer (and/or require explicit re-confirmation naming the exact owner/repo/tree-SHA) whenever `gh skill update` is about to fetch and overwrite a skill from a remote source, not just at initial install. Consider additionally recording and verifying repository identity (e.g., GitHub numeric repo ID rather than only owner/repo name) so that a repo-name reuse or ownership change is detected and surfaced to the user before silently trusting the new content.

### Proof of Concept
Not applicable as concrete exploit code — this is a design/logic gap identified by comparing `install.go`'s disclaimer flow to `update.go`'s silent re-fetch flow. Full confirmation of exploitability (e.g., exact GitHub repo-reuse mechanics, whether `github-tree-sha` pinning mitigates unpinned skills) would require running `gh skill install` then `gh skill update` end-to-end in a live environment, which is outside the scope of static code review here.
