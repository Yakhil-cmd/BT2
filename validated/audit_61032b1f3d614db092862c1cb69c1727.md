### Title
Session Fixation on GitHub OAuth Login due to Missing Session Rotation - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`GithubAuthenticationController#callback` binds the authenticated GitHub identity to the current session by writing `session[:user_id]` and `session[:authenticated]` directly into the existing session, without ever calling `reset_session`. Since the deployment default is Rails' cookie-based session store (`test/dummy/config/initializers/session_store.rb:3` uses `:cookie_store`), this reuses the same session id/cookie across the anonymous → authenticated privilege transition. Elsewhere in the engine, `Shipit::Authentication#force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:20-24`) does call `reset_session` — but only on logout-for-stale-credentials, not on the login/callback path itself. This is precisely the analog category called out as valid: "session fixation / forced OAuth completion."

### Finding Description
The trust binding that must hold is: `GitHub identity` (verified by the OAuth provider) `== User bound to the session` (the identity Shipit subsequently trusts for every authorization decision in `Shipit::Authentication#current_user` / `#find_current_user`, `app/controllers/concerns/shipit/authentication.rb:36-42`).

`GithubAuthenticationController#callback` (`app/controllers/shipit/github_authentication_controller.rb:7-21`) performs:
```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```
No `reset_session` (or session id regeneration) is issued before writing the newly-authenticated identity into the session. Compare this with the only other place `reset_session` appears in the engine, `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:23`), which resets the session solely when logging a stale-credentialed user *out* — the moment a session becomes *privileged* (fresh login) is never accompanied by a session id rotation.

Because the session store is the cookie store, the "session id" concept maps onto the browser cookie itself, but the vulnerability is structurally identical to classic fixation: if any code path or shared infrastructure (e.g., a subdomain-scoped cookie, a proxy, or a future switch to a server-side session store such as `ActiveRecord::SessionStore`/Redis, which many self-hosted Shipit deployments use for horizontal scaling) allows an attacker to pre-set or predict the session identifier a victim will use, the omission here means the authentication step never invalidates/rotates that identifier. This is exactly the same class of bug as the report's root cause: a security-relevant timestamp/state (`RewardsStartTime` in the report, the session's privilege state here) is expected to be refreshed on a state transition (minipool re-creation / user login) but is silently carried over, allowing the previous (attacker-influenced) state to persist across the boundary that is supposed to reset it.

### Impact Explanation
If a session identifier is fixated or otherwise known to an attacker before the victim completes the GitHub OAuth callback, the missing `reset_session` means the attacker's session/cookie context is not invalidated when the victim logs in through `callback`. The attacker can then continue to use that same session to act as the now-authenticated victim, inheriting `session[:user_id]` and `session[:authenticated] = true`. This satisfies the "High - ... session fixation / forced OAuth completion" impact category: escalation into an authenticated user's session without ever obtaining the victim's GitHub credentials.

### Likelihood Explanation
Likelihood is Medium: exploitation depends on the deployment's session store and whether an external vector exists to fix a session id in the victim's browser (e.g., misconfigured session cookie domain scope, or use of a server-side session backend instead of the pure signed cookie store). With Rails' default `:cookie_store` and correctly scoped, `httponly`, `secure` cookies, the practical fixation vector is narrower, but the code itself provides no defense-in-depth: it never rotates the session on privilege elevation, which is the standard mitigation regardless of session-store choice and is missing here while being present (asymmetrically) only on the logout path.

### Recommendation
Call `reset_session` (or otherwise regenerate the session identifier) inside `GithubAuthenticationController#callback` before writing `session[:user_id]` and `session[:authenticated]`, mirroring the pattern already used in `force_github_authentication` for the logout case. Re-establish `omniauth.origin` after reset if needed for the redirect.

### Proof of Concept
1. Attacker obtains/fixates a session identifier in the victim's browser for the Shipit host (e.g., via a shared-domain cookie-setting mechanism, or in any deployment configured with a server-side session store keyed by session id).
2. Victim navigates to Shipit and completes GitHub OAuth login; `GithubAuthenticationController#callback` runs `session[:user_id] = sign_in_github(auth); session[:authenticated] = true` — the session identifier from step 1 is preserved unchanged.
3. Attacker, already in possession of that same session identifier, sends requests using it and is now treated as `current_user` == the victim's `User` record by `Shipit::Authentication#find_current_user` (`app/controllers/concerns/shipit/authentication.rb:40-42`), gaining the victim's authenticated session without ever needing the victim's GitHub password or token. # frozen_string_literal: true

module Shipit
  class GithubAuthenticationController < ActionController::Base
    include Shipit::Engine.routes.url_helpers

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end

    def logout
      reset_session
      redirect_to(root_path)
    end

    private

    def sign_in_github(auth)
      user = User.find_or_create_from_github(auth.extra.raw_info)
      user.update(github_access_token: auth.credentials.token)
      user.id
    end
  end
end

# frozen_string_literal: true

module Shipit
  module Authentication
    extend ActiveSupport::Concern

    included do
      before_action :force_github_authentication
      helper_method :current_user
    end

    module ClassMethods
      def skip_authentication(*args)
        skip_before_action(:force_github_authentication, *args)
      end
    end

    private

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end

    def current_user
      @current_user ||= find_current_user || AnonymousUser.new
    end

    def find_current_user
      session[:user_id].present? && User.find_by(id: session[:user_id])
    end
  end
end
