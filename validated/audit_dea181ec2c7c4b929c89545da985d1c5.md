### Title
Missing `return` after caught hash exception causes duplicate/undefined-key processing of private payment chains - ([File: network.js])

### Summary
In `handleSavedPrivatePayments`'s inner `validateAndSave` function, a `try { ... } catch (e) { ... }` block around the hash computation used to key/validate an incoming private-payment chain does not `return` on failure, so control flow falls through to code that uses the (unset) hash result and re-invokes the validation/save pipeline that was already short-circuited in the catch branch.

### Finding Description
`objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` — which internally calls `string_utils.getJsonSourceString` — can throw for attacker-supplied payloads (e.g. objects containing `null`, non-finite numbers, empty arrays/objects without `bAllowEmpty` semantics being met, or unsupported types), because `getJsonSourceString` explicitly throws `Error` in these cases. [1](#0-0) 

The caller wraps this call in try/catch, but on exception it only logs, optionally sends an error to the peer, and calls `deleteHandledPrivateChain(..., cb)` — **without returning**: [2](#0-1) 

Execution then continues past the catch block to compute `key` using the now-`undefined` `json_payload_hash`, and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose `ifOk`/`ifError`/`ifWaitingForChain` callbacks each also call `deleteHandledPrivateChain(..., cb)` or `cb()` directly: [3](#0-2) 

This mirrors the CVE's bug class: an internal function's failure/error state is not properly checked/propagated (no `return` after the catch), so the code proceeds to use partially-computed/stale data (`undefined` `json_payload_hash`) and to execute a second, redundant code path (a duplicate call into the DB-connection-driven validation/save pipeline and duplicate invocation of `cb` inside `async.each`), producing unpredictable control flow rather than a clean, single-path failure.

### Impact Explanation
`cb` (the `async.each` iteratee callback) can be invoked twice for the same row — once from `deleteHandledPrivateChain` in the catch branch, and again from whichever callback (`ifOk`/`ifError`/`ifWaitingForChain`) fires inside `privatePayment.validateAndSavePrivatePaymentChain`, which itself opens its own DB transaction (`BEGIN`/`COMMIT`/`ROLLBACK`) concurrently with the `deleteHandledPrivateChain` DELETE query on the same row. Depending on interleaving and driver behavior (`async.each` double-callback, overlapping transactions on the same `unhandled_private_payments` row), this can corrupt the async control flow of the private-payment intake queue and produce inconsistent bookkeeping of processed private payment chains (e.g. records deleted/inserted out of order, or the `all_private_payments_handled` completion event firing with incorrect state). This is a correctness/control-flow bug in the private-payment intake pipeline reachable by any private-payment counterparty who can trigger `getJsonSourceString` to throw for a crafted payload.

### Likelihood Explanation
The path is reachable from an untrusted private-payment counterparty: private payment chains received over the wire are stored in `unhandled_private_payments` and later processed by `handleSavedPrivatePayments`, which is exactly where this code lives. However, `getBase64Hash`/`getJsonSourceString` throwing on the payload requires the payload to already contain `null`/non-finite/empty-without-allow values — most such payloads would likely already be rejected earlier by JSON-schema-style validation in `handlePrivatePaymentChains` (`wallet.js`) or `validatePrivatePayment`/`initPrivatePaymentValidationState`. I was not able to fully verify, within the available context, whether any code path allows a payload to reach `handleSavedPrivatePayments` bypassing those earlier checks while still causing `getJsonSourceString` to throw (e.g. via `output_index`/`denomination`/array fields with `NaN`, or fields with `-0`/non-finite floats not otherwise rejected). This uncertainty means the concrete exploitability (versus purely defensive/dead code) could not be conclusively confirmed with the tools available.

### Recommendation
Add a `return` (or restructure to an `if/else`) after the catch block so that on hash-computation failure the function exits immediately without falling through to compute `key` from an undefined value or to re-invoke `privatePayment.validateAndSavePrivatePaymentChain`, which duplicates `deleteHandledPrivateChain`/`cb` invocation:
```js
try {
    var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
}
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```

### Proof of Concept
Not independently reproduced with the available tools. Conceptually: a peer sends (or a stored `unhandled_private_payments` row contains) a private-payment chain whose head element's `payload` includes a value that causes `string_utils.getJsonSourceString` to throw (e.g. a nested `null`, a non-finite number, or an empty array/object where `bAllowEmpty` is not honored for this call — `getBase64Hash(payload, true)` passes `bJsonBased=true` but `bAllowEmpty` is not passed, so an empty array/object anywhere in `payload` throws). When `handleSavedPrivatePayments` next runs and processes this row, `getBase64Hash` throws, the catch branch fires `deleteHandledPrivateChain(...,cb)`, and then the same function continues to build `key` with `json_payload_hash === undefined` and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose callback also calls `cb`/`deleteHandledPrivateChain` a second time — producing a double callback into `async.each` and overlapping DB operations on the same row.

function getJsonSourceString(obj, bAllowEmpty) {
	let cache = new WeakMap();  // object to stringified result
	function stringify(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				return toWellFormedJsonStringify(variable);
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
			case "boolean":
				return variable.toString();
			case "object":
				// return cached result if already processed
				if (cache.has(variable))
					return cache.get(variable);
				let result;
				if (Array.isArray(variable)){
					if (variable.length === 0 && !bAllowEmpty)
						throw Error("empty array in "+JSON.stringify(obj));
					result = '[' + variable.map(stringify).join(',') + ']';
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0 && !bAllowEmpty)
						throw Error("empty object in "+JSON.stringify(obj));
					result = '{' + keys.map(function(key){ return toWellFormedJsonStringify(key)+':'+stringify(variable[key]) }).join(',') + '}';
				}
				cache.set(variable, result);  // memoize for future references
				return result;
			default:
				throw Error("getJsonSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}
