### Title
Cross-repository status forgery reaches `Commit#schedule_continuous_delivery` via unscoped SHA lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by SHA alone with `Commit.where(sha: params.sha)`, with no constraint tying the match to the repository that actually sent the webhook. Because `sha` is a globally shared, content-derived value across the entire `commits` table (one table shared by all stacks/tenants), a correctly-signed `status` webhook originating from repository B can create a `Status` on a commit that belongs to stack A, which then fires `Commit#schedule_continuous_delivery` and enqueues `Shipit::ContinuousDeliveryJob` for stack A.

### Finding Description
The binding that should hold is: `payload['repository']['full_name'] == commit.stack.repository.full_name` for every `Status` created from a webhook. This binding is never checked.

Code path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, i.e. the GitHub App/webhook secret bound to the *organization* derived from the payload, not the specific repository. This proves the request came from GitHub for "some repo in that org/app installation," it does not prove the SHA in the payload belongs to the stack being mutated.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
There is no `stack_id`, `repository_id`, or `github_repo_name` filter — every `Commit` row across every `Stack` in the installation with a matching `sha` is updated, regardless of which repository the webhook came from. The `branches` field is accepted by the `ExplicitParameters` schema but is never read or enforced in `process`, so it provides no protection either.
3. `Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:24-33`) creates the `Status` scoped to the *commit's own real* `stack_id` — meaning the forged status lands on stack A's commit, not some attacker-controlled stack.
4. `Status` has `after_commit :schedule_continuous_delivery ... on: :create` (`app/models/shipit/status.rb:19,42-44`), which calls `commit.schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`):
```ruby
def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
```
If stack A has `continuous_deployment?` enabled and is otherwise deployable, `ContinuousDeliveryJob.perform_later(stack)` is enqueued for stack A — triggered entirely by a webhook about repository B.

Exploit flow: an attacker who has write/API access to some repository B (which they own, and which is under an org/GitHub App installation already configured in Shipit) obtains the exact git commit object of an already-merged commit in repository A (trivial if that commit is public, since a git SHA is a content hash, not a GitHub-issued signature) and pushes that identical commit object into repository B. The attacker then uses GitHub's real Commit Status API against repository B for that SHA (`POST /repos/B/commits/{sha}/statuses`, permitted since they own B). GitHub itself computes and signs the resulting `status` webhook with the correctly configured secret and delivers it to Shipit. `verify_signature` passes because the signature is genuinely valid for org B/the shared GitHub App. `StatusHandler#process` then matches stack A's pre-existing commit row purely by SHA and creates a `Status` on it, cascading into `schedule_continuous_delivery` for stack A.

None of the listed guards catch this: `verify_signature` only authenticates "an org configured in Shipit sent this," not "this SHA belongs to this repository"; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape; `force_github_authentication`, `User#authorized?`, `require_permission!` and the `stacks` scope are session/API-token controls irrelevant to unauthenticated webhook ingestion; model validations on `Repository`/`Stack` do not constrain cross-stack `Commit` lookups.

### Impact Explanation
An attacker with no relationship to repository/stack A can cause Shipit to record a status for stack A's commit and, if stack A has continuous deployment enabled, cause an unauthorized `Shipit::ContinuousDeliveryJob` to be enqueued and (subject to `stack.deployable?`/occupancy checks) an unauthorized deploy of tenant A's already-merged commit — a payload for one repository mutating another tenant's stack/commit/deploy pipeline. This is repeatable against any stack whose commit SHA the attacker can reproduce and matches the Critical category ("a payload for one repository mutating another's stack, commit, task ... or an unauthorized deploy").

### Likelihood Explanation
Preconditions: the attacker needs (a) push/API access to some repository B that is part of an org/installation Shipit already trusts for webhook signing (plausible in any multi-repo/org-wide Shipit deployment, which is the documented common configuration), and (b) the ability to reproduce the exact git commit object (tree+parents+metadata) of an already-existing commit in stack A's repository, which is straightforward for any commit that was ever publicly fetchable. No Shipit session, API token, or secret is required. The attack is repeatable per target stack/commit and costs only a `git push` plus one GitHub Status API call against the attacker's own repository.

### Recommendation
In `StatusHandler#process`, constrain the `Commit` lookup by the reporting repository, e.g. join through `stack` and filter on `stack.repository.full_name == params.name` (or the equivalent repository identifier in the payload) before applying the status, rather than matching on `sha` alone across all tenants. Apply the same repository-scoping fix to `CheckRunHandler`/other handlers that key off `sha` if they have the same pattern.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status for same SHA from a different repository must not trigger CD on stack A" do
  stack_a = shipit_stacks(:shipit)
  stack_a.update!(continuous_deployment: true)
  Shipit::Stack.any_instance.stubs(:continuous_deployment?).returns(true)
  Shipit::Stack.any_instance.stubs(:deployable?).returns(true)
  Shipit::Commit.any_instance.stubs(:deployable?).returns(true)

  commit_a = stack_a.commits.last # SHA belongs to repo A, never touched by attacker

  ContinuousDeliveryJob.expects(:perform_later).with(stack_a).never # binding: repo B payload must not affect stack A

  # forged/legit-signed payload claiming to come from repository B, but reusing commit_a.sha
  params = {
    'sha' => commit_a.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'name' => 'attacker/repo-b', # different repository than stack_a's
  }

  Shipit::Webhooks::Handlers::StatusHandler.new(params).process

  # After the fix: no Status should be created on commit_a, and CD must not fire.
  assert_equal 0, commit_a.reload.statuses.where(context: 'ci/attacker').count
end
```
Currently (pre-fix), this test fails: `Commit.where(sha: params.sha)` matches `commit_a` regardless of the `name`/repository field, a `Status` is created on stack A's commit, and `ContinuousDeliveryJob.perform_later(stack_a)` is enqueued, demonstrating the broken binding.
