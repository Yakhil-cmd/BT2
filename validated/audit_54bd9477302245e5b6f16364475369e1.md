### Title
Cross-organization webhook forgery via mismatched signature-verification org and event-processing repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This finding maps the report's root cause — "ticket IDs and address keys are not authenticated against a particular user ID/access token" — onto Shipit's multi-organization GitHub App webhook path. The controller verifies the HMAC signature using one attacker-influenced field (`repository.owner.login`) to pick which organization's `webhook_secret` to check against, while the event handlers that actually act on the payload key off a *different* field (`repository.full_name`). These two fields are never cross-validated against each other, so an attacker who legitimately controls a GitHub App/org configured in Shipit (and thus its `webhook_secret`) can forge a signature that validates for their own org while pointing the payload's `repository.full_name` at a stack belonging to a different, victim organization also configured in the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the signing secret to check against using `repository_owner`, which is read directly from the unauthenticated JSON body before any signature check occurs: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the per-organization config (and thus `webhook_secret`) purely by that string, with no binding to the rest of the payload: [3](#0-2) 

However, the event handlers invoked by `WebhooksController#create` resolve which `Stack`/`Repository` to act on using a *different* payload field, `repository.full_name`, via `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks`: [4](#0-3) 

and `Repository.from_github_repo_name` simply splits that string on `/` with no relation to `repository.owner.login`: [5](#0-4) 

Because `repository_owner` (used to select the verification secret) and `repository.full_name` (used to select the target repository/stack) are two independent, attacker-controlled JSON fields with no cross-check that `full_name` actually starts with `repository_owner`, a Shipit deployment configured with multiple GitHub organizations (as documented in `config/secrets.development.shopify.yml`) breaks the intended binding: `{organization whose secret authenticated the request} == {repository the event handlers act on}`.

The `push` handler is a concrete high-impact example: it walks matching stacks by branch and unconditionally calls `stack.sync_github`, which enqueues `GithubSyncJob` to fetch and append attacker-referenced commits from GitHub for that stack: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who is a legitimate member/owner of one GitHub organization configured in a shared Shipit instance can forge a validly-signed webhook (using their own org's `webhook_secret`) whose `repository.full_name` names a stack belonging to a *different* organization hosted on the same Shipit instance. This lets them trigger `GithubSyncJob` for the victim's stack (causing Shipit to fetch and append commits/state using its own `GITHUB_TOKEN`/GitHub App credentials against the target repo), and, depending on which handler is invoked (`status`, `check_suite`, `membership`, `pull_request`, etc.), influence commit statuses, team/membership records, or pull-request/merge-queue state associated with a repository the attacker does not own. This crosses the "organization that authenticated versus the repository that is written" boundary called out in scope, and can result in cross-repository state mutation without the attacker ever having credentials for the victim org's GitHub App — matching the High-impact category ("escalation into `Shipit.github_teams` authorization" / unauthorized effect on stack state) depending on handler reached.

### Likelihood Explanation
Exploitability requires: (1) the Shipit instance to be configured for multiple GitHub organizations (the multi-org config schema is explicitly documented and supported — `config/secrets.development.shopify.yml`, `lib/shipit.rb#github_organizations`), and (2) the attacker to control (or compromise) the webhook secret of at least one of those configured organizations — which is the normal, expected level of access for an org admin setting up their own GitHub App integration, not a Shipit-privileged credential. Given that no Shipit session, `ApiClient` token, or GitHub App private key is required — only a legitimately-issued `webhook_secret` for any one of the co-tenant organizations — likelihood is credible in any multi-org Shipit deployment.

### Recommendation
Bind signature verification to the same identifier used for routing: either verify the HMAC signature using the organization derived from `repository.full_name`'s owner segment (not a separately-read `repository.owner.login`/`organization.login` field), or explicitly assert `repository.owner.login == full_name.split('/').first` before dispatching to handlers, rejecting the request (422) on mismatch. More robustly, resolve the target `Repository`/`Stack` first, then verify the signature using the `webhook_secret` associated with that repository's own owner/organization configuration only — never trust a payload field to select the verification key.

### Proof of Concept
1. Configure two organizations in `secrets.yml`, `victim-org` and `attacker-org`, each with distinct `webhook_secret`s (as supported by `config/secrets.development.shopify.yml`).
2. As a member of `attacker-org`, compute a valid `X-Hub-Signature` for a `push` event JSON payload using `attacker-org`'s known `webhook_secret`, but set:
   - `repository.owner.login = "attacker-org"` (so `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` selects and successfully validates against `attacker-org`'s secret)
   - `repository.full_name = "victim-org/victim-repo"`, `ref = "refs/heads/<victim-branch>"`, `after = "<attacker-chosen-sha>"`
3. POST to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` succeeds (secret matches `attacker-org`), and `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) resolves stacks via `repository.full_name`, matching `victim-org/victim-repo`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, enqueuing `GithubSyncJob` against the victim's stack — despite the forged request never being signed by `victim-org`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
