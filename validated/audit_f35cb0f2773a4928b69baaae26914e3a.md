## Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login`, but every event handler resolves the target repository from the unverified `repository.full_name` field, allowing cross-repository webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`). [1](#0-0) [2](#0-1)  Every actual event handler, however, determines which repository/stack to act on using a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`. [3](#0-2) 

Because the signature only proves that the payload was signed with the secret belonging to whatever organization is named in `repository.owner.login`, and that org name is never cross-checked against `repository.full_name`, an attacker who legitimately controls one onboarded GitHub organization (and therefore knows that organization's `webhook_secret`) can forge a webhook body claiming `repository.owner.login = "their-org"` while setting `repository.full_name = "victim-org/victim-repo"`. The signature verifies (it was computed correctly for "their-org"), but the handler acts on the victim's stack.

### Finding Description
- `verify_signature` binds trust to the organization derived from `repository.owner.login`/`organization.login`: `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. [1](#0-0) 
- `GitHubApp#verify_webhook_signature` only checks the HMAC over the raw body using that organization's configured `webhook_secret`; it has no notion of which repository is inside the body. [4](#0-3) 
- Every default handler (`PushHandler`, `StatusHandler`, `PullRequest::*`, `CheckSuiteHandler`, etc.) inherits `Handler#stacks`/`#repository_name`, which resolves the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')`, with no re-validation that this repository actually belongs to the organization that was used to select the signing secret. [3](#0-2) 
- `PushHandler#process`, for example, uses `stacks` (scoped by `repository_name`) to find matching stacks by branch and trigger `stack.sync_github(expected_head_sha: params.after)`. [5](#0-4) 
- The `status` event handler creates a `Status` record directly from attacker-supplied fields (`sha`, `state`, `target_url`, `description`, `context`, `created_at`) for the commit resolved via `repository.full_name`, as shown by the existing test asserting the created `Status`'s fields are copied verbatim from the payload. [6](#0-5) 

The equality that should hold is:
`organization authenticated by verify_signature (repository.owner.login / organization.login) == organization that owns the repository acted upon (repository.full_name)`

This equality is never enforced, so an attacker who is a legitimate GitHub org owner integrated with a shared Shipit instance (and thus knows their own org's `webhook_secret`) can forge a signed request whose "acted-upon" repository is any other org/repo tracked by the same Shipit instance.

### Impact Explanation
Because `StatusHandler` writes commit-status fields (`state`, `target_url`, `description`, `context`) verbatim from the payload rather than fetching them from GitHub's API, an attacker can forge a `success` status for a specific commit SHA in a victim's stack. [6](#0-5)  If that stack's `shipit.yml` uses `ci.require` to gate deploys on that same status context, this forged status can satisfy the CI gate for a commit that never actually passed CI, enabling an **unauthorized deploy** through Shipit's normal deploy flow. This satisfies the required "Critical" impact bucket (unauthorized deploy) via a cross-organization/cross-repository write that should never have been reachable by an org that doesn't own the target repository.

Other handlers using the same unverified `repository_name` binding (`PushHandler`, `membership` handler creating `User`/`Team`/`Membership` records, `PullRequest::*` handlers archiving/unarchiving review stacks) extend the same class of cross-tenant writes, though with lower direct severity than the CI-status forgery.

### Likelihood Explanation
This requires the attacker to control at least one organization that is legitimately configured/onboarded on the shared Shipit instance (and knows that org's `webhook_secret`, which they set when registering the GitHub webhook against the Shipit instance). No `ApiClient` token, `api_clients_secret`, GitHub App private key, or Shipit login session is required — only knowledge of a secret the attacker legitimately possesses for their own org, plus the ability to POST an arbitrary raw body with a matching header to the public webhooks endpoint. This is realistic in any Shipit deployment that serves multiple GitHub organizations/repositories from one instance (the multi-org `Shipit.github(organization:)` lookup by design implies this multi-tenant use case). [2](#0-1) 

### Recommendation
After signature verification succeeds for organization `O`, re-validate that `repository.full_name`'s owner segment equals `O` (or that `repository.owner.login`/`organization.login` used for verification matches the owner portion of `repository.full_name`) before any handler resolves/mutates a `Stack`. Reject the webhook (422) on mismatch. Alternatively, compute the signing key strictly from the owner embedded in `repository.full_name` itself, so the two fields cannot diverge.

### Proof of Concept
1. Attacker owns/administers GitHub organization `atk-org`, which is a legitimately configured organization on the target shared Shipit instance; the attacker therefore knows `atk-org`'s `webhook_secret` (it was set when they configured the GitHub webhook pointing at the Shipit instance).
2. Attacker crafts a JSON body:
```json
{
  "action": "success",
  "sha": "<victim-tracked-commit-sha>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "description": "forged CI pass",
  "context": "required-ci-context",
  "created_at": "2026-09-01T00:00:00Z",
  "branches": [{"name": "main"}],
  "repository": {
    "owner": {"login": "atk-org"},
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(atk-org_webhook_secret, raw_body)>` and sends `POST /webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"atk-org"` and validates successfully against `atk-org`'s secret. [1](#0-0) 
5. `StatusHandler` (via `Handler#repository_name`/`#stacks`) resolves the target repository from `repository.full_name = "victim-org/victim-repo"` and creates/updates a `Status` for the specified commit SHA in the victim's stack — a repository the attacker's organization never owned or had signing authority over. [3](#0-2) 

Note: I was unable to locate/view the exact `StatusHandler` source file in this pass (only its registration and observed behavior via the controller test), so the precise field-to-attribute mapping in that handler should be confirmed directly in `app/models/shipit/webhooks/handlers/status_handler.rb` before remediation.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
