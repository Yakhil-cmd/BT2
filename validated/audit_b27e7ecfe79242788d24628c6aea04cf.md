### Title
Attestations and asset "spender_attested" trust are bound only to an address hash and are never invalidated when the address's controlling definition changes - ([File: validation.js])

### Summary
Keycloak's bug (CVE-2023-0105) stems from binding "verified" trust to a mutable identifier (email) without resetting that trust when the identifier's underlying ownership changes. ocore has a structurally analogous pattern: attestations (`attestation` messages) and asset spend-eligibility checks (`spender_attested`) are keyed solely by the recipient's BB **address string** (a hash of a *definition*), never by the specific definition/keys that controlled that address at attestation time. Because an address's controlling definition can legitimately change over time via `address_definition_change` (multisig membership rotation, key replacement, etc.), any previously granted attestation/KYC status permanently and silently carries over to whoever controls the address afterwards, with no re-verification step.

### Finding Description
When an attestor posts an `attestation` message, validation only checks that `payload.address` is a syntactically valid address; there is no binding to the definition that currently or previously controlled it: "it is ok if the address has never been used yet... it is also ok to attest oneself" [1](#0-0) . The resulting record is stored keyed purely by `address` in `attestations` / `attested_fields` [2](#0-1) .

Every consumer of this data (asset spend gating and the `attestation[[...]]` oscript/AA formula) looks the record up by address alone, with no check of which definition/keys were in control of the address at attestation time versus now:
- Asset transfer/issue gating for `spender_attested` assets checks `objAsset.arrAttestedAddresses.indexOf(owner_address)` purely by address string [3](#0-2) , and again for change/output addresses via `storage.filterAttestedAddresses` [4](#0-3) .
- The oscript/AA `attestation[[attestors=..., address=...]]` formula, usable by any AA trigger/definition author, resolves the "last" attestation for that address with the same address-only key, "ORDER BY main_chain_index DESC ... LIMIT 1" [5](#0-4) .

Meanwhile, ocore explicitly supports changing which definition (i.e., which keys/cosigners) controls a given address without changing the address string itself, via `address_definition_change` [6](#0-5) . Once such a change occurs, the address is the same primary key used everywhere attestation trust is looked up, so the new controlling definition automatically and silently inherits every attestation, KYC flag, or `spender_attested` eligibility that was ever granted to that address — exactly the "verified state is not reset when the underlying identity changes" failure pattern from the Keycloak advisory (CWE-287/CWE-841), just with "definition/keys" playing the role of "email".

### Impact Explanation
This allows:
- **Bypass of asset transfer/issuance restrictions (fund control bypass):** for a `spender_attested` private or public asset, once *any* address has ever been attested by a trusted attestor, control of that address can be handed to a different party via a definition change (e.g., swap out one multisig cosigner for another, or migrate to entirely new keys) and the new controller is treated by validators as still attested, letting them receive/spend the restricted asset without the attestor ever verifying them. This is a concrete unauthorized-spending/fund-control vector guarded by `spender_attested`, using the exact code paths in `validation.js:2504-2507` and `validation.js:2630-2642`.
- **Impersonation in AA logic:** any AA that gates behavior on `attestation[[attestors=KYC_bot, address=trigger.address]]` (a common oscript idiom for KYC/identity-gated AAs) will keep granting privileges tied to that address to whoever currently controls it, letting a new/different real-world party impersonate the previously-verified identity for the AA's purposes (locking out or spoofing the original attested party from the AA's perspective) — the AA-reachable analog of Keycloak's impersonation/lockout.

Severity is comparable to Medium: it does not directly forge signatures or break DAG consensus, but it defeats an identity/eligibility control (attestations, `spender_attested`) that is explicitly part of ocore's asset and AA trust model.

### Likelihood Explanation
Exploitation requires only standard, unprivileged operations already reachable by any wallet/AA-trigger sender: (1) obtain or become an attested address (self-attestation is explicitly allowed, and many real deployments use multisig/shared addresses whose membership changes over time), (2) issue a normal `address_definition_change` for that address, and (3) subsequently use it to pass `spender_attested` checks or satisfy an AA's `attestation[[...]]` condition. No attestor cooperation, no network/consensus manipulation, and no special privilege are needed.

### Recommendation
Bind attestation validity to the specific definition (or a definition-change epoch/mci) in effect at attestation time rather than to the bare address string, e.g., by recording the `definition_chash`/mci alongside `attestor_address`/`address` in `attestations`/`attested_fields`, and requiring consumers (`validation.js` spender_attested checks, `storage.filterAttestedAddresses`, and the `attestation[[...]]` oscript function) to verify that the address's controlling definition has not changed since the attestation (or to require a fresh attestation after any `address_definition_change`). At minimum, document and surface to attestors/AA authors that address-based attestations do not survive definition changes safely, and consider invalidating/expiring `spender_attested` status automatically on `address_definition_change`.

### Proof of Concept
1. Attestor `ATT` attests address `A` (owned by Alice) as `spender_attested`-eligible for asset `X`, or an AA condition uses `attestation[[attestors=ATT, address=trigger.address]].kyc`.
2. `A` is defined as a 2-of-2 multisig `["and",[["address","B1"],["address","B2"]]]`.
3. Alice and cosigner `B1` cooperatively post `address_definition_change` for `A`, swapping `B1` out for `C1` (an entirely different, previously-unattested party), producing a new definition `["and",[["address","C1"],["address","B2"]]]` while `A`'s address string stays unchanged.
4. `C1`/new co-owners now jointly control `A`. Because `validation.js`'s `spender_attested` check (`validation.js:2504-2507`, `validation.js:2630-2642`) and the AA `attestation[[...]]` formula (`formula/evaluation.js:966-999`) key solely off `address = A`, the new controllers can spend/receive `X` or satisfy the AA's KYC condition without `ATT` ever attesting them.
