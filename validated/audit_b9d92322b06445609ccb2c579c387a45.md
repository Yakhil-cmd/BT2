### Title
Cross-repository commit-state forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `sha`, with no filter on repository, unlike other handlers which scope through the `stacks` helper keyed on `repository_name` from the payload. Because git SHAs are content-addressed and not globally unique to a repository (forks trivially share identical SHAs with their upstream, and bit-for-bit-identical commits can also be constructed independently), an attacker who controls any repository/fork whose webhook signature validates (their own repo, using their own installation) can cause `Commit` rows belonging to an unrelated, victim-owned stack to be mutated.

### Finding Description
The broken binding: the code assumes `sha -> repository` is 1:1, i.e. `Commit.where(sha: params.sha).repository == payload.repository`, but in reality git SHAs are content-addressed and repository-independent, so this equality does not hold in general.

Code path: [1](#0-0) 
`process` iterates `Commit.where(sha: params.sha)` — across *all* stacks/repositories in the Shipit instance — and calls `commit.create_status_from_github!(params)` on each match, with zero repository scoping.

Compare to the base `Handler` class, which provides a `stacks` helper explicitly scoped to the webhook's own repository: [2](#0-1) 
Other handlers (e.g. push, pull_request handlers) use this `stacks`/`repository_name` scoping before touching any records, but `StatusHandler` does not — it never reads `payload.dig('repository', 'full_name')` at all.

`verify_signature` in `WebhooksController` only checks that the payload is signed by *some* configured GitHub App/organization matching `repository_owner` from the payload — it authenticates that the webhook genuinely came from GitHub for the attacker's own repository, not that the `sha` inside the payload belongs to that repository: [3](#0-2) 

Exploit flow: an attacker forks `victim/repoB` into `attacker/repoA`, or otherwise creates a commit with an identical SHA to a commit already stored in a victim `Stack`'s `Commit` table (trivial via a fork, since forks start with byte-identical history/SHAs, or reproducible by re-creating identical tree/parent/author/timestamp/message). The attacker configures their own CI on their own repo/fork (a legitimate, attacker-controlled GitHub App/webhook installation) which emits a `status` event for that `sha` with `state: success`. GitHub signs this webhook correctly for the attacker's own installation/org, so `verify_signature` passes. `StatusHandler#process` then finds the `Commit` row(s) in the *victim's* stack matching that `sha` (since `Commit.where(sha:)` has no repository/stack filter) and calls `create_status_from_github!`, mutating the victim's commit status. Since `deployable?` depends on `success?` from `status` [4](#0-3)  and `add_status` schedules merges/deploy eligibility on success [5](#0-4) , this can make an otherwise-blocked victim commit appear CI-green and eligible for deploy/merge.

No existing guard prevents this: `verify_signature` authenticates the source app/org of the webhook but not the `sha`-to-repository binding claimed inside the payload body; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `StatusHandler` only validates types of `sha`/`state`/etc., not repository ownership.

### Impact Explanation
This lets an unprivileged attacker (owner of any repository/fork whose GitHub App/webhook signs correctly for their own installation) write forged CI status onto `Commit` records of a completely different, victim-owned `Stack`/repository — a payload for one repository mutating another's commit/task/stack state, and directly enabling an unauthorized deploy or merge once the victim commit is marked `success`. This matches the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). It is repeatable against any repository configured in the same Shipit instance whose commits the attacker can reproduce/share a SHA with (most easily via forking).

### Likelihood Explanation
Preconditions are low-cost and fully attacker-controlled: fork a public target repo (or otherwise reconstruct an identical commit), wire up any CI provider to the fork/attacker repo, and let that CI's status webhook fire — all without any Shipit credentials, GitHub App keys, or webhook secrets belonging to the victim. The signature check only requires the webhook be validly signed for *the attacker's own* organization/repo context, which the attacker fully controls. This is highly feasible and repeatable at will.

### Recommendation
Scope `StatusHandler#process` to the repository the webhook actually originated from, analogous to the `stacks` helper used elsewhere: restrict the `Commit` lookup to `stacks` (i.e., commits belonging to stacks whose `Repository` matches `payload.dig('repository', 'full_name')`) instead of a bare `Commit.where(sha: params.sha)` across the whole instance.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks/repositories, `repo_a` (attacker-controlled) and `repo_b` (victim), each with a `Commit` record sharing the identical `sha` value (e.g. `"deadbeef" * 5`).
2. Build a `status` webhook payload whose `repository.full_name` is `repo_a`'s full name, `sha` equal to the shared value, and `state: "success"`.
3. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
4. Assert: `repo_b`'s `Commit` (victim) now has `state == "success"` even though the webhook's `repository.full_name` was `repo_a` — proving the sha-to-repository binding does not hold and cross-repository mutation occurred. Also assert `repo_a`'s commit was updated as expected (control case), demonstrating the divergence is specifically the missing repository scope in the query.
