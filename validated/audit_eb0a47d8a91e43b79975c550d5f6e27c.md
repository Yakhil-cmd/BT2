Confirmed vulnerability: the webhook signature is verified against the HMAC secret for the organization named in `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), but every event handler (`PushHandler`, `OpenedHandler`, `ClosedHandler`, etc.) resolves the target `Repository`/`Stack` independently from `params.dig('repository','full_name')` via `Handler#repository_name` / `Repository.from_github_repo_name`. Nothing binds these two fields together, so a signature that is valid for organization A's webhook secret authorizes a payload whose `repository.full_name` names a stack belonging to organization B.

### Title
Webhook signature scoped to `repository.owner.login` does not bind to the `repository.full_name` acted upon, allowing cross-organization stack forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's HMAC secret to verify against using `repository.owner.login` (or `organization.login`), but the event handlers that mutate application state operate on `repository.full_name`, a separate, unrelated field in the same unsigned JSON envelope that GitHub never scopes together for HMAC purposes the way Shipit assumes. An attacker who controls (or has leaked) the webhook secret for one organization configured in Shipit can craft a payload where `repository.owner.login` matches their own organization (so the signature check passes) while `repository.full_name` names a repository/stack belonging to a different organization also configured in the same Shipit instance.

### Finding Description
`verify_signature` in [1](#0-0)  computes `repository_owner` from the payload and fetches `Shipit.github(organization: repository_owner)` to obtain the per-organization `webhook_secret`, then verifies the raw body against `X-Hub-Signature` using that secret via `GithubApp#verify_webhook_signature` [2](#0-1) .

Once the signature is accepted, `create` dispatches the *entire* JSON body to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . Every handler resolves its target repository/stack purely from `payload.dig('repository', 'full_name')`, e.g. `Handler#repository_name` [4](#0-3) , and this is reused verbatim in `PushHandler#process` (`stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }`) [5](#0-4)  as well as in every PR handler (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.), all of which call `Shipit::Repository.from_github_repo_name(params.repository.full_name)`.

This breaks the intended binding: the value that determines *which HMAC secret authorizes the request* (`repository.owner.login`) is never checked for consistency with the value that determines *which repository/stack is acted upon* (`repository.full_name`). Shipit supports hosting multiple GitHub organizations from a single instance (`docs/setup.md:181-216` — "Using Multiple Github Applications"), each with its own `webhook_secret`. Any organization admin (or anyone who has captured/guessed that organization's webhook secret through normal, non-privileged means such as reading their own app's webhook config) can sign a payload whose `repository.full_name` is set to `otherorg/some-repo`, and Shipit will process it as if GitHub itself delivered it for that other org's repository — triggering `GithubSyncJob`, provisioning/archiving review stacks, or updating PR state for a stack it does not own.

### Impact Explanation
This is a cross-repository/cross-organization write: an actor who can produce a valid signature for organization A's webhook secret can force Shipit to sync commits, archive/unarchive review stacks, or otherwise mutate state for a stack belonging to organization B, purely by controlling the `repository.full_name` field of the payload. This matches the "cross-repository writes" Critical impact category, since the security decision (which secret authorizes the request) and the write target (which repository/stack is mutated) are governed by two different, unlinked payload fields.

### Likelihood Explanation
Exploitation requires knowledge of one organization's `webhook_secret` that is already configured in the target Shipit instance — an org admin for one of the multiple GitHub organizations Shipit is configured to serve (per `docs/setup.md`'s "Using Multiple Github Applications") already has legitimate access to their own webhook secret and needs no other privilege to forge a payload naming a different org's repository.

### Recommendation
After verifying the HMAC signature with the secret selected via `repository.owner.login`, re-validate that `repository.full_name` actually belongs to that same owner/organization before dispatching to handlers (e.g., assert `params.dig('repository','full_name')&.start_with?("#{repository_owner}/")`), or resolve the signing organization strictly from the repository/organization records already known to Shipit rather than trusting the payload's owner field independently of the repository field acted upon.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with distinct `webhook_secret`s (per the multi-org setup docs).
2. As a legitimate member of `orgA`, obtain `orgA`'s `webhook_secret` (already accessible to them via GitHub App settings).
3. Craft a `push` event JSON body: `{"ref": "refs/heads/master", "after": "<attacker-chosen sha>", "repository": {"owner": {"login": "orgA"}, "full_name": "orgB/some-private-repo"}}`.
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, body)>` and POST it to `/webhooks`.
5. `verify_signature` looks up `Shipit.github(organization: "orgA")` and validates successfully.
6. `PushHandler` resolves `Repository.from_github_repo_name("orgB/some-private-repo")` and enqueues `GithubSyncJob` / mutates the `orgB` stack, despite the request only ever being authenticated against `orgA`'s secret. [6](#0-5) [2](#0-1) [4](#0-3) [5](#0-4)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
