### Title
Missing Private/Internal Address Filtering in `isValidWsUrl` Allows SSRF via Attacker-Controlled Device Hub URL - (File: `network.js`, `device.js`)

### Summary
`network.isValidWsUrl()` only validates that a peer/hub URL uses the `ws:`/`wss:` scheme and has no credentials or fragment; it performs **no check at all** against private, loopback, or link-local IP ranges (`127.0.0.1`, `10.x.x.x`, `192.168.x.x`, `169.254.x.x`, etc.). [1](#0-0) 

This function is the sole gatekeeper for hub URLs that are attacker-influenced through device-message fields, most notably `json.device_hub` sent by a *paired correspondent device* in a `hub/message` justsaying, and through `updateCorrespondentProps`/`addIndirectCorrespondents` when adding cosigners (e.g. via shared-address/arbiter-contract flows). [2](#0-1) [3](#0-2) 

### Finding Description
This is the same bug class as `private_address_check` (CVE-2017-0909, incomplete/absent private-address blacklist used to prevent SSRF), except here the blacklist is entirely missing rather than merely incomplete. The only sanitization performed on hub URLs supplied by a remote, low-privilege actor (a paired device, or an indirect correspondent added through a shared-address/arbiter workflow) is `network.isValidWsUrl`, which checks protocol scheme and absence of embedded credentials/fragment, but does not reject private, loopback, link-local, or multicast address ranges: [1](#0-0) 

Once accepted, the attacker-controlled `device_hub`/`hub` value is persisted (`correspondent_devices.hub`) and subsequently used by the node whenever it needs to contact that correspondent's "home hub" — e.g. to relay pairing messages, requests, or arbstore/arbiter lookups — causing the local `ocore` node to open outbound WebSocket connections to a URL fully chosen by the remote peer: [4](#0-3) [5](#0-4) 

Because the value only needs to look like a `ws://`/`wss://` URL, an attacker can set it to `ws://127.0.0.1:<port>`, `ws://10.x.x.x:<port>`, `ws://169.254.169.254/`, or any other RFC1918/loopback/link-local target reachable from the victim's host, and the node's `network.findOutboundPeerOrConnect`/`connectToPeer` machinery will dial it as if it were a legitimate hub. [6](#0-5) 

### Impact Explanation
This enables Server-Side Request Forgery from an unprivileged, already-paired device (or an indirect correspondent introduced through normal cosigner/shared-address flows) against the victim node's internal network / localhost services. Depending on what else the node operator runs on the same host or LAN (wallet RPC/API endpoints, database admin panels, other internal daemons), the attacker can use the victim node as a network probe/relay to reach otherwise-unreachable internal endpoints, and can repeatedly force reconnection attempts to arbitrary internal hosts by updating `device_hub` in subsequent messages. This does not directly cause fund loss, but it is a concrete network/trust-boundary violation reachable purely by messages from a paired device, consistent with the reachable-actor set defined for this analog.

### Likelihood Explanation
Any already-paired correspondent device can trigger this by sending a `hub/message` justsaying whose decrypted body sets `device_hub` to an internal address; the same class of correspondent-hub value is also settable via `updateCorrespondentProps`/`addIndirectCorrespondents` when cosigners are exchanged. No special privileges beyond an existing pairing (which is a normal, low-trust wallet operation) are required, making this straightforward to trigger.

### Recommendation
Extend `isValidWsUrl` (or add a dedicated check invoked wherever `device_hub`/correspondent `hub` values are accepted) to resolve/parse the hostname and reject private (RFC1918), loopback (127.0.0.0/8, ::1), link-local (169.254.0.0/16, fe80::/10), and other non-public address ranges, mirroring the fix applied to `private_address_check` 0.4.1 (i.e., use a complete, actively-maintained private-IP blacklist rather than an ad hoc scheme/credential check), and apply it consistently at every place a peer- or correspondent-supplied URL is persisted or dialed (`device.js:206`, `device.js:895`, `device.js:910`, `network.js:717`, `network.js:2927`).

### Proof of Concept
1. Node A pairs with Node B (attacker) through the normal pairing flow.
2. Attacker (Node B) sends a `justsaying` of subject `hub/message` to Node A's hub, with the encrypted `json.device_hub` field set to `"127.0.0.1:<internal-port>"` (or `"10.0.0.5:<port>"`).
3. Node A's `handleJustsaying` code path checks only `json.device_hub.length <= 200 && network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub)` — both pass since the string parses as a valid `ws://`/`wss://` URL — and updates `correspondent_devices.hub` for the attacker's device address. [7](#0-6) 
4. Any subsequent operation that needs to reach that correspondent's hub (e.g., `sendPairingMessage`, arbstore/arbiter requests) causes Node A to call `network.findOutboundPeerOrConnect`/`connectToPeer` against the attacker-chosen internal address, letting the attacker probe or interact with internal services on Node A's host/LAN. [6](#0-5)

function isValidWsUrl(url) {
	try {
		const { protocol, hash, username, password } = new URL(url);
		if (hash)
			return false;
		if (url.includes('#')) // empty trailing hash
			return false;
		if (username || password) // no legitimate peer url needs credentials
			return false;
		if (!['wss:', 'ws:'].includes(protocol))
			return false;
		if (conf.WS_PROTOCOL === 'wss://' && protocol !== 'wss:')
			return false;
		return true;
	}
	catch {
		return false;
	}
}
