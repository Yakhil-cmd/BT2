### Title
Webhook signature verification is scoped to the wrong organization, allowing any onboarded GitHub org to forge commit statuses / trigger syncs for repositories owned by other organizations - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC `webhook_secret` to validate a payload against using `repository_owner`, a value read from the *same untrusted JSON body* (`repository.owner.login` / `organization.login`). Once the signature is confirmed valid for that self-selected organization, the event is dispatched to handlers that key off a *different* field of the same payload — `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name`) — to decide which `Stack`/`Repository`/`Commit` to act on, with `StatusHandler` not even scoping by repository at all. This breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end
```
`repository_owner` is attacker-controlled data taken from the JSON body itself, not from any authenticated GitHub identity. In a multi-organization Shipit deployment (`config/secrets.*.yml` supports one `webhook_secret` per GitHub org - see `config/secrets.development.shopify.yml`), a party that legitimately administers **Org B**'s GitHub App (and therefore knows Org B's `webhook_secret`) can construct an arbitrary raw JSON body, set `repository.owner.login` to `"OrgB"` (so `verify_signature` selects and validates against Org B's own secret — which always succeeds since they are self-signing), while setting `repository.full_name` to any other value, e.g. `"OrgA/victim-repo"`.

The dispatched handlers key off `full_name`, not `owner.login`:
```ruby
# app/models/shipit/webhooks/handlers/handler.rb
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
`PushHandler` uses `stacks` (scoped by `full_name`) to trigger `stack.sync_github`. More critically, `StatusHandler` does **not** scope by repository at all:
```ruby
# app/models/shipit/webhooks/handlers/status_handler.rb
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
It looks up commits by `sha` alone, globally across every repository/stack tracked by the Shipit instance. Since git SHAs are public/derivable from any repository's history, an attacker who controls the webhook credentials for one onboarded org can forge a `status` event carrying `state: "success"` for a commit SHA that belongs to a completely unrelated stack owned by a different organization.

### Impact Explanation
`Commit#deployable?` and `schedule_continuous_delivery` (`app/models/shipit/commit.rb`) gate continuous deployment directly on commit status state:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end

def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
```
By forging a `success` status webhook for a target commit in a stack the attacker does not control, the attacker can flip that commit's CI gate to green and trigger `ContinuousDeliveryJob`, resulting in an unauthorized deploy of a repository/organization they have no legitimate relationship with. This satisfies the "High" bar: "escalation... or an unauthorized deploy" without holding any Shipit session, API token, or write access to the victim repository — only requiring administration of a *different*, unrelated GitHub App/org that happens to also be configured in the same Shipit instance.

### Likelihood Explanation
Requires a multi-tenant/multi-org Shipit deployment (explicitly supported and documented in `config/secrets.development.shopify.yml`), and requires the attacker to know or guess a target commit SHA (which is public GitHub data, not secret). No compromise of the victim org's GitHub App or webhook secret is needed. The verification logic itself creates the gap regardless of how many orgs are configured, so likelihood is moderate-to-high specifically for shared/multi-tenant deployments, which is the deployment model the code explicitly caters for.

### Recommendation
- Verify the webhook signature using the organization actually referenced by `repository.full_name` (or cross-check that `repository.owner.login` matches the owner segment of `repository.full_name`) before accepting the payload.
- In `Shipit::Webhooks::Handlers::StatusHandler` (and any other handler that queries by SHA/global identifiers), scope `Commit.where(sha: params.sha)` to the repository parsed from the verified payload (`repository_name`) rather than searching across all stacks.
- Reject requests where `repository.owner.login` and `repository.full_name`'s owner segment disagree.

### Proof of Concept
1. Attacker administers the GitHub App for `orgB`, which is configured in Shipit's `github:` secrets alongside `orgA` (multi-org setup as documented in `config/secrets.development.shopify.yml`).
2. Attacker crafts a raw JSON body:
```json
{
  "sha": "<sha-of-commit-in-orgA/victim-repo>",
  "state": "success",
  "repository": { "owner": { "login": "orgB" }, "full_name": "orgA/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orgB_webhook_secret, raw_body)` using their own legitimately-known `orgB` secret.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "orgB")` and successfully validates the signature (self-signed).
6. `StatusHandler#process` finds `Commit.where(sha: ...)` — matching the victim's commit in `orgA/victim-repo` regardless of the org used for signature verification — and creates a `success` status, potentially triggering `ContinuousDeliveryJob` for `orgA`'s stack.

Note: I could not fully trace whether additional downstream validation (e.g., in `RefreshStatusesJob` or merge-queue logic) would reconcile/overwrite this forged status against real GitHub state before a deploy actually executes; that reconciliation timing window and its exact effect on `ContinuousDeliveryJob` scheduling would need to be confirmed with a live/integration test, which is outside what static code reading can settle. module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
