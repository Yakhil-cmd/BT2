## Analysis Result

Based on my investigation, I found a concrete analog of the "verified check applies to a different scope than the one that is written" bug pattern (the UF-4 mint off-by-one where `random() % (counter+1)` allowed an index outside the verified/existing set).

### Title
Cross-repository commit status injection via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `status` webhook is authenticated per-organization (`Shipit.github(organization: repository_owner)` in `WebhooksController#verify_signature`), but the handler that acts on the verified payload never checks that the commit it mutates belongs to the repository/organization whose signature was verified.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC against using `repository_owner`, derived from `params.dig('repository','owner','login')` of the *same untrusted payload* being verified: [1](#0-0) 

Every other handler in the engine scopes its side effects to the repository named in the payload via `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)`: [2](#0-1) 

`StatusHandler`, however, does not use this scoping at all — it looks up commits by SHA alone, globally, with no `repository`/`full_name` requirement in its parameter schema: [3](#0-2) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` will match **any** `Commit` record across **any** stack/repository in the installation that happens to have that SHA — not just commits belonging to the repository that authenticated the webhook.

Because Git commit SHAs are content-addressed and identical across forks/mirrors of the same history, an attacker who owns (or compromises) a fork of a tracked repository can register a webhook on their own fork, sign a legitimate `status` event (using their own repo/org secret, which passes `verify_webhook_signature` since it's genuinely their own valid HMAC), and set `sha` to a commit shared with the upstream ancestor history. That status is then written onto the **victim's** commit in the **victim's** stack, because `StatusHandler#process` never re-validates that the SHA actually belongs to the repository whose owner/org was used to satisfy the signature check.

This is the same class of defect as UF-4: the verified/authenticated boundary (organization signature covering `repository.owner.login`) is not the same boundary that the write operation actually respects (commit lookup is global by SHA, unbound from `repository`).

### Impact Explanation
`Commit#create_status_from_github!` persists a `Status` and can flip a commit's simple state (e.g., to `success`), which is used by `next_commit_to_deploy` / `deployable_commits` for continuous deployment, and by `StatusChecker` for merge-queue gating (`MergeRequest#reject_unless_mergeable!`, `all_status_checks_passed?`): [4](#0-3) 

An attacker forging a passing CI status on someone else's commit can therefore cause an unauthorized deploy to be triggered by continuous delivery, or allow a pull request to pass required-status gating in the merge queue and be auto-merged — this matches the "unauthorized deploy, rollback, or merge" Critical/High impact bar.

### Likelihood Explanation
This requires the attacker to control a repository (e.g., a fork) that shares commit history/SHAs with the tracked repository, and for that fork's GitHub App/webhook to be configured for the same Shipit instance (multi-org or shared installation scenarios are explicitly supported per `docs/setup.md` and `config/secrets.development.example.yml` multi-org config examples). Given forks of tracked repos are common and SHAs of shared ancestor commits are identical by construction, this is practically reachable without needing any Shipit session, API token, or privileged account — only ordinary GitHub push/webhook access to a fork.

### Recommendation
Scope `StatusHandler#process` the same way other handlers do: require `repository.full_name` in the parameter schema and restrict the `Commit` lookup to `stacks` (i.e., commits belonging to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`), matching the pattern already used in `Handler#stacks` and in `PushHandler`.

### Proof of Concept
1. Attacker forks `victim-org/victim-repo` to `attacker-org/victim-repo-fork`, sharing a common ancestor commit `abc123...`.
2. Attacker configures a GitHub App/webhook on their fork pointed at the shared Shipit instance (a legitimate, self-owned configuration — no victim credentials needed).
3. Attacker triggers a `status` webhook event from their own repo/org with `sha: "abc123..."`, `state: "success"`, `context: "ci/required-check"`. This passes `verify_signature` because it is HMAC-signed with the attacker's own valid organization webhook secret.
4. `WebhooksController#create` dispatches to `Shipit::Webhooks::Handlers::StatusHandler`, which runs `Commit.where(sha: "abc123...")` — this matches the commit row in `victim-org/victim-repo`'s stack (same SHA, different repo) and calls `commit.create_status_from_github!(params)`, writing a fabricated "success" status onto the victim's commit.
5. If that commit is next in `next_commit_to_deploy` for a continuous-deployment-enabled stack, or is the head of a pending `MergeRequest`, the forged status can trigger an unauthorized deploy or unblock an auto-merge.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
