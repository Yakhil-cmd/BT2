### Title
Session Fixation via missing `reset_session` on GitHub OAuth login completion - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` elevates a session to an authenticated `User` identity by writing `session[:user_id]` and `session[:authenticated]` directly into the *existing* session, without first calling `reset_session`. This breaks the binding "GitHub identity that completed OAuth" == "session/cookie the server issues to that identity", allowing an attacker who has pre-established a session (fixed it into a victim's browser) to inherit the victim's authenticated identity once the victim completes the GitHub OAuth flow.

### Finding Description
The OAuth callback action is: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true

  redirect_to(return_url)
end
```

No `reset_session` is called before binding `session[:user_id]`. Compare this with the pattern already used elsewhere in the engine for de-authenticating a stale identity, `force_github_authentication`, which explicitly calls `reset_session` when invalidating credentials: [2](#0-1) 

The absence of an equivalent `reset_session` call on the *authenticating* path means the session identifier (cookie value / session key, depending on session store configuration) that existed **before** OAuth completion is the exact same one that becomes bound to `session[:user_id] = <victim's User#id>` **after** completion. `current_user` is subsequently derived purely from that session key: [3](#0-2) 

Binding broken (before vs. after the attack sequence):
- Before: `session_key S` → unauthenticated / attacker-controlled, `github_identity` → not yet resolved.
- After victim completes OAuth using the same `S` (e.g., attacker pre-plants `S` in the victim's browser, or sends a link/cookie that forces the browser to reuse `S`, then lures the victim to `/github/auth/github`): `session_key S` → bound to `victim.User#id`, and the attacker, who already possesses `S`, now presents `S` as their own cookie and is treated as the victim (`current_user` resolves to the victim) by every downstream controller relying on `Shipit::Authentication#current_user`.

This is a session-fixation / forced-OAuth-completion pattern, not a webhook/token/DoS issue, and requires no `ApiClient` token, `webhook_secret`, GitHub App private key, or prior repository access — only the ability to get the victim's browser to authenticate the OAuth flow while sharing a session identifier the attacker already knows, which is the classic session-fixation delivery vector (e.g., cross-subdomain cookie injection, or a shared/non-rotated session id delivered via a crafted link if the underlying session store assigns an id before login).

### Impact Explanation
Once the attacker's pre-established session is elevated to the victim's `User` after OAuth completion, the attacker gains a fully authenticated session as the victim across the entire engine: they can trigger deploys/rollbacks/tasks, manage `ApiClient`s, and access any UI/API endpoint gated by `Shipit::Authentication`, effectively an authentication bypass / account takeover — matching the Critical "authentication bypass" category.

### Likelihood Explanation
Exploitability depends on the session store configuration of the host application (cookie store vs. server-side store) and on the attacker's ability to force the victim's browser to reuse a specific session identifier before the OAuth callback runs (e.g., via subdomain cookie tossing, or an environment where session ids are assigned before authentication and not rotated). The engine's own code provides no mitigation (no `reset_session` at authentication time), so the vulnerability is present regardless of host configuration; the practical likelihood is therefore governed only by the attacker's ability to plant/share a session identifier, a well-known and previously exploited class of web vulnerability.

### Recommendation
Call `reset_session` (or otherwise rotate/regenerate the session identifier) in `GithubAuthenticationController#callback` immediately before assigning `session[:user_id]`/`session[:authenticated]`, mirroring the pattern already used in `Shipit::Authentication#force_github_authentication` when invalidating a session.

### Proof of Concept
1. Attacker visits the Shipit instance (or otherwise forces a known session identifier into the victim's browser, e.g. via subdomain cookie injection) to obtain/establish session `S`, currently unauthenticated (`current_user` → `AnonymousUser`).
2. Attacker lures the victim into using session `S` and completing the GitHub OAuth login flow at `GET /github/auth/github` → GitHub → `callback`.
3. `GithubAuthenticationController#callback` executes `session[:user_id] = sign_in_github(auth)` on session `S` without calling `reset_session`.
4. Attacker, still in possession of session `S`, now issues requests to the Shipit instance and is recognized as the victim by `current_user` in `app/controllers/concerns/shipit/authentication.rb`, gaining full access to the victim's authenticated privileges (deploys, task triggers, API client management, etc.).
