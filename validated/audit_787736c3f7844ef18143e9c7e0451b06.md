### Title
Webhook signature verification is keyed on `repository.owner.login` while the acted-upon repository is resolved from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate the inbound webhook HMAC by reading `repository.owner.login` (or `organization.login`) out of the **unverified** JSON body. The handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolve the target `Repository`/`Stack` from a **different** field of the same unverified body: `repository.full_name`. Because Shipit explicitly supports multi-org configurations where individual organizations may have `webhook_secret: nil` (documented as "optional"), an attacker can pick the org with no secret to satisfy `verify_signature`, while pointing `repository.full_name` at a repository belonging to a different, secured organization.

### Finding Description
`verify_signature` computes the org used for verification purely from payload content, before the signature is validated: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected org's `webhook_secret` is blank: [3](#0-2) 

This is a documented, supported configuration — the setup guide explicitly calls the webhook secret "optional": [4](#0-3) 
and the multi-org secrets schema allows independent per-org `webhook_secret` values, including `nil`: [5](#0-4) 

Meanwhile, the base `Handler` class resolves which `Repository`/`Stack`s to operate on from an entirely different payload field, `repository.full_name`, not `repository.owner.login`/`organization.login`: [6](#0-5) [7](#0-6) 

The equality that should hold — "organization whose webhook_secret authenticated this request" == "organization owning the repository the handler mutates" — is never enforced. `verify_signature` binds trust to `repository.owner.login`; the handler binds action to `repository.full_name`. An attacker fully controls both fields in the same unsigned request body, so they can decouple them: set `repository.owner.login`/`organization.login` to an org configured with `webhook_secret: nil` (verification always passes), while setting `repository.full_name` to `<secured-org>/<repo>` so the handler acts on a repository belonging to an org that *does* have a webhook secret configured.

### Impact Explanation
Depending on the handler dispatched (selected via `X-Github-Event`, itself unauthenticated), an attacker can act on a stack belonging to a securely-configured organization without ever knowing that organization's `webhook_secret`:
- `push` → `PushHandler#process` invokes `stack.sync_github(expected_head_sha:)` on stacks of the targeted repo, forcing a git resync from an attacker-chosen `after` sha: [8](#0-7) 
- `status` → `StatusHandler#process` injects a forged commit status (`state`, `description`, `context`) onto any commit matching the given `sha`, which can satisfy deploy-blocking CI checks: [9](#0-8) 
- `check_suite` → schedules check-run refresh for a targeted stack/commit: [10](#0-9) 

Forged commit statuses that gate deploy pipelines can lead to an unauthorized deploy decision being made on a secured organization's stack, satisfying the "unauthorized deploy" High-impact category, without possessing any Shipit session, `ApiClient` token, or the targeted organization's `webhook_secret`.

### Likelihood Explanation
Requires only that the Shipit deployment configures at least one GitHub organization/app without a `webhook_secret` (an explicitly documented, supported configuration) alongside at least one organization that does have a secret. No credentials, sessions, or write access to any repository are needed — the attacker only needs to know the login of the unsecured org and the `owner/name` of the target repo, both of which are typically public information (org/app installation names, repository names).

### Recommendation
Do not select the verifying GitHub App/organization from unverified payload content that differs from the field used to resolve the acted-upon repository. Concretely:
1. Verify the signature using the organization the repository is actually mapped to in Shipit's own `Repository`/`Stack` records (resolved from `repository.full_name`), not from the attacker-supplied `repository.owner.login`/`organization.login`.
2. Alternatively, after verification, re-check that `repository.owner.login` (used to pick the webhook secret) matches the owner segment of `repository.full_name` (used to resolve the repository) before dispatching to handlers, and reject on mismatch.
3. Treat organizations configured with `webhook_secret: nil` as verification-scoped strictly to their own known repositories, never as a bypass path callable with an arbitrary `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations: `OrgB` (no `webhook_secret`, per the documented optional setting) and `OrgA` (has a stack tracking `OrgA/secured-repo`, with a `webhook_secret` configured).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/secured-repo" },
  "sha": "<head sha of a commit blocking OrgA's deploy>",
  "state": "success",
  "context": "ci/required-check"
}
```
No valid `X-Hub-Signature` for `OrgA` is supplied (or any arbitrary value).
3. `WebhooksController#verify_signature` computes `repository_owner = "OrgB"`, calls `Shipit.github(organization: "OrgB").verify_webhook_signature(...)`, which returns `true` unconditionally because `OrgB`'s `webhook_secret` is blank.
4. `StatusHandler#process` is invoked with the full payload; it resolves the commit purely by `sha` (global lookup, not scoped by the verified org) and creates a forged successful status, potentially unblocking a deploy gate on `OrgA/secured-repo` — a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
