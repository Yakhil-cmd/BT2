## Title
Scoped `ApiClient` token bypasses stack authorization in `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack via the `stack_id` column, and every other API controller enforces that scope by resolving the target stack through the `stacks` collection that is filtered by `current_api_client.stack_id`. `Api::CCMenuController`, however, overrides the `stack` accessor to resolve the stack directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the per-client stack scoping. The permission check only verifies the string `read:stack` is present in the client's `permissions` array — it never verifies which stack that permission applies to.

### Finding Description
`Shipit::Api::BaseController#stack` correctly limits stack lookups to the client's authorized set: [1](#0-0) 

`Shipit::ApiClient#check_permissions!` only checks the operation/scope string, with no stack-awareness at all: [2](#0-1) 

`Api::CCMenuController`, which is reachable with `require_permission :read, :stack`, overrides `stack` to bypass the `stacks` scoping entirely: [3](#0-2) 

Because `require_permission!` only calls `current_api_client.check_permissions!(:read, :stack)` — which merely checks that `"read:stack"` is included in the client's `permissions` array — any client holding that permission string, regardless of its `stack_id` binding, can pass `params[:stack_id]` for an arbitrary, unrelated stack and `Stack.from_param!` will happily resolve it. This breaks the intended equality: **stack a token authorizes == stack a token touches**.

Every other stack-scoped API endpoint (e.g. `Api::StacksController#show`) inherits the correct `BaseController#stack`, which is filtered through `stacks` (`Stack.where(id: current_api_client.stack_id)` when scoped): [4](#0-3) 

The CCMenu-specific token minted for read-only status widgets is created with `permissions: %w[read:stack]` and — depending on how it's provisioned — can be scoped to one stack; that scoping is meaningless against this controller since `stack` never consults `current_api_client.stack_id`.

### Impact Explanation
An unprivileged holder of a legitimately-issued, stack-scoped `read:stack` `ApiClient` token (e.g. a CI status widget token meant to see only its own stack's build state) can use it against `Api::CCMenuController#show` with any other `stack_id` to read that other stack's build/deploy status (last build outcome, label, lock state, etc.) without ever being authorized for that stack. This matches the "High — unauthenticated read of stack state" bucket: the attacker is not unauthenticated in the strict sense, but is authenticated only for one stack and escalates the read scope to any stack in the installation, which is the intended access-control boundary of `ApiClient.stack_id`.

### Likelihood Explanation
Any actor possessing a stack-scoped `read:stack` token — which is deliberately restricted precisely so it cannot see other stacks — can trivially exploit this by changing the `stack_id` route/query parameter. No additional privilege, secret, or timing condition is required beyond holding that one legitimately scoped token, making exploitation straightforward and repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` collection (as `BaseController` does) instead of `Stack.from_param!` directly, e.g. `stacks.from_param!(params[:stack_id])`, so that a client's `stack_id` binding is enforced consistently across all API controllers, including CCMenu.

### Proof of Concept
1. Admin creates (or the app auto-creates via `CCMenuUrlController#client`) an `ApiClient` with `permissions: ['read:stack']` intended to be scoped to `stack_id: A` (analogous to the `here_come_the_walrus` fixture which is scoped via `stack: shipit`) — see [5](#0-4) .
2. That token is handed to a third party (e.g., embedded in a CI status-badge URL) who is only supposed to view stack A.
3. The holder calls `GET /api/stacks/:stack_id/ccmenu.xml?token=<token>` with `stack_id` set to stack B instead of A.
4. `Api::CCMenuController#authenticate_api_client` authenticates the token; `require_permission :read, :stack` succeeds because the token has the `read:stack` string; `stack` resolves stack B directly via `Stack.from_param!`, bypassing the `stacks` scoping used everywhere else.
5. The response discloses stack B's build/deploy status even though the token was never authorized for stack B.
