### Title
Cross-repository Status forgery via unscoped sha lookup in `StatusHandler#process` — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to attach a forged GitHub `status` event to by SHA alone, with no check that the originating webhook's repository matches the `Repository` owning the target `Commit`'s `Stack`. Unlike `PushHandler`, which scopes its query through `Handler#stacks` (which resolves `Repository.from_github_repo_name(repository_name)`), `StatusHandler` never calls `stacks` at all, so a validly-signed webhook from a repository the attacker owns can write a `Status` row onto a commit belonging to a completely different stack/repository whenever the SHA coincides (e.g. via a fork sharing upstream history). The specific "flip aggregate to success" mechanism described in the question does not work as stated, because `Status::Group#select_significant_status` always prefers non-success statuses (failure/error/pending) over injected success ones, but the underlying authorization gap — unauthorized Status rows contributing to `commit.status` — is real and exploitable in the opposite direction.

### Finding Description
The claimed binding is: every `Status` row that contributes to `commit.status` must be authorized by the org owning `commit.stack.repository` — i.e. `status.commit.stack.repository.full_name == webhook.payload['repository']['full_name']` for every `Status` created from a webhook.

Tracing the code:
- `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`: [1](#0-0) 
resolves target commits purely with `Commit.where(sha: params.sha)`, with no reference to `repository_name`/`stacks` at all.
- Contrast with `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`, which scopes through `stacks.not_archived.where(branch:)` — `stacks` being `Repository.from_github_repo_name(repository_name)&.stacks` defined in `app/models/shipit/webhooks/handlers/handler.rb:32-38`. [2](#0-1) 

So `StatusHandler` is the one handler in this family that skips the repository-ownership check other handlers perform. `create_status_from_github!` then writes the Status against the matched commit's own `stack_id` (`app/models/shipit/commit.rb:165-169`), not the webhook's stated repository, so a webhook that is legitimately signed for repository A can create authoritative `Status` rows on a commit that belongs to Stack B tracking repository B — as long as the SHA in the payload coincides with a commit SHA already tracked by Stack B.

`verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves the payload was signed with the secret for `repository_owner` (taken from the attacker-controlled `payload['repository']['owner']['login']`); it never checks that the referenced `sha` actually belongs to that repository. Per the threat model, the attacker is granted the ability to "emit webhooks from a repository they own," so this check is satisfied trivially for a repository they legitimately control (e.g. a public fork of the repository backing the victim's Stack). Because forking preserves upstream commit SHAs, the attacker can set a GitHub commit status on a shared ancestor commit inside their own fork via the normal GitHub Status API, causing GitHub to deliver a genuinely signed `status` webhook naming the attacker's fork but containing a SHA that also exists as a `Commit` row on the victim's Stack.

Once this reaches `StatusHandler#process`, the unscoped `Commit.where(sha:)` lookup matches the victim's commit and `commit.create_status_from_github!(params)` writes a new `Status` row (`app/models/shipit/status.rb:24-33`, `find_or_create_by!` with an arbitrary attacker-chosen `context`/`state`) attributed to the victim Stack.

Note on the specific "flip to success" claim in the question: `Status::Group#select_significant_status` (`app/models/shipit/status/group.rb:75-83`) always returns a non-success status when one exists — `non_success_statuses.reject(&:pending?).first || non_success_statuses.first`. Adding forged `success` rows alongside a real `pending`/`failure` cannot move the aggregate to `success`; it is proven correct by `test/models/commits_test.rb:779-803` ("status hierarchy" test) which the question itself cites. So the "manipulate to success" direction is not exploitable. The exploitable direction is the reverse: injecting a forged `failure`/`error` status with a new attacker-chosen `context` on a victim commit that is currently `pending` or `success`, which *does* dominate per the same hierarchy, corrupting `commit.state`, `deployable?`, and firing `deployable_status`/`commit_status` webhooks and `ProcessMergeRequestsJob` state transitions (`test/models/commits_test.rb:671-712`, `763-777`) for a repository that never authenticated the payload.

### Impact Explanation
An attacker can write a `Status` row for a stack/repository they do not control, changing that victim commit's aggregate CI state (`commit.state`, `commit.status`, `deployable?`) and triggering downstream side effects (`enable_ci_on_stack`, `schedule_continuous_delivery`, `deployable_status`/`commit_status` webhook emission, `ProcessMergeRequestsJob` enqueue/skip decisions). This is a case of "a payload for one repository mutating another's stack, commit" — matching the Critical impact category. It does not grant RCE or credential exfiltration, but it is a genuine unauthorized cross-tenant write reachable purely by SHA coincidence, repeatable for every shared commit between the attacker's repository and any victim repository/fork relationship.

### Likelihood Explanation
Exploitability depends on the attacker's repository and the victim's tracked repository sharing at least one commit SHA (most realistically via a fork of a publicly tracked upstream repository, which is common for open-source projects onboarded to Shipit) and the attacker being able to have GitHub deliver a `status` webhook for that repository to the same Shipit endpoint (requiring the GitHub App/webhook to be configured for that repository/org, granted per the stated threat model). Given these preconditions, the attacker cost is low (no secrets, one GitHub Status API call) and fully repeatable for any shared SHA and any stack tracking the shared upstream history.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` is scoped: restrict the affected commits to those belonging to stacks resolved from the webhook's own `repository_name`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently filter `Commit.where(sha: params.sha)` by `stack_id: stacks.pluck(:id)` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process does not attach a status to a commit belonging to another stack's repository" do
  victim_stack = shipit_stacks(:shipit)               # tracks "shipit-engine/shipit-engine"
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...)

  attacker_repo_payload = {
    'sha' => victim_commit.sha,
    'state' => 'failure',
    'context' => 'attacker/forged',
    'repository' => { 'full_name' => 'attacker/unrelated-fork' } # attacker's own repo
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_repo_payload)
  end
end
```
Currently this assertion fails: `StatusHandler.call` creates the `Status` row on `victim_commit` regardless of the payload's `repository.full_name`, because `Commit.where(sha: params.sha)` is unscoped by repository/stack ownership.
