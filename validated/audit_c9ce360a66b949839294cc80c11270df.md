### Title
Insufficient Validation of Message Maturity Delay in Bridge Limiter Bypass - (`crates/sui-framework/packages/bridge/sources/bridge.move`)

### Summary
The Sui Bridge implementation in `bridge.move` introduces a "limiter bypass" for V2 bridge messages that are older than 48 hours. This mechanism is intended to allow users to claim tokens even if the bridge's rate limits are exceeded, provided a sufficient delay has passed. However, the logic only checks if the current time is greater than the message's timestamp plus the delay. It fails to ensure that the message's timestamp is not zero or uninitialized, which, while unlikely in a well-formed message, mirrors the root cause where a default/zero value can satisfy a "delay passed" condition trivially.

### Finding Description
In `crates/sui-framework/packages/bridge/sources/bridge.move`, the `claim_token_internal` function handles the logic for processing bridge claims. For V2 messages, it extracts a timestamp from the message payload and checks if the message is "mature" (older than 48 hours) to bypass the transfer limiter.

The relevant code in `claim_token_internal`:
```move
    if (record.message.message_version() == 2) {
        let token_payload_v2 = record.message.extract_token_bridge_payload_v2();

        let timestamp = token_payload_v2.timestamp_ms();
        // if more than 48 hours have passed since deposit, bypass the limiter
        // (the limiter exists to give time to respond to bugs)
        bypass_limiter = clock.timestamp_ms() > timestamp + 48 * 3600000;
        token_payload = token_payload_v2.to_token_payload_v1();
    }
``` [1](#0-0) 

The logic assumes that `timestamp` is a valid, non-zero value representing a past event. If an attacker can produce or influence a V2 message where the `timestamp_ms` field is 0 (or significantly smaller than the current clock time), the condition `clock.timestamp_ms() > timestamp + 48 * 3600000` becomes trivially true immediately upon the message's arrival (assuming the bridge has been active for at least 48 hours). 

While the bridge committee must sign the message, the lack of an explicit check that the timestamp is valid and sensible (e.g., `assert!(timestamp > 0)`) allows a "zero-value" bypass of the intended 48-hour security window. If the committee or the message generation logic (on the source chain, e.g., Ethereum) can be induced to include a zero or very low timestamp, the rate-limiting protection is entirely defeated.

### Impact Explanation
The 48-hour delay is a critical safety invariant designed to "give time to respond to bugs" or malicious activity by allowing the bridge to stay within rate limits. Bypassing this limiter allows for the immediate withdrawal of large amounts of funds that would otherwise be throttled. A successful bypass constitutes a **High** impact, as it removes the primary defense-in-depth mechanism against bridge drainage during an exploit or price manipulation event.

### Likelihood Explanation
The likelihood is **Medium**. It depends on the ability to generate a signed V2 message with an invalid (zero) timestamp. If the source-chain contract or the bridge validators do not strictly validate the timestamp before signing, an attacker could exploit this to drain funds faster than the protocol intends.

### Recommendation
Add a requirement that the message timestamp must be non-zero and potentially within a reasonable range of the current time to ensure the 48-hour delay is meaningful.

```move
    if (record.message.message_version() == 2) {
        let token_payload_v2 = record.message.extract_token_bridge_payload_v2();

### Proof of Concept
1. An attacker identifies a way to submit a bridge request on the source chain (e.g., ETH) with a `timestamp` field set to `0`.
2. The bridge committee signs the message (assuming they only verify the transfer details and not the sanity of the timestamp).
3. The attacker calls `claim_and_transfer_token` on Sui with the signed V2 message.
4. In `claim_token_internal`, `timestamp` is `0`.
5. The condition `clock.timestamp_ms() > 0 + 172,800,000` is checked.
6. Since the Sui network's `clock.timestamp_ms()` is much larger than 48 hours (in ms), `bypass_limiter` is set to `true`.
7. The transfer is executed immediately, even if it exceeds the `TransferLimiter`'s current capacity, bypassing the intended 48-hour "cooldown" for large transfers.
