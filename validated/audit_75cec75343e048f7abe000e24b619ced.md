Based on my investigation, this confirms the analog vulnerability: `sc-chain-spec` (`substrate/client/chain-spec/Cargo.toml`) and `staging-chain-spec-builder` depend on plain `serde_json` **without** the `arbitrary_precision` feature [1](#0-0) , while `sp-genesis-builder` (used on the runtime/wasm side) explicitly enables `arbitrary_precision` [2](#0-1) . Genesis patch/full-config JSON (containing `Balance`/`u128` amounts) is parsed client-side into a `serde_json::Value` in `GenesisSource::resolve` via `json::from_slice`/`json::from_reader` [3](#0-2) , and in `GenesisConfigBuilderRuntimeCaller::get_storage_for_patch`/`get_storage_for_config` the merged `Value` is re-serialized with `serde_json::to_string_pretty` before being sent to the wasm runtime [4](#0-3) .

### Title
Genesis-config JSON balance/amount fields silently lose precision when parsed by `sc-chain-spec`/`chain-spec-builder` without `arbitrary_precision` - ([File: substrate/client/chain-spec/Cargo.toml])

### Summary
`sc-chain-spec` and `staging-chain-spec-builder` parse user-supplied genesis patch/full-config JSON files (which may contain `u128` `Balance` literals, e.g. `balances.balances` entries) using plain `serde_json::Value` without the `arbitrary_precision` feature. `serde_json::Number`, without that feature, can only exactly represent integers that fit in `i64`/`u64`; any JSON integer literal larger than `u64::MAX` (but still a valid `u128` `Balance`, e.g. values in the multi-quintillion+ range) is silently converted to an approximate `f64` during parsing, exactly the "interoperability problem" the DeGate report describes for JSON numbers outside the IEEE-754-safe range.

### Finding Description
`GenesisSource::resolve` (`substrate/client/chain-spec/src/chain_spec.rs:118,123`) deserializes the raw genesis/patch/full-config file bytes into a `GenesisContainer` holding a `Genesis` enum, whose `RuntimeGenesisConfigJson::Config`/`Patch` variants are plain `serde_json::Value` [5](#0-4) . Because `sc-chain-spec`'s `serde_json` dependency does not enable `arbitrary_precision` [1](#0-0) , any JSON number literal exceeding `u64::MAX` in this `Value` tree is stored as a lossy `f64`, not as the original digit string.

Later, `GenesisConfigBuilderRuntimeCaller::get_storage_for_patch`/`get_storage_for_config` merges the patch into the default config `Value` and calls `serde_json::to_string_pretty(&config)` to produce the exact JSON text handed to the runtime's `GenesisBuilder_build_state` wasm entrypoint [6](#0-5) . Once the huge integer has already been rounded to an `f64` approximation during the client-side parse, re-serializing it produces a different decimal string than the one the user (or `chain-spec-builder` operator) originally wrote — even though the runtime-side `sp-genesis-builder` crate itself correctly uses `arbitrary_precision` [2](#0-1) , that protection is defeated because the damage already happened one layer up, in the client tooling that produced the string being fed into the wasm call.

This mirrors the DeGate finding precisely: a value entered by a legitimate user/operator (a `Balance` amount in a genesis patch/full config JSON file, e.g. `substrate/bin/utils/chain-spec-builder/tests/input/patch.json` and the documented patch-file format [7](#0-6) ) is silently reinterpreted with a different numeric value than intended, purely due to a JSON-number-precision boundary that the produced chain spec/genesis storage does not validate against.

### Impact Explanation
If an operator building a chain spec via `chain-spec-builder create ... patch/full <file>.json` (or programmatically via `sc-chain-spec`) supplies a genesis balance, vesting amount, or any other `u128`/`Balance` field whose literal value exceeds `u64::MAX` (~1.8×10^19, well within valid `Balance` range for most runtimes with 12–18 decimal token precision), the resulting genesis storage/chain spec written to disk will silently contain a different (rounded) balance than intended — with no error, warning, or validation failure. This is an integrity/data-corruption issue affecting the genesis state derivation pipeline, not attacker theft of already-issued funds, but it can produce unbacked/mismatched issuance at genesis if undetected (e.g., total issuance computed from unrounded inputs elsewhere while actual per-account balances get rounded).

### Likelihood Explanation
This requires values genuinely close to or above `u64::MAX` (≈1.8×10^19) in a Balance field, which is plausible for high-decimal-precision tokens (e.g., 18-decimal balances representing amounts above ~18 whole tokens can already exceed 2^53, and above ~18.4 whole tokens with 18 decimals exceed `u64::MAX`). It requires no attacker privilege — any operator/user preparing a genesis file is affected — but is a tooling/config-generation-time issue rather than a live-runtime exploit reachable through a signed extrinsic, so likelihood of triggering *unnoticed* corruption depends on whether operators inspect the produced raw storage.

### Recommendation
Enable the `arbitrary_precision` feature for `serde_json` in `sc-chain-spec` (`substrate/client/chain-spec/Cargo.toml`) and `staging-chain-spec-builder`, matching what `sp-genesis-builder` already does, so that large integer literals are preserved exactly as their original digit string end-to-end through parsing, merging, and re-serialization. Alternatively/additionally, follow the DeGate report's short-term recommendation and require `Balance`/large numeric genesis fields to be authored as JSON strings rather than raw JSON numbers, consistent with the pattern already used for RPC-facing `u128` types (`serde_balance` in `substrate/frame/transaction-payment/src/types.rs:118-135` and `NumberOrHex` in `substrate/primitives/rpc/src/number.rs`) [8](#0-7) [9](#0-8) .
