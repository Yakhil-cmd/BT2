### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets any tenant's signed webhook flip status on another tenant's commit and trigger deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by the raw `sha` column alone, with no `stacks`/`repository_name` predicate, unlike every other handler in this engine. Because git commit SHAs are content-addressed and not repository-scoped, an attacker who legitimately owns Repo A can get a real, GitHub-signed `status` webhook delivered for a commit object whose SHA happens to also exist as a tracked commit in an unrelated victim `Stack`, causing that victim commit's status (and potential continuous deployment) to be driven entirely by the attacker's own repository.

### Finding Description
Broken binding: `authenticated_scope(Repo A's stacks via Handler#stacks) == stack_mutated(Commit#stack for the row matched by sha)`. This should always hold but does not.

`StatusHandler#process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This queries `Commit` globally by `sha`, with no join/filter on `repository_name` or the requesting repository's `stacks`. Every other handler in the engine scopes to the authenticated repository via `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks`: [2](#0-1) 

For example `CheckSuiteHandler#process` scopes through `stacks.where(branch: ...)` before touching commits: [3](#0-2) 

`StatusHandler` alone skips this scoping entirely.

`WebhooksController#verify_signature` authenticates only that the payload was signed by the GitHub App/organization owning the *sending* repository (`repository_owner`) — it says nothing about which `Commit`/`Stack` rows the handler is allowed to touch: [4](#0-3) 

Exploit flow: SHA1 commit hashes are derived purely from commit content (tree, parents, author/committer, message, timestamps) — not from which repository stores them. An attacker can fetch the exact victim commit object (`git fetch <public-victim-url> <sha>`) and push that identical object into a branch of their own Repo A (a completely legal git operation on a repo they own). GitHub then delivers a normal, validly-signed `status` webhook event for Repo A with `sha: <victim's sha>, state: 'success'`. `WebhooksController#verify_signature` correctly validates this signature — it is a real, legitimate webhook for Repo A. `StatusHandler#process` then matches `Commit.where(sha: ...)` against the entire `commits` table, finds the victim `Stack`'s row with that SHA (already synced there from the victim's real push history), and calls `commit.create_status_from_github!(params)` on it.

`create_status_from_github!` → `add_status` → new status becomes `success`; `Commit#schedule_continuous_delivery` is invoked as an `after_commit` callback on statuses (via `Status` model / `add_status`), and if the victim `Stack` has `continuous_deployment? == true` and the commit is `deployable?` (`!locked? && (ignore_ci? || (success? && !blocked?))`), `ContinuousDeliveryJob` is enqueued for the victim stack: [5](#0-4) [6](#0-5) 

No existing guard prevents this: `verify_signature` only checks the sender repo's HMAC, not which stack is mutated; the `ExplicitParameters` schema only validates payload shape (`sha`, `state`, etc.), not repository ownership; and `StatusHandler` never calls `stacks` at all, so `Repository.from_github_repo_name` is never consulted for this handler.

### Impact Explanation
A signed webhook authenticated for Repo A causes a status write (`Status` row, `success` state) on a `Commit` belonging to an unrelated victim `Stack`, and — if that stack has `continuous_deployment: true` — enqueues `ContinuousDeliveryJob` for that stack, driving an unauthorized deploy of the victim's already-merged code, triggered and timed entirely by the attacker. This is a cross-tenant write ("a payload for one repository mutating another's stack/commit") and an unauthorized deploy trigger, matching the Critical impact category. Blast radius: any Shipit-hosted stack whose head commit SHA is publicly observable (which is nearly always true for public GitHub repos) is at risk from any other onboarded tenant of the same Shipit instance.

### Likelihood Explanation
Preconditions: attacker must own/control at least one repository already onboarded as a Shipit stack (so their webhook is validly signed), and the victim stack must have `continuous_deployment: true` for the deploy trigger to fire (status corruption alone occurs regardless). Attacker cost is low: fetching and re-pushing a known public commit object into an owned repo, then letting GitHub deliver the resulting status webhook (or triggering their own CI on that commit) — no secrets, no privileged role, no social engineering required. This is repeatable against any stack whose commit SHAs are publicly known.

### Recommendation
Scope `StatusHandler#process` to the requesting repository's own stacks/commits, mirroring `CheckSuiteHandler` and other handlers: resolve `stacks` via `Handler#stacks` (backed by `repository_name` from the payload) and restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalent `Commit.where(stack_id: stacks.select(:id), sha: params.sha)`), instead of a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "cross-tenant sha collision lets a foreign repo's status flip a victim stack's commit and schedule CD" do
          victim_stack = shipit_stacks(:shipit) # unrelated to attacker repo
          victim_stack.update!(continuous_deployment: true, ignore_ci: false)
          shared_sha = "deadbeefcafefeed0000000000000000000000"
          victim_commit = victim_stack.commits.create!(
            sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus),
            authored_at: Time.now, committed_at: Time.now, message: "victim commit"
          )

          # Payload as authenticated/signed for attacker's OWN repo ("attacker/repoA"),
          # not victim_stack's repository, but with the victim's sha re-declared.
          payload = {
            "sha" => shared_sha,
            "state" => "success",
            "context" => "ci",
            "repository" => { "full_name" => "attacker/repoA" }
          }

          assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack]) do
            StatusHandler.new(payload).process
          end

          assert_predicate victim_commit.reload, :success?
        end
      end
    end
  end
end
```
Both sides of the binding: `stacks_authenticated_for_request = Repository.from_github_repo_name("attacker/repoA")&.stacks` (does NOT include `victim_stack`) vs. `stack_actually_mutated = victim_commit.stack` (IS `victim_stack`) — they differ, proving the violation, and the enqueued `ContinuousDeliveryJob` demonstrates the unauthorized-deploy impact.
