### Title
Webhook signature is verified for one GitHub organization while the event is applied to a repository/commit taken from unvalidated payload fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to check the HMAC signature against using `repository_owner`, a value read straight out of the untrusted JSON body. Once the signature check passes, the raw, unconstrained payload is handed to event handlers that resolve the *actual* repository/commit to act on from other fields of that same payload (`repository.full_name`, or in `StatusHandler`'s case, a bare commit SHA with no repository filter at all). Nothing re-derives or cross-checks that the organization whose secret validated the signature is the same organization/repository the handler ultimately mutates.

### Finding Description
`verify_signature` picks the GitHub App configuration to validate against like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

`repository_owner` is derived purely from attacker-controlled JSON: [2](#0-1) 

After the signature check passes, `create` dispatches the entire parsed payload to handlers without any additional binding between the "authenticated" `repository_owner` and the data the handler subsequently acts on: [3](#0-2) 

Handlers resolve their target independently from other payload keys. `Handler#repository_name` uses `repository.full_name`, a separate field from `repository.owner.login`: [4](#0-3) 

`StatusHandler` is the most severe case — it applies the incoming CI status to **every** `Commit` row in the database matching the given SHA, with no repository/organization scoping whatsoever: [5](#0-4) 

Because a Shipit instance can be configured with multiple GitHub Apps/organizations (`Shipit.github_organizations`, `github_app_config`), and `verify_webhook_signature` returns `true` unconditionally whenever an organization's `webhook_secret` is blank/unset: [6](#0-5) 

any org whose signature check can be satisfied (secret known to the attacker, or left blank as shown as an accepted config in `docs/setup.md` and `config/secrets.development.shopify.yml`) lets the attacker submit a payload where `repository.owner.login` == that org (so the signature check passes) while `repository.full_name` / `sha` reference a completely different organization's stack/commit. The equality the code should enforce — *organization whose secret validated the signature* == *organization/repository the handler is about to mutate* — is never checked.

### Impact Explanation
This is an authentication-bypass class issue: signing for organization A is treated as authorization to write into organization B's Shipit state.
- Via `StatusHandler`, an attacker who can produce *any* valid signature (e.g., because their own org's `webhook_secret` is configured/blank on this multi-tenant instance) can mark an arbitrary commit SHA belonging to any other tracked repository as `success`, satisfying `deployable?`/CI-gating logic used by continuous deployment (`Stack.schedule_continuous_delivery`, `ContinuousDeliveryJob`) — resulting in an unauthorized deploy of a repository the attacker never had rights over.
- Via `PushHandler`, forging `repository.full_name` to point at a different, tracked repository triggers `GithubSyncJob`/`sync_github` for that stack using attacker-supplied `after` SHA, again outside the authenticated organization's scope.
- `MembershipHandler` similarly trusts `organization.login`/`team`/`member.login` from the body to add arbitrary users to arbitrary teams once *some* org's signature validates, potentially escalating into `Shipit.github_teams` authorization used by `Authentication#force_github_authentication`.

This matches the Critical/High bar: unauthorized deploy and escalation into `Shipit.github_teams` authorization.

### Likelihood Explanation
Requires the attacker to be able to produce a valid `X-Hub-Signature` for *some* organization configured on the instance — either because that org's `webhook_secret` was left unset (a documented, accepted configuration state per `docs/setup.md`/`config/secrets.development.shopify.yml`), or because the attacker legitimately controls that organization's own GitHub App webhook delivery and can freely author the JSON body it sends (GitHub does not constrain what an App's webhook payload contains beyond what the App's own event triggers, and Shipit does no further validation). No `ApiClient` token, GitHub session, or repository write access is needed — only network access to `/webhooks` and control (or absence) of one configured org's webhook secret, satisfying the "unprivileged attacker" bar.

### Recommendation
After computing the authenticated organization from the signature, re-derive the acted-upon repository/organization strictly from the same trusted source and reject the request if the handler's target repository/organization does not match the organization whose secret validated the signature. Specifically:
- Bind `PushHandler`/other repo-scoped handlers to `repository_owner` (verified) rather than independently trusting `repository.full_name`.
- Scope `StatusHandler`'s `Commit.where(sha:)` lookup by the stack(s) belonging to the authenticated organization's repositories, not globally.
- Reject webhooks where `repository.owner.login` differs from the organization that validated the signature.

### Proof of Concept
1. Shipit instance configured with two GitHub orgs, `AttackerOrg` (webhook secret known to/controlled by attacker, or left blank) and `VictimOrg` (tracked stack with continuous deployment enabled).
2. Attacker POSTs to `/webhooks` with `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "AttackerOrg/whatever" },
  "sha": "<victim commit sha>",
  "state": "success"
}
```
signed with `AttackerOrg`'s webhook secret (or unsigned if blank).
3. `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and succeeds.
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the victim's commit (belonging to `VictimOrg`'s stack), and calls `create_status_from_github!`, marking it deployable — independent of `AttackerOrg` having any relationship to `VictimOrg`'s repository. [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
