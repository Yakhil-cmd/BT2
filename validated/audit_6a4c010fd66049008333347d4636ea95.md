### Title
Bridge KAIA Transfer Permanently Blocked by Reverting Recipient — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge updates all nonce-tracking state before attempting the actual KAIA transfer to `_to`. If `_to` is a contract whose `receive()` or fallback reverts, the `require(ok, "handleKLAYTransfer: transfer failed")` causes the entire transaction to revert, rolling back every state mutation. Because there is no alternative path (no emergency-skip, no fallback recipient), operators can never advance past that nonce, permanently locking the bridged KAIA and freezing `lowerHandleNonce` and `recoveryBlockNumber`.

---

### Finding Description

In `handleKLAYTransfer`:

```solidity
_setHandledRequestTxHash(_requestTxHash);          // (1) marks tx handled
handleNoncesToBlockNums[_requestedNonce] = ...;    // (2) records block
_updateHandleNonce(_requestedNonce);               // (3) advances nonces

emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");          // (4) external call
require(ok, "handleKLAYTransfer: transfer failed");// (5) reverts all of (1-3) on failure
``` [1](#0-0) 

Steps (1)–(3) write to `handledRequestTx`, `handleNoncesToBlockNums`, `lowerHandleNonce`, `upperHandleNonce`, and `recoveryBlockNumber`. Step (5) reverts all of them atomically when `_to` refuses KAIA. The Solidity 0.5.6 `.call.value()` forwards all remaining gas, so any reverting or gas-exhausting `receive()` in `_to` triggers this path.

`_updateHandleNonce` advances `lowerHandleNonce` only through a contiguous run of filled `handleNoncesToBlockNums` entries:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [2](#0-1) 

Because nonce N's entry is never written (the write is reverted), the loop halts at N on every subsequent call, leaving `lowerHandleNonce` and `recoveryBlockNumber` permanently frozen at N.

The same pattern exists in `handleERC20Transfer` (non-mintBurn mode): `safeTransfer` reverts if the bridge holds insufficient ERC20 balance, producing the same nonce freeze. [3](#0-2) 

---

### Impact Explanation

- **KAIA permanently locked**: The `_value` KAIA is held in the bridge contract and can never be released to `_to` or returned to the sender. No operator function exists to redirect or reclaim it.
- **Bridge nonce state corrupted**: `lowerHandleNonce` is frozen at N. `recoveryBlockNumber` never advances past the block preceding N. The value-transfer recovery subsystem (`VTRecovery`) re-scans from that stale block on every cycle.
- **Subsequent nonces unaffected for execution but recovery is broken**: Higher nonces can still be individually handled, but `lowerHandleNonce` never catches up, so the recovery window (`lowerHandleNonce + 200`) drifts and the recovery system's hint becomes permanently stale.

This satisfies the allowed impact gate: bridged KAIA is permanently locked, and the bridge's protected nonce/recovery state is irreversibly corrupted.

---

### Likelihood Explanation

Any user on the source chain who specifies a `_to` address that is a contract without a payable fallback (e.g., a multisig, a proxy, or a deliberately crafted griefing contract) triggers this path. No special privilege is required. The attacker forfeits their source-chain KAIA but permanently disrupts the bridge's nonce accounting. Accidental triggering (e.g., a user bridging to a smart-contract wallet that lacks `receive()`) is also realistic.

---

### Recommendation

Mirror the external bug's recommended fix: separate the asset transfer from the nonce-state update, and provide a fallback path when the transfer fails.

1. **Commit nonce state unconditionally** before the external call (or use a try/catch pattern).
2. **On transfer failure**, emit a `TransferFailed` event and send the KAIA to a designated recovery address (e.g., the bridge owner or a treasury), rather than reverting the entire transaction.
3. Alternatively, add an operator-callable `skipHandleNonce(uint64 nonce)` that marks a nonce as handled without transferring, allowing `lowerHandleNonce` to advance past a permanently stuck entry.

---

### Proof of Concept

1. Deploy a contract `Rejecter` with `receive() external payable { revert(); }`.
2. On the source chain, call `requestKLAYTransfer(address(Rejecter), value, "")` — this locks `value` KAIA in the source bridge and emits `RequestValueTransfer(nonce=N)`.
3. Bridge operators observe the event and call `handleKLAYTransfer(..., address(Rejecter), value, N, ...)` on the destination bridge.
4. The `_to.call.value(value)("")` call returns `ok = false`; `require(ok, ...)` reverts the transaction.
5. All state writes (`handledRequestTx[txHash]`, `handleNoncesToBlockNums[N]`, `lowerHandleNonce`) are rolled back.
6. Operators retry indefinitely; every attempt reverts identically.
7. Observe: `lowerHandleNonce` remains at N; `recoveryBlockNumber` remains at the block before N; `value` KAIA is permanently locked in the destination bridge. [4](#0-3) [5](#0-4)
