### Title
Asset definer can unilaterally rotate the `spender_attested` attestor list to permanently freeze or gate all holders' funds - ([File: validation.js])

### Summary
An Obyte asset can be created with `spender_attested: true`, which requires every address that spends the asset to be attested by one of a whitelisted set of attestor addresses declared for that asset [1](#0-0) . The list of attestors is not fixed at asset creation: the asset's `definer_address` can publish an `asset_attestors` message at any time, with no cooldown, no notice, and no on-chain constraint tying it to the previous list, and the network always uses only the *latest* attestor list when deciding whether a spender is attested [2](#0-1) [3](#0-2) .

### Finding Description
When `spender_attested` is set on an asset, the payment validator requires the payer's address to appear in `attestations` issued by one of the addresses in the asset's *current* attestor list before a transfer/issue is accepted [4](#0-3) . The current list is looked up by finding the most-recently-published `asset_attestors` (or the initial `asset` definition) unit for that asset and reading only the attestors listed there [3](#0-2) , and then filtering addresses by attestations that were issued by one of *that* list's `attestor_address` values [5](#0-4) .

The only check performed when an `asset_attestors` update is submitted is that the sender is the asset's `definer_address` and that the new list is well‑formed (sorted, valid addresses, under `MAX_ATTESTORS_PER_ASSET`) [2](#0-1) [6](#0-5) . There is no restriction preventing the definer from:
- Replacing all attestors with new addresses the definer controls, invalidating every attestation previously relied upon by existing holders (since `filterAttestedAddresses` only matches attestations from addresses currently in the list) — this freezes every holder's ability to spend until they can somehow get re-attested by the new (definer-controlled) attestors.
- Selectively re-attesting only addresses favorable to the definer (e.g., addresses the definer controls) while withholding attestation from other holders, effectively locking competitors' balances forever while the definer's own funds remain spendable.

This mirrors the reported bug class: a privileged role (here, the asset "definer", who is trusted implicitly by anyone who accepts/holds the asset) can, after the fact, swap out a critical authorization dependency (the attestor set / "oracle" of who is allowed to spend) to rug or freeze users, exactly as an admin swapping a `feeBurner` or oracle address can steal fees or corrupt price checks in the referenced report.

### Impact Explanation
Any holder of a `spender_attested` asset can have their funds permanently frozen (or selectively frozen while the definer's own associates remain spendable) purely by the definer publishing a new `asset_attestors` message. Since this only requires a single signed unit from the definer address and no timelock/governance delay exists, it is a concrete, unilateral fund-freezing/rug vector for any asset relying on this attestation mechanism, which is a mainline supported ocore feature (not a hub/peer/node compromise, but a feature reachable by an ordinary asset issuer address). This qualifies as AA/asset-issuer fund freezing under the accepted impact categories.

### Likelihood Explanation
High for any asset that opts into `spender_attested`. The action requires nothing more than the definer signing and broadcasting a normal `asset_attestors` unit — a capability explicitly exposed via `composeAssetAttestorsJoint` [7](#0-6)  and reachable by any wallet that created the asset. No special network position or hub/peer trust is required, and validation imposes no restriction beyond "sender is the definer."

### Recommendation
- Do not retroactively invalidate previously valid attestations when the attestor list changes: consider matching attestations against the attestor list that was current when the attestation was issued (or when the funds were received), rather than only the latest list.
- Require a minimum notice period / timelock before an `asset_attestors` update becomes effective, giving holders time to react.
- Consider capping how often (or whether at all) attestors can be fully replaced versus only added, and emit clear warnings in asset metadata/wallets that `spender_attested` assets carry this admin-freeze risk so holders can evaluate trust in the definer before acquiring the asset.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true` and `attestors: [X]` [8](#0-7) .
2. Attestor `X` attests holder `H`; `H` receives and later holds asset `A` under the belief that being attested by `X` lets them spend indefinitely.
3. Definer publishes `asset_attestors` message via `composeAssetAttestorsJoint(definer_address, A, [Y])`, replacing `X` with an attestor `Y` the definer controls but who never attests `H` [7](#0-6) .
4. On the next `validatePayment` for `H`'s output of asset `A`, `storage.readAsset` resolves the attestor list to `[Y]` (the latest `asset_attestors` unit) [3](#0-2) , `filterAttestedAddresses` finds no attestation of `H` by `Y` [5](#0-4) , and `validatePayment` rejects `H`'s spend with `"none of the authors is attested"` [4](#0-3) , permanently freezing `H`'s balance unless the definer's chosen attestor `Y` chooses to attest them.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
