## Confirmed root cause

`StatusHandler#process` (and `PushHandler`, `CheckSuiteHandler`, etc.) trust the webhook payload's `repository.full_name` to select which `Stack`/`Commit` records to mutate [1](#0-0) , while `WebhooksController#verify_signature` selects which HMAC secret to verify against using a *different* payload field, `repository.owner.login` (falling back to `organization.login`) — also attacker-supplied, unauthenticated JSON [2](#0-1) [3](#0-2) . Critically, `verify_webhook_signature` short-circuits to `true` whenever the resolved GitHub App/organization has no `webhook_secret` configured: `return true unless webhook_secret` [4](#0-3) .

This breaks exactly the binding the task asks about: **the organization that authenticated ≠ the repository that is written**. An attacker who knows (or guesses) that *some* configured GitHub organization/App in this Shipit install has no `webhook_secret` set (a supported, documented configuration — not a leaked secret) can send an unauthenticated POST to `/webhooks` claiming `repository.owner.login` = that unsecured org, while setting `repository.full_name`/`sha` to name a commit belonging to an entirely different, secured stack. Because `verify_signature` only checks the secret keyed by the org name pulled from the payload, and never cross-checks that the acted-upon `repository.full_name` actually belongs to that same organization, the request passes verification and `StatusHandler` will create arbitrary CI statuses (`success`) for arbitrary commits: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . Since `Commit#deployable?` is gated on CI statuses, this can make an otherwise-non-deployable commit deployable, enabling an unauthorized deploy — one of the accepted High-impact categories.

I could not fully verify, within available tool budget, how `Shipit.github(organization:)` resolves configured organizations/secrets from `lib/shipit.rb` (the relevant methods were only partially inspected), nor whether the engine enforces a global minimum of one non-blank `webhook_secret` across all configured orgs. Confirming exploitability in a real deployment requires checking the host application's `secrets.yml`/GitHub App configuration, which is outside this engine's own code and cannot be settled by static analysis alone.

### Title
Webhook status/push handlers trust attacker-controlled `repository.full_name` independently of the organization whose secret validated the signature - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to check based on `repository.owner.login`/`organization.login` taken from the unauthenticated JSON body, but the handlers that actually mutate state (`StatusHandler`, `PushHandler`, `CheckSuiteHandler`, etc.) resolve the target `Stack`/`Commit` using a separate field, `repository.full_name`, from the same untrusted body. No code ties these two fields together, so the "authenticated organization" and the "repository being written to" are never proven to be the same entity.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and fetches `Shipit.github(organization: repository_owner)` to obtain the app-specific `webhook_secret` [2](#0-1) [3](#0-2) . `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that app's `webhook_secret` is blank [4](#0-3) . Once verification passes, `create` dispatches the *entire raw payload* — including `repository.full_name`, `sha`, and `state` — to the handler chain [6](#0-5) . `Handler#stacks`/`#repository_name` resolve the affected `Stack` purely from `payload.dig('repository', 'full_name')` [1](#0-0) , with zero cross-check against `repository_owner`, the value that actually gated signature verification. `StatusHandler` and `PushHandler` then write commit statuses / trigger syncs for whatever repo the attacker names in `full_name` [5](#0-4) [7](#0-6) .

### Impact Explanation
An attacker able to find any configured organization/App on the Shipit instance with a blank `webhook_secret` can forge a `status` event that fabricates a `success` CI status on an arbitrary commit belonging to a *different, protected* repository/stack, which feeds directly into `Commit#deployable?`. This can enable an unauthorized deploy of a commit that never actually passed CI — matching the accepted High-impact class "unauthorized deploy". It can also spuriously trigger `GithubSyncJob`/`RefreshCheckRunsJob` for stacks unrelated to the authenticating organization.

### Likelihood Explanation
Likelihood is Low/Medium: it requires the deployment to have at least one configured GitHub organization/App with `webhook_secret` left blank (a real, supported configuration path in the code, not a hypothetical), and requires the attacker to know or guess that org's login and a target commit SHA. No GitHub App private key, session, or API token is needed — only unauthenticated HTTP access to `/webhooks`.

### Recommendation
Bind the two fields together: after selecting the signing organization from the payload, verify that `repository.full_name`'s owner matches `repository_owner` (or, better, resolve the target repository/stack strictly from the same field used to select the signing secret) before handlers act on it. Additionally, consider rejecting webhook events entirely when the resolved GitHub App has no `webhook_secret` configured, rather than treating a blank secret as "verification passed."

### Proof of Concept
1. Configure (or find) two GitHub Apps/organizations in the Shipit deployment: `org-unsecured` (no `webhook_secret`) and `org-protected` (has a stack tracking commit `abc123...` that is not yet CI-passing).
2. POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature`, body:
```json
{
  "repository": { "owner": { "login": "org-unsecured" }, "full_name": "org-protected/some-repo" },
  "sha": "abc123...",
  "state": "success",
  "context": "ci/forged",
  "branches": [{"name": "master"}]
}
```
3. `verify_signature` resolves `Shipit.github(organization: "org-unsecured")`, whose `webhook_secret` is blank, so verification passes.
4. `StatusHandler` matches `Commit.where(sha: "abc123...")` (which belongs to `org-protected`'s stack) and creates a `success` status, potentially flipping `deployable?` to true and enabling an unauthorized deploy.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
