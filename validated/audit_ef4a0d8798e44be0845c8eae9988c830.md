### Title
Api Client Token Scope Bypass in CCMenu Endpoint Allows Cross-Stack Deploy-State Disclosure - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the shared stack-resolution helper in a way that removes the scoping check every other API endpoint relies on, letting a stack-scoped `ApiClient` token read the CI/deploy status of any stack in the installation, not just the one it was issued for.

### Finding Description
Every other API controller resolves the target stack through `BaseController#stack`, which is scoped by the authenticated client: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the client is scoped to a stack (`current_api_client.stack_id?`), and `stack` looks the requested `params[:stack_id]` up only within that restricted set — this is the binding: *token's authorized stack == stack the request may touch*.

`CCMenuController` breaks that binding by redefining `stack` to bypass the scoped `stacks` relation entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` directly against the global `Stack` model, ignoring `current_api_client.stack_id`. The only gate left is `require_permission :read, :stack`, which calls `current_api_client.check_permissions!(operation, scope)`: [3](#0-2) 
That check only verifies the client has the `read:stack` *permission string* — it never checks that the specific stack being requested matches `current_api_client.stack_id`. So a token created scoped to Stack A (e.g. via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(stack: stack_a, ...)`, as done for the CCMenu client in `CCMenuUrlController`) can be replayed with any other stack's `stack_id` param.

### Impact Explanation
This is a stack-scope escalation: an attacker holding a legitimately-issued, narrowly-scoped `read:stack` token for one stack can use it to read deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) for every other stack managed by the Shipit instance, including stacks they were never granted access to. This matches the High-impact class of "escalation into authorization scope / unauthenticated read of stack state" since the token holder is authenticated only for a narrower resource than what they can read.

### Likelihood Explanation
Exploitation requires only possession of a valid, stack-scoped CCMenu token (these tokens are routinely generated and distributed for CI dashboard integrations via `CCMenuUrlController`) and knowledge/guessing of another stack's `to_param` (owner/repo/env/branch — largely public/discoverable information). No privileged account, GitHub App key, or session is required beyond the token itself, so likelihood is high among any party that has been issued (or leaks) one such token.

### Recommendation
Remove the `stack` override in `CCMenuController` and use the inherited, scope-aware `stack` method from `BaseController` (or explicitly re-check `stacks.exists?(id: requested_stack.id)` before rendering), so a stack-scoped `ApiClient` can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. Obtain (or be issued) a CCMenu URL/token scoped to `stack_a` via `CCMenuUrlController#fetch`, which creates an `ApiClient` with `permissions: %w[read:stack]` and `stack: stack_a`: [4](#0-3) 
2. Send `GET /api/:stack_b_id/ccmenu.xml?token=<stack_a_token>` where `stack_b` is a different, unrelated stack.
3. `authenticate_api_client` accepts the token (valid signature) and sets `current_api_client` to the `stack_a`-scoped client: [5](#0-4) 
4. `require_permission :read, :stack` only checks that `read:stack` is in the client's permission list, not which stack — it passes.
5. `stack` resolves `stack_b` directly via `Stack.from_param!`, bypassing the `current_api_client.stack_id` restriction, and the controller renders `stack_b`'s deploy status XML — data the token was never authorized to see.
