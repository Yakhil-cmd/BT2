Confirmed. Route `GET /api/stacks/*stack_id/ccmenu` maps to `Shipit::Api::CCMenuController#show` [1](#0-0) , and this controller bypasses the standard stack-scoping mechanism.

### Title
Stack-scoped ApiClient tokens can read any stack's CCMenu deploy status via unscoped `stack` lookup - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's `stack` accessor to bypass the `ApiClient` stack-scoping check, allowing a token that is authorized only for one stack to read the deploy/build state of any stack in the installation.

### Finding Description
The base API controller enforces per-token stack scoping through two cooperating methods: `stacks`, which restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` has a `stack_id` set, and `stack`, which resolves the requested resource through that scoped relation via `stacks.from_param!(params[:stack_id])` [2](#0-1) . Every other API controller that needs a single stack (e.g. `StacksController`, `LocksController`) relies on this inherited, scoped `stack` method.

`CCMenuController`, however, defines its own private `stack` method that queries `Stack.from_param!(params[:stack_id])` directly against the whole `Stack` table, completely skipping the `stacks` scoping relation [3](#0-2) . The controller only checks `require_permission :read, :stack`, which merely verifies the token's permission list contains `read:stack` via `ApiClient#check_permissions!` [4](#0-3) ; it never checks whether the requested stack matches `current_api_client.stack_id`.

This breaks the intended binding: `stack a token authorizes == stack it touches`. An `ApiClient` created with `stack: <Stack A>` (as seen in the `here_come_the_walrus` fixture used across the test suite) and `permissions: ['read:stack']` is meant to only see Stack A, per the assertions in `StacksControllerTest` ("an api client scoped to a stack will only see that one stack") [5](#0-4) . But because `CCMenuController#stack` doesn't go through `stacks`, that same token can supply any other stack's `stack_id` in the URL and successfully render its CCMenu XML.

Authentication for this endpoint is also token-in-query-string based: `authenticate_api_client` is overridden to accept `params[:token]` directly (used for polling tools like CCTray/CCMenu clients that can't send Basic-Auth headers) [6](#0-5) , and the route is `GET /api/stacks/*stack_id/ccmenu` [1](#0-0) .

### Impact Explanation
Any holder of a legitimately-issued, stack-scoped `ApiClient` token with `read:stack` permission can enumerate and read the deploy/build state (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`) of every stack on the Shipit instance, not just the one it was provisioned for, by changing the `stack_id` path segment. This is an authorization-scope escalation: it crosses the trust boundary between "stack a token authorizes" and "stack it touches", yielding unauthorized read of stack/deploy state, matching the High-impact class of "unauthenticated read of stack state, task streams or deploy output" (here achieved with a token that is authenticated but not authorized for the target stack).

### Likelihood Explanation
Any project that issues narrowly-scoped `ApiClient` tokens (e.g. to give a third-party CI dashboard or a specific team read access to only its own stack) is affected as soon as that token is used, since CCMenu is a documented, routed, unauthenticated-header endpoint intended for polling tools. No special privileges beyond possessing one valid stack-scoped token are required, and exploitation is a single unauthenticated-style GET request with a different `stack_id`.

### Recommendation
Remove the `CCMenuController#stack` override and rely on the inherited, scoped `stack`/`stacks` methods from `BaseController` so that stack-scoped tokens can never resolve a stack outside `current_api_client.stack_id`, matching the behavior of every other stack-scoped controller.

### Proof of Concept
1. Create an `ApiClient` with `stack: <Stack A>` and `permissions: ['read:stack']`, obtaining its `authentication_token`.
2. Send `GET /api/stacks/<OrgB>/<RepoB>/<envB>/ccmenu?token=<token>` where `<OrgB>/<RepoB>/<envB>` is a different stack the token was never scoped to.
3. Observe the response renders `shipit/ccmenu/project` with Stack B's `lastBuildStatus`/`lastBuildLabel`/`activity`, per `CCMenuController#show` [7](#0-6) , despite the token being scoped to Stack A only, whereas the same token against `StacksController#show` (which uses the scoped `stack` method) would 404/scope-fail for Stack B.
