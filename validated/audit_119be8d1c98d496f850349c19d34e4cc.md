### Title
`OpenedHandler#provision?` operator-precedence bug lets `review_stacks_enabled: false` repos create review stacks that `UnlabeledHandler` can never archive - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` uses `&&`/`||` without parentheses so `review_stacks_enabled` is only bound to the `allow_all` clause, not to the `allow_with_label`/`prevent_with_label` clauses, letting a PR author create (and enqueue for provisioning) a review stack even when the operator has set `review_stacks_enabled = false`. `UnlabeledHandler#respond_to_label_change?` correctly ANDs `review_stacks_enabled` across the whole condition, so once such a stack exists it can never be archived by removing the label, leaving it permanently `awaiting_provision`.

### Finding Description
The claimed binding, stated as an equality: `review_stacks_enabled` consulted in `OpenedHandler#provision?` (creation) must equal `review_stacks_enabled` consulted in `UnlabeledHandler#respond_to_label_change?` (teardown) for the same `Shipit::Repository` row — and it does not, because the two methods parenthesize the same boolean expression differently.

`OpenedHandler#provision?`: [1](#0-0) 
Ruby's `&&`/`||` precedence makes this `(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present?) || (prevent_with_label? && !label_present?)`. `review_stacks_enabled` is only ANDed into the first disjunct. If `provisioning_behavior == "allow_with_label"` and the provisioning label is present, `provision?` is `true` **regardless of `review_stacks_enabled`**, so `respond_to_pull_request_opened?` returns true and `ReviewStackAdapter#find_or_create!` creates the stack and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [2](#0-1) 

`UnlabeledHandler#respond_to_label_change?`, by contrast, correctly ANDs `review_stacks_enabled` over the entire expression: [3](#0-2) 

Exploit flow: an attacker opens a PR against a repository whose operator has configured `review_stacks_enabled = false`, `provisioning_behavior = "allow_with_label"` (intending review stacks to be fully off), and applies the repo's provisioning label to their own PR (`labeled` action is not required for creation — the label just needs to be present on the `opened` payload). `OpenedHandler` creates and enqueues the stack due to the precedence bug. The attacker then removes the label (`POST /webhooks` with a `pull_request` `unlabeled` event). `UnlabeledHandler#respond_to_label_change?` evaluates `review_stacks_enabled` (`false`) ANDed with everything else, short-circuits to `false`, and `process` no-ops — `archive?`/`unarchive?` are never evaluated and `stack.archive!`/`remove_from_provisioning_queue` are never called: [4](#0-3) 

The stack remains `awaiting_provision: true` / `provision_status: deprovisioned` and is picked up by `Shipit::ReviewStackProvisioningQueue#work`, which calls `stack.provisioner.provision?` / `stack.provision` on it: [5](#0-4) 

No existing guard catches this: `respond_to_pull_request_opened?`/`provision?` do not re-check `review_stacks_enabled` outside the buggy expression, there is no model validation on `Repository#provisioning_behavior` vs `review_stacks_enabled` combination, and `LabeledHandler`/`ReopenedHandler` share the exact same unparenthesized precedence bug (`repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || …`), so re-labeling or reopening does not self-correct the state either.

### Impact Explanation
The operator's explicit `review_stacks_enabled = false` policy for a repository is not enforced when `provisioning_behavior == "allow_with_label"`: any PR author who can apply the repository's provisioning label to their own PR (a normal, unprivileged PR action) can force creation of a `Shipit::ReviewStack`, queue it for provisioning, and — once created — it is permanently stuck `awaiting_provision`/undeprovisionable via the `unlabeled` webhook path, since `UnlabeledHandler` will never act while `review_stacks_enabled` stays `false`. This does not cross repository boundaries (it's confined to the misconfigured repository) and does not directly leak secrets or grant `Shipit.github_teams` access, so it sits below the Critical/High bar defined for this audit (no forged auth, no cross-tenant mutation, no confirmed RCE/secret exfiltration demonstrated purely from this logic bug); it is a policy-bypass / stuck-resource logic defect rather than an authentication or command-execution bypass as scoped by the rules.

### Likelihood Explanation
Preconditions are narrow but realistic: the operator must set `review_stacks_enabled = false` together with `provisioning_behavior = "allow_with_label"` (an internally inconsistent but permitted configuration state, since nothing in `Repository` validates the combination). The attacker needs only the ability to open a PR and apply the configured provisioning label, both ordinary unprivileged actions on a PR they control, and no secrets or elevated permissions are required. This is fully repeatable per PR against the same misconfigured repository.

### Recommendation
Parenthesize `review_stacks_enabled` across the full boolean expression in `OpenedHandler#provision?`, `LabeledHandler#respond_to_label_change?`/`archive?`/`unarchive?`, `UnlabeledHandler`, and `ReopenedHandler#unarchive?` consistently, e.g. `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && label_present?) || (prevent_with_label? && !label_present?))`, so `review_stacks_enabled` is a hard gate for every handler and every provisioning-behavior branch.

### Proof of Concept
minitest plan (extends `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` and `unlabeled_handler_test.rb` style):
1. Configure `repository.review_stacks_enabled = false`, `provisioning_behavior = :allow_with_label`, `provisioning_label_name = "pull-requests-label"`.
2. Assert the binding before: `repository.review_stacks_enabled == false` on both the creation path and the removal path (same repository row).
3. Call `OpenedHandler.new(payload_with_label).process` with the label present in `pull_request.labels`; assert `Shipit::Stack.count` increased by 1 (demonstrating the precedence bug bypasses `review_stacks_enabled == false`), and `stack.awaiting_provision? == true`.
4. Call `UnlabeledHandler.new(payload_without_label).process` for the same PR/repository.
5. Assert `stack.reload.archived? == false` and `stack.reload.awaiting_provision? == true` — proving the same `review_stacks_enabled == false` value that failed to block creation now (correctly, but inconsistently) blocks teardown, leaving the erroneously-created stack permanently queued.
