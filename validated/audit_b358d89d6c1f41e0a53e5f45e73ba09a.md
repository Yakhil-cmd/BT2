### Title
Resource exhaustion via decompression-bomb in private-textcoin ZIP payload accepted from an untrusted counterparty - (File: wallet.js)

### Summary
`wallet.js`'s `handlePrivatePaymentFile()` decompresses an attacker-supplied ZIP file (`private_textcoin`) sent by a private-payment counterparty, guarding against oversized output only by trusting the ZIP's *declared* `uncompressedSize` metadata before calling `entry.async("string")`, which performs the actual inflate. This mirrors the `jose` CVE-2024-28176 pattern: a size/limit check performed on attacker-controlled metadata rather than during/after the actual decompression, allowing a compression-ratio bomb to bypass the guard and exhaust CPU/memory.

### Finding Description
`handlePrivatePaymentFile()` loads a ZIP received as a "textcoin" payment file and unconditionally decompresses the `private_textcoin` entry: [1](#0-0) 

The only safeguard is:
```js
if (entry._data && entry._data.uncompressedSize > 100 * 1024 * 1024)
    return cb("private_textcoin entry is too large");
```
This value comes from the ZIP's own local-file-header/central-directory metadata, which is fully attacker-controlled — the sender who crafts the ZIP chooses what `uncompressedSize` to declare. Nothing enforces that this declared value matches the amount of data `zlib`'s inflate will actually emit during `entry.async("string")`, so a maliciously crafted archive with a small declared size but an extremely high real compression ratio (a classic decompression bomb) can pass the check and still force the wallet to decompress an unbounded amount of data into memory/JSON.parse.

The path is reachable by an unprivileged private-payment counterparty: a textcoin sender creates the ZIP via `storePrivateAssetPayload()` (same function family, using JSZip DEFLATE) and delivers it to the victim (e.g. as a file attachment tied to a textcoin claim link), and the victim's wallet calls `handlePrivatePaymentFile()` to process it, which then feeds the parsed content into `handlePrivatePaymentChains()`: [2](#0-1) 

### Impact Explanation
A malicious private-payment counterparty can cause the recipient wallet to consume excessive CPU and memory while decompressing/parsing the crafted archive, potentially freezing or crashing the wallet process (denial of service against the victim's node/wallet). Because `data` is subsequently `JSON.parse`d and driven into `handlePrivatePaymentChains`, the resource cost compounds with parsing/validation of an oversized payload.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to open/import a file received from an untrusted party through the textcoin/private-payment flow, but this is an expected, user-facing feature of the wallet (claiming a textcoin/private-asset payment via a stored payload file), so a targeted attacker distributing a poisoned textcoin file is a realistic scenario within the intended trust model (an unprivileged private-payment counterparty).

### Recommendation
Do not trust the ZIP's declared `uncompressedSize`. Instead, enforce a hard byte cap during actual decompression (e.g., stream the entry through `nodeStream("string")`/`internalStream` and abort once a fixed limit, e.g. 250 KB–few MB, is exceeded), consistent with the fix pattern adopted by `jose` (limiting decompressed output to 250 kB regardless of any declared/reported size).

### Proof of Concept
1. Attacker crafts `private_textcoin.zip` containing an entry named `private_textcoin` whose central-directory/local-file-header declares `uncompressedSize` just under 100 MB, but whose actual deflate stream is engineered/corrupted to decompress to an unbounded amount of highly repetitive data larger than declared (or simply just under the 100 MB cap, which itself is already large enough to be an effective DoS payload for a mobile/light wallet).
2. Attacker delivers this file to the victim as the payload for a textcoin claim (e.g. via `handlePrivatePaymentFile(fullPath, content, cb)` invoked from the wallet UI when importing a received private payment file).
3. `handlePrivatePaymentFile` passes the size check based on declared metadata and calls `entry.async("string")`, forcing full inflate of the bomb into memory, followed by `JSON.parse`, exhausting CPU/memory on the victim's device. [1](#0-0)
