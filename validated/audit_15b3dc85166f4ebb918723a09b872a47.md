### Title
Governance Vote Consistency Check Validates Bounds Independently, Allowing `LowerBoundBaseFee > UpperBoundBaseFee` Inversion That Forces `header.BaseFee` Above the Governance-Mandated Ceiling - (`kaiax/gov/headergov/impl/header.go`)

---

### Summary

The `checkConsistency` function validates each governance vote for `kip71.lowerboundbasefee` and `kip71.upperboundbasefee` independently against the **current** (already-ratified) parameter set. It does not check the combined effect of multiple votes cast in the same epoch. This allows two individually-valid votes to ratify a state where `LowerBoundBaseFee > UpperBoundBaseFee`. Once that inverted state is active, `NextMagmaBlockBaseFee` produces a `header.BaseFee` that exceeds the governance-mandated upper bound, causing users to pay more than the maximum fee the governance intended.

---

### Finding Description

**Vote validation — independent, not joint:**

In `checkConsistency`, each bound is checked only against the *current* param set:

```go
case gov.Kip71LowerBoundBaseFee:
    params := h.GetParamSet(blockNum)
    if vote.Value().(uint64) > params.UpperBoundBaseFee {
        return ErrLowerBoundBaseFee
    }
case gov.Kip71UpperBoundBaseFee:
    params := h.GetParamSet(blockNum)
    if vote.Value().(uint64) < params.LowerBoundBaseFee {
        return ErrUpperBoundBaseFee
    }
``` [1](#0-0) 

Neither branch inspects pending votes for the *other* bound that are already queued in the same epoch. In `none` governance mode, two different GC members can each cast a valid vote for a different parameter:

- GC member A votes `LowerBoundBaseFee = 600 gwei` → passes because `600 <= current UpperBound (750)`
- GC member B votes `UpperBoundBaseFee = 400 gwei` → passes because `400 >= current LowerBound (25)`

At the epoch boundary both are ratified (different parameter names, so both survive the "last vote wins" rule). The resulting `ParamSet` has `LowerBoundBaseFee = 600 > UpperBoundBaseFee = 400`.

The same scenario is reachable in `single` mode: the governing node casts two votes in the same epoch, one for each bound, each individually valid.

**Base-fee calculation with inverted bounds:**

`NextMagmaBlockBaseFee` contains no guard against `LowerBound > UpperBound`. After the even-rounding adjustments:

```go
lowerBoundBaseFee := new(big.Int).SetUint64(kc.LowerBoundBaseFee)
upperBoundBaseFee := new(big.Int).SetUint64(kc.UpperBoundBaseFee)
makeEvenByCeil(lowerBoundBaseFee)   // rounds lower UP
makeEvenByFloor(upperBoundBaseFee)  // rounds upper DOWN
``` [2](#0-1) 

The clamp that follows assumes `lower <= upper`:

```go
if parentBaseFee.Cmp(upperBoundBaseFee) >= 0 {
    parentBaseFee = upperBoundBaseFee
} else if parentBaseFee.Cmp(lowerBoundBaseFee) <= 0 {
    parentBaseFee = lowerBoundBaseFee
}
``` [3](#0-2) 

With `lower = 600, upper = 400`, any `parentBaseFee` in `[400, 600]` satisfies `>= upper (400)` and is clamped to `400`. Then in the low-gas branch:

```go
// parentBaseFee (400) != lowerBoundBaseFee (600) → computes decrease
nextBaseFee := x.Sub(parentBaseFee, baseFeeDelta)
if nextBaseFee.Cmp(lowerBoundBaseFee) < 0 {
    return makeEvenByFloor(lowerBoundBaseFee)  // returns 600
}
``` [4](#0-3) 

The function returns `600 gwei` — the `LowerBoundBaseFee` — which is **above** the governance-mandated `UpperBoundBaseFee` of `400 gwei`. Both proposer and verifier call the same function with the same inverted config, so they agree on the incorrect value and the block is accepted by all honest nodes.

The header validator confirms the base fee matches the computed expected value:

```go
expectedBaseFee := kc.NextMagmaBlockBaseFee(...)
if headerBaseFee.Cmp(expectedBaseFee) != 0 {
    return fmt.Errorf("invalid baseFee: ...")
}
``` [5](#0-4) 

Because both sides compute the same wrong value, the invalid block passes `VerifyMagmaHeader` on every honest node.

---

### Impact Explanation

Every transaction in every block produced under the inverted config pays `baseFee = LowerBoundBaseFee` (e.g., 600 gwei) instead of being capped at `UpperBoundBaseFee` (e.g., 400 gwei). The excess fee (200 gwei × gasUsed per transaction) is an unauthorized fee charge on all users. This is a persistent, chain-wide effect lasting until governance corrects the bounds — which requires another epoch cycle (up to 604,800 blocks / ~1 week on Mainnet).

---

### Likelihood Explanation

In `none` governance mode, any two GC members independently casting valid votes for the two different parameters in the same epoch trigger this. Neither member needs to act maliciously; each vote is individually correct. In `single` mode, the governing node must cast two votes in the same epoch, which is a normal operational pattern (e.g., adjusting both bounds simultaneously). The epoch is long (604,800 blocks), making it easy for both votes to land in the same epoch.

---

### Recommendation

`checkConsistency` must validate the *combined* effect of all pending votes in the current epoch alongside the incoming vote. Specifically, when validating a `LowerBoundBaseFee` vote, retrieve the pending `UpperBoundBaseFee` vote for the current epoch (if any) and check against that pending value rather than (or in addition to) the current param set value. Apply the symmetric check for `UpperBoundBaseFee` votes.

Additionally, `NextMagmaBlockBaseFee` should add a defensive guard:

```go
if lowerBoundBaseFee.Cmp(upperBoundBaseFee) > 0 {
    // bounds are inverted; clamp to upper (or return an error)
    return makeEvenByFloor(upperBoundBaseFee)
}
```

### Proof of Concept

**Setup:** `none` governance mode, epoch = 604,800. Current params: `LowerBound = 25 gwei, UpperBound = 750 gwei`.

1. At block 100,000: GC member A casts vote `kip71.lowerboundbasefee = 600 gwei`.  
   `checkConsistency`: `600 <= 750` → accepted. [6](#0-5) 

2. At block 200,000: GC member B casts vote `kip71.upperboundbasefee = 400 gwei`.  
   `checkConsistency`: `400 >= 25` → accepted. [7](#0-6) 

3. At block 604,800 (epoch boundary): both votes are ratified. `GetParamSet` now returns `LowerBound = 600, UpperBound = 400`. [8](#0-7) 

4. Block 604,801 is produced. `NextMagmaBlockBaseFee` is called with `lower = 600, upper = 400`. With low gas usage, it returns `600 gwei`. [9](#0-8) 

5. `VerifyMagmaHeader` computes the same `600 gwei` and accepts the block. All honest nodes accept it. Users pay `600 gwei` base fee, exceeding the governance-mandated ceiling of `400 gwei` by 50%.
