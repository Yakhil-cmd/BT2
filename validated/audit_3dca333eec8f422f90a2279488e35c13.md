## Confirmed root cause

`WebhooksController#verify_signature` picks *which* GitHub App config (and thus which `webhook_secret`) to validate the HMAC signature against by reading an attacker-controlled JSON field from the still-unverified payload: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once the signature check passes, the actual event handler (`Handlers::Handler#stacks`) resolves the *repository actually acted upon* using a **different** field of the same payload: `repository.full_name`: [3](#0-2) 

Shipit supports being configured with multiple GitHub organizations, each with its own App/`webhook_secret` (`Shipit.github(organization:)`, `Shipit.github_app_config`): [4](#0-3) 

This is exactly the class of bug described in the report: two different trust decisions (which secret authenticates the request vs. which repository's state gets mutated) are bound to two different, independently-attacker-influenced fields of the same unverified payload, instead of a single verified value.

**Binding that should hold:** `organization_used_to_select_secret == organization_owning_repository_being_written`.
**What actually happens:** `repository.owner.login` (used to select the secret) and `repository.full_name` (used to select the `Repository`/`Stack` to mutate) are two unrelated JSON keys that an attacker fully controls before any signature check occurs.

### Exploit precondition
This requires the attacker to control (or know the webhook secret of) **at least one** organization configured in Shipit's multi-org `github:` block — e.g. their own org that they legitimately connected to the same Shipit instance. Shipit explicitly supports this multi-tenant configuration (see `config/secrets.development.shopify.yml`, `docs/setup.md`). No token, session or write access to the *victim* org/repo is required.

### Attack
1. Attacker's org `attacker-org` has a GitHub App installed in this Shipit instance with webhook secret `S_attacker` (attacker can obtain this by triggering any real webhook from a repo they control, or simply configuring the App themselves).
2. Attacker crafts a `push` (or `status`, `check_suite`) JSON body:
   - `repository.owner.login = "attacker-org"` (selects `S_attacker` for the HMAC check)
   - `repository.full_name = "victim-org/private-repo"`, `ref = "refs/heads/main"`, `after = <attacker-chosen sha>`
3. Attacker signs this raw body with `S_attacker` (`sha1=HMAC(S_attacker, body)`), sets `X-Hub-Signature`, POSTs to `/webhooks`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")`, verifies successfully against `S_attacker`.
5. `PushHandler#process` (or `StatusHandler`) then resolves `Repository.from_github_repo_name("victim-org/private-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on stacks the attacker does not own, using an attacker-chosen `after` sha and forged commit statuses.

## Impact
`sync_github` drives what Shipit believes is the deployable HEAD of the victim stack and can inject/force-associate arbitrary commit shas and forged CI statuses (`StatusHandler#process` → `Commit#create_status_from_github!`) for a repository the attacker has no legitimate access to. Because Shipit uses commit status/CI checks to gate whether a deploy is safe (`ci.require`, `deployable?`), forging a passing status for a malicious/unreviewed sha lets an unprivileged outsider make an unreviewed commit appear deployable, or corrupt undeployed-commit tracking, on a victim's stack — satisfying the "unauthorized deploy" bar via cross-repository writes to stack/commit state without any credential belonging to the victim org.

## Recommendation
Verify the webhook signature using the secret belonging to the organization that actually owns the repository being modified (`repository.full_name`'s owner segment), not a separately-controlled `repository.owner.login`/`organization.login` field — i.e., derive the lookup key from the same field the handlers use to select the target repo, and reject if it's absent/mismatched, before any handler logic runs.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end
