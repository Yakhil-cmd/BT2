### Title
Membership webhook trusts attacker-signed payload to add members to a Team looked up only by `github_id`, with no `repository` scoping requirement - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#params` never requires a `repository` key, and `WebhooksController#repository_owner` falls back to `params.dig('organization','login')` when it's absent, so a webhook signed with an attacker-owned GitHub organization's secret passes `verify_signature` unconditionally. Once inside `process`, `find_or_create_team!` resolves the target `Team` by `github_id` alone, ignoring which organization is asserted in the same payload, so a colliding `team.id` lets the attacker add an arbitrary user to a `Team` that belongs to a completely different organization/stack.

### Finding Description
The broken binding: the code assumes `team.github_id == params.team.id ⟹ team.organization == params.organization.login`, but `Team.find_or_create_by!(github_id: params.team.id)` in `find_or_create_team!` [1](#0-0)  only matches/creates on `github_id`; the `organization` field is set only inside the `create` block, which never runs when a `Team` with that `github_id` already exists. This means an existing `Team` row for organization A can be returned even though the payload's `organization.login` is organization B (the attacker's own org).

Path: `WebhooksController#create` parses raw JSON and dispatches to registered handlers [2](#0-1) . `verify_signature` computes `repository_owner`, which falls back to `organization.login` when `repository` is absent from the payload [3](#0-2) , and calls `Shipit.github(organization: repository_owner).verify_webhook_signature` [4](#0-3) . Because `repository_owner` resolves to the attacker's own verified organization, signature verification succeeds legitimately for a payload the attacker fully controls.

`MembershipHandler#params` only requires `:action`, `:team` (`id`, `name`, `slug`, `url`), `:organization.login`, and `:member.login` — no `:repository` key is required at all [5](#0-4) . `process` then calls `find_or_create_team!` and `team.add_member(member)` [6](#0-5) , and `Team#add_member` unconditionally appends the member if not already present [7](#0-6) .

Attacker's exact request: POST `/webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with the attacker's own organization's webhook secret, and a JSON body containing only `action`, `team` (with `id` set to the victim team's real `github_id`, plus fabricated `name`/`slug`/`url`), `organization.login` set to the attacker's own org, and `member.login` set to the attacker's GitHub username. No `repository` key is present or required.

Exploit flow: `verify_signature` succeeds against the attacker's own org → `MembershipHandler#process` runs → `find_or_create_team!` finds the pre-existing `Team` row whose `github_id` collides with the attacker-supplied `team.id`, regardless of that team's true `organization` → `team.add_member(User.find_or_create_by_login!(params.member.login))` inserts a `Membership` row binding the attacker's GitHub identity to a team belonging to an organization/stack the attacker does not own.

Existing guards fail because: `verify_signature` only proves the payload's *asserted* organization owns a valid secret — it never cross-checks that the `team.id` inside the payload actually belongs to that same organization; and `find_or_create_team!`'s lookup key (`github_id`) is not scoped by `organization` in the `WHERE` clause, only in the `create` fallback block that's skipped on a match.

### Impact Explanation
A successful request lets an attacker who owns any GitHub organization (or can spin one up for free) insert themselves as a member of a `Team` belonging to a different organization/stack, without ever needing repo-level webhook config, `Shipit.github_teams` membership, or any Shipit credential. Team membership in Shipit gates authorization checks (`User#authorized?`/`require_permission!` elsewhere in the engine rely on `Team#members`), so this is a payload asserted by one organization mutating another organization's authorization data — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). The attack is repeatable against any `github_id` the attacker can enumerate/guess (GitHub team IDs are small sequential integers, easily brute-forced), and against any organization configured in `Shipit.github_teams`/`Shipit.github` that has ever created a matching `Team` row.

### Likelihood Explanation
Preconditions are minimal: the attacker needs one real GitHub organization with a `membership` webhook configured toward the Shipit host (something any GitHub user can create for free) and must know/guess a `github_id` for a target team. No Shipit session, API token, or GitHub App key is required. Cost is low (create an org, install a webhook, brute-force integer IDs), and the attack is repeatable at will since nothing rate-limits or re-validates organization ownership of a `Team` row on lookup.

### Recommendation
Scope the `Team` lookup by both `github_id` and `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/raise if a `Team` with that `github_id` exists under a different `organization`, rather than silently reusing it.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb
test "membership handler does not add a member to a team belonging to another organization" do
  victim_team = shipit_teams(:shipit) # arbitrary fixture team with a known github_id, organization: 'victim-org'

  payload = {
    'action' => 'added',
    'team' => { 'id' => victim_team.github_id, 'name' => 'evil', 'slug' => 'evil', 'url' => 'https://api.github.com/teams/1' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker' },
  }

  assert_no_difference -> { victim_team.reload.members.count } do
    assert_raises(SomeExpectedGuardError) do # or assert record still scoped correctly
      Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)
    end
  end

  # Equality that must hold and currently doesn't:
  # victim_team.organization == 'victim-org' AND payload['organization']['login'] == 'attacker-org'
  # yet Team.find_by(github_id: victim_team.github_id).organization is unaffected by attacker-org,
  # while add_member still succeeds, proving cross-org write.
end
```

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end
