## Analog Found

### Title
Missing cosigner ACL check in the `sign` device-message handler allows any paired device to trigger signing requests for shared/multisig addresses it does not own - (File: `wallet.js`)

### Summary
CVE-2020-29006 is a MISP authorization bug where a controller (`GalaxyElementsController.php`) performed an action on an object without verifying the caller is actually entitled to touch it. The structural analog in `ocore` is in the `sign` case of `handleMessageFromHub` in `wallet.js`, which processes signing requests received from paired devices. For locally-hosted addresses (`ifLocal` branch), the code explicitly skips the check that the requesting device is a legitimate cosigner of the address, whereas the parallel `ifRemote` branch enforces exactly this check.

### Finding Description
`handleMessageFromHub` dispatches the `"sign"` subject to request that this wallet co-sign a unit for a shared/multisig address [1](#0-0) . After validating the unit's shape, it calls `findAddress` and branches on whether the address is hosted locally or on a remote device [2](#0-1) .

In the `ifRemote` branch, the code correctly verifies that the sender (`from_address`) is actually listed as a cosigner of the referenced address before forwarding/proxying the signing request: [3](#0-2) 

In the `ifLocal` branch, however, the equivalent membership check is commented out with a note that "the commented check would make multilateral signing impossible": [4](#0-3) 

As a result, when the target address is one that this device locally hosts (its own multisig address or a multilateral-signing "dumb contract" address), **any device that is a known correspondent of this wallet (or, for `pairing`/`my_xpubkey`/`wallet_fully_approved`, even a non-correspondent per the whitelist in `device.js`)** can submit a `sign` request naming that address, without the code confirming that `from_address` is actually one of the signing-path device addresses for that address. The request is accepted (`callbacks.ifOk()`), the unit is validated via `network.handleOnlineJoint`, and a `signing_request` event is emitted to the wallet UI to prompt the user for a signature [5](#0-4) .

This mirrors the CVE's root cause: an action affecting a resource (here, the signing workflow of a shared address) is executed based only on data supplied by the caller (`body.address`), without an ACL/ownership check tying the caller to that resource — while the parallel code path (`ifRemote`) shows the intended check exists elsewhere but was omitted here.

### Impact Explanation
An attacker who is any correspondent device of the victim's wallet (a low bar — correspondents are commonly acquired through chat/pairing flows, and some subjects are even allowed from non-correspondents) can flood the victim with spoofed signing requests for any locally-hosted multisig/shared address, not just addresses the attacker is actually a party to. This can be used to:
- Trigger repeated, unsolicited signing confirmation dialogs for otherwise-unrelated shared addresses, as a phishing/social-engineering vector to trick a cosigner into approving a malicious payment that drains a shared address (unauthorized spending of shared/multisig funds is possible if the victim approves).
- For "dumb" multilateral-signing contracts (arbiter/prosaic contract flows built on this same `sign` mechanism), craft signing requests impersonating a counterparty that was never actually part of the arrangement, since there is no verification that the sender belongs to the authors/signing paths of that specific address before displaying the confirmation UI.

This meets the "AA fund loss" / "unauthorized spending" bar if a user is tricked into signing, and independently constitutes a missing-ACL condition reachable directly from a single paired device's message, matching the CVE's bug class.

### Likelihood Explanation
Any device that has previously paired/chatted with the victim (a correspondent) can immediately exploit this by sending a crafted `sign` message; no additional privilege is required beyond being a correspondent, and the code path is reached unconditionally for any locally-known address matching `body.address`. The comment in the code confirms the omission is intentional/known, increasing the likelihood that it has not been revisited to add a safer, scoped check.

### Recommendation
Add a membership check in the `ifLocal` branch analogous to the `ifRemote` branch: before emitting `signing_request` (and before running validation/side effects), verify that `from_address` is one of the device addresses associated with the specific `signing_path` for `body.address` (e.g. via `shared_address_signing_paths` / `wallet_signing_paths`), rejecting the request with `callbacks.ifError(...)` if the sender is not an authorized party for that address/path. If multilateral signing genuinely requires accepting requests from other definition authors, restrict the check to "sender must be one of the authors/signers for this address" rather than omitting it entirely.

### Proof of Concept
1. Device `M` (malicious) pairs/chats with victim device `V` (becomes a correspondent).
2. `M` learns (from prior chats, invitations, or public metadata) the `BASE32` address of a shared/multisig address `S` that `V` hosts locally, along with the `signing_path` used by another legitimate cosigner (paths are often static, e.g. `r.0.0`, `r.1`).
3. `M` sends `V` a device message: `{"subject":"sign","body":{"address":"S","signing_path":"r.1","unsigned_unit":{...crafted malicious payment...}}}` — even though `M` is not a cosigner of `S`.
4. `V`'s `handleMessageFromHub` reaches the `ifLocal` branch (since `S` is locally hosted), skips any cosigner-membership check on `from_address`, validates the unit, and emits `signing_request`, prompting `V`'s wallet UI to display a signing confirmation dialog for `M`'s crafted transaction as if it came from a legitimate cosigner.
