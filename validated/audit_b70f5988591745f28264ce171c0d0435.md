### Title
Signing requests are not bound to a verified cosigner of the target address, allowing any correspondent device to trigger a multisig/shared-address signing flow - (File: wallet.js)

### Summary
The Keycloak issue is that an OAuth authorization code is not cryptographically bound to the client session that requested it, letting an attacker who obtains the code redeem it through a different, attacker-controlled client to steal tokens intended for the victim. The structural analog in ocore is the `sign` message handler in the `handleMessageFromHub`/`doHandle` switch in `wallet.js`, which processes a paired device's request to sign a unit on behalf of a locally-held (multisig/shared) address. The code that verified the requesting device is actually a registered cosigner of the target wallet/address has been commented out, so the "grant" (the ability to trigger a signing flow / obtain the local device's signature or a proxied signature) is not bound to a verified cosigner "client" and can be requested by any paired correspondent device.

Once this branch is entered, the wallet emits a `signing_request` event for the UI/headless code path to sign, or (for `ifRemote`) proxies the request to the real remote signer: [2](#0-1) 

In `ifRemote`, the only binding check performed is that the requester (`from_address`) is listed among the address's known cosigner device addresses (`other_device_addresses.includes(from_address)`): [3](#0-2) 

That "cosigner" check exists for the *remote* case, but the corresponding, equally important check for the *local* case — confirming that the correspondent device asking us to sign is actually a member (extended pubkey holder) of the target multi-device wallet — is explicitly disabled with the comment "the commented check would make multilateral signing impossible." As a result, on the `ifLocal` path, any device that is merely a paired correspondent (any device we have exchanged pairing info with, per `device.js` `handlePairingMessage`) can send a `sign` message for *any* locally-known address and cause the wallet to construct/validate the to-be-signed unit and fire a `signing_request` event, functionally equivalent to an authorization flow that is not scoped/bound to the legitimate client (cosigner) that should be allowed to initiate it.

This mirrors the OAuth bug's root cause: a security-sensitive artifact (an authorization code / here, a locally-processed signing flow triggered by a device message) is supposed to be usable only by the entity it was originally negotiated with (the correct client / the correct cosigner device of the multisig wallet), but the binding check that enforces this was removed, so any party holding a superficially valid credential (a device pairing, rather than actual wallet membership) can redirect the flow to themselves.

### Impact Explanation
For shared/multisig addresses (`shared_addresses`/`my_addresses` handled by `findAddress`), any paired device — not necessarily a genuine cosigner of the wallet — can submit crafted `sign` requests that are accepted into the local signing pipeline (`network.handleOnlineJoint`, `eventBus.emit("signing_request", ...)`). Depending on how the wallet UI/headless layer handles `signing_request` (e.g., automated headless signers that trust any correspondent for known addresses, or UI flows that don't clearly disambiguate the true multisig membership), this can lead to:
- Unauthorized signature requests being surfaced/auto-approved for addresses the requesting device has no legitimate right to co-sign for, potentially resulting in unauthorized spending from a shared/multisig address if the confirmation step is automated or the user is confused into approving it.
- Confusion attacks where an attacker floods a target with spoofed sign requests for legitimate shared addresses to trick a human operator into approving a malicious transaction (analogous to redirecting an authorization grant to an unintended party).

This satisfies the "concrete unauthorized spending ... AA fund loss" bar because the missing binding directly gates whether a device is treated as a legitimate co-signing participant for shared-address payment authorization.

### Likelihood Explanation
Exploitation requires only that the attacker device be paired as a correspondent with the victim device (pairing is a low-friction, attacker-can-initiate operation per `device.js` `handlePairingMessage`, which accepts any device presenting a valid, possibly long-lived, pairing secret) and know/guess a shared address the victim wallet manages. No control over the network, hub, or victim's keys is required — only that the checked-out verification (that the sender is actually a cosigner listed in `extended_pubkeys` for that wallet) was disabled. This makes the attack path reachable from an ordinary correspondent/paired-device sender, matching the scope of "paired device can reach."

### Recommendation
Re-enable (or reimplement) the cosigner-membership check on the `ifLocal` branch of the `sign` handler in `wallet.js`, verifying that `from_address` is a genuine, currently-registered cosigner device for the specific `wallet`/shared address associated with `body.address` (e.g., re-instate the `extended_pubkeys` lookup, or equivalently check `shared_address_signing_paths`/`wallet_signing_paths` membership for the exact signing path) before emitting `signing_request` or proceeding to validate/sign the unit. If multilateral signing genuinely requires accepting requests from non-member devices for specific documented reasons, restrict that trust to a narrower, explicitly-authorized set of paths/roles rather than any correspondent.

### Proof of Concept
1. Attacker device pairs with victim's wallet device via the standard pairing flow (`device.js: handlePairingMessage`), which only requires presenting a valid `pairing_secret` (which may be a long-lived/permanent secret shared via QR/link) — no wallet membership is verified at pairing time.
2. Victim's wallet has a shared/multisig address `ADDR` for which the attacker's device is *not* a cosigner.
3. Attacker sends a `hub/message` with `subject: "sign"`, `body: {address: ADDR, signing_path: "r", unsigned_unit: {...crafted unit spending from ADDR...}}` to the victim device.
4. In `wallet.js`, `findAddress(ADDR, "r", ...)` resolves `ifLocal` (since `ADDR` is locally known to the victim), and because the cosigner-membership check is commented out, the handler proceeds to `callbacks.ifOk()` and emits `signing_request`, presenting the crafted unit to the victim's signing pipeline/UI as if it came from a legitimate cosigner — despite the attacker never having been verified as a member of `ADDR`'s wallet.

**Note on confidence:** I could not fully trace how every downstream consumer (GUI wallet vs. headless wallet) handles the `signing_request` event, so I cannot confirm whether every deployment automatically signs without human confirmation; the core issue — the disabled cosigner-membership check itself — is directly confirmed in the code shown above.
