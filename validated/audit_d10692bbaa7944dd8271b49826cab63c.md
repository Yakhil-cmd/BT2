### Title
Webhook signature is verified against the organization named in an unauthenticated payload field, while a different unauthenticated field (`repository.full_name`) is used to select the target stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the HMAC signature against based on `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated JSON body. Every downstream handler, however, resolves the target `Stack`/`Repository` using a *different* field from that same unauthenticated body: `repository.full_name`. Nothing enforces that the organization used to pick the verification secret is the same organization that owns the repository the handlers actually act on.

### Finding Description
`verify_signature` computes the signing organization purely from request data, before any cryptographic check has happened: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit::GithubApp#verify_webhook_signature` further weakens this because, if the selected organization has no `webhook_secret` configured (explicitly documented as optional in `docs/setup.md`), verification is skipped entirely: [3](#0-2) 

Meanwhile, every handler resolves the repository/stack to act on using an entirely different, also-unauthenticated field: [4](#0-3) [5](#0-4) 

The engine explicitly supports multiple, independently keyed GitHub App configs, one per organization, each with its own `webhook_secret`: [6](#0-5) 

The binding that should hold is:
`organization whose secret authenticated the request` == `organization that owns the repository the handler mutates`.

Because `repository_owner` (used to pick the verification key) and `repository.full_name` (used to pick the stack) are two independently attacker-controlled fields in the same unsigned JSON body, an attacker can set them to different values. If any configured organization in the multi-org setup has no `webhook_secret` (allowed by the optional-secret design) or a secret weaker/leaked from a lower-trust org, the attacker can:
1. Set `repository.owner.login` (or `organization.login`) to that low/no-secret organization so `verify_signature` passes trivially.
2. Set `repository.full_name` (and other repo-scoped fields consumed by the handler, e.g. `sha`, `state`, `ref`, `after`) to point at a *different*, fully trusted organization's repository/stack.

This is a direct analog of the reported bug class: a verification mechanism is bound to one field of a message while a security-relevant action is driven by a sibling field that was never covered by that verification — exactly like the `approve()` call trusting the immutable `conduit` binding while a different, unchecked assumption (fresh allowance) is silently violated.

### Impact Explanation
This breaks the "org authenticated == repo written" trust binding described in-scope. Concretely, an unauthenticated network attacker who knows (or is themselves the owner of) any organization configured in Shipit's multi-org `github:` block with no `webhook_secret` can forge webhook deliveries that are processed as if verified, but that target a stack under a different organization:
- Forge a `status` event (`Handlers::StatusHandler`) marking an arbitrary commit SHA on a victim repository as `state: success`. Shipit's merge/CI status pages (`MergeStatusController`) and deploy readiness logic rely on these `Status` records, so this can make an unreviewed/unvetted commit appear "ready to ship," directly threatening an unauthorized deploy.
- Forge `push` events to trigger `GithubSyncJob` against a victim stack with an attacker-chosen `expected_head_sha`.
- Forge `check_suite` events to spoof check-run refresh state.

This maps to the in-scope Critical impact category "an unauthorized deploy, rollback or merge," since it lets an attacker manufacture the CI-success signal Shipit uses to gate shipping.

### Likelihood Explanation
Requires: (a) the operator to run Shipit in the documented multi-organization mode with per-org `webhook_secret`s, and (b) at least one configured organization to have no `webhook_secret` set (explicitly optional/allowed) or a secret known to the attacker (e.g., attacker's own low-trust GitHub org routed through the same Shipit instance). Given the setup docs present the "optional" secret and multi-org configuration as first-class, supported patterns, this is a realistic deployment shape, not a contrived edge case.

### Recommendation
Bind signature verification and target-resolution to the same authenticated identity:
- After computing `repository_owner` for key selection, re-verify that the resolved `Repository`/`Stack` (looked up via `repository.full_name`) actually belongs to that same `repository_owner`; reject the webhook if they diverge.
- Make `webhook_secret` mandatory for every configured organization (remove the `return true unless webhook_secret` bypass in `Shipit::GithubApp#verify_webhook_signature`), so no organization can be used as a "trivially verified" pivot.
- Consider deriving the verification organization directly from `repository.full_name`'s owner segment (the same field handlers use) rather than a separately-provided `repository.owner.login`/`organization.login`, eliminating the two-field split entirely.

### Proof of Concept
Conceptual PoC (assuming multi-org config with `OrgNoSecret` having no `webhook_secret` and `OrgVictim` having a stack in Shipit):

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # OrgNoSecret has no secret -> verify_webhook_signature returns true

{
  "organization": { "login": "OrgNoSecret" },
  "repository": { "owner": { "login": "OrgNoSecret" }, "full_name": "OrgVictim/target-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/whatever",
  "branches": [{ "name": "main" }]
}
```

`verify_signature` resolves `repository_owner` = `"OrgNoSecret"`, whose `verify_webhook_signature` short-circuits to `true` because no `webhook_secret` is configured. `StatusHandler`, however, resolves the target stack via `repository.full_name` = `"OrgVictim/target-repo"` [4](#0-3) , creating a forged `success` status on `OrgVictim`'s commit despite never validating a signature tied to `OrgVictim`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
