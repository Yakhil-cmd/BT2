### Title
`extract_frontmatter` fails to strip inline comments, causing `enabled: false # comment` to parse as a truthy string instead of boolean `False` - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
In `extract_frontmatter` (plugins/hookify/core/config_loader.py, lines 136-152), a top-level `key: value` line is parsed by splitting on the first `:`, then only trimming whitespace and surrounding quotes from `value`. There is no logic anywhere in the function to strip trailing inline comments (`# ...`) from a value — the only comment handling is the full-line check `stripped.startswith('#')` at line 118, which only skips lines that are *entirely* a comment.

Given a rule file containing:
```
---
name: test-rule
enabled: false  # temporarily off
event: bash
pattern: "rm -rf"
---
```
the line `enabled: false  # temporarily off` is split into `key='enabled'`, `value='false  # temporarily off'` (line 136-138). The boolean coercion at lines 148-151 checks `value.lower() == 'false'`, which evaluates to `'false  # temporarily off' != 'false'` → False, so the coercion branch is never taken and `frontmatter['enabled']` retains the raw string `'false  # temporarily off'`.

This value flows into `Rule.from_dict` at line 77 (`enabled=frontmatter.get('enabled', True)`), assigning `Rule.enabled` the non-empty string, which is truthy in Python. `load_rules()` then evaluates `if rule.enabled:` at line 225 and includes the rule in the active rule set, even though the file's author clearly intended to disable it.

### Impact Explanation
A rule the file author intended to disable (via `/hookify:configure` or manual edit with an explanatory inline comment) instead remains active and is evaluated against subsequent bash/file/stop events. Depending on the rule's `action` field, this can cause hookify to unexpectedly `warn` or `block` operations the victim expected to proceed silently, i.e., unintended enforcement caused purely by a parser defect — a state-drift bug that undermines the documented disable workflow's guarantee that `enabled: false` means inactive.

### Likelihood Explanation
Any actor who can write or generate a `.claude/hookify.*.local.md` rule file with an inline comment on the `enabled:` line triggers this deterministically — no special privilege is required beyond the ability to place such a file (which is the normal/expected way rules are authored, including by `/hookify:configure`). The bug is 100% reproducible for any value line with a trailing `#` comment, not just `enabled`.

### Recommendation
Strip inline comments before value coercion in `extract_frontmatter`, e.g. split `value` on an unquoted `#` (being careful not to break quoted strings containing `#`) prior to the `strip('"').strip("'")` and boolean-coercion checks at lines 146-152.

### Proof of Concept
```python
from plugins.hookify.core.config_loader import extract_frontmatter, Rule

content = """---
name: test-rule
enabled: false  # temporarily off
event: bash
pattern: "rm -rf"
---

message body
"""

fm, msg = extract_frontmatter(content)
assert fm['enabled'] is False, f"expected False, got {fm['enabled']!r}"

rule = Rule.from_dict(fm, msg)
assert rule.enabled is False, f"expected False, got {rule.enabled!r}"
```
Currently `fm['enabled']` equals the string `'false  # temporarily off'` and `rule.enabled` is truthy, so both assertions fail, confirming the vulnerability. [1](#0-0) [2](#0-1) [3](#0-2)
