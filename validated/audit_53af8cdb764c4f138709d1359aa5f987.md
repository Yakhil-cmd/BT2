### Title
Webhook signature is verified against the organization named in the unauthenticated payload, but the write target is a different, unchecked repository field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against using a value taken directly out of the untrusted JSON body (`repository.owner.login` / `organization.login`), while the actual side-effecting webhook handlers key their writes off a *different* field of the same untrusted body (`repository.full_name`). Nothing forces these two fields to refer to the same repository/organization.

### Finding Description
`verify_signature` computes the organization used to look up the correct per-org `webhook_secret`: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the JSON body before signature validation occurs. `Shipit.github(organization: repository_owner)` returns the `GitHubApp` config (and its `webhook_secret`) for whichever organization name is present in the payload, per the documented multi-org configuration: [3](#0-2) [4](#0-3) 

The signature is verified with `verify_webhook_signature`, keyed to that org's secret: [5](#0-4) 

Once the signature check passes, `create` dispatches the raw JSON body to the registered handlers: [6](#0-5) 

Every handler determines *which stacks/repositories to mutate* using `repository.full_name` — a completely independent field of the same payload, never covered by the org-scoped signature check: [7](#0-6) 

For example, the push handler syncs (fetches refs into and updates) every non-archived stack matching that `full_name`/branch: [8](#0-7) 

Pull-request handlers use the same unguarded field to create, archive, or unarchive review stacks and mutate `PullRequest` records: [9](#0-8) [10](#0-9) 

**The binding that is broken:** `organization authenticated by signature` (`repository.owner.login` / `organization.login`) is treated as equal to `repository actually written to` (`repository.full_name`), but the code never enforces this equality. An entity that legitimately controls the GitHub App installation/webhook secret for Organization A (e.g., an org owner who configured Shipit for their own org in a multi-tenant `secrets.yml`) can sign an arbitrary payload with Organization A's secret while setting `repository.full_name` to `OrgB/some-repo`. `verify_signature` succeeds (it only checks Org A's secret against the raw body, it never inspects `full_name`), and the handler then acts on Org B's stack — an org/repository the attacker has no legitimate access to.

### Impact Explanation
This breaks a repository-write trust boundary the app is documented to rely on ("Webhook secret ... keep it in clear on the side") for scoping which organization's events are trusted. It allows an actor who only administers their own organization's GitHub App/webhook secret to forge webhook events (`push`, `pull_request`, `status`, `check_suite`, `membership`) that are processed as authentic for a completely unrelated organization/repository configured on the same Shipit instance. Concretely this enables: forcing arbitrary stacks in a victim org to `sync_github`/fetch attacker-chosen refs, spuriously creating/archiving/unarchiving review stacks (which can trigger provisioning/deprovisioning task execution) and forging commit statuses/check-suite state for a repository the attacker does not control. This is a cross-repository/cross-organization write achieved without any credential belonging to the victim organization — matching the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Exploitability is bounded by the deployment being multi-tenant (multiple GitHub orgs configured under one Shipit instance sharing `config.github`), which is an explicitly documented and supported configuration. In that configuration, any org admin who legitimately possesses their own org's `webhook_secret` — not a Shipit session, `ApiClient` token, or the victim org's secret — can trigger this. In a single-org deployment, `repository.owner.login` and `repository.full_name`'s owner segment normally coincide, so the practical impact is confined to multi-org setups, but the code has no check preventing the mismatch in general.

### Recommendation
After signature verification, cross-check that the organization/owner used to select and validate the webhook secret matches the owner segment of `repository.full_name` (and `organization.login` for org-scoped events) before dispatching to any handler; reject the request otherwise.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub App config, e.g. `github: { orgA: {webhook_secret: "secretA", ...}, orgB: {webhook_secret: "secretB", ...} }`, with stacks configured for `orgB/victim-repo`.
2. As an attacker who administers the `orgA` GitHub App (and thus knows `secretA`), craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-controlled-sha>",
  "repository": { "full_name": "orgB/victim-repo", "owner": { "login": "orgA" } }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(secretA, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")`, verifies the signature against `secretA`, and succeeds — because `repository_owner` was taken from `orgA`, matching the secret used to sign.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")`, matching the victim's stack, and calls `stack.sync_github(expected_head_sha: "<attacker-controlled-sha>")`, causing the victim's stack to sync against attacker-chosen state despite the attacker never having authenticated as, or held credentials for, `orgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
