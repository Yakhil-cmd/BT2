### Title
Market accrual becomes permanently unexecutable after a sufficiently long dormant period - ([File: contracts/pool/src/interest.rs])

### Summary
Pool accrual advances a market from its stored `last_timestamp` to the current ledger time in one transaction, splitting the elapsed interval into chunks of at most one year. Because the loop must process the entire interval atomically and has no caller-provided bound or resumable progress, a sufficiently long gap makes every transaction that needs accrual exceed the Soroban execution budget. The permissionless `Controller::update_indexes(caller, assets)` entrypoint reaches this code directly, and ordinary market mutations such as `withdraw` and `claim_revenue` depend on the same synchronized market state.

### Finding Description
`PoolStateRaw::last_timestamp` is initialized when the market is created and later persisted by `Cache::commit`. Each `Cache::load` stores the current ledger timestamp alongside that last accrual timestamp, and `elapsed_ms` computes their saturating difference. [1](#0-0) [2](#0-1) 

`interest::global_sync` then loops until `remaining` reaches zero, choosing a chunk bounded by `MAX_COMPOUND_DELTA_MS`. That constant is one year in milliseconds, so the required iteration count is `ceil(elapsed_ms / MILLISECONDS_PER_YEAR)`. [3](#0-2) [4](#0-3) 

Every iteration runs `accrue_chunk`, which recalculates utilization, the borrow rate, a compounded interest factor, both indexes, and protocol revenue shares. [5](#0-4) [6](#0-5) 

There is no partial accrual API: `ops::market::accrue` always calls `global_sync`, which only marks the market accrued after the entire elapsed interval has been processed. [7](#0-6) [8](#0-7) 

The strongest permissionless route is `Controller::update_indexes(caller, assets)`, which authorizes any caller and forwards the supplied `assets` to the pool. [9](#0-8) [10](#0-9)  `LiquidityPool::update_indexes` invokes the same per-market accrual implementation. [11](#0-10) 

### Impact Explanation
Once `elapsed_ms` spans enough yearly chunks that one transaction cannot finish them, the market cannot be synchronized. Because the failed transaction rolls back, repeated calls do not make incremental progress; they begin from the same old `last_timestamp` and fail again.

This freezes all state-dependent value associated with that market. Suppliers cannot realize accrued interest or reliably exit because withdrawal performs accrual before burning shares and transferring tokens. [12](#0-11) [13](#0-12)  Protocol revenue also cannot be claimed: revenue claiming syncs before paying, and accrued revenue shares are embedded in the synchronized supply state. [14](#0-13) [15](#0-14) 

The result is permanent freezing of supplied funds and unclaimed yield for any market left untouched beyond the executable accrual horizon, rather than merely a caller-selected oversized batch.

### Likelihood Explanation
The defect requires extreme market dormancy because each loop iteration can cover a full year. The loop count is not attacker-controlled beyond being able to invoke the permissionless `update_indexes` path and choose which existing markets to accrue. [9](#0-8) 

Nevertheless, time accumulation is unbounded: `elapsed_ms` is only a saturating timestamp difference, and neither `update_indexes` nor `global_sync` imposes a maximum elapsed interval or permits incremental catch-up. [2](#0-1) [8](#0-7)  The risk is therefore concrete for abandoned or infrequently touched markets, including inactive markets that continue to hold supply, debt, or revenue.

### Recommendation
Make accrual resumable across transactions instead of requiring the full elapsed interval atomically. For example:

- Add an explicit `max_chunks` or target timestamp argument to pool accrual.
- Persist `last_timestamp` after each processed chunk, or commit the latest fully processed timestamp before returning.
- Let `Controller::update_indexes` invoke bounded accrual repeatedly until the market catches up.
- Ensure all operations can either complete within a bounded catch-up window or expose a dedicated catch-up operation that users and keepers can call before withdraw, repay, liquidation, or revenue claim.

This is the same mitigation shape as claim-by-cycle: process a bounded amount of accrued history per transaction while preserving deterministic final accounting.

### Proof of Concept
1. Create or identify an existing pool market with nonzero supply, debt, or revenue and stored `last_timestamp = T0`.
2. Leave the market untouched until the current ledger timestamp `T1` satisfies `(T1 - T0) / MILLISECONDS_PER_YEAR` greater than the number of `accrue_step` executions that fit in one transaction.
3. Call:

   ```text
   Controller::update_indexes(
       caller = attacker_or_keeper,
       assets = vec![hub_asset],
   )
   ```

   `caller.require_auth` is the only controller-level caller check, and the controller forwards the market to `pool_update_indexes_call`. [10](#0-9) 
4. Pool `update_indexes` loads the market and invokes `global_sync`. [11](#0-10) [7](#0-6) 
5. `global_sync` attempts one `accrue_chunk` per elapsed year. The transaction exhausts the execution budget before `mark_accrued`, so the whole call rolls back and `last_timestamp` remains `T0`. [8](#0-7) [16](#0-15) 
6. Repeating the call cannot make progress. A subsequent `withdraw(caller, account_id, vec![(hub_asset, 0)], to)` also requires synchronized accounting before shares can be burned and cash debited, so the supplier's principal and accrued interest remain inaccessible. [17](#0-16) [13](#0-12)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
pub(crate) fn accounting(
    env: &Env,
    is_liquidation: bool,
    entry: &PoolWithdrawEntry,
) -> WithdrawOutcome {
    require_nonneg_amount(env, entry.protocol_fee);
    let (mut cache, position) = ops::load_leg(env, &entry.action);

    let (burned, gross_amount) = resolve_close_or_partial(&cache, entry.action.amount, position);
    // Burn first: `protocol_fee_shares` caps the fee mint at `i128::MAX - supplied`.
    let remaining = burn_position(env, &mut cache, position, burned);
    let net_transfer = withhold_liquidation_fee(
        env,
        &mut cache,
        gross_amount,
        is_liquidation,
        entry.protocol_fee,
    );

    // A footprint-only close must not add a utilization gate to same-market
    // net settlement: it burns no shares and moves no cash.
    let empty_close = position.raw() == 0 && entry.action.amount == i128::MAX;
    gate_and_debit(env, &mut cache, net_transfer, is_liquidation || empty_close);

    let snapshot = cache.commit();
    let mutation = cache.position_mutation(remaining, gross_amount);
```
