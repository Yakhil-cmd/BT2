### Title
ERC20Transactor caches nominal `amount` from `transfer()`'s boolean return instead of verifying actual balance delta, breaking XCM accounting for fee-on-transfer/rebasing ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor`, wired into `AssetTransactors` on the production Asset Hub Westend runtime, moves ERC20 tokens by calling the Solidity `transfer()` function and treats a `true` boolean return as proof that the full nominal `amount` moved. It never re-checks the actual balance delta of the checking account or beneficiary. Any ERC20 contract deployed via `pallet-revive` with fee-on-transfer or rebasing semantics — the exact bug class from the referenced report — will desynchronize the XCM holding register's nominal value from the checking account's real balance, causing stuck/trapped assets and deterministic instruction failures.

### Finding Description
`ERC20Matcher` matches *any* local `AccountKey20` location as a fungible asset [1](#0-0) , and `ERC20Transactor` is registered in the production `AssetTransactors` tuple for Asset Hub Westend [2](#0-1) . This means any smart contract deployed by any unprivileged user via `pallet-revive` can be referenced as an XCM fungible asset simply by using its address as an `AccountKey20` junction, with no whitelist or asset-registration step.

`withdraw_asset_with_surplus` moves `amount` from the user to a `TransfersCheckingAccount` by invoking the ERC20 `transfer()` function and, on a `true` boolean return, unconditionally credits the XCM holding register with the full nominal `amount` via `Erc20Credit(amount)` — never checking the checking account's actual balance change: [3](#0-2) 

Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the checking account to the beneficiary and, on a `true` boolean return, reports success/consumes the holding — again without checking the beneficiary's real balance delta: [4](#0-3) 

This is the exact analog of the reported bug class: the code caches the nominal `amount` argument used in a token-moving call and propagates it through downstream accounting (here, the XCM holding register / `AssetsInHolding`) instead of measuring the actual balance change. For a fee-on-transfer token, the checking account receives `amount - fee` on withdraw but the holding register believes it holds the full `amount`. For a rebasing token, an intervening rebase can shrink the checking account's balance below what the holding register expects.

### Impact Explanation
Because the checking account's real ERC20 balance can end up lower than what the XCM holding register nominally represents, any later `DepositAsset`/`InitiateReserveWithdraw`/`InitiateTransfer` instruction operating on that credited amount will attempt to move `amount` out of the checking account via `deposit_asset_with_surplus`. Standard ERC20 `transfer()` implementations revert on insufficient balance, so this bare_call will either revert or return `false`, causing `deposit_asset_with_surplus` to return `Err`. Depending on where this occurs in an XCM program, this results in:
- Assets becoming permanently untransferable from the checking account (funds effectively stuck, matching "tokens stuck in the protocol" in the original report), and/or
- The whole XCM instruction failing and the remaining holding assets being trapped via `AssetTrap`, requiring a manual `ClaimAssets` recovery that a normal user may not know to perform.
- Repeated fee-on-transfer withdrawals accumulate a growing discrepancy between checking-account real balance and nominal holding-register credits system-wide, since the checking account is meant to act as a net-zero escrow across all users' round-trips.

This does not directly mint value or allow theft of others' funds (the trapped assets are not stolen, and impact is confined to whichever XCM programs interact with such a token), so it is best characterized as a Medium-severity availability/asset-freezing issue consistent with the original report's severity rating, contingent on such an ERC20 contract actually being used as an XCM asset on Asset Hub.

### Likelihood Explanation
Reaching this code path requires no privilege: any user can (1) deploy an ERC20-like contract via `pallet-revive` with fee-on-transfer or rebasing logic, and (2) submit an XCM program (e.g. via `pallet_xcm::execute`) that references that contract's address as an `AccountKey20` asset and withdraws/deposits it. `ERC20Matcher`/`IsLocalAccountKey20` places no restriction requiring the contract to be a "safe" or vetted ERC20 — matching is purely structural on the location shape. The existing test suite already demonstrates that malformed/uncooperative ERC20 contracts (e.g., ones with unexpected return-value encoding) cause `PolkadotXcm::execute` to fail without panicking [5](#0-4) , confirming the general reachability of this code path with arbitrary attacker-deployed contracts, though I did not find (and could not execute) a specific test exercising a fee-on-transfer/rebasing contract's balance-delta mismatch.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the relevant account's ERC20 balance immediately before and after the `transfer()` call (via `IERC20::balanceOfCall`, as already used elsewhere in `substrate/frame/revive/src/impl_fungibles.rs`), and credit/report the *actual* balance delta rather than the nominal `amount` argument. This mirrors the original report's recommendation to cache the actual transferred difference rather than the nominal amount, and prevents cross-account accounting divergence for fee-on-transfer or rebasing ERC20 assets referenced via XCM.

### Proof of Concept
I was not able to execute a live reproduction in this session (no code-execution access), so this cannot be confirmed as a working exploit — it is a static-analysis finding based on direct reading of `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` and its wiring into `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`. A concrete reproduction would require:
1. Deploying (via `pallet-revive::bare_instantiate`, as done in the existing `smart_contract_does_not_return_bool_fails` test) a Solidity contract implementing `IERC20` with a `transfer()` function that deducts a fee from the sender or applies a rebase, while still returning `true`.
2. Executing an XCM program via `PolkadotXcm::execute` that does `WithdrawAsset` on this contract's `AccountKey20` location for `amount`, followed by `DepositAsset` to a beneficiary.
3. Asserting that `pallet_revive::Pallet::<T>::bare_call` for the deposit reverts/returns `false` because the checking account's real balance (`amount - fee`) is less than the nominal `amount` the holding register believes it should forward, while the existing test harness pattern (`ExtBuilder`, `bare_instantiate`, `compile_module_with_type`) in `asset-hub-westend/tests/tests.rs` provides the necessary scaffolding to build and run such a test.

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {

// Here the contract returns a number but because it can be cast to true

#[test]
fn smart_contract_does_not_return_bool_fails() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 10_000_000_000_000u128;

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));

		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		// This contract implements the ERC20 interface for `transfer` except it returns a uint256.
		let code = compile_module_with_type("MyTokenFake", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);

		let Contract { addr: non_erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let wnd_amount_for_fees = 1_000_000_000_000u128;
		let erc20_transfer_amount = 100u128;
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: non_erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.build();
		// Execution fails but doesn't panic.
		assert!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(2_500_000_000, 220_000),
		)
		.is_err());
	});
}
