### Title
Global write-lock deadlock caused by unhandled internal-consistency exceptions in `saveJoint()` - (File: writer.js)

### Summary
`writer.saveJoint()` acquires the global `"write"` mutex before it starts writing a unit to the database and does not release it until the very end of a long, deeply-nested asynchronous callback chain. Several internal-consistency checks inside that chain use a bare `throw Error(...)` instead of routing the error through the `async.series`/`commit_fn` callback path that eventually calls `unlock()`. Any code path that reaches one of these `throw` statements after the `"write"` lock has been acquired leaves the mutex permanently held, exactly the same root-cause pattern as ALPINE-CVE-2022-31622 (lock acquired, error path taken, lock never released → deadlock/DoS), except here the affected resource is ocore's own single global write lock that every future unit write depends on.

### Finding Description
`mutex.js`'s `exec()` only releases a lock when the caller explicitly invokes the `unlock` callback it is handed [1](#0-0) . There is no `try/finally` around the wrapped `proc`, so if the code inside the locked section throws instead of calling `unlock`, the entry in `arrLockedKeyArrays` is never removed, and `isAnyOfKeysLocked` will forever report the key as locked for any subsequent caller [2](#0-1) .

`writer.saveJoint()` takes the `"write"` lock at the very top of the function: [3](#0-2) 
and only calls `unlock()` once, at the bottom of a chain of `async.series`/`commit_fn` callbacks hundreds of lines later: [4](#0-3) 

In between, several helper functions used while assembling/writing the unit perform sanity checks with bare `throw Error(...)` rather than passing the error to their callback (which would eventually reach `commit_fn`/`unlock`):
- `determineInputAddressFromSrcOutput` throws on "multiple src outputs found", "src output not found", "asset doesn't match", "denomination doesn't match", "src output address not among authors" [5](#0-4) 
- `updateBestParent` throws on "zero or more than one best parent unit?" and on a best-parent mismatch between the validator and the writer [6](#0-5) 
- `updateLevel`/`updateWitnessedLevelByWitnesslist` throw on "different max level" and "different witnessed levels" mismatches [7](#0-6) [8](#0-7) 
- Further down, additional invariant throws exist for "no initial_trigger_mci", "system_vote_count message not found", stabilization invariants, and batch-write failures [9](#0-8) 

Any of these `throw` statements fires while the process is holding the `"write"` mutex acquired at line 34. Because the throw unwinds the JS call stack instead of invoking the `unlock` callback captured by `mutex.exec`, the `"write"` key stays in `arrLockedKeyArrays` forever (as long as the process keeps running). Every subsequent call to `writer.saveJoint()` — for every future unit submitted by any peer, own composed transactions, or AA trigger execution paths that call `saveJoint` — will queue behind this permanently-held lock and never execute, since `handleQueue()` only re-examines queued jobs when some lock is explicitly released [10](#0-9) .

This is the direct functional analog of the MariaDB bug: "when an error occurs ... the held lock is not released correctly, which allows ... a denial of service due to the deadlock." Here the "error" is one of these internal consistency `throw`s, and the lock is ocore's own `"write"` mutex rather than a pthread mutex.

### Impact Explanation
The `"write"` mutex serializes literally every unit write in the node — normal joints received from peers (`network.js` `handleJoint` → `writer.saveJoint`), the node's own composed transactions (`composer.js`, `divisible_asset.js`, `indivisible_asset.js` saving callbacks), and AA-trigger-driven writes (`aa_composer.js`). Once the lock is stuck, no new unit — payment, AA trigger response, or otherwise — can ever be committed by that node again: this matches the "network unable to confirm new units" impact criterion, at least for the affected node, and if the same triggering condition (e.g., a witness-list/`best_parent` disagreement introduced by a borderline unit near a protocol boundary) is broadcast network-wide, multiple/most full nodes could independently hit the same deadlock, since the consistency checks are deterministic functions of unit content already accepted by `validation.js`.

### Likelihood Explanation
Reaching most of these `throw` sites in the ordinary flow requires the writer's independently recomputed values (best parent, level, witnessed level, src-output addresses) to diverge from what `validation.js` already computed and put into `objValidationState` — this is intended to never happen for a unit that passed validation, so these are "should never happen" invariants, not paths intentionally reachable by a spec-compliant unit. This significantly lowers likelihood relative to the CVE's straightforward `pthread_create` failure trigger; exploitation would need an edge case (e.g. a race in a witness-list change, an OP-list-vote transition, or a `content_hash`/`content_hash`-less boundary condition) where the writer's recomputation and the validator's precomputed state genuinely disagree for a syntactically-valid unit. Because these are unverified without live reproduction in this codebase snapshot, I could not confirm a concrete unit that deterministically triggers one of the mismatches; this is the main uncertainty in this finding.

### Recommendation
- Wrap the entire locked body of `saveJoint()` in a construct that guarantees `unlock()` is called on any exception (e.g., a top-level `try/catch/finally`, or converting the function to `async`/`await` fully and calling `unlock()` in a `finally` block), rather than relying on every nested callback reaching the final `commit_fn`.
- Harden `mutex.exec()` itself to release the lock on an exception thrown by `proc`, e.g. by wrapping the call to `proc` in `try { proc(unlock) } catch(e) { release(arrKeys); throw e; }`, so a bug anywhere in the locked code cannot permanently wedge the mutex.
- Replace the internal-consistency `throw Error(...)` calls inside `determineInputAddressFromSrcOutput`, `updateBestParent`, `updateLevel`, and `updateWitnessedLevelByWitnesslist` with proper error propagation through their callbacks so the existing `commit_fn`/`unlock` path is always exercised.

### Proof of Concept
A full PoC unit that forces a best-parent/level/witnessed-level mismatch between `validation.js` and `writer.js` could not be constructed with the available static analysis (this would require live execution/fuzzing of the validation vs. write path, e.g. around witness-list or OP-list-vote transition boundaries, which is out of scope for this read-only review). The structural PoC is:
1. Any code path causes `writer.saveJoint()` to reach one of the `throw Error(...)` statements at [11](#0-10) , [12](#0-11) , [13](#0-12) , or [14](#0-13)  while the `"write"` lock taken at [15](#0-14)  is held.
2. Because the throw unwinds the stack without calling the `unlock` function captured by `mutex.exec` [1](#0-0) , the key `"write"` remains in `arrLockedKeyArrays` indefinitely.
3. Every subsequent `mutex.lock(["write"], ...)` call (from any future `saveJoint` invocation, whether from `network.js` handling incoming joints, `composer.js`/`divisible_asset.js`/`indivisible_asset.js` saving own transactions, or `aa_composer.js` processing AA triggers) is queued forever in `arrQueuedJobs` and never executed, since `handleQueue()` only runs when some lock is released.

	for (var i=0; i<arrQueuedJobs.length; i++){
		var job = arrQueuedJobs[i];
		if (isAnyOfKeysLocked(job.arrKeys))
			continue;
		arrQueuedJobs.splice(i, 1); // do it before exec as exec can trigger another job added, another lock unlocked, another handleQueue called
