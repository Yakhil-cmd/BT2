### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while all event handlers dispatch on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC against using a payload field (`repository.owner.login` or `organization.login`), but every webhook `Handler` subsequently identifies the target `Repository`/`Stack` to act on using a *different* payload field (`repository.full_name`). Because the signature only proves "this payload was signed with Org X's secret," not "this payload's `repository.full_name` belongs to Org X," an attacker who knows/controls one organization's webhook secret can forge a payload whose `owner.login` matches Org X (to pass signature verification) while `repository.full_name` points at an entirely different org/repo tracked by the same Shipit instance, causing writes/actions against a repository outside that org's authenticated scope.

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end
``` [1](#0-0) [2](#0-1) 

This chooses the `GithubApp`/`webhook_secret` used for HMAC comparison based on a value taken directly from the unauthenticated request body itself, before the signature has been checked. The HMAC only proves the raw body matches *some* secret associated with the org named in the body — it does not bind or cross-check that the org used for verification is consistent with the repository the payload ultimately claims to act on.

Every `Handler` (base class and all concrete handlers such as `PushHandler`) instead resolves the actual `Repository`/`Stack` to write to via a *separate* field:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [3](#0-2) 

`PushHandler#process` uses this to trigger a real GitHub sync for whichever stacks match:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 

`Repository.from_github_repo_name` performs a straight DB lookup on `owner/name` parsed out of `full_name`, with no relation to `repository_owner` used for signature verification:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [5](#0-4) 

In a multi-organization Shipit deployment (explicitly supported — `config/secrets.development.example.yml` documents per-organization `github:` blocks each with its own `webhook_secret`), the binding that should hold is: `organization authenticated via HMAC == organization owning the repository the handler writes to`. Because `repository_owner` (used to pick the verification secret) and `repository.full_name` (used to pick the repository actually acted on) are two independent, attacker-controlled fields in the same unsigned-until-verified JSON body, this binding is never enforced. An attacker who possesses Org A's `webhook_secret` (a much lower-privilege credential than a GitHub App private key or a Shipit session) can sign a payload where `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/some-repo"`. The signature check passes (it's validated against Org A's real secret over the real bytes), yet `GithubSyncJob` is enqueued against `OrgB/some-repo`'s `Stack`, which is fetched from GitHub using Shipit's *legitimate* installation credentials for Org B (`stack.github_api`, ultimately `Shipit.github(organization: owner)` in `Repository#github_app`) — i.e., the attacker forces Shipit to perform authenticated GitHub API calls and stack-state mutations for a repository/org whose webhook secret they never had.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary called out in the rules. With only Org A's `webhook_secret` (out of scope credentials explicitly excluded are session tokens, `ApiClient` tokens, GitHub App private keys, `api_clients_secret` — a webhook secret is none of these and is the intended "unprivileged" credential for this endpoint), an attacker can:
- Force `GithubSyncJob`/`CacheDeploySpecJob` to run against any tracked `Stack` belonging to a *different* organization served by the same Shipit instance, causing Shipit to fetch and append attacker-chosen-timing commits and re-cache deploy specs for that stack.
- Depending on continuous-deployment configuration for the targeted stack, this sync can be the trigger that leads to an actual deploy being scheduled, i.e., an unauthorized cross-repository/cross-organization action initiated with credentials scoped to a different org.

This satisfies the Critical bucket ("cross-repository writes" / "an unauthorized deploy") because the attacker is causing writes and background job execution against a `Stack`/`Repository` that is not the one whose secret they hold, purely by manipulating an unauthenticated field in the payload.

### Likelihood Explanation
Requires the attacker to already know one organization's `webhook_secret` for a Shipit instance that manages multiple GitHub organizations (each documented to have its own secret in `secrets.yml`) — this is a real, supported, and likely deployment shape for shared Shipit instances. No GitHub App private key, session, or `ApiClient` token is needed; only the webhook secret, which is a comparatively lower-value/lower-scrutiny secret and the exact credential this endpoint is designed to check against attacker-supplied requests. The forgery itself is trivial: compute an HMAC over a crafted JSON body.

### Recommendation
After `verify_signature` succeeds, re-derive the organization from the same field the handlers use (`repository.full_name`'s owner segment, or equivalently look up the `Repository`/`Stack` and compare its `owner` to `repository_owner`) and reject the request if they don't match. Alternatively, have `verify_signature` iterate over all configured organizations' secrets (or bind verification strictly to the `Repository` resolved from `full_name`) rather than trusting an unauthenticated field to select which secret to check against.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `OrgA` and `OrgB`, each with distinct `webhook_secret`s, and each with at least one tracked `Stack` (e.g. `OrgB/victim-repo`).
2. Obtain/know `OrgA`'s `webhook_secret` (e.g., because you are a legitimate collaborator of an OrgA repo hooked to this Shipit instance).
3. Craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-or-real-sha>",
  "repository": {
     "full_name": "OrgB/victim-repo",
     "owner": { "login": "OrgA" }
  }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC validates successfully against the real Org A secret.
6. `PushHandler#process` resolves the target via `repository.full_name` = `"OrgB/victim-repo"`, finds the corresponding `Stack`, and enqueues `GithubSyncJob`/`stack.sync_github` for it — an action on Org B's stack triggered solely by knowledge of Org A's webhook secret.

*(Note: I was unable to execute this end-to-end in a live environment; the analysis above is based on static code tracing of `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/push_handler.rb`, `app/models/shipit/repository.rb`, and `app/jobs/shipit/github_sync_job.rb`. Whether the sync alone is sufficient to trigger an actual unauthorized *deploy* additionally depends on each targeted stack's continuous-deployment/CI configuration, which I could not fully verify within the tool budget.)*
