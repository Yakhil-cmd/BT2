### Title
Stack exhaustion (unbounded recursion) in address/asset definition evaluation via deeply nested operators - ([File: definition.js])

### Summary
`definition.js`'s `evaluate()` function, which validates address and asset spending-condition definitions submitted in any ordinary unit, recurses once per nesting level for operators such as `not`, `and`, and `or` with no explicit call-stack-depth guard. Unlike the analogous evaluator in `aa_validation.js`, which was hardened specifically against deep-nesting stack exhaustion, `definition.js`'s recursive `evaluate()` relies solely on `complexity`/`count_ops` counters to bound recursion, not on stack-depth interruption.

### Finding Description
`aa_validation.js`'s recursive `validate()` function explicitly protects against deep nesting: it tracks `depth`, rejects with `"max depth reached"` past `MAX_DEPTH`, and periodically calls `setImmediate` to interrupt the native call stack: [1](#0-0) 
There is even a comment elsewhere in the file explicitly noting the purpose of interrupting the call stack "to protect against deep nesting": [2](#0-1) 

In contrast, `definition.js`'s `evaluate()` function — the recursive core of `validateDefinition()`, which validates address definitions and asset spending conditions (`issue_condition`/`transfer_condition`) supplied by an unprivileged unit author — has no equivalent depth-tracking or `setImmediate` interruption. It only increments `complexity`/`count_ops` and compares them to `MAX_COMPLEXITY`/`MAX_OPS`: [3](#0-2) 

Operators such as `not` recurse directly into `evaluate()` for their nested sub-expression, adding a JavaScript call frame per level while incrementing `complexity` by only 1 per level: [4](#0-3) 

Similarly `and`/`or` (in `validateDefinition`'s `evaluate`, and again in `validateAuthentifiers`'s `evaluate`) recurse into nested boolean sub-trees via `async.eachSeries`, which is synchronous when only a single array element is present, allowing an attacker to construct a long chain of single-element `and`/`or`/`not` wrappers: [5](#0-4) 

This function is reached from `validateAuthor()` in `validation.js` for every author of every posted unit that declares (or references) a definition: [6](#0-5) 
and from `validateAuthentifiers()` which re-invokes `validateDefinition()` on every signature check (`definition.js:1454`): [7](#0-6) 

Because the recursion depth is bounded only by `MAX_COMPLEXITY`/`MAX_OPS` (not by an explicit stack-depth check with periodic `setImmediate`), an attacker who can keep per-level complexity accounting minimal (e.g. via `not` wrapping, which costs only 1 complexity unit per level) can potentially reach a recursion depth sufficient to exhaust the V8 stack before hitting the complexity/ops cap, depending on the actual numeric value of `MAX_COMPLEXITY`/`MAX_OPS` (I was unable to confirm this exact constant value from the available index — `constants.js` matches were found but content not retrieved). This mirrors the CVE-class bug in libexpat's `build_model`, where attacker-controlled nesting depth in a document drove native stack exhaustion because the parser recursed per nesting level without a depth cap independent of other resource limits.

### Impact Explanation
If reachable, an unprivileged unit author could post a unit whose author `definition` (or an asset's `issue_condition`/`transfer_condition`) contains deeply nested `not`/`and`/`or` expressions. When full nodes validate this unit (in `validateAuthor` → `validateDefinition` and later `validateAuthentifiers` on every subsequent spend), the recursive `evaluate()` call could exhaust the Node.js stack, crashing or hanging the validating process with an uncaught `RangeError: Maximum call stack size exceeded`. Because every node must independently validate the same unit to reach the same stability/validity verdict, a crash during validation could cause nodes to become unable to process the unit (denial of service on validation), which affects the network's ability to confirm units authored with (or referencing) the crafted definition. This aligns with the "network unable to confirm new units" / "node disagreement on validity" impact category.

### Likelihood Explanation
Likelihood depends on the concrete value of `MAX_COMPLEXITY`/`MAX_OPS`, which I could not verify with certainty from indexed content. If either limit is large enough (e.g., in the thousands) relative to Node's default stack frame budget for this recursion pattern, this is trivially reachable by any unprivileged party who can post a unit with a self-authored or asset-spending-condition definition — no special privileges are required, matching the strongest reachable "unit posted by any user" path. If the limits are small (e.g., low hundreds), the risk is reduced. This uncertainty should be resolved by checking the actual `MAX_COMPLEXITY`/`MAX_OPS` values in `constants.js` and empirically testing the maximum achievable recursion depth for `not`-only or single-element `and`/`or` chains against Node's stack limits.

### Recommendation
Apply the same protection pattern already used in `aa_validation.js`'s `validate()` to `definition.js`'s `evaluate()` (both in `validateDefinition` and `validateAuthentifiers`): track an explicit `depth` parameter, enforce a `MAX_DEPTH` independent of `complexity`/`count_ops`, and periodically yield the call stack via `setImmediate` for deeply recursive branches (or convert the traversal to an explicit iterative stack-based algorithm) so that native stack usage is decoupled from the complexity/ops budget.

### Proof of Concept
Construct an address definition (or asset `issue_condition`/`transfer_condition`) consisting of many nested single-argument `not` wrappers around a valid leaf condition, e.g. (conceptually):
```
["not", ["not", ["not", ... ["sig", {...}] ... ]]]
```
repeated N times, where N is chosen just under whatever `MAX_COMPLEXITY`/`MAX_OPS` allows (since `not` costs 1 complexity unit per level) but large enough to exceed V8's default recursion limit. Post this as the `definition` field of a unit author (`validation.js:1464`) or as an asset's `issue_condition`; when a node validates it via `definition.js`'s `evaluate()` (`definition.js:397-399`), the recursive calls should trigger stack exhaustion. I was not able to execute this PoC or confirm the exact `MAX_COMPLEXITY` value against Node's stack limit using the available read-only tools — this should be verified in a live/test environment before treating this as confirmed exploitable.
