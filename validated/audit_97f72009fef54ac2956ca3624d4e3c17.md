### Title
Rotated/stale git credentials are never revoked from the on-disk credential store - (File: main.go)

### Summary
The BathHouse "can't revoke a strategist" bug class maps to git-sync's credential lifecycle: `git-sync` has code to *grant* (approve) git credentials but never a corresponding call to *revoke* (reject) them. [1](#0-0)  Once a URL/username/password is approved via `git credential approve`, it is written to git's persistent credential store and remains usable for authenticating to that host indefinitely, even after the underlying secret is rotated, removed, or changed in git-sync's own configuration.

### Finding Description
`StoreCredentials` is the only function that touches the git credential store, and it always calls `git credential approve`, never `git credential reject`: [1](#0-0) 

This is invoked from `refreshCreds`, which runs on every sync cycle for each entry in `--credential`/`GITSYNC_CREDENTIAL` and for `--askpass-url` responses: [2](#0-1) 

For `--askpass-url`, credentials are dynamic and re-fetched every sync via `CallAskPassURL`, which also only calls `StoreCredentials` (i.e., `approve`), never rejecting the previous entry: [3](#0-2) 

Git's default `credential.helper` "store" backend appends a `url=/username=/password=` line to a plaintext credential file when approving a credential; it does not delete or overwrite prior entries for the same host/user when the password changes. Because git-sync never issues `git credential reject`, every password/token that has ever been used for a given URL+username (including passwords that were rotated out via `--password-file`, or older `--askpass-url` responses, or credentials for URLs that were later removed from the `--credential` list) remains valid and stored on disk for the lifetime of the container's home directory/volume. If `HOME` (and hence the credential store file) is backed by a persistent or shared volume (e.g., a long-lived pod or a mounted `emptyDir`/PV reused across restarts), a compromised, rotated-out, or intentionally revoked token/password is never actually invalidated from git-sync's perspective — it stays usable by anything with access to that file or by git itself on subsequent credential lookups until the file is manually purged.

### Impact Explanation
This is directly analogous to the "strategist can't be removed" issue: a previously-granted authentication credential cannot be revoked through any exposed git-sync mechanism. If a token used via `--credential`/`--askpass-url` is later found to be compromised and rotated (new value supplied), the old value is not removed from the on-disk store, so:
- Disclosure of the credential file (e.g., via a container filesystem dump, backup, or shared volume) reveals not just current but also historical/rotated credentials that operators believed were revoked.
- Any process with read access to the same `HOME`/credential file (e.g., another container sharing the volume, or a future pod reusing a persistent volume) can still authenticate with the old, "revoked" credential against the remote host, since `git credential fill` will happily return any matching stored entry.

### Likelihood Explanation
Requires that the credential store persists across credential rotations, i.e., `HOME`/git's credential-store file survives multiple `refreshCreds` cycles, which is the normal case for a long-running git-sync sidecar that is not restarted on every credential change (this is exactly the scenario `--askpass-url` and `--credential` with `password-file` are designed for — rotating credentials without a restart). No attacker control of git-sync internals is required; it is inherent in `StoreCredentials` always approving and never rejecting.

### Recommendation
Before approving a new credential for a given URL/username in `StoreCredentials`/`CallAskPassURL`, first issue `git credential reject` for that URL (and previously known username, if changed) to purge the stale entry from the credential store, or switch to a non-persistent credential helper (e.g., `cache` with a short timeout, or an in-memory helper) so that old credentials cannot outlive their intended validity window.

### Proof of Concept
1. Start git-sync with `--credential='{"url":"https://example.com","username":"u","password-file":"/creds/pass"}'` where `/creds/pass` contains `secret-v1`.
2. Let git-sync run through a sync cycle; `StoreCredentials` calls `git credential approve` with `password=secret-v1`, persisting it to the credential store file under `HOME`. [4](#0-3) 
3. Rotate the secret: update `/creds/pass` to `secret-v2` (this is the documented token-rotation flow: "re-read it from disk to pick up token rotation"). [5](#0-4) 
4. On the next sync cycle, `StoreCredentials` approves `secret-v2`, but `secret-v1` is never rejected and remains present as a separate valid entry in the credential store file.
5. Inspect the credential store file (default `~/.git-credentials`) — both `secret-v1` and `secret-v2` are present and usable by `git credential fill` for `https://example.com`, demonstrating that the "revoked" (rotated-out) credential was never actually invalidated.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}

// CallAskPassURL consults the specified URL looking for git credentials in the
// response.
//
// The expected URL callback output is below,
// see https://git-scm.com/docs/gitcredentials for more examples:
//
//	username=xxx@example.com
//	password=xxxyyyzzz
func (git *repoSync) CallAskPassURL(ctx context.Context) error {
	git.log.V(3).Info("calling auth URL to get credentials")

	var netClient = &http.Client{
		Timeout: time.Second * 1,
		CheckRedirect: func(req *http.Request, via []*http.Request) error {
			return http.ErrUseLastResponse
		},
	}
	httpReq, err := http.NewRequestWithContext(ctx, http.MethodGet, git.authURL, nil)
	if err != nil {
		return fmt.Errorf("can't create auth request: %w", err)
	}
	resp, err := netClient.Do(httpReq)
	if err != nil {
		return fmt.Errorf("can't access auth URL: %w", err)
	}
	defer func() {
		_ = resp.Body.Close()
	}()
	if resp.StatusCode != http.StatusOK {
		errMessage, err := io.ReadAll(resp.Body)
		if err != nil {
			return fmt.Errorf("auth URL returned status %d, failed to read body: %w", resp.StatusCode, err)
		}
		return fmt.Errorf("auth URL returned status %d, body: %q", resp.StatusCode, string(errMessage))
	}
	authData, err := io.ReadAll(resp.Body)
	if err != nil {
		return fmt.Errorf("can't read auth response: %w", err)
	}

	username := ""
	password := ""
	for line := range strings.SplitSeq(string(authData), "\n") {
		keyValues := strings.SplitN(line, "=", 2)
		if len(keyValues) != 2 {
			continue
		}
		switch keyValues[0] {
		case "username":
			username = keyValues[1]
		case "password":
			password = keyValues[1]
		}
	}

	if err := git.StoreCredentials(ctx, git.repo, username, password); err != nil {
		return err
	}

	return nil
}
