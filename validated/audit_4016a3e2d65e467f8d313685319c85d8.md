### Title
Cross-repository CI status forgery via unscoped `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Shipit's webhook signature check authenticates a GitHub webhook against the GitHub App/secret configured for the *organization named in the payload* [1](#0-0) . However, the `status` event handler updates commit statuses by matching **only** the commit SHA globally, with no scoping to the repository/organization that was actually authenticated, breaking the binding `organization authenticated == repository written`.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the HMAC secret) to check against using `repository_owner`, a value read straight out of the untrusted JSON payload (`repository.owner.login` or `organization.login`) [2](#0-1) . This is the correct model when a Shipit instance is configured with a `github:` section per-organization (documented in `docs/setup.md`, "Using Multiple Github Applications") — each organization has its own webhook secret, and only that organization's key can produce a valid signature for events "belonging" to it.

Most webhook handlers correctly scope their side effects to the repository named in the payload via `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` before touching any records [3](#0-2) . `PushHandler`, the `pull_request` handlers, etc. all filter through `repository`/`stacks` derived from `params.repository.full_name`.

`StatusHandler` does not do this. It looks up `Commit` rows by `sha` alone, with no repository/organization scoping at all, and pushes the attacker-supplied status onto every matching commit in the entire Shipit database: [4](#0-3) 

Each `Commit` belongs to a `Stack`, which belongs to a `Repository`/organization [5](#0-4) , and commit statuses gate deploys via `required_statuses`/`blocking_statuses`, which are delegated from `Commit` to `Stack` [6](#0-5) .

Because git commit SHAs are content-addressed, two different, unrelated repositories can contain a `Commit` object with an identical SHA (e.g. via forks, or an attacker deliberately replicating tree/parent/author/committer/timestamp data of a public commit into their own repository). If a Shipit installation is configured for multiple GitHub organizations (a documented, supported configuration), an attacker who controls one onboarded organization/repository can:
1. Author (or otherwise legitimately obtain, via forking) a commit whose SHA collides with a commit that exists in a *different, victim* organization's tracked stack.
2. Send a genuinely-signed `status` webhook for their own organization, referencing that SHA with `state: success` (or any other status/context).
3. Because `StatusHandler` matches on SHA only, Shipit records this forged status against the victim's commit, even though the webhook was authenticated for a completely different repository/organization.

This breaks the equality binding "organization authenticated == repository written": the signature proves control of organization A, but the record written belongs to organization B's stack.

### Impact Explanation
Commit statuses recorded this way feed directly into deploy gating (`required_statuses`/`blocking_statuses`, `ci.require` in `shipit.yml`, as documented in `README.md`). By forging a passing/required CI status for a victim's commit from an attacker-controlled but legitimately-onboarded organization, an attacker can cause Shipit to treat a commit as CI-green when it is not, potentially unblocking or triggering an unauthorized deploy for a stack/repository the attacker does not otherwise have write access to. This matches the "unauthorized deploy" High/Critical impact category in scope.

### Likelihood Explanation
Exploitation requires the Shipit instance to be configured for at least two GitHub organizations (a supported, documented configuration) and requires the attacker to control one of them (an unprivileged attacker relative to the victim organization) and to be able to produce/obtain a colliding SHA in the victim's stack (trivial via forking a public repository, or crafting an identical commit object independently, both realistic given git's content-addressing). No privileged Shipit credentials, `webhook_secret`, or `GITHUB_TOKEN` are needed — only a validly signed webhook from the attacker's own, legitimately configured organization.

### Recommendation
Scope `StatusHandler#process` the same way other handlers are scoped: resolve the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` (as `Handler#stacks` already does) and restrict the `Commit.where(sha: params.sha)` lookup to commits belonging to that repository's stacks, rejecting or ignoring any commit whose owning stack does not match the authenticated repository.

### Proof of Concept
1. Configure Shipit for two organizations, `victim-org` and `attacker-org`, each with its own GitHub App/webhook secret (per `docs/setup.md`).
2. `victim-org/repo` has a tracked `Stack` with a commit `C` (SHA `S`) awaiting a required CI status.
3. Attacker forks/creates a commit with identical content (same tree, parent, author, committer, timestamps, message) in `attacker-org/repo`, producing the same SHA `S`.
4. Attacker's CI (or attacker directly) sends a GitHub `status` webhook to `POST /webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with `attacker-org`'s webhook secret, and payload `{"sha": "S", "state": "success", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/repo"}, ...}`.
5. `WebhooksController#verify_signature` verifies successfully against `attacker-org`'s secret [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: 'S')`, finds `C` in `victim-org`'s stack, and calls `commit.create_status_from_github!(params)`, recording a forged `success` status on the victim's commit [4](#0-3) .
7. If `S` was the only missing required status for `victim-org`'s stack, the commit now appears deployable, potentially enabling an unauthorized deploy.

Note: I was unable to further verify the exact deploy-gating condition logic in `app/models/shipit/stack.rb` (`required_statuses`, `deployable?`) within the available exploration budget; this should be confirmed by a follow-up review of that file before treating the "unauthorized deploy" consequence as fully proven end-to-end.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )
      head(422) unless verified

      Rails.logger.info([

    rescue Shipit::GithubOrganizationUnknown => e

        "status=#{status}"
      ].join(' '))
    end
