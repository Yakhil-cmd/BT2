### Title
Webhook signature verification is scoped to the payload's `repository.owner.login`, but stack mutation is scoped to `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to verify the request against based on `repository.owner.login` (or `organization.login`) extracted from the *unverified* JSON body. The actual write target of the request — which `Stack`/`Repository` gets synced — is selected by a *different* field in the same body, `repository.full_name`, inside `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing binds these two fields together, so the "authenticating organization" and the "repository that is written" can diverge.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) [2](#0-1) 

It calls `Shipit.github(organization: repository_owner)` and checks `verify_webhook_signature` against that organization's configured secret only. In `lib/shipit/github_app.rb`: [3](#0-2) 

Critically, `return true unless webhook_secret` — if the organization resolved from `repository.owner.login` has **no `webhook_secret` configured** (an explicitly supported/documented configuration, see `config/secrets.development.shopify.yml` and `docs/setup.md` showing `webhook_secret: # nil`), signature verification is bypassed unconditionally for any payload claiming that organization, regardless of the `X-Hub-Signature` header content.

Meanwhile, every webhook handler (`PushHandler`, pull-request handlers, etc.) resolves the actual `Stack`/`Repository` to mutate via a **different** payload field: [4](#0-3) 

`Repository.from_github_repo_name(repository_name)` looks up the repo by `repository.full_name`, independent of `repository.owner.login`. `PushHandler#process` then directly triggers a sync against whatever `Stack` matches that `full_name`: [5](#0-4) 

Nothing in the request pipeline requires `repository.owner.login == owner-portion-of(repository.full_name)`. Since the org used for authentication (`repository_owner`) and the repo used for the write (`repository.full_name`) are independently attacker-supplied fields in the same unauthenticated-until-verified JSON body, an attacker who knows (or can determine, e.g., by trial) that some organization configured on the instance has no `webhook_secret` set can:
1. Send a POST to `WebhooksController#create` with `X-Github-Event: push`.
2. Set `repository.owner.login` (or `organization.login`) to the org with no secret configured — signature check passes trivially via the `return true unless webhook_secret` short-circuit.
3. Set `repository.full_name` to `victim-org/victim-repo`, a real repository tracked by a Stack under a *different*, properly-secured organization.
4. `PushHandler` resolves the real victim `Stack` via `Repository.from_github_repo_name` and calls `stack.sync_github(expected_head_sha: params.after)`, enqueuing `GithubSyncJob`, which fetches commits from GitHub and can trigger `continuous_deployment` on that stack.

This is a direct analog of the Sherlock M-3 bug class in the rules ("an organization that authenticated versus the repository that is written").

### Impact Explanation
This can cause `GithubSyncJob` to run against a stack that the attacker was never authenticated for, potentially triggering continuous deployment / merge-queue behavior on a repository whose organization has a properly configured webhook secret, purely because a *different, unrelated* organization on the same Shipit instance forgot to set (or intentionally left blank) its `webhook_secret`. This maps to "an unauthorized deploy" impact category, since it can kick off `sync_github` → CD pipeline for a repository the forged request was never cryptographically authorized to act on.

### Likelihood Explanation
This requires the operator to have at least one configured GitHub organization on the multi-org install with `webhook_secret` unset — a state the shipped example config (`config/secrets.development.shopify.yml`) and `docs/setup.md` explicitly show as valid/expected ("If it's missing, the Shipit installation will be public..."). It does not require any GitHub App private key, session, API token, or repository write access — only knowledge/guessing of one configured organization's login without a secret, and the target `full_name`. Given webhook payloads and instance behavior can be probed unauthenticated (repeated `422`s reveal unknown orgs vs `200`/`204` reveal known/handled ones), this is a plausible unprivileged attack path once such a misconfiguration exists.

### Recommendation
Bind the org resolved for signature verification to the same repository that the handlers act on: derive `repository_owner` from `repository.full_name`'s owner segment (or require them to match) instead of trusting `repository.owner.login`/`organization.login` independently. Additionally, do not silently treat a missing `webhook_secret` as "verification passes" — require an explicit opt-in (e.g., only skip verification if no orgs at all have secrets configured, not per-organization) to avoid a single misconfigured organization undermining others' verification guarantees.

### Proof of Concept
```
POST /github/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef        # arbitrary, unverified because org has no secret
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "attackercontrolledsha",
  "repository": {
    "owner": { "login": "org-without-webhook-secret" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`verify_signature` resolves `Shipit.github(organization: "org-without-webhook-secret")`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`). `PushHandler` then resolves `victim-org/victim-repo`'s real `Stack` via `repository.full_name` and calls `stack.sync_github(expected_head_sha: "attackercontrolledsha")`, enqueuing `GithubSyncJob` against a stack the forged signature never actually authenticated for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
