### Title
Nested-address evaluation skip uses unanchored prefix match on signing paths, letting an unsigned branch be treated as "has signature" — ([File: definition.js])

### Summary
`ocore`'s `validateDefinition` optimization for skipping evaluation of unused nested (`["address", …]`) branches decides whether a branch's signature requirement even needs to be checked by testing if the branch's `path` is a *string prefix* of one of the supplied authentifier paths, exactly the class of bug in the Hono `serveStatic` advisory: one component decides "is this under a protected/signed path?" using naive prefix comparison instead of a properly delimited/normalized path match, while the component that actually performs signature verification (`assocAuthentifiers[path]`) uses exact-path matching.

### Finding Description
`pathIncludesOneOfAuthentifiers` performs a plain `substr` prefix comparison with no separator boundary check: [1](#0-0) 

This is used by `needToEvaluateNestedAddress` to decide, for every `["address", other_address]` leaf encountered while validating/evaluating an address definition, whether the nested definition actually needs to be evaluated at all: [2](#0-1) 

and it is consumed at the `address` op both in `validateDefinition` and in `validateAuthentifiers`: [3](#0-2) [4](#0-3) 

When `needToEvaluateNestedAddress(path)` returns `false`, the code short-circuits with `cb(null, true)` — i.e. it *assumes* the branch is satisfied/has a signature without actually verifying anything, purely as a "this branch is irrelevant to the presented authentifiers, so skip it for speed" optimization (guarded by `skipEvaluationOfUnusedNestedAddressUpgradeMci`).

Because `pathIncludesOneOfAuthentifiers` uses `authentifier_path.substr(0, path.length) === path` with no check that the next character in `authentifier_path` is a path separator (`.`) or end-of-string, paths that are only *numerically* similar but structurally distinct will incorrectly match. For example, path `r.1` is treated as a prefix of authentifier path `r.10.0`, because `"r.10.0".substr(0, 3) === "r.1"`. Sibling branch `r.10` would wrongly be judged "needed" (or, depending on ordering/branch structure, an unrelated sibling like `r.1` vs. `r.19` could cause a branch that should be skipped to instead be evaluated, or vice versa) purely due to lexical prefix collision on the numeric path segments, not genuine tree containment.

This is architecturally identical to the reported bug class: `serveStatic`'s router-level authorization check normalizes/matches `/admin/*` textually while the underlying resource resolution treats `//admin/secret.txt` differently — here, the "is this branch relevant to a provided authentifier" decision is made with unanchored substring matching while the actual authentifier lookup (`assocAuthentifiers[path]`, an exact-key object lookup in the `sig`/`hash` cases) is exact-match. The two components ("do we need to check this branch" vs. "does this branch's signature verify") disagree on path semantics.

### Impact Explanation
If the optimization can be tricked into skipping evaluation of a branch that actually requires a real, unverified signature (treating it as `bHasSig = true` for free), an attacker who controls the numeric structure of an `or`/`and`/`r of set` address definition (which any user can define, since address definitions are user-supplied and validated once per unit) could satisfy a multi-branch signature policy without providing a valid signature/hash for one of the required branches, as long as they supply an authentifier at a colliding-prefix path for an unrelated branch. This would let an unauthorized party spend from a shared/multisig address or pass an AA/asset spending condition it should not be able to satisfy — i.e., unauthorized spending — which is a Medium/High-severity impact class matching the scope rules (concrete unauthorized spending).

### Likelihood Explanation
Exploitability depends on constructing an address definition (or AA-referenced definition) whose `or`/`r of set` branches have numeric path indices that collide under naive prefix matching (e.g. more than 9 siblings at one level, producing paths like `r.1` and `r.10`), and on the target validation running at/after `skipEvaluationOfUnusedNestedAddressUpgradeMci` so the skip path is active. This requires the attacker to control (or influence the layout of) the address definition being spent from, which is realistic for definitions the attacker themselves authored or for AA/shared-address templates with attacker-supplied branch counts, making it reachable by a normal unprivileged unit poster. It is not proven from source alone whether the effective evaluation order/short-circuiting in `or`/`and` actually turns this into a full signature-bypass end-to-end (as opposed to only an internal optimization inefficiency); this requires a live PoC to confirm.

### Recommendation
Change `pathIncludesOneOfAuthentifiers` to require a proper path-boundary match, e.g. compare `authentifier_path === path || authentifier_path.startsWith(path + '.')`, so that `r.1` is never considered a prefix of `r.10`. Add a regression test with an `or`/`r of set` definition containing 10+ branches (so two-digit and one-digit indices coexist) verifying that skipping/evaluating nested addresses is decided only by genuine path containment.

### Proof of Concept
Conceptual PoC (needs to be validated against live `validateAuthentifiers`/`validateDefinition` flow, not confirmed executable from static review alone):
1. Construct an address definition containing an `or` (or `r of set`) with ≥ 11 members, where member index `1` is `["address", A1]` (a nested address requiring a real signature) and index `10` (or any two-digit index beginning with "1") is a simple `["sig", …]` branch.
2. Submit a unit spending from this address supplying only the authentifier at path `r.10` (satisfying the simple sig branch) and no authentifier for `r.1`/the nested address branch.
3. During validation, `needToEvaluateNestedAddress("r.1")` calls `pathIncludesOneOfAuthentifiers("r.1", ["r.10"], …)`, which incorrectly returns `true` because `"r.10".substr(0,3) === "r.1"`, even though `r.10` is not actually within the `r.1` subtree.
4. If this causes the `r.1` (`["address", A1]`) branch to be evaluated with a stale/incorrect assumption, or — depending on control flow inversion — to be skipped and short-circuited as `bHasSig = true`, the overall `or` requirement can be satisfied without a genuine signature for that branch, exact behavior needs to be confirmed with a running test against `Definition.validateAuthentifiers`.

function pathIncludesOneOfAuthentifiers(path, arrAuthentifierPaths, bAssetCondition){
	if (bAssetCondition)

		var authentifier_path = arrAuthentifierPaths[i];

	}
	return false;
