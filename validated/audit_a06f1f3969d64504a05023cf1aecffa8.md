### Title
Webhook signature is verified against `repository.owner.login`, but the acted-upon repository is resolved from the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to validate a webhook against using `repository_owner`, extracted from the JSON body as `params.dig('repository', 'owner', 'login')` (or `params.dig('organization', 'login')` as a fallback). [1](#0-0) [2](#0-1)  Once the signature check passes, every event handler resolves the actual `Repository`/`Stack` that will be mutated using a completely different field of the same body: `payload.dig('repository', 'full_name')`, via `Handler#repository_name` and `Repository.from_github_repo_name`. [3](#0-2) [4](#0-3) 

Nowhere is it enforced that `repository.owner.login == repository.full_name.split('/').first`. This is structurally the same defect class as the reported M-34 issue: one part of the system (the field used to pick the verifying key/organization) is decoupled from the field that is actually acted upon (the field used to select the repository whose stacks get synced/mutated), so the HMAC verification does not cover the value that drives the write.

### Finding Description
- `verify_signature` authenticates the request against the `GitHubApp` config for `repository_owner` (`repository.owner.login`, falling back to `organization.login`). [1](#0-0) 
- Each handler (e.g. `PushHandler`) then loads the target `stacks` via `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository', 'full_name')`. [5](#0-4) [3](#0-2) 
- `Repository.from_github_repo_name` splits `full_name` on `/` to get `owner`/`name` and looks up the `Stack` to act on, entirely independent of the `owner.login` value used earlier for signature-key selection. [4](#0-3) 
- In a Shipit installation onboarding multiple GitHub organizations, each organization has its own `webhook_secret` configured under `Shipit.github(organization: ...)`. [6](#0-5)  Because `verify_webhook_signature` only checks the HMAC against the secret picked for `repository_owner`, and the handlers act on `repository.full_name` instead, a party who legitimately possesses a valid webhook secret for one onboarded organization ("Org B") can produce a payload whose `repository.owner.login`/`organization.login` is `"Org B"` (so the correct, known-to-them secret is selected and validated) while `repository.full_name` names a repository belonging to a different onboarded organization ("Org A"), causing Shipit to sync/act on Org A's stack using a signature that was only ever checked against Org B's key.

Binding broken (equality that should hold but is not enforced):
`organization authenticated by verify_signature (repository.owner.login)` == `organization implied by repository.full_name (used to select the Repository/Stack that is written)`.

### Impact Explanation
If exploitable, this allows a tenant organization with valid credentials for its own webhook secret to trigger writes (e.g. `PushHandler` calling `stack.sync_github(expected_head_sha:)`, or other handlers mutating `Team`/`User`/stack state) against repositories/stacks owned by a different organization on the same shared Shipit instance — i.e., cross-repository/cross-tenant writes, which is explicitly listed as a Critical impact category.

### Likelihood Explanation
Exploitability is conditioned on Shipit being deployed multi-tenant (multiple organizations configured under `Shipit.github`), and on the attacker already holding a legitimate webhook secret for at least one onboarded organization — this is the minimum privilege needed to pass `verify_webhook_signature` at all. Within that constraint, no additional cross-check exists anywhere in `WebhooksController` or `Handler` to bind the authenticated organization to the repository actually resolved and acted upon, so likelihood is high once the multi-tenant precondition holds.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), after determining `repository_owner`, also verify that any `repository.full_name` present in the same payload has an owner segment matching `repository_owner` before dispatching to handlers; reject the request (422) on mismatch.

### Proof of Concept
1. Onboard two organizations to the same Shipit instance: `org-b` (attacker-controlled, attacker knows `webhook_secret_b`) and `org-a` (victim, has a stack tracking `org-a/victim-repo`).
2. Craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "organization": { "login": "org-b" },
  "repository": { "owner": { "login": "org-b" }, "full_name": "org-a/victim-repo" }
}
```
3. Compute `X-Hub-Signature` as `sha1=HMAC(webhook_secret_b, body)` and send it as `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner = "org-b"`, loads `Shipit.github(organization: "org-b")`, and the HMAC validates successfully. [1](#0-0) 
5. `PushHandler#process` then resolves stacks via `Repository.from_github_repo_name("org-a/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim organization's stack, using an attacker-supplied `after` SHA that was never checked against `org-a`'s own secret. [5](#0-4)
