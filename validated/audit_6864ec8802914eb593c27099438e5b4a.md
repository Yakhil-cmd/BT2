### Title
Cross-organization Team hijack via globally-unique `github_id` lookup in `MembershipHandler` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves `Shipit::Team` rows solely by the attacker-supplied `params.team.id` (mapped to the global `github_id` column), with no scoping to the organization whose webhook secret verified the request. Because `Team` has no compound uniqueness on `(organization, github_id)`, a webhook legitimately signed by organization A's own webhook secret can name organization B's real team `github_id` and mutate B's already-existing `Team` row, adding an attacker-controlled user to it.

### Finding Description
The binding that should hold is: **the `Team` row created or mutated by a membership payload must belong to the same organization that verified that payload**, i.e. `team.organization == repository_owner_used_for_signature_verification`.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and verifies the signature using `Shipit.github(organization: repository_owner)`'s per-organization `webhook_secret` [2](#0-1) . For a `membership` event this is `params.organization.login` — fully controlled by whichever tenant is sending the request, and it must equal the attacker's own organization (A) for the HMAC check to pass with A's secret.
- Once verified, `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login; ... }` [3](#0-2) . The `github_id: params.team.id` key is declared only as `requires :id, Integer` in the params schema [4](#0-3)  — a bare integer with no relation to the verified organization A.
- If a `Team` row with that `github_id` already exists (e.g., legitimately created earlier from organization B's own membership webhook), `find_or_create_by!` returns the **existing** record and the `organization:` assignment inside the block is skipped (block only runs `on create`). The row still belongs to B, but the handler proceeds to mutate it: `team.add_member(member)` where `member = User.find_or_create_by_login!(params.member.login)` — a Shipit user the attacker controls (their own GitHub login) [5](#0-4) .
- The result: an attacker-controlled `User` is inserted as a `Membership` on organization B's `Team`, even though the request was authenticated only against organization A's secret.

None of the existing guards prevent this: `verify_signature` only proves "this payload matches org A's secret," it does not constrain which `github_id`/team the payload may reference; the `ExplicitParameters` schema only checks types (`Integer`, `String`), not ownership; and `Team.find_or_create_by!` has no organization-scoped uniqueness constraint to stop a global `github_id` collision from resolving to another tenant's row.

### Impact Explanation
An attacker who legitimately controls (or creates) one small Shipit-connected GitHub organization A can add their own Shipit user as a member of any pre-existing `Team` belonging to a different, more privileged organization B, as long as they know that team's numeric `github_id` (visible via GitHub's public UI/API for public org teams). If that `Team` corresponds to one of `Shipit.github_teams` (used for authorization checks, see `Shipit.github_teams` mapping org OAuth teams to `Team` rows) [6](#0-5) , this is a privilege-escalation primitive: the attacker's Shipit user becomes a "member" of a team that may be relied upon elsewhere for authorization, without B's organization ever consenting or B's webhook secret being used. This matches the "escalation into `Shipit.github_teams` authorization" High-severity category. It is repeatable against any target team whose `github_id` is discoverable and already exists as a `Team` row in the host's database.

### Likelihood Explanation
Preconditions: the attacker must operate (or register) at least one organization that the Shipit host has configured with a distinct `webhook_secret` (multi-tenant Shipit host with per-org GitHub App/webhook config), and must know the target's team `github_id` (obtainable from public GitHub org/team pages/APIs) and the target `Team` row must already exist in Shipit's DB (created by a prior legitimate membership event from org B). No Shipit credentials, session, or secrets are needed beyond the attacker's own organization's webhook secret, which they legitimately possess. This is a low-cost, fully repeatable attack via a single crafted HTTP POST to `/webhooks`.

### Recommendation
Scope `Team` lookups/uniqueness by `(organization, github_id)` instead of `github_id` alone, and have `MembershipHandler#find_or_create_team!` verify that any existing row's `organization` matches `params.organization.login` (the organization that was cryptographically verified for this request) before mutating membership — rejecting or logging a mismatch rather than silently applying the change to a foreign team.

### Proof of Concept
minitest plan (webhooks controller / integration level):
1. Fixtures: two `GithubHook::Organization` rows, `org_a` (organization: "org-a", secret: "secretA") and `org_b` (organization: "org-b", secret: "secretB"), each configured in `Shipit.github` test config with distinct `webhook_secret`s.
2. Create a pre-existing `Team` fixture `team_b` with `github_id: 999, organization: "org-b"`.
3. Build a membership payload: `{ action: "added", team: { id: 999, name: "x", slug: "x", url: "http://x" }, organization: { login: "org-a" }, member: { login: "attacker" } }`.
4. Sign the payload with `secretA` (org A's real secret) and POST to `/webhooks` with `X-Github-Event: membership` and the resulting `X-Hub-Signature`.
5. Assert response is `:ok` (200), proving signature verification against org A succeeded (`repository_owner` == "org-a").
6. Assert equality on both sides of the binding:
   - Expected (safe) binding: `team_b.reload.organization == "org-a"` should be false (it stays "org-b"), and `team_b.members` should NOT include the attacker's user — this is what SHOULD happen if scoping is enforced.
   - Observed (vulnerable) behavior: `team_b.reload.members.map(&:login)` includes `"attacker"`, proving a payload verified under org A's secret mutated org B's `Team` row (`Shipit::Team.find_by(github_id: 999).organization` is still `"org-b"` while membership was added by an org-A-signed request), confirming the cross-tenant write.
