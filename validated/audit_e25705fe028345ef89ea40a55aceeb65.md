### Title
Webhook signature verification org (`repository.owner.login`) is never checked against the org used to resolve the mutated repository (`repository.full_name`), allowing cross-tenant ReviewStack mutation - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/*.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `params.dig('repository','owner','login')`, while every `PullRequest` handler (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `EditedHandler`, `AssignedHandler`, `LabeledHandler`, `UnlabeledHandler`) resolves the repository/stack to mutate using the *separate* `params.repository.full_name` field. Nothing enforces that these two independently-attacker-controlled JSON fields refer to the same organization, so a party who legitimately controls one org's webhook secret can sign a payload naming a different org's repository and have it acted on.

### Finding Description
The broken binding, stated as an equality that must hold but is never checked:

`verifying_org := params.dig('repository','owner','login')` (or `params.dig('organization','login')`) used in `verify_signature` at [1](#0-0)  and [2](#0-1) 

must equal

`acting_org := params.repository.full_name.split('/').first` used by every handler's `repository` method, e.g. [3](#0-2)  and equivalently in `opened_handler.rb` [4](#0-3) .

`Shipit.github(organization: repository_owner)` picks the `GitHubApp`/secret solely keyed by the org name string, via `github_app_config` [5](#0-4) , and `verify_webhook_signature` is a pure HMAC-over-raw-bytes check with that one secret [6](#0-5) . It does not, and cannot, verify that any other field inside the JSON body (such as `repository.full_name`) is consistent with the org whose secret was used.

Both `repository.owner.login` and `repository.full_name` are independent JSON fields inside the same raw POST body that the attacker fully controls when POSTing directly to `/webhooks` (this is not a GitHub-relayed request; the controller just does `JSON.parse(request.raw_post)` [7](#0-6) ). On genuine GitHub-originated payloads these two fields always agree because GitHub derives both from the same repository object, but Shipit never re-validates this invariant server-side.

Exploit flow: attacker legitimately administers `org-a`'s GitHub App integration with Shipit (per `docs/setup.md`'s multi-org setup, the org's admin supplies/knows the `webhook_secret` value that the Shipit operator places in `secrets.yml`), so the attacker knows `org-a`'s `webhook_secret`. Attacker crafts a `pull_request` `closed` JSON payload with `repository.owner.login = "org-a"` (or omits it and sets `organization.login = "org-a"`) but `repository.full_name = "org-b/target-repo"`, `number` / `pull_request.number` set to a real open PR in `org-b` that has a live `ReviewStack`. Attacker computes `sha1=HMAC(org-a-secret, raw_body)` and sets the `X-Hub-Signature` header, then POSTs directly to Shipit's `/webhooks`. `verify_signature` resolves `org-a`'s secret via `repository_owner` and the signature matches, so the request passes. `ClosedHandler#process` then resolves `repository` via `params.repository.full_name` = `org-b/target-repo`, builds `review_stack` via `ReviewStackAdapter` scoped to that repo's real `review_stacks`, and calls `review_stack.archive!` [8](#0-7) , which finds the existing stack by `environment` (`pr#{number}`) and deprovisions/archives it [9](#0-8) . No code path re-checks that `org-b` ever verified this payload.

Existing guards do not close this gap: `verify_signature` only checks HMAC validity for whichever org key it derives from `repository.owner.login`/`organization.login`; it never compares that key to `repository.full_name`'s owner segment. `ExplicitParameters` schemas on each handler only assert `repository.full_name` is a `String`, imposing no cross-field consistency constraint [10](#0-9) . `Repository#from_github_repo_name` and `Repository` validations only constrain the owner/name character set, not which org "authenticated" the request [11](#0-10) .

### Impact Explanation
An attacker who legitimately controls one org's Shipit GitHub App integration can archive (deprovision/tear down) or otherwise mutate `ReviewStack`/`PullRequest` state belonging to *any other org* onboarded to the same Shipit instance, as long as they can guess/observe a real open PR number with a live review stack in the target org. This is a cross-tenant write authorized under the wrong tenant's credentials — matching "a payload for one repository mutating another's stack" in the Critical impact category. It is repeatable against arbitrary target repositories/PR numbers and is not limited to `ClosedHandler`; the same `repository` derivation pattern with the same unchecked field is present in `OpenedHandler`, `ReopenedHandler`, `EditedHandler`, `AssignedHandler`, `LabeledHandler`, and `UnlabeledHandler`, so an attacker could also fabricate/provision review stacks, forge label/assignment-driven archive/unarchive transitions, or overwrite `PullRequest` metadata (`EditedHandler#process`) for a foreign org's PR.

### Likelihood Explanation
Preconditions: the Shipit instance must be configured for multiple GitHub orgs (per `docs/setup.md`'s "Using Multiple Github Applications"), the attacker must legitimately operate one onboarded org (`org-a`) and know its `webhook_secret`, and the target org (`org-b`) must have `review_stacks_enabled` with a live `ReviewStack` tied to a PR number the attacker can determine (PR numbers are small integers and often discoverable from the target's public GitHub repo). Attacker cost is low: crafting and POSTing an HMAC-signed JSON body requires no GitHub interaction at all, just direct HTTP access to the Shipit host's `/webhooks` endpoint. This is fully repeatable for as many target orgs/PRs as the attacker can enumerate.

### Recommendation
In `WebhooksController#verify_signature`, after determining the verifying organization, cross-check it against the organization embedded in `repository.full_name` (and `organization.login` if present) and reject the request (`head(422)`) on mismatch, e.g. derive `expected_owner = params.dig('repository','full_name')&.split('/')&.first` and require `expected_owner.casecmp?(repository_owner)`. Alternatively/additionally, in each handler's `repository` method, verify that `Shipit::Repository.from_github_repo_name(params.repository.full_name)&.owner` matches the same organization key that authenticated the request (threaded through from the controller), and no-op if it doesn't.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, using `secrets_double_github_app.yml`-style multi-org fixtures with `OrgOne`/`OrgTwo`):

```ruby
test "pull_request payload signed by org-a cannot mutate org-b's review stack" do
  org_a_secret = "org-a-secret"
  org_b_secret = "org-b-secret"
  Shipit.stubs(:github_app_config).with("org-a").returns(webhook_secret: org_a_secret)
  Shipit.stubs(:github_app_config).with("org-b").returns(webhook_secret: org_b_secret)

  repo_b = shipit_repositories(:org_b_repo) # owner: "org-b", review_stacks_enabled: true
  review_stack = shipit_review_stacks(:org_b_open_pr) # environment "pr42", not archived

  payload = {
    action: "closed",
    number: 42,
    pull_request: { id: 1, number: 42, url: "u", title: "t", state: "closed",
                     additions: 1, deletions: 1, head: { sha: "s", ref: "r" },
                     user: { login: "attacker" }, assignees: [], labels: [] },
    repository: { full_name: "org-b/#{repo_b.name}", owner: { login: "org-a" } },
    organization: { login: "org-a" },
    sender: { login: "attacker" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", org_a_secret, payload)

  request.headers["X-Github-Event"] = "pull_request"
  request.headers["X-Hub-Signature"] = signature

  refute review_stack.reload.archived?
  post :create, body: payload, as: :json
  assert_response :ok

  # Equality that should hold but doesn't: verifying_org ("org-a") != acting_org ("org-b")
  assert review_stack.reload.archived?, "org-b's review stack was archived by a payload verified with org-a's secret"
end
```

This asserts both sides of the equality: the org whose secret verified the signature (`org-a`) versus the org whose `ReviewStack` was mutated (`org-b`), demonstrating they diverge and the mutation still succeeds.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
