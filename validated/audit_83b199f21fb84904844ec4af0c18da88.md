### Title
Stale/revoked attestations are still honored by AA `attestation[]` formula lookups even after the attested address's definition (and thus signing authority) has been revoked - (File: formula/evaluation.js)

### Summary
The Mastodon advisory describes a logic error where content tied to a suspended/revoked identity keeps being honored by downstream consumers because the suspension state is checked at the wrong point (or not re-checked when the content is reached through another path). ocore has an analogous "identity trust" primitive: an `attestation` recorded on-chain by a trusted attestor about an `address`. Address-definition based evaluation of `attested` conditions already accounts for later revocation of that address's keys/definition, but the AA-facing `attestation[...]` oscript/ojson formula that AAs use to check KYC/whitelisting/eligibility does not.

### Finding Description
When an address's signing definition is changed (e.g., to revoke a compromised key, hand over control, or intentionally invalidate the address after a KYC provider's attestation was mis-issued), `definition.js`'s `attested` operator (used when evaluating **address/asset spending conditions**) calls `storage.filterAttestedAddresses`, which explicitly discounts attestations that predate the most recent `address_definition_change`: [1](#0-0) 

```
"... WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good'
    AND main_chain_index>IFNULL(
        (SELECT main_chain_index FROM address_definition_changes ...
         WHERE address_definition_changes.address=attestations.address ...),
    0)"
```

This means: if address `A`'s definition is changed after an attestation was posted about `A`, that attestation is no longer considered valid for spending-condition purposes — the intent is clearly that a definition change invalidates prior attestations (since control of the address may have changed hands).

However, the **AA formula evaluator's `attestation[...]` function**, which AAs use in `oscript`/`ojson` to gate fund release, whitelist checks, KYC checks, etc., queries the `attestations`/`attested_fields` tables directly with no such revocation check: [2](#0-1) 

Neither the "recent unstable AA units" query nor the "stable units" fallback query joins against `address_definition_changes` to discard attestations that predate a later definition change of the attested address. Both queries only filter by `attestor_address`, `address`, `field`, and mci/sequence — there is no `main_chain_index > IFNULL((SELECT ... address_definition_changes ...), 0)` guard analogous to `filterAttestedAddresses`.

This is directly analogous to the Mastodon bug class: a suspension/revocation event (definition change invalidating the address's control/trust) is correctly enforced in one code path (`definition.js` condition evaluation via `filterAttestedAddresses`) but is silently bypassed in another reachable path (`formula/evaluation.js`'s `attestation[]` used by AAs), letting stale, now-untrustworthy attestation data keep being "processed" by any AA that reads it.

### Impact Explanation
Any AA whose oscript/ojson logic relies on `attestation[attestors=..., address=$trigger.address, ...]` to gate fund release, minting, whitelisting, or KYC-style eligibility (a very common pattern for regulated-token AAs, ICO/whitelist AAs, and similar dApps) can be manipulated: an attacker who once received a legitimate attestation, then changes/rotates their address definition (e.g., after selling/losing control of the underlying private key, or intentionally to detach from a later attestor correction/retraction), continues to be treated by the AA as still attested. Since attestations often cannot be "un-issued" on-chain (attestors typically post a corrective/negative attestation rather than deleting the old one), and the intended enforcement mechanism against such stale trust is exactly the `address_definition_change` cutoff that `filterAttestedAddresses` implements, its absence in the AA formula path allows an unprivileged trigger sender to keep exploiting an AA that should have stopped trusting them. This can lead to unauthorized fund release/AA fund loss from the AA's perspective and is reachable purely by posting AA triggers — no privileged or node-level access required.

### Likelihood Explanation
This is directly reachable by any AA trigger sender: no special privileges, node cooperation, or timing races beyond ordinary transaction posting are required. Any AA author who uses `attestation[...]` for permission/whitelist gating is affected. The bug is a straightforward missing predicate compared to the sibling function `filterAttestedAddresses`, so it is a genuine, provable logic omission rather than a hypothetical/contrived path.

### Recommendation
Add the same `address_definition_change` recency guard used in `storage.filterAttestedAddresses` to both queries in the `attestation` case of `formula/evaluation.js`, i.e., require:
```
main_chain_index > IFNULL(
    (SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit)
     WHERE address_definition_changes.address = <table>.address AND is_stable=1 AND sequence='good'
       AND main_chain_index<=<mci> ORDER BY main_chain_index DESC LIMIT 1),
    0)
```
for both the "recent unstable AA units" and "stable units" branches, consistent with how address-definition-based `attested` conditions already treat definition changes as invalidating older attestations.

### Proof of Concept
1. Attestor `T` posts an attestation for address `A` with field `kyc_ok=1` (`attested_fields`/`attestations` tables populated).
2. An AA is deployed with logic gating fund transfer on `attestation[attestors=T, address=$trigger.address, field="kyc_ok"] == 1`.
3. `A`'s owner changes `A`'s definition (e.g., `address_definition_change` message) — semantically "revoking" the identity that was originally attested (analogous to a suspension), same as what `filterAttestedAddresses` treats as invalidating.
4. `A` (now under different/rotated key control) sends a trigger to the AA.
5. Because `formula/evaluation.js`'s `attestation[...]` query does not check `address_definition_changes`, the AA formula still returns the old attestation value (`kyc_ok=1`), letting the trigger pass the gate and drain/misuse AA funds, even though the equivalent `attested` condition in `definition.js`/`storage.filterAttestedAddresses` would have correctly rejected it.
