### Title
Webhook event processing uses a different, attacker-influenced `params` object than the one whose organization/secret was actually signature-verified - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against based on `repository_owner`, which reads from the Rails-parsed `params`. The actual event handling in `#create` re-parses `request.raw_post` into a **separate, independent** `params` local variable. These two representations of "the request" are not guaranteed to be the same payload, breaking the binding: `organization whose secret authenticated the request == organization/repository whose data is written`.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 

where `repository_owner` is derived from the controller's `params` method (populated by Rails from route/query-string/body according to `Content-Type`), not from `request.raw_post` directly:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Then `#create` independently re-parses the raw body and dispatches handlers using *that* content, with no re-verification that it matches the organization used to select the secret:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

`GitHubApp#verify_webhook_signature` trivially returns `true` when the selected organization has no `webhook_secret` configured — which the setup docs explicitly describe as optional:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) [5](#0-4) 

Because Rails' `params` is populated from the request depending on `Content-Type` (auto-parsed only for content types registered as JSON parsers), an attacker can send a POST to `/webhooks` with:
- a `Content-Type` that Rails does not parse into `params` (so `params` only reflects query-string values, e.g. `?repository[owner][login]=org-with-no-secret`), and
- a raw JSON body targeting a **different**, victim organization/repository (with any content, including `membership`, `push`, or other handled events).

`verify_signature` will resolve `repository_owner` to the attacker-chosen org (query string), fetch that org's `GitHubApp`, and — if that org has no `webhook_secret` configured — pass verification unconditionally, regardless of the actual raw body content. `#create` then processes the real (forged) JSON body against the victim's data with no further ownership check.

This is directly analogous to the reported oracle bug class: a value used for validation (`day` derived from `block.timestamp`, calculated once) diverges from the value actually acted upon at execution time, letting an attacker bypass an intended protection by controlling the mismatch window/field. Here the "day" is analogous to `repository_owner`/webhook secret selection, computed once from a source (`params`) different from the source actually processed (`request.raw_post`).

### Impact Explanation
Successful exploitation allows forging arbitrary GitHub webhook events without any valid signature, e.g.:
- `membership` events adding an attacker-controlled GitHub login to a `Team` tied to `Shipit.github_teams`, escalating access into `Shipit.github_teams` authorization [6](#0-5) [7](#0-6) .
- `push` events triggering `stack.sync_github` for arbitrary stacks/branches [8](#0-7) .

This matches the "High" impact bar: escalation into `Shipit.github_teams` authorization and unauthenticated triggering of stack state changes, achieved via bypassing the webhook authentication boundary entirely.

### Likelihood Explanation
This requires no credentials, session, or API token — the `/webhooks` endpoint is publicly reachable and unauthenticated by design. The only precondition is that at least one configured GitHub organization in `secrets.github` lacks a `webhook_secret` (explicitly documented as optional, and shown as `# nil` in example configs), or that the attacker knows any one organization's secret. Multi-organization Shipit deployments are an explicitly supported configuration [9](#0-8) , making this a realistic misconfiguration to encounter. Exact Rails parameter-parsing behavior for various `Content-Type` values (which content types are/aren't parsed into `params`) was not independently verified in this codebase and depends on the host Rails app's `ActionDispatch::Request::Utils`/registered parsers configuration; this is a limitation of the analysis.

### Recommendation
Do not use two independently derived representations of the same request for authorization vs. processing. `verify_signature` should determine the organization/repository strictly from the same parsed JSON body that `#create` will act on (parse `request.raw_post` once, before verification, and reuse it), and the signature must be verified using that same organization's secret. Additionally, treat an organization/app configured with a blank `webhook_secret` as unable to authenticate any inbound webhook by default (fail closed rather than `return true`), or require operators to explicitly opt into unsigned webhooks.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs in `secrets.github`: `victim-org` (has a real `webhook_secret`) and `attacker-org` (misconfigured/left `webhook_secret: nil`, matching the documented default) — analogous to the double-app config in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker sends:
   ```
   POST /webhooks?repository[owner][login]=attacker-org
   Content-Type: text/plain
   X-Github-Event: membership

   {"action":"added","team":{"id":<victim_team_id>,...},"organization":{"login":"victim-org"},"member":{"login":"attacker-github-login"}}
   ```
3. `verify_signature` calls `repository_owner` → resolves via `params.dig('repository','owner','login')` to `"attacker-org"` (from the query string, since the body wasn't parsed into `params` due to `Content-Type: text/plain`).
4. `Shipit.github(organization: "attacker-org").verify_webhook_signature(...)` returns `true` immediately because `attacker-org`'s `webhook_secret` is blank — no valid `X-Hub-Signature` needed.
5. `#create` parses `request.raw_post` (the real JSON body targeting `victim-org`) and dispatches `MembershipHandler`, adding the attacker's GitHub login to the victim's team, escalating them into `Shipit.github_teams` authorization without ever presenting a valid signature for `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
