## Title
Missing chain-id domain separation in `SignerCapabilityOfferProofChallengeV2` allows cross-chain replay of signer-capability delegation - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
`account::offer_signer_capability` binds its authorization proof to a `SignerCapabilityOfferProofChallengeV2` struct that contains only `sequence_number`, `source_address`, and `recipient_address` — no `chain_id`. Its sibling function `offer_rotation_capability` uses `RotationCapabilityOfferProofChallengeV2`, which explicitly adds a `chain_id` field for the documented purpose of "prevent[ing] replaying the challenge message" across chains. The asymmetry means a signer-capability delegation signed by a user on one Aptos chain/network can be replayed verbatim on a different chain where the same account address and sequence number exist, granting the recipient a `signer` for the victim's account there without the victim's actual authorization for that chain.

### Finding Description
`account.move` defines two parallel delegation proof structs: [1](#0-0) 

`RotationCapabilityOfferProofChallengeV2` explicitly documents the addition of `chain_id`/`source_address` as domain separation to stop replay, but `SignerCapabilityOfferProofChallengeV2` was never given the same treatment — it still only carries `sequence_number`, `source_address`, `recipient_address`.

`offer_signer_capability` constructs this under-bound challenge and verifies it purely via signature check, with no `chain_id` comparison anywhere in the function: [2](#0-1) 

The signature check itself (`verify_signed_message`) only compares the signer's current authentication key and validates the signature over the passed-in message; it has no notion of chain identity: [3](#0-2) 

Because Aptos networks (mainnet, testnet, devnet, or any custom chain) are independent ledgers with independently tracked account state, it is entirely possible for the same address (deterministically derived from a public key with no prior key rotation) to exist with an identical `sequence_number` on two different chains — most naturally right after account creation, when `sequence_number == 0` on every chain simultaneously. In that state, a `SignerCapabilityOfferProofChallengeV2` signed by the user's key for use on chain A is byte-for-byte valid input to `offer_signer_capability` on chain B, since neither the struct nor the verification path check `chain_id`.

This directly parallels the external report's bug class: two logically related authorization flows exist in the same module (`offer_rotation_capability` vs. `offer_signer_capability`), one was hardened with a domain-binding field to prevent misuse across contexts, and the other was not, so the "wrong context" bypasses the intended admission invariant (that a capability delegation is only valid for the chain it was signed for).

### Impact Explanation
A successful replay grants the `recipient_address` a `signer` for the victim's account via `create_authorized_signer` on a chain the victim never intended to authorize: [4](#0-3) 

Holding a `signer` for the victim's account is equivalent to unauthorized transaction execution under the wrong signer — the attacker (or a colluding recipient address) can act as the victim account on that chain, moving funds, invoking authenticated entry functions, etc. This satisfies the "Unauthorized transaction execution... under the wrong sender/signer" and "domain-binding failure that lets an attacker reuse or rebind" impact categories.

### Likelihood Explanation
Exploitability depends on the same account existing at the same sequence number on two chains — most reliably immediately after account creation (`sequence_number == 0` universally) with an address that has never had a rotation. Wallet/tooling flows that create an account and immediately offer a signer capability (e.g., automated custody/onboarding tooling used across multiple networks) are the most exposed. This is a real but narrower-than-ideal window compared to a fully unconditional replay, so likelihood is moderate rather than trivial, but the missing field is an unambiguous, provable code gap relative to the intentionally-fixed sibling function.

### Recommendation
Add a `chain_id` field to `SignerCapabilityOfferProofChallengeV2` (mirroring `RotationCapabilityOfferProofChallengeV2`) and verify it in `offer_signer_capability`, e.g.:
```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    chain_id: u8,
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```
and include `chain_id: chain_id::get()` when constructing the challenge in `offer_signer_capability`, matching the pattern already used in `offer_rotation_capability`. This requires a versioned migration path (old signatures over the V2-without-chain_id struct must be rejected or a new V3 struct introduced) to avoid breaking existing callers while closing the replay gap.

### Proof of Concept
1. On chain A (e.g., testnet), create account `alice` with fresh keypair; `sequence_number == 0`.
2. Alice signs `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: alice, recipient_address: bob }` and submits `offer_signer_capability(...)` on chain A — succeeds, matching existing test `test_valid_check_signer_capability_and_create_authorized_signer` pattern: [5](#0-4) 
3. On chain B (e.g., mainnet or a separate devnet), an account with the identical address `alice` (derived from the same public key, no rotation) is created and also sits at `sequence_number == 0`.
4. Attacker (or a party who intercepted step 2's transaction) submits the identical `signer_capability_sig_bytes`, `account_scheme`, `account_public_key_bytes`, `recipient_address` to `offer_signer_capability` on chain B.
5. Because `SignerCapabilityOfferProofChallengeV2` and `verify_signed_message` never reference `chain_id`, the same signature verifies successfully on chain B, and `bob` (or an address colluding with the attacker) is granted `signer_capability_offer.for = bob` on chain B's `alice` account without her chain-B-specific consent.

    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
