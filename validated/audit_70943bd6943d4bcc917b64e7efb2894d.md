## Analysis

The SillyTavern bug class is: **a credential (session cookie) survives past the moment its "owner" believes it was rotated/revoked**, because the system never actively invalidates the old credential — it just keeps trusting whatever was previously issued.

The direct on-chain analog in this repo is in `pox-5.clar`'s signer-key **grant** system, which pairs a `signer-key` with a `signer-manager` principal via `grant-signer-key`, and is meant to be superseded by rotation and cleared by `revoke-signer-grant`.

### Root cause

`grant-signer-key` persists a permanent `signer-key-grants` entry for `{signer-key, signer-manager}` once a valid signature is produced: [1](#0-0) 

This grant is only removed by an explicit call to `revoke-signer-grant`: [2](#0-1) 

The unit-test suite documents, in plain language, that **rotating a signer's key does not revoke the previous grant** — it only overwrites the `signers` map pointer to the new key while the old `(old-key, signer-manager)` grant entry stays live in `signer-key-grants`: [3](#0-2) [4](#0-3) 

The comment on `revoke-signer-grant` explicitly states that *every new-stake entry point re-checks the grant via `verify-signer-key-grant`* — i.e., the grant map, not just the currently-registered `signers` entry, is the thing that gates new stacking commitments for that manager: [5](#0-4) 

### Finding

This is the exact shape of the reported bug class: an old authorization ("session") that the operator believed was superseded by rotating to a new key remains live and independently checkable, because rotation performs an *additive* `map-set`/`map-insert` on the new key rather than an invalidation of the old one. Anyone still holding the private key that corresponds to a previously-rotated-out `signer-key` can produce a fresh, valid `secp256k1` signature and continue to satisfy `verify-signer-key-grant`/`grant-signer-key` checks for that `signer-manager`, even though the pool/manager has already "changed its key" and believes the old key is no longer trusted. This can be leveraged to authorize new stacking commitments (`register-self`, new-stake entry points) under the old, supposedly-retired key — an unsigned-by-the-current-authority stacking action, matching the rules' High-impact category ("signing weight or reward slots exceeding locked value, an unsigned stacking action").

### Caveat

I could not fully trace, within the available tool calls, the exact downstream code path of every "new-stake entry point" that calls `verify-signer-key-grant` in `pox-5.clar` to confirm there is no additional cross-check against the *currently active* `signers[signer-manager]` key (which would neutralize the stale-grant risk). The finding rests on: (1) the explicit test-code documentation that rotation does not revoke the prior grant, and (2) the design comment stating new-stake entry points check the grant map rather than a "current key only" invariant. A full confirmation would require reading the complete `stack-stx`/`register-signer`/`delegate-stack-stx` bodies in `pox-5.clar` to verify whether they also compare against the live `signers` map entry — this was not completed due to iteration limits.

### Title
Stale signer-key grants remain valid after key rotation in pox-5.clar, allowing a retired signer key to keep authorizing stacking actions - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`grant-signer-key` creates a permanent `signer-key-grants` entry that is only removed by an explicit `revoke-signer-grant` call. Key rotation (`register-self`) does not perform this revocation — it only overwrites the `signers` map with the new key, per `RotateSignerKey.ts`. The old grant remains independently valid.

### Finding Description
`verify-signer-key-grant`, used by "every new-stake entry point" per the contract's own design comment, checks the `signer-key-grants` map keyed by `{signer-key, signer-manager}`, not the currently active `signers[signer-manager]` entry. Because rotation is additive rather than revocation, the old `(old-key, signer-manager)` pair remains a valid grant indefinitely.

### Impact Explanation
Whoever retains the private key material for a `signer-key` that the operator believes has been retired via rotation can continue signing/authorizing new stacking commitments for that `signer-manager`, bypassing the intended effect of rotation. This is functionally equivalent to the CVE's stale-session reuse after password change, mapped onto a signing-authority equality: the stacking action was never authorized by the current/authoritative key, yet the contract accepts it.

### Likelihood Explanation
Requires the attacker to have obtained the old signer-key's private key (the same threat model that would prompt rotation in the first place, e.g., key leakage), then produce a fresh valid signature — this is plausible in the scenario key rotation was designed to defend against.

### Recommendation
`register-self`/key-rotation should call `revoke-signer-grant` on the previous `(old-key, signer-manager)` pair as part of the rotation transaction, or `verify-signer-key-grant` should additionally check that the presented `signer-key` matches the currently registered `signers[signer-manager]` key.

### Proof of Concept
1. Signer-manager `P` calls `grant-signer-key` with key `K1`, then `register-self`, establishing `signers[P] = K1` and `signer-key-grants[{K1,P}] = true`.
2. `K1` is leaked/compromised; `P` rotates by calling `register-self` again with new key `K2` (per `RotateSignerKey.ts`), setting `signers[P] = K2` and `signer-key-grants[{K2,P}] = true` — but `signer-key-grants[{K1,P}]` is untouched and still `true`.
3. Attacker, holding `K1`'s private key, signs a message for a new-stake entry point tied to `signer-manager P` and submits it; `verify-signer-key-grant` finds the still-live `{K1,P}` grant and accepts it, even though `P` has moved on to `K2`.
