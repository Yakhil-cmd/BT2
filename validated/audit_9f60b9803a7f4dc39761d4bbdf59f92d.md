### Title
Unsanitized peer-controlled contract `title`/`text` displayed to user before signing induces fraudulent Prosaic/Arbiter contract acceptance - (File: prosaic_contract.js / arbiter_contract.js / wallet.js)

### Summary
Both the prosaic contract and arbiter contract flows accept `title` and `text` fields from a remote, untrusted peer device and persist/relay them to the user with no content validation (no length limit, no character filtering, no markdown/control-character stripping). These fields are exactly the "message the user reads before deciding to accept a legally/financially binding action" analog of the reported `renderSignTransaction`/`renderSignAllTransactions` bug: the party requesting the user's signature (a less-trusted counterparty) fully controls the content that the user relies on to decide whether to sign.

### Finding Description
In `wallet.js`, the `prosaic_contract_offer` handler only checks that `title`/`text` are truthy: [1](#0-0) 
No sanitization, length limit, or character-class restriction is applied to `body.title`/`body.text` before they are stored via `prosaic_contract.store(body)` and surfaced to the wallet UI for the user's accept/decline decision.

Similarly, `arbiter_contract.js`'s `createAndSend`/`store` functions persist attacker/peer-supplied `title`, `text`, `my_contact_info`, `peer_contact_info` fields without any sanitization: [2](#0-1) [3](#0-2) 

These text fields are the sole basis on which the user approves creation of a shared (co-signed escrow) address and subsequent transfer of funds into it — analogous to the `simulationResult`/`message` fields in the external report that a dapp fully controls and which the user relies upon to decide whether to sign. Just as the Snap UI `text()` component can render Markdown or inject control characters to make the displayed content misleading, if the ocore-based wallet UI renders `contract.title`/`contract.text` as rich/markdown text (a common practice for chat-like contract text in Obyte wallets), a peer can inject formatting/control characters (e.g. right-to-left override characters, newlines that visually truncate or move critical clauses off-screen, or markdown link/image syntax) to disguise the true terms of the contract (amount, payer/payee roles, obligations) while still passing the SHA-256 `getHash()` check that only binds `title+text+creation_date` together — it does not validate the semantic safety of the content itself: [4](#0-3) 

The `handleReceivedSigningUnit` functions in both `prosaic_contract.js` and `arbiter_contract.js` only verify that the `contract_text_hash` matches the previously agreed contract hash — they never re-validate that the underlying text is safe/unambiguous for display: [5](#0-4) [6](#0-5) 

### Impact Explanation
If a malicious counterparty crafts a `title`/`text` payload containing control characters or markdown constructs that visually misrepresent contract terms (payer/payee direction, amount, conditions, arbiter identity), the victim can be induced to accept a contract and cosign a shared address / sign a unit that transfers funds under materially different terms than what they believed they approved. Because acceptance directly triggers `composer.composeAuthorsAndMciForAddresses` and later on-chain fund movement into/out of the shared escrow address, this can result in concrete unauthorized spending of the victim's funds — matching the report's core concern that the user "might decide whether to sign or reject the transaction based on... potentially false information."

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to be an actual pairing/chat counterparty (not an arbitrary p2p network attacker), which is within the reachable attack surface described (an untrusted contract counterparty/AA-trigger-like party sending an application message the victim relies on for a signing decision). No special privileges beyond normal wallet pairing are needed, and the vulnerable code paths (`prosaic_contract_offer`, `arbiter_contract_offer`) are exposed to any paired device.

### Recommendation
- Enforce strict validation on `title`/`text`/`my_contact_info`/`peer_contact_info`: max length, printable-character allowlist, and explicit rejection of control characters (e.g. `\u0000`-`\u001F` except `\n`, bidi override characters, zero-width characters).
- Do not let wallet UIs render these fields as Markdown/HTML; render as plain, pre-formatted text.
- Consider a canonicalization/normalization step (e.g. NFKC normalization plus control-char stripping) applied uniformly before hashing and before display, so `getHash()` binds to the same sanitized content the user actually sees.
- Show contract-critical structured fields (amount, asset, payer address, arbiter address) as separately rendered, trusted, non-freeform elements rather than embedding them only inside freeform `text`.

### Proof of Concept
1. Attacker pairs with victim's wallet and sends an `arbiter_contract_offer` (or `prosaic_contract_offer`) message with:
   - `title`: "Sale Agreement"
   - `text`: a string containing a Unicode right-to-left-override character sequence or interleaved newlines designed to make the displayed amount/payer role appear reversed from the actual structured `amount`/`me_is_payer` field, or containing markdown link syntax that a rendering wallet UI would auto-linkify to a phishing URL.
2. `wallet.js`'s handler only checks `!body.title || !body.text || !body.creation_date` truthiness and validates the hash binds `title+text+creation_date`, and `arbiter_contract.js`/`prosaic_contract.js` store the raw payload: [7](#0-6) 
3. The victim's wallet UI displays the crafted `text` and the victim accepts, triggering shared-address derivation and eventual signing of a funding/settlement unit reflecting terms the victim did not actually agree to.

*Note: the actual UI rendering layer (where markdown/control-char interpretation would occur) lives in the downstream wallet application, not in this `ocore` repository; this repo is the root cause enabler in that it performs no input sanitization on these user-facing, peer-controlled fields before persisting/relaying them for a signing decision.*

function handleReceivedSigningUnit(contract, unit, from_cosigner, retry_count = 0) {
	db.query("SELECT 1 FROM unit_authors WHERE unit=? AND address=?", [unit, contract.shared_address], async function (rows) {
		if (rows.length === 0) {
			if (retry_count >= 10)
				return console.log(`signing tx ${unit} not found in db after 10 retries, giving up`);
			console.log(`signing tx ${unit} not yet in db, waiting for 30 seconds and trying again`);
			return setTimeout(handleReceivedSigningUnit, 30000, contract, unit, from_cosigner, retry_count + 1);
		}
		console.log(`signing tx ${unit} found in db, setting contract's unit and status to signed`);
		const objUnit = await storage.readUnit(unit);
		const dataMessage = objUnit.messages.find(message => message.app === "data");
		if (!dataMessage)
			return console.log(`data message not found in purported signing unit ${unit}`);
		const { payload } = dataMessage;
		const contacts_hash = getContactsHash(contract);
		if (payload.arbiter !== contract.arbiter_address || payload.contract_text_hash !== contract.hash || payload.contacts_hash !== contacts_hash)
			return console.log(`data message payload does not match contract ${contract.hash} in purported signing unit ${unit}`);
		const author = objUnit.authors.find(author => author.address === contract.shared_address);
		const signing_paths = Object.keys(author.authentifiers);
		const isMutuallySigned = signing_paths.find(p => p.startsWith('r.0.0')) && signing_paths.find(p => p.startsWith('r.0.1'));
		if (!isMutuallySigned)
			return console.log(`signing unit ${unit} is not mutually signed, authentifiers: ${JSON.stringify(author.authentifiers)}`);
		const err = await fillArbstoreAddresses(contract);
		if (err)
			console.log(`failed to fill arbstore addresses for contract ${contract.hash} while handling received signing unit ${unit}`, err);
		setField(contract.hash, "status", "signed", null, true);
		setField(contract.hash, "unit", unit, function(contract) {
			eventBus.emit("arbiter_contract_update", contract, "unit", unit);
		}, from_cosigner);
	});
}
