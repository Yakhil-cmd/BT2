### Title
Cross-organization `Team.find_or_create_by!(github_id:)` in `MembershipHandler#find_or_create_team!` allows escalation into `Shipit.github_teams` authorization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team` rows solely by `github_id`, a column that carries no per-organization uniqueness constraint and no cross-check against the organization whose `webhook_secret` verified the request. Since `WebhooksController#verify_signature` only authenticates that the payload came from *some* configured organization (`repository_owner`, taken from the same attacker-controlled JSON body), an attacker who administers their own configured Shipit organization/GitHub App can forge a `membership` webhook whose `team.id` collides with an existing victim `Team`'s `github_id`, causing `team.add_member(member)` to attach the attacker's `User` to that pre-existing (victim) `Team` row.

### Finding Description
The broken binding: `(organization whose webhook_secret verified this payload)` should equal `(organization that owns the Team row being mutated)`, but the code enforces only `Team.github_id == params.team.id` [1](#0-0) , with no scoping by `params.organization.login`.

- `WebhooksController#verify_signature` resolves the signing app via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read directly from the attacker-controlled payload (`organization.login` fallback), and only proves the payload was signed by *that* organization's own `webhook_secret` [2](#0-1) . It says nothing about which `Team.github_id` is legitimate for that org.
- `MembershipHandler#process` calls `find_or_create_team!` then `team.add_member(member)` for `action == 'added'` [3](#0-2) .
- `find_or_create_team!` performs `Team.find_or_create_by!(github_id: params.team.id)` [1](#0-0) . If a `Team` row already exists with that `github_id` (created for a different organization, e.g. via `Shipit.github_teams` at boot through `Team.find_or_create_by_handle`), `find_or_create_by!` returns the existing record and does **not** run the creation block, so the attacker's `organization.login`/slug/name are silently ignored — the found record is the pre-existing victim `Team`.
- The `teams` table schema only enforces uniqueness on `["organization", "slug"]`; `github_id` has no unique or organization-scoped index [4](#0-3) .
- `Team#add_member` then inserts a `Membership` linking the attacker's `User` to that Team's database `id` [5](#0-4) .
- `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) . `Shipit.github_teams` resolves configured team handles (`org/slug`) to `Team` rows via `Team.find_or_create_by_handle` [7](#0-6) ; if the victim `Team` (whose `id` was reused) is one of those configured teams, the attacker's membership in that row's `id` makes `authorized?` return true for the attacker's `User`.

Attacker's request: a raw HTTP POST to `/webhooks` with `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with the attacker's own organization's `webhook_secret` (which the attacker, as the administrator/owner of that org's GitHub App, knows/controls), and body:
```json
{
  "action": "added",
  "team": { "id": <victim_team_github_id>, "name": "attacker-team", "slug": "attacker-team", "url": "https://api.github.com/teams/..." },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-login" }
}
```
`drop_unhandled_event` and `check_if_ping` don't block `membership`; `verify_signature` passes because it only checks the attacker's own org's secret against `repository_owner` derived from `organization.login = "attacker-org"`, which is exactly the org the attacker controls. `ExplicitParameters` only validates types/presence, not cross-organization consistency of `team.id`.

### Impact Explanation
The attacker's own `Shipit::User` gains membership in an arbitrary pre-existing `Team` row identified only by guessing/observing its `github_id`, and if that `Team` is part of `Shipit.github_teams` (the configured allow-list gating API client creation, OAuth login access, etc.), the attacker's account becomes `authorized?` for the entire Shipit instance despite never being part of the victim organization or its real GitHub team. This is a cross-tenant authorization escalation (matches "escalation into `Shipit.github_teams` authorization" — High severity) and is repeatable for any Team the attacker can enumerate/guess by `github_id`.

### Likelihood Explanation
Preconditions: Shipit must be configured in the multi-organization mode (`github:` keyed by organization) with the attacker's own organization as one of the configured tenants, giving the attacker a legitimately verifiable `webhook_secret` for their own org; the attacker must know or guess a victim `Team`'s numeric `github_id` (these are sequential/enumerable GitHub team IDs, and often knowable if the victim team is public or previously interacted with the instance). Given those, the attack is a single crafted HTTP POST with a correctly computed HMAC — no GitHub-side action or privileged token is needed. This is feasible and cheaply repeatable, but does depend on the multi-org, multi-tenant deployment shape and knowledge of a colliding `github_id`.

### Recommendation
Scope the `Team` lookup by both `github_id` and the verified organization (`params.organization.login`, cross-checked against the org that signed the webhook), and add a unique/composite index or explicit guard preventing a `github_id` collision across different `organization` values from being treated as the same row (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)` and reject/raise if an existing row for that `github_id` belongs to a different organization).

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":membership cannot hijack a Team belonging to another organization" do
  victim_team = shipit_teams(:shopify_developers) # existing Team, github_id: X, organization: 'shopify'
  Shipit.stubs(:github_teams).returns([victim_team])

  @request.headers['X-Github-Event'] = 'membership'
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  post :create, as: :json, body: {
    action: 'added',
    team: { id: victim_team.github_id, name: 'attacker-team', slug: 'attacker-team', url: 'https://example.com' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-login' }
  }.to_json
  assert_response :ok

  attacker = Shipit::User.find_by!(login: 'attacker-login')
  # BEFORE fix: this is true (bug) -- attacker escalated via a Team they don't belong to.
  # AFTER fix: this must be false, and no Membership row should link attacker to victim_team.id.
  assert_equal false, attacker.authorized?
  assert_not Shipit::Membership.exists?(user_id: attacker.id, team_id: victim_team.id)
end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner

      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
