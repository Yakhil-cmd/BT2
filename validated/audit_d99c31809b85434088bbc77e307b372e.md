### Title
Stale delegate authorization reactivates after position NFT returns to prior owner - (File: contracts/controller/src/storage/account.rs)

### Summary
Controller account delegates are bound only to `account_id` and the address that granted them. Transferring the position NFT temporarily disables the old owner's grants, but the grant is not deleted or stamped with an ownership epoch. If the same NFT later returns to the granting address, the old delegate becomes authorized again without a fresh owner signature. An active manager with a stale grant can then borrow or withdraw the returned account's collateral to an address it chooses.

### Finding Description
`ControllerKey::Delegates(account_id)` stores a `DelegateGrant` containing `granted_by` and a delegate list. `get_delegates` returns that list whenever `granted_by` equals the account's current NFT owner; it does not distinguish a new ownership period from the original one. [1](#0-0) 

When an NFT is transferred to another owner, that stored grant remains in persistent storage. Once ownership returns to `granted_by`, the equality check succeeds again and the stale delegate list is live. [2](#0-1) 

The authorization path then accepts any listed delegate that is also a globally active position manager. [3](#0-2) 

Both `borrow` and `withdraw` expose an optional output recipient and require only owner-or-delegate authorization. [4](#0-3) 

### Impact Explanation
The stale delegate can take the returned account's collateral or create debt against it and direct proceeds to an address the current owner did not authorize for this ownership period. This can steal user collateral or leave the account with unsustainable debt.

The issue is especially dangerous in transfers or marketplace purchases: the prior owner may believe ownership transfer reset delegate permissions, while a dormant manager authorization silently becomes valid when the token is transferred back.

### Likelihood Explanation
The vulnerability requires a prior owner to have granted an active manager, then lose and later regain the same account NFT without the grant being overwritten or deleted. The grant must also still correspond to an active position manager. Those conditions are plausible for managed positions, position sales, portfolio transfers, and account recovery flows.

No privileged action, oracle manipulation, or code upgrade is required once the grant exists. The NFT transfer back can be performed by the interim holder or an approved operator, and the stale delegate can immediately call `borrow` or `withdraw` with its own signature.

### Recommendation
Bind delegate grants to an ownership epoch rather than only to the granting address. For example:

- Maintain a per-account ownership nonce that increments on every NFT mint or ownership transition observed by the controller.
- Store that epoch in `DelegateGrant`.
- Return delegates only when both `granted_by == current_owner` and `grant.epoch == current_epoch`.
- Alternatively, delete `Delegates(account_id)` whenever the NFT owner changes, although the controller would need a reliable transfer hook or permissioned transfer wrapper to observe that event.

The grant should not be able to regain authority merely because the same address becomes owner again.

### Proof of Concept
1. Alice owns account NFT `account_id = 7` and grants the active position manager Mallory through `add_delegate(alice, 7, mallory)`.
2. Alice transfers token `7` to Bob through `transfer(alice, bob, 7)`. The controller now resolves Bob as owner and `granted_by == alice` no longer matches, but the grant remains stored.
3. Bob later transfers token `7` back to Alice through `transfer(bob, alice, 7)`.
4. `account_owner(7)` again returns Alice, so `get_delegates(7, alice)` returns the old list containing Mallory.
5. Mallory calls `borrow(mallory, 7, borrows, Some(mallory))` or `withdraw(mallory, 7, withdrawals, Some(mallory))`.
6. `require_owner_or_delegate` accepts Mallory because the revived grant lists it and Mallory remains an active position manager; the call succeeds without any authorization from Alice during this new ownership period.

/// Returns grants stamped by `owner`, or an empty list. Ownership changes
/// invalidate a previous owner's grants without deleting them.
pub(crate) fn get_delegates(env: &Env, account_id: u64, owner: &Address) -> Vec<Address> {
    get_user::<DelegateGrant>(env, &ControllerKey::Delegates(account_id))
        .filter(|grant| grant.granted_by == *owner)
        .map(|grant| grant.delegates)
        .unwrap_or_else(|| Vec::new(env))
}
```

/// Accepts the owner or a registered, active manager delegated by that owner.
pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}

/// Requires the owner or a registered, active manager delegated by that owner.
pub(crate) fn require_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) {
    if is_owner_or_delegate(env, account_id, caller, owner) {
        return;
    }
    panic_with_error!(env, GenericError::NotAuthorized);
```
