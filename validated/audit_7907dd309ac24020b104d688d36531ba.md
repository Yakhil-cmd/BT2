### Title
`StatusHandler#process` writes GitHub commit-statuses by bare SHA with no repository scoping, letting one repository's status webhook flip `blocked?`/`deployable?` for a commit belonging to a different repository's stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and writes a status to every matching row, regardless of which repository the webhook payload's `repository.full_name` refers to [1](#0-0) . This is inconsistent with the base `Handler` class, which exposes a `stacks` helper that correctly scopes lookups through `Repository.from_github_repo_name(repository_name)` [2](#0-1) , but `StatusHandler` never uses it. Because `Status#blocking?`/`Commit#blocked?`/`Commit#deployable?` derive directly from whatever status rows exist for a commit, a status written via a cross-repository SHA collision can flip a victim stack's block/ship state.

### Finding Description
The broken binding is: **status.stack_id (and thus the affected stack) must equal the stack of the repository that authenticated the webhook** (`payload.dig('repository','full_name') == stack.repository.full_name`). In `StatusHandler`, this equality is never checked.

Path:
1. `WebhooksController#create` parses the raw JSON body and dispatches to handlers for the `status` event after `verify_signature` [3](#0-2) .
2. `verify_signature` validates the HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the attacker-supplied payload (`params.dig('repository','owner','login')`) [4](#0-3) . The signing key is scoped to the **organization**, not to an individual repository, so any repository/webhook belonging to that org can produce a validly-signed payload.
3. `StatusHandler#process` then runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped lookup across the entire `commits` table (all stacks, all repositories) [1](#0-0) .
4. `create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, which writes the status against the **matched commit's own `stack_id`** [5](#0-4) [6](#0-5) .
5. `Status::Common#blocking?` is `!success? && commit.blocking_statuses.include?(context)` [7](#0-6) , and `Commit#blocked?`/`#deployable?` aggregate this over the undeployed commit range of the stack [8](#0-7) .

Exploit flow: since Git commit SHAs are content-addressed, an attacker who owns or controls a repository within the same GitHub organization (or who can reproduce a commit with an identical tree/author/committer/timestamp/message to one already present in a victim stack) can push that commit to their own repository and set a GitHub commit status (`context: codecov/project`, `state: failure`) via the GitHub API on their own repo. GitHub delivers a webhook for the attacker's own repository, signed with the organization-level secret, which `verify_signature` accepts. `StatusHandler` then matches the SHA against every `Commit` row sharing that SHA — including the victim's commit in a different stack — and writes the failure status onto the victim's commit's own `stack_id`. If the victim stack has `codecov/project` configured under `blocking_statuses`, this write flips `blocking?` for that commit, which can set or clear `blocked?`/`deployable?` for later commits in the victim stack, forcing a block (or, using `state: success` to override an existing failing context via the "most recent status per context" resolution) forcing a ship.

Existing guards do not prevent this: `verify_signature` authenticates only the organization, not the specific repository named in the payload; there is no `ExplicitParameters` field or model validation binding `params.dig('repository','full_name')` to the resolved `Commit#stack`; and `StatusHandler` bypasses the `stacks`/`repository_name` scoping helper entirely.

### Impact Explanation
A commit-status webhook that is only legitimately authenticated for repository/organization A is applied to a commit record belonging to stack/repository B, mutating B's status/blocking state and therefore B's `deployable?`/`blocked?` computation — a payload for one repository mutating another repository's stack/commit records. This matches the "Critical" category: a payload for one repository mutating another's stack, commit, task, or team, potentially causing an unauthorized deploy or block. The blast radius is bounded by SHA collisions occurring, but is repeatable against any stack whose repository shares the target organization's webhook signing key or whose commit content the attacker can reproduce.

### Likelihood Explanation
Preconditions: (a) attacker needs a repository (owned by them or one they can push to) whose webhook deliveries are signed with a key Shipit accepts for some organization — per `verify_signature`, this key is per-organization, so this is realistic in any multi-repo/multi-team GitHub organization using a single Shipit deployment; (b) attacker needs to produce a commit SHA identical to one that exists (or will exist) in the victim stack's commit history — feasible by forking/mirroring the victim's public repository and pushing the identical commit object to their own repository, since Git SHAs are deterministic hashes of content, not repo-specific; (c) the victim stack must have `blocking_statuses` (or a required/soft-failing context) configured to make the flip observable/impactful. Given these, the attack is cheap (a single GitHub API call to set a status) and repeatable at will.

### Recommendation
Scope `StatusHandler#process` (and any commit lookups keyed by bare SHA) to the stacks belonging to the repository named in `payload.dig('repository','full_name')`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent use of the existing `stacks`/`repository_name` helper from `Handler`, so a status can only be written onto commits within stacks whose repository matches the authenticated webhook's repository.

### Proof of Concept
Minitest plan (no live GitHub):
```ruby
test "StatusHandler does not write cross-repository statuses by bare SHA" do
  victim_stack = shipit_stacks(:cyclimse)   # some fixture stack with blocking_statuses configured, e.g. requiring 'codecov/project'
  other_stack  = shipit_stacks(:shipit)     # different repository/org
  shared_sha   = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim", authored_at: Time.now, committed_at: Time.now)
  # simulate identical-SHA commit existing under a different repository's stack
  attacker_commit = other_stack.commits.create!(sha: shared_sha, message: "attacker", authored_at: Time.now, committed_at: Time.now)

  before_blocked = victim_commit.blocked?

  payload = {
    'repository' => { 'full_name' => other_stack.repository.full_name, 'owner' => { 'login' => other_stack.repository.owner } },
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'codecov/project'
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  after_blocked = victim_commit.blocked?

  # Binding under test: a status delivered for other_stack's repository must not affect victim_stack's commit.
  assert_equal before_blocked, after_blocked,
    "status webhook authenticated for repository #{other_stack.repository.full_name} altered blocked? state of a commit in #{victim_stack.repository.full_name}"
  assert_empty victim_commit.statuses.where(context: 'codecov/project'),
    "cross-repository status was written onto victim commit's stack_id"
end
```
This test demonstrates that `StatusHandler.call` (equivalent to what `WebhooksController#create` invokes after signature verification) writes a `Status` row against `victim_commit` even though the payload's `repository.full_name` names `other_stack`'s repository, violating the invariant that a status affects only the repository that authenticated it.
