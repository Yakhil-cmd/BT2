Rationale: The reported Linea bug is a classic Go data race — a shared, lazily-mutated cache object (`ExpressionBoard`/`PlonkInWizard`) accessed concurrently by multiple segment-prover goroutines without synchronization, corrupting proof computation. I searched polkadot-sdk for structurally analogous "lazy-mutate-shared-cache-without-lock, reachable from an untrusted user-triggered concurrent path" patterns and found none that hold up:

- The Substrate Wasm `RuntimeCache::with_instance` performs its cache check-then-insert entirely under a single `Mutex` guard before dropping the lock, so there is no race window comparable to `ExpressionBoard.Compile`'s in-place mutation on first `Evaluate`. [1](#0-0) 
- The trie `SharedNodeCache`/`SharedValueCache` and `SharedVoterSetState` (GRANDPA) are `Arc<RwLock<...>>`/`Arc<Mutex<...>>` protected throughout, and known concurrency issues in this class of structure (e.g., GRANDPA's `finalize_block` race) were already identified and fixed with explicit lock ordering, not left unguarded. [2](#0-1) [3](#0-2) 
- PVF candidate validation — the actual "prover"-equivalent, untrusted-input-driven compute path reachable from parachain block authoring/backing — does not share a mutable compiled-artifact object across concurrent validations at all: each execute-worker process reads the artifact bytes from disk and calls `create_runtime_from_artifact_bytes`/`execute_artifact` independently per job, and preparation/execution concurrency is coordinated through message-passing queues (`host.rs`, `execute/queue.rs`) rather than a shared object mutated in place. [4](#0-3) [5](#0-4) 
- The one truly process-global lazily-initialized shared object I found, the PolkaVM `ENGINE: LazyLock<Engine>`, is initialized once via `LazyLock` (thread-safe by construction) and not mutated afterward per-call, unlike the Go `Compile`-on-first-`Evaluate` pattern. [6](#0-5) 

None of these represent an unsynchronized lazy-mutation-of-shared-state pattern reachable via a permitted, unprivileged user entry point (signed extrinsic, contract call, or XCM message) as required by the scan's methodology; the polkadot-sdk analogs are either already lock-protected end-to-end or architected without cross-job shared mutable state in the first place.

			.call("validate_block", params)
	}) {
