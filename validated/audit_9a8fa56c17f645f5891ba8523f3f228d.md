### Title
Predictable AA "randomness" via `number_from_seed`/`mc_unit`/`response_unit` lets a trigger sender always win gambling AAs - ([File: formula/evaluation.js])

### Summary
The OnePlay incident exploited a smart-contract "random number" that was actually derived from data the attacker could observe or predict before betting, letting them only submit winning bets. `ocore`'s oscript layer provides a similarly deterministic pseudo-random primitive, `number_from_seed`, whose output is fully determined by the seed value passed to it [1](#0-0) . Any AA author who seeds it (directly or indirectly) with values that are knowable to the trigger sender before the trigger unit is broadcast — such as `mc_unit`, `trigger.unit`, `trigger.data`, `timestamp`, or state variables readable from chain state — creates a gambling/lottery AA whose outcome can be computed off-chain by an unprivileged trigger sender ahead of time.

### Finding Description
`number_from_seed` hashes the evaluated seed with SHA-256 and maps the digest deterministically to a number/int range [2](#0-1) . This is a pure, stateless, deterministic function — it never draws on hidden/unpredictable entropy internal to the node. The formula language exposes many candidate "seed" ingredients that an attacker fully controls or can read before submission:
- `trigger.unit`, `trigger.data`, `trigger.address` — literally authored by the attacker [3](#0-2) .
- `mc_unit` — the last stable MC unit hash, which is public chain state known before composing/broadcasting the trigger [4](#0-3) , and is passed into AA execution from `objMcUnit.unit` at trigger-handling time [5](#0-4) .
- `response_unit` — deterministically computed from the response content, and exposed inside the same AA execution that also computes the "random" number, so an author who naively bases randomness only on values fixed prior to placing the bet gives the sender full foreknowledge.
- State variables — public and queryable before sending a trigger.

Because AA execution is fully deterministic (same trigger + same state + same mci → same result), and light/full nodes let anyone read current AA state, mci and the last stable MC unit before composing a unit, an attacker can locally evaluate the exact same oscript formula the AA will run (the same interpreter code lives in `formula/evaluation.js`) and learn the "random" outcome before ever broadcasting the wager. If it's a loss, they simply do not send that trigger; if it's a win, they send it. Repeating this lets them drain the AA's balance with (near) 100% win rate, exactly mirroring the reported OnePlay/EOS "random number attack" pattern (attacker precomputes/controls the "random" seed, e.g., block/tx info, to guarantee wins).

There is a purpose-built, correct alternative — `vrf_verify`, which validates an externally supplied, unpredictable RSA-signed randomness proof [6](#0-5)  — but `number_from_seed` itself has no built-in protection or warning-enforced constraint preventing authors from feeding it attacker-known values, and the interpreter does not restrict which fields may be used as its seed.

### Impact Explanation
An AA offering a bet/lottery seeded from predictable/self-controlled inputs allows an unprivileged trigger sender to guarantee wins, resulting in concrete AA fund loss — direct analog of the "unauthorized spending"/"AA fund loss" impact class in scope. This mirrors the real-world OnePlay loss (449 EOS drained, then repeated for token ONE) achieved purely through predictable on-chain randomness with no privileged access needed.

### Likelihood Explanation
Likelihood is high for any AA gambling/lottery contract built on `number_from_seed` with a naive seed choice (a very natural, common design mistake, as evidenced by the equally deterministic `EOS` blockhash-based games in the wild). The attack requires only: (1) reading public AA/chain state, (2) locally running the published, deterministic oscript formula, (3) selectively broadcasting winning triggers — all reachable by any wallet/trigger sender with no special privileges.

### Recommendation
- Document and strongly discourage seeding `number_from_seed` with any value known to the trigger sender ahead of submission (`trigger.*`, `mc_unit`, `timestamp`, state vars readable pre-trigger).
- Where true unpredictability is required, mandate/point AA templates toward `vrf_verify` (external verifiable randomness from a committed oracle) instead of `number_from_seed`, or a commit-reveal scheme spanning two rounds so the seed is fixed only after the bet is irrevocably placed.
- Consider adding formula-validation-time linting/warnings when `number_from_seed`'s seed expression references only pre-trigger-known values, to reduce the chance that new AAs replicate this class of bug.

### Proof of Concept
1. Author (or attacker) deploys an AA lottery: `if (number_from_seed(mc_unit || trigger.unit) > 0.5) { pay 2x } else { keep bet }`.
2. Before broadcasting a trigger, the attacker reads the current stable `mc_unit` (public) and constructs a candidate trigger unit content, computing its would-be `trigger.unit` hash locally (units are content-addressed, so the hash is computable before broadcast in the same way `objectHash.getUnitHash` computes it deterministically [7](#0-6) ).
3. The attacker runs the exact same `number_from_seed` formula locally (same algorithm as `formula/evaluation.js`) offline to predict the outcome for that specific `mc_unit`/`trigger.unit` pair.
4. If the local computation predicts a loss, the attacker perturbs the trigger content (e.g., changes `trigger.data`, unused message ordering, or timing to shift to the next `mc_unit`) and recomputes until a winning combination is found, then broadcasts only that unit.
5. Repeating step 2–4 for every wager drains the AA's balance analogous to the OnePlay EOS incident.
