### Title
Cross-organization `Team`/`Membership` escalation via mismatched `repository_owner` used for webhook signature verification vs. `organization.login` used to write membership - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GithubApp`/`webhook_secret` used to authenticate a request based on `repository_owner`, which is computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) [2](#0-1) . `MembershipHandler#find_or_create_team!` however trusts `params.organization.login` unconditionally as the org that owns the `Team` being written, and `process` adds the attacker-chosen `member.login` to it [3](#0-2) . In a multi-org `secrets.yml` setup, an attacker who legitimately controls their own org's GitHub App entry can sign a payload with their own known `webhook_secret` while the payload's `organization.login`/`team.id` name a different org's real, already-authorized team.

### Finding Description
The broken binding: the code implicitly assumes `repository_owner` (used to pick the verifying secret) `== params.organization.login` (used to write `Team.organization`/`Membership`). These are two independently attacker-controlled JSON fields with no cross-check.

- `WebhooksController#repository_owner` prefers `repository.owner.login` over `organization.login` [2](#0-1) .
- `verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies the raw body against that org's `webhook_secret` via `GitHubApp#verify_webhook_signature` [1](#0-0) [4](#0-3) .
- `MembershipHandler`'s `ExplicitParameters` schema only requires `action`, `team`, `organization`, `member` — it never requires or validates `repository`, so an attacker can freely add an unrelated `repository.owner.login` block to steer signature verification while leaving `organization.login` pointed at the victim org [5](#0-4) .
- `find_or_create_team!` uses `Team.find_or_create_by!(github_id: params.team.id)`, and if a `Team` with that `github_id` already exists (e.g., it was created earlier from a legitimate `membership` event, or bootstrapped via `Team.find_or_create_by_handle`/`teams.rake`), the existing row (organization = victim org) is returned unchanged; `team.add_member(member)` then attaches the attacker's `User` (looked up by attacker-supplied `member.login`) to that pre-existing team [6](#0-5) [7](#0-6) .
- Membership in that `Team` is exactly what `User#authorized?` checks against `Shipit.github_teams` [8](#0-7) .

Exploit flow: operator has configured multiple GitHub Apps in `secrets.yml` (one per org, as documented under "Using Multiple Github Applications"), and the attacker controls one such org (`attacker-org`), knowing its `webhook_secret` legitimately. The attacker crafts:
```json
{
  "action": "added",
  "team": {"id": <victim's real, already-authorized team github_id>, "name": "x", "slug": "x", "url": "x"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker-login"},
  "repository": {"owner": {"login": "attacker-org"}}
}
```
signs it with `attacker-org`'s webhook secret, and POSTs to `/webhooks` with `X-Github-Event: membership`. `repository_owner` resolves to `attacker-org`, signature verification passes using the attacker's own legitimately-known secret, and the handler then mutates `victim-org`'s `Team`/`Membership` state.

No existing guard prevents this: `verify_signature` only checks the HMAC against whichever org it derives from the body, never that this org matches the org referenced by the payload contents consumed by the handler; `drop_unhandled_event` and the `ExplicitParameters` schema only check presence/type of required fields, not cross-field consistency; there is no re-fetch of team membership from GitHub (unlike `Team#refresh_members!`) to confirm the event is genuine.

### Impact Explanation
The attacker can add themselves (or any GitHub login they choose) as a member of a `Team` belonging to a different organization than the one whose secret was used to authenticate the request, provided that `Team`'s `github_id` already exists in Shipit's database. If that `Team` is one of the entries in `Shipit.github_teams`, `User#authorized?` returns true for the attacker [8](#0-7) , granting them authenticated/authorized status across the whole multi-tenant Shipit instance — escalation into `Shipit.github_teams` authorization, matching the High severity category. This is repeatable against any team whose numeric `github_id` the attacker can learn (team IDs are often discoverable via the GitHub API for public org teams, or leaked in prior webhook deliveries), and against arbitrary victim orgs sharing the Shipit instance, as long as the attacker independently controls one configured org's GitHub App.

### Likelihood Explanation
This requires a specific, non-default configuration: a multi-org `secrets.yml` where multiple independent GitHub orgs each have their own `GithubApp`/`webhook_secret`, and the attacker legitimately administers one of those orgs (so they know its `webhook_secret`) while targeting a different org on the same Shipit instance. This is a real supported deployment mode per `docs/setup.md`'s "Using Multiple Github Applications" section, but it is not the typical single-org Shipit deployment. The attacker additionally needs the victim's target team's real GitHub numeric `team.id` (public/discoverable for public org teams via the GitHub API). Given these preconditions, the attack is cheap (a single crafted HTTP POST, no live GitHub interaction needed) and fully repeatable.

### Recommendation
In `WebhooksController#verify_signature`, do not let an attacker-supplied `repository.owner.login` silently override the org context; more importantly, `MembershipHandler` (and any other org-scoped handler) should validate that `params.organization.login` equals the `repository_owner`/org that was used to select the verifying `webhook_secret`, rejecting the event otherwise. Alternatively, always derive the verifying org strictly from `organization.login` for org-scoped events (`membership`) rather than falling back based on payload shape, and reject events where `repository.owner.login` and `organization.login` disagree.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative)
test "membership event signed by org A cannot write org B's team membership" do
  # Org A: attacker-controlled, secret known to attacker
  Shipit.stubs(:secrets).returns(
    'github_apps' => {
      'attacker-org' => { 'webhook_secret' => 'attacker-secret' },
      'victim-org' => { 'webhook_secret' => 'victim-secret' }
    }
  )
  victim_team = shipit_teams(:victim_org_authorized_team) # pre-existing Team, organization: 'victim-org', github_id: 999
  Shipit.stubs(:github_teams).returns([victim_team])

  body = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'victim-org' },
    member: { login: 'attacker-login' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', body)

  request.headers['X-Github-Event'] = 'membership'
  request.headers['X-Hub-Signature'] = signature

  post :create, body:, as: :json
  assert_response :ok

  victim_team.reload
  attacker = User.find_by(login: 'attacker-login')
  # Equality claimed broken: repository_owner ('attacker-org') != organization.login ('victim-org')
  assert_includes victim_team.members, attacker # attacker is now in an org they never proved membership in
  assert attacker.authorized? # escalated into Shipit.github_teams
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
