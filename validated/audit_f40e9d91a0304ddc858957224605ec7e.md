This confirms the vulnerability. `User#authorized?` at [1](#0-0)  gates access to the whole application (enforced by `force_github_authentication` in [2](#0-1) ) based on `teams.where(id: Shipit.github_teams.map(&:id))`. Team membership is populated exclusively by the `membership` webhook handler, which trusts `params.organization.login` for the `Team#organization` binding without ever cross-checking it against the field used to select the webhook secret during signature verification.

### Title
Cross-organization webhook forgery lets an attacker join any `Shipit::github_teams` team and bypass authentication - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
The webhook signature check verifies the HMAC using a GitHub-App secret selected from `params.dig('repository', 'owner', 'login')` (fallback `params.dig('organization', 'login')`), but the `membership` event handler that actually mutates state trusts an independent field, `params.organization.login`, without ever confirming it equals the field used for authentication. In a multi-organization Shipit deployment (`Shipit.github`/`github_app_config`), each organization has its own `webhook_secret`, and an org owner legitimately knows their own org's secret. That owner can therefore forge a POST to `/webhooks` that authenticates as "their org" while claiming to be a `membership` event for a completely different, victim organization — including one referenced in `Shipit.github_teams`, which gates authentication for the entire Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the HMAC secret) using `repository_owner`, itself pulled from `params.dig('repository', 'organization', 'login')`/`organization.login`: [3](#0-2) [4](#0-3) 

`Shipit.github(organization:)` looks up per-organization secrets from `secrets.github` when multiple GitHub Apps are configured — a documented and supported deployment mode: [5](#0-4)  and [6](#0-5) .

For a `membership` event, however, the actual organization that gets written to the database comes from a *different, unauthenticated-relative-to-signature* field, `params.organization.login`, with no consistency check against `repository_owner`: [7](#0-6) 

Because `Team` records are looked up/created purely by `github_id`/`organization` from this payload and membership is granted unconditionally for `action == 'added'`, an attacker who is a legitimate owner/admin of one Shipit-configured org (and thus knows that org's real `webhook_secret`, which they configured themselves when creating the GitHub webhook) can sign an arbitrary payload with their own secret while setting `organization.login` and `team` to values belonging to a *different* org managed by the same Shipit instance — including the org(s) referenced by `Shipit.github_teams`.

`Team#find_or_create_by_handle` and the `github_teams` list are exactly what gates login-time authorization: [1](#0-0)  and [2](#0-1) . By forging `team.id`/`team.slug` to match (or create) a `Team` whose `id` is then included by `Shipit.github_teams`, and adding their own GitHub login as `member.login`, the attacker satisfies `authorized?` for their own `User` row without ever actually being a member of the victim GitHub organization/team.

This is a direct analog of the reported re-entrancy bug's class: a value acted upon (`organization.login` used to create/mutate `Team`/`Membership`) is never bound to the value that was actually authenticated (`repository_owner` used to select the HMAC secret). Just as the exploit swapped the pair contract used for pricing versus the pair actually swapped against, this swaps the organization whose secret authenticates the request versus the organization whose team-membership state gets mutated.

### Impact Explanation
This is an authentication bypass / escalation into `Shipit.github_teams` authorization (explicitly listed as a High-impact criterion): an external attacker who only controls one org's webhook secret in a multi-org Shipit deployment can grant themselves membership in the team(s) that gate access to the entire Shipit UI/API for every repository hosted on that instance, without any actual GitHub team membership, repository write access, or Shipit session/API token.

### Likelihood Explanation
Requires a Shipit deployment configured with the documented multi-organization GitHub App mode and `Shipit.github_teams` restricting access; the attacker only needs to be able to configure/know one org's webhook secret (which any org that installs the app on itself controls, since org admins choose their own secret when wiring up the GitHub webhook) and knowledge of the victim org's login/team id/slug (public information on GitHub).

### Recommendation
Bind the authenticated organization to every field the handlers act on: after `verify_signature` succeeds, pass the authenticated `repository_owner`/organization down to handlers, and have `MembershipHandler` (and any other handler that reads an `organization`/`repository` field) assert that `params.organization.login`/`params.repository.full_name` matches (or is scoped under) the organization whose secret validated the signature. Reject the webhook otherwise.

### Proof of Concept
1. Shipit is configured with multiple GitHub orgs, e.g. `OrgOne` (attacker-controlled) and `Victim` (has a `Shipit::Team` referenced in `Shipit.github_teams`).
2. Attacker knows `OrgOne`'s `webhook_secret` (they set it when installing the webhook on their own org/repo).
3. Attacker computes `sha1=HMAC(OrgOne_secret, body)` over a crafted body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Victim Team", "slug": "victim-team", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "Victim" },
  "member": { "login": "attacker" },
  "repository": { "owner": { "login": "OrgOne" } }
}
```
4. POST to `/webhooks` with header `X-Github-Event: membership` and `X-Hub-Signature: sha1=<computed>`.
5. `verify_signature` resolves `repository_owner` = `"OrgOne"`, fetches `OrgOne`'s `GitHubApp`, and the signature validates successfully against `OrgOne_secret`.
6. `MembershipHandler#process` runs, using `params.organization.login == "Victim"` to create/find a `Team` and add `attacker` as a member — as shown by `find_or_create_team!` and `team.add_member(member)` in [8](#0-7) .
7. If this `Team` is (or matches) one listed in `Shipit.github_teams`, the attacker's `User#authorized?` now returns true, granting them full access to the Shipit instance.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
