Based on my investigation, I found a concrete analog to CVE-2019-8379's pattern (an unvalidated parser function crashing on malformed attacker-supplied input).

### Title
Uncaught exception / DoS via unvalidated merkle proof deserialization in address definition authentifier evaluation - (File: definition.js, merkle.js)

### Summary
`merkle.deserializeMerkleProof()` in [1](#0-0)  assumes its input is a string and calls `.split("-")` on it with no type check. It is invoked directly, without a preceding type check or a `try/catch`, from the `'in merkle'` authentifier-evaluation case in `definition.js`: [2](#0-1) 

Here `serialized_proof = assocAuthentifiers[path]` is taken straight from the unit's `authentifiers` map supplied by the unit's author/poster, and passed unchecked to `deserializeMerkleProof`.

### Finding Description
This mirrors the CVE-2019-8379 bug class: a low-level parsing routine (`be_uint32_read` there, `deserializeMerkleProof` here) is fed attacker-controlled, structurally-unvalidated data and dereferences/operates on it assuming a specific shape, producing an unhandled crash instead of a clean rejection.

In `ocore`, the sibling code path in `formula/evaluation.js` (used for oscript's `is_valid_merkle_proof`) is careful to check `typeof proof === 'string'` before calling `merkle.deserializeMerkleProof(proof)` [3](#0-2) , and it further wraps `verifyMerkleProof` in a `try/catch` [4](#0-3) .

By contrast, the `'in merkle'` authentifier case inside `validateAuthentifiers`/`evaluate` in `definition.js` performs no type check on `assocAuthentifiers[path]` before calling `deserializeMerkleProof`, and the call is not wrapped in `try/catch` [5](#0-4) . `assocAuthentifiers` is built from the unit's `authors[].authentifiers` object, whose values are supplied verbatim by whoever posts the unit — an ordinary, unprivileged unit poster.

If the JSON value at that authentifier path is not a string (e.g., a number, `null`, an object, or an array), `serialized_proof.split("-")` throws a `TypeError` synchronously inside the address-definition evaluator. Because this call sits deep inside the recursive `evaluate()` used during unit/spend-condition validation and is not guarded, the exception propagates up out of the normal control flow of `validateAuthentifiers`, which is not designed to expect synchronous throws at this point (all sibling branches signal failure via `cb2(false)` rather than throwing).

### Impact Explanation
An uncaught exception thrown mid-validation, if not intercepted higher up the call stack, will surface as an unhandled synchronous exception during processing of an incoming unit. Depending on where in the async chain this surfaces, this can crash the node process handling unit validation (denial of service) — the same end effect as the segfault in the original CVE, translated to the Node.js runtime. This affects any node that validates units carrying an address definition using `['in merkle', ...]` as a spending/authentication condition, triggered by supplying a malformed (non-string) authentifier value for that path.

### Likelihood Explanation
Reaching this code path requires:
1. An address whose definition includes an `'in merkle'` clause (a standard, documented definition-language primitive).
2. A unit author supplying a non-string value at the corresponding authentifier path.

Both are fully within the control of an ordinary unit poster/author; no special network position or privilege is required. The main uncertainty is whether an outer `try/catch` in the general unit-validation dispatch machinery (e.g. around `validateAuthentifiers`/`evaluate` calls in `validation.js`) already catches and gracefully converts such exceptions to a validation error — I was not able to fully confirm the exact exception-handling wrapper around this specific evaluator call within the available search budget.

### Recommendation
- In `definition.js`, before calling `merkle.deserializeMerkleProof(serialized_proof)` in the `'in merkle'` case, validate `typeof serialized_proof === 'string'` (and reasonable length bounds), mirroring the check already present in `formula/evaluation.js`.
- Wrap the `deserializeMerkleProof`/`verifyMerkleProof` calls in `definition.js` in a `try/catch` (as `verifyMerkleProof` itself already does internally) so malformed input degrades to a validation failure (`cb2(false)`) rather than an uncaught exception.
- Harden `merkle.deserializeMerkleProof` itself to defensively check `typeof serialized_proof === 'string'` and throw a clean, catchable error otherwise.

### Proof of Concept
1. Create/use an address whose definition contains an `['in merkle', [['SOME_ADDRESS'], 'feed_name', 'expected_value']]` condition at some authentifier path, e.g. `r`.
2. Construct a unit authored by that address where `authors[0].authentifiers.r` is set to a non-string value, e.g. `12345` or `{}` or `null`, instead of the expected `"index-sibling1-sibling2-root"` string.
3. Submit the unit for validation. During `validateAuthentifiers`, the `'in merkle'` branch executes `merkle.deserializeMerkleProof(assocAuthentifiers['r'])`, which internally calls `(12345).split` / `({}).split` / `null.split`, throwing a `TypeError` synchronously and uncaught at that point in `definition.js`.
