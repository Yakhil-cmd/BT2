### Title
Null pointer dereference crash from missing `payload` field in `private_payment` justsaying - ([File: network.js])

### Summary
`network.js`'s `handleOnlinePrivatePayment()` dereferences `arrPrivateElements[0].payload.denomination` before ever checking that `payload` exists, mirroring the CVE-2023-37036 pattern of dereferencing an expected-but-absent field (`ENB_UE_S1AP_ID`) coming straight from an unauthenticated, network-adjacent message.

### Finding Description
`handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks)` is reached directly from the `private_payment` justsaying handled in `network.js`, and indirectly from `handlePrivatePaymentChains()` in `wallet.js` (device-message path, `case 'private_payments'`). The only guard before the crash site is: [1](#0-0) 

```
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
```

`isNonemptyArray` only checks that the array is non-empty; it does not check that `arrPrivateElements[0]` is a non-empty object, nor that it has a `payload` property. An attacker-controlled peer can send a `private_payment` justsaying with `arrPrivateElements[0]` equal to `{}`, `{unit: "..."}`, or any object lacking `payload`. Evaluating `arrPrivateElements[0].payload.denomination` then throws `TypeError: Cannot read properties of undefined (reading 'denomination')`.

This is directly analogous to CVE-2023-37036: an expected sub-field (`payload`) of an untrusted, unauthenticated protocol message is assumed present and dereferenced without a null/undefined check, causing an unhandled exception.

The same missing-field issue is repeated in `handlePrivatePaymentChains()` in `wallet.js`, where `objHeadPrivateElement.payload.denomination` is read at line 1024 after only checking `arrChains.every(...)` earlier in the function — but that earlier `every()` check does validate `isNonemptyObject(e.payload)` for every chain element, so the `wallet.js` path is actually guarded. The unguarded path is specifically the standalone `network.js`/`handleOnlinePrivatePayment` justsaying entry point, which can be invoked without going through `handlePrivatePaymentChains`'s stricter validation.

### Impact Explanation
If this `TypeError` is thrown synchronously inside a message-handling callback that is not wrapped in a `try/catch`, it becomes an uncaught exception at the top of the event loop, crashing the whole Node.js process. Because the crash is triggered by network-adjacent peer input (a single malformed `private_payment` justsaying), a single connected peer/hub correspondent can crash a full node or light wallet, taking it offline and preventing it from relaying/validating/confirming new units — directly matching the "network unable to confirm new units" impact bar in the validation rules.

### Likelihood Explanation
The trigger requires no special privilege: any peer that can send a justsaying to a node (or, via `wallet.js`, any paired device that can send a `private_payments` message) can supply a private-payment element without a `payload` field. The check present (`isNonemptyArray`) does not validate the internal shape of the first array element, so the malformed input passes the only guard before the crash site.

### Recommendation
Add explicit shape validation at the top of `handleOnlinePrivatePayment()` before dereferencing nested fields, e.g.:
```
if (!ValidationUtils.isNonemptyArray(arrPrivateElements) ||
    !ValidationUtils.isNonemptyObject(arrPrivateElements[0]) ||
    !ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload))
    return callbacks.ifError("bad private_payment content");
```
Additionally, ensure this handler (and any similar entry points parsing peer-supplied JSON before validation) is invoked within a try/catch that reports the error via `callbacks.ifError` rather than allowing propagation to the event loop.

### Proof of Concept
A connected peer sends the justsaying:
```
["justsaying", {"subject": "private_payment", "body": [{"unit": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA="}]}]
```
`arrPrivateElements[0]` has no `payload` property. Execution reaches
`arrPrivateElements[0].payload.denomination` in `handleOnlinePrivatePayment`, throwing `TypeError: Cannot read properties of undefined (reading 'denomination')`. If uncaught, the node process crashes.

Note: I was unable to fully verify, within the available tool budget, whether the specific call site that invokes `handleOnlinePrivatePayment` from the raw `private_payment` justsaying (in `network.js`'s message-dispatch switch) wraps the call in a try/catch that would downgrade this to a handled error rather than a process crash. This should be confirmed by a maintainer/agent with direct repository access before treating the crash impact as fully proven.
