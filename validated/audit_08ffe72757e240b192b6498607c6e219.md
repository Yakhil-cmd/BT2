### Title
Stale block-scoped `index-cache` in `market.clar` lets a same-block liquidation's `lindex` write-down be invisible to concurrent users' health/price checks - (File: `local-testing/contracts/market/market.clar` / `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The bug report describes MAXMEM: a global register (`MAXMEM`) that is set once, never reset per execution step, and can be pushed by a low-cost transaction into a value that breaks a downstream bound check (`diffMem in Global.BYTE2`) for every subsequent step in the same batch, freezing the whole batch for everyone else. The structural analog in Zest is the market's `index-cache` map, keyed only by `{ timestamp: stacks-block-time, aid }` [1](#0-0) . Exactly like `MAXMEM`, this is a single register shared by *all* callers for the duration of one "batch" (here, one block), it is written once and then trusted as a cache HIT for the remainder of that scope, and nothing re-validates or invalidates it when the underlying vault state it represents changes mid-scope.

### Finding Description
`accrue-and-cache` is the sole gate for populating/reading this cache: [2](#0-1) 

Once a value is cached for `{stacks-block-time, aid}`, any later call in the same block returns the cached tuple `{ index, lindex }` verbatim, without re-querying the vault. `liquidate()` relies on exactly this pattern: it primes the cache at the start of the call via `accrue-user-debts`/`accrue-user-collateral`, uses the (now cached) values to compute collateral/debt USD values and later, at the very end of the same function, may trigger bad-debt socialization: [3](#0-2) [4](#0-3) 

Bad-debt socialization calls into the vault's `socialize-debt`, which directly mutates the vault's `lindex` (the liquidity/supply index used to price that asset's zToken) without going through `accrue`: [5](#0-4) 

Crucially, this write-down of `lindex` happens **after** the market has already cached `{index, lindex}` for that `(timestamp, aid)` pair in the current block, and no code path deletes or refreshes the `index-cache` entry afterward. Every other read of `get-cached-indexes`/`accrue-and-cache` for that same asset later in the *same block* — by a different user's `borrow`, `collateral-add`, or `liquidate` transaction — will get a cache HIT and silently use the pre-write-down (stale, overstated) `lindex`, instead of the correct post-socialization value: [6](#0-5) 

This mirrors the MAXMEM root cause precisely: a shared register (`MAXMEM` / `index-cache`) is written by one execution context and then blindly trusted by later, unrelated execution contexts sharing the same scope (batch / block), with no mechanism to detect that the underlying truth changed in between.

### Impact Explanation
Any user who has zToken collateral or debt on the socialized asset, and who transacts later in the same block as the liquidation that triggered bad-debt socialization, will have their collateral valuation, LTV/health computation, or borrow-index scaling computed against a stale, overstated `lindex`/`index`. This can let an under-collateralized position pass a health check that should have failed (over-borrowing against overstated zToken collateral), or cause another liquidator's `remaining-debt-to-repay`/collateral-seizure math (which explicitly reads `unwrap-panic (get-cached-indexes debt-aid)`) to be computed on incorrect data: [7](#0-6) 

Concretely this is an ordering dependence between two unrelated users within one block, where one user's socialization event corrupts a shared cache consumed by another user's transaction, producing an incorrect valuation that can be used to extract excess borrow capacity or distort a legitimate liquidation. This lands in the **High** impact bucket (temporary freezing/mispricing of funds, and unfair loss on liquidation seizure/health evaluation for the victim) similar to the report's "High" rating for MAXMEM.

### Likelihood Explanation
The precondition is narrow but realistic: it requires a liquidation that triggers bad-debt socialization to occur in the same block as another transaction touching the same underlying asset's cached index (borrow, collateral-add, or another liquidation). On a busy chain with liquidation bots and active borrowers, colliding within one block is plausible but not guaranteed, so likelihood is moderate rather than trivially exploitable on demand (an attacker cannot unilaterally force another user's transaction to land in the same block, though a liquidator could try to time their own subsequent action to exploit the stale cache for themselves or a colluding party).

### Recommendation
Invalidate or refresh the `index-cache` entry for an asset whenever vault state is mutated outside of the normal `accrue`-then-cache path — in particular, immediately after `vault-socialize-debt` succeeds, `map-delete index-cache { timestamp: stacks-block-time, aid: aid }` (or re-populate it with the vault's freshly returned indexes) so that any subsequent read in the same block is forced to re-query the vault. More generally, any vault function that can change `index`/`lindex` outside of `accrue` (e.g. `socialize-debt`) should be treated as a cache-invalidating event from the market's perspective.

### Proof of Concept
1. Block N: User A holds zToken-X collateral; User B (borrower) has debt causing them to be at/near the liquidation partial threshold on the same underlying vault X.
2. Liquidator L calls `market.liquidate(...)` on User B in block N. Inside this call: `accrue-user-collateral`/`accrue-user-debts` populate `index-cache` for `{ timestamp: N, aid: X }` with the pre-liquidation `lindex`. Liquidation proceeds; because B has no remaining collateral, `bad-debt-socialized` triggers `vault-socialize-debt`, which calls the vault's `socialize-debt`, writing `lindex` down to a lower value in vault-X storage — but `index-cache` for `{N, X}` is untouched and still holds the old, higher `lindex`.
3. Still in block N, User A calls `market.collateralAdd`/`market.borrow`, using zToken-X as collateral. `accrue-and-cache` returns the stale (higher) cached `lindex` for `{N, X}` instead of querying the vault again, so A's zToken-X collateral is valued higher than it actually is post-socialization.
4. User A can borrow more than their true (post-write-down) collateral would support, or pass a health check that should have failed, because the health/LTV computation used the stale cached index rather than the vault's authoritative post-socialization state.

**Uncertainty note:** I was not able to fully trace every downstream consumer of `get-cached-indexes`/`index-cache` (e.g., the exact zToken price-resolution path via `price-resolve`/oracle `callcode`) within the available search budget, so the precise magnitude of the valuation delta and all affected call sites (beyond `liquidate`, `borrow`, and `collateral-add`) are not fully confirmed from the indexed code. A full review of `price-resolve` for ztoken oracle type and all call sites of `accrue-and-cache`/`get-cached-indexes` in `market.clar` would be needed to confirm the complete blast radius.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
