### Title
Cross-organization webhook forgery: HMAC signature is verified against the org named in the payload, not the org that owns the repository being written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate a webhook against using an attacker-controlled field of the same JSON body (`repository.owner.login` / `organization.login`). The handlers that actually decide *which repository/stack* the event acts on (`Handler#repository_name` -> `payload.dig('repository', 'full_name')`) read a **different, independently-controlled field** of that same body. Nothing ties the two together, so a party who legitimately possesses the `webhook_secret` for one configured GitHub organization (org A) can sign an arbitrary payload and have it processed as an event for a repository belonging to a *different* configured organization (org B), because the signature is checked against org A's secret while the repository operated on is read from an unrelated field.

### Finding Description
`WebhooksController#verify_signature` computes the organization used to look up the verifying secret purely from the incoming, unauthenticated payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a per-organization `GitHubApp` instance holding that organization's own `webhook_secret`, as configured for multi-tenant installs (each org has its own `app_id`, `private_key`, and `webhook_secret`): [3](#0-2) [4](#0-3) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the same raw payload to event handlers: [5](#0-4) 

Every handler determines the target repository/stacks from a **separate** JSON path in the very same body: [6](#0-5) 

and resolves it via `Repository.from_github_repo_name`, with no cross-check that the resolved repository's `owner` matches the organization whose secret validated the signature: [7](#0-6) 

Because the HMAC only proves "the sender knows organization X's `webhook_secret`," and `repository_owner` (used to pick which secret to check) and `repository.full_name` (used to pick which repository is acted on) are two independent, unauthenticated fields inside the attacker's own request body, an attacker who holds org A's `webhook_secret` can craft and sign a body where `repository.owner.login` = "orgA" (so verification succeeds against orgA's secret) while `repository.full_name` = "orgB/some-repo" (so the handler acts on a repository owned by orgB). This breaks the intended binding: *the organization that authenticated the request* ≠ *the repository that the request writes to*.

Concretely, `PushHandler` would call `stack.sync_github(expected_head_sha: params.after)` for a stack under org B's repository even though only org A's webhook secret was proven: [8](#0-7) 

`MembershipHandler` is similarly exposed: it trusts `params.organization.login` (attacker controlled, only implicitly related to which secret validated the signature) to create/attach a `Team`, and can add/remove team memberships (which back `Shipit.github_teams` authorization) for an organization other than the one whose secret was actually used: [9](#0-8) 

### Impact Explanation
This allows a party who legitimately controls a webhook secret for one tenant organization (a normal, low-privilege actor in a multi-org Shipit install — e.g. an org admin who can view/reset their own GitHub App's webhook secret) to forge state-changing GitHub events (`push`, `status`, `membership`, `check_suite`, `pull_request`) attributed to a completely different organization's repositories that they do not administer. Depending on handler, this can:
- Trigger `GithubSyncJob`/`sync_github` and continuous-delivery flows on another org's stack (push/status), influencing what is deployed - an unauthorized deploy/rollback pathway.
- Mutate `Team` membership via `MembershipHandler`, which is the basis for `Shipit.github_teams` authorization checks (`app/controllers/concerns/shipit/authentication.rb`), enabling escalation into another organization's team-based authorization.

This matches the "High: escalation into `Shipit.github_teams` authorization" / cross-repository writes / unauthorized deploy impact classes.

### Likelihood Explanation
This requires the deployment to be running in the documented multi-organization GitHub configuration (multiple orgs each with a distinct `webhook_secret`), which the engine explicitly supports and documents (`config/secrets.development.shopify.yml`, `config/secrets.development.example.yml`, `docs/setup.md`). Any actor who is a legitimate holder of *one* tenant's webhook secret — not a privileged Shipit account, GitHub App private key, or `ApiClient` token — can exploit this purely by crafting an HTTP POST to the shared `/webhooks` endpoint with a body they sign themselves. No session, TLS interception, or social engineering is needed. Likelihood is moderate-to-high specifically for multi-tenant installs; single-organization installs are not affected because `Shipit.github(organization: nil)` always resolves to the single configured app regardless of payload content (`lib/shipit.rb` lines 170-181, 183-188).

### Recommendation
After signature verification succeeds, revalidate that every repository/organization reference the selected handler will act on (`repository.full_name`, `organization.login`, `team.organization`, etc.) actually belongs to the organization (`repository_owner`) whose secret validated the signature — i.e., derive a single canonical organization from the verified payload and reject the request (422) if any downstream org/repo reference diverges from it. Alternatively, iterate over all configured organizations' secrets and require the payload's repository owner to match the organization whose secret validated, enforced as an explicit equality check rather than an implicit assumption.

### Proof of Concept
Conceptual PoC (illustrative, not executable without a live multi-org Shipit instance):
1. Configure two organizations, `orgA` and `orgB`, each with a distinct `webhook_secret` (per `config/secrets.development.shopify.yml` schema). `orgA`'s repos and `orgB`'s repos are both registered as Shipit `Repository`/`Stack` records.
2. As a party who legitimately knows `orgA`'s `webhook_secret` (e.g., an org admin who can view it in `orgA`'s GitHub App settings), construct a JSON body for a `push` event:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker chosen sha>",
     "repository": {
       "owner": { "login": "orgA" },
       "full_name": "orgB/target-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner` = `"orgA"`, loads `orgA`'s `GitHubApp`, and the signature matches (since it was computed with `orgA`'s secret) → request passes.
5. `PushHandler#process` resolves `repository_name` from `full_name` = `"orgB/target-repo"`, finds `orgB`'s stacks via `Repository.from_github_repo_name`, and triggers `sync_github` on them - despite `orgB`'s own webhook secret never being presented.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
