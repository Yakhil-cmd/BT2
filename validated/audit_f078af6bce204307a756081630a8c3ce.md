## Equality being validated

Claimed binding: `repository that authenticated/originated the webhook signal (payload['repository']['full_name'] == "org_b/repo_b")` **must equal** `repository whose stack's github_api/GITHUB_TOKEN executes the resulting merge (stack_a.repository.full_name == "org_a/repo_a")`.

Tracing the code shows this equality is never enforced — it is not even checked.

## Trace

`WebhooksController#create` dispatches the raw JSON `params` to `Shipit::Webhooks.for_event('status')`, i.e. `Handlers::StatusHandler`, after only verifying the HMAC signature against the org derived from `payload['repository']['owner']['login']` (`app/controllers/shipit/webhooks_controller.rb:10-49`). That check authenticates *who sent* the payload (org B) but says nothing about *which stacks* the payload may affect.

`StatusHandler#process` then resolves target commits purely by SHA, with no repository filter at all: [1](#0-0) 

Compare this with `PushHandler`, which correctly scopes via the `Handler#stacks` helper that filters by `Repository.from_github_repo_name(repository_name)`: [2](#0-1) [3](#0-2) 

`StatusHandler` never calls `stacks` and its `ExplicitParameters` schema (`requires :sha, :state`, `accepts :description/:target_url/:context/:created_at/:branches`) has no repository field at all, so nothing in the schema, in `verify_signature`, or in `drop_unhandled_event` constrains which stack's commit gets updated: [4](#0-3) 

`Commit.create_status_from_github!` → `Commit#add_status` then fires `stack.schedule_merges` for whichever stack owns that SHA, purely based on state transition, with no relation to which repo signed the webhook: [5](#0-4) 

`Stack#schedule_merges` enqueues `ProcessMergeRequestsJob` for *that* stack: [6](#0-5) 

The job then re-evaluates and potentially merges pending PRs using `stack.github_api`, which is stack A's (i.e. that stack's configured/GitHub-App-derived) credentials — completely decoupled from the repository (B) that actually supplied the triggering webhook: [7](#0-6) [8](#0-7) 

## Root cause

`Commit` rows are keyed by `sha` (a content-addressed, attacker-influenceable value), and multiple `Stack`s (tracking different repos, potentially different orgs/tenants) can hold `Commit` records with the same `sha` if the underlying git objects are identical (forks sharing history, or a deliberately reproduced commit object with identical tree/parents/author/committer/timestamps/message). `StatusHandler` never validates that `payload['repository']['full_name']` corresponds to the `stack.repository` of the commits it mutates, unlike `PushHandler`, `CheckSuiteHandler`, and the `pull_request` handlers which resolve stacks through `Handler#stacks` (repository-scoped). This lets a webhook that is legitimately authenticated for repository B (an attacker-owned/attacker-controlled repo, satisfying `verify_signature` with org B's real secret) mutate commit status state for a completely different repository/stack A, driving that unrelated stack's automatic merge queue.

## Exploit flow

1. Attacker identifies (or produces) a commit whose SHA is shared between their own repository B (which they own, and which is onboarded under a Shipit GitHub App installation they can legitimately trigger events from — e.g., a fork of repo A, or any repo where they can reproduce byte-identical commit content) and a commit tracked by target stack A's queue (e.g. the head commit of a pending `MergeRequest` awaiting a specific CI `context`).
2. Attacker creates/sets a commit status on repo B with that SHA, `state: success`, and a `context` matching one of stack A's `merge_request_required_statuses`. GitHub delivers a real, correctly-signed `status` webhook for repo B.
3. `verify_signature` passes (org B's real secret, real payload) — this only proves the payload came from org B, not that its effects are scoped to org B.
4. `StatusHandler#process` finds `Commit.where(sha: ...)`, which includes stack A's commit row, and calls `create_status_from_github!` on it, forging a "required" green check for stack A's PR.
5. `Commit#add_status` sees a `pending → success` transition and calls `stack.schedule_merges` for **stack A**.
6. `ProcessMergeRequestsJob` finds the queued PR now "fully green" and calls `merge_request.merge!`, which invokes `stack_a.github_api.merge_pull_request(...)` — merging code in repository A using stack A's own GitHub App/token, triggered entirely by a webhook the attacker legitimately sent for repository B.

## Impact

An attacker who owns any repository onboarded to the same Shipit instance (even in an unrelated organization/tenant) can forge commit-check-passed signals for a **different** stack/repository and cause an unauthorized merge to execute against that other repository, using that repository's own GitHub credentials. This is a cross-tenant "payload for one repository mutating another's stack" issue, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). It is repeatable against any stack whose queued PR head commit SHA can be reproduced/shared by the attacker.

## Likelihood

Requires: (a) Shipit multi-tenant deployment with more than one org/repo onboarded (the documented normal case), (b) attacker control of some repo with a valid GitHub App/webhook installation (their own repo, fork, or org), and (c) ability to make a target commit's SHA exist in that attacker-controlled repo (trivial for forks that share history with the upstream repo; possible in general via content-identical commit crafting). No Shipit secrets, sessions, or privileged roles are needed — only the attacker's own repository and the webhook signature that GitHub legitimately computes for it.

## Recommendation

`StatusHandler#process` (and any other handler resolving commits solely by `sha`) must additionally scope the lookup by the stack's own repository, e.g. via the existing `Handler#stacks` helper (`stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or filter `commit.stack.repository == Repository.from_github_repo_name(repository_name)`), so a status can only affect commits belonging to the repository that authenticated the webhook.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
