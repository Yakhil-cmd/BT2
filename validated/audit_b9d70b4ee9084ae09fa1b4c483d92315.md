### Title
Webhook signature is verified against the wrong organization's secret while the acted-upon repository/commit is taken from an unverified payload field, enabling cross-organization writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the HMAC against using `repository.owner.login` (or `organization.login`), but the handlers that actually act on the payload resolve the target repository/commit from a *different*, unauthenticated payload field (`repository.full_name`, or no repository field at all for `status` events). Since the whole raw body is what gets HMAC-signed, an attacker who can produce a valid signature for **any one** configured organization's `webhook_secret` can freely choose the `repository.full_name` (or an arbitrary commit `sha`) embedded in that same signed body, causing Shipit to act on stacks/commits belonging to a completely different, unrelated organization/repository.

### Finding Description
`verify_signature` picks the `GithubApp` instance (and thus which `webhook_secret` is checked) purely from `repository_owner`: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple GitHub organizations, each with its own independent `webhook_secret`: [3](#0-2) 

Once the signature check passes, every registered handler is invoked with the entire, attacker-controlled `params` hash: [4](#0-3) 

However, the base `Handler` class resolves the target repository/stacks not from `repository.owner.login` (the field the signature was checked against) but from the independent `repository.full_name` field, which is part of the *same signed body* and therefore fully attacker-controlled: [5](#0-4) 

`PushHandler` uses this to locate stacks purely by `full_name` + branch, with no re-validation that the resolved repository actually belongs to the organization whose secret was used to verify the request: [6](#0-5) 

`StatusHandler` is worse: it doesn't even look at the repository field. It looks up **any** `Commit` in the entire database matching the attacker-supplied `sha`, across all stacks/repositories, and materializes a `Status` record directly from attacker-controlled fields (`state`, `description`, `target_url`, `context`): [7](#0-6) 

This is confirmed by the existing test, which shows the `Status` fields are taken verbatim from the webhook JSON body with no cross-check against GitHub's actual API state: [8](#0-7) 

**The binding that is broken:** `organization authenticated by webhook_secret == organization whose repository/commit is written`. Before the fix (conceptually), these are supposed to be the same entity; in the current code the left side is chosen from `repository.owner.login`/`organization.login` while the right side is independently derived from `repository.full_name` or from a bare `sha` lookup with no owner scoping at all — two different, attacker-influenced fields inside the same signed payload.

### Impact Explanation
Any actor who legitimately holds (or can otherwise obtain a validly-signed delivery for) **one** configured GitHub organization's `webhook_secret` in a multi-org Shipit deployment can forge events that mutate state belonging to a completely different organization's stacks:
- Forge a `status` event naming an arbitrary commit `sha` tracked by *any* stack in the Shipit instance and set its CI status/context to `success`, directly falsifying the `ci.require` gate that governs whether a commit is deployable — a path to an **unauthorized deploy**.
- Forge a `push` event naming another organization's `repository.full_name`, triggering `stack.sync_github` and other push-driven side effects on that unrelated stack — a **cross-repository write**.
- Similarly, `pull_request`/`membership`/`check_suite` handlers resolve their target the same way (via `repository.full_name`), extending the same class of cross-org write to PR label capture, team membership changes, and check-run refreshes.

This matches the "Critical" impact bar defined for this scan (unauthorized deploy, cross-repository writes) because the CI-status forgery path can directly clear the gate that authorizes a deploy without ever touching GitHub's real API state.

### Likelihood Explanation
This is directly exploitable in any Shipit deployment configured with more than one GitHub organization (a documented, supported configuration — see `test/dummy/config/secrets_double_github_app.yml` and the multi-org example in `docs/setup.md`). Any party with legitimate access to one org's webhook delivery configuration (e.g., can view/rotate that org's GitHub App webhook secret, or has delivery access through that org's app settings) can compute a valid signature and does not need any credentials for the victim organization's repositories, satisfying the "unprivileged-attacker" bar relative to the victim stack.

### Recommendation
After signature verification succeeds for organization `O`, require every downstream handler to confirm that the repository/commit it is about to act on actually belongs to a repository owned by `O` (e.g., compare `repository.full_name`'s owner segment, or the resolved `Stack`'s `Repository#owner`, against `repository_owner`) before performing any lookup or mutation. For `StatusHandler` specifically, scope the `Commit` lookup to commits whose stack's repository owner matches the authenticated organization, rather than a bare, global `sha` lookup.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), both with stacks tracked by the same Shipit instance.
2. As an actor who knows `OrgOne`'s `webhook_secret` (but has no access to `OrgTwo`), craft a JSON body:
   ```json
   {
     "sha": "<commit sha belonging to an OrgTwo-tracked stack>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgOne" } }
   }
   ```
3. Sign the raw body with `OrgOne`'s `webhook_secret` (`sha1=HMAC(webhook_secret, body)`), set `X-Hub-Signature` and `X-Github-Event: status`, and POST to `/webhooks`.
4. `verify_signature` resolves `repository_owner` to `"OrgOne"`, fetches `OrgOne`'s `GithubApp`, and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) looks up `Commit.where(sha: params.sha)` globally — matching the `OrgTwo` commit — and creates a `success` `Status` on it, even though the request was never signed by `OrgTwo`'s secret.
