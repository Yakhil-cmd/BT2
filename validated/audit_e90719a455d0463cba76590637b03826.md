### Title
Webhook signature is verified against `repository.owner.login`'s org secret while handlers act on the independently-controlled `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification purely from attacker-supplied JSON fields, while the handlers that actually mutate state select the target `Stack`/`Repository` from a *different*, unrelated field in the same payload. Because these two fields are never cross-checked, a party who is onboarded as *any* organization on a multi-tenant Shipit instance can forge signed webhooks for stacks belonging to a completely different organization.

### Finding Description
`verify_signature` computes the organization used to fetch the webhook secret like this: [1](#0-0) [2](#0-1) 

`repository_owner` is taken directly from the untrusted payload (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), and `Shipit.github(organization: repository_owner)` returns the `GithubApp`/config entry (and its `webhook_secret`) registered for *that* organization name. The signature is verified only against that organization's secret via `verify_webhook_signature`: [3](#0-2) 

Once the signature check passes, `create` dispatches to handlers using `params` (the parsed JSON body), e.g. `PushHandler`: [4](#0-3) [5](#0-4) 

Handlers resolve the target repository/stack from a **different** field, `repository.full_name`, in the base `Handler` class: [6](#0-5) 

Nothing enforces that `repository.owner.login` (used to pick the verifying secret) equals the owner encoded in `repository.full_name` (used to select the `Stack` that gets written to). An attacker who legitimately controls their own GitHub organization onboarded into the same Shipit instance (each org has its own `github_apps`/`webhook_secret` entry, as shown by the `Shipit.github(organization: ...)` lookup and `test/fixtures/shipit/github_hooks.yml` per-org secrets) can:

1. Take a webhook secret they legitimately know (their own org's secret configured in Shipit).
2. Build a JSON body where `repository.owner.login` = their own org (so the correct secret is selected and the HMAC they compute validates), but `repository.full_name` = `"victim-org/victim-repo"` (a stack that belongs to a different, unrelated organization/app in the same Shipit instance).
3. Compute a valid `X-Hub-Signature` using their own secret over that crafted body and POST it to `/webhooks`.

`verify_signature` will succeed (it only validates the org derived from `repository.owner.login`, which matches the attacker's own secret), and `PushHandler`/other handlers will then act on the victim's stack looked up via `repository.full_name`.

Equality broken: **the organization whose signature was authenticated ≠ the repository that is written/acted upon.**

### Impact Explanation
Any event handled by `Shipit::Webhooks` (push, status, check_suite, membership, etc.) can be forged for a victim stack that belongs to a different onboarded organization, without any credentials for that victim org or repository. Concretely, a forged `push` event triggers `GithubSyncJob`/`stack.sync_github` on the victim stack — an unauthorized cross-organization write into Shipit's tracked commit/ref state for a repository the attacker does not control. Forged `status`/`check_suite` events can fabricate CI results that gate deploy eligibility, enabling an unauthorized deploy to proceed. This is a cross-tenant/cross-repository write reachable by an unprivileged external actor who only needs to be a legitimate tenant of the same multi-tenant Shipit deployment — satisfying the Critical bucket ("cross-repository writes" / "unauthorized deploy").

### Likelihood Explanation
This requires only that the Shipit instance is multi-tenant (supports more than one GitHub organization/app, as its config format explicitly supports via per-organization `github_apps`/`webhook_secret`), and that the attacker controls one such onboarded organization (a common, low-privilege scenario — e.g., any team allowed to add their own repos to a shared Shipit instance). No access to the victim's secret, GitHub App private key, or Shipit session is needed, matching the "unprivileged attacker" threat model.

### Recommendation
In `WebhooksController`, after verifying the signature for the organization derived from the payload, cross-check that the same organization owns the repository named in `repository.full_name` (and any other repository-identifying field consumed by handlers) before dispatching. Alternatively, verify the signature using the secret associated with the resolved `Stack`'s actual repository/organization (looked up the same way handlers do), rather than trusting `repository.owner.login`/`organization.login` in isolation.

### Proof of Concept
1. Shipit instance configured with two organizations: `attacker-org` (secret `S1`, known/controlled by attacker) and `victim-org` (hosting stack `victim-org/victim-repo`).
2. Attacker crafts payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S1, body)>` using their own known secret `S1`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, verifies the signature successfully against `S1`.
6. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and triggers `sync_github` on the victim's stack, all without any credential belonging to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
