### Title
Unauthenticated Peer Can Inject Arbitrary `StakingInfo` During Fast Sync, Corrupting Reward Distribution and Validator Qualification — (File: `datasync/downloader/queue.go`)

---

### Summary

During fast sync, `P2PStakingInfo` received from any connected peer is written to the persistent database without any content validation. The `queue.DeliverStakingInfos` function explicitly skips validation with a `// TODO-Kaia-Snapsync update validation logic` comment, and `commitFastSyncData` / `commitPivotBlock` write the peer-supplied staking info directly to the DB. A malicious peer can respond to staking info requests with crafted data — arbitrary validator addresses, staking amounts, and reward addresses — which gets persisted and subsequently used for reward distribution calculations and validator qualification for pre-Kaia blocks.

---

### Finding Description

The Kaia fast sync protocol downloads staking info from peers alongside block headers, bodies, and receipts. Unlike bodies (validated against `header.TxHash`) and receipts (validated against `header.ReceiptHash`), staking info has **no cryptographic anchor in the block header** and no equivalent integrity check.

**Root cause — `datasync/downloader/queue.go` lines 956–958:**

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
```

The `validate` closure passed to the generic `deliver()` helper is a permanent no-op. Every other data type (`DeliverBodies`, `DeliverReceipts`) performs a cryptographic check against the already-validated block header; `DeliverStakingInfos` does not.

**Write path — `datasync/downloader/downloader.go` lines 1881–1884 (`commitFastSyncData`) and lines 1896–1898 (`commitPivotBlock`):**

```go
if result.StakingInfo != nil {
    d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
}
```

The peer-supplied `StakingInfo` is written directly to the miscellaneous DB with no further validation.

**Ingestion path — `node/cn/handler.go` lines 1198–1213 (`handleStakingInfoMsg`):**

```go
var stakingInfos []*staking.P2PStakingInfo
if err := msg.Decode(&stakingInfos); err != nil { ... }
pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos)
```

Any connected peer (no special role required) can send a `StakingInfoMsg` response. The handler decodes it and forwards it to the downloader without inspecting the content.

**Downstream consumers of the corrupted DB entry:**

- `kaiax/reward/impl/blockstate.go` `FinalizeState()` calls `GetDeferredReward()` → `GetStakingInfo()` → reads from DB for pre-Kaia blocks → distributes KAIA rewards based on the corrupted `StakingAmounts` and `RewardAddrs`.
- `kaiax/valset` `GetQualifiedValidators()` reads the same staking info to decide which validators meet `reward.minstake` and are therefore eligible to propose and sign blocks.

**Scope boundary:** `kaiax/staking/README.md` documents that for blocks before the Kaia hardfork, `SourceNum(num) = RoundDown(num-1, StakingInterval) - StakingInterval`, so the DB-persisted staking info is the authoritative source. After the Kaia hardfork, staking info is re-derived from the previous block's live state and the DB is not consulted. The attack therefore corrupts the node's view of all pre-Kaia staking epochs that were fast-synced.

---

### Impact Explanation

1. **Wrong reward distribution (KAIA):** `FinalizeState` calls `state.AddBalance(addr, amount)` for each entry in `spec.Rewards`. If `StakingAmounts` or `RewardAddrs` are forged, KAIA is credited to wrong addresses or in wrong proportions for every pre-Kaia block the node processes after fast sync completes.

2. **Invalid validator qualification:** `GetQualifiedValidators` uses the corrupted `StakingAmounts` to decide which council members are demoted. A forged entry with a zero staking amount for a legitimate validator demotes it; a forged entry with an inflated amount for an attacker-controlled address promotes it. This can cause the node to accept blocks signed by an invalid committee or reject blocks signed by the legitimate one — an invalid state transition / consensus divergence on the honest node.

3. **Persistent DB corruption:** `WriteStakingInfo` writes to the miscellaneous DB with `db.Put`. There is no overwrite guard; the corrupted entry survives node restarts and is used for all future queries at that block number.

---

### Likelihood Explanation

- **Attacker precondition:** Connect to a syncing node as a valid P2P peer. No privileged key, no governance role, no operator credential is required.
- **Trigger:** The syncing node must be in fast sync mode (the default for a new or lagging node). The downloader requests staking info from all idle peers; the attacker only needs to win the race for a given block hash request.
- **Detectability:** The node logs `"Imported new staking information"` but does not log the content, so the corruption is silent.

---

### Recommendation

1. **Implement content validation in `queue.DeliverStakingInfos`** (resolve the `TODO-Kaia-Snapsync` comment). The staking info for a given block can be verified by re-executing the `AddressBook` multicall against the already-committed state root for that block, or by comparing a hash of the staking info against a commitment stored in the block header or a trusted checkpoint.

2. **Do not write peer-supplied staking info to the DB before verification.** Move `PutStakingInfoToDB` calls in `commitFastSyncData` and `commitPivotBlock` to after the integrity check passes.

3. **Add a hash commitment to the block header** (or use an existing field such as `header.Extra`) so that staking info can be authenticated the same way bodies and receipts are.

---

### Proof of Concept

1. Attacker runs a modified Kaia node that connects to a victim node currently performing fast sync.
2. Victim node sends a `StakingInfoRequestMsg` containing block hashes for which it needs staking info.
3. Attacker's node responds with a `StakingInfoMsg` containing `P2PStakingInfo` entries where `StakingAmounts` are set to `math.MaxUint64` for the attacker's own `NodeId` and `0` for all legitimate validators, and `RewardAddrs` point to attacker-controlled addresses.
4. `handleStakingInfoMsg` decodes the message and calls `pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos)`.
5. `queue.DeliverStakingInfos` calls `validate(i, header)` which returns `nil` unconditionally, then stores the forged entry in the result cache.
6. `commitFastSyncData` calls `d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))`, persisting the forged staking info.
7. After fast sync completes, `FinalizeState` for any pre-Kaia block reads the forged staking info and calls `state.AddBalance(attackerRewardAddr, inflatedAmount)`, crediting KAIA to the attacker's address instead of the legitimate validators.
8. `GetQualifiedValidators` reads the forged zero-staking entries for legitimate validators and demotes them, causing the node to diverge from the honest chain on validator set computation.

// handleStakingInfoMsg handles staking information response message.
func handleStakingInfoMsg(pm *ProtocolManager, p Peer, msg p2p.Msg) error {
	if pm.chainconfig.Istanbul == nil || pm.chainconfig.Istanbul.ProposerPolicy != uint64(istanbul.WeightedRandom) {
		return errResp(ErrUnsupportedEnginePolicy, "the engine is not istanbul or the policy is not weighted random")
	}

	// A batch of stakingInfos arrived to one of our previous requests
	var stakingInfos []*staking.P2PStakingInfo
	if err := msg.Decode(&stakingInfos); err != nil {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	// Deliver all to the downloader
	if err := pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos); err != nil {
		logger.Debug("Failed to deliver staking information", "err", err)
	}
	return nil
