### Title
Webhook signature verification authenticates the wrong organization, allowing cross-repository writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate a webhook's HMAC signature against using an attacker-influenced field, while the repository that is actually acted upon by the dispatched handler is derived from a different, independently-controlled field in the same JSON payload. This breaks the equality `{organization that authenticated} == {repository that is written}`, mirroring the oracle report's pattern of one governance/administrative binding (which oracle is set) diverging from the value actually relied upon downstream (the oracle read during reward distribution).

### Finding Description
`verify_signature` computes the organization used for signature verification as: [1](#0-0) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This value is fed into `Shipit.github(organization: repository_owner)` to fetch the `GithubApp` instance whose `webhook_secret` is used to verify `X-Hub-Signature`: [2](#0-1) 

The `rescue Shipit::GithubOrganizationUnknown` branch confirms that Shipit supports multiple, independently configured GitHub Apps/organizations, each presumably with its own `webhook_secret`, per `GithubApp#initialize`: [3](#0-2) 
and signature comparison: [4](#0-3) 

Once the signature check passes, the raw `params` (including whatever `repository.full_name` value was sent) is dispatched unmodified to event handlers: [5](#0-4) 

Because `repository_owner` (used purely to pick a validation secret) is computed independently from `repository.full_name`/other repository identifiers that handlers use to locate the target `Stack`/`Repository`, nothing in `verify_signature` ties the two together. An attacker who legitimately administers Organization A's webhook (and therefore knows Organization A's real `webhook_secret`) can:
- Omit `repository.owner.login` so the fallback picks `organization.login = "OrgA"`.
- Set `repository.full_name` (or other repository-identifying fields the specific handler reads) to point at a stack belonging to Organization B, a different tenant configured in the same Shipit instance.
- Sign the raw payload with Organization A's own valid `webhook_secret`.

`verify_signature` will authenticate the request as "coming from Organization A" and let it through, but the handler that runs afterwards (e.g. push/status/check_suite handlers) will act on Organization B's repository/stack because it reads a different, un-cross-checked field of the same payload.

### Impact Explanation
This lets an attacker who controls one legitimately onboarded (but lower-trust) organization forge webhook events that are accepted as authentic and then get applied to a completely different organization's repository/stack that they do not control — a cross-repository write via a spoofed but "validly signed" webhook. Depending on which handler is invoked (e.g., `push`, `status`, `merge_status`, `check_suite`), this can trigger unwanted `GithubSyncJob`s, commit statuses, or affect merge-queue/deploy state for a repository the attacker was never authorized to touch. This matches the "cross-repository writes" / unauthorized deploy-adjacent-state impact category.

### Likelihood Explanation
Requires the attacker to already administer (or have webhook delivery credentials for) at least one organization/repo that is onboarded into the same multi-tenant Shipit deployment — a believable scenario for a shared internal deploy platform serving several teams/orgs, but not a fully unauthenticated attacker. Likelihood is Low, mirroring the original report's own Low likelihood rating, while Impact is High given the trust-boundary break between tenants.

### Recommendation
- Do not use payload-provided fields (`repository.owner.login` / `organization.login`) purely to select a verification secret without also confirming the *same* value/derivation is what handlers use to locate/act on the target resource.
- After verifying the signature, re-derive `repository_owner` used by handlers strictly from the same authenticated organization context, and reject (422) any request where `repository.full_name`'s owner does not match the organization whose secret validated the signature.
- Consider requiring `repository.owner.login` presence and rejecting payloads that must fall back to `organization.login` for security-sensitive events, closing the ambiguity window entirely.

### Proof of Concept
1. Shipit instance is configured with `github_apps` for two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s, both having Stacks tracked.
2. Attacker, an admin of OrgA's webhook configuration, crafts a JSON payload:
```json
{
  "repository": { "full_name": "OrgB/victim-repo", "owner": {} },
  "organization": { "login": "OrgA" },
  "after": "<attacker chosen sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(payload, OrgA_webhook_secret)>` using OrgA's known secret and sends it with `X-Github-Event: push` to `/webhooks`.
4. `repository_owner` resolves to `"OrgA"` (since `repository.owner.login` is absent), `Shipit.github(organization: "OrgA")` succeeds, and `verify_webhook_signature` passes because the signature was legitimately produced with OrgA's secret.
5. `Shipit::Webhooks.for_event('push')` handlers run against `params['repository']['full_name'] == "OrgB/victim-repo"`, causing sync/state changes on OrgB's stack despite OrgB's own webhook secret never being used to authorize the request.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
