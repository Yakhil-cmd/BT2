### Title
Cross-organization team hijack via unvalidated `github_id` lookup in `MembershipHandler` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` looks up `Team` records solely by `github_id`, ignoring the `organization` field carried in the same webhook payload. Because GitHub webhook signature verification only proves the request came from *a* known organization (via `Shipit.github(organization: repository_owner)` and `GitHubApp#verify_webhook_signature`), an attacker who controls a valid webhook for one configured Shipit organization can send a `membership` event naming a `team.id` that belongs to a different organization's `Team` row and get themselves (or any GitHub login) added as a member of that team.

### Finding Description
The broken binding is: `params.organization.login == team.organization` (the org that authenticated the request must equal the org that owns the target team). This is never checked.

Code path:
- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) resolves the GitHub App config purely from `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`) and validates the HMAC signature against that org's `webhook_secret`. This only proves "this request came from organization X's webhook," it proves nothing about the `team` sub-object in the payload. [1](#0-0) 
- `MembershipHandler#find_or_create_team!` does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [2](#0-1) 
The block that sets `team.organization` only runs on **creation**. If a `Team` row with that `github_id` already exists (created earlier for a legitimate different organization), `find_or_create_by!` returns the existing row untouched — no comparison between `params.organization.login` and `team.organization` is ever performed.
- `Team`'s schema enforces uniqueness only on `(organization, slug)`, not on `github_id` alone: [3](#0-2) . So a single `github_id` can legitimately collide across organizations in this table's design (GitHub team IDs are per-org, so this ambiguity is unique to this schema's lack of scoping) and Shipit does not defend against it.
- `MembershipHandler#process` then calls `team.add_member(member)` where `member = User.find_or_create_by_login!(params.member.login)` — an arbitrary GitHub login supplied entirely by the attacker in the payload. [4](#0-3) 

Attack: attacker controls "attacker-org" wired into Shipit's multi-org `github:` config (its webhook produces valid signatures for its own `webhook_secret`). Attacker POSTs `/webhooks` with `X-Github-Event: membership`, `organization.login: "attacker-org"` (so `verify_signature` passes), but `team.id` set to the numeric `github_id` of a `Team` row already persisted for `"victim-org"` (team IDs on public GitHub orgs are enumerable/discoverable), and `member.login` set to the attacker's own GitHub login. `find_or_create_team!` returns the victim's existing `Team` row (organization mismatch never checked), and the attacker's user is appended to `victim-org`'s team's `memberships`.

Existing guards do not catch this: `verify_signature` only checks org-vs-webhook_secret binding, not org-vs-team binding; the `ExplicitParameters` schema (`params do ... end` block) only validates types/presence, not cross-field/tenant consistency; there is no model validation on `Team` or `Membership` enforcing that a membership write for a team is authorized by the org that produced the webhook.

### Impact Explanation
`Team` membership is the basis of `User#authorized?`, which gates access when `Shipit.github_teams` is configured: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` (`app/models/shipit/user.rb:80-82`). If any of the `Shipit.github_teams` entries corresponds to a `Team` whose `github_id` an attacker can guess/enumerate on GitHub, the attacker can grant themselves (or an accomplice account) full Shipit access — an authorization-boundary bypass across organizational tenants. This is repeatable against any `Team` row for any configured organization as long as the attacker knows/can enumerate a `team.id`, and it does not require any privilege in the victim organization. This matches "escalation into `Shipit.github_teams` authorization" (High), and in a deployment where `Shipit.github_teams` gates deploy/merge actions, it can escalate to unauthorized deploys (Critical-adjacent), because membership crosses the repository/organization scope boundary entirely undetected.

### Likelihood Explanation
Requires: (1) multi-org Shipit configuration (documented and supported, `docs/setup.md:182-209`), (2) attacker has a valid webhook-producing channel for at least one configured organization (a precondition granted by the question), (3) attacker can determine/guess a `team.id` (GitHub numeric team IDs) belonging to another configured organization — teams for public orgs are visible via the GitHub API without special privilege. No Shipit secrets, sessions, or API tokens are needed beyond the attacker's own org's webhook capability. The exploit is a single crafted POST and is trivially repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization`, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally reject/raise if a `Team` with that `github_id` already exists under a *different* `organization` (to surface tampering rather than silently creating a duplicate). Add a uniqueness validation/index on `github_id` scoped per organization to make this invariant explicit at the DB layer as well.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership webhook cannot bind a team belonging to a different organization" do
  victim_team = Shipit::Team.create!(
    github_id: 999,
    organization: "victim-org",
    slug: "victim-team",
    name: "Victim Team",
    api_url: "https://api.github.com/teams/999"
  )

  payload = {
    "action" => "added",
    "team" => { "id" => 999, "name" => "Victim Team", "slug" => "victim-team", "url" => "https://api.github.com/teams/999" },
    "organization" => { "login" => "attacker-org" }, # signature verifies for THIS org
    "member" => { "login" => "attacker" }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

  victim_team.reload
  # BEFORE: organization mismatch exists but is not checked; membership still written
  assert_equal "victim-org", victim_team.organization
  assert_not_equal payload["organization"]["login"], victim_team.organization
  assert victim_team.members.exists?(login: "attacker") # crosses tenant boundary — vulnerability confirmed
end
```
Both sides of the binding (`params.organization.login = "attacker-org"` vs `victim_team.organization = "victim-org"`) diverge, and the handler still writes the membership — confirming the vulnerability.
