Based on my investigation, I found a genuine analog of this bug class in the ocore AA state-variable assignment logic.

### Title
State var `||=` concatenation bypasses `MAX_STATE_VAR_VALUE_LENGTH` cap enforced only on plain assignment - (File: formula/evaluation.js)

### Summary
The Elfi bug is a cap check performed on the pre-update value instead of the post-update (current + new) value, letting the final state exceed its configured limit. In ocore's `state_var_assignment` handling, the string length cap `MAX_STATE_VAR_VALUE_LENGTH` is explicitly checked only for the `"="` (direct assignment) operator, but not for the `"||="` (concat) operator, which combines the existing stored value with the new right-hand-side value.

### Finding Description
In `formula/evaluation.js`, the `state_var_assignment` case reads the current stored value via `readVar` and then branches on `assignment_op`: [1](#0-0) 

For `assignment_op === "="`, the code explicitly checks `res.length > constants.MAX_STATE_VAR_VALUE_LENGTH` before storing: [2](#0-1) 

But for `assignment_op === '||='`, the code calls `concat(value, res)` and stores `ret.result` directly with **no check against `MAX_STATE_VAR_VALUE_LENGTH`** for the combined result: [3](#0-2) 

The `concat()` helper function itself only enforces `MAX_AA_STRING_LENGTH` (a much larger general string limit), never `MAX_STATE_VAR_VALUE_LENGTH`: [4](#0-3) 

This is structurally identical to the Elfi bug: a cap is validated against the pre-addition state (or, in the `"="` branch, only against the freshly-supplied value alone) rather than against the actual resulting/combined value that gets persisted when the update operator (`||=`) is used. An AA author can repeatedly issue `var[$key] ||= $chunk;` statements, each individual RHS staying under `MAX_STATE_VAR_VALUE_LENGTH` (or even exceeding it once concatenated), and grow a state var's stored string length without bound up to `MAX_AA_STRING_LENGTH`, which is a much higher ceiling.

Note: the object-var branch (`res instanceof wrappedObject`) does check `json.length > MAX_STATE_VAR_VALUE_LENGTH` before storing, but that check is applied to the new `res` object alone, before it's concatenated into the existing object via `concat()` — again checking the added value, not the resulting combined value that concat() will produce and that will actually be persisted. [5](#0-4) 

### Impact Explanation
State vars whose serialized length exceeds `MAX_STATE_VAR_VALUE_LENGTH` are supposed to be rejected to bound per-key storage size (this limit exists precisely to cap resource usage / DB row size per state var, similar in spirit to a user collateral cap bounding per-user exposure). Bypassing it via chained `||=` lets an AA state var string/array/object grow well past the intended limit (bounded only by the much larger `MAX_AA_STRING_LENGTH`), inflating `aa_addresses.storage_size`/state storage beyond the protocol's designed limits and creating inconsistent capacity assumptions across nodes evaluating the same AA logic (all full nodes, however, would compute the same value deterministically since AA execution is consensus-critical — so this manifests as unbounded state growth / storage bloat rather than fork risk, unless downstream storage_size accounting or serialization assumptions built on `MAX_STATE_VAR_VALUE_LENGTH` are violated elsewhere).

### Likelihood Explanation
Any AA author can trivially write an oscript AA definition with `var[$key] ||= trigger.data.chunk;` in a message case, and any unprivileged unit poster can trigger it repeatedly with successive units, incrementally growing the var each time. No special privileges are required beyond deploying/using a normal AA.

### Recommendation
Add an explicit length check on the **result** of `concat(value, res)` before storing it in the `'||='` branch of `state_var_assignment`, analogous to the check already done for `assignment_op === "="`:
```js
if (assignment_op === '||=') {
    var ret = concat(value, res);
    if (ret.error)
        return setFatalError("state var assignment: " + ret.error, { arr }, false, cb);
    value = ret.result;
    if (typeof value === 'string' && value.length > constants.MAX_STATE_VAR_VALUE_LENGTH)
        return setFatalError("state var value too long after concat: " + value, { arr }, false, cb);
    if (value instanceof wrappedObject) {
        var json = string_utils.getJsonSourceString(value.obj, true);
        if (json.length > constants.MAX_STATE_VAR_VALUE_LENGTH)
            return setFatalError("state var value too long when in json after concat: " + json, { arr }, false, cb);
    }
}
```

### Proof of Concept
```
var stateVars = {}; // 'key' state var initially unset (false)
var formula = `
    var['key'] ||= '${'a'.repeat(constants.MAX_STATE_VAR_VALUE_LENGTH - 1)}';
    var['key'] ||= '${'b'.repeat(constants.MAX_STATE_VAR_VALUE_LENGTH - 1)}';
`;
// Each individual RHS chunk is < MAX_STATE_VAR_VALUE_LENGTH so the '=' check
// path is never triggered; concat() is only checked against MAX_AA_STRING_LENGTH.
// Result: stateVars['key'].value.length grows to ~2*(MAX_STATE_VAR_VALUE_LENGTH-1),
// far exceeding MAX_STATE_VAR_VALUE_LENGTH, and this can be repeated across many
// units/triggers to approach MAX_AA_STRING_LENGTH.
```
This mirrors the existing test pattern for `||=` on state vars (e.g. `concat array in state vars` / `double concat array in state vars`) which confirms `||=` bypasses the `"="`-only length gate: [6](#0-5)
