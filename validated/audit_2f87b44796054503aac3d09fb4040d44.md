### Title
Webhook signature verification authenticates only the sending organization, but `StatusHandler` writes commit statuses globally by SHA with no repository/organization scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` proves only that the inbound `status` webhook was signed with the `webhook_secret` belonging to the GitHub App configured for the organization named in `params.dig('repository','owner','login')`. It never binds that authenticated organization/repository to the record the handler subsequently mutates. `StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the *entire* Shipit installation and writes a CI status onto every matching commit, regardless of which stack/repository it belongs to. This breaks the same trust binding pattern as the referenced Caviar `PrivatePool.flashLoan` bug: a value the signature covers (the *organization*) is disjoint from the value the write actually targets (*any commit with a matching SHA, in any repo/stack*).

### Finding Description
`verify_signature` derives `repository_owner` from the payload and fetches the GitHub App config for that org only: [1](#0-0) 

This only proves "whoever signed this payload controls the webhook secret for organization X." It says nothing about which repository's data may be referenced elsewhere in the same JSON body, because `repository.owner.login` and any other field in the payload are never cross-checked.

The generic `Handler` base class does scope work to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [2](#0-1) 

But `StatusHandler` does not use this scoping at all. Its declared params only require `sha` and `state` (no `repository` block), and `process` resolves the target commits purely by SHA, across all stacks in the database: [3](#0-2) 

`Commit#create_status_from_github!` then writes a `Status` record based on attacker-supplied `state`/`context`/`description`/`target_url`, which downstream feeds directly into deployability checks via `stack.blocking_statuses` / `required_statuses` (delegated on `Commit`): [4](#0-3) 

The security-relevant binding that should hold is:
`organization authenticated by X-Hub-Signature (via repository.owner.login)` == `organization/repository owning the commit whose status is written`

`StatusHandler` never enforces this equality; it substitutes a SHA equality check across the whole database instead. Any operator who legitimately controls a GitHub App/webhook for **their own** organization onboarded into a shared Shipit instance (a supported, documented multi-org configuration — see `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`'s `github: { OrgOne: {...}, OrgTwo: {...} }` schema) can sign a `status` event with their own valid `webhook_secret`, but pick `sha` to match a commit that actually belongs to a *different* organization's stack (e.g., a SHA they can observe from that stack's public timeline/API, or a coincidental/shared base commit). The `verify_signature` check passes (it's genuinely signed with a real webhook secret), yet the effect is written onto a commit belonging to a stack they were never authenticated for.

### Impact Explanation
By forging a `commit_status` update for a commit in a stack that is not "theirs," an attacker can:
- Mark a required/blocking CI status (`ci.require`) as `success` on an arbitrary commit belonging to another organization's stack, making it appear deployable.
- If that stack has continuous deployment enabled, this directly triggers an unauthorized automatic deploy of a commit whose real CI status the attacker fabricated, bypassing the safety gate Shipit's CI-status mechanism is specifically designed to enforce.

This matches the required impact bar: "an unauthorized deploy" resulting from escalation across an authentication boundary (the webhook's org-scoped signature) into control over the state of a resource (another org's commit/stack) that the signature was never meant to authorize.

### Likelihood Explanation
Requires only that the attacker is a legitimate onboarded organization in a shared/multi-tenant Shipit deployment (a supported configuration in this codebase) with their own valid `webhook_secret` — no theft of another org's secret, no `ApiClient` token, and no privileged Shipit account is required. The attacker needs to know a target commit SHA in another stack, which is typically discoverable via the target stack's public activity/timeline pages or GitHub itself. This is a realistic, unprivileged-relative-to-the-target-stack attack path, though it does depend on the operator running multiple organizations behind one Shipit instance.

### Recommendation
In `StatusHandler` (and any other handler that resolves records purely by content-derived keys such as SHA), scope the lookup through the authenticated repository, mirroring the pattern already used by `Handler#stacks` / `repository_name`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
i.e., require and use `repository.full_name` from the payload, and additionally verify that `repository.full_name`'s owner matches the `repository_owner` that was used to select the webhook secret in `verify_signature`, so the authenticated organization and the mutated repository are provably the same entity.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` (attacker-controlled) and `OrgB` (victim), each with its own GitHub App/`webhook_secret`, per the documented multi-org `github:` config schema.
2. `OrgB` has a stack with `ci.require: ["ci/build"]` and continuous deployment enabled; a pending commit with SHA `deadbeef...` currently lacks a passing `ci/build` status.
3. Attacker, using `OrgA`'s legitimate webhook secret, computes a valid `X-Hub-Signature` for the payload:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/build",
  "repository": { "owner": { "login": "OrgA" } }
}
```
4. `POST /webhooks` with header `X-Github-Event: status`. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against `OrgA`'s real secret — request passes.
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")`, matches the commit in `OrgB`'s stack (since the lookup is global, unscoped by organization/repository), and creates a `success` status for `ci/build` on it via `create_status_from_github!`.
6. `OrgB`'s stack now considers that commit deployable and, if continuous deployment is enabled, deploys it — despite the attacker never being authenticated for `OrgB`.
