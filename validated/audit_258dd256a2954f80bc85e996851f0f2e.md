### Title
Cross-organization webhook forgery via decoupled signature-org and target-repository fields enables unauthorized CI status injection to unblock deploys/merges - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-GitHub-App deployments of Shipit (documented in `docs/setup.md` "Using Multiple Github Applications", exemplified by `test/dummy/config/secrets_double_github_app.yml`), each onboarded GitHub organization has its own distinct `webhook_secret`. `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC against using `repository_owner`, read from `params.dig('repository','owner','login')` (or `organization.login`), but this value is never cross-checked against the `repository.full_name` field that downstream `Handler` subclasses actually use to resolve which `Stack`/`Repository`/`Commit` to mutate.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` purely to pick a per-organization `webhook_secret` via `Shipit.github(organization: repository_owner)`, then validates the HMAC over the entire raw POST body: `verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)`. [1](#0-0) [2](#0-1) 

Once verification succeeds, the *entire attacker-crafted JSON body* is dispatched unmodified to event handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 

Handlers resolve the target `Stack`/`Repository` from a *separate* field, `repository.full_name`, which is never compared to the `repository_owner` used for authentication: [4](#0-3) 

`StatusHandler` in particular takes fully attacker-supplied `state`, `description`, `target_url`, `context`, and `created_at` fields and writes them straight into the `Status` table for any commit matching the given `sha`, with no call back to the GitHub API to confirm authenticity: [5](#0-4) [6](#0-5) 

Because the webhook_secret used to authenticate is keyed off `repository.owner.login` while the actual mutation target is looked up via `repository.full_name`, and both fields are attacker-controlled parts of the same raw POST body, an attacker who legitimately controls the GitHub App (and thus knows its `webhook_secret`) registered for **any** one onboarded organization (`Org-A`) can forge a signed webhook whose `repository.owner.login` = `"Org-A"` (to pass signature verification) but whose `repository.full_name` = `"Org-B/victim-repo"` (to target any other tenant's tracked repository). The equality that should hold — `repository_owner == owner segment of repository.full_name` for the given signature's origin — is never enforced.

### Impact Explanation
This breaks the tenant-isolation boundary between separately onboarded GitHub organizations sharing one Shipit instance. The clearest concrete impact is via `StatusHandler`: an attacker can inject a fabricated `"state": "success"` commit status for a target commit belonging to a completely different organization's stack. Because CI/status checks gate the merge queue (`MergeRequest#all_status_checks_passed?` relies on `StatusChecker` reading `Status` rows written this way) and continuous deployment (`Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery`), injecting fake "success" statuses can unblock automatic merges and continuous deploys on a stack the attacker has no legitimate access to — an unauthorized-deploy/merge class impact, achieved purely by controlling a *different* org's GitHub App webhook secret.

### Likelihood Explanation
Requires the deployment to use the documented multi-organization GitHub App configuration (as opposed to the single-app default). Given that configuration, exploitation only requires: (1) legitimate administrative control over one onboarded org's GitHub App (which the attacker configured themselves, hence knows its `webhook_secret`), and (2) crafting a POST to the shared `/webhooks` endpoint with a mismatched `repository.owner.login` vs `repository.full_name`. No GitHub API access or write permission to the victim's repository is needed.

### Recommendation
In `WebhooksController#verify_signature` / `Shipit::Webhooks::Handlers::Handler`, verify that the `repository.owner.login` (or `organization.login`) used to select the webhook secret matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting the request (422) on mismatch.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub App config as in `test/dummy/config/secrets_double_github_app.yml`, onboarding `OrgOne` (attacker-controlled) and `OrgTwo` (victim), each tracking their own stacks with a valid `webhook_secret`.
2. Attacker, knowing `OrgOne`'s `webhook_secret` (they configured that GitHub App themselves), crafts:
```json
{
  "sha": "<victim-commit-sha-pending-deploy>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
3. Compute `X-Hub-Signature` using `OrgOne`'s `webhook_secret` over the raw body, set `X-Github-Event: status`, POST to `/webhooks`.
4. `verify_signature` reads `repository_owner` = `"OrgOne"`, fetches `OrgOne`'s secret, signature matches → 200 OK.
5. `StatusHandler` matches `Commit.where(sha: ...)` against the victim commit (found via `repository.full_name` = `OrgTwo/victim-repo`, unrelated to `OrgOne`) and creates a `Status` row with `state: "success"`, satisfying merge-queue/CI gating for a stack the attacker never had access to.
