### Title
Webhook signature verification is scoped by `organization.login` while stack matching is scoped by `repository.full_name`, allowing cross-organization forgery of `push` events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) used to authenticate a webhook based on `repository_owner`, which falls back to the top-level `organization.login` field when `repository.owner.login` is absent from the JSON body. `PushHandler#process`, however, matches stacks purely by `branch` within the `stacks` scope built from the request body's `repository` data (e.g. `repository.full_name`), with no re-check that the org whose secret verified the signature is the same org that owns the matched repository/stack.

### Finding Description
The claimed binding is: `organization_that_verified_signature == organization_that_owns_mutated_stack`. Tracing the code shows this does not hold.

`repository_owner` is computed as:
```ruby
# app/controllers/shipit/webhooks_controller.rb:59-62
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
An attacker-controlled payload can omit `repository.owner.login` entirely and only include `organization.login`, forcing `repository_owner` to resolve from the attacker-chosen `organization` sub-object rather than from the `repository.full_name` that will actually be used to select stacks.

`verify_signature` then does:
```ruby
# app/controllers/shipit/webhooks_controller.rb:24-30
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
head(422) unless verified
```
`GitHubApp#verify_webhook_signature` short-circuits:
```ruby
# lib/shipit/github_app.rb:76-77
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```
If the resolved `github_app` (for `org-without-secret`) has no `webhook_secret` configured, verification is unconditionally satisfied with **no signature header required at all**.

After that, `#create` re-parses the same raw body and dispatches to handlers:
```ruby
# app/controllers/shipit/webhooks_controller.rb:10-15
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
```
`PushHandler#process` selects stacks by branch only, within a `stacks` scope that is derived independently from the payload's `repository` data (not from `repository_owner`/the org that was authenticated):
```ruby
# app/models/shipit/webhooks/handlers/push_handler.rb:12-17
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
```
There is no code anywhere in this path that re-validates that the repository/stack matched by `stacks` belongs to the same organization (`repository_owner`) whose (absent) secret was used to accept the request. Consequently, an attacker who knows of any configured GitHub App entry in `Shipit.github_apps` lacking a `webhook_secret` can send an unsigned `push` payload naming an arbitrary victim `repository.full_name`/`branch`, and the request will pass `verify_signature` and reach `PushHandler#process`, enqueuing `stack.sync_github` (and thus `GithubSyncJob#perform`) for the victim's stack — using the victim org's own GitHub API credentials to fetch commits, with zero authentication tying the request to that victim org.

None of the existing guards prevent this: `drop_unhandled_event` only checks the event type is handled; `ExplicitParameters` (`PushHandler.params`) only validates presence of `ref`/`after`, not org/repo consistency; there is no `force_github_authentication`/`require_permission!` on this controller (webhooks are inherently server-to-server); and `Stack`/`Repository` validations only constrain format, not cross-referencing which org authenticated the request.

### Impact Explanation
This is a payload-for-one-repository (or rather, one org) mutating another organization's stack/commit state, matching the Critical impact category explicitly listed ("a payload for one repository mutating another's stack, commit, task or team"). The attacker can force `GithubSyncJob#perform` to run `fetch_missing_commits`/`append_commit` against an arbitrary victim stack using the victim's own configured GitHub API credentials, without possessing any secret, session, or API token. This is repeatable against any stack whose branch/repo the attacker knows, as long as at least one configured `Shipit.github_apps` entry lacks a `webhook_secret` (or the attacker can otherwise choose an `organization.login` mapping to such an entry).

### Likelihood Explanation
Exploitability depends on the operator's `Shipit.github_apps` configuration containing at least one organization entry without a `webhook_secret` set — a realistic and known-weak configuration (e.g., a newly onboarded org, a test org, or an app entry created before secrets were rotated in). No GitHub credentials, Shipit session, or API token are required; the attacker only needs network access to `POST /webhooks` and knowledge of the victim's `repository.full_name` and branch name (both public information for any repository on GitHub). This is a cheap, fully repeatable attack per victim stack.

### Recommendation
In `verify_signature`, derive `repository_owner` strictly from `repository.owner.login` (or from `repository.full_name`'s owner segment) rather than falling back to an independently attacker-suppliable `organization.login`. Additionally, in `PushHandler#process` (and other handlers), enforce that the `stacks` scope is restricted to repositories owned by the same `repository_owner`/GitHub App that was used to verify the signature, so the org that authenticated the webhook cryptographically matches the org whose stack is mutated. Also consider rejecting webhooks outright when the resolved `GitHubApp` has no `webhook_secret` configured, rather than treating an absent secret as an automatic pass.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "push event with organization fallback and no webhook_secret can trigger sync on an unrelated victim stack" do
  victim_stack = shipit_stacks(:shipit) # repo_owner: "victim-org", repo_name: "victim-repo", branch: "main"

  Shipit.stubs(:github_apps).returns({
    'org-without-secret' => Shipit::GitHubApp.new('org-without-secret', { app_id: 1, installation_id: 1 })
  })

  payload = {
    organization: { login: 'org-without-secret' },
    repository: { full_name: "#{victim_stack.repo_owner}/#{victim_stack.repo_name}" },
    ref: "refs/heads/#{victim_stack.branch}",
    after: 'deadbeef'
  }.to_json

  assert_enqueued_with(job: Shipit::GithubSyncJob, args: [{ stack_id: victim_stack.id, expected_head_sha: 'deadbeef' }]) do
    post '/webhooks', params: payload,
      headers: { 'X-Github-Event' => 'push', 'Content-Type' => 'application/json' }
      # deliberately no X-Hub-Signature header
  end

  assert_response :ok
end
```
This asserts that despite `organization.login` ("org-without-secret") having no relationship to `victim-org` (the owner of `repository.full_name`), the unsigned request is accepted and `GithubSyncJob` is enqueued for the victim's stack — demonstrating the broken binding between the authenticated org and the mutated stack's org.
