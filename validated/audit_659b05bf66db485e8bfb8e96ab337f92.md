### Title
Webhook signature verification selects the GitHub App/organization by `repository.owner.login`/`organization.login`, but event handlers act on the repository named by `repository.full_name` with no cross-check - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks *which* organization's `webhook_secret` is used to validate the HMAC signature purely from `repository_owner`, i.e. `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1)  Once the signature is accepted, the actual event handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers) resolve the target `Repository`/`Stack` independently, from `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`stacks`. [3](#0-2)  Nothing ties the organization whose secret authenticated the request to the owner segment of `full_name` that is actually written to.

### Finding Description
This is a case of "the organization that authenticated versus the repository that is written" being different bindings on the same payload. Shipit is explicitly designed to be multi-tenant across GitHub organizations, each with its own `github.<org>.webhook_secret` in `config/secrets.yml` (see `config/secrets.development.shopify.yml` and `docs/setup.md`), and `Shipit.github(organization: ...)` looks up the app config for a specific org name. [4](#0-3)  The controller resolves which org's secret to verify against using `repository_owner`, taking either `repository.owner.login` or, if absent, `organization.login`, from the untrusted JSON body itself. [2](#0-1) 

The HMAC check only proves the payload was signed with *some* configured org's secret matching whichever org name is embedded in that same payload - it does not prove that the `repository.full_name` used later by the handlers actually belongs to that org. A caller who legitimately owns the webhook secret for OrgA (a tenant configured on this same Shipit instance) can therefore craft a request where `repository.owner.login`/`organization.login` = "OrgA" (so `verify_signature` uses OrgA's real secret and passes) while `repository.full_name` = "OrgB/victim-repo" (so `PushHandler`/`StatusHandler`/etc. act on OrgB's `Stack`/`Commit` records). `Handler#stacks` and `Repository.from_github_repo_name` simply parse `full_name` as `owner/name` and locate whatever `Repository` row matches, with no re-derivation from, or comparison to, the org that was cryptographically verified. [3](#0-2) 

### Impact Explanation
Once the org-to-secret binding is decoupled from the org-to-acted-repository binding, an attacker who legitimately controls one tenant org's webhook secret on a shared Shipit deployment can forge events for a different tenant's repositories:
- `StatusHandler` writes fabricated commit statuses (`state`, `context`, `target_url`) onto arbitrary `Commit` records of another org's stack via `commit.create_status_from_github!`, which can flip status checks that the merge queue/deploy pipeline relies on. [5](#0-4) 
- `PushHandler` triggers `stack.sync_github(expected_head_sha: params.after)` on another org's stacks, influencing what SHA Shipit believes is at the head of a branch. [6](#0-5) 

This is a cross-repository/cross-organization write achieved without possessing the victim organization's own webhook secret, matching the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (an explicitly supported and documented deployment mode) and requires the attacker to be a legitimate owner/admin of at least one of the tenant orgs so they can sign requests with that org's own real webhook secret. This is a realistic multi-tenant misconfiguration-class issue rather than a purely theoretical one, but it is contingent on this multi-org setup being used, which I could not fully verify is the primary/only supported deployment shape from the indexed files (the single-org `template.rb`/dummy config are more common in the repo).

### Recommendation
After resolving the `Repository`/`Stack` in each handler from `payload.dig('repository', 'full_name')`, verify that the owner segment of `full_name` matches the `repository_owner` (org) whose secret was used to authenticate the request in `WebhooksController#verify_signature`, and reject the webhook (422) if they differ.

### Proof of Concept
Conceptual (not executed, no filesystem/terminal access):
1. Deploy Shipit configured with two orgs, `OrgA` (attacker-controlled) and `OrgB` (victim), each with a distinct `webhook_secret`.
2. Attacker builds a `push` webhook JSON body: `{"organization": {"login": "OrgA"}, "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen-sha>"}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` using their own legitimately-held OrgA secret.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'OrgA')` and the signature validates successfully.
5. `Webhooks.for_event('push')` dispatches to `PushHandler`, whose `repository_name` reads `full_name` = `"OrgB/victim-repo"`, resolving `OrgB`'s `Stack` and invoking `sync_github(expected_head_sha: "<attacker-chosen-sha>")`, affecting a repository the attacker never authenticated for.
