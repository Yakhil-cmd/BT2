### Title
Webhook signature verification is scoped to `repository.owner.login`, but event handlers act on the unvalidated `repository.full_name` field, allowing an attacker with any legitimate GitHub App installation on this Shipit instance to forge events for other tenants' repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App configuration (and therefore the HMAC secret) used to authenticate an inbound webhook based on `repository.owner.login` (falling back to `organization.login`), [1](#0-0) [2](#0-1) . Once the signature validates, `Shipit::Webhooks.for_event` dispatches the *entire raw payload* to handlers, and those handlers resolve the target `Repository`/`Stack` using a *different* field, `repository.full_name`, via `Handler#repository_name`/`#stacks` and multiple pull-request handlers' `#repository` methods [3](#0-2) [4](#0-3) . Nothing checks that `repository.full_name` actually belongs to the org/owner used to select and validate the signing secret.

### Finding Description
`Shipit.github(organization:)` looks up a distinct `GitHubApp` (and its own `webhook_secret`) per configured organization key, supporting multi-tenant deployments where several independent GitHub App installations (and thus independent webhook secrets) are configured under `secrets.github` [5](#0-4) . The dummy config exercising this multi-tenant mode (`OrgOne`/`OrgTwo`) confirms each organization has its own, independently-controlled `webhook_secret` [6](#0-5) [7](#0-6) .

`WebhooksController#verify_signature` builds the `GitHubApp` from `repository_owner`, which is read off `params.dig('repository', 'owner', 'login')`, and uses that app's secret to validate `X-Hub-Signature` against the raw POST body [8](#0-7) . This only proves that whoever crafted the payload knows the webhook secret associated with `repository.owner.login` - it says nothing about `repository.full_name`, which lives in the same JSON body and can be set to any string by whoever controls the sending side of that app's webhook secret (e.g., a tenant/org onboarded onto this same Shipit instance).

After signature verification, `create` simply forwards the parsed JSON to the handlers for the event type [9](#0-8) . The base `Handler` class resolves the affected `Repository`/`Stack` purely from `repository.full_name`:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` (and other handlers) use this to look up stacks and call `stack.sync_github(...)` directly from attacker-controlled `full_name` [10](#0-9) . Pull-request handlers (`OpenedHandler`, `ReopenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`) similarly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then archive/unarchive review stacks or write pull-request labels based on it [11](#0-10) [12](#0-11) .

**The broken equality:** `repository.owner.login` (the identity that authenticated via the signature) ≠ `repository.full_name` (the repository whose Stack is actually written to). In a single-tenant deployment (one GitHub App, one org) this is harmless because there is only one secret and one org to worry about. But on a Shipit instance that hosts multiple organizations/tenants as separate GitHub App configs (exactly the scenario the engine explicitly supports via `github_app_config`), a party that legitimately controls their own org's app installation - and therefore legitimately possesses their own `webhook_secret` - can sign a payload with `repository.owner.login` set to their own org (so `verify_signature` picks their own, legitimately-known secret and passes), while setting `repository.full_name` to a victim tenant's repository. The handler layer will then act on the victim's `Stack`/`Repository` (trigger `sync_github`, archive/unarchive review stacks, mutate labels, etc.) because it never re-derives or cross-checks the owner from `full_name` against the owner used for signature verification.

### Impact Explanation
This breaks the trust boundary between tenants of a multi-org Shipit deployment: an attacker who is a legitimate GitHub App installer/owner for one organization on the instance can trigger unauthorized state changes (`sync_github`, review-stack archive/unarchive, pull-request label capture) against repositories/stacks belonging to a different organization they do not control, without needing that victim organization's secret. This is a cross-repository/cross-tenant write achieved purely by manipulating an unverified payload field, matching the "cross-repository writes" / "unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitability depends entirely on the deployment running Shipit in the multi-organization GitHub App configuration mode (`github_default_organization` non-nil, multiple orgs under `secrets.github`), which is a documented and tested configuration (`test/dummy/config/secrets_double_github_app.yml`) rather than a hypothetical host misconfiguration. Any party who is one of the configured tenants can mount the attack against any other tenant purely by crafting the JSON body; no secret belonging to the victim is required.

### Recommendation
After successfully verifying the signature for `repository_owner`, re-validate that every subsequent lookup of a repository/stack derived from the payload (`repository.full_name`, and the `owner`/`organization` fields used by handlers such as `Handler#repository_name`, `PullRequest::*Handler#repository`) is actually owned by the same `repository_owner` that authenticated the request - e.g., assert `repository.full_name.split('/').first == repository_owner` (case-insensitively) before dispatching to handlers, or derive the app/secret lookup key directly from the same `full_name` used downstream instead of the separate `owner.login`/`organization.login` fields.

### Proof of Concept
1. Attacker legitimately installs/owns a GitHub App configured on the shared Shipit instance as tenant `AttackerOrg`, and therefore knows `AttackerOrg`'s `webhook_secret`.
2. Attacker crafts a `push` (or `pull_request`) webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-controlled sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(AttackerOrg_webhook_secret, body)` and POSTs to `/github_webhooks` (or the mounted webhooks path) with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'AttackerOrg')` (from `repository.owner.login`), verifies successfully against the attacker's own known secret, and lets the request through.
5. `PushHandler#process` resolves `Repository.from_github_repo_name('VictimOrg/victim-repo')` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack - a cross-tenant write triggered without ever knowing `VictimOrg`'s secret.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
