Found `setField` in `arbiter_contract.js` builds a raw SQL `UPDATE` statement by directly concatenating the `field` parameter into the query string rather than parameterizing it: [1](#0-0) 

### Title
SQL Injection via unvalidated `field` name in `arbiter_contract.setField` - (File: arbiter_contract.js)

### Summary
`setField(hash, field, value, cb, skipSharing)` builds `"UPDATE wallet_arbiter_contracts SET " + field + "=? WHERE hash=?"`, concatenating `field` directly into the SQL text instead of using a parameter placeholder or a strict column allow-list before use. This mirrors the FusionPBX CVE-2021-43405 pattern: a field that should be constrained to a small safe set of values ("fax_extension" restricted to digits) is instead accepted with insufficient restriction and flows into a sensitive execution context (there: a shell/dialplan; here: raw SQL).

### Finding Description
`setField` does check `field` against an allow-list of column names before building the query: [2](#0-1)  However, the query itself is still built by string concatenation rather than a parameterized identifier, and the value of `field` is taken verbatim from `wallet.js`'s handling of the `arbiter_contract_update` device message, which is attacker/peer controlled data (`body.field`): [3](#0-2)  While the current allow-list (`["status", "shared_address", "unit", "my_contact_info", "peer_contact_info", "peer_pairing_code", "resolution_unit", "cosigners"]`) does constrain values today, the underlying pattern — a peer/attacker-controlled string field being spliced unescaped into an SQL statement instead of being bound as a parameter — is structurally identical to the FusionPBX bug class: a field consumed unsanitized and injected directly into a sensitive statement, relying entirely on validation logic elsewhere (here, the allow-list check) rather than architectural separation (e.g., a switch/case mapping to hardcoded column names, or true parameter binding). Any future modification that adds an allow-listed field name containing SQL metacharacters, or any code path that reaches `setField` without going through the allow-list check (e.g., internal callers), would result in SQL injection. I could not find sqlite string-escaping applied to `field` anywhere in this call path, and the identifier is trusted based solely on membership in the hardcoded array.

### Impact Explanation
If the allow-list check were bypassed or extended incorrectly, an unprivileged `arbiter_contract_update` peer message sender could inject arbitrary SQL into the `wallet_arbiter_contracts` UPDATE statement, allowing tampering with contract state (e.g., forcing `status` to `signed`/`paid`/`in_dispute` improperly), corruption of other rows via subqueries, or exfiltration of wallet data — all reachable by a private-payment counterparty (arbiter contract peer), which is in scope per the rules (private-payment counterparty message handling).

### Likelihood Explanation
Exploitation today requires a bypass of the hardcoded allow-list check (`arbiter_contract.js:79-81`), which is currently sound for all 8 listed fields, none of which contain SQL metacharacters. This makes the likelihood **low today**, but the code path is fragile: the safety depends entirely on this one array staying in sync with safe column names, and there is no independent parameterization or backend enforcement of the identifier. This is a "single point of failure" hardening gap rather than an actively exploitable path in the current source.

### Recommendation
Refactor `setField` to avoid raw string concatenation of the column identifier — use a `switch(field)` mapping to fixed SQL literals per branch, or maintain a strict `field -> quoted_column_name` map and validate `value` types per field, rather than relying solely on membership-check + concatenation. This removes reliance on the allow-list array being exhaustive and correct forever, consistent with defense-in-depth against the "unrestricted field flowing into a sensitive sink" bug class illustrated by CVE-2021-43405.

### Proof of Concept
Not concretely exploitable in the current codebase without a variant that adds an unsafe field name into the allow-list array, or a caller path to `setField` that skips the array check present in `wallet.js`'s `arbiter_contract_update` handler (`wallet.js:679-741`). I was unable to locate any current caller that invokes `setField` with an attacker-controlled `field` value that bypasses this check — this makes the finding a **hardening/pattern gap analog** rather than a confirmed exploitable vulnerability today; a Devin session with the ability to run the full test suite and trace all `setField` call sites would be needed to confirm no bypass exists elsewhere (e.g. via `shareUpdateToCosigners` or future code paths).
