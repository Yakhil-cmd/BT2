### Title
Stack-scoped ApiClient token bypasses its stack binding in `Api::CCMenuController#stack` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` records can be bound to a single stack via the `stack_id` column, and `Api::BaseController#stacks`/`#stack` is designed to enforce that binding by scoping all lookups to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped. `Api::Ccmenu::Controller` (used for the "CCMenu" build-status XML feed) overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, completely bypassing the scoping helper. This breaks the binding `stack a token authorises == stack it touches`.

### Finding Description
`Api::BaseController` defines the intended enforcement for stack-scoped tokens: [1](#0-0) 

Any controller relying on `stack`/`stacks` from this base is limited to the stack(s) its `current_api_client` is authorized for. However, `Api::CCMenuController` explicitly redefines `stack` to look up any stack by the request parameter, ignoring `current_api_client.stack_id` entirely: [2](#0-1) 

The `require_permission :read, :stack` before_action only checks that the token carries the `read:stack` permission string — it never checks whether the specific `stack_id` param matches the token's bound stack (`ApiClient#check_permissions!` only inspects the `permissions` array, not `stack_id`): [3](#0-2) 

So a token that is nominally scoped to stack A (has `read:stack` and a non-nil `stack_id` pointing at stack A) can be presented against `GET /api/stacks/:owner/:repo/:branch/ccmenu.xml?token=...` for stack B, and the controller will happily render B's build/deploy status. This is exactly analogous to the reported bug class: the authorization state (`stack_id` binding) that should gate the operation is never consulted/updated in the code path that actually executes the action, so the token is used as if it had global scope even though it was minted with a narrower one.

Tokens with a `stack_id` are the normal case for the CCMenu feature itself: `CCMenuUrlController` mints a `read:stack` client via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` without passing a `stack:` scope in this codebase version, but the `ApiClient` model and `Api::BaseController` clearly support (and are built to enforce) per-stack scoping for exactly this permission (`read:stack`), and the UI (`ApiClientsController`) allows an operator to create/update clients whose `stack_id` is set to restrict them to one stack. `Api::CCMenuController` is the only controller under `Api::BaseController` observed to override `#stack` and skip the scoping logic, so any stack-scoped client (however it was provisioned) loses its scope specifically on this endpoint.

### Impact Explanation
This allows an attacker in possession of a legitimately-issued, narrowly-scoped `read:stack` API token (scoped to stack A) to read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, activity, lock state) for any other stack in the Shipit instance, including private/internal repositories the token was never meant to access. This is an unauthenticated-for-that-resource read of stack state (deploy/build status), matching the "High" impact category of unauthorized read of stack state via broken authorization scoping.

### Likelihood Explanation
Low to medium: it requires possession of any valid stack-scoped `read:stack` API client token (a credential that is by design meant to be shared more widely than admin tokens, since CCMenu URLs are typically embedded in CI dashboards, build-status widgets, or intranet pages). No repository write access or privileged account is needed beyond already holding such a token — the vulnerability is purely in the controller not respecting the scope the token was issued with.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reintroduce scoping in it) so it uses the same `stacks.from_param!(params[:stack_id])` logic as `Api::BaseController`, ensuring `current_api_client.stack_id` is honored:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Additionally, ensure `CCMenuUrlController#client` explicitly sets `stack:` on the created `ApiClient` so newly minted CCMenu tokens are properly bound to the stack they're generated for.

### Proof of Concept
1. As a Shipit user, generate a CCMenu URL for `stack-a` via `GET /stack-a/... -> CCMenuUrlController#fetch`, obtaining a token `T` for an `ApiClient` with `permissions: ["read:stack"]` (and, once scoping is fixed to be applied at creation, `stack_id` pointing to `stack-a`).
2. Request `GET /api/other-org/stack-b/ccmenu.xml?token=T`.
3. Observe that `Api::CCMenuController#stack` resolves `stack-b` via `Stack.from_param!` regardless of `T`'s intended stack binding, and the response renders `stack-b`'s deploy/build status — demonstrating the token authorizes access to a stack it was never bound to.
