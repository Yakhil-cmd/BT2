## Analysis

`StatusHandler#process` is decisive here: it looks up commits **globally by SHA alone**, with no scoping to the repository that authenticated the webhook:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Meanwhile signature verification in `WebhooksController` is keyed off `repository_owner`, computed independently from the JSON body:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) [3](#0-2) 

The equality that is *supposed* to hold is: `org whose secret signed the request == org that owns the repository/commit acted upon`. `verify_signature` only proves the first half (the request was signed by *some* configured org's `webhook_secret`). Nothing ties that org to the record being mutated by the handler — `StatusHandler` never checks `payload.dig('repository','full_name')` or `repository_owner` before writing a `Status`. This is the same class of bug as `setTreasuryWeights` in the report: a piece of state (which org's authority is applied) is decoupled from the write it protects.

In this multi-org engine (see `docs/setup.md`'s "Using Multiple GitHub Applications" section and `lib/shipit/github_app.rb#initialize`), any org onboarded with its own `github_app_id`/`webhook_secret` [4](#0-3)  can compute a *valid* signature over an arbitrary JSON body using its own legitimately-known secret, then set `sha` in that body to a SHA belonging to a commit in a completely different, unrelated repository/stack hosted on the same Shipit instance. Because `Commit.where(sha: params.sha)` is unscoped, the forged "status" event is applied to that foreign commit's `Status`. Since deploy/merge gating (`ci.require`, `ci.blocking`, merge-queue `all_status_checks_passed?`) relies on `Status` records [5](#0-4) , an attacker who only controls their own org's webhook secret can inject a fabricated "success" status onto another organization's commit and unblock/trigger a deploy or merge there — a genuine cross-repository, unauthorized-deploy primitive, not merely a config nit.

### Title
Cross-repository status forgery via SHA-only lookup breaks the "authenticated org == written repository" binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` locates commits to update solely by `sha`, without checking that the commit belongs to the repository/organization whose `webhook_secret` produced the incoming signature. `WebhooksController#verify_signature` only proves that the payload was signed by *some* onboarded GitHub organization's secret (chosen via `repository.owner.login`/`organization.login` from the attacker-supplied JSON body); it does not bind that organization to the specific repository the handler subsequently mutates.

### Finding Description
- `verify_signature` selects the verifying `GitHubApp` based on `repository_owner`, a value read straight out of the untrusted JSON payload, and only checks the HMAC against that org's `webhook_secret` [6](#0-5) .
- Once verification passes, `WebhooksController#create` dispatches the parsed body to all registered handlers for the event type with no further authorization [7](#0-6) .
- `StatusHandler#process` performs `Commit.where(sha: params.sha)`, a global, unscoped lookup across every repository/stack tracked by this Shipit instance, and writes a new `Status` on each match [1](#0-0) .
- In a multi-org Shipit deployment (explicitly documented, `docs/setup.md` "Using Multiple GitHub Applications" [4](#0-3) ), each org has its own GitHub App, its own `webhook_secret`, and its own installation — meaning any onboarded org legitimately knows its own secret and can produce a validly-signed webhook delivery for **any JSON body it chooses**, including one whose `sha` field references a commit belonging to a totally different org's repository.
- The binding that should hold — *the org whose secret signed the request must equal the org/repository being written to* — is never checked. Only the org-to-secret binding is checked; the org-to-*written-record* binding is missing entirely for this handler.

### Impact Explanation
Because `Status` rows created via forged webhooks feed directly into deploy/merge-blocking logic (`StatusChecker`, `MergeRequest#all_status_checks_passed?` / `any_status_checks_failed?`) [8](#0-7) , an attacker who administers Org C (with a legitimately configured, distinct GitHub App/secret on the same Shipit instance) can:
1. Craft a `status` webhook payload with `repository.owner.login = "C"` (so signature verification passes using Org C's secret) and `sha` equal to a commit SHA in Org D's repository/stack.
2. Set `state: "success"` for a required CI context.
3. Have Shipit record that fabricated success `Status` against Org D's commit, unblocking or advancing Org D's merge queue / continuous-delivery / deploy gating — an unauthorized deploy or merge across repositories the attacker has no legitimate access to. This matches the Critical impact bucket ("cross-repository writes... unauthorized deploy, rollback, or merge").

### Likelihood Explanation
Medium-to-high in any deployment that onboards more than one GitHub organization (a documented, supported configuration), since exploitation only requires knowledge of one's own legitimately-provisioned webhook secret plus a predictable/known target SHA (visible via GitHub's public commit history or Shipit's own UI/API for that stack). No credential theft, session, or API token is required — only participation as a normal, unprivileged tenant org on the shared instance.

### Recommendation
Scope the commit lookup in `StatusHandler` (and any other handler using a payload-provided identifier without organization/repository context) to the repository indicated by `payload.dig('repository','full_name')`, and cross-check that this repository's owner matches the `repository_owner` that was used to select the verifying `webhook_secret`. Concretely, replace `Commit.where(sha: params.sha)` with a query joined through `stacks: { repository: { owner: repository_owner, name: ... } } }`, mirroring the scoping already used correctly in handlers such as `PullRequest::AssignedHandler#pull_request` [9](#0-8) .

### Proof of Concept
1. Shipit instance configured per `docs/setup.md` "Using Multiple GitHub Applications" with Org C and Org D, each with its own `app_id`/`webhook_secret` [4](#0-3) .
2. Attacker (legitimate admin of Org C's GitHub App) knows Org C's `webhook_secret`.
3. Attacker looks up a real commit SHA on Org D's tracked repository (via GitHub's public API/UI or Shipit's own read-only stack pages).
4. Attacker builds a `status` event JSON body: `{"sha": "<Org D commit sha>", "state": "success", "context": "<required CI context>", "repository": {"owner": {"login": "OrgC"}}}`, computes `X-Hub-Signature` using Org C's known `webhook_secret` over the raw body, and sets `X-Github-Event: status`.
5. POSTs to the shared `/github/webhooks` endpoint. `verify_signature` succeeds (matches Org C's secret) [2](#0-1) .
6. `StatusHandler#process` finds the commit belonging to Org D by SHA (no owner check) and creates a `success` `Status` on it [1](#0-0) , potentially unblocking Org D's merge queue/deploy that requires that context to pass.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      ].join(' '))
    end
