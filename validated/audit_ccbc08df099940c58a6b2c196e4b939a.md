### Title
Unvalidated `creator` account in `initialize_with_permission` allows permanent freezing of creator fees - (File: programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
`initialize_with_permission` records an arbitrary, caller-supplied `creator` pubkey as the pool's permanent `pool_creator` without requiring that address to sign or otherwise prove control of it. This is set once and there is no instruction anywhere in the program to update `pool_creator` afterward.

### Finding Description
In `InitializeWithPermission`, the `creator` account is declared as an `UncheckedAccount` with no `Signer` constraint and no relation to `payer` or to the `permission` PDA's `authority`: [1](#0-0) 

Only `payer` (validated against a `permission` PDA seeded by `payer.key()`) is authorized to invoke the instruction; `creator` is accepted as raw, attacker-controlled input: [2](#0-1) 

The supplied `creator.key()` is then permanently written into `pool_state.pool_creator` with no further verification step, comment, or later opportunity to change it: [3](#0-2) 

This value gates two downstream instructions responsible for paying out accumulated creator swap fees:
- `CollectCreatorFee` requires `creator` to be a `Signer` matching `pool_state.pool_creator`: [4](#0-3) 
- `CollectCreatorFeePermissionless` allows **anyone** to trigger a payout, sending fees into an ATA owned by `pool_state.pool_creator` regardless of whether that address can ever sign: [5](#0-4) [6](#0-5) 

There is no `update_pool_creator` (or similar) instruction in the program to correct `pool_creator` once set — a search across the codebase shows `pool_creator` is only referenced in `pool.rs` (definition/init) and the two collect-fee instructions, never mutated after initialization.

This mirrors the reported bug class: an unprivileged/loosely-privileged caller can bind a critical role (here, `pool_creator`, analogous to "project owner") to an address that never consented and never proved control, with no mechanism to reverse or cancel the assignment.

### Impact Explanation
Because `creator` need not sign and can be set to any 32-byte value (including a PDA of an unrelated program, a burn-style address, or any pubkey with no known private key), the pool initializer can permanently misconfigure `pool_creator`. Since `collect_creator_fee_permissionless` requires no signature from the creator and will happily create an ATA and transfer funds to that unconfigurable address, all `creator_fees_token_0`/`creator_fees_token_1` accrued by the pool for its entire lifetime become irrecoverably locked — the funds land in a token account nobody can ever move, and `collect_creator_fee` (the signer-gated path) can never succeed because no valid signer exists for `pool_creator`. This is a permanent freezing of protocol/creator fee funds tied to the pool, with no remediation path since `pool_creator` is immutable post-initialization.

### Likelihood Explanation
Exploitation requires only that the caller already holds a valid `permission` PDA to invoke `initialize_with_permission` — no additional privilege escalation is needed beyond what's normally required to create a permissioned pool. The `creator` field is entirely attacker/payer-controlled input in the same transaction, so this can be triggered deterministically and atomically at pool-creation time, either accidentally (a client passing a wrong/mistyped address) or maliciously (an attacker deliberately locking future creator fees, e.g. to grief a launch or as a denial-of-value attack against a token project relying on creator-fee income).

### Recommendation
Require `creator` to be a `Signer` in `InitializeWithPermission` (consistent with the permissionless `initialize` instruction, where `creator` is already a `Signer`), or alternatively add an explicit constraint tying `creator` to `payer`/`permission.authority` so it cannot be set to an arbitrary unverified address. Additionally, consider adding an authorized `update_pool_creator` instruction (signed by the current `pool_creator` or an admin) to allow recovery in case a pool is ever left with an unreachable creator address.

### Proof of Concept
1. Attacker (or any account holding a valid `permission` PDA) calls `initialize_with_permission` with `payer` = their own signing key, but sets `creator` = an arbitrary pubkey they do not control (e.g., a random keypair's public key discarded immediately, or a PDA of another program) — no signature for `creator` is required by the accounts struct.
2. `pool_state.initialize(...)` stores this address permanently as `pool_creator`. [3](#0-2) 
3. Over time, swaps accrue `creator_fees_token_0`/`creator_fees_token_1` in `pool_state`.
4. Anyone calls `collect_creator_fee_permissionless`; the instruction succeeds (no signature needed from `creator`), creates ATAs owned by the unreachable `creator` address, and transfers all accrued creator fees into them, permanently locking the funds since no one holds the private key for that address and `pool_creator` can never be updated. [7](#0-6)

```rust
pub fn collect_creator_fee_permissionless(
    ctx: Context<CollectCreatorFeePermissionless>,
) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;
```
