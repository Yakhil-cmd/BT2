### Title
Setting `trade_fee_rate` and `creator_fee_rate` (or `AmmConfig`) to `0` causes `swap_base_input`/`swap_base_output` to revert via division-by-zero in `split_creator_fee` — ([File: programs/cp-swap/src/curve/calculator.rs])

### Summary
When both `trade_fee_rate` and `creator_fee_rate` are `0` for a given `AmmConfig`, any swap that lands on the "creator fee on input" branch triggers a division-by-zero inside `Fees::split_creator_fee`, causing `CurveCalculator::swap_base_input`/`swap_base_output` to return `None`, which propagates to `ErrorCode::ZeroTradingTokens` and reverts the whole swap transaction. This is the same bug class as the reported issue: an admin-configurable fee parameter set to `0` causes a mandatory downstream computation to unconditionally revert, permanently blocking a core user-facing function (buy/sell → here `swap_base_input`/`swap_base_output`).

### Finding Description
`Fees::split_creator_fee` divides by `trade_fee_rate + creator_fee_rate`: [1](#0-0) 

`floor_div` explicitly returns `None` when the denominator is `0`: [2](#0-1) 

`split_creator_fee` is invoked unconditionally inside `CurveCalculator::swap_base_input` (when `is_creator_fee_on_input` is true) and inside `CurveCalculator::swap_base_output` (same input branch): [3](#0-2) [4](#0-3) 

If `trade_fee_rate == 0` and `creator_fee_rate == 0`, the denominator passed to `floor_div` is `0`, so `split_creator_fee` returns `None`, the `?` operator short-circuits, and the enclosing function returns `None`. Both `swap_base_input.rs` and `swap_base_output.rs` convert that `None` directly into a revert: [5](#0-4) [6](#0-5) 

This zero-fee configuration is reachable in two ways, both unprivileged from the swap-execution perspective:
1. At pool/config creation time, `create_amm_config` only asserts `trade_fee_rate + creator_fee_rate < FEE_RATE_DENOMINATOR_VALUE`, which is trivially satisfied when both are `0`: [7](#0-6) 
2. Via `update_amm_config`, the admin can independently set `trade_fee_rate` to `0` (`param = 0`) and `creator_fee_rate` to `0` (`param = 7`), each check only bounding the sum against the denominator, not against being simultaneously zero: [8](#0-7) 

Once such a zero-fee `AmmConfig` exists and a pool uses it with `is_creator_fee_on_input` true for a given trade direction, **every** subsequent swap in that direction by any unprivileged user permanently reverts, exactly mirroring the reported `BondingTax::swapForAsset` revert-on-zero DoS pattern where an admin-settable fee of `0` causes a mandatory nested computation to revert unconditionally.

### Impact Explanation
This causes a full denial of service on `swap_base_input`/`swap_base_output` for any pool whose `AmmConfig` has `trade_fee_rate == 0` and (effective) `creator_fee_rate == 0`, for the trade direction where creator fee is charged on input. No user can swap through that pool/direction until the config is changed, which is a availability/DoS impact on core AMM functionality — a fee-free pool (a legitimate and plausible operator/admin choice, just like setting `buyTax`/`sellTax` to `0` in the original report) becomes permanently unusable for swapping.

### Likelihood Explanation
The precondition (`trade_fee_rate == 0` and `creator_fee_rate == 0`) is a normal, intuitively valid administrative/pool-creation choice (a "no fee" pool), not an edge case requiring adversarial manipulation — matching the original report's framing that "setting fees to 0 is a very valid and intuitive value to set." Once set, the bug triggers deterministically on every relevant swap, with no attacker action required beyond calling the already-permissionless `swap_base_input`/`swap_base_output` instructions.

### Recommendation
In `Fees::split_creator_fee` (and any other divide-by-rate-sum helper), guard against a zero denominator and return `0` (no creator fee to split) instead of `None`/reverting:
```rust
pub fn split_creator_fee(
    total_fee: u128,
    trade_fee_rate: u64,
    creator_fee_rate: u64,
) -> Option<u128> {
    if trade_fee_rate == 0 && creator_fee_rate == 0 {
        return Some(0);
    }
    floor_div(
        total_fee,
        u128::from(creator_fee_rate),
        u128::from(trade_fee_rate + creator_fee_rate),
    )
}
```
Alternatively, disallow `trade_fee_rate == 0 && creator_fee_rate == 0` simultaneously in `create_amm_config`/`update_amm_config` validation.

### Proof of Concept
1. Admin calls `create_amm_config` (or `update_amm_config` with `param = 0` then `param = 7`) to set `trade_fee_rate = 0` and `creator_fee_rate = 0` for a config, and creates/uses a pool with `enable_creator_fee = true` and `creator_fee_on` such that `is_creator_fee_on_input` is `true` for one trade direction (see `pool_state.get_swap_params`/`is_creator_fee_on_input` used in `swap_base_input.rs`/`swap_base_output.rs`, lines 91-98 / 29-36 respectively).
2. Any unprivileged user calls `swap_base_input` (or `swap_base_output`) in that direction.
3. Inside `CurveCalculator::swap_base_input`, `Fees::trading_fee(input_amount, 0)` yields `total_fee = 0`, then `Fees::split_creator_fee(0, 0, 0)` calls `floor_div(0, 0, 0)` which returns `None` because `fee_denominator == 0`.
4. The `?` propagates `None` out of `swap_base_input`, `.ok_or(ErrorCode::ZeroTradingTokens)?` in `swap_base_input.rs` line 120 turns it into a revert, and the transaction fails — permanently, since the config's zero fee rates persist across future swap attempts.
