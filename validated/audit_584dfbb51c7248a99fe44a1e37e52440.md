### Title
Cross-repo forged commit status via `StatusHandler#process` satisfies `MergeRequest#all_status_checks_passed?` and triggers premature merge of another contributor's PR - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` creates a `Status` for every `Shipit::Commit` matching the webhook's `sha`, with no check that the webhook's declared `repository` matches the repository that actually owns that commit/stack. Because signature verification only proves the payload came from *some* GitHub organization known to Shipit, not that the `sha` belongs to that organization's repository, an attacker who can trigger any validly-signed `status` webhook (from their own repo/org) can forge a `success` status on a victim PR's head SHA in a completely different stack, causing `ProcessMergeRequestsJob` to merge that PR before its real CI passes.

### Finding Description
The binding that should hold for every ingested status webhook is:

`payload.dig('repository','full_name') == commit.stack.repository.full_name` (or equivalently, the commit that receives the forged status must belong to the same repository that GitHub signed the webhook for)

`StatusHandler#process` does not enforce this at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

It looks up commits purely by `sha` across the entire `commits` table, spanning every stack/repository tracked by the Shipit instance, and never compares `params.dig('repository', 'full_name')` (or owner) to the matched commit's own repository.

The only gate before this handler runs is `WebhooksController#verify_signature`, which resolves the webhook secret using the *payload's own* `repository.owner.login` field:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
``` [2](#0-1) 

This only proves the request was genuinely signed by GitHub for the organization named in the attacker-controlled payload — it says nothing about whether the `sha` field inside that payload actually corresponds to a commit belonging to that organization/repository. `create_status_from_github!` then unconditionally creates the `Status` record for whichever commit matched the sha:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [3](#0-2) 

From there, `MergeRequest#all_status_checks_passed?` reads the commit's statuses without any repository provenance check:
```ruby
def all_status_checks_passed?
  return false unless head

  StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
end
``` [4](#0-3) 

And `ProcessMergeRequestsJob` merges the PR as soon as this returns true:
```ruby
merge_requests.select(&:pending?).each do |merge_request|
  merge_request.refresh!
  next unless merge_request.all_status_checks_passed?

  begin
    merge_request.merge!
``` [5](#0-4) 

**Exploit flow:**
1. Victim: a legitimate contributor opens a PR on `victim-org/victim-repo` against a Shipit-tracked stack using `merge_requests`/review-stack workflow; its head SHA `S` is queued as pending with real CI still running.
2. Attacker (unprivileged, no Shipit session/token/secrets) owns or has push access to any repository whose organization is configured in Shipit (e.g. their own repo/fork under an org with the GitHub App/webhook installed, or their own separately-registered Shipit org). Because GitHub's Statuses API does not validate that a `sha` belongs to the target repo, the attacker can call `POST /repos/attacker/whatever/statuses/S` with `state: success` on their own repo, referencing the victim's public head SHA `S` (visible from the victim's public PR).
3. GitHub delivers a `status` webhook to Shipit's `/webhooks` endpoint, correctly signed for the attacker's own organization (since GitHub itself computes the signature using that org's real webhook secret).
4. `verify_signature` passes because the signature is valid for `repository_owner = attacker's org`, independent of the `sha` inside the payload.
5. `StatusHandler#process` finds the `Commit` row with `sha == S` (belonging to `victim-repo`'s stack) and calls `create_status_from_github!`, creating a `success` `Status` scoped to the victim's stack.
6. `MergeRequest#all_status_checks_passed?` now returns true for the victim's pending merge request, and `ProcessMergeRequestsJob` merges the victim's PR via `merge_request.merge!`, even though the PR's real CI never finished/passed.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema in `StatusHandler.params`) do not close this gap — they validate the *shape* and *authenticity of the sender*, but never cross-check the payload's declared repository against the repository that actually owns the target commit.

### Impact Explanation
This allows any repository/organization onboarded to a Shipit instance to inject fabricated CI results for commits belonging to a completely different repository/stack, resulting in an unauthorized merge of a pull request that a legitimate contributor (not the attacker) authored, without that PR's real CI having passed. This is a cross-tenant payload mutating another repository's stack/commit state and results in an unauthorized merge — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). It is repeatable against any commit SHA the attacker can learn (trivial for public PRs), and the blast radius spans every stack/commit tracked by the Shipit instance, not just repositories the attacker interacts with directly. [1](#0-0) 

### Likelihood Explanation
The attacker needs: (a) the target commit's SHA, trivially available from any public PR, and (b) the ability to trigger a genuinely GitHub-signed `status` webhook — achievable by pushing/creating a status on any repository under an organization/GitHub App installation that Shipit is configured to trust (their own repo, fork, or an org they legitimately participate in). No Shipit credentials, secrets, or elevated GitHub permissions are required beyond ordinary repo push/status-write access on a repo they control. This is low-cost and fully repeatable against arbitrary target commits/stacks. [6](#0-5) 

### Recommendation
In `StatusHandler#process` (and the equivalent check-run handler), validate that the incoming payload's declared repository (`params.dig('repository','full_name')` / owner) matches the `stack`/`repository` that owns each matched `Commit` before creating a `Status`; discard or ignore statuses whose repository does not match the commit's own stack repository.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
    test "forged status from a different repository merges another contributor's pending PR early" do
      victim_stack = shipit_stacks(:shipit) # e.g. victim-org/victim-repo
      merge_request = shipit_merge_requests(:pending) # legitimate contributor's PR, no real CI success yet
      head_sha = merge_request.head.sha

      refute merge_request.all_status_checks_passed?

      # Attacker's payload: repository field names a completely different repo,
      # but sha matches the victim's PR head commit.
      forged_payload = ActionController::Parameters.new(
        'sha' => head_sha,
        'state' => 'success',
        'context' => 'ci/attacker',
        'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
      )

      Handlers::StatusHandler.new.call(forged_payload)

      merge_request.reload
      assert merge_request.all_status_checks_passed?, "forged cross-repo status incorrectly satisfied gating check"

      # Simulate ProcessMergeRequestsJob picking this up
      Shipit.github.api.stubs(:merge_pull_request).returns(true)
      merge_request.merge!
      assert merge_request.merged?, "victim PR merged despite forged, cross-repo CI status"
    end
  end
end
```
This demonstrates the broken binding: `payload['repository']['full_name'] ('attacker/unrelated-repo') != commit.stack.repository.full_name ('victim-org/victim-repo')`, yet the status is accepted and gates a real merge.
