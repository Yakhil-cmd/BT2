### Title
Unauthenticated `creator` account in `initialize_with_permission` lets an attacker hijack pool-creator fee rights - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`InitializeWithPermission` accepts a `creator` account that is only checked for existence/type, never for signature or binding to the transaction's actual `payer`. That raw, attacker-controlled pubkey is written straight into `PoolState.pool_creator`, which is later trusted by `collect_creator_fee` and `collect_creator_fee_permissionless` as the sole authority entitled to accumulated creator-fee funds.

### Finding Description
In `InitializeWithPermission`, the `creator` field is declared as an `UncheckedAccount` with no `Signer` requirement and no constraint tying it to `payer` or any authenticated party: [1](#0-0) 

The only authorization gate on this instruction is the `permission` PDA, which is derived from `payer.key()` — it says nothing about `creator`: [2](#0-1) 

When the pool is created, this unchecked value is persisted directly as `pool_creator` in `PoolState::initialize`: [3](#0-2) 

Downstream, both fee-collection paths trust `pool_state.pool_creator` as the ultimate identity/authority for all accrued creator fees, without any further linkage back to who actually funded or built the pool: [4](#0-3) [5](#0-4) 

This mirrors the CVE-2026-37235 bug class exactly: an identity field (`xapp_id` there, `creator` here) taken from the caller-supplied payload is trusted as an authorization/routing key without being bound to the actual authenticated sender (the SCTP association there, the transaction `Signer` here). `valid_xapp_id()` only range-checked the value; here Anchor only type-checks that `creator` is *an* account, not that it is *the signer* or matches `payer`.

Because Solana instructions and their account lists are public in the mempool/RPC before finalization, and because `payer` is the only party gated by the whitelist check (the `permission` PDA), any third party can observe a pending or template `initialize_with_permission` transaction and resubmit an equivalent instruction with the same whitelisted `payer`-derived accounts (if `payer`'s permission PDA is reusable — the PDA is per-payer, not single-use), or more directly, any legitimately-permissioned `payer` who is instructed by tooling/UI to pass through a `creator` argument has no cryptographic guarantee it will be honored: nothing in the accounts structure prevents an attacker who controls transaction construction (e.g., a compromised or malicious frontend, or a copy-and-resubmit of an unsigned/partially-signed instruction) from swapping in their own pubkey as `creator` while keeping a legitimate, permissioned `payer` intact, since `creator` requires no signature at all.

### Impact Explanation
`pool_creator` is not cosmetic — it is the exclusive recipient of `creator_fees_token_0`/`creator_fees_token_1` accrued on every swap through `collect_creator_fee` / `collect_creator_fee_permissionless`. Setting `pool_creator` to an attacker-chosen address diverts all future creator-fee revenue of the pool away from the intended project/LP to the attacker indefinitely — a permanent, unauthorized redirection of pool fee revenue (an unauthorized privileged effect / fee-ledger misdirection), reachable from a single `initialize_with_permission` transaction with attacker-chosen `creator` data.

### Likelihood Explanation
Exploitability only requires the ability to influence or resubmit the account list of an `initialize_with_permission` call while a permissioned `payer` co-signs it — a realistic scenario in ecosystems where pool creation is proxied through a frontend, launcher, or shared script where `creator` is passed as a plain argument rather than derived from a signer. No special privilege beyond the ordinary whitelist check is needed, and the flaw is triggerable in a single transaction.

### Recommendation
Require `creator` to either be identical to `payer.key()`, or require `creator` to co-sign the transaction as a `Signer<'info>` (mirroring how the permissionless `Initialize` instruction sets `pool_creator = creator.key()` where `creator` is itself the `Signer`, as seen in `programs/cp-swap/src/instructions/initialize.rs`). This binds the recorded `pool_creator` identity to a cryptographically authenticated party instead of an arbitrary caller-supplied pubkey.

### Proof of Concept
1. A whitelisted `payer` account with a valid `permission` PDA (created via `create_permission_pda`) prepares an `initialize_with_permission` instruction intended to set `creator = payer`.
2. Before the transaction lands (or via a manipulated client/frontend that lets the attacker choose the `creator` account), an attacker substitutes `creator` with their own pubkey, leaving all other required, properly-constrained accounts (`payer`, `amm_config`, `pool_state`, `token_0/1_mint`, vaults, `permission`) unchanged so the transaction still passes all Anchor checks.
3. The pool is initialized with `pool_state.pool_creator = attacker_pubkey`, as set by `programs/cp-swap/src/states/pool.rs:152`.
4. On every subsequent swap, creator fees accumulate in `pool_state.creator_fees_token_0/1`.
5. The attacker calls `collect_creator_fee_permissionless` (no signature from the real project required) and receives all accrued creator fees, as the instruction only checks `creator.key() == pool_state.pool_creator`.
