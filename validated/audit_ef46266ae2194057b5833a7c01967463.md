### Title
Webhook signature validated against `repository.owner.login`'s org secret while the target Stack is selected via the unrelated `repository.full_name` field, allowing cross-tenant `sync_github` forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/push_handler.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to check based on `payload.dig('repository','owner','login')`, while `Handler#stacks` (used by `PushHandler#process`) resolves the target repository/stack from the completely independent `payload.dig('repository','full_name')` field. Because both values are read from the same attacker-supplied JSON body with no cross-validation, an attacker who owns org `X` and knows `X`'s webhook secret can sign a push payload whose `repository.owner.login` is `X` but whose `repository.full_name` names a victim repository `Y/repo`, causing `stack.sync_github(expected_head_sha: params.after)` to run on `Y`'s real Stack with an attacker-chosen `expected_head_sha`.

### Finding Description
The claimed binding is: `signing_org (used to select webhook_secret)` == `target_repository_owner (used to select the Stack that gets mutated)`.

- Signature verification: `Shipit.github(organization: repository_owner)` where `repository_owner` is `params.dig('repository', 'owner', 'login')`, then `github_app.verify_webhook_signature(signature, raw_post)` HMAC-checks the raw body against that org's `webhook_secret`. [1](#0-0) [2](#0-1) 

- Secret configuration is per-organization in multi-org deployments (`test/dummy/config/secrets_double_github_app.yml` shows distinct `webhook_secret` per org key), meaning an org owner only knows their own org's secret. [3](#0-2) 

- Once signature verification passes, `PushHandler#process` resolves the target stacks purely from `payload.dig('repository', 'full_name')` via `Handler#stacks` / `Repository.from_github_repo_name`, a field entirely disjoint from the one used to pick the verification secret. [4](#0-3) [5](#0-4) 

Root cause: the controller authenticates "who signed this body" by trusting `repository.owner.login` out of the body itself, but the handler layer trusts a different attacker-controlled field (`repository.full_name`) to decide which tenant's data gets mutated. No code anywhere asserts `repository.owner.login == full_name.split('/').first`, nor does it bind the verified org to the resolved `Repository`/`Stack`.

Exploit flow: Attacker owns/administers a GitHub App installation for org `X` (a normal, unprivileged setup step available to anyone who can register a GitHub org and install their own GitHub App integration pointed at the target Shipit instance's webhook URL, as documented in `docs/setup.md`). They know `X`'s `webhook_secret`. They POST to `/webhooks` with `X-Github-Event: push`, a body such as:
```json
{"ref":"refs/heads/master","after":"<attacker-chosen-sha>","repository":{"owner":{"login":"X"},"full_name":"Y-owner/victim-repo"}}
```
signed with `sha1=HMAC(webhook_secret_X, raw_body)`. `verify_signature` looks up `Shipit.github(organization: "X")`, verifies successfully (attacker legitimately knows this secret), and lets the request through. `PushHandler#process` then finds `Y-owner/victim-repo`'s real Stack(s) on branch `master` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, which per existing tests enqueues `GithubSyncJob` with that stack's real `stack_id` and the attacker-chosen `expected_head_sha`. [6](#0-5) 

None of the existing guards prevent this: `drop_unhandled_event` only checks the event type exists a handler; `verify_signature` only checks the raw body against a secret keyed by a field the attacker also controls; the `ExplicitParameters` schema in `PushHandler` only requires `ref` and `after` be present, it does not constrain `repository.owner.login`; there is no `force_github_authentication`/`User#authorized?`/team check on this unauthenticated webhook path since webhooks are meant to be verified by signature alone.

### Impact Explanation
This lets an attacker who controls only their own GitHub org/App installation cause a resync request (`GithubSyncJob` with an attacker-chosen `expected_head_sha`) to be enqueued against an arbitrary victim Stack, i.e., a payload authenticated for one repository mutates another repository's stack/state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The blast radius spans any Stack hosted on the Shipit instance, regardless of tenant/org, as long as the attacker can register any GitHub App with a webhook secret and target the shared `/webhooks` endpoint. This is repeatable per request against arbitrary victim repositories by simply changing `full_name`, `ref`, and `after`.

### Likelihood Explanation
Preconditions: a Shipit deployment configured with more than one GitHub organization (multi-org `github:` config, as shown supported by `secrets_double_github_app.yml`) or any setup where the attacker can register/install their own GitHub App pointing at the shared `/webhooks` endpoint and knows only their own org's `webhook_secret`. Attacker cost is low — creating a GitHub org/App and crafting a raw HTTP POST is within the stated unprivileged attacker capability ("any internet user who can send HTTP requests to the Shipit host, including POST /webhooks"). No Shipit session, token, or victim secret is required. The attack is fully repeatable and scriptable.

### Recommendation
Bind the verified organization to the resolved repository/stack: after computing `repository_owner` for signature selection, require that the same value equals the owner segment of `payload.dig('repository','full_name')` (and of `organization.login` if present) before dispatching to handlers; reject the payload (422) on mismatch. Alternatively, resolve the target `Repository` first, verify the signature using the secret belonging to the `Repository`'s known/configured owner (not the payload-supplied owner), and only proceed if they match.

### Proof of Concept
minitest (webhooks_controller or push_handler level):
1. Configure two orgs' secrets (`X` and `victim-org`) as in `secrets_double_github_app.yml`.
2. Create a victim `Stack` for `victim-org/victim-repo` on branch `master` (fixture).
3. Build payload: `{"ref"=>"refs/heads/master","after"=>"attackerchosen0000sha","repository"=>{"owner"=>{"login"=>"X"},"full_name"=>"victim-org/victim-repo"}}`.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', webhook_secret_for_X, payload.to_json)`.
5. POST to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature: signature`.
6. Assert `response` is not `:unprocessable_entity` (signature accepted).
7. Assert `GithubSyncJob` enqueued with `args: [stack_id: victim_stack.id, expected_head_sha: "attackerchosen0000sha"]`, proving the equality `signing_org("X") == target_repository_owner("victim-org")` was never enforced, letting `X`'s credential mutate `victim-org`'s Stack.
