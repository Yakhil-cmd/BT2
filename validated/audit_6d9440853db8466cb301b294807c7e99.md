### Title
RAY value overflow before index ceiling permanently freezes a whale-scale market - (contracts/pool/src/interest.rs)

### Summary
The pool accrues interest by multiplying scaled market totals by their current RAY indexes before enforcing the configured index ceilings. For a sufficiently large 18-decimal market under sustained high utilization, that product can exceed `i128::MAX` while `borrow_index` is still below `MAX_BORROW_INDEX_RAY`, causing `accrue_step` to panic with `MathOverflow` before `last_timestamp` is committed. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Every pool market mutation loads the market through `synced_market`, which unconditionally calls `interest::global_sync` before performing the requested operation. [4](#0-3) 

`global_sync` processes elapsed time in bounded chunks, but each chunk calls `accrue_step`, which first computes `borrowed * borrow_index` and `supplied * supply_index` through `scaled_to_original`. [5](#0-4) [6](#0-5) [7](#0-6) 

The index ceiling is applied only inside `update_borrow_index` after this total-value multiplication, so an oversized scaled book can hit the `i128` value ceiling before the borrow-index ceiling has any opportunity to stop growth. [8](#0-7) [9](#0-8) 

A user can create this state through the unprivileged controller paths `supply` and `borrow`, and any subsequent user can trigger the same state-dependent panic through `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, `recapitalize`, or `update_indexes` for that market. [10](#0-9) [11](#0-10) [12](#0-11) 

The existing regression test demonstrates the concrete cliff: a one-billion-token, 18-decimal market at 98% utilization eventually fails inside the accrual path before reaching `MAX_BORROW_INDEX_RAY`, after which withdrawal and repayment attempts continue to return `MathOverflow`. [13](#0-12) 

### Impact Explanation
Once the market crosses the value-overflow boundary, the panic occurs before `mark_accrued`, so the stale timestamp remains stored and every later market operation repeats the same overflow. [5](#0-4) [14](#0-13) 

This permanently freezes supplier withdrawals and borrower repayments in that market and also prevents liquidation or bad-debt cleanup paths that need to synchronize its pool state, absent a privileged contract upgrade. [15](#0-14) [16](#0-15) [17](#0-16) 

### Likelihood Explanation
The attacker needs an admitted market whose caps and collateral constraints permit a very large position, but the state itself can be built using only `supply` and `borrow`; no privileged entrypoint is required after market listing. [18](#0-17) 

The scenario is capital-intensive and depends on sustained high utilization, but the repository's test proves the boundary is reachable before the intended index ceiling and that the resulting freeze is repeatable rather than a one-time transaction rejection. [19](#0-18) 

### Recommendation
Enforce market share and revenue-share totals against a precomputed `i128::MAX / MAX_*_INDEX_RAY` ceiling at every mint, and calculate accrual totals with a wider type or a saturation-aware path so index capping occurs before an `i128` product can panic. [1](#0-0) [20](#0-19) 

Add release coverage equivalent to `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`, then verify that `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, `recapitalize`, and `update_indexes` remain executable at the configured maximum market size. [13](#0-12) 

### Proof of Concept
The repository test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` supplies `1_000_000_000 * 10^18` base units, borrows 98% of it, advances ledger time until accrual fails, and confirms that the borrow index remains below `MAX_BORROW_INDEX_RAY`. [21](#0-20) 

```text
1. Controller.supply(caller, 0, spoke_id,
     [(hub_asset, 1_000_000_000 * 10^18)])
2. Controller.borrow(caller, account_id,
     [(hub_asset, principal * 98 / 100)], Some(caller))
3. Let interest accrue while utilization remains high.
4. Controller.update_indexes([hub_asset]),
   Controller.repay(...), or Controller.withdraw(...)
5. Pool.global_sync → accrue_step → scaled * index overflows.
```

The test then observes `MathOverflow` from index synchronization, a one-base-unit withdrawal, and a debt repayment, proving that the same committed market state blocks both exits and risk-reducing repayments. [22](#0-21)

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
