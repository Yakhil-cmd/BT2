### Title
Webhook signature verifies only the org's key, not that `repository.full_name` belongs to that org, allowing cross-tenant `ReviewStack` creation - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to check using `repository_owner` (`params.dig('repository','owner','login')`), but nothing ties that authenticated owner to the `repository.full_name` value later trusted by `OpenedHandler`/`ReviewStackAdapter#create!` to select which `Repository`/`ReviewStack` row gets written. An attacker who legitimately controls one org's Shipit webhook secret can therefore sign a payload as their own org while naming a completely different (victim) repository in `repository.full_name`, causing Shipit to create and provision a `ReviewStack` for a repository the attacker's credentials do not belong to.

### Finding Description
The broken binding is:
`repository_owner (params.dig('repository','owner','login'), used to pick the signing key)` **==** `owner encoded in params.repository.full_name (used to select the target Shipit::Repository / ReviewStack scope)`

Trace:
1. `verify_signature` computes `repository_owner` from the top-level `repository.owner.login` field of the JSON body and uses it only to pick which `GitHubApp`/secret to verify with: `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 

2. Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs on the **raw JSON body**, and every pull-request handler independently derives the target repository from `params.repository.full_name` with no re-check against `repository.owner.login`: [3](#0-2) 

3. `Repository.from_github_repo_name` simply splits `owner/name` out of whatever `full_name` string was supplied and looks it up directly: [4](#0-3) 

4. `ReviewStackAdapter#create!` then writes into `scope = repository.review_stacks` (the victim repository resolved above) using attacker-controlled `stack_attributes` (including `branch: params.pull_request.head.ref`) and immediately enqueues provisioning: [5](#0-4) 

Root cause: `repository_owner` is used purely as a **key selector** for the HMAC secret; it is never compared against the owner segment of `repository.full_name` that the handlers actually trust to resolve records. No model validation, `ExplicitParameters` schema, or handler code cross-checks these two independently-attacker-supplied strings within the same JSON body. `ExplicitParameters` only validates types/presence (`requires :full_name, String`), not consistency with `repository.owner.login`. [6](#0-5) 

Exploit: attacker (who owns/administers an org onboarded to Shipit and therefore possesses that org's webhook secret) crafts a `pull_request` "opened" JSON body with `repository.owner.login = "attacker-org"` (so `verify_signature` picks and validates against the attacker's own known secret) but `repository.full_name = "victim-org/victim-repo"`, computes the correct HMAC using their own secret, and POSTs to `/webhooks`. `verify_signature` passes because it only checks the signature against attacker-org's key. `OpenedHandler` then resolves `repository` via `victim-org/victim-repo`, and if that repository has `review_stacks_enabled` and `provisioning_behavior_allow_all`, `ReviewStackAdapter#create!` creates a `ReviewStack` row scoped to the victim repository and enqueues it for provisioning (`Shipit::ReviewStackProvisioningQueue.add(stack)`), causing the state machine's `provision` transition to run against the victim's infrastructure.

Existing guards do not stop this: `verify_signature` authenticates "a request signed by org X" but never authenticates "this request's named repository belongs to org X"; `drop_unhandled_event` only filters by event type; `ExplicitParameters` only enforces shape/types of fields, not cross-field consistency.

### Impact Explanation
A payload authenticated as one tenant (org) causes record creation and a provisioning action against another tenant's repository — exactly the "payload for one repository mutating another's stack" Critical category. The attacker gets an unauthorized `ReviewStack`/`PullRequest` row for the victim repository with attacker-controlled `branch`, and triggers the provisioning state-machine event against a repository outside the attacker's authority. This is repeatable against any repository with `review_stacks_enabled` + `allow_all` (or matching label) as long as the attacker can name it in `full_name`, and is not limited to one repo per attacker org.

### Likelihood Explanation
Requires: (a) the target repository has `review_stacks_enabled` with a provisioning behavior that doesn't require a label check the attacker can't satisfy (`allow_all` trivially qualifies), and (b) the attacker controls a legitimate, distinct webhook secret for some org onboarded into the same Shipit instance (multi-tenant deployment model, as evidenced by support for per-organization GitHub App configs). Given those two preconditions — both plausible in a multi-org Shipit deployment — the attack costs a single crafted HTTP POST with a correctly-computed HMAC using the attacker's own known secret, and is trivially repeatable against any repository name.

### Recommendation
In `Shipit::WebhooksController` or in each webhook handler, after signature verification, assert that the owner segment of `repository.full_name` matches `repository.owner.login` (or resolve the target `Repository` strictly by the authenticated `repository_owner`, not by parsing the attacker-supplied `full_name` string independently). Reject the request (e.g., 422) on mismatch before any handler logic runs.

### Proof of Concept
Add a minitest in `test/controllers/webhooks_controller_test.rb` style (or `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
1. Configure two orgs/`Repository` fixtures: `attacker-org/attacker-repo` (with a known webhook secret A) and `victim-org/victim-repo` (`review_stacks_enabled: true`, `provisioning_behavior: allow_all`).
2. Build a `pull_request` "opened" JSON payload where `repository.owner.login == "attacker-org"` and `repository.full_name == "victim-org/victim-repo"`.
3. Sign the raw body with secret A (attacker-org's known secret) and POST to `/webhooks` with `X-Hub-Signature` and `X-Github-Event: pull_request`.
4. Assert the response is `200`/`204` (signature accepted) and then assert:
   - `stack = Shipit::ReviewStack.find_by(environment: "pr#{number}")`
   - `stack.repository == shipit_repositories(:victim)` (equals the repo named in `repository.full_name`)
   - while the HMAC key actually used to authenticate belonged to `attacker-org`, i.e. `payload["repository"]["owner"]["login"] != stack.repository.owner`.

This demonstrates the equality `repository_owner (signing org) == owner(repository.full_name) (mutated repo's org)` is false, proving the cross-tenant write.
