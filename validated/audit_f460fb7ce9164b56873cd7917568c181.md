### Title
Cross-tenant webhook forgery via mismatched `repository.owner.login` and `repository.full_name` in multi-organization webhook verification - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-GitHub-organization Shipit deployment, `WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), but every event handler that actually mutates state resolves the target repository/stack using the separate `repository.full_name` field from the same JSON body. Because these two fields are never cross-checked, an attacker who controls (or has compromised) the webhook secret for *one* tenant organization configured in Shipit can forge a signed payload whose `repository.owner.login` matches their own org (satisfying signature verification) while `repository.full_name` points at a **different** tenant's repository, causing Shipit to act on that victim repository's stacks.

### Finding Description
`Shipit.github` supports a multi-organization configuration schema (`lib/shipit.rb:170-200`, and documented in `config/secrets.development.example.yml:18-38`), where each GitHub organization has its own `webhook_secret`.

The webhook signature check picks the app/secret to verify against solely from the payload's `repository.owner.login` (falling back to `organization.login`):

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

Once the signature is accepted, the event is dispatched to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (same file, `create` action) [2](#0-1) . Every handler, however, resolves the actual repository/stack to act on using a *different* field, `repository.full_name`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

This same pattern (`params.repository.full_name` used to resolve `Repository`/`Stack`) recurs in `PushHandler` [4](#0-3) , `CheckSuiteHandler` [5](#0-4) , and the pull-request handlers (`opened`, `closed`, `reopened`, `edited`, `label_capturing`, `assigned`) which use `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to locate the repository and its stacks/review-stacks [6](#0-5) [7](#0-6) .

Nothing in `WebhooksController` or `Handler` validates that `repository.owner.login` (the field used to pick the verifying secret) is consistent with `repository.full_name` (the field used to select which tenant's data is mutated). These are independent, attacker-supplied JSON leaves inside the same signed raw body — the HMAC only proves the *body as a whole* was signed by the holder of the secret for the org named in `repository.owner.login`; it proves nothing about which repository that secret's owner is authorized to act on.

**Binding broken:** the organization that authenticated (`repository.owner.login`, used to select the HMAC secret) ≠ the repository that is written (`repository.full_name`, used by every handler to resolve `Stack`/`Repository`).

### Impact Explanation
An attacker who legitimately administers the GitHub App/webhook configuration for one tenant organization onboarded to a multi-org Shipit instance (and thus knows that organization's `webhook_secret`) can forge webhook deliveries that are correctly verified for their own organization but whose `repository.full_name` names an arbitrary other tenant's repository. Depending on event type this enables:

- `PushHandler`: triggers `stack.sync_github(expected_head_sha:)` for the victim's stack via `GithubSyncJob`, which is the mechanism that ingests new commits and, combined with continuous deployment (`app/models/shipit/stack.rb`, `app/jobs/shipit/continuous_delivery_job.rb`), can lead to an **unauthorized deploy** on the victim's stack.
- `CheckSuiteHandler`/`StatusHandler`: forges CI/status state for the victim's commits, which can unblock or mislead continuous-deployment gating and merge-queue logic (`Shipit::MergeRequest#all_status_checks_passed?`), again enabling an unauthorized ship/merge.
- Pull-request handlers: can archive/unarchive or otherwise manipulate review stacks belonging to a victim tenant.

This matches the required "cross-repository writes / unauthorized deploy" impact class for a Critical/High finding.

### Likelihood Explanation
Exploitation requires the attacker to control the webhook secret of *some* organization already configured in the same multi-tenant Shipit instance — a realistic scenario for hosted/shared Shipit deployments serving multiple GitHub orgs, where each org's admins independently manage their own GitHub App/webhook secret but the app instance and database are shared. No access to the victim org's secret, GITHUB_TOKEN, or Shipit session/API token is needed, and the request is a plain unauthenticated HTTP POST to `/webhooks` with a forged JSON body — only knowledge of one's own org's `webhook_secret` is required, which is not a Shipit-privileged credential relative to other tenants.

### Recommendation
Cross-validate the field used for signature-organization selection against the field used for repository resolution before dispatching to handlers: e.g., in `WebhooksController`, derive `repository_owner` from `repository.full_name`'s owner segment (or require `repository.owner.login` to equal the owner segment of `repository.full_name`) and reject the request (422) on mismatch. Alternatively, make every handler's `Handler#repository_name`/`#stacks` resolution consult only data already bound to the verified organization, and reject webhooks whose `full_name` owner does not match the organization the secret belongs to.

### Proof of Concept
1. Shipit is configured with two tenant orgs under `secrets.github`: `orga` (with `webhook_secret: SECRET_A`) and `orgb` (with `webhook_secret: SECRET_B`), each having repositories/stacks registered in Shipit (`Repository.from_github_repo_name`).
2. Attacker is an authorized admin of `orga`'s GitHub App/webhook config and thus knows `SECRET_A`. They have no access to `orgb`'s resources in Shipit.
3. Attacker crafts a `push` event payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orga" },
    "full_name": "orgb/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` as `sha1=HMAC_SHA1(SECRET_A, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner` = `"orga"`, fetches `Shipit.github(organization: "orga")`, and successfully verifies the signature against `SECRET_A` [8](#0-7) .
6. `PushHandler#process` resolves `stacks` via `repository_name` = `payload.dig('repository','full_name')` = `"orgb/victim-repo"` [9](#0-8) , and calls `stack.sync_github(expected_head_sha: params.after)` on `orgb`'s stack — a stack the attacker has no legitimate access to — despite the request having been authenticated only for `orga`.
