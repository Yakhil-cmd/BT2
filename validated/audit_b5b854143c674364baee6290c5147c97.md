Found a concrete analog: a stale-reference/retry race in `network.js`'s pruned-content recovery path, which mirrors the CVE-2017-11176 pattern (retry logic re-using a handle/pointer that should have been invalidated across an intervening close/free), but reachable only by unprivileged unit posters, not by a malicious peer/node — matching the required scope.

### Title
Stale `assocUnitsInWork` / withheld-joint state can be re-armed and replayed twice, allowing double handling of a unit during pruned-content recovery - ([File: network.js])

### Summary
`handleJoint()` uses `assocUnitsInWork[unit]` as a re-entrancy guard while a unit is being validated/handled [1](#0-0) . In the `ifNeedParentUnits` branch that handles spending a locally-pruned final-bad output, the code deletes `assocUnitsInWork[unit]` immediately after persisting the joint to `kvstore` and registering it in `assocUnitsWaitingForPrunedContent`, *before* the recovery/replay path has actually consumed and cleared that state [2](#0-1) .

### Finding Description
This is analogous to the CVE-2017-11176 bug class: retry/queued logic re-uses a reference (`sock`/pointer in the kernel case, `assocUnitsWaitingForPrunedContent[unit]` / the `'wj\n'+unit` KV entry here) without invalidating it before it can be raced by another path that also frees/consumes it, letting the same object be processed twice.

Concretely:
1. An unprivileged sender posts/forwards a unit `U` that spends a locally-pruned final-bad output. `handleJoint` hits `ifNeedParentUnits` with `bRequestPrunedContent=true`, stores the joint under key `'wj\n'+U` in rocksdb, and pushes `{unit: U, expiry_ts}` onto `assocUnitsWaitingForPrunedContent[missing_unit]` for each missing unit [3](#0-2) . It then deletes `assocUnitsInWork[U]`, re-opening the re-entrancy guard [4](#0-3) .
2. Once the missing content is recovered (from any peer, not necessarily malicious), `tryRecoverPrunedContentOfFinalBadUnit` walks `arrWaitingJoints`, reads back `'wj\n'+o.unit` from kvstore, deletes the key, and calls `handleOnlineJoint`/`handleJoint` again for `U` via `async.eachSeries` [5](#0-4) [6](#0-5) .
3. Because `assocUnitsInWork[U]` was already cleared in step 1 (long before the KV entry is actually consumed in step 2), any concurrent re-post of the *same* unit `U` by its original unprivileged author (e.g., re-broadcasting the same unit while recovery is in flight) can re-enter `handleJoint` for `U` a second time and hit the *same* `ifNeedParentUnits`/`bRequestPrunedContent` branch again, overwriting `'wj\n'+U` in rocksdb and re-pushing a *second* entry onto `assocUnitsWaitingForPrunedContent[missing_unit]` for the same `unit: U` before the first entry's stored payload has been read and deleted.
4. When recovery completes, `tryRecoverPrunedContentOfFinalBadUnit`'s `async.eachSeries` iterates `arrWaitingJoints`, which now contains two `{unit: U, ...}` entries. The first iteration reads and deletes `'wj\n'+U` and calls `handleOnlineJoint` for it; the second iteration's `kvstore.get(key, ...)` finds the key already deleted and just no-ops via the `if (!strSavedJoint) return cb();` guard [7](#0-6)  — but only if the timing lines up. If instead a second copy of `U` (or content for a second missing unit that `U` also depends on) is queued before the first is drained, the same unit can be dispatched into `handleOnlineJoint`/`handleJoint` twice for the same underlying joint object once for each `missing_unit` it was waiting on, without `assocUnitsInWork[U]` blocking the second dispatch, since it was cleared prematurely in step 1 and only re-set once actually re-validated.

The root cause mirrors the CVE: the guard/pointer (`assocUnitsInWork[unit]`) is cleared ("set to NULL") too early, before the corresponding retry-queue entry (`assocUnitsWaitingForPrunedContent` / `'wj\n'+unit`) has been fully drained, permitting overlapping re-entry into the same recovery/replay pipeline for one unit.

### Impact Explanation
If the same unit can be dispatched into `handleJoint`/`writer.saveJoint` concurrently through two independent code paths (the direct retry via `requestJoints` and the queued replay via `tryRecoverPrunedContentOfFinalBadUnit`), the mutex around `handleJoint` reduces the risk of double-saving the same unit, but the pre-mutex bookkeeping race in `assocUnitsWaitingForPrunedContent`/`kvstore` can cause duplicate entries, duplicate `kvstore.put`/`del` races, and duplicate `requestJoints` calls, which can lead to redundant/duplicate validation attempts and inconsistent state in `assocUnitsWaitingForPrunedContent` (a unit entry that should have been purged remains referenced, or a unit is replayed against stale joint bytes). In the worst case this creates a path where a unit's spend of a pruned final-bad output is processed more than once, risking inconsistency between nodes on whether that spend is considered valid/serial, i.e., a node-disagreement-on-validity condition.

### Likelihood Explanation
This requires a specific and somewhat narrow race: an unprivileged unit poster must resend the same unit while its pruned-parent content is being recovered, and the timing window between the `assocUnitsInWork[unit]` delete and the `kvstore` drain must overlap with the recovery's `async.eachSeries` replay. It is plausible for an ordinary (non-malicious) sender's client to auto-retry sending the same unit, and no privileged position is required to trigger it, but the practical exploitation into a definite double-spend or fund-loss outcome is not fully demonstrated by static review alone — it relies on precise interleaving of asynchronous callbacks.

### Recommendation
Do not delete `assocUnitsInWork[unit]` in the `bRequestPrunedContent` branch until the corresponding `'wj\n'+unit` entry has actually been consumed by `tryRecoverPrunedContentOfFinalBadUnit`, or de-duplicate entries pushed into `assocUnitsWaitingForPrunedContent[missing_unit]` by unit so the same unit cannot be queued twice. Guard `kvstore.put('wj\n'+unit, ...)` with a check for an existing key so a resend does not silently overwrite in-flight recovery state.

### Proof of Concept
1. Have node `A` receive a unit `U` from an unprivileged sender that spends an output of a locally pruned final-bad unit `P`. `handleJoint` enters the `bRequestPrunedContent` branch, stores `'wj\n'+U`, pushes `{unit:U}` into `assocUnitsWaitingForPrunedContent[P]`, and deletes `assocUnitsInWork[U]` [8](#0-7) .
2. Before `P`'s content is recovered from any peer, resend the identical unit `U` (e.g., simulate the sender's client retry logic). Because `assocUnitsInWork[U]` is no longer set, `handleJoint` re-enters and repeats step 1, pushing a second `{unit:U}` entry into `assocUnitsWaitingForPrunedContent[P]` and overwriting `'wj\n'+U`.
3. Once `P`'s content arrives, `tryRecoverPrunedContentOfFinalBadUnit` iterates the (now duplicated) `arrWaitingJoints` for `P` and dispatches `handleOnlineJoint` for `U` through `async.eachSeries`, exercising the double-entry path described above [9](#0-8) .

**Uncertainty**: I could not fully trace whether the `mutex.lock(['handleJoint'], ...)` inside `handleJoint` fully serializes the two dispatches of `U` to prevent an actual double-save at the `writer.saveJoint` layer — that would require tracing `mutex.js` queueing behavior end-to-end under this specific interleaving, which was not confirmed with certainty from the retrieved code alone.

function tryRecoverPrunedContentOfFinalBadUnit(ws, objJoint){
	const unit = objJoint.unit.unit;
	const arrWaitingJoints = assocUnitsWaitingForPrunedContent[unit];
	if (!arrWaitingJoints)
		return false;
	if (!validation.allHashesAreValid(objJoint)){
		console.log('recovered content for pruned unit ' + unit + ' from ' + ws.peer + ' failed hash check');
		return false;
	}
	archiving.cachePrunedJoint(objJoint);
	breadcrumbs.add('recovered pruned content of final-bad unit ' + unit + ' from ' + ws.peer);
	delete assocUnitsWaitingForPrunedContent[unit];
	// replay the waiting joints in the background, don't make the peer who sent us the recovered content wait for this
	async.eachSeries(arrWaitingJoints, function(o, cb){
		const key = 'wj\n' + o.unit;
		kvstore.get(key, strSavedJoint => {
			kvstore.del(key);
			if (!strSavedJoint) // already replayed via another missing unit it was also waiting on, or expired
				return cb();
			const { objJoint: objWaitingJoint, peer } = JSON.parse(strSavedJoint);
			handleOnlineJoint(peer ? getPeerWebSocket(peer) : null, objWaitingJoint, cb);
		});
	});
	return true;
