### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook's HMAC signature against by reading an attacker-controlled field out of the very payload it is about to verify (`repository.owner.login` / `organization.login`). This is the same "trust binding is established from an uninitialized/unchecked value" pattern as the reported `DepositSecurityModule.sol` bug: a critical authorization decision is derived from data that has not yet been validated to belong to the entity acting on it. In this codebase the analogous binding that breaks is: *the organization whose secret authenticated the request* vs. *the repository/commit that is actually written to*. Every other event handler (`PushHandler`, `CheckSuiteHandler`, `PullRequest::OpenedHandler`) re-establishes that binding by scoping their side effects through `Repository.from_github_repo_name(payload['repository']['full_name'])`, but `StatusHandler` does not — it looks up commits globally by `sha` alone.

### Finding Description
`WebhooksController#verify_signature` picks the signing secret using a field taken straight from the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

Because Shipit is multi-tenant (one instance can track many GitHub organizations, each with its own `webhook_secret` — see `Shipit.github(organization:)`/`lib/shipit/github_app.rb`), any organization legitimately onboarded to the instance can compute a valid HMAC signature for a payload it fully controls, as long as it declares itself (`repository.owner.login`) as the signing organization. The HMAC only proves "this body was signed by whichever org's secret we looked up using a field from this same body" — it does not prove the body's other fields (e.g. the `sha` it targets) actually belong to that org's repositories.

For every event except `status`, this is harmless because the handler re-derives the target repository from the payload and scopes all writes to it: [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler`, however, never uses `stacks`/`repository_name` at all — it resolves the target purely by commit SHA, globally, across the entire instance: [6](#0-5) 

The database only enforces SHA uniqueness per `(sha, stack_id)`, not globally, confirming that the same SHA value can legitimately be attached to commits belonging to different stacks/repositories (e.g., multiple stacks tracking the same underlying repository, forks, or mirrored history): [7](#0-6) 

So the binding that should hold is:
`organization_that_signed_the_webhook == organization_that_owns_the_commit_being_mutated`

Before the attack, this equality is implicitly true for every handler because they all scope through `repository.full_name`. After an attacker's crafted `status` webhook, this equality is broken: organization A signs the request, but `StatusHandler` mutates any commit anywhere on the instance whose SHA matches the attacker-chosen value, irrespective of which stack/organization that commit belongs to.

### Impact Explanation
`Commit#create_status_from_github!` (via `add_status`) updates the commit's status set and can flip a commit from "not deployable" to "deployable": [8](#0-7) 

A forged "success" status on a victim stack's commit can satisfy required-status checks and trigger `stack.schedule_merges`, i.e., it can cause an unauthorized merge/deploy decision to be made on a repository the attacker does not control and never authenticated for — a cross-repository write with unauthorized-deploy/merge consequences, matching the Critical impact bar ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation requires the attacker to control (legitimately, as an org admin) at least one GitHub organization/App already onboarded to the same multi-tenant Shipit instance, and to know or guess a target commit SHA belonging to another tracked stack (SHAs are frequently public — visible in PRs, CI logs, status pages, etc.). No stolen secrets, no privileged Shipit account, and no GitHub write access to the victim repository are needed — only the attacker's own already-configured webhook secret for their own organization.

### Recommendation
`StatusHandler#process` must scope its `Commit` lookup through the same `repository`/`stacks` binding used by every other handler, e.g. restrict to `stacks.commits.where(sha: params.sha)` (via `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) instead of the global `Commit.where(sha: params.sha)`. More broadly, `WebhooksController#verify_signature` should not use an unauthenticated payload field to pick the verification key without re-validating, post-verification, that every other identity-bearing field in the payload (repository, organization) is consistent with the org whose secret validated the signature.

### Proof of Concept
1. Attacker is a legitimate admin of `attacker-org`, which is configured in this Shipit instance with its own `webhook_secret`.
2. Attacker discovers a commit SHA `deadbeef...` that belongs to a stack under `victim-org/victim-repo` (e.g., from a public PR or CI log).
3. Attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<computed with attacker-org's own webhook_secret>

{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "attacker-org")` and successfully verifies the HMAC (attacker knows this secret) — request passes. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` — it finds and updates the commit belonging to `victim-org/victim-repo`, without ever checking that `attacker-org` matches that commit's stack/repository. [6](#0-5) 
6. The forged "success" status can flip `victim-org`'s commit to deployable, triggering `stack.schedule_merges`/continuous delivery on a repository the attacker never authenticated against.
