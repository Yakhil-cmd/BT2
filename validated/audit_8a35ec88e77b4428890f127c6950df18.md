### Title
Cross-organization webhook forgery lets any GitHub-App-owning attacker inject fake commit statuses / sync events for repositories they don't control - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a request against based on `repository.owner.login` (or `organization.login`) read from the **unverified** request body, while the event handlers that actually mutate data (`StatusHandler`, `PushHandler`, etc.) key off a different field — `repository.full_name` (or, for `StatusHandler`, nothing at all). This breaks the binding: `organization that authenticated == repository that is written`.

### Finding Description
`verify_signature` computes the signing org purely from attacker-controlled JSON:

<cite repo="Jortegata/shipit-engine--025" path="app/controllers/shipit/webhooks_controller.rb" start="24-30" end="59-62" />

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
<cite repo="Jortegata/shipit-engine--025" path="app/controllers/shipit/webhooks_controller.rb" start="24="49" end="61" />

Signature verification only proves the payload was signed with the secret belonging to *whatever organization the attacker names in `repository.owner.login`* — not that this org owns the data the handler will subsequently act on. Handlers determine the actual target independently:

- `Handler#repository_name` (base class) reads `payload.dig('repository', 'full_name')`, a field the attacker fully controls and which need not match `repository.owner.login`: <cite repo="Jortegata/shipit-engine--025" path="app/models/shipit/webhooks/handlers/handler.rb" start="32-38" end="32-38" />
- `StatusHandler#process` doesn't even use repository scoping — it looks up commits **globally by SHA** and writes a CI status: <cite repo="Jortegata/shipit-engine--025" path="app/models/shipit/webhooks/handlers/status_handler.rb" start="20-24" end="20-24" />

Since `Shipit.github(organization:)` resolves per-organization `webhook_secret` config <cite repo="Jortegata/shipit-engine--025" path="lib/shipit.rb" start="170-181" end="196-200" />, any actor who legitimately administers *any one* GitHub App organization configured in this Shipit instance (and therefore knows that org's `webhook_secret` from their own GitHub App settings) can:

1. Craft an arbitrary JSON body for the `status` (or `push`) event.
2. Set `repository.owner.login` to *their own* organization so `verify_signature` picks their own known secret and the HMAC check passes.
3. Set the actual target fields (`sha` for `status`, or `repository.full_name`/`ref` for `push`) to reference a **victim** repository/stack they have no access to.
4. POST directly to the public `/webhooks` endpoint (unauthenticated aside from the HMAC).

This is the exact analog of the report's core flaw: a value used for authorization/validation (`repository.owner.login`, driving the signature check) is never actually verified against the value the write operation is keyed on (`repository.full_name` / bare `sha`).

### Impact Explanation
Via `StatusHandler`, the attacker can fabricate a passing (`state: success`) CI status for an arbitrary commit SHA belonging to a victim stack, which feeds directly into `Commit#deployable?` (`success? && !blocked?`) <cite repo="Jortegata/shipit-engine--025" path="app/models/shipit/commit.rb" start="227-229" end="227-229" /> and into `Commit#schedule_continuous_delivery`, which triggers `ContinuousDeliveryJob` for stacks with `continuous_deployment: true` once the forged status makes the commit look deployable <cite repo="Jortegata/shipit-engine--025" path="app/models/shipit/commit.rb" start="281-287" end="281-287" />. It also lets an attacker satisfy `require_ci` gating on manual deploys (`DeploysController#create`) for a commit that never actually passed the victim's real CI. This can result in an unauthorized deploy of a commit — matching the "unauthorized deploy" High-impact category. Via `PushHandler`, the attacker can also trigger `stack.sync_github` for a victim stack using an arbitrary claimed `after` SHA, forging the perceived HEAD of the tracked branch.

### Likelihood Explanation
Requires only that the attacker control/administer any single GitHub organization that has the Shipit GitHub App installed (giving them that org's `webhook_secret` from their own App settings) — not any credential, session, or write access to the victim repository. Given this is an unauthenticated public HTTP endpoint gated solely by this mis-bound HMAC check, likelihood is High in any multi-organization Shipit deployment (the `secrets.yml`/`config/secrets.development.shopify.yml` layout with multiple orgs under `github:` is a supported, documented configuration <cite repo="Jortegata/shipit-engine--025" path="config/secrets.development.shopify.yml" start="1-23" end="1-23" />).

### Recommendation
- In `WebhooksController#verify_signature`, do not let the payload dictate which secret to check against without cross-validating that the resolved organization actually matches the repository being modified.
- In `Handler#repository_name`/`stacks`, and specifically in `StatusHandler#process`, scope the commit/repo lookup to the same organization whose secret validated the signature (`repository_owner`), rejecting events where `repository.owner.login` doesn't match `repository.full_name`'s owner segment.
- Have `StatusHandler` filter `Commit.where(sha: ...)` further by the stack's repository ownership rather than a bare global SHA lookup.

### Proof of Concept
1. Attacker administers `evil-org`, which has legitimately installed the Shipit GitHub App and thus knows `webhook_secret` for `evil-org` (configured under `secrets.github.evil-org.webhook_secret`).
2. Attacker crafts a `status` event payload:
```json
{
  "repository": { "owner": { "login": "evil-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha, publicly known from GitHub>",
  "state": "success",
  "context": "ci/forged"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(evil-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "evil-org")` and the signature validates successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (no repo/org filter) and calls `commit.create_status_from_github!(params)`, writing a fabricated "success" CI status onto the victim's commit, potentially making it `deployable?` and triggering continuous delivery or bypassing `require_ci` on a subsequent manual deploy request.
