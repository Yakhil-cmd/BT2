### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but handlers act on the repository named in the unauthenticated `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/secret to validate the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). [1](#0-0) [2](#0-1)  However, every event handler that actually mutates state (`PushHandler`, the `PullRequest::*` handlers, etc.) resolves the target repository using a *different* JSON field, `repository.full_name`, via `Handler#repository_name`. [3](#0-2)  Nothing in the code enforces that `repository.owner.login` and `repository.full_name` refer to the same repository/organization. Since Shipit officially supports multiple GitHub Apps/organizations, each with its own independently configured `webhook_secret` (some of which are documented as optional and can be left blank), an attacker who can produce a valid signature for *any one* configured organization (including one with no `webhook_secret` configured, in which case `verify_webhook_signature` short-circuits to `true`) [4](#0-3)  can submit a webhook body whose `repository.owner.login` matches that weak/known organization, while `repository.full_name` names a repository belonging to an entirely different, properly-secured organization managed by the same Shipit instance.

### Finding Description
The equality that should hold is: *the organization whose credential authenticated the webhook == the organization/repository the webhook payload is allowed to act on*. The engine breaks this binding:

1. `verify_signature` selects the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) purely from `repository.owner.login` (or `organization.login` if `repository` is absent):
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

2. Once the signature check passes, `create` dispatches the *entire raw payload* to the registered handlers for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [6](#0-5) 

3. All handlers resolve which `Stack`/`Repository` to operate on via `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 
`PushHandler#process`, for example, triggers `stack.sync_github` for whatever stacks match that `full_name`: [8](#0-7) 

Because `repository.owner.login` and `repository.full_name` are two independent fields inside the same attacker-controlled JSON body, and only the former is bound to signature verification, an attacker who can forge/obtain a valid signature for organization A can submit a payload claiming `owner.login: "A"` (satisfying `verify_signature`) but `full_name: "B/some-repo"` (which is what the handler actually acts on), causing state changes against organization B's stacks without ever having B's `webhook_secret`.

This directly mirrors the analog bug class in the report: a verified/authenticated identity (the org whose secret validated the request) is decoupled from the entity actually written/acted upon (the repository resolved from a separate, unverified field) — analogous to `pendingGov` not being invalidated together with `gov` in `__abdicate()`.

### Impact Explanation
This allows an unauthenticated (with respect to organization B) attacker to trigger `GithubSyncJob`/`stack.sync_github` and other webhook-driven mutations (pull request state changes, review-stack archive/unarchive, label capture, etc.) against repositories/stacks belonging to organization B, using only a signature valid for organization A — provided the Shipit deployment manages multiple GitHub organizations (a documented, supported configuration) and at least one of them has a weak or unset `webhook_secret`. This crosses a repository-write trust boundary the app is supposed to enforce per-organization, matching the "cross-repository writes" / "unauthorized deploy" high-impact criteria.

### Likelihood Explanation
Exploitability is conditional: it requires (a) the Shipit instance to be configured with more than one GitHub organization (explicitly documented as supported in `docs/setup.md`), and (b) at least one of those organizations to have a guessable/leaked or unset `webhook_secret` while another is properly secured. In such multi-tenant configurations this is a straightforward, single unauthenticated HTTP POST — no session, API token, or GitHub write access is required to exploit the affected (target) organization.

### Recommendation
Bind signature verification to the same identity that determines the acted-upon repository. Concretely, derive the app/secret used for `verify_webhook_signature` and the repository/stack resolution from the *same* field (e.g., always use `repository.full_name`'s owner segment, or the `Repository` record's stored organization, rather than the independently-supplied `repository.owner.login`), and reject requests where they disagree.

### Proof of Concept
Assume Shipit is configured with two GitHub orgs: `weak-org` (no `webhook_secret` set) and `secure-org` (owns stack `secure-org/prod-app`, tracked branch `master`).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "full_name": "secure-org/prod-app",
    "owner": { "login": "weak-org" }
  }
}
```
- `verify_signature` computes `repository_owner => "weak-org"`, fetches `Shipit.github(organization: "weak-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of any/no `X-Hub-Signature` header. [4](#0-3) 
- `create` then parses the body and calls `PushHandler`, which resolves `repository_name => "secure-org/prod-app"` and triggers `sync_github` for that stack, even though the request was never signed by `secure-org`'s webhook secret. [8](#0-7)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
