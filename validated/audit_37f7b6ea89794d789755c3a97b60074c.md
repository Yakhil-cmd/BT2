### Title
Unvalidated P2P Staking Info Delivery Allows Reward Address Poisoning During Fast-Sync — (`datasync/downloader/queue.go`)

### Summary

`queue.DeliverStakingInfos` contains a deliberately stubbed-out `validate` function that unconditionally returns `nil`, accepting any peer-supplied `P2PStakingInfo` content without verifying it against the block header. This is in direct contrast to `DeliverBodies` and `DeliverReceipts`, which both cryptographically bind delivered data to the header hash. A malicious P2P peer can inject arbitrary `KEFAddr`, `KIFAddr`, and `CouncilRewardAddrs` into the syncing node's result cache, which are then committed to the database and used for reward distribution.

### Finding Description

In `datasync/downloader/queue.go`, the `DeliverStakingInfos` function defines its `validate` callback as a no-op:

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
``` [1](#0-0) 

The `reconstruct` callback then stores the unvalidated peer data directly into the `fetchResult`:

```go
reconstruct := func(index int, result *fetchResult) {
    result.StakingInfo = stakingInfoList[index]
    result.SetStakingInfoDone()
}
``` [2](#0-1) 

Compare this to `DeliverBodies`, which validates the transaction root against `header.TxHash`: [3](#0-2) 

And `DeliverReceipts`, which validates the receipt root against `header.ReceiptHash`: [4](#0-3) 

Both of those bind delivered data to the committed header hash. `DeliverStakingInfos` has no such binding. The `P2PStakingInfo` struct carries `KEFAddr`, `KIFAddr`, and `CouncilRewardAddrs` — all addresses that govern block reward distribution: [5](#0-4) 

The `fetchResult.StakingInfo` field is the direct container for this poisoned data: [6](#0-5) 

Staking info tasks are only scheduled for pre-Kaia-fork blocks at `stakingUpdateInterval` boundaries: [7](#0-6) 

Once `commitFastSyncData` writes the completed `fetchResult` to the database, the poisoned staking info becomes the canonical source for reward distribution for those block numbers.

### Impact Explanation

An attacker controlling a P2P peer can redirect block rewards — including `KEFAddr` (ecosystem fund), `KIFAddr` (infrastructure fund), and all validator `CouncilRewardAddrs` — to attacker-controlled addresses for any pre-Kaia-fork block at a staking update interval boundary. This satisfies the **unauthorized reward distribution** impact gate. The poisoned data is durably committed to the DB and used by `PostInsertBlock` → `GetStakingInfo` for all subsequent reward calculations referencing those block numbers. [8](#0-7) 

### Likelihood Explanation

- The attacker only needs to be a connected P2P peer to a node performing fast-sync (no special privileges required).
- The TODO comment confirms this is a known gap, not an intentional design choice.
- The attack window is any fast-sync session on a pre-Kaia-fork chain segment.

### Recommendation

Implement content validation in `DeliverStakingInfos` analogous to `DeliverReceipts`. The staking info must be cryptographically bound to the block header — for example, by hashing the RLP-encoded `P2PStakingInfo` and committing that hash into the block header (or an auxiliary commitment structure), then verifying the delivered data matches that commitment before calling `reconstruct`.

### Proof of Concept

1. Connect a malicious peer to a fast-syncing node.
2. When the node sends a `GetStakingInfosMsg` for a block at a `stakingUpdateInterval` boundary, respond with a `P2PStakingInfo` whose `BlockNum` matches the requested block but whose `CouncilRewardAddrs`, `KEFAddr`, and `KIFAddr` are attacker-controlled addresses.
3. `DeliverStakingInfos` calls `validate(i, header)` → returns `nil` unconditionally.
4. `reconstruct` stores the poisoned info into `fetchResult.StakingInfo`.
5. `commitFastSyncData` writes it to the DB.
6. All subsequent reward distributions for that staking epoch use the attacker's addresses.
