### Title
Missing critical-section locking when concurrently validating private payment chains allows double-spend of a private asset output - (File: `network.js`, `private_payment.js`, `indivisible_asset.js`, `divisible_asset.js`)

### Summary
The Linux CVE fixes a bug where `ath11k` accessed a shared per-pdev object via `ath11k_mac_get_ar_by_pdev_id()` without holding the RCU read-side lock that protects it against concurrent mutation/free, opening a use-after-free window. The analogous bug class in `ocore` is a check‑then‑act race: private‑payment counterparties' chains are validated and their referenced source outputs are marked spent *without* any lock serializing access to the shared `outputs`/`inputs` rows, even though the codebase elsewhere (in `validation.js`) explicitly introduces a dedicated `"private_write"` mutex to protect exactly this kind of shared mutable state for private assets.

### Finding Description
`network.js`'s `handleSavedPrivatePayments` explicitly validates multiple pending private-payment chains **in parallel**, with the comment "handle different chains in parallel": [1](#0-0) [2](#0-1) 

Each row is passed independently to `privatePayment.validateAndSavePrivatePaymentChain`, which opens its own DB connection/transaction, checks for a duplicate output, and if not found, dispatches to `indivisibleAsset.validateAndSavePrivatePaymentChain` or `divisibleAsset.validateAndSavePrivatePaymentChain`: [3](#0-2) 

Inside `indivisible_asset.js`'s `validatePrivatePayment`, the correctness of a transfer input relies on `validateSpendProof` (checking `spend_proofs` table) and, for full nodes, `graph.determineIfIncluded` — neither of which locks the referenced source output against a concurrently-running validation of a second, conflicting chain that spends the same source output: [4](#0-3) 

The actual state mutation — marking the spent source output — happens later in `validateAndSavePrivatePaymentChain`, in a completely separate connection/transaction from any other concurrently-running chain: [5](#0-4) 

Critically, the codebase already recognizes that private-asset spend bookkeeping needs an explicit lock to avoid races: the consensus (`validation.js`) doublespend-acceptance code path for private assets explicitly acquires a dedicated `["private_write"]` mutex before mutating the `is_unique`/spend state of conflicting inputs: [6](#0-5) 

However, the parallel `handleSavedPrivatePayments` / `handleOnlinePrivatePayment` path that processes privately-shared payment chains received from wallet counterparties (or a hub) does **not** acquire this `"private_write"` lock, or any per-output lock, around its own check-then-act sequence (duplicate check → spend-proof/inclusion check → mark-spent). This is architecturally the same root cause as the kernel CVE: a shared resource (`outputs.is_spent`, `inputs` uniqueness) is read and later written by independently-scheduled concurrent execution contexts without the critical section that the rest of the codebase (`validation.js`) demonstrates is required for the same class of data.

### Impact Explanation
Two private-payment chains sent by (or on behalf of) counterparties/cosigners that both claim to spend the same private source output can be processed concurrently by `async.each` in `handleSavedPrivatePayments` (or via simultaneously arriving `handleOnlinePrivatePayment` calls), each in its own DB transaction. Because there is no lock serializing the "check spend_proof / determine included → mark output spent" sequence across chains referencing the same source output, both transactions can pass their independent checks before either commits, resulting in the wallet accepting and recording two independent spends against a single private (divisible or indivisible) asset output — i.e., a double-spend of a private-payment output that the wallet believes is confirmed/valid. This directly matches the "double-spend of a stable output" impact class called out as in-scope.

### Likelihood Explanation
The trigger requires only that a private-payment counterparty (or a malicious/duplicated hub forward, which explicitly happens per `handlePrivatePaymentChains`'s dedup cache) deliver two conflicting private-payment chains referencing the same source output in close succession so that `handleSavedPrivatePayments`'s `async.each` (or two concurrent `handleOnlinePrivatePayment` invocations) processes them before either commits. This does not require any node/hub/peer compromise — it is reachable purely by a private-payment counterparty crafting/sending payloads, matching the allowed threat model (private-payment counterparty). The race window is bounded by asynchronous DB round-trips (`SELECT` duplicate/spend-proof checks then later `UPDATE`/`INSERT`), which are non-trivial but realistically winnable, especially under DB load or with an attacker who can control message timing.

### Recommendation
Serialize private-payment-chain validation and spend-state updates the same way the consensus path already does for private assets: acquire the existing `mutex.lock(["private_write"])` (or a per-source-output/per-asset key) around the full check-then-act sequence in `private_payment.js`'s `validateAndSavePrivatePaymentChain`, in `indivisible_asset.js`'s `validatePrivatePayment`/`validateAndSavePrivatePaymentChain`, and in `divisible_asset.js`'s `validateAndSaveDivisiblePrivatePayment`, before the `is_spent` state is queried and updated. Alternatively, process `handleSavedPrivatePayments` rows serially (`async.eachSeries`) instead of in parallel when they reference overlapping source outputs, or add a DB-level uniqueness/locking constraint that atomically enforces single-spend of `(unit, message_index, output_index)` across concurrent transactions.

### Proof of Concept
1. A wallet is set up as the recipient of a private (indivisible or divisible) asset payment chain that spends source output `O`.
2. An attacker (or malicious cosigner/counterparty) crafts two distinct private-payment chains, `chain_A` and `chain_B`, that both claim to spend the same source output `O` to different destination addresses, and delivers both to the victim wallet in quick succession (e.g., via `light/private_payment` device messages or direct `handleOnlinePrivatePayment` submissions).
3. `network.js`'s `handleSavedPrivatePayments` (or two near-simultaneous `handleOnlinePrivatePayment` calls) begins validating `chain_A` and `chain_B` concurrently, each opening its own DB connection/transaction and independently checking `spend_proofs`/inclusion for `O` — both checks pass because neither transaction has yet committed the spend of `O`.
4. Both `validateAndSavePrivatePaymentChain` calls commit, each recording an independent spend of `O`, resulting in the wallet accepting two conflicting spends of the same private output — a successful double-spend of the private asset from the victim's perspective.

Note: I was not able to execute this scenario in a live environment; the analysis is based on static code review of the locking/mutex patterns described above. A background Devin session with test-harness access would be needed to empirically confirm the race window size and reproduce the double acceptance.
