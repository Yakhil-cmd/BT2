### Title
Unsalted single-round SHA-256 used as the sole spending authenticator in the `hash` address-definition op enables offline brute-force forgery of shared/hash-locked addresses - (File: definition.js)

### Summary
`ocore` supports an address-definition opcode `["hash", {algo:"sha256", hash:"base64"}]` whose sole security property is that a spender must reveal a preimage matching a stored SHA-256 digest [1](#0-0) . Authorization at spend time compares the raw, single-round, unsalted `sha256` of the caller-supplied authentifier string to this stored digest [2](#0-1) . Exactly like the WeGIA report (fast, general-purpose hash with no salt, no iteration count) this construction is vulnerable to offline dictionary/rainbow-table attacks against low-entropy secrets, letting an attacker who observes the digest recover the secret and forge the authorization needed to spend funds from that address before the legitimate owner does.

### Finding Description
The `hash` opcode is a first-class address/authentication primitive, alongside `sig` and `address`, usable in ordinary payment addresses and shared addresses (`wallet_defined_by_addresses.js`) [3](#0-2) . Definition validation only checks that the stored value is a valid base64 SHA-256-length string; it enforces no minimum secret entropy and no use of a salt or slow KDF [1](#0-0) .

At spend-authorization time, `validateAuthentifiers` recomputes `sha256(assocAuthentifiers[path])` with a single unsalted round and compares it byte-for-byte to the digest embedded in the definition: [2](#0-1) 

Because:
1. The definition (and therefore the target digest) becomes public the first time it is used/referenced in a unit (or can be recovered from `readDefinitionByAddress`/witness proofs, `witness_proof.js`), and
2. SHA-256 is a fast, general-purpose digest with no salt or work factor,

any observer of a `hash`-defined address that protects a human-memorable or otherwise low-entropy secret can run an offline brute-force/rainbow-table attack against the exposed digest to recover the secret, entirely outside the protocol's validation path. This mirrors the WeGIA root cause precisely: authentication material is hashed with a fast, unsalted, general-purpose algorithm instead of a slow, salted password-hashing function, so a single digest leak lets an attacker precompute or brute-force the secret and impersonate the legitimate authenticator.

### Impact Explanation
If an attacker recovers the secret before or concurrently with the legitimate owner, they can submit a spending unit supplying the recovered preimage as the `hash` authentifier and race the legitimate spend, resulting in **unauthorized spending of funds** secured by such a hash-locked definition (e.g., shared addresses, cross-device or atomic-swap style commitments that use the `hash` opcode). This satisfies the "concrete unauthorized spending" bar because control of funds is transferred to whoever first supplies the valid preimage, and the preimage's secrecy is only as strong as the unsalted SHA-256 digest's resistance to offline search.

### Likelihood Explanation
Exploitability depends on the entropy of the secret chosen by whichever wallet/application composes the `hash`-locked definition; `ocore` itself does not enforce or generate a high-entropy secret for this opcode, and does not prevent reuse or premature exposure of the digest. Any deployment (wallet UI, exchange integration, cross-chain swap tool) that lets a user pick or reuses a lower-entropy value for this authenticator is directly exposed once the definition is observed on-chain. This is a realistic misuse-enabling weak-by-design primitive rather than a purely theoretical issue, comparable in class/severity to the WeGIA CVE (Medium, AC:High because it requires a low/moderate-entropy secret and pre-image search).

### Recommendation
- Deprecate or restrict the `hash` opcode to only permit high-entropy (e.g., ≥128-bit random) secrets generated by the wallet itself, never user-chosen values.
- Consider hardening the comparison, e.g., require a salted digest (`algo` extended to include a per-address salt component derived from the address/definition) so the same secret does not always produce the same public digest across contexts.
- Document that revealing/reusing a `hash`-defined address's definition exposes the digest to unlimited offline attack, and that using the primitive for anything other than high-entropy machine-generated secrets is unsafe.

### Proof of Concept
1. Wallet software (or a user) creates a shared/cross-chain address with definition `["hash", {"hash": sha256("swap-secret-123").toString("base64")}]`.
2. The address is funded, and the definition is later published/referenced on the DAG (e.g., as part of the first spend attempt, or shared via `wallet_defined_by_addresses.js`'s `handleNewSharedAddress`) [4](#0-3) .
3. An attacker who observes the digest performs an offline brute-force/dictionary search against common secret formats (fast because SHA-256 is unsalted and single-round) and recovers `"swap-secret-123"`.
4. The attacker submits a unit whose author signs/authenticates using authentifier `{"r": "swap-secret-123"}` at the `hash` path; `validateAuthentifiers`'s `case 'hash'` accepts it because `sha256("swap-secret-123") === args.hash` [5](#0-4) , allowing the attacker to spend the funds before the legitimate party.
