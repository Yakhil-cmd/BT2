### Title
Membership webhook `organization.login` is decoupled from the signature-verification identity (`repository.owner.login`), allowing team/authorization forgery when any onboarded org has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` is used to authenticate an incoming webhook by reading `repository.owner.login` (or `organization.login`) straight out of the unauthenticated JSON body. `Shipit::Webhooks::Handlers::MembershipHandler`, however, resolves and writes to a `Team` using a completely independent JSON field, `params.organization.login`. Because `GitHubApp#verify_webhook_signature` trivially returns `true` when an organization has no configured `webhook_secret` (an explicitly documented, optional setting), an attacker can pick whichever configured org lacks a secret to satisfy signature verification while forging a `membership` payload that creates/updates a `Team` for a *different* organization and adds an arbitrary GitHub login as its member — directly manipulating the data that gates `User#authorized?` and thus the whole app's authentication boundary.

### Finding Description
`repository_owner` (used to choose the verification secret) is computed purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally passes when the selected organization has no `webhook_secret` configured: [3](#0-2) 

The webhook secret is explicitly documented as optional per-organization, and multi-organization installs are a first-class, documented feature (each org gets its own independent secret): [4](#0-3) 

`MembershipHandler` never re-derives or cross-checks the organization used for verification. It trusts a *different* payload field (`params.organization.login`) to find-or-create a `Team`, and trusts attacker-supplied `member.login` to add that user to it: [5](#0-4) 

`Team.find_or_create_by!` sets `name`, `slug`, `api_url`, and `github_id` straight from the attacker-controlled `params.team` object with no callback to the GitHub API to validate the team exists or that its members/org are genuine: [6](#0-5) 

That `Team`'s `organization/slug` (i.e., its `handle`) is exactly what `Shipit.github_teams` uses to gate authorization, and `User#authorized?` checks membership in those teams: [7](#0-6) [8](#0-7) 

**The broken binding**: the organization whose `webhook_secret` authenticated the request (`repository.owner.login`, selected in `verify_signature`) is never required to equal the organization the `MembershipHandler` actually writes team-membership data for (`organization.login`). An attacker only needs one onboarded org (possibly the only org, since the secret is optional) to have no `webhook_secret`, and can then freely set `organization.login` to any org/team handle that is present in `Shipit.github_teams`, injecting themselves (any real GitHub login they control) as a member of an authorization-gating team — with no GitHub API round-trip to validate the forged claim.

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization (an explicitly in-scope High-impact category): an unprivileged internet attacker who merely knows/guesses that one org onboarded to the Shipit instance has no `webhook_secret` set (a state the engine's own docs present as a normal, optional configuration, not a misuse of the engine) can add their own GitHub account to a `Team` record whose `handle` matches a `Shipit.github_teams` entry. Combined with a normal self-service GitHub OAuth login (any GitHub user can authenticate to Shipit), this grants them `authorized?` status and full access to the Shipit UI/API for every stack on the instance — not just the org whose secret was missing.

### Likelihood Explanation
Requires no privileged credentials, no `ApiClient` token, no knowledge of any real `webhook_secret`, no repository write access, and no social engineering — only that some org configured in `secrets.yml` has `webhook_secret` left blank, which the setup docs present as optional (`docs/setup.md` line 30) and which the shipped sample config demonstrates as a valid state (`config/secrets.development.shopify.yml`). This is a plausible, even common, real-world configuration, especially for single-org or lower-priority multi-tenant installs.

### Recommendation
- In `MembershipHandler` (and any other handler that trusts an `organization`/`repository` field distinct from the field used for signature verification), require that the field used to select/verify the webhook secret is the *same* field used to determine which `Team`/organization is mutated, and reject the event otherwise.
- Do not allow `Team` records to be created or have membership silently mutated purely from unauthenticated webhook payload content; validate the team/organization against the GitHub API (as `Team.find_team_on_github` already does) before trusting membership changes, or require a valid signed webhook secret specifically scoped to that organization.
- Consider making `webhook_secret` mandatory (fail closed) rather than optional, at least whenever more than one organization is configured, or whenever `Shipit.github_teams` is non-empty.

### Proof of Concept
Assume org `low-trust-org` is configured under `secrets.github` with `webhook_secret: nil` (a documented/valid config), and `Shipit.github_teams` contains `victim-org/admins`.

```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": 999999, "name": "Admins", "slug": "admins", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-real-github-login" },
  "repository": { "owner": { "login": "low-trust-org" } }
}
```

1. `verify_signature` selects `Shipit.github(organization: "low-trust-org")`; since that org has no `webhook_secret`, `verify_webhook_signature` returns `true` with no signature header required. [1](#0-0) 
2. `MembershipHandler#process` runs, creating `Team(organization: "victim-org", slug: "admins", github_id: 999999)` and adding `User.find_or_create_by_login!("attacker-real-github-login")` as a member. [9](#0-8) 
3. The attacker logs into Shipit via normal GitHub OAuth as `attacker-real-github-login`; `User#authorized?` now returns `true` because they belong to a `Team` whose handle matches `victim-org/admins` in `Shipit.github_teams`. [7](#0-6) 
4. The attacker is granted full, unrestricted access to the Shipit application (deploys, rollbacks, stacks) for every organization served by the instance.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
