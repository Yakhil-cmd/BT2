### Title
Block-scoped `index-cache-` in market.clar lets one user's transaction permanently lock a stale/attacker-influenced vault index for every other user's health check in the same block - ([File: local-testing/contracts/market/market.clar], mirrored in [mainnet/contracts/market/v0-4-market.clar])

### Summary
`market.clar` caches vault `{index, lindex}` values keyed only by `{timestamp: stacks-block-time, aid}`, not by caller or by the vault's live state. The first transaction in a block to touch a given vault (via `accrue-and-cache`) computes and freezes the index for that vault for the *entire block*; every later transaction that needs that vault's index (collateral valuation, health checks, price resolution) reads the frozen snapshot instead of re-accruing, exactly mirroring the "stale `oldObject`" pattern in the report where a snapshot taken at one point is silently reused for a different actor's evaluation.

### Finding Description
`accrue-and-cache` implements the caching: [1](#0-0) 

```
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)          ;; cache HIT: reuse frozen snapshot
      (let ((indexes (try! (vault-accrue aid))))  ;; cache MISS: compute fresh + freeze
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```

The cache key contains only `timestamp` and `aid` — no caller identity and no dependency on the vault's *current* `assets`/`total-borrowed` state. `vault-accrue` (the underlying `accrue`) computes `next-index`/`next-liquidity-index` from the elapsed time since `last-update` and the utilization/rate implied by the vault's state **at the moment it is called**: [2](#0-1) 

This value is consumed by every subsequent price/health computation in the same block through `resolve-ztoken`/`get-cached-indexes`: [3](#0-2) 

and through the collateral-accrual path used before every health/notional evaluation: [4](#0-3) 

Because a vault's `total-borrowed`/`assets` (and hence utilization and the interest rate applied over the *entire* elapsed period since `last-update`) can be moved by any user's deposit/borrow/repay immediately before that user triggers the first `accrue-and-cache` call for that vault in a block, whichever transaction is first to touch a vault effectively chooses the index/lindex that is then locked and blindly reused for every other unrelated user's collateral valuation and health check for the rest of that block — the shared cache is "primed" by one caller and "consumed" (without revalidation) by another, the exact bug class flagged in the report (a stale snapshot passed off as current data to a validation routine).

### Impact Explanation
A user (attacker) can, immediately before an operation that primes the cache for a given vault, change that vault's `assets`/`total-borrowed` (e.g., via a large deposit/withdraw or borrow/repay) to skew the interest-rate/utilization used in the one-time `vault-accrue` computation for the block, then be the first to call any market function that triggers `accrue-and-cache` for that vault. Every other user's zToken-collateral valuation, debt valuation, and liquidation health check for that vault, for the remainder of the block, is computed off this frozen, attacker-influenced index rather than the vault's true state. This can push a solvent victim's position into apparent unhealthiness (enabling wrongful/opportunistic liquidation) or hide an actually unhealthy position from liquidators for the rest of the block (temporary freezing of the ability to liquidate/recover funds). This lands in the in-scope "temporary freezing of funds" impact category, since victims' positions are mis-evaluated for the duration of the block due to a third party's action, independent of the victim's own transaction.

### Likelihood Explanation
Requires only ordinary user-level transactions (deposit/withdraw/borrow/repay to shift utilization, followed by any market call touching the vault) within the attacker's control of transaction ordering inside a single block — no privileged access or DAO compromise needed. Reaching the exact economic threshold to flip a victim's health status requires favorable timing and sizing, which is plausible but not guaranteed every block, so likelihood is moderate rather than trivial.

### Recommendation
Bind the cache to the actual vault state rather than only to the block timestamp — e.g., include a monotonically-increasing vault state nonce (incremented on any state-changing vault call) in the cache key, or simply invalidate/refresh `index-cache-` whenever an intervening vault operation changes `assets`/`total-borrowed` for that `aid` within the same block, so later callers always observe the vault's current index/lindex rather than a stale snapshot primed by an earlier, possibly adversarial, caller.

### Proof of Concept
1. Attacker deposits/borrows against vault X to shift its utilization sharply (raising or lowering the interest rate that will be applied over the elapsed period since `last-update`).
2. Attacker immediately performs any market operation that touches vault X's collateral or debt, triggering `accrue-and-cache(X)`, which computes `vault-accrue(X)` under the manipulated utilization and stores the result in `index-cache-` keyed by the current `stacks-block-time`.
3. Within the same block, victim (or a liquidator evaluating the victim) calls `borrow`/`collateralAdd`/liquidation, which resolves zToken(X) price or accrues X's debt via `accrue-and-cache(X)` — this hits the cache and reuses attacker's frozen index instead of recomputing from X's now-different true state.
4. The victim's health/liquidation evaluation is computed against the stale, attacker-primed index for the rest of the block, producing incorrect (over- or under-) valuation of their position relative to ground truth.
