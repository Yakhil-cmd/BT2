### Title
Webhook organization used for signature verification is not bound to the repository the payload actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the `X-Hub-Signature` against using an organization name pulled from the **unauthenticated JSON body itself**, while the event handlers that actually mutate state (e.g. `PushHandler`) select the target `Repository`/`Stack` from a **different field of the same unauthenticated body**. Nothing ties "the organization whose secret validated the signature" to "the repository whose stacks get written to." In a multi-organization deployment (the engine explicitly supports this — see `Shipit.github_organizations` / `secrets.github` keyed by org, exercised by `test/dummy/config/secrets_double_github_app.yml`), a webhook that is validly signed for organization A can carry a `repository.full_name` pointing at a stack belonging to organization B, and it will be processed as if it came from B.

### Finding Description
`verify_signature` computes the signing organization from the raw JSON body before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) — both are attacker-controlled JSON fields, not header/signature-protected metadata. This value is used only to pick which `Shipit.github(organization:)` (and hence which `webhook_secret`) to validate against: [3](#0-2) 

Once `verify_webhook_signature` passes (using organization A's secret because `repository.owner.login` == "A" or `organization.login` == "A"), the request body is handed unmodified to the event handlers: [4](#0-3) 

The handlers, however, resolve the actual `Repository` to act on from a *different* field — `repository.full_name` — with no re-validation that it belongs to the organization whose secret was used: [5](#0-4) [6](#0-5) 

The broken binding, stated as an equality that the code assumes but never enforces:
```
organization_that_signed(payload) == owner_of(payload["repository"]["full_name"])
```
`repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the mutated `Stack`) are two independent, attacker-supplied strings inside the same unsigned-until-verified JSON body; the HMAC only proves the byte string was signed by *some* configured organization's secret — it says nothing about which organization's repository the payload claims to touch.

### Impact Explanation
On a multi-tenant/multi-organization Shipit deployment (a configuration this engine explicitly supports, per `Shipit.github_organizations` and per-org `secrets.github` blocks such as `OrgOne`/`OrgTwo` in `test/dummy/config/secrets_double_github_app.yml`), an actor who controls (or has legitimately configured) a GitHub App/webhook for one organization present in the same Shipit instance can produce a webhook body whose `X-Hub-Signature` is valid for their own org's secret, but whose `repository.full_name` names a `Stack` owned by a different organization on the same instance. Handlers such as `PushHandler` will then call `stack.sync_github(expected_head_sha: params.after)` against the victim organization's stack using attacker-chosen `ref`/`after` values, and similarly `MembershipHandler`/`PullRequest` handlers act on `params.repository.full_name` for team/PR provisioning decisions — i.e., an unauthorized cross-organization/cross-repository write is achievable using only credentials the attacker legitimately possesses for their own tenant, not the victim's.

### Likelihood Explanation
This requires: (1) the host running a genuine multi-organization Shipit configuration (explicitly built and tested in this engine), and (2) the attacker controlling any one configured organization's `webhook_secret` (which is the expected, unprivileged-relative-to-other-tenants capability of a tenant admin in a multi-org setup — they never need the victim's secret, GitHub token, or Shipit session). Given the engine ships and tests this exact multi-org topology, the precondition is realistic rather than theoretical.

### Recommendation
After signature verification, re-derive and enforce that the organization that verified the signature matches the owner of `repository.full_name` (or any org identifier) actually used by the handlers — reject the webhook if `repository.owner.login`/`organization.login` and `repository.full_name`'s owner segment diverge, and thread the *verified* organization (not a re-parsed field) into `Webhooks.for_event(event).each { |handler| handler.call(params, organization:) }` so handlers can scope repository lookups to the verified tenant.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `OrgA` (attacker-controlled webhook secret) and `OrgB` (victim, has a `Stack` for `orgb/private-repo`), per the pattern in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "orgb/private-repo" }
}
```
3. Attacker signs the raw body with `OrgA`'s `webhook_secret` and sends it as `X-Hub-Signature`.
4. `WebhooksController#repository_owner` returns `"OrgA"` → `verify_signature` validates successfully using `OrgA`'s secret. [1](#0-0) 
5. `PushHandler#stacks` resolves via `Repository.from_github_repo_name("orgb/private-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on `OrgB`'s stack, despite the signature never having been checked against `OrgB`'s secret. [6](#0-5)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
```
