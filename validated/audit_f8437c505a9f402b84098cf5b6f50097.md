## Broken Binding (stated as equality)

The code implicitly assumes:

`verified_webhook_organization (repository_owner from payload, checked against Shipit.github(organization:).webhook_secret) == team.organization (the org that actually owns params.team.id in GitHub)`

In reality, `Team.find_or_create_by!(github_id: params.team.id)` looks the team up **only by `github_id`**, with no comparison to the organization that the webhook signature was actually verified against. So for a pre-existing team, `verified_webhook_organization` and `team.organization` can silently diverge and the code never notices. [1](#0-0) 

## Trace

- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and verifies the HMAC using `Shipit.github(organization: repository_owner)`'s **own** `webhook_secret`. This only proves the payload was genuinely signed by *that* organization's GitHub App installation — it says nothing about the `team` object embedded in the same payload. [2](#0-1) 

- `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { ... }`. The block (which sets `team.organization = params.organization.login`) only runs on **creation**. If `params.team.id` matches an existing `Team` row (e.g. a privileged team belonging to a different, already-onboarded organization), that existing row is returned as-is, and its `organization` is never re-checked against the organization that the signature was actually verified against. [3](#0-2) 

- `User.find_or_create_by_login!(params.member.login)` then creates/finds a `User` purely from the attacker-supplied `login` string, fetching real GitHub profile data via `Shipit.github.api.user(login)` — this ties the row to a real GitHub identity but does **not** verify that this login is actually a member of the team/org in question. [4](#0-3) 

- Finally `team.add_member(member)` inserts the `Membership` row unconditionally. [5](#0-4) 

- This matters because Shipit explicitly supports multi-organization deployments where each org has its own `webhook_secret`, `app_id`, etc., and any one of these orgs can independently target the *same* `Team` table by numeric `github_id`. [6](#0-5) 

- `User#authorized?` treats team membership as authorization-bearing: `teams.where(id: Shipit.github_teams.map(&:id)).exists?`. [7](#0-6) 

None of `verify_signature`, `ExplicitParameters` schema validation, or `find_or_create_team!` cross-check `params.organization.login` against the resolved `team.organization` for pre-existing teams, so the divergence is real and exploitable in a multi-org Shipit configuration.

### Title
Cross-organization team hijack via `membership` webhook - lookup by `github_id` ignores verified organization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely by the numeric `params.team.id`, without confirming that this team actually belongs to the organization whose `webhook_secret` was used to authenticate the request. In a Shipit deployment configured for multiple GitHub organizations, an admin of one onboarded (but lower-privileged) organization can send a genuinely-signed `membership` webhook naming a privileged team's `github_id` from a different organization and an arbitrary `member.login`, causing Shipit to add that login to the privileged team.

### Finding Description
The broken equality is `verified_webhook_organization == team.organization`. `WebhooksController#verify_signature` only proves the payload's HMAC matches the `webhook_secret` configured for `repository_owner`/`organization.login` in the payload — it never re-validates that `params.team.id` belongs to that same organization. `find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { ... }`; for an already-existing `Team` row (the scenario the question specifies — "targeting an existing Shipit.github_teams team.id"), the creation block that assigns `team.organization` is skipped, so the found team's actual organization is never compared to the organization that produced the valid signature. `User.find_or_create_by_login!(params.member.login)` then creates/finds a `User` for any attacker-chosen `login`, and `team.add_member(member)` inserts the `Membership` unconditionally. An attacker who administers any organization already onboarded into this Shipit instance (which is enough to make GitHub sign a `membership` webhook with a secret that Shipit will verify) can spoof `team.id` to point at a different organization's privileged team and grant team membership to any login of their choosing.

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization (High): a `Membership` row is written granting an attacker-named GitHub login membership in a team that backs `User#authorized?`. Because the lookup key (`github_id`) is global while `webhook_secret` verification is per-organization, the vulnerability breaks the tenant boundary that the multi-organization GitHub App feature is supposed to provide — one organization's webhook can mutate another organization's authorization state. This is repeatable per request and works against any team whose numeric `github_id` the attacker can determine.

### Likelihood Explanation
Requires a Shipit deployment configured with multiple GitHub organizations (a documented, supported configuration) and the attacker having admin rights on one of the already-onboarded organizations (so that GitHub emits a validly-signed webhook using that org's own `webhook_secret`). The attacker also needs to learn/guess the numeric `github_id` of the target team, which is discoverable in various ways (e.g., via GitHub's team API for teams they can see, or trial across a small ID range). No Shipit secrets are needed by the attacker directly, and the exploit is a straightforward crafted webhook.

### Recommendation
Scope the team lookup by both `github_id` and the verified organization: `Team.find_or_create_by!(github_id: params.team.id, organization: repository_owner_from_verified_request)`, and reject/raise if an existing team's `organization` does not match the organization the webhook signature was verified against, rather than silently reusing the found row.

### Proof of Concept
```ruby
test ":membership webhook from OrgTwo cannot add members to OrgOne's team" do
  # Existing privileged team belongs to OrgOne
  privileged_team = shipit_teams(:org_one_developers) # github_id: 999, organization: 'OrgOne'
  Shipit.stubs(:github_teams).returns([privileged_team])

  @request.headers['X-Github-Event'] = 'membership'
  Shipit.github(organization: 'OrgTwo').expects(:verify_webhook_signature).returns(true)
  Shipit.github.api.stubs(:user).with('attacker-picked-login').returns(stub(
    id: 999, name: 'X', login: 'attacker-picked-login', email: nil,
    avatar_url: 'https://x', url: 'https://api.github.com/user/attacker-picked-login'
  ))

  payload = {
    action: 'added',
    team: { id: privileged_team.github_id, name: privileged_team.name, slug: privileged_team.slug, url: privileged_team.api_url },
    organization: { login: 'OrgTwo' }, # attacker's own onboarded org, NOT OrgOne
    member: { login: 'attacker-picked-login' },
    repository: { owner: { login: 'OrgTwo' } }
  }.to_json

  post :create, body: payload, as: :json
  assert_response :ok

  member = Shipit::User.find_by(login: 'attacker-picked-login')
  assert member.teams.include?(privileged_team) # FAILS to be prevented: cross-org membership granted
  assert member.authorized? # attacker-chosen login now authorized via OrgOne's privileged team
end
```
Both sides of the equality (`repository_owner/organization.login == 'OrgTwo'` vs `privileged_team.organization == 'OrgOne'`) diverge, and the assertion demonstrates the membership/authorization is granted anyway.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
