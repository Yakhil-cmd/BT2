### Title
Webhook status/CI forgery via organization-secret / repository-identity binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The webhooks endpoint selects which GitHub organization's `webhook_secret` to use for HMAC verification from `repository.owner.login` (or `organization.login`), but the event handlers that act on the verified payload identify the affected repository/commit from an entirely different, unauthenticated-relative field (`repository.full_name`, or for `status` events, nothing at all — just a bare `sha`). Anyone who legitimately controls a webhook secret for *one* organization configured in this Shipit instance can forge a fully valid, self-signed webhook whose body claims to concern a *different* organization's repository, or, in the `status` handler's case, any commit SHA at all, regardless of which repository it belongs to.

### Finding Description
`WebhooksController#verify_signature` picks the app/secret to verify against using only the owner login found in the payload: [1](#0-0) [2](#0-1) 

Because the entire raw JSON body is attacker-authored before signing (the attacker computes the HMAC themselves with a secret they legitimately know for their own org), the signature check only proves "this body was signed with organization X's secret." It does **not** bind the verified organization X to the repository that the handler subsequently mutates state for.

The dispatched handler's base class then resolves the target repository purely from a different JSON field, `repository.full_name`, with no cross-check against the organization that was actually verified: [3](#0-2) 

`Repository.from_github_repo_name` splits this attacker-controlled string on `/` and looks up any `Repository` record by owner/name, again with no relation to the verified `repository_owner`: [4](#0-3) 

The `StatusHandler` (which creates GitHub commit-status records used to gate deploys) is even more exposed: it never consults `repository` at all, it matches commits **globally by SHA** across the whole install: [5](#0-4) 

So the binding that is actually enforced is:
- `verified organization (via webhook_secret) == organization named in repository.owner.login`

But the binding that matters for state mutation is:
- `repository/commit actually written == repository.full_name / sha, unconstrained`

These two are not the same value, and nothing ties them together. Any org whose webhook secret is known to the attacker (e.g., an org they administer that is itself tracked by this Shipit instance) can send a self-signed webhook where `repository.owner.login` = their own org (to pass `verify_signature`) while `repository.full_name`/`sha` reference a stack or commit belonging to a completely different, victim organization tracked by the same Shipit instance.

### Impact Explanation
Using the `status` event, an attacker who knows any one configured org's webhook secret can inject a fabricated GitHub commit status (`state: success`, arbitrary `context`) for **any commit SHA already known to Shipit**, in any stack/repository, without any relation to the organization whose secret they used. Because commit statuses are commonly used by Shipit to gate merges/deploys (CI-required checks), this allows forging a "green" CI status on a victim repository's commit to bypass a deploy-blocking check, leading to an unauthorized deploy. Push/check_suite/pull_request handlers are similarly reachable cross-repository via the `repository.full_name` mismatch, enabling cross-organization write actions (e.g., triggering syncs, review-stack provisioning) on repositories the attacker's known secret was never scoped to. This satisfies the "Critical – unauthorized deploy" and cross-repository-write impact bar, since it breaks the binding between the GitHub organization that authenticated the webhook and the repository that is actually written.

### Likelihood Explanation
Exploitability requires only that the attacker legitimately possess (or can retrieve) a `webhook_secret` for *some* organization already onboarded to the same Shipit instance — a routine, low-privilege condition in any multi-tenant Shipit deployment where multiple GitHub orgs are configured (`Shipit.github(organization:)`), each potentially with distinct webhook secrets set by their own org admins. No GitHub App private key, no Shipit session, and no repository write access to the victim org is required — only knowledge of one's own org's shared secret and the ability to POST to the public `/github_webhook` (or equivalent) endpoint.

### Recommendation
Bind the verified signing organization to the object actually mutated:
- After signature verification succeeds for organization X, require that `repository.owner.login`/`organization.login` used for signature selection matches `repository.full_name`'s owner segment before dispatching to handlers, rejecting mismatches.
- In `Handler#stacks`/`Repository.from_github_repo_name`, verify the resolved `Repository#owner` equals the organization used to verify the signature (pass it through explicitly instead of re-deriving it from an unauthenticated-relative field).
- In `StatusHandler#process`, scope the `Commit` lookup by the verified repository/organization instead of matching by bare `sha` across the entire installation.

### Proof of Concept
1. Attacker administers (or otherwise knows the webhook secret of) GitHub org `attacker-org`, which is configured in this Shipit instance's `Shipit.github` config (`webhook_secret: S`).
2. Victim org `victim-org` has a stack tracked by the same Shipit instance, with a known/guessable commit `sha` (e.g., copied from the public commit history of `victim-org/app`).
3. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
   }
   ```
4. Attacker signs the raw body with `S` (which they know) and sets `X-Hub-Signature: sha1=<hmac>`, `X-Github-Event: status`.
5. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `attacker-org`'s app/secret `S`, and the HMAC matches — signature accepted. [6](#0-5) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (irrespective of `attacker-org` being unrelated to it), and calls `commit.create_status_from_github!(params)`, marking the victim commit as `success` for a required check. [5](#0-4) 
7. If `victim-org`'s stack requires that status to deploy, the attacker has forged the CI gate needed to trigger/allow an unauthorized deploy on a repository they have no legitimate relationship to.
