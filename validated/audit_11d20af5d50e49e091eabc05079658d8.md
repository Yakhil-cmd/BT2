### Title
Cross-repository CI status forgery via organization-scoped webhook signature but repository-unscoped commit lookup - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook payload only at the **organization** granularity — it looks up `repository_owner` (`params.dig('repository', 'owner', 'login')`) and validates the HMAC using the `webhook_secret` configured for that organization [1](#0-0) . Once the signature is accepted, `create` dispatches the entire attacker-influenced JSON body to the handler registered for the event with no further scoping [2](#0-1) .

`StatusHandler#process`, however, resolves which DB row to mutate purely by commit SHA, globally, with **no repository/stack scoping at all**: [3](#0-2) 

This breaks the binding the rules describe as "an organization that authenticated versus the repository that is written": the signature only proves the payload came from GitHub *for some repository belonging to organization X*, but the code applies the `sha`/`state` write to **any** `Commit` row in the database that shares that SHA, irrespective of which repository/stack it belongs to, and irrespective of the `repository.full_name` field carried in the same payload.

### Finding Description
- `Shipit.github(organization: repository_owner)` selects the webhook secret keyed by `repository.owner.login` [4](#0-3) , i.e. authentication is at organization granularity, not repository granularity.
- All handlers, including `PushHandler` and `CheckSuiteHandler`, correctly re-scope by `repository.full_name` via `Handler#stacks` before acting [5](#0-4) , [6](#0-5) , [7](#0-6) .
- `StatusHandler` does not call `stacks`/`repository_name` at all — it queries `Commit.where(sha: params.sha)` across the *entire* table, with no repository filter, then calls `create_status_from_github!` on every match [8](#0-7) .
- Any legitimate `status` webhook GitHub sends for *any* repository within an authenticated organization (i.e., an event whose signature the organization-level `webhook_secret` validates) will be applied to every `Commit` row in Shipit sharing that SHA — including commits belonging to a completely unrelated repository/stack in the same organization, since Git SHAs are content-derived and an attacker who can create a commit object with identical tree/parent/author/committer/message/timestamp fields (all of which are public metadata for any commit visible via the GitHub UI/API) in a repository they merely have push access to (not necessarily the victim repository) can trigger a validly-signed `status` event carrying that colliding SHA.
- The equality the code implicitly (and incorrectly) assumes is: `organization(repository.owner.login) == repository(commit.stack.repository)`. In reality only the organization is verified; the repository the commit belongs to is never checked against the payload's `repository.full_name`, so **any** repo inside the org can write CI status onto commits that live in a different repo's stack.

### Impact Explanation
Shipit gates deploys and merges on required CI statuses (`ci.require` in `shipit.yml`, enforced through `Commit`/`Status` records populated by this exact handler) — see the extensive `ci.require`/status handling logic referenced in `app/models/shipit/commit.rb` and `app/models/shipit/stack.rb`. An attacker who can push a colliding commit to any repository in the same GitHub organization (a repo they have legitimate, unprivileged write access to, not the victim's repo) can fabricate a `status` webhook that GitHub will sign with the org's real webhook secret. Shipit will then accept that signature and apply the forged `state`/`context` to the *victim* commit row in a different stack, satisfying `ci.require` checks it should never have satisfied. This can lead to an unauthorized deploy or merge in a stack the attacker has no access to — matching the "unauthorized deploy, rollback or merge" impact category.

### Likelihood Explanation
Exploitation needs: (1) the attacker to have ordinary push access to some repository within the same GitHub organization that hosts the target Shipit stacks (a common situation for internal engineers who are not authorized on the target repo/stack), and (2) the ability to construct a commit object with identical SHA to a target commit, which only requires replicating public commit metadata (tree hash, parent hash(es), author/committer identity and timestamps, message) — all obtainable via the GitHub API/UI for any commit the attacker can view. No possession of `webhook_secret`, `api_clients_secret`, GitHub App private key, or a Shipit session is required, satisfying the "unprivileged attacker" constraint. This is a realistic, moderately achievable attack for a determined actor.

### Recommendation
Scope `StatusHandler#process` (and any other handler that trusts payload-provided identifiers without cross-checking) to only update commits whose `stack.repository` matches `payload.dig('repository', 'full_name')`, mirroring the pattern already used by `PushHandler`/`CheckSuiteHandler` via `Handler#stacks`. E.g., restrict the lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or join through `Repository.from_github_repo_name(repository_name)`) instead of a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Attacker has ordinary write access to `org/attacker-repo` inside the same GitHub organization that also hosts the Shipit-tracked `org/victim-repo` (stack requiring `ci.require: ["ci/tests"]`).
2. Attacker inspects the target commit in `org/victim-repo` (public metadata: tree SHA, parent SHA, author/committer name/email/date, commit message) via the GitHub UI/API.
3. Attacker reproduces an identical commit object (same tree/parent/author/committer/message/timestamps) in `org/attacker-repo`, producing an identical 40-character SHA, and pushes it (or otherwise triggers a `status` event on that SHA, e.g. via any CI integration on `attacker-repo`) with `state: success`, `context: ci/tests`.
4. GitHub signs and delivers the `status` webhook to Shipit's `/webhooks` endpoint using the organization's real `webhook_secret`; `WebhooksController#verify_signature` validates it successfully because it only checks `repository.owner.login` against the org's secret.
5. `StatusHandler#process` executes `Commit.where(sha: <colliding sha>)`, finds the victim commit in `org/victim-repo`'s stack, and calls `create_status_from_github!`, marking `ci/tests` as `success` for that commit — even though the actual CI event came from `org/attacker-repo`.
6. The victim stack's deploy/merge gating on `ci/tests` is now satisfied, allowing an unauthorized deploy or merge.
