### Title
Unhandled TypeError (undefined-property dereference) when an AA formula's `unit[...]` selector reads a stored unit whose `temp_data` message has a non-inline `payload_location` - (File: formula/evaluation.js)

### Summary
The oscript `unit[hash]` selector in the AA formula evaluator unconditionally executes `delete m.payload.data` for every message with `app === "temp_data"` found in a unit retrieved from storage, without checking that `m.payload` actually exists. [1](#0-0) 

### Finding Description
`validation.js` explicitly allows a `temp_data` message (like any message) to be posted with `payload_location` set to `"none"` or `"uri"`, in which case the `payload` field must be *absent* from the message: [2](#0-1) 

Such a unit passes full unit validation and gets written to the DAG normally — nothing in `validateInlinePayload`'s `temp_data` branch requires `payload_location === "inline"`; that branch is only reached for inline payloads. [3](#0-2) 

Later, when any AA formula evaluates a `unit['<hash>']` selector (an operation directly available to any AA author, and driven by trigger data or state that an attacker fully controls), the evaluator reads the referenced joint from storage and, if any message in it has `app === "temp_data"`, does:
```
for (let m of objUnit.messages)
    if (m.app === "temp_data")
        delete m.payload.data;
```
If that particular `temp_data` message was posted with `payload_location` other than `"inline"`, `m.payload` is `undefined`, and `delete m.payload.data` throws `TypeError: Cannot read properties of undefined (reading 'data')` — the JS analog of a NULL pointer dereference in the C++ report (`MPDevice_win.cpp` dereferencing a null pointer without a check). This happens synchronously inside `storage.readJoint`'s `ifFound` callback with no surrounding `try/catch`, so the exception is not converted into a formula evaluation error/`false`, it propagates as an uncaught exception in the calling stack (AA trigger/response processing chain in `aa_composer.js`'s `handleTrigger`/`evaluateAA`). [4](#0-3) 

Because this code path runs identically on every full node that processes the same stable unit and the same AA trigger (deterministic execution is required for AA consensus), the crash is not a single-node incident — every node reaching this MC index for this AA/trigger combination throws the same uncaught exception at the same point in bookkeeping (mid-transaction, mid-`kvstore` batch), which halts AA response processing network-wide and prevents new units built on top of that AA activity from being confirmed.

### Impact Explanation
An uncaught exception thrown deterministically during AA trigger/response composition crashes (or otherwise permanently wedges, since it occurs inside an open DB transaction/batch under a write lock) every node that reaches this code path. Because AA processing is required for the network to keep confirming units depending on that AA, and the same exception fires on all conforming nodes, this constitutes a network-wide inability to confirm new units — matching the "node disagreement on validity/stability" / "network unable to confirm new units" impact bar required by the validation rules. This is High severity, consistent with the reference CVE (NULL pointer dereference, CVSS 7.5, availability impact only).

### Likelihood Explanation
Likelihood is high because:
- Posting a valid unit containing a `temp_data` message with `payload_location` `"none"` or `"uri"` and no `payload` field is fully permitted by `validation.js`; any unprivileged unit poster can create such a unit. [2](#0-1) 
- The `unit[hash]` selector is a standard, documented oscript primitive available to any AA author/trigger sender; a trigger message can carry the target hash as trigger data, so no special privilege is required to make an AA dereference an attacker-chosen unit. [5](#0-4) 

### Recommendation
Guard the delete with a presence check before touching `m.payload`, mirroring the pattern already used elsewhere in the code base to defend against optional/absent `payload`:
```
for (let m of objUnit.messages)
    if (m.app === "temp_data" && m.payload)
        delete m.payload.data;
```
Additionally, wrap the `readJoint`/`ifFound` handling (and generally any user-triggered formula evaluation branch that mutates externally-sourced unit data) in a `try/catch` that converts unexpected exceptions into a formula evaluation failure (`cb(false)` / fatal formula error) rather than letting them propagate to the AA trigger-processing transaction.

### Proof of Concept
1. Post a valid unit `U` containing a message `{ app: "temp_data", payload_location: "none", payload_hash: <valid hash>, payload_hash_of_length HASH_LENGTH> }` with no `payload` field — this passes `validateInlinePayload`'s `temp_data` branch because that branch only fires for `payload_location !== inline` when checking hash equality earlier in `validation.js`, and the `temp_data` case body itself is only reached with `payload_location` allowed to be non-inline via the generic message loop. [2](#0-1) 
2. Deploy or use an existing AA whose formula (in `init`, message conditions, or a message payload) contains `unit['<hash of U>']` where the hash is supplied via `trigger.data` or hard-coded.
3. Send a trigger unit to that AA causing it to evaluate `unit['<hash of U>']` once `U` is stable and at or before the current MCI.
4. During evaluation, `storage.readJoint`'s `ifFound` callback executes `delete m.payload.data` on the `temp_data` message from `U`, where `m.payload` is `undefined`, throwing an uncaught `TypeError` inside the AA trigger-handling transaction on every node that processes this trigger, per `formula/evaluation.js` lines 1611-1615. [1](#0-0)
