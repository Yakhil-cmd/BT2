This report's core pattern maps to a concrete, already-conceded analog in `pallet-election-provider-multi-block`'s signed-phase pallet: a mechanism that shows a user a "pending reward" that isn't guaranteed to be backed by pot funds, and — unlike the Solidity report where the fix is "just document it" — this pallet actually has code that silently and irreversibly destroys the legitimate reward once a bounded queue fills up.

### Title
Bounded `UnpaidRewards` queue permanently and silently destroys legitimate round-winner rewards when the `RewardSource` pot stays depleted - ([File: substrate/frame/election-provider-multi-block/src/signed/mod.rs])

### Summary
`pallet-election-provider-multi-block::signed` pays round winners from a configurable `RewardSource` pot [1](#0-0) . If the pot cannot cover the payment, the pallet does not fail the extrinsic; instead it defers the reward into a `BoundedVec` capped at `MAX_UNPAID_REWARDS = 16` entries [2](#0-1) . When that bounded queue is already full and another deferral occurs, the oldest entry is evicted with no funds moved and the reward becomes permanently unrecoverable, as the code comments themselves state [3](#0-2) .

### Finding Description
The winner of a signed round is determined and rewarded by `report_result` when a solution is verified as `Queued` [4](#0-3) . `pay_reward` calls `transfer_or_mint`, which — when `T::RewardSource::account()` returns `Some(pot)` — does a `Preservation::Preserve` transfer from the pot to the winner [5](#0-4) . If that transfer fails (pot balance insufficient, e.g. due to existential-deposit preservation or genuine depletion), the reward is pushed into `UnpaidRewards` instead of being reverted or retried [6](#0-5) .

Crucially, `UnpaidRewards` is bounded to 16 entries. The pallet's own event documentation acknowledges the consequence: `UnpaidRewardEvicted` fires when "`UnpaidRewards` was full, so this (the oldest) entry was evicted to make room for a new deferral; no funds moved, the reward is now unrecoverable" [7](#0-6) . This is the direct structural analog of the Solidity report's root cause: a reward that is "visible"/promised to a specific account (via `RewardPaymentDeferred`/`UnpaidRewards` storage) with no invariant tying the promised total to actually available/reserved funds, and no bound-safe fallback when funds run short — except here, instead of merely "expecting rewards that are not even available," the design goes one step further and actively deletes the obligation once the small fixed-size queue overflows.

Winning a round requires no privileged role — it only requires being the leader of a signed submission for that round, which is reachable by `register`/`submit_page` from any signed account [8](#0-7) .

### Impact Explanation
A legitimate election-round winner can have their earned reward permanently destroyed through no fault of their own, purely because the pot happened to be depleted for 16+ consecutive rounds before they could claim via the permissionless `claim_unpaid_reward` [9](#0-8) . This is an irreversible loss of an entitled, already-computed reward amount — not a griefing/DoS or gas-optimization issue, and not merely theoretical: the code path is exercised any time `RewardSource` is configured with `Some(pot)` (as it is in `asset-hub-westend-runtime` per `prdoc/pr_12843.prdoc`).

### Likelihood Explanation
This requires no attacker privilege and no malicious node/validator behavior — only that the configured pot's balance lags behind cumulative owed rewards for a sustained stretch (16 rounds by default), which is entirely plausible under normal emission-curve/DAP-buffer timing rather than an artificially engineered attack, matching the "acknowledged, no easy fix, document it" character of the original report rather than a directly attacker-triggerable theft.

### Recommendation
Either remove the hard bound on `UnpaidRewards` (accept unbounded/paged storage growth with a cleanup mechanism) or make eviction fail-safe (e.g., re-queue into on-chain balance debt tracked per-account rather than a fixed-size FIFO, or require governance to top up the pot before any eviction can occur). At minimum, document prominently — analogous to the client's original recommendation — that operators must guarantee the `RewardSource` pot remains solvent for at least `MAX_UNPAID_REWARDS` rounds' worth of obligations, since the current design offers no on-chain guarantee that visible/pending obligations are backed by available funds.

### Proof of Concept
No dispatchable-level exploit was executed; this is a code-level analog matching the report's exact invariant gap (visible pending reward not proven backed by available balance), evidenced directly by the pallet's self-documented eviction behavior at [10](#0-9)  and the `UnpaidRewardEvicted` event semantics at [7](#0-6) . A full integration reproduction would drive 17+ signed rounds with `RewardSource::account()` pot balance held below cumulative owed rewards and assert the 17th `UnpaidRewardEvicted` against the original winner's entry — this was not executed against a live test harness as part of this analysis.

			let _ = ensure_signed(origin)?;
			let mut unpaid = UnpaidRewards::<T>::get();

				.position(|entry| entry.round == round)
				.ok_or(Error::<T>::NoUnpaidReward)?;

			UnpaidRewards::<T>::put(unpaid);
			Self::deposit_event(Event::<T>::Rewarded(entry.round, entry.who, entry.amount));

	fn pay_reward(round: u32, to: &T::AccountId, amount: BalanceOf<T>) {

			Self::deposit_event(Event::<T>::Rewarded(round, to.clone(), amount));
			return;

				));
			}

		});
		Self::deposit_event(Event::<T>::RewardPaymentDeferred(round, to.clone(), amount));
