### Title
Null Pointer Dereference via Malformed `signers` Object in `new_shared_address` Device Message Crashes the Node - ([File: wallet_defined_by_addresses.js])

### Summary
`handleNewSharedAddress()` in `wallet_defined_by_addresses.js` processes the `new_shared_address` device message sent by a paired correspondent device when proposing a new multi-signature shared address. The function validates that `body.signers` is a non-empty object, but never validates that each individual entry of `body.signers` is itself a non-null object before dereferencing `.address` on it. A paired device can send a `signers` map whose values are `null` (or any non-object primitive), causing an uncaught `TypeError: Cannot read properties of null (reading 'address')`, which — per this codebase's global `uncaughtException` handler — re-throws and crashes the whole node process. This mirrors the null-pointer-dereference DoS pattern of CVE-2018-20024 (dereferencing an unvalidated pointer/field from untrusted peer-supplied data).

### Finding Description
`handleNewSharedAddress(body, callbacks)` performs the following checks before iterating over `body.signers`: [1](#0-0) 

It then loops over every entry of `body.signers` and immediately accesses `signerInfo.address`: [2](#0-1) 

The only guard is `typeof body.signers !== "object" || Object.keys(body.signers).length === 0`, which passes for an object like `{"r.0": null}` — `body.signers` is still `"object"` typed and has at least one key. `signerInfo` is then `null`, and `signerInfo.address` throws a `TypeError`.

This handler is reachable from `createNewSharedAddress()` (used to compose and locally validate outgoing offers) and, more importantly, is the exact function invoked by `wallet.js` when the `new_shared_address` device message subject arrives from a correspondent device — i.e., data supplied by a paired device that is not required to be trusted content-wise, only pairing-authenticated. No caller wraps this code path with a try/catch that would convert the exception into a normal `ifError` callback; the message-handling code depends on synchronous logic staying within `if`-return control flow, not throwing.

Because `network.js` installs a global handler that re-throws any uncaught exception in order to "crash the process to avoid ending up in an inconsistent state": [3](#0-2) 

any TypeError thrown synchronously during device-message processing that is not caught anywhere up the call stack terminates the entire node process — full nodes and wallets alike that process this device message.

### Impact Explanation
A single paired device (a correspondent that the victim's wallet has already added, which is the minimum bar for sending device messages) can crash the victim node/wallet process by sending one `new_shared_address` message with a bad `signers` value. This is a denial-of-service against the recipient's wallet/node, consistent with the "unauthorized... freezing"/"network unable to confirm new units" class of impact when the affected process is a full node acting also as a wallet (common deployment in this codebase, since `wallet.js` is loaded in the same process as `network.js`/`validation.js`). It is directly analogous to the LibVNC null-pointer dereference DoS referenced in CVE-2018-20024: untrusted, partially-validated input from a network peer is dereferenced without a type/null check, crashing the client.

### Likelihood Explanation
High: the attack requires only that the victim has the attacker as a paired correspondent device (a very low bar — pairing is a routine, low-trust operation in this wallet system), and the malicious payload is a single, trivially constructed device message with `signers: { "<path>": null }`. No mining, no waiting for stabilization, and no special network position is required.

### Recommendation
In `handleNewSharedAddress()`, validate that every value of `body.signers` is a non-empty object before accessing any of its properties, e.g.:
```js
for (var signing_path in body.signers){
    var signerInfo = body.signers[signing_path];
    if (typeof signerInfo !== 'object' || signerInfo === null)
        return callbacks.ifError("invalid signer info at path " + signing_path);
    if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
        return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
}
```
More broadly, review all device-message handlers reachable from paired-device input for similar unguarded property access on attacker-controlled nested structures, and ensure the dispatcher wraps message processing in try/catch that reports errors instead of allowing exceptions to propagate to the process-level `uncaughtException` handler.

### Proof of Concept
1. Attacker pairs with victim's wallet as a correspondent device (normal pairing flow).
2. Attacker sends a device message with subject `new_shared_address` and body:
```json
{
  "address": "<chash160 of definition below>",
  "definition": ["sig", {"pubkey": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA="}],
  "signers": { "r": null }
}
```
3. On receipt, `handleNewSharedAddress()` passes the initial checks (`body.definition` is a 2-element array, `body.signers` is a non-empty object), computes `addr`, and then in the `for (var signing_path in body.signers)` loop accesses `null.address`, throwing an uncaught `TypeError`.
4. The process-level `uncaughtException` handler in `network.js` re-throws, terminating the victim's node/wallet process.
