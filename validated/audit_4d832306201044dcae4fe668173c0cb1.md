### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no repository scoping, then calls `Commit#create_status_from_github!` → `Status.replicate_from_github!` which persists the webhook's `description`/`target_url` verbatim. Because the base `Handler` class already provides a `stacks` helper that scopes lookups to the payload's `repository.full_name`, but `StatusHandler` bypasses it and queries `Commit` globally, a `status` webhook sent for repository B can write attacker-controlled `description`/`target_url` text onto a `Commit` row that actually belongs to repository A's stack, whenever a `Commit` with the same `sha` exists in both (e.g., shared/forked git history).

### Finding Description
The broken binding, stated as an equality:
`commit.stack.repository.full_name == payload.dig('repository', 'full_name')` — this MUST hold before any `Status` write occurs, but the code never checks it.

Code path:
- `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` **globally by `sha` only**, with no join/filter on `repository_id`/`stack_id` derived from `payload['repository']['full_name']`.

- Contrast with the base class `app/models/shipit/webhooks/handlers/handler.rb:32-38`, which defines exactly the scoping primitive that should have been used:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
def repository_name
  payload.dig('repository', 'full_name')
end
```
`StatusHandler` never calls `stacks`; it directly hits the `Commit` table unscoped.

- `app/models/shipit/commit.rb:165-169`:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
```
`stack_id` here is the **victim commit's own** `stack_id` (from `Commit#stack_id`), not derived from the attacker's payload's repository at all.

- `app/models/shipit/status.rb:24-33`:
```ruby
def replicate_from_github!(stack_id, github_status)
  find_or_create_by!(
    stack_id:, state: github_status.state,
    description: github_status.description,
    target_url: github_status.target_url,
    context: github_status.context, created_at: github_status.created_at
  )
end
```
This persists `description`/`target_url` verbatim, with no origin/repository check — the row is stamped with stack A's `stack_id` while the free-text fields are attacker-authored from repo B's webhook.

Exploit flow: precondition is a `Commit` row with the same `sha` existing under both repo A's stack and repo B's stack (git commits are content-addressed; this occurs naturally for forks/shared history, cherry-picked/rebased commits with identical content, or vendored/subtree histories — not a cryptographic SHA-1 preimage attack). Given that, the attacker (who owns repo B and can freely emit `status` webhooks for it) sends `POST /webhooks` with `X-Github-Event: status`, `repository.full_name = "attacker/repoB"`, `sha` = the shared sha, and `description`/`target_url` of their choosing. `GithubHook#verify_signature` only validates that the payload is legitimately signed for *whatever repo's webhook secret is configured for repo B* (an unprivileged action the attacker fully controls since they own repo B); it does not, and cannot, assert that the `sha` inside the payload "belongs" to repo B. `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler.params` only validate shape (`sha`, `state`, `description`, `target_url` types), not repository ownership of the commit. No guard in this path re-derives `stack_id` from `repository_name`.

### Impact Explanation
An attacker who controls any GitHub repository (repo B) mirrored/forked from, or otherwise sharing commit content with, a monitored stack A's repository can inject arbitrary `description`/`target_url` strings that are persisted verbatim into stack A's `Status` records and rendered in stack A's UI as if reported by GitHub for stack A's commit. This is a cross-tenant write into a repository that never authenticated the payload for repo B, matching the "payload for one repository mutating another's stack, commit" category. It is repeatable per shared-sha commit and is not limited to a single stack — any stack tracking a repository whose history overlaps with an attacker-owned repo is affected. It is not RCE or credential exfiltration, but it is an unauthenticated cross-repository content-injection/spoofing primitive (phishing `target_url`, fabricated failure `description`) attributed to "GitHub" in victim org UI.

### Likelihood Explanation
Requires the sha-collision precondition (a `Commit` with identical `sha` present in both the victim stack's repo and an attacker-controlled repo) — feasible via forks/shared history, not requiring any secret. No Shipit session, API token, or webhook secret for the victim's repo is needed; the attacker only needs their own repo's webhook (which they fully control as repo owner) to fire a `status` event. Cost is low and the action is repeatable against any repository whose commit history overlaps with an attacker-owned fork.

### Recommendation
In `app/models/shipit/webhooks/handlers/status_handler.rb`, scope the commit lookup through the repository-derived `stacks` (or an explicit join on `stack_id`s belonging to `Repository.from_github_repo_name(repository_name)`), e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each { |commit| commit.create_status_from_github!(params) }`, so a status webhook can only mutate commits belonging to stacks whose repository matches the payload's `repository.full_name`.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or similar):
1. Create `stack_a` backed by `repository_a` (`full_name: "victim-org/A"`) with `commit_a` having `sha: "deadbeef"`.
2. Create `stack_b` backed by `repository_b` (`full_name: "attacker/B"`) with `commit_b` having the same `sha: "deadbeef"` (simulating shared history).
3. Build a `status` webhook payload with `repository.full_name = "attacker/B"`, `sha: "deadbeef"`, `description: "PHISH: click http://evil.example.com"`, `target_url: "http://evil.example.com"`.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert:
   - `commit_a.statuses.last.description == "PHISH: click http://evil.example.com"` and `commit_a.statuses.last.target_url == "http://evil.example.com"` even though `commit_a` belongs to `stack_a`/`repository_a`, which never received a signed webhook for its own repository — demonstrating `commit.stack.repository.full_name != payload['repository']['full_name']` while the write still occurred, proving the binding is broken.
