This confirms the vulnerability. `CheckSuiteHandler` and `PushHandler` both scope their database queries through `stacks`, which resolves via `Repository.from_github_repo_name(repository_name)&.stacks` — i.e., filtered to the repository named in the *verified* payload. `StatusHandler#process`, however, queries `Commit.where(sha: params.sha)` globally, with no `stacks`/`repository` scoping at all.

### Title
Unscoped `Commit.where(sha:)` lookup lets a verified webhook for one repository mutate `Status`/deploy state for commits belonging to unrelated stacks sharing the same sha - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` only proves that the payload's `repository.owner.login` organization is authentic [1](#0-0) , but `StatusHandler#process` never restricts its commit lookup to that repository's stacks — it runs `Commit.where(sha: params.sha)` against the entire `commits` table and calls `create_status_from_github!` on every match [2](#0-1) . Other handlers such as `CheckSuiteHandler` and `PushHandler` correctly scope through the `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) before touching any records [3](#0-2) [4](#0-3) , but `StatusHandler` bypasses this shared base-class helper entirely.

### Finding Description
The binding the system should enforce is: `{ organization authenticated by verify_signature via repository_owner } == { organization(s)/stack(s) whose Commit rows are mutated by process }`. In `StatusHandler`, this equality is broken whenever the same `sha` exists in `Commit` rows belonging to more than one `Repository`/`Stack` (a documented, common setup — mirrors/forks tracked as separate Shipit stacks).

Code path:
1. `WebhooksController#create` parses raw JSON and dispatches to handlers matched to the `status` event [5](#0-4) .
2. `verify_signature` looks up `Shipit.github(organization: repository_owner)` from `params.dig('repository','owner','login')` and validates the HMAC signature against that org's `webhook_secret` [1](#0-0) [6](#0-5) . This only proves the payload is authentic *for that one organization's repository*.
3. `StatusHandler#process` ignores `repository_name`/`stacks` entirely and does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) .
4. `Commit#create_status_from_github!` calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }` [7](#0-6) , which writes a `Status` row scoped to that commit's own `stack_id` and can trigger `enable_ci_on_stack`, `schedule_continuous_delivery`, hooks (`commit_status`/`deployable_status`), and downstream `ProcessMergeRequestsJob` enqueuing as shown in `test/models/commits_test.rb` [8](#0-7) .
5. Because step 3's query has no `WHERE stack_id IN (...)`/repository filter, if the same `sha` exists under `Commit` rows in N different stacks (e.g., N mirrors of the same upstream repo, each its own `Repository`/`Stack` tenant), a single signed webhook — authenticated for only 1 of those N organizations — fans out and mutates all N stacks' commit state, enabling unauthorized simulated CI success/deploy triggering across tenants that never authenticated this payload.

This contrasts directly with `CheckSuiteHandler`, which correctly narrows to `stacks.where(branch: ...)` before touching `stack.commits.where(sha: ...)` [3](#0-2) , and `PushHandler`, which scopes via `stacks.not_archived.where(branch:)` [9](#0-8) . None of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema in `StatusHandler` (which only validates `sha`/`state`/etc. types, not repository ownership) prevent this cross-tenant fan-out [10](#0-9) .

### Impact Explanation
A single verified `status` webhook payload for organization A can create `Status` rows, flip `commit.state`, enable CI, and trigger `schedule_continuous_delivery`/`ProcessMergeRequestsJob` for commits belonging to stacks owned by organizations B, C, ... N, as long as they happen to share the identical sha with a commit tracked under A. This is a payload for one repository mutating another's stack/commit state and can trigger unauthorized deploy-adjacent side effects (CI-enabled state, merge-request processing), matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). The attack is repeatable against any sha collision across tracked stacks and requires no privilege beyond ownership of one webhook-emitting repository whose commit sha happens to coincide with commits in other stacks (most realistically via forks/mirrors of the same upstream, where identical commits are pushed to multiple GitHub repos each backing their own Shipit `Stack`).

### Likelihood Explanation
Requires: (1) Shipit tracking ≥2 `Repository`/`Stack` records that at some point contain a `Commit` row with an identical sha — realistic in mirrored/forked-repo deployments, a documented Shipit pattern; (2) attacker controls (or can trigger a webhook from) at least one of those repositories/organizations, which they can do without any Shipit credentials since anyone can push/PR to their own repo and GitHub will emit the `status` webhook, or fork the upstream so the same commit sha exists in their fork's tracked stack. No `secret_key_base`, `webhook_secret`, or Shipit session is needed — signature verification succeeds legitimately for the attacker's own org.

### Recommendation
Scope `StatusHandler#process` through the same `stacks` helper used by other handlers, e.g. iterate `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) } }`, so only commits belonging to the repository named in the authenticated payload are mutated.

### Proof of Concept
Add a minitest to `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or extend `webhooks_controller_test.rb`):
1. Create `stack_a` (repository `org-a/repo`) and `stack_b` (repository `org-b/repo`), each with a `Commit` row sharing sha `"deadbeef"`.
2. Stub/verify signature for `org-a` only (`Shipit.github(organization: 'org-a')` verifies true; no stub/expectation allows `org-b`'s secret to be used).
3. POST a `status` webhook with `repository.owner.login = "org-a"`, `repository.full_name = "org-a/repo"`, `sha: "deadbeef"`.
4. Assert binding before: `stack_b.commits.find_by(sha: "deadbeef").statuses.count == 0` and after dispatch it becomes `> 0` — proving `create_status_from_github!` ran against `stack_b`, an organization that did not authenticate the request (assert `commit_b.reload.statuses.count == 1` and `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [stack_b])` if state transition qualifies), demonstrating equality `{authenticated org} == {mutated stacks}` is false.
