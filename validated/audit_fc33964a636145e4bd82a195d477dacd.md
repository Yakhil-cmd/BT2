### Title
Webhook organization used for signature verification is not the organization whose repository/stack is mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), while every webhook `Handler` resolves the actual target repository/stack to mutate from a *different* JSON field, `repository.full_name`. Because these two fields are never cross-checked, an attacker who legitimately controls the webhook secret for one onboarded organization can forge a signed payload whose `owner.login` matches their own org (so it passes signature verification) but whose `full_name` points at a completely different, victim organization/repository, causing Shipit to mutate the victim's `Stack`/`Commit`/`PullRequest` state.

### Finding Description
The controller picks the verifying GitHub App like this: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `repository.owner.login` (falling back to `organization.login`). `Shipit.github(organization: repository_owner)` resolves the per-organization `GithubApp` instance, and `verify_webhook_signature` HMACs the *entire raw body* with **that organization's** `webhook_secret`.

Once the signature check passes, the raw params are dispatched unchanged to every registered handler: [3](#0-2) 

But `Shipit::Webhooks::Handlers::Handler`, the base class every push/status/pull_request handler inherits from, determines which repository (and therefore which `Stack`) to act on using a **different field**: [4](#0-3) 

Concretely, `PushHandler` uses this to locate the target stacks and trigger a resync with an attacker-supplied `after` SHA: [5](#0-4) 

Pull-request handlers likewise resolve the repository from `params.repository.full_name`, independent of the field used for signature selection: [6](#0-5) 

Because Shipit is designed to serve multiple GitHub organizations, each configured with its own `webhook_secret` (raising `Shipit::GithubOrganizationUnknown` for unmapped ones, per `verify_signature`'s rescue clause), an attacker who is a legitimate member/administrator of *any one* onboarded organization (`org-a`) knows `org-a`'s webhook secret. They can then hand-craft an HTTP POST to `/webhooks` where:
- `repository.owner.login = "org-a"` (or `organization.login = "org-a"`) — satisfies the signature check, since the whole raw body is HMAC-signed with `org-a`'s own secret, which the attacker legitimately possesses.
- `repository.full_name = "victim-org/victim-repo"`, `ref`, `after`, `sha`, `state`, `pull_request.head.sha`, etc. — freely chosen by the attacker, since nothing in `full_name` or the rest of the payload is bound to the signature-selection field.

This breaks the equality that should hold: `organization authenticated by the signature == organization/repository actually written by the handler`. Before an attacker's request: only webhooks genuinely signed with `victim-org`'s secret can mutate `victim-org/victim-repo`'s stacks. After the crafted request: any onboarded org's webhook secret is sufficient to mutate any other org's `Stack`, `Commit`, `PullRequest`, or `ReviewStack` records, because verification and dispatch consult unrelated payload fields.

### Impact Explanation
With a valid signature computed from their own organization's secret, the attacker can act on a victim stack:
- Force `GithubSyncJob` to run against the victim's stack/branch with an attacker-chosen `after` commit SHA (`PushHandler#process`), influencing which commits Shipit believes are the head of the tracked branch.
- Inject or forge commit `Status` records (`status`/`check_suite` handlers use the same `stacks`/`repository_name` resolution pattern) on arbitrary victim commits — since commit status/CI checks gate `Commit#deployable?` and Continuous Delivery auto-triggering, this can be used to make an unreviewed victim commit appear CI-green and eligible for an automatic deploy.
- Archive/unarchive `ReviewStack`s or create new review stacks under the victim repository, and overwrite `PullRequest#github_pull_request` (including `head.sha`/`head.ref`) for the victim's pull requests.

This crosses the "an organization that authenticated versus the repository that is written" trust boundary and can escalate into unauthenticated writes to another organization's stack state, and potentially an unauthorized/forged-CI-triggered deploy — matching the High/Critical impact classes (unauthenticated write of stack state; unauthorized deploy via forged status).

### Likelihood Explanation
Requires only that the attacker be a legitimate member/operator of any single organization onboarded to a multi-tenant Shipit instance (i.e., they know that org's own `webhook_secret`, which they are entitled to as that org's GitHub App owner) — no access to the victim org, no `ApiClient` token, and no repository write access to the victim repo is needed. The only work required is crafting a raw JSON body and computing its HMAC-SHA1 with a secret the attacker already possesses.

### Recommendation
Bind the field used to select the verification secret to the field used for repository resolution: after selecting the `GithubApp`/secret via `repository.owner.login`, re-derive `repository.full_name`'s owner segment and reject the webhook (or re-verify) if the two owners don't match, e.g. in `Shipit::WebhooksController#verify_signature`:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  full_name_owner = params.dig('repository', 'full_name')&.split('/')&.first
  head(422) unless verified && full_name_owner&.casecmp?(repository_owner)
  ...
```
Alternatively, make every `Handler` resolve its target repository from the same field (`repository.owner.login` + `repository.name`) that was used to select the signing secret, rather than the independent `repository.full_name` field.

### Proof of Concept
1. Attacker is a legitimate admin of `org-a`, which is onboarded to a shared Shipit instance and has its own `webhook_secret` configured under `Shipit.github(organization: 'org-a')`.
2. Attacker builds a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s `GithubApp`, and successfully verifies the signature against the attacker's own secret.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks`/`repository_name` resolve `Repository.from_github_repo_name('victim-org/victim-repo')`, and `stack.sync_github(expected_head_sha: params.after)` is enqueued for the **victim's** stack — despite the request never being signed by `victim-org`'s secret.
