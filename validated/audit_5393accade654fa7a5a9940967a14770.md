### Title
De-listing an asset as collateral (`can_collateral=false`) never deactivates existing supply positions — stamped LTV/LT keep backing new borrows - (File: contracts/controller/src/risk/params.rs)

### Summary
Each supply position stores its own copy of LTV, liquidation threshold, bonus, and fees, copied from the spoke listing at creation. The bug-class analog of "a deactivated passport still works because nothing checks revocation" is that `edit_asset_in_spoke` clearing `can_collateral` only gates *new* supplies via `require_can_supply`; every existing position keeps its stamped parameters and continues to count as collateral for health factor and new borrows indefinitely. No path zeroes or disqualifies a supply position whose listing was de-collateralized.

### Finding Description
- `require_can_supply` checks `asset_config.is_collateralizable` only on the deposit-entry path (`contracts/controller/src/positions/mod.rs:216-228`).
- Once a position exists, solvency is computed purely from the stored stamp: `calculate_account_risk_totals` uses `position.liquidation_threshold`, and the borrow limit uses `position.loan_to_value` (per `docs/reference/runbooks/liqvid-listing-params.md:362-371`).
- The permissionless refresh `update_account_threshold` (`risk/params.rs:124-144`) and the implicit restamp inside `enforce_post_pool_solvency` → `restamp_listed_supply_ltv` (`params.rs:44-64`) copy `config.loan_to_value` from `AssetConfig::from(&spoke_config)` — they never consult `is_collateralizable`, `paused`, or `frozen`. A de-collateralized listing still carries a nonzero `loan_to_value`, so the restamp actively *re-arms* the deactivated collateral rather than disabling it.
- `enforce_spoke_asset_flags` (`positions/mod.rs:257-278`) checks only `paused`/`frozen`/`no_seize`; `is_collateralizable` has no exit-time or solvency-time check. Confirmed by tests: deprecated-spoke and edited-listing positions retain stamped thresholds (`keeper.rs:343-364`, `spoke.rs:1199-1258`).
- Borrowing requires the *debt* asset to be borrowable (`require_can_borrow`), but the collateral side only needs the stamped parameters — so an account holding a now-disabled collateral asset can still call `borrow`, `multiply`, or `flash_position` against it.

### Impact Explanation
When governance de-lists an asset as collateral — the only reason to do so being that the asset is now considered unsafe to back debt — all existing positions continue to generate borrowing power and count toward HF at their stamped LTV/LT. An unprivileged holder of the de-listed asset can draw new borrows (`borrow`, `multiply`, `swap_debt` collateral legs) up to the old LTV against collateral the protocol explicitly revoked, and avoid liquidation per the stamped LT even while new deposits of that asset are rejected. If the asset was disabled because of depeg/manipulation/toxicity, this converts directly into under-collateralized debt and protocol insolvency. Medium.

### Likelihood Explanation
- Requires an admin `edit_asset_in_spoke` clearing `can_collateral` — a plausible emergency response (depeg, oracle degradation, supply-cap breach).
- After that, the attacker path is fully unprivileged and persistent: `borrow` and `multiply` on the debt side only check the debt asset's flags and the stamped-collateral HF. `update_account_threshold` (permissionless) cannot be used to neutralize the position either, since it writes the still-nonzero config LTV.
- Lower than a pure permissionless bug because it needs the admin flag change, but the dangerous state then persists for every existing holder. Medium-Low / Medium.

### Recommendation
Treat `is_collateralizable=false` like deactivation for existing positions, not just for new deposits:
- In `restamp_listed_supply_ltv` / `refresh_supply_risk_params`, write `loan_to_value = 0` and `liquidation_threshold = 0` (or exclude the position from `calculate_account_risk_totals`) when the live listing's `is_collateralizable` is false, so a de-listing actually revokes the collateral's voting power in HF.
- Alternatively, gate `enforce_post_pool_solvency` to skip non-collateralizable listings, and add a seize-only mode so the position remains withdrawable/liquidatable but contributes zero borrowing power.

### Proof of Concept
1. Alice supplies 50,000 USDC into spoke 1 (LTV 9700 / LT 9800 stamps onto her position).
2. Governance calls `edit_asset_in_spoke` with `can_collateral=false` for USDC (e.g., USDC depeg concern).
3. New USDC supplies revert with `NotCollateral`, but Alice's position is untouched.
4. Any keeper calling `update_account_threshold` rewrites her LTV from `config.loan_to_value` — still nonzero — via `restamp_listed_supply_ltv` (`params.rs:44-64`), which never reads `is_collateralizable`.
5. Alice calls `borrow` (or `multiply`): `require_can_borrow` only inspects the debt asset's listing; `enforce_post_pool_solvency` restamps her USDC LTV to the nonzero listing value and her HF is computed on the stamped LT. She draws debt against collateral the protocol revoked — the "deactivated passport" still votes.

Uncertainty: if `edit_asset_in_spoke` is expected to also set `ltv=0`/`threshold=0` atomically whenever `can_collateral` is cleared, the admin *can* mitigate this manually — but nothing enforces that pairing, and the flag alone is documented as the deactivation mechanism.
