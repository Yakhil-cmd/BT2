### Title
Indivisible (fixed-denomination) assets sent to an Autonomous Agent become permanently locked - ([File: aa_composer.js])

### Summary
When an Autonomous Agent (AA) receives an indivisible/fixed-denomination asset (ocore's closest analog to an NFT — coins of a capped denomination rather than a fungible balance), the AA's balance bookkeeping credits the asset, but the trigger-response composer that builds outgoing payment messages unconditionally strips out any payment referencing a fixed-denomination asset before authoring the response unit. There is no code path in `aa_composer.js` that can construct a valid outgoing payment for such an asset, so once credited, the coins can never be spent out of the AA — mirroring the reported HegicModule issue where the NFT is removed from account bookkeeping but only conditionally transferred back to its owner, leaving it permanently stuck in the contract.

### Finding Description
In `sendUnit()` inside `aa_composer.js`, when the composer processes each outgoing `payment` message it loads asset info and explicitly defers/skips completion of the payload for fixed-denomination assets: [1](#0-0) 

After all messages are processed, a second filter pass unconditionally removes any payment message whose asset is a fixed-denomination asset, regardless of what the AA's oscript logic intended to send: [2](#0-1) 

Meanwhile, when the AA receives a payment carrying such an asset in the trigger unit, `updateFinalAABalances()` credits the asset into `aa_balances` for that address just like any other asset, with no distinction that this balance can never be moved out again: [3](#0-2) 

This is the direct analog of the reported bug: an "in the money"/redeemable resource (the option NFT there, the indivisible asset here) is accounted for in the holder's ledger (`erc721ByContract` there, `aa_balances` here), but the code path responsible for returning/spending it back out (`liquidate`'s conditional transfer there, `sendUnit`'s payment-message filter here) has no branch that can ever release fixed-denomination assets. The `balance[asset]` formula getter and state vars will happily reflect a nonzero balance for the indivisible asset, encouraging AA authors to write logic assuming it is spendable, while `oscript`/`ojson` code that generates a `payment` message for such an asset is silently dropped at composition time — the AA is never notified of the failure to spend, and no bounce is triggered from this specific filtering step (a bounce only happens if the message list becomes completely empty).

### Impact Explanation
Any indivisible/fixed-denomination asset paid to an AA is permanently frozen and unrecoverable via any oscript-authored payment: it cannot be forwarded to the sender, definer, or anyone else by the AA's own logic. This constitutes AA fund loss/freezing of user assets sent into any deployed AA that accepts (or does not explicitly reject) fixed-denomination assets, since the ocore engine — not the AA author — silently discards the outgoing message rather than surfacing the constraint as a bounce, making the loss invisible to the AA's own error-handling logic (identical in spirit to the option NFT being silently retained by `MarginAccount` instead of returned or flagged).

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires a user or another AA to send an indivisible/NFT-style asset to an AA address, and it requires the AA author not to have anticipated/rejected such deposits explicitly (which is easy to overlook since ocore documentation for AAs primarily discusses divisible/base assets). Given ocore's ecosystem does support and encourage issuance of indivisible assets, and AAs are commonly used as generic escrow/exchange contracts, accidental or adversarial deposit of such an asset into an AA is a realistic trigger, with no privileged access required — any regular unit author can send the payment.

### Recommendation
- Reject fixed-denomination assets in payments received by an AA at validation time (bounce the trigger), OR
- Allow AAs to author valid outgoing messages for fixed-denomination assets (implement `completePaymentPayload` support for indivisible coin selection within `aa_composer.js`), so an AA can redistribute or refund such deposits, and
- Ensure the message-filtering step for fixed-denomination assets triggers a bounce/error surfaced to the AA (rather than silently dropping the message), so AA authors are not misled into believing a payment succeeded when it was dropped.

### Proof of Concept
Conceptual reproduction (would need to be exercised against `aa_composer.test.js`/`dryRunPrimaryAATrigger` harness):
1. Issue an indivisible (fixed-denomination) asset, e.g. an NFT-like collectible coin, using `indivisible_asset.js`.
2. Deploy a simple AA whose `messages` case accepts any payment and, upon receiving the indivisible asset, attempts to immediately forward it back to `trigger.address` via a `payment` message with `asset: "{trigger.output[[asset!=base]].asset}"`.
3. Send a trigger unit carrying that indivisible asset to the AA.
4. Observe: `updateFinalAABalances()` credits `aa_balances` for the AA address with the asset (visible via `balance[asset]` in a later trigger), but the response unit generated by `sendUnit()` never contains the intended outgoing payment message for that asset — confirmed by the filter at `aa_composer.js:1356-1361` which drops any payment referencing a fixed-denomination asset before the unit is built. The asset remains stuck in the AA's balance indefinitely with no oscript-level mechanism to move it out.
