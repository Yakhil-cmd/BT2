### Title
Webhook signature verification keys off attacker-suppliable `organization`/`repository.owner` field while handlers act on the unrelated `repository.full_name`/`team.id` fields, allowing a Shipit-configured organization to forge events for any other organization it shares the engine with - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify an incoming payload against by reading `repository.owner.login`, falling back to `organization.login`, both fully attacker-controlled fields inside the raw, unsigned-at-parse-time JSON body. `Shipit::Webhooks::Handlers::Handler`, however, resolves which `Stack`/`Team` records to mutate using a *different* field, `repository.full_name` (or `team.id` for membership events). Nothing forces these fields to agree. This is the same class of bug as the reported UsualX issue: two code paths that are supposed to compute/verify the "same" value independently, using different inputs, so satisfying one does not guarantee the other is consistent.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) [2](#0-1) 

It picks the GitHub App/webhook config with `Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')`. The signature is only checked against *that* organization's `webhook_secret`.

Meanwhile, event handlers determine the target `Stack`(s) using an entirely different, independently attacker-controlled field: [3](#0-2) 

and, for `push` events, further scope by `branch`: [4](#0-3) 

For `membership` events, the target `Team` is resolved purely by attacker-supplied `team.id`/`team.slug` with `organization` used only to label a freshly created team: [5](#0-4) 

The binding that should hold is: **organization authenticated (`repository_owner` used for `verify_webhook_signature`) == repository/team actually written (`repository.full_name` / `team.id`)**. Because the raw JSON body is entirely attacker-crafted (this is a webhook endpoint that only checks an HMAC over the body, not any structural cross-field consistency), an operator who legitimately administers *their own* GitHub organization/App configured in this same Shipit instance (a normal, unprivileged multi-tenant scenario supported by `secrets.*.yml`'s per-organization `github:` map) knows their own org's `webhook_secret`. They can:

1. Set `repository.owner.login` (or `organization.login`, if `repository.owner` is omitted) to their **own** organization "A" — the one whose `webhook_secret` they legitimately possess.
2. Set `repository.full_name` (used only by the handler layer) to point at a *different* organization "B"'s repository/stack that already exists in the same Shipit deployment.
3. Sign the whole raw body with A's `webhook_secret`.

`verify_signature` loads `Shipit.github(organization: "A")` and validates successfully, because the HMAC matches A's secret over the body the attacker itself produced. The `push`/`status`/`check_suite` handler code then resolves stacks purely via `repository.full_name == "B/..."`, and drives `Stack#sync_github`, `Status` updates, or check-run refreshes for organization B's stack — none of which the attacker has any legitimate GitHub-side permission over.

The `membership` handler is more severe: it trusts `params.team.id`/`slug` unconditionally (only using `organization.login` to label a *new* team) and will happily `add_member`/`remove` members on any pre-existing `Team` record matching an attacker-chosen `github_id`, including a `Team` that backs `Shipit.github_teams` (the set of teams used by `Shipit::Authentication#force_github_authentication` and `User#authorized?` to authorize a user's *login* to the whole Shipit UI): [6](#0-5) [7](#0-6) 

By signing a forged `membership` payload with organization A's own webhook secret, but supplying `team.id` equal to the numeric GitHub team ID of an authorization-gating team belonging to organization B, and `member.login` equal to the attacker's own GitHub login, the attacker's `User` record gets added as a `Membership` of that `Team`. On next login, `current_user.authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, which will now be true for the attacker — granting them authenticated access to the whole Shipit application (stacks, deploy triggers, task logs) despite never actually belonging to organization B's GitHub team.

### Impact Explanation
This breaks the equality "organization whose secret authenticated the webhook == organization/team the webhook payload is permitted to mutate." The concrete outcomes:
- Forged `push`/`status`/`check_suite` events for any stack already configured in the Shipit instance, triggering `sync_github`, status writes and check-run refreshes attributable to organization B, using only organization A's credentials.
- Forged `membership` events can add an arbitrary GitHub-identified `member.login` to any pre-existing `Team` by numeric `github_id`, including a team listed in `Shipit.github_teams`, which is Shipit's authorization gate for logging in — a direct escalation into `Shipit.github_teams` authorization, matching the "High" impact bucket defined by the rules.

### Likelihood Explanation
Requires only: (a) the operator's own organization is configured in the same multi-tenant Shipit deployment (documented, supported configuration via `secrets.*.yml`'s per-org `github:` map), which is not a privileged capability relative to other tenants — each org config is independent and the attacker only needs their own; and (b) knowledge of a target team's numeric GitHub `id` or a target repository's `full_name`, both of which are public/discoverable via the GitHub API. No Shipit session, `ApiClient` token, or GitHub App private key is required — only the webhook endpoint (`config/routes.rb` mounts `WebhooksController` unauthenticated aside from the per-org HMAC check) and the ability to craft an HMAC with a secret the attacker legitimately holds for their own tenant.

### Recommendation
Cross-validate the field used for signature-organization selection against the field(s) used by the handlers before dispatching:
- After `verify_signature` succeeds, require that `repository.owner.login` (or `organization.login`) equal the owner segment of `repository.full_name` used by `Handler#repository_name`, rejecting mismatches with 422.
- In `MembershipHandler`, do not blindly `find_or_create_team!`/mutate an existing `Team` purely by attacker-supplied `team.id`; verify `params.organization.login` matches the authenticated organization used in `verify_signature`, and that it matches the `Team#organization` already on file for that `github_id` before allowing membership mutation.
- More generally, treat `verify_webhook_signature`'s selected organization as the single source of truth for every field the handler subsequently trusts, rather than re-reading independently attacker-controlled JSON fields deeper in the handler.

### Proof of Concept
Given Shipit configured for two organizations `org-a` (attacker-administered, webhook secret known to attacker) and `org-b` (victim, has an existing `Team` with `github_id: 999` referenced in `Shipit.github_teams`, and existing `Stack` for `org-b/victim-repo`):

```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<HMAC-SHA1 of body using org-a's webhook_secret>

{
  "action": "added",
  "team": { "id": 999, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "org-a" },
  "member": { "login": "attacker-github-login" }
}
```

`repository_owner` resolves to `"org-a"` (via `organization.login` fallback, since no `repository` key is present), so `Shipit.github(organization: "org-a").verify_webhook_signature` succeeds using the attacker's own secret. `MembershipHandler#find_or_create_team!` then finds the existing `Team` with `github_id: 999` (org-b's authorization team) and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`, granting the attacker membership in org-b's authorization-gating team, and thus login access via `User#authorized?`.
