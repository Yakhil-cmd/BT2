### Title
`StatusHandler#process` updates commits by SHA across all repositories, letting a status from an unrelated repo clear a victim stack's blocking condition - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves commits to update via `Commit.where(sha: params.sha)`, with no filter on the payload's `repository.full_name`, unlike every other handler that scopes work through the `Handler#stacks` helper (which resolves `Repository.from_github_repo_name(repository_name)`). A correctly-signed GitHub `status` webhook for *any* repository whose commit history happens to share a SHA with a commit tracked in a completely different stack (e.g. a fork, a shared upstream commit, a rebase-preserved commit, or any repo under the same GitHub App/organization) will create a `Status` row on the victim's commit, and can flip `Commit#blocked?` for an unrelated stack's deploy queue.

### Finding Description
The broken binding is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` is assumed but never checked for `StatusHandler`.

Trace:
- `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) dispatches `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` after `verify_signature`, which only checks that the signature matches the secret for `Shipit.github(organization: repository_owner)` — i.e. it verifies the webhook came from *some* GitHub org known to Shipit, not that the SHA inside belongs to that org's repository.
- `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) is the intended scoping mechanism: `Repository.from_github_repo_name(repository_name)&.stacks`, where `repository_name` comes from `payload.dig('repository', 'full_name')`. `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and `CheckSuiteHandler` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`) both correctly scope through `stacks.where(...)` before touching any commit.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does not use `stacks` at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This looks up commits globally by SHA across every `Stack`/`Repository` Shipit tracks, and writes a `Status` (`Commit#create_status_from_github!` → `Status.replicate_from_github!`, `app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:24-33`) for each matching commit regardless of which repository the signed webhook payload actually describes.

Exploit flow:
1. Victim stack `V` has `blocking_statuses` configured (`stack.blocking_statuses` non-empty) and a commit `B` (older, undeployed) whose blocking-context status is currently missing/pending, making `B.blocking?` true and thus `Commit#blocked?` true for a newer victim commit `C` (`app/models/shipit/commit.rb:231-237`, matching the pattern in the existing test `"#deployable? is false if a blocking status is failing on a previous undeployed commit"`, `test/models/commits_test.rb:591-599`).
2. Attacker controls a separate GitHub repository `A/attacker-repo` that is also tracked by Shipit (or is under an org whose GitHub App/webhook secret is valid for signature verification) and whose history contains a commit with the exact same SHA as `B` (via fork, shared merge/rebase commit, or vendored history — SHAs are content hashes, so identical commit metadata across repos naturally coincide; no SHA-1 collision attack is required for the exploit's precondition to hold).
3. Attacker pushes/creates that commit in their own repo and drives a real GitHub CI or manually simulated `status` event stating `state: success` for `B`'s SHA and a `context` in `V`'s `blocking_statuses` list. Because the payload is legitimately signed by GitHub for the attacker's own org/repo, `verify_signature` passes.
4. `StatusHandler#process` finds `Commit.where(sha: B.sha)`, which includes victim commit `B` (belonging to stack `V`, a repository that never authenticated this payload), and calls `B.create_status_from_github!(params)`, creating a `success` `Status` on `B` with the blocking context.
5. `B.blocking?` (`Status::Common#blocking?`, `app/models/shipit/status/common.rb:46-48`) is now false because `success?` is true, so `Commit#blocked?` for `C` (`app/models/shipit/commit.rb:231-237`) re-evaluates to `false`, clearing the safety gate for stack `V`'s deploy queue — without any action from `V`'s repository or its CI.

Existing guards do not stop this: `verify_signature` only authenticates the *origin org*, not that the SHA inside belongs to that org's repository; `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not repository ownership; there is no `stacks`/`repository_name` check in `StatusHandler` as there is in `PushHandler`/`CheckSuiteHandler`.

### Impact Explanation
A payload correctly authenticated for repository `A` mutates commit/state data belonging to a stack that tracks a different repository (`V`), satisfying the "payload for one repository mutating another's stack/commit" Critical category. Concretely, it clears a `blocking_statuses` safety gate (`Commit#blocked?`), which is consumed by `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) and `UndeployedCommit#deploy_disallowed?`/`#deploy_state` (`app/models/shipit/undeployed_commit.rb`), directly influencing whether an otherwise-blocked commit becomes eligible for automatic or manual deploy — an unauthorized bypass of a deploy safety gate for a stack the attacker does not own. This is repeatable against any stack/commit whose SHA the attacker can reproduce in a repository they control (forks, shared history, vendored commits), and scales to every stack tracked by the Shipit instance that shares commit history with an attacker-reachable repository.

### Likelihood Explanation
Preconditions: the victim stack must have `blocking_statuses` configured in its `.shipit.yml` (`ci.blocking`, `app/models/shipit/deploy_spec.rb:202-204`), and have an undeployed commit currently blocked purely due to a missing/failing status in that blocking context. The attacker needs a GitHub repository whose commit history overlaps in SHA with the victim's tracked commit (most realistically via forking the victim's repo, which is a zero-cost, unprivileged action any GitHub user can take, and is common since many Shipit deployments track upstream + fork relationships or reuse shared merge commits). No Shipit credentials, GitHub App keys, or webhook secret are needed by the attacker — GitHub itself signs the webhook for the attacker's own repository/organization. This makes the attack low-cost and repeatable.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: resolve the commit only within stacks belonging to `Repository.from_github_repo_name(repository_name)` (i.e., use the existing `stacks` helper), for example:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a status webhook can only mutate commits that belong to the repository that the verified payload actually describes.

### Proof of Concept
Minitest plan (model-level, no live GitHub, mirroring `test/models/commits_test.rb:591-599` but exercised through the handler instead of a direct `Status#create`):

```ruby
test "StatusHandler does not clear a blocking status for a commit belonging to a different repository" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine" or similar
  victim_stack.stubs(:blocking_statuses).returns(['ci/blocking'])

  blocking_commit = shipit_commits(:soc_second) # belongs to victim_stack
  blocking_commit.statuses.delete_all
  assert_predicate blocking_commit, :pending?
  assert_predicate blocking_commit, :blocking?

  victim_commit = shipit_commits(:soc_third)
  assert_predicate victim_commit, :blocked? # gate is up before the forged event

  attacker_payload = {
    'sha' => blocking_commit.sha, # SHA shared with an attacker-controlled repo
    'state' => 'success',
    'context' => 'ci/blocking',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' } # NOT victim_stack's repository
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  blocking_commit.reload
  victim_commit.reload

  # BOTH SIDES OF THE BINDING, evaluated after the forged webhook:
  refute_equal 'attacker/unrelated-repo', blocking_commit.stack.repository.full_name # binding is false: repos differ
  assert_predicate blocking_commit, :success?          # status was written anyway (BUG)
  refute_predicate blocking_commit, :blocking?         # blocking gate cleared (BUG)
  refute_predicate victim_commit, :blocked?            # victim stack's safety gate defeated (BUG)
end
```
Expected today (vulnerable): the assertions pass, proving the forged cross-repo status clears the blocking gate. After applying the recommended fix (scoping via `stacks`), `blocking_commit.statuses` should remain unchanged and `victim_commit.blocked?` should stay `true`.
