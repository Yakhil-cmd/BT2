### Title
Webhook signature verification keys off an attacker-controlled `repository.owner.login`/`organization.login` field that is decoupled from the `repository.full_name` the event handlers actually act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization secret to validate the HMAC against by reading `repository.owner.login` (or `organization.login`) straight out of the unauthenticated JSON body, before any signature has been checked. The event handlers that are subsequently invoked with the full, still-unverified payload act on a *different* field — `repository.full_name` — to resolve the target `Stack`. Nothing binds "the organization whose secret was used to authenticate this request" to "the repository the handlers are about to mutate." This is the exact bug class from the MapleLoan report: a privileged operation (accepting and acting on webhook data) is gated on one field while a different, unauthenticated field determines what is actually written.

### Finding Description
`repository_owner` is computed from the raw, unverified body before `verify_signature` runs: [1](#0-0) 

That value is used to pick the GitHub App config (and its `webhook_secret`) used to check the signature: [2](#0-1) 

`GithubApp#verify_webhook_signature` explicitly treats a blank `webhook_secret` as "always verified": [3](#0-2) 

A blank `webhook_secret` per organization is a documented, supported configuration (used e.g. in local/dev setups): [4](#0-3) 

Once `verify_signature` passes, the *entire* raw payload (not scoped to the organization that was authenticated) is handed to every registered handler for the event: [5](#0-4) 

Handlers resolve the target `Stack`/`Commit` using `repository.full_name` from that same payload, which was never covered by the signature check — the check only validated the request against the secret belonging to whatever `repository.owner.login` the attacker chose. The equality that should hold — `organization authenticated == organization whose repository is mutated` — is broken: the code enforces `organization authenticated == Shipit.github(organization: attacker_supplied_owner)`, while the write path uses `repository.full_name`, an independently attacker-controlled string.

### Impact Explanation
If any organization configured in this Shipit installation has no `webhook_secret` set (an explicitly supported configuration per the shipped secrets template), an unauthenticated attacker can send a forged webhook whose `repository.owner.login`/`organization.login` names that unsecured org (so `verify_webhook_signature` short-circuits to `true`), while `repository.full_name` in the same payload names a *different*, secured stack/repository. The handler dispatch loop then processes push/status/check_suite/membership events for that unrelated, secured repository — e.g., queuing `GithubSyncJob`, updating commit CI status, or (for stacks with `continuous_deployment: true`) triggering an automatic deploy — without ever presenting a valid signature for the org that actually owns the targeted stack. This crosses the "unauthorized deploy" / "cross-repository writes" bar.

### Likelihood Explanation
Exploitability depends on the deployment having at least one configured GitHub organization/App without a `webhook_secret` (documented as valid, zero-config setup) alongside another organization/stack the attacker wants to target. In single-tenant installs where every org has a secret, this is not exploitable without already possessing a valid secret. This is a real but configuration-dependent gap in the trust binding rather than a universally exploitable bug.

### Recommendation
Bind signature verification to the same identity that is used for the mutation: after determining `event` and `repository_owner`, re-derive the target repository/stack strictly from data already tied to the authenticated organization (e.g., require `repository.full_name`'s owner segment to equal the `repository_owner` that was used to select the webhook secret), and reject (422) any payload where they differ. Additionally, treat a missing/blank `webhook_secret` for any organization as "verification disabled for that organization only" and never let it be used to authorize events referencing repositories belonging to other organizations.

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `UnsecuredOrg` (no `webhook_secret`) and `SecuredOrg` (has a stack, `webhook_secret` set, `continuous_deployment: true`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "UnsecuredOrg" },
    "full_name": "SecuredOrg/target-repo"
  },
  "after": "<attacker-chosen sha>",
  "ref": "refs/heads/master"
}
```
3. `verify_signature` calls `Shipit.github(organization: "UnsecuredOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (absent/garbage) `X-Hub-Signature` header.
4. The push handler processes the payload against `SecuredOrg/target-repo`, enqueuing `GithubSyncJob`/triggering deploy logic for a stack the attacker never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
