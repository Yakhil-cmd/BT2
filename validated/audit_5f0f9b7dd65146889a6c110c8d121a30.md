### Title
Uncaught exception in `data_feed` formula lookup crashes nodes evaluating an AA trigger - ([File: data_feeds.js])

### Summary
The external CVE (CVE-2024-25583) describes a crafted upstream response causing an unhandled condition that crashes the PowerDNS Recursor when recursive forwarding to an external server is configured. The analogous "trust an external, attacker-influenced data source" pattern in ocore is an Autonomous Agent (AA) reading a `data_feed` value from oracle addresses it is configured to trust. A crafted pair of concurrent, unstable data-feed posts from the configured oracle addresses can drive the AA's `data_feed[]` formula evaluation into a code path that performs a raw synchronous `throw`, which is not caught anywhere in the call chain, crashing the node process that is evaluating the AA trigger.

### Finding Description
When a formula evaluates `data_feed[...]` inside an AA (trigger/state-update formula), `bAA` is `true`, and this value is passed straight through as the `unstable_opts` parameter of `dataFeeds.readDataFeedValue`: [1](#0-0) 

Inside `readDataFeedValue`, when `unstable_opts` is truthy but not the string `'all_unstable'` (exactly the case for `bAA === true`), the function scans all currently-unstable messages from the oracle addresses listed in `arrAddresses` and, if more than one candidate `data_feed` message matches the requested feed name/value and `ifseveral` is not `'abort'`, it sorts the candidates by `latest_included_mc_index` then by `level`: [2](#0-1) 

If two competing candidate messages (posted by two different oracle addresses in the same `oracles` list, or the same address with two units) happen to tie on both `latest_included_mc_index` and `level` — which is a normal, attacker-inducible situation for two units posted in parallel DAG branches — and `bIncludeAllUnstable` is `false` (guaranteed for `bAA` triggers because `unstable_opts` is `true`, not `'all_unstable'`), the comparator executes:
```js
throw Error("can't sort candidates "+a+" and "+b);
```
This is a synchronous `throw` executed from inside `Array.prototype.sort`'s comparator callback, deep inside AA formula evaluation (`evaluate` → `getDataFeed` → `dataFeeds.readDataFeedValue`). This call chain is invoked from `aa_composer.js`'s `handleTrigger`/`replace`/`evaluateAA` functions via `formulaParser.evaluate`, none of which wrap the formula evaluation in a `try/catch` that would gracefully convert this into an AA bounce error (unlike malformed-formula errors, which are returned via the `cb(err)` callback pattern used throughout `evaluation.js`). Because it is a genuine JS `throw` rather than an error passed to a callback, it propagates as an uncaught exception through the async call stack, which in Node.js typically terminates the process (or is only caught by a top-level `process.on('uncaughtException')` handler if present, which would still abort in-flight processing).

Every full/AA-processing node in the network that has to evaluate this same AA trigger (since AA execution is deterministic and required for stability) hits the identical code path and the identical tie condition, so the crash is fully synchronized network-wide, not a local anomaly.

### Impact Explanation
Any AA definition that uses a `data_feed[oracles=...]` formula with a multi-address oracle list (a common, encouraged pattern to avoid single-oracle trust) and does not set `ifseveral='abort'` is exposed. An attacker who controls, or can induce timing collisions between, two of the configured oracle addresses (or even relies on natural concurrent posting by independent oracles) can produce two unstable `data_feed` messages that tie in `latest_included_mc_index` and DAG `level`. Triggering that AA then crashes every node that processes the trigger — a network-wide denial of service preventing confirmation of that AA's units (and, if the crash affects the whole node process rather than an isolated worker, all further unit processing on that node). This matches the "network unable to confirm new units" impact class.

### Likelihood Explanation
Reaching this requires: (1) an existing AA using `data_feed[]` with multiple oracle addresses and `ifseveral` left at its default (`'last'`), which is a normal, likely-used configuration; (2) two data-feed-posting units from within the oracle set landing at the same `latest_included_mc_index` and same DAG `level` while both are still unstable. Level ties between independently authored units in parallel branches are a routine DAG occurrence rather than a rare edge case, and an active attacker who controls (or colludes with) oracle addresses, or simply races two legitimate oracle posts, can reliably reproduce the tie. No special privilege beyond being able to post a trigger unit to the AA (fully unprivileged) and controlling/timing oracle posts is required.

### Recommendation
Replace the `throw Error(...)` in the sort comparator (`data_feeds.js`, inside `readDataFeedValue`) with a deterministic, non-throwing tie-break (e.g., compare by `unit` hash or another canonical, stable field) so that ties never produce an unhandled exception, and ensure the result is still deterministic across all nodes. Additionally, audit all formula-evaluation code paths reachable from AA execution for other raw `throw` statements that are not converted to callback errors, since `evaluate()`'s architecture expects errors to be reported via callbacks, not exceptions.

### Proof of Concept
1. Define/select an AA whose formula includes `data_feed[oracles="ORACLE1:ORACLE2", feed_name="price"]` (default `ifseveral` = `'last'`).
2. Have `ORACLE1` and `ORACLE2` each post a `data_feed` unit with the same `feed_name` (and a matching/compatible value) as parallel, independent DAG branches such that both units end up unstable with identical `latest_included_mc_index` and identical `level` (achievable by posting them at the same time referencing sibling parents at the same DAG depth).
3. Send a trigger unit to the AA before either data-feed unit stabilizes.
4. Every node evaluating the trigger executes `formula/evaluation.js`'s `data_feed` case → `dataFeeds.readDataFeedValue` → the `arrCandidates.sort` comparator, hits the tie condition, and throws an uncaught `Error("can't sort candidates ...")`, crashing the node process handling AA execution. 	if (bIncludeUnstableAAs) {
		var arrCandidates = [];
		for (var unit in storage.assocUnstableMessages) {
			var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];

				if (value === null || value === feed_value || value.toString() === feed_value.toString())
