### Title
Global, repository-unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` allows cross-tenant status forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by `sha` alone across the entire `Commit` table, ignoring the `repository`/organization that the webhook signature was verified against. Since git SHA1s are content-addressed and legitimately shared across forks and cherry-picks of the same commit, an attacker who owns a valid webhook secret for their own GitHub organization can cause a forged CI status to be attached to a completely unrelated `Stack`'s commit, as long as that commit happens to share a SHA (e.g., because the attacker forked the victim's repository).

### Finding Description
The claimed binding is: `organization whose secret verified the payload == organization owning the Commit row mutated by sha lookup`. Tracing the code shows this binding is **not enforced**.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from `params.dig('repository','owner','login')` in the payload body. This confirms only that the caller controls a webhook secret for the organization named in `repository.owner.login` in the payload — it says nothing about which `Commit`/`Stack` rows the handler is allowed to touch. [1](#0-0) 

- The base `Handler` class already provides the correct scoping primitive: `stacks` resolves `Repository.from_github_repo_name(repository_name)&.stacks`, deriving the repository strictly from `payload.dig('repository','full_name')`. [2](#0-1) 

- `StatusHandler` never uses this `stacks` scoping helper. Its `params` schema doesn't even capture the `repository` field, and `process` runs a completely global lookup: [3](#0-2) 

- `Commit#create_status_from_github!` then unconditionally writes a new `Status` row using attacker-supplied `state`/`description`/`target_url`/`context`: [4](#0-3) 

**Exploit flow:** An attacker owns/controls GitHub organization `attacker-org` with a Shipit-registered webhook secret (entirely their own configuration — no victim secrets needed). The attacker forks the victim's public repository (or otherwise ends up with a repository that shares a commit SHA with the victim's tracked stack, e.g., via cherry-pick or shared upstream history — a normal, unprivileged, extremely common occurrence, not a hash collision attack). The attacker pushes/references that shared commit in their own fork and sends (or GitHub sends, if the attacker configures the webhook themselves) a `status` event to `POST /webhooks`, signed correctly with `attacker-org`'s own webhook secret, with `sha` equal to the shared commit and `repository.owner.login: "attacker-org"`. `verify_signature` passes because the signature is valid for `attacker-org`. `StatusHandler#process` then finds **every** `Commit` row across **all** stacks/organizations with that `sha` — including the victim's — and calls `create_status_from_github!` on each, writing the attacker's chosen `state` (e.g., `"success"`), `description`, and `target_url` onto the victim's commit.

None of the existing guards prevent this: `verify_signature` only authenticates the caller as controlling `attacker-org`'s secret, not as being authorized to mutate commits belonging to other organizations; the `ExplicitParameters` schema in `StatusHandler` has no `repository` scoping requirement; and the `stacks`/`repository_name` scoping helper defined in the base `Handler` class is simply not used by this handler.

### Impact Explanation
A cross-tenant write: an attacker who authenticates only as their own organization can inject a fabricated CI `Status` (including `state: "success"`) onto a `Commit` belonging to a victim organization's `Stack` they do not control and never authenticated for. Since `Commit#deployable?` and continuous-delivery gating (`schedule_continuous_delivery`) key off status/state, this can influence deploy gating decisions for the victim's stack. This is repeatable against any commit SHA the attacker's repository happens to share with a victim (forks of public repos are a common, low-cost vector), and the blast radius spans all tenants hosted on the same Shipit instance, matching the "payload for one repository mutating another's stack/commit" Critical category.

### Likelihood Explanation
Preconditions are low-cost and fully within attacker capability: register any GitHub organization/repository with Shipit (or use one already registered), configure/obtain a legitimate webhook secret for it (attacker's own, via normal Shipit setup), and identify a commit SHA shared with a victim stack — trivially achievable by forking a victim's public repository, since forks share identical SHAs for common history. No victim secrets, sessions, or elevated roles are required. This is realistically and repeatably exploitable, not merely theoretical.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository indicated by the verified webhook payload, mirroring the `stacks` helper already provided by the base `Handler` class (e.g., restrict `Commit.where(sha: params.sha)` to `stacks.flat_map(&:commits)` or add a `stack_id`/`repository` join constraint derived from `payload.dig('repository','full_name')`), so a status can only be applied to commits belonging to stacks whose repository matches the webhook's verified organization/repository.

### Proof of Concept
Minitest plan (no live GitHub calls):
1. Create `stack_a` for repository `org-a/repo` and `stack_b` for repository `org-b/repo` (different `Repository`/`Stack` rows).
2. Create `commit_a` under `stack_a` and `commit_b` under `stack_b` with the identical `sha` value (simulating a shared commit from a fork).
3. Build a GitHub `status` webhook JSON payload with `sha` equal to that shared sha, `state: "success"`, and `repository.owner.login` = `"org-a"`.
4. Stub/configure `Shipit.github(organization: "org-a")` webhook secret so the payload's HMAC signature validates for `org-a` only (attacker's own legitimate secret) — do not configure or use `org-b`'s secret anywhere.
5. `POST /webhooks` with the correctly signed payload and `X-Github-Event: status`.
6. Assert: `commit_a.statuses.reload` has a new `Status` with `state: "success"` (expected, org-a authenticated its own repo) **and** `commit_b.statuses.reload` also has a new `Status` with `state: "success"` — the assertion that fails the security expectation: `commit_b.stack.repository.owner` (`"org-b"`) was never the organization that authenticated the request (`"org-a"`), yet `commit_b` was mutated. Before the fix, both assertions pass (vulnerability confirmed); after scoping `process` to the verified repository, only `commit_a` receives the new status and `commit_b.statuses.reload` remains unchanged.
