## Title
Share-price (pricePerShare) manipulation via first-depositor / balance-donation attack in the market-maker AA template's `mm_asset` issuance logic - (File: `test/samples/uniswap_like_market_maker.oscript`)

### Summary
The bundled Uniswap-like market-maker AA template mints a pooled "LP-share" asset (`mm_asset`) whose issuance rate is derived from the ratio of the AA's *raw* on-chain balances (`balance[base]`, `balance[$asset]`) to the tracked outstanding share supply `var['mm_asset_outstanding']`. Because any user can pay bytes/asset directly to the AA address without triggering the `invest` branch, an attacker can (1) become the first depositor with a negligible deposit, minting a tiny amount of `mm_asset`, then (2) "donate" a large, disproportionate balance directly to the AA to inflate the implied price per share, causing later legitimate depositors' minted-share calculation to round down to zero while their funds are still absorbed into the pool balance. This is the same root cause as the Sherlock H-1 report against `Vault.sol`: share price is derived from a spendable pool balance that can be inflated by direct donation, and `round()` precision loss lets the attacker steal subsequent depositors' funds.

### Finding Description
In the AA "invest in MM" case: [1](#0-0) 

* `$asset_balance` / `$bytes_balance` are read from the AA's live `balance[...]` (post-trigger balances minus the current trigger's own contribution) — i.e., the *total* balance held by the AA, not a value tied 1:1 to `mm_asset_outstanding`.
* When either balance is zero ("initial deposit"), the *entire* current `balance[base]` is issued as shares to the first depositor: [2](#0-1) 
* For subsequent deposits, the number of new shares minted is `round($investor_share_of_prev_balance * var['mm_asset_outstanding'])`, where `$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance`: [3](#0-2) 

Crucially, `$bytes_balance`/`$asset_balance` reflect the AA's *entire* wallet balance, which can be increased by anyone simply sending a payment to the AA address that does **not** match any `if` condition (e.g., an amount below `1e5`, or one with `trigger.output[[asset=$asset]] == 0` when `mm_asset_outstanding` doesn't exist yet, or any output the case-matching logic doesn't intercept) — such a payment is silently absorbed into `balance[]` without any state update, i.e., a pure balance donation that does not mint any `mm_asset`. This is exactly analogous to sending extra `LINK` tokens directly to `Vault.sol` in the original report to inflate `pricePerShare` from `convertToShares()`.

Attack sequence, mirroring the H-1 report:
1. Attacker sends `trigger.data.define` to create `mm_asset` (case "define share asset").
2. Attacker deposits a minimal amount (e.g. 100001 base + 1 unit of `$asset`) to trigger "initial deposit": `$issue_amount = balance[base]` (≈100001), minting ≈100001 `mm_asset` while owning nearly all outstanding shares.
3. Attacker (or an accomplice) sends a large, disproportionate donation of `base`/`$asset` directly to the AA address in a way that bypasses the "invest" `if` condition (or simply exploits rounding thresholds), inflating `$bytes_balance`/`$asset_balance` far beyond what `mm_asset_outstanding` represents.
4. A genuine investor then calls "invest in MM" with a normal-sized deposit. Because `$bytes_balance` has been inflated, `$investor_share_of_prev_balance = trigger.output[[base]] / $bytes_balance` becomes extremely small, and `round(...)` rounds `$issue_amount` down to `0`.
5. The victim's payment message for `mm_asset` still executes with `amount: 0`... more importantly, the AA still records `trigger.output[[asset=base]]` and matching `$asset` amount into its balance (the payment is accepted by the trigger unit itself before the AA responds), so the victim's real funds are absorbed into the pool while they receive `0` (or a negligible) amount of `mm_asset`. The attacker can later "divest" and redeem a share of the now-larger pool using their disproportionately large `mm_asset_outstanding` allocation from step 2, capturing the victim's deposited value: [4](#0-3) 

This is executed entirely through the standard, unprivileged AA trigger path — any address can send a payment message that the `aa_composer.js` trigger handler will evaluate against this oscript, exactly the "AA definitions and triggers, oscript/ojson evaluation" reachable surface.

### Impact Explanation
A legitimate depositor into this market-maker AA can lose part or all of their deposited bytes/asset to an earlier depositor who manipulated the share/balance ratio, exactly as described in the original report ("Users may suffer a significant portion or even 100% of the funds they deposited"). Because `mm_asset` is a real, transferable asset backed by AA-held funds, this constitutes concrete unauthorized fund loss for future depositors and disproportionate profit for the attacker upon divestment — a Medium/High severity AA fund-loss issue.

### Likelihood Explanation
The attack requires only: (1) being first (or an early) depositor, which any unprivileged user racing to interact with a freshly deployed instance of this template can achieve, and (2) sending an additional payment that increases the AA's balance without matching the "invest" `if` branch (trivial — e.g. a below-threshold amount, or an asset-only/base-only payment that falls through to no state change). Both steps are ordinary, permissionless trigger submissions, so the likelihood is high whenever this AA template (or a derivative copied from it, since it is shipped as a reference implementation) is deployed and used by real depositors.

### Recommendation
- Track pool reserves in AA state variables (e.g., `var['bytes_reserve']`, `var['asset_reserve']`) that are updated only inside the "invest"/"divest"/"exchange" branches, instead of reading the live `balance[...]` which includes any unaccounted donations.
- Require a minimum `mm_asset` issuance amount on first deposit and/or permanently lock a portion of the first mint (e.g., to a null/treasury state var) so the initial price-per-share cannot be trivially set to an extreme value by a single wei-level deposit.
- Reject/refund any incoming payment that does not match a defined case (make the fallback case explicitly bounce non-matching payments) rather than silently absorbing them into the AA's spendable balance, closing the "donation" vector used to inflate the ratio.
- Guard the minted-share formula so that `$issue_amount` cannot be `0` for a nonzero deposit; bounce if rounding would yield 0 shares.

### Proof of Concept
Using the shipped template as-is:
1. Post `trigger.data.define` to the AA → creates `mm_asset`, `var['mm_asset']` set.
2. Post a trigger with `trigger.output[[asset=base]] = 100001` and `trigger.output[[asset=$asset]] = 1` → hits "initial deposit" branch (`$asset_balance==0 OR $bytes_balance==0` before this trigger) → `$issue_amount = balance[base] ≈ 100001`; attacker now owns `var['mm_asset_outstanding'] = 100001` shares 1:1 with pool.
3. Post a second trigger from the attacker sending, e.g., `trigger.output[[asset=base]] = 99999` (below `1e5` threshold, so it does not match the "invest" `if`, nor "exchange" cases if `$asset` amount also fails their conditions) → funds land in `balance[base]` with no `mm_asset` minted, inflating `$bytes_balance` for the next investor.
4. A victim posts a normal-sized "invest" trigger, e.g. `trigger.output[[asset=base]] = 1e5`, matching required asset ratio. `$investor_share_of_prev_balance = 1e5 / $bytes_balance(≈2e5)= 0.5`; but with a larger pre-existing inflated `$bytes_balance` (repeatable via more sub-threshold donations), `$issue_amount = round(0.5-ish tiny fraction * 100001)` can be driven to `0` while the victim's real bytes/asset are still received by the AA.
5. Attacker later triggers "divest MM shares" with their `100001` `mm_asset`, redeeming a share of the now-larger `balance[base]`/`balance[$asset]` pool that includes the victim's absorbed deposit, realizing profit at the victim's expense: [5](#0-4)
