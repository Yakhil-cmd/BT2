### Title
Bridge KLAY Transfer Permanently Sticks `lowerHandleNonce` via Reverting Recipient — (`File: contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge uses a push-payment pattern to deliver KLAY to the recipient address. If the recipient is a contract whose fallback reverts, the entire `handleKLAYTransfer` transaction reverts atomically, leaving `handleNoncesToBlockNums[N]` unset. Because `_updateHandleNonce` advances `lowerHandleNonce` only through a consecutive-nonce scan of that mapping, the bridge's `lowerHandleNonce` is permanently stuck at nonce N. The deposited KLAY on the source chain has no refund path and is permanently locked.

---

### Finding Description

`handleKLAYTransfer` executes in this order:

```solidity
// contracts/service_chain/bridge/BridgeTransferKLAY.sol  lines 75-99
_lowerHandleNonceCheck(_requestedNonce);
if (!_voteValueTransfer(_requestedNonce)) { return; }

_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;   // (A)
_updateHandleNonce(_requestedNonce);                                 // (B)

emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");                           // (C)
require(ok, "handleKLAYTransfer: transfer failed");                  // (D)
``` [1](#0-0) 

If `_to` is a contract whose fallback reverts, line (C) returns `false` and line (D) reverts the entire transaction. Solidity reverts all state changes atomically, so the write at (A) is rolled back: `handleNoncesToBlockNums[N]` remains `0`.

`_updateHandleNonce` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive `i` starting from `lowerHandleNonce`:

```solidity
// contracts/service_chain/bridge/BridgeTransfer.sol  lines 149-155
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    delete handleNoncesToBlockNums[i];
    delete closedValueTransferVotes[i];
}
lowerHandleNonce = i;
``` [2](#0-1) 

Because `handleNoncesToBlockNums[N]` is never written, the loop stops immediately at `i = N` on every subsequent call, leaving `lowerHandleNonce` permanently at N regardless of how many higher nonces are successfully handled.

The value-transfer recovery module reads `RecoveryBlockNumber` (which is also stuck) and `LowerHandleNonce` to determine the scan window:

```go
// node/sc/vt_recovery.go  lines 211-228
hint.blockNumber, err = to.bridge.RecoveryBlockNumber(nil)
...
handleNonce, err := to.bridge.LowerHandleNonce(nil)
...
to.UpdateLowerHandleNonce(handleNonce)
``` [3](#0-2) 

The recovery loop (`retrievePendingEventsFrom`) keeps re-scanning from the stuck `blockNumber`, re-queuing nonce N, and the operators keep submitting `handleKLAYTransfer` for nonce N — which always reverts. [4](#0-3) 

---

### Impact Explanation

- **Bridged asset locked**: The KLAY deposited on the source chain via `requestKLAYTransfer` is held in the source bridge contract. There is no `cancelTransfer` or refund function; the funds are permanently unrecoverable.
- **`lowerHandleNonce` corruption**: The protected bridge state variable `lowerHandleNonce` is permanently stuck at nonce N. `recoveryBlockNumber` is also stuck. No subsequent successful handle can unblock it.
- **Recovery DoS**: The `valueTransferRecovery` goroutine (`node/sc/vt_recovery.go`) enters an infinite retry loop for nonce N, wasting operator gas and preventing the recovery subsystem from making progress on any genuinely missed events beyond N.

The corrupted values are:
- `lowerHandleNonce` — stuck at N (should advance to N+1 after handling)
- `recoveryBlockNumber` — stuck at the block before N

---

### Likelihood Explanation

The trigger is fully unprivileged. Any user can call `requestKLAYTransfer` (or the payable fallback) on the source bridge and specify any address as `_to`, including a contract they deploy that reverts on receive. No special role, key, or majority-validator cooperation is required. A single malicious transaction on the source chain is sufficient to permanently corrupt the destination bridge's nonce state.

---

### Recommendation

Replace the push-payment pattern with a pull-payment or a try-catch pattern that does not revert the nonce bookkeeping on delivery failure:

1. **Separate nonce advancement from delivery**: Record `handleNoncesToBlockNums[N]` and advance `lowerHandleNonce` unconditionally before attempting the transfer. If the transfer fails, emit a `TransferFailed` event and allow the recipient to pull funds later (pull-payment pattern).

2. **Alternatively, use a try-catch wrapper** (Solidity ≥0.6): catch the revert from `_to.call.value(_value)("")` and, on failure, store the KLAY in a claimable mapping keyed by `(_requestedNonce, _to)` rather than reverting the whole transaction.

3. **Add a `skipNonce` owner function** as a last-resort escape hatch that advances `lowerHandleNonce` past a permanently-stuck nonce, allowing the bridge to continue operating while the stuck funds are handled out-of-band.

---

### Proof of Concept

```solidity
// Attacker contract deployed on the destination chain
contract RevertOnReceive {
    receive() external payable { revert("no KLAY accepted"); }
    fallback() external payable { revert("no KLAY accepted"); }
}
```

**Steps:**

1. Attacker deploys `RevertOnReceive` at address `C` on the destination chain.
2. Attacker calls `requestKLAYTransfer(C, value, "")` on the source bridge, depositing `value` KLAY. This emits `RequestValueTransfer` with `requestNonce = N`.
3. Bridge operators observe the event and call `handleKLAYTransfer(txHash, attacker, C, value, N, blockNum, "")` on the destination bridge.
4. Inside `handleKLAYTransfer`, `(bool ok,) = C.call.value(value)("")` returns `false` because `C` reverts.
5. `require(ok, "handleKLAYTransfer: transfer failed")` reverts the entire transaction. All state changes — including `handleNoncesToBlockNums[N] = blockNum` — are rolled back.
6. Operators retry; result is identical every time.
7. `lowerHandleNonce` remains at N. `recoveryBlockNumber` remains at the block before N.
8. The `valueTransferRecovery` goroutine keeps re-queuing nonce N from `recoveryBlockNumber`, operators keep submitting failing transactions.
9. The `value` KLAY deposited on the source chain is permanently locked with no refund path. [5](#0-4) [6](#0-5) [7](#0-6)

    // _updateHandleNonce increases lower and upper handle nonce after the _requestedNonce is handled.
    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }

        require(lowerHandleNonce <= _requestedNonce, "removed vote");

		return nil, errors.New("from bridge is nil")

	if to.bridge == nil {
		return nil, errors.New("to bridge is nil")
	}
	if hint.requestNonce == hint.handleNonce {
		return nil, nil
	}
	if !checkRecoveryCondition(hint) {
		return nil, nil
	}

	var pendingEvents []IRequestValueTransferEvent

	curBlkNum, err := from.GetCurrentBlockNumber()
	if err != nil {
		return nil, err
	}

	startBlkNum := hint.blockNumber
	endBlkNum := startBlkNum + filterLogsStride

pendingTxLoop:
	for startBlkNum <= curBlkNum {
		if endBlkNum > curBlkNum {
			endBlkNum = curBlkNum
		}
		opts := &bind.FilterOpts{Start: startBlkNum, End: &endBlkNum}
		reqVTevIt, err := from.bridge.FilterRequestValueTransfer(opts, nil, nil, nil)
		if err != nil {
			return nil, err
		}
		reqVTencodedDataIt, err := from.bridge.FilterRequestValueTransferEncoded(opts, nil, nil, nil)
		if err != nil {
			return nil, err
		}

		// For the FilterRequestValueTransfer type
