## Analog Found

### Title
Non-atomic in-memory cache reset (`storage.resetMemory`) races with concurrent unit validation/writing, corrupting stability/spend state - (File: `storage.js`, `writer.js`)

### Summary
The CVE describes a Xen `evtchn_reset()` race: resetting shared kernel state while other operations still assume its old invariants leads to corruption/privilege escalation. Ocore has an analogous pattern: `writer.saveJoint()` optimistically mutates the shared in-memory unit caches (`storage.assocUnstableUnits`, `assocBestChildren`, `assocUnstableMessages`) before the DB write commits, and if the write fails, it wipes and asynchronously rebuilds those same global caches via `storage.resetMemory()` — all without any lock that serializes this reset against concurrently-running validations/writes for other units.

### Finding Description
In `writer.js`, before the SQL/queries are actually executed, `saveJoint` speculatively installs the new unit into shared caches: [1](#0-0) 

Note the comment right above showing the previous global `mutex.lock(["write"], ...)` has been removed/commented out: [2](#0-1) 

If the write ultimately fails (`err`), the code deletes per-unit cache entries and then calls `storage.resetMemory(conn)`, which deletes and repopulates the *global* unstable/stable unit caches from the DB: [3](#0-2) 

`resetMemory` performs a synchronous delete of every key in `assocBestChildren`, `assocUnstableUnits`, `assocStableUnits`, `assocStableUnitsByMci`, followed by asynchronous DB queries (`initUnstableUnits`, `initStableUnits`) that repopulate them: [4](#0-3) 

Between the synchronous delete and the asynchronous repopulation (which itself does multi-step async queries in `initUnstableUnits`/`initStableUnits`/`initParenthoodAndHeadersComissionShareForUnits`), the caches are empty or partial. Validation and other concurrent `saveJoint` calls are only serialized per author address (`mutex.lock(arrAuthorAddresses, ...)` in `validation.js`), not by a single global lock covering cache mutation: [5](#0-4) 

So a unit posted by address A that fails to write (triggering the reset) can run concurrently with a unit from address B that is mid-validation/mid-write and is reading or mutating `storage.assocUnstableUnits`/`assocBestChildren` (e.g. main-chain determination in `main_chain.js`, or the speculative cache writes at `writer.js:591-613`). The reset can wipe out B's just-inserted cache entry, or B can populate the cache with stale data that the still-running `initUnstableUnits` re-overwrites, producing an inconsistent view of which units are on the main chain, free, or stable.

### Impact Explanation
Corrupting `assocUnstableUnits`/`assocBestChildren`/`assocStableUnits` mid-flight affects main-chain computation and stability determination (`main_chain.js`), which directly drives which outputs are considered stable/spendable and which unit sequence (`good`/`temp-bad`/`final-bad`) is assigned. Divergent or corrupted views of this state across validation runs can lead to:
- Nodes disagreeing on unit validity/stability (consensus fork potential).
- Spending checks (`checkForDoublespends` in `validation.js`) relying on cache state that no longer matches DB reality, opening a window for double-spend acceptance or incorrect finalization of a bad sequence unit as good.

This matches the required impact bar: node disagreement on validity/stability and potential double-spend of an output.

### Likelihood Explanation
Triggering the reset only requires causing a `saveJoint` write to fail for a unit that otherwise passed validation (e.g., a transient DB error, a duplicate-key race, or any of the various post-validation SQL steps in `writer.js` raising an error) while a second, independent unit (different author) is concurrently being validated/written — both are ordinary, unprivileged actions (posting units). No malicious peer, node, or hub role is required; a single busy node processing multiple posted units concurrently is enough to hit the window. This makes the race plausible under normal network load, though the failure path itself (forcing the write error) requires some effort/luck, which is why this is rated medium-to-high rather than trivially exploitable.

### Recommendation
Serialize `storage.resetMemory()` (and the optimistic cache writes in `writer.saveJoint`) behind a single global lock (e.g., reinstate the removed `mutex.lock(["write"], ...)` around the full `saveJoint` critical section, or wrap `resetMemory` calls in that same lock) so cache resets cannot interleave with concurrent cache reads/writes for other units. Alternatively, make `resetMemory` build the new cache into temporary objects and atomically swap them in only after full repopulation completes, rather than deleting live global caches in place.

### Proof of Concept
1. Two unrelated unpriviledged users concurrently post valid-looking units from different author addresses, U1 and U2.
2. U1's validation passes but a downstream `writer.saveJoint` SQL step fails (any transient error, e.g. constraint violation from a race with another write) triggering the `err` branch at `writer.js:708-712`, calling `storage.resetMemory(conn)`.
3. While `resetMemory`'s `initUnstableUnits`/`initStableUnits` asynchronous queries are still running (caches temporarily emptied), U2's concurrent `saveJoint` (running under only its own author-address lock) executes its optimistic cache write at `writer.js:591-613`, inserting into `storage.assocUnstableUnits`/`assocBestChildren`.
4. Because `initUnstableUnits` is still populating those same maps from a `SELECT ... WHERE is_stable=0` snapshot taken before U2's insert, either U2's entry gets silently dropped from `assocBestChildren` bookkeeping, or the reset's rebuild overwrites U2's state, producing inconsistent `is_on_main_chain`/`level` bookkeeping that downstream `main_chain.js` stability logic consumes for spend/stability decisions.
