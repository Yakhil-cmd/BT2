### Title
`MembershipHandler#find_or_create_team!` never checks `params.organization.login` (or `params.team.id`) against `repository_owner`, allowing any onboarded org's webhook secret to add users to or claim any GitHub team - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a `membership` webhook using `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')`, and looks up the signing secret via `Shipit.github(organization: repository_owner)`. [1](#0-0)  `MembershipHandler#process`/`#find_or_create_team!` then independently trusts `params.team.id` and `params.organization.login` from the same JSON body to locate or create a `Team` and to add/remove a `Membership`, with no comparison back to `repository_owner`. [2](#0-1)  Because the org that supplies the HMAC secret is never bound to the org recorded on the `Team`, or to the `team.id` being mutated, a party who legitimately owns one Shipit-onboarded org/repo (and thus its own valid webhook secret) can forge a `membership` event that creates or mutates a `Team` belonging to a different organization, including adding an arbitrary member to a pre-existing team whose GitHub numeric `id` they merely guess or learn.

### Finding Description
The intended binding is: `repository_owner` (the org whose secret validated `X-Hub-Signature`) `==` the organization actually mutated by the handler for that request. Tracing the code:

- `repository_owner` is read once in the controller and used only to pick the verification secret via `Shipit.github(organization: repository_owner)` / `github_app.verify_webhook_signature`. [3](#0-2) [4](#0-3) 
- After verification, the full parsed body is dispatched unchanged to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` — `repository_owner` is never passed along or re-checked. [5](#0-4) 
- `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }`. [6](#0-5)  Two failure modes exist:
  1. **New team path**: `params.organization.login` can be any attacker-chosen string — it need not equal `repository_owner`. If `repository.owner.login`/`organization.login` used for signing differs from a second, attacker-controlled value read for team creation, or if the attacker simply owns an onboarded org and picks an arbitrary `organization.login` string for the new `Team`, the resulting `Team.organization` is written with no relation to the authenticated org.
  2. **Existing team path**: if `github_id` already exists (a real GitHub team id, discoverable/guessable since GitHub team ids are small sequential integers or otherwise learnable), `find_or_create_by!` returns the existing record and the block (which sets `organization`) is **skipped entirely** — but `process` still unconditionally proceeds to `team.add_member(member)` for `action == 'added'`, with `member` built from attacker-controlled `params.member.login` via `User.find_or_create_by_login!`. [7](#0-6) 

No guard anywhere (`ExplicitParameters` schema, `Handler#stacks`/`repository_name`, `drop_unhandled_event`) enforces that `params.team.id` or `params.organization.login` belongs to the org that authenticated the signature; `Handler` base class only exposes `repository_name`/`stacks`, never `repository_owner`. [8](#0-7) 

This becomes a real authorization escalation because `Shipit.github_teams` resolves configured OAuth team handles via `Team.find_or_create_by_handle`, which does a plain `find_by(organization:, slug:)` lookup **before** ever calling GitHub, and memoizes the result for the process lifetime. [9](#0-8) [10](#0-9)  `User#authorized?` gates all controller access via `force_github_authentication`, and it only checks Team **id** membership against `Shipit.github_teams`. [11](#0-10) [12](#0-11)  If an attacker who owns any Shipit-onboarded org's webhook secret pre-creates a `Team` row whose `organization`/`slug` match a legitimate `github_teams` handle (org/slug strings are typically visible/known, e.g. `"shopify/developers"`), and adds themselves as a member in the same forged request, `Team.find_or_create_by_handle` will find that attacker-controlled row first and never reconcile it against real GitHub team membership, granting the attacker's account `authorized?` status without ever being a real member of that GitHub team.

### Impact Explanation
This matches "escalation into `Shipit.github_teams` authorization" (High) and, once authorization is bypassed, enables unauthorized deploys/rollbacks/merges gated behind `force_github_authentication` (Critical territory), since the whole app is behind that authorization check. It also independently enables writing arbitrary `Membership`/`Team` rows attributable to organizations the requester never authenticated for, a cross-tenant data-integrity issue in any multi-org Shipit deployment.

### Likelihood Explanation
The precondition is that the attacker is a legitimate owner/maintainer of at least one org/repo already onboarded into this Shipit instance's `secrets.github` config with its own `webhook_secret` (multi-org deployments) — a real GitHub user who can register a webhook against their own repo and compute a valid signature is exactly the threat actor described in the audit's rules. They must also know or guess a target `Team`'s GitHub `id`, or the `organization`/`slug` handle string used in `Shipit.github_teams` config, both of which are commonly non-secret/discoverable values. This is feasible and repeatable per onboarded org.

### Recommendation
In `MembershipHandler`, thread the authenticated `repository_owner`/org through to the handler (e.g., pass it from `WebhooksController#create` into `Handler.call`) and assert `params.organization.login.casecmp?(authenticated_organization)` before any `Team.find_or_create_by!`/`add_member` mutation; reject (422/`drop`) on mismatch. Additionally, when `find_or_create_by!` finds an existing team by `github_id`, verify `team.organization == authenticated_organization` before performing `add_member`/`delete`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (proof sketch)
test ":membership from org A can add member to a team belonging to org B" do
  other_org_team = shipit_teams(:shopify_developers) # organization == 'shopify'
  @request.headers['X-Github-Event'] = 'membership'

  # Signature verified for 'other-org' (attacker's own onboarded org), NOT 'shopify'
  payload = {
    action: 'added',
    team: { id: other_org_team.github_id, name: other_org_team.name, slug: other_org_team.slug, url: other_org_team.api_url },
    organization: { login: 'other-org' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'other-org' } }
  }.to_json

  Shipit.github(organization: 'other-org').expects(:verify_webhook_signature).returns(true)

  assert_difference -> { other_org_team.memberships.count }, 1 do
    post :create, body: payload, as: :json
  end
  # binding check: repository_owner ('other-org') != other_org_team.organization ('shopify')
  assert_not_equal 'other-org', other_org_team.reload.organization
end
```
This demonstrates the divergence: the signature-verifying org (`repository_owner` = `other-org`) differs from the mutated `Team#organization` (`shopify`), and the mutation (adding a `Membership`) still succeeds because `MembershipHandler` never compares the two values.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|

            team.organization = params.organization.login
          end
        end
