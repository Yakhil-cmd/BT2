## Title
CCMenu API endpoint ignores `ApiClient` stack scope, allowing a stack-scoped token to read the build status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` authenticates a caller with an `ApiClient` token and then resolves the target `Stack` directly from `Stack.from_param!(params[:stack_id])`, bypassing the scoping that every other API controller applies through `BaseController#stacks`/`#stack`. An `ApiClient` that was intentionally scoped to a single stack (`stack_id` set on the `ApiClient` record) is therefore not restricted to that stack when it hits the CCMenu endpoint, breaking the binding "stack a token authorizes == stack it touches."

### Finding Description
`BaseController#stacks` restricts the resolvable set of stacks to the ones the authenticated `ApiClient` is scoped to: [1](#0-0) 

This means, for every controller that inherits `BaseController#stack`, if `current_api_client.stack_id?` is true, only that one stack is reachable; `Stack.from_param!` for any other stack raises `RecordNotFound`.

`Api::CCMenuController`, however, overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, completely independent of `current_api_client.stack_id`: [2](#0-1) 

The `require_permission :read, :stack` before_action still runs and checks that the token has the `read:stack` permission string via `ApiClient#check_permissions!`, but that check is purely permission-name based and has no knowledge of which stack is being requested: [3](#0-2) 

So the only binding that was supposed to restrict a stack-scoped token (e.g. `here_come_the_walrus`, scoped to the `shipit` stack) to its own stack is the `stacks`/`stack` scoping in `BaseController`, and `CCMenuController` doesn't use it. The equality that should hold is:

`token.stack_id (if present) == stack_id requested/rendered`

but for this controller it becomes:

`token.stack_id (if present) != stack_id requested/rendered (attacker controlled via params[:stack_id])`

Compare with `Api::StacksController`, which correctly relies on the inherited `stacks`/`stack` scoping and is explicitly tested to enforce it: [4](#0-3) 

There is no equivalent test, or scoping code path, for `CCMenuController`.

### Impact Explanation
A holder of any valid `ApiClient` token that has the `read:stack` permission — even one deliberately scoped by an administrator to a single, low-sensitivity stack — can query `/stacks/:stack_id/ccmenu.xml` (or equivalent route) for **any** other stack in the Shipit instance by supplying a different `stack_id`. The response includes the target stack's name, activity, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and web URL: [5](#0-4) 

This is an unauthenticated-for-that-stack read of stack/deploy state, matching the "High - unauthenticated read of stack state, task streams or deploy output" impact category: a client credential legitimately issued for one stack is used to read build/deploy status of stacks it was never authorized to see.

### Likelihood Explanation
Any party holding a legitimately-issued, narrowly-scoped `ApiClient` token (a routine, low-privilege credential meant to be handed to CI dashboards, status widgets, etc.) can exploit this with a single unauthenticated-parameter change (`stack_id`) — no additional secrets, no privileged account, and no interaction with GitHub is required. This is a pure authorization-boundary bug reachable by any existing unprivileged API token holder.

### Recommendation
Make `Api::CCMenuController#stack` go through the same scoped lookup as every other API controller, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the direct `Stack.from_param!` call, so that a stack-scoped `ApiClient` cannot resolve stacks outside its `stack_id` scope. Add a regression test mirroring the one in `stacks_controller_test.rb` ("an api client scoped to a stack will only see that one stack") for the CCMenu endpoint.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: <stack_A.id>` with `permissions: ['read:stack']` (e.g. fixture `here_come_the_walrus`).
2. Authenticate as this client and request:
   ```
   GET /<stack_B_owner>/<stack_B_repo>/<stack_B_environment>/ccmenu.xml?token=<token for client scoped to stack_A>
   ```
   where `stack_B` is a different stack the client was never granted access to.
3. Observe HTTP 200 with `stack_B`'s `lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc. returned, despite the token being scoped only to `stack_A`. Compare with the same request against `Api::StacksController#show` using the same token, which correctly 404s for `stack_B` because of the `stacks` scoping test at [4](#0-3) .
