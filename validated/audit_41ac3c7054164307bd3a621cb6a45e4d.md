## Finding

The RustDesk CVE describes a server that authenticates a message's *sender* but fails to check whether the *sender's granted session scope* permits the specific message type it sends — a peer paired for a limited purpose (FileTransfer) can inject messages that only a full-Remote session should be allowed to send. `ocore--017` has the same bug class in its device-message dispatcher.

### Where it lives

`wallet.js`'s `handleMessageFromHub` is the single entry point that dispatches every incoming device message (`subject`/`body`) by `switch(subject)`, covering everything from chat text to `sign` (spend a unit), `create_new_shared_address`, `new_wallet_address`, `private_payments`, etc. [1](#0-0) 

`device.js` establishes two distinct trust/scope levels for a `correspondent_devices` row: a normal, explicitly-paired correspondent, and an `is_indirect` correspondent — added automatically (without any pairing handshake or user confirmation) whenever another device merely lists a device as a co-signer in a shared-wallet definition template. [2](#0-1) 

This `is_indirect` flag is read from the DB and forwarded as `bIndirectCorrespondent` into `handle_message_from_hub`: [3](#0-2) 

The scope-restriction that was supposed to keep such indirect (low-trust) correspondents confined to a narrow allow-list of subjects (`cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`) is **commented out**: [4](#0-3) 

Because that check is disabled, `bIndirectCorrespondent` is received by `doHandle()` but never consulted again anywhere in the ~900-line `switch` statement — an indirect correspondent can now reach every `case`, including `sign`, `create_new_shared_address`, `approve_new_shared_address`, `private_payments`, `arbiter_contract_*`, exactly mirroring RustDesk's missing server-side enforcement of a connection's granted scope.

### Why this matters (impact)

- `addIndirectCorrespondents` is invoked purely based on what a *third party* declares as "other cosigners" in a shared-wallet definition template offer, i.e., an attacker who is merely named as a cosigner candidate by someone else's device gets silently inserted as a correspondent capable of sending any subject. [2](#0-1) 
- With the scope check disabled, that untrusted party can, e.g., drive the `sign` flow (subject to `findAddress`'s own per-address cosigner check) or trigger `create_new_shared_address` / wallet-approval flows meant to be reachable only from confirmed, directly-paired correspondents. [5](#0-4) 

This matches the required analog criteria: it's reachable by an ordinary posted wallet/AA-adjacent message from an unprivileged peer device (no hub/node compromise needed), and it is a concrete authorization/scope-enforcement gap in wallet message handling rather than a p2p/hub/DoS issue.

### Title
Missing Enforcement of Indirect-Correspondent Message Scope Allows Out-of-Scope Wallet Command Injection - (File: wallet.js)

### Summary
`handleMessageFromHub` in `wallet.js` dispatches all device messages by `subject` without enforcing the intended scope restriction for `is_indirect` correspondents. The restriction exists in code but is commented out, so a device added only as an indirect/low-trust correspondent (via `addIndirectCorrespondents`, triggered by another peer merely naming it as a cosigner) can send any subject, including ones meant to be confined to trusted, directly-paired correspondents.

### Finding Description
`device.js`'s `handleJustsaying` looks up `is_indirect` for the sending device and passes it through as `bIndirectCorrespondent` to `handle_message_from_hub`. `wallet.js` receives this flag in `handleMessageFromHub`/`doHandle()` but the code that was meant to restrict indirect correspondents to a small allow-list of subjects is commented out, leaving no scope check at all. As a result the full `switch(subject)` — `sign`, `create_new_shared_address`, `approve_new_shared_address`, `private_payments`, `arbiter_contract_*`, etc. — is reachable by any correspondent regardless of trust tier.

### Impact Explanation
An indirect correspondent — added with no explicit pairing/confirmation from the local user, solely because a third party's wallet-creation offer named it as a cosigner — obtains the same message-scope as a fully paired, trusted device. This can be used to inject shared-address creation/approval flows, contract flows, and signing-related requests toward a wallet that never explicitly agreed to communicate with that device, expanding the attack surface for social-engineering the user into approving fraudulent shared addresses or contracts, or interfering with in-flight multi-device signing/contract state machines it was never meant to reach.

### Likelihood Explanation
Becoming an indirect correspondent requires no interaction from the victim beyond someone else offering to create a shared wallet naming the attacker's device as a cosigner (`create_new_wallet` → `handleOfferToCreateNewWallet` → `addIndirectCorrespondents`), which is a low-friction, attacker-controllable step. Once indirect status is established, the disabled check means every subject is reachable, so likelihood of triggering out-of-scope handlers is high once that low-friction precondition is met.

### Recommendation
Re-enable and enforce the scope restriction for `bIndirectCorrespondent` in `wallet.js`, restricting indirect correspondents to the minimal allow-listed subjects, and re-validate which subjects genuinely need to be reachable pre-pairing versus post-pairing.

### Proof of Concept
1. Attacker's device is referenced as `other_cosigners` in a `create_new_wallet` offer sent by a colluding/compromised third device to the victim, causing the victim's node to call `device.addIndirectCorrespondents`, inserting the attacker as `is_indirect=1` correspondent with no pairing confirmation. [2](#0-1) 
2. Attacker's device now sends a `hub/message` with any `subject` (e.g., `create_new_shared_address`, `sign`) directly to the victim.
3. `device.js` resolves `is_indirect=1` and forwards `bIndirectCorrespondent=true` unchanged into `handleMessageFromHub`. [3](#0-2) 
4. Because the scope-restriction line is commented out, `doHandle()` proceeds directly into the full `switch(subject)`, processing the message as if it came from a fully trusted correspondent. [6](#0-5)
