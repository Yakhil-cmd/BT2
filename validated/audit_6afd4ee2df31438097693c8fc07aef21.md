This confirms the mechanism: the `state` message and its formula (`objStateUpdate`) are executed via `executeStateUpdateFormula(objUnit, ...)` [1](#0-0)  completely independently of whether a `payment` message for the same trigger response actually survives into `objUnit.messages`. The state-formula evaluation only depends on `objStateUpdate` captured during template evaluation (`bStateUpdates` path) [2](#0-1) , not on the final filtered message list.

Based on this, here is the finding:

### Title
AA payment messages for indivisible (`fixed_denominations`) assets are silently dropped while state-var bookkeeping still executes, letting an AA's promised payout diverge from what is actually sent - ([File: aa_composer.js])

### Summary
When an Autonomous Agent (AA) response includes a `payment` message for an asset that has `fixed_denominations` set (an indivisible/precious-metal-style token, analogous to a non-standard token that is "incompatible" with the normal transfer path), `sendUnit()` in `aa_composer.js` does not compose that payment. Instead it is entirely and silently filtered out of the response unit, while the AA's own `state` formula (balance/var bookkeeping) is executed unconditionally against the *original* `objUnit`, independent of which payment messages actually survived.

### Finding Description
While collecting AA response messages, for every non-base `payment` message the code loads the asset and, if `objAsset.fixed_denominations` is true, simply calls `cb()` without completing the payload, annotated "will skip it later": [3](#0-2) 

After the per-message loop, any payment message whose asset is `fixed_denominations` is filtered out of `messages` a second time, and if this empties the whole message list the AA finishes with a "successful empty response": [4](#0-3) 

Crucially, `objUnit` is only built and hashed *after* this filtering [5](#0-4) , and `executeStateUpdateFormula(objUnit, ...)` is invoked on this already-filtered unit [1](#0-0) . The state-update formula itself, however, is captured once from the AA's `state` template and evaluated from `objStateUpdate` — a value fixed earlier during formula substitution and unrelated to which payment messages made it into the final unit [6](#0-5) . Consequently, an AA definition that says (in oscript) "pay out N units of indivisible asset X to the trigger address" *and* "decrement var balance by N" will have its `var` update applied even though the indivisible-asset payment silently never happens, because indivisible/fixed-denomination assets require input selection with denomination-matched serial numbers and (for private ones) spend proofs that the deterministic AA payment composer cannot produce — as acknowledged directly in the code's own comments ("will skip it later", "it'll fail validation anyway due to lack of spend_proofs") [7](#0-6) .

This mirrors the reported bug class precisely: a specific, valid asset configuration (indivisible/fixed-denomination assets, and separately private assets) is fundamentally incompatible with the payment composition path used by the "multipool"-like AA response engine, and the system does not fail loudly (bounce/revert) for the incompatible case — it silently proceeds, only bouncing for the `is_private` case but not for `fixed_denominations` case, where it silently continues with mismatched bookkeeping.

### Impact Explanation
An AA holding a `fixed_denominations` asset that its own definition intends to pay out will retain the asset balance (it is never actually transferred), while any `var[...]` state that the AA definer scripted to reflect "this was paid" is nonetheless updated. This produces AA state/balance data that is inconsistent with on-chain reality: the AA's on-chain asset balance stays untouched, but its off-chain-tracked business logic believes the funds were sent. Depending on the AA's logic, this can permanently strand the indivisible-asset balance inside the AA (freezing of funds it can never re-attempt to send once its internal state says "paid"), which fits the "AA fund loss or freezing" criterion.

### Likelihood Explanation
This triggers deterministically and silently any time an AA definer writes a payment message for an asset that turns out to have `fixed_denominations: true` (something not always obvious to AA authors reusing an asset they don't control), and reachable by any user whose trigger causes such a branch to execute — no privileged access required.

### Recommendation
Rather than silently filtering out `fixed_denominations` (and effectively no-op) payment messages after the state-update formula's data has already been fixed, `handleTrigger`/`sendUnit` should bounce the whole response (similar to the existing `is_private` bounce at aa_composer.js:1329-1330) whenever a payment message targets a `fixed_denominations` asset, so that the AA's state changes are not committed against a payment that never actually executes.

### Proof of Concept
1. Define an asset with `fixed_denominations: true` (indivisible) and fund an AA with units of it.
2. Write an AA whose response includes:
   - a `payment` message paying out some amount of that indivisible asset to `trigger.address`, and
   - a `state` message that decrements `var['balance']` by the same amount as if the payment succeeded.
3. Trigger the AA. The payment message is dropped per `aa_composer.js:1356` filtering, but `executeStateUpdateFormula` still runs and updates `var['balance']` per `aa_composer.js:1405-1407` and `1431-1462`. Observe that the AA's actual asset holdings of the indivisible token are unchanged while its tracked `var['balance']` decreased, permanently desynchronizing the AA's accounting from its true asset custody.
