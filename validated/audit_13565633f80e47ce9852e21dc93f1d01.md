## Analysis

The report's bug class — a security-relevant value that is *never checked against its "unset" state*, so the guard condition degrades to "always true" — maps directly onto `Shipit::GithubApp#verify_webhook_signature`:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [1](#0-0) 

Exactly like `rewardGenerationStartTime` not being checked against `0`, `webhook_secret` is never required to be present: when it's blank/`nil`, the entire HMAC verification is skipped and the method unconditionally returns `true`. This is invoked from `WebhooksController#verify_signature`, which resolves the GitHub App / secret to check *from the same untrusted payload* (`repository_owner`) that will subsequently be trusted and dispatched to handlers:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
  ...
end
``` [2](#0-1) 

This breaks the binding "payload acted on == payload covered by the verified signature": when `webhook_secret` is unset for an organization, the full payload is dispatched to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` with zero cryptographic verification. [3](#0-2) 

The most severe reachable handler is `MembershipHandler`, which trusts the forged payload to add an arbitrary GitHub login to an arbitrary `Team` record identified only by `github_id`:

```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  ...
``` [4](#0-3) 

Team membership is exactly the authorization gate used by `Authentication#force_github_authentication` / `User#authorized?`:

```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
``` [5](#0-4) 

So an attacker who forges a `membership` webhook (no secret required if `webhook_secret` is unset for the target org) can insert their own already-registered `User` into any `Team` matching `Shipit.github_teams`, escalating from an unauthorized visitor to a member authorized to browse stack state, trigger tasks and, depending on team-scoped policy, deploy/rollback.

### Title
Missing-webhook-secret bypasses signature verification, allowing forged `membership` events to escalate into `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Finding Description
`GithubApp#verify_webhook_signature` treats an absent `webhook_secret` as automatic verification success rather than rejecting the request, exactly mirroring the reported analog (a guard variable that is never checked against its unset/zero state, making the condition always true). `WebhooksController#verify_signature` derives which app/secret to check from attacker-controlled `repository.owner.login`/`organization.login` fields, then—once "verified" (trivially, for orgs without a configured secret)—hands the same untrusted payload to `Shipit::Webhooks` handlers, including `MembershipHandler`, which writes team memberships directly from the payload. [1](#0-0) [6](#0-5) 

### Impact Explanation
An unprivileged, unauthenticated actor can POST a crafted `membership` webhook to `/webhooks` for any organization whose GitHub App has no `webhook_secret` configured (a state the setup docs present as optional/normal), adding any known GitHub login into any Shipit `Team`. Because `User#authorized?` and `force_github_authentication` gate the entire application on team membership against `Shipit.github_teams`, this is a direct escalation into that authorization boundary — matching the High-severity impact category "escalation into `Shipit.github_teams` authorization".

### Likelihood Explanation
Requires no session, API token, or GitHub write access — only that the target org's webhook secret is unset (a documented, non-enforced configuration). The webhooks endpoint is intentionally public/unauthenticated by design, and the payload shape needed (`action`, `team{id,name,slug,url}`, `organization{login}`, `member{login}`) is fully attacker-controlled JSON.

### Recommendation
Require `webhook_secret` to be configured for every registered GitHub organization and fail closed (reject the request) instead of returning `true` when it is blank. Additionally, do not let `Team`/membership-affecting handlers trust organization/team identifiers taken from an unauthenticated payload without an independent server-side verification step against GitHub.

### Proof of Concept
1. Target a Shipit deployment where an org's `github.webhook_secret` is left unset (per `docs/setup.md`, this is optional).
2. POST to `/webhooks` with header `X-Github-Event: membership` and no/garbage `X-Hub-Signature`, body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/999"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker-handle"}
}
```
3. `verify_webhook_signature` returns `true` (no secret configured) so the request passes `verify_signature`.
4. `MembershipHandler#process` creates/finds `Team(github_id: 999)` and adds `User(login: "attacker-handle")` (created via `User.find_or_create_by_login!`) as a member.
5. If team id `999` matches a team in `Shipit.github_teams`, the attacker's account, once it authenticates via OAuth, now passes `User#authorized?` and gains access previously restricted to that team.
