### Title
Oversized receipts created via known bug #12606 can stall in the outgoing buffer because `generate_bandwidth_request` under-reports their true size - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
The `generate_bandwidth_request` logic caps each reported receipt-group size at `params.max_receipt_size` via `std::cmp::min(group_size, params.max_receipt_size)`, which assumes no buffered receipt can exceed `max_receipt_size`. However, `#12606` — acknowledged in the code comment and reproduced by `test_max_receipt_size_promise_return` / `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs` — shows that a receipt whose size is validated at creation time (before `output_data_receivers`/return-value data is attached) can grow above `max_receipt_size` afterward and still be accepted into the outgoing buffer, undercutting the very invariant the bandwidth request logic depends on.

### Finding Description
`generate_bandwidth_request`'s size-capping (`receipt_sizes_iter.map_ok(|group_size| std::cmp::min(group_size, params.max_receipt_size))`) is designed under the assumption that no receipt in `outgoing_buffers`/`TrieKey::BufferedReceipt` can be larger than `max_receipt_size`, since the bandwidth-request/scheduler protocol represents sizes in bounded "size classes" up to that limit. The test suite in `test-loop-tests/src/tests/max_receipt_size.rs` demonstrates that this assumption is false: a contract can create a promise DAG where a receipt passes the size check at creation time but is later mutated (e.g., `output_data_receivers` appended after a `promise_return`, or a return value wrapped into a data receipt) so its final serialized size exceeds `max_receipt_size`. This is entirely reachable by an unprivileged account through ordinary `FunctionCall` actions and cross-contract promise usage — no elevated privileges required, only a deployed contract exercising promise APIs (`promise_then`, `promise_return`, value return) with large argument/return sizes, as shown in `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return`.

Once such an oversized receipt is buffered under `TrieKey::BufferedReceipt`, `generate_bandwidth_request` reports its size as capped at `max_receipt_size` when building `BandwidthRequest`s for the scheduler. The bandwidth scheduler then grants bandwidth sized according to that capped report. When `try_forward` later attempts to actually send the receipt, the real (oversized) serialized size exceeds the granted bandwidth, so the forwarding condition against `outgoing_limit.size`/granted bandwidth fails and the receipt cannot be forwarded that chunk. Because the scheduler will keep granting exactly the (under-reported) capped amount every time bandwidth requests are recomputed from the same buffered oversized receipt, there is no mechanism that grants a bandwidth allowance larger than `max_receipt_size` for a single receipt — the receipt can become permanently stuck in the buffer, unable to ever be forwarded, as acknowledged directly by the `#12606` comment in `congestion_control.rs`.

### Impact Explanation
This is a receipt/congestion-accounting failure: an oversized receipt permanently parked in `TrieKey::BufferedReceipt` consumes buffer space indefinitely, can hold locked balance/promises associated with the receipt (deposits, gas reservations already charged/burned when the receipt was created), and — because the buffer is a `TrieQueue` typically processed FIFO per receiver shard — can potentially block forward progress of other buffered receipts destined for the same shard behind it, contributing to a chain-level congestion/stall condition for that shard pair. This matches the "receipt or congestion accounting failures" bounty class explicitly called out in scope.

### Likelihood Explanation
The precondition is simply deploying a contract that uses promise chaining (`promise_then`/`promise_return`) or large return values to grow a receipt's size after its initial validation, exactly as reproduced by the existing regression tests `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return`. Any unprivileged account can deploy and call such a contract via public RPC; no special node/validator access is needed. The underlying creation-time bug (#12606) is already known and demonstrated to be reproducible, making the downstream bandwidth-under-reporting consequence highly likely to be triggerable once cross-shard forwarding is exercised (the existing tests only assert the receipt is created oversized and doesn't crash the runtime; they do not yet assert eventual forwarding or permanent buffering, which is the gap this finding highlights).

### Recommendation
Two complementary fixes are needed:
1. Fix the root cause (#12606): revalidate receipt size *after* all mutations (`output_data_receivers` additions from `promise_return`, wrapped return values becoming data receipts) rather than only at initial creation, and reject/fail the transaction if the final size exceeds `max_receipt_size`.
2. Defensively harden `generate_bandwidth_request` in `runtime/runtime/src/congestion_control.rs`: do not silently cap reported sizes with `std::cmp::min`; if a buffered receipt's true size exceeds `params.max_receipt_size`, this should be treated as an invariant violation (e.g., logged/metriced and handled explicitly, such as via a dedicated request path that guarantees forwarding, or by asserting/erroring in non-production builds) rather than silently under-reporting, so oversized receipts cannot silently stall forwarding.

### Proof of Concept
Extend `test-loop-tests/src/tests/max_receipt_size.rs`'s existing `test_max_receipt_size_promise_return` / `test_max_receipt_size_value_return` tests (which already produce a receipt above `max_receipt_size` and call `assert_oversized_receipt_occurred`) with a cross-shard setup:
1. Deploy the test contract on account A (shard 0) and configure the target receiver account on a different shard (shard 1) so the produced oversized receipt must go through `ReceiptSinkV2`/`outgoing_buffers`/bandwidth-scheduler forwarding rather than being applied locally.
2. Trigger `max_receipt_size_promise_return_method1` (or the value-return variant) with sizes tuned to produce a receipt above `max_receipt_size` destined for the other shard.
3. Run the test loop for many additional chunks/epochs (well beyond normal forwarding latency) and assert that either: (a) the oversized receipt is rejected before being buffered (fixing #12606), or (b) it is eventually observed as forwarded/applied on the receiving shard (via `get_incoming_receipts_for_shard` or receipt proofs) — asserting it does **not** remain indefinitely in `TrieKey::BufferedReceipt` in `ShardsOutgoingReceiptBuffer`. Currently, per the acknowledged bug, this assertion would fail because the receipt would be under-reported by `generate_bandwidth_request` and never receive sufficient bandwidth to forward via `try_forward`.
