### Title
Session fixation on GitHub OAuth login — no session ID rotation on authentication - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`GithubAuthenticationController#callback` binds a freshly authenticated GitHub identity to the current session by writing `session[:user_id]` and `session[:authenticated]` into the *existing* session, without ever calling `reset_session` (or otherwise rotating the session identifier) before establishing the new authenticated identity. This breaks the equality that should hold: `session_id before login == session_id after login` must never be true across a privilege change — anyone who can set a victim's session cookie prior to login retains access to it after the victim authenticates.

### Finding Description
The callback action is: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```

`sign_in_github` resolves/creates a `Shipit::User` from the GitHub identity and returns its id, which is then merely assigned into the pre-existing session hash: [2](#0-1) 

No call to `reset_session` (Rails' standard mitigation, which regenerates the session ID while preserving the hash) is made at any point in the authentication flow — `reset_session` is only invoked in `logout`: [3](#0-2) 

Because Shipit relies on `session[:user_id]`/`session[:authenticated]` as the sole binding between the browser's session cookie and the authenticated `Shipit::User`, the identity that is "supposed" to be attached to a given session cookie (the equality `session_id ⇔ authenticated User`) is never re-established at the moment of privilege elevation. Any session id fixed into a victim's browser before login remains valid to the same, now-privileged session record after `callback` runs, exactly mirroring the report's core class of bug: a security-relevant UI/session context that is shared/reused across a trust boundary (in the Uniswap case, across tabs; here, across the pre-auth/post-auth boundary of one browser session) without being partitioned when the enclosing context's authority is expected to change.

### Impact Explanation
This maps to the explicitly listed High-impact category: "session fixation / forced OAuth completion." If an attacker can cause a known session identifier to be set in a victim's browser (e.g. session cookie not marked `secure`/scoped broadly, or set via any mechanism that plants a cookie for the Shipit host) and then induces the victim to complete the GitHub OAuth login flow, the attacker's held session id becomes an authenticated Shipit session for the victim's `Shipit::User`. From there the attacker inherits everything that user's session grants: access to deploy actions, hooks, api_clients management, and any privileged UI-driven operations gated by `current_user`/`Shipit.github_teams` membership (`app/models/shipit/user.rb#authorized?`).
