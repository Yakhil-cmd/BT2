### Title
AA custom-asset balance can be permanently locked via unbounded dust-output flooding in payment composition - ([File: aa_composer.js])

### Summary
When an Autonomous Agent (AA) needs to compose an outgoing payment in a custom asset, `completePaymentPayload`'s `readStableOutputs`/`readUnstableOutputsSentByAAs` queries fetch **all** unspent outputs of that asset owned by the AA with no dust-amount filter (the filter only applies to the base asset) and no `LIMIT`, and `iterateUnspentOutputs` then keeps pushing every returned row into `payload.inputs` until the target amount is reached, with no bound on how many inputs get added.

### Finding Description
In `completePaymentPayload` (`aa_composer.js`), `readStableOutputs` builds the outputs query as: [1](#0-0) 
The dust-amount guard (`amount>=FULL_TRANSFER_INPUT_SIZE`) is only applied when `asset` is null (base asset); for any custom asset there is no minimum-amount filter and no row-count limit, so the query can return an arbitrarily large result set.

`iterateUnspentOutputs` then loops over every row of that result set and unconditionally appends an input for each one until `total_amount >= target_amount`: [2](#0-1) 

The protocol enforces a hard cap of `MAX_INPUTS_PER_PAYMENT_MESSAGE = 128` inputs per payment message: [3](#0-2) 

An attacker can issue their own asset cheaply (or use any asset accepted by the target AA) and send a very large number of minimal-amount deposits (e.g. quantity = 1) to the AA in that asset, exactly analogous to the reported Solidity bug where an attacker floods an unbounded `deposits` array with dust to make a later loop over that array run out of gas. Once the number of unconsumed dust outputs held by the AA in that asset exceeds 128, any future AA response that needs to send out that asset (oldest-first, deterministic ordering via `ORDER BY main_chain_index, unit, output_index`) will need more than 128 inputs to reach the required amount, producing a payment message that exceeds `MAX_INPUTS_PER_PAYMENT_MESSAGE` and fails unit composition/validation. Because the query always returns the same oldest dust outputs first and the AA has no mechanism to skip or coalesce them, the AA can never successfully compose a valid spend of that asset — the same failure repeats on every future trigger.

### Impact Explanation
This causes permanent freezing of AA funds/state for the affected asset: any legitimate user withdrawal or AA-internal accounting operation that must move balance in the flooded asset out of the AA will perpetually fail (bounce), locking the honest depositors' funds in that AA forever. This matches the accepted impact class of "AA fund loss or freezing" from unauthorized-cost/unbounded-growth abuse, mirroring the original bounty-lock report where an attacker cheaply grows an unbounded array to permanently block a legitimate refund/payout path.

### Likelihood Explanation
Any address can send arbitrarily many dust deposits of a custom asset to a target AA at will; the only cost is the base network fee per unit (bytes commissions), which is small and entirely attacker-controlled (they can even self-issue the asset they flood with). No special privileges, timing, or race conditions are required — a single unprivileged user can execute this against any AA that accepts variable, non-base-asset deposits and pays them out later (e.g., token vaults, DEXes, bonding curves, escrow-style AAs).

### Recommendation
- Apply a minimum-amount (dust) filter to non-base assets in `readStableOutputs`/`readUnstableOutputsSentByAAs`, similar to the existing `FULL_TRANSFER_INPUT_SIZE` filter for base payments.
- Bound the number of rows fetched/iterated (e.g. `LIMIT MAX_INPUTS_PER_PAYMENT_MESSAGE` in the SQL, or stop `iterateUnspentOutputs` once `payload.inputs.length` reaches `MAX_INPUTS_PER_PAYMENT_MESSAGE`), and treat leftover unspent dust as "not currently spendable" rather than blocking the whole payment.
- Consider a periodic/opportunistic dust-consolidation mechanism so previously-received small outputs get merged rather than accumulating unboundedly.

### Proof of Concept
1. Deploy/target an AA that accepts deposits of a non-base asset and later needs to pay out that asset (e.g., in response to a withdrawal trigger).
2. Attacker defines (or already owns) that asset and sends 200+ separate units, each depositing the minimum possible amount (e.g. 1 unit) of the asset to the AA address. Each deposit is accepted normally by `receiveFunds`-equivalent path (regular payment processing), since there is no minimum-amount validation for non-base assets, and these outputs remain unspent (`is_spent=0`).
3. A legitimate user later triggers the AA to withdraw/pay out a target amount in that asset that requires accumulating from many of the existing unspent outputs.
4. `readStableOutputs` returns all 200+ dust rows (oldest first); `iterateUnspentOutputs` pushes >128 inputs into `payload.inputs` trying to reach `target_amount`.
5. Unit composition/validation rejects the payload for exceeding `MAX_INPUTS_PER_PAYMENT_MESSAGE`, and the AA response bounces. Because the ordering is deterministic and the dust outputs are never consumed, every subsequent attempt to spend that asset from the AA fails identically, permanently freezing the balance.
