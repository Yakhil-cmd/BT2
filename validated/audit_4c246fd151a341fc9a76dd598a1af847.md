### Title
Unbounded in-memory buffering of git command stdout/stderr enables attacker-controlled memory exhaustion (DoS) - ([File: pkg/cmd/cmd.go])

### Summary
`runWithStdin` in `pkg/cmd/cmd.go` captures all stdout/stderr from every git subprocess into unbounded `bytes.Buffer` values before returning, with no size cap or streaming/truncation. Since git-sync's git operations (fetch, log, ls-remote, submodule commands) on an attacker-controlled repository produce output whose size scales with attacker-controlled repo properties (ref count, commit messages, submodule listings), a crafted repo can force git-sync to buffer arbitrarily large output in memory.

### Finding Description
`runWithStdin` (pkg/cmd/cmd.go:63-94) allocates `outbuf := bytes.NewBuffer(nil)` and `errbuf := bytes.NewBuffer(nil)`, assigns them directly as `cmd.Stdout`/`cmd.Stderr`, and lets `cmd.Run()` write into them without any `io.LimitReader`, size ceiling, or streaming discard. [1](#0-0) 

Every git subcommand git-sync issues (via `Runner.Run`/`Runner.RunWithStdin`) goes through this function, so any git command whose textual output size is influenced by attacker-controlled repository content (e.g. number of refs reported by `git fetch`, commit log/message content, submodule listings) accumulates fully in process memory before the calling code even inspects it. There is no upstream limiting of ref count, commit message size, or output line count in `main.go`'s use of the `Runner` API. The buffers are read only after `cmd.Run()` completes (`outbuf.String()`), so growth is unbounded during the entire command execution. [2](#0-1) 

Because the attacker in this threat model already controls the content and refs of the repository git-sync fetches, they can inflate the volume of textual output any called git command would produce (e.g. very many branches/tags causing many summary lines from `fetch`, or large content flowing through commands whose output isn't filtered), without needing any non-default flag or elevated privilege.

### Impact Explanation
This matches the "persistent stall/exhaustion" impact class: if the buffered output grows large enough, the git-sync process can be OOM-killed by the kernel/cgroup limits. Because the sync loop re-runs the same git operations against the same attacker-controlled repository/branch on every interval, a Kubernetes pod would crash-loop indefinitely (CrashLoopBackOff), producing a persistent denial of service for the sidecar and, by extension, for any workload depending on the synced volume being kept current.

### Likelihood Explanation
Feasibility is moderate to low in practice: it requires the attacker-controlled repository to actually generate git command output whose size is large enough to exceed the container's memory limit (which in a typical Kubernetes deployment can be substantial, e.g. hundreds of MB or GB). This depends on how much text a single git invocation can be made to emit (e.g., number of refs printed by `fetch`, or verbose logging), which was not confirmed in this codebase to reach unbounded scale under default flags — no non-default flags (e.g., `--verbose`) were found wired into the actual fetch/log invocations in `main.go` within the scope investigated. The vulnerability is real at the code level (no size bound exists), but concrete exploitability strength depends on git's own default output verbosity for the commands git-sync issues, which is comparatively terse (e.g., default `git fetch` without `-v` prints a small number of summary lines regardless of ref count in most cases). This limits real-world severity to lower-probability, higher-ref-count scenarios rather than a trivially reproducible OOM with a single crafted commit.

### Recommendation
Bound the amount of output captured from git subprocesses, e.g. wrap `cmd.Stdout`/`cmd.Stderr` with an `io.LimitWriter`-style guard (or a custom writer that stops accepting bytes past a configurable cap such as a few MB) and treat truncated output as an error/log-worthy condition rather than silently buffering indefinitely. Alternatively, stream output line-by-line for commands with potentially large output and process/discard incrementally instead of accumulating full buffers in memory.

### Proof of Concept
Integration test sketch: create a local bare repository with a very large number of refs (e.g. 200,000 lightweight branches) or a single blob/commit message of many hundreds of MB, point `runWithStdin`/`Runner.Run` at a git command whose output volume scales with that content (e.g. `git for-each-ref` or `git log` with unbounded `-n`), and measure process RSS growth via `runtime.ReadMemStats` before/after the call — assert memory growth is bounded (e.g., capped at a fixed ceiling) rather than proportional to the crafted repo's ref/content size. As found, no such cap exists in `runWithStdin`, so the test would show unbounded growth proportional to attacker-controlled input size.
