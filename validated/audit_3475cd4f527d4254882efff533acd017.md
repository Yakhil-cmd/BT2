### Title
Block-revenue-sharing reward calculation can misattribute lamports when recalculated stake exceeds the frozen denominator - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`calculate_block_reward` distributes a vote account's `pending_delegator_rewards` pool to individual stake accounts proportionally to `stake / total_active_stake`. The denominator `total_active_stake` is fixed at the reward-epoch boundary via `RewardEpochDelegatedStakes`, but the numerator `stake` for an individual delegation can grow between the original calculation and a later recalculation (e.g. after that delegation has already received an earlier inflation stake reward), so `stake > total_active_stake` can occur for one or more delegations under the same vote account. This is the same bug class as the funding-fee issue: a fixed pool is split among claimants using independently-computed per-claimant shares whose sum is not provably bounded by (or equal to) the pool total, so payouts drift from the entitled proportional share. [1](#0-0) 

### Finding Description
`calculate_block_reward` computes, per stake delegation:
```
(pending_delegator_rewards * stake / total_active_stake).min(pending_delegator_rewards)
``` [2](#0-1) 

The function's own comment acknowledges the root cause directly: "During recalculation, if stake account has already received rewards, it's possible to have `stake > total_active_stake`... We can also have individual rewards look greater than the pending rewards." [3](#0-2) 

This mirrors the audited pattern precisely:
- The "PnL pool" analog is the vote account's `pending_delegator_rewards` balance, funded via `deposit_delegator_rewards` [4](#0-3) .
- The "openNotional" analog is per-delegation `stake` (from `delegation_effective_stake`), and the "sum of openNotionals" analog is `total_active_stake`, a value snapshotted once at epoch boundary via `RewardEpochDelegatedStakes` and reused during `recalculate_stake_rewards` even though the underlying `stakes_cache` state has since mutated (a stake's `Delegation::stake` grows after a stake reward is applied). [5](#0-4) 
- Just as in the Sherlock report, each individual share is computed independently and clamped only against the *total* pool (`.min(pending_delegator_rewards)`), not against the *unallocated remainder* of the pool after other delegations under the same vote account have already been paid. If more than one delegation under the same vote account satisfies `stake > total_active_stake` at recalculation time, each one can independently compute a share approaching or equal to the full `pending_delegator_rewards`, so the cumulative block-reward lamports attributed across all of that validator's delegations can exceed the true `pending_delegator_rewards` balance actually available in the vote account.

The recalculation path exists specifically to handle partitioned/partial reward distribution across multiple blocks, where some stake rewards have already been applied to `StakesCache` before the remaining partitions are recomputed [6](#0-5) , so the described state (some delegations already boosted, denominator stale) is a directly reachable, unprivileged-user condition (any delegator's stake account participates in this accounting merely by being staked to a validator with `block_revenue_sharing` enabled).

### Impact Explanation
If the cumulative `block_reward` computed for a validator's delegations during a recalculation exceeds the vote account's actual `pending_delegator_rewards`, later-processed stake accounts in the distribution partition are attributed and paid lamports beyond what is actually funded/reserved for them, i.e., misattributed rewards between delegators of the same validator, and/or a shortfall against the vote account's block-revenue pool. This falls under the accepted "misattributed rewards" impact category, since the same underlying pool of lamports is split via independently-derived per-claimant fractions rather than a running remainder, exactly analogous to the referenced funding-fee issue.

### Likelihood Explanation
Requires `block_revenue_sharing` feature active, a partitioned epoch-reward distribution that spans multiple blocks (already the normal path for validators with many delegations), and at least one delegation whose `Delegation::stake` was already bumped by an earlier-applied stake reward within the same recalculation window, causing `stake > total_active_stake` for that entry — a state the code comment itself calls out as reachable ("it's possible to have `stake > total_active_stake`"). This is a specific, but not contrived, sequence of ordinary epoch-boundary/reward-distribution mechanics, comparable in likelihood to the "specific state required" characterization that led the original Sherlock issue to be rated Medium.

### Recommendation
Track a running remainder of `pending_delegator_rewards` as delegations are processed within a recalculation/partition (or compute the block-reward shares once over the full, unmutated delegation set the pool.rewards use of the epoch to snapshot the necessary per-delegation stake, not derived from a possibly-mutated `StakesCache` state that reflects already-paid stake rewards), so that per-vote-account block reward attribution is provably bounded by, and sums to no more than, `pending_delegator_rewards`, mirroring the recommendation from the referenced report to key the split off values that are invariant across partial distribution (position size / stake) rather than values whose sum can drift between calculation and recalculation.

### Proof of Concept
1. Enable `block_revenue_sharing`; a validator's vote account has `pending_delegator_rewards = P` funded via `DepositDelegatorRewards`.
2. At epoch boundary, `RewardEpochDelegatedStakes` snapshots `total_active_stake = T` for the validator (sum of all its delegations' stake at that time).
3. Rewards are distributed across multiple blocks/partitions. In an early partition, delegation `A`'s stake reward is applied, increasing `Delegation::stake` for `A` in `StakesCache` beyond its epoch-boundary value.
4. `recalculate_stake_rewards` is invoked for a later partition, re-running `calculate_stake_rewards_and_commissions` → `calculate_block_reward` for the *same* validator's remaining delegations, still using the stale `T` from `RewardEpochDelegatedStakes` (per the code path in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:1038-1087`).
5. For delegation `A` (now with `stake_A > T`), `calculate_block_reward` computes `P * stake_A / T`, which mathematically exceeds `P`, clamped to exactly `P`.
6. If any other delegation `B` under the same vote account also independently computes a nonzero block reward in the same or a different partition, the sum of block rewards attributed across `A` and `B` for that vote account can exceed `P`, since each computation is clamped only against the full pool total, not against `P` minus amounts already attributed to other delegations in the same distribution cycle.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
