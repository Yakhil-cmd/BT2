### Title
Webhook organization used for HMAC key selection is decoupled from the repository the webhook payload writes to, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on an untrusted, attacker-controlled field of the same payload it is verifying (`repository.owner.login`, falling back to `organization.login`), while every webhook `Handler` resolves the actual repository/stacks to act on from a *different* field of the same payload (`repository.full_name`). In a multi-organization Shipit deployment (explicitly supported, see `config/secrets.development.example.yml`), this breaks the binding: `organization that authenticated == repository that is written`. An operator who legitimately controls one configured organization's GitHub App webhook secret can forge a signed payload whose `repository.owner.login` matches their own org (so their own secret produces a valid signature) but whose `repository.full_name` names a repository belonging to a *different* configured organization, causing Shipit to act on that other organization's stacks.

### Finding Description
- Signature verification: `verify_signature` picks the GitHub App config via `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature`, where `repository_owner` comes straight from the JSON body: [1](#0-0) [2](#0-1) 

- `verify_webhook_signature` just HMACs the raw request body against the secret configured for whichever organization was picked: [3](#0-2) 

- After verification passes, `WebhooksController#create` dispatches to handlers using only the event type, passing the full untrusted `params` along; nothing re-checks that the org used for verification matches the repository being mutated: [4](#0-3) 

- Every handler independently resolves which repository/stacks to touch from `payload.dig('repository', 'full_name')`, a field unrelated to the `repository.owner.login` value used for key selection: [5](#0-4) 

- `PushHandler`, for example, uses that same `stacks` helper to sync arbitrary stacks based on `full_name`: [6](#0-5) 

- Multi-organization configuration, where each org has its own independent `webhook_secret`, is a first-class, documented configuration shape: [7](#0-6) 

Because the HMAC *key* is chosen dynamically from attacker-supplied content in the very payload being verified, and the field used for key selection (`repository.owner.login`/`organization.login`) is not the same field later trusted to identify the target repository (`repository.full_name`), an attacker who is a legitimate administrator of Organization A's GitHub App (and therefore knows Org A's `webhook_secret`) can craft a payload with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/some-repo"`. The signature check succeeds using Org A's secret, but the effect is applied to Org B's repository/stacks, which Org A's operator has no authorization over from Shipit's perspective.

### Impact Explanation
This is a cross-organization/cross-repository write achievable without any Shipit session, `ApiClient` token, or the target organization's own webhook secret — only knowledge of a *different*, already-configured organization's webhook secret is required. Depending on event type dispatched, this can:
- Trigger `sync_github` / `GithubSyncJob` for arbitrary stacks belonging to another org's repository via forged `push` events.
- Create commit `Status` records for arbitrary shas via forged `status` events.
- Create/modify `Team`/`Membership`/`User` records via forged `membership` events (`membership_handler.rb`).
- Trigger `RefreshCheckRunsJob` via forged `check_suite` events.

These are unauthorized cross-repository writes to another organization's stack/task state, matching the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Requires the attacker to be a legitimate GitHub App administrator/owner of one of the organizations already configured in the same multi-tenant Shipit instance (i.e., they control that org's own `webhook_secret`, which they set themselves when creating their GitHub App per `docs/setup.md`). No Shipit account, session, or the victim organization's secret is needed — only the ability to POST a crafted, correctly-signed body to the shared `/webhooks` endpoint. This is realistic for any Shipit deployment that follows the documented multi-org configuration pattern to serve several organizations from one instance.

### Recommendation
Bind the HMAC key selection to the same trusted identifier that handlers use to select the target repository/stacks, and validate that the two agree before dispatching:
1. In `verify_signature`, after verifying with the secret chosen for `repository_owner`, also verify that `repository.full_name`'s owner segment equals `repository_owner` (or, more robustly, iterate/verify signature against the secret of the org that actually owns `repository.full_name`, not a value taken from an as-yet-unverified field).
2. Alternatively, do not use a value from the unverified body to pick the verification key at all — dispatch each configured organization's secret and require exactly one specific match consistent with the destination repository, or scope webhook URLs per-organization (`/webhooks/:organization`) so the URL segment (server-side, trusted routing data) — not payload content — determines which secret is used.
3. Add a check that rejects requests where `repository.owner.login` (used for authentication) does not match the owner of `repository.full_name` (used for the actual mutation).

### Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and distinct `webhook_secret`, per `config/secrets.development.example.yml`'s documented multi-org schema.
2. As the (unprivileged w.r.t. Shipit) administrator of `OrgA`'s GitHub App, obtain `OrgA`'s `webhook_secret` (which you legitimately possess since you configured it).
3. Craft a `push` event JSON body with:
   - `"repository": {"full_name": "OrgB/victim-repo", "owner": {"login": "OrgA"}}`
   - `"ref": "refs/heads/main"`, `"after": "<arbitrary-sha>"`
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and successfully verifies the signature using `OrgA`'s secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, triggering `sync_github` for `OrgB`'s stacks — an org that never approved this payload and whose secret was never used.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
