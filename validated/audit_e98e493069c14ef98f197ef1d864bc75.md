### Title
Cross-repository status forgery via unscoped sha lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits by SHA alone across the entire `commits` table, with no check that the commit's stack belongs to the repository the inbound webhook was signed for. Because git commit SHAs are content-derived and identical across forks/mirrors of the same upstream history, an attacker who owns any repository sharing ancestor commits with a victim stack can send a legitimately-signed `status` webhook from their own repo and have it applied to the victim's `Commit`, flipping `Commit#deployable?` to true and triggering `schedule_continuous_delivery`.

### Finding Description
The claimed binding is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` — i.e., a status update should only ever be applied to a commit whose stack belongs to the repository that the webhook's signature was verified against. This binding is never checked.

`WebhooksController#verify_signature` verifies the HMAC using `repository_owner` derived from the payload's own repository/organization fields [1](#0-0) , so an attacker who owns any GitHub repository/org can get a webhook they control signed and accepted, as long as it's registered with a `secret` shipit knows about for *their own* org.

`Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper that scopes operations to `Repository.from_github_repo_name(repository_name)` derived from `payload.dig('repository', 'full_name')` [2](#0-1) , and other handlers (e.g. pull_request handlers) use `repository_owner`/`repository.full_name` to scope. `StatusHandler#process`, however, ignores this and instead does:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

This query has no `stack_id`/repository filter at all — it matches any `Commit` row across the entire database with the given `sha`, regardless of which repository's stack it belongs to. `Commit#create_status_from_github!` then calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }` [4](#0-3) , which creates a `Status` row bound to the victim commit's actual `stack_id` (not the attacker's), and `Status.replicate_from_github!` just persists whatever state is supplied [5](#0-4) .

`Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [6](#0-5) , and `success?` is delegated to `status.state` [7](#0-6) . Since SHAs are content hashes, any commit shared between a victim's tracked branch history and an attacker-controlled repository (e.g. a public fork, or any repo seeded with the same commit objects) will produce colliding rows in `Commit.where(sha: ...)`. The attacker doesn't need to guess a hash — they legitimately possess a repository containing the exact same commit object (same tree/parents/author/message/timestamps) as an ancestor of the victim's branch, register a webhook for their own repo, and fire a `status` event carrying that SHA with `state: 'success'`.

None of the existing guards intervene: `verify_signature` only proves the payload came from the org named in the payload, not that the SHA it references is scoped to that org's stacks; the `ExplicitParameters` schema in `StatusHandler` only validates types (`sha`, `state`, etc.), not repository ownership of the commit [8](#0-7) ; and `StatusHandler` never calls the `stacks`/`repository_name` scoping helper that other handlers use.

### Impact Explanation
An attacker can write a fabricated `success` `Status` row onto a victim stack's undeployed commit that they do not control, without any legitimate CI ever reporting success for that repository. This flips `Commit#deployable?` and can trigger `schedule_continuous_delivery` if the victim stack has continuous deployment enabled, or otherwise unlocks manual deploys of a commit that never passed real CI — an unauthorized-deploy class impact ("a payload for one repository mutating another's stack/commit," matching the Critical impact category). This is repeatable against any victim stack whose tracked branch shares ancestor commit SHAs with any repository the attacker controls (very common via public forks, mirrors, or template repositories), and the attacker pays only the cost of owning/registering a webhook on such a repo.

### Likelihood Explanation
Preconditions: victim stack has `ignore_ci: false`, an undeployed commit at `pending`/`failure`, and — critically — shares at least one commit SHA with a repository the attacker owns or controls (trivial via forking any public repo tracked by Shipit, since fork history retains identical SHAs for shared commits). The attacker needs no Shipit credentials, no maintainer access to the victim repo, and no GitHub secrets — only the ability to register/own a repository and send a normal, correctly-signed webhook from it. This is low-cost and repeatable at will against any stack tracking a forkable/public repository.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository the webhook was verified for, e.g. filter `Commit.where(sha: params.sha, stack: stacks)` (using the existing `Handler#stacks` helper based on `payload.dig('repository', 'full_name')`) instead of an unscoped `Commit.where(sha: ...)`, so a status can only ever be applied to commits belonging to stacks of the repository that authenticated the webhook.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from a foreign repository cannot mark a victim commit deployable" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine"
  victim_commit = shipit_commits(:first)
  victim_commit.statuses.destroy_all
  victim_commit.update!(state: 'pending') # via a real Status row if needed
  refute victim_commit.reload.deployable?

  # Attacker's own repo shares this SHA (e.g. shared fork ancestor) and is
  # correctly signed for their own org - simulated here by calling the
  # handler directly with a foreign repository payload.
  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'attacker/ci',
    'repository' => { 'full_name' => 'attacker/forked-repo', 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert victim_commit.reload.deployable?, "victim commit became deployable from a foreign repository's webhook"
end
```
This asserts `victim_commit.deployable?` flips `false -> true` purely as a side effect of a webhook payload whose `repository.full_name` never matches `victim_stack`'s repository, proving `StatusHandler#process`'s unscoped `Commit.where(sha: ...)` breaks the repository-ownership binding.
