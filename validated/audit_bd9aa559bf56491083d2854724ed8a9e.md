### Title
CCMenu API endpoint ignores API client's stack scope, allowing a stack-scoped token to read any stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor used by every other API controller and resolves the target stack with an *unscoped* `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!(params[:stack_id])` helper defined in `BaseController`. This breaks the binding "the stack a token authorises == the stack it touches": an `ApiClient` record that is scoped to a single stack via `belongs_to :stack, optional: true` can still read the CI/deploy status of *any* stack, because the permission check only validates the `read:stack` string permission, never the stack identity.

### Finding Description
`ApiClient` supports being scoped to a single stack: [1](#0-0) . Enforcement of that scope is centralized in `BaseController#stacks`/`#stack`, which restricts the queryable stacks to `current_api_client.stack_id` when the client is scoped: [2](#0-1) .

Authorization itself is enforced only by permission-name matching, not by stack identity: [3](#0-2) .

`CCMenuController` re-declares `stack` to bypass the scoped `stacks` collection entirely, resolving the stack directly from the global `Stack` model: [4](#0-3) . It also swaps the whole authentication mechanism to a raw query-string token instead of basic auth: [5](#0-4) .

Because `require_permission :read, :stack` only calls `check_permissions!('read', 'stack')`, which checks `permissions.include?('read:stack')` with no reference to the requested `params[:stack_id]` [6](#0-5) , and `stack` no longer restricts to the client's own stack, any token that has the `read:stack` permission — including one created and scoped to stack A — can be replayed against `/api/stacks/:stack_id/ccmenu.xml` for stack B and successfully render B's status: [7](#0-6) .

This is the structural analog of the audited bug: in the flash-loan case, the check used the wrong variable (`remaining` instead of the raw deposited value) so the guard didn't actually validate what it claimed to validate; here, the guard (`check_permissions!`) validates the wrong thing too — it validates the permission label but not the specific resource (`stack_id`) that the request touches, and the code path that would have supplied that missing check (`stacks.from_param!`) is deliberately bypassed by `CCMenuController#stack`.

### Impact Explanation
This allows unauthenticated (relative to the target stack) reads of another stack's deploy state and CI status — the exact "High" bucket item: "unauthenticated read of stack state, task streams or deploy output". A stack-scoped CCMenu/API token leaked or shared for one project (these tokens are long-lived signed IDs, see `ApiClient#authentication_token`) grants the holder read access to every other stack's latest deploy/rollback state and lock status in the installation, not just the stack it was issued for.

### Likelihood Explanation
Likelihood is moderate to high wherever stack-scoped `ApiClient`s exist: the model explicitly supports `stack_id` scoping (`belongs_to :stack, optional: true`), and the test suite itself demonstrates and relies on stack-scoping being respected elsewhere in the API (`"an api client scoped to a stack will only see that one stack"`), confirming this is an intended security boundary that `CCMenuController` fails to honor. Any caller in possession of a stack-scoped `read:stack` token (e.g., a scoped CCMenu URL, or any client provisioned with a `stack_id`) can trivially exploit this by changing the `stack_id` route parameter — no additional privilege or secret is required beyond the token itself.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped resolver from `BaseController` (`stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!(params[:stack_id])`, so a stack-scoped API client can never resolve a stack outside its `stack_id`.

### Proof of Concept
1. Provision (e.g. via console/rake, mirroring the test fixture `here_come_the_walrus`) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id; obtain its `authentication_token`.
2. Request `GET /api/stacks/<Stack-B-id>/ccmenu.xml?token=<token>`.
3. `authenticate_api_client` in `app/controllers/shipit/api/ccmenu_controller.rb:33-36` accepts the token via `ApiClient.authenticate(params[:token])`.
4. `require_permission :read, :stack` passes because the token has `read:stack` in its permission list, regardless of `stack_id`.
5. `stack` (overridden, `app/controllers/shipit/api/ccmenu_controller.rb:29-31`) resolves `Stack.from_param!(params[:stack_id])` against Stack B directly, ignoring that the token is scoped to Stack A.
6. The response renders Stack B's latest deploy/rollback status and lock state — data the token was never authorized to see.
