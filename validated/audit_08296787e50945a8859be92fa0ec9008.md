### Title
Webhook signature verification is keyed off an unauthenticated payload field, decoupling the authenticated organization from the repository/stack that is actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses which GitHub App's `webhook_secret` to validate the `X-Hub-Signature` against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified JSON body. In a multi-organization deployment (a mode explicitly documented and supported, see `docs/setup.md` "Using Multiple Github Applications"), this couples "the organization whose secret authenticated the request" to a field of the payload that is otherwise never cross-checked against the field the downstream handlers use to identify the target repository/stack (`repository.full_name`, `organization.login`, `sender.login`, etc.).

### Finding Description
`Shipit::WebhooksController` runs `verify_signature` as a `before_action`: [1](#0-0) 

`repository_owner` is derived purely from the attacker-supplied JSON body, before any signature check has occurred: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a per-organization `GitHubApp` instance keyed by this attacker-influenced string, and `verify_webhook_signature` is checked using *that* org's `webhook_secret`: [3](#0-2) 

Multi-org configuration is a first-class, documented feature (`docs/setup.md`, "Using Multiple Github Applications" and `config/secrets.development.shopify.yml`), where each organization has its own, separately-configured, independently-optional `webhook_secret`: [4](#0-3) 

Crucially, `webhook_secret` is explicitly documented as **optional** in `docs/setup.md` ("Webhook secret (optional)"), and if it is left unset for a given org, `verify_webhook_signature` unconditionally passes:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

Once `verify_signature` passes (either because a secret was correctly guessed/known for the org named in `repository.owner.login`, or because that org has no secret configured at all — a documented, supported state), the raw JSON body is handed unmodified to every registered handler for the event type: [5](#0-4) 

Handlers then resolve the *actual* target repository/stack from a **different** field of the same body — `repository.full_name` (or, for `membership`, `organization.login` independently) — with no re-validation that it matches the organization whose secret was used to authenticate the request: [6](#0-5) [7](#0-6) [8](#0-7) 

This is the equality-binding break called out in the prompt: **organization that authenticated == repository that is written** is never enforced. `repository_owner` (auth-selection key) and `repository.full_name` / `organization.login` (write-target key) are two independent fields of the same attacker-controlled JSON body, and nothing forces them to agree.

### Impact Explanation
For an instance running Shipit in the documented multi-org mode where at least one configured organization has no `webhook_secret` (an explicitly optional, documented setting), an unauthenticated network attacker can post arbitrary, fully-controlled JSON directly to `/webhooks` with `repository.owner.login` (or `organization.login`) set to the org lacking a secret, while setting `repository.full_name` (or the `membership` handler's `organization.login`) to any other tracked repository/organization in the instance. Because the "no secret" org's check always returns `true`, signature verification never inspects the actual target org/repo at all, and the forged event is processed as if it came from GitHub for that unrelated repository. This lets an attacker:
- Trigger `push`/`status`/`check_suite` events that force `GithubSyncJob`/`RefreshCheckRunsJob` to re-sync and mark arbitrary commits as passing/CI-green, unblocking continuous deployment and merge queues.
- Forge `membership` events to add/remove arbitrary GitHub logins from any `Shipit.github_teams`-backed `Team`, which directly feeds `User#authorized?` and thus the `Shipit.github_teams` authorization boundary that gates all UI/API access.
- Forge `pull_request` events to archive/unarchive review stacks for other repositories.

This maps to the High/Critical impacts called out in the prompt's rules: escalation into `Shipit.github_teams` authorization, and (depending on what continuous delivery/merge automation is configured) an unauthorized ship/merge.

### Likelihood Explanation
Exploitability is conditioned on the operator running the documented multi-org configuration with at least one organization configured without a `webhook_secret` — a state the code and docs both treat as legitimate ("optional"), not a misconfiguration outside the documented deployment model. Given that condition, the attack requires no credentials, no session, and no GitHub App access at all — only knowledge of the organization login lacking a secret (discoverable via the public, unauthenticated `merge_status#check`/`show` actions, which reveal stack `repo_owner`/`repo_name`) and the target repository's `full_name`. I could not verify from the codebase whether any concrete deployment ships with an org missing a `webhook_secret` by default; this is an operator choice permitted (and documented as fine) by the engine.

### Recommendation
Do not use an attacker-controlled payload field to select the authentication material. Options:
- Require `webhook_secret` to be present for every configured organization and fail closed (raise, not `return true`) when it is absent, removing the "no-secret" bypass entirely.
- After verifying the signature, cross-check that every repository/organization identifier the handler will act on (`repository.full_name`, `organization.login`, etc.) belongs to the same organization key that authenticated the request (`repository_owner`), rejecting the webhook otherwise.

### Proof of Concept
Preconditions: multi-org Shipit config with organizations `no-secret-org` (no `webhook_secret` configured) and `victim-org` (tracked stacks exist, e.g. `victim-org/victim-repo`).

```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json
(no valid X-Hub-Signature required, or an arbitrary one)

{
  "action": "added",
  "team": { "id": 1, "name": "Deployers", "slug": "deployers", "url": "https://github.com/x" },
  "organization": { "login": "no-secret-org" },
  "member": { "login": "attacker-controlled-github-login" }
}
```

Because `repository_owner` resolves `organization.login` = `no-secret-org` and that org has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally, and `MembershipHandler` creates/updates a `Team` and membership using the `organization.login` value from the body without any tie-back to the org that "authenticated" the request. Repeating with `push`/`status`/`pull_request` payloads whose `repository.full_name` points at `victim-org/victim-repo` similarly lets the attacker drive `GithubSyncJob`, commit statuses, or review-stack archive/unarchive for a repository unrelated to the organization used to pass signature verification.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
