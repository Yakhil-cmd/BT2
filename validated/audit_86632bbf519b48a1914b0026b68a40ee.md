### Title
Textcoin claim fails permanently when network TPS fee rises after the textcoin was funded, freezing the recipient's funds - (File: wallet.js)

### Summary
When a sender creates a "textcoin" (a one-time-use address funded with bytes/asset that the recipient later claims), the sender pre-pays a dynamic `tps_fee` estimated *at creation time* and adds it to the textcoin's output amount. When the recipient later claims the textcoin, the actual `tps_fee` required to compose the claiming unit is recomputed fresh based on the *current* network TPS. If TPS (and therefore the required fee) has risen since the textcoin was created, the amount reserved for fees is insufficient and the claim transaction cannot be composed, permanently stranding the recipient's funds — the same "stale fee vs. currently required fee" bug class as the reported `relayerFee`/`mintDepositInQueue` issue, where an operation queued/funded against one fee value fails once the fee increases before it is actually executed.

### Finding Description
In `wallet.js`, `sendMultiPayment`'s `addFeesToParams` computes the textcoin's `tps_fee` once, at the moment of sending, via `composer.estimateTpsFee`, and bakes it into the textcoin output amount: [1](#0-0) 

This `tps_fee` is a dynamic, network-load-dependent value (see `composer.estimateTpsFee` / `parentComposer.getTpsFee`, which scale with current TPS): [2](#0-1) 

Later, when the recipient calls `receiveTextCoin` to claim the funds, the claiming unit is composed via `composer.composeJoint`, which independently recomputes the `tps_fee` required for *that* unit based on the network conditions *at claim time*, not the fee that was reserved when the textcoin was funded: [3](#0-2) 

If the freshly computed fee exceeds the funds available on the textcoin (bytes reserved at creation for `TEXTCOIN_CLAIM_FEE + tps_fee_at_creation_time`), `composeJoint` reports `NOT_ENOUGH_FUNDS`: [4](#0-3) 

`receiveTextCoin`'s `ifNotEnoughFunds` handler only recovers if a local signer for the recipient's *own* wallet address is available and can supplement the fee; otherwise (e.g., web-wallet/email-claim flows, or private-asset claims which explicitly disable this retry) it fails outright and returns a hard error to the user: [5](#0-4) 

This mirrors the Y2K `relayerFee` issue exactly: a value is computed and "locked in" against an asset amount at one point in time (deposit into queue / textcoin funding), but a later privileged/automatic step (relayer minting / recipient claiming) recomputes the fee dynamically, and if the fee has increased in the interim the operation fails because the pre-committed amount can no longer cover it.

### Impact Explanation
Any bytes or asset funds sent as a textcoin become effectively unspendable/frozen if network TPS fee levels rise between creation and claim, since the shortfall cannot be covered by the recipient except in the narrow case where they control an already-funded wallet address to subsidize the missing fee. For private-asset textcoins the retry path is explicitly disabled (`opts._private = true` blocks the fallback), so the funds are provably stuck. This is a fund-freezing condition reachable purely by ordinary wallet users through the standard textcoin send/claim flow — no privileged actor is required.

### Likelihood Explanation
TPS fees in ocore are explicitly designed to fluctuate with network load (`getCurrentTpsFee`, `getLocalTpsFee`, exponential scaling with TPS). Any textcoin that sits unclaimed for a period during which network activity increases (a realistic and common scenario, e.g., emailed textcoins claimed days/weeks later) will encounter this discrepancy. The window of exposure is the entire time between sending and claiming a textcoin, which is unbounded by design.

### Recommendation
- When composing a textcoin, over-provision the reserved fee with a safety margin (e.g., a fixed multiple of the estimated `tps_fee`) so minor TPS increases don't break claimability, and/or
- When claiming, always allow supplementing the fee shortfall from the recipient's own address regardless of whether the payment is private (adjusting only the fee-paying inputs, not the private asset amount itself), and/or
- Store/lock the `tps_fee` value used at the time of funding and permit the claim transaction to reuse that value instead of recomputing it fresh against current network conditions, mirroring the audit's suggestion to store the fee value alongside the queued data rather than reading a mutable global at settlement time.

### Proof of Concept
1. Sender calls `wallet.sendMultiPayment` with a textcoin output; `addFeesToParams` reserves `TEXTCOIN_CLAIM_FEE + tps_fee_T0` bytes on the generated one-time address, where `tps_fee_T0` reflects network TPS at time `T0`.
2. Network TPS increases substantially before the textcoin is claimed (e.g., recipient waits, or network load organically grows).
3. Recipient calls `wallet.receiveTextCoin`; internally `checkStability` → `composer.composeJoint` (or `divisibleAsset`/`indivisibleAsset` composer) recomputes `tps_fee` at time `T1 > T0`, which is now higher than `tps_fee_T0`.
4. `composeJoint`'s change computation goes non-positive; since `opts.send_all = true` for byte textcoins, `handleError` returns `NOT_ENOUGH_FUNDS` instead of throwing.
5. `receiveTextCoin`'s `ifNotEnoughFunds` callback rejects the claim unless a local signer for another funded address is supplied; for private-asset textcoins this fallback is disabled entirely (`opts._private = true`), so the funds are permanently unclaimable.

async function estimateTpsFee(arrFromAddresses, arrOutputAddresses) {
//	if (storage.getMinRetrievableMci() < constants.v4UpgradeMci)
//		return 0;
	const max_aa_responses = constants.MAX_RESPONSES_PER_PRIMARY_TRIGGER;
	const arrWitnesses = storage.getOpList(Infinity);
	if (conf.bLight) {
		const network = require('./network.js');
		const response = await network.requestFromLightVendor('light/get_parents_and_last_ball_and_witness_list_unit', {
			witnesses: arrWitnesses,
			from_addresses: arrFromAddresses,
			output_addresses: arrOutputAddresses,
			max_aa_responses,
		});
		return (response.last_stable_mc_ball_mci >= constants.v4UpgradeMci) ? response.tps_fee : 0;
	}
	const timestamp = Math.round(Date.now() / 1000);
	const { arrParentUnits, last_stable_mc_ball_unit, last_stable_mc_ball_mci } =
		await parentComposer.pickParentUnitsAndLastBall(db, arrWitnesses, timestamp, arrFromAddresses);
	if (last_stable_mc_ball_mci < constants.v4UpgradeMci)
		return 0;
	const rows = await db.query("SELECT 1 FROM aa_addresses WHERE address IN (?)", [arrOutputAddresses]);
	const count_primary_aa_triggers = rows.length;
	const tps_fee = await parentComposer.getTpsFee(db, arrParentUnits, last_stable_mc_ball_unit, timestamp, 1 + count_primary_aa_triggers * max_aa_responses);
	// in this implementation, tps fees are paid by the 1st address only
	const [row] = await db.query("SELECT tps_fees_balance FROM tps_fees_balances WHERE address=? AND mci<=? ORDER BY mci DESC LIMIT 1", [arrFromAddresses[0], last_stable_mc_ball_mci]);
	const tps_fees_balance = row ? row.tps_fees_balance : 0;
	return Math.max(tps_fee - tps_fees_balance, 0);
}
