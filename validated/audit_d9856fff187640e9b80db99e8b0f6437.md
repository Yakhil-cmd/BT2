Based on my analysis, I found a plausible analog vulnerability in the webhook signature verification flow.

### Title
Webhook signature verified against organization derived from payload, but processed repository is derived from a separate unauthenticated payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner`, which is read directly from the untrusted JSON payload (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). However, the handler code that actually determines which `Stack`/`Repository` record gets mutated uses a *different* payload field, `payload.dig('repository', 'full_name')` [1](#0-0) . Neither of these two payload fields is cross-checked against the other, nor is the signature itself scoped to the specific repository being written.

### Finding Description
`verify_signature` computes the app/secret to verify against solely from `repository_owner`: [2](#0-1)  and derives that owner login independently of `full_name`: [3](#0-2) .

Once the HMAC check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` is invoked with the raw, attacker-controlled JSON body [4](#0-3) . Handlers resolve the target `Stack` via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [1](#0-0) .

In a multi-organization Shipit deployment (explicitly documented and supported, each org configured with its own `webhook_secret`) [5](#0-4) , `Shipit.github(organization: repository_owner)` is looked up per-organization [6](#0-5) . The binding that should hold is: *the organization whose secret authenticated the signature* == *the repository whose Stack is written to by the handler*. Because `repository.owner.login` (used for auth) and `repository.full_name` (used for the write) are two independent, attacker-controlled fields in the same JSON body, an attacker who knows or controls one organization's `webhook_secret` (e.g., because they administer that org's own GitHub App installation in a multi-tenant Shipit instance) can compute a valid signature over a forged body where `repository.owner.login` names their own org (so the signature validates), while `repository.full_name` names a repository belonging to a completely different, victim organization also hosted on the same Shipit instance. The handler will then act on the victim's `Stack` (e.g., trigger `GithubSyncJob`, record commit `Status`, process `check_suite`, or `membership`/`pull_request` events) using data that was never authenticated by the victim organization's own secret.

### Impact Explanation
This breaks a repository-write/authentication binding: an org that legitimately authenticated a webhook is not the same org as the repository being mutated. Depending on which handler fires, an attacker could inject fabricated commit statuses, trigger sync/deploy-relevant background jobs (`GithubSyncJob`), or manipulate team membership/pull-request state for a stack they do not own on a shared multi-org Shipit instance, without ever possessing that org's webhook secret. This aligns with the "cross-repository writes" / unauthorized-action class of High-severity impact.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (a supported and documented configuration) and requires the attacker to control or know the `webhook_secret` for at least one of the configured organizations — typically true for any org admin allowed to manage their own GitHub App integration on a shared instance. Given that constraint, forging the payload is trivial (plain HTTP POST with a computed HMAC). This is a real but narrower-scope condition (multi-tenant hosting), so likelihood is moderate rather than universal.

### Recommendation
After signature verification, re-derive the repository owner strictly from the same GitHub App/organization context used for verification, and reject (422) any payload where `repository.full_name`'s owner segment does not match `repository_owner`/the verifying organization. Alternatively, look up the `Stack`/`Repository` scoped to the verified organization instead of trusting `full_name` from the unauthenticated JSON body directly.

### Proof of Concept
1. Deploy Shipit with two organizations configured per `docs/setup.md`'s multi-org example, `OrgA` (attacker-controlled, secret known) and `OrgB` (victim, hosts a tracked Stack, e.g. `orgb/victim-repo`).
2. Attacker crafts payload:
```json
{
  "repository": { "full_name": "orgb/victim-repo", "owner": { "login": "OrgA" } },
  ...event-specific fields (e.g. push "after" sha, or "sha"/"state" for status)...
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, raw_body)`.
4. POST to `/webhooks` with `X-Github-Event: status` (or `push`).
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully (attacker knows this secret).
6. `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` runs, and the handler resolves the target via `payload.dig('repository', 'full_name')` = `"orgb/victim-repo"`, writing a forged `Status` (or triggering `GithubSyncJob`) against the victim's stack — despite the request never being authenticated by `OrgB`'s secret.

Note: I was unable to fully trace `Shipit.github`'s exact per-organization secret lookup implementation and `Repository.from_github_repo_name` internals within the available index (their full bodies were not returned by search), so the exact mechanics of the organization-to-secret mapping and repository resolution should be verified directly in `lib/shipit.rb` and `app/models/shipit/repository.rb` before treating this as confirmed exploitable; a Devin session with full file access would be needed to validate every line involved.
