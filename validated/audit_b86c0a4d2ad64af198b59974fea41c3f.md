Confirmed: `Repository.from_github_repo_name` at [1](#0-0)  does a plain `owner/name` lookup with no relation whatsoever back to the `repository.owner.login` field that `verify_signature` used to pick the HMAC secret.

### Title
Webhook signature is verified against `repository.owner.login`, but the repository written to is looked up from the independently‑controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate the inbound webhook based on `repository.owner.login` (or `organization.login`) taken from the same JSON body that is being verified. Every webhook `Handler` (e.g. `PushHandler`), however, resolves the target `Stack`/`Repository` to mutate using a *different* field of that body: `repository.full_name`, via `Handler#stacks` → `Repository.from_github_repo_name`. Nothing ties `repository.full_name`'s owner segment back to `repository.owner.login`.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)   # repository.owner.login
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [2](#0-1) , using `repository_owner` derived at [3](#0-2) .

The signature check only proves the sender knows the `webhook_secret` configured for **the organization named in `repository.owner.login`**. In Shipit's supported multi-tenant configuration, each GitHub organization has its own independent App/`webhook_secret` [4](#0-3) , and any account that legitimately owns/administers one such organization's GitHub App knows that org's own `webhook_secret` (it is generated by/shared with the org's app admin, not global to Shipit).

After signature verification passes, the actual mutation target is chosen independently:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) , and
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [1](#0-0) .

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack: [6](#0-5) , which fetches commits with the GitHub credentials belonging to `stack`'s own repository/owner, not the org whose secret authenticated the request.

The invariant that should hold is:
`organization authenticated by verify_signature (repository.owner.login)` == `owner of repository.full_name used by Handler#stacks to pick the Repository/Stack that gets written`

That equality is never checked. A caller who legitimately controls org `A`'s GitHub App (and therefore knows `A`'s `webhook_secret`) can craft a raw POST body where `repository.owner.login == "A"` (so `verify_signature` picks `A`'s secret and the HMAC computed over the whole `raw_post` validates) while `repository.full_name == "B/some-repo"` for a completely unrelated organization/repository `B` also hosted on the same Shipit instance. Because the HMAC only proves "this body was signed with A's secret," not "this body only describes org A's resources," the mismatch is undetected, and `Handler#stacks` happily resolves and acts on stacks belonging to `B`.

This is the same bug class as the Anvil report ("credited"/authorized quantity vs. the quantity actually acted upon are allowed to diverge because the update/consistency check was never enforced on all code paths) mapped onto the rule's named binding: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
An admin of one onboarded GitHub organization/App (attacker-controlled, not privileged in the target org `B`) can forge a `push` (or other) webhook body that is validly signed for their own org but names another tenant's repository in `repository.full_name`. Depending on handler and event type this can trigger unauthorized `GithubSyncJob`s, `Stack#sync_github` calls, commit/status ingestion, or PR/review-stack actions against `B`'s stacks — an unauthorized write into another tenant's repository/stack scope. This matches the "cross-repository writes" High/Critical impact category, since it lets an authenticated-but-unrelated organization write into stacks it does not own or administer.

### Likelihood Explanation
Requires only that the attacker legitimately controls/administers a second GitHub organization/App already configured on the same multi-tenant Shipit instance (a documented, supported deployment configuration — see "Using Multiple Github Applications" in `docs/setup.md`), and the ability to POST an arbitrary raw body directly to the public `/github/webhooks` endpoint (no GitHub-side enforcement is involved, since Shipit's own controller performs signature verification itself). No `ApiClient` token, session, or `webhook_secret` of the target org is needed. This is a moderate-likelihood scenario limited to multi-org deployments, but requires no special privilege on the victim org.

### Recommendation
- Short term: In `Shipit::Webhooks::Handlers::Handler#stacks` (and anywhere `repository.full_name` is used to resolve a `Repository`/`Stack`), require that the owner segment of `repository.full_name` matches the `repository_owner`/organization that was actually used to select the `webhook_secret` in `WebhooksController#verify_signature`, and reject the request otherwise.
- Long term: Thread the authenticated organization through to every `Handler`, and add an assertion/test that a webhook signed for org `A` can never resolve to a `Stack` belonging to a `Repository` with a different `owner`. Add regression tests analogous to `test/controllers/webhooks_controller_test.rb`'s existing signature tests, but covering `repository.owner.login != repository.full_name`'s owner.

### Proof of Concept
1. Deploy Shipit with the multi-org config shown in `docs/setup.md` ("Using Multiple Github Applications"), onboarding organization `A` (attacker-administered) and organization `B` (victim, hosts stack `B/victim-repo`).
2. Attacker, who administers org `A`'s GitHub App and therefore knows `A`'s `webhook_secret`, crafts:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha that exists on B/victim-repo>",
  "repository": { "owner": { "login": "A" }, "full_name": "B/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(A_webhook_secret, raw_body)>` and POSTs it to `/github/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "A")`, verifies the HMAC using `A`'s secret against `raw_post`, and passes [2](#0-1) .
5. `PushHandler#process` resolves `Repository.from_github_repo_name("B/victim-repo")` → the real `B` repository/stack, and calls `stack.sync_github(expected_head_sha: ...)`, causing Shipit to fetch/sync commits and enqueue jobs against org `B`'s stack, entirely on the say-so of an unrelated org `A`'s credentials [6](#0-5) .
