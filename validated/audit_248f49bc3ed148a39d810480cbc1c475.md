## #Vulnerability found for this question.

### Title
Permanent, protocol-wide freezing of lender funds due to lack of an emergency write-off/force-liquidate path when a borrower's asset oracle becomes permanently unresolvable - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The external report's bug class — a protocol offering no way to resolve a position when the normal resolution path (an oracle-dependent settlement) can never succeed — maps directly onto Zest v2's `liquidate()` flow. Liquidation requires successfully resolving the price of **every** asset in the borrower's position mask (all enabled collateral and debt assets), and there is no DAO/emergency function anywhere in the codebase (`grep` for `emergency|force-liquidate|write-off|admin-liquidate` returns no contract matches) that can force a write-off, force-liquidate, or exclude a broken asset from a position's health/liquidation evaluation. If any single asset's oracle feed becomes permanently unresolvable, the affected position can never be liquidated again — even though the position is unhealthy — permanently freezing the corresponding vault liquidity for unrelated, unprivileged lenders.

### Finding Description
`liquidate()` in `v0-4-market.clar` builds the borrower's full position and calls `get-notional-evaluation`, which resolves prices for **all** assets referenced by the position's bitmask via `get-assets`/`price-multi-resolve`/`price-resolve`: [1](#0-0) 

Price resolution for any single asset is all-or-nothing: `price-resolve` calls `resolve-price-feed` → `resolve-pyth`/`resolve-dia`, each of which `unwrap!`s the external oracle call into `ERR-ORACLE-PYTH`/`ERR-ORACLE-DIA`, and further asserts staleness/positivity into `ERR-ORACLE-INVARIANT`: [2](#0-1) 

`price-multi-resolve`/`iter-price-multi` propagate a single failed resolution into `ERR-ORACLE-MULTI` for the *entire* multi-asset call: [3](#0-2) 

Because `liquidate()` uses `try!` throughout this chain, a single unresolvable asset (e.g., a Pyth `ident` that is delisted/deprecated, or the hardcoded `SP1G48FZ4Y7JY8G2Z0N51QTCYGBQ6F4J43J77BQC0.dia-oracle` permanently reverting or losing the queried key) reverts the whole `liquidate()` call for that borrower — for every collateral/debt pair in the position, not just the broken asset. There is no fallback: no "disable this asset and evaluate the rest," no DAO override to force a liquidation using a manually supplied/emergency price, and no write-off mechanism analogous to `socialize-debt` that can be invoked independently of a successful `liquidate()` execution. `check-dao-auth`/`.dao-executor` gated functions only cover configuration (asset enable/disable, pause states, impl swaps) — none of them can force resolution of an unhealthy position whose oracle is dead.

### Impact Explanation
The victim class here is the vault's other, unrelated depositors/lenders (unprivileged principals distinct from the borrower and any would-be liquidator), harmed through the shared vault liquidity state. If a borrower's position becomes undercollateralized while one of its assets' oracle feeds is permanently broken, no liquidator can ever repay/seize that position: `liquidate()` unconditionally reverts before reaching health/liquidation-amount logic. The debt keeps compounding on paper via `accrue`/`total-borrowed`, but principal is never returned to the vault (`system-repay`/`socialize-debt` are never reached), so the corresponding vault's real backing is impaired. Other suppliers to that same asset vault who attempt to `redeem` share the same underlying liquidity pool and can be left unable to withdraw their principal — a **temporary/permanent freezing of funds** for parties who never interacted with the broken-oracle position. This matches the in-scope impact class of "temporary freezing of funds" (and can escalate to insolvency for that vault if the position never recovers).

### Likelihood Explanation
Likelihood is driven by oracle availability, which is realistic given the design: Pyth feed IDs can be deprecated/rotated, and the DIA oracle dependency is a hardcoded external principal (`SP1G48FZ4Y7JY8G2Z0N51QTCYGBQ6F4J43J77BQC0.dia-oracle`) outside Zest's control — if that contract's `get-value` call for a given key ever reverts or the key is removed, every position holding that asset (as either collateral or debt) becomes permanently unliquidatable via the normal path, with no admin escape hatch. This does not require any special privilege or attacker action beyond having (or causing) a position with debt against an asset whose feed later becomes unresolvable.

### Recommendation
Add a DAO/emergency-gated liquidation and/or write-off path that does not depend on `price-multi-resolve` succeeding for the borrower's entire asset mask, e.g.:
- An `emergency-liquidate`/`force-socialize-debt` function, callable only via `.dao-executor`, that can (a) exclude a specific broken asset from a position's mask when evaluating health/liquidation for the remaining assets, or (b) accept an emergency-supplied price for that asset (analogous to a "market invalidation" flag) to allow bad-debt socialization to proceed.
- Alternatively, decouple bad-debt socialization (already implemented as `socialize-debt-asset`/`vault-socialize-debt`) from a fully successful `liquidate()` execution, so a DAO-triggered write-off can occur for a specific `{borrower, asset-id}` pair without requiring all of the borrower's other assets to price-resolve successfully.

### Proof of Concept
Not directly reproducible as a unit test without external oracle infrastructure, but the failure chain is deterministic from the code:
1. Borrower opens a position with collateral asset A (or debt asset A) whose oracle `ident` is registered against a Pyth/DIA feed.
2. The feed ID is later deprecated/removed from the oracle contract (or the DIA contract call reverts for that key going forward) — `call-pyth`/`call-dia` now permanently return an error.
3. Borrower's position becomes unhealthy (price of debt asset rises, or unrelated collateral price falls).
4. Any liquidator calls `liquidate(borrower, ...)`; `get-full-position`/`get-notional-evaluation` invoke `price-multi-resolve` over the mask, which calls `price-resolve` for asset A, which reverts with `ERR-ORACLE-PYTH`/`ERR-ORACLE-DIA`/`ERR-ORACLE-INVARIANT`, propagated as `ERR-ORACLE-MULTI`.
5. `liquidate()` reverts; this repeats forever. The position's debt is never repaid to the vault, and no DAO function exists to force resolution — confirmed by the absence of `emergency`/`force-liquidate`/`write-off` public functions in the contracts (only doc mentions in `docs/dao.md`). [4](#0-3)

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))

        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))

        (timestamp (get timestamp resolution))
