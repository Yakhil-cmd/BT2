### Title
Missing `nonReentrant` on `_requestERC20Transfer` Allows `requestNonce` Duplication via ERC20 Token Callback — (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20._requestERC20Transfer` increments `requestNonce` **after** making external calls to the token contract. Unlike `BridgeTransferKLAY._requestKLAYTransfer`, which is explicitly protected by `nonReentrant`, `_requestERC20Transfer` carries no reentrancy guard. A registered ERC20 token with transfer hooks (e.g., an ERC777 token used via its ERC20 interface) can re-enter `onERC20Received` during `_payERC20FeeAndRefundChange`, causing two `RequestValueTransfer` events to be emitted with **consecutive nonces** for a single user deposit. The bridge operator on the counterpart chain processes both events, resulting in double minting or double unlocking of bridged assets.

---

### Finding Description

`BridgeTransferKLAY` explicitly inherits `ReentrancyGuard` and applies `nonReentrant` to both `handleKLAYTransfer` and `_requestKLAYTransfer`. The comment in `BridgeFee.sol` at line 41–42 even documents this requirement:

```
// Caller of this function must be nonReentrant.
// - BridgeTransferKLAY._requestKLAYTransfer() is nonReentrant
``` [1](#0-0) 

However, `_payERC20FeeAndRefundChange` — the ERC20 analogue — carries no such comment and its callers carry no such guard: [2](#0-1) 

Inside `_requestERC20Transfer`, the execution order is:

1. `_payERC20FeeAndRefundChange` → calls `IERC20(_token).safeTransfer(feeReceiver, fee)` **(external call)**
2. `ERC20Burnable(_tokenAddress).burn(_value)` **(external call, if `modeMintBurn`)**
3. `emit RequestValueTransfer(..., requestNonce, ...)` — uses current nonce
4. `requestNonce++` — increments **after** all external calls [3](#0-2) 

If the token's `transfer` implementation invokes a callback on the bridge (e.g., via ERC777's `tokensReceived` hook on `feeReceiver`, or a custom `onERC20Received` call), the reentrant execution path is:

| Step | Execution | `requestNonce` |
|------|-----------|----------------|
| 1 | Outer call enters `_requestERC20Transfer` | N |
| 2 | `safeTransfer(feeReceiver, fee)` triggers callback | N |
| 3 | **Reentrant** `onERC20Received` → `_requestERC20Transfer` | N |
| 4 | Reentrant emits `RequestValueTransfer(nonce=N)` | N |
| 5 | Reentrant `requestNonce++` | N+1 |
| 6 | Outer call resumes, emits `RequestValueTransfer(nonce=N+1)` | N+1 |
| 7 | Outer `requestNonce++` | N+2 |

Two `RequestValueTransfer` events are emitted — nonces N and N+1 — for a single user deposit. The bridge operator's Go-side handler (`handleRequestValueTransferEvent`) submits both as separate `HandleERC20Transfer` calls on the counterpart chain. [4](#0-3) 

The counterpart bridge's `handleERC20Transfer` has no `nonReentrant` guard either, and each nonce is distinct, so both pass `_lowerHandleNonceCheck` and `_voteValueTransfer`: [5](#0-4) 

The same structural flaw exists in `BridgeTransferERC721._requestERC721Transfer`, which also increments `requestNonce` after external calls (`tokenURI` call and `burn`) and has no `nonReentrant` guard: [6](#0-5) 

---

### Impact Explanation

- **Unauthorized mint / unlock of bridged assets**: The counterpart bridge processes two handle-transfer calls for a single deposit. In `modeMintBurn` mode this mints `_value` tokens twice; in lock/unlock mode it releases `_value` tokens twice from the counterpart bridge's reserves.
- **Broken bridge accounting invariant**: The total locked/burned supply on the source chain diverges from the total minted/unlocked supply on the destination chain, permanently corrupting the bridge's asset peg.
- **Exact corrupted value**: `_value` extra tokens are minted or unlocked on the counterpart chain per reentrant invocation.

---

### Likelihood Explanation

The trigger requires a registered ERC20 token with transfer callbacks. Token registration is an owner-controlled operation, making this a semi-trusted trigger. However:

- ERC777 tokens are fully ERC20-compatible and are commonly registered on bridges. An operator may register one without awareness of the reentrancy risk.
- The asymmetry is telling: the developers explicitly guarded the KLAY path (`nonReentrant` + comment in `BridgeFee.sol`) but omitted the same protection for ERC20 and ERC721, indicating the risk was partially recognized but incompletely applied. [7](#0-6) [8](#0-7) 

---

### Recommendation

1. Add `nonReentrant` to `_requestERC20Transfer` and `_requestERC721Transfer` (and their public entry points `requestERC20Transfer`, `onERC20Received`, `requestERC721Transfer`, `onERC721Received`).
2. Move `requestNonce++` to **before** any external call (checks-effects-interactions pattern), consistent with how `_requestKLAYTransfer` emits the event and increments nonce before the fee-payment external call is made.
3. Have `BridgeTransferERC20` and `BridgeTransferERC721` inherit `ReentrancyGuard` as `BridgeTransferKLAY` already does. [9](#0-8) 

---

### Proof of Concept

```solidity
// Malicious ERC20 token registered on the bridge
contract MaliciousERC20 is ERC20 {
    address bridge;
    address victim;

    function transfer(address to, uint256 amount) public returns (bool) {
        // Standard transfer
        super.transfer(to, amount);
        // Re-enter bridge during fee payment
        if (to == feeReceiver && !reentered) {
            reentered = true;
            IBridge(bridge).onERC20Received(
                victim,      // _from
                attacker,    // _to (on counterpart chain)
                depositValue,
                0,           // _feeLimit
                ""
            );
        }
        return true;
    }
}
```

**Attack flow:**

1. Attacker registers `MaliciousERC20` on the bridge (or exploits a legitimately registered ERC777 token).
2. Attacker calls `requestERC20Transfer(maliciousToken, attacker, value, feeLimit, "")`.
3. `_payERC20FeeAndRefundChange` calls `maliciousToken.safeTransfer(feeReceiver, fee)`.
4. `MaliciousERC20.transfer` re-enters `onERC20Received` → `_requestERC20Transfer`.
5. Reentrant call emits `RequestValueTransfer(nonce=N)` and increments nonce to N+1.
6. Outer call emits `RequestValueTransfer(nonce=N+1)` and increments nonce to N+2.
7. Bridge operator submits `handleERC20Transfer` for both nonces N and N+1 on the counterpart chain.
8. Both pass `closedValueTransferVotes` (distinct nonces) and both mint/unlock `value` tokens.
9. Attacker receives `2 * value` tokens on the counterpart chain for a single deposit. [10](#0-9) [11](#0-10)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}
