### Title
Cross-Organization Webhook Spoofing via Mismatched `repository.owner.login` (signature key) and `repository.full_name` (record lookup) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
When Shipit is configured with the multi-organization GitHub App schema, `WebhooksController#verify_signature` selects the HMAC secret to validate an incoming webhook using `repository.owner.login` (or `organization.login`) taken from the *attacker-controlled* JSON body, while the event handlers that actually mutate state (e.g. `PushHandler`, `StatusHandler` via `Commit`, PR handlers) resolve the target `Repository`/`Stack` using `repository.full_name`, a separate field from the same body. Because both fields are attacker-supplied in the raw JSON payload, they are never checked for consistency, breaking the binding: `organization that authenticated == repository that is written`.

using `repository_owner`, defined as: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the app/webhook secret for that organization key in the multi-org config schema documented in `docs/setup.md` ("Using Multiple Github Applications") and `lib/shipit.rb#github_app_config`. The signature (`X-Hub-Signature`) is verified with `GitHubApp#verify_webhook_signature`, which HMACs the *entire raw body* against that org's `webhook_secret`.

Once the signature passes, `WebhooksController#create` dispatches the **same raw JSON body** to registered handlers: [3](#0-2) 

Handlers resolve the affected `Repository`/`Stack` independently, using `repository.full_name` (a different JSON key than `repository.owner.login`): [4](#0-3) [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` simply splits `full_name` on `/`, with no cross-check against `repository.owner.login`.

Because an attacker (e.g. an organization admin who legitimately controls one configured GitHub org — call it `attacker-org` — and therefore knows or can trigger a webhook with `attacker-org`'s valid `webhook_secret`) crafts the raw JSON body itself, they can set:
- `repository.owner.login = "attacker-org"` (used only for HMAC key selection — passes verification with the secret they legitimately possess), and
- `repository.full_name = "victim-org/victim-repo"` (used by the handler to locate the real target `Stack`/`Repository`/`Commit`).

The signature check validates that the byte stream was signed by `attacker-org`'s secret, but the *content* interpreted by the handler targets a stack belonging to an entirely different, unrelated organization (`victim-org`) that the attacker was never authorized to write to. This is the exact class of bug described in the external report's bug class: a payload field acted upon (`full_name`) is never covered/pinned by the field the verified signature is actually keyed to (`owner.login`).

### Impact Explanation
This allows unauthorized cross-repository/cross-organization state mutation: an admin of one onboarded GitHub organization can forge webhook events (`push`, `status`, `pull_request`, `membership`, `check_suite`) that are attributed to and act upon a completely different organization's stacks — e.g. triggering `PushHandler#process` to call `stack.sync_github` on a victim stack, injecting fabricated commit statuses via `StatusHandler`, or manipulating `PullRequest`/`ReviewStack` archive/unarchive state for a victim's repository — without ever having write access, an `ApiClient` token, or the victim organization's `webhook_secret`. This constitutes a cross-organization write achieved purely by exploiting a validated-signature/acted-upon-field mismatch, matching the "cross-repository writes" high/critical impact bucket.

### Likelihood Explanation
Exploitability requires: (1) the deployment to use the multi-organization GitHub App configuration schema (`docs/setup.md`, explicitly supported and documented feature, not a misconfiguration), and (2) the attacker to be a legitimate, authenticated party for at least one of the configured organizations (i.e., they can get a real webhook delivered/signed for `attacker-org`, or replay/craft a POST to `/webhooks` with a valid signature for that org). Given that webhook payload fields are otherwise fully attacker-controlled JSON and GitHub's own delivery does not prevent a self-hosted forwarding proxy or a modified webhook payload from being sent directly to the `/webhooks` endpoint (which is a plain unauthenticated HTTP endpoint gated only by HMAC), likelihood is realistic in any multi-tenant Shipit deployment.

### Recommendation
Bind the field used for cryptographic key selection to the field used for record lookup: after computing `repository_owner` for the HMAC key, validate that the same organization also owns the repository referenced by `repository.full_name` (i.e., assert `full_name.split('/').first.casecmp?(repository_owner)`), rejecting the request (422) on mismatch. Alternatively, once verified, always derive the repository/stack lookup exclusively from `repository.owner.login` (the field actually covered by the signature) rather than re-parsing an independent `full_name` field.

### Proof of Concept
1. Deploy Shipit with the multi-org config schema, onboarding `attacker-org` (attacker is an org owner/admin, knows or can obtain `attacker-org`'s `webhook_secret` through legitimate access) and `victim-org` (unrelated, has its own stacks).
2. Craft a POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>`.
4. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and validates the signature successfully (it is a correct HMAC for that key).
5. `PushHandler#process` then executes `stacks` → `Repository.from_github_repo_name("victim-org/victim-repo")`, matching and syncing the victim's actual stack — despite the request never being signed by `victim-org`'s secret. [7](#0-6) [8](#0-7) [6](#0-5)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
