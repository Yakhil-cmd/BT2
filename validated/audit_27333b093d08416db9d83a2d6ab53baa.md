### Title
CCMenu API endpoint bypasses per-stack `ApiClient` scoping, letting a stack-scoped token read any stack's build/deploy state - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` may only touch the stack it was authorized for by resolving the target record through the `stacks` scope (`stacks.from_param!(params[:stack_id])`), where `stacks` is filtered to `current_api_client.stack_id` when the client is scoped. `Shipit::Api::CCMenuController` overrides `#stack` and resolves the record directly via `Stack.from_param!(params[:stack_id])`, completely bypassing that scoping check. This is the exact analog of the Vyper bug: the "declared" authorization surface (the permission/scope an `ApiClient` is granted) is checked, but the "effective" behavior (which stack record is actually acted upon) silently diverges from what was authorized.

### Finding Description
`Shipit::ApiClient` supports scoping a token to a single stack via `belongs_to :stack, optional: true`, and `Api::BaseController#stacks`/`#stack` enforce this scope: [1](#0-0) 

Every other API controller inherits this `#stack` method and is therefore correctly bound: a client whose `stack_id` is set can only resolve stacks inside `Stack.where(id: current_api_client.stack_id)`. `Api::CCMenuController`, however, defines its own `#stack`: [2](#0-1) 

This calls `Stack.from_param!(params[:stack_id])` directly — it never touches `current_api_client.stack_id` at all. The `require_permission :read, :stack` before_action only checks that the token carries the generic `read:stack` permission string; it does not verify that the token is scoped to *this* stack: [3](#0-2) [4](#0-3) [5](#0-4) 

The binding that should hold is: `current_api_client.stack_id == stack.id` (enforced everywhere else via `stacks.from_param!`). In `CCMenuController#show`, that binding is broken: any valid token with `read:stack` permission — including ones fixtures show are created scoped to exactly one stack, e.g. `here_come_the_walrus` (`stack: shipit`, `permissions: [read:stack]`) — can supply an arbitrary `stack_id` route segment and read the CI/deploy status XML for any stack in the installation, not just the one it was authorized for. [6](#0-5) 

The route exposing this is registered without any additional scoping middleware: [7](#0-6) 

`CCMenuController#show` then renders the last deploy/rollback state for the resolved (unscoped) stack: [8](#0-7) 

producing fields such as name/activity/lastBuildStatus/lastBuildLabel/lastBuildTime/webUrl for a stack the requester was never authorized to see, as tested for the "own" stack case (but never for a foreign one) in: [9](#0-8) 

### Impact Explanation
This is a cross-stack authorization boundary break: an `ApiClient` token that is intentionally restricted to a single stack (a common integration pattern, e.g. CI status widgets) discloses build/deploy state and CI status for every other stack managed by the Shipit instance, including unrelated repositories/environments/teams. This matches the "High" category "unauthenticated/unauthorized read of stack state, task streams or deploy output" through a scope the attacker's own token does not carry.

### Likelihood Explanation
The bug requires only possession of any valid `ApiClient` token that has `read:stack` permission (regardless of which stack it is scoped to) — no privileged account, GitHub access, or session is needed beyond what any legitimate API integration already holds. Because `CCMenuController` is the only controller that reimplements `#stack` this way, the flaw is easy to trigger by simply changing the `stack_id` route segment and unlikely to be caught by tests that only exercise the "correct" stack.

### Recommendation
Remove the `#stack` override in `Api::CCMenuController` (or make it call `stacks.from_param!(params[:stack_id])` like `BaseController`) so that stack-scoped `ApiClient` tokens can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. Create (or use) a stack-scoped `ApiClient` with `stack: <stack A>` and `permissions: ['read:stack']` (mirrors the `here_come_the_walrus` fixture).
2. Compute its `authentication_token`.
3. Send `GET /api/stacks/<owner-B>/<repo-B>/<env-B>/ccmenu?token=<token>` where `owner-B/repo-B/env-B` identifies a different stack B that the client is not scoped to.
4. Observe HTTP 200 with a full `project.xml.builder` response describing stack B's last deploy/rollback status, name, activity, and URLs — despite the token only being authorized for stack A. Compare against any other API endpoint (e.g. `GET /api/stacks/<owner-B>/<repo-B>/<env-B>`) with the same token, which correctly returns 404/empty scope because it goes through `BaseController#stack` → `stacks.from_param!`.
