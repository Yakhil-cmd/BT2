### Title
Webhook signature verification is bound to the payload's `repository.owner`/`organization.login`, not the repository the event actually writes to, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate a webhook against using an **unverified** field taken from the same JSON body it is trying to authenticate: `repository_owner` (`params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')`). Once verification passes, `create` re-parses the body and dispatches it to handlers that determine the actual `Repository`/`Stack` to write to using a *different, independently-read* field: `payload.dig('repository', 'full_name')`. Nothing ties these two payload-derived values together, so the organization whose secret authenticates the request and the repository whose stack is mutated can be made to diverge.

### Finding Description
The controller performs verification before dispatch: [1](#0-0) [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The secret used for HMAC comparison is looked up per organization, and Shipit explicitly supports multiple independently configured GitHub organizations/apps on a single instance, each with its own optional `webhook_secret`: [3](#0-2) [4](#0-3) 

Critically, `verify_webhook_signature` **returns `true` unconditionally when no `webhook_secret` is configured** for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```
This is a documented, supported configuration state — every shipped example config ships `webhook_secret: # nil` and the "Using Multiple Github Applications" setup docs describe per-organization secrets that can be left unset.

After verification, the actual event processing looks up the target `Repository`/`Stack` using a completely separate payload field, `repository.full_name`, inside `Handler#stacks`/`#repository_name` and every concrete handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`, etc.): [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

This is the exact bug-class analog described in the report: a field that is used to authorize/verify (`repository.owner.login`, standing in for "vesting order/inherited stepsClaimed") is never actually bound to the field that determines what gets mutated (`repository.full_name`, standing in for "the listing that gets the inherited state"). The equality the engine implicitly (and incorrectly) assumes is:

`organization_whose_secret_verified(payload) == organization_that_owns(repository.full_name)`

but nothing enforces this. An attacker can pick any org name that is configured on the instance but has a blank `webhook_secret` for `repository.owner.login`/`organization.login`, while setting `repository.full_name` to point at a *different, fully-configured* org/repository that has real stacks tracked by Shipit.

### Impact Explanation
Because verification is trivially satisfied (`return true unless webhook_secret`) for any configured-but-secretless organization, and the write path is keyed independently off `repository.full_name`, an unauthenticated attacker can forge events against any tracked stack belonging to a *different, properly-secured* organization:
- `PushHandler` → forces `stack.sync_github(expected_head_sha:)` for arbitrary target stacks. [9](#0-8) 
- `StatusHandler` → injects fabricated commit statuses (`create_status_from_github!`) that deploy-safety checks rely on to gate deploys. [7](#0-6) 
- `CheckSuiteHandler` → schedules check-run refreshes against arbitrary commits. [8](#0-7) 
- `PullRequest::OpenedHandler`/`ReopenedHandler` → can auto-provision or unarchive review stacks for a repository the attacker does not own. [10](#0-9) 

Forging fabricated "success" commit statuses that deployability checks consult is a direct path toward an **unauthorized deploy** of a commit that never actually passed CI on the real repository — this lands in the Critical bucket ("an unauthorized deploy, rollback or merge"), and forging events across organization boundaries constitutes a **cross-repository write**, also Critical.

### Likelihood Explanation
Exploitability requires only that: (1) the Shipit instance tracks at least two GitHub organizations (a documented, first-class configuration — "Using Multiple Github Applications"), and (2) at least one of them has not set a `webhook_secret` (a state every shipped example/config template defaults to). No session, API token, or knowledge of any actual secret is required — the attacker only needs to know or guess the name of a configured organization with a blank secret, which is entirely plausible during rollout/onboarding of a new org onto a shared Shipit instance. This is a moderate-likelihood, high-impact issue rather than a purely theoretical one, since the vulnerable default (`webhook_secret` optional/blank) is baked into the documented setup flow itself.

### Recommendation
Bind signature verification to the same identity used for dispatch: derive the organization used to select the `GitHubApp`/secret from the **already-resolved `Repository`** record looked up via `repository.full_name` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner`), not from a separately-trusted `owner.login`/`organization.login` field. Additionally, treat a missing `webhook_secret` for a configured organization as a hard failure (reject unsigned webhooks) rather than an implicit bypass, and require operators to explicitly opt in (e.g. an `allow_unsigned_webhooks: true` flag) if they intentionally want to skip verification for a given org.

### Proof of Concept
Given a Shipit instance configured with two orgs (as `test/dummy/config/secrets_double_github_app.yml` demonstrates is a normal supported topology): `OrgA` (webhook_secret unset) and `OrgB` (webhook_secret set, tracks a real stack for `OrgB/real-repo`):

```
POST /github/webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # irrelevant, verification short-circuits

{
  "organization": { "login": "OrgA" },
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/real-repo" },
  "sha": "<sha of a commit under review on OrgB/real-repo>",
  "state": "success",
  "context": "ci/tests",
  "description": "forged",
  "target_url": "https://attacker.example"
}
```
`verify_signature` resolves `repository_owner` → `"OrgA"`, calls `Shipit.github(organization: "OrgA")`, and `verify_webhook_signature` returns `true` unconditionally because `OrgA`'s `webhook_secret` is blank. `create` then re-parses the same body and `StatusHandler#process` matches `Commit.where(sha: params.sha)` — which belongs to `OrgB/real-repo` — and writes a fabricated "success" status on it, despite `OrgB` having its own `webhook_secret` correctly configured and never having authenticated this request.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
