### Title
Cross-tenant webhook forgery: verification keyed on `repository.owner.login` while stack lookup keyed on `repository.full_name` allows unsigned requests naming a secretless org to archive a victim org's review stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used for HMAC verification based on `params.dig('repository','owner','login')`, but the actual repository/stack acted upon by handlers (e.g. `LabeledHandler`) is resolved from the independent `params.dig('repository','full_name')` field. Because these two fields are never cross-validated, an attacker can set `repository.owner.login` to an org that has no `webhook_secret` configured (which makes `GitHubApp#verify_webhook_signature` return `true` unconditionally) while setting `repository.full_name` to a victim org's fully-configured repository, bypassing signature verification entirely for that victim repo.

### Finding Description
The broken binding: the code implicitly assumes `repository_owner (used for verification) == owner segment of repository.full_name (used for handler dispatch)`, but no code enforces `params.dig('repository','owner','login') == params.dig('repository','full_name').split('/').first`.

Code path:
1. `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` using `repository_owner` defined as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` returns `true unless webhook_secret`, i.e., if the org named by `repository.owner.login` has no `webhook_secret` configured, verification passes unconditionally regardless of signature presence/validity. [3](#0-2) 
3. Once verification passes, `create` dispatches `params` (the full raw JSON, unmodified) to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [4](#0-3) 
4. `LabeledHandler#repository` resolves the repository to act on using `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — a field completely independent from `repository_owner` used in step 1. [5](#0-4) 
5. `LabeledHandler#handle` calls `stack.archive!` on the `ReviewStack` resolved from that repository/environment, with no further ownership check tying it back to the verified org. [6](#0-5) 

Attacker's exact request: POST `/webhooks` with header `X-Github-Event: pull_request`, no `X-Hub-Signature` header (or an empty/garbage one), and JSON body containing `"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}`, `"action": "labeled"`, a valid `pull_request` object with `state: "open"` and a label matching the victim repo's provisioning label. Since `attacker-org` is configured in `Shipit.github` but has no `webhook_secret`, `verify_webhook_signature` returns `true` without ever checking the signature, and `Shipit.github(organization: "attacker-org")` does not raise `GithubOrganizationUnknown` (attacker must control/configure an org that exists in `Shipit.github`'s app config — trivial if any onboarded org has been set up without a webhook secret, e.g., during rollout). The handler then operates entirely on `victim-org/victim-repo`, archiving the victim's review stack.

Why existing guards fail: `drop_unhandled_event` only checks the event type is handled; `verify_signature` only rescues `GithubOrganizationUnknown` for the owner-org lookup, it never inspects `full_name`; `ExplicitParameters` schema in `LabeledHandler` only requires `repository.full_name` to be a `String`, with no consistency check against the owner used for verification; there is no model or controller-level assertion binding `repository.owner.login` to `repository.full_name`.

### Impact Explanation
An attacker who has any organization configured in `Shipit.github` without a `webhook_secret` (or can get one onboarded, e.g. a fresh/misconfigured tenant) can forge unsigned webhook payloads naming that org's login while targeting an arbitrary victim organization's repository via `full_name`. This lets them archive (or unarchive) any victim `ReviewStack` — a cross-tenant write triggered by a payload that never authenticated against the victim's secret. This matches the "payload for one repository mutating another's stack" Critical impact category. It's repeatable against any repository/stack combination as long as one org in the whole Shipit deployment lacks a `webhook_secret`, and blast radius spans the entire multi-tenant install.

### Likelihood Explanation
Preconditions: at least one org configured under `Shipit.github` must have no `webhook_secret` set (this is an operator-side omission, not something the attacker sets, but is plausible in real deployments — e.g., during onboarding of a new org, dev/staging orgs, or if an operator simply never rotates in a secret for a low-traffic org). The attacker needs no Shipit credentials and no knowledge of any secret — they only need to know that such an org exists and know the victim's `full_name` and an open PR/label to trigger `LabeledHandler`'s archive path. This is low-cost and fully repeatable once the secretless-org precondition holds.

### Recommendation
Cross-validate that `params.dig('repository','owner','login')` matches the owner segment parsed from `params.dig('repository','full_name')` before dispatching to handlers, and reject the request (`head(422)`) on mismatch. Additionally, do not allow `verify_webhook_signature` to pass unconditionally for orgs with no secret in production configurations that host multiple tenants — require a `webhook_secret` to be present for every configured org, or bind verification directly to the repository derived from `full_name` rather than a separately-supplied `owner.login`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
```ruby
test "unsigned webhook naming a secretless org but a victim org's full_name does not bypass verification" do
  # config: two orgs — "attacker-org" (no webhook_secret) and "victim-org" (webhook_secret: "s3cr3t")
  victim_repo = shipit_repositories(:shipit) # full_name "victim-org/repo", review_stacks_enabled: true
  stack = create_review_stack(repository: victim_repo, ...)

  payload = {
    action: "labeled",
    number: stack.pull_request.number,
    pull_request: { ..., state: "open", head: { sha: "x", ref: stack.branch }, labels: [{ name: victim_repo.provisioning_label_name }] },
    repository: { owner: { login: "attacker-org" }, full_name: "victim-org/repo" },
    sender: { login: "attacker" }
  }.to_json

  post shipit.webhooks_path, params: payload, headers: { 'X-Github-Event' => 'pull_request', 'Content-Type' => 'application/json' } # no X-Hub-Signature

  assert_response :success   # binding broken: head(422) is NOT returned despite unsigned request naming a secret-bearing victim org
  assert stack.reload.archived?  # victim stack archived by unauthenticated cross-tenant request
end
```
Both sides of the equality (`repository_owner`'s org secret presence vs. the org actually authorizing `full_name`'s repository) diverge: verification passes for `attacker-org` (no secret) yet the mutation lands on `victim-org`'s stack (secret-protected), confirming the bypass.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
