### Title
Webhook signature verifier is selected by `organization.login`/`repository.owner.login` while the event's target repo is selected by the independent `repository.full_name` field, letting a payload authenticated by one organization's (weaker) secret mutate another repository's review-stack `PullRequest` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#repository_owner` picks the GitHub App/secret used to verify `X-Hub-Signature` from `params.dig('repository','owner','login') || params.dig('organization','login')`, while `LabelCapturingHandler` (and all other `pull_request` handlers) resolve the actual affected repository from the independently-controlled `params.repository.full_name`. An attacker can supply a `repository` object that has `full_name` set to a victim repo but omits the nested `owner.login`, forcing `repository_owner` to fall back to a different `organization.login` value that is verified with a different (and potentially secret-less) GitHub App configuration.

### Finding Description
The claimed broken binding, stated as an equality that must hold but does not:

`Shipit.github(organization: repository_owner).webhook_secret` (verifier selector) **==** the GitHub App/secret that actually governs `params.repository.full_name` (target selector)

Code path:
- `WebhooksController#repository_owner` [1](#0-0)  falls back to `organization.login` whenever `repository.owner.login` is absent.
- `WebhooksController#verify_signature` uses that value to pick the `GitHubApp` instance and calls `verify_webhook_signature` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` trivially returns `true` when the resolved org's config has no `webhook_secret` [3](#0-2) .
- `LabelCapturingHandler` never consults `repository_owner`; it resolves the target repository strictly from `params.repository.full_name` [4](#0-3) , and only requires that nested `full_name` field in its schema, not `repository.owner.login` [5](#0-4) .
- If `reopened_active_stack?` matches (an active, existing review stack for that repo/PR), `capture_labels` persists `params.pull_request.labels.map(&:name)` onto the stack's existing `PullRequest` record [6](#0-5) .
- `ReviewStack#env` later upcases every stored label name into a `"NAME"=>"true"` environment entry merged into deploy/rollback command environments [7](#0-6) .

Root cause: two independently attacker-controlled JSON fields (`organization.login` used for authentication, `repository.full_name` used for authorization/target selection) are never checked for consistency against each other, and the multi-tenant `GitHubApp` config model (confirmed by `test/dummy/config/secrets_double_github_app.yml`, which defines multiple orgs each with their own `webhook_secret`/`bot_login`) allows one organization's weak/absent secret to authenticate events "on behalf of" an unrelated repository whose real owner has a properly configured secret.

Existing guards do not catch this: `verify_signature` only checks the signature against whichever org `repository_owner` resolves to, it never cross-checks that org against `repository.full_name`'s actual owner; `drop_unhandled_event` and the `ExplicitParameters` schema only enforce presence/types, not cross-field consistency; `GithubOrganizationUnknown` only fires when the org name is unrecognized, not when it mismatches the target repo.

### Impact Explanation
An attacker who can compose a raw webhook POST (no session, no API token required) and who knows the login of some organization configured on the same multi-tenant Shipit instance with a missing/weak `webhook_secret`, can forge a `pull_request` `reopened` event that is authenticated under that org's identity but targets `params.repository.full_name` pointing at a different, victim repository. If that victim repository already has an active `ReviewStack` with an associated `PullRequest`, the attacker overwrites `pull_request.labels` with arbitrary strings, which become uppercased environment variables injected into the review stack's deploy/rollback command environment (`ReviewStack#env`). Because the victim stack has `bot_login` (i.e., `Shipit.user`) configured, any auto-triggered deploy runs using that bot's GitHub identity, so attacker-controlled environment variables reach deploy tooling under the bot's authority — matching the Critical category "a payload for one repository mutating another's stack" and potentially "unauthorized deploy" if the injected env values affect deploy command behavior. This is repeatable against any repository/stack in the same Shipit instance as long as a matching organization with a lenient secret exists.

### Likelihood Explanation
This requires a specific, non-trivial configuration: (1) the Shipit instance manages multiple GitHub organizations/Apps (confirmed as a supported, tested topology via `secrets_double_github_app.yml`), (2) at least one configured organization has no `webhook_secret` (or one the attacker can produce a valid signature for), separate from the victim organization's own (properly secured) secret, and (3) the victim repository already has an active review stack with a real `PullRequest` record for the attacker to overwrite labels on (LabelCapturingHandler does not create the record itself for `reopened`). Attacker cost is low (a single crafted HTTP POST, no credentials), but the precondition of "a co-tenant organization with a weak secret" is an operator-configuration dependency rather than a guaranteed universal bypass in a single-org deployment.

### Recommendation
In `WebhooksController#verify_signature`, derive the verifying organization strictly and consistently with the value handlers use to resolve the target repository (e.g., always require and use `repository.owner.login`, or verify that `repository.full_name`'s owner matches the org used to select the `GitHubApp`/secret) and reject the request if they diverge, rather than silently falling back to `organization.login`.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure two GitHub Apps in test config: `victim-org` (has `webhook_secret`) and `attacker-org` (no `webhook_secret`), mirroring `secrets_double_github_app.yml`.
2. Create a `Repository` for `victim-org/victim-repo`, an active `ReviewStack` with `bot_login` set, and an existing `PullRequest` record with `labels: []`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no valid `X-Hub-Signature` for `victim-org`'s secret, and body:
```json
{
  "action": "reopened",
  "number": 1,
  "pull_request": { ...valid schema..., "labels": [{"name": "MALICIOUS_ENV"}] },
  "repository": { "full_name": "victim-org/victim-repo" },
  "organization": { "login": "attacker-org" },
  "sender": { "login": "attacker" }
}
```
4. Assert equality before: `pull_request.labels == []` and `repository_owner` resolves to `"attacker-org"` while `params.repository.full_name` resolves to `"victim-org/victim-repo"` (the broken binding).
5. Assert response is `200 OK` (not `422`), and after the request `pull_request.reload.labels == ["MALICIOUS_ENV"]`, demonstrating a write to the victim repo's stack authenticated under a different organization's secret. [8](#0-7) [3](#0-2) [9](#0-8) [7](#0-6)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
