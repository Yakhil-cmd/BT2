Based on the available context, the strongest analog to the "copy your own portfolio" bug class in this codebase is a **cross-organization repository binding break** in the inbound webhook handling path.

### Title
Webhook signature is verified against one organization's secret while handlers act on a different repository named in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization's webhook secret to use for HMAC verification based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) in the *same* JSON body being verified: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: ...)` resolves a distinct `GithubApp` instance (with its own `webhook_secret`) per organization, and unknown organizations raise `Shipit::GithubOrganizationUnknown`, which the controller explicitly rescues — confirming multi-organization webhook secrets are a supported, documented configuration rather than a host-misconfiguration: [3](#0-2) [4](#0-3) 

Once the signature is accepted, `create` dispatches the *entire* parsed payload to event handlers (`PushHandler`, `StatusHandler`, etc.), which resolve the target `Stack`/`Repository` using the payload's `repository.full_name` field, as shown by the test that manipulates `full_name` independently of the owner used for verification: [5](#0-4) [6](#0-5) 

The equality that should hold is: `organization whose secret authenticated the request == organization that owns the repository the handlers write to`. Nothing ties `repository.owner.login` (used to pick the secret) to `repository.full_name` (used to pick the Stack that gets mutated) beyond both living in the same JSON blob — the signature only proves "this body wasn't tampered with by someone lacking org A's secret," not "org A owns the repository named inside the body."

### Impact Explanation
An attacker who legitimately controls (or has installed the Shipit GitHub App on) their own organization "A" — a normal, supported tenant of a multi-org Shipit deployment — knows org A's `webhook_secret`. They can craft a raw POST to the public, unauthenticated `/webhooks` endpoint with `repository.owner.login: "A"` (so `verify_signature` validates against A's known secret) while setting `repository.full_name: "victim-org/victim-repo"` for a stack that belongs to a different tenant. Because handlers key off `full_name`, this can enqueue `GithubSyncJob`, mutate commit statuses, or otherwise force state changes on a stack the attacker does not own or authenticate for — a cross-repository/cross-tenant write with no Shipit session, API token, or GitHub credential for the victim org required. This matches the Critical "cross-repository writes" category.

### Likelihood Explanation
Likelihood depends entirely on the deployment being multi-organization with per-org webhook secrets (the code explicitly supports and expects this, per `GithubOrganizationUnknown` handling), and on the attacker owning/controlling at least one registered organization in that Shipit instance — a low bar for anyone permitted to onboard a repo, and importantly requires **no** privileged Shipit credential.

### Recommendation
After signature verification, re-derive the organization from `repository.full_name` (the field handlers actually act on) and confirm it matches the organization whose secret validated the signature (`repository_owner`) before dispatching to any handler; reject the request otherwise.

### Proof of Concept
1. Attacker registers/owns GitHub org `attacker-org`, which is configured in this Shipit instance with its own `webhook_secret` (per `lib/shipit/github_app.rb`).
2. Attacker computes `sha1=HMAC(attacker_secret, body)` over a crafted JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, ...push event fields...}`.
3. POST to `/webhooks` with `X-Github-Event: push` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully against the attacker's own secret.
5. `PushHandler` (dispatched in `create`) resolves the stack via `repository.full_name = "victim-org/victim-repo"`, mutating state for a repository the attacker doesn't control.

**Uncertainty note:** I could not inspect `app/models/shipit/webhooks/handlers/push_handler.rb` / `status_handler.rb` directly in this session (a tool-call error prevented reading them in the final round), so the exact lookup mechanism for `full_name` → `Stack` is inferred from `test/controllers/webhooks_controller_test.rb` (which manipulates `full_name` independently to test unknown-repo behavior) rather than confirmed by reading the handler source directly. I recommend verifying this lookup path directly in a follow-up session before treating this as fully confirmed.
