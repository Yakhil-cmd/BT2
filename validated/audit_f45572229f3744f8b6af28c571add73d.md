### Title
Missing validation of the unprivileged `creator` account in `initialize_with_permission` permanently freezes future creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`InitializeWithPermission::creator` is an `UncheckedAccount` with no signer requirement, no `address` constraint, and no zero/system-program-address validation. Its key is stored directly as `pool_creator` in `PoolState`, which becomes the sole, non-updatable recipient of all swap creator fees for the life of the pool.

### Finding Description
In `initialize_with_permission.rs`, the `creator` account is declared as: [1](#0-0) 
with no constraints at all — it is neither required to sign, nor checked against `Pubkey::default()`/`system_program::ID`, nor checked to be a valid, spendable wallet.

The value is passed straight into `pool_state.initialize(...)` as the pool creator address: [2](#0-1) 

This differs from `Initialize` (the unpermissioned path), where the equivalent field is the `creator` `Signer`, which at least has to sign the transaction, i.e. the caller must possess a real keypair for it.

By contrast, `amm_config.protocol_owner` and `amm_config.fund_owner` — set in `create_amm_config` — are protected: any later change goes through `update_amm_config`, which explicitly validates `require_keys_neq!(new_owner, Pubkey::default())`: [3](#0-2) 
There is no equivalent update path for `pool_creator` — the field is set once at `initialize`/`initialize_with_permission` time and is never modified anywhere else in the program (confirmed by the absence of any other reference to `pool_creator` besides the pool state definition and the two `collect_creator_fee*` instructions).

`pool_creator` is later used to gate and address the creator-fee collection instructions: [4](#0-3) [5](#0-4) 
In `collect_creator_fee_permissionless`, the ATA that receives the fee is derived with `associated_token::authority = creator`, and `creator` is only required to equal `pool_state.pool_creator`, without being a signer: [6](#0-5) 

If `pool_creator` is set to `Pubkey::default()` (or any other address with no known private key), the associated token account for creator fees can still be created and can still receive funds (SPL ATAs don't require the owner to be a real signer to receive tokens), but nobody can ever sign a transaction to further move or utilize those tokens out of that account, since the only path to spend from it requires the owner (`creator`) to sign, and no such keypair exists for the zero/default address.

### Impact Explanation
Every pool created through `initialize_with_permission` accrues `creator_fees_token_0`/`creator_fees_token_1` on every swap (see `pool_state.update_fees` calls in `swap_base_input.rs`/`swap_base_output.rs`). If `pool_creator` is the zero address, all creator fees generated by that pool for its entire lifetime become permanently locked in an ATA nobody can control — a permanent freezing of protocol/user funds. This is a High severity issue: unbacked/unspendable funds accumulate with no remediation path, since `pool_creator` cannot be updated after pool creation.

### Likelihood Explanation
`initialize_with_permission` is reachable by any account holding a valid `Permission` PDA (an unprivileged-but-permissioned caller from the swapper/pool-creator side, not an admin signer), and the attacker fully controls the `creator` account field in the same transaction — it can be set to `Pubkey::default()` or any other unspendable address with zero cost. Since there is no signer requirement or zero-address check, this is trivially triggerable in a single transaction with attacker-chosen accounts.

### Recommendation
Add validation on the `creator` account in `InitializeWithPermission`:
- Require `creator.key() != Pubkey::default()` (and ideally `!= system_program::ID`) via a constraint such as `constraint = creator.key() != Pubkey::default() @ ErrorCode::InvalidCreator`.
- Consider also requiring `creator` to be a signer, consistent with the unpermissioned `Initialize` path, or provide an admin/permission-holder controlled instruction to update `pool_creator` post-initialization (mirroring `set_new_protocol_owner`/`set_new_fund_owner` in `update_config.rs`) so misconfigured pools are recoverable.

### Proof of Concept
1. Attacker (or any account holding a valid `Permission` PDA) calls `initialize_with_permission` with `creator = Pubkey::default()` (or `11111111111111111111111111111111`).
2. `pool_state.initialize(...)` stores this value as `pool_creator` with no validation.
3. Swaps occur on this pool via `swap_base_input`/`swap_base_output`, accruing `creator_fees_token_0`/`creator_fees_token_1` in `pool_state`.
4. Anyone can call `collect_creator_fee_permissionless`, which creates the creator's ATA (owner = `Pubkey::default()`) and transfers the accrued fees into it.
5. Because no private key exists for the zero address, the tokens in that ATA can never be moved again — the creator fees are permanently frozen, with no on-chain mechanism to recover or redirect them since `pool_creator` is immutable after initialization.
