### Title
Cross-tenant commit status forgery via unscoped `sha` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha` with `Commit.where(sha: params.sha)`, without any scoping to the repository that the verified webhook payload belongs to. Because git SHAs (especially well-known ones like the empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`) can collide across unrelated repositories/stacks, a single signed webhook from one repository updates the CI status of every `Shipit::Commit` row across the entire instance that happens to share that SHA.

### Finding Description
The broken binding, stated explicitly: the set of `Commit` rows mutated by a verified payload should equal `{commits belonging to Repository == payload.repository.full_name}`, but the actual code computes `{commits in the DB where sha == payload.sha}` — a strictly larger, tenant-unaware set.

Code path: `WebhooksController#create` dispatches the parsed JSON to `Shipit::Webhooks.for_event(event)` handlers [1](#0-0) . Before dispatch, `verify_signature` only checks that the payload was signed by the GitHub App secret belonging to `repository_owner` (derived from `payload['repository']['owner']['login']`) [2](#0-1) [3](#0-2) . This proves authenticity of *who sent the payload* (the owning org/repo), but does not constrain *which DB rows* the handler is allowed to touch.

`Handler` (the base class) does provide a `repository_name`/`stacks` helper meant for exactly this kind of repository scoping [4](#0-3) , but `StatusHandler#process` does not use it — it queries `Commit` globally by `sha` alone: [5](#0-4) . Each matched commit, regardless of which stack/repository it belongs to, gets `create_status_from_github!(params)` invoked, mutating its CI status.

Exploit flow: attacker owns Repo A, creates an orphan/empty-tree commit (`git commit-tree` yields the deterministic SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904` with no tree entries), pushes it, and has any CI system they control POST a `status` event to `/webhooks` with `state: success`, `sha: 4b825dc642cb6eb9a060e54bf8d69288fbee4904`, and their own `repository.owner.login` (so the signature verifies against their own registered GitHub App/webhook secret for Repo A). If unrelated Stack B (owned by a different tenant) also has a `Commit` row with that same SHA — plausible since many repos use orphan/empty initial commits — that commit's `statuses` association is mutated too, potentially flipping Stack B's UI/gating state to "success" for a commit it never actually built.

Existing guards do not prevent this: `verify_signature` authenticates the sender's identity/org but is blind to the DB-wide `Commit.where(sha:)` query; `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.), not scope; there is no `Repository`/`Stack` uniqueness constraint tying `sha` to a single tenant, since `sha` is not unique across `Commit` rows.

### Impact Explanation
A single webhook from an attacker-controlled repository can write CI status records (`Shipit::Status` via `commit.create_status_from_github!`) onto commits belonging to unrelated stacks/tenants, without ever authenticating against those tenants' repositories. This is a cross-tenant payload-mutates-another-stack's-commit-state issue — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category. It is repeatable at will (attacker can push and re-push, replaying status webhooks) against any tenant stack that happens to contain a matching SHA, most reliably the well-known empty-tree SHA which is common for orphan/initial commits across many unrelated repositories. Since Shipit's deploy gating (`Stack#build_status`/pending-commits/mergeable logic) can consult commit statuses, forging a "success" status on someone else's commit could contribute to unblocking or misrepresenting deploy readiness for a repository the attacker never touched.

### Likelihood Explanation
Preconditions: (1) attacker needs any GitHub repository they control with a registered Shipit-integrated GitHub App/webhook (a normal, low-cost setup available to any user who onboards a repo to Shipit), and (2) some other tenant stack in the same Shipit instance must contain a `Commit` row with a colliding SHA — trivially true for the empty-tree SHA, which many repositories generate for orphan branches/initial state. No secrets, sessions, or elevated privileges are required; the attacker only uses their own legitimate webhook signing capability. This is fully repeatable and requires no timing race or GitHub-side cooperation beyond the attacker's own repo.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository named in the verified payload, e.g. join against `stacks`/`Repository.from_github_repo_name(repository_name)` (using the `stacks` helper already defined in `Handler`) before applying `where(sha: params.sha)`, so only commits belonging to the authenticated repository can be mutated.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create `stack_a` and `stack_b` (two distinct `Shipit::Stack` fixtures with distinct `Repository` rows, e.g. `org-a/repo-a` and `org-b/repo-b`).
2. Create `commit_a = stack_a.commits.create!(sha: '4b825dc642cb6eb9a060e54bf8d69288fbee4904', ...)` and `commit_b = stack_b.commits.create!(sha: '4b825dc642cb6eb9a060e54bf8d69288fbee4904', ...)`.
3. Build a `status` webhook payload with `repository.full_name = 'org-a/repo-a'`, `state: 'success'`, `sha: '4b825dc642cb6eb9a060e54bf8d69288fbee4904'`, stub/sign it so `verify_signature` passes for org-a only.
4. POST to `/webhooks` with `X-Github-Event: status`.
5. Assert: `commit_a.statuses.reload.count` increased by 1 (expected/legitimate), AND `commit_b.statuses.reload.count` also increased by 1 — proving the binding `{mutated commits} == {commits of repo org-a/repo-a}` is false, since `commit_b` belongs to `org-b/repo-b` and was never authenticated by this request.
