### Title
Burning a position NFT permanently bricks the account: liquidation and bad-debt cleanup both panic on the missing owner entry, stranding uncollectable debt - ([File: contracts/controller/src/storage/account.rs])

### Summary
The controller resolves every account's owner through the position-NFT `owner_of` cross-contract call. If the NFT token no longer exists, `try_account_owner` returns `None` and `get_account` panics with `AccountNotFound`. Because `liquidate`, `clean_bad_debt`, and `force_socialize_bad_debt` all load the account via `get_account`, an underwater borrower who burns their own NFT makes the debt unliquidatable and unsocializable forever — the analog of CVE-2019-9772's NULL dereference: a missing-object read on a path that assumed the object exists, crashing every caller.

### Finding Description
Ownership is never stored on the controller side; it is derived per call from the NFT: [1](#0-0) [2](#0-1) 

`try_get_account` requires both meta and resolved owner, so a missing `Owner` entry turns every account-scoped entrypoint into `AccountNotFound`: [3](#0-2) 

The harness tests prove the blast radius: after `PositionNftClient::burn(token_id)` on an underwater account, `try_liquidate` fails with `ACCOUNT_NOT_FOUND`, and both `try_clean_bad_debt` and `try_force_socialize_bad_debt` fail the same way — the protocol's entire loss-absorption path is dead for that account: [4](#0-3) 

Unlike the expired-TTL case (which the host auto-restores during simulation, per the same test file), a burned token is gone permanently — there is no re-mint or ownership-override path in scope that recovers the account.

### Impact Explanation
An unprivileged borrower executes: supply collateral, borrow near max LTV, wait (or push price) until the account is underwater, then call `burn` on their own position NFT (burn is an owner-authorized NFT operation, not controller-gated). From that point:

- No liquidator can touch the debt (`liquidate` → `AccountNotFound`).
- Keepers cannot socialize it (`clean_bad_debt`, `force_socialize_bad_debt` → `AccountNotFound`).
- The borrower's own collateral is also frozen, but when debt > collateral the attacker loses nothing net.

The pool books keep a debt line that can never be repaid, seized, or written down. Each such account is permanent bad debt; aggregated, this is protocol insolvency — suppliers' principal is silently impaired with no on-chain remediation. This meets "permanent freezing of funds / protocol insolvency."

### Likelihood Explanation
Fully unprivileged: the attacker needs only a normal borrow position and the owner auth on their own NFT. No admin, no timing race, no oracle manipulation required beyond ordinary market movement (which the attacker can wait for, since the burn works any time after they go underwater — and even before, as a pre-emptive griefing hedge). The cost is only the underwater collateral they were going to lose anyway. Medium-High likelihood conditional on the NFT `burn` entrypoint being reachable by the token owner (consistent with OZ-style NFT burn semantics used by this contract; I could not re-verify `position-nft/src/contract.rs` burn auth within the iteration budget).

### Recommendation
- Cache the owner (or an explicit `owner` field) in `AccountMeta` at mint/transfer time, and have `try_account_owner` fall back to it when the NFT lookup returns `None`, so burning a token cannot orphan account state.
- Alternatively, gate NFT `burn`/`transfer` on the account being position-free and debt-free (controller callback or NFT-side check), so a debt-bearing token can never be destroyed.
- At minimum, give `clean_bad_debt`/`force_socialize_bad_debt` a path that operates on position maps without resolving NFT ownership, so bad debt remains socializable even if the ownership leg is destroyed.

### Proof of Concept
1. Attacker calls `supply` then `borrow` on controller, obtaining `account_id` (NFT `token_id = u32(account_id)`).
2. Price moves so `is_liquidatable(account_id) == true` (debt > collateral).
3. Attacker calls `PositionNftClient::burn(token_id)` — succeeds with their owner auth.
4. Any `liquidate(liquidator, account_id, payments, SeizeMode::Transfer)` panics `AccountNotFound` at `get_account` → `try_account_owner` → `nft_try_owner_of_call` returning `None` (owner_of fails on missing token).
5. `clean_bad_debt(keeper, account_id)` and `force_socialize_bad_debt(account_id)` panic identically.
6. Debt sits on the books permanently; suppliers cannot be made whole. (Directly reproduced by the existing harness tests at `tests/test-harness/tests/controller/position_nft_ttl_and_ownership_reads.rs:296-333`, minus the adversarial framing.)

pub(crate) fn nft_try_owner_of_call(env: &Env, nft: &Address, account_id: u64) -> Option<Address> {
    let token_id = u32::try_from(account_id).ok()?;
    match PositionNftClient::new(env, nft).try_owner_of(&token_id) {
        Ok(Ok(owner)) => Some(owner),
        _ => None,
    }
