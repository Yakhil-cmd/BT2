### Title
`StatusHandler` writes CI status by SHA alone, breaking the organization-authenticated-vs-repository-written binding, enabling cross-tenant CI status forgery and unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook `status` event handler resolves the target `Commit` purely by `sha`, without verifying that the commit belongs to the repository/organization whose webhook secret authenticated the request. This breaks the equality `organization_that_authenticated == repository_that_is_written`, letting an attacker who controls any org/repo already configured in this Shipit instance forge CI status updates for commits belonging to a different tenant's stack.

### Finding Description
Webhook signature verification in `WebhooksController#verify_signature` selects the verifying GitHub App/organization config using a field taken from the payload itself: [1](#0-0) [2](#0-1) 

This only proves the payload was signed by *some* org's registered webhook secret — it says nothing about which repository the payload's data should be allowed to mutate. Every other handler enforces that binding by scoping lookups through `Handler#stacks`, which resolves the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')`: [3](#0-2) 

For example, `PushHandler` and `CheckSuiteHandler` both scope through `stacks`: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, does not call `stacks`/`repository_name` at all — it looks up `Commit` globally by `sha` only: [6](#0-5) 

`Commit.create_status_from_github!` then writes a new `Status` (state/context/description/target_url) onto whatever commit matched, regardless of which repository or organization it belongs to: [7](#0-6) 

That written status directly feeds `Commit#deployable?` (`success? && !blocked?`) and continuous-delivery triggering: [8](#0-7) [9](#0-8) 

**Before the attack:** the equality holds implicitly only because in practice every `status` payload historically originates from GitHub for the correct repo. **After the attack:** an attacker who has legitimate write access to *any* organization/repository already registered in this Shipit instance's `secrets.yml` (multi-tenant deployments configure many orgs, see `test/dummy/config/secrets_double_github_app.yml`) can send (or, since they legitimately own that org's repo, actually cause GitHub to send) a `status` webhook signed with their own org's webhook secret, but containing an arbitrary `sha` value. If that `sha` happens to correspond to a commit tracked under a *different* organization's stack in the same Shipit install (e.g., a fork/mirror, a shared commit due to cherry-pick/rebase, or simply guessing/observing a target commit's public SHA from GitHub), `StatusHandler` will attach a forged `success` status to that unrelated stack's commit — with no check that `payload['repository']['full_name']` matches the commit's actual `stack.repository`.

### Impact Explanation
This is a cross-repository write: `verified_organization != repository_written`. A forged `success` status can satisfy `ci.require`/`Commit#deployable?` for a victim stack, enabling that commit to pass Shipit's CI gating and be deployed/merged without having actually passed the victim repository's real CI checks — an unauthorized deploy condition explicitly listed as Critical impact.

### Likelihood Explanation
Exploitation requires only that the attacker control an org/repo that is *already* configured in the same multi-tenant Shipit instance (a common deployment pattern, as evidenced by `secrets_double_github_app.yml` supporting multiple GitHub Apps/orgs) — no privileged Shipit account, `ApiClient` token, or webhook secret theft is needed, since the attacker's own legitimate GitHub webhook for their own repo is correctly signed. The main precondition for a colliding `sha` is either a shared commit history between the attacker's and victim's repositories (forks, mirrors, template-based repos) or a known target SHA, which is realistic in many organizational setups sharing a single Shipit instance.

### Recommendation
Scope `StatusHandler#process` through the same repository binding used by other handlers: resolve the target stacks via `stacks` (i.e., `payload.dig('repository','full_name')`) and only update statuses for commits belonging to those stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, instead of an unscoped `Commit.where(sha: ...)`.

### Proof of Concept
1. Attacker's own GitHub org `attacker-org/attacker-repo` is registered in this Shipit instance (legitimate tenant).
2. Attacker pushes a commit to a fork/mirror of the victim's repo (or otherwise learns/controls a SHA that also exists as an undeployed `Commit` row under `victim-org/victim-repo`'s stack).
3. Attacker triggers (or crafts, using their own valid `webhook_secret`) a `status` event: `{"sha": "<victim_commit_sha>", "state": "success", "context": "ci/attacker", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/attacker-repo"}}`.
4. `WebhooksController#verify_signature` verifies successfully using `attacker-org`'s webhook secret.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the victim's commit row (from a totally different stack/org), and calls `create_status_from_github!`, adding a forged `success` status to it.
6. If this satisfies the victim stack's `ci.require`, the victim commit becomes `deployable?` and can be deployed/merged via continuous delivery without ever having passed the victim's actual CI.
