Webhook signature verification uses the org derived from `repository.owner.login`, but downstream handlers act on the (unauthenticated) `repository.full_name` — organization that authenticated ≠ repository that is written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to verify the incoming GitHub webhook by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* JSON body, before the signature has been checked. Once verification "passes," the controller hands the **entire, still-unauthenticated** `params` hash to the registered event handlers, which locate the target `Stack`/`Repository` using a *different* field of the same body — `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name`). Nothing ties the field used to select the verification secret to the field used to select the repository that gets acted upon. This mirrors the Curve report's root cause: two related values that should be the same authenticated quantity are instead independently attacker-controlled, and only one of them is checked.

### Finding Description
- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` from the raw, unverified JSON body and uses it to select which GitHub App/org config (and therefore which `webhook_secret`) to verify the signature against: [1](#0-0) 
- `repository_owner` itself: [2](#0-1) 
- After verification "succeeds" (i.e., the signature matches *some* configured org's secret), the whole body is dispatched to handlers unmodified: [3](#0-2) 
- Handlers resolve the affected repository/stack using `repository.full_name`, a completely separate field of the same payload, with no cross-check against `repository.owner.login`: [4](#0-3) 
- `PushHandler`, for example, uses that repository/stack lookup and then calls `stack.sync_github(expected_head_sha: params.after)`, which enqueues `GithubSyncJob` for the resolved stack: [5](#0-4) [6](#0-5) 

Shipit explicitly supports multi-organization configurations where each org has its own independent `webhook_secret`, documented in `docs/setup.md` and exercised by `Shipit.github(organization:)`: [7](#0-6) 

Binding that should hold: `organization that authenticated the signature == organization that owns the repository being written to`. Before the fix path, this is enforced only implicitly (both derived from the same JSON field), but the controller lets an attacker supply *inconsistent* values for "the org used to pick the secret" (`repository.owner.login`) and "the repo used to decide what gets written" (`repository.full_name`), because the two are read independently and never cross-validated against each other or against the resolved `Repository`'s actual owner.

### Impact Explanation
An attacker who legitimately administers their **own** GitHub organization/App that is one of the multiple organizations configured in this Shipit instance (a normal, unprivileged multi-tenant scenario per `docs/setup.md`'s "Using Multiple GitHub Applications" section) knows their own org's `webhook_secret`. They can craft a POST to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) = their own org, so `verify_signature` selects their own known secret and the HMAC check passes.
- `repository.full_name` = `"victim-org/victim-repo"`, an entirely different organization's repository that also has a `Stack` configured on the same shared Shipit instance.

Because handlers only look up the target via `repository.full_name` (`Handler#repository_name`), the victim's stack is resolved and acted on, even though the signature was verified against the attacker's own org's secret rather than the victim's. For the `push` event this triggers `Stack#sync_github`, enqueuing `GithubSyncJob` for the victim stack with an attacker-chosen `expected_head_sha`, which fetches commits via the victim stack's *own* GitHub API credentials (`stack.github_api`, scoped to the real owner) — so it cannot forge arbitrary commit content, but it can force synchronization/cache-spec recomputation and, depending on configuration (`continuous_deployment`), influence when deploys are triggered on a victim stack the attacker does not own. Other event types (`status`, `check_suite`, `membership`, `pull_request`) are similarly reachable using the same mismatch, letting the attacker inject spoofed CI-status/check-suite/team-membership events for a repository/organization they do not control, using only a webhook secret that belongs to their own unrelated org. This is a cross-repository/cross-organization write via a spoofed webhook: unauthenticated with respect to the victim's actual GitHub App, satisfying the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires only that the shared Shipit deployment is configured for multiple GitHub organizations (a documented, supported configuration) and that the attacker controls one of those organizations' GitHub Apps well enough to know its own `webhook_secret` — a routine capability for a legitimate but otherwise unprivileged tenant, requiring no Shipit session, API client token, or access to the victim's secrets. Crafting the payload only requires knowledge of the JSON shapes already documented in the fixtures (`push_master.json`, etc.) and does not require any race condition or timing.

### Recommendation
After signature verification, re-derive the organization from the *same* trusted source used for verification and require that every downstream lookup (`repository.full_name`, `organization.login` used by handlers) be scoped to/validated against that verified organization before any `Stack`/`Repository` lookup occurs. Concretely: after `verify_signature` succeeds, pass the already-resolved `repository_owner` (and the specific `GitHubApp`/org it matched) into `Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization) }`, and have `Handler#repository_name`/`#stacks` reject (or scope its `Repository.from_github_repo_name` lookup) if the repository's actual owner does not match `verified_organization`.

### Proof of Concept
Assume a multi-org Shipit config:
```yml
production:
  github:
    attacker-org:
      webhook_secret: "known_to_attacker_secret"
      ...
    victim-org:
      webhook_secret: "victim_secret_unknown_to_attacker"
      ...
```
1. Attacker computes `signature = "sha1=" + HMAC-SHA1(known_to_attacker_secret, raw_body)` for a `push` payload where:
```json
{
  "ref": "refs/heads/master",
  "after": "attacker_chosen_sha",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
2. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: <signature>`.
3. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, calls `Shipit.github(organization: "attacker-org").verify_webhook_signature(signature, raw_body)`, which succeeds because the attacker signed with their own known secret — see: [1](#0-0) 
4. `PushHandler.call(params)` runs; `Handler#repository_name` reads `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, resolves the victim's `Stack`, and calls `stack.sync_github(expected_head_sha: "attacker_chosen_sha")`, enqueuing `GithubSyncJob` against the victim stack despite the request never having been signed by `victim-org`'s webhook secret: [4](#0-3) [8](#0-7)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
