### Title
CCMenu API token created for one stack authorizes CCMenu status reads on every stack in the instance - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The `CCMenuUrlController#fetch` action mints a `read:stack` `ApiClient` token intended to expose a single stack's build status to unauthenticated CI-monitoring tools, but the token is created with no `stack:` association, and the consuming controller (`CCMenuController`) never checks the token's `stack_id` against the requested `stack_id` param. As a result, a token generated (and possibly leaked) for stack A can be replayed against any other stack B to read its deploy/build/lock status.

### Finding Description
`CCMenuUrlController#client` creates the token like this: [1](#0-0) 

Note that `stack:` is never passed to `create_with`/`find_or_create_by!`, so the resulting `ApiClient` record has `stack_id == nil`. `ApiClient#stack_id?` therefore evaluates to false for this client.

The generated URL embeds only the raw signed token as a query parameter: [2](#0-1) 

On the consuming side, `CCMenuController` authenticates purely by verifying the token's signature and looks up the target stack directly from `params[:stack_id]`, with no cross-check against the client's `stack_id`: [3](#0-2) 

Contrast this with the generic `BaseController#stacks`/`#stack` helpers used by other API controllers, which do enforce that scoped clients only see their own stack: [4](#0-3) 

`CCMenuController` overrides `stack` itself instead of using `BaseController#stack`/`#stacks`, so this scoping is bypassed entirely. Combined with the fact that the token is never bound to a stack in the first place, the equality that should hold — "the stack the token authorizes" == "the stack the token is used against" — is broken on both sides: the token isn't scoped when minted, and the controller doesn't enforce scoping when used.

`ApiClient.authenticate` only verifies the cryptographic signature over the client id, and `check_permissions!` only checks the coarse-grained `read:stack` permission string, not any per-stack binding: [5](#0-4) 

### Impact Explanation
CCMenu tokens are explicitly designed to work without a Shipit session — they are meant to be embedded in unauthenticated polling URLs consumed by build-monitor tools (CCTray/CCMenu clients), and are commonly pasted into third-party dashboards, shared team channels, browser bookmarks, etc. Any holder of one such token — regardless of which stack it was generated for — gains unauthenticated read access to the CCMenu status (`stack.deploys_and_rollbacks`, lock state, latest deploy status via `NoDeploy`/deploy serialization) of every stack that exists in the Shipit instance, including stacks the original user had no access to mint tokens for. This matches the "High - unauthenticated read of stack state" impact class: an artifact intended to disclose state for a single authorized stack instead discloses state for the entire fleet of stacks.

### Likelihood Explanation
Any authenticated Shipit user can trivially obtain a valid CCMenu token for a stack they have `read:stack` access to via `CCMenuUrlController#fetch`, and CCMenu URLs are designed to be shared/embedded outside of the authenticated session by nature of the feature. Once obtained, exploitation requires nothing more than changing the `stack_id` path/query parameter on the token's request — no additional secrets, signatures, or privileged access are needed. This is a straightforward, always-reachable API misuse rather than a race condition or edge case.

### Recommendation
- Bind the `ApiClient` created in `CCMenuUrlController#client` to the specific stack (`ApiClient.create_with(permissions: %w[read:stack], stack:)`), matching the pattern already used elsewhere in the codebase.
- In `CCMenuController`, reuse (or replicate) `BaseController#stacks`/`#stack` scoping logic so that a stack-scoped `ApiClient` can only be used against the stack it was minted for, rejecting requests where `current_api_client.stack_id` is present and differs from the requested `stack_id`.

### Proof of Concept
1. As User A (with `read:stack` on Stack A only), call `GET /stacks/A/ccmenu_url` (routes to `CCMenuUrlController#fetch`). Response includes `ccmenu_url` containing a `token` query parameter — the token is minted with `stack: nil`.
2. Take that token and issue `GET /api/stacks/B/ccmenu.xml?token=<token>` for an arbitrary Stack B that User A was never granted access to.
3. `CCMenuController#authenticate_api_client` succeeds because the token's signature is valid (`ApiClient.authenticate`), and `require_permission :read, :stack` succeeds because the client has the generic `read:stack` permission string.
4. `stack` resolves via `Stack.from_param!(params[:stack_id])` to Stack B, and `show` renders Stack B's latest deploy/rollback and lock status — despite the token never having been scoped to, or authorized for, Stack B.

    class << self
      def authenticate(token)
        find_by(id: message_verifier.verify(token).to_i)
      rescue Shipit::SimpleMessageVerifier::InvalidSignature
      end

      def message_verifier
        @message_verifier ||= Shipit::SimpleMessageVerifier.new(Shipit.api_clients_secret)
      end
    end

    def authentication_token
      self.class.message_verifier.generate(id)
    end

    def check_permissions!(operation, scope)
      required_permission = "#{operation}:#{scope}"
      unless permissions.include?(required_permission)
        raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
      end

      true
    end
