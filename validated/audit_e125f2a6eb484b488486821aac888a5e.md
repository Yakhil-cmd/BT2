### Title
Unauthenticated webhook signature verification bypass when `webhook_secret` is unset allows forged CI status → unauthorized deploy - ([File: lib/shipit/github_app.rb])

### Summary
`GithubApp#verify_webhook_signature` returns `true` unconditionally whenever no `webhook_secret` is configured for an organization, and this check is the sole authentication gate on the public `/webhooks` endpoint. Because Shipit's own setup documentation lists the webhook secret as *optional*, a documented, supported deployment leaves `POST /webhooks` open to unauthenticated payload injection, including forged `status` events that flip a commit's CI state to `success`, which is exactly the input `Commit#deployable?` trusts when deciding whether a ref may be shipped.

### Finding Description
`WebhooksController#verify_signature` gates all webhook processing on `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`: [1](#0-0) 

That method is implemented as: [2](#0-1) 

`return true unless webhook_secret` means that for any organization configured without a `webhook_secret` — a configuration explicitly called out as optional in the setup docs (`Webhook secret (optional): ...`) — **every** payload is treated as verified regardless of the `X-Hub-Signature` header content (missing, malformed, or attacker-supplied).

The controller then dispatches the raw, unverified JSON body directly to registered handlers: [3](#0-2) 

The `status` handler writes a `Status` record straight from the payload, keyed only by `sha` — with no cross-check against the real GitHub API: [4](#0-3) 

That injected status is exactly what `Commit#deployable?` consults to gate deploys: [5](#0-4) 

This breaks the trust binding: **the ref's approved CI status (verified GitHub signature) ≠ the ref whose `shipit.yml` steps are actually authorized to execute** (`deployable?` used by `trigger_deploy`/`build_deploy` and continuous delivery). An attacker who can reach `/webhooks` (a pre-auth, publicly routed endpoint per `config/routes.rb`) and who knows/guesses a tracked repository's `sha` can inject a fabricated `success` status for that commit, and also inject fabricated `push` events to move the tracked branch/commit set, membership events to manipulate `Shipit.github_teams` membership, etc. — all without ever authenticating to Shipit.

### Impact Explanation
This satisfies the Critical bar of "an unauthorized deploy": forging a `success` status flips `Commit#deployable?` to true for an arbitrary tracked sha, which combined with `continuous_deployment?`/`trigger_continuous_delivery` or a caller triggering `stack.trigger_deploy` can cause Shipit to run the `deploy` steps of `shipit.yml` for a commit whose CI never actually passed (or that never existed as a legitimate CI-approved ref). The same primitive (forged `membership` webhook) can also add an attacker-controlled GitHub login to a `Shipit.github_teams`-mapped `Team`, which is the authorization boundary checked by `Authentication#force_github_authentication`, escalating into application access.

### Likelihood Explanation
Requires only network access to the `/webhooks` route and a target Shipit instance operated with an organization whose `webhook_secret` is left blank — a state the project's own setup guide presents as a supported, optional configuration rather than a misuse of the engine. No GitHub credentials, Shipit session, or API token are needed, matching the "unprivileged attacker" threat model.

### Recommendation
Make `webhook_secret` mandatory for all configured GitHub organizations (fail closed, not `return true unless webhook_secret`), and reject webhook requests outright when no secret is configured rather than treating an absent secret as "verified." Update `docs/setup.md` to remove "(optional)" and add a startup-time check that raises if any configured organization lacks a `webhook_secret`. Additionally, consider having `StatusHandler`/`PushHandler` corroborate injected state against the GitHub API for security-sensitive fields (commit status) rather than trusting the webhook body verbatim.

### Proof of Concept
1. Deploy Shipit with an organization entry in `secrets.yml` that omits `webhook_secret` (a configuration the setup docs mark optional).
2. As an unauthenticated attacker, send:
   ```
   POST /webhooks
   X-Github-Event: status
   Content-Type: application/json

   {"sha":"<tracked-commit-sha>","state":"success","context":"ci/attacker","repository":{"owner":{"login":"<org>"}}}
   ```
   `verify_signature` calls `verify_webhook_signature(nil_or_bogus_signature, body)`, which returns `true` because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
3. `Handlers::StatusHandler#process` creates a `Status` record with `state: 'success'` for that commit (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), matching the observable behavior in `test/controllers/webhooks_controller_test.rb:42-59`.
4. `Commit#deployable?` now returns `true` for that sha regardless of real CI outcome (`app/models/shipit/commit.rb:227-229`), enabling `stack.trigger_deploy`/continuous delivery to run the stack's `deploy` steps against it.

*(Note: I was unable to fully trace whether every deployed instance in practice always sets `webhook_secret`, since that is an operator-side configuration choice outside the indexed code; the vulnerability is contingent on that documented-optional field being left unset.)*

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
