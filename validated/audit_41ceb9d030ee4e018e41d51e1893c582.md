## Title
Stack-scoped API token authorization bypass in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via its `stack_id` column, and `Api::BaseController` enforces that scope by resolving the target stack through `stacks.from_param!(params[:stack_id])`, where `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` whenever the client is stack-scoped. `Api::CCMenuController` overrides `#stack` to instead call `Stack.from_param!(params[:stack_id])` directly, dropping this scoping filter entirely.

### Finding Description
The intended invariant, enforced in `Api::BaseController`, is:

`stack acted upon == stack the presented token is authorized for` (when `current_api_client.stack_id?`) [1](#0-0) 

`Api::CCMenuController` breaks this equality by redefining `stack`: [2](#0-1) 

`CCMenuController` only declares `require_permission :read, :stack`, which merely checks that the client's `permissions` array includes `"read:stack"` — it never re-validates that the requested `stack_id` matches the client's `stack_id`: [3](#0-2) 

So any client holding `read:stack` permission — including one an operator deliberately scoped to a single stack via `stack_id` — can pass an arbitrary `stack_id` in the URL and have `show` render CI/CD status information for a stack it was never authorized to see: [4](#0-3) 

The scoping mechanism itself is a real, tested feature of the engine (not dead code): the test suite explicitly asserts that a stack-scoped client is restricted to its own stack in other controllers. [5](#0-4) 

### Impact Explanation
An attacker in possession of a stack-scoped API token (e.g. one intentionally handed to a third party or CI system to only view a specific stack) can use that token against `GET /api/stacks/:stack_id/ccmenu` with a different `stack_id` and read lock status, last deploy status, and other stack metadata for any stack in the installation — an unauthorized read of stack state that the token's issuer explicitly did not grant. This matches the "High" bucket: unauthenticated (out-of-scope) read of stack state via a token whose authorization boundary is not the boundary the code enforces.

### Likelihood Explanation
Exploitation only requires possessing any valid stack-scoped `read:stack` API token and knowledge/guessing of another stack's `owner/repo/environment` identifier (which is often predictable or discoverable), and a single HTTP GET request — no privileged account or session is needed beyond the token itself.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it to route through `stacks.from_param!`, matching `Api::BaseController`) so stack-scoped tokens cannot be used to view stacks outside their granted `stack_id`.

### Proof of Concept
1. An administrator creates (e.g. via Rails console or an internal tool) an `ApiClient` with `permissions: ["read:stack"]` and `stack_id` set to Stack A's id, intending it to only ever see Stack A.
2. Using that client's `authentication_token` as Basic Auth credentials, the attacker sends:
   `GET /api/stacks/<owner>/<repo-b>/<env-b>/ccmenu`
   for Stack B (any other stack in the installation), instead of Stack A.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!`, the request succeeds and returns Stack B's CI/CD status XML, even though the token was only authorized for Stack A.
