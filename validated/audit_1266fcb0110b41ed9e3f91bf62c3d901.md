### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` repositories - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` combines `review_stacks_enabled` with `provisioning_behavior` using `&&`/`||` in a way that Ruby parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. Because `review_stacks_enabled` is only ANDed into the first disjunct, a repository with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (or `prevent_with_label`) will still have `provision?` return `true` whenever the label condition is met, causing an unauthorized `ReviewStack` to be created and queued for provisioning.

### Finding Description
The intended binding is: review stack auto-provisioning should only occur when `repository.review_stacks_enabled == true`, regardless of `provisioning_behavior`. The actual code at [1](#0-0)  is:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Since `&&` binds tighter than `||` in Ruby, this evaluates as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. `review_stacks_enabled` is not distributed across the other two clauses. Consequently, for a repository with `review_stacks_enabled: false`, `provisioning_behavior: allow_with_label`, the second clause alone (`allow_with_label? && has_label`) is sufficient to make `provision?` return `true`, and similarly for `prevent_with_label?` when the label is absent.

`respond_to_pull_request_opened?` calls `provision?` directly [2](#0-1) , and `process` unconditionally proceeds to `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` if it returns true [3](#0-2) . `ReviewStackAdapter#create!` then builds the stack with `branch: params.pull_request.head.ref` from the attacker-controlled PR payload and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [4](#0-3) .

The attacker action: open a PR (or push to their own fork) against a real, tracked repository whose owner has explicitly set `review_stacks_enabled: false` but left `provisioning_behavior: allow_with_label` configured, and attach the (often default/guessable) `provisioning_label_name` label. No forged webhook signature, session, or token is required beyond normal GitHub webhook delivery for a real PR event on that repo — this is a logic bug in the engine, not a signature-bypass, so `verify_signature`/`GitHubApp#verify_webhook_signature` are irrelevant to and do not prevent this bug. None of `ExplicitParameters` schema validation, `force_github_authentication`, `Repository` format validators, or the `Stack`/environment validators check or enforce the `review_stacks_enabled` gate — that check only happens (incorrectly) inside `provision?`.

Verification: the existing test suite at [5](#0-4)  tests `allow_with_label` and `prevent_with_label` behaviors using `configure_provisioning_behavior` with its default `provisioning_enabled: true` [6](#0-5) , so the combination of `review_stacks_enabled: false` with `allow_with_label`/`prevent_with_label` is never exercised by tests — confirming the gap is unguarded.

### Impact Explanation
An unprivileged attacker able to open a pull request (or label their own PR) on any repository tracked by this Shipit instance can force creation of a `ReviewStack` and enqueue it for provisioning, even though the repository owner explicitly disabled review-stack auto-provisioning (`review_stacks_enabled: false`). The provisioned stack's `branch` is taken directly from the attacker's PR head ref, meaning attacker-controlled code/branch becomes subject to deployment/provisioning workflows that the repository owner opted out of. This matches "unauthorized deploy/provisioning" under the Critical impact category — a record (ReviewStack + provisioning queue enqueue) is written and workflow is triggered for a repository that did not authorize this path via its configured `review_stacks_enabled` flag. It is repeatable against any repository configured with `provisioning_behavior != allow_all` while `review_stacks_enabled: false` (a plausible, non-default-but-intentional combination for owners who want to fully disable review stacks while leaving behavior settings unchanged).

### Likelihood Explanation
Preconditions: the target repository must be registered in Shipit (`Repository.from_github_repo_name` must resolve), have `review_stacks_enabled: false`, and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`. For `allow_with_label`, the attacker additionally needs to know/guess `provisioning_label_name` and apply it to their own PR (trivial if they can label PRs on the repo, or if the label name is a common default). For `prevent_with_label`, no label at all is required — simply opening a PR without the label triggers it, making this variant especially low-cost. Attacker cost is minimal: opening a pull request against a public repository is normal, unprivileged GitHub activity. This is fully reproducible with a minitest test and does not require any secrets.

### Recommendation
Fix operator precedence so `review_stacks_enabled` gates all three provisioning behaviors, e.g.:

```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
minitest test to add under `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (location noted for reference; per rules test files are out of scope for modification but this is the proof plan):

```ruby
test "does not create stacks when review_stacks_enabled is false even with allow_with_label + matching label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,      # review_stacks_enabled == false
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```

Assert both sides of the binding: `repository.review_stacks_enabled == false` (set explicitly) versus the actual observed behavior `Shipit::ReviewStack.exists?(environment: "pr#{payload_parsed(:pull_request_opened)['number']}")` — with the current buggy code this test fails (a stack is created), demonstrating the divergence; after applying the recommended fix, the test passes (no stack created).
