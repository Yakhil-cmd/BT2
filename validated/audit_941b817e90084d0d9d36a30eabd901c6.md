### Title
Unfiltered PR label names become deploy-time environment variables, allowing `GIT_SSH_COMMAND` injection into task execution - (File: app/models/shipit/review_stack.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull request label name, uppercased, directly into the stack's environment hash with no allowlist. `TaskCommands#env` merges this attacker-influenced `@stack.env` into the environment used for `install_dependencies`/`perform` steps, which is passed unfiltered through `Command#start` to `PTY.spawn`, so a label literally named `GIT_SSH_COMMAND` becomes a real environment variable for every shell command a repo's `shipit.yml` runs during that task.

### Finding Description
The broken binding: the set of environment variable keys reaching `PTY.spawn` for a review-stack task should equal `Shipit.env ∪ {GITHUB_DOMAIN, GITHUB_TOKEN, GIT_ASKPASS} ∪ stack-derived fixed keys ∪ deploy_spec.machine_env ∪ filtered(task/deploy env)`. In practice it also equals `∪ pull_request.labels.map(&:upcase)` with no name restriction, because:

- `ReviewStack#env` unconditionally does `super.merge(pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" })` [1](#0-0) .
- `TaskCommands#env` merges `@stack.env` (this method, for a `ReviewStack`) directly into the environment used to build every `Command` for `install_dependencies` and `perform` (deploy) steps, then merges `deploy_spec.machine_env` and `@task.env` on top [2](#0-1) .
- Unlike the explicit user-supplied deploy/task env (which goes through `EnvironmentVariables#permit` via `filter_deploy_envs`/`filter_rollback_envs`/`filter_task_envs`, see `Stack#build_deploy` and `Stack#trigger_task`), `@stack.env`/label-derived keys are never passed through any allowlist [3](#0-2) [4](#0-3) .
- The final merged env is handed to `Command.new(..., env:, ...)`; `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` where `unbundled_env` is `BASE_ENV.merge(...).merge(@env.stringify_keys)` — i.e. any attacker-supplied key, including `GIT_SSH_COMMAND`, is passed straight to the spawned child process [5](#0-4) .

Exploit flow: an attacker opens a PR against a repo and gets (or has) a label literally named `git_ssh_command` applied to it; `ReviewStack#env` uppercases it to `GIT_SSH_COMMAND` and injects `"true"` as its value; every subsequent `install_dependencies`/deploy step Command for that review stack's task inherits `GIT_SSH_COMMAND=true` (or any value the label encodes) in its process environment. If any step in the fork/PR's `shipit.yml` (deploy/dependency steps) invokes `git` with a remote operation (fetch/clone/pull, common in build scripts), git will use `GIT_SSH_COMMAND` as the program to execute in place of `ssh`, giving the attacker arbitrary command execution on the deploy host. Existing guards (`EnvironmentVariables#permit`, `filter_deploy_envs`, `filter_task_envs`) do not apply to this path because they only filter the values coming from `env:` request/trigger params, not the label-derived `@stack.env`.

Note: `TaskCommands#clone`/`#checkout` themselves use `Commands#base_env` (via the `git` helper), not the full `TaskCommands#env`, so the direct fetch/clone step is not directly affected; the exploitable surface is any git invocation performed from within `install_dependencies`/`deploy` steps (arbitrary shell commands defined in the repo's `shipit.yml`), which do receive the full unfiltered `TaskCommands#env`.

### Impact Explanation
If exploited, arbitrary environment variables set via a PR label reach every subprocess spawned for that review stack's dependency/deploy steps, including `GIT_SSH_COMMAND`, `LD_PRELOAD`-style or other environment-driven attack vectors that a step's toolchain may honor. Where a deploy/dependency step shells out to `git` for network operations, this becomes Remote Code Execution on the Shipit deploy host under the identity running the Shipit task, matching the Critical RCE class via `Command`/`PTY.spawn`. It is repeatable for every PR/task run on the affected review stack and scoped to the stack/repository that has review-stack provisioning enabled.

### Likelihood Explanation
Preconditions: the repository must be configured for review stacks (`ReviewStack`), and its `shipit.yml` dependency/deploy steps must perform a git network operation (a common pattern) or otherwise consume attacker-influenced environment variables. The attacker needs the ability to have a label applied to their PR and to control (or influence via the PR fork's `shipit.yml`) the deploy/dependency steps executed. This is low-cost and repeatable — no secrets or elevated Shipit/GitHub privileges are required beyond what's already assumed unprivileged in this audit's threat model.

### Recommendation
Do not merge raw pull-request label names into the process environment for tasks. Either drop `ReviewStack#env`'s label-merging behavior entirely, or restrict it to a fixed, explicitly allowlisted set of variable names (e.g., prefix-gated like `LABEL_<name>` and passed through `EnvironmentVariables#permit` against a whitelist), and explicitly strip/block dangerous names such as `GIT_SSH_COMMAND`, `GIT_SSH`, `LD_PRELOAD`, `BUNDLE_*`, `PATH`, etc., before merging into `TaskCommands#env`.

### Proof of Concept
minitest plan (`test/` under this engine, no live GitHub calls):
1. Build a `Shipit::ReviewStack` with an associated `pull_request` stub whose `labels` returns `["git_ssh_command"]`.
2. Assert `review_stack.env["GIT_SSH_COMMAND"] == "true"` (binding: label name uppercased equals injected env key).
3. Build a `Shipit::TaskCommands` (or `DeployCommands`) for a task on that stack with a `deploy_spec` whose `machine_env` does not define `GIT_SSH_COMMAND`.
4. Assert `task_commands.env["GIT_SSH_COMMAND"] == "true"` (binding: label-derived key survives into the full task environment unfiltered).
5. Build a `Command.new("git --version", env: task_commands.env, chdir: tmp_dir).start` and assert (via a stub/fake `PTY.spawn` or `Command#unbundled_env`) that `command.unbundled_env["GIT_SSH_COMMAND"] == "true"`, proving the value reaches the spawned process's environment with no allowlist rejection (contrast with `EnvironmentVariables.with(env).permit(deploy_variables)` raising `NotPermitted` for the same key when going through the deploy env path).

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
