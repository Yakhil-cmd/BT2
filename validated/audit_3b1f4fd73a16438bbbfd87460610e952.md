### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler resolves the target `Stack` from the unrelated `repository.full_name` field, letting one org's webhook secret authorize writes against another org's tracked repositories - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). [1](#0-0) [2](#0-1)  Every webhook handler, however, resolves the `Repository`/`Stack` that will actually be acted upon from a *different* JSON field, `repository.full_name`, via `Handler#repository_name` / `Handler#stacks`. [3](#0-2)  Nothing ties `repository.owner.login` to `repository.full_name` — both are attacker-controlled JSON fields inside the same signed body, and the signature only proves "this body was signed with Org X's secret," not "this body may only reference Org X's repositories."

### Finding Description
Shipit explicitly supports configuring multiple GitHub Apps/organizations, each with its own `webhook_secret` set by that organization's own admin during app installation. [4](#0-3) [5](#0-4)  In `verify_webhook_signature`, the HMAC is computed with whichever organization's secret was looked up: `Shipit.github(organization: repository_owner)` where `repository_owner` came straight from the untrusted JSON body. [6](#0-5)  An organization admin who legitimately possesses their own org's `webhook_secret` (Org A) can therefore craft an arbitrary POST to `/webhooks` where:
- `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) so `verify_signature` looks up and matches Org A's secret, and
- `repository.full_name = "OrgB/some-repo"`, an entirely different, unrelated tracked repository.

Because the handler base class's `stacks`/`repository_name` helpers only ever look at `repository.full_name`, [3](#0-2)  every handler that resolves a target via `Repository.from_github_repo_name` — e.g. `PushHandler#process`, `OpenedHandler#repository`, `ClosedHandler#repository`, `LabelCapturingHandler#repository`, `UnlabeledHandler#repository`, `ReopenedHandler#repository` — will act on Org B's stack even though the request was only authenticated against Org A's secret. [7](#0-6) [8](#0-7) [9](#0-8) 

This breaks the binding: **organization that authenticated (Org A) == organization whose repository is written (Org B)**.

### Impact Explanation
Exploiting this lets Org A forge push/pull_request events that trigger real side effects against Org B's stacks that Org A has no authorization over in this Shipit instance:
- `PushHandler` enqueues `stack.sync_github(...)` for Org B's stacks matching the forged `ref`/`branch`, forcing an unsolicited re-sync using the app's real GitHub credentials for Org B. [10](#0-9) 
- `ReopenedHandler`/`ClosedHandler` can unarchive or archive Org B's review stacks. [11](#0-10) 
- `LabelCapturingHandler` can rewrite label state on Org B's pull requests. [12](#0-11) 

I was not able to fully confirm within this session whether a forced `GithubSyncJob` can, by itself, trigger an *unauthorized deploy* of Org B's code: `GithubSyncJob#perform` re-fetches real commits from GitHub via `stack.github_commits` using the app's own credentials rather than trusting attacker-supplied commit data, [13](#0-12)  and I did not finish tracing whether newly-synced commits automatically trigger continuous-deployment deploys (`continuous_delivery_schedule` / `ContinuousDeliveryJob`) on `Stack`. [14](#0-13)  If continuous deployment is enabled on the victim stack, forcing a premature/unsolicited resync could cause an unintended deploy to occur earlier or against state the victim organization did not intend, which would place this at the "unauthorized deploy" bar; absent that confirmation, the concretely provable impact is limited to cross-organization triggering of syncs, and archive/unarchive/label mutations on review stacks belonging to a repository the calling organization does not administer.

### Likelihood Explanation
This requires the attacker to be an org admin who has been granted their own GitHub App/webhook_secret in a multi-organization Shipit deployment (a documented, supported configuration) — not a fully anonymous internet attacker, but also not a privileged Shipit user, API-client token holder, or GitHub App private-key holder. Within the intended trust model, such an org is expected to only be able to affect its own repositories; this bug lets it affect any repository tracked by the same Shipit instance, which is a meaningful privilege escalation across the organizational boundary that Shipit's multi-org webhook_secret design is meant to enforce.

### Recommendation
After signature verification succeeds, validate that `repository.full_name`'s owner segment matches the `repository_owner` (or `organization.login`) that was used to select the verifying secret, and reject the webhook (422) if they differ. Alternatively, pass the verified `repository_owner` into each `Handler` and require handlers to scope `Repository.from_github_repo_name` lookups to that verified owner instead of trusting the unauthenticated-relative `full_name` field alone.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret`, per the documented multi-org schema. [5](#0-4) 
2. As the admin of `OrgA` (who legitimately knows `OrgA`'s `webhook_secret`), construct a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<any sha>",
  "repository": {
    "owner": {"login": "OrgA"},
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature` as `sha1=` HMAC-SHA1 of the raw body using `OrgA`'s `webhook_secret`, and set `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `OrgA`'s secret. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` [3](#0-2)  and enqueues `sync_github` for `OrgB`'s stack, even though the request was only ever authenticated as `OrgA`. [10](#0-9)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
