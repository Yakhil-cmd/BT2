### Title
`Api::CCMenuController` ignores the API-client's stack scope, letting a stack-scoped token read any stack's build status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`ApiClient` records can be bound to a single stack via `stack_id` (e.g. the `here_come_the_walrus` fixture), and every other `Api::BaseController` action correctly enforces that scope through the `stacks`/`stack` helpers. `Api::CCMenuController`, however, redefines `stack` to bypass that scoping, so a client token that is only authorized for one stack can be used to read the CC-menu status (build status, label, last build time) of any stack on the install by simply changing `stack_id` in the URL.

### Finding Description
`Api::BaseController` implements token-based stack authorization as an equality: `client.stack_id == requested_stack.id` (or `Stack.all` when the client is unscoped): [1](#0-0) 

This is what the test suite explicitly documents as the security guarantee ("an api client scoped to a stack will only see that one stack"): [2](#0-1) 

`Api::CCMenuController` inherits from `BaseController` and requires only the generic `read:stack` permission (not stack-specific), then overrides the private `stack` method to resolve the stack directly from the global `Stack` collection instead of the client-scoped `stacks` collection: [3](#0-2) 

Because `stack` is redefined to call `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(params[:stack_id])`, the `client.stack_id == requested_stack.id` binding that every other API endpoint enforces (via `stacks`) is never checked in this controller. The `show` action then renders the target stack's latest deploy/rollback status straight from that unscoped lookup: [4](#0-3) 

The route confirms `stack_id` is a free-form, attacker-controlled path segment: `get '/ccmenu' => 'ccmenu#show', as: :ccmenu` under `scope '/stacks/*stack_id'`. [5](#0-4) 

This is the direct structural analog of the reported bug class: a binding that is supposed to be enforced (in the original report, "auction/liquidator state before acting"; here, "the stack a token authorizes" ) is checked everywhere except one code path that re-implements the lookup and drops the check, letting an authenticated-but-limited-scope actor touch a resource outside the scope they were granted.

### Impact Explanation
An `ApiClient` token scoped to a single stack (`stack_id` set, permission `read:stack` only) is meant to only ever see that one stack's state. Via this endpoint that same token can enumerate/read `lastBuildStatus`, `lastBuildLabel`, and `lastBuildTime` for every other stack on the Shipit instance, including private/internal repositories/environments the token holder has no authorization for. This is an authorization-scope escalation / unauthenticated (out-of-scope) read of stack deploy state, matching the High-severity bucket "escalation into ... authorization" / "unauthenticated read of stack state ... deploy output".

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped API token (a normal, low-privilege credential type explicitly supported by the schema and tested in the suite) can exploit this with a single unauthenticated-beyond-their-scope GET request, just by supplying a different `stack_id`. No special timing, race, or privileged access is required beyond possessing one valid scoped token — directly analogous to the "any adversary can call the endpoint" nature of the original report.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it using the scoped `stacks` collection, i.e. `stacks.from_param!(params[:stack_id])`) so the client's `stack_id` binding is enforced identically to every other `Api::BaseController`-derived action.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to stack A (`stack_id = A.id`, permissions `['read:stack']`) — this is a normal, supported configuration per `test/fixtures/shipit/api_clients.yml` (`here_come_the_walrus`).
2. Using that client's `authentication_token`, issue:
   `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu` for an unrelated stack B that the client is not scoped to.
3. `Api::CCMenuController#authenticate_api_client`/`require_permission :read, :stack` only checks the generic permission string, and `#stack` resolves `Stack.from_param!(params[:stack_id])` without checking `current_api_client.stack_id`, so the request returns HTTP 200 with stack B's CC-menu XML (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`) — bypassing the scoping enforced everywhere else (compare with `test/controllers/api/stacks_controller_test.rb:217-223`, which shows the same token type restricted to one stack in the sibling `StacksController`).

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
```
