### Title
Sustained high-utilization debt overflows the RAY value domain during accrual, permanently freezing a market's funds — (`common/src/rates/index.rs`)

### Summary
A single unprivileged address can push a listed market to near-total utilization (supply a large amount, borrow ~98% of it). Interest accrual then multiplies the scaled debt by the borrow index inside `calculate_supplier_rewards` via `Ray::mul` (`scaled_to_original`). This multiplication panics with `MathOverflow` once `borrowed * borrow_index` exceeds `i128::MAX` — which the codebase's own test shows happens **before** the `MAX_BORROW_INDEX_RAY` cap in `update_borrow_index` can clamp the index. Because every controller verb accrues the market first (`global_sync` → `accrue_chunk` → `accrue_step` → `calculate_supplier_rewards`), the panic bricks the market: no `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, or `borrow` can ever execute again. All supplied and collateral funds in that market are permanently frozen.

### Finding Description
The bug class from CVE-2024-21196 (low-privileged, network-reachable complete denial of service) maps directly onto the accrual path any user can trigger.

The overflow lives in `calculate_supplier_rewards`, which computes `old_total_debt = borrowed.mul(old_borrow_index)` and `new_total_debt = borrowed.mul(new_borrow_index)` — both raw `i128` RAY multiplications that panic on overflow (common/src/rates/index.rs:80-81).

The index cap check in `update_borrow_index` clamps `new_index` only **after** the same mul is used to compute accrued debt, so it never protects the value-domain ceiling (common/src/rates/index.rs:13-19).

The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the full chain end-to-end: after the index grows (~170x on the XLM curve at 98% utilization), `try_update_indexes_for` fails with `MATH_OVERFLOW`, the cap "did not engage before the value overflow," and both `try_withdraw_raw` and `try_repay` revert with `MATH_OVERFLOW` — "the market is frozen: exits and repayments accrue first and hit the same panic" (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361).

Reachable entrypoints for the attacker: `supply` and `borrow` on `Controller` (no privilege, caps permitting — and `calculate_scaled_cap` saturates open), plus permissionless `update_indexes` to accelerate the crash once enough time has passed.

### Impact Explanation
Permanent freezing of all user funds in the affected market. Every state-changing controller flow syncs indexes first (`global_sync` in contracts/pool/src/interest.rs:20-33 runs on every verb), so once `borrowed * index` overflows `i128`, repay, withdraw, liquidation, bad-debt cleanup, and recapitalize all panic before touching balances. Suppliers can never exit; borrowers can never repay; liquidators cannot reduce risk. This is exactly the "complete DOS" impact of the advisory, realized as irreversible fund lockup rather than a recoverable outage.

### Likelihood Explanation
Requires substantial capital (the harness uses ~10^27 wei-scale principal and a steep rate curve at ~98% utilization sustained over years of ledger time) — but no privilege, no timing race, and no cooperation. An attacker can also use `flash_position`/`multiply` to maximize debt share, and `update_indexes` is permissionless so the panic can be triggered deliberately the moment the bound is crossed. The failure is deterministic once the math bound is hit, and irreversible because no code path can reduce the index or the scaled debt without first accruing. Medium severity: high impact, high capital/time precondition.

### Recommendation
- Compute accrued interest in a saturating or widened domain inside `calculate_supplier_rewards` (e.g., `mul_div`-based interest delta instead of `borrowed.mul(index)` per side), or clamp `new_borrow_index` to `MAX_BORROW_INDEX_RAY` **before** any `borrowed * index` multiplication, so the cap always engages before the RAY value ceiling.
- Alternatively, enforce an index-growth headroom check at debt-mint time (`calculate_scaled_borrow` / `borrow`) that rejects borrows where `borrowed * MAX_BORROW_INDEX_RAY` cannot fit in `i128`, keeping every reachable book below the panic cliff.
- The fixed code should make `update_indexes` itself panic-proof so the market can always accrue to the cap and remain operable.

### Proof of Concept
```text
1. Governance has listed a high-decimals asset (18 decimals) on a hub/spoke
   with ordinary caps (or caps lifted / saturated via calculate_scaled_cap).
2. Attacker calls Controller::supply(account_id=0, assets=[(BIG18, ~1e9 * 1e18)])
   to seed the market, then supplies a collateral asset on another account.
3. Attacker calls Controller::borrow(borrows=[(BIG18, 0.98 * supplied)])
   driving utilization to ~98% — reachable by any funded address.
4. As ledger time advances, each accrual chunk in global_sync calls
   accrue_step → calculate_supplier_rewards:
       old_total_debt = borrowed.mul(old_borrow_index)   // grows unbounded
   When borrowed * index crosses i128::MAX, Ray::mul panics (MathOverflow)
   while borrow_index is still far below MAX_BORROW_INDEX_RAY.
5. Any subsequent call — withdraw(1 unit), repay(1 unit), liquidate,
   update_indexes — re-runs global_sync first and panics identically.
   The market's supplied funds, collateral, and debt are permanently frozen.
```
This mirrors `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`, which asserts `MATH_OVERFLOW` on `update_indexes`, `withdraw`, and `repay` while `borrow_index < MAX_BORROW_INDEX_RAY`.
