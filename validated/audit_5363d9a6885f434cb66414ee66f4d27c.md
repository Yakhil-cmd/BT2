## Analysis

The claimed binding: `deploy.variables` step env (spawned via `PTY.spawn`) should equal only `{keys ∈ deploy_variables.map(&:name)} ∪ {fixed Shipit keys}`. In practice `TaskCommands#env` merges `@stack.env` (which for a `ReviewStack` includes every PR label name uppercased with value `"true"`) directly and unconditionally, without going through `EnvironmentVariables#permit`/`filter_deploy_envs`.

Trace:
- `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" } ` into the stack env, with no key allowlist. [1](#0-0) 
- `LabelCapturingHandler#capture_labels` writes `params.pull_request.labels.map(&:name)` straight into `pull_request.labels`, driven by the raw `pull_request.labeled`/`opened`/etc. webhook payload for any repo/stack it can resolve. [2](#0-1) 
- `TaskCommands#env` builds the deploy/task env as `super.merge(@stack.env).merge({fixed keys...}).merge(deploy_spec.machine_env).merge(@task.env)` — note `@stack.env` is merged with no filtering. [3](#0-2) 
- The only allowlist mechanism in the codebase, `DeploySpec#filter_deploy_envs` / `EnvironmentVariables#permit`, is applied to `@task.env` — i.e., the user-supplied deploy-form variables — via `Deploy#env`/controller `env:` params, **not** to `stack.env`. [4](#0-3) [5](#0-4) 
- `Command#start` spawns the process with `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, where `unbundled_env` merges `@env.stringify_keys` (the fully-merged, unfiltered env) over `BASE_ENV`/`PATH`. There is no denylist of dangerous keys such as `LD_LIBRARY_PATH`, `LD_PRELOAD`, `DYLD_*`, etc. [6](#0-5) 

Existing tests already confirm labels reach the process env unfiltered: `DeployCommandsTest#env includes the stack's pull request labels` and `ReviewStackTest#env includes the stack's pull request labels` assert `env["WIP"] == "true"` etc. with no key restriction. [7](#0-6) [8](#0-7) 

`filter_deploy_envs` and the `EnvironmentVariables#permit` allowlist do **not** guard this path because they are wired to the deploy-form `env` params, not to `stack.env`/labels. `require_permission!`, `verify_signature`, and `ExplicitParameters` schemas on the webhook only gate whether a label is captured for a *known, non-archived* review stack of a repo with `review_stacks_enabled`; they do not sanitize the label's string content, and label names are free-form GitHub strings fully controlled by the PR author (fork/unprivileged user for their own PR).

## Preconditions and scope

This requires: `Repository#review_stacks_enabled` = true and `provisioning_behavior` set such that a stack exists/remains active for the attacker's own PR (e.g., `allow_with_label` or `allow_all`), which are host/repo owner configuration choices, not code guarantees. Given that, an attacker who can open a PR from their own fork and add a label named `ld_library_path` (case-insensitive, becomes `LD_LIBRARY_PATH` after `.upcase`) to their own PR controls this env var for their own review stack's deploy/task commands. This is a real gap in env sanitization for label-derived variables, but the blast radius is confined to **the attacker's own review stack's deploy processes** on the shared deploy host — it does not cross into other stacks/tenants directly since the label only affects `stack.env` for that stack's `pull_request`. The severity of this depends on whether commands spawned during `deploy.variables`/`deploy` steps dynamically link against attacker-supplied libraries on the shared host (potential local sandbox escape / host compromise, since the deploy host executes multiple stacks' commands), which is plausible given `Command#start` spawns real subprocesses with this merged environment.

### Title
Unsanitized PR label names injected into `stack.env` allow env-var poisoning (e.g. `LD_LIBRARY_PATH`) of deploy/task subprocess environment - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` uppercases every PR label name and merges it into the stack env with no key allowlist, and this merged env flows unfiltered through `TaskCommands#env`/`DeployCommands#env` into `Command#start`'s `PTY.spawn` call. Any GitHub user who can label their own fork PR (on a repo with review stacks enabled) can therefore set arbitrary env var names such as `LD_LIBRARY_PATH` for that review stack's deploy/task subprocesses on the shared Shipit host.

### Finding Description
Broken binding: the deploy/task subprocess env should equal `base_env ∪ {fixed keys} ∪ filter(deploy_variables, declared_names)`, but it actually equals `base_env ∪ {fixed keys} ∪ stack.env ∪ deploy_spec.machine_env ∪ task.env`, where `stack.env` for a `ReviewStack` includes `{label.upcase => "true" for label in pull_request.labels}` with no allowlist (`app/models/shipit/review_stack.rb:84-93`). Labels are populated straight from the webhook body via `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) for any `opened`/`labeled`/`unlabeled`/`reopened` event on a stack that is present and not archived. `TaskCommands#env` merges `@stack.env` unconditionally (`lib/shipit/task_commands.rb:33-48`), and this merged hash reaches `PTY.spawn(unbundled_env, ...)` in `Command#start` (`lib/shipit/command.rb:85-105`) with no denylist for sensitive dynamic-linker/interpreter variables. The only sanitization mechanism, `DeploySpec#filter_deploy_envs`/`EnvironmentVariables#permit` (`app/models/shipit/deploy_spec.rb:174-176`, `lib/shipit/environment_variables.rb:13-18`), is applied to the deploy-form `env:` param path (`Deploy` model / API controllers), not to `stack.env`. An attacker with a fork PR on a review-stack-enabled repo (`allow_with_label`/`allow_all`) adds the label `ld_library_path` to their own PR; when the review stack's deploy or task commands run, `LD_LIBRARY_PATH` is set from that label and inherited by every spawned binary in `deploy.pre`/`deploy.override`/`deploy.variables`-adjacent steps.

### Impact Explanation
For the attacker's own review stack, any command spawned by `Command#start` (dependencies, deploy steps, tasks) inherits attacker-chosen dynamic-linker environment variables. If any spawned binary in those steps performs dynamic linking and the attacker can place a malicious shared object reachable via a controllable path (e.g., checked-out fork content in `chdir`), this can escalate to code execution in the context of the deploy host process for that stack. This does not directly let the attacker mutate another repository's stack, but it does compromise the shared deploy host process running under the Shipit operator's privileges, matching a Critical "command running that should not" / RCE-on-deploy-host style impact once combined with a controllable library path.

### Likelihood Explanation
Requires `review_stacks_enabled` and `provisioning_behavior` of `allow_with_label` or `allow_all` on the target repo (repo/operator configuration, common for open PR-preview workflows). Given that, attacker cost is minimal: open a PR from a fork and add one label. Fully repeatable per review stack; each PR/stack the attacker controls can independently poison its own deploy env.

### Recommendation
Do not merge free-form PR label names as literal env var keys. Either (a) prefix label-derived keys (e.g., `LABEL_<name>`) so they can never collide with sensitive/reserved names, or (b) restrict label-derived env injection to an explicit allowlist (similar to `deploy_variables`), and additionally strip/deny known dangerous names (`LD_LIBRARY_PATH`, `LD_PRELOAD`, `DYLD_*`, `PATH`, etc.) from any user-influenced env source before merging in `TaskCommands#env`/`ReviewStack#env`.

### Proof of Concept
minitest plan (extends existing `DeployCommandsTest`):
```ruby
test "#env does not leak LD_LIBRARY_PATH from an attacker-controlled PR label" do
  stack = shipit_stacks(:review_stack)
  deploy = stack.trigger_continuous_delivery
  stack.pull_request.labels = ["ld_library_path"]

  env = Shipit::DeployCommands.new(deploy).env

  # Binding under test: LD_LIBRARY_PATH must not be attacker-controllable
  assert_nil env["LD_LIBRARY_PATH"], "fork PR label should not set LD_LIBRARY_PATH for spawned deploy commands"
end
```
This currently fails (asserting non-nil `"true"`), proving the label flows unfiltered into the env reaching `Command#start`/`PTY.spawn`.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    end
