### Title
Unallowlisted swap routes can smuggle unauthorized wallet-token transfers into the caller's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller swap strategies accept an attacker-influenced `StrategySwap` route and delegate it to the configured router while the caller's authorization remains active. Because route venue addresses are not constrained by the controller, a malicious venue can request `token.transfer(caller -> attacker, amount)` during the route. A simulation records that call as a child of the caller's strategy authorization; if the wallet signs the simulated tree, the venue can steal unrelated wallet tokens.

### Finding Description
`swap_tokens` accepts the caller-provided `swap` payload, authorizes only the controller's intended input transfer to the configured router, then invokes `router.execute_strategy` inside the flash guard. [1](#0-0)  The authorization helper narrowly specifies one token `transfer(controller -> router, amount)` for the controller itself, but it does not constrain what arbitrary downstream venue code may request from the externally owned caller. [2](#0-1) 

The route payload names the pool/token addresses used by each hop, and the protocol documentation explicitly notes that the router does not maintain a venue allowlist. [3](#0-2)  A regression test demonstrates that a pool contract selected by the route can invoke `wallet_token.transfer(victim -> attacker, amount)` during `swap_collateral`; simulation records that transfer as a child under the victim's `swap_collateral` authorization. [4](#0-3)  When that poisoned authorization tree is signed, the host accepts the nested transfer and moves the victim's wallet tokens. [5](#0-4) 

### Impact Explanation
An attacker can steal arbitrary token balances held directly by the caller, beyond the collateral or debt amount intentionally routed through the lending strategy. [6](#0-5)  Neither the controller's measured router spend, its positive-output check, nor the final account risk check bounds a transfer from the caller's wallet to the attacker. [7](#0-6)  The same authorization shape can affect any strategy that calls `swap_tokens`, including `multiply`, `swap_collateral`, `swap_debt`, and `repay_debt_with_collateral`. [8](#0-7) 

### Likelihood Explanation
A single unprivileged attacker can deploy a pool-shaped contract, encode a route through it, return enough output to satisfy the router/controller checks, and cause the victim's simulation to request the additional wallet transfer. [9](#0-8)  Exploitation still requires the victim or wallet UI to sign the poisoned authorization tree, so it is not fully unilateral; however, the malicious child is embedded in the same strategy authorization users are expected to sign, and the tested path proves the host enforces it. [10](#0-9)  This matches a Medium-severity authorization-boundary bypass rather than a governance-only or purely off-chain issue.

### Recommendation
Do not let user-supplied routes reach arbitrary pool contracts under a privileged caller authorization. Bind every executable hop to a governance-approved venue/pool registry, or change the router interface so venue identity is resolved from immutable protocol configuration rather than route bytes. Independently, wallets and SDK verification must reject a strategy authorization containing any child call other than the expected protocol transfer, but client-side checking should not be the primary contract boundary. [11](#0-10) 

### Proof of Concept
1. Deploy `RogueHopPool` with `(victim, wallet_token, attacker, victim_wallet_balance)` as its plan; its `swap` function calls `wallet_token.transfer(victim, attacker, victim_wallet_balance)`. [12](#0-11) 
2. Build a `swap_collateral` route whose hop pool is `RogueHopPool`, while arranging a fair token output so measured settlement succeeds. [9](#0-8) 
3. Simulate the victim's `swap_collateral` call. The recorded authorization tree contains the strategy invocation and a child `wallet_token.transfer(victim -> attacker, WALLET_BALANCE)`. [13](#0-12) 
4. Submit the call with that simulated authorization tree. The malicious transfer succeeds and the victim's wallet balance becomes zero while the attacker receives `WALLET_BALANCE`. [5](#0-4)

pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();

    s.t.env.mock_all_auths();

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
