## Finding

**Unhandled exception (crash / DoS) via `'definition template'` in `validateAuthentifiers` — ([File: definition.js])**

### Summary
`definition.js` implements two evaluators for address-definition expression trees: `validateDefinition()` (used when a new address/asset definition is first validated) and `validateAuthentifiers()` (used every time a unit is authenticated against an already-registered address definition). Both support the `'definition template'` operator, which loads a previously stored `definition_template` message and expands it with caller-supplied parameters via `replaceInTemplate()`. In `validateDefinition`, this expansion is wrapped in a `try/catch` that explicitly handles `NoVarException` (and rethrows anything else, which is caught further up by the surrounding `try{...}catch(e){return cb2(false)}` framework used elsewhere). In `validateAuthentifiers`, the equivalent code path does **not** wrap the `JSON.parse` / `replaceInTemplate` call in any `try/catch`. [1](#0-0) [2](#0-1) 

### Finding Description
`validateDefinition`'s handling of `'definition template'`:
```
var arrTemplate = JSON.parse(template);
try{
    var arrFilledTemplate = replaceInTemplate(arrTemplate, params);
    ...
}
catch(e){
    if (e instanceof NoVarException)
        return cb(e.toString());
    else
        throw e;
}
evaluate(arrFilledTemplate, path, bInNegation, cb);
``` [3](#0-2) 

`validateAuthentifiers`'s handling of the same operator has no guard at all:
```
case 'definition template':
    var unit = args[0];
    var params = args[1];
    conn.query(
        "SELECT payload FROM messages JOIN units USING(unit) \n\
        WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
        [unit, objValidationState.last_ball_mci],
        function(rows){
            if (rows.length !== 1)
                throw Error("not 1 template");
            var template = rows[0].payload;
            var arrTemplate = JSON.parse(template);
            var arrFilledTemplate = replaceInTemplate(arrTemplate, params);
            evaluate(arrFilledTemplate, path, cb2);
        }
    );
    break;
``` [2](#0-1) 

`validateAuthentifiers` is invoked for **every** unit signed by an address whose definition (or a nested address referenced from it) uses `'definition template'` — this is normal, unprivileged signature verification performed on every incoming unit, not a special/privileged code path. `replaceInTemplate` throws `NoVarException` for template variables that cannot be resolved from the supplied `params` (this exact exception class is imported/caught only in the `validateDefinition` sibling function, confirming it is a legitimate, reachable failure mode, not merely a defensive check). Because the throwing call occurs inside a `db.query` callback with no surrounding `try/catch` anywhere up the call chain in this function, a thrown exception becomes an unhandled asynchronous exception in Node.js, which by default terminates the process (crash).

An address owner controls both: (a) the `definition_template` unit content that was stored earlier (attacker-authored), and (b) the `params` passed to `'definition template'` in the address definition that references it. A well-formed unit signed by an address defined this way, when the two are mismatched in a way `replaceInTemplate` cannot resolve (missing variable, wrong param type/shape, etc.), will trip the unguarded `throw` during ordinary authentifier validation — this is the direct control-flow analog of the CVE's `parseNormalModeParameters` pattern, where a malformed-but-syntactically-legal input reaches a parser/expander path lacking exception handling and crashes the process handling it.

### Impact Explanation
An unhandled exception thrown inside `conn.query`'s callback in `evaluate()` will propagate as an uncaught exception at the Node.js event-loop level, since it is not caught anywhere in `validateAuthentifiers`'s asynchronous chain (`async.eachSeries` callbacks, `conn.query` callbacks). This crashes the validating node process. Since `validateAuthentifiers` runs on every full/light node validating a unit signed with such a definition, a single crafted unit can be broadcast to crash any node (including witnesses/hubs) that attempts to validate it — a network-wide denial-of-service / inability to confirm new units, which matches the "network unable to confirm new units" impact criterion.

### Likelihood Explanation
Likelihood is moderate-to-high for a determined poster: an ordinary unprivileged user can (1) post a `definition_template` message defining an address template with formula/variable placeholders, (2) create/fund an address whose definition uses `'definition template'` referencing that message with a `params` object, and (3) post a payment/other unit from that address using parameters that `replaceInTemplate` cannot resolve. All three steps use standard, publicly available unit types (`definition_template`, custom address definitions, and `'definition template'` op) with no special permissions required.

### Recommendation
Wrap the `JSON.parse(template)` / `replaceInTemplate(arrTemplate, params)` call in `validateAuthentifiers`'s `'definition template'` case (`definition.js`, inside the `conn.query` callback around line 814-816) in a `try/catch`, mirroring the handling already present in `validateDefinition` (`definition.js:330-339`), converting any thrown exception (including `NoVarException`) into `cb2(false)` (authentifier check fails) rather than letting it propagate as an unhandled exception.

### Proof of Concept
1. Attacker's device posts a `definition_template` message (`app: "definition_template"`) whose payload is an address-definition template referencing a template variable, e.g. `['address@REPLACE_ME', ...]` or a template with a variable used inconsistently (so that `replaceInTemplate` will raise `NoVarException` for some parameter combinations, e.g. a variable referenced in the template body that is not present among the substitution keys derivable from `params`).
2. Attacker creates address `A` whose definition is `['definition template', [<hash_of_step_1_unit>, { <params that don't satisfy all template variables> }]]` and funds it minimally.
3. Attacker posts any unit authored by address `A` (e.g. a trivial payment). During validation, `validateAuthentifiers` is invoked to check the author's signature against definition of `A`; it fetches the template, calls `JSON.parse` + `replaceInTemplate` unguarded (`definition.js:814-815`), which throws `NoVarException` (or any other error from `replaceInTemplate`), crashing the validating node process before any error callback is reached.

Note: I could not directly view the source of `replaceInTemplate`/`NoVarException` (defined in `definition.js` but outside the excerpts I was able to retrieve within the available tool budget) to enumerate every exact input that triggers the exception; however, the fact that the sibling function `validateDefinition` explicitly imports and special-cases `NoVarException` around the identical `replaceInTemplate` call confirms this exception is a real, reachable failure mode that the `validateAuthentifiers` code path fails to guard against. A full Devin session with file-read access could confirm the exact triggering conditions in the `replaceInTemplate` implementation.
