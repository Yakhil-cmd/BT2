### Title
Cross-organization team-membership write via unscoped `github_id` lookup allows escalation into `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
The `membership` webhook handler resolves the `Team` record to mutate using only the numeric `github_id` supplied in the (correctly signed) webhook payload, without verifying that the team actually belongs to the GitHub organization whose secret validated the request. In a multi-organization Shipit deployment, an administrator of any onboarded-but-untrusted organization can send a genuine, validly-signed `membership` webhook that references another organization's `Team` by its `github_id`, and add an arbitrary Shipit `User` to that team — including teams listed in `Shipit.github_teams`, which gate access to the whole application.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp`/secret to validate the payload based on a field taken from the payload itself: for `membership` events, `repository_owner` falls back to `params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

This is legitimate in Shipit's documented multi-tenant setup, where distinct GitHub organizations each get their own `GitHubApp`/webhook secret entry under `secrets.github`. [3](#0-2) [4](#0-3) 

So the signature check only proves "this payload was really sent by organization X's GitHub App installation" — it says nothing about which `Team` record inside Shipit that payload is allowed to affect. The `MembershipHandler` then resolves and mutates a `Team` purely by the attacker-supplied `team.id` (GitHub's numeric team ID), with no check that `team.organization` matches the authenticated `organization.login`:

```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [5](#0-4) 

`Team` has no uniqueness or scoping validation tying `github_id` to `organization`. [6](#0-5) 

Because `find_or_create_by!` looks the record up by `github_id` alone, if a `Team` row already exists for that `github_id` (created earlier from the legitimate organization's own membership sync), the `do |team| ... end` initializer block — which is the only place `team.organization` is set — is skipped entirely, and the existing (foreign) `Team` object is returned unchanged and then mutated:

```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)

  case params.action
  when 'added'
    team.add_member(member)
  when 'removed'
    team.members.delete(member)
  end
end
``` [7](#0-6) 

This is structurally the same class of bug as the Augur `MarketFactory` report: a value that is authenticated for one scope (the calling organization / the calling `_universe`) is trusted to select and act on a completely different, more privileged resource (an arbitrary `Team` / arbitrary market's CASH transfer) because the code never checks that the acted-upon entity actually belongs to the authenticated principal.

The binding that should hold but doesn't:
`organization.login` (verified by the webhook signature) `==` `Team#organization` (the org actually written to by `find_or_create_team!`)

Before the attack: Team #1 (`github_id: 1`) belongs to `shopify`, and is one of `Shipit.github_teams` gating access.
After the attack: an admin of an unrelated onboarded org (e.g. `cyclimse`) sends a genuinely-signed `membership` event with `team: { id: 1, ... }` and `member: { login: 'attacker' }`, `action: 'added'`. `Team.find_or_create_by!(github_id: 1)` returns the `shopify` Team, and `team.add_member(User attacker)` adds the attacker as a member of the `shopify` team.

### Impact Explanation
`User#authorized?` grants application-wide access based on membership in `Shipit.github_teams`:
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
``` [8](#0-7) 
and `force_github_authentication` uses exactly this check to gate the entire engine. [9](#0-8) 

An attacker who is not a member of the required GitHub team, and controls (or is an admin within) any other GitHub organization onboarded to the same multi-tenant Shipit instance, can grant themselves membership in a required, privileged team, and thereby bypass Shipit's team-based authorization — directly matching the "escalation into `Shipit.github_teams` authorization" High-impact criterion.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (documented, supported configuration) where the attacker administers or has team-membership-webhook-triggering rights in one onboarded organization, and (2) knowledge of the target team's numeric `github_id` (obtainable via the public/authenticated GitHub API for org teams, or via `GET /orgs/{org}/teams`, or by observing prior webhook deliveries/logs). No Shipit session, API token, or webhook secret of the target organization is required — only legitimate, validly-signed webhook traffic from the attacker's own organization.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup to the authenticated organization, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and reject (or `NotFound`) if an existing team with that `github_id` belongs to a different organization than the one that authenticated the webhook. Add a uniqueness/consistency validation on `Team` tying `github_id` to `organization`, and add regression tests covering cross-organization `membership` webhooks that target an existing team's `github_id` from a different org.

### Proof of Concept
1. Shipit is configured with multiple GitHub organizations (`shopify` and `cyclimse`), each with its own webhook secret, as in `test/dummy/config/secrets_double_github_app.yml`.
2. `Shipit.github_teams` includes `shopify/developers` (Team `github_id: 1`), used to gate access.
3. Attacker is an admin of the `cyclimse` organization (also onboarded to this Shipit instance) and triggers/crafts a legitimate `membership` webhook from `cyclimse`, signed with `cyclimse`'s real webhook secret:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "cyclimse" },
  "member": { "login": "attacker" }
}
```
4. `verify_signature` validates using `cyclimse`'s secret — succeeds, because it truly came from `cyclimse`.
5. `MembershipHandler#find_or_create_team!` calls `Team.find_or_create_by!(github_id: 1)`, which returns the existing `shopify/developers` Team (id 1) instead of creating a `cyclimse` team.
6. `team.add_member(User.find_or_create_by_login!('attacker'))` adds `attacker` to the `shopify/developers` team.
7. `attacker.authorized?` now returns `true` via `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, granting full access to the Shipit instance despite never being a real member of `shopify/developers`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  class Team < Record
    REQUIRED_HOOKS = %i[membership].freeze

    has_many :memberships
    has_many :members, class_name: :User, through: :memberships, source: :user

    has_many :github_hooks,
             -> { where(event: REQUIRED_HOOKS) },
             foreign_key: :organization,
             primary_key: :organization,
             class_name: 'GithubHook::Organization',
             inverse_of: false

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
