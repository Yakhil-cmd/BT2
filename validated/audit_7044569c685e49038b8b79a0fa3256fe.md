## Title
Concurrent redemption of the same private-payment chain via non-atomic check-then-insert allows double-spend of a private asset output before the DB unique constraint applies — (File: private_payment.js)

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain` (the entry point reached by any private-payment counterparty sending a `private_payment` message) performs a classic find-then-act sequence: it opens a *new* database connection, `BEGIN`s a transaction, runs a `SELECT` to check whether the chain's head output was already recorded, and only if that `SELECT` finds nothing does it proceed to validate and `INSERT` the chain into `outputs`/`inputs` [1](#0-0) . Unlike the public-unit path, this function acquires **no mutex** before performing the check — no `mutex.lock(['handleJoint'])` and no `mutex.lock(arrAuthorAddresses, ...)`, both of which are mandatory for ordinary joint validation [2](#0-1) , and are used precisely to serialize concurrent claims on the same resource.

### Finding Description
For public payments, `validation.validate()` always takes `mutex.lock(arrAuthorAddresses, ...)` before touching the DB [3](#0-2) , and `network.handleJoint` additionally serializes all incoming joints under `mutex.lock(['handleJoint'], ...)` [4](#0-3) . This gives the "read-then-write" combination effective atomicity across concurrent submissions.

Private payments bypass this. `network.handleOnlinePrivatePayment` calls straight into `privatePayment.validateAndSavePrivatePaymentChain` with no mutex around the call [5](#0-4) , and the `handleSavedPrivatePayments` bulk-flush path processes rows from `unhandled_private_payments` **in parallel** with `async.each` (not `eachSeries`), each spawning its own call into the same unguarded function [6](#0-5) .

Inside `private_payment.js`, the "duplicate" check is a plain `SELECT ... FROM outputs WHERE unit=? AND asset=? AND message_index=?` on a freshly acquired connection, followed conditionally by an `INSERT` performed by `indivisible_asset.js`/`divisible_asset.js` on the *same* connection's transaction [7](#0-6) . Two concurrent deliveries of the same private-payment chain (trivial for a counterparty to cause — e.g. relaying the same chain both directly and via the hub, or simply resending it twice, both of which `handleOnlinePrivatePayment`/`handleSavedPrivatePayments` are explicitly designed to tolerate as "received twice") each open their own connection, both run the duplicate-check `SELECT` before either has committed its `INSERT`, both see zero rows, and both proceed to validate and write the chain.

The DB-level `UNIQUE KEY bySrcOutput(src_unit, src_message_index, src_output_index, is_unique)` on the `inputs` table, which is what prevents this exact race for *public* payments [8](#0-7) , does **not** fire here: both `divisible_asset.js` and `indivisible_asset.js` explicitly set `is_unique = null` for any not-yet-stable private element ("unstable still have chances to become nonserial therefore nonunique") [9](#0-8) , and SQL unique indexes treat `NULL` values as distinct, so two rows spending the very same source output can both be inserted concurrently without violating the constraint [10](#0-9) .

### Impact Explanation
A malicious private-payment counterparty (a role explicitly in scope) can cause the same private-asset source output to be registered as spent into two independent output chains at the recipient/light-wallet node, each of which is locally treated as valid pending stabilization. Because the light-wallet comment in `checkForDoublespends` states "we can't use graph in light wallet, the private payment can be resent and revalidated when stable" [11](#0-10) , a light node receiving both branches independently (e.g. from two different senders/paths) has no reliable way to detect the conflict before accepting funds, enabling the same coin to be presented as valid private balance twice — a double-spend of value that is not caught by the atomic-uniqueness protection relied on for public payments.

### Likelihood Explanation
Triggering the race requires only sending (or replaying) the identical `private_payment` message concurrently through two channels that the protocol already accepts as normal (direct peer delivery + hub-relayed delivery, or duplicate resend while a previous copy is still queued in `unhandled_private_payments`). No cryptographic break, elevated privilege, or malicious node/hub behavior is needed — a single unprivileged private-payment counterparty controls both message deliveries, and the code paths that process them (`handleOnlinePrivatePayment`, `handleSavedPrivatePayments`) are specifically designed to accept duplicate deliveries, so hitting the narrow window between the `SELECT` duplicate-check and the `INSERT` on two racing connections is a realistic, repeatable condition, not a purely theoretical one.

### Recommendation
Serialize private-payment validate-and-save calls the same way public joints are serialized — e.g. acquire a `mutex.lock` keyed by `(unit, message_index[, output_index])` (or by the underlying source-output identity) in `private_payment.js` before running the duplicate-check `SELECT`, and hold it until the transaction commits/rolls back. Alternatively, make the duplicate-check-and-insert atomic by relying on a DB-level uniqueness guarantee that also applies to unstable rows (e.g. use a non-`NULL` uniqueness key based on `(src_unit, src_message_index, src_output_index)` regardless of `is_unique`/stability, with conflict handling that mirrors `checkForDoublespends`) instead of allowing `NULL` `is_unique` to bypass the constraint for unstable private elements.

### Proof of Concept
1. Prepare a valid private-asset payment chain spending output `O` to recipient `R` (a single `arrPrivateElements` chain, unit `U`, message_index `M`).
2. As the sender/counterparty, deliver the same chain content twice concurrently to the victim node before it has stabilized/committed either copy — e.g. once via `network.handleOnlinePrivatePayment` directly (peer message) and once by causing it to also land in `unhandled_private_payments` so `handleSavedPrivatePayments`'s parallel `async.each` picks it up at the same time [6](#0-5) .
3. Both invocations reach `private_payment.js`'s `validateAndSave`, each opening its own connection and `BEGIN`ning independently; both execute the "check if duplicate" `SELECT` before either has inserted/committed, so both see zero matching rows [12](#0-11) .
4. Both connections proceed to `indivisibleAsset`/`divisibleAsset`'s `validateAndSavePrivatePaymentChain`, each inserting an `outputs`/`inputs` row for the same source output `O` with `is_unique=NULL` (unstable), which does not collide with the `UNIQUE KEY bySrcOutput(..., is_unique)` constraint [13](#0-12) .
5. Both transactions `COMMIT` successfully — the same private-asset output is now recorded as spent into two independent recipient chains, each accepted locally, with resolution only deferred to later (unreliable, per-comment) doublespend graph analysis at stabilization time.
