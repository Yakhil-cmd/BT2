### Title
Recipient Contract Revert in `handleKLAYTransfer` Permanently Locks Bridged KLAY — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`BridgeTransferKLAY.handleKLAYTransfer` updates bridge nonce state before transferring KLAY to `_to`, then hard-reverts on transfer failure. If `_to` is a contract that rejects KLAY, the entire transaction — including the nonce update — rolls back. Operators can never advance past that nonce, and the KLAY deposited on the source chain is permanently locked in the destination bridge contract with no rescue path.

---

### Finding Description

`handleKLAYTransfer` executes in this order:

```solidity
// BridgeTransferKLAY.sol lines 81-99
_setHandledRequestTxHash(_requestTxHash);          // (1) marks tx hash handled
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber; // (2) records block
_updateHandleNonce(_requestedNonce);               // (3) advances nonce

emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed"); // (4) hard revert on failure
```

If `_to` is a contract whose fallback reverts (e.g., a multisig that was bricked, a contract upgraded to reject native tokens, or a sanctioned address), step (4) causes the entire transaction to revert. Because Solidity reverts all state changes atomically, steps (1)–(3) are also rolled back:

- `_setHandledRequestTxHash` is undone → the request tx hash is not marked handled
- `_updateHandleNonce` is undone → `lowerHandleNonce` / `upperHandleNonce` are not advanced
- The nonce slot remains open

Bridge operators (driven by `BridgeInfo.handleRequestValueTransferEvent` in `node/sc/bridge_manager.go`) will keep re-submitting `handleKLAYTransfer` for the same event, but every attempt reverts. The KLAY sits in the destination bridge contract indefinitely. There is no owner-callable rescue or redirect function in `BridgeTransferKLAY`; `chargeWithoutEvent` only adds funds, and `_to` is fixed by the source-chain event parameters that operators must reproduce verbatim.

The analogous pattern in `BridgeFee._payKLAYFeeAndRefundChange` (lines 49–55) also performs two sequential `require`-guarded native transfers — first to `feeReceiver`, then a refund to `msg.sender` — so a reverting `feeReceiver` contract blocks all KLAY bridge requests. However, that path only causes a DoS (the user's KLAY is returned on revert). The `handleKLAYTransfer` path is more severe because the source-chain deposit is already irrevocably consumed.

---

### Impact Explanation

- **Bridged KLAY permanently locked**: KLAY deposited on the source chain cannot be delivered on the destination chain and cannot be recovered by any party.
- **Bridge nonce stuck**: The unprocessable nonce remains open; depending on the nonce-window logic (`upperHandleNonce` window of 200), subsequent nonces may still be processed, but the stuck nonce's KLAY is never released.
- **No operator or owner escape hatch**: `handleKLAYTransfer` parameters are dictated by the source-chain event; operators cannot substitute a different `_to`. No withdrawal function exists in `BridgeTransferKLAY`.

---

### Likelihood Explanation

Low. Requires `_to` to be a contract that reverts on receiving native tokens. Realistic scenarios:

1. User bridges to a multisig or proxy contract that is later upgraded or bricked.
2. User bridges to a contract whose `receive()` / fallback was intentionally or accidentally made to revert.
3. `_to` is a sanctioned contract address that has been frozen at the EVM level by a future upgrade.

The user sets `_to` on the source chain; there is no validation that `_to` can accept KLAY on the destination chain.

---

### Recommendation

Apply a pull-payment (claim) pattern for the destination transfer: instead of pushing KLAY to `_to` and reverting on failure, credit the amount to a claimable balance mapping and let `_to` withdraw it. Alternatively, on transfer failure, emit a `TransferFailed` event and allow the bridge owner to redirect the KLAY to a fallback address, rather than reverting the entire nonce-update transaction.

---

### Proof of Concept

1. Alice calls `requestKLAYTransfer(contractAddr, 1 ether, "0x")` on the source bridge, where `contractAddr` is a contract whose `receive()` always reverts. The source bridge records `requestNonce = N` and holds Alice's KLAY.
2. Bridge operators observe the `RequestValueTransfer` event and call `handleKLAYTransfer(txHash, alice, contractAddr, 1 ether, N, blockNum, "0x")` on the destination bridge.
3. Steps (1)–(3) in `handleKLAYTransfer` execute: tx hash marked, nonce recorded, `_updateHandleNonce` called.
4. `contractAddr.call.value(1 ether)("")` returns `ok = false`; `require(ok, "handleKLAYTransfer: transfer failed")` reverts the entire transaction.
5. All state from steps (1)–(3) is rolled back. Nonce `N` is not consumed.
6. Operators retry indefinitely; every attempt reverts identically.
