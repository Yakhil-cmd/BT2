### Title
Webhook signature verification authenticates a different organization than the repository a handler subsequently writes to - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a signature against using `repository.owner.login` (or `organization.login`) taken from the *unverified* request body, while the handlers invoked afterwards (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolve the target `Stack`/`Commit` using a *different* field of the same body — `repository.full_name` or a bare `sha`. Nothing ties the organization whose secret validated the HMAC to the repository/stack that the handler actually mutates.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is read straight from the JSON body before any signature check has occurred: [2](#0-1) . Shipit supports multiple GitHub organizations, each with its own independently configured `webhook_secret` (optional per the setup docs) [3](#0-2) . `verify_webhook_signature` even explicitly returns `true` unconditionally when the selected org has no secret configured: [4](#0-3) .

Once the signature is accepted for whatever organization `repository.owner.login` names, `create` re-parses the full raw body and dispatches it, unmodified, to handlers: [5](#0-4) . The base `Handler` class resolves the acted-upon repository from a *different* payload field, `repository.full_name`, with no cross-check against `repository.owner.login`: [6](#0-5) , and `Repository.from_github_repo_name` simply splits that string on `/` and looks up whichever `Stack`s exist for it: [7](#0-6) .

Concretely:
- `PushHandler` finds any non-archived stacks matching the branch under that repository and calls `stack.sync_github(expected_head_sha: params.after)` [8](#0-7) .
- `StatusHandler` looks up commits purely by `sha` (global, not scoped to any repo/org check at all) and calls `commit.create_status_from_github!(params)`, which writes a CI status for that commit under whatever stack it belongs to [9](#0-8) .
- `CheckSuiteHandler` similarly resolves stacks by repository and schedules check-run refreshes [10](#0-9) .

This maps to the required binding-break class: **an organization that authenticated versus the repository that is written**. Before the attack: signature verification is intended to prove "this payload originated from GitHub for organization X, and everything in it (including the acted-upon repository) is trustworthy for X." After the attack: the signature only proves the payload matches organization X's secret; the repository/commit actually mutated is named by an unrelated field the attacker fully controls and can point at another organization/stack hosted on the same multi-tenant Shipit instance.

### Impact Explanation
An attacker who is a legitimate administrator of *any* one GitHub organization configured on a shared/multi-org Shipit instance (or any org configured without a `webhook_secret`, which the setup docs explicitly allow) knows or can trivially satisfy that organization's webhook secret. They can then POST directly to `/webhooks` with a body whose `repository.owner.login`/`organization.login` names their own org (so `verify_signature` picks their own, known secret) but whose `repository.full_name` (for push/check_suite) — or bare `sha` (for status, which isn't even repository-scoped) — names a victim stack belonging to a different organization on the same instance.

Using the `status` event this is most severe: `StatusHandler` matches purely by commit `sha` with no organization/repository binding at all, so the attacker can forge a `success` CI status for a specific commit SHA in a victim's repository. If that stack has `continuous_deployment` enabled, `Commit#deployable?` will now consider that commit deployable [11](#0-10) , and the continuous delivery job will trigger an actual deploy of that (attacker-chosen) commit — this is an **unauthorized deploy**, one of the explicitly in-scope Critical impacts.

### Likelihood Explanation
Requires the attacker to control (or have credentials for) at least one GitHub organization/App entry configured in the shared Shipit instance's `secrets.yml` — a realistic scenario for any organization operating a shared, multi-tenant Shipit deployment serving several GitHub orgs/teams, which is a documented, supported configuration [3](#0-2) . No GitHub webhook secret for the *victim* org is needed at all; only the attacker's own (possibly org-with-no-secret) org's credential is required, and the endpoint is reachable unauthenticated by design (it is the public webhook receiver).

### Recommendation
Bind the field used to select the verification key to the field(s) used by every handler to resolve the acted-upon entity. Concretely:
- Verify the signature using the raw body only (already done), but after verification, re-derive `repository_owner`/organization strictly from `repository.full_name`'s owner segment (the same field handlers use), not from `repository.owner.login`/`organization.login`, or require both to match.
- In `Handler#stacks`/`StatusHandler#process`, additionally assert that the resolved `Stack`'s `repository.owner` matches the organization whose secret validated the request, rejecting the event otherwise.
- Do not allow `verify_webhook_signature` to return `true` when no secret is configured; require every configured organization to have a webhook secret, or refuse events for orgs with a blank secret.

### Proof of Concept
1. Shipit instance is configured with two orgs in `secrets.yml`: `attacker-org` (attacker is an admin, knows/controls `webhook_secret`, or it is left blank) and `victim-org` (hosts a stack `victim-org/victim-repo` with `continuous_deployment: true`).
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/attacker-forged"
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s webhook secret (known to them) over the raw body, sets `X-Github-Event: status`, and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")`, verifies successfully.
5. `StatusHandler#process` runs `Commit.where(sha: "<victim-commit-sha>")` — matching the commit in `victim-org/victim-repo` regardless of which org validated the signature — and creates a `success` status for it.
6. If `victim-org/victim-repo`'s stack has `continuous_deployment` enabled and no other blocking status, `Commit#deployable?` becomes true and the stack's continuous delivery job triggers an actual deploy of the attacker-chosen commit.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
