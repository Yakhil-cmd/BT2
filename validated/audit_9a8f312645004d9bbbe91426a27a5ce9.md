### Title
Blackholed / unpaired correspondent device is still treated as a valid, trusted correspondent for incoming messages - (File: [device.js](https://github.com/hirayap/ocore--008/blob/main/device.js), [wallet.js](https://github.com/hirayap/ocore--008/blob/main/wallet.js))

### Summary
The CVE-2024-25628 bug class is "session/identity invalidated but still accepted for privileged access." In ocore, the analogous trust boundary is the paired-device correspondent relationship: a device that has been unpaired/invalidated (`is_blackhole=1`) is never actually excluded from the lookup that gates which incoming hub messages are treated as coming from a "known correspondent," so the invalidated device keeps its trusted status.

### Finding Description
When a device receives a `removed_paired_device` justsaying and `conf.bIgnoreUnpairRequests` is set, the correspondent row is *not* deleted; it is only flagged: [1](#0-0) 

This is meant to revoke the peer while keeping bookkeeping (the row still exists but is marked `is_blackhole=1`). However, the gate that decides whether an incoming `hub/message` is from a "known correspondent" (as opposed to an untrusted stranger, which is restricted to a small whitelist of subjects) only checks for row existence, not the `is_blackhole` flag: [2](#0-1) 

Because the query is `SELECT hub, is_indirect FROM correspondent_devices WHERE device_address=?` with no `AND is_blackhole=0` predicate, a device that was supposedly invalidated is still found, `handleMessage(rows[0].is_indirect)` is still invoked, and the message is dispatched into `wallet.js`'s full `handleMessageFromHub` switch as if the sender were a fully trusted, still-paired correspondent. `readCorrespondent`/`readCorrespondents`, used elsewhere to decide whether to accept requests from a device (e.g. cosigner checks, shared-address flows), likewise select without filtering on `is_blackhole`: [3](#0-2) 

`removeCorrespondentDevice` (the actual full revocation path used when `bIgnoreUnpairRequests` is false) does delete the row and the outbox, which is the correct behavior: [4](#0-3) 

But this is only invoked in the non-`bIgnoreUnpairRequests` branch. When `bIgnoreUnpairRequests` is enabled (a config flag explicitly meant to make unpairing "soft" for retained history), the "revoked" state (`is_blackhole=1`) is not actually enforced anywhere in the incoming-message dispatch path.

### Impact Explanation
Once a device address is compromised or becomes malicious and the wallet owner "unpairs" it while `bIgnoreUnpairRequests` is set, the attacker's device keeps the ability to send any of the full correspondent-trusted subjects handled in `wallet.js`'s `handleMessageFromHub` (signing requests, private payment chains, shared-address/multisig flows, prosaic contract responses, etc.) because `device.js`'s correspondent lookup never excludes blackholed devices. This can lead to continued unauthorized signing-request injection, private-payment/shared-address manipulation, or other fund-impacting interactions with a device the user believed had been cut off — a direct analog of "invalidated identity still granted privileged access."

### Likelihood Explanation
This requires `conf.bIgnoreUnpairRequests = true` (default `false`, per `conf.js` line 62) and a correspondent device that was supposed to be revoked. Given that this flag exists specifically to support "soft" unpairing (e.g., preserving chat/contract history), any deployment enabling it is exposed. The likelihood is Medium: the flag is off by default, but any product built on ocore that turns it on for UX reasons (keep history, avoid re-pairing) inherits this gap without realizing the `is_blackhole` flag is cosmetic in the message-dispatch path.

### Recommendation
Add `AND is_blackhole=0` (or equivalent) to the correspondent lookup in `device.js`'s `hub/message` handler (line 204) and to `readCorrespondent`/`readCorrespondents`/`readCorrespondentsByDeviceAddresses`, so that a blackholed device is treated the same as an unknown correspondent (subject to the strict whitelist) rather than a trusted one. Alternatively, reject `hub/message` outright for `is_blackhole=1` devices before invoking `handleMessage`.

### Proof of Concept
1. Pair device B with device A; B accumulates trust as a correspondent of A.
2. Configure A with `conf.bIgnoreUnpairRequests = true`.
3. B sends `removed_paired_device` to A; A sets `is_blackhole=1` on B's `correspondent_devices` row but keeps the row (per `wallet.js:124-135`).
4. B (now supposedly revoked) sends further `hub/message` traffic, e.g. a `signing_request` or `new_shared_address` payload, to A.
5. In `device.js`'s `hub/message` handler, `SELECT hub, is_indirect FROM correspondent_devices WHERE device_address=?` still returns B's row (`is_blackhole` not checked), so `handleMessage(rows[0].is_indirect)` proceeds and B's message is routed into `wallet.js`'s full correspondent-trusted switch statement instead of being restricted to the non-correspondent whitelist (`pairing`, `my_xpubkey`, `wallet_fully_approved`).

	db.query("SELECT device_address, hub, name, my_record_pref, peer_record_pref FROM correspondent_devices WHERE device_address=?", [device_address], function(rows){
		handleCorrespondent(rows.length ? rows[0] : null);
	});
}

function removeCorrespondentDevice(device_address, onDone){
	breadcrumbs.add('correspondent removed: '+device_address);
	var arrQueries = [];
	db.addQuery(arrQueries, "DELETE FROM outbox WHERE `to`=?", [device_address]);
	db.addQuery(arrQueries, "DELETE FROM correspondent_devices WHERE device_address=?", [device_address]);
	async.series(arrQueries, onDone);
	if (bCordova)
		updateCorrespondentSettings(device_address, {push_enabled: 0});
}
