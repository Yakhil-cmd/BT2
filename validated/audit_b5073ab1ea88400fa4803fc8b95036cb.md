### Title
Default `--max-failures=0` causes a single attacker-triggerable sync error to permanently abort git-sync, denying sync indefinitely - (File: `main.go`)

### Summary
`git-sync`'s main loop treats *any* error from `repoSync.SyncRepo` as a "failure", and by default (`--max-failures` defaults to `0`) a single failure is enough to call `os.Exit(1)` and terminate the process entirely, rather than degrading gracefully or retrying with backoff. This mirrors the Unitas `_checkPrice` bug class: a strict, non-recoverable check on externally-influenced input (there, oracle price bounds; here, the state of a git object/ref fetched from the remote) causes the entire pipeline to halt rather than continue operating with best-effort/last-known-good state.

### Finding Description
The sync loop in `main()` increments `failCount` on any error from `git.SyncRepo` and aborts the whole process once `failCount >= maxFails`, where `maxFails` comes from `getMaxFailures()`: [1](#0-0) 

`--max-failures` (`flMaxFailures`) defaults to `0`: [2](#0-1) 

and the manual explicitly documents that "0" means "any sync failure will terminate git-sync": [3](#0-2) 

`SyncRepo` can fail for reasons that are entirely a function of remote/attacker-controlled repository content, not just transport errors — e.g. `sanityCheckRepo`'s `git fsck --no-progress --connectivity-only` check, which is run on the internal repo directory that has just fetched attacker-supplied objects: [4](#0-3) 

and `sanityCheckWorktree`'s analogous fsck/HEAD-match check on the checked-out worktree: [5](#0-4) 

If a pushed commit produces a repo/worktree state that fails these checks (or any other step of `fetch`/`rev-parse`/checkout, including submodule handling, which `flSubmodules` controls), `SyncRepo` returns an error every single sync attempt for that ref, because the remote ref keeps resolving to the same broken commit. With the default `--max-failures=0`, the very first such failure is fatal: `os.Exit(1)` at `main.go:1061`, permanently stopping the sync loop until an operator intervenes (e.g., pins to an older ref/hash or bumps `--max-failures`).

### Impact Explanation
This is a persistent sync denial: once an attacker-pushed commit (or any transient environmental condition, like a broken object) triggers one `SyncRepo` failure while `--max-failures` is left at its default, `git-sync` exits and stops publishing updates altogether, freezing the symlink at whatever was last published. Any Kubernetes restart policy would simply re-run `git-sync`, re-fetch the same broken ref, and exit again — an unrecoverable crash loop until the operator manually changes configuration or the remote ref is fixed. This matches the "core functionality disabled" impact from the oracle report: legitimate downstream consumers stop receiving fresh data indefinitely.

### Likelihood Explanation
Requires: (1) `--max-failures` left at its default (`0`), which is the out-of-the-box behavior unless an operator explicitly raises it, and (2) an attacker able to push a commit/ref to the synced repository (or otherwise cause one `SyncRepo` failure), which is the stated attacker model ("attacker-pushed commit ... reachable"). Given the default flag value, likelihood of hitting this from any single failure (not necessarily malicious — the same code path is reachable from an attacker-crafted commit that fails `fsck`/checkout) is high in default deployments.

### Recommendation
Do not default `--max-failures` to `0`. Prefer retry-with-backoff semantics by default (continue polling, keep serving the last-known-good published link, and only fail process health/readiness rather than exiting the whole process) so a single malformed remote object/ref cannot permanently disable syncing. If a hard-abort policy is desired for repeated failures, require an explicit, larger failure threshold and expose it clearly as a required opt-in for "fail-fast" semantics.

### Proof of Concept
1. Deploy `git-sync` with default flags (`--max-failures` unset ⇒ `0`) against a repository the operator does not fully control (e.g., syncing a branch that receives external contributions/merges).
2. An attacker with push access to that branch/ref commits content that causes a subsequent `git fsck --connectivity-only` or checkout step to fail (e.g., a broken/incomplete history reachable via a shallow-fetch edge case, or a submodule reference the environment cannot resolve, depending on `--submodules` setting).
3. On the next sync cycle, `git.SyncRepo` returns an error; `failCount` becomes `1`, which is `>= maxFails (0)`, so `main.go:1059-1061` logs "too many failures, aborting" and calls `os.Exit(1)`.
4. The container/process exits; any orchestrator restart re-runs the identical fetch against the same broken ref and exits again, permanently denying sync until an operator manually intervenes (change `--ref`, raise `--max-failures`, or fix the remote). [1](#0-0)
