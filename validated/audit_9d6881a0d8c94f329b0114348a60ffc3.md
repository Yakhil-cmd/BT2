### Title
TOCTOU race in private payment duplicate-output check allows double-crediting of private asset outputs - ([File: private_payment.js])

### Summary
`validateAndSavePrivatePaymentChain` in `private_payment.js` performs a classic check-then-act sequence — it `SELECT`s for an existing output row to detect a duplicate private payment, and only *after* seeing no row (or a non-matching row) does it call into `indivisibleAsset`/`divisibleAsset` to validate and insert the private-payment outputs. Unlike the public-unit save path, which is serialized behind `mutex.lock('handleJoint')` before `validation.validate`/`writer.saveJoint` runs, this private-payment path takes only a per-connection `BEGIN`/`COMMIT` and no application-level mutex around the "check duplicate, then insert" sequence. This mirrors the crayon `HandleLike` TOCTOU bug class: a check on a resource's state is separated in time from the action taken on that state, and a second actor can interleave between the check and the act.

### Finding Description
`validateAndSavePrivatePaymentChain` (`private_payment.js:23-119`) is the entry point used to validate and save an incoming private payment chain (used for private-asset transfers received directly or relayed between wallets/devices). The relevant sequence is:

1. `storage.readAsset` reads the asset definition (no lock).
2. `db.takeConnectionFromPool` + `conn.query("BEGIN")` opens an independent connection/transaction.
3. A `SELECT address, denomination, amount, blinding FROM outputs WHERE unit=? AND asset=? AND message_index=? [AND output_index=?]` is run to detect whether this private output was already saved (`private_payment.js:62-73`).
4. If no matching/duplicate row is found, `assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks)` is invoked, which performs further validation and inserts the outputs/inputs and commits.

This entire "check → act" sequence is guarded only by that single connection's own `BEGIN`/`COMMIT`, not by any cross-connection mutex such as `mutex.lock(['private_write'])` (which is used elsewhere in `validation.js`'s `checkInputDoubleSpend`, e.g. at `validation.js:2283-2295`, precisely because the public payment double-spend / "ununique" logic needs mutual exclusion). Because there is no equivalent lock wrapping the duplicate-detection `SELECT` and the subsequent insert in `private_payment.js`, two private-payment messages for the same chain/output that arrive close together (e.g. a legitimately resent private payment from a counterparty, or a private payment forwarded via two different device/message paths as is explicitly anticipated by `findUnfinishedPastUnitsOfPrivateChains`) can both open independent connections, both run the duplicate-check `SELECT` before either has committed its `INSERT`, both observe "no existing row," and both proceed to validate and insert — a time-of-check to time-of-use race on the `outputs` row for that unit/message_index(/output_index). Contrast with the deliberately-locked public path in `composer.js`/`divisible_asset.js`/`indivisible_asset.js`, which explicitly serializes validate-then-save with `mutex.lock('handleJoint')`: [3](#0-2) 

And the explicit private-write mutex used elsewhere for the analogous public double-spend "ununique" TOCTOU protection, which is conspicuously absent from `private_payment.js`: [4](#0-3) 

### Impact Explanation
If the race is won by two concurrent private-payment save attempts, the private asset's off-chain bookkeeping (the `outputs` table entries used to track ownership/spendability of private, on-DAG-but-hidden amounts) can end up processed twice for what should be a single output, or under partially-overlapping validation, produce inconsistent per-node state for the same private chain. Because private outputs back real asset value transferred between counterparties, a successful double-processing translates to unauthorized duplicate crediting of a private-payment output — an asset-accounting integrity violation analogous to the "double spend of a stable output" / inflation class called out in the validation rules.

### Likelihood Explanation
This requires a private-payment sender (or a compromised/malicious counterparty in a private-payment/AA private-chain flow) to intentionally deliver the same private-payment chain twice in rapid succession, exploiting the window between the duplicate-check `SELECT` on one connection and the `COMMIT` of the insert on another connection. `findUnfinishedPastUnitsOfPrivateChains` and the light-wallet retry path in `private_payment.js:113-118` show that re-delivery of the same private chain is an expected/normal occurrence in this codebase, meaning the conditions for triggering concurrent duplicate processing are readily reachable by an unprivileged private-payment counterparty without needing any protocol violation — only timing.

### Recommendation
Wrap the "duplicate check → validate → insert" sequence in `private_payment.js` with a mutex keyed by `(unit, asset, message_index[, output_index])` (or reuse a `private_write`-style global mutex, consistent with the pattern already used in `validation.js`'s `checkInputDoubleSpend`) so that concurrent saves of the same private-payment output cannot interleave between the duplicate check and the insert. Alternatively, enforce a unique DB constraint on `(unit, asset, message_index, output_index)` in the `outputs` table and treat a constraint-violation on insert as the duplicate signal instead of relying on a preceding `SELECT`.

### Proof of Concept
Conceptual PoC (cannot be executed without a live node):
1. Attacker/counterparty sends the same private-payment chain (`arrPrivateElements` for a given `unit`/`asset`/`message_index`) to the victim node twice in quick succession (e.g., via two race-timed calls to `private_payment.validateAndSavePrivatePaymentChain`, or via light-wallet flows that legitimately resend unfinished chains).
2. Both invocations reach `private_payment.js:45` and open separate pooled connections/transactions.
3. Both run the duplicate-check `SELECT` at `private_payment.js:62-73` before either transaction commits, both see zero/no-matching rows.
4. Both proceed to `assetModule.validateAndSavePrivatePaymentChain` and insert/commit, resulting in the private output being processed twice.
