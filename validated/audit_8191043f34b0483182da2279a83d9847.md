### Title
Stack-scoped API tokens can read CCMenu status for arbitrary stacks — (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the stack-lookup helper defined in `Shipit::Api::BaseController` in a way that drops the stack-scoping check that is supposed to bind an `ApiClient` token to the single stack it was issued for.

### Finding Description
`Shipit::Api::BaseController` defines the authorization boundary between an `ApiClient` token and the stacks it may touch: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the client is scoped, and `stack` resolves `params[:stack_id]` only within that restricted relation — so `Stack.from_param!` raises `ActiveRecord::RecordNotFound` if a scoped client requests any stack other than its own.

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely and resolve the parameter against **all** stacks: [2](#0-1) 

The class only guards access with a permission-string check, `require_permission :read, :stack`, which is enforced via `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` only verifies that the token carries the `read:stack` permission string — it never verifies that the requested stack matches `current_api_client.stack_id`. Fixtures confirm scoped clients exist in practice, e.g. `here_come_the_walrus` is bound to the `shipit` stack: [4](#0-3) 

and the base controller's own `stacks` scoping is exercised and expected to restrict such a client to a single stack elsewhere in the API: [5](#0-4) 

The route also exposes the token via a query-string parameter rather than only an `Authorization` header, and `CCMenuController#authenticate_api_client` explicitly supports this query-token flow: [6](#0-5) [7](#0-6) 

This is the same class of bug as the reported unchecked-return-value issue: an authorization value (the token's bound `stack_id`) is computed by the framework but its result is never checked/enforced on this specific code path, so the security invariant `current_api_client.stack_id == accessed_stack.id` silently fails to hold.

### Impact Explanation
Any holder of a valid `ApiClient` token that carries `read:stack` permission — even one deliberately scoped by an administrator to a single, non-sensitive stack — can use the CCMenu endpoint to read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock status) of **any** stack in the Shipit installation, not just the stack the token was issued for. This is an unauthorized cross-stack read of stack state, matching the "High — unauthenticated/unauthorized read of stack state" impact bucket, because it breaks the `ApiClient.stack_id` authorization boundary that the rest of the API relies on.

### Likelihood Explanation
Exploitation requires only possession of any valid, non-`disable_api_authentication` `ApiClient` token with `read:stack` permission (e.g. one legitimately created and scoped to a single, low-sensitivity stack, such as the ones generated automatically by `CCMenuUrlController#client`, which mints `read:stack`-only tokens on every visit to a stack's CCMenu URL). No special privilege beyond an ordinary scoped read token is needed, and the deviation from `BaseController#stack` is a straightforward code override, making this a concrete and easily triggered logic flaw rather than a theoretical one.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it to use the inherited `stacks` relation, i.e. `stacks.from_param!(params[:stack_id])`) so that stack-scoped `ApiClient` tokens are restricted to their bound stack exactly as in every other API controller.

### Proof of Concept
1. Create (or use `CCMenuUrlController#client`) an `ApiClient` scoped to `stack_id: <stack-A.id>` with permission `read:stack` (mirrors fixture `here_come_the_walrus`).
2. Call `GET /ccmenu/<stack-B-owner>/<stack-B-repo>/<stack-B-env>?token=<stack-A-scoped-token>` for a different stack B that the token was never authorized for.
3. Observe that `Shipit::Api::CCMenuController#stack` resolves stack B via unscoped `Stack.from_param!`, `require_permission :read, :stack` passes (the token has the `read:stack` string permission), and the response returns stack B's CCMenu XML — even though a request to `GET /api/stacks/<stack-B>` with the same token would correctly raise `RecordNotFound` due to `BaseController#stacks` scoping.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
