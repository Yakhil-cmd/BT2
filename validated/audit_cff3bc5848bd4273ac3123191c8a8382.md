### Title
Cross-tenant Team hijack via `find_or_create_team!` ignoring the verified organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the request was signed with the `webhook_secret` of the organization named in the payload's `organization.login`/`repository.owner.login`, but `MembershipHandler#find_or_create_team!` looks up the mutated `Team` purely `by github_id`, never checking that `params.organization.login` matches the `organization` already stored on that `Team` row. Any operator of a legitimately configured multi-tenant org in `Shipit.github` can therefore forge a `membership` webhook that adds an attacker-controlled GitHub login as a member of a `Team` belonging to a different, victim organization, and if that team is in `Shipit.github_teams`, the attacker's `User#authorized?` becomes `true` instance-wide.

### Finding Description
The binding that must hold is: `organization_that_signed_the_request (params.organization.login, verified via that org's webhook_secret in Shipit.github(organization: repository_owner)) == organization_that_owns_the_Team_row_being_mutated (existing_team.organization)`. This does not hold in the code.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) resolves `repository_owner` from the payload (`params.dig('organization', 'login')` for membership events, since there is no `repository` key) and verifies the signature using `Shipit.github(organization: repository_owner)`. This proves only that the request came from a party who controls the webhook secret for **that named organization** (e.g. `attacker-org`) — it says nothing about which `Team`/`github_id` is safe to touch.
- `MembershipHandler#find_or_create_team!` (app/models/shipit/webhooks/handlers/membership_handler.rb:38-43) does:
  ```ruby
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
  ```
  The `find_or_create_by!` lookup key is only `github_id`. If a `Team` row with that `github_id` already exists (belonging to a legitimate victim org), the block (which sets `organization`) is **not executed** — `find_or_create_by!` only runs the block on creation — so the existing team, with its real `organization`, is returned untouched, but is now the object mutated by `#process`.
- `#process` (app/models/shipm/webhooks/handlers/membership_handler.rb:22-34) then does `team.add_member(User.find_or_create_by_login!(params.member.login))` for `action == 'added'`, appending the attacker's forged `User` (`attacker-login`) to the victim `Team`'s `members` association — a real, persisted `Membership` row, with no cross-check that `attacker-org` is the org that actually owns `github_id`.
- If that guessed/known `Team` is included in `Shipit.github_teams` (app/models/shipit/user.rb:80-82, `authorized? = Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?`), the attacker's newly created `User` immediately satisfies `authorized?`.

None of the existing guards prevent this: `verify_signature` authenticates the org name in the payload, not the target `github_id`; `drop_unhandled_event` only filters unregistered event types, not payload content; there is no `ExplicitParameters` cross-field validation enforcing `params.organization.login == existing_team.organization`; `require_permission!`/`force_github_authentication` are unrelated to webhook ingestion. GitHub team IDs are small, sequential, public-facing integers obtainable from GitHub's API for any team, so guessing/brute-forcing a target `github_id` used by `Shipit.github_teams` is feasible for an attacker who merely needs to enumerate integers (or observe a public org's team IDs) and does not need any Shipit secret.

### Impact Explanation
A single unprivileged attacker who owns any tenant org configured in Shipit's `github:` multi-org config (their own legitimate `webhook_secret`) can, per request, add an arbitrary attacker-chosen GitHub login as a member of any `Team` row identified by `github_id`, regardless of which org actually owns that team. This directly escalates into `Shipit.github_teams` authorization (`Shipit::User#authorized?`), granting the attacker (or anyone whose login they choose) full authenticated/authorized access across the whole Shipit instance — deploys, rollbacks, merges, and all repositories/stacks it manages. This matches the "High — escalation into `Shipit.github_teams` authorization" category, and arguably crosses into Critical territory since it is effectively an authentication/authorization bypass affecting the entire instance, not just one org. The attack is repeatable against any `Team` `github_id` and any login the attacker chooses, and is fully cross-tenant: one org's verified webhook mutates another org's authorization-relevant data.

### Likelihood Explanation
Preconditions: (1) Shipit must be configured with more than one GitHub org/tenant in `Shipit.github`, at least one of which the attacker legitimately controls (a realistic multi-tenant Shipit deployment scenario, as implied by the question); (2) `Shipit.github_teams` must be non-empty and reference at least one `Team` row whose `github_id` the attacker can determine or guess. GitHub team IDs are sequential integers and often discoverable via GitHub's public API for teams visible to the attacker or via brute force over a small integer space. The attacker's cost is one signed HTTP POST to `/webhooks` using their own legitimately-configured `webhook_secret` — no Shipit secret, session, or privileged role is required. This is fully repeatable and scriptable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` **and** `organization` (`Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify (rejecting the webhook, e.g. raising/discarding) if a `Team` with that `github_id` already exists under a *different* `organization` than `params.organization.login`, since that indicates either a spoofed payload or a genuine GitHub team ID collision across orgs that must not be silently merged.

### Proof of Concept
Minitest plan for `test/controllers/webhooks_controller_test.rb`:
1. Create a fixture `Team` `victim_team` with `organization: 'victim-org'`, `github_id: 4242`, and add `victim_team` to `Shipit.github_teams` (stub `Shipit.github_teams` to include it).
2. Stub `Shipit.github(organization: 'attacker-org').verify_webhook_signature` to return `true` (simulating a legitimately signed request from `attacker-org`), while leaving `victim-org`'s secret unknown/unstubbed.
3. POST `/webhooks` with header `X-Github-Event: membership`, a signature that only passes verification for `attacker-org`, and body:
   ```json
   {
     "action": "added",
     "team": { "id": 4242, "slug": "attacker-slug", "name": "x", "url": "x" },
     "organization": { "login": "attacker-org" },
     "member": { "login": "attacker-login" }
   }
   ```
4. Assert before the request: `victim_team.organization == 'victim-org'` and `User.find_by(login: 'attacker-login')` is `nil`.
5. After the request, assert: `victim_team.reload.members.exists?(login: 'attacker-login')` is `true`, and `User.find_by(login: 'attacker-login').authorized?` is `true` — demonstrating that a webhook verified under `attacker-org`'s secret mutated `victim-org`'s `Team` and granted instance-wide authorization, i.e. `organization_that_signed != team.organization` yet the mutation succeeded.
