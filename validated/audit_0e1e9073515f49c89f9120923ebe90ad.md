### Title
Unhandled `throw Error` during address-definition resolution can crash a node while validating a unit/authentifiers — analog of GnuTLS crash-on-malformed-chain (ALPINE-CVE-2024-28835) - ([File: definition.js])

### Summary
ALPINE-CVE-2024-28835 is a crash induced by GnuTLS while walking/verifying a malformed certificate chain (`certtool --verify-chain`). The reachable analog in ocore is the "inner address" resolution branch of address/AA-condition evaluation, where a malformed but unprivileged input (a posted unit whose `authors` array contains conflicting entries for the same referenced address) causes the validator to `throw Error(...)` from inside an asynchronous callback instead of returning an error to the callback chain, which is not caught by any surrounding `try/catch` and therefore propagates as an uncaught exception, crashing the Node.js process — analogous to certtool's crash on a malformed chain being verified.

### Finding Description
When evaluating an `['address', other_address]` condition in an address/asset-condition definition, both `validateDefinition`'s `evaluate()` and `validateAuthentifiers`'s `evaluate()` look up the address definition. If it is not found in storage, they fall back to looking for a matching definition supplied inline by one of the unit's `authors`: [1](#0-0) [2](#0-1) 

In both places, if more than one author in `objUnit.authors` matches the same `other_address` and the same `definition_chash`, the code does:
```
if (arrDefiningAuthors.length > 1)
    throw Error("more than 1 address definition");
```
This `throw` happens synchronously inside the `ifDefinitionNotFound` callback passed to `storage.readDefinitionByAddress`, i.e. inside a DB-callback / async control-flow context (`async.eachSeries`/`evaluate` recursion), not inside a `try {...} catch` that funnels back into the `cb`/`handleResult` error path used elsewhere in the same function. An exception thrown from this depth is not caught by the `try { ... } catch (e) { return cb(...) }` blocks that wrap the `objectHash.getChash160` calls just above it — those catches only cover the hash computation, not the `.length > 1` branch. As a result, the exception surfaces as an uncaught exception in the unit-validation code path, which for a Node.js process results in a crash of the full node (unless a higher-level global exception handler restarts it, in which case the node still stops processing/relaying at that moment).

Both `validateDefinition` (used for definitions and asset conditions) and `validateAuthentifiers` (used when checking signatures/authentifiers against an address's definition) are invoked from the core unit-validation flow (`validation.js`) whenever a posted unit contains an `address` reference inside a definition or an authentifier check needs to resolve a nested address definition supplied by a co-author.

An attacker who posts a unit with two co-authors that share the same address value in the `authors` array (both providing inline `definition`s that hash to the same `definition_chash`, i.e. two authors objects with `author.address === other_address` and `objectHash.getChash160(author.definition) === definition_chash`) can trigger `arrDefiningAuthors.length > 1` and cause the `throw Error("more than 1 address definition")` to fire during validation of a completely different, referencing unit that has `['address', other_address]` in its definition and does not include a ball for that address yet.

### Impact Explanation
An uncaught `throw` inside unit/AA/asset-condition validation is a crash-inducing defect reachable by any unprivileged unit poster who can craft: (1) a unit with multiple co-authors sharing the same on-chain address and colliding inline definitions, and (2) any other unit/definition/AA that references that address via `['address', ...]`. If it crashes the validating node process, that node stops confirming units until restarted, which can produce network-wide disagreement about validity/stability if the crash is deterministic and repeatedly hit by different validators reprocessing the same units (e.g., during resync or reorg), potentially stalling confirmation of new units on affected nodes. This matches the required "network unable to confirm new units" / "node disagreement on validity" outcome category.

### Likelihood Explanation
Likelihood is moderate: the trigger requires crafting a specific `authors` array (two authors resolving to the same address/definition_chash pair) combined with a second unit that references that address inside an `['address', ...]` condition before a stable definition exists in storage — both fully within the capability of any unit poster, no privileged access needed. I was not able to fully verify from the available index whether an upstream check already forbids two authors from sharing the same address in a single unit (no explicit "duplicate address in authors" validator was found in the reachable code), which is the main open uncertainty for exploitability; this should be confirmed against the full `validation.js` author-array validation logic before treating this as a confirmed 0-day.

### Recommendation
Wrap the `arrDefiningAuthors.length > 1` branch (and the `objectHash.getChash160` calls it depends on) in both occurrences in `definition.js` in a `try/catch` that routes to the existing error callback (`cb(...)`/`cb2(false)`) instead of `throw`, and additionally validate at the unit-author level that `authors` cannot contain duplicate addresses (independent of definition content) so this state can never legitimately arise.

### Proof of Concept
Conceptual PoC (requires confirming author-array duplicate-address validation does not already block it):
1. Author a unit `U1` whose `authors` array contains two entries with the same `address` field `A`, each carrying an inline `definition` such that `objectHash.getChash160(definition)` is identical for both (e.g., identical definitions or definitions colliding on chash), and where `A` has no definition yet in storage.
2. Author/post a second unit `U2` (or reuse the address condition inside `U1` itself, e.g. an asset condition or nested address definition) that contains `['address', 'A']` and is validated while `A`'s definition is not yet found in storage, forcing the `ifDefinitionNotFound` branch in `definition.js:284-301` / `definition.js:783-797` to run and hit `arrDefiningAuthors.length > 1`.
3. Observe the validating node throw an uncaught `Error("more than 1 address definition")`, crashing the process instead of returning a validation error. [3](#0-2) [4](#0-3)
