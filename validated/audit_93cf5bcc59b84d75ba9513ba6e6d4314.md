### Title
Unhandled `throw Error` on zero-share TPS fee recipient can abort unit validation instead of gracefully rejecting the unit - (File: validation.js)

### Summary
`validateTpsFee()` in `validation.js` computes a per-recipient `share` from `earned_headers_commission_recipients` and uses it as a divisor. Instead of returning a normal validation-failure via `callback(...)` when the divisor would be invalid, the code `throw`s a raw `Error` from inside an `async function`, breaking the callback-based error-handling convention used everywhere else in the validation pipeline.

### Finding Description
`validateTpsFee` is invoked for every incoming unit once the network is past `constants.v4UpgradeMci`, i.e. for units posted by ordinary, unprivileged users: [1](#0-0) 

It derives `recipients` from the unit's own `earned_headers_commission_recipients` field (attacker/user controlled) and then, for each recipient, computes `share = recipients[address] / 100` and immediately uses it as a divisor for `tps_fees_balance / share`: [2](#0-1) 

The explicit guard `if (!share) throw Error(...)` shows the authors anticipated that `share` could be `0` (this is corroborated by the composer's comment "for backward compatibility with the old buggy getTpsFeeRecipients", indicating recipient shares of `0` are a real, previously-occurring case): [3](#0-2) 

The same divide-by-share pattern, with the same lack of a `try/catch`-safe validation-failure path, also appears in `storage.getPaidTpsFee`: [4](#0-3) 

Rather than calling `callback("invalid share...")`, which is how every other validation failure in this function is signaled (e.g. line 1089, 1093), a `0` (or otherwise falsy) share causes a JavaScript exception to be thrown from within an `async function`. Unlike the rest of `validateTpsFee`, which propagates rejection results through the `callback` parameter that the rest of `validation.js`'s pipeline (and ultimately `write.js`/network code) expects, a thrown exception here becomes an unhandled promise rejection unless every caller in the chain specifically awaits and wraps this call in `try/catch`. This is architecturally identical to the GoGoPool class of bug: an edge-case divisor value (zero) that is reachable from ordinary user input is not handled through the code's normal graceful-rejection path, but instead causes an abrupt failure that can propagate uncontrolled instead of simply rejecting the single offending unit.

### Impact Explanation
If the thrown exception is not caught synchronously by the caller of `validateTpsFee` (this depends on how `validation.js`'s calling code awaits/wraps this particular async step, which was not fully visible in the retrieved code), the unhandled rejection can crash the node process validating the unit, or otherwise leave validation of that unit and subsequent units in an inconsistent state. This can manifest as a node being unable to validate/confirm new units, and if different nodes handle the resulting unhandled rejection differently (e.g. based on Node.js version/`--unhandled-rejections` mode), it can cause honest nodes to diverge on whether a given unit is accepted, which maps to the "node disagreement on validity or stability" / "network unable to confirm new units" impact classes.

### Likelihood Explanation
Reaching this code path only requires posting a normal unit with an `earned_headers_commission_recipients` field whose resulting recipient share is `0` (e.g. an author declares `earned_headers_commission_share: 0` for one address while giving the rest to another). This is fully reachable by any unprivileged unit poster and does not require any special role, matching the report's "single posted unit" reachability requirement. Whether the base unit-schema validation for `earned_headers_commission_recipients` currently rejects a `0` share value before reaching `validateTpsFee` could not be fully confirmed from the retrieved code, so the exact likelihood (whether a `0`-share unit can pass earlier field-level checks) remains uncertain and should be verified directly against the full `validation.js` recipient-share validation logic.

### Recommendation
Replace the `throw Error(...)` in `validateTpsFee` (and the analogous unguarded division in `storage.getPaidTpsFee`) with the same graceful-rejection convention used elsewhere in the function: return `callback("invalid share for address ...")` instead of throwing, and audit the caller chain to ensure this async step cannot produce an unhandled promise rejection. Additionally, confirm that unit-level validation for `earned_headers_commission_recipients` rejects non-positive `earned_headers_commission_share` values before this code is reached, so that the divisor can never legitimately be zero.

### Proof of Concept
Not independently confirmed in this review; would require crafting and submitting a unit with `earned_headers_commission_recipients` producing a `0` share for at least one recipient address and observing whether `validateTpsFee` throws an uncaught exception rather than invoking `callback` with a validation error, and whether that exception propagates as an unhandled rejection in the process handling unit validation.
