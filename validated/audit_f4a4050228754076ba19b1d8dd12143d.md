### Title
Webhook signature verification uses attacker-controlled `repository.owner.login` to select the GitHub App secret, decoupled from `repository.full_name` used by handlers - cross-organization webhook forgery in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate an incoming webhook's HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body. The handlers that actually act on the payload (e.g. `PushHandler`, `Repository.from_github_repo_name`) instead resolve the target repository from a completely different, independently attacker-controlled field: `repository.full_name`. Because HMAC verification only proves the payload was signed with *some* known-to-Shipit secret—not that the secret's organization matches the object the payload claims to modify—an attacker who knows (or is issued) the webhook secret for one configured GitHub organization can forge a validly-signed webhook that targets a stack/repository belonging to a *different* configured organization.

### Finding Description
`verify_signature` picks the signing secret using data taken from the raw, not-yet-verified body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization app config (including `webhook_secret`) using exactly this attacker-supplied `organization` string: [3](#0-2) 

This "Using Multiple GitHub Applications" mode, where each org has its own distinct `webhook_secret`, is a documented, supported configuration: [4](#0-3) 

Meanwhile, `Webhooks::Handlers::Handler` (the base class for `PushHandler`, `StatusHandler`, etc.) resolves the actual repository/stack that is mutated using a separate JSON field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

**The broken equality:** the engine implicitly assumes
`organization whose secret authenticated the request == organization that owns the repository the handler writes to`.
Nothing enforces this. Both `repository.owner.login` and `repository.full_name` live inside the same attacker-supplied JSON body and can be set independently of each other (e.g. `owner.login = "OrgTwo"`, `full_name = "OrgOne/target-repo"`). Since HMAC-SHA1 covers the raw body as a whole, the signature check only proves "this exact byte string was signed with OrgTwo's secret" — it says nothing about internal consistency between the `owner.login` field used for key-selection and the `full_name` field used for authorization/routing. An attacker holding *any one* configured organization's `webhook_secret` can therefore forge webhooks (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) claiming to originate from any repository in *any other* configured organization, because the controller never re-validates that `full_name`'s owner matches `owner.login`.

This is analogous to the audited `TokensFarm._removeParticipant()` bug class in spirit only insofar as both stem from an implicit invariant that is never explicitly checked/enforced by the code — here the invariant is "the field used to select the verification key must match the field used to authorize the write," and it silently doesn't hold.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. Concretely, in a multi-org Shipit instance:
- An attacker can trigger `GithubSyncJob`/`sync_github` for a stack in an organization whose secret they don't hold, causing unwanted resync/deploy-trigger behavior against a foreign org's stack (`push` event → `PushHandler#process` → `stack.sync_github`).
- Attacker-controlled `status`/`check_suite`/`pull_request` events can inject fabricated CI status, commit statuses, or pull-request metadata into a foreign organization's stacks, which can influence deploy-eligibility checks (`ci.require`), potentially enabling an unauthorized deploy for a repository the attacker's known webhook secret does not belong to.
- This is a cross-organization write achieved purely from having valid credentials for one configured org — a real authentication-boundary violation.

Whether this rises to "Critical" (cross-repository writes / unauthorized deploy) depends on which specific webhook events' handlers can be abused to actually flip deploy-relevant state; `push`→sync and `status`→commit status manipulation are directly reachable and documented above.

### Likelihood Explanation
This only manifests when a Shipit instance is configured with the multi-organization `github:` schema (multiple orgs, each with distinct `webhook_secret`) as documented in `docs/setup.md`. Single-org deployments (the default/most common case) are not affected because there's only one secret regardless of the `organization` value used to select it. So exploitability is conditioned on that deployment topology — a legitimate, documented, but non-default configuration.

### Recommendation
After computing `verified` in `verify_signature`, additionally re-derive the "owning organization" from the same field(s) the handlers will use (`repository.full_name` / `organization.login` used for routing) and assert they match the `repository_owner` used to select the verification secret. Reject (422) if they diverge. Alternatively, verify the signature against *all* configured organizations' secrets and require that the winning organization also match the owner encoded in `full_name` before dispatching to handlers.

### Proof of Concept
Conceptual (requires a multi-org Shipit config with `OrgOne` and `OrgTwo`, each with a distinct `webhook_secret`, and an attacker who has obtained/knows `OrgTwo`'s `webhook_secret`, e.g. by being a legitimate maintainer with webhook access on an OrgTwo repo):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(body, OrgTwo_webhook_secret)>

{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "OrgTwo" },      // used only to pick the verification secret
    "full_name": "OrgOne/target-repo"     // used by PushHandler/Repository.from_github_repo_name
  }
}
```
`verify_signature` computes `repository_owner = "OrgTwo"`, fetches `OrgTwo`'s `webhook_secret`, and successfully verifies the signature (since the attacker signed with that exact secret). The request passes, and `PushHandler#process` is then invoked with `repository.full_name = "OrgOne/target-repo"`, causing `Repository.from_github_repo_name("orgone/target-repo")` to resolve and `sync_github` to fire against a stack in `OrgOne` — an organization for which the attacker never proved knowledge of any secret.       github_app = Shipit.github(organization: repository_owner)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
