### Title
Malicious Recipient Fallback Permanently Blocks Bridge Operators from Delivering KAIA and Locks Bridged Assets — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`BridgeTransferKLAY.handleKLAYTransfer` sends KAIA to a user-controlled `_to` address using an unlimited-gas `.call.value()`. If `_to` is a contract whose fallback always reverts (or exhausts gas), every operator attempt to settle that bridge nonce fails. Because the `require(ok, ...)` causes the entire transaction to revert, all nonce-state updates are also rolled back, so the nonce can never be marked as handled. The user's KAIA is permanently locked in (or burned from) the source-chain bridge, and `lowerHandleNonce` is stuck, degrading the bridge's recovery accounting.

---

### Finding Description

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` follows this sequence:

1. Nonce and vote checks (`_lowerHandleNonceCheck`, `_voteValueTransfer`)
2. State updates: `_setHandledRequestTxHash`, `handleNoncesToBlockNums[nonce]`, `_updateHandleNonce`
3. Event emission
4. **Native KAIA transfer to `_to` with unlimited gas**
5. `require(ok, "handleKLAYTransfer: transfer failed")` [1](#0-0) 

Because step 5 is a hard `require`, any revert from `_to`'s fallback causes the entire transaction to revert, undoing all state changes from steps 1–3. The vote (`closedValueTransferVotes[_requestedNonce]`) is reset to `false`, `handledRequestTx[_requestTxHash]` is reset to `false`, and `handleNoncesToBlockNums[_requestedNonce]` is reset to `0`. [2](#0-1) 

The `_to` address is freely chosen by the user on the source chain when calling `requestKLAYTransfer` or the fallback function: [3](#0-2) 

There is no admin escape hatch to skip or force-settle a stuck nonce. The `_updateHandleNonce` loop advances `lowerHandleNonce` only through consecutive entries where `handleNoncesToBlockNums[i] > 0`; a permanently unhandled nonce freezes that pointer: [4](#0-3) 

A secondary surface exists in `_payKLAYFeeAndRefundChange`, which also uses unlimited-gas `.call.value()` to `msg.sender` and `feeReceiver`, with hard `require(ok, ...)` guards: [5](#0-4) 

However, in `_requestKLAYTransfer` the caller is `msg.sender` themselves, so the refund-path revert is self-harm. The `feeReceiver` is owner-controlled, making that path an operator misconfiguration rather than a user exploit.

---

### Impact Explanation

- **Permanent loss of bridged KAIA**: The user's KAIA is locked in the destination bridge (or burned on the source chain in `modeMintBurn` mode) and can never be delivered. No recovery path exists in the contract.
- **Bridge nonce stuck**: `lowerHandleNonce` cannot advance past the stuck nonce. The `recoveryBlockNumber` also freezes, degrading the bridge's event-recovery mechanism for all future transfers.
- **Operator gas drain**: Every retry by every operator wastes gas with no possibility of success.

This satisfies the allowed impact gate: *unauthorized loss of bridged assets* and *bridge privilege escalation that changes protected chain state*.

---

### Likelihood Explanation

Any user who initiates a KLAY bridge transfer can set `_to` to a contract they control. Deploying a contract with a reverting `receive()`/fallback is trivial. The attacker loses only the bridged KAIA (which they may consider acceptable to grief the bridge or a specific counterparty). No special privilege is required beyond being a normal bridge user.

---

### Recommendation

1. **Cap gas on the KAIA transfer** to prevent gas-exhaustion griefing:
   ```solidity
   (bool ok, ) = _to.call{value: _value, gas: 2300}("");
   ```
2. **Decouple state update from delivery**: Mark the nonce as handled before attempting the transfer, and if the transfer fails, store the amount in a pull-payment mapping so the recipient can claim it later (pull-over-push pattern). This prevents a reverting fallback from rolling back the nonce state.
3. **Add an admin skip/rescue function** that allows the bridge owner to mark a nonce as permanently failed and release the stuck funds to an alternate address, preventing `lowerHandleNonce` from being frozen indefinitely.

---

### Proof of Concept

1. Deploy a malicious contract `MaliciousReceiver` on the destination chain:
   ```solidity
   contract MaliciousReceiver {
       receive() external payable { revert("blocked"); }
   }
   ```
2. On the source chain, call `requestKLAYTransfer(address(maliciousReceiver), value, "")` with sufficient KAIA. This locks/burns KAIA and emits `RequestValueTransfer` with `_to = address(maliciousReceiver)`.
3. Bridge operators observe the event and call `handleKLAYTransfer(..., address(maliciousReceiver), value, nonce, ...)` on the destination bridge.
4. The call reaches line 98: `(bool ok, ) = _to.call.value(_value)("")` — `MaliciousReceiver.receive()` reverts.
5. `require(ok, ...)` causes the entire transaction to revert. All state (vote, nonce, tx hash) is rolled back.
6. Operators retry indefinitely; every attempt reverts. `lowerHandleNonce` never advances past `nonce`. The user's KAIA is permanently undeliverable. [6](#0-5) [7](#0-6)
