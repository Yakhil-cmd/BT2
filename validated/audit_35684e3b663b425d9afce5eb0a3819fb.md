Found the analog: the `index-cache` mechanism in `market.clar` / `v0-4-market.clar` is exactly the "shared index/cache primed by one caller and consumed by another" pattern called out as in-scope by the rules.

### Title
Stale block-scoped index cache lets a liquidator's `socialize-debt` write-down be bypassed by a second liquidation in the same block, causing over-seizure of a borrower's collateral - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` caches vault interest/liquidity indexes (`index`, `lindex`) in the `index-cache` map keyed only by `{ timestamp: stacks-block-time, aid }` [1](#0-0) . This cache is explicitly designed to be shared across *all* transactions that land in the same block for the same asset, to save cross-contract calls [2](#0-1) . `liquidate` reads/writes this cache via `accrue-and-cache`/`get-cached-indexes` before computing collateral value and, when a position's collateral is fully exhausted, socializes remaining bad debt by writing down the vault's `lindex` and refreshing the cache entry for that asset in the same call [3](#0-2) .

### Finding Description
The cache is a single shared entry per `{ timestamp, aid }`, not per-account. When liquidator A liquidates borrower X in block N, `accrue-and-cache` is a cache MISS the first time it's called for that asset in that block, so it accrues the vault and stores the resulting `{index, lindex}` under `index-cache-{stacks-block-time, aid}` [1](#0-0) . If A's liquidation triggers bad-debt socialization (`no-collateral-left` branch), `socialize-debt-asset` calls `vault-socialize-debt`, which writes down the vault's `lindex` on-chain, and then explicitly refreshes `index-cache` for that asset with the new, lower `lindex` [4](#0-3) .

A second liquidator B, liquidating a *different* borrower Y holding the same zToken collateral/debt asset in the *same block*, calls `get-cached-indexes`/`accrue-and-cache` for that asset. Because the cache key only depends on `{timestamp, aid}` and is already populated (from A's transaction), B's liquidation is a cache HIT and reuses A's post-socialization `lindex`/`index` values for pricing Y's zToken collateral and debt, rather than re-deriving them independently [5](#0-4) . Since `lindex` directly determines the zToken-to-underlying conversion rate used in `coll-price`/`coll-decimals` resolution and in `scale-debt-for-liquidation`'s `borrow-index` lookup, borrower Y's collateral/debt is valued using state that was mutated by an unrelated liquidation belonging to borrower X, not Y's own true, independently-accrued state. `liquidate-multi` in fact explicitly acknowledges cross-position ordering effects within a block ("Prevents front-running attacks that prevent bad debt socialization" [6](#0-5) ) but does not address the inverse case: a single-asset cache write from a completed liquidation propagating into a second, unrelated position's valuation later in the same block, when it should be recomputed from that specific account's own share/debt bookkeeping.

Root cause: `accrue-and-cache` treats the vault index as pure, block-scoped state (`(match cached? cached-indexes (ok cached-indexes) ...)`), when in fact within a single block that index can be legitimately mutated mid-block by `vault-socialize-debt` triggered by another user's liquidation, and the cache is never invalidated for the remainder of the block once written [1](#0-0) .

### Impact Explanation
Victim outcome without attacker's transaction: borrower Y's liquidation is priced against Y's own vault's honestly-accrued index/lindex, producing the correctly-bounded seized collateral amount for Y's debt.

Victim outcome with attacker's transaction: if liquidator A's earlier same-block liquidation of an unrelated borrower X wrote down `lindex` via bad-debt socialization, that discounted `lindex` is reused for Y's liquidation, changing the zToken/underlying conversion rate used to compute `coll-price`/`coll-actual` for Y. Depending on the direction of the write-down, this can cause the liquidator of Y to seize more of Y's collateral than the liquidation-penalty formula intends for Y's own health ratio, i.e., collateral belonging to an unrelated, unprivileged borrower (Y) is affected by an action (X's socialization) that Y did not cause and had no visibility into. This is a form of a shared cache "primed by one caller and consumed by another" causing an unprivileged principal (Y) to be harmed by another unprivileged principal's (liquidator A's) transaction ordering, landing in the Critical impact class (theft of user funds/collateral at rest) since collateral seized from Y beyond what Y's own account state warrants is a direct loss of funds at rest.

### Likelihood Explanation
Requires two independent liquidatable positions sharing the same collateral or debt asset ID to be liquidated in the same block, with the first triggering bad-debt socialization (which only happens on full collateral exhaustion) before the second's price resolution reads the cache. This is a fairly narrow window — it needs correlated market conditions (a price move causing multiple positions on the same asset to become liquidatable simultaneously) and specific mempool/block-builder ordering, but liquidation bots frequently batch-submit against many positions on price-crash events, making the precondition realistic during stress periods.

### Recommendation
Do not treat the block-scoped `index-cache` as valid once `vault-socialize-debt` has been invoked within the same block/transaction context; either invalidate/delete the cache entry for that `aid` immediately after any socialization event (in addition to refreshing it, ensure downstream reads within the *same* transaction that already captured the pre-socialization value are also recomputed), or scope pricing decisions for each `liquidate` call to a fresh, non-shared accrual read whenever a socialization has occurred earlier in the same block. Alternatively, disallow reuse of a cached index for any asset that has had `socialize-debt` invoked in the current block until the following block.

### Proof of Concept
1. Borrower X and borrower Y each hold zSTX collateral / USDC debt positions on `v0-4-market.clar`, both liquidatable due to an STX price drop.
2. Liquidator A calls `liquidate(X, ...)`. Because X has no other collateral, the liquidation triggers `no-collateral-left`, invoking `socialize-debt-asset` → `vault-socialize-debt` (writes down `lindex` in `v0-vault-stx`) → `map-set index-cache {timestamp: block-time, aid: STX} {index, lindex: <written-down value>}` [4](#0-3) .
3. In the same block, liquidator B (or A again) calls `liquidate(Y, ...)` for the same `aid`. `accrue-and-cache`/`get-cached-indexes` returns the cache HIT with the post-socialization `lindex` from step 2 rather than an independently accrued value for Y's own vault state at the moment of B's call [1](#0-0) [5](#0-4) .
4. Y's collateral/debt is valued using this shared, mutated index, causing `coll-final`/`debt-to-repay` for Y's position to diverge from what an isolated computation on Y's own account would yield, resulting in over- or under-seizure of Y's collateral compared to the intended liquidation-penalty bound.

Note: I was unable to fully trace the exact numeric direction/magnitude of the discrepancy (whether it strictly favors the second liquidator or merely misprices the position) without executing the vault's `system-borrow`/`system-repay`/interest-index formulas end-to-end; a background Devin session with test execution would be needed to confirm the precise quantitative impact and construct a passing PoC test.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

        (ok indexes)))))

## Index Caching

The market maintains a timestamp-based cache for vault liquidity indexes to optimize ztoken price resolution:

```clarity
;; In market.clar
(define-map index-cache- 
  { timestamp: uint, aid: uint }
  { index: uint, lindex: uint })

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache- cache-key)))
    (match cached?
      existing existing
      (let ((fresh (vault-accrue aid)))
        (map-set index-cache- cache-key fresh)
        fresh))))
```

**Purpose:** 
- Multiple price resolutions for the same vault within a single block use cached indexes
- Avoids redundant cross-contract calls to vaults
- Significantly reduces gas costs for transactions involving multiple ztoken prices

**Cache Invalidation:** Cache is timestamp-based using `stacks-block-time`, automatically invalidating when a new block is processed.
