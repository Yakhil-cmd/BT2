### Title
Cross-repository `Stack#enable_ci!` mutation via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits globally by SHA (`Commit.where(sha: params.sha)`) with no repository/stack scoping, unlike the base `Handler#stacks` helper which correctly scopes by `payload.dig('repository', 'full_name')`. Since the `commits` table only enforces uniqueness on `(sha, stack_id)`, an attacker who owns a repository (e.g. a fork sharing commit history with a victim's tracked repo) can emit a legitimately-signed `status` webhook from their own repo that matches a SHA also present on a victim `Stack`, causing `Status.create!` on the victim's `Commit`, which triggers `after_create :enable_ci_on_stack` → `commit.stack.enable_ci!` on the victim `Stack`.

### Finding Description
The binding the code should enforce is: `status.stack_id == stack_owned_by(payload['repository']['full_name'])`. In reality the code enforces only: `commit.sha == params.sha`, with `commit.stack_id` taken from whichever pre-existing `Commit` row matches that SHA — independent of which repository authenticated the webhook.

Path: `WebhooksController#create` → `Shipit::Webhooks.for_event('status')` → `StatusHandler#process`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This contrasts with the base `Handler` class, which provides a `stacks` helper explicitly scoped to `repository_name` derived from the payload — a pattern other handlers use but `StatusHandler` bypasses entirely: [3](#0-2) 

`Commit#create_status_from_github!` then uses the found commit's own `stack_id` (the victim's), not any stack derived from the incoming payload: [4](#0-3) 

`Status.create!` fires `after_create :enable_ci_on_stack`, which mutates `commit.stack` — the victim's stack — as a side effect: [5](#0-4) 

`Stack#enable_ci!` writes to the stack's CI-enabled cache key, changing `ci_enabled?`/CI-derived behavior for that stack (e.g. `deployable?` depends on `stack.ignore_ci?`, and other logic gates on CI having ever been observed): [6](#0-5) [7](#0-6) 

**Why existing guards don't stop this:** `verify_signature` in `WebhooksController` only validates that the payload's signature matches the `Shipit.github(organization: repository_owner)` app credentials for the *attacker's own* organization (derived from `payload['repository']['owner']['login']`), which is expected to succeed since it's the attacker's own repo/installation making a legitimate webhook call: [8](#0-7) 
This guard authenticates *who sent the request*, not *which Commit/Stack rows the request is allowed to mutate*. `StatusHandler` never checks that the found `Commit`'s `stack.repository` matches `payload['repository']['full_name']`, so the cross-tenant binding is never enforced.

**Precondition for exploitation:** a `Commit` row with the identical SHA must already exist under the victim's `Stack` (e.g., attacker forks the tracked repo, which shares full git history including SHAs, and Shipit has previously synced/ingested that commit into the victim stack's `commits` table via `GithubSyncJob`/branch sync). This is a realistic and attacker-controllable precondition for any public repo with a fork-friendly history, since git SHAs are content-addressed and identical across fork and upstream until diverged.

### Impact Explanation
An attacker with no privileges on the victim's Shipit stack, repository, or organization — only ownership of a separate (e.g. forked) repository with its own legitimate webhook installation — can inject a `Status` row and flip `Stack#enable_ci!`/`ci_enabled?` state on a victim's `Stack` purely by sending a webhook their own repo naturally emits. This is a cross-repository write mutating another tenant's `Stack` configuration state, matching the "payload for one repository mutating another's stack/commit" Critical impact category. It is repeatable against any victim stack that shares commit SHAs with an attacker-controlled repo (any public fork), and the blast radius extends to any multi-tenant Shipit deployment tracking forkable repositories.

### Likelihood Explanation
Preconditions: (1) attacker owns/controls a repository with its own legitimate webhook/App installation pointed at the Shipit host (a normal SaaS/multi-tenant setup), (2) that repository shares at least one commit SHA with a `Commit` row already present under a victim `Stack` (trivial via forking a public tracked repo before or after Shipit ingests it). No secrets, sessions, or privileged roles are required — the attacker only sends a normal `status` webhook from a repo they own. This is highly feasible and fully repeatable per matching SHA.

### Recommendation
Scope `StatusHandler#process` (and `Commit.create_status_from_github!`/`refresh_statuses!` call sites reachable from webhooks) to only touch commits belonging to stacks whose `repository.full_name` matches `payload.dig('repository', 'full_name')`, mirroring the `Handler#stacks` helper, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
Apply the same scoping to any other unscoped-by-repository lookups keyed only by `sha` (e.g. check-run/commit-status handlers).

### Proof of Concept
```ruby

test "status webhook from an unrelated repository cannot mutate a victim stack via shared SHA" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:cyclimse) # different repository/org
  shared_sha = 'deadbeef' * 5

  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  Rails.cache.delete(victim_stack.ci_enabled_cache_key)
  refute_predicate victim_stack.reload, :ci_enabled?

  # Simulate an attacker-owned Commit row with the same sha existing under attacker's own stack
  attacker_stack.commits.create!(sha: shared_sha, ...)

  payload = ExplicitParameters::Parameters.define { }.parse!(
    'sha' => shared_sha, 'state' => 'success',
    'repository' => { 'full_name' => attacker_stack.repository.full_name }
  )

  assert_no_changes -> { victim_stack.reload.ci_enabled? } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload_hash)
  end
end
```
The equality to assert on both sides: before, `victim_stack.ci_enabled? == false`; after a status webhook authenticated only for `attacker_stack.repository`, it must remain `false` (currently it flips to `true`, proving the binding `status.stack_id == stack_owned_by(payload.repository)` is violated).
