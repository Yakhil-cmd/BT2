### Title
CCMenu tokens are never scoped to a stack, so a `read:stack` token authorizes reading every stack via `Api::TasksController`/`Api::StacksController` - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#client` mints an `ApiClient` with `permissions: %w[read:stack]` but never sets the `stack` association, leaving `stack_id` `nil`. Because `Api::BaseController#stacks` only restricts the visible stack set when `current_api_client.stack_id?` is true, a CCMenu token with `stack_id` nil resolves to `Stack.all`, so the token authorizes reading tasks/commits for every stack in the instance, not just the one the CCMenu URL was generated for.

### Finding Description
The claimed binding is: `authorized_stacks(token) == { stack_for_which_ccmenu_url_was_generated }`. Tracing the code shows this is false; the actual binding is `authorized_stacks(token) == Stack.all`.

- `CCMenuUrlController#client` creates the token: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` [1](#0-0)  — note `stack:` is not part of either `create_with` or `find_or_create_by!`, so the created/found record's `stack_id` column is left `nil`. Also, because the lookup key is only `creator` + fixed `name: 'CCMenu Client'`, a second call for a *different* stack by the same user reuses the exact same `ApiClient` record/token (`find_or_create_by!` matches on creator+name only).
- `Shipit::ApiClient#check_permissions!` only checks the permission string `"#{operation}:#{scope}"` against the stored `permissions` array; it carries no notion of which stack is allowed [2](#0-1) .
- Stack scoping is supposed to happen in `Api::BaseController#stacks`: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [3](#0-2) . Since the CCMenu-minted client's `stack_id` is `nil`, this always evaluates to `Stack.all`.
- `Api::TasksController` and `Api::StacksController` both call `require_permission :read, :stack` and then resolve records through `stacks.from_param!(...)` or `stack.tasks` [4](#0-3) [5](#0-4) . Both rely on the `stacks` helper for scoping, which is unscoped for this token.

Attacker flow: an authenticated Shipit user (any user who can click "CCMenu URL" for a stack — not a privileged action) fetches `GET /stacks/:owner/:repo/:branch/ccmenu_url` for one stack, obtaining a bearer token intended only for CI-status XML of that stack. That same token, sent as HTTP Basic auth to `GET /api/stacks` or `GET /api/stacks/:owner/:repo/:branch/tasks`, passes `authenticate_api_client` and `require_permission :read, :stack` for *any* stack because `check_permissions!` never inspects `stack_id`, and `stacks` falls back to `Stack.all` when `stack_id` is `nil`.

None of the existing guards catch this: `require_permission!` only forwards to `check_permissions!`, which has no stack dimension; `stacks` is the only place stack-scoping would be enforced, and it is bypassed by the `nil` `stack_id`; there is no model validation forcing CCMenu-created `ApiClient` records to carry a `stack_id`.

### Impact Explanation
An attacker with legitimate low-privilege access to trigger the CCMenu URL feature for one stack (which any user permitted to view that stack can do) obtains a bearer token that, when replayed against `Api::TasksController#index/#show` or `Api::StacksController#index/#show`, discloses task lists, task details, and stack metadata for **every** stack in the Shipit instance — including stacks belonging to repositories the attacker has no relationship to. This is repeatable indefinitely (the token doesn't expire) and constitutes unauthenticated (from the target stack's perspective) read of stack state and task data across tenants — matching the High severity category "unauthenticated read of stack state, task streams or deploy output" and arguably escalates further since `Api::TasksController#trigger`/`#abort` require `deploy:stack`, which this token lacks, limiting it to read-only disclosure.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to be a Shipit user able to access the CCMenu URL feature for at least one stack (a routine, low-privilege UI action), then reuse the resulting token against unrelated API endpoints. No secrets, GitHub credentials, or elevated roles are required. The behavior is deterministic and always reproducible because `stack_id` is never populated by `CCMenuUrlController#client` for any stack.

### Recommendation
Set the `stack` association explicitly when creating/finding the CCMenu `ApiClient`, e.g. scope both the lookup and creation by stack: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')`, and additionally enforce in `check_permissions!`/`require_permission!` that when `stack_id` is present it must match the requested stack (defense in depth), so a stack-scoped token can never resolve to `Stack.all`.

### Proof of Concept
Add a minitest to `test/controllers/api/tasks_controller_test.rb` (or a new test file) exercising the real controller stack:
1. Create two stacks, `stack_a` and `stack_b`, owned by different repositories.
2. As `current_user`, hit `CCMenuUrlController#fetch` with `stack_id: stack_a.to_param`; capture the returned token from the JSON response.
3. Assert `ApiClient.last.stack_id` — expected (per the claimed binding) to equal `stack_a.id`; actual: `nil`.
4. Using that token as HTTP Basic auth, send `GET /api/stacks/:owner_b/:repo_b/:branch_b/tasks` (i.e., `Api::TasksController#index` for `stack_b`).
5. Assert expected behavior: `assert_response :forbidden` (token should not authorize `stack_b`).
6. Actual behavior observed: `assert_response :ok` and the response body contains `stack_b`'s tasks, proving the divergence between the claimed binding (token authorizes only `stack_a`) and the real binding (token authorizes `Stack.all`).
