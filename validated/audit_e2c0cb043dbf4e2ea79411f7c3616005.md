### Title
`StatusHandler#process` resolves target `Commit` rows by raw `sha` only, with no `Repository`/stack scope, allowing a genuinely-signed status webhook for one repository to mutate `Commit`/`Status` state belonging to a different stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Every other `Handler` subclass (`LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `ClosedHandler`, etc.) derives its target scope from `Repository.from_github_repo_name(payload/params.repository.full_name)` before touching any record. `StatusHandler#process` is the sole exception: it queries `Commit.where(sha: params.sha)` directly and calls `commit.create_status_from_github!(params)` on every match, regardless of which repository the webhook's `repository.full_name` field names. Because `sha` is not globally unique to one Shipit stack (multiple stacks legitimately track the same repository, and forks of a repository share identical commit objects/SHAs with their upstream), a validly-signed status webhook from one repository can write a `Status` row onto a `Commit` belonging to a stack that tracks a different, unrelated repository.

### Finding Description
Binding claimed broken: `repository_name` (`payload.dig('repository','full_name')`, used via `Repository.from_github_repo_name` in every sibling `Handler` subclass, e.g. `Shipit::Webhooks::Handlers::PullRequest::LabeledHandler#repository` at [1](#0-0) ) == the scope enforced inside `StatusHandler#process`.

Tracing `StatusHandler#process`: [2](#0-1) 
It never calls `Repository.from_github_repo_name`, `stacks`, or `repository_name` — those helpers exist on the base `Handler` class but are unused here: [3](#0-2) 

Comparing to `LabeledHandler`, which always resolves `repository = Repository.from_github_repo_name(params.repository.full_name)` and scopes all downstream mutation to `repository.review_stacks`/`repository`-derived data, `StatusHandler` performs zero such scoping — the right-hand side of the equality is empty. The two sides do not match: the binding is broken.

Root cause: `Commit.where(sha: params.sha)` matches every `Commit` row across every `Stack`/`Repository` sharing that SHA value. Since multiple stacks legitimately track the same repository, and forked repositories retain identical commit objects (and therefore identical SHAs) for shared ancestor history, this is not a purely theoretical collision — it is the expected/common case in git history sharing across repositories.

`verify_signature` in `WebhooksController` only checks that the payload was signed with the webhook secret configured for `repository_owner` extracted from the *submitted* payload's own `repository.owner.login`: [4](#0-3) 
This only proves the payload originated from a source holding a valid secret for that named owner — it does nothing to constrain which `Commit` rows `StatusHandler#process` is allowed to touch. It does not enforce that the `sha` referenced in the payload actually belongs to that named repository's stacks.

Exploit flow: An attacker who owns/controls a repository/fork that is itself connected to Shipit (satisfying the "repository they own" precondition) pushes or already has a commit whose SHA is shared with a commit tracked by a different, unrelated stack (e.g., a shared ancestor commit from a fork relationship). The attacker (or GitHub, driven by attacker actions such as CI status updates on their own repo/fork) triggers a genuinely-signed `status` webhook naming that shared SHA. `WebhooksController#verify_signature` passes because the signature is valid for the attacker's own repository/organization. `StatusHandler#process` then updates the `Status` for every `Commit` row with that SHA — including the one belonging to the unrelated victim stack — via `commit.create_status_from_github!(params)`, which can flip `success?`/`pending?` state and, through `add_status`, trigger `stack.schedule_merges` and continuous-delivery job scheduling (`schedule_continuous_delivery`) on the victim stack: [5](#0-4) [6](#0-5) 

### Impact Explanation
A crafted/legitimate status payload from a repository the attacker controls can write `Status` rows and toggle deployability signals (`deployable?`, `blocked?`) on `Commit` records belonging to a stack for an entirely different repository the attacker does not control, potentially unblocking or blocking a victim's continuous delivery/merge flow. This matches the "payload for one repository mutating another's stack/commit" Critical category. The blast radius spans every pair of stacks that ever share a commit SHA (any fork relationship, or shared history across repositories tracked by Shipit), and is repeatable for every subsequent shared commit.

### Likelihood Explanation
Preconditions: the attacker must control a repository already integrated with Shipit (webhook configured with a signing secret known to Shipit for that owner/org) and must be able to get a shared-SHA commit's status delivered — both plausible for anyone who forks a tracked upstream repository or who runs CI against their own connected fork. No Shipit session, API token, or GitHub secret theft is required; only ordinary GitHub repository ownership and standard status API/webhook delivery, matching the stated unprivileged attacker model.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: resolve `Repository.from_github_repo_name(params.repository.full_name)`, then restrict the `Commit` lookup to `repository.stacks` (e.g. `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))`) before calling `create_status_from_github!`, so a status payload can only mutate commits belonging to stacks of the repository named in the verified payload.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, not created here per scope, but this is the shape of the required proof):
```ruby
test "#process never scopes by Repository.from_github_repo_name and can mutate a foreign stack's commit" do
  victim_stack = shipit_stacks(:shipit)
  foreign_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, message: "shared ancestor")

  payload = {
    'sha' => foreign_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' } # not victim's repo
  }

  Shipit::Repository.expects(:from_github_repo_name).never

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert foreign_commit.reload.statuses.exists?(state: 'success'),
    "status was written to a commit whose owning stack was never validated against payload['repository']['full_name']"
end
```
This demonstrates both sides of the claimed binding: `Repository.from_github_repo_name` is never invoked (unlike `LabeledHandler#repository`), and a status payload naming an unrelated repository nonetheless mutates the victim stack's `Commit`.
