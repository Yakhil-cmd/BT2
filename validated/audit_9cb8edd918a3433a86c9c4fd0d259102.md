### Title
Asset metadata `name` is stored and displayed without sanitization, enabling asset-identity spoofing - ([File: wallet.js])

### Summary
`fetchAssetMetadata()` in `wallet.js` reads an untrusted `data` message pointed to by a hub-supplied `metadata_unit`/`registry_address` pair and persists `payload.name` verbatim into `asset_metadata.name`, which is later shown to the user everywhere an asset ticker/name is displayed (balances, payment confirmation dialogs, transaction history). No sanitization of the `name` value is performed — no length limit, no character-set restriction, no check against control characters, RTL-override characters, or homoglyphs — mirroring the CVE-2020-1340 pattern where package metadata values are not sanitized and are trusted for display, enabling spoofing of another party's identity.

### Finding Description
When a wallet needs metadata for an asset it holds, it calls `fetchAssetMetadata()`: [1](#0-0) 

The only validations performed are on `metadata_unit` (hash length), `registry_address` (valid address) and `decimals` (non-negative integer). The `name` field taken from `payload.name` is only checked for truthiness (`!payload.name`) before being written straight into the `asset_metadata` table and returned to callers: [2](#0-1) 

This `name` is subsequently combined with an optional `suffix` and surfaced to the user as the human-readable asset name/ticker throughout the wallet (`readAssetMetadata`): [3](#0-2) 

Because any address that authors the metadata unit (an "asset issuer"/registry, which is an unprivileged, self-declared role — anyone can author a `data` message with `asset` + `name` fields) can set `name` to an arbitrary string, an attacker can:
- Register metadata that copies the exact display name of a well-known/trusted asset (spoofing) since the DB uniqueness constraint is only `(name, registry_address)` — different registry addresses can register the identical `name` for a *different* asset unit.
- Embed non-printable, bidi-control, or visually confusable (homoglyph) Unicode characters in `name`, since there is no character filtering (`data_feed` values elsewhere in the codebase explicitly reject `\n` and enforce `MAX_DATA_FEED_VALUE_LENGTH`, but this asset-metadata `name`/`suffix` path has no equivalent checks — see the data-feed validation in `validation.js` for contrast). [4](#0-3) 

The `db.getIgnore()`/`REPLACE` insert logic further shows the intended data model allows multiple registries to define metadata for arbitrary assets independently, with no cross-registry name-collision defense beyond the DB unique index: [5](#0-4) 

### Impact Explanation
A malicious asset issuer can cause a victim wallet to display a spoofed asset name (identical or confusably similar to a legitimate, valuable asset's ticker) for a worthless or malicious asset that the attacker controls. A user, trusting the displayed name during a private-asset payment or multi-asset transfer flow, can be induced to send funds under the belief they are transacting the genuine asset, or to trust a counterfeit token as legitimate — a direct spoofing-driven fund-loss vector consistent with the "NuGetGallery Spoofing" analog (untrusted metadata trusted for identity display).

### Likelihood Explanation
Likelihood is moderate-to-high: any address can author the metadata `data` message and become the "registry" for an asset it controls; the wallet automatically fetches and displays this metadata for any asset that appears in the wallet's balance (including assets sent unsolicited via textcoins/private payments), requiring no explicit user opt-in to the malicious registry.

### Recommendation
- Enforce a strict allow-list character set (e.g., alphanumerics and a few punctuation marks) and a bounded length for `asset_metadata.name`/`suffix`, similar to the `MAX_DATA_FEED_NAME_LENGTH`/`\n` checks already applied to data-feed values in `validation.js`.
- Strip or reject control characters, bidi-override characters, and normalize Unicode (NFKC) before storage/display, with additional confusable-character (homoglyph) detection against already-known asset names.
- Consider surfacing the underlying `asset` unit hash or `registry_address` alongside the display name in payment-confirmation UI so users can distinguish same-named assets from different registries.

### Proof of Concept
1. Attacker creates asset `X` and issues a `data` message from address `R_attacker` with payload `{asset: X, name: "GBYTE", decimals: 9}`.
2. Attacker uses `hub/get_asset_metadata` handler (which returns whatever is stored server-side for that asset) or otherwise gets a victim node to call `fetchAssetMetadata(X, ...)`.
3. `fetchAssetMetadata` validates only hash/format of `metadata_unit`/`registry_address`, not the `name` string; it stores `name: "GBYTE"` into `asset_metadata`.
4. Victim wallet subsequently displays asset `X` balance/payment confirmation as "GBYTE", visually indistinguishable from the real GBYTE base asset display, and the user approves a payment believing it involves the trusted asset.
