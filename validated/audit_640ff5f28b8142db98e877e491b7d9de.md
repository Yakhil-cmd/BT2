### Title
Webhook signature verification is fully bypassed when `webhook_secret` is unset, allowing forged GitHub events to inject CI status and trigger deploys/merges - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for the organization derived from the incoming payload, and `WebhooksController#verify_signature` relies exclusively on this check to authenticate every inbound webhook. Because the org used to pick the secret is itself read out of the unauthenticated JSON body, and `webhook_secret` is explicitly documented and shipped as an optional/`nil`-by-default setting, an attacker can submit a completely forged webhook body that is treated as an authentic GitHub event and immediately consumed by handlers that write directly to the database (e.g. commit statuses), with no independent corroboration via the GitHub API.

### Finding Description
`WebhooksController#verify_signature` computes the "organization" purely from attacker-controlled JSON (`repository.owner.login` or `organization.login`), fetches that org's `GitHubApp`, and asks it to verify the HMAC signature: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` is the sole authentication gate, and it unconditionally returns `true` if `webhook_secret` is blank: [3](#0-2) 

`webhook_secret` is explicitly documented and templated as optional/`nil`: [4](#0-3) [5](#0-4) [6](#0-5) 

Once "verified," the raw, attacker-supplied JSON is dispatched straight to the registered handler for the `X-Github-Event` header with no further trust boundary: [7](#0-6) 

The most damaging handler is `StatusHandler`, which takes `sha`/`state`/`context`/`target_url` directly from the forged payload and persists them as a real CI status on the matching commit — without ever calling back into the GitHub API to confirm the status actually exists: [8](#0-7) 

This binding — "the organization that authenticated the webhook" versus "the payload data that is trusted and persisted" — is broken: when `webhook_secret` is unset (a supported, documented configuration), there is no authentication at all, so the binding collapses to always-true regardless of which org or payload is sent.

### Impact Explanation
A forged `status` event lets an unauthenticated attacker mark any commit's required CI context as `success`. `MergeRequest#all_status_checks_passed?` and `reject_unless_mergeable!` rely on exactly this stored `Status` data via `StatusChecker`: [9](#0-8) 

`ProcessMergeRequestsJob` merges pull requests once `all_status_checks_passed?` is true: [10](#0-9) 

and stacks with `ignore_ci: false`/CI requirements gate deploys on the same status records. This means a forged webhook can cause an **unauthorized merge** of a pull request or unblock an **unauthorized deploy**, matching the Critical impact bar defined by the rules. This is a direct analog of the reported "missing timelock/verification guarantee" bug class: just as `setPlatformFee()` had no protective delay so a single privileged call could change fee state instantly and irreversibly, here a single unauthenticated call can instantly and irreversibly (from the app's perspective) alter trusted CI/merge state that downstream automation acts on without any additional check.

### Likelihood Explanation
Likelihood depends entirely on whether the deployment leaves `webhook_secret` unset. Since this is the value shown by the project's own example configs and setup docs as an accepted "optional"/`nil` state (not a "misconfiguration" the docs warn against), it is plausible in real installs, especially early setup or where operators skip the optional field. No credentials, tokens, repository write access, or session are required to exploit it — only knowledge of a target's `/webhooks` endpoint and the target stack's repo name/branch, which are visible on the public Shipit UI.

### Recommendation
Do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank; instead:
- Require a `webhook_secret` to be configured for every GitHub App entry (fail closed, reject at boot/config-validation time if missing), or
- If a secret-less/legacy mode must be supported, gate any state-mutating consequences of unauthenticated events (in particular `status` and `push`) behind an independent GitHub API confirmation (e.g., re-fetch the commit status/check run from GitHub rather than trusting the webhook body verbatim), analogous to adding a "verification delay/second check" rather than acting on unverified input immediately.

### Proof of Concept
1. Deploy Shipit with the documented optional configuration and leave `github.webhook_secret` unset (as shown in `docs/setup.md` and `config/secrets.development.example.yml`).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: status` and a JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "<org-with-no-secret>"}}
}
```
No `X-Hub-Signature` header (or any arbitrary value) is required, since `verify_webhook_signature` returns `true` unconditionally for that org.
3. `WebhooksController#create` dispatches this straight to `StatusHandler#process`, which calls `commit.create_status_from_github!(params)`, persisting a forged `success` status for the targeted commit.
4. If that commit backs a pending pull request in the merge queue or a stack pending deploy, `ProcessMergeRequestsJob`/deploy-gating logic will treat the forged status as legitimate CI, resulting in an unauthorized merge or unblocking deploy.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
