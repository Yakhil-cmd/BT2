### Title
Stack-scoped API token bypasses stack scoping in CCMenu status endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor from `Shipit::Api::BaseController` and, in doing so, drops the stack-scoping enforcement that the base controller performs for `ApiClient`s that are restricted to a single `Stack`. This lets a token that is only authorized to read one stack fetch the CI/deploy status of any stack in the installation.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . The only place this scoping is actually enforced is `Api::BaseController#stacks`, which restricts the queryable set of stacks to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `Api::BaseController#stack` which loads the requested stack through that scoped relation: `@stack ||= stacks.from_param!(params[:stack_id])` [2](#0-1) .

Authorization itself (`require_permission :read, :stack`) only checks that the string `"read:stack"` is present in `ApiClient#permissions`, independent of which stack is targeted: `check_permissions!` just does `permissions.include?(required_permission)` [3](#0-2) . The actual per-stack restriction is entirely delegated to the `stacks`/`stack` scoping helper in the base controller.

`Api::CCMenuController`, however, redefines `stack` to bypass that helper entirely: [4](#0-3) 
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This calls `Stack.from_param!` directly (the unscoped class method) instead of `stacks.from_param!` (the api-client-scoped relation). As a result, the binding "the stack(s) a token is authorized to touch" (`current_api_client.stack_id`) is never checked against "the stack the request actually touches" (`params[:stack_id]`) in this controller.

### Impact Explanation
Any holder of a valid `ApiClient` credential with `read:stack` permission — even one deliberately created and scoped to a single stack (as the `here_come_the_walrus` fixture demonstrates, and as is exercised for scoping in `Api::StacksControllerTest` [5](#0-4) ) — can query `GET /api/:stack_id/cc_menu.xml` (or equivalent) for an arbitrary other stack ID and receive its build/deploy status (`lastBuildStatus`, `activity`, `lastBuildLabel`, `webUrl`, lock state) rendered from `app/views/shipit/ccmenu/project.xml.builder`. This is an unauthorized cross-stack read of stack/deploy state using a credential that was supposed to be confined to one stack, matching the "High — unauthenticated/unauthorized read of stack state ... via a token" class of impact.

### Likelihood Explanation
This does not require any privileged access beyond possessing an already-issued, narrowly-scoped `ApiClient` token (e.g., a CCMenu-purpose token created by a low-privilege project for its own stack). The only "attacker" action needed is supplying a different `stack_id` in the URL; no signature forgery, no additional secret, and no server misconfiguration is required — it's a direct code-path bypass of the scoping guarantee that the rest of the API deliberately enforces (`BaseController#stack`).

### Recommendation
Have `Api::CCMenuController#stack` use the scoped `stacks` relation instead of the raw `Stack` model, consistent with `Api::BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures a stack-scoped `ApiClient` cannot read status for stacks outside its `stack_id`.

### Proof of Concept
1. Create (or use console/fixture) an `ApiClient` with `permissions: ['read:stack']` and `stack: stack_a`.
2. Authenticate as that client via HTTP Basic auth using its `authentication_token`.
3. Request `GET /api/<stack_b_param>/cc_menu.xml` where `stack_b` is a different stack the client was never granted.
4. `require_permission :read, :stack` passes (permission string present), and `CCMenuController#stack` resolves `stack_b` directly via `Stack.from_param!`, bypassing the `stacks` scoping check that `Api::BaseController#stack` would have applied — the response renders `stack_b`'s CI/deploy status even though the client is scoped only to `stack_a`.
