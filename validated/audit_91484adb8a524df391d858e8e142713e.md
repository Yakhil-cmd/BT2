### Title
CCMenu API endpoint bypasses stack-scoped `ApiClient` authorization, allowing cross-stack read of deploy/build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor inherited from `BaseController` with an unscoped lookup, breaking the binding between the stack(s) an `ApiClient` token is authorized for and the stack it actually reads data from.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) , and this scoping is meant to be enforced everywhere via `BaseController#stacks`/`#stack`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Every other API controller that resolves a stack from `params` goes through this scoped `stacks`/`stack` helper (e.g. `Api::StacksController#stack` calls `stacks.from_param!(params[:id])` [3](#0-2) ).

`Api::CCMenuController`, however, redefines `stack` to bypass the scope entirely:

```ruby
def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
...
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

`require_permission :read, :stack` only checks that the client's permission list contains `read:stack` [5](#0-4) ; it never checks *which* stack the client is scoped to. Because `stack` calls `Stack.from_param!` directly instead of `stacks.from_param!`, the `current_api_client.stack_id` restriction (enforced everywhere else in the API) is never applied here.

### Impact Explanation
An `ApiClient` token created and scoped to one stack (e.g. via the `api_clients` UI, as in the `here_come_the_walrus` fixture which is scoped to the `shipit` stack) can be replayed against `GET /ccmenu/*stack_id` with an arbitrary `stack_id` belonging to a different stack. The controller will happily render that other stack's CCMenu XML — name, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl` — even though the token was never authorized (`stack_id`) for that stack. This is a cross-stack authorization bypass: the equality the engine is supposed to maintain, `token.stack_id == stack.id` (when scoped), is broken specifically in this controller, since `stack` resolves via the global `Stack` scope rather than the token-restricted `stacks` scope.

### Likelihood Explanation
Any holder of a stack-scoped API token (a routine, low-privilege credential meant to be handed out to CI dashboards/build-status widgets for a single stack) can trivially trigger this by changing the URL's `stack_id` segment — no additional exploitation complexity, no extra secret required.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped helper, e.g. `stacks.from_param!(params[:stack_id])`, so the stack-scope restriction on `current_api_client` is enforced consistently with the rest of the API surface.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to `stack_a` with permission `read:stack` (as done in `test/fixtures/shipit/api_clients.yml` for `here_come_the_walrus`, scoped to `shipit`) [6](#0-5) .
2. Request `GET /ccmenu/<stack_b_owner>/<stack_b_name>/<stack_b_env>?token=<here_come_the_walrus_token>` where `stack_b` is a different, unrelated stack.
3. `authenticate_api_client` accepts the token [7](#0-6) , `require_permission :read, :stack` passes because the client has `read:stack` in its permission list, and `stack` resolves `stack_b` unscoped [8](#0-7) , leaking `stack_b`'s build/deploy status to a client that was only ever authorized for `stack_a`.
