### Title
Type confusion in `Definition.replaceInTemplate` lets a shared-wallet co-signer inject arbitrary definition sub-trees when approving a shared/multisig address - ([File: definition.js])

### Summary
The XWiki advisory's root cause is that content supplied by a low-privilege actor (an unprivileged document editor) is later substituted into a template/sheet that is executed with elevated trust, without the substitution path re-validating the type/shape of the injected content. The structural analog in ocore is `replaceInTemplate`/`replaceInVar` in `definition.js`, which blindly substitutes `params[name]` into an address-definition template regardless of its type, and this function is called from two different contexts with two different trust models: the on-chain `'definition template'` opcode (which restricts `params` values to `string`/`number` only, [1](#0-0) ) and the peer-to-peer shared-wallet flows in `wallet_defined_by_addresses.js` / `wallet_defined_by_keys.js`, which call the same `replaceInTemplate` with attacker-influenced `params` values **without that type restriction**.

### Finding Description
`replaceInTemplate` walks the template tree and, for every string leaf beginning with `$`, replaces it with `params[name]` verbatim - including if that value is itself an object/array (a nested op sub-tree): [2](#0-1) 

When this function is reached through the on-chain `'definition template'` address-definition opcode (used when an address definition references another unit's template), validation explicitly enforces that every param value must be a `string` or `number`, precisely to prevent this substitution from injecting arbitrary op nodes into the definition tree: [3](#0-2) 

However, `replaceInTemplate` (exported as `Definition.replaceInTemplate`) is also invoked directly by the shared-address/shared-wallet device-message protocol, with `params` built from data supplied by *other, potentially malicious, paired devices/co-signers* during shared-address approval and address derivation: [4](#0-3) [5](#0-4) 

In these flows, the `params` map is built from fields (`row.address`, `device_addresses_by_relative_signing_paths`, extended pubkeys, etc.) that arrive over the device-messaging protocol from a co-signer device and are not restricted to `string`/`number` before being handed to `replaceInTemplate`, unlike the on-chain path. Because `replaceInVar`'s `object`/`array` case only recurses to look for more `$name` placeholders and otherwise assigns the substituted value as-is, a malicious co-signing device that controls one signing-path leaf of a shared-address template can supply a full op sub-tree (e.g. `['or', [...]]`) instead of a plain address string for its own leaf. The resulting address definition — which is subsequently accepted via `Definition.validateDefinition` on the *victim's own node* — could therefore end up with unintended structure (e.g., a backdoor branch, or a leaf that resolves the co-signer's own path in a way not represented to the honest party during template review), because it is the raw (attacker-supplied) definition tree, not the intended templated one, that other devices/store as the shared address's spending condition.

This mirrors the AWM bug class: content from an untrusted party is substituted into a construct that is executed/interpreted with a different (higher) trust level than the content's actual origin, and the type/shape restriction that would normally prevent this is enforced only on one of the two code paths that reach the same sink.

### Impact Explanation
If an attacker-controlled co-signer of a shared wallet can inject an arbitrary op node instead of a plain address at their leaf of the address-definition template, the resulting shared address's effective spending policy differs from what other, honest signers believe/reviewed. This can lead to:
- Unauthorized spending: the attacker's injected sub-tree could weaken the effective signature threshold or add itself as an unconditional signer for outputs from the shared address.
- Node disagreement: because the shared address (and its derived chash) is computed locally by each device from the filled-in template, a malformed/asymmetric substitution could result in honest devices deriving different addresses/definitions than intended, or accepting spending conditions that do not match what was displayed to the user for approval.

This satisfies the "unauthorized spending" / "node disagreement on validity" bar for a Medium-High severity finding, reachable purely through paired-device (co-signer) protocol messages, which is in scope per the rules (unlike node/hub/p2p-sync compromises, which are excluded).

### Likelihood Explanation
Exploitation requires the victim to have added an untrusted party as a co-signer of a shared address/wallet (a supported, user-initiated workflow, not privileged/operator access), and for that party to reply during the shared-address negotiation with a manipulated `address`/pubkey field instead of a normal address/pubkey. The client-side UI is expected to display the resulting definition for review, so real-world exploitability depends on whether a user notices a malformed definition before approving — this reduces but does not eliminate likelihood, since the underlying code path lacks the type check that would categorically prevent it (as the on-chain path does).

### Recommendation
Enforce the same restriction as the on-chain `'definition template'` opcode wherever `Definition.replaceInTemplate` is called with externally-supplied `params`: require that every `params[name]` value used for substitution be a `string` or `number` (reject object/array values) before calling `replaceInVar`, in `wallet_defined_by_addresses.js` (`approvePendingSharedAddress`, `validateAddressDefinitionTemplate`) and `wallet_defined_by_keys.js` (`deriveAddress`, `validateWalletDefinitionTemplate`). Alternatively, move this type check inside `replaceInTemplate`/`replaceInVar` itself in `definition.js` so all callers are protected uniformly, regardless of which code path invokes it.

### Proof of Concept
Not independently verified end-to-end against the live device-message handlers (their exact validation of the `address` field received from a co-signer during shared-address approval could not be fully traced within the available index — `wallet.js`'s device-message dispatch for `approve_new_shared_address`/`create_new_shared_address` was only partially inspectable). Conceptually:
1. Attacker device is invited as a co-signer to a shared address whose template contains a `$address@<attacker_device>` placeholder.
2. Instead of replying with a valid Base32 address string, the attacker's device message supplies an object/array value for its `address` field.
3. That value flows unfiltered into `params` in `approvePendingSharedAddress`, and `Definition.replaceInTemplate` substitutes it directly into the shared address's definition tree without the string/number restriction present in `definition.js`'s on-chain `'definition template'` validator.
4. The resulting `arrDefinition` (with an injected sub-tree) is hashed to produce the shared address and stored/broadcast to other co-signers via `sendNewSharedAddress`, potentially causing them to adopt spending conditions differing from those they intended to approve.

Given that the exact device-message entry point's field-level validation (in `wallet.js`) could not be fully confirmed in this pass, this should be validated with the full source before treating it as conclusively exploitable, but the missing type check inside `replaceInTemplate`'s off-chain callers is a concrete, provable root-cause discrepancy against the on-chain equivalent.

function replaceInTemplate(arrTemplate, params){
	function replaceInVar(x){
		switch (typeof x){
			case 'number':
			case 'boolean':
				return x;
			case 'string':
				// searching for pattern "$name"
				if (x.charAt(0) !== '$')
					return x;
				var name = x.substring(1);
				if (!ValidationUtils.hasOwnProperty(params, name))
					throw new NoVarException("variable "+name+" not specified, template "+JSON.stringify(arrTemplate)+", params "+JSON.stringify(params));
				return params[name]; // may change type if params[name] is not a string
			case 'object':
				if (Array.isArray(x))
					for (var i=0; i<x.length; i++)
						x[i] = replaceInVar(x[i]);
				else
					for (var key in x)
						assignField(x, key, replaceInVar(x[key]));
				return x;
			default:
				throw Error("unknown type");
		}
	}
	return replaceInVar(_.cloneDeep(arrTemplate));
}
