### Title
Donation-based balance inflation lets an unprivileged trigger sender manipulate `balance[asset]`-derived exchange rates in bonding-curve / pool-style AAs, enabling an Euler-style value-extraction attack - ([File: formula/evaluation.js], [File: aa_composer.js])

### Summary
Yield Protocol's loss stemmed from an AA-like pool contract computing its solvency/exchange accounting from a raw, unauthenticated on-chain balance that an attacker could distort (the Euler exploit corrupted Euler's internal balance/health accounting via a crafted donation-like sequence, and Yield's pool of eTokens inherited that corrupted state). The structurally equivalent primitive in ocore is the `balance[asset]` oscript operator, which reports the AA's raw ledger balance (all unspent good/stable outputs sent to the address) rather than a value reconciled against the AA's own internal accounting (`var[...]`). Any unprivileged unit poster can send bytes/assets directly to a bonding-curve/liquidity-pool AA's address in a way that increases `balance[asset]` without being recorded in the AA's internal reserve/supply state variable, corrupting the exchange-rate math used for later invest/divest calls, analogous to a donation attack.

### Finding Description
`balance[asset]` is resolved by `readBalance()` in `formula/evaluation.js`, which returns `objValidationState.assocBalances[address][asset]`, sourced from the `aa_balances` table. [1](#0-0) 
This value is populated from *any* unspent good/stable output sent to the AA's address (`updateInitialAABalances`), independent of whether the sender's unit matched any `if` condition in the AA's message cases: [2](#0-1) 

When a trigger unit doesn't satisfy any case condition in the AA definition, `handleTrigger` filters out all messages and, finding none, calls `handleSuccessfulEmptyResponseUnit(null)` — the coins are silently retained by the AA with **no response and no state update**: [3](#0-2) 

This is exactly the pattern documented (and thereby propagated to real AA authors) in the shipped Uniswap-like market-maker example, where investment/divestment math is derived directly from `balance[asset]` rather than from an internally tracked reserve variable: [4](#0-3) [5](#0-4) 

Root cause: the AA's accounting invariant (`var['mm_asset_outstanding']` representing the amount of pool shares backed by the pool's tracked reserves) can be silently decoupled from `balance[base]`/`balance[$asset]`, because:
1. Any bytes sent below the case thresholds (e.g. `trigger.output[[asset=base]] > 1e5`) match no `if` branch, so the AA retains the funds with no state change (per `aa_composer.js:1868-1877`).
2. `balance[base]`/`balance[asset]` nonetheless reflect this "donated" amount immediately, because `updateInitialAABalances` adds `trigger.outputs` to `assocBalances` unconditionally before any case evaluation (`aa_composer.js:474-490`).
3. Every subsequent `invest`, `divest`, and swap calculation reads `balance[...]` directly (not a segregated reserve var) to compute ratios/payouts: [6](#0-5) 

This lets an attacker inflate the effective share price before the first real deposit (classic first-depositor/donation-attack), or inflate `balance[$asset]`/`balance[base]` after the pool is seeded to shift the swap curve (`$p = $asset_balance * $bytes_balance`) and the divest payout formula `round($investor_share * balance[base])` in their own favor, extracting value from other LPs/investors — mirroring how Euler's/Yield's accounting became inconsistent between actual token balance and internally tracked debt/collateral state.

### Impact Explanation
This is an AA-fund-loss/value-extraction bug class: an unprivileged trigger sender can permanently and silently distort the relationship between an AA's raw ledger balance and its self-tracked share/reserve accounting variable, causing other participants (LPs/investors in a pool-style AA) to receive incorrect payouts or share allocations. Because `balance[asset]` is the officially exposed and documented mechanism for AA authors to compute exchange rates (as shown in the shipped reference sample), this design flaw can propagate to real production AAs built by the ecosystem using this exact pattern, resulting in concrete fund loss for depositors — the same fund-loss category triggered in the Yield/Euler incident (corrupted internal accounting causing loss of pooled funds).

### Likelihood Explanation
Medium: exploitation requires an AA whose author followed the documented `balance[]`-based accounting pattern (as in the shipped `uniswap_like_market_maker.oscript` sample) rather than tracking reserves purely in state vars. The attack itself only requires posting one or more ordinary payment units to the AA's address with amounts chosen to fall outside all matching `if` conditions (trivial and unprivileged), so likelihood is high once such an AA is deployed, but depends on the specific AA's use of the pattern.

### Recommendation
- Do not use raw `balance[asset]`/`balance[address][asset]` as the sole source of truth for share-price/exchange-rate math in pool-like AAs; track reserves explicitly in dedicated state variables (`var['reserve_base']`, `var['reserve_asset']`) that are updated only inside matched cases, and reconcile/ignore any balance surplus not accounted for by those variables.
- Update the reference sample `test/samples/uniswap_like_market_maker.oscript` to demonstrate reserve-variable-based accounting instead of relying on `balance[...]`, since it is used as documentation/onboarding material for AA authors.
- Consider adding a documentation warning near the `balance[]` operator definition (`formula/evaluation.js` `readBalance`) clarifying that it reflects the *raw* address balance and can be inflated by unmatched/no-op triggers, and is unsuitable for share-price accounting without reconciliation against internal state vars.

### Proof of Concept
1. Deploy an AA following the `uniswap_like_market_maker.oscript` pattern (`test/samples/uniswap_like_market_maker.oscript:1-148`) with `$asset` as a pool token.
2. Before any real investor deposits (`var['mm_asset_outstanding']` still 0/undefined), attacker sends a very small amount of `base` (below `1e5`) and/or `$asset` (amount such that none of the `if` conditions match) directly to the AA address.
3. Per `aa_composer.js:1868-1877`, no case matches, so the AA silently swallows the funds; `balance[base]`/`balance[$asset]` increase (per `aa_composer.js:474-490`), but `var['mm_asset_outstanding']` remains unset.
4. Attacker then performs the legitimate "initial deposit" branch (`uniswap_like_market_maker.oscript:38-40`, `$asset_balance == 0 OR $bytes_balance == 0`) is bypassed once *both* balances are nonzero from the donation, forcing the "invest" branch's ratio math (`uniswap_like_market_maker.oscript:42-47`) to compute `$issue_amount` using the inflated `balance[...]` denominators, letting the attacker mint a disproportionate number of pool shares for a given real deposit, or later divest (`uniswap_like_market_maker.oscript:70-101`) to redeem more of the pool's real reserves than their actual contribution — extracting value from subsequent legitimate depositors.
