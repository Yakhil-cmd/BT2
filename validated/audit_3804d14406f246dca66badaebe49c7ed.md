### Title
Attacker-chosen `arbiter_address` in an arbiter-contract offer causes the wallet to leak the victim's private contract data and permanent pairing secret to an attacker-controlled ArbStore URL - (File: arbiter_contract.js)

### Summary
When a peer proposes an arbiter-mediated contract via a `arbiter_contract_offer` device message, `store()` persists the peer-supplied `arbiter_address` without checking that it names an actual, mutually-agreed arbiter. Later wallet actions (`openDispute`, `appeal`, `getAppealFee`) resolve this attacker-chosen address through the hub's `hub/get_arbstore_url` lookup and then POST the contract's private data — including the victim's permanent pairing code (`device_pubkey@hub#pairing_secret`), asset, amount, and encrypted contract terms — to whatever URL that address' owner registers with the hub.

### Finding Description
`arbiter_contract.js` implements the "arbiter contract" flow: one wallet creates and sends an offer (`createAndSend`, `arbiter_contract.js:21-36`), the peer stores it (`store`, `arbiter_contract.js:91-116`) and can `respond` (`arbiter_contract.js:118-155`). The `arbiter_address` field in the offer is taken directly from the remote device message body with no validation that it corresponds to a well-known/trusted arbiter — it's simply written into the `wallet_arbiter_contracts` table: [1](#0-0) 

Once the contract is accepted and later disputed or appealed, the wallet resolves the arbiter's ArbStore URL by asking its own hub `hub/get_arbstore_url` for the address that was supplied by the (possibly malicious) peer: [6](#0-5) 

Because the hub returns whatever URL is registered for that address (an address the peer fully controls, since they proposed it as `arbiter_address`), the peer effectively dictates the destination host. The wallet then builds a payload containing the victim's permanent pairing code, contact info, contract amount/asset (for private assets) and an encrypted contract blob, and POSTs it to that host: [7](#0-6) 

The same pattern recurs in `appeal()` and `getAppealFee()`, both of which reuse `hub/get_arbstore_url`/`hub/get_arbstore_url_by_address` keyed on the attacker-supplied address and then call the shared `httpRequest` helper: [8](#0-7) [9](#0-8) 

Critically, the pairing code sent is generated by `getOrGeneratePermanentPairingInfo`, which reuses a single **permanent** `pairing_secret` shared across *all* of the user's correspondents/QR pairings (`is_permanent=1`, valid until 2038, and explicitly reusable by "multiple peers"): [10](#0-9) [11](#0-10) 

This is directly analogous to the wolfictl bug class: a credential (there, `GITHUB_TOKEN`; here, the wallet's permanent pairing secret plus private contract data) is transmitted to a network endpoint whose host is derived from attacker-influenced input, without any allow-listing/verification that the destination is the intended, trusted counterparty.

### Impact Explanation
An attacker who is one of the two parties to an arbiter contract (or who successfully offers such a contract to a victim through the normal `arbiter_contract_offer` flow) can set `arbiter_address` to an address they control and register a URL of their choosing for it via the hub's ArbStore lookup. When the victim later disputes, appeals, or queries the appeal fee for the contract — normal user actions triggered by the contract's own lifecycle — the wallet automatically leaks:
- The victim's **permanent pairing secret** and hub, which can be reused by the attacker to add themselves (or impersonate future pairing) to the victim's device as a correspondent.
- Private contract details: amount, asset, contact info, and contract text (double-encrypted to the "arbiter" pubkey, which is attacker-controlled anyway) — but the pairing secret leakage is the more serious cross-cutting harm since it is not scoped to this one contract.

This does not directly enable double-spend or fund theft, but it discloses a durable authentication/pairing credential to an untrusted host as a side effect of routine dispute-handling logic, matching CWE-668/CWE-552 in the referenced advisory.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to accept an arbiter contract from a counterparty who nominates themselves (or a colluding address) as arbiter, and to subsequently invoke dispute/appeal functionality — both of which are ordinary, expected user actions in the arbiter-contract feature, not privileged operations. No hub or node compromise is required; only control over one address and its ArbStore registration.

### Recommendation
- Validate that `arbiter_address` in incoming `arbiter_contract_offer`/`store()` calls is not one of the contract parties' own addresses/devices, and preferably require the arbiter to be selected from a vetted list rather than accepted blindly from peer input.
- Before sending any pairing code or private contract data to the resolved ArbStore URL, verify out-of-band (e.g., via a separate signed attestation from the arbiter, or a fixed registry) that the URL genuinely belongs to a legitimate arbiter, rather than trusting whatever the hub returns for an address chosen by the counterparty.
- Avoid reusing the single permanent pairing secret for arbiter-contract dispute correspondence; generate a contract-scoped, single-use pairing secret instead so a leak cannot be reused to pair as the victim generally.

### Proof of Concept
1. Attacker (Mallory) proposes an arbiter contract to Victim via `createAndSend`, setting `arbiter_address` to an address Mallory controls and for which Mallory registers `hub/get_arbstore_url` → `http://mallory-server.example`.
2. Victim's wallet stores the offer via `store()` with no validation of `arbiter_address` (`arbiter_contract.js:91-116`) and later accepts it via `respond()`.
3. A dispute arises; Victim calls `openDispute(hash, cb)`. The wallet resolves `hub/get_arbstore_url` for Mallory's `arbiter_address`, obtaining `http://mallory-server.example`, and POSTs `my_pairing_code` (containing Victim's permanent `pairing_secret`), `my_contact_info`, `amount`, `asset`, and the encrypted contract to `http://mallory-server.example/api/dispute/new` (`arbiter_contract.js:262-303`).
4. Mallory's server logs the request, obtaining Victim's permanent pairing secret and private contract metadata, which Mallory can replay to pair with Victim's device as a new correspondent.

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}

function requestInfoFromArbStore(url, cb){
	http.get(url, function(resp){
		var data = '';
		resp.on('data', function(chunk){
			data += chunk;
		});
		resp.on('end', function(){
			try {
				cb(null, JSON.parse(data));
			} catch(ex) {
				cb(ex);
			}
		});
	}).on("error", cb);
}

function getArbstoreInfo(arbiter_address, cb) {
	if (!cb)
		return new Promise(function(resolve, reject){
			getArbstoreInfo(arbiter_address, function(err, info){
				if (err) return reject(err);
				resolve(info);
			});
		});
	if (arbStoreInfos[arbiter_address]) return cb(null, arbStoreInfos[arbiter_address]);
	device.requestFromHub("hub/get_arbstore_url", arbiter_address, function(err, url){
		if (err) {
			return cb(err);
		}
		if (!validationUtils.isNonemptyString(url))
			return cb("invalid url received from hub");
		requestInfoFromArbStore(url+'/api/get_info', function(err, info){
			if (err)
				return cb(err);
			if (!validationUtils.isNonemptyObject(info))
				return cb("invalid info received from arbstore");
			const cut = parseFloat(info.cut);
			if (!info.address || !validationUtils.isValidAddress(info.address) || isNaN(cut) || cut < 0 || cut >= 1) {
				return cb("malformed info received from ArbStore");
			}
			info.url = url;
			arbStoreInfos[arbiter_address] = info;
			cb(null, info);
		});
	});
}
