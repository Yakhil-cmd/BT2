## Finding

### Title
CCMenu API token authorization bypasses per-stack scoping, allowing cross-stack deploy-status disclosure - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` resolver inherited from `Shipit::Api::BaseController` in a way that drops the stack-scoping check that is normally enforced for `ApiClient` tokens. As a result, a token that is supposed to be limited to a single stack can be used to read the CCMenu deploy status of *any* stack, breaking the binding "a stack the token authorises" ⟺ "the stack the code actually touches" — the exact analog of the vault-strategy bug where the amount a recipient is *authorised* to claim (`claims[recipientId][token]`) diverged from the amount actually *held/transferable* by the vault.

### Finding Description
`ApiClient` supports being scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . `Shipit::Api::BaseController` enforces this scope generically:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Every controller that inherits `stack` from `BaseController` (e.g. `DeploysController`, `StacksController`, `TasksController`) therefore honours a scoped token's `stack_id`: if the client is bound to stack A, `stack` will 404/`RecordNotFound` for any other stack, no matter what `stack_id` is passed in the URL.

`CCMenuController`, however, redefines `stack` and bypasses this scoping entirely:

```ruby
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end

  def authenticate_api_client
    @current_api_client = ApiClient.authenticate(params[:token])
    super unless @current_api_client
  end
end
``` [3](#0-2) 

`require_permission :read, :stack` only checks that the operation `read:stack` is in the token's `permissions` list [4](#0-3) ; it never checks whether the resolved `stack` matches `current_api_client.stack_id`. Since `CCMenuController#stack` calls `Stack.from_param!` directly instead of the scoped `stacks.from_param!`, any token carrying `read:stack` permission — including a token that was deliberately restricted to a single stack — can be replayed against `/api/stacks/*stack_id/ccmenu` with a *different* `stack_id` and successfully retrieve that other stack's CCMenu payload (name, activity, lastBuildStatus, lastBuildLabel, lastBuildTime, webUrl) via the route `get '/ccmenu' => 'ccmenu#show'` [5](#0-4) .

This is exactly analogous to the reported bug: the `claims` bookkeeping in `_afterAllocate()` assumed the recorded/authorised amount equalled the amount actually transferable, when a transfer fee broke that equality. Here, the code assumes "token authorises operation X on scope `:stack`" implies "token is entitled to scope X on *this specific* stack", but the `CCMenuController#stack` override severs that binding for the one endpoint that re-implements resolution instead of reusing the scoped helper.

### Impact Explanation
This crosses the "unauthenticated read of stack state ... or deploy output" High-impact category defined in the rules: a token that was minted (e.g. via `CCMenuUrlController#client`, which is `find_or_create_by!` per-user and scoped `read:stack` only [6](#0-5) ) or any manually-created `ApiClient` intentionally restricted to one stack (see fixture `here_come_the_walrus`, `stack: shipit` [7](#0-6) ) can be used to disclose deploy state for stacks it was never authorised to see, purely by changing the `stack_id` path segment.

### Likelihood Explanation
Any holder of a valid, unrevoked `read:stack`-scoped `ApiClient` token (regardless of which stack it was created for) can exploit this with a single unauthenticated (from the app's perspective, other than presenting the token) HTTP GET request — no privilege escalation, race condition or timing dependency is required.

### Recommendation
Make `CCMenuController#stack` reuse the scoped `stacks` helper from `BaseController` instead of calling `Stack.from_param!` directly, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This restores the invariant that `current_api_client.stack_id` (when present) must equal the stack the request actually touches.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to Stack A with permission `read:stack` (e.g. via `CCMenuUrlController#fetch` for Stack A, or an admin-created client with `stack: A`).
2. Note the token from the generated CCMenu URL / `authentication_token`.
3. Send `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<token>` for an unrelated Stack B.
4. Observe HTTP 200 with Stack B's CCMenu XML (`name`, `lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.), even though the token is scoped to Stack A only — while the same token used against `/api/stacks/<owner>/<repo-B>/<env-B>/` (e.g. `DeploysController#index`) correctly returns 404/empty due to `BaseController#stacks` scoping.

module Shipit
