### Title
Unhandled `throw Error` on attacker-influenced `last_ball_unit` state crashes the daemon during unit validation - (File: `validation.js`)

### Summary
CVE-2022-47516 crashes the drachtio SIP daemon because a crafted network message reaches an internal `assert()`/invariant check in `libsofia-sip-ua/tport/tport.c` that the attacker can violate, and the failed assertion aborts the whole process. The ocore analog is the internal invariant check inside `validateParents()` in `validation.js`, reached by every posted unit through `validateParents(conn, objJoint, objValidationState, cb)` [1](#0-0) , where a bad-state condition throws a raw `Error` instead of returning a normal validation error to the caller.

### Finding Description
When a joint/unit is validated, `validateParents` resolves `last_ball_unit` from the unit and looks up its stored properties: [2](#0-1) 

If the row for `last_ball_unit` has `is_stable=1` but `ball IS NULL`, the code does not return a normal validation error via `callback(...)` — it does `throw Error("last ball unit "+last_ball_unit+" is stable but has no ball")`. This throw happens inside a `conn.query` callback, deep in an `async.eachSeries`/`async.series` chain with no surrounding `try/catch`, so it is not caught by the `validate()` error-handling logic in `validation.js:445-472` (which only handles values passed via `callback(err)`), and instead propagates as an uncaught exception.

All entry points that invoke `validation.validate()` for a network-received or self-posted unit (e.g. `handleJoint` in `network.js`) do not wrap the call in a `try/catch` either [3](#0-2) , so the exception bubbles up to Node's `process.on('uncaughtException')` handler, which deliberately re-throws to kill the process: [4](#0-3) 

This is structurally identical to the CVE: a piece of state derived from external/untrusted unit content (`last_ball_unit`, which is fully attacker-chosen inside a posted unit) reaches a "should never happen" invariant check that, when violated, throws/aborts rather than gracefully rejecting the unit — killing the whole node instead of just rejecting the bad unit.

### Impact Explanation
Any full node that reaches this code path with `is_stable=1 && ball IS NULL` for the referenced `last_ball_unit` local row crashes immediately (uncaught exception → process exit via the deliberate re-throw at `network.js:4542`). Because `validate()` is invoked for every unit received from peers and every unit submitted by local composers/wallets, an attacker who can construct or trigger this specific local-DB state combination (e.g. via a stability race, or by pointing at a unit that the node itself computed as stable through its own bookkeeping but has not yet persisted a `ball` row for) can remotely crash the daemon — a network-wide denial of service if reproduced against multiple full nodes, matching "a network unable to confirm new units."

### Likelihood Explanation
This is a genuinely reachable invariant guard (it is not "if (never) throw"; it's checking a real race between the stability-advancement code path and ball computation/persistence). The comment directly above it ("it can be unstable and have a received... ball") shows the invariant is fragile and was already relaxed once. Reaching it reliably would require crafting a unit whose `last_ball_unit` lands on a locally-stable unit for which the ball row hasn't been written yet — plausible during catch-up, reorg-adjacent processing, or units racing the stabilization advance in `validateParents`/`determineIfStableInLaterUnitsAndUpdateStableMcFlag`. Exact reproduction requires deeper knowledge of the stability/ball-writing sequencing, which is not fully visible from static analysis alone.

### Recommendation
Replace `throw Error(...)` at `validation.js:732` with a graceful validation failure path, e.g. `return callback(createTransientError("last ball unit "+last_ball_unit+" is stable but has no ball"))`, so an unexpected local-state mismatch causes the single unit to be rejected/deferred rather than crashing the whole process. More broadly, audit all `throw Error` calls reachable from `validate()`'s async callback chains (e.g. `checkForDoublespends` at `validation.js:1673/1688/1692`, `validateAuthor` at `validation.js:1171`) for the same pattern, and ensure `handleJoint`/`validation.validate` callers wrap execution so that any unexpected internal exception is converted into a rejected unit instead of an `uncaughtException` process kill.

### Proof of Concept
Not independently reproducible from static review alone — triggering the exact DB state (`units.is_stable=1` while the corresponding `balls.ball` row is absent) requires driving the node through a specific stability-advancement/ball-persistence race, which cannot be confirmed without runtime access to the sqlite/mysql state machine and the full stabilization pipeline (`main_chain.js`, `writer.js`). This should be validated with a live/test node: submit or replay a unit whose `last_ball_unit` references a unit that the target node has locally marked stable via its own MC-advance logic but for which the ball-writing step (in `writer.saveJoint`) has not yet run, and observe the daemon crash via the `throw Error` at `validation.js:732` propagating to the `uncaughtException` handler in `network.js:4530-4543`.
