## Title
Ungoverned/legacy `system_vote` values for `tps_interval` can drive TPS-fee formulas to `Infinity`/`NaN`, permanently blocking unit acceptance — (File: `storage.js`, `main_chain.js`, `validation.js`)

### Summary
The `tps_interval`, `base_tps_fee`, and `tps_fee_multiplier` network parameters are set by median vote through `system_vote` messages that any unit author can post, counted by `countVotes()` in `main_chain.js`, and consumed unconditionally by the exponential TPS-fee formulas in `storage.js`. Just as MakerDAO's `DAIInterestRateModel` assumed `dsr >= 1e27` forever and reverted once governance broke that assumption, ocore's TPS-fee formulas assume `tps_interval` stays comfortably positive/large; `countVotes()` never re-validates the median value it writes to `system_vars`, and it aggregates votes cast under looser historical validation rules. This mirrors the reported bug class: an externally/governance-influenced numeric input that unexpectedly violates an implicit invariant and causes the dependent arithmetic path to blow up, taking down a function all unit validation depends on.

### Finding Description
`storage.getFinalTpsFee`/`getLocalTpsFee`/`getCurrentTpsFee` compute:
```js
Math.round(base_tps_fee * (exp(tps / tps_interval) - 1))
``` [1](#0-0) [2](#0-1) 

`exp()` is `Decimal(x).exp()` [3](#0-2) . If `tps_interval` is very small, `tps/tps_interval` explodes and `exp()` returns `Infinity`, making `min_tps_fee`/`current_tps_fee` `Infinity`.

`tps_interval` (like `base_tps_fee`, `tps_fee_multiplier`) is set by any unit author's `system_vote` message and later tallied by `countVotes()`:
```js
const rows = await conn.query(`SELECT value, SUM(balance) AS total_balance
    FROM numerical_votes CROSS JOIN voter_balances USING(address)
    WHERE timestamp>=? AND subject=? GROUP BY value ORDER BY value`, ...);
...
storage.systemVars[subject].unshift({ vote_count_mci: mci, value, is_emergency });
``` [4](#0-3) 

This median-selection logic performs **no bounds re-validation** of the resulting `value` before writing it into `storage.systemVars` / the `system_vars` table (compare to the DSR case where the model trusted `dsr` without re-checking it). The only bounds check exists at message-validation time, and even that is **conditionally gated**:
```js
case "base_tps_fee":
case "tps_interval":
case "tps_fee_multiplier":
    if (!(typeof payload.value === 'number' && isFinite(payload.value) && payload.value > 0))
        return callback(...);
    if (objValidationState.last_ball_mci >= constants.pemCurvesFixMci || ...) {
        if (payload.subject === "tps_interval" && payload.value < 0.1)
            return callback(...);
        ...
    }
``` [5](#0-4) 

Votes cast **before** `constants.pemCurvesFixMci` were only required to be `> 0` — no `0.1` floor existed — and those historical `numerical_votes` rows are never purged or re-validated. `countVotes()`'s vote-window logic can reach far back in time (it expands the lookback window year-by-year until enough balance has voted) [6](#0-5) , so pre-fix extreme votes remain eligible to be selected as the current median value long after the fix was deployed, exactly as MakerDAO governance could theoretically push `dsr` below the developer's assumed floor.

Once `tps_interval` becomes effectively "negative" relative to the formula's assumption (i.e., too small to keep `exp()` finite), every call into `validateTpsFee()` computes `min_tps_fee = Infinity`:
```js
const min_tps_fee = await storage.getLocalTpsFee(conn, objUnitProps, count_units);
...
if (tps_fees_balance + objUnit.tps_fee * share < min_tps_fee * share)
    return callback(`tps_fee ... less than required ${min_tps_fee} ...`);
``` [7](#0-6) 
No finite `tps_fee` an honest unit author supplies can ever satisfy `>= Infinity`, so **all new non-OP units are rejected** from that point on.

### Impact Explanation
`validateTpsFee` is invoked for every regular (non-AA-response) unit under version ≥4.0 [8](#0-7) . If `tps_interval`'s stored value becomes small enough for `exp()` to overflow to `Infinity`, honest units can no longer pass validation (only OPs are exempted with a warning) — this is a network unable to confirm new units, matching the "Accept only ... a network unable to confirm new units" bar in scope.

### Likelihood Explanation
Reaching this requires accumulating enough voter balance behind a stale/extreme pre-fix `tps_interval` vote (or a new vote exactly at the permitted `0.1` floor combined with a sufficiently high observed `tps`), which is not trivial but is fully reachable by ordinary unit posters casting `system_vote` messages — no privileged role, node, hub, or network-level compromise is needed. It hinges on the absence of any bounds re-validation in `countVotes()`, a genuine code-level gap independent of how likely a specific vote outcome is.

### Recommendation
- In `main_chain.js` `countVotes()`, re-validate the selected median `value` against the current (strictest) bounds for `subject` before writing to `system_vars`/`storage.systemVars`, discarding/ignoring out-of-bounds legacy votes when computing the median.
- In `storage.js`, defensively clamp/guard `getFinalTpsFee`/`getLocalTpsFee`/`getCurrentTpsFee` against non-finite results (e.g., treat `Infinity`/`NaN` as an internal error rather than silently propagating it into fee comparisons), so a bad system var cannot indefinitely brick unit validation.
- Consider a one-time migration that deletes or clamps `numerical_votes` rows for `tps_interval`/`base_tps_fee`/`tps_fee_multiplier` cast before `pemCurvesFixMci` that fall outside the now-enforced bounds.

### Proof of Concept
1. Multiple addresses (accumulating sufficient balance share per `SYSTEM_VOTE_MIN_SHARE`) cast `system_vote` messages for `subject: "tps_interval"` with a very small positive value before `constants.pemCurvesFixMci` is reached (legal at the time since only `value > 0` was enforced) [9](#0-8) .
2. After stabilization, a `system_vote_count` message for `tps_interval` (postable by any unit author per `uri.js`'s subject whitelist) triggers `countVotes(conn, mci, 'tps_interval')` [10](#0-9) [11](#0-10) .
3. The lookback window in `countVotes` can extend back years until it reaches the vote's `activation_timestamp`, still including the extreme pre-fix vote in the median computation [6](#0-5) .
4. The median `tps_interval` value is written to `system_vars` without any bounds check [12](#0-11) .
5. Subsequent calls to `getLocalTpsFee`/`getFinalTpsFee` divide `tps / tps_interval`, and `exp()` overflows to `Infinity` [3](#0-2) [13](#0-12) .
6. All subsequent non-OP units fail `validateTpsFee` because `min_tps_fee` is `Infinity` [14](#0-13) , halting normal unit acceptance network-wide.
