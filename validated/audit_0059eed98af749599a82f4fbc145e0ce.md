### Title
Webhook signature scoped to `repository.owner.login`, but repository/stack lookup keyed on unverified `repository.full_name` — cross-organization write via `GithubSyncJob` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to authenticate a webhook against using `repository_owner = params.dig('repository', 'owner', 'login')`, but every event `Handler` resolves the target `Stack`/`Repository` using a *different, unverified* field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')`. Because the HMAC only proves the request came from *an org whose secret is configured in Shipit*, not that `repository.owner.login` and `repository.full_name` are internally consistent, an attacker who controls one Shipit-tracked GitHub organization (and therefore knows/controls that org's webhook secret) can forge a webhook whose signature validates for their own org while `repository.full_name` points at a stack belonging to a completely different, victim organization.

### Finding Description
`WebhooksController#verify_signature` [1](#0-0)  does:

```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

with

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up the app config keyed by organization name (multiple orgs, each with its own `webhook_secret`, are supported — see `config/secrets.development.shopify.yml`) [3](#0-2) , and `verify_webhook_signature` HMACs the *raw body* against that org's secret [4](#0-3) . This only proves the sender knows the secret for the org named at `repository.owner.login` — it says nothing about any other field in the same payload.

However, once the signature is accepted, every handler resolves the actual repository/stack to act on via `Handler#repository_name`:

```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

and `stacks` does `Repository.from_github_repo_name(repository_name)&.stacks` [6](#0-5) . `PushHandler` and `CheckSuiteHandler` both consume this to find stacks and act on attacker-supplied SHAs:

```ruby
stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
``` [7](#0-6) 

Nothing ties `repository.full_name` back to `repository.owner.login`/the org whose secret validated the request. GitHub itself always sends these fields consistently, but the attacker fully controls the raw JSON body of a forged, self-signed request; they can set `repository.owner.login` to their own (Shipit-configured) org so the signature check passes with their own known secret, while setting `repository.full_name` to `"victim-org/victim-repo"` so the handler looks up and mutates a stack belonging to a different organization entirely.

This breaks the intended binding: **organization authenticated (`repository.owner.login`, validated against that org's `webhook_secret`) == repository/stack written (`repository.full_name`, used unchecked by every `Handler` to locate the `Stack`)**. The engine treats these two fields as if they must agree, but never checks that they do.

### Impact Explanation
A successfully forged `push` event lets the attacker invoke `stack.sync_github(expected_head_sha: <attacker value>)` for any stack belonging to any repository configured in this Shipit instance, not just the org whose secret they control. `GithubSyncJob#perform` [8](#0-7)  uses `stack.github_commits`/`stack.github_api` (Shipit's own installation token for the actual repository) to fetch and append commits, and unconditionally schedules `CacheDeploySpecJob` for that victim stack, forcing a re-fetch/re-cache of the victim's `shipit.yml` and commit history outside of any real push to that repository. This is a cross-repository write into another organization's stack state driven entirely by unprivileged attacker-controlled webhook content, matching the Critical "cross-repository writes" impact bucket in scope.

### Likelihood Explanation
This requires the attacker to be able to compute a valid webhook signature — i.e., to know a `webhook_secret` configured in this Shipit instance for *some* organization (e.g., their own org, if this Shipit instance is shared/multi-tenant across orgs as the config format explicitly supports). No repository write access, API token, or GitHub App private key for the *victim* organization is required — only knowledge of one's own org's webhook secret, which is exactly what a self-service org onboarding a GitHub App integration for Shipit would legitimately hold. Given the multi-org config support built into `lib/shipit/github_app.rb` and `config/secrets.*.yml`, this is a realistic deployment shape.

### Recommendation
Cross-check that `repository.owner.login` (or `organization.login`) equals the owner segment implied by `repository.full_name` before dispatching to handlers — e.g. in `WebhooksController#verify_signature`/`#create`, reject the payload if `repository.full_name.split('/').first.casecmp(repository_owner) != 0`. Alternatively, have `Handler#repository_name`/`#stacks` derive the repository strictly from the same verified `repository.owner.login` field rather than trusting the independent `full_name` field.

### Proof of Concept
1. Shipit is configured with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as supported by `config/secrets.*.yml`); attacker knows `attacker-org`'s webhook secret because they administer that org's GitHub App integration.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, raw_body)`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `attacker-org`'s `GithubApp`, and the signature validates successfully [9](#0-8) .
5. `PushHandler#process` runs `stacks` → `Handler#repository_name` returns `"victim-org/victim-repo"` [10](#0-9) , resolving the real victim `Stack`, and calls `stack.sync_github(expected_head_sha: "deadbeef...")`, enqueuing `GithubSyncJob` against the victim repository using Shipit's own credentials for that repo.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
