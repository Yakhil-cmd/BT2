### Title
Missing validation that a peer-supplied `shared_address` matches the expected arbiter-contract definition, allowing a counterparty to redirect escrow payment - ([File: wallet.js])

### Summary
In `wallet.js`'s `handleMessageFromHub`, the `arbiter_contract_update` message handler accepts a `shared_address` value from the remote contract counterparty (`peer_device_address`) and stores it via `arbiter_contract.setField`/`handleReceivedSharedAddress` after only checking that it is *syntactically* a valid address and that the contract's status is `"accepted"`. There is no check that the supplied `shared_address` actually hashes to the definition that should govern the escrow (i.e., the mutual-signature definition combining `my_address`, `peer_address`, and `arbiter_address`, as later required when validating an incoming signing `unit`). This is analogous to the Jenkins CVE-2016-3725 class of bug: a party who is authenticated for the flow (a paired, known correspondent participating in the contract) but who should not have authority to unilaterally dictate a security-critical value is nonetheless able to set it, because the permission/consistency check on that action is missing.

`pay()` sends the contract `amount` straight to `objContract.shared_address` with no re-derivation/verification that this address is the chash of the expected 2-of-2 (or arbiter-inclusive) escrow definition.

### Impact Explanation
A counterparty in an arbiter contract (an already-paired device that is legitimately part of the negotiation, i.e., the analog of an "authenticated but under-privileged" actor) can supply an arbitrary `shared_address` — one whose definition is fully controlled by the attacker (e.g., a plain single-sig address they own) — instead of the true mutual escrow address. If the local `pay()` flow is later invoked, the paying party's wallet sends the full contract amount to this attacker-controlled address believing it is funding the shared/escrow address, resulting in fund loss (unauthorized diversion of a payment) rather than funding of the intended arbitrated escrow. This maps to the "concrete unauthorized spending / AA-fund-loss-equivalent contract fund loss" impact class required by the validation rules, since the payer's own contract logic (not the base-layer consensus) is tricked into paying an address the peer chose with no permission/consistency check tying it to the agreed contract parties.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the victim to be actively negotiating and about to pay through the arbiter-contract feature, and the attacker must already be a paired counterparty in that specific contract flow (the normal case for using this feature at all — no separate compromise needed). Because the check gap is purely a missing validation on data received from the counterparty over the existing device-message protocol (no network-level or hub-level trust needed beyond the design's existing peer trust model), a malicious contract counterparty can trigger it deterministically in every contract they participate in.

### Recommendation
When handling `body.field === "shared_address"` in `wallet.js`'s `arbiter_contract_update` case (and in `arbiter_contract.handleReceivedSharedAddress`), recompute the expected shared-address definition from `objContract.my_address`, `objContract.peer_address`, and `objContract.arbiter_address` (the same mutual-definition template used to validate the signing unit in `arbiter_dispute_request`), hash it with `objectHash.getChash160`, and reject the update unless `body.value` equals that computed chash. Only after this equality check should `handleReceivedSharedAddress`/`setField` be allowed to persist the value that `pay()` will later trust.

### Proof of Concept
1. Alice and Bob (attacker) establish an arbiter contract via `arbiter_contract_offer`/`arbiter_contract_response`, reaching `status = "accepted"` (`wallet.js` case `arbiter_contract_response`, lines 864-940).
2. Bob's device sends `arbiter_contract_update` with `{hash, field: "shared_address", value: <address Bob fully controls, e.g. a plain single-key address>}`.
3. In `wallet.js`, the permission gate at lines 687-690 passes because Bob is `objContract.peer_device_address`. The subsequent `shared_address` branch (lines 726-734) only checks `isValidAddress(body.value)` and that no `shared_address` is already set — it accepts Bob's arbitrary address and calls `arbiter_contract.handleReceivedSharedAddress`.
4. Later, when Alice's wallet calls `arbiter_contract.pay(hash, ...)` (arbiter_contract.js lines 692-704), it sends `objContract.amount` of `objContract.asset` directly to `objContract.shared_address` — which is Bob's address, not a genuine 2-of-2/arbiter escrow — resulting in Alice's funds being paid straight to Bob with no arbiter involved and no recourse through the dispute mechanism (which expects a properly-derived shared address).
