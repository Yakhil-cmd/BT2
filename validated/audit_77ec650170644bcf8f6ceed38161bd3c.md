#### Title
Unbounded nearley/Earley grammar parsing of attacker-controlled formula strings enables a parser-hang Denial of Service - ([File: formula/validation.js])

### Summary
The reported CVE (`git_revparse_single`) shows how a crafted, attacker-controlled input string fed into a hand-written parsing loop can drive the parser into unbounded/pathological work, denying service to any caller that invokes the parsing routine. In `ocore`, the oscript/ojson formula grammar is parsed with the `nearley` Earley parser, which has a documented worst-case parsing complexity that grows superlinearly (up to cubic) with input length for ambiguous or deeply recursive grammars. Every formula string embedded in an AA definition, output condition (`if`), or `init` clause is fed directly into this parser with no upper bound on the formula's length or structural complexity before parsing begins.

### Finding Description
`formula/validation.js` builds a `nearley.Parser` from the compiled oscript grammar and feeds the raw formula text straight from the message payload: [1](#0-0) 

There is no length check, nesting-depth check, or complexity gate on `opts.formula` *before* the string reaches `parser.feed(formula)`. The only defenses (`count`, `depth`, `MAX_OPS`/`MAX_COMPLEXITY`-style checks) are applied to the resulting **AST after** parsing succeeds, in the `evaluate()` walker: [2](#0-1) 

The same unguarded pattern exists in the evaluation path used during AA-trigger execution: [3](#0-2) 

and in the ojson-to-oscript bridge used when parsing an AA’s definition JSON, which also calls `parseOscriptGrammar`/`parseOjsonGrammar` (both simple `nearley.Parser` + `.feed()` wrappers) with no pre-parse length/complexity gate: [4](#0-3) 

Formula strings originate from data that an *unprivileged* actor fully controls: any user can post a unit defining an Autonomous Agent (`aa_validation.js`), where every `if`, `init`, `amount`, `attestors`, `cap`, `denominations`, etc. field is checked only via `getFormula()` (a cheap brace-stripping check) and then handed to the nearley parser for full grammar validation: [5](#0-4) [6](#0-5) 

Because Earley parsing time depends on the grammar's ambiguity and the input length (not on any complexity counter enforced by ocore), a sufficiently long/ambiguous formula string (e.g., deeply nested parenthesized arithmetic expressions, chained `otherwise`/ternary/`AND`/`OR` operators, or repeated concatenation operators that are all valid per the grammar) can force the parser itself — before any AST-walking limits apply — into disproportionately large processing time relative to input size. This mirrors the `git_revparse_single` bug class: a parsing routine operating on attacker-supplied text with no bound on the internal work the parser performs, leading to CPU exhaustion / hang in the calling process.

### Impact Explanation
Every full node that receives and validates a unit containing such an AA definition (or evaluates an AA trigger against an existing pathological AA) must run this same unbounded parse before it can accept/reject the unit. If the parse work is large enough to cause a multi-second or longer stall on a subset of the network's validating nodes (or all of them, since validation is deterministic and identical software runs it), this can:
- Delay/deny confirmation of new units network-wide while nodes are busy re-parsing the same pathological formula repeatedly (once per validation, and again on every AA trigger that invokes it),
- Create asymmetric slow paths that let one attacker-controlled unit consume disproportionate validation resources compared to normal units, degrading throughput for the whole network.

This is a resource-exhaustion vector directly reachable by a single, unprivileged AA-definition author, matching the "network unable to confirm new units" impact bucket requested.

### Likelihood Explanation
Likelihood is speculative rather than proven: nearley's Earley implementation with a fixed, non-highly-ambiguous grammar can also behave close to linear/quadratic in many practical cases, and `constants.MAX_AA_STRING_LENGTH` and complexity checks do exist for the *evaluation* phase (post-parse), which somewhat limits how large a "useful" formula can realistically be embedded in a valid AA definition. I was not able to execute the parser locally to empirically measure worst-case timing for a crafted formula of realistic size, so I cannot confirm the exact degree of slowdown achievable within ocore's existing size constraints (e.g., is there a hard total-unit-size or total-definition-size cap that would already bound formula length enough to make this impractical?). This uncertainty should be validated with the actual nearley grammar (`formula/grammars/oscript.js`) and realistic unit size limits before treating this as confirmed-exploitable versus purely theoretical.

### Recommendation
- Enforce an explicit maximum length/complexity bound on any formula string *before* it is handed to `nearley.Parser`/`.feed()`, in both `formula/validation.js`, `formula/evaluation.js`, and `formula/parse_ojson.js`.
- Consider adding a parse-time budget (e.g., wall-clock or token-count ceiling) around the `parser.feed()` calls, aborting and rejecting the unit/definition if exceeded.
- Audit the oscript/ojson grammars for rules that permit high ambiguity (e.g., deeply left-recursive `AS`/`MD`/`Exp` rules) and consider grammar restructuring to bound Earley chart growth for adversarial inputs.

### Proof of Concept
Not independently verified against a running node; a concrete PoC would consist of an AA definition unit whose `if`/`init`/`amount` fields contain a formula string built from many repeated ambiguity-triggering tokens (e.g., long chains of `((((...))))`, `a||b||c...`, or nested `?:`/`otherwise` operators) submitted via `aa_validation.js`'s `validateAADefinition`, then measuring wall-clock time spent inside `formula/validation.js`'s `parser.feed(formula)` call for increasing input sizes to confirm superlinear growth. This step requires local execution against the `formula/grammars/oscript.js` grammar, which was not performed here.
