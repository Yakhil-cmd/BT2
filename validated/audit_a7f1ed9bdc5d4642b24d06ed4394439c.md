### Title
`StatusHandler` resolves incoming statuses by bare `sha` across all stacks, letting a same-org repository forge CI success for every `ignore_ci?: false` stack that shares the sha - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Commit#deployable?` returns `stack.ignore_ci? || (success? && !blocked?)`, so for stacks with `ignore_ci: true` a forged status changes nothing — the commit is already deployable. For every stack with `ignore_ci: false` (the default), deployability is entirely driven by `success?`/`blocked?`, both of which are derived from `Status` rows created by `Webhooks::Handlers::StatusHandler#process`, which matches commits by `sha` alone with no repository/stack scoping, and no field in `Stack` or `DeploySpec` exists to opt a CI-gated stack out of this.

### Finding Description
Binding checked: `exposure_to_forgery(stack) == !stack.ignore_ci?` for every stack, with no other mitigating flag.

- `Commit#deployable?` — [1](#0-0) . When `stack.ignore_ci?` is true, the right side of `||` (`success? && !blocked?`) is never evaluated (Ruby short-circuit), so any forged `Status` row has zero effect on this stack's deployability, confirmed by `test/models/commits_test.rb:558-562` (`#deployable? is true if stack is set to 'ignore_ci'`). This matches the "no marginal risk" half of the question.
- For `ignore_ci?: false` stacks, `success?`/`blocked?` are delegated to `status`, built from `statuses_and_check_runs` — [2](#0-1) . `Status` rows are created by `StatusHandler#process`: [3](#0-2) . `Commit.where(sha: params.sha)` matches every commit row across every repository/stack that has that sha — there is no check that `params` (`repository`, `context`, etc.) belongs to the commit's own `stack.repository`.
- `WebhooksController#verify_signature` only proves the payload was signed with the webhook secret configured for the organization named in the attacker-supplied JSON body (`repository_owner` = `params.dig('repository','owner','login')`) — [4](#0-3)  and [5](#0-4) . `GitHubApp#verify_webhook_signature` is purely an HMAC check against `@webhook_secret`, scoped per-organization, not per-repository or per-sha: [6](#0-5) . It authenticates "this org's GitHub App sent this", not "this commit/repository is the one the sha belongs to."
- Consequence: an attacker who controls any repository under an org where Shipit's GitHub App is installed (e.g., their own fork of a public repo in that org) can push/build a commit whose SHA is identical to a commit already tracked by a *different*, unrelated stack in the same org (forks preserve upstream SHAs), then have their own CI (or a raw POST to `/webhooks` with `X-Github-Event: status`, correctly signed with that org's secret) report `state: success` for that sha. `StatusHandler` writes that status onto every `Commit` record sharing the sha, including the victim's `ignore_ci: false` stack, flipping `success?` to true and (absent an unrelated blocking commit) `deployable?` to true.
- No guard in `Stack` (`ignore_ci`, `blocking_statuses`, `required_statuses`) or `DeploySpec` (`ci.hide`, `ci.allow_failures`, `ci.blocking`) checks repository provenance of a `Status` — they only filter by `context` string, which the forger fully controls.

### Impact Explanation
For every `ignore_ci?: false` stack, a forged status record written from an attacker-controlled repository can make `Commit#deployable?` true for a commit the victim's own CI never validated, enabling `stack.trigger_deploy` (Critical: unauthorized deploy triggered from another repository's payload) or unblocking merge-queue processing (`ProcessMergeRequestsJob`) via `add_status`'s hook path. Blast radius as claimed: every CI-gated (`ignore_ci: false`) stack in the instance is independently exposed via this shared-sha technique; `ignore_ci: true` stacks are unaffected because `deployable?` never consults `success?`/`blocked?` for them. This is a genuine cross-repository write (`Commit`/`Status` for repo B mutated by a payload validly signed only for repo A's org), matching the Critical category "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy."

### Likelihood Explanation
Preconditions: attacker needs push/CI access to some repository under an org that has Shipit's GitHub App installed (commonly org-wide installs), and a victim stack tracking a repository whose commit history/SHAs are shared with that attacker-controlled repository (typical for forks, or any repo pair sharing a merge-base). No Shipit session, API token, or secret is required — only the ability to make GitHub emit (or directly POST) a correctly-signed `status` event for that org. This is cheap and repeatable per victim commit sha and does not require guessing any secret.

### Recommendation
In `StatusHandler#process`, scope the lookup by the webhook's own repository, not by sha alone — restrict to `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_from_payload.id })` (or equivalent), so a status can only be attributed to commits belonging to the same repository that emitted it.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
test "status for one repository's sha does not mark another repository's commit deployable" do
  victim_stack = shipit_stacks(:shipit)          # ignore_ci: false
  victim_stack.update!(ignore_ci: false)
  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  refute victim_commit.deployable?

  attacker_repo_stack = shipit_stacks(:cyclimse) # different repository, attacker-controlled
  attacker_repo_stack.commits.create!(sha: shared_sha, ...)

  Shipit::Webhooks::Handlers::StatusHandler.new(
    'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/forged',
    'repository' => { 'full_name' => attacker_repo_stack.github_repo_name }
  ).process

  refute victim_commit.reload.deployable?, "status from another repository must not affect victim stack's commit"
end

test "ignore_ci stack is deployable independent of forged/absent statuses" do
  stack = shipit_stacks(:shipit_undeployed) # ignore_ci: true fixture
  commit = stack.commits.first
  commit.statuses.destroy_all
  assert commit.deployable?, "ignore_ci stack must be deployable with no status"
end
```
The first assertion currently fails against `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`, proving the forgery for `ignore_ci?: false` stacks; the second confirms `ignore_ci?: true` stacks are unaffected, validating both halves of the claimed binding.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
