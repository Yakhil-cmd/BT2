### Title
Webhook signature verification authenticates the payload's `repository.owner` while all handlers act on the payload's `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to check the HMAC against using `repository_owner`, a field read out of the attacker-controlled JSON body itself. Every event handler, however, resolves the target `Stack`/`Commit`/`Repository` using a *different* field from the same body, `repository.full_name`. Because the signature only proves "this body was HMAC-signed with the secret belonging to whatever org name appears in `repository.owner.login`," and nothing ties that org to the `repository.full_name` that is actually acted on, a party who legitimately controls a second GitHub App/org configured in the same Shipit instance's multi-org `github:` config can forge a webhook that authenticates as their own org but is dispatched against a completely different (victim) repository's stacks.

### Finding Description
`verify_signature` computes the authenticating identity purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp`/secret for that org name and calls `verify_webhook_signature`, which is a straightforward HMAC-SHA1 comparison of the raw body against that org's `webhook_secret`: [3](#0-2) [4](#0-3) 

Nothing in this check constrains `repository.full_name` to belong to `repository.owner.login`/the resolved organization — the HMAC only certifies that *some* known secret produced this exact byte string, not that the "owner" field used to pick the secret matches the "repository" field used to act on data.

After verification, `create` hands the full, un-scoped JSON to handlers: [5](#0-4) 

and every handler resolves its target purely from `repository.full_name`, independent of which org's secret validated the request: [6](#0-5) [7](#0-6) [8](#0-7) 

In a multi-organization deployment — an explicitly documented and supported configuration — each org in `github:` has its own independent `webhook_secret` that its own admins set when creating their GitHub App: [9](#0-8) 

An attacker who legitimately owns/administers one of those secondary orgs' GitHub Apps (and therefore knows *their own* `webhook_secret`, which they picked) can:
1. Build a JSON body with `repository.owner.login = "attacker-org"` (so `verify_signature` picks the attacker's own known secret) and `repository.full_name = "victim-org/victim-repo"`.
2. Compute a valid `sha1=` HMAC over that body using their own secret.
3. POST it to `/webhooks`; `verify_signature` passes (correct secret for `attacker-org`), then handlers act on `victim-org/victim-repo`'s stacks/commits, which the attacker has no credential or repository access to.

This is the equality the rules call out directly: "an organization that authenticated versus the repository that is written" — here `repository_owner` (authenticated identity) ≠ `repository.full_name` (data acted upon), and the engine never checks that they agree.

### Impact Explanation
Depending on event type dispatched with the forged, cross-repository payload, this lets an attacker with no privileges on the victim repo:
- Inject arbitrary commit statuses (`StatusHandler` → `Commit#create_status_from_github!`) onto any commit sha the attacker names, which feeds into a stack's deployability/merge-status gating used to decide if a commit can be shipped.
- Force `PushHandler` to trigger a GitHub sync against an attacker-chosen `expected_head_sha` for the victim stack.
- Trigger check-run refresh cycles (`CheckSuiteHandler`) for victim stacks.

The most severe of these — forging a passing/successful status on a victim's commit — can feed directly into the deploy-readiness checks that gate whether a commit is presented as deployable, which is the kind of cross-repository-write / unauthorized-ship precondition the rules flag as High/Critical impact, achieved without ever holding a `github_access_token`, `ApiClient` token, or write access to the victim repository.

### Likelihood Explanation
This requires: (a) the target Shipit instance to be configured with more than one GitHub organization (a documented, supported setup), and (b) the attacker to control a legitimate GitHub App/webhook secret for one of the *other* configured orgs (which they set themselves as that org's App owner). Given those two preconditions — both realistic for a shared, multi-tenant Shipit deployment — forging the cross-repository payload is trivial (just JSON + HMAC with a key the attacker already knows).

### Recommendation
After `verify_webhook_signature` succeeds, cross-check that the organization whose secret validated the signature (`repository_owner`) actually owns/matches the `repository.full_name` that handlers are about to act on, and reject the request (422) on mismatch, rather than trusting `repository.full_name` unconditionally once "some" signature check passes.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with independent `webhook_secret`s (per `docs/setup.md` "Using Multiple Github Applications").
2. As the admin of the GitHub App for `attacker-org`, craft:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"},
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/forged"
}
```
3. Compute `sha1=<hmac>` over the exact JSON body using `attacker-org`'s known `webhook_secret`.
4. `POST /webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<hmac>`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and succeeds (attacker's own secret matches).
6. `StatusHandler#process` runs against `Commit.where(sha: "<victim-commit-sha>")` for `victim-org/victim-repo`'s stack, creating a forged successful status the attacker was never authorized to produce for that repository.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
