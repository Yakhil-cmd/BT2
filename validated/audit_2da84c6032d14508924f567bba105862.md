### Title
Cross-organization commit-status forgery via unscoped `StatusHandler` breaks the webhook-authenticator-to-repository-written binding - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
Shipit supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret` [1](#0-0) . The webhook HMAC is verified per-organization based on `repository_owner`, resolved from the incoming payload itself [2](#0-1) [3](#0-2) . However, `Shipit::Webhooks::Handlers::StatusHandler#process` acts on commits purely by `sha`, without ever checking the `repository` field or re-deriving the owning stack the way the base `Handler` class otherwise supports.

### Finding Description
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the `X-Hub-Signature` against using `repository_owner`, which is read straight out of the attacker-controlled JSON body (`params.dig('repository','owner','login')` or `organization.login`) [4](#0-3) [3](#0-2) . This only proves the request was signed with the secret belonging to whichever organization the attacker names, not that the *content* being acted upon belongs to that organization.

The base `Handler` class does provide a way to scope processing to the actual repository named in the payload, via `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository','full_name')` [5](#0-4) . `PushHandler` and the `PullRequest` handlers use this scoping [6](#0-5) [7](#0-6) .

`StatusHandler`, however, does not use `stacks`/`repository_name` scoping at all — it only requires `sha` and directly loads every `Commit` matching that sha, then writes a status onto it, regardless of which repository/organization the commit actually belongs to: [8](#0-7) .

Root cause / broken binding (equality that should hold but doesn't):
`organization authenticated by verify_signature (repository_owner)` == `organization owning the Commit/Stack actually written by StatusHandler`.

Because a legitimate, self-hosted organization admin can install their own GitHub App on their own org (org A) and legitimately obtain org A's `webhook_secret` (it's configured by them, per the multi-org config format shown in `config/secrets.development.example.yml`), they can freely author and correctly HMAC-sign an arbitrary JSON payload for the `status` event using org A's own secret — the signature only proves "this came from someone who knows org A's secret," not "this event actually originates from org A's repositories." `StatusHandler` then trusts the `sha` field in that self-signed payload with zero further scoping, and will happily attach a forged CI status to any commit in the Shipit instance whose sha matches — including commits belonging to a completely different organization's stack that org A has no access to on GitHub.

### Impact Explanation
This is a cross-repository/cross-organization write in the sense targeted by the rules: an attacker who legitimately controls one organization's webhook secret in a multi-tenant Shipit deployment can inject arbitrary commit statuses (`state`, `context`, `description`, `target_url`) onto commits belonging to a stack/repository they were never granted access to [9](#0-8) . If a target stack gates deploys/merges on required checks/green commit statuses, this can be used to force a commit into a "success" state it never actually achieved on GitHub, directly influencing whether that stack is deployable — matching the "unauthorized deploy" impact category. The prerequisite (knowing a target commit sha) is commonly satisfiable since shas are frequently public (open-source repos, PR pages, CI badges) even without repository write access.

### Likelihood Explanation
Requires the attacker to control at least one legitimately configured organization/app in a multi-org Shipit deployment (a realistic and documented deployment topology per `config/secrets.development.example.yml`), plus knowledge of a target commit's sha (often public). No compromise of the victim organization's own webhook secret, GitHub token, or Shipit session is required — only the attacker's own already-valid webhook credentials, satisfying the "unprivileged attacker relative to the victim organization" requirement.

### Recommendation
In `StatusHandler` (and any other handler operating on cross-cutting identifiers like `sha`), scope commit lookups to the repository actually named in `payload.dig('repository','full_name')` — mirroring the pattern already used in `Handler#stacks`/`PushHandler` — and additionally cross-check that the organization used to select the `webhook_secret` in `WebhooksController#verify_signature` matches the owner of `repository.full_name` in the payload before dispatching to any handler.

### Proof of Concept
1. Attacker operates their own legitimate GitHub App installation on `org-a`, with Shipit configured for `org-a`'s `webhook_secret` (a normal, documented multi-org setup).
2. Attacker crafts a `status` event JSON body with `sha` = a known commit sha belonging to `victim-org/victim-repo`'s stack (obtained e.g. from GitHub's public commit history or a public PR), `state` = `"success"`, and any `context`/`description`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-webhook_secret, body)` using their own known secret, and sets `repository.owner.login`/`organization.login` = `"org-a"` so `WebhooksController#verify_signature` resolves and passes verification against `org-a`'s secret [4](#0-3) .
4. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which finds `Commit.where(sha: params.sha)` — the victim's commit — and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled status onto a commit in a stack the attacker never had access to [9](#0-8) .

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
