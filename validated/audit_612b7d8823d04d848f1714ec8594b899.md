### Title
Stack-scoped API token can read CI/deploy status of any stack via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` resolves the target stack with an unscoped `Stack.from_param!(params[:stack_id])` lookup instead of using the scoped `stacks`/`stack` helper defined in `BaseController`. This breaks the invariant that a stack-scoped `ApiClient` (`stack_id` set) may only read the one stack it was authorized for, letting that token read any stack's build/deploy status by simply changing the `stack_id` path parameter.

### Finding Description
`Shipit::ApiClient` supports being scoped to a single stack via its `stack_id` column, and `Api::BaseController` is designed to enforce that scope everywhere: [1](#0-0) 

The permission check itself is scope-agnostic — it only checks that the required `"#{operation}:#{scope}"` string (e.g. `"read:stack"`) is present in the client's `permissions` array, with no reference to which specific stack is being accessed: [2](#0-1) 

The actual restriction to "only the stacks this token is allowed to see" is implemented solely in `BaseController#stacks`/`#stack` (`Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped). Every other API controller that reads a stack from params (`Api::StacksController`, `Api::TasksController`, etc.) relies on this scoped method — this is exercised by the test asserting a stack-scoped client sees only its own stack: [3](#0-2) 

`Api::CCMenuController`, however, overrides `stack` with its own unscoped lookup, bypassing `BaseController#stacks` entirely: [4](#0-3) 

This is the exact analog of the reported bug class: two values that are supposed to be kept in lock-step (`stack the ApiClient's `stack_id` authorizes` and `stack the controller action actually touches`) diverge in one code path, because that path independently re-implements the "convert param to model" step instead of going through the single authoritative, scope-checked conversion.

Equality that should hold but is broken:
`{stacks readable by client} == Stack.where(id: current_api_client.stack_id)` for a stack-scoped client — but in `CCMenuController#show`, `{stacks readable by client} == Stack.all` regardless of `stack_id`.

### Impact Explanation
A token that was deliberately scoped to a single stack (created with `stack_id` set and `permissions: ["read:stack"]`, the documented, supported way to hand out narrowly-scoped read access) can be replayed against `Api::CCMenuController#show` with a different `stack_id` in the URL to read another stack's build/deploy status (name, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) — data the token holder was never authorized to see. This is an authorization-scope escalation: the permission check passes (the client does have `read:stack`), but the stack boundary that the token issuer intended to enforce is not applied, giving unauthorized read of stack/deploy state across stack boundaries.

### Likelihood Explanation
Any holder of a valid, intentionally stack-scoped `ApiClient` token (a routine, lower-privilege credential by design) can trigger this simply by calling the CCMenu XML endpoint with a `stack_id`/`token` combination for a stack other than the one the token was scoped to — no additional secrets, signing keys, or special access are required beyond possessing that one legitimately-scoped token.

### Recommendation
Remove `CCMenuController#stack`'s private unscoped override and use the inherited, scope-enforcing `stack`/`stacks` method from `Api::BaseController` (i.e. `stacks.from_param!(params[:stack_id])`), so every API controller resolves stacks through the single authoritative, `current_api_client.stack_id`-aware code path.

### Proof of Concept
1. An operator creates a stack-scoped, read-only `ApiClient`: `ApiClient.create!(creator: user, name: "CI badge", stack_id: stackA.id, permissions: ["read:stack"])`, intending it to only ever report on `stackA`.
2. The token is used against the CCMenu endpoint for the stack it's scoped to: `GET /api/1/stacks/:ownerA/:repoA/:envA/ccmenu.xml?token=<token>` → succeeds, returns `stackA`'s status (expected).
3. Using the same token, the attacker requests a different stack's endpoint: `GET /api/1/stacks/:ownerB/:repoB/:envB/ccmenu.xml?token=<token>`.
4. `authenticate_api_client` authenticates the token to the same `ApiClient` (still scoped to `stackA`); `require_permission :read, :stack` passes because `check_permissions!` only checks the `permissions` array, not the target stack.
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` [5](#0-4)  — an unscoped, global lookup — returning `stackB` instead of raising `ActiveRecord::RecordNotFound`.
6. `show` renders `stackB`'s CI/deploy status XML [6](#0-5) , leaking build/deploy state for a stack outside the token's authorized scope.
