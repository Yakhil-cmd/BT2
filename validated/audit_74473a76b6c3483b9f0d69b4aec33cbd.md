### Title
Git credentials (passwords, password-file contents, askpass-url secrets, GitHub App tokens) are persisted via `git credential approve` without confirmed use of a non-persistent helper - (File: main.go)

### Summary
`git-sync` funnels all of its dynamic secrets — static passwords, `--password-file` contents (re-read every sync for rotation), `--askpass-url` responses, and short-lived GitHub App installation tokens — through a single `StoreCredentials` call, which is backed by `git credential approve`.

### Finding Description
Every authentication mode converges on the same sink, `git.StoreCredentials(ctx, url, username, password)`:
- Static/rotating file-based credentials: [1](#0-0) 
- `--askpass-url` HTTP responses: [2](#0-1) 
- GitHub App installation tokens minted from a private key: [3](#0-2) 

`git credential approve` itself does not encrypt anything — it hands the username/password/url tuple to whatever `credential.helper` is configured in the effective git config. Git's built-in helpers include `cache` (in-memory, ephemeral) and `store` (plaintext file, `~/.git-credentials`, persisted indefinitely). The report's underlying bug class — "secrets copied to the filesystem without encryption" — applies directly if git-sync's git configuration does not pin `credential.helper` to a non-persistent option (or explicitly disables persistence) before calling `approve`. Documentation confirms the design intent is for `--credential`/`--username`+password to be "fed into 'git credential approve'": [4](#0-3) . The askpass docs also explicitly warn "credentials will pass in plain text" over the network leg, but say nothing about at-rest handling once stored via `approve`: [5](#0-4) .

### Impact Explanation
If the effective `credential.helper` resolves to `store` (or any file-backed helper) rather than `cache`, every secret git-sync is trusted with — long-lived PATs, rotated secrets from an external secret manager, and freshly minted GitHub App installation tokens (valid up to an hour) — ends up world-readable-by-owner in a plaintext file under the container's home directory / `--root`-adjacent paths, persisting across syncs and outliving token rotation. Anyone who can read that file (e.g., via another sidecar sharing the pod's filesystem, a misconfigured volume, or a container escape) obtains live git credentials, directly mirroring the wallet.dat exposure in the original report: sensitive data at rest, unencrypted, and copyable.

### Likelihood Explanation
This path is reached on every normal authenticated sync — no attacker interaction is required beyond the credential-refresh flow already exercised by `--password-file`, `--askpass-url`, `--credential`, or GitHub App auth flags, all of which are officially supported, common configurations documented in `README.md`. The likelihood of exploitation depends entirely on whether the surrounding git config pins a non-persistent `credential.helper`; I was not able to confirm this configuration within available searches, so this should be treated as **requires verification** rather than a confirmed default-vulnerable state.

### Recommendation
Verify (by reading the full `StoreCredentials` implementation and any git config setup in `main.go`) that `credential.helper` is explicitly and unconditionally set to a non-persistent value (e.g., a custom in-memory helper, or `cache --timeout=<short>`) before any `git credential approve` call, and that no code path allows the ambient/global git config to override it with `store`. If a persistent helper can be selected via inherited git config, treat any resulting `~/.git-credentials`-style file as sensitive: restrict permissions, avoid mounting it into shared volumes, and document that operators must not override `credential.helper` in a way that persists secrets to disk unencrypted.

### Proof of Concept
Not independently verified in this pass — a concrete PoC would require confirming the git config sequence around `StoreCredentials`/`credential approve` (i.e., what `credential.helper` resolves to at call time) and then demonstrating that `~/.git-credentials` (or equivalent) contains the plaintext username/password/token after a sync using `--password-file`, `--askpass-url`, or `--github-app-*` flags. I recommend a background session read `StoreCredentials` in full and any `git config credential.helper` invocation in `main.go` to close this gap before treating the finding as confirmed.
