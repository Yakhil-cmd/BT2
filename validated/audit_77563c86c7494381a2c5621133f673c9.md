### Title
Webhook organization used for signature verification is never bound to the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate a webhook against using `repository.owner.login` (or `organization.login`) taken directly from the untrusted, attacker-supplied JSON body. [1](#0-0) [2](#0-1)  The event handlers, however, resolve the actual `Repository`/`Stack` to act on using a *different* field of the same payload: `repository.full_name`. [3](#0-2)  Nothing enforces that `repository.owner.login` and the owner embedded in `repository.full_name` refer to the same repository. In a multi-organization deployment (the shipped config format explicitly supports several independent GitHub Apps/orgs, each with its own `webhook_secret`), this lets a party who legitimately controls one configured organization's webhook secret sign a payload whose `full_name` field points at a *different* organization's repository, and have Shipit act on that other repository/stack.

### Finding Description
The equality that should hold is:

`organization authenticated by verify_signature (repository.owner.login / organization.login)` == `repository actually written to by the handler (repository.full_name)`

`verify_signature` fetches the GitHub App config for `repository_owner` and calls `verify_webhook_signature` against the raw body: [4](#0-3) 

`repository_owner` is parsed straight out of the JSON body: [2](#0-1) 

Once the signature is deemed valid, `create` hands the *entire raw params hash* to the registered handlers unchanged: [5](#0-4) 

Every handler that touches a repository resolves it via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` - a completely separate JSON field from the one used for signature routing - and splits it on `/` to look up the `Repository` record: [6](#0-5) [7](#0-6) 

For example, `PushHandler` uses that repository/stack lookup to force a stack sync with an attacker-supplied `expected_head_sha`: [8](#0-7) 

Because a real GitHub-issued webhook always keeps `repository.owner.login` consistent with `repository.full_name`, this divergence is invisible under normal operation. But the controller trusts the raw, unauthenticated request body to pick the verification key *before* the signature has actually validated that body's contents; only after picking the org-specific secret does it check the signature over the whole raw body. This is the same class of bug as the reported "conditional check acts on a field the signature/authorization doesn't actually bind" - here the org identity used to select the verification secret is decoupled from the repository identity the handlers subsequently mutate.

### Impact Explanation
In any deployment configured with more than one GitHub organization/App (as shown in `config/secrets.development.shopify.yml`, Shipit explicitly supports this), a holder of one configured org's valid `webhook_secret` (i.e., anyone who legitimately administers that org's Shipit-integrated GitHub App and can therefore produce a correctly HMAC-signed request) can submit a forged webhook whose `repository.owner.login` names their own org (satisfying `verify_signature`) while `repository.full_name` names an arbitrary other configured repository/stack. This lets them drive that other stack's webhook-triggered behavior - e.g., forcing `Stack#sync_github` with a chosen `expected_head_sha` via `PushHandler`, or exercising `StatusHandler`/`CheckSuiteHandler` against a repository they do not own - without holding any credential or permission scoped to that repository. Depending on downstream handler logic this crosses a repository-authorization boundary that GitHub's own webhook model is intended to prevent (each org's App secret should only be able to speak for that org's own repositories).

### Likelihood Explanation
Exploitation only requires the ability to send an HTTP POST to the public `/webhooks` endpoint (no Shipit session, no `ApiClient` token, no GitHub push access to the victim repo) plus knowledge of any *one* configured organization's `webhook_secret` in the deployment - which is the normal, expected capability of anyone permitted to install/administer that org's own GitHub App integration with Shipit. No race condition, timing, or privileged access to the victim's org/repo is needed.

### Recommendation
Cross-validate the identity used to select the verification key against the identity the handlers will act on: after computing `repository_owner`, verify that any `repository.full_name` present in the same payload actually belongs to that owner (e.g., `full_name.split('/').first.casecmp?(repository_owner)`) and reject (422) on mismatch. More robustly, derive the App/secret to check purely from routing metadata that cannot be spoofed by the payload body (e.g., a per-organization webhook path/token), rather than from attacker-controlled JSON fields, and additionally scope handler repository lookups to only the organization whose secret verified the signature.

### Proof of Concept
Given a Shipit deployment configured with two orgs, `attacker-org` (secret known to the attacker, who administers that org's GitHub App) and `victim-org` (containing a tracked stack), the attacker can send:

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_of_attacker-org, raw_body)>

{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```

`verify_signature` computes `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and validates the signature against that org's secret - which succeeds because the attacker genuinely knows it. [1](#0-0)  `create` then dispatches to `PushHandler`, which resolves the stack via `payload.dig('repository','full_name') == "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack. [8](#0-7) [3](#0-2) 

Note: I was unable to fully trace `StatusHandler`/`CheckSuiteHandler` and how forged commit statuses feed into deploy-gating logic within the remaining tool budget; the core signature/repository-identity binding break is confirmed directly from the code above, but the full severity ceiling (e.g., whether this can be leveraged into an actual unauthorized deploy versus a forced/early sync) would benefit from further review of those handlers and `Stack#sync_github`/`deployable_status` logic.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
