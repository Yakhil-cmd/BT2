### Title
Signature verification silently succeeds when an organization's `webhook_secret` is unset, letting an unauthenticated attacker post forged webhook events that trigger unauthorized deploys and team-membership escalation - ([File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` derives which GitHub App/organization config to use for HMAC verification directly from the untrusted JSON body, then delegates to `GitHubApp#verify_webhook_signature`, which treats a missing `webhook_secret` as an automatic pass rather than a failure. This breaks the binding "the organization that authenticated" == "the organization the payload claims to write to," because when no secret is configured for the org named in the payload, no authentication occurs at all, yet the request is processed as if it had been verified.

### Finding Description
The controller reads the "authenticating organization" out of the same attacker-suppliable payload it is about to verify: [1](#0-0) [2](#0-1) 

It then calls into `GitHubApp#verify_webhook_signature`, which unconditionally returns `true` whenever no `webhook_secret` is configured for that organization: [3](#0-2) 

The test fixture configuration demonstrates that `webhook_secret` is expected to be an optional, nullable value in this engine's own config schema (not merely a host-integration omission): [4](#0-3) 

Once past `verify_signature`, the raw JSON is dispatched to handlers keyed only by `X-Github-Event`, with no further authentication: [5](#0-4) 

Downstream handlers resolve which `Stack`/`Repository` to mutate purely from `repository.full_name` in the same untrusted body: [6](#0-5) 

For any organization onboarded to this Shipit instance whose `webhook_secret` is left blank/null, an unprivileged attacker (no session, no `ApiClient` token, no GitHub App private key) can `POST` arbitrary crafted JSON directly to `/webhooks` with `X-Github-Event` set to `status`, `push`, or `membership`, and have it processed as a fully trusted GitHub event.

### Impact Explanation
- Forged `status`/`commit_status` events let an attacker mark arbitrary commits with passing CI states for required contexts, satisfying `ci.require` checks and enabling an **unauthorized deploy** of an unreviewed commit (Critical).
- Forged `push` events trigger `stack.sync_github(expected_head_sha:)`, letting an attacker manipulate which commit is considered the branch head for a tracked stack: [7](#0-6) 
- Forged `membership` events create/modify `Team`/`Membership`/`User` records, directly escalating into `Shipit.github_teams` authorization (High), matching behavior exercised in: [8](#0-7) 

### Likelihood Explanation
Requires only that one onboarded organization's `webhook_secret` be left unset — a state the engine's own config schema explicitly permits (`null` is a valid, tested value) rather than requiring the host app to deviate from documented mounting. No credentials, sessions, or tokens are needed by the attacker; the endpoint is public.

### Recommendation
Fail closed instead of open: `verify_webhook_signature` should reject requests (return `false`/422) when `webhook_secret` is blank, rather than treating an absent secret as implicit trust. Additionally, decouple "which secret verifies the signature" from "which repository the handler writes to" so the two are derived from the same already-authenticated source, not two independently-read fields off the unauthenticated payload.

### Proof of Concept
1. Identify (or wait for) an onboarded organization/repo in the target Shipit instance whose GitHub App config has no `webhook_secret` set (schema explicitly allows `null`, as shown in `test/dummy/config/secrets.test.json`).
2. `POST /webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "<target commit sha>",
  "state": "success",
  "context": "<required-ci-context>",
  "repository": {"full_name": "org/repo", "owner": {"login": "org"}}
}
```
No `X-Hub-Signature` header value need be valid — `verify_webhook_signature` returns `true` because `webhook_secret` is blank.
3. `StatusHandler` processes the forged event and calls `commit.create_status_from_github!`, satisfying required CI checks, after which the attacker (or any user) can trigger a deploy of that commit — an unauthorized deploy achieved with zero credentials.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
