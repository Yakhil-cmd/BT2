**Full attack trace:**

2. Attacker sends a `ServiceChainParentChainInfoResponseMsg` with `Nonce=0`.
3. `handleParentChainInfoResponseMsg` decodes it: `pcInfo.Nonce = 0`.
4. `poolNonce = GetMaxTxNonce(...)` returns 0 (all prior txs confirmed, pool empty — normal operational state).
5. `poolNonce > 0` is false; `getParentOperatorNonce() > pcInfo.Nonce` (e.g., 5 > 0) is true.
6. `setParentOperatorNonce(0)` is called. Nonce is now 0.

`nonceSynced` is set to `true` after the attack, so `LocalChainHeadEvent` takes the `getParentOperatorNonceSynced()` branch and keeps generating txs with nonce=0. The `handleParentChainInvalidTxResponseMsg` path does not re-sync on nonce errors. Recovery only happens if a new peer connects or the operator restarts.

### Title
Unauthenticated Bridge Peer Can Regress Parent Operator Nonce to Zero, Permanently Halting Bridge Value Transfers — (`node/sc/sub_bridge_handler.go`)

### Summary
`handleParentChainInfoResponseMsg` unconditionally accepts a peer-supplied nonce and sets the parent operator nonce to it when the bridge tx pool is empty, even if the supplied nonce is lower than the current confirmed on-chain nonce. An attacker who connects as a bridge peer can send `Nonce=0`, resetting the operator nonce and causing all subsequent bridge transactions to be rejected as nonce-too-low, permanently halting anchoring and value transfers.

### Finding Description
In `handleParentChainInfoResponseMsg`, when `poolNonce == 0` (bridge tx pool is empty, a normal post-confirmation state) and `getParentOperatorNonce() > pcInfo.Nonce`, the code logs an error but then calls `setParentOperatorNonce(pcInfo.Nonce)`, regressing the nonce to the attacker-controlled value. [1](#0-0) 

The `poolNonce > 0` branch correctly uses `poolNonce` as a floor and never regresses below it, but the `poolNonce == 0` branch has no such protection. [2](#0-1) 

After the nonce is corrupted, `setParentOperatorNonceSynced(true)` is called, so the system believes the nonce is valid and continues generating transactions with the corrupted nonce. [3](#0-2) 

### Impact Explanation
All bridge transactions (anchoring and value transfers) are built using `getParentOperatorNonce()`: [4](#0-3) 

With the nonce reset to 0, every submitted transaction is rejected by the parent chain as nonce-too-low. The `handleParentChainInvalidTxResponseMsg` handler only re-syncs on `ErrGasPriceBelowBaseFee`, not on nonce errors, so there is no automatic recovery path. [5](#0-4) 

This constitutes a durable halt of bridge value transfers and anchoring — a loss of core bridge functionality.

### Likelihood Explanation
The only guard before processing this message is the chainID check in `RegisterNewPeer`. No signature or operator-key authentication is required on the message content. The bridge P2P port, if reachable, accepts any peer presenting the correct chainID. The `poolNonce == 0` precondition is the normal state after all pending bridge txs have been confirmed and their receipts processed. [6](#0-5) [7](#0-6) 

### Recommendation
In the `else if` branch, do not regress the nonce. Replace:
```go
} else if sbh.getParentOperatorNonce() > pcInfo.Nonce {
    logger.Error(...)
    sbh.setParentOperatorNonce(pcInfo.Nonce)  // BUG: regresses nonce
```
with:
```go
} else if sbh.getParentOperatorNonce() > pcInfo.Nonce {
    logger.Error(...)
    // Do NOT lower the nonce; keep the current higher value.
```
Additionally, add peer authentication (e.g., verify the peer is a known/configured parent chain node) before accepting nonce-update messages.

2. Connect a malicious peer to the bridge P2P port with the correct parent chainID.
3. Send `ServiceChainParentChainInfoResponseMsg` with `parentChainInfo{Nonce: 0, GasPrice: 1}`.
4. Assert `getParentOperatorNonce() == 0` (nonce regressed).
5. Trigger an anchoring tx generation; observe the tx is built with nonce=0.
6. Observe the parent chain rejects it as nonce-too-low.
7. Confirm no automatic recovery occurs (nonceSynced remains true, no re-sync triggered). [8](#0-7)

func (sbh *SubBridgeHandler) handleParentChainInfoResponseMsg(p BridgePeer, msg p2p.Msg) error {
	var pcInfo parentChainInfo
	if err := msg.Decode(&pcInfo); err != nil {
		logger.Error("failed to decode", "err", err)
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	sbh.LockParentOperator()
	defer sbh.UnLockParentOperator()

	poolNonce := sbh.subbridge.bridgeTxPool.GetMaxTxNonce(sbh.GetParentOperatorAddr())
	if poolNonce > 0 {
		poolNonce += 1
		// just check
		if sbh.getParentOperatorNonce() > poolNonce {
			logger.Error("parent chain operator nonce is bigger than the chain pool nonce.", "BridgeTxPoolNonce", poolNonce, "mainChainAccountNonce", sbh.getParentOperatorNonce())
		}
		if poolNonce < pcInfo.Nonce {
			// BridgeTxPool journal miss txs which already sent to parent-chain
			logger.Error("chain pool nonce is less than the parent chain nonce.", "chainPoolNonce", poolNonce, "receivedNonce", pcInfo.Nonce)
			sbh.setParentOperatorNonce(pcInfo.Nonce)
		} else {
			// BridgeTxPool journal has txs which don't receive receipt from parent-chain
			sbh.setParentOperatorNonce(poolNonce)
		}
	} else if sbh.getParentOperatorNonce() > pcInfo.Nonce {
		logger.Error("parent chain operator nonce is bigger than the received nonce.", "mainChainAccountNonce", sbh.getParentOperatorNonce(), "receivedNonce", pcInfo.Nonce)
		sbh.setParentOperatorNonce(pcInfo.Nonce)
	} else {
		// there is no tx in bridgetTxPool, so parent-chain's nonce is used
		sbh.setParentOperatorNonce(pcInfo.Nonce)
	}
	sbh.setParentOperatorNonceSynced(true)
	sbh.setRemoteChainValues(pcInfo)
	logger.Info("ParentChainNonceResponse", "receivedNonce", pcInfo.Nonce, "gasPrice", pcInfo.GasPrice, "mainChainAccountNonce", sbh.getParentOperatorNonce())
	return nil
}
