### Title
SSRF via attacker-controlled ArbStore URL in arbiter contract flows - (File: `arbiter_contract.js`)

### Summary
`ocore` implements arbiter-contract functionality (`arbiter_contract.js`) in which the URL of the "arbstore" service backing a chosen arbiter is looked up dynamically (`device.requestFromHub("hub/get_arbstore_url", ...)`) and then used directly, with no validation of scheme/host, to issue outbound HTTP(S) requests from the victim's own node, including POSTing sensitive contract data.

### Finding Description
When a user creates or interacts with an arbiter contract, the `arbiter_address` — chosen by whichever party proposes the contract — is used to resolve an arbstore URL via the hub (`getArbstoreAddresses`, `openDispute`, `appeal`, `getAppealFee` in <cite repo="Camomtat/ocore--001" path="arbiter_contract.js" start="228,262,321,357" end="245,319,355,375" />). That URL is then passed straight into `httpRequest(url, path, data, cb)` <cite repo="Camomtat/ocore--001" path="arbiter_contract.js" start="377,388" end="386,389" />, which builds request options via `url.parse(host)` and issues `http.request` with attacker-influenced `host`/`path`, with zero allow-listing of destination host (no rejection of loopback, link-local metadata addresses, or private RFC1918 ranges).

The same unrestricted pattern exists in `arbiters.js`, where `requestInfoFromArbStore(url, cb)` performs `http.get(url, ...)` for `getInfo` and `getArbstoreInfo` <cite repo="Camomtat/ocore--001" path="arbiters.js" start="10,35,51" end="33,49,80" />. In both files the URL originates from the hub's response to `hub/get_arbstore_url`/`hub/get_arbstore_url_by_address`, which is itself controlled indirectly by whoever the counterparty designates as `arbiter_address` when proposing the contract — an attacker acting as an unprivileged contract counterparty (or acting as the "arbiter" party in the exchange) can steer this value toward an internal address (e.g., `127.0.0.1`, a cloud metadata endpoint, or an internal service on the victim's LAN).

Critically, when the dispute (`openDispute`) or appeal (`appeal`) flow fires, the wallet not only issues a GET/POST to the attacker-chosen host, it POSTs a JSON payload containing sensitive contract data — including the encrypted contract package, `my_pairing_code`, `my_contact_info`, and (for private assets) `asset`/`amount` — to that host <cite repo="Camomtat/ocore--001" path="arbiter_contract.js" start="276,301,303" end="296,302,304" />. The response body from that internal endpoint is then parsed as JSON and returned to the calling code, and ultimately surfaced back through the contract flow (`cb(null, resp, objContract)`), giving the attacker a read/reflect channel for whatever the internal endpoint returns.

### Impact Explanation
This is a genuine SSRF that: (1) forces the victim node to make outbound requests to arbitrary internal/local addresses chosen by an unprivileged counterparty in a wallet-level contract flow, (2) leaks sensitive contract details (pairing codes, contact info, asset/amount for private assets) to that attacker-controlled or attacker-redirected endpoint, and (3) can reflect internal-service responses back into the wallet UI/flow, enabling internal network reconnaissance or interaction with local services (e.g., other RPC/API endpoints bound to localhost) purely by getting a victim to negotiate/dispute/appeal an arbiter contract with an attacker-designated arbiter address.

### Likelihood Explanation
Exploitation requires only that the attacker act as a counterparty proposing an arbiter contract (or as/controlling the arbiter identity resolved by the hub for a given `arbiter_address`) — no special privilege, hub-operator access, or node compromise is needed. The victim triggers the vulnerable code path merely by using the standard wallet arbiter-contract UI actions (viewing arbiter info, opening a dispute, filing an appeal, or checking the appeal fee), all of which are normal, expected user interactions with an attacker-supplied `arbiter_address`.

### Recommendation
Validate and restrict the arbstore URL before use in `httpRequest`/`requestInfoFromArbStore`: enforce HTTPS, resolve and reject requests to loopback, link-local (169.254.0.0/16 incl. 169.254.169.254), and RFC1918 private ranges, and disallow redirects to such ranges. Consider requiring arbstore URLs to be pinned/allow-listed (e.g., only URLs previously vetted or matching known ArbStore registrations) rather than trusting whatever the hub returns for an attacker-influenced `arbiter_address`.

### Proof of Concept
1. Attacker proposes or participates in an arbiter contract where the resolvable `arbiter_address` maps (via the hub's `hub/get_arbstore_url`) to an internal URL such as `http://127.0.0.1:6000` or `http://169.254.169.254`.
2. Victim, using standard wallet flow, calls `arbiters.getInfo(arbiter_address, ...)` (triggers `requestInfoFromArbStore`) or proceeds to `openDispute`/`appeal`/`getAppealFee` on that contract.
3. Victim's node issues an HTTP GET/POST to the internal address with `arbiter_contract.js`'s `httpRequest`/`arbiters.js`'s `requestInfoFromArbStore`, including sensitive contract JSON in the POST body for dispute/appeal calls.
4. The internal endpoint's response is parsed and propagated back through the contract callback chain, confirming successful SSRF and potential data exfiltration/reflection.
