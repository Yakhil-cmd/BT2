### Title
Webhook signature is verified against the org derived from `repository.owner.login`/`organization.login`, but handlers act on the unrelated `repository.full_name` field, allowing a legitimate multi-tenant org to forge webhooks that trigger actions against another org's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This is the same rounding-class bug pattern as the report ("the value used to authorize an operation differs from the value the operation is actually performed with"), applied to Shipit's webhook trust boundary. `WebhooksController#verify_signature` selects *which* GitHub App/organization secret to validate the HMAC-SHA1 signature against using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the signature check passes, the raw `params` are handed unmodified to the event handlers, which instead key off a completely different, unverified field: `payload.dig('repository','full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`). Nothing binds these two fields together.

### Finding Description
`verify_signature` picks the GitHub App used for verification purely from an attacker-controlled JSON field: [1](#0-0) [2](#0-1) 

Shipit explicitly supports hosting multiple independent GitHub organizations from a single instance, each with its own `webhook_secret` (`docs/setup.md:181-216`). A tenant that legitimately administers one of these onboarded organizations (e.g. `OrgEvil`) knows their own `webhook_secret` — this is not a leaked or privileged credential, it is the credential the multi-org feature intentionally hands to each onboarded org.

Once `verify_webhook_signature` succeeds using `OrgEvil`'s own secret, the *entire, unmodified* JSON body is dispatched to event handlers: [3](#0-2) 

But every handler resolves the target `Repository`/`Stack` from a **different** field than the one used to select the verifying secret: [4](#0-3) 

Nothing checks that `repository.full_name`'s owner equals `repository_owner` (the field used to pick the verifying app/secret). So `OrgEvil` can send a webhook whose `repository.owner.login`/`organization.login` = `"OrgEvil"` (so it is verified with a secret `OrgEvil` legitimately possesses) while `repository.full_name` = `"OrgVictim/private-repo"` (so the handler acts on a stack that belongs to a completely different, unrelated tenant).

This breaks the intended binding:
`organization that authenticated (repository_owner used for HMAC secret selection) == repository that is written (repository.full_name used by Handler#stacks/#repository_name)`

### Impact Explanation
Concretely reachable handlers act on the forged `repository.full_name` without any re-validation against the authenticated org:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the branch of `OrgVictim`'s repository [5](#0-4) . If `continuous_deployment` is enabled on the victim's stack, this can drive an unauthorized deploy of a specific (attacker-chosen, already-existing) commit SHA on the victim's stack — a Critical, unauthorized-deploy outcome as defined by the reward scope.
- `CheckSuiteHandler#process` schedules check-run refreshes against arbitrary victim commits [6](#0-5) .
- `StatusHandler#process` writes commit statuses keyed only by `sha`, with no repository/stack scoping at all, meaning any tenant able to pass signature verification can inject fabricated CI statuses onto commits belonging to any repository tracked by the instance [7](#0-6) .

This constitutes cross-repository/cross-tenant writes and a path to an unauthorized deploy — matching the Critical impact bar in the rules.

### Likelihood Explanation
Likelihood requires the host to be configured with the documented multi-organization feature (`docs/setup.md:181-216`) and the attacker to control (as an unprivileged, non-victim tenant) at least one onboarded GitHub App/organization with its own `webhook_secret` — a configuration Shipit explicitly documents and supports, not a hypothetical. No `ApiClient` token, no GitHub App private key of the victim org, and no privileged Shipit account are required; only the attacker's own legitimately-issued webhook secret for their own org.

### Recommendation
After `verify_signature` selects the app/secret using `repository_owner`, re-validate that the owner of `repository.full_name` (and/or `organization.login`) in the same payload matches the organization whose secret verified the signature, rejecting the webhook (422) on mismatch. Handlers should also independently assert that the resolved `Repository`'s `owner` matches the authenticated organization before acting, rather than trusting `repository.full_name` unconditionally.

### Proof of Concept
1. Configure/observe a Shipit instance with two onboarded orgs, `OrgEvil` and `OrgVictim`, per the documented multi-app setup (`docs/setup.md:181-216`), each with distinct `webhook_secret`s.
2. As the legitimate admin of `OrgEvil`'s GitHub App, craft a `push` event payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<known-victim-commit-sha>",
     "repository": { "owner": { "login": "OrgEvil" }, "full_name": "OrgVictim/private-repo" }
   }
   ```
3. Sign the raw body with `OrgEvil`'s own `webhook_secret` using HMAC-SHA1, and set `X-Hub-Signature`.
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `Shipit.github(organization: "OrgEvil")` and successfully verifies the signature.
5. `PushHandler` resolves the target stack via `Repository.from_github_repo_name("OrgVictim/private-repo")` and enqueues `GithubSyncJob`/triggers deploy logic for a stack `OrgEvil` has no authorization over.
