### Title
Webhook signature verification is keyed on an attacker-controlled organization field while event handlers act on a different, independently attacker-controlled repository field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify the inbound webhook signature against using `repository_owner`, a value read straight out of the *unverified* JSON body. Once verification passes, the actual event handlers (`PushHandler`, `StatusHandler`, etc.) resolve the target `Stack`/`Repository` using `payload.dig('repository', 'full_name')` - a separate field from the same unverified body. Because `Shipit.github_app.verify_webhook_signature` returns `true` unconditionally when the selected organization has no `webhook_secret` configured, an attacker can pick, via the payload, whichever configured organization has a blank secret to trivially satisfy signature verification, while pointing `repository.full_name` at a stack belonging to a *different* organization that Shipit actually manages. This breaks the invariant `organization that authenticated == repository that is written`.

### Finding Description
- `verify_signature` derives the signing org purely from the payload, before any cryptographic check: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` short-circuits to `true` when no secret is configured for that organization: [3](#0-2) 

  Shipit's own docs/templates document `webhook_secret` as **optional**, and multiple sample/production config stanzas ship with it unset, so a org-with-no-secret is a realistic, documented configuration, especially in multi-org setups: [4](#0-3) [5](#0-4) 

- After signature "verification" passes, the handler layer resolves the affected `Repository`/`Stack` from a *different* payload field (`repository.full_name`), completely decoupled from whichever org was used to pick the webhook secret: [6](#0-5) [7](#0-6) 

- Concrete handlers then mutate/act on that resolved stack, e.g. `PushHandler` triggers a GitHub sync job for the target stack based only on attacker-supplied `ref`/`after`: [8](#0-7) 

  and `StatusHandler` writes a commit status onto any commit matching the attacker-supplied `sha`, independent of the "verified" org: [9](#0-8) 

Concretely: `Shipit.github(organization: repository_owner)` is looked up using `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`, both attacker-controlled JSON fields, prior to any signature check. If that organization's `webhook_secret` is `nil`/blank (an explicitly supported, documented configuration), `verify_webhook_signature` returns `true` for **any** (or missing) `X-Hub-Signature` header. The request then proceeds to dispatch handlers keyed off `payload['repository']['full_name']`, which the attacker can set independently to name any repository/stack actually configured in this Shipit instance (owned by a different, properly-secured organization). The equality the code implicitly (and incorrectly) assumes is:

`org used to select webhook_secret for signature check == org owning the repository the handler mutates`

but nothing enforces that the `owner.login` used for verification matches the `owner`/`name` embedded in `full_name` used for the actual write.

### Impact Explanation
This lets an unauthenticated, unprivileged attacker forge webhook events (`push`, `status`, `check_suite`, etc.) against any stack managed by the Shipit instance, as long as the deployment has at least one configured GitHub App/org with no `webhook_secret` (a state the project's own setup docs treat as normal/optional). Concretely reachable writes include:
- Forcing `Stack#sync_github` with an attacker-chosen `expected_head_sha` via `PushHandler`, causing Shipit to resync/re-fetch and treat attacker-influenced state as the branch head.
- Injecting arbitrary commit statuses via `StatusHandler#process` → `Commit#create_status_from_github!`, which can flip a commit from red to green and unblock the merge queue / deploy-safety checks that Shipit and its `shipit.yml` "required status" gating rely on.

Both are write paths into stack/commit state that legitimately should only be reachable by a verified webhook from the owning GitHub organization. This qualifies as an authentication-bypass class issue (crossing a credential/organization boundary to write into another organization's tracked repository state), matching the report's core theme of a validated set of data (deposit/HTP in the original; here the signing organization) being decoupled from the object actually mutated (bucket/pool state there; the target `Stack`/commit here).

### Likelihood Explanation
Likelihood depends entirely on deployment configuration: it requires (a) a multi-org (or even single, with unset secret) Shipit deployment where at least one configured GitHub App has no `webhook_secret`, and (b) the attacker knowing/guessing the `full_name` of a target repository already registered in the instance (repository names are not secret—stacks and repos are visible in the UI to any of Shipit's read-only surfaces or simply guessable from the org's public GitHub repos). Given the setup docs explicitly call `webhook_secret` "optional" and ship several templates with it blank by default, this is a plausible real-world configuration rather than a purely theoretical one.

### Recommendation
Bind the signature verification to the same repository identity the handler will act on:
- Verify the signature using the webhook secret belonging to the organization embedded in `repository.full_name` (or `organization.login` for org-only events), not solely `repository.owner.login`, and ensure both fields (when present) agree before dispatch.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank in a multi-org configuration—only permit the "no secret configured" bypass when exactly one GitHub App is configured for the whole instance and no ambiguity in target-organization exists.
- Add a check in `Handler#stacks`/`Handler#repository_name` that the resolved `Repository#owner` matches the organization that was actually verified in `verify_signature`, rejecting the event if they differ.

### Proof of Concept
Preconditions: Shipit instance configured with two GitHub Apps, `OrgA` (has `webhook_secret` set) and `OrgB` (no `webhook_secret`, i.e., `nil`), and a `Stack` under `OrgA/private-repo` exists.

1. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/private-repo" },
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
2. `verify_signature` computes `repository_owner == "OrgB"`, fetches `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the (absent or garbage) `X-Hub-Signature` header. [3](#0-2) 
3. Request proceeds to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("OrgA/private-repo")` (from `full_name`, unrelated to the verified "OrgB"), and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on `OrgA`'s stack. [8](#0-7) [6](#0-5) 

This demonstrates a full round trip where the "authenticated" organization (`OrgB`, trivially bypassed) and the repository actually written to (`OrgA/private-repo`) are decoupled, with no code path enforcing their equality.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
