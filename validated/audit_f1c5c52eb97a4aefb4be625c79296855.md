### Title
Health-check readiness flag is set once and never unset, masking persistent sync failures - ([File: main.go])

### Summary
The external report's root cause is a state variable (`feeds[token]`) that can only be set once and can never be updated or cleared, so the system cannot reflect that a previously-valid configuration is no longer valid — leading to persistent denial of correct behavior. The analogous pattern in `git-sync` is the package-level `repoReady` flag: it is guarded by a mutex but only ever has a setter (`setRepoReady`), never a corresponding "unset"/reset function, so once a sync has succeeded, the HTTP readiness/health endpoint reports "ready" forever, regardless of any subsequent sync failures.

### Finding Description
`repoReady` is a global boolean guarded by `readyLock`, with only two accessors: `getRepoReady()` and `setRepoReady()`. There is no `clearRepoReady()` or equivalent, so the flag is monotonic — it can transition from `false` to `true`, but never back. [1](#0-0) 

In the main sync loop, `setRepoReady()` is called after every successful `SyncRepo` call, and again inside `SyncRepo` itself immediately after a successful publish. Crucially, when `SyncRepo` returns an error (e.g., due to a fetch failure, an unreachable/renamed ref, upstream repo deletion, or repeated network/auth failures), the code only increments `failCount` and logs an error — it never calls a corresponding "not ready" function. [2](#0-1) [3](#0-2) 

This is structurally the same "write-once" defect described in the report: a piece of state that reflects a point-in-time condition ("this feed/this repo is valid and working") is captured once and then treated as permanently true, with no mechanism to invalidate it when the underlying condition (a working feed address / a working sync) stops holding.

### Impact Explanation
Because `repoReady` can only be set and never cleared, the HTTP readiness endpoint exposed by `git-sync` will continue to report success (e.g., `200`) even after the sync loop starts failing continuously (broken ref, upstream outage, revoked credentials, exhausted retries below `--max-failures`). In a Kubernetes sidecar deployment, this readiness probe is what gates whether the pod is considered healthy/ready to serve traffic. A permanently "stuck-true" readiness value means orchestration tooling cannot detect that the synced content is stale or that syncing has silently died, which can result in serving indefinitely stale/wrong content without any automated remediation (restart/reschedule) being triggered — a persistent-sync-denial condition that isn't surfaced through the intended health-check contract.

### Likelihood Explanation
This does not require a malicious operator or a leaked key — it is reachable simply by any condition that causes recurring sync failures after at least one prior success (e.g., an attacker-controlled ref/branch being force-pushed to something that breaks `git fetch`/checkout, or the remote temporarily becoming unreachable). This is a realistic, unprivileged, naturally-occurring scenario in the normal operation of the sidecar, not a contrived edge case.

### Recommendation
Add a corresponding "clear ready" path that is invoked when `SyncRepo` returns an error (particularly once `failCount` exceeds some threshold, or on every failure), e.g. a `clearRepoReady()` function mirroring `setRepoReady()`, so the readiness state can transition back to `false` when sync health degrades: [4](#0-3) 
This would make the readiness signal accurately reflect current sync health instead of being a one-way latch.

### Proof of Concept
1. Start `git-sync` against a reachable repo/ref; wait for the first successful sync — `setRepoReady()` fires and the HTTP health endpoint returns `200`. [5](#0-4) 
2. Cause subsequent syncs to fail persistently (e.g., force-push the tracked branch to a broken/garbage state, or block network access to the remote), so `SyncRepo` returns an error on every loop iteration. [4](#0-3) 
3. Query the health endpoint repeatedly — because `repoReady` was already set to `true` and there is no code path that resets it to `false`, the endpoint keeps reporting healthy/ready even though the repo has not been successfully synced for an arbitrary length of time, hiding the persistent sync failure from any monitoring/orchestration relying on that signal. // repoReady indicates that the repo has been synced.
var readyLock sync.Mutex
var repoReady = false

func getRepoReady() bool {
	readyLock.Lock()
	defer readyLock.Unlock()
	return repoReady
}

func setRepoReady() {
	readyLock.Lock()
	defer readyLock.Unlock()
	repoReady = true
}
