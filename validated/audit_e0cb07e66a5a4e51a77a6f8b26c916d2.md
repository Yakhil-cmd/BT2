Based on the evidence gathered, I can identify a valid analog vulnerability in the multi-organization webhook signature verification flow.

### Title
Webhook signature verification selects the GitHub App/secret from an attacker-controlled payload field that is decoupled from the repository the event handlers act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports hosting multiple GitHub organizations on a single Shipit instance, each with its own GitHub App and `webhook_secret` [1](#0-0) , backed by `Shipit.github(organization:)` which looks up per-organization config [2](#0-1) . The `WebhooksController` picks which organization's secret to verify the incoming signature against by reading `repository.owner.login` (or `organization.login`) straight out of the **unverified** JSON body, before the signature has been checked [3](#0-2) [4](#0-3) . The signature is then verified only against that one field's secret via `verify_webhook_signature` [5](#0-4) , and the entire raw payload — including any other embedded repository identifiers used later by event handlers — is passed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) .

### Finding Description
The binding that should hold is: *the organization whose secret authenticated the request* == *the repository/organization the event handlers act on*. `verify_signature` only proves the request holder knows the `webhook_secret` for whatever organization `repository_owner` names in the JSON body; it does not prove that the rest of the payload (e.g. `repository.full_name`, commit SHAs, PR data used downstream by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, and the `PullRequest::*Handler`s) actually belongs to that same organization. Because HMAC verification only certifies the raw bytes came from a holder of *some* configured secret, and the organization used to pick that secret is attacker-supplied and unchecked against the object it's nested inside for internal consistency, an operator of one tenant organization on a shared multi-org Shipit instance (who legitimately possesses their own `webhook_secret`, since that secret is generated by whoever registers the GitHub App per `docs/setup.md` §"Webhook secret") can construct a payload where `repository.owner.login`/`organization.login` names their own org (to pass signature verification with their known secret) while other repository-identifying fields inside the same JSON reference a different, victim organization's repository/stack.

### Impact Explanation
If successful, this allows a tenant of a multi-org Shipit deployment to inject forged webhook events (pushes, commit statuses, check-suite completions, pull-request events, membership changes) that are attributed to and acted upon a different organization's stacks, without ever knowing that victim organization's `webhook_secret`. Depending on which handler is targeted, this could trigger unauthorized `GithubSyncJob`s, fake commit/deployable statuses that unblock deploy gating, or forged `check_suite`/`pull_request` events feeding the merge queue — i.e., cross-repository/cross-tenant interference in the deploy pipeline, which the rules classify as a cross-repository write / unauthorized deploy path.

### Likelihood Explanation
This requires the deployment to use the documented multi-organization configuration (an explicitly supported, documented feature — not an undocumented mounting assumption) and requires the attacker to be an administrator of at least one tenant organization on that shared instance (who can legitimately obtain their own `webhook_secret`). No GitHub App private key, `ApiClient` token, or Shipit session is needed — only a raw HTTP POST to `/webhooks` with a crafted body and computed HMAC. I was not able to fully inspect `PushHandler`/`StatusHandler`/`CheckSuiteHandler` internals in this session (tool errors prevented reading their contents) to confirm exactly which payload field each handler uses to resolve the target `Stack`/`Repository`, so the precise handler-level exploitability (i.e., whether `repository.full_name` vs `repository.owner.login` are cross-checked anywhere downstream) is not fully verified.

### Recommendation
Have `verify_signature` re-derive/validate the organization used for the App lookup from a value that is cryptographically tied to the payload as a whole (e.g., verify against every configured organization's secret and require the matching organization to equal the repository's actual owner used by the handler), or reject payloads where `repository.owner.login`/`organization.login` doesn't match the owner segment of `repository.full_name`. More generally, ensure the same trust-anchor field is used both to select the verification secret and to scope which `Stack`/`Repository` a handler is allowed to mutate.

### Proof of Concept
1. Attacker is an admin of `OrgA`, a tenant configured in Shipit's multi-org `github:` config, and knows `OrgA`'s `webhook_secret` (they generated it when registering their GitHub App, per `docs/setup.md`).
2. Attacker crafts a JSON body such as:
```json
{
  "action": "opened",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  },
  ...
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)`.
4. `repository_owner` resolves to `"OrgA"` [4](#0-3) , `Shipit.github(organization: "OrgA")` loads OrgA's app/secret [7](#0-6) , and `verify_webhook_signature` succeeds since the attacker signed correctly with the secret they legitimately know [5](#0-4) .
5. The full, unvalidated `params` (containing `OrgB/victim-repo`) is dispatched to the registered handlers [6](#0-5) , potentially causing state changes against `OrgB`'s stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
