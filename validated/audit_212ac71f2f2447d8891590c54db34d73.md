### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` merging into the single trust-blind `Commit#create_status_from_github!` chokepoint - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits globally by SHA (`Commit.where(sha: params.sha)`) with no repository/stack scoping, then writes a `Status` through `Commit#create_status_from_github!`, the same method used by the API-trusted `refresh_statuses!`. Because `Status` carries no provenance of which repository actually produced it, a validly-signed webhook for one repository can create a `Status` row consulted by `deployable?`/`all_status_checks_passed?` for a commit that belongs to a *different* stack/repository, as long as the SHA happens to collide (e.g. an unmodified fork shares identical commit SHAs with its upstream).

### Finding Description
The broken binding: for every `Status` created via `create_status_from_github!`, it must hold that `status.commit.stack.repository.full_name == <verified source repository of the webhook>`. No such field exists on `Status` (`app/models/shipit/status.rb:1-33`), and no such check exists in the write path, so the equality can never be enforced.

Code path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) validates the HMAC signature against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-supplied JSON body (`params.dig('repository','owner','login')`). This only proves the payload was actually sent by GitHub for *some* app/org context — it does not bind the payload's `sha` to that repository.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a raw, cross-stack, cross-repository query — it never calls the `stacks` helper (`Handler#stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-34`) that filters by `Repository.from_github_repo_name(repository_name)`. Compare this to the codebase's own established convention: `CheckSuiteHandler#process` and `PushHandler#process` both scope through `stacks.where(...)` before touching any commit [1](#0-0) [2](#0-1) . `StatusHandler` alone omits this scoping.
- `create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) then calls `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/status.rb:24-33`) unconditionally for whatever `commit` was matched by the global SHA lookup, tagging it only with `commit.stack_id` — never checking that `commit.stack_id`'s repository matches the webhook's originating repository.
- Downstream, `add_status` (`app/models/shipit/commit.rb:366-386`) fires `Hook.emit(:commit_status, ...)`/`:deployable_status` and schedules `stack.schedule_merges`, and `MergeRequest#all_status_checks_passed?` / `Commit#deployable?` (`app/models/shipit/merge_request.rb:193-197`, `app/models/shipit/commit.rb:227-229`) consult the resulting `Status` rows identically regardless of origin.

Exploit: git commit SHAs are content-addressed hashes of tree+parents+author/committer+message+timestamps. An unmodified fork of a public repository retains byte-identical SHAs for every pre-fork commit. An attacker who owns a fork/repo that is within the scope of *any* Shipit-trusted GitHub App installation (their own account/org onboarded to a multi-tenant Shipit instance, per `docs/setup.md`'s "Using Multiple Github Applications") can trigger a real, GitHub-signed `status` event for their own repo carrying a SHA that is identical to a commit tracked by an unrelated victim stack. GitHub signs and delivers this webhook genuinely; `verify_signature` passes because the signature is legitimately computed by GitHub for the attacker's own org/repo. `StatusHandler#process` then finds and updates the *victim's* `Commit` row (matched purely by SHA), injecting an arbitrary `state`/`context`/`description` (e.g. `state: success`, `context: <required-CI-context>`) that the victim stack's merge queue or deploy pipeline will treat as its own CI result.

Why guards don't catch it: `verify_signature` only authenticates "a legitimate GitHub App sent this," not "this SHA belongs to the repository named in the payload." `drop_unhandled_event` only filters by event type. `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.), not repository ownership. `Repository.from_github_repo_name`/`Handler#stacks` exist precisely to perform that binding but are never invoked by `StatusHandler`.

### Impact Explanation
Impact: Critical — a payload legitimately authenticated for one repository/tenant mutates another repository's stack/commit state, and this false `Status` is consulted identically by `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) and `MergeRequest#all_status_checks_passed?` (`app/models/shipit/merge_request.rb:193-197`), which gates `ProcessMergeRequestsJob#perform` (`app/jobs/shipit/process_merge_requests_job.rb:21-26`) into calling `merge_request.merge!` — an unauthorized merge/deploy driven by forged CI status for a repository the attacker never controls. Blast radius spans every stack/tenant hosted on the same Shipit instance whose repositories share commit history (forks, mirrors, template repos) with any repository under the attacker's control.

### Likelihood Explanation
Requires: (1) the Shipit instance hosting multiple orgs/repos (single documented supported configuration, `docs/setup.md` "Using Multiple Github Applications"), (2) the attacker owning/controlling a repository whose GitHub App webhook delivery is legitimately signed by a Shipit-trusted app (their own fork/repo onboarded to that app installation), and (3) SHA collision between the attacker's repository and a target commit, which is trivially satisfied for unmodified forks of public repos or shared history among stacks tracked in the same instance. No secrets, sessions, or privileged roles are needed by the attacker — only a genuine GitHub-signed webhook from their own repository, which they get for free by pushing/forking normally. Fully repeatable and automatable against any commit SHA the attacker can reproduce.

### Recommendation
Scope `StatusHandler#process` the same way as `CheckSuiteHandler`/`PushHandler`: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` from the webhook payload, and restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), so a `Status` can only be written for a commit belonging to a stack whose repository matches the verified webhook's `repository.full_name`. Additionally consider persisting a provenance/source column on `Status` if defense-in-depth against payload spoofing of the `repository` field itself is desired.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "Status has no provenance column distinguishing webhook origin from API-poll origin" do
          refute Status.column_names.include?('source'),
                 "expected no provenance column to exist yet, proving the binding cannot be checked"
        end

        test "StatusHandler#process writes a Status for a commit belonging to an unrelated stack/repo" do
          victim_stack = shipit_stacks(:shipit)          # repository e.g. "shopify/shipit-engine"
          attacker_stack = shipit_stacks(:cyclimse)       # unrelated repository e.g. "attacker/fork"

          shared_sha = 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef'
          victim_commit = victim_stack.commits.create!(
            sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus),
            authored_at: Time.now, committed_at: Time.now, message: 'victim commit'
          )

          # Payload legitimately signed for the ATTACKER's own repo (attacker_stack's repository),
          # but referencing a sha that collides with the victim's commit.
          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'ci/required',
            'repository' => { 'full_name' => attacker_stack.repository.github_repo_name,
                               'owner' => { 'login' => attacker_stack.repository.owner } }
          }

          assert_difference -> { victim_commit.statuses.count }, 1 do
            StatusHandler.call(payload)
          end

          # Binding check: the Status written for victim_commit did NOT originate from
          # victim_stack.repository.full_name -- it came from attacker_stack's verified webhook.
          written_status = victim_commit.statuses.last
          assert_equal victim_stack.id, written_status.stack_id
          refute_equal attacker_stack.repository.full_name, victim_stack.repository.full_name,
                       "attacker's verified repo differs from victim's repo, yet the Status was still written"

          assert victim_commit.deployable?, "forged status now makes an unrelated tenant's commit deployable"
        end
      end
    end
  end
end
```
This demonstrates: (a) no schema-level provenance field exists to check the binding, and (b) `StatusHandler#process`, given a payload validly signed for one repository, still mutates a `Commit`/`Status` belonging to a different, unrelated stack purely via SHA match — feeding directly into `deployable?`/`all_status_checks_passed?`.
