### Title
Cross-organization webhook forgery due to unbound organization-vs-repository fields - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound GitHub webhook using `repository_owner`, a field read from the payload (`repository.owner.login`/`organization.login`), while the payload's `repository.full_name` field — an entirely separate, unauthenticated field — is what all downstream `Webhooks::Handlers` use to resolve which `Stack`/`Repository` to act on. Nothing ties these two fields together, so the "organization that authenticated" and the "repository that is written" are never checked for consistency.

### Finding Description
`verify_signature` computes the org used for secret lookup purely from the payload: [1](#0-0) [2](#0-1) 

That org name is used to fetch a `GitHubApp` instance and its `webhook_secret`, then verify the HMAC over the raw request body: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when the resolved organization has no `webhook_secret` configured — a supported, documented configuration for any org in a multi-org Shipit deployment (`github.<org>.webhook_secret` may be left blank): [4](#0-3) [5](#0-4) 

Once the request passes this check (or the request is legitimately unsigned because a secret-less org was targeted for verification purposes), the *entire raw JSON body* — unmodified — is dispatched to handlers: [6](#0-5) 

All handlers resolve the target `Stack`/`Repository` from a *different* payload field, `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` used earlier for authentication: [7](#0-6) [8](#0-7) 

`PushHandler`, for example, uses this unbound `full_name`-derived repository lookup to schedule a resync of any matching stack: [9](#0-8) 

Because `repository.owner.login` (checked for authentication) and `repository.full_name` (used to select the acted-upon `Stack`) are independent JSON fields with no relationship enforced in code, an attacker can set `repository.owner.login`/`organization.login` to any organization configured **without** a `webhook_secret` (satisfying `verify_signature` trivially, since `return true unless webhook_secret`), while setting `repository.full_name` to `"<secured-org>/<target-repo>"` belonging to a completely different, secured organization. This decouples the "organization that authenticated" from the "repository that is written," breaking the intended binding: `authenticated_org(payload.repository.owner.login) == acted_upon_repo_owner(payload.repository.full_name)` — which the code never enforces.

### Impact Explanation
This lets an unauthenticated, unprivileged attacker trigger webhook handlers (e.g. `PushHandler`, pull-request handlers, `review_stack` provisioning/archival, label handlers) against any `Stack`/`Repository` configured in the Shipit instance, as long as at least one org in that multi-tenant deployment has no `webhook_secret` set — a config state explicitly supported and documented, not requiring any secret, token, or repository access from the attacker. This can force premature `sync_github` calls (potentially advancing continuous-deployment pipelines) or manipulate review-stack archive/unarchive/provisioning state for a repository the attacker has no relationship to, i.e. an unauthorized deploy/action trigger against a repository outside the "authenticated" organization's scope.

### Likelihood Explanation
Requires: (1) the target Shipit instance to use the multi-organization GitHub app config (`Shipit.github(organization:)`), and (2) at least one configured organization with a blank `webhook_secret`. Both are normal, documented configurations (`docs/setup.md`, `config/secrets.development.example.yml`), so this is plausible in real multi-tenant Shipit deployments without requiring any credential compromise — only knowledge of the login name of the unsecured organization, which is discoverable from that org's own legitimate webhook traffic/stack pages.

### Recommendation
Bind the two fields together: derive the acted-upon repository strictly from the same organization that was cryptographically verified (or vice versa), e.g. reject the request if `payload.dig('repository','full_name')&.split('/')&.first != repository_owner` (case-insensitively), or require every configured organization to have a non-blank `webhook_secret` and refuse to boot/serve webhooks otherwise.

### Proof of Concept
1. Deploy Shipit configured with two orgs: `safe-org` (has `webhook_secret` set) and `open-org` (has `webhook_secret` left blank), per `config/secrets.development.example.yml`.
2. POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<any-real-sha-of-safe-org/target-repo>",
  "repository": { "owner": { "login": "open-org" }, "full_name": "safe-org/target-repo" }
}
```
No `X-Hub-Signature` header, or any garbage value, is required.
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"open-org"` [2](#0-1) , fetches `open-org`'s (blank) secret, and `verify_webhook_signature` returns `true` unconditionally [4](#0-3) .
4. `PushHandler` resolves the stack via `repository.full_name = "safe-org/target-repo"` [7](#0-6)  and calls `stack.sync_github(expected_head_sha: ...)` on the `safe-org` stack [9](#0-8)  — despite the request only having been "authenticated" as `open-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
