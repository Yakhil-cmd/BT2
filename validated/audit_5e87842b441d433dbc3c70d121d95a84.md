### Title
Creator fees permanently frozen if the pool creator's associated token account is frozen/blocked - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` are the only two instructions that release the pool creator's accumulated `creator_fees_token_0`/`creator_fees_token_1` from the vaults. Both instructions hard-bind the destination token account to a PDA derived from the `creator` address (`associated_token::authority = creator`), with no parameter to redirect the transfer to a different recipient account, mirroring the exact bug class described in the referenced Ajna report (borrower/kicker funds frozen because the beneficiary address cannot be substituted).

### Finding Description
In `CollectCreatorFee`, `creator_token_0`/`creator_token_1` are constrained to `associated_token::authority = creator`, i.e., the fixed ATA of the `pool_creator` recorded immutably in `pool_state` [1](#0-0) . The permissionless variant has the identical constraint, only relaxing who can pay for/trigger the instruction, but still requiring the destination be the creator's own ATA [2](#0-1) .

The actual transfer is a standard `transfer_checked` CPI with no fallback recipient logic [3](#0-2) . If the mint (e.g. a Token-2022 mint with a freeze authority, permanent delegate, or a transfer-hook based allow/deny-list) freezes or blocks the creator's specific ATA/authority — a Token-2022 analog of an ERC-20 "blacklist" — `transfer_checked` into `creator_token_0`/`creator_token_1` will permanently fail. There is no way to specify an alternate recipient address for either instruction, so `pool_state.creator_fees_token_0`/`creator_fees_token_1` accrue at the vault indefinitely and can never be withdrawn [4](#0-3) .

By contrast, `Withdraw`'s `token_0_account`/`token_1_account` only carry a `token::mint` constraint with no `token::authority` requirement, letting the LP owner redirect proceeds to any compatible token account they choose, avoiding this freeze scenario for LP withdrawals [5](#0-4) . No equivalent escape hatch exists for creator fee collection.

### Impact Explanation
Creator fees (`creator_fees_token_0`/`creator_fees_token_1`) accumulate continuously from every swap through the pool's fee split and are only ever releasable to the creator's fixed ATA. If that specific account/authority becomes frozen or blocked (freeze authority action, or a mint using Token-2022 extensions such as a transfer hook/permanent delegate that can restrict a given address), the pool creator's accrued fee funds become permanently locked in `token_0_vault`/`token_1_vault` with no recovery path — matching the "permanent freezing of user funds" impact class.

### Likelihood Explanation
This requires the creator's own token account/authority to become frozen or blocked by the specific mint's extension configuration (e.g., a Token-2022 mint with freeze authority or a restrictive transfer hook chosen for the pool). This is a low-probability, mint-dependent event, similar to the "low probability" characterization in the referenced report, but the resulting fund lock is total and irreversible for a legitimate, unprivileged pool creator.

### Recommendation
Add an optional `recipient`/authority override capability to `collect_creator_fee` (and consider similarly for `collect_creator_fee_permissionless`), or allow the creator to sign a request specifying a destination account not constrained to their own ATA authority, so accrued fees can be redirected to a non-frozen address if the primary account becomes unusable.

### Proof of Concept
1. Create a pool with a Token-2022 mint for `token_0` that has a freeze authority (or an equivalent extension capable of blocking a specific account).
2. Perform swaps so that `pool_state.creator_fees_token_0` accrues a nonzero balance.
3. Freeze the pool creator's associated token account for `token_0` (or otherwise make transfers to it fail) using the mint's freeze authority.
4. Call `collect_creator_fee` (or `collect_creator_fee_permissionless`): the `transfer_checked` CPI in `transfer_from_pool_vault_to_user` fails because the destination `creator_token_0` is frozen, and since the destination is hard-constrained to `associated_token::authority = creator` with no alternate-recipient parameter, the accrued `creator_fees_token_0` remains permanently stuck in `token_0_vault`.

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;

```

```rust
pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
```
