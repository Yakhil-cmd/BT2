### Title
Unvalidated route pool can execute attacker code and steal unrelated wallet tokens - (File: contracts/swap-aggregator/src/venues/aquarius/pool.rs)

### Summary
`execute_strategy` accepts caller-supplied pool addresses for every hop and invokes those contracts without any venue allowlist or contract-identity validation. [1](#0-0) [2](#0-1)  A malicious pool can call `token.transfer(victim, attacker, amount)` on any unrelated token held by the victim; the authorization for that transfer is recorded as a child of the victim’s signed controller invocation. [3](#0-2) 

### Finding Description
A route contains an arbitrary `assets` registry and compact instructions whose indices identify the pool, input token, and output token. [1](#0-0)  `Program::decode` checks only sizes, opcodes, registry bounds, token-chain structure, split weights, and related syntax; it does not check that a pool address identifies an authentic venue contract. [4](#0-3) [5](#0-4) 

During execution, `execute_op` resolves `hop.pool` directly from the caller-controlled registry and passes it to `venues::dispatch_hop`. [6](#0-5)  For an Aquarius hop, the router queries the arbitrary address’s `get_tokens` method and then invokes its `swap` method. [7](#0-6) [8](#0-7) [2](#0-1) 

The exploit is not limited to the amount routed through the swap. The repository’s auth-tree test deploys a rogue pool whose `swap` method calls `token::Client::transfer(victim, attacker, WALLET_BALANCE)` on a token unrelated to the route. [9](#0-8)  Transaction simulation places that theft as a sub-invocation under the victim’s `swap_collateral` authorization, and submitting the returned poisoned tree authorizes the transfer. [3](#0-2) [10](#0-9) 

### Impact Explanation
This permits theft of user funds beyond the declared swap input. The test demonstrates a victim holding `77,770,000,000` units of an unlisted wallet token losing the full balance while receiving a nominal fair swap output. [11](#0-10) [12](#0-11) 

The balance measurements in `dispatch_hop` protect only the router’s declared input/output accounting and cannot observe or bound a token transfer made directly from the victim to the attacker by third-party code. [13](#0-12)  The same exposure applies to controller strategy routes, where the controller invokes the configured router with caller-supplied swap bytes. [14](#0-13) 

### Likelihood Explanation
A single unprivileged account can create and submit a malicious route through `swap_collateral` or another route-taking controller strategy; the test constructs the route with an attacker-controlled `hop_pool`, legitimate input/output tokens, and a plausible `min_out`. [15](#0-14) [16](#0-15) 

Exploitation requires the victim to sign the authorization tree produced for the poisoned route, but the added child is structurally hidden beneath a normal `swap_collateral` invocation rather than appearing as a separate top-level authorization. [17](#0-16)  If a wallet or quote client presents route bytes and authorization trees without fully decoding and independently validating every nested transfer, the malicious operation can appear economically valid because the rogue pool can arrange a fair-looking output.

### Recommendation
Introduce an owner- or governance-managed venue/pool allowlist and require every hop’s `pool` to be registered for the selected `SwapVenue` before invoking it. Validation should occur during `Program::decode` or before the first external call in `dispatch_hop`.

At minimum, store approved `(venue, pool)` pairs and reject unknown addresses:

```rust
if !storage::is_approved_pool(env, hop.venue, &hop.pool) {
    panic_with_error!(env, Error::PoolNotApproved);
}
```

The allowlist should be populated through governance rather than inferred from interface calls, because a malicious contract can trivially implement `get_tokens`, `share_id`, and `swap`. Clients should also decode every route and refuse authorization trees containing child invocations other than the expected input transfer.

### Proof of Concept
The repository already contains a concrete reproduction in `rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

1. The victim supplies USDC and holds a separate wallet token that is unrelated to the listed swap markets. [18](#0-17) 
2. A malicious pool is configured with `(victim, wallet_token, attacker, WALLET_BALANCE)`; its `swap` function transfers the wallet token from the victim to the attacker. [19](#0-18) 
3. A route names that contract as `hop_pool` while presenting USDC as `token_in`, ETH as `token_out`, and a plausible output amount. [15](#0-14) 
4. Simulation records the wallet-token theft under the victim’s `swap_collateral` authorization root. [20](#0-19) 
5. Signing the returned poisoned tree allows the malicious transfer; Alice’s wallet balance becomes zero and the attacker receives the full balance. [10](#0-9)

    /// Validates every instruction's opcode, mode, and indices before execution begins,
    /// including the `Prev` chain, same-token swaps, and split-weight bounds.
    fn validate(&self, env: &Env, assets_len: u32, amounts_len: u32, weight_count: u32) {
        for i in 0..self.op_count {
            let record = self.raw(i);
            let Some(opcode) = Opcode::from_u8(record[field::OPCODE]) else {
                panic_with_error!(env, Error::InvalidRouteXdr);
            };
            let mode = Mode::from_u8(record[field::MODE]);
            let (idx_a, idx_b, idx_c) = (
                record[field::POOL] as u32,
                record[field::TOKEN_IN] as u32,
                record[field::TOKEN_OUT] as u32,
            );

            // `Prev` is a purely structural link: the predecessor must exist,
            // must have a single output, and that output must be this
            // instruction's input.
            if mode == Mode::Prev {
                if i == 0 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
                let previous = self.raw(i - 1);
                let produced = match Opcode::from_u8(previous[field::OPCODE]) {
                    // A swap produces its `token_out`, a mint its share token.
                    Some(Opcode::Swap(_)) => previous[field::TOKEN_OUT],
                    Some(Opcode::Mint) => previous[field::TOKEN_IN],
                    // A burn releases every constituent at once.
                    _ => panic_with_error!(env, Error::BrokenTokenChain),
                };
                if idx_b != produced as u32 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
            }
            match mode {
                Mode::Fixed(idx) if idx as u32 >= amounts_len => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                Mode::Ppm(idx) if idx as u32 >= weight_count => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                _ => {}
            }

            if idx_a >= assets_len || idx_b >= assets_len {
                panic_with_error!(env, Error::InvalidRouteXdr);
            }
            match opcode {
                Opcode::Swap(_) => {
                    if idx_c >= assets_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_b == idx_c {
                        panic_with_error!(env, Error::SameToken);
                    }
                }
                // Liquidity legs spend the full vault balance, so only `Mode::All` is valid.
                Opcode::Burn | Opcode::Mint => {
                    if mode != Mode::All {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_c >= amounts_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                }
            }
        }
