### Title
Webhook signature check keys off an unverified `repository.owner.login`/`organization.login` field, letting an attacker choose which GitHub organization's secret is checked while a different repository's stacks are acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to verify the `X-Hub-Signature` against using a field taken directly from the *unauthenticated* JSON body, before the signature has been checked. Because `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatic success, an attacker who knows (or can guess) that any configured organization has no `webhook_secret` set can pick that organization for the verification step while pointing the payload's `repository.full_name` at a completely different organization/repository whose stacks then get processed by the event handler. This is the same class of bug as the reported issue: an identifier used to select a resource/credential is not covered by the same integrity check that protects the rest of the request, so the value used for authorization/verification and the value used for the actual action diverge.

### Finding Description
In multi-organization mode, `verify_signature` does: [1](#0-0) 

`repository_owner` is derived purely from the JSON body, which is fully attacker-controlled at this point since the signature has not yet been validated: [2](#0-1) 

`Shipit.github(organization:)` looks up the `GitHubApp` config for whatever organization string is supplied: [3](#0-2) 

`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization: [4](#0-3) 

Once the signature "passes" (using organization A's - possibly secret-less - config), `create` dispatches the same raw payload to the event handler: [5](#0-4) 

The handler base class then resolves the target stacks using a **different** field from the very same payload - `repository.full_name` - which has no relationship to the organization that was used for signature verification: [6](#0-5) 

So the binding that should hold - "the organization whose secret authenticated this request" == "the repository/stacks the handler acts on" - is broken. An attacker can set `repository.owner.login` (or `organization.login`) to organization A (chosen because it has no `webhook_secret`, or because its secret is known/weak) purely to satisfy `verify_signature`, while setting `repository.full_name` to `victim-org/victim-repo` so that `PushHandler`, `StatusHandler`, or `CheckSuiteHandler` acts on victim-org's stacks: [7](#0-6) [8](#0-7) [9](#0-8) 

### Impact Explanation
`StatusHandler` writes commit CI statuses via `Commit#create_status_from_github!`, and `PushHandler`/`CheckSuiteHandler` trigger `sync_github`/check-run refresh for arbitrary stacks resolved solely from the attacker-supplied `repository.full_name`. If any deploy gating logic in the host relies on commit CI status (`Status`) records populated this way, an attacker can forge green CI statuses for a victim repository's commits without ever presenting a valid signature for that repository's organization, undermining the "which organization authenticated this webhook" vs. "which repository/stacks are written by it" binding. This does not directly grant RCE, but it is an unauthenticated write path into a stack's commit/status state gated only by the accidental existence of a secret-less org (or a leaked/guessed secret for an unrelated org), which several downstream flows treat as trusted GitHub-origin data.

### Likelihood Explanation
This requires a Shipit deployment to run in multi-organization mode (`github_organizations`) with more than one org configured, and at least one configured organization lacking a `webhook_secret` (or an attacker who has obtained/guessed one org's secret). This is a plausible, non-privileged configuration state - `webhook_secret` is optional per the `verify_webhook_signature` code path itself - and no session, API token, or repository write access is needed; only an outbound HTTP POST to the public `/github/webhooks` endpoint (routed to `WebhooksController#create`) is required.

### Recommendation
Do not let a payload field select the verification credential before the signature is validated. Instead: (1) verify the signature against every configured organization's secret (or require the target organization to be explicit and independently authenticated, e.g., via a URL path segment tied to the org), and (2) ensure the same, already-verified organization/repository identity is what the handler subsequently acts on - i.e., cross-check that `repository.full_name`'s owner matches the organization whose secret validated the signature, and reject requests where they diverge. Also consider treating a missing `webhook_secret` as a hard configuration error rather than an automatic pass.

### Proof of Concept
1. Deploy Shipit configured with two organizations in `github_organizations`: `org-a` (no `webhook_secret` set) and `org-b` (victim, has stacks tracked).
2. POST to the webhooks endpoint with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged"
}
```
3. `verify_signature` calls `Shipit.github(organization: "org-a")`; since `org-a` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of any `X-Hub-Signature` header (or its absence).
4. `StatusHandler` resolves `Commit.where(sha: params.sha)` via `org-b/victim-repo`'s stacks and writes an attacker-controlled `Status` record for that commit, despite no valid signature ever being presented for `org-b`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
