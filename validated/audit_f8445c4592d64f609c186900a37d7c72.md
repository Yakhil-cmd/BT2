### Title
Cross-Organization Webhook Spoofing via Signature/Repository Binding Mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a value pulled from `repository.owner.login` (falling back to `organization.login`). The verified HMAC only proves the request was signed by *that* organization's secret. However, the code that subsequently acts on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name` / `#stacks`) resolves the target `Repository`/`Stack` from an entirely different, independently-controlled field: `repository.full_name`. Nothing in the engine cross-checks that the organization used to select the verifying secret is the same organization that owns the repository actually acted upon.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`lib/shipit/github_app.rb#verify_webhook_signature` returns `true` unconditionally when the resolved app has no `webhook_secret` configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

Meanwhile, every handler resolves the repository/stack that will actually be mutated from a *separate* JSON field, never reconciled with `repository_owner`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Shipit's own documented multi-tenant deployment model (`Shipit.github(organization:)`) supports hosting several GitHub organizations behind one Shipit instance, each with its own `webhook_secret` in `secrets.yml`: [4](#0-3) 

The binding that should hold is:
`organization whose secret authenticated the request == organization owning the repository the handler writes to`

Because `repository_owner` (used for signature selection) and `repository.full_name` (used for repository/stack resolution) are two independent, attacker-supplied JSON fields with no cross-validation, this equality is never enforced. If any one configured organization on the instance has no `webhook_secret` set — an accepted configuration shape shown in the engine's own sample config (`config/secrets.development.shopify.yml` lists `webhook_secret: # nil`) — `verify_webhook_signature` trivially returns `true` for that organization with **no signature at all**. An attacker can then set `repository.owner.login` to that unsecured organization (satisfying `verify_signature`) while setting `repository.full_name` to `"<secured-org>/<target-repo>"`, causing handlers to act on a completely different, protected organization's `Stack`.

### Impact Explanation
This breaks the trust boundary between organizations sharing one Shipit deployment: an entirely unauthenticated request (zero credentials, no `webhook_secret` required) can trigger `PushHandler#process` (`stack.sync_github`), archive/unarchive review stacks via the label handlers, or drive review-stack provisioning for stacks belonging to an organization that *does* have a properly configured, secret-protected GitHub App — because signature verification and target-resolution use disjoint, unauthenticated fields of the same JSON body. This is a cross-organization/cross-repository write capability achieved purely by binding confusion, matching the "organization authenticated vs. repository written" class of flaw called out in the analog rules.

### Likelihood Explanation
Exploitability requires only: (1) a Shipit instance configured with multiple GitHub organizations (a documented, supported feature) where at least one organization has no `webhook_secret`, and (2) the ability to POST to the public, unauthenticated `WebhooksController#create` endpoint. No session, API token, or GitHub credential of any kind is needed to reach the vulnerable code path.

### Recommendation
`verify_signature` should derive `repository_owner` and validate that it matches the organization prefix of `repository.full_name` (or `organization.login` for org-level events) before dispatching to handlers, rejecting mismatches with `422`. Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank in a multi-organization configuration — at minimum this should be a hard configuration error rather than a silent bypass.

### Proof of Concept
1. Configure Shipit with two GitHub orgs in `secrets.yml`: `unsecured-org` (no `webhook_secret`) and `secured-org` (has a `webhook_secret`, hosts a real `Stack`).
2. Send, with no signature header at all:
```
POST /github/webhooks
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "secured-org/target-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "unsecured-org")`, whose `verify_webhook_signature` returns `true` because `webhook_secret` is blank.
4. `PushHandler#process` resolves `Repository.from_github_repo_name("secured-org/target-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the protected stack — with no valid credential ever presented for `secured-org`.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
