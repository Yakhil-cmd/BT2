### Title
Unauthenticated membership webhook grants arbitrary GitHub user membership on any existing Shipit team via unbound `team.id` lookup - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` purely by `params.team.id` (`github_id`) with `Team.find_or_create_by!`, and `MembershipHandler#process` then calls `team.add_member(member)` unconditionally, without ever checking that the team's `organization` matches the organization whose `webhook_secret` was used to authenticate the request. Combined with `GitHubApp#verify_webhook_signature` returning `true` unconditionally when an organization's `webhook_secret` is blank, an attacker who controls (or registers) an org with no configured `webhook_secret` in this Shipit deployment can send a completely unsigned `membership` webhook that adds an arbitrary GitHub login to any pre-existing, privileged Shipit `Team` by ID.

### Finding Description
The claimed binding, stated as an equality that should hold but doesn't:

`Shipit.github(organization: repository_owner).webhook_secret.present? == true` **must** hold before `MembershipHandler#process` is permitted to mutate `Membership` records for the team identified in the payload. In the vulnerable path this equality is `false`, yet the mutation still occurs.

Trace:
- `WebhooksController#verify_signature` resolves the GitHub App using `repository_owner`, which is `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that resolved organization: `return true unless webhook_secret` [3](#0-2) . This is a real, supported configuration state — the dummy secrets fixture itself configures orgs with `webhook_secret:` blank [4](#0-3) .
- Once signature verification trivially passes, `MembershipHandler#process` runs: it calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { ... team.organization = params.organization.login }` [5](#0-4) . Critically, `find_or_create_by!`'s block only executes on **creation**; if a `Team` with that `github_id` already exists (e.g., a real, privileged team previously synced from a legitimate org), the existing record is returned untouched — its `organization` is never re-validated against the request's org.
- `process` then unconditionally executes `team.add_member(member)` [6](#0-5) , and `Team#add_member` simply appends the member with no organization check at all [7](#0-6) .
- `member` itself is resolved via `User.find_or_create_by_login!(params.member.login)` [8](#0-7) , an attacker-controlled login string, so the attacker can name themselves or an accomplice.

Attacker's request: a `POST /webhooks` with header `X-Github-Event: membership`, no (or garbage) `X-Hub-Signature`, and a JSON body where `repository.owner.login` (or `organization.login`, used as fallback for `repository_owner`) is `attacker-org` — an organization configured in this Shipit deployment's `secrets.github` with a blank `webhook_secret` — while `team.id` is set to the `github_id` of an already-existing, privileged `Team` (e.g., one that gates `Shipit.github_teams` used by `User#authorized?` [9](#0-8) ), and `member.login` is the attacker's own GitHub username.

Why existing guards fail: `verify_signature` only ensures the caller can produce a signature valid for *some* configured organization (or that organization requires none at all); it never binds the *team* being mutated to that organization. `find_or_create_team!`'s `organization=` assignment is dead code for any team that already exists, and `Team#add_member`/`process` perform no cross-check between `params.organization.login` and the found team's `organization`, nor between `repository_owner` (used for auth) and `params.organization.login` (used for the mutation). No `ExplicitParameters` validation, `require_permission!`, or model validation on `Team`/`Membership` closes this gap.

### Impact Explanation
A successful request grants an attacker-controlled GitHub identity membership on an arbitrary, already-existing Shipit `Team` — including teams whose handles are configured in `Shipit.github_teams`, which gate `User#authorized?` for the whole application [9](#0-8) . This is an escalation into the authorization model: an attacker with no Shipit session, no OAuth token, and no valid webhook signature can grant themselves (via GitHub OAuth login using their real GitHub account) the same access as a legitimately-authorized privileged user, then perform any action gated by team membership (deploys, rollbacks, merges, etc., depending on how the host app uses `authorized?`). The blast radius is scoped to Shipit deployments that configure at least one GitHub organization with a blank `webhook_secret`; it is repeatable against any `Team#github_id` the attacker can learn (team IDs are often discoverable via GitHub's own team/org APIs or UI for the target org).

### Likelihood Explanation
Preconditions: (1) the Shipit deployment must have at least one organization entry in `secrets.github` with `webhook_secret` blank/unset — a state explicitly supported and present in this codebase's own fixtures [10](#0-9) [11](#0-10) ; (2) the target `Team` must already exist in Shipit's database (i.e., previously synced from a legitimate membership/oauth event) with a `github_id` the attacker can supply. Attacker cost is minimal — one unauthenticated HTTP POST, no cryptographic material, no valid GitHub App private key or webhook secret needed. It is fully repeatable and can be scripted against any number of teams once team IDs are known.

### Recommendation
In `MembershipHandler#process` (and `find_or_create_team!`), re-derive the organization from the same trusted source `WebhooksController#repository_owner` used for signature verification (e.g., pass it through to the handler), and reject/ignore the request if `params.organization.login` (or the found `Team#organization`) does not match that trusted organization. Additionally, enforce `webhook_secret.present?` for the resolved organization as a hard authentication requirement before processing any mutating webhook (do not treat blank `webhook_secret` as "always verified"), or at minimum require operators to explicitly opt into unauthenticated webhooks per-organization rather than defaulting to trust.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, illustrative — actual file is out of scope per rules but describes the exploit precisely):
1. Configure/stub `Shipit.github(organization: 'attacker-org')` to return a `GitHubApp` built with `webhook_secret: nil`.
2. Create a privileged `Team` fixture, e.g. `privileged = Team.create!(organization: 'shopify', github_id: 999, name: 'Privileged', slug: 'privileged', api_url: 'https://example.com')`, and stub `Shipit.github_teams` to include it.
3. POST to `/webhooks` with header `X-Github-Event: membership` and **no** `X-Hub-Signature` header, body:
   ```json
   {
     "action": "added",
     "team": {"id": 999, "name": "Privileged", "slug": "privileged", "url": "https://example.com"},
     "organization": {"login": "shopify"},
     "member": {"login": "attacker"},
     "repository": {"owner": {"login": "attacker-org"}}
   }
   ```
4. Assert `response.status == 200` (not `422`) despite no valid signature.
5. Assert `Membership.exists?(team: privileged, user: User.find_by(login: 'attacker'))` is `true`.
6. This demonstrates the binding `webhook_secret.present? == true` fails to hold (it's `false` for `attacker-org`) while the privileged team's membership is still mutated — proving authentication and authorization for the write are decoupled.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
