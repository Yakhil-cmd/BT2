### Title
Race in `determineIfStableInLaterUnitsAndUpdateStableMcFlag` uses a bare unit-id reference across an async lock-wait gap, risking a crash on legitimate concurrent state changes - (File: main_chain.js)

### Summary
The Linux CVE fixes a bug where `folio_wait_writeback()` was called on a page after the page-table lock was dropped, without pinning the folio with a reference first — allowing the folio to be concurrently freed and turning the wait into a use-after-free. The analogous pattern in ocore's consensus/stability code is calling back to the caller early, then continuing asynchronous work that dereferences a unit's cached state by its bare string id (`earlier_unit`) after crossing an unprotected mutex-wait boundary, with no guarantee that the referenced unit's in-memory state is still consistent with the assumptions made before the wait began.

### Finding Description
`determineIfStableInLaterUnitsAndUpdateStableMcFlag` in `main_chain.js` first determines `bStable` for `earlier_unit`, and if stable, **immediately invokes `handleResult(bStable, true)`** to unblock the caller [1](#0-0) . It then continues running in the background to move the stability point forward, first queuing on `mutex.lock(["handleJoint"], ...)` [2](#0-1) . This lock acquisition is asynchronous and can be queued behind an arbitrary number of other jobs (see the generic FIFO queueing in `mutex.js`'s `handleQueue`/`exec`) [3](#0-2) .

Once the lock is finally granted, the code calls `storage.readUnitProps(db, earlier_unit, ...)` and dereferences `earlier_unit`'s in-memory cached props as if they must still exist and be consistent [4](#0-3) . `readUnitProps` has a hard invariant: if the unit is not marked stable, it insists `assocUnstableUnits[unit]` still exists and `throw Error("no unstable props of "+unit)` otherwise [5](#0-4) . Nothing in `determineIfStableInLaterUnitsAndUpdateStableMcFlag` "pins" `earlier_unit`'s cache entry across the unprotected async gap between the initial stability check and the point the `handleJoint` lock is actually granted. Other code paths freely mutate/evict this exact cache entry through `storage.forgetUnit()`, which unconditionally does `delete assocUnstableUnits[unit]` [6](#0-5) , and this is invoked by legitimately concurrent flows such as archiving/purging of joints, e.g. `purgeUncoveredNonserialJoints` (`joint_storage.js`) which itself also takes the `handleJoint` lock before calling `storage.forgetUnit` [7](#0-6) , and `archiveJointAndDescendants` in `storage.js` [8](#0-7) .

This mirrors the CVE's root cause structurally: the code drops synchronization (`handleResult` fires immediately, decoupling the caller from the remaining background work) and then, after an async wait for a different lock, blindly re-uses a raw identifier expecting the referenced object's cached state to be exactly as it left it — without any reference-count/pinning mechanism to guarantee the object survives the wait unmodified by concurrent legitimate mutations of the same shared cache structures (`assocUnstableUnits`).

### Impact Explanation
If, during the window while `determineIfStableInLaterUnitsAndUpdateStableMcFlag`'s background continuation is queued for the `handleJoint` lock, the referenced `earlier_unit`'s unstable-unit cache entry is removed/mutated by a concurrent legitimate operation (unit voiding/archiving of non-serial units, or unit forgetting on stability-shrink), the subsequent `storage.readUnitProps` call can throw an uncaught exception ("no unstable props of X" or a similarly guarded invariant violation elsewhere in the props-diffing logic at lines 1540-1550) inside an `async` callback with no surrounding try/catch, crashing the Node.js process. Because this stability-advancement path is exercised as part of ordinary consensus processing when a unit's stability is determined via later units (called from `validation.js` and `network.js`, including the AA-catchup-trigger path `tryToAdvanceStabilityPointForCatchupAATrigger`), an attacker able to shape the timing/DAG topology of posted units could reliably trigger this race on full nodes, causing repeated crashes and a node's inability to process/confirm new units — a network-availability/consensus-processing impact rather than a purely local one.

### Likelihood Explanation
Triggering requires a specific interleaving: a unit stability check must resolve `bStable=true` while `bStableInDb=false`, the background continuation must be queued behind other `handleJoint`-lock holders long enough for the referenced unit to be archived/forgotten by an independent, legitimate maintenance path (nonserial purge / archive-descendants), all of which are ordinary node operations that occur continuously and are influenced by the shape and timing of units an attacker posts to the DAG. This makes the race plausible but not trivially reproducible on demand, so likelihood is assessed as Medium.

### Recommendation
Before scheduling the deferred stability-advancement work in `determineIfStableInLaterUnitsAndUpdateStableMcFlag`, snapshot/validate that `earlier_unit` is still present and consistent in `storage.assocUnstableUnits` immediately after acquiring the `handleJoint` lock, and treat its absence as a benign "already handled/forgotten" case (skip/return) instead of allowing `storage.readUnitProps` to throw an unhandled error. More generally, any deferred continuation that resumes after crossing an async lock-wait boundary and depends on a previously-observed piece of shared, mutable in-memory state (units cache, best-children lists, etc.) should re-validate that state rather than assuming it is still valid, analogous to how the kernel fix requires holding an explicit folio reference before calling a function that can block.

### Proof of Concept
Conceptual PoC (exact reproduction requires precise DAG/timing control and is not independently verified in this review):
1. Post/relay a set of units such that some earlier unit `U` becomes provably stable via `arrLaterUnits` while the DB has not yet marked it stable (`bStableInDb=false`), invoking `determineIfStableInLaterUnitsAndUpdateStableMcFlag(conn, U, arrLaterUnits, false, cb)` from the normal validation/catchup-AA-trigger path.
2. Simultaneously flood the node with other units/joints that keep the `handleJoint` mutex busy long enough, and craft a companion unit set so that `U` ends up voided/archived by `purgeUncoveredNonserialJoints`/`archiveJointAndDescendants` (both of which also use `handleJoint`) while the pending continuation for step 1 is still queued.
3. When the queued continuation in `determineIfStableInLaterUnitsAndUpdateStableMcFlag` finally acquires `handleJoint` and calls `storage.readUnitProps(db, U, ...)`, `assocUnstableUnits[U]` no longer exists, causing the code to throw inside `readUnitProps`, crashing the process.
