### Title
`MembershipHandler` binds `Team` by global `github_id` without checking it belongs to the signed webhook's organization, allowing cross-tenant `Shipit.github_teams` membership escalation - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook using `repository_owner` (an attacker-controlled JSON field), then `MembershipHandler#find_or_create_team!` looks up/creates a `Team` using only `params.team.id` (`github_id`) with no check that this `github_id` actually belongs to `params.organization.login` or to the organization whose secret validated the request. Any org administrator who legitimately controls a Shipit-integrated org (and thus knows that org's `webhook_secret`) can forge a `membership` payload naming a foreign org's team `github_id` and add an arbitrary user to that privileged `Team` row.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:

`signing_org (used to fetch the webhook_secret via repository_owner) == params.organization.login == Team.find_by(github_id: params.team.id).organization`

Trace:
1. `WebhooksController#verify_signature` derives the org for secret lookup purely from the JSON body: `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`, then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(sig, raw_body)`. [1](#0-0) [2](#0-1) 
2. Each organization has its own `webhook_secret` in config (`GitHubApp#initialize` / `verify_webhook_signature`), so a signature only proves the raw body was HMAC'd with the secret belonging to whichever org name is embedded in the body's own `repository.owner.login`/`organization.login` field. [3](#0-2) [4](#0-3) 
3. `MembershipHandler` requires `team.id`, `team.slug`, `team.name`, `team.url`, and `organization.login` as independent, uncorrelated fields — nothing ties them together. [5](#0-4) 
4. `find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id)`. `github_id` is a global (cross-org) key. If a `Team` row with that `github_id` already exists (e.g. a privileged team referenced by `Shipit.github_teams`/`oauth.teams`), `find_or_create_by!` returns the existing record and the `organization:`/`github_team=` block (which would set organization/slug) is **not** re-run, but the found `team` object is still handed to `team.add_member(member)`/`team.members.delete(member)` unconditionally. [6](#0-5) [7](#0-6) 

Attacker request: the attacker legitimately administers `attacker-org`, which is a real Shipit-integrated org (so they know or can supply `attacker-org`'s `webhook_secret` by directly POSTing to `/webhooks`, bypassing GitHub delivery). They craft:
```json
{
  "action": "added",
  "team": {"id": <victim_team_github_id>, "name": "x", "slug": "unrelated", "url": "y"},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker_user"},
  "repository": {"owner": {"login": "attacker-org"}}
}
```
signed with `attacker-org`'s secret. `verify_signature` passes because `repository_owner` = `attacker-org` and the signature is valid for that org's secret — the controller has no way to know that `team.id` inside the same body references a different org's team. `MembershipHandler` then finds the pre-existing `Team` row for the victim's `github_id` and appends `attacker_user` as a member, with no validation that `attacker_user` is genuinely part of that team on GitHub or that the team belongs to `attacker-org`.

None of the existing guards catch this: `verify_signature` only authenticates "this body was signed by *some* org's secret, chosen from a field in the same untrusted body"; the `ExplicitParameters` schema only enforces types, not cross-field/tenant consistency; there is no `require_permission!`/`User#authorized?` check in the webhook path (webhooks are not user-authenticated); model validations on `Team`/`Membership` don't check organization consistency either.

### Impact Explanation
An attacker who administers any single Shipit-integrated GitHub organization can inject arbitrary users into any other organization's `Team` record purely by knowing that team's numeric `github_id` — a value that is either public (GitHub's public teams API), guessable (small sequential integers), or previously observed. If the targeted `Team` is one referenced by `Shipit.github_teams` (built from `oauth.teams` config, used for permission/authorization checks such as deploy/rollback approval), this is a direct escalation into a privileged authorization group for a tenant the attacker does not control. This matches the "High - escalation into `Shipit.github_teams` authorization" impact category. The attack is repeatable against any `github_id` the attacker can enumerate, and the blast radius spans the whole Shipit instance (cross-tenant), not just the attacker's own org.

### Likelihood Explanation
Preconditions: (1) the attacker must legitimately administer at least one organization integrated with this Shipit instance and know/control that org's `webhook_secret` (a realistic scenario for self-serve multi-tenant Shipit deployments where org admins configure their own GitHub App/webhook secret); (2) a `Team` row for the target `github_id` must already exist in Shipit's DB (true for any team already referenced via `oauth.teams`/`Shipit.github_teams`, which is exactly the privileged case that matters); (3) the attacker must know or guess the target team's `github_id`. These are moderate-cost, plausible conditions, and the attack requires only a single crafted HTTP POST — fully repeatable.

### Recommendation
- In `MembershipHandler#find_or_create_team!`, verify that the found `Team`'s `organization` matches `params.organization.login` (and that `params.organization.login` matches the verified `repository_owner`/signing org) before performing `add_member`/`members.delete`; raise/reject on mismatch.
- In `WebhooksController#verify_signature`, ensure the org used to select the webhook secret is cross-checked against every organization-identifying field elsewhere in the payload (e.g. `organization.login`) rather than trusting a single attacker-controlled field.
- Consider scoping `Team` lookup by `(organization, github_id)` instead of `github_id` alone, since `github_id` is not org-scoped in this schema's usage.

### Proof of Concept
```ruby
# test/models/webhooks/membership_handler_test.rb (conceptual)
test "cross-org github_id cannot hijack a privileged team" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: 1

  payload = {
    'action' => 'added',
    'team' => { 'id' => victim_team.github_id, 'name' => 'x', 'slug' => 'unrelated', 'url' => 'y' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker_user' }
  }

  assert_no_difference -> { victim_team.reload.members.count } do
    assert_raises(SomeConsistencyError) do # or handler should reject
      Shipit::Webhooks::Handlers::MembershipHandler.call(payload)
    end
  end
end
```
Both sides of the equality to assert: `verified_signing_org` (`attacker-org`, from `repository_owner`) must equal `victim_team.organization` (`shopify`) before `add_member` runs; currently they diverge and the handler still executes `team.add_member(member)`, which is the escalation to flag.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
