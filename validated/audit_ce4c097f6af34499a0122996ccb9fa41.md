### Title
Windows reserved-filename check can be bypassed with alternate-data-stream colon syntax, allowing `os.OpenFile` to target a reserved Windows device - (File: pkg/cmd/release/download/download.go)

### Summary
`isWindowsReservedFilename` only strips text after the *first dot* before comparing against the reserved-device-name list, so it fails to normalize the *colon* used by Windows NTFS alternate-data-stream (ADS) syntax. An attacker who publishes a release asset named e.g. `CON:evil.txt` or `COM1:foo` on Windows targets defeats the filter, and the untouched name is passed straight into `os.OpenFile` at download.go:442, which on Windows resolves reserved device names even when followed by a colon.

### Finding Description
`downloadRun` only rejects an asset if `isWindowsReservedFilename(a.Name)` returns true (download.go:203-205), and the accepted name is later handed unmodified to `destinationWriter.Copy`/`makePath`/`os.OpenFile` (download.go:379-384, 416-442). The filter itself is: [1](#0-0) 

It only calls `strings.Split(filename, ".")[0]` — it removes anything after the *first period* but does nothing about a colon. On Windows, reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COMn`, `LPTn`) are recognized by the kernel independent of any trailing extension *or* ADS-style suffix; naming a file `CON:something` (or `COM1:something`) still redirects `CreateFile`/`os.OpenFile` to the underlying device rather than creating a real file on disk, in the same way `CON.txt` does (which is exactly why this function exists at download.go:456-462, per its own comment).

Because the split is only on `.`, a name like `CON:evil.txt` produces `"CON:EVIL"` after `strings.Split(filename, ".")[0]` is applied to `"CON:evil.txt"` — wait, more precisely: `strings.Split("CON:evil.txt", ".")[0]` yields `"CON:evil"`, which uppercased is `"CON:EVIL"`, not present in `reservedFilenames`, so the check returns `false` and the asset is allowed through. Similarly `COM1:foo` (no dot at all) yields `"COM1:FOO"`, also not matched. The asset name is attacker-controlled via the GitHub Release API `assets[].name` field, which any unprivileged user can set on a public release/fork they own, and it reaches `os.OpenFile` unmodified once the victim runs `gh release download` on Windows.

The Unicode-confusable variant mentioned in the question (e.g. a Cyrillic look-alike of "CON") is not a real bypass vector: Windows only special-cases the exact ASCII reserved names, so a confusable string would simply create an ordinary file with that name — no device redirection occurs, so there's no exploitable impact from that vector.

### Impact Explanation
On a victim's Windows machine, downloading such an asset causes `os.OpenFile` to open a system device (console `CON`, serial port `COMn`, printer `PRN`/`LPTn`) instead of writing the file to the intended destination directory. Depending on the device this can hang the `gh` process (e.g. `CON` may block waiting on console I/O) or write attacker-supplied release content to a physical device, silently failing to save the expected file. This is a confinement bypass of the exact check the code introduces to prevent "an exploit vector for bad actors" (per the function's own comment), though the effect is limited to local denial-of-service/misdirected I/O rather than arbitrary file write to an attacker-chosen filesystem path, code execution, or credential exposure.

### Likelihood Explanation
Trivial to trigger: any unprivileged GitHub user can attach an asset with a crafted name (e.g. `CON:x`, `COM1:x`) to any release on a repo/fork they control, and any victim running `gh release download` (without `--pattern`/`--output` restrictions preventing that name) on Windows will be affected. No authentication bypass or special privileges required on the attacker side.

### Recommendation
Normalize the filename fully before comparison: split on both `.` and `:` (or, more robustly, use a regex to extract only the leading `[A-Za-z]+[0-9]?` device-name component before any `.`, `:`, or trailing spaces), and also account for trailing dots/spaces which Windows also ignores when resolving device names.

### Proof of Concept
```go
func TestIsWindowsReservedFilename_ColonBypass(t *testing.T) {
    tests := []struct {
        name     string
        filename string
        want     bool
    }{
        {"reserved with ADS colon", "CON:evil.txt", true}, // currently returns false — bug
        {"reserved COM1 with colon, no dot", "COM1:foo", true}, // currently returns false — bug
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got := isWindowsReservedFilename(tt.filename)
            assert.Equal(t, tt.want, got, "expected %q to be treated as reserved", tt.filename)
        })
    }
}
```
Running this against the current implementation shows `isWindowsReservedFilename("CON:evil.txt")` and `isWindowsReservedFilename("COM1:foo")` both return `false`, confirming the asset would pass the `runtime.GOOS == "windows" && isWindowsReservedFilename(a.Name)` guard at download.go:203 and proceed to `dest.Copy`/`os.OpenFile` at download.go:442.
