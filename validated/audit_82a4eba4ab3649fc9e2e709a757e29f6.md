### Title
`OpenedHandler#provision?` operator precedence bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` intends `review_stacks_enabled` to gate all three provisioning behaviors, but Ruby operator precedence (`&&` binds tighter than `||`) causes `review_stacks_enabled` to apply only to the `allow_all` clause. This lets an attacker who owns a source repository configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) create a review stack even when `review_stacks_enabled` is `false`, simply by labeling (or not labeling) their own PR.

### Finding Description
The claimed binding is: `provision? == true` should require `repository.review_stacks_enabled == true` AND (behavior-specific condition), i.e. `review_stacks_enabled` should be `&&`-ed with the entire disjunction of behavior checks. In the actual code: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` has higher precedence than `||`, this actually parses as:

`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So `review_stacks_enabled` only gates the `allow_all` branch. For `allow_with_label` or `prevent_with_label`, `provision?` is true regardless of `review_stacks_enabled`.

`pull_request_has_provisioning_label?` and `pull_request_label_names` derive purely from the webhook's own `pull_request.labels` array, which is data the attacker controls by labeling their own PR on their own repository: [2](#0-1) 

This is a genuine, correctly-signed GitHub webhook (the attacker owns the repo and PR, no forged signature needed), so signature verification (`verify_webhook_signature`) does not block this — it is out of scope for this bug since the attacker is not forging anything.

`process` then calls `ReviewStackAdapter#find_or_create!`, which creates a `Stack`/`ReviewStack` using `params.pull_request.head.ref` as the branch and enqueues provisioning: [3](#0-2) [4](#0-3) 

Existing test coverage confirms the gap: the only test exercising `review_stacks_enabled: false` uses `behavior: :allow_all`, and all `allow_with_label`/`prevent_with_label` tests leave `review_stacks_enabled` at its default `true`, so this exact combination (`review_stacks_enabled: false` + `allow_with_label`/`prevent_with_label`) is untested: [5](#0-4) 

Nothing else in the path (params schema validation, `Repository` model validations, `NullRepository` fallback) re-checks `review_stacks_enabled` before stack creation, so the guard is fully bypassed for these two behaviors.

### Impact Explanation
An unprivileged GitHub user who owns/controls a source repository with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` can force review-stack creation (`Shipit::Stack`/`ReviewStack` records, which subsequently get provisioned and run `Command`/deploy steps) even though the repository/org has explicitly disabled review stacks (`review_stacks_enabled: false`). This is an unauthorized stack creation/provisioning action that the repository owner or Shipit operator explicitly opted out of, matching the "unauthorized deploy" / "record written for a repository" Critical impact category. It is repeatable per PR/branch on any repository configured this way, and the resulting stack's branch is directly attacker-controlled (`pull_request.head.ref`), so whatever commands/scripts the provisioning/deploy pipeline runs against that branch execute despite the disabled flag.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (an operator/maintainer configuration choice), with `review_stacks_enabled: false`. The attacker needs only to know (or guess/discover) the exact `provisioning_label_name` for `allow_with_label`, or nothing at all for `prevent_with_label` (simply not labeling the PR triggers it). Labeling one's own PR or opening an unlabeled PR requires no elevated GitHub permissions. This is a low-cost, fully repeatable bug triggered by ordinary, legitimately-signed webhook events — no secret material or privileged role needed.

### Recommendation
Fix operator precedence so `review_stacks_enabled` gates all branches, e.g.:

```ruby
def provision?
  repository.review_stacks_enabled? && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

Apply the same fix to `ReopenedHandler`, `LabeledHandler`, and `UnlabeledHandler` if they share the same pattern, since the same precedence bug likely exists there.

### Proof of Concept
```ruby
test "does not create stacks for allow_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end

test "does not create stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :prevent_with_label,
    provisioning_label_name: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```

Both assertions currently **fail** against the existing code (i.e. `Shipit::Stack.count` does increase), demonstrating the bypass of the `review_stacks_enabled == false` gate.
