## Analysis

The Canto report's bug class is: a payload field that is *acted upon* is not covered by the check meant to authorize that action (here, `callvalue` was processed but not validated by the `payable` gate). The closest analog reachable by an unprivileged attacker in this engine is in the webhook ingestion path, where the *field used to select the authentication key* is disjoint from the *field used to determine which repository/stack the payload is applied to* — and the authentication check itself can be trivially satisfied for one tenant while the payload is applied to another.

### Root cause

`WebhooksController#verify_signature` picks which GitHub App config (and therefore which `webhook_secret`) to validate against using an attacker-supplied, **unverified** field of the raw JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from `params.dig('repository', 'owner', 'login')` (or `organization.login`) of the un-authenticated `raw_post` — before any signature has been checked.

That value is used to fetch a per-organization `GithubApp`/secret, and `verify_webhook_signature` short-circuits to `true` whenever that organization has **no configured `webhook_secret`**: [3](#0-2) 

`webhook_secret` is an explicitly optional, per-organization setting (`webhook_secret: # nil` is the documented default for every sample config, including the multi-org example that configures **independent** secrets per org): [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, `create` re-parses the same raw body and dispatches it to event handlers keyed only by event type, with no re-check that the authenticated organization matches the repository the handler subsequently mutates: [6](#0-5) 

Downstream handlers such as `PushHandler` resolve target `Stack`s from repository/branch fields of that same untrusted body and immediately act (e.g., trigger `sync_github`): [7](#0-6) 

### Break in the trust binding

The equality the code is supposed to guarantee is:

`organization whose secret authenticated the request == organization owning the repository the handler writes to`

Before a malicious request: for a genuine GitHub-signed webhook, `repository.owner.login` (used to pick the secret) and the repository identity used by the handler are always the same, consistent GitHub-generated payload, so the equality holds.

After an attacker's forged request: since the whole HTTP body is attacker-controlled (no prior authentication is required to reach `WebhooksController#create`), an attacker can set `repository.owner.login` (and/or `organization.login`) to any organization configured in this Shipit instance whose `webhook_secret` happens to be blank (a normal, documented configuration), while leaving the rest of the payload (e.g. `repository.full_name`, `ref`, `after`) pointing at a *different*, secret-protected organization's repository. `verify_webhook_signature` returns `true` unconditionally for the blank-secret org, so the request passes `verify_signature`, and the handler then acts on the other organization's stack using attacker-chosen `ref`/`after`/etc. The equality above is broken: authentication was performed against org A's (absent) secret while the write happens against org B's repository.

## Impact

In a multi-organization Shipit deployment (the engine explicitly supports and documents per-org `github:` sections with independent, optional `webhook_secret`s), an unauthenticated attacker can forge webhook events (push, status, check_suite, membership, pull_request, merge, etc.) for any organization/repository configured in the instance, as long as at least one configured organization in the same instance has no `webhook_secret` set. This is an authentication bypass on the sole gate protecting the webhook ingestion endpoint, letting the attacker trigger `GithubSyncJob`, forge commit statuses, or manipulate `Team`/`Membership`/`User` records for repositories they do not control, without ever knowing any organization's actual webhook secret.

## Likelihood

Requires: (1) the target instance to configure more than one GitHub organization, and (2) at least one of those organizations to leave `webhook_secret` unset — both are normal, documented, supported configurations (`webhook_secret` is explicitly optional per `docs/setup.md`). No credentials, tokens, or prior access are needed; the attacker only needs to know the app's public webhook URL and the name of any configured no-secret organization.

## Recommendation
- Do not select the verification key from the unauthenticated payload; require a stable, out-of-band mapping (e.g., verify against every configured org's secret, or bind the webhook route/URL to a single org) and reject if no configured org has a matching, non-blank secret.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank in a multi-org configuration; instead fail closed if the payload's target repository does not belong to an organization with a verifiable secret.
- Cross-check that the organization used to authenticate a request equals the organization that owns the repository/stack the handler subsequently mutates.

## Proof of Concept
1. Configure Shipit with two GitHub Apps: `OrgA` (no `webhook_secret`) and `OrgB` (real repos/stacks, `webhook_secret` set), as in [8](#0-7) .
2. POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` for `OrgB`, and a JSON body:
   ```json
   {
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" },
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>"
   }
   ```
3. `repository_owner` resolves to `OrgA` (app/controllers/shipit/webhooks_controller.rb:59-62); `Shipit.github(organization: "OrgA").verify_webhook_signature` returns `true` because `OrgA`'s `webhook_secret` is blank (lib/shipit/github_app.rb:76-77).
4. `create` dispatches the same body to `PushHandler`, which looks up `OrgB/target-repo`'s stacks and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17) — an unauthenticated write against `OrgB`'s stack, despite `OrgB` having a configured secret that was never checked.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
