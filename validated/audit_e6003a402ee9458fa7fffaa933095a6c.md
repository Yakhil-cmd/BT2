### Title
Webhook signature verification authenticates the payload's `repository.owner.login`/`organization.login`, while event handlers dispatch writes based on the unrelated `repository.full_name` field — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to validate an inbound webhook against using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), but the event handlers (e.g. `PushHandler`, and other `Handler` subclasses) resolve the `Stack`/`Repository` to act on using a completely different, independently attacker-supplied field: `repository.full_name`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Shipit.github(organization: repository_owner)` looks up the GitHub App configuration (and its `webhook_secret`) keyed by whatever value the attacker puts in the payload's `repository.owner.login` (falling back to `organization.login`), as seen in `verify_signature`. [4](#0-3) [5](#0-4) 

Once the signature check passes (`github_app.verify_webhook_signature`), `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)` handlers with the raw parsed JSON. [6](#0-5) 

Every handler then determines *which Stack/Repository to act on* not from the field used for authentication, but from `payload.dig('repository', 'full_name')`: [3](#0-2) 

This creates exactly the "identity used for verification vs. identity acted on" mismatch described in the analog bug class: the organization whose credential (webhook secret) authenticated the request is not cryptographically bound to the repository the handler subsequently writes to. In Shipit's documented "Using Multiple Github Applications" mode, distinct GitHub organizations each configure their own GitHub App and `webhook_secret`, all pointing at the same shared Shipit instance. [7](#0-6) 

An org admin who legitimately owns their own GitHub App installation (and therefore legitimately knows their own `webhook_secret`, which they configured themselves — not a privileged Shipit secret) can craft a payload where `repository.owner.login` is set to their own org (so `Shipit.github(organization: ...)` resolves their own app/secret and the HMAC they compute with their own secret validates), while `repository.full_name` is set to `"other-org/victim-repo"`. Because the HMAC only proves "this body was signed by org A's secret" and does not itself constrain which repository name may appear inside that body, and because the handler layer never re-checks that `full_name`'s owner matches the verified `repository_owner`, the forged event is processed against `other-org`'s Stack — e.g. triggering `GithubSyncJob`, creating fake commit `Status` rows, enqueuing `RefreshCheckRunsJob`, or triggering pull-request driven actions — for a repository/stack the attacker's org has no relationship to. [8](#0-7) [9](#0-8) 

### Impact Explanation
This breaks the trust boundary between GitHub organizations sharing a multi-tenant Shipit deployment: an organization's own valid webhook credential can be used to forge webhook events for a completely different organization's stacks. This can cause unauthorized `GithubSyncJob` enqueues, forged commit statuses/check-run refreshes, and manipulation of merge/deploy-adjacent state for stacks the attacker does not own, without requiring any Shipit session, API token, or the victim organization's secret — satisfying the "cross-repository writes" / "unauthenticated read of stack state" high-severity criteria via a credential-scope escape.

### Likelihood Explanation
Likelihood is High for deployments that use the documented multi-organization GitHub configuration (each org supplies its own app/secret to one shared Shipit instance), since any onboarded organization admin already possesses everything needed (their own `webhook_secret`) to mount the attack — no secret theft, session, or API token is required. For single-org Shipit deployments the attack surface collapses to needing the org's own secret (out of scope), but the code path itself does not enforce any binding between `repository_owner` and `repository.full_name` at all.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after in `#create`), assert that the organization used to select the verifying GitHub App (`repository_owner`) matches the organization portion of `repository.full_name` (and of `organization.login` when present) before dispatching to handlers. Reject the webhook (422) if they diverge, so a validated org secret can only authorize events for repositories under that same organization.

### Proof of Concept
1. Configure Shipit in multi-org mode with two organizations, `org-a` and `org-b`, each with their own GitHub App and `webhook_secret` (per `docs/setup.md`), and a Stack registered for `org-b/victim-repo`.
2. As an entity that controls `org-a`'s GitHub App (and thus legitimately knows `org-a`'s `webhook_secret`), build a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Sign the raw body with `org-a`'s webhook secret (SHA1 HMAC, `X-Hub-Signature` header) and POST it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")`, verifies the signature successfully against `org-a`'s secret. [4](#0-3) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")`, and enqueues `GithubSyncJob` for `org-b`'s stack, even though `org-b` never authenticated this request. [3](#0-2) [10](#0-9)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. # frozen_string_literal: true

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
