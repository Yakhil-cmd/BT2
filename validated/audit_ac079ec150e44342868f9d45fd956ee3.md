### Title
Membership webhook grants Shipit team access based on `github_id` collision without organization binding - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely by `github_id`, ignoring which organization's webhook secret actually authenticated the request. Because `WebhooksController#verify_signature` only proves the payload came from *some* legitimately configured Shipit tenant (`repository_owner` from the payload itself), an attacker who owns their own onboarded org can forge a `membership` event whose `team.id` collides with an existing `Team` row belonging to a different, victim organization, and add themselves as a member of that team.

### Finding Description
The broken binding: `verify_signature`'s authenticated organization (`params.dig('organization','login')`, resolved as `repository_owner`) must equal the organization owning the `Team` row being mutated (`team.organization`). This is never checked.

`WebhooksController#verify_signature` looks up `Shipit.github(organization: repository_owner)` and validates the HMAC signature against that organization's own `webhook_secret`: [1](#0-0) 
`repository_owner` is derived entirely from attacker-controlled payload fields: [2](#0-1) 
This only proves the request was signed by *the organization named in the payload* — i.e., self-authentication, not authorization to mutate arbitrary rows.

`MembershipHandler#process` then calls `find_or_create_team!`, which does: [3](#0-2) 
`Team.find_or_create_by!(github_id: params.team.id)` searches only on `github_id`. If a `Team` row already exists with that `github_id` (e.g. belonging to `victim-org`), the block that would set `team.organization = params.organization.login` is **not executed** (ActiveRecord only runs the block on creation), so the existing row and its `organization` are untouched — but the found `team` object is returned and used regardless of which org signed the request.

Attacker flow: attacker owns `attacker-org`, a genuine Shipit-configured tenant with its own real `webhook_secret`. They send `POST /webhooks` with `X-Github-Event: membership`, `X-Hub-Signature` computed with `attacker-org`'s real secret, and body:
```json
{"action":"added","team":{"id":<victim team's github_id>,"name":"...","slug":"...","url":"..."},"organization":{"login":"attacker-org"},"member":{"login":"attacker-login"}}
```
`verify_signature` succeeds because `attacker-org`'s own secret correctly signs its own payload. `find_or_create_team!` finds the pre-existing `victim-org` `Team` row by `github_id` alone and returns it. `process` then calls `team.add_member(User.find_or_create_by_login!('attacker-login'))`: [4](#0-3) [5](#0-4) 
This adds attacker-login to victim-org's team membership, even though the request was never authenticated by victim-org.

None of the existing guards catch this: `verify_signature` validates provenance only against the payload's own claimed org, not against the target `Team`'s `organization`; the `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not organization consistency; there is no `require_permission!` or cross-check between `params.organization.login` and `team.organization` anywhere in `find_or_create_team!` or `Team.add_member`.

### Impact Explanation
`User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`: [6](#0-5) 
and `force_github_authentication` uses this to gate the entire application: [7](#0-6) 
If the victim's colliding `Team` is included in `Shipit.github_teams`, the attacker's `attacker-login` `User` becomes `authorized?` and can bypass `force_github_authentication` app-wide — an authentication bypass into a multi-tenant Shipit instance, matching the Critical "authentication bypass (forged webhook ... accepted)" category. This is repeatable for any `github_id` collision the attacker can predict or brute-force (GitHub team IDs are sequential/enumerable), and requires no privileged secrets beyond the attacker's own legitimately-issued `webhook_secret`.

### Likelihood Explanation
Preconditions: (1) Shipit must be configured for multiple GitHub organizations/tenants (per `docs/setup.md`'s "Using Multiple Github Applications" section) with the attacker controlling one legitimately onboarded org; (2) a `Team` row must already exist in Shipit's database for the victim org with a `github_id` the attacker can supply or guess; (3) `Shipit.github_teams` must reference that team for the bypass to have `authorized?` impact. GitHub team IDs are not secret and are discoverable/enumerable, and Shipit only requires the attacker to control any single onboarded tenant to craft a validly-signed forged payload. The attack costs a single HTTP POST.

### Recommendation
In `find_or_create_team!`, scope the lookup/creation by both `github_id` and the authenticated `organization` (derived from the verified `repository_owner`, not `params.organization.login`), e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: verified_org)`, and reject (or no-op) if an existing `Team` with that `github_id` has a different `organization` than the one that authenticated the webhook. Additionally, pass the authenticated org from the controller into the handler rather than trusting `params.organization.login`, since it currently is both the value used for signature verification and the value trusted for team creation without cross-validation against pre-existing rows.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, integration test):
1. Fixtures: create `Team` `victim_team` with `organization: 'victim-org'`, `github_id: 999`, and ensure `Shipit.github_teams` (via `oauth.teams` config for some org) includes `victim_team`.
2. Configure Shipit with two orgs: `attacker-org` (attacker-controlled, `webhook_secret: 'attacker-secret'`) and `victim-org` (`webhook_secret: 'victim-secret'`).
3. Build payload: `{"action"=>"added","team"=>{"id"=>999,"name"=>"...","slug"=>"...","url"=>"..."},"organization"=>{"login"=>"attacker-org"},"member"=>{"login"=>"attacker-login"}}`.
4. Compute `X-Hub-Signature` HMAC using `'attacker-secret'` (the real secret for `attacker-org`) and `request.headers['X-Github-Event'] = 'membership'`.
5. POST to `/webhooks` with that body and signature.
6. Assert `response.status == 200`.
7. Assert `Team.find_by(github_id: 999).organization == 'victim-org'` (unchanged — proving the binding equality `repository_owner ('attacker-org') == team.organization ('victim-org')` is false yet the mutation still succeeded).
8. Assert `User.find_by(login: 'attacker-login').authorized?` is `true`, demonstrating the authentication bypass.
