### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up the target `Commit` by `sha` alone, with no scoping to the repository/organization whose webhook signature was actually verified for the inbound request. This breaks the trust binding: **the GitHub organization/app whose `webhook_secret` authenticated the request** must equal **the repository/stack whose commit status gets written**. `PushHandler` and `CheckSuiteHandler` both scope their writes through `stacks` (which is derived from `payload.dig('repository','full_name')`), but `StatusHandler` does not.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` to validate the payload against using `repository_owner`, itself derived from the same untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`): [1](#0-0) [2](#0-1) 

That check only proves the payload was signed by *some* organization's configured GitHub App — it says nothing about which repository/commit the payload is entitled to mutate. Every other handler re-derives the target scope from the same payload's `repository.full_name` before writing: [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler`, however, resolves the target purely by SHA, globally across every repository/stack tracked by this Shipit instance, with no `stacks`/`repository_name` scoping at all: [6](#0-5) 

Because a git commit SHA is a deterministic hash of commit content (tree, parents, author/committer, timestamps, message) and is not itself secret, an org admin who legitimately owns a GitHub App installation on this multi-tenant Shipit instance (as documented in "Using Multiple Github Applications") can reconstruct an identical commit object (same tree/parents/metadata) in their own repository, producing the exact same SHA as a commit that exists in a *different* organization's tracked stack. Firing (or replaying) a real, validly-signed `status` webhook from their own org/app for that SHA will pass `verify_signature` (since it's signed with their own org's genuine `webhook_secret`), then `StatusHandler` will match and mutate the `Commit` row belonging to the unrelated organization's stack, because the lookup is global.

### Impact Explanation
This is a cross-repository write across tenant boundaries with no repository-write permission on the target repository required. `Commit#create_status_from_github!` populates commit statuses that gate deploy eligibility (CI/status checks used elsewhere in the app to determine whether a commit is deployable). An attacker who only administers their own onboarded organization/app can forge a `success` status on a commit belonging to a completely different organization's stack, potentially making an otherwise-blocked commit appear deployable and enabling an unauthorized deploy on infrastructure they have no access to — squarely within the "cross-repository writes" / "unauthorized deploy" Critical impact bucket.

### Likelihood Explanation
Exploitation requires the attacker to control a legitimately onboarded GitHub organization/App on the same multi-tenant Shipit instance (a normal, unprivileged tenant, not a Shipit admin or `Shipit.github_teams` member) and to know/reconstruct the exact commit metadata of the target commit to reproduce its SHA — feasible for any commit that was ever public (open-source history, a previous public repo, a leaked patch, etc.), since SHA1 commit hashing is fully deterministic and not secret. No `webhook_secret`, `api_clients_secret`, or GitHub App private key belonging to the victim organization is needed; only the attacker's own, already-known secret is used, satisfying the "no privileged credential of the target required" bar.

### Recommendation
Scope `StatusHandler#process` to the repository declared in the same payload (via the inherited `stacks`/`repository_name` helper already used by `PushHandler` and `CheckSuiteHandler`) before matching commits, e.g. restrict the `Commit.where(sha: params.sha)` lookup to commits belonging to `stacks` (or otherwise verify `commit.stack.repository.full_name == repository_name`) so a status can only be applied to commits that actually belong to the repository the verified webhook was signed for.

### Proof of Concept
1. Attacker owns/administers "attacker-org", which has a legitimate GitHub App installed and configured (`webhook_secret` known to GitHub for that org) on the shared Shipit instance, per the "Using Multiple Github Applications" setup.
2. Victim org "victim-org" has a stack tracking a commit with SHA `abcd123...` (git commit hash is deterministic and derivable from publicly known tree/parent/author/timestamp/message metadata, e.g. because the commit was at some point public).
3. Attacker crafts/pushes an identical commit object (same tree, parents, author, committer, timestamps, message) into a repository under `attacker-org`, producing the identical SHA `abcd123...`.
4. Attacker triggers (or has GitHub trigger) a `status` webhook event from `attacker-org`'s repo for that SHA (e.g., via the real Statuses API on their own repo), which GitHub signs with `attacker-org`'s real `webhook_secret`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org` from the payload, fetches `attacker-org`'s GitHub App, and validates the signature successfully — it is a real, correctly signed request. [7](#0-6) 
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)` globally, finds the victim-org commit with the same SHA (belonging to an unrelated stack the attacker cannot access), and calls `create_status_from_github!`, applying the attacker-controlled status/state to that commit. [6](#0-5)

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
