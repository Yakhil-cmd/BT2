### Title
Webhook signature verified against payload's `repository.owner.login` while the acted-upon repository is taken from the unbound `repository.full_name` field, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature with by reading `repository.owner.login` (or `organization.login`) out of the untrusted request body itself, then verifies the signature against the *entire raw body*. However, every event handler (`PushHandler`, `PullRequest::ClosedHandler`, `PullRequest::LabeledHandler`, etc.) resolves the actual `Stack`/`Repository` to act on using a *different*, independently-controlled JSON field: `repository.full_name`. Because the field used to pick the verification key and the field used to pick the target repository are not the same value and are not cross-checked against each other, an attacker who legitimately controls the webhook secret for *any one* organization configured in a multi-org Shipit deployment can forge a payload whose `repository.owner.login` matches their own org (so the signature check passes with their own known secret) while `repository.full_name` names a repository belonging to a *different* organization, causing Shipit to act on that unrelated stack.

### Finding Description
`verify_signature` picks the signing key like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
``` [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` directly out of the same unauthenticated JSON body that is about to be checked.

Downstream, `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` (the base class used by `PushHandler`, `PullRequest::ClosedHandler`, `PullRequest::LabeledHandler`, etc.) resolves the target repository using a **separate** key: [3](#0-2) 

`Shipit.github(organization:)` looks up per-organization app configuration (including `webhook_secret`) via `github_app_config`, a documented Shipit feature for hosting multiple GitHub orgs from one instance: [4](#0-3) 

Because HMAC verification only proves "whoever sent this raw body knows organization X's `webhook_secret`" and not "every field inside this body legitimately concerns organization X's repositories," an attacker who knows (or legitimately possesses, as the owner of that org's own GitHub App installation) the `webhook_secret` for organization A can freely set `repository.owner.login = "orgA"` (to pass the signature check) while setting `repository.full_name = "orgB/victim-repo"` (to target an unrelated organization's stack), since nothing binds these two fields together.

`PullRequest::ClosedHandler#process` demonstrates a concrete high-impact sink: it unconditionally archives the resolved review stack: [5](#0-4) 

The binding that should hold but is broken: `organization used to select verification key == organization that owns the repository being acted upon`. Before the attacker's request, only genuine GitHub webhooks for organization A's own repositories could pass signature verification and act on organization A's stacks. After the forged request, an org-A-scoped signature can be replayed to act on organization B's stacks, because the two fields are never checked for consistency.

### Impact Explanation
This breaks the tenant isolation between GitHub organizations hosted on the same Shipit instance (a supported, documented configuration — see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`). An operator of one onboarded organization can forge webhook events that are processed as if they came from a different organization's repository, causing unauthorized state-changing actions (e.g., forced `GithubSyncJob` re-sync via `PushHandler`, or destructive `review_stack.archive!` via `PullRequest::ClosedHandler`/`LabeledHandler`) against stacks/repositories they have no legitimate relationship with, without ever needing that other organization's actual webhook secret.

### Likelihood Explanation
Requires the attacker to already be a legitimate operator/admin of at least one GitHub organization configured in the same multi-tenant Shipit deployment (so they know that organization's `webhook_secret`), which is a realistic, low-privilege position relative to any other org hosted on the shared instance — no access to the victim org's secrets, GitHub App, or Shipit account is needed.

### Recommendation
Bind signature-key selection to the same trust anchor used for repository resolution: after verifying, re-derive/require the organization from the *verified* repository record (e.g., look up `Repository.from_github_repo_name(full_name)` and check that its `owner` matches `repository_owner`, or select the app config from the resolved `Stack`'s configured organization rather than trusting `repository.owner.login`/`organization.login` from the raw, not-yet-verified payload) before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with distinct `webhook_secret`s, per `docs/setup.md`'s multi-org setup — attacker only knows `orgA`'s secret (e.g., they administer `orgA`'s own GitHub App).
2. Craft a `pull_request` "closed" JSON payload where `repository.owner.login = "orgA"` but `repository.full_name = "orgB/victim-repo"`, and `pull_request.head.ref` matches an existing review stack of `orgB/victim-repo`.
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, raw_body)`.
4. POST to `/webhooks` with `X-Github-Event: pull_request`.
5. `verify_signature` calls `Shipit.github(organization: "orgA")` and the signature validates successfully.
6. `PullRequest::ClosedHandler#process` resolves `repository` via `Repository.from_github_repo_name("orgB/victim-repo")` and calls `review_stack.archive!`, archiving `orgB`'s review stack despite the attacker never possessing `orgB`'s credentials.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
