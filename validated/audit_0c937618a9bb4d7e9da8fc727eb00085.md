### Title
Unhandled exception in c-hash validation on malformed address/chash length crashes the node - (File: `chash.js`)

### Summary
`chash.js`'s `isChashValid()` decodes an attacker-supplied base32/base64 string and then derives bit offsets from the *decoded buffer length* without validating that this length actually matches the expected 160/288-bit c-hash size before calling `separateIntoCleanDataAndChecksum()`. If the decode succeeds but yields an unexpected number of bytes, `separateIntoCleanDataAndChecksum()` throws an uncaught `Error`, which — combined with the global crash-on-uncaught-exception handler in `network.js` — takes down the whole node process. This is the same bug class as CVE-2017-12912: a decoder/parser that assumes a fixed, self-consistent data length derived from crafted attacker input, and dereferences/traverses that data using offsets calculated from an unchecked size assumption, causing a crash when the assumption is violated.

### Finding Description
`isChashValid()` only wraps the *decode* call in a `try/catch`; everything downstream (offset calculation and slicing) is unprotected: [1](#0-0) 

`separateIntoCleanDataAndChecksum()` explicitly assumes the decoded bit-length is exactly 160 or 288 and `throw`s a plain `Error` otherwise, with no caller-side try/catch around it: [2](#0-1) 

This function is reached from `isValidChash()`/`isValidAddress()` in `validation_utils.js`, which is used pervasively to validate any address string embedded in a unit posted by an untrusted peer (author addresses, output addresses, inner address definitions, data-feed oracle addresses, etc.): [3](#0-2) 

Because Node's `Buffer.from(str, 'base64')` silently tolerates/skips characters outside the strict base64 alphabet rather than throwing, a crafted 48-character string can decode successfully to a buffer whose length differs from the expected 36 bytes (288 bits), producing a length that is neither 160 nor 288 and triggering the uncaught `Error` in `separateIntoCleanDataAndChecksum`.

Any uncaught exception anywhere in the process is turned into a hard crash by the global handler: [4](#0-3) 

### Impact Explanation
A single, unprivileged unit poster (or AA trigger author, or device-message sender referencing an address field) can embed a crafted address/chash-shaped string that decodes to an unexpected byte length. When a full node validates the unit and reaches address/chash validation, the uncaught exception fires and the node process crashes via the `uncaughtException` handler that intentionally re-throws to "crash the process to avoid ending up in an inconsistent state." This lets a remote, unprivileged peer remotely crash any full node that attempts to validate the malicious unit/message, matching the "network unable to confirm new units" impact category (denial of service against consensus-critical validation) analogous to the crash-on-crafted-input class described in CVE-2017-12912.

### Likelihood Explanation
Likelihood is moderate-to-high for triggering a crash if the attacker can produce a base64/base32 string that (a) satisfies the length pre-check (32 or 48 characters) and (b) decodes without throwing yet yields a byte count that isn't exactly 20 or 36 bytes. This depends on the exact leniency of Node's built-in base64 decoder and the `thirty-two` package's base32 decoder toward non-alphabet characters; I was not able to fully confirm the precise decode semantics of the `thirty-two` library in this repository (its source was not indexed/found), so the base32 (160-bit / address) path is unverified, while the base64 (288-bit) decode path via Node's native `Buffer.from` is a well-known source of length-mismatch behavior on malformed input.

### Recommendation
- In `separateIntoCleanDataAndChecksum()` (and the equivalent length checks in `chash.js`), validate the decoded buffer's exact byte length (20 or 36 bytes) immediately after decode and return `false` from `isChashValid()` instead of throwing, or wrap the offset-calculation call in the same `try/catch` that already guards the decode step.
- Additionally, validate that the input string only contains the strict base32/base64 alphabet before calling the decoder, so length-truncating "lenient" decoding cannot occur.
- Audit other decode entry points (`buffer2bin`/`bin2buffer` in `chash.js`) for similar unchecked-length assumptions.

### Proof of Concept
1. Construct a 48-character string intended to decode as a 288-bit (36-byte) c-hash for use as an asset/definition-template chash field in a unit message, but insert characters outside the base64 alphabet (e.g., spaces or symbols) such that `Buffer.from(str, 'base64')` decodes successfully but yields a buffer that is not exactly 36 bytes.
2. Submit a unit (e.g., in an `address_definition_change` payload's `definition_chash`, or another field validated via `isValidChash(str, 32)`/`isValidChash(str, 48)`) containing this crafted 48-character string to a full node.
3. During validation, `isChashValid()` decodes the string successfully, then `buffer2bin()`/`separateIntoCleanDataAndChecksum()` computes a bit-length outside {160, 288} and throws an uncaught `Error`.
4. The global `process.on('uncaughtException', …)` handler in `network.js` re-throws, crashing the node process — denying service to that node and preventing it from confirming further units until manually restarted.
