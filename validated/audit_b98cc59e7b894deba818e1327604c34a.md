### Title
Cross-repository status forgery via `StatusHandler#process` enables unauthorized-looking deploy of another tenant's stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` with no check that the webhook's originating repository matches the repository owning the target commit's stack, unlike every other handler in the engine which scopes through `Handler#stacks` / `Repository.from_github_repo_name(repository_name)`. Because GitHub forks and shared-history repositories legitimately reuse identical commit SHAs, an attacker who controls (or forks) a repository can send a validly-signed status webhook for their own org that writes a `success` `Status` row onto a commit belonging to an unrelated stack B, flipping `UndeployedCommit#deploy_disallowed?` to `false` and removing the disabled class from `StacksHelper#deploy_button` for code that never passed stack B's actual CI.

### Finding Description
The broken binding: `params.dig('repository', 'full_name')` (the webhook's actual, signature-verified repository) must equal `Stack#repository`'s `full_name` for every `Stack` that owns a `Commit` mutated by that webhook. That equality is enforced by `Handler#stacks`, defined in [1](#0-0) , and used by other handlers (push, pull_request, etc.) to scope which stacks/commits a webhook may touch. `StatusHandler#process` never calls `stacks`; it instead does: [2](#0-1) 

`Commit.where(sha: params.sha)` is a global, unscoped lookup across every stack/repository tracked by the Shipit instance. `create_status_from_github!` creates a `Status` row using the matched commit's own `stack_id` (see `Status.replicate_from_github!`, [3](#0-2) ), i.e. the *target* commit's real stack, not the attacker's stack.

`WebhooksController#verify_signature` only checks that the signature is valid for `repository_owner` derived from the payload itself ( [4](#0-3) ) - it authenticates "this webhook really came from GitHub for repo A," it does not authenticate "repo A is authorized to write status for stack B." Nothing downstream re-checks that binding for `StatusHandler`.

`deployable?` and `deploy_disallowed?` then trust the resulting `Status` unconditionally: [5](#0-4) [6](#0-5) 

Exploit flow: attacker owns/forks a repository A that shares git history (and therefore commit SHAs) with the repository backing victim stack B (a common scenario for any public/open-source project with forks, or any two Shipit stacks tracking related repos). Attacker pushes a commit or opens a PR on repo A causing GitHub to send `POST /webhooks` (event `status`) for a SHA that also exists as an undeployed commit on stack B. This webhook is legitimately signed for repo A's org, passes `verify_signature`, and `StatusHandler#process` matches the SHA against `Commit.where(sha: ...)` system-wide, creating a `success` `Status` on stack B's commit. `UndeployedCommit#deployable?`/`deploy_disallowed?` for that commit now flip to allowed, and `StacksHelper#deploy_button` renders the deploy button without the `disabled` class for an operator viewing stack B, even though B's own CI never ran or passed for that commit.

None of the listed guards catch this: `verify_signature` authenticates the webhook's own repo, not the target stack's repo; `drop_unhandled_event` only checks event type is registered; `ExplicitParameters` schema only validates payload shape (`sha`, `state`, etc.), not repository ownership; there is no `stacks`/`Repository.from_github_repo_name` check in `StatusHandler`.

### Impact Explanation
A record (`Status`) is written for stack B without B's own repository ever authenticating that status, satisfying "a payload for one repository mutating another's stack, commit, task." This changes the UI-rendered deploy affordance for stack B (`StacksHelper#deploy_button` disabled-class removal) and can induce an operator with a legitimate Shipit session to trigger a real deploy of code that never passed stack B's actual CI - an unauthorized deploy induced across tenant boundaries. It is repeatable against any pair of repositories/stacks that share commit SHAs (forks, mirrors, shared upstream history), and the attacker needs no Shipit credentials, no GitHub App secret, and no membership in `Shipit.github_teams`.

### Likelihood Explanation
Preconditions: the target stack B must contain a `Commit` row whose `sha` also exists in a repository the attacker controls (fork or repository sharing git history with B's upstream) - a very common real-world topology for GitHub-hosted projects. The attacker's cost is trivial: push a commit/open a PR on their own repo so GitHub emits a normally-signed `status` webhook; no special GitHub App access or Shipit privilege is needed. This is fully repeatable per matching SHA and scales to any number of victim stacks sharing history with the attacker-controlled repository.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through the same repository-authenticated path used by other handlers, e.g. restrict to commits belonging to `stacks` (`Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`) instead of a bare `Commit.where(sha: params.sha)` across the whole table.

### Proof of Concept
Minitest plan (model/integration level, no live GitHub):
```ruby
test "StatusHandler#process must not update Status for a commit owned by a different repository's stack" do
  repo_a = shipit_repositories(:repo_a) # attacker-controlled repo
  repo_b = shipit_repositories(:repo_b) # victim repo/stack B
  stack_b = repo_b.stacks.first
  shared_sha = "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"

  commit_b = stack_b.commits.create!(sha: shared_sha, message: "shared history commit")
  undeployed_commit_b = Shipit::UndeployedCommit.new(commit_b, index: 0)
  assert_predicate undeployed_commit_b, :deploy_disallowed? # binding LHS: no success status for stack B yet

  payload = {
    "repository" => { "full_name" => repo_a.github_repo_name, "owner" => { "login" => repo_a.owner } },
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/attacker"
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit_b.reload
  undeployed_commit_b = Shipit::UndeployedCommit.new(commit_b, index: 0)

  # Assert the binding still holds: a webhook signed for repo_a must not make stack_b's commit deployable
  refute_predicate undeployed_commit_b, :deployable?, "cross-repo webhook must not mark stack B's commit deployable"
  assert_predicate undeployed_commit_b, :deploy_disallowed?

  # Render StacksHelper#deploy_button for stack_b and assert 'disabled' class remains present
  view = ActionView::Base.with_empty_template_cache.new(ActionView::LookupContext.new([]), {}, nil)
  view.extend(Shipit::StacksHelper)
  html = view.deploy_button(stack_b, undeployed_commit_b)
  assert_includes html, "disabled"
end
```
This test currently fails against the shown code (the status gets created on `commit_b` and `deployable?`/`deploy_button` flip), demonstrating the cross-repo forgery.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

      ].join(' '))
