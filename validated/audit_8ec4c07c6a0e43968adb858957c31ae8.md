### Title
Webhook Signature Verification is Keyed to an Attacker-Chosen `repository.owner.login`, Decoupled from the `repository.full_name`/Commit SHA Actually Mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which HMAC secret) to validate a webhook against using `repository_owner`, a value read straight out of the unauthenticated JSON body (`params.dig('repository','owner','login')`). The event handlers that actually mutate state (`StatusHandler`, `PushHandler`, etc.) use a *different* field from the very same body — `repository.full_name` (or, for statuses, only `sha`, with no repository scoping at all) — to decide what gets written. Because these two fields are independently attacker-controlled inside one JSON payload, the "organization whose signature was checked" and "the resource that gets written to" are not the same binding, breaking the intended equality `verified_org == acted_upon_repository`.

### Finding Description
`WebhooksController#verify_signature` picks the app/secret to validate against based on attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` short-circuits to `true` whenever that selected organization has no `webhook_secret` configured — and `webhook_secret` is explicitly documented as *optional*: [3](#0-2) [4](#0-3) [5](#0-4) 

Meanwhile, the handlers that actually mutate Shipit state use a *different* field from the same JSON body to decide the target of the mutation. `Handler#stacks`/`#repository_name` reads `repository.full_name`: [6](#0-5) 

and `StatusHandler#process` does not even scope by repository at all — it matches purely on commit `sha` across the *entire* Shipit instance: [7](#0-6) 

Because `repository.owner.login` (used only to pick the verification key) and `repository.full_name`/`sha` (used to select what gets written) are two independent fields inside the same attacker-controlled JSON body, an attacker can craft a payload where `repository.owner.login` names an organization that has no `webhook_secret` configured (a documented, supported configuration), causing `verify_webhook_signature` to return `true` unconditionally, while `repository.full_name` (for push/pull_request events) or `sha` (for status events) references a completely unrelated, secret-protected repository/commit tracked by the same Shipit instance. The signature check therefore authenticates nothing about the repository actually acted upon.

### Impact Explanation
This breaks the equality `organization that authenticated the payload == repository/commit that is written`, which is the exact analog of the reported bug class (a verified field decoupled from the field actually acted upon). Concretely:
- Via `StatusHandler`, an unauthenticated attacker can forge a `success` commit status for **any** commit SHA tracked anywhere in the Shipit instance (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), which can satisfy Shipit's blocking-status/CI-gating checks used before merges/deploys — leading to an unauthorized deploy or merge.
- Via `PushHandler`, an attacker can trigger `sync_github` for any tracked stack whose `full_name` they guess/know, regardless of which organization's (secret-less) key was used to pass signature verification.

This maps to the "unauthorized deploy/merge" Critical/High impact bucket defined in scope.

### Likelihood Explanation
Exploitability depends on at least one configured GitHub organization in the Shipit deployment having no `webhook_secret` set. This is not a misconfiguration outside the documented setup — the setup guide explicitly labels the webhook secret as "(optional)" and the shipped example config (`config/secrets.development.example.yml`) ships it commented out/nil by default. Any multi-organization Shipit instance (supported natively, see `test/dummy/config/secrets_double_github_app.yml`) where even one org omits the secret exposes every other org's tracked repositories/commits to forgeable webhooks, with zero attacker credentials required (no session, no `ApiClient` token, no GitHub write access).

### Recommendation
- Do not let an attacker-controlled field select the verification key independent of the field(s) used to select the mutation target. Verify the webhook signature using the secret for the organization that actually owns `repository.full_name` (or reject if they disagree), not `repository.owner.login` alone.
- Reject webhooks entirely if no `webhook_secret` is configured, rather than treating a missing secret as "verification passed" (`return true unless webhook_secret` in `lib/shipit/github_app.rb:76-77`).
- Scope `StatusHandler#process` (and any other handler) to the repository identified in the payload rather than matching purely on `sha` across all repositories.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgA` (no `webhook_secret`) and `OrgB` (tracked repo with real CI blocking statuses), similar to `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature`, body:
```json
{
  "sha": "<sha-of-a-commit-in-OrgB/target-repo>",
  "state": "success",
  "context": "ci/blocking-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/anything" }
}
```
3. `WebhooksController#verify_signature` resolves `repository_owner` to `OrgA` (`app/controllers/shipit/webhooks_controller.rb:59-61`), calls `Shipit.github(organization: 'OrgA').verify_webhook_signature(...)`, which returns `true` unconditionally because `OrgA` has no `webhook_secret` (`lib/shipit/github_app.rb:76-77`).
4. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then creates a `success` status on the target commit in `OrgB`'s repository, without ever validating a signature tied to `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
