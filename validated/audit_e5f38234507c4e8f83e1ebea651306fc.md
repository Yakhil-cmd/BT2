### Title
Cross-organization webhook forgery via organization-scoped signature verification decoupled from the repository actually acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/webhook secret to validate a request against using an attacker-supplied field of the still-unverified JSON body (`repository.owner.login` / `organization.login`), then hands the *entire* unverified body to event handlers, which independently resolve the target `Repository`/`Stack` from a *different* field (`repository.full_name`). In a multi-organization Shipit deployment, if any one configured GitHub organization has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` unconditionally returns `true` for that organization, letting an attacker forge webhook events that name any *other* tracked organization's repository as the target.

### Finding Description
`verify_signature` derives the authenticating organization purely from the incoming (unauthenticated) payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves the app config for that org via `github_app_config`, and organizations are configured independently, each with its own optional `webhook_secret`: [3](#0-2) 

Critically, `GitHubApp#verify_webhook_signature` treats an absent secret as "always verified": [4](#0-3) 

This is a documented, supported configuration state — per-organization secrets can be left blank: [5](#0-4) 

Once `verify_signature` passes (trivially, for the weak/unset-secret organization), `WebhooksController#create` dispatches the *entire, attacker-controlled* JSON body to all registered handlers for the event type, unmodified: [6](#0-5) 

Handlers do not re-check `repository.owner.login` against the resource they act on. Instead, they independently resolve the target `Repository`/`Stack` from `repository.full_name`, a separate, equally attacker-controlled field of the same unauthenticated body: [7](#0-6) [8](#0-7) 

The binding that should hold is:
`organization whose secret authenticated the request == organization owning the repository the handler mutates`

Because `verify_signature` and the handlers each consult a different, independently-attacker-controlled field of the same forged payload, and because the "authenticating organization" selection step can be satisfied for free whenever *any* configured org lacks a webhook secret, this equality is not enforced. This is the direct structural analog of the reported bug class: `authorizeOperator`/`approve()` checked only `tokenOwner == msg.sender` (a narrower authority) while the actual object being granted control over (`tokenId`) was not cross-checked against the broader authorized set — here, the "authenticated organization" is not cross-checked against the "organization that is actually written to."

### Impact Explanation
An unprivileged, unauthenticated external actor (no Shipit session, no `ApiClient` token, no GitHub App key) can forge `status`, `check_suite`, `push`, `pull_request`, `membership`, etc. webhook events for **any repository/stack tracked by the Shipit instance**, as long as the instance is configured with at least one GitHub organization lacking a `webhook_secret`, by simply setting `repository.owner.login`/`organization.login` to that weak organization while setting `repository.full_name` to the real target repository. Depending on which handler is targeted, this can:
- Inject forged commit/check statuses (`status`, `check_suite` handlers), which the merge queue and continuous-deployment logic rely on to gate merges/deploys — enabling an **unauthorized merge or deploy**.
- Create/mutate `Team`/`Membership` records via the `membership` handler, corrupting `Shipit.github_teams` authorization state.
- Trigger `GithubSyncJob`/review-stack lifecycle actions (archive/unarchive, provisioning) on stacks belonging to organizations the attacker has no legitimate relationship with.

This lines up with the Critical/High impact categories: unauthorized deploy/merge, and escalation into `Shipit.github_teams` authorization.

### Likelihood Explanation
Requires only that the Shipit deployment configures more than one GitHub organization (a supported and documented feature — `Shipit.github_organizations`/`github_app_config`) and that at least one of them has no `webhook_secret` set (also an explicitly supported, non-error configuration, as shown in `config/secrets.development.shopify.yml`). No credentials, GitHub App keys, or Shipit accounts are needed — only a plain HTTP POST to the public `/webhooks` endpoint. The likelihood is contingent on this specific multi-org/weak-secret configuration; where every configured org enforces a `webhook_secret`, the immediate bypass path does not apply, though the root design flaw (authenticating org field never cross-checked against the org field handlers actually act on) remains.

### Recommendation
After successfully verifying the webhook signature, re-derive the organization from the verified payload and enforce that it matches the owner of the repository (`repository.full_name` or equivalent) that the corresponding handler is about to mutate, rejecting the request otherwise. Additionally, consider making `webhook_secret` mandatory for every configured organization (removing the "return true unless webhook_secret" bypass, or at least warning/erroring loudly when any organization is left unsecured while others are secured), since a single weakly configured organization currently undermines isolation for all organizations tracked by the same Shipit instance.

### Proof of Concept
Preconditions: Shipit configured with two organizations, e.g. `weak-org` (no `webhook_secret`) and `victim-org` (has a `webhook_secret`, owns tracked repository `victim-org/app` with an active stack).

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json
(no X-Hub-Signature header needed, or any garbage value)

{
  "repository": {
    "owner": { "login": "weak-org" },
    "full_name": "victim-org/app"
  },
  "sha": "<victim-org/app HEAD sha>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://attacker.example.com",
  "created_at": "2026-09-01T00:00:00Z",
  "branches": [{"name": "main"}]
}
```

- `WebhooksController#repository_owner` returns `"weak-org"`. [2](#0-1) 
- `Shipit.github(organization: "weak-org")` resolves `weak-org`'s config, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) `X-Hub-Signature`. [4](#0-3) 
- The request passes `verify_signature`, and `Shipit::Webhooks.for_event('status')` handlers execute against the full JSON body, which references `victim-org/app` — a repository the attacker has no relationship to — allowing a forged "success" status to be recorded on the victim's stack/commit, potentially unblocking deploy/merge gating that depends on that status.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
