### Title
Webhook signature is verified against an organization chosen from the unauthenticated payload, but the write actions are performed against a repository named elsewhere in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization's `webhook_secret` to validate the request signature against by reading `params.dig('repository', 'owner', 'login')` (or `organization.login`) straight out of the **unauthenticated** request body. The handlers that actually act on the payload (create commits, push jobs, update statuses, merge/pull-request state, etc.) resolve the target repository independently, from `payload.dig('repository', 'full_name')`. Nothing binds "the organization whose secret validated this signature" to "the repository the handler is about to write to." [1](#0-0) [2](#0-1) 

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` is derived from attacker-controlled JSON body fields (`repository.owner.login`, falling back to `organization.login`) — not from any authenticated source. [3](#0-2) 

`GitHubApp#verify_webhook_signature` explicitly short-circuits to `true` when no `webhook_secret` is configured for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

Handlers, however, never re-check which organization/secret validated the request — they independently resolve the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

This breaks the intended binding: *"the organization that authenticated the request" should equal "the repository the request is allowed to write to."* Because both values come from the same untrusted body and are read independently, an attacker can:
1. Set `repository.owner.login` (used only for signature lookup) to any organization configured in Shipit's multi-org `secrets.github` config that happens to have no `webhook_secret` set (or one that is otherwise easy to satisfy), causing `verify_webhook_signature` to return `true` unconditionally.
2. Set `repository.full_name` (used by all downstream handlers to select the actual `Stack`/`Repository`) to point at a *different*, security-conscious organization's repository.

The signature check therefore authenticates nothing meaningful about the payload's real target repository, letting an unprivileged external attacker forge events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against any repository tracked by Shipit, as long as any one configured organization in the multi-tenant `secrets.github` config lacks (or has a guessable) `webhook_secret`.

### Impact Explanation
Forged `push`/`status`/`check_suite` events can fabricate passing CI status or push new commits into Shipit's tracked history for a target stack (`GithubSyncJob`, commit status creation, check-run refresh, merge-queue processing all trust these payloads once "verified"). Combined with continuous deployment (`continuous_deployment: true`) or the merge queue (which relies on `StatusChecker` reading these same forged statuses, see `MergeRequest#all_status_checks_passed?`), this can lead to an **unauthorized deploy or unauthorized merge** of a repository the attacker does not control, without ever needing a Shipit session, API token, or the real repository's webhook secret. This satisfies the Critical "unauthorized deploy, rollback or merge" impact bar. [6](#0-5) 

### Likelihood Explanation
Requires: (a) Shipit configured with the multi-org `secrets.github` schema (supported and documented via `github_app_config`/`TOP_LEVEL_GH_KEYS`), and (b) at least one configured organization without a `webhook_secret` (or one whose secret an attacker can otherwise satisfy). This is plausible in real deployments where operators add organizations incrementally and only set secrets for some. The rest of the exploitation path (crafting a JSON body with mismatched `repository.owner.login` vs `repository.full_name`) requires no credentials at all — pure external HTTP POST to the public webhooks endpoint. [7](#0-6) 

### Recommendation
- Never let the request body determine which secret is used to validate itself. Route webhook signature verification by a stable, server-side identifier (e.g. resolve the target `Repository`/`Stack` first from `full_name`, then look up that repository's *own* organization/secret for verification) instead of trusting `repository.owner.login`/`organization.login` from the payload for secret selection.
- Do not allow `verify_webhook_signature` to silently pass (`return true unless webhook_secret`) for organizations that are supposed to have webhooks configured; require an explicit "no verification desired" opt-in rather than defaulting to bypass on missing config.
- After signature verification, assert that the organization associated with the verified secret matches the owner of `repository.full_name` that handlers will act upon, rejecting the event otherwise.

### Proof of Concept
Assume `secrets.github` is configured for two orgs: `org-a` (no `webhook_secret` set) and `org-b` (has a `webhook_secret`, tracked by Shipit with continuous deployment enabled).
```http
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/production-app" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://example.com"
}
```
`repository_owner` resolves to `org-a"`, so `Shipit.github(organization: "org-a")` is used; since `org-a` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (bogus) `X-Hub-Signature`. The status handler then resolves the target stack from `repository.full_name = "org-b/production-app"` and records a forged "success" status for `org-b`'s repository, potentially unblocking continuous delivery/merge for a commit that never actually passed CI.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
