### Title
Cross-organization Team mutation via github_id-keyed lookup in `MembershipHandler#find_or_create_team!` bypassing webhook organization provenance - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook solely against the top-level `organization`/`repository.owner` login [1](#0-0) [2](#0-1) , but `MembershipHandler#find_or_create_team!` looks up the `Team` record purely by `params.team.id` (GitHub's numeric team ID), never checking that the found/created record's `organization` matches the org that actually signed the request [3](#0-2) . Because `Team.find_or_create_by!(github_id:)` only assigns `organization` inside the creation block (which is skipped when a row already exists), an attacker who owns any org can send a signed `membership` webhook naming a pre-existing victim team's `github_id`, and have `team.add_member(member)` mutate that victim-owned `Team` row using only the attacker's own `webhook_secret`.

### Finding Description
The binding that should hold is: `signing_org (repository_owner used in verify_signature) == team_owning_org (Team#organization for the record mutated by team.id)`.

- `verify_signature` resolves `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) , and verifies the signature with that org's own `webhook_secret` [1](#0-0) . This only proves the request was signed by the org named in the top-level `organization`/`repository.owner` key — call this `attacker-org`.
- `Shipit::Webhooks.for_event('membership')` dispatches the raw payload to `MembershipHandler#process` [4](#0-3) .
- `find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . `find_or_create_by!` performs a `find_by(github_id:)` first; the block (which sets `organization`) executes **only on creation**. If a `Team` row with that `github_id` already exists — e.g. created earlier by a legitimate webhook from `victim-org` — it is returned unchanged, regardless of what org is in the current, attacker-signed payload.
- `process` then calls `team.add_member(member)` where `member = User.find_or_create_by_login!(params.member.login)`, and `params.member.login` is fully attacker-controlled [5](#0-4) , `Team#add_member` simply appends the membership [6](#0-5) .

Attack: attacker discovers (or brute-forces, since GitHub team IDs are small sequential integers, or is already visible via public GitHub org API for public teams) the `github_id` of a `Team` row Shipit already created for `victim-org` (e.g. a team listed in `Shipit.github_teams` used for authorization). Attacker sends `POST /webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with their own `attacker-org` `webhook_secret`, and a JSON body:
```
{ "action": "added", "team": {"id": <victim_team_github_id>, "name":"x","slug":"x","url":"x"},
  "organization": {"login": "attacker-org"}, "member": {"login": "attacker-controlled-user"} }
```
`verify_signature` passes because it only checks `attacker-org`'s secret against `attacker-org`. `find_or_create_team!` finds the pre-existing victim `Team` by `github_id` and returns it untouched (organization stays `victim-org`); `add_member` then adds the attacker's user to that team.

No existing guard prevents this: `verify_signature` and `drop_unhandled_event` only gate on event type and the top-level org, `ExplicitParameters` only validates types/presence (not cross-field consistency) [7](#0-6) , and there is no check anywhere comparing `team.organization` to the org that signed the current request.

### Impact Explanation
If the victim `Team` is one of the teams configured in `Shipit.github_teams`, `User#authorized?` grants access based purely on `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [8](#0-7) . Adding an attacker-controlled `User` to that `Team` row therefore grants that user Shipit-authorized status without ever being a member of the victim's real GitHub organization/team — an escalation into `Shipit.github_teams` authorization, and more generally a payload signed by one organization mutating a `Team`/`Membership` record belonging to a different organization. This is repeatable against any `Team` row whose `github_id` the attacker can learn, and requires no session, API token, or victim secret at all — only the attacker's own `webhook_secret` for their own org.

### Likelihood Explanation
Preconditions: the attacker must own/administer at least one GitHub organization registered with Shipit (so they legitimately know their own `webhook_secret` and can send correctly-signed webhooks), and the target `Team` row must already exist in Shipit's database with a known `github_id` (created by a prior legitimate `membership`/team-sync webhook from the victim org). GitHub numeric team IDs are low-cardinality sequential integers and are exposed via GitHub's public API for public teams, making them easy to enumerate or observe. No GitHub App private key, victim `webhook_secret`, or Shipit session is required — cost is a single crafted HTTP POST, fully repeatable and scriptable against any known victim `github_id`.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (`Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify that `params.organization.login` (or `params.dig('organization','login')`) matches `repository_owner`/the org used in `verify_signature` before processing any handler, rejecting the webhook if a `Team` already exists under a different `organization` for that `github_id`.

### Proof of Concept
```ruby
test "membership webhook signed by attacker org cannot mutate a team belonging to another organization" do
  victim_team = Shipit::Team.create!(github_id: 4242, organization: 'victim-org', slug: 'admins', name: 'Admins')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 4242, 'name' => 'Admins', 'slug' => 'admins', 'url' => 'https://api.github.com/teams/4242' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker-controlled-user' },
  }

  Shipit.expects(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true)
  )
  Shipit::User.expects(:find_or_create_by_login!).with('attacker-controlled-user').returns(
    Shipit::User.create!(login: 'attacker-controlled-user', name: 'attacker')
  )

  post :create, body: payload.to_json, headers: {
    'X-Github-Event' => 'membership',
    'X-Hub-Signature' => 'sha1=attacker-org-signature',
  }

  victim_team.reload
  assert_equal 'victim-org', victim_team.organization
  refute victim_team.members.exists?(login: 'attacker-controlled-user'),
    "attacker-org signed webhook must not be able to add a member to a team owned by victim-org"
end
```
Before the fix this assertion fails (the membership is added); it demonstrates that `signing_org` (`attacker-org`) and `team_owning_org` (`victim-org`) diverge and are never cross-checked.
