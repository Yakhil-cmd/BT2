### Title
Missing cosigner ownership check in device "sign" request handler allows unauthorized signing requests for a victim's own addresses - ([File: wallet.js])

### Summary
The Craft Commerce advisory describes an IDOR where a user-supplied `number` identifier is used to load and operate on a cart with no check that the requester actually owns it. The analogous flaw in ocore is in the peer-to-peer "sign" message handler in `wallet.js`, where a paired correspondent device supplies an `address` (a public, guessable/known identifier, since Obyte addresses are visible on-chain) to request that the local wallet sign an attacker-controlled unit. The code path that would verify the sender is actually an authorized cosigner/party for that address was deliberately commented out, so any correspondent device can reach the signing workflow for any address the local wallet locally controls.

### Finding Description
In the `handleMessageFromHub` dispatcher, the `"sign"` case processes a signing request received from any known correspondent device: [1](#0-0) 

After validating the address format, signing path format, and that the target address is among the authors of the unsigned unit, the code calls `findAddress(body.address, body.signing_path, {...})`. When the address is a locally-controlled key (`ifLocal`), the intended ownership check — verifying that the sender device (`from_address`) is actually a recorded cosigner (extended pubkey holder) for that address's wallet — is explicitly disabled: [2](#0-1) 

The comment states plainly: *"the commented check would make multilateral signing impossible"* — i.e., the ownership/ acccess check was intentionally removed to support the "dumb contract"/arbiter/prosaic-contract multilateral-signing use case, where a counterparty's device is allowed to request that the local device sign a message with its own key. But this generic removal means **any** correspondent (not just a legitimate contract counterparty) can send a `sign` request naming **any** address the local wallet locally controls, supplying arbitrary unit content, and the code proceeds straight to firing a `signing_request` event: [3](#0-2) 

The only remaining discriminator between a legitimate multilateral-signing contract flow and an attacker-crafted request is a heuristic performed later, purely for UI/popup-selection purposes (not access control), which inspects the payment outputs for known arbiter/prosaic contract "charge amounts" to decide which confirmation text to show: [4](#0-3) 

This is the same root-cause class as the Craft Commerce bug (CWE-639): a client-supplied object identifier (`address`, analogous to the cart `number`) is used to reach a sensitive operation (producing a cryptographic signature with a wallet-controlled private key) without verifying that the requester has any legitimate relationship (cosignership) to that identifier — the check exists in the code but was purposely disabled.

### Impact Explanation
A malicious paired correspondent can trigger the local wallet's signing subsystem for any address it locally controls, using unit content fully crafted by the attacker, without ever having been a party to a shared/multisig address involving that attacker. Depending on how the host application's `signing_request` event listener is implemented (some wallet/bot integrations use heuristics keyed on the same "known contract charge amount" logic to auto-approve certain flows), this can be leveraged to solicit signatures over attacker-chosen payment outputs, potentially leading to unauthorized spending of the victim's funds from an address the victim believed was only used with a specific, mutually-agreed counterparty. Even absent full auto-approval, it lowers the bar for social-engineering a signature since the code deliberately foregoes cryptographic/ownership gating in favor of trusting the correspondent-level pairing alone.

### Likelihood Explanation
Requires only that the attacker already be a paired correspondent device of the victim (a normal, low-privilege relationship established via routine device pairing, not requiring being a cosigner of any specific address) and that they know one of the victim's addresses (which are inherently public once used on-chain). This matches the "paired device" actor explicitly in scope, and the guarded code path is directly reachable from network input (`handleMessageFromHub`) with no additional authorization.

### Recommendation
Restore and correctly scope an authorization check before honoring a "sign" request for a locally-controlled address: verify that `from_address` is actually a member/cosigner of the wallet or shared-address definition associated with `body.address`/`body.signing_path`, or, for multilateral (non-multisig) "dumb contract" flows, verify that the request corresponds to a wallet-tracked contract record where `from_address` is the recorded peer/cosigner (as is already done for `arbiter_contract_update`). Do not rely solely on heuristic payload inspection (`prosaic_contract.CHARGE_AMOUNT`/`arbiter_contract.CHARGE_AMOUNT`) for access control decisions.

### Proof of Concept
1. Attacker pairs with the victim's device through normal device pairing (no special privilege required).
2. Attacker learns one of the victim's on-chain addresses `A` that the victim's wallet locally controls (addresses are public).
3. Attacker sends a `"sign"` message to the victim's device: `{address: "A", signing_path: "r", unsigned_unit: <attacker-crafted unit spending from A>}`.
4. In `wallet.js`, the format checks pass, `findAddress` resolves `A` as `ifLocal`, and because the ownership check is commented out, the code proceeds directly to emit `signing_request` for the attacker's unit — without ever verifying the attacker has any relationship to `A`.
