### Title
Cross-repository CI status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)` [1](#0-0)  without any scoping to the repository/stack named in the webhook payload. Because git commit SHAs are content-addressed and identical across forks/mirrors of the same history, any GitHub organization onboarded to the same Shipit instance can emit a genuinely signed webhook (for their own repository) whose `sha` happens to match a commit that also exists in a *different* tenant's stack, and that webhook will mutate the victim stack's `Status` history and fire `deployable_status`/`commit_status` hooks for the victim.

### Finding Description
The broken binding: **statuses applied to a `Commit` row should equal statuses whose delivering webhook was authenticated for the repository/stack that `Commit` row belongs to** — i.e. `commit.stack.repository == verified_repository_owner_of_signature`. This binding is violated because:

1. `WebhooksController#verify_signature` only checks that the HMAC signature matches `Shipit.github(organization: repository_owner)` — the organization named in the *attacker's own* payload — using that organization's real webhook secret [2](#0-1) . It proves the request came from GitHub for *some* org the attacker legitimately controls; it says nothing about which `Commit`/`Stack` the payload's `sha` is allowed to touch.
2. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0)  — a global, cross-stack, cross-repository lookup keyed only on `sha`. `Commit belongs_to :stack` [3](#0-2) , and nothing in the handler filters by `stack_id`/`repository`.
3. `Commit#create_status_from_github!` → `#add_status` unconditionally emits `Hook.emit(:commit_status, stack, ...)` and, on the state transitions defined by the `expected_webhook_transitions` matrix, `Hook.emit(:deployable_status, stack, ...)` for whichever `stack` the matched `Commit` row belongs to [4](#0-3) [5](#0-4) .

Exploit flow: an attacker who controls their own GitHub org/repo forks (or otherwise shares commit history with) a victim repository that is also tracked as a Shipit stack (the identical git commit therefore exists as separate `Commit` rows in both the attacker's stack and the victim's stack, sharing the same `sha`). The attacker triggers (or directly crafts, since the payload's `state`, `description`, `context`, `target_url` fields are attacker-authored content sent alongside a real GitHub signature for their own org) two consecutive `status` webhooks for that shared SHA — first `pending`, then `success` — signed with their own org's real webhook secret. `verify_signature` passes because the signature is valid for the attacker's own org. `StatusHandler` then updates **every** `Commit` row with that SHA, including the victim's, and `add_status` fires `commit_status`/`deployable_status` on the victim's stack, potentially making `Commit#deployable?` true and unblocking hooks/merges/deploys keyed on CI success [6](#0-5) .

None of the existing guards prevent this: `verify_signature` is scoped to organization-level authenticity, not commit/repository ownership; `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.) [7](#0-6) ; the base `Handler#stacks`/`repository_name` scoping helper exists but is **not used** by `StatusHandler#process`, unlike other handlers (e.g. `PullRequest::ClosedHandler` explicitly resolves `repository` from `params.repository.full_name` before acting) [8](#0-7) .

### Impact Explanation
A forged/legitimately-signed webhook from an attacker-controlled repository can write `Status` records and fire `deployable_status` hooks against a victim stack the attacker never authenticated for, synthesizing a fake CI life-cycle (`pending → success`) on a commit that is not deployable. This can flip `Commit#deployable?` to `true` and trigger `ContinuousDeliveryJob`/merge-request processing/hooks configured on the victim stack — a payload for one repository mutating another's commit/stack state, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). The precondition (shared commit SHA across two Shipit-tracked stacks) is realistic in multi-tenant Shipit deployments that track both upstream and forked/mirrored repositories.

### Likelihood Explanation
Requires: (a) a Shipit instance tracking more than one stack whose git histories overlap (fork of a tracked repo, mirrored repo, or a repo added twice), and (b) the attacker being able to get GitHub to deliver, or self-construct with a valid signature for their own org's webhook secret, a `status` event whose `sha` equals a commit shared with the victim stack. Part (b) is straightforward for any organization admin able to configure/replay their own org's real webhook traffic; part (a) depends on deployment topology but is a common pattern (upstream + fork both tracked, e.g. for review-app or fork-based CI workflows). No secrets or privileged Shipit roles are required beyond control of one's own onboarded GitHub organization.

### Recommendation
Scope `StatusHandler#process` (and any other SHA-keyed handler) to the repository named in the payload, mirroring the `Handler#stacks`/`repository_name` helper already present in the base class, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or explicitly `Commit.joins(:stack).merge(Stack.where(id: stacks.select(:id))).where(sha: params.sha)`, so only commits belonging to stacks whose repository matches the authenticated payload's `repository.full_name` are updated.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (new)
test "status webhook does not update commits belonging to a different stack sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = Shipit::Stack.create!(repository: Shipit::Repository.create!(owner: 'attacker', name: 'fork'), environment: 'production', branch: 'master')

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared', authored_at: Time.now, committed_at: Time.now)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'shared', authored_at: Time.now, committed_at: Time.now)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => 'attacker/fork' }
  }

  # binding under test: statuses written to victim_commit == 0 (no legitimate webhook authenticated for victim repo)
  assert_equal 0, victim_commit.statuses.count

  Shipit::Webhooks::Handlers::StatusHandler.call(ExplicitParameters::Parameters.define { }.parse!(payload))

  victim_commit.reload
  attacker_commit.reload

  # EXPECTED (fixed): victim untouched, only attacker's own stack's commit updated
  assert_equal 0, victim_commit.statuses.count, "victim commit must not receive statuses from a webhook authenticated for a different repository"
  assert_equal 1, attacker_commit.statuses.count
end
```
Currently (unfixed), both `victim_commit` and `attacker_commit` receive the status update because `StatusHandler#process` queries `Commit.where(sha: ...)` globally, demonstrating the divergence between "0 legitimate webhooks scoped to the victim repository" and "1 forged status actually written to the victim's commit."

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
