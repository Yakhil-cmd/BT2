## Title
Cross-organization CI status forgery via unscoped `sha` lookup in `StatusHandler` bypasses the organization-that-authenticated ↔ repository-that-is-written binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization `webhook_secret` to validate a webhook's HMAC signature against, based solely on `repository.owner.login` (or `organization.login`) taken from the *unauthenticated* JSON body. Once that signature check passes, the resulting handler dispatch for GitHub `status` events (`StatusHandler`) never re-derives or checks the target repository/stack at all — it matches purely by commit `sha`, globally across every stack in the Shipit instance. This breaks the equality that should hold between "the organization whose secret validated this signature" and "the repository that the event is allowed to mutate."

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the payload (`repository.owner.login`, falling back to `organization.login`) and looks up the corresponding `GitHubApp`/`webhook_secret` via `Shipit.github(organization: repository_owner)`: [1](#0-0) 

`GitHubApp#verify_webhook_signature` then HMACs `request.raw_post` with that organization's `webhook_secret`: [2](#0-1) 

Because the raw body is attacker-controlled and the secret selection field (`repository.owner.login`) is likewise inside that same attacker-controlled body, an attacker who legitimately owns *any* organization/repo configured in this Shipit instance (i.e. they know their own org's `webhook_secret`, e.g. because they configured their own GitHub App/webhook) can craft an arbitrary payload where `repository.owner.login` == "their own org" (so the correct, known secret is used and the signature check passes) while every other field in the payload — crucially `sha` — refers to an object in a completely different repository/organization.

Once past `verify_signature`, `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, whose `process` method does not use `repository_name`/`stacks` scoping (unlike `PushHandler`, `PullRequest::*Handler`, which all resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting): [3](#0-2) 

Instead it does a bare, instance-wide lookup:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This matches **every** `Commit` row in the database with that SHA, regardless of which stack/repository/organization it belongs to. The base `Handler#stacks`/`repository_name` scoping mechanism that every other handler relies on is defined but simply unused here: [4](#0-3) 

Equality that should hold but doesn't:
`organization authenticated by verify_signature (repository.owner.login → webhook_secret)` == `organization/repository actually mutated by StatusHandler (Commit.where(sha:))`

Before the attack: only the organization owning `sha`'s repository can produce a validly-signed `status` event for that commit's stacks.
After the attack: any organization configured in the Shipit instance, using its own valid webhook secret, can inject a `status` webhook whose `sha` belongs to any other tracked repository, and `StatusHandler` will happily create a `Status` record on that foreign commit.

### Impact Explanation
`Commit#create_status_from_github!` → `#add_status` recomputes the commit's aggregate `status`, which feeds `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`): [5](#0-4) 

and drives continuous deployment / merge-queue progression via `add_status`'s status-transition side effects (`schedule_merges`, `deployable_status`/`commit_status` hook emission which downstream can enqueue `ContinuousDeliveryJob`): [6](#0-5) [7](#0-6) 

By forging a `success` status for a victim repository's commit SHA, an attacker (who only controls their own unrelated organization's webhook secret) can flip a foreign commit into `deployable?`/CI-green state, which — on a stack with `continuous_deployment: true` — leads to an unauthorized deploy being triggered on infrastructure the attacker has no legitimate access to. This satisfies the "unauthorized deploy" Critical impact bucket. It also allows polluting/falsifying a victim repo's commit status history (denial of trust in CI signal) even without CD enabled.

### Likelihood Explanation
Requires the attacker to be a legitimate, low-privilege tenant of the same multi-org Shipit deployment (they must know/control at least one org's `webhook_secret`, which they set up themselves for their own repo) — this is exactly the "unprivileged attacker" class described: no `ApiClient` token, no `webhook_secret` of the *victim*, no repository write access, no GitHub App private key of the target org is needed. SHAs are not secret (visible in any public/private repo's commit history, PRs, CI logs, etc.), and no interaction with the victim is required — this is a direct unauthenticated-relative-to-victim POST to `/github/webhooks`.

### Recommendation
`StatusHandler#process` (and any other handler that does not scope by `repository.full_name`) must resolve the target repository/stacks the same way `Handler#stacks`/`repository_name` does, and only update `Status` records for commits belonging to stacks under that resolved repository — i.e. `stacks.commits.where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`. More fundamentally, `verify_signature` should bind the *verified* organization to the specific repository being mutated for every event type, not just implicitly assume handlers will re-derive and check it themselves.

### Proof of Concept
1. Attacker controls org `attacker-org` in this Shipit instance and knows its `webhook_secret` (self-configured GitHub App/webhook for their own tracked repo).
2. Attacker learns (public knowledge) the commit `sha` of a commit tracked in victim stack `victim-org/victim-repo` (e.g. from a public PR, or by observing merge status pages).
3. Attacker builds body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/attacker-forced",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(attacker-org webhook_secret, body)>` and `X-Github-Event: status`, then POSTs directly to the Shipit webhooks endpoint.
5. `verify_signature` resolves `repository_owner == "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the HMAC check passes (attacker knows this secret).
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and matches the victim's commit, calling `commit.create_status_from_github!(params)`, injecting a fabricated `success` status onto `victim-org/victim-repo`'s commit — independent of `attacker-org` having any relationship to that repository.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state

      end
      new_status
