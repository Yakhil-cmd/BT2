### Title
Cross-repository status forgery escalates arbitrary victim commits to deployable — `StatusHandler#process` resolves commits by bare SHA with no repository check ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)`, with no comparison against the `repository`/`repository_owner` named in the signed webhook payload. Because a GitHub App's webhook secret is shared across every installation of that App (not scoped per-repository), any attacker who owns a repository where the App is installed can send a validly-signed `status` webhook naming an arbitrary SHA, and Shipit will attach that status to whichever commit(s) in its database happen to share that SHA — including a completely unrelated victim stack's commits.

### Finding Description
The claimed binding is: `{commits selectable by Stack#next_commit_to_deploy as deployable} == {commits whose Status rows originate from a payload naming that stack's own repository}`. This binding is **false** in the code.

`Stack#next_commit_to_deploy` (`app/models/shipit/stack.rb:235-243`) calls the private `deployable_commits`, which iterates commits and calls `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`), which in turn depends on `success?`/`blocked?` derived from `statuses` (`Commit#status`, line 304-306, aggregating `statuses_and_check_runs`).

Those `Status` rows are created exclusively via `StatusHandler#process`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This query is global across the `commits` table — it is **not** scoped by `repository_id`, `stack_id`, or any comparison to a `repository`/`owner`/`name` field carried in the webhook payload. `create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` using the found commit's own `stack_id` — i.e., the *victim's* stack — regardless of which org/repo actually signed the incoming request. [2](#0-1) 

Because git commit SHAs are content-addressed, an attacker who forks the victim's public repository automatically shares identical SHAs for every commit up to the fork point (and can craft further commits with attacker-controlled trees that still hash predictably, or simply reuse the shared ancestor commits from the still-undeployed backlog). If the attacker's own account/org has the GitHub App or webhook installed on any repository they control, they can trigger (or directly forge, since GitHub App webhook secrets are shared per-App rather than per-installation) a `status` event naming `state: success` for those shared SHAs. `verify_signature`/`GitHubApp#verify_webhook_signature` only proves the payload was signed with a secret known to that GitHub App installation — it does not, and cannot from the code shown, bind the payload's SHA to the specific repository/stack the victim owns, because `StatusHandler#process` never re-checks the payload's `repository` against the commit's actual `stack.repository`.

Repeating this for each of several sequential undeployed, CI-less victim commits flips `Commit#deployable?` to `true` for the whole set. `Stack#next_commit_to_deploy` with `maximum_commits_per_deploy` set will then walk the capped batch of commits and select the "most recent, now-deployable" commit via `deployable_commits(commits.to_a.reverse.find(&:deployable?))` (`app/models/shipit/stack.rb:645-647`), returning a batch that was never validated by the victim's real CI. If `continuous_deployment?` is enabled, this can directly trigger `trigger_deploy` via `ContinuousDeliveryJob` (`Commit#schedule_continuous_delivery`, `app/models/shipit/commit.rb:281-287`), i.e., an unauthorized deploy.

None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `force_github_authentication`, `User#authorized?`, `require_permission!`, model validations) address this, because they operate at the transport/authentication layer or on unrelated models — none of them assert that the `sha` in a `status` payload belongs to the repository that actually produced the signed request.

### Impact Explanation
A `Status` record (fabricated `success` state) is written against a victim stack's commit that never underwent CI, driven by a webhook the attacker signed using only their own org/App installation credentials — this is a payload for one repository mutating another repository's commit/stack data, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). Repeated across a backlog of undeployed commits, this can escalate an entire batch to deployable and, with continuous deployment configured, produce an actual unauthorized deploy. The blast radius spans any victim stack whose commit SHAs the attacker can reproduce (trivial via forking public repos) and is repeatable indefinitely since nothing rate-limits or revalidates repository provenance for `status` events.

### Likelihood Explanation
Preconditions match realistic operation: a victim stack with `maximum_commits_per_deploy` set and several undeployed commits lacking CI status is a normal steady state. The attacker needs only: (1) a fork or knowledge of the victim's commit SHAs (public repos make this trivial), and (2) the ability to have the GitHub App/webhook installed on a repository they control so they can emit a validly-signed `status` payload naming an arbitrary SHA. No Shipit session, API token, or `webhook_secret` for the victim's own org is required — only their own org's installation. This is low-cost and fully repeatable against any public victim repository/stack pair.

### Recommendation
In `StatusHandler#process` (and analogous handlers that resolve records purely by SHA), scope the `Commit` lookup by the repository named in the webhook payload — e.g., join through `stack.repository` and compare `owner`/`name` (or `repository.full_name`) against `params.repository` before creating/updating any `Status`, rejecting or ignoring statuses whose payload repository does not match the commit's own stack repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb
class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
  test "forged cross-repo status batch escalates victim backlog to deployable" do
    victim_stack = shipit_stacks(:shipit)
    victim_stack.update!(cached_deploy_spec: DeploySpec::Cached.new(
      DeploySpec.new({}, maximum_commits_per_deploy: 3)
    ))

    victim_commits = 3.times.map do |i|
      victim_stack.commits.create!(sha: "victimsha#{i}" * 5, message: "victim #{i}")
    end

    # Before: all commits non-deployable (no CI statuses at all)
    assert_nil victim_stack.next_commit_to_deploy

    # Attacker forges 'status' webhooks naming the shared SHAs, unrelated to victim_stack's repo,
    # signed only with the attacker's own org webhook_secret / GitHub App installation.
    victim_commits.each do |commit|
      Shipit::Webhooks::Handlers::StatusHandler.new(
        stack: nil,
        params: { sha: commit.sha, state: 'success', context: 'ci/attacker' }
      ).process
    end

    victim_commits.each(&:reload)
    assert victim_commits.all?(&:deployable?),
      "victim commits became deployable via forged cross-repo statuses"

    # Broken binding demonstrated: next_commit_to_deploy now returns a commit
    # whose Status did NOT originate from the victim stack's own repository payload.
    assert_equal victim_commits.last, victim_stack.next_commit_to_deploy
  end
end
```
This demonstrates that the equality `{deployable-selectable commits} == {commits with statuses originating from that stack's own repository payload}` does not hold: statuses created via `StatusHandler#process` are accepted purely on SHA match, letting `Stack#next_commit_to_deploy` select commits validated only by an unrelated, attacker-controlled repository's webhook.
