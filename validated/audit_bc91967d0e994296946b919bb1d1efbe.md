### Title
Uncaught exception in `getHeadersSize` crashes node on malformed `earned_headers_commission_recipients`/header numeric field in a posted unit - (File: object_length.js)

### Summary
The CVE describes Wireshark's TCP dissector crashing when it encountered an unexpected/invalid checksum value (`0xFFFF`) that wasn't properly handled before further processing. The analogous bug class here is: a numeric field inside an untrusted, attacker-supplied unit is not range/type-validated before being fed into a length-computation routine that `throw`s on invalid input, and that computation is invoked in `validation.js` **without a surrounding try/catch**, unlike its sibling call.

### Finding Description
`getLength()` in [1](#0-0)  throws `Error("invalid number: " + value)` whenever it encounters a non-finite JS number (`Infinity`/`-Infinity`/`NaN`). `getHeadersSize(objUnit)`, defined at [2](#0-1) , calls `getLength` on a cloned copy of the unit header that still includes attacker-supplied fields such as `authors`, `witness_list_unit`, `witnesses`, `earned_headers_commission_recipients`, `last_ball`, `last_ball_unit`, `tps_fee`, `burn_fee`, and `max_aa_responses`.

In `validate()`, `getHeadersSize` is invoked directly, with no try/catch, at [3](#0-2) :
```
if (objectLength.getHeadersSize(objUnit) !== objUnit.headers_commission)
    return callbacks.ifJointError("wrong headers commission, expected "+objectLength.getHeadersSize(objUnit));
```
Compare this to the immediately following call to `getTotalPayloadSize`, which the author explicitly wrapped in try/catch to convert any thrown error into a joint error instead of letting it escape: [4](#0-3) .

At the point `getHeadersSize` is called (line 257), most numeric unit fields (`tps_fee`, `burn_fee`, `max_aa_responses`) have already been type-checked as finite integers earlier in the function (lines 199-210), but nested, attacker-controlled numeric values inside `authors` (e.g., inside `definition`/`authentifiers` structures) and especially `earned_headers_commission_recipients` (whose shape/type is only validated later, inside `validateHeadersCommissionRecipients`, which runs *after* line 257, and only if `objUnit.content_hash` is falsy) have not yet been validated. A JSON payload containing a numeric literal that overflows to `Infinity` when parsed (e.g. `1e400`) is valid JSON and will deserialize to `Infinity` in JavaScript. If such a value appears anywhere in the header-relevant part of the unit (outside of `messages`, which is stripped before this call), `getLength` throws, and because line 257 is not wrapped in try/catch, the exception propagates out of the synchronous portion of `validate()`. Depending on the caller (e.g., unit processing paths in `network.js` reachable from `handleJoint`/`processIncomingUnitsBatch` or joint-storage read paths), this can surface as an unhandled exception, crashing the node process or corrupting the shared validation flow for that connection/queue.

### Impact Explanation
Because `validate()` is the sole gate through which any posted unit passes before acceptance/rejection, an uncaught exception thrown deep inside this pre-mutex-lock code path means every full node that receives the malicious unit hits the same crash deterministically. This matches the "network unable to confirm new units" / "node disagreement on validity" impact classes: nodes that crash stop confirming any unit, and any nodes that happen to handle the exception differently (e.g., depending on process-level uncaught-exception handlers) could diverge in whether they persist partial state, creating consensus disagreement. This is reachable by any unprivileged unit poster — no special privileges, hub, or node compromise required.

### Likelihood Explanation
Likelihood is limited by two open questions I could not fully verify given index constraints:
1. Whether `objJoint` objects reaching `validate()` are always produced via `JSON.parse` of raw network/composer input (which would let `1e400`-style literals become `Infinity`) or whether some intermediate sanitation elsewhere strips/rejects non-finite numbers before `validate()` is reached.
2. The exact structure and prior-validation order of `earned_headers_commission_recipients` and whether any earlier check (e.g., `isTooDeeplyNestedOrHasTooManyNodes`, `isObjectWellFormed`) already rejects non-finite numbers before line 257.

Both would need confirmation by tracing `network.js`'s `handleOnlineJoint`/`handleSavedJoint` parsing path and `string_utils.js`'s `isObjectWellFormed` in a full checkout, which the current index does not fully expose. Given the asymmetric try/catch treatment between the two adjacent calls (`getHeadersSize` uncaught vs. `getTotalPayloadSize` caught) in the same function, this looks like a genuine oversight rather than an intentional design decision, which increases confidence that this is a real analog rather than a false positive — but I flag this as not fully proven root-cause due to the above unknowns.

### Recommendation
Wrap the `getHeadersSize` call at [3](#0-2)  in the same try/catch pattern already used for `getTotalPayloadSize` immediately below it, converting any thrown error (invalid/non-finite number, non-own property, unknown type) into `callbacks.ifJointError(...)` instead of letting it propagate as an uncaught exception. Additionally, consider validating that all numeric leaves in an incoming unit are finite integers as part of the early structural checks (`isObjectWellFormed`/`isTooDeeplyNestedOrHasTooManyNodes`), before any length/commission computation is performed.

### Proof of Concept
Construct and broadcast a unit whose header-relevant JSON contains a numeric literal that overflows to `Infinity` on `JSON.parse`, e.g. as an extra field permitted by `hasFieldsExcept` in `earned_headers_commission_recipients` (or another header field not yet type-checked at the time `getHeadersSize` runs):
```json
{
  "unit": { ...
    "earned_headers_commission_recipients": [
      { "address": "SOME32CHARBASE32ADDRESS........", "earned_headers_commission_share": 1e400 }
    ],
    ...
  }
}
```
When this joint reaches `validate()`, execution reaches line 257 (`objectLength.getHeadersSize(objUnit)`), which internally calls `getLength()`; encountering the `Infinity` value at [1](#0-0)  causes a thrown `Error("invalid number: Infinity")` that is not caught anywhere in `validate()`'s synchronous preamble, propagating up to the caller. This step could not be fully exercised against a live node process from the index alone, so the exact downstream effect (process crash vs. caught by an outer domain/try) should be confirmed by running the actual `validate()` call with this crafted joint in a Devin session with full repo/runtime access.
