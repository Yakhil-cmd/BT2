## Finding: Stack-scoped `ApiClient` tokens can read the CCMenu status of any stack, bypassing their stack authorization

### Title
Stack-scoped `ApiClient` tokens bypass stack authorization in `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController#stack` resolves the target stack directly from the request parameter instead of going through the stack-scoping helper used by every other API controller, letting a token that is only authorized for one stack read the CI/deploy status of any other stack.

### Finding Description
`Shipit::ApiClient` can be scoped to a single stack via its optional `stack` association, and its authorization check is purely permission-string based: [1](#0-0) [2](#0-1) 

`check_permissions!` only verifies that `"#{operation}:#{scope}"` (e.g. `read:stack`) is present in the client's `permissions` array; it says nothing about *which* stack instance the client is entitled to touch. The actual binding enforcing "this token may only see its own stack" lives in `Api::BaseController`: [3](#0-2) 

Here, `stacks` is scoped down to `current_api_client.stack_id` when that attribute is set, and `stack` is derived from that already-scoped collection. This is the binding: *the stack a token authorizes == the stack the request may touch*, enforced through `stacks.from_param!(params[:stack_id])`.

`Api::CCMenuController` inherits from `BaseController` and declares only a generic permission requirement, but it overrides `stack` to bypass the scoped `stacks` collection entirely: [4](#0-3) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

This resolves `params[:stack_id]` against **all** stacks (`Stack.from_param!`), not the client's authorized subset. It also accepts authentication via a plain `params[:token]` in addition to the inherited Basic-Auth path:

```ruby
def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

So the equality that holds everywhere else in the API (`current_api_client.stack_id == requested stack.id`, when the client is stack-scoped) is broken specifically in this controller: `require_permission :read, :stack` only checks the client possesses *some* `read:stack` permission, and `stack` no longer intersects that permission with the client's own `stack_id`.

The existence of stack-scoped tokens as a real security boundary is demonstrated by the test suite itself and by `CCMenuUrlController`, which is one legitimate producer of such tokens tied to a specific stack's CCMenu URL, and by other fixtures/tests asserting that a stack-scoped client "will only see that one stack": [5](#0-4) [6](#0-5) 

### Impact Explanation
This is the direct analog of the CEI-style trust-binding violation in the report: the token's *authorized* scope (one stack) is checked once via a generic permission string, but the actual resource acted upon (*any* stack via `params[:stack_id]`) is never re-verified against that authorization before use — exactly the "check vs. effect" gap pattern, here manifesting as "a stack a token authorises versus a stack it touches" rather than reentrancy. Any holder of a stack-scoped `read:stack` `ApiClient` token (a routine, low-privilege credential, e.g. a CI integration or a CCMenu URL issued for one project) can enumerate other stacks and read their build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state, etc.) for stacks they were never granted access to. This is an unauthenticated-for-that-resource read of stack state, matching the High-severity criterion "escalation into ... unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Any party in possession of a legitimately-issued, narrowly stack-scoped `ApiClient` token (which the engine's own design encourages via `CCMenuUrlController`, and via UI-created `ApiClient`s tied to a `stack`) can trivially exploit this by changing the `stack_id` route parameter on a request to `Api::CCMenuController#show`. No privileged account, session, secret, or social engineering is required beyond holding one such token.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the inherited, properly scoped `stacks` collection (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the client's `stack_id` restriction from `ApiClient#stack_id?` is enforced consistently with the rest of the API.

### Proof of Concept
1. Create (or use `CCMenuUrlController#fetch`) an `ApiClient` scoped to Stack A: `ApiClient.create!(creator: user, name: 'x', stack: stack_a, permissions: ['read:stack'])`.
2. Using that client's `authentication_token`, request `GET /api/:stack_b_id/ccmenu.xml?token=<token>` where `stack_b` is a different stack the client was never granted access to.
3. `authenticate_api_client` succeeds because the token is valid; `require_permission :read, :stack` passes because `read:stack` is present; `stack` resolves to Stack B via `Stack.from_param!`, unrelated to the client's own `stack_id`.
4. The response renders Stack B's CCMenu XML (build/deploy status), proving the stack-authorization binding was bypassed.

module Shipit
  module Api

          0
        end

          Time.now.utc
        end

          false
        end
      end

        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      end
