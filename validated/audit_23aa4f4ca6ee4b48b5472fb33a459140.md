### Title
Unbounded commission (fee) basis points settable via vote program `UpdateCommissionBps` instruction - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The vote program instruction handler `update_commission_bps` allows the vote account's authorized withdrawer to set `inflation_rewards_commission_bps` and `block_revenue_commission_bps` to any `u16` value (0–65,535) with no upper-bound validation at the point of storage, mirroring the "lack of bounds for fees" pattern from the external report: a privileged party can set a profit-sharing fee parameter to an unreasonably high (or overflowing) value that is only supposed to represent a percentage (0–10,000 bps = 0–100%), and this value directly determines how much of stakers' inflation/block-revenue rewards are diverted to the vote account owner.

### Finding Description
`update_commission_bps` in `programs/vote/src/vote_state/mod.rs` explicitly removes the previous timing/monotonicity restriction ("No commission update rule, per SIMD-0249 and SIMD-0291") and stores the caller-supplied `commission_bps: u16` directly into `inflation_rewards_commission_bps` or `block_revenue_commission_bps` without validating that it is within the meaningful `0..=10_000` (0%–100%) range: [1](#0-0) 

This is confirmed by the unit test `test_set_inflation_rewards_commission_bps`, which explicitly documents that values above 10,000 (i.e., above 100%) are accepted and persisted at the program/storage level, with the comment "Capping happens during reward calculation, not storage": [2](#0-1) 

This value is later consumed as `voter_commission_bps` in the reward redemption path (`redeem_rewards` / `redeem_stake_rewards` in `runtime/src/inflation_rewards/mod.rs`), which computes the split between staker and voter rewards for every delegator to that vote account: [3](#0-2) [4](#0-3) 

Because the bound enforcement is deferred entirely to downstream reward-calculation logic (which was not fully verifiable in the available index) rather than being enforced at the instruction/storage layer, this is structurally identical to the reported bug class: "no limit on the amount that can be set for these fees" at the point of update, relying on a separate, undocumented invariant elsewhere in the codebase to prevent the fee from exceeding 100%.

### Impact Explanation
If any code path that consumes `inflation_rewards_commission_bps` / `block_revenue_commission_bps` (present or future) fails to re-clamp the value to `0..=10_000`, delegators' stake rewards could be fully or over-confiscated (values >10,000 imply >100% "commission", i.e., stakers could receive zero or, in a flawed calculation, an underflowed/incorrect reward), representing misattributed rewards diverted away from unprivileged stakers. Even where a downstream clamp exists, storing an out-of-domain value with no validation at the authoritative update entrypoint is the exact anti-pattern flagged in the original report — a typo or malicious value is not caught at the source and can silently propagate through the system.

### Likelihood Explanation
The instruction is reachable by any vote account's authorized withdrawer with a single signed transaction, and no epoch-timing gate applies to `update_commission_bps` unlike the legacy `update_commission` (which enforces `is_commission_update_allowed`). This makes an accidental or malicious commission value trivial to set instantly, at any point in an epoch, affecting all current and future stake delegated to that vote account.

### Recommendation
Enforce `commission_bps <= 10_000` (and, for `BlockRevenue`, whatever protocol-defined maximum applies) directly inside `update_commission_bps` before calling `set_inflation_rewards_commission_bps` / `set_block_revenue_commission_bps`, returning `InstructionError::InvalidInstructionData` otherwise, instead of relying solely on capping during reward calculation.

### Proof of Concept
1. Vote account authorized withdrawer submits a `VoteInstruction` that invokes `update_commission_bps` with `commission_bps = 65_000` (650%) and `kind = CommissionKind::InflationRewards`. [5](#0-4) 
2. The value is accepted and persisted with no bounds check, as demonstrated by the test asserting acceptance of `bps` up to `u16::MAX`. [2](#0-1) 
3. On the next reward distribution, `voter_commission_bps` (now 65,000) is passed into `redeem_rewards`/`redeem_stake_rewards`, which is the sole authoritative point where this value determines the staker/voter reward split for every delegator to this vote account. [3](#0-2)

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
