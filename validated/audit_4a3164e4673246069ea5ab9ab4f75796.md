### Title
Cross-organization `membership` webhook forgery escalates arbitrary GitHub users into `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound `membership` webhook using the **signing organization** derived from the payload (`organization.login`), but `MembershipHandler#process` grants team membership by looking up the target `Team` **only by the global, non-org-scoped `team.id`** field. Because Shipit supports multiple independently configured GitHub App organizations, each with its own `webhook_secret` [1](#0-0) , an attacker who controls (as an ordinary admin of) their own separate GitHub organization registered with the same Shipit instance can forge a `membership` webhook signed with their own org's secret, but referencing the `github_id` of a `Team` that belongs to a different, victim organization and is part of `Shipit.github_teams`. This adds the attacker's own GitHub identity to that authorized team in Shipit's database, bypassing GitHub's real team-membership check entirely.

### Finding Description
`verify_signature` picks the GitHub App configuration (and thus the HMAC secret) to validate the request against using a value extracted from the payload itself: [3](#0-2) [4](#0-3) 

For a `membership` event, GitHub's real payload has no `repository` key, so `repository_owner` resolves to `organization.login` — the org that owns the webhook installation whose secret was used to sign the raw body. This is the only identity that `verify_signature` actually certifies: "this body was produced by (or on behalf of) organization X."

`MembershipHandler`, however, does not scope the team lookup to that verified organization: [5](#0-4) 

`find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id)`. GitHub team IDs are globally unique numeric identifiers, not scoped by the organization named in the payload. When the team already exists (the common case for a pre-configured `Shipit.github_teams` entry), the `organization:` assignment inside the block never runs — the found `Team` record is used as-is, regardless of which org's secret validated the request. There is no equality check asserting `team.organization == params.organization.login` (or any check that the `team.id` actually belongs to the authenticated organization).

`Shipit.github` explicitly supports multiple, independently secured organizations under one Shipit instance [1](#0-0) , and the authorization gate that decides whether any given GitHub user may use Shipit at all is: [6](#0-5) 

which checks membership against `Shipit.github_teams`, itself built from `Team` records [2](#0-1) .

**The broken binding, as an equality:**
`organization authenticated by verify_signature (payload.organization.login → webhook_secret)` ≠ `organization whose Team record is mutated by MembershipHandler (payload.team.id, unscoped lookup)`.

Before the attack: victim's `Team` (github_id = T) is in `Shipit.github_teams`; attacker's GitHub identity has no membership in it and is unauthorized (`authorized?` → false).
After the attack: the attacker crafts and signs a `membership` "added" payload with their own org's secret (`organization.login = "attacker-org"`, which they legitimately administer and for which they configured/know the `webhook_secret`), setting `team.id = T` and `member.login = <attacker's own GitHub login>`. `verify_signature` succeeds (signature matches attacker-org's secret). `MembershipHandler#process` finds the victim's existing `Team` (github_id T), creates/finds the attacker's `User` via `User.find_or_create_by_login!` [7](#0-6) , and calls `team.add_member(member)` [8](#0-7) . The attacker's `User` is now recorded as a member of the victim's authorized team in Shipit's database, and `authorized?` now returns true — without ever being added to the real GitHub team.

### Impact Explanation
This is an "escalation into `Shipit.github_teams` authorization" per the listed High-impact categories — an explicitly unprivileged external GitHub user is granted access to log into and use the Shipit instance (view stacks, potentially trigger deploys depending on `ApiClient`/UI-session-based authorization checks elsewhere) by forging a webhook payload signed with a webhook secret from an organization the attacker legitimately, but separately, administers.

### Likelihood Explanation
Requires the target Shipit deployment to be configured for multiple GitHub organizations (multi-org config schema in `lib/shipit.rb`) and requires the attacker to be able to administer at least one such organization registered on that instance (e.g., a public/self-serve Shipit deployment, or an org onboarding flow) so they know that org's `webhook_secret`, plus knowledge/guessability of the victim team's numeric GitHub team ID (discoverable via GitHub's public team APIs in many cases). This is plausible in any Shipit deployment that onboards multiple, mutually-untrusted GitHub organizations.

### Recommendation
Scope the `Team` lookup by both `github_id` and the authenticated `organization.login` (i.e., require `team.organization == params.organization.login`, or look up `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/ignore `membership` webhooks whose `team.organization` does not match the org that produced a valid signature.

### Proof of Concept
1. Configure Shipit with two organizations under `secrets.github`: `victim-org` (owns `Team` with `github_id: 999`, included in `Shipit.github_teams`) and `attacker-org` (admin-controlled by the attacker, who therefore knows its `webhook_secret`).
2. Attacker computes `sha1=HMAC(attacker-org secret, raw_body)` for:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "Victim Team", "slug": "victim-team", "url": "https://api.github.com/teams/999"},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker-github-login"}
}
```
3. POST this body to `/webhooks` with header `X-Github-Event: membership` and `X-Hub-Signature: sha1=<computed>`.
4. `WebhooksController#verify_signature` succeeds (`repository_owner` → `attacker-org`, valid secret). `MembershipHandler#find_or_create_team!` finds the existing victim `Team` (`github_id: 999`) and `team.add_member(User.find_or_create_by_login!("attacker-github-login"))` runs, per [5](#0-4) .
5. `User#authorized?` for `attacker-github-login` now returns `true` [6](#0-5) , granting Shipit access without any real GitHub team membership.
