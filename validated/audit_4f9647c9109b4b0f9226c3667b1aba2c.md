### Title
GitHub App installation token leaks to attacker-controlled submodule URLs on the same host via git's host-scoped credential cache - (File: main.go)

### Summary
`RefreshGitHubAppToken` stores the minted GitHub App installation token with `git.StoreCredentials(ctx, git.repo, "-", token)`, which git records into the `credential.helper=cache` store keyed only by protocol+host (not full path) since `credential.useHttpPath` is never set. Because git-sync supports submodule recursion, an attacker who controls the synced repository's content can add a `.gitmodules` entry pointing at any other repository on the same host (e.g. `github.com`), and when submodules are fetched, git's credential cache will hand over the cached installation token to that unrelated URL.

### Finding Description
`SetupDefaultGitConfigs` unconditionally sets `credential.helper = cache --timeout 3600` globally [1](#0-0) , without ever setting `credential.useHttpPath=true`. Git's `cache` credential helper, when `useHttpPath` is not enabled, indexes stored credentials solely by `protocol://host`, discarding the path component. `RefreshGitHubAppToken` then calls `git.StoreCredentials(ctx, git.repo, "-", tokenResponse.Token)` [2](#0-1) , which internally invokes `git credential approve`/`fill` against `git.repo` — this seeds the cache for `protocol+host` derived from `git.repo`, not the exact repo path.

Git-sync supports submodule recursion as a first-class, documented feature (confirmed by numerous submodule-related code paths in `main.go`). When submodules are enabled and a submodule fetch is performed for a `.gitmodules` URL under the same host as `git.repo`, git issues a `git credential fill` for that host during the HTTPS handshake. Because the cache is scoped by host only, it returns the previously stored GitHub App installation token — intended to authorize only the primary repository/installation — to the submodule URL, which the attacker fully controls via repo content (`.gitmodules`). No existing check in git-sync validates that submodule URLs are confined to the same repository/installation scope as `git.repo`; git itself performs no path-based confinement by default.

### Impact Explanation
This is a cross-repository secret disclosure: a short-lived but privileged GitHub App installation token — meant to be scoped to fetching only the primary tracked repository — is transmitted (via HTTPS `Authorization` header) to an attacker-chosen destination path/repo on the same host. This matches the "secret leakage" impact class: an unprivileged attacker who can only influence repository content (adding a submodule entry) can exfiltrate a live authentication token to an endpoint they control, then use that token (within its installation-wide permission scope) against other repositories the installation can access, defeating the intended repo confinement of GitHub App tokens.

### Likelihood Explanation
Preconditions are: (1) GitHub App authentication configured (a documented, supported, opt-in git-sync feature), (2) submodule recursion enabled (also a documented, supported flag), and (3) default git credential-cache scoping (host-level, which is git's actual default absent `credential.useHttpPath=true`, and git-sync never sets that config). All three conditions rely only on documented, supported settings — no operator misconfiguration or privileged access is required beyond normal use of advertised features. The attacker only needs write access to repository content, which is exactly the threat model in scope (attacker controls repo content/refs that git-sync fetches). This is fully repeatable on every sync cycle where submodules are fetched after the token is minted.

### Recommendation
- Set `credential.useHttpPath = true` alongside `credential.helper` configuration, and store/scope credentials per exact repository path (`git.repo` including full path) rather than relying on host-only matching.
- Alternatively/additionally, disable or restrict submodule URL resolution to the same repository/host+path as `git.repo`, or require explicit opt-in allow-listing of submodule hosts/paths when GitHub App auth is active.
- Consider scoping the installation token request itself (via GitHub App installation permissions) to the single repository instead of installation-wide, if the GitHub API/installation supports repository-scoped tokens, to reduce blast radius even if cache leakage occurs.

### Proof of Concept
Integration test sketch:
1. Stand up a local HTTPS test server acting as two "repos" under the same host (`github.com` equivalent via `/etc/hosts` or a test double), logging all `Authorization` headers received.
2. Configure git-sync with GitHub App auth flags pointed at `--repo=https://fakehost/org/primary.git`, mock the GitHub App token endpoint to return a known token `T`.
3. In `primary.git`, commit a `.gitmodules` file with `url = https://fakehost/otherorg/otherrepo.git` and enable `--recurse-submodules` (or git-sync's submodule flag).
4. Run git-sync's sync cycle (`RefreshGitHubAppToken` followed by the clone/submodule-update path).
5. Assert: the request log for `https://fakehost/otherorg/otherrepo.git` fetch contains `Authorization: Basic <base64(-:T)>` (or equivalent Bearer), proving token `T` — minted for `primary.git` — was sent to `otherrepo.git`.
