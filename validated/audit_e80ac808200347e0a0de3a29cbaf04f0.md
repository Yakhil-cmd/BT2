### Title
Cross-tenant CCMenu status disclosure via unscoped `stack` lookup bypassing token's `stack_id` binding - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the `stack` helper to call `Stack.from_param!(params[:stack_id])` directly, instead of using the scoped `stacks.from_param!` defined in `Api::BaseController`. This lets any valid `ApiClient` token — including a token minted for the attacker's own public stack — read the CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, `webUrl`) of an arbitrary, unrelated stack, including one backed by a private repository.

### Finding Description
The intended binding is: `current_api_client.stack_id == stack.id` for any stack rendered by `'shipit/ccmenu/project'`. In `Api::BaseController#stack` this binding is enforced via the `stacks` scope: [1](#0-0) 
`stacks` filters to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and only falls back to `Stack.all` for stack-agnostic/unscoped clients.

However, `Api::CCMenuController` defines its own private `stack` method that completely bypasses this scope: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` model rather than `stacks.from_param!`. `require_permission :read, :stack` only checks that the token has the `read:stack` permission string via `ApiClient#check_permissions!` — it never compares `current_api_client.stack_id` to the requested `stack.id`: [3](#0-2) 

So the equality `current_api_client.stack_id == stack.id` is never checked in `CCMenuController#show`; only "token has `read:stack` permission" and "stack_id param resolves to *some* stack" are checked. The attacker's own CCMenu token (minted via `CCMenuUrlController#fetch` for their own public stack, with permission `read:stack` and a bound `stack_id`) can be reused with a different `stack_id` param pointing at any other stack, public or private: [4](#0-3) 

`show` then renders the private stack's live CI data: [5](#0-4) [6](#0-5) 

None of the checked guards (`verify_signature`, `force_github_authentication`, `User#authorized?`, model validators) apply here since this is a token-authenticated API endpoint; the only relevant guard, the `stacks` scope, is simply not used by this controller.

### Impact Explanation
Any GitHub user who can obtain a legitimate CCMenu token for a stack they can see (e.g. their own public fork's stack, or any stack whose Shipit URL/token they can access) can enumerate `stack_id` values and read `lastBuildStatus`, `lastBuildLabel`/deploy id, `activity` (building/sleeping), and `webUrl` for any stack in the Shipit instance, including stacks tied to private/internal repositories the attacker has zero GitHub access to. This is a cross-tenant confidentiality breach — unauthenticated (relative to the target stack) read of stack build/deploy state — matching the High severity category "unauthenticated read of stack state." It is fully repeatable against every stack ID in the system with a single valid token.

### Likelihood Explanation
Preconditions match the question: attacker needs any CCMenu token minted for a stack they legitimately control/view (trivially obtainable for their own public repo's stack via the normal "CCMenu URL" feature). No secrets, no GitHub App key, no webhook signature bypass, and no privileged role are required. The only additional information needed is the target's `stack_id`/`to_param`, which is low-entropy (often the repo `owner/name/branch` slug) and often guessable or discoverable. This is trivially repeatable — one HTTP GET per target stack.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and use the scoped `stacks.from_param!` from `Api::BaseController` (or explicitly assert `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering), so token-bound clients can only read the stack their token was minted for.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb`, no live GitHub needed):
```ruby
setup do
  @public_stack  = shipit_stacks(:shipit)          # attacker's own stack
  @private_stack = shipit_stacks(:cyclimse)        # unrelated/private stack
  @attacker_token = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'CCMenu Client',
    permissions: %w[read:stack],
    stack: @public_stack
  ).authentication_token
end

test "token bound to public stack cannot read a different stack's CCMenu XML" do
  get :show, params: { stack_id: @private_stack.to_param, token: @attacker_token }, format: :xml

  # Binding under test: current_api_client.stack_id == stack.id
  assert_equal @public_stack.id, ApiClient.authenticate(@attacker_token).stack_id
  refute_equal @public_stack.id, @private_stack.id

  # Vulnerable behavior: request still succeeds and leaks the private stack's data
  assert_response :ok
  assert_includes response.body, @private_stack.to_param   # information disclosure
end
```
Before the fix, this test passes with `response.body` containing the private stack's `name`/`webUrl`, proving the divergence. After scoping `stack` through `stacks.from_param!`, the request should raise `ActiveRecord::RecordNotFound` (404) instead.
