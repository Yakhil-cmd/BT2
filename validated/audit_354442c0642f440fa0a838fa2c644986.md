This is highly significant. The `StatusHandler` confirms the confused-deputy pattern is even worse than push events: `StatusHandler#process` matches on `Commit.where(sha: params.sha)` — a bare SHA lookup with **no repository/stack binding check at all** — meaning a webhook authenticated (signature-verified) as belonging to Org B can set CI status on any commit in the entire Shipit instance that happens to share that SHA, across any org/stack, and this directly drives `commit.create_status_from_github!` → `enable_ci_on_stack`, `schedule_continuous_delivery`, and `ProcessMergeRequestsJob` (merge-queue merges). This is a stronger and clearer confirmation of the binding break than the push case.

### Title
Webhook signature authenticates one GitHub organization while handlers act on an attacker-controlled repository/commit reference from the same unverified-binding payload, enabling cross-organization status/CI forgery and forced syncs - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification based on `repository_owner`, a value read from the *same* untrusted JSON payload it is about to verify [1](#0-0) . Once the signature check passes, `Shipit::Webhooks::Handlers::Handler#stacks` and its subclasses (e.g. `PushHandler`, `StatusHandler`) act on `repository.full_name` or a bare commit `sha` taken from that same payload, with no cross-check that these fields belong to the organization whose secret actually authenticated the request [2](#0-1) [3](#0-2) .

### Finding Description
In a multi-organization Shipit deployment (a supported, documented configuration — see `github:` maps keyed by organization in `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`), each organization has its own GitHub App config and optional `webhook_secret` [4](#0-3) .

`WebhooksController#verify_signature` picks the `github_app` to verify against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — fields fully controlled by whoever crafts the payload [1](#0-0) [5](#0-4) . `GithubApp#verify_webhook_signature` computes an HMAC over the full raw body using that organization's secret [6](#0-5) , and — critically — `return true unless webhook_secret`, meaning any organization configured without a webhook secret (explicitly documented as optional) causes signature verification to be skipped entirely for any payload claiming that `repository.owner.login`.

Once verification passes (either because the secret genuinely matches for Org B, or trivially because Org B has no secret configured), the event is dispatched to handlers that determine the **target** of the action from a *different* field:
- `Handler#repository_name` uses `payload.dig('repository', 'full_name')` to resolve the `Repository`/`Stack` to act on [2](#0-1) .
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack, using attacker-supplied `full_name` and `expected_head_sha` [7](#0-6) , which enqueues `GithubSyncJob` [8](#0-7) .
- `StatusHandler#process` is worse: it does not even use `repository.full_name` — it matches on a bare `Commit.where(sha: params.sha)` across the entire instance and calls `create_status_from_github!` on every match [3](#0-2) , which triggers `enable_ci_on_stack` and `schedule_continuous_delivery` [9](#0-8)  and, via `Commit#create_status_from_github!`/`add_status`, can enqueue `ProcessMergeRequestsJob` for the merge queue.

The binding that should hold is: `organization authenticated by verify_signature == organization/repository actually acted upon by the handler`. Nothing in the code enforces this equality — the payload supplies both values independently and only one of them is covered meaningfully by the signature-selection logic while the other drives all side effects.

### Impact Explanation
An attacker who controls (or can obtain a webhook secret for, or exploits a no-secret-configured) organization "Org B" registered on the same Shipit instance can submit a webhook whose `repository.owner.login`/`organization.login` says "Org B" (satisfying signature selection) while `repository.full_name` or `sha` targets stacks/commits belonging to an entirely unrelated "Org A". This lets the attacker:
- Force `GithubSyncJob` runs and `expected_head_sha` values on Org A's stacks (`PushHandler`), interfering with sync state and inaccessible/accessible flags.
- Forge arbitrary CI/status states (`pending`/`success`/`failure`) on any commit SHA in the whole Shipit instance regardless of owning org (`StatusHandler`), which can flip `enable_ci_on_stack`, trigger `schedule_continuous_delivery`, and feed the merge-queue (`ProcessMergeRequestsJob`) — potentially causing an unauthorized/accelerated deploy or merge decision on a stack the attacker has no legitimate relationship with.

This satisfies the "cross-repository writes" / "unauthorized deploy or merge" high/critical impact bar, since the deputy (Shipit) is tricked into acting on a repository/stack outside the scope of the credential that was actually verified.

### Likelihood Explanation
Requires the target Shipit instance to host more than one GitHub organization (a documented, supported configuration) and requires the attacker to either control a second org's GitHub App/webhook secret, or for that org to have no webhook secret configured (also documented as optional) — a realistic setup for smaller/less carefully configured multi-tenant deployments. No Shipit session, `ApiClient` token, or GitHub write access to the *target* org is required, satisfying the "unprivileged attacker" bar for that org.

### Recommendation
After (or as part of) signature verification, re-derive the organization that must own the acted-upon repository/commit from the verified organization context, and reject/ignore events where `repository.full_name`'s owner segment (or the resolved `Repository#owner`) does not match the organization whose secret verified the signature. For `StatusHandler`, additionally scope the `Commit` lookup by `stack.repository` matching the verified organization rather than a bare, instance-wide `sha` match.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` (private, secret configured) and `OrgB` (attacker-controlled GitHub App, secret known to attacker or unset).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "repository": {"owner": {"login": "OrgB"}, "full_name": "OrgB/whatever"},
  "sha": "<sha-of-a-commit-belonging-to-OrgA-stack>",
  "state": "success",
  "context": "ci/forged"
}
```
signed with `OrgB`'s webhook secret (or unsigned if `OrgB` has none configured).
3. `verify_signature` resolves `Shipit.github(organization: "OrgB")` and successfully verifies (matches its own secret, or trivially passes if none set) [1](#0-0) .
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the OrgA commit, and calls `create_status_from_github!`, marking it `success` and potentially triggering continuous delivery/merge logic on OrgA's stack [3](#0-2)  — despite the request never having been authenticated for OrgA.
