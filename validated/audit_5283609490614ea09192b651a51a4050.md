### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets a status webhook for one repository mutate a commit belonging to a different repository's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits to attach a GitHub status to purely `Commit.where(sha: params.sha)`, with no repository/organization scoping, unlike every other handler (e.g. `CheckSuiteHandler`) which uses the `Handler#stacks` helper that filters via `Repository.from_github_repo_name(repository_name)`. Any commit row anywhere in the Shipit install that shares the reported SHA (e.g. because two onboarded repos/forks share commit ancestry) receives the attacker-supplied status, including on a stack with `merge_queue_enabled: true`, where a status write can change `Commit#state`/`StatusChecker` results and trigger `ProcessMergeRequestsJob`/`MergeRequest#merge!`.

### Finding Description
The broken binding: the code should enforce `commit.stack.repository.full_name == payload['repository']['full_name']` for every `Commit` mutated by a `status` webhook, i.e. a webhook authenticated for repository R must only write statuses onto commits belonging to stacks of R. Instead: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with zero reference to `payload['repository']`. Compare to the base `Handler`, which explicitly provides a repository-scoped `stacks` accessor used by sibling handlers such as `CheckSuiteHandler`: [2](#0-1) [3](#0-2) 

`StatusHandler` never calls `stacks`, so it queries `Commit` globally by bare `sha` across every stack/repository tracked by the Shipit instance.

Signature verification in `WebhooksController` only proves the request came from GitHub for the organization named in `payload['repository']['owner']['login']`; it does not, and cannot, prove that the `sha` in the body actually belongs to that repository: [4](#0-3) 

So the guard chain (`check_if_ping`, `drop_unhandled_event`, `verify_signature`) only binds the webhook to *an organization's secret*, never to the specific `sha`/commit graph. Once verified, `StatusHandler.call(params)` runs unconstrained by that organization.

Exploit flow: an attacker who legitimately controls a repository that is itself onboarded to the same Shipit instance (their own fork/org, satisfying "unprivileged" per the rules — pushing to a fork/owning a repo is allowed) can, through ordinary GitHub actions on their own repo (e.g. via GitHub's status API on a commit they control, or CI configured by them), cause GitHub to deliver a legitimately-signed `status` webhook whose `sha` field equals a SHA that also exists in a victim stack's `commits` table (this happens routinely for forks/shared-ancestry repos, since pre-fork commits are identical SHAs in both the fork and upstream, and both may be onboarded as separate Shipit stacks). Because `StatusHandler` does not check `repository.full_name`, that single, honestly-signed webhook for the attacker's own repo also creates a `Shipit::Status` row (`context: ci/smoke`, `state: failure`) on the identically-SHA'd commit in the victim's stack via `Commit#create_status_from_github!` → `add_status`.

On a stack with `merge_queue_enabled: true`, `Commit#add_status` can enqueue `ProcessMergeRequestsJob` on state transitions, and `Stack#allows_merges?` / `MergeRequest#reject_unless_mergeable!`/`merge!` depend on the aggregated status state of stack commits: [5](#0-4) [6](#0-5) [7](#0-6) 

Injecting a `failure` status for a required context on the victim's commit can flip `Stack#allows_merges?`/`MergeRequest#reject_unless_mergeable!` to block a legitimate merge (denial of a specific merge), and, symmetrically, injecting a fabricated `success` for a required/missing context can make `all_status_checks_passed?` return true and let `merge_request.merge!` fire prematurely — i.e. a payload authenticated for repository A mutates repository B's commit/stack/merge state, matching the Critical impact category "a payload for one repository mutating another's stack, commit, task or team" / "unauthorized deploy, rollback or merge".

None of the existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler`) check the target commit's owning repository; the schema only validates `sha`/`state`/`context` types, not repository identity.

### Impact Explanation
An attacker who owns/controls any repository onboarded to the same Shipit instance can write arbitrary `Shipit::Status` rows (any `context`, any `state`, arbitrary `description`/`target_url`) onto any other stack's commit that happens to share a SHA with one of their own commits — most realistically forks or repositories with shared git history. This can: block deploys/merges on the victim stack (spurious `failure` for a required context), or unblock/force a merge in a `merge_queue_enabled` stack that would otherwise be rejected (spurious `success`), leading to unauthorized merges. The blast radius spans every stack in the multi-tenant Shipit instance whose commit history can intersect with an attacker-controlled repository's history, and the write is repeatable per SHA/context/state combination.

### Likelihood Explanation
Preconditions: the attacker's repository must be onboarded to Shipit (webhooks configured, which is routine for any repo added to the platform) and must share at least one commit SHA with the victim stack's commit table (common for forks, mirrors, or repos with a shared upstream). No Shipit session, API token, or webhook secret needs to be stolen — the attacker uses their own legitimately signed webhook traffic, so this fully satisfies the "unprivileged" attacker model. The attack is cheap (a single GitHub status update) and repeatable against any repository sharing history with the attacker's own.

### Recommendation
Scope `StatusHandler#process` to the reporting repository, matching the pattern used elsewhere in the codebase (`Handler#stacks`): resolve `stacks` from `payload['repository']['full_name']` and restrict the `Commit` lookup to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or iterate `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`) before calling `create_status_from_github!`, so a status webhook can never write onto a commit belonging to a stack outside the authenticated repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process does not create a status on a commit belonging to a different repository's stack" do
  attacker_stack = shipit_stacks(:shipit)              # repo A, attacker-controlled repo
  victim_stack   = shipit_stacks(:cyclimse)             # repo B, merge_queue_enabled: true
  victim_stack.update!(merge_queue_enabled: true)

  shared_sha = "a" * 40
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "shared", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, message: "shared", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'ci/smoke',
    'repository' => { 'full_name' => attacker_stack.repository.full_name, 'owner' => { 'login' => attacker_stack.repository.owner } },
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
  # currently FAILS: victim_commit.statuses.count increases by 1 even though the webhook
  # only authenticated for attacker_stack.repository, proving cross-repository mutation.
end
```
Both sides of the invariant "a `ci/smoke` status affects only the repository that authenticated it" are demonstrated unequal: `payload['repository']['full_name']` (attacker's repo) ≠ `victim_commit.stack.repository.full_name` (victim's repo), yet the status is written to `victim_commit` regardless.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end

    def reject_unless_mergeable!
      return reject!('merge_conflict') if merge_conflict?
      return reject!('ci_missing') if any_status_checks_missing?
      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
