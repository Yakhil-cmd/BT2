### Title
Cross-repository commit-status mutation via unscoped `Commit.where(sha:)` lookup — `branches[].name` provides no authorization binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits solely by `Commit.where(sha: params.sha)`, iterating over every `Commit` record in the database that shares that SHA regardless of which stack/repository it belongs to [1](#0-0) . The `branches` array is declared in the `ExplicitParameters` schema and accepted from the payload, but it is never read anywhere in `process`, so naming the victim's branch (e.g. `main`) in that array creates no additional scoping and cannot bind the status write to the attacker's own repository [2](#0-1) .

### Finding Description
Claimed binding: `params.branches[].name == "main"` (victim's branch) `==` an authorization check that the mutated commit/stack belongs to the repository that signed the webhook. Tracing the code shows no such check exists.

`verify_signature` in `WebhooksController` only proves the payload was signed by *some* organization's registered webhook secret — specifically the organization derived from `params.dig('repository','owner','login')` [3](#0-2) [4](#0-3) . It does not tie the `sha` or `branches` values inside the JSON body to that same organization/repository — GitHub signs the whole payload, but nothing downstream cross-checks `repository.full_name` against the commit being mutated.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This query is global across all stacks/repositories in the Shipit instance [5](#0-4) . Because git commit SHAs are content-addressed and identical across forks/clones of the same history, an attacker who forks or clones a public victim repository will have local commits whose SHAs are byte-identical to commits already recorded in Shipit for the victim's stack (created via the victim's legitimate push/pull_request webhooks, see `Commit.from_github`) [6](#0-5) .

Attack flow:
1. Attacker forks/clones the victim's public repo, obtaining commits with SHAs already present in Shipit as `Commit` rows belonging to the victim's `Stack`.
2. Attacker configures the GitHub App/webhook on their *own* repository (using their own account/org, which they legitimately control and for which they can obtain a valid signature).
3. Attacker triggers (or directly POSTs, since only the signature over the raw body is checked, not field consistency) a `status` event referencing that shared `sha`, optionally including a `branches` array with `name: "main"` to make the payload superficially resemble the victim's branch.
4. `verify_signature` passes because the signature is valid for the attacker's own configured organization — the check never inspects `sha` or `branches` for repository correspondence.
5. `StatusHandler#process` finds the victim's existing `Commit` row by bare `sha` match and calls `commit.create_status_from_github!(params)`, writing a forged status (state/description/target_url/context arbitrary) onto the victim's commit/stack, which can flip `deployable?`/CI gating and trigger `schedule_continuous_delivery` [7](#0-6) [8](#0-7) .

The `branches` field is inert: including or omitting it, or setting it to any value, does not change which `Commit` rows are matched or mutated, since `process` never references `params.branches`.

### Impact Explanation
An attacker can write arbitrary CI/status state onto a victim's commit/stack that they do not own or control, potentially unblocking `deployable?` checks and triggering continuous deployment (`schedule_continuous_delivery`) for a repository the attacker never authenticated against. This is a cross-repository write matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any Shipit-tracked repository/stack whose commit history overlaps (via fork/shared history) with a repository the attacker controls and has registered with Shipit's webhook signing.

### Likelihood Explanation
Preconditions: the attacker needs their own GitHub repository/org registered with a Shipit-recognized webhook secret (achievable if Shipit is configured to accept webhooks from any org that installs the app, or if the attacker's own org is already onboarded) and a commit SHA that also exists as a `Commit` row for the victim's stack (trivially obtained by forking a public repo whose commits Shipit has already ingested). No Shipit session, API token, or GitHub App private key is required. This is feasible at low cost for any public target repo tracked by the same Shipit instance.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and equivalent handlers such as `CheckRunHandler`) by the repository identified in the webhook payload, e.g. `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_id: repository.id })`, resolving `repository` from `params.repository.full_name`/`owner.login` and matching it against `Stack#repository`, rather than trusting a bare, repository-agnostic `sha` match.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "status webhook mutates commit regardless of branches array content" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = shipit_commits(:first)
  # victim_commit.sha already exists in DB, tied to victim_stack

  payload_no_branches = { sha: victim_commit.sha, state: "success", context: "attacker-ctx" }
  payload_with_forged_branch = payload_no_branches.merge(branches: [{ name: "main" }])

  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload_no_branches)
  status1 = victim_commit.reload.statuses.last.state

  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload_with_forged_branch)
  status2 = victim_commit.reload.statuses.last.state

  assert_equal status1, status2
  # both writes succeed identically -> branches field provides no binding,
  # and the commit belonging to a different "repository" than the payload's
  # own org (simulated via distinct repository_owner) is still mutated.
end
```
