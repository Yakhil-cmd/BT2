### Title
Untrusted `shipit.yml` from a PR author's own branch can exfiltrate host process secrets via `$VAR` interpolation, bypassing the environment-variable whitelist - ([File: lib/shipit/environment_variables.rb])

### Summary
`EnvironmentVariables#interpolate` and `Command#interpolate_environment_variables` substitute `$VAR` references found in `shipit.yml` step command lines. When a variable is not present in the task/stack's own env hash, the code silently falls back to the real process environment (`ENV[variable]`) of the Shipit host, rather than refusing or restricting to the whitelist used everywhere else (`EnvironmentVariables#permit`). Review stacks are created automatically from an unprivileged PR author's own branch (`ReviewStackAdapter#stack_attributes` uses `branch: params.pull_request.head.ref`), and `shipit.yml` for that branch is read and its steps executed by `CacheDeploySpecJob`/`Commands` without any additional approval. This breaks the same class of trust binding as the reversed funding-rate bug: the binding "environment variable names permitted for injection" vs. "environment variable names actually resolved and spawned" is not equal — the interpolation step widens the permitted set to the entire host process environment.

### Finding Description
- The whitelist model in the codebase is: any environment variable a user/stack wants to inject into a step must be declared in `shipit.yml`'s `variables` and is filtered through `EnvironmentVariables#permit`: [1](#0-0) 
- However, when *interpolating* `$VAR` references embedded directly in step command strings (which are also fully attacker-controlled via `shipit.yml`), a completely different, unrestricted code path is used: [2](#0-1) 
The `@env.fetch(variable) { ENV[variable] }` fallback means any `$VAR` that isn't already in the (whitelisted) task/stack env hash is resolved against the actual OS-level environment of the Shipit worker/deploy process — completely bypassing the `permit`/`NotPermitted` boundary that the rest of the codebase treats as the authorization gate for env exposure.
- This is invoked for every argument of every shell command run for a stack, including deploy, rollback, fetch, and custom task steps: [3](#0-2) [4](#0-3) 
- `shipit.yml` (and thus the step command strings that get interpolated) is read from the stack's configured `branch` by `DeploySpec::FileSystem`, which is populated by `CacheDeploySpecJob`/`StackCommands#build_cacheable_deploy_spec` by checking out that branch: [5](#0-4) 
- For **review stacks**, the `branch` is set directly to the PR author's own head ref, with no approval step, whenever the repository is configured with `provisioning_behavior_allow_all` (or the PR carries the provisioning label): [6](#0-5) [7](#0-6) 

So the equality that should hold — "environment variable names an attacker's `shipit.yml` may cause to be spawned" == "environment variable names that were explicitly permitted for that task/stack" — is broken. An unprivileged contributor who can open a pull request (which is all that's required for `provisioning_behavior_allow_all` repositories) can supply a `shipit.yml` step like `echo $RAILS_MASTER_KEY` or `echo $GITHUB_APP_PRIVATE_KEY` (or any secret name they can guess or enumerate) and Shipit will run it on the deploy host as part of automatic review-stack provisioning, printing the value of that host-side environment variable into the task's output stream.

### Impact Explanation
This matches the "Critical: exfiltration of `GITHUB_TOKEN` … or credential exfiltration" bucket. Many production Rails/Shipit deployments pass secrets (Rails master key, database URL credentials, GitHub App private key/webhook secret if provided via env rather than credentials.yml, cloud provider tokens used by the deploy host, etc.) through the process environment of the worker that runs `Command`/`PTY.spawn`. Because `BASE_ENV` (in `lib/shipit/command.rb`) is derived from `Bundler.unbundled_env`/`Bundler.clean_env` and only strips bundler-specific keys, essentially the entire real host environment is available to `ENV[variable]` and thus to `$VAR` interpolation in step strings. Anyone who can get `shipit.yml` steps to run — including an unprivileged, external PR author on an `allow_all` review-stack repository — can read out that data via the task output stream, which is visible to any Shipit user with read access to the stack (or in some configurations without authentication if hooks/streams are exposed externally).

### Likelihood Explanation
Requires only that the target repository has review stacks enabled with `provisioning_behavior_allow_all` (a documented, supported configuration for automatic per-PR review environments), a common setup for open/semi-open review workflows. No repository write access, API token, or Shipit session is required — merely the ability to open a pull request with a modified `shipit.yml`, which review-stack repositories are explicitly designed to accept from external branches.

### Recommendation
Make `EnvironmentVariables#interpolate` consistent with `EnvironmentVariables#permit`: only allow interpolation of variables that are part of the explicitly whitelisted/declared variable set (or the fixed, hard-coded stack/task env keys), and refuse (or interpolate as empty/error) any `$VAR` reference that is not part of that permitted set instead of silently falling back to the real process `ENV`.

### Proof of Concept
1. Configure a repository with `provisioning_behavior: allow_all` and review stacks enabled (`app/models/shipit/repository.rb`, `review_stacks_enabled`).
2. As an unprivileged external contributor, open a pull request whose branch contains a `shipit.yml` with, e.g.:
   ```yaml
   deploy:
     override:
       - "echo $RAILS_MASTER_KEY"
   ```
3. The `pull_request` `opened` webhook fires `OpenedHandler#process` → `ReviewStackAdapter#find_or_create!` → `create!`, which sets `branch: params.pull_request.head.ref` (the attacker's branch) with no approval gate (`app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:87-94`).
4. `Shipit::ReviewStackProvisioningQueue` triggers provisioning/deploy, which runs `CacheDeploySpecJob`/`Commands`, checking out the attacker's branch and its `shipit.yml`, then executing the `deploy.override` step through `Command#interpolate_environment_variables` → `EnvironmentVariables#interpolate` (`lib/shipit/command.rb:51-55`, `lib/shipit/environment_variables.rb:20-27`).
5. Since `RAILS_MASTER_KEY` is not part of the stack/task's permitted `@env` hash, it is resolved via `ENV['RAILS_MASTER_KEY']` from the real host process, and its value is printed into the task's log/output stream, which is then visible to anyone with read access to the stack's task output.

Note: I could not fully confirm within the indexed code which specific host secrets are passed as process-level `ENV` variables to the Shipit application/worker in a typical production deployment (this depends on deployment configuration, e.g., whether `RAILS_MASTER_KEY`/`GITHUB_TOKEN`/private keys are supplied via `ENV` vs. `credentials.yml`/`Shipit.github` YAML config); this affects the concrete severity of what can be exfiltrated but not the existence of the trust-binding break itself.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
