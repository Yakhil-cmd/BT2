### Title
Permissionless, front-runnable pool creation allows an attacker to dictate the initial price of a `PoolState` before the intended creator - (File: `programs/cp-swap/src/instructions/initialize.rs`)

### Summary
`initialize` (and the equivalent `initialize_with_permission`) creates a `PoolState` at a deterministic PDA derived solely from public data (`amm_config`, `token_0_mint`, `token_1_mint`), and lets the caller (`creator`) freely choose `init_amount_0`/`init_amount_1`, which fix the pool's initial price ratio. Any unprivileged account can call this instruction for any mint pair and any existing `AmmConfig`.

### Finding Description
The `pool_state` PDA seeds are fully public and predictable: `[POOL_SEED, amm_config, token_0_mint, token_1_mint]` [1](#0-0) , and `create_pool` allocates the account only if it does not already exist, otherwise the call fails [2](#0-1) . The `creator` (any `Signer`) freely supplies `init_amount_0`/`init_amount_1`, which are transferred straight into the vaults and used to compute the pool's initial `liquidity = sqrt(x*y)` and effectively its starting price, with no check that the ratio matches any external/expected price beyond `CurveCalculator::validate_supply` (a minimal-liquidity/non-zero check, not a price constraint) [3](#0-2) .

Because the same `amm_config` + mint pair produces the same PDA for anyone, this is directly analogous to the reported Ajna `ERC20PoolFactory`/`ERC721PoolFactory` issue: a legitimate pool creator's `initialize` transaction is visible in the mempool (Solana leader mempool / private RPC), and an attacker can construct and land a competing `initialize` instruction with the identical `amm_config`/mint accounts but attacker-chosen `init_amount_0`/`init_amount_1`. The attacker's transaction succeeds first, permanently claiming the deterministic `pool_state` PDA and setting the initial price ratio; the legitimate creator's transaction then reverts because `create_pool` rejects an already-initialized account (`pool_account_info.owner != &system_program::ID`).

### Impact Explanation
The attacker can force the pool's initial exchange rate to any ratio they choose (with only small capital, since no minimum reserve-ratio or oracle check exists), then immediately trade against the mispriced pool or wait for arbitrageurs/depositors to fund it at the skewed rate, extracting value from the intended creator/first LPs. Additionally, the legitimate creator's transaction reverts (loss of transaction fee / griefing), and once the attacker owns the pool at a given `amm_config`+mint-pair combination, no other party can ever create that exact pool identity again (permanent squatting of the deterministic PDA for that config/mint pair), since a new pool would require the intended party to use a different `amm_config` (which requires a governance-created config) or an entirely different token account instance.

### Likelihood Explanation
This requires only observing a pending `initialize` transaction (public mempool data — mint addresses and `amm_config` are unencrypted, deterministic instruction fields) and submitting a competing transaction with higher priority fee, which is a standard, low-cost front-running technique on Solana. No privileged signer, special build flag, or off-chain trust assumption is needed — any account holding the required token balances can execute `initialize`.

### Recommendation
Bind the initial deposit ratio to a value the intended creator commits to unlinkably (e.g., a commit-reveal scheme, or requiring the creator's signature over the exact `init_amount_0`/`init_amount_1`/pool identity combination validated on-chain), or allow a creator-specified salt/nonce in the PDA derivation combined with an access-list/pre-registration step so PDA squatting by third parties is not possible, or add a minimum/maximum acceptable price-ratio bound (oracle-anchored) enforced in `initialize`/`initialize_with_permission` before minting LP tokens.

### Proof of Concept
1. Legitimate user `A` builds and signs an `initialize` instruction for `token_0_mint = X`, `token_1_mint = Y`, `amm_config = C`, with `init_amount_0 = 1000`, `init_amount_1 = 1000` (intending a 1:1 price), and broadcasts it.
2. Attacker `B` observes the pending transaction, computes the same deterministic `pool_state` PDA `find_program_address([POOL_SEED, C, X, Y])` [4](#0-3) , and submits their own `initialize` instruction for the same `(C, X, Y)` triple but with `init_amount_0 = 1`, `init_amount_1 = 1_000_000` (an extreme skewed ratio), paying a higher priority fee so it lands first.
3. `B`'s transaction succeeds, creating the pool at the skewed price and minting LP tokens to `B` [5](#0-4) .
4. `A`'s transaction then fails in `create_pool` because the `pool_state` account is no longer owned by `system_program::ID` [6](#0-5) , wasting `A`'s fee and forcing `A` to either abandon the pair or trade into the attacker-controlled mispriced pool.
