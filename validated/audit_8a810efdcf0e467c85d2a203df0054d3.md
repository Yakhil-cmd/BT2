### Title
Cross-tenant upstream redirect in skill install silently omits host in provenance warning, enabling token routing to attacker-chosen host - ([File: pkg/cmd/skills/install/install.go])

### Summary
`checkUpstreamProvenance` detects a mismatch between the current skill repo and the `github-repo` frontmatter metadata by comparing full URLs (which include host) via `source.BuildRepoURL`/`source.ParseRepoURL`, but the warning/prompt shown to the user only displays `ghrepo.FullName(upstreamRepo)` — an "owner/repo" string with no host component — before redirecting `opts.repo` (and subsequent API calls) to the upstream repo. This allows an attacker who controls a re-published skill to point `github-repo` at a same-looking `owner/repo` on a different but still "supported" host (e.g. a `*.ghe.com` tenant distinct from the one the victim is authenticated against), causing gh to silently issue authenticated requests to that different tenant without any host-mismatch indication in the UI.

### Finding Description
`checkUpstreamProvenance` fetches `SKILL.md`, parses `github-repo` frontmatter into `existingRepo` [1](#0-0) , then compares it against `source.BuildRepoURL(hostname, opts.repo.RepoOwner(), opts.repo.RepoName())`, which is a full canonical URL including hostname [2](#0-1) . If they differ, `source.ParseRepoURL(existingRepo)` is called, which delegates to `ghrepo.FromFullName`, capable of parsing a full URL (including an arbitrary host) into a `ghrepo.Interface` with that host [3](#0-2) . The resulting `upstreamRepo` can therefore carry a host that differs from the current session's host/tenant.

The user-facing warning only prints `ghrepo.FullName(upstreamRepo)`, which is defined as `fmt.Sprintf("%s/%s", r.RepoOwner(), r.RepoName())` — it never includes `RepoHost()` [4](#0-3) . So the message `"This skill was originally published in %s"` and the interactive choice label `"%s (upstream)"` both show only `owner/repo`, with no indication that the redirect target lives on a completely different host/tenant [5](#0-4) . When `opts.Upstream` is set (`--upstream` flag) the redirect happens automatically with no additional confirmation of the host change [6](#0-5) .

`source.ValidateSupportedHost` only checks that the host is `github.com` or `ghauth.IsTenancy(host)`-classified (any GHEC data-residency tenant) — it does not check the parsed host against the hostname/tenant the user is currently operating against [7](#0-6) . There is no code in the reviewed path that compares `upstreamRepo.RepoHost()` to the original `hostname` parameter before using it to redirect `opts.repo`.

### Impact Explanation
This falls under "wrong-host or wrong-account request routing." An unprivileged attacker who publishes/re-publishes a skill can set `github-repo` frontmatter to `owner/repo` on a different `*.ghe.com` tenant they control (which still passes `ValidateSupportedHost`) while keeping the displayed `owner/repo` label identical or similar to the legitimate upstream, since the warning text never surfaces the host. If the victim runs with `--upstream` or picks the "upstream" choice interactively, install continues against the attacker's tenant using the victim's OAuth credentials for that operation, since subsequent API calls are keyed on the redirected repo/host.

### Likelihood Explanation
Requires the victim to run `gh skill install` (interactively accepting the upstream prompt, or with `--upstream`) against a skill published by the attacker. This is a plausible, low-effort attack since publishing skills and crafting `SKILL.md` frontmatter is fully within an unprivileged attacker's control, and the UI gives the victim no way to notice the host is different because the display omits host entirely.

### Recommendation
Include the resolved host/tenant in both the detection warning and the interactive choice labels (e.g., render `ghrepo.GenerateRepoURL(upstreamRepo, "")` instead of `ghrepo.FullName(upstreamRepo)`), and explicitly compare `upstreamRepo.RepoHost()` against the current session hostname — require explicit, unambiguous user confirmation (not just accepting a generic "(upstream)" label) whenever the redirect target's host differs from the host currently being used.

### Proof of Concept
Add a test in `pkg/cmd/skills/install/install_test.go` mirroring `TestInstallRun_UpstreamDetection`'s "non-interactive with --upstream redirects to upstream" case, but set the republished `SKILL.md`'s `github-repo` frontmatter to `https://attacker-tenant.ghe.com/monalisa/original-skills` while `opts.repo` is on `github.com`. Assert that:
1. `client.REST` calls after redirect are stubbed only for `attacker-tenant.ghe.com` and the test fails/aborts if `github.com` credentials/tokens are used against that host without an explicit host-mismatch message, and
2. `wantStderr` should contain an explicit mention of the differing host (e.g. `"attacker-tenant.ghe.com"`) — current code will fail this assertion because `wantStderr` only ever contains `"Redirecting install to monalisa/original-skills"` with no host shown [8](#0-7) .

func ValidateSupportedHost(host string) error {
	host = normalizeHost(host)
	if host == "" {
		return fmt.Errorf("could not determine repository host")
	}
	if host == SupportedHost || ghauth.IsTenancy(host) {
		return nil
	}
	if ghauth.IsEnterprise(host) {
		return fmt.Errorf("GitHub Skills does not currently support GitHub Enterprise Server; got %s", host)
	}
	return fmt.Errorf("unsupported host for GitHub Skills: %s", host)
}

// FromFullName extracts the GitHub repository information from the following
// formats: "OWNER/REPO", "HOST/OWNER/REPO", and a full URL.
func FromFullName(nwo string) (Interface, error) {
	return FromFullNameWithHost(nwo, defaultHost())
}

// FromFullNameWithHost is like FromFullName that defaults to a specific host for values that don't
// explicitly include a hostname.
func FromFullNameWithHost(nwo, fallbackHost string) (Interface, error) {
	repo, err := repository.ParseWithHost(nwo, fallbackHost)
	if err != nil {
		return nil, err
	}
	return NewWithHost(repo.Owner, repo.Name, repo.Host), nil
}
