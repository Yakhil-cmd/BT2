### Title
Reentrancy in `_requestERC20Transfer` via `_payERC20FeeAndRefundChange` Allows Duplicate Cross-Chain Transfer Requests — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeFee.sol`)

---

### Summary

`_requestERC20Transfer` makes external ERC20 token calls inside `_payERC20FeeAndRefundChange` before incrementing `requestNonce`. Unlike the KLAY path, no `nonReentrant` guard is applied. A registered ERC20 token with transfer hooks (e.g. ERC777) can re-enter `onERC20Received` during the fee-payment step, causing two `RequestValueTransfer` events to be emitted with sequential nonces for a single token deposit. Bridge operators on the counterpart chain process both events, resulting in unauthorized minting or transfer of bridged assets.

---

### Finding Description

`BridgeTransferKLAY` explicitly applies `nonReentrant` to both `handleKLAYTransfer` and `_requestKLAYTransfer`, and `BridgeFee._payKLAYFeeAndRefundChange` carries a comment stating its caller must be `nonReentrant`. No equivalent protection exists for the ERC20 path. [1](#0-0) 

`_payERC20FeeAndRefundChange` makes two external ERC20 token calls — `safeTransfer` to `feeReceiver` and `safeTransfer` back to `from` — before returning: [2](#0-1) 

`_requestERC20Transfer` calls `_payERC20FeeAndRefundChange` first, then emits `RequestValueTransfer` with the current `requestNonce`, and only then increments it: [3](#0-2) 

`onERC20Received` is public with no access control beyond `onlyRegisteredToken(_tokenAddress)` (enforced via `msg.sender` inside `_requestERC20Transfer`): [4](#0-3) 

`requestERC20Transfer` (the 2-step path) also lacks `nonReentrant`: [5](#0-4) 

A parallel reentrancy exists in `_requestERC721Transfer`, which makes an unguarded low-level call to `tokenURI` on the token contract before the burn and nonce increment: [6](#0-5) 

---

### Impact Explanation

When reentrancy fires during `_payERC20FeeAndRefundChange`:

- **Outer call** (`requestNonce = N`): enters `_payERC20FeeAndRefundChange`, external token transfer triggers hook → inner call executes.
- **Inner call** (reentrant via `onERC20Received`, `msg.sender` = registered token): `_payERC20FeeAndRefundChange` with `_feeLimit = 0` returns immediately (no external calls), emits `RequestValueTransfer(nonce = N)`, increments `requestNonce` to `N+1`.
- **Outer call resumes**: emits `RequestValueTransfer(nonce = N+1)`, increments `requestNonce` to `N+2`.

Both events are valid from the bridge operators' perspective. The counterpart bridge processes both, minting or transferring bridged ERC20 tokens twice for a single deposit. The attacker receives double the cross-chain value for one on-chain deposit.

The same logic applies to `_requestERC721Transfer` in non-mintBurn mode: the `tokenURI` external call fires before the nonce increment, allowing a second `RequestValueTransferEncoded` event for the same tokenId, causing the counterpart bridge to transfer two NFTs for one deposit.

---

### Likelihood Explanation

The trigger requires a registered ERC20 token with transfer hooks (ERC777 is the canonical example, but any token with a custom `transfer` or `safeTransfer` implementation that calls back into the bridge qualifies). Token registration is controlled by bridge operators, making this semi-trusted rather than fully unprivileged. However, ERC777 tokens are a well-known standard, and a bridge operator registering one without awareness of this reentrancy path is a realistic scenario. The KLAY path being explicitly guarded while the ERC20 path is not suggests the risk was recognized for one asset class but not extended to the other.

---

### Recommendation

Apply `nonReentrant` (from the already-imported `ReentrancyGuard`) to `requestERC20Transfer`, `onERC20Received`, `requestERC721Transfer`, and `onERC721Received`, mirroring the protection already present on the KLAY path: [7](#0-6) 

Alternatively, follow the checks-effects-interactions pattern: increment `requestNonce` before any external call, and emit the event after the increment using the pre-incremented value.

---

### Proof of Concept

**Setup**: Attacker deploys `MaliciousERC20` — an ERC777-compatible token registered on the bridge. Its `transfer` function, when called with `feeReceiver` as recipient, calls `bridge.onERC20Received(attacker, to, value, 0, extraData)`.

**Initial state**: `requestNonce = N`, bridge holds no tokens.

1. Attacker approves bridge for `value + feeLimit` tokens.
2. Attacker calls `bridge.requestERC20Transfer(maliciousToken, to, value, feeLimit, extraData)`.
3. Bridge calls `maliciousToken.safeTransferFrom(attacker, bridge, value + feeLimit)` — tokens arrive at bridge.
4. Bridge calls `_requestERC20Transfer(maliciousToken, attacker, to, value, feeLimit, extraData)`.
5. Bridge calls `_payERC20FeeAndRefundChange(attacker, maliciousToken, feeLimit)`.
6. Bridge calls `maliciousToken.safeTransfer(feeReceiver, fee)`.
7. `MaliciousERC20.transfer` hook fires → calls `bridge.onERC20Received(attacker, to, value, 0, extraData)`.
8. **Inner call**: `_payERC20FeeAndRefundChange(attacker, maliciousToken, 0)` returns 0 immediately (no external calls). Emits `RequestValueTransfer(nonce = N)`. `requestNonce = N+1`.
9. **Outer call resumes**: emits `RequestValueTransfer(nonce = N+1)`. `requestNonce = N+2`.
10. Bridge operators observe two valid events (nonces N and N+1) and submit two `handleERC20Transfer` transactions on the counterpart chain.
11. Counterpart bridge mints/transfers `value` tokens twice to `to`.

**Result**: Attacker deposited `value + feeLimit` tokens on the source chain and received `2 × value` tokens on the counterpart chain. The bridge's counterpart-side reserve or mint authority is drained by the extra `value` tokens.

```text
    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```
