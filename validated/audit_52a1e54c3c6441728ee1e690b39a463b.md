### Title
CCMenuController#stack uses unscoped `Stack.from_param!` instead of the `stacks` scope, allowing a stack-A CCMenu token to read stack B's data - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides both `authenticate_api_client` and `stack` from `BaseController`. The override of `stack` calls `Stack.from_param!(params[:stack_id])` against the global `Stack` relation instead of the base class's tenant-scoped `stacks` helper, so the `current_api_client.stack_id` binding that normally restricts a scoped `ApiClient` to a single stack is never enforced for this controller.

### Finding Description
The intended binding is: for any request, `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` must hold, i.e. `stacks.from_param!(params[:stack_id])` in [1](#0-0)  which resolves `stacks` as `Stack.where(id: current_api_client.stack_id)` when `stack_id` is present, else `Stack.all`.

`CCMenuController` re-implements `stack` to bypass this scope entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` class, and separately overrides `authenticate_api_client` to accept `params[:token]` from the query string via `ApiClient.authenticate`, which only looks up by verified token id, with no stack check: [3](#0-2) .

The token minted by `CCMenuUrlController#fetch` is created via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` with `permissions: %w[read:stack]` but **no `stack:` attribute set at all** — `stack_id` stays `nil` for every CCMenu client belonging to that user, regardless of which stack the URL was generated for: [4](#0-3) . The stack the URL points to is baked only into the query string path (`stack_id: stack.to_param`) in [5](#0-4) , not into the ApiClient record.

Since `current_api_client.stack_id` is `nil`, the base class's `stacks` method would return `Stack.all` anyway — the scoping design here relies entirely on `ApiClient.stack_id` being tied to one stack, which `CCMenuUrlController#client` never does. `require_permission :read, :stack` in [6](#0-5)  only checks the `permissions` array (`read:stack` is a global capability flag, not stack-specific) via `ApiClient#check_permissions!` [7](#0-6) , so no per-stack authorization ever occurs.

Exploit: attacker legitimately obtains a CCMenu URL/token for stack A (e.g., from a publicly shared dashboard settings page). They send `GET /api/1/stacks/<stack-B-param>/cc_menu.xml?token=<token-for-A>`. `authenticate_api_client` succeeds (token is valid, belongs to the same `ApiClient` row). `stack` resolves `Stack.from_param!('stack-B-param')` against the whole `Stack` table, returning stack B regardless of which stack the client was originally created for. The rendered XML (`shipit/ccmenu/project`) exposes stack B's deploy/task status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.) to an attacker with zero authorization tied to repository B.

### Impact Explanation
This is an unauthenticated-equivalent cross-tenant read of stack B's deploy state (name, last build status/label/time, web URL) using a token that was only ever intended to scope to stack A. Because the underlying `ApiClient.stack_id` is never populated by `CCMenuUrlController`, this is repeatable against **any** stack in the installation — the attacker only needs one valid CCMenu token (from any stack they can view) and can substitute any other stack's `to_param` value. This matches "High - unauthenticated read of stack state."

### Likelihood Explanation
Preconditions are low-cost and realistic: any user who can view a stack's settings page (or otherwise obtain a CCMenu URL, e.g., shared publicly for CI dashboard integration) gets a valid `token`. No GitHub secrets, session, or elevated Shipit role are required beyond having once fetched a CCMenu URL for some stack. Guessing/obtaining another stack's `to_param` (format `owner/repo/branch`) is trivial since Shipit stack identifiers are typically public repository/branch names. The attack is a single GET request and fully repeatable.

### Recommendation
- In `CCMenuUrlController#client`, associate the created `ApiClient` with the specific stack (`stack: stack`) so `current_api_client.stack_id` is actually populated per-stack.
- In `CCMenuController`, remove the custom `stack` override and use the inherited `stacks.from_param!(params[:stack_id])` from `BaseController` so the `current_api_client.stack_id` scope is honored, consistent with other API controllers.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (conceptual addition)
test "a token minted for stack A cannot be used to read stack B" do
  repo_a = Repository.create!(owner: 'acme', name: 'app-a')
  repo_b = Repository.create!(owner: 'acme', name: 'app-b')
  stack_a = Stack.create!(repository: repo_a, branch: 'main')
  stack_b = Stack.create!(repository: repo_b, branch: 'main')

  # Simulate CCMenuUrlController#fetch minting a token for stack A
  client = ApiClient.create!(creator: shipit_users(:walrus), name: 'CCMenu Client', permissions: %w[read:stack])
  assert_nil client.stack_id # precondition: never scoped

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

  assert_response :ok
  # Binding violated: current_api_client.stack_id (nil) != stack_b.id, yet stack B's data is rendered
  project = Hash.from_xml(response.body)['Projects']['Project']
  assert_equal stack_b.to_param, project['name'] # attacker reads stack B despite token minted for stack A
end
```
