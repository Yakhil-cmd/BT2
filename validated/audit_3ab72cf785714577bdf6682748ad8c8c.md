### Title
Unauthenticated `wallet_fully_approved` / `my_xpubkey` device messages let any paired (even non-correspondent) device permanently freeze multisig wallet approval - (File: `wallet.js`, `wallet_defined_by_keys.js`)

### Summary
The device-message handlers for `my_xpubkey` and `wallet_fully_approved` in `wallet.js` are explicitly marked "allowed from non-correspondents" and forward `from_address` to `wallet_defined_by_keys.js` without verifying that the sending device is actually one of the cosigners named in the target wallet's `wallet_definition_template`. This lets any device that can reach a victim's hub inbox (no pairing/authorization beyond knowing the wallet id) inject a permanent row into `extended_pubkeys` for a wallet it has no part in, which can never acquire `approval_date`, permanently blocking `checkAndFullyApproveWallet` from ever setting `full_approval_date` for that wallet.

### Finding Description
In `wallet.js`: [1](#0-0) [2](#0-1) 

Both cases dispatch directly to `wallet_defined_by_keys.js` using the caller-supplied `body.wallet` and the message's `from_address`, with **no check that `from_address` is a cosigner device of that wallet** (i.e., no lookup against `wallet_signing_paths`/the wallet's definition template before mutating state): [3](#0-2) 

`addDeviceXPubKey` and `handleNotificationThatWalletFullyApproved` both perform `INSERT IGNORE INTO extended_pubkeys (wallet, device_address) VALUES(?,?)` for **any** `wallet` id and **any** `device_address`, then update only `member_ready_date` (in the `wallet_fully_approved` path) while leaving `approval_date` and `extended_pubkey` `NULL` forever, because nothing else in the codebase later sets `approval_date` for a row that the real cosigner protocol never created.

`checkAndFullyApproveWallet` requires **every** row in `extended_pubkeys` for the wallet to have `approval_date` set before it will ever assign `full_approval_date`: [4](#0-3) 

Once the attacker's spurious row exists with `approval_date = NULL`, this condition can never be satisfied again for that wallet — the wallet is permanently prevented from reaching `full_approval_date`.

`deriveAddress`, used by all address issuance functions (`issueAddress`, `issueNextAddress`, `issueOrSelectNextAddress`, `issueOrSelectNextChangeAddress`, `scanForGaps`, `issueOrSelectAddressForApp`), hard-fails whenever `full_approval_date` is missing: [5](#0-4) 

So a wallet poisoned this way can never derive any further address (new receiving or change addresses), even though the legitimate cosigners have completed their own key exchange correctly.

### Impact Explanation
This is directly analogous to the referenced report's core issue: a function that mutates sensitive shared state is exposed without any authorization/membership check, letting an unrelated party corrupt state belonging to others. Here, any device capable of delivering a single hub message (explicitly permitted even "from non-correspondents") can permanently freeze a targeted multisig/shared wallet's ability to generate new addresses, by injecting one poisoned `extended_pubkeys` row keyed on a wallet id it does not own or participate in. This is a persistent, low-cost denial-of-service against legitimate cosigners' wallet, matching the "freezing" impact class.

### Likelihood Explanation
Likelihood is meaningfully non-trivial for any attacker who can determine or brute-force a `wallet` id belonging to a target multisig wallet (the id is disclosed in plaintext during any legitimate cosigner interaction, e.g., visible to any device the wallet-creation offer was broadcast through, or leaked via any of the several `wallet.js` message types that echo `body.wallet`), and who can get one message accepted by the target device (the two handlers are explicitly designed to accept messages from non-correspondents). No cryptographic secret or private key is required — just a single crafted device message with a known/guessed wallet id.

### Recommendation
Before mutating `extended_pubkeys` in `addDeviceXPubKey` and `handleNotificationThatWalletFullyApproved`, verify that `from_address` is actually one of the device addresses derivable from the wallet's stored `definition_template` (i.e., present in `wallet_signing_paths` for that `wallet`), and reject the message otherwise. Additionally, consider not creating new `extended_pubkeys` rows via `INSERT IGNORE` for device addresses that are not already expected members of the wallet.

### Proof of Concept
1. Attacker (any device that can send messages to the victim's device, even as declared "non-correspondent" per the code comments) learns/guesses the `wallet` id of a target multisig wallet (a base64 hash disclosed during normal wallet setup traffic).
2. Attacker sends a device message with `subject: "wallet_fully_approved"`, `body: {wallet: "<target_wallet_id>"}`.
3. `wallet.js`'s handler calls `walletDefinedByKeys.handleNotificationThatWalletFullyApproved(body.wallet, from_address, ...)` with no membership check.
4. This inserts a new row `(wallet, attacker_device_address)` into `extended_pubkeys` with `approval_date = NULL`, and sets `member_ready_date`.
5. `checkAndFinalizeWallet`/`checkAndFullyApproveWallet` for that wallet now permanently see a row with `approval_date IS NULL` that will never be filled in by the real protocol, so `full_approval_date` is never set again.
6. Any subsequent call to `issueAddress`/`issueNextAddress`/etc. for that wallet throws `"wallet not fully approved yet"` in `deriveAddress`, permanently blocking new address generation for the victims' wallet.

function checkAndFullyApproveWallet(wallet, onDone){
	db.query("SELECT approval_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0) // wallet not created yet
			return onDone ? onDone() : null;
		if (rows.some(function(row){ return !row.approval_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET full_approval_date="+db.getNow()+" WHERE wallet=? AND full_approval_date IS NULL", [wallet], function(){
			db.query(
				"UPDATE extended_pubkeys SET member_ready_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[wallet, device.getMyDeviceAddress()], 
				function(){
					db.query(
						"SELECT device_address FROM extended_pubkeys WHERE wallet=? AND device_address!=?", 
						[wallet, device.getMyDeviceAddress()], 
						function(rows){
							// let other members know that I've collected all necessary xpubkeys and ready to use this wallet
							rows.forEach(function(row){
								sendNotificationThatWalletFullyApproved(row.device_address, wallet);
							});
							checkAndFinalizeWallet(wallet, onDone);
						}
					);
				}
			);
		});
	});
}

		"INSERT "+db.getIgnore()+" INTO extended_pubkeys (wallet, device_address) VALUES(?,?)",
		[wallet, device_address],

			db.query(
				"UPDATE extended_pubkeys SET extended_pubkey=?, approval_date="+db.getNow()+" WHERE wallet=? AND device_address=?",

				function(){
					eventBus.emit('wallet_approved', wallet, device_address);
					checkAndFullyApproveWallet(wallet, onDone);
				}
			);
		}
	);
}
