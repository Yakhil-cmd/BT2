## Title
Cross-organization CI status forgery via webhook signature/repository binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a request against using the *claimed* `repository.owner.login` (or `organization.login`) field from the unauthenticated JSON body, but individual event handlers (notably `StatusHandler`) act on data (`sha`) that is never cross-checked against that same organization. This breaks the equality "organization that authenticated == repository/commit that is written," analogous to the Witch.sol finding where a field acted upon (`auctioneer`) was never covered by the validation applied elsewhere in the flow.

### Finding Description
`WebhooksController` verifies inbound webhooks like this: [1](#0-0) 

The organization used to pick the verification secret is derived purely from the untrusted request body: [2](#0-1) 

Once the HMAC check passes for *that* organization's `webhook_secret`, `Shipit::Webhooks.for_event(event)` dispatches the same raw `params` to handlers, e.g. `StatusHandler`: [3](#0-2) 

`StatusHandler#process` looks up commits **only by `sha`**, globally across the entire `Commit` table, with no scoping to the organization/repository whose secret was used to authenticate the request: [4](#0-3) 

In a multi-tenant Shipit deployment (`config/secrets*.yml` supports a `github:` map keyed by organization, each with its own `app_id`/`installation_id`/`webhook_secret`), this means: the value used to satisfy signature verification (`repository.owner.login` in the body) is never the same value used to constrain the side effect (`sha` lookup, global). Anyone who knows one tenant organization's `webhook_secret` (e.g. a legitimate admin who configured their own org's GitHub App webhook in this shared Shipit instance) can POST directly to `/github/webhooks` with a signature computed for their own org, while setting `sha` to a commit belonging to a completely different, unrelated stack/organization onboarded to the same Shipit instance. `Commit.create_status_from_github!` will create/overwrite a commit status (state, description, context, target_url) for that foreign commit.

### Impact Explanation
Commit statuses gate deploy safety checks (`ci.require`, blocking/required statuses used by `Commit#deployable?` and CI-gating logic referenced in `README.md`'s `ci.require` section and `app/models/shipit/deploy_spec.rb`). Forging a passing status (e.g. `state: "success"`, matching `context`) on a commit belonging to another tenant's stack can allow an unauthorized deploy of a commit that never actually passed CI for that stack — this falls under the "unauthorized deploy" Critical/High impact defined in the rules, achieved purely by exploiting the mismatch between the organization used for authentication and the entity actually written, without needing that victim organization's own webhook secret, an `ApiClient` token, or repository write access.

### Likelihood Explanation
Requires the attacker to possess a valid `webhook_secret` for *any one* organization/app configured on the shared Shipit instance (which is plausible in any Shipit deployment serving multiple orgs/teams, since each org's own maintainers typically know/configure the secret they use to register their GitHub App webhook) plus knowledge of a target commit `sha` in another tenant's stack (SHAs are not secret — visible in PRs, commit lists, Shipit UI). No other credential, session, or write access is required, and the webhook endpoint is unauthenticated by design (only HMAC-checked).

### Recommendation
- Scope every handler's side effects to the same organization/repository that was used to select the verification key, e.g. `StatusHandler` should filter `Commit` by joining `stack.repository.owner == repository_owner` (or `full_name`) matching the value used in `verify_signature`, not merely by `sha`.
- More generally, pass the verified `repository_owner`/`organization` value into each handler and require handlers to assert that any repository/commit/stack they touch belongs to that same verified owner before mutating state.
- Consider deriving the app/secret selection and the entity-scoping key from the same, single trusted field, rather than independently reading `repository.owner.login` in the controller and `repository.full_name`/`sha` in handlers.

### Proof of Concept
1. Shipit instance configured with two tenants in `secrets.yml`: `orgA` (attacker-controlled, attacker knows `webhook_secret_A`) and `orgB` (victim, has stack with commit `sha=deadbeef` requiring `ci: { require: ["ci/travis"] }`).
2. Attacker computes `sha1=HMAC(webhook_secret_A, body)` for body:
```json
{"sha":"deadbeef","state":"success","context":"ci/travis","repository":{"owner":{"login":"orgA"}}}
```
3. POST to `/github/webhooks` with `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "orgA")` and passes because the HMAC matches `webhook_secret_A`. [5](#0-4) 
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef")` and finds the commit belonging to `orgB`'s stack (unrelated to `orgA`), creating a forged `success` status for `ci/travis` on it. [4](#0-3) 
6. This status can now satisfy `orgB`'s `ci.require` gate for an otherwise-non-CI-passing commit.

Note: I could not fully verify how `Commit#deployable?`/`ci.require` consumes these statuses (the file `app/models/shipit/commit.rb` read was truncated due to a tool error in the final iteration), so the exact deploy-gating mechanics should be re-confirmed by a developer with full repository access before treating this as conclusively "Critical." The core root-cause finding — the authenticated-organization vs. written-entity mismatch in `WebhooksController`/`StatusHandler` — is confirmed directly from the cited code.

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
```
