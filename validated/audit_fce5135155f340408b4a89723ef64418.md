### Title
Webhook signature verification is org-selectable from the unauthenticated payload and silently bypassed when that org has no `webhook_secret`, allowing cross-repository/cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The bug report's "duplicate mapping" pattern (a key used to make a security decision comes from the same untrusted data whose integrity that decision is supposed to protect) has a direct analog in `WebhooksController#verify_signature`. The controller picks *which* GitHub App/`webhook_secret` to validate against using a field taken straight out of the unverified request body, and `GithubApp#verify_webhook_signature` treats a missing secret as automatic success. This breaks the binding "organization that authenticated == repository/stack that is written."

### Finding Description
`WebhooksController#verify_signature` derives the organization used to select the webhook secret entirely from the JSON payload it is trying to authenticate: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a per-organization `GithubApp` config (as documented for multi-org installs), and calls `verify_webhook_signature`: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally whenever `webhook_secret` is blank for that organization's config (`return true unless webhook_secret`). Shipit explicitly supports running with multiple GitHub Apps/organizations configured under distinct top-level keys, each with its own independent `webhook_secret`: [4](#0-3) 

If any one of those configured organizations has no `webhook_secret` set (a state the code accepts silently rather than rejecting), then a request whose `repository.owner.login` (or `organization.login`) names that organization will pass signature verification with **no cryptographic check performed at all** — regardless of what the rest of the payload contains, including which `repository`/stack the handlers (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`) subsequently act on. The same untrusted JSON body supplies both (a) the value used to pick/skip the authenticator, and (b) the target repository/stack that gets mutated, so nothing forces those two to correspond to a genuinely GitHub-signed event for the org whose stacks are actually touched.

### Impact Explanation
An unauthenticated network attacker who knows (or guesses) that a Shipit instance is configured for multiple GitHub organizations, and that at least one of them has no `webhook_secret` set, can forge arbitrary webhook payloads (`push`, `status`, `check_suite`, `membership`, etc.) claiming to originate from that unsecured organization while targeting a repository/stack that belongs to a different, secured organization tracked by the same Shipit instance. This can drive `GithubSyncJob`, commit/status ingestion, check-run refreshes, and membership changes on stacks the attacker has no legitimate access to — a cross-repository write that can feed into continuous-deployment triggers, i.e. an unauthorized deploy path, without ever presenting a valid `X-Hub-Signature`.

### Likelihood Explanation
Exploitation only requires network access to the public webhooks endpoint and knowledge that one configured organization lacks a `webhook_secret` — no session, `ApiClient` token, or repository write access is needed, matching the "unprivileged attacker" scope. Multi-org configuration with an unset `webhook_secret` is a realistic real-world misconfiguration explicitly permitted (and exemplified with `webhook_secret: # nil`) by the engine's own sample configs.

### Recommendation
Do not let the organization used for signature validation be inferred from the same untrusted payload without independently confirming the resulting repository belongs to that organization. Additionally, `verify_webhook_signature` should never silently succeed when `webhook_secret` is unset — either require it to be present for every configured organization, or fail closed (`return false`) instead of `true` when it is missing.

### Proof of Concept
1. Operator configures two GitHub Apps in `secrets.yml` (as shown in `docs/setup.md`): `OrgA` (has `webhook_secret` set) and `OrgB` (no `webhook_secret`, `nil`) — both orgs' repos are tracked as Shipit stacks.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and a JSON body where `repository.owner.login = "OrgB"` (or `organization.login = "OrgB"`) but `repository.full_name`/other repo identifiers actually correspond to a stack under `OrgA`.
3. `verify_signature` resolves `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` without checking any HMAC.
4. The forged, entirely attacker-controlled payload is then dispatched to `Shipit::Webhooks.for_event('push')` handlers, which act on the `OrgA` stack despite no valid signature ever being verified for it.

**Uncertainty:** I could not fully re-verify the exact field(s) `PushHandler` uses to resolve the target `Stack`/`Repository` (tool access ended before reading `push_handler.rb` and `handler.rb` in full), so the precise payload shape needed to target a specific cross-org stack is not 100% confirmed from source — this should be validated by a background agent with file access before treating the PoC as final.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
