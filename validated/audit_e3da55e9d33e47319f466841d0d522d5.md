Found it: `Shipit::Api::CCMenuController` binds the API token to the wrong scope check.

### Title
API token authorization checked against the wrong stack: CCMenu token issued for one stack authorizes reading any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`CCMenuController` overrides `authenticate_api_client` to authenticate the `ApiClient` from a raw `token` query-string parameter, but it never re-validates that the authenticated client's `stack_id` (the stack the token was scoped/issued for) matches the `stack_id` in the URL that the request actually touches. This breaks the binding: *"a stack a token authorises versus a stack it touches"*.

### Finding Description
`BaseController#stacks` correctly scopes stack access by the current API client: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) , and `#stack` looks the requested stack up only within that scoped relation via `stacks.from_param!(params[:stack_id])` [2](#0-1) .

`CCMenuController`, however, overrides both the authentication and the stack lookup:
```ruby
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end

private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [3](#0-2) 

Here `stack` is resolved via `Stack.from_param!` against **all** stacks (not `stacks`, the client-scoped relation from `BaseController`), and `require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)` [4](#0-3) , which checks the permission list only, never the `stack_id` binding.

The token itself is only a signed client id (`Shipit::SimpleMessageVerifier.verify(token).to_i`) [5](#0-4) , with no stack information embedded or bound at verification time; `ApiClient#stack_id` is a separate, unauthenticated-at-request-time DB column consulted only in `BaseController#stacks`, which `CCMenuController` bypasses.

`CCMenuUrlController` issues exactly this kind of scoped, read-only token for a specific stack and hands the URL/token to any logged-in user (any Shipit user, not necessarily one with write/deploy rights) who can view that one stack:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
``` [6](#0-5) 

Because `ApiClient.find_or_create_by!(creator: current_user, name: 'CCMenu Client')` is looked up by `creator` + `name` only (not `stack:`), a given user's token is the *same* `ApiClient` record no matter which stack triggered its creation - the `stack_id` on that record simply reflects the stack that happened to create it. Since `CCMenuController#stack` ignores `current_api_client.stack_id` entirely, **any** holder of a valid (previously issued to them) CCMenu token can supply an arbitrary `stack_id` in the URL and read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, activity, etc.) for a stack the token was never scoped to - an unauthenticated read of stack state via a token whose authorized scope binding is not enforced.

### Impact Explanation
This matches the "High" bucket: "unauthenticated read of stack state, task streams or deploy output" via a token whose claimed scope (`stack_id`) is not checked against the resource actually accessed. The disclosed data (deploy status/labels/activity/last build info) is limited to what the CCMenu XML view exposes, so it is a read-only information-disclosure/scope-escalation across stacks, not RCE or write access.

### Likelihood Explanation
Requires only possession of a legitimately-issued read-only CCMenu token (obtainable by any authenticated Shipit user for any stack they can view) and knowledge/guessing of another stack's `to_param` (owner/repo/env), which is often discoverable/enumerable. No privileged role or secret beyond a self-obtained token is needed, matching the "unprivileged attacker" requirement.

### Recommendation
In `CCMenuController#stack`, resolve the stack through the client-scoped `stacks` relation (as `BaseController` does) instead of `Stack.from_param!` directly, e.g. `stacks.from_param!(params[:stack_id])`, and/or explicitly assert `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering.

### Proof of Concept
1. As User A, visit `stacks/A-owner/A-repo/production` and trigger `CCMenuUrlController#fetch`, obtaining `ccmenu_url` with `token=<A's ApiClient token, scoped stack_id=A-stack>`.
2. Note that the underlying `ApiClient` is looked up by `creator: current_user, name: 'CCMenu Client'` only [6](#0-5) , so the same token is reused/valid regardless of which stack it was minted for.
3. Call `GET /api/stacks/B-owner/B-repo/staging/ccmenu.xml?token=<A's token>` where B-stack is a different, unrelated stack.
4. `authenticate_api_client` succeeds (token verifies) [7](#0-6) ; `stack` resolves B-stack via unscoped `Stack.from_param!` [8](#0-7) ; `require_permission :read, :stack` only checks the permission list, not `stack_id` [4](#0-3) .
5. Response 200 with B-stack's build/deploy status is returned, despite the token being scoped to A-stack.
