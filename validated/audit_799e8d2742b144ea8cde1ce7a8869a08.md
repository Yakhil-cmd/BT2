### Title
Signature verification is bound to an attacker-chosen organization while the write targets an unrelated repository/commit - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to check the `X-Hub-Signature` against using an unauthenticated field taken straight out of the JSON body, while the downstream handlers that actually write data (create commit statuses, sync commits, etc.) key off a *different* field of that same body. Because `verify_webhook_signature` trivially passes when the selected organization has no `webhook_secret` configured, an attacker who names such an organization can forge a signed-looking webhook that performs writes against a completely different, unrelated repository/stack.

### Finding Description
`verify_signature` derives the organization used for authentication purely from the unauthenticated payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GithubApp` instance configured per-organization, and its `verify_webhook_signature` is: [3](#0-2) 

Note line 77: `return true unless webhook_secret` — if the organization picked via `repository_owner` has no `webhook_secret` configured (the documented default in every example secrets file, e.g. `webhook_secret: # nil`), verification unconditionally passes regardless of the actual signature header or body content. [4](#0-3) 

Meanwhile, once the request is accepted, handlers resolve *which stack/repository/commit to mutate* using a different field of the same attacker-supplied body — `repository.full_name` (not `repository.owner.login`) for repository-scoped handlers: [5](#0-4) 

and, even more permissively, the `status` event handler looks up commits **globally by `sha`** with no repository/organization scoping at all: [6](#0-5) 

This breaks the binding "organization that authenticated == repository that is written": the signature check authenticates against org A (selected via `repository.owner.login` / `organization.login`), but the actual write (`Commit.where(sha:).create_status_from_github!`, or `GithubSyncJob` via `repository.full_name`) targets whatever repository/commit the attacker puts in the unrelated field of the same JSON body.

### Impact Explanation
An unprivileged external attacker who knows (from the public multi-org setup docs/deployment conventions) the name of any GitHub organization configured on the Shipit instance without a `webhook_secret` (a documented, common default state) can craft an arbitrary JSON payload with:
- `repository.owner.login` / `organization.login` = that unsecured org (to make `verify_signature` pass trivially), and
- `repository.full_name` / commit `sha` = a target repository/commit belonging to an entirely different, properly secured organization tracked by the same Shipit instance.

This lets the attacker forge a GitHub `status` event that creates an arbitrary `CommitStatus` (`state: success`, attacker-chosen `context`) for any tracked commit, or forge a `push`/`membership` event affecting an unrelated stack. Forged "success" statuses can satisfy deploy-spec required-status checks, enabling an unauthorized deploy of a commit whose CI never actually passed. This qualifies as Critical under the engine's rules ("unauthorized deploy").

### Likelihood Explanation
Requires no credentials, no repository access, and no Shipit session — only knowledge that the Shipit instance is configured with multiple GitHub organizations (a documented setup pattern) and that at least one of them has no `webhook_secret` set, which is the out-of-the-box default in every shipped example (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `docs/setup.md`). This is a realistic misconfiguration/default rather than a theoretical edge case.

### Recommendation
Do not select the verification secret from unauthenticated payload content that differs from the field used for authorization decisions downstream. Concretely:
- Verify the webhook signature against every configured `webhook_secret` (or a single shared secret) rather than picking the org/secret from an untrusted field of the same body being verified.
- After verifying the signature under a specific org's secret, cross-check that the same org actually owns the `repository.full_name` (and, for `status` events, that the commit's stack belongs to that org) before dispatching to handlers.
- Do not treat a blank/missing `webhook_secret` as an implicit "always valid" signature; require `webhook_secret` to be configured for every organization in production, and fail closed if it is unset.

### Proof of Concept
1. Shipit is configured with two GitHub orgs per `docs/setup.md`'s "Using Multiple Github Applications": `OrgA` (no `webhook_secret` set) and `OrgB` (tracked stack `OrgB/real-repo`, real `webhook_secret`).
2. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<sha of a real commit in OrgB/real-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/real-repo" }
}
```
3. `repository_owner` resolves to `OrgA`; `Shipit.github(organization: 'OrgA').verify_webhook_signature` returns `true` immediately because `OrgA.webhook_secret` is blank (`lib/shipit/github_app.rb:77`), regardless of the `X-Hub-Signature` header sent (or omitted).
4. `StatusHandler#process` runs and creates a forged `success` `CommitStatus` on the real `OrgB` commit (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), potentially satisfying required-status checks and enabling an unauthorized deploy.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
