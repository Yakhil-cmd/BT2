### Title
Integer overflow in C# binding size checks bypasses length validation, causing native heap-buffer-overflow in `verify_cell_kzg_proof_batch` - (File: bindings/csharp/Ckzg.Bindings/Ckzg.cs)

### Summary
The C# `Ckzg` binding validates the caller-supplied buffer lengths for cell/commitment/proof arrays by multiplying the untrusted `int numCells` (or `count`) parameter by 32-bit `int` size constants before comparing against the actual `Span<byte>.Length`. Because C# `int` multiplication is unchecked by default, a sufficiently large `numCells` overflows the 32-bit product, producing a small (or zero) "expected length" that a tiny, legitimately-sized buffer can satisfy. The unwrapped, full-size `numCells` value is then cast to `UInt64` and passed straight into the native `verify_cell_kzg_proof_batch` in `src/eip7594/eip7594.c`, which iterates and reads/writes `numCells` elements from the undersized native buffer, causing a heap-buffer-overflow. This mirrors the ImageMagick `WriteUHDRImage` bug class: `int` arithmetic used to size a buffer overflows, the allocation/validation is undersized, and the subsequent write/read walks past the buffer.

### Finding Description
`VerifyCellKzgProofBatch` in [1](#0-0)  validates argument lengths via:
```
ThrowOnInvalidLength(cells, nameof(cells), BytesPerCell * numCells);
```
`BytesPerCell` is `FieldElementsPerCell (64) * BytesPerFieldElement (32) = 2048`, and both it and `numCells` are 32-bit `int`s [2](#0-1) . `ThrowOnInvalidLength` simply checks `data.Length != expectedLength` [3](#0-2) .

Because `BytesPerCell` (2048 = 2^11) is a power of two, `BytesPerCell * numCells` computed as 32-bit signed multiplication equals `(numCells & 0x1FFFFF) << 11` modulo 2^32. Choosing `numCells = 2,097,152` (2^21) makes this product exactly `0`. The `ThrowOnInvalidLength` check for `cells` then only requires a zero-length (or otherwise tiny-mismatched) span to "pass," even though the real intended cell-array size for `numCells = 2,097,152` should be gigabytes.

After the (bypassed) checks, the *real*, unwrapped `numCells` is forwarded unchanged as `(UInt64)numCells` to the native call:
```
KzgResult kzgResult = VerifyCellKzgProofBatch(out var result, commitmentsPtr,
    cellIndicesPtr, cellsPtr, proofsPtr, (UInt64)numCells, ckzgSetup);
``` [4](#0-3) 

On the native side, `verify_cell_kzg_proof_batch` in `src/eip7594/eip7594.c` trusts `num_cells` and immediately loops over it to validate cell indices and later to copy/hash cell data:
```
for (size_t i = 0; i < num_cells; i++) {
    if (cell_indices[i] >= CELLS_PER_EXT_BLOB) return C_KZG_BADARGS;
}
...
memcpy(unique_commitments, commitments_bytes, num_cells * sizeof(Bytes48));
``` [5](#0-4) [6](#0-5) 

Since the .NET-side `commitments`, `cells`, and `proofs` spans are backed by managed arrays that were only required to satisfy the wrapped (tiny) expected size, `fixed` pins a buffer far smaller than `num_cells` requires. The native function's index/memcpy loops (and `compute_verify_cell_kzg_proof_batch_challenge`'s memcpy loop at [7](#0-6) ) then read out of bounds from these undersized pinned buffers — a heap out-of-bounds read/write directly analogous to the `int`-overflow-driven undersized allocation in ImageMagick's `WriteUHDRImage`.

The same pattern applies to `VerifyBlobKzgProofBatch` (`BytesPerBlob * count`, `BytesPerCommitment * count`, `BytesPerProof * count`) and `RecoverCellsAndKzgProofs` (`BytesPerCell * numCells`) in the same file [8](#0-7) [9](#0-8) .

### Impact Explanation
Any node/application built on the C# `Ckzg` bindings that passes a large `numCells`/`count` (e.g., derived from an untrusted network-supplied cell/blob batch) to these APIs can be driven into reading/writing past the bounds of the pinned managed buffer. This causes memory corruption/heap-buffer-overflow inside the native library call, crashing the process (denial of service) for every node using this binding when it processes a maliciously sized cell/blob batch — matching the High-severity "one blob or sidecar crashes or aborts every node running this library" criterion. In the worst case, since the corruption occurs during pinned native memory access, it can also lead to reads of adjacent heap memory being fed into the hash/verification logic (`compute_verify_cell_kzg_proof_batch_challenge`), which could affect derived verification results — but crash/DoS is the concretely provable outcome.

### Likelihood Explanation
The bug is directly reachable by any caller of the public `Ckzg.VerifyCellKzgProofBatch`, `Ckzg.VerifyBlobKzgProofBatch`, or `Ckzg.RecoverCellsAndKzgProofs` APIs that accepts a cell/blob count derived from external/untrusted data (e.g., a consensus client deserializing a peer-supplied number of cells/blobs before allocating buffers). No special privileges are required — only the ability to influence the `numCells`/`count` argument together with correspondingly (mis)sized buffers, which is a realistic binding-usage pattern when array lengths are computed from an attacker-controlled count field.

### Recommendation
Perform all buffer-size computations in `bindings/csharp/Ckzg.Bindings/Ckzg.cs` using 64-bit (`long`/`ulong`) arithmetic instead of `int`, and validate `numCells`/`count` against a sane maximum (e.g., `CellsPerExtBlob`) before any multiplication, mirroring the bounds checks already present in native `verify_cell_kzg_proof_batch`/`recover_cells_and_kzg_proofs` (`num_cells > CELLS_PER_EXT_BLOB` check at [10](#0-9) ). Reject negative or excessively large counts explicitly before computing `expectedLength`.

### Proof of Concept
1. Call `Ckzg.VerifyCellKzgProofBatch(commitments, cellIndices, cells, proofs, numCells: 2097152, ckzgSetup)`.
2. Supply `cells` as a zero-length (or minimally-sized) `Span<byte>` — this satisfies `ThrowOnInvalidLength(cells, nameof(cells), BytesPerCell * numCells)` because `2048 * 2097152` overflows 32-bit `int` to `0`.
3. Supply `cellIndices` as a genuinely-sized `2,097,152`-element `ulong` array (this check is not multiplication-based and passes normally).
4. The call proceeds to native `verify_cell_kzg_proof_batch(..., num_cells = 2097152, ...)` in `src/eip7594/eip7594.c`, which reads/copies `num_cells` elements from the pinned (empty) `cells` buffer, causing a heap out-of-bounds access and process crash.
