### Title
Webhook signature verified against `repository.owner.login`'s secret while the write target is selected by unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the inbound webhook HMAC against using `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Once the signature check passes, every event handler resolves the `Stack`/`Repository`/`Commit` to mutate using a completely different payload field, `payload.dig('repository', 'full_name')`, defined in the shared `Handler` base class. Nothing enforces that these two fields describe the same repository, so signature validation against org A's secret does not guarantee the payload's effects are scoped to org A's repositories.

### Finding Description
The controller resolves the signing organization from the request body itself, before any cryptographic check is performed: [1](#0-0) [2](#0-1) 

It uses `repository.owner.login` (or `organization.login`) purely to pick which `Shipit.github(organization: ...)` webhook secret to HMAC-verify the raw body against.

However, every webhook `Handler` subclass determines which `Stack`/`Repository`/`Commit` records to act on using an entirely separate field, `repository.full_name`, which is never checked against `repository.owner.login`: [3](#0-2) 

This field feeds directly into stack/commit mutation logic in handlers such as `PushHandler` (triggers `stack.sync_github`), `CheckSuiteHandler` (schedules check-run refresh on arbitrary commits), and `StatusHandler` (creates commit statuses matched only by SHA, with no repository scoping at all): [4](#0-3) [5](#0-4) [6](#0-5) 

**The broken equality:** the report's slippage-check analogy is "a value acted upon that was never covered by the check performed at authorization time." Here: `organization that authenticated` (via `verify_webhook_signature` keyed by `repository.owner.login`) `≠` `repository that is written` (selected by `repository.full_name` inside `Handler#stacks`/`#repository_name`). Shipit is explicitly designed to be multi-tenant across GitHub organizations — `config/secrets.development.shopify.yml` shows multiple independent org configs, each with its own `webhook_secret`: [7](#0-6) 

An operator/admin who legitimately owns a GitHub App installation for one onboarded organization (call it org A, with a Shipit-known `webhook_secret`) can freely construct a webhook body where `repository.owner.login = "org-A"` (so the correct, own secret is used and the HMAC passes) but `repository.full_name = "org-B/victim-repo"` (a repo/stack belonging to a completely different tenant org B). `verify_signature` only checks the raw body against org A's secret — it never inspects `full_name` — so the signature passes, and the handler then mutates org B's stack/commit data (triggers syncs, forces GitHub status writes, schedules check-run refreshes) despite the request never being authenticated as coming from org B's GitHub App/installation.

### Impact Explanation
This breaks the cross-tenant isolation the signature check is meant to enforce: a request cryptographically authenticated for organization A can be used to write to, sync, and inject fabricated commit statuses/check-run states for a repository/stack belonging to organization B. Depending on how `Shipit.github_teams`/deploy gating consumes `Commit#create_status_from_github!` and check-run state, this can be leveraged to falsify CI/status signals that unlock deploys for another tenant's stack (`StatusHandler`, `CheckSuiteHandler`), i.e. cross-repository writes / escalation into another tenant's deploy authorization — matching the High/Critical "cross-repository writes" and "unauthorized deploy" impact categories.

### Likelihood Explanation
Requires only that the attacker administers (or has webhook_secret knowledge for) any one organization/GitHub App onboarded into the shared Shipit instance — no privileged Shipit session, `ApiClient` token, or GitHub App private key for the *victim* org is needed, and no repository write access to the victim repo is needed. Any multi-org Shipit deployment (explicitly supported by the config format) is exposed. The attack is a single crafted HTTP POST to `/webhooks` with a valid HMAC for the attacker's own org.

### Recommendation
Bind the value used to select/verify the signing secret to the same value used to resolve the write target. Either:
- Verify the signature using the org derived from `repository.full_name`'s owner segment (not a separate `repository.owner.login`/`organization.login` fallback), or
- After signature verification, assert that `repository.owner.login` (the field used to pick the secret) matches the owner segment of `repository.full_name` (the field used to resolve the `Stack`), rejecting the webhook otherwise.

### Proof of Concept
1. Shipit is configured with two tenant orgs, `org-A` and `org-B`, each with its own GitHub App and `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. Attacker controls org A's GitHub App/webhook secret (legitimately, as org A's admin).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body:
```json
{
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-B/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
signed with org A's `webhook_secret` via `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-A"`, fetches org A's secret, and the HMAC matches → request proceeds.
5. `Shipit::Webhooks::Handlers::StatusHandler#process` matches `Commit.where(sha: params.sha)` — with no organization/repository scoping at all — and calls `commit.create_status_from_github!`, injecting a fabricated passing CI status onto org B's commit, potentially unblocking a deploy that depends on that status check, despite the request never being authenticated for org B.
