### Title
StatusHandler ignores webhook `repository`, allowing any authenticated repo to write cross-stack `Status` rows by sha collision - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no scoping to the webhook's own `repository.full_name`, then calls `commit.create_status_from_github!(params)`, which calls `statuses.replicate_from_github!(stack_id, github_status)` using `self.stack_id` (the commit's own stack) rather than any value derived from the payload. This is unlike every `PullRequest::*Handler`, which resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any record.

### Finding Description
The claimed binding is: `commit.stack_id` (used in `Status.replicate_from_github!(stack_id, ...)`, [1](#0-0) ) should equal `Repository.from_github_repo_name(params.repository.full_name).stack_id` (the stack asserted by the verified webhook's own repository). Tracing the code:

- `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . It never calls `repository_name`, `stacks`, or `Repository.from_github_repo_name`, even though the base `Handler` class exposes exactly that helper (`stacks` / `repository_name`) for this purpose [3](#0-2) .
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, where `stack_id` is simply the receiver commit's own `stack_id` column [1](#0-0) .
- `Status.replicate_from_github!` persists a `Status` row keyed to that `stack_id` with state/description/context/target_url/created_at taken straight from the attacker-controlled webhook body [4](#0-3) .
- By contrast, all `PullRequest::*Handler`s (`ClosedHandler`, `LabeledHandler`, `AssignedHandler`, etc.) resolve the acting repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before any mutation, joining the payload's asserted repository to a Shipit `Repository`/`Stack` [5](#0-4) .

Existing guards do not close this gap: `verify_signature` in `WebhooksController` only proves the payload was HMAC-signed by the GitHub App configured for `repository_owner` (the payload's organization) [6](#0-5) , and `GitHubApp#verify_webhook_signature` validates against that organization's `webhook_secret` only [7](#0-6) . Neither check constrains which `Stack`/`Commit` rows the event may touch — that constraint is architecturally absent from `StatusHandler`. Since `Commit` rows are scoped per `stack` (`belongs_to :stack`) [8](#0-7) , and multiple stacks/repositories can independently contain a `Commit` row with an identical `sha` (e.g., shared ancestor commits from forks/mirrors of the same upstream history, which is common and requires no cryptographic "collision", just identical git object content), a legitimately-signed status webhook from repository A's own GitHub App/organization will iterate over and write `Status` rows against every `Commit` in the database sharing that sha — including commits owned by unrelated stacks/repositories/organizations that never asserted anything in this payload.

### Impact Explanation
A `Status` row (state/description/context/target_url) is created for a `Commit` belonging to a stack the attacker's webhook never named. Because `Status#after_create :enable_ci_on_stack` and `Commit#add_status` drive `deployable_status`/`commit_status` hook emission, CI gating, and `ProcessMergeRequestsJob` enqueuing (as shown in `test/models/commits_test.rb`'s `add_status` transition tests), a forged/replayed "success" status on someone else's stack can flip that commit's deployability state and trigger downstream automation (merge-request processing, deploy gating) for a repository/stack the attacker does not own or control. This matches the "payload for one repository mutating another's stack/commit" Critical category, and is repeatable against any stack that happens to share a commit sha with the attacker's own repository, with no per-request cost beyond triggering their own repo's status event.

### Likelihood Explanation
Preconditions: the attacker's own repository must already have Shipit's GitHub App installed and be a genuine webhook source for the `status` event (so `verify_signature` passes for their org) — no privileged Shipit role, session, or secret needed. The attacker needs a target commit sha that exists as a `Commit` row in another stack; this is realistic whenever stacks track the same open-source project (forks/mirrors), since git commit shas are deterministic on content, not secret. No unusual Shipit configuration is required beyond the normal multi-repository setup this engine is designed for. Cost is low (one legitimate GitHub status event from the attacker's own repo); exploitability depends on sha overlap existing, which is plausible in shared-upstream/mono-history setups but not guaranteed for arbitrary target stacks — this bounds it below a fully-arbitrary-target attack while still being a real cross-tenant write for the overlap case.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to stacks tied to `params.repository.full_name`, mirroring the `PullRequest::*Handler` pattern: require `repository` in the params schema, resolve `Repository.from_github_repo_name(params.repository.full_name)`, and filter `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))` (or equivalent join) before calling `create_status_from_github!`. Additionally, `Commit#create_status_from_github!`/`Status.replicate_from_github!` should not implicitly trust `commit.stack_id` as authoritative without this upstream scoping.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "process never resolves Repository.from_github_repo_name, unlike PullRequest handlers" do
          commit = shipit_commits(:first) # belongs to stack A
          other_stack_commit = shipit_commits(:second) # belongs to a different stack, same sha as commit
          other_stack_commit.update_column(:sha, commit.sha) # simulate shared upstream sha across stacks

          payload = {
            'sha' => commit.sha,
            'state' => 'success',
            'context' => 'ci/attacker',
            'repository' => { 'full_name' => 'attacker-org/attacker-repo' } # asserts nothing about the other stack
          }

          Repository.expects(:from_github_repo_name).never

          assert_difference -> { Status.where(stack_id: other_stack_commit.stack_id).count }, 1 do
            StatusHandler.call(payload)
          end

          # Binding under test: commit.stack_id (used) should have equaled
          # Repository.from_github_repo_name(payload['repository']['full_name'])&.stack_id (asserted), but never does.
          assert_not_equal Repository.from_github_repo_name('attacker-org/attacker-repo')&.id, other_stack_commit.stack.repository_id
        end
      end
    end
  end
end
```
This demonstrates `Repository.from_github_repo_name` is never invoked during `StatusHandler#process` (unlike every `PullRequest::*Handler`), and a `Status` is written against a stack the payload's `repository` never named, purely because a `Commit` row with a matching sha exists there.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
