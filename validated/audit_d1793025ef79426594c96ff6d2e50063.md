### Title
Asset definer can post `asset_attestors` updates to strip attestation and permanently freeze already-held asset balances - (File: validation.js)

### Summary
For any asset created with `spender_attested: true`, the asset definer alone controls the live attestor list via the `asset_attestors` message. Because spend validation always checks the balance holder's address against the *current* (latest) attestor list rather than the list that was in force when the tokens were acquired, the definer can unilaterally publish a new attestor list that excludes existing holders. Those holders' previously-acquired balances become permanently unspendable, mirroring the reported `UXDController.setRedeemable()` issue where a single privileged call retroactively locks funds that users already deposited/hold.

### Finding Description
An asset with `spender_attested=true` requires that every payer/payee address be in the asset's attestor-approved set at spend time: [1](#0-0) 

Whether an output address is allowed is decided against `objAsset.arrAttestedAddresses`, which storage.js populates from the **most recent** `asset_attestors` unit (not the list active when the holder received the funds): [2](#0-1) 

The attestor list can be replaced at any time by a single-authored `asset_attestors` message. The only authorization check is that the author must be the asset's `definer_address`; there is no restriction preventing removal of addresses that already hold a balance, no minimum retained set, and no grace period: [3](#0-2) 

`checkAttestorList` only enforces basic formatting (non-empty, sorted, valid addresses, count limit) — it does not protect existing holders in any way: [4](#0-3) 

For divisible/transferable assets, the transfer additionally requires all *output* addresses to be attested when `spender_attested` is set, further compounding the freeze — a definer-controlled attestor list swap blocks all transfers, not just issuance: [5](#0-4) 

Analogous to `UXDController.setRedeemable()`, which lets a privileged role flip a flag that retroactively locks user-deposited collateral, here the asset definer (an actor explicitly reachable as a single "asset issuer" posting a unit) can post a message that retroactively removes previously-valid authorization from holders who already legitimately acquired/hold asset units, with no way for the holder to reverse it themselves.

### Impact Explanation
Any holder of a `spender_attested` asset can have their entire balance of that asset permanently frozen at the sole discretion of the asset definer, at any point after the tokens were issued/transferred to them — even though they satisfied every attestation requirement at the time they received the funds. This is a concrete freezing of user funds triggered by a normal, validator-accepted unit (`asset_attestors`), fitting the "AA/asset fund freezing" impact class from a single privileged-but-reachable poster (the asset definer).

### Likelihood Explanation
Likelihood is high for any asset that opts into `spender_attested`: the definer only needs to compose and post one additional `asset_attestors` unit (via `composer.composeAssetAttestorsJoint`) omitting addresses it wants to freeze — no special network conditions, timing races, or additional privileges are required beyond being the asset's own definer, which is a normal, expected actor in the asset lifecycle. However, this only affects assets that developers deliberately configure as `spender_attested`; base-currency and non-attested assets are unaffected.

### Recommendation
- Snapshot/lock the attestor list applicable to each output at the time the payment is validated and stable, rather than always reading the latest list, or
- Require that `asset_attestors` updates cannot remove addresses that currently hold a non-zero balance without providing a compensating exit mechanism, or
- Document explicitly (and warn wallet/asset-integrators) that `spender_attested` assets carry an inherent risk of definer-triggered freezing of existing balances, and require dApps built on such assets to treat the definer as a trusted, centralized authority equivalent to an admin key.

### Proof of Concept
1. Definer `D` creates asset `A` with `spender_attested: true` and an initial attestor list `[X, Y]` (via the `asset` message, or `asset_attestors` immediately after — see `writer.js:218-243`).
2. Holder `H` (address `X`) legitimately receives units of asset `A` from `D` while attested.
3. `D` posts a new `asset_attestors` message for asset `A` with attestor list `[Y]` only (validated purely by `validateAttestorListUpdate`, `validation.js:2829-2848`, requiring only that `D` is the definer).
4. `storage.readAsset`'s `addAttestorsIfNecessary` (storage.js:1917-1946) now returns `arrAttestedAddresses = [Y]` as the current list for asset `A`.
5. `H` attempts to spend/transfer their previously-held balance of asset `A`. `validatePayment` (validation.js:2115-2122) rejects the unit because `H`'s address `X` is no longer in `arrAttestedAddresses`; for transfers, `validatePaymentInputsAndOutputs` (validation.js:2630-2641) also rejects any output to `X`.
6. `H`'s asset `A` balance is now permanently unspendable unless `D` chooses, at its sole discretion, to re-add `X` to the attestor list.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
