### Title
Unauthenticated User Impersonation via `X-Shipit-User` Header Bypasses the API-Token-to-User Binding - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The Shipit API authenticates requests by verifying an `ApiClient` token, but the `User` identity attributed to the request (`current_user`) is derived from an attacker-controlled `X-Shipit-User` HTTP header with no cryptographic binding to the authenticated `ApiClient`. Any holder of a valid API token can set this header to impersonate an arbitrary `User` record in the system, breaking the equality: `ApiClient (creator/owner) == User attributed for the operation`.

### Finding Description
`Shipit::Api::BaseController#authenticate_api_client` verifies the request using HTTP Basic Auth against `ApiClient.authenticate(token)`, establishing `@current_api_client` [1](#0-0) .

Separately, `current_user` — the identity that is recorded as the actor for privileged operations — is computed from `identify_user`, which trusts the client-supplied `X-Shipit-User` header verbatim, looking up any `User` by login with no relationship check to `current_api_client`: [2](#0-1) 

This is the same bug class as the reported `ERC20Rewarder.claim()` issue: the function/endpoint authenticates one identity (the token/`msg.sender` in the analogy) but acts on behalf of a second, unauthenticated identity (the destination address / `X-Shipit-User`) supplied in the payload, with no check that the acting party is authorized to act "as" that identity.

`current_user` is not just cosmetic — it is passed directly into state-changing model methods that record authorship/authorization-relevant actor of privileged actions across the API surface:
- Locking a stack: `stack.lock(params.reason, current_user)` [3](#0-2) 
- Triggering a deploy task: `stack.trigger_task(params[:task_name], current_user, env: params.env)` [4](#0-3) 
- Aborting a running deploy: `task.abort!(aborted_by: current_user)` [5](#0-4) 
- Triggering a rollback / aborting active task on rollback: `active_task.abort!(aborted_by: current_user, ...)` / `deploy.trigger_rollback(current_user, ...)` [6](#0-5) 
- Requesting a merge: `MergeRequest.request_merge!(stack, params[:id], current_user)` [7](#0-6) 

Test fixtures confirm the header is trusted as the sole basis for attributing an action to a `User`: [8](#0-7) 

### Impact Explanation
The vulnerability lets any caller in possession of a legitimately-issued, narrowly-scoped `ApiClient` token forge the identity of any other `User` in the system for the purposes of authorship attribution on deploys, rollbacks, aborts, locks, and merges. This corrupts the audit trail used for accountability (e.g., "who deployed/aborted/merged") and can be used to attribute destructive or unauthorized actions (aborting another team's deploy, forcing a rollback, requesting a merge) to an arbitrary victim user, undermining any downstream logic or review process that trusts `aborted_by`/`lock_author`/`merge_requested_by` as a legitimate, verified actor. This does not itself grant a new authorization scope beyond what the token's own `permissions`/`stack_id` already allow (the `ApiClient.check_permissions!` gate in `require_permission!` still applies) — the compromised binding is strictly the actor-attribution one (token vs. user identity), not privilege escalation of the token's own scope. I could not verify within the available context whether any additional downstream authorization decision (e.g., merge-queue eligibility, GitHub team checks) keys off `current_user.authorized?` or team membership in a way that would let this identity spoof escalate into a `Shipit.github_teams` authorization bypass; this would need further investigation of `Stack#trigger_task`, `MergeRequest.request_merge!`'s full body, and `Task#abort!`, which were only partially visible in the indexed context.

### Likelihood Explanation
Any party that has been issued an `ApiClient` token — even one scoped to `read:stack`/minimal permissions on a single stack — can trivially set the `X-Shipit-User` header on any authenticated API request; no additional secret or privilege is required. This makes exploitation straightforward for any authenticated API consumer.

### Recommendation
Do not derive `current_user` from an unauthenticated, client-supplied header. Bind the acting user to the authenticated `ApiClient` itself (e.g., its `creator`), or require a signed/verified assertion of identity (similar to the GitHub OAuth session flow in `GithubAuthenticationController`) before attributing any action to a specific `User` record.

### Proof of Concept
1. Obtain any valid `ApiClient` token scoped to a target stack (e.g., with only `deploy:stack` permission).
2. Send `PUT /:stack_id/tasks/:id/abort` (or `POST /:stack_id/tasks/:definition_id`, `POST /:stack_id/merge_requests/:id`, etc.) with HTTP Basic Auth using that token and header `X-Shipit-User: <victim-login>`.
3. Observe that the resulting `Task#aborted_by` (or `lock_author`, `merge_requested_by`) is set to the victim `User`, as confirmed by `test/controllers/api/tasks_controller_test.rb:118-126`, even though the victim never made the request and the token was never issued to them.
