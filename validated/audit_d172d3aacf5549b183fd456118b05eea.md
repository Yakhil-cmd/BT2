This confirms the key gap: `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb`) looks up commits purely by `Commit.where(sha: params.sha)` — global, with no repository/organization scoping at all — while `Shipit.github(organization:)` (`lib/shipit.rb:170-181`) selects an entirely separate, per-organization `GitHubApp`/webhook secret keyed only by the attacker-controlled `repository_owner` value read from the same unverified JSON body before verification occurs.### Title
Cross-organization webhook authentication confusion allows forged commit statuses and stack sync via mismatched signature-selection vs. lookup fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The webhook signature check in `WebhooksController#verify_signature` selects **which** organization's `webhook_secret` to validate against using an attacker-supplied, unverified field (`repository.owner.login` / `organization.login`) taken from the very payload being verified, but the downstream `Webhooks::Handlers` never confirm that the record they act on (`Commit`, `Repository`, `Stack`, `Team`) actually belongs to that same organization. This breaks the intended binding `signing_organization == acted_upon_organization`.

### Finding Description
`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) is read directly from the JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` (`lib/shipit.rb:170-181`) picks a per-organization `GitHubApp` config/secret from `secrets.github` based purely on this attacker-controlled string; a request for any organization configured on the Shipit instance (multi-tenant `secrets.github` schema) is verified only against **that** organization's secret. [3](#0-2) 

Once verification succeeds, the raw JSON is dispatched to `Webhooks::Handlers` (`app/controllers/shipit/webhooks_controller.rb:10-15`) which perform lookups against **completely independent** fields of the same payload:
- `StatusHandler#process` looks up commits globally with no organization/repository scoping at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`). [4](#0-3) 
- `PushHandler`/generic `Handler#stacks` resolve the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), a field never cross-checked against `repository_owner`. [5](#0-4) 

Because `X-Hub-Signature`/`verify_signature` only proves "this payload was signed by organization X's secret," and nothing enforces `repository.owner.login == repository.full_name`'s organization prefix or that `Commit.sha` belongs to organization X, an operator who legitimately controls (and knows the `webhook_secret` for) one configured organization on a multi-org Shipit instance can forge a webhook body that:
- Sets `organization.login` / `repository.owner.login` to their own controlled org (so `verify_signature` succeeds using a secret they legitimately possess), while
- Setting `repository.full_name` to a victim repository belonging to a *different* organization configured on the same instance, or
- Setting `sha` in a `status` event to the SHA of any commit that exists anywhere in the Shipit database (`StatusHandler` has zero repository scoping).

This is directly analogous to the reported bug class: a value is *acted upon* (the org used to select the signing key vs. the org/repo the event is applied to) without the two being bound together, exactly as `transfer`'s return value was never checked against the intended lock-step invariant between "funds sent" and "event emitted."

### Impact Explanation
The most severe reachable consequence is via `StatusHandler`: any org whose `webhook_secret` the attacker knows (their own legitimately-configured org, or an org left with `webhook_secret: nil`, which causes `verify_webhook_signature` to `return true unless webhook_secret` and thus skip verification entirely, per `lib/shipit/github_app.rb:76-83`) can forge a `status` webhook event for **any commit SHA in the entire Shipit database**, regardless of which real repository/organization it belongs to. This lets an attacker inject a fabricated "success" `CommitStatus`, which the merge/deploy gating logic (`merge_status`/`deployable_status`, `app/models/shipit/merge_request.rb`, `app/models/shipit/stack.rb`) can treat as a legitimate CI result, satisfying required-status checks for a merge or deploy the attacker does not otherwise have permission to trigger — an unauthorized deploy/merge, which falls under the "Critical" impact category. [6](#0-5) 

Secondary impact: `MembershipHandler` creates/deletes `Team`/`Membership` rows keyed by `params.team.id`/`params.organization.login` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`) without confirming the signing organization matches `params.organization.login`, letting a cross-org forgery manipulate team membership records used by `Shipit.github_teams` authorization. [7](#0-6) 

### Likelihood Explanation
Requires: (a) the deployment to use the multi-organization `secrets.github` schema (documented and supported, `config/secrets.development.shopify.yml`), and (b) the attacker to legitimately control at least one configured organization's webhook secret (e.g., an org admin who set up their own GitHub App installation on the shared Shipit instance) or to find one org configured without a `webhook_secret`. This is plausible in any Shipit instance shared across multiple teams/organizations, which is exactly the use case the multi-org config schema is built for.

### Recommendation
- In `WebhooksController#verify_signature`, after signature verification succeeds, re-derive the organization strictly from the verified `repository_owner`/`organization.login` and pass it explicitly into every handler; reject events where `repository.full_name`'s owner segment, or the commit/team's actual owning repository, does not match the organization whose secret validated the signature.
- Scope `StatusHandler#process`'s `Commit.where(sha: params.sha)` lookup to commits belonging to stacks/repositories owned by the verified organization instead of a global, unscoped SHA lookup.
- Scope `MembershipHandler`'s team lookups/creation to the verified organization as well.
- Treat organizations with a blank/nil `webhook_secret` as unconfigured for `verify_webhook_signature`, rather than defaulting to unconditionally trusted (`return true unless webhook_secret`).

### Proof of Concept
1. Multi-org Shipit instance configured with `secrets.github` containing `orgA` (attacker controls this org's app installation and thus knows its `webhook_secret`) and `orgB` (victim org, hosts the target `Stack`/`Commit`).
2. Attacker crafts a `status` event body:
   ```json
   {
     "sha": "<sha of a real commit belonging to orgB's stack>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/decoy-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, body)` and POSTs to `/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")`, whose secret matches, so `verified` is `true` — despite the event being applied to a commit that belongs to `orgB`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (global, unscoped) and calls `create_status_from_github!` on the matching commit in `orgB`'s stack, injecting a forged "success" status that can satisfy merge/deploy gating for that stack.
