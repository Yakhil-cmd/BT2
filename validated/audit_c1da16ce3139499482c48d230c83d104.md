### Title
Webhook signing organization is never cross-checked against the target `repository.full_name`, allowing cross-repository writes across tenants - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification purely from the `repository.owner.login` field of the untrusted JSON body (falling back to `organization.login` only if `repository` is absent): [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This value is used only to look up `Shipit.github(organization: repository_owner)` and verify the raw payload's HMAC against that organization's `webhook_secret`. Nothing ties this "authenticated organization" to the actual repository the event handlers subsequently act on. Handlers (e.g. `PushHandler`, `CheckSuiteHandler`) determine the target repository from an entirely separate field in the very same JSON body: `repository.full_name`, via `Handler#repository_name` / `Handler#stacks`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

and [4](#0-3) 

`repository.owner.login` (used for signature/authentication) and `repository.full_name` (used to select the target `Stack`) are independent, attacker-controlled JSON fields with no cross-validation. In a genuine GitHub payload these are always consistent, but nothing in this engine enforces that consistency for a forged payload.

**The broken binding, as an equality that is never checked:**
`repository_owner` used by `verify_signature` to select the authenticating organization **≠** the owner encoded in `repository.full_name` used by `Handler#stacks` to select the repository that is written to.

### Impact Explanation
In any multi-organization Shipit deployment (the engine explicitly supports multiple GitHub Apps/orgs, see `Shipit.github(organization:)` and `test/dummy/config/secrets_double_github_app.yml`), an attacker who is able to obtain or forge a valid signature for **any one** configured organization's webhook secret (e.g., an org they legitimately administer and configured to send webhooks to the shared Shipit instance) can craft a payload where:
- `repository.owner.login` = their own organization (so `verify_signature` picks their own known secret and the HMAC passes), and
- `repository.full_name` = `"other-org/other-repo"` (an unrelated tenant's repository tracked by the same Shipit instance).

Before the attack: only GitHub, holding the org-specific webhook secret for `other-org`, can produce events that make `PushHandler` call `stack.sync_github(expected_head_sha: ...)` for `other-org`'s stacks.
After the attack: an operator who only controls `their-org`'s webhook secret can forge a `push` event naming `other-org/other-repo` in `repository.full_name`, still passing signature verification (because it's checked against `their-org`'s secret, matched via `repository.owner.login`), and trigger `GithubSyncJob` for `other-org`'s stack with an attacker-chosen `expected_head_sha`. Because `Stack#continuous_delivery` and `CacheDeploySpecJob` react to newly synced commits, this can be used to influence which commit `other-org`'s stack considers deployable/latest, causing a cross-tenant, cross-repository state change without any credential belonging to `other-org`. This breaks the organization-authenticated-vs-repository-written trust binding and matches the High/Critical impact class of cross-repository writes / unauthorized deploy triggering.

### Likelihood Explanation
Requires the attacker to control (or forge signatures for) at least one organization/app configured on the shared Shipit instance — a realistic scenario for any multi-tenant deployment where different teams/orgs each configure and manage their own GitHub App/webhook secret pointed at a shared Shipit installation. No Shipit session, `ApiClient` token, or GitHub repository write access to the victim's repository is required — only knowledge of one (possibly unrelated) organization's webhook secret.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after verifying the signature, cross-check that `repository.owner.login` (the organization used to select the verifying secret) matches the owner segment parsed from `repository.full_name` before dispatching to handlers; reject the request (422) on mismatch. Equivalently, have `Handler#repository_name`/`Handler#stacks` derive the repository strictly from `repository.owner.login` + `repository.name`, rather than trusting the independent `full_name` field.

### Proof of Concept
Given two organizations configured in Shipit, `victim-org` (with stacks the attacker does not control) and `attacker-org` (whose GitHub App webhook secret the attacker knows because they administer that org's App):

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC computed with attacker-org's webhook_secret over the exact body below>

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-that-exists-on-victim-org-repo>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```

- `WebhooksController#repository_owner` returns `"attacker-org"`.
- `verify_signature` calls `Shipit.github(organization: "attacker-org").verify_webhook_signature(...)`, which succeeds because the attacker signed the body with `attacker-org`'s real secret.
- `PushHandler#process` calls `stacks` → `Handler#repository_name` returns `"victim-org/victim-repo"` → `Repository.from_github_repo_name("victim-org/victim-repo")` resolves to the victim's `Repository`/`Stack`.
- `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` is enqueued via `GithubSyncJob` for the victim's stack, even though the attacker never authenticated as, or was authorized by, `victim-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
