### Title
Unhandled exception during AA trigger processing leaves the `aa_triggers` mutex lock permanently held, freezing all future AA trigger execution — ([File: mutex.js], [File: aa_composer.js])

### Summary
`mutex.js`'s lock implementation marks a key as "locked" and relies exclusively on the locked callback later invoking `unlock()` to release it — there is no `try/catch`/`finally` around the protected work. If the protected function throws synchronously (or an inner async callback throws before reaching its `unlock()` call), the key stays in `arrLockedKeyArrays` forever. `aa_composer.js`'s `handleAATriggers()` locks the global `'aa_triggers'` key for the duration of processing *all* pending AA triggers, and the code path from `handlePrimaryAATrigger` → `handleTrigger` → `handleSecondaryTriggers`/`validateAndSaveUnit` contains multiple `throw Error(...)` statements that fire before `unlock()`/`onDone()` are reached. This is directly analogous to the reported Linux kernel bug: `HCI_UART_SENDING` is a "busy" bit that is not cleared when the protected work is aborted instead of completing normally, permanently blocking future work. Here, the `'aa_triggers'` mutex key is the equivalent "busy" flag.

### Finding Description
`mutex.js`'s `exec()` pushes the lock key onto `arrLockedKeyArrays` and calls `proc(unlock)`, with `release()`/deletion of the entry happening only inside the `unlock` callback: [1](#0-0) 

There is no protection against `proc` throwing before it calls `unlock`. `handleAATriggers()` in `aa_composer.js` acquires this lock for the `'aa_triggers'` key and only releases it in the final callback of `async.eachSeries`: [2](#0-1) 

Processing of each trigger flows into `handlePrimaryAATrigger` → `handleTrigger`, whose call chain (secondary-trigger handling, `validateAndSaveUnit` for the response unit, and various error-path assertions such as `handleSecondaryTriggers`'s `"secondary triggers while bouncing"` and `validateAndSaveUnit`'s `"nonserial AA"`) is guarded only by defensive `throw Error(...)` statements, not `try/catch`: [3](#0-2) [4](#0-3) 

If any of these paths throws — e.g. because the AA response unit built for the trigger ends up non-serial (`sequence !== 'good'`) due to interaction between concurrent/secondary triggers touching the same AA balance/inputs, or another of the "should never happen" assertions actually fires for a specific, adversarially crafted trigger/AA-definition combination — the exception propagates out of the `db.query`/`async.eachSeries` callback chain *before* `unlock()` in `handleAATriggers` is ever called. Because `mutex.exec` has no cleanup on exception, the `'aa_triggers'` key remains locked in `arrLockedKeyArrays` forever, exactly like the kernel leaving `HCI_UART_SENDING` set after `write_work` is canceled instead of completing.

The same unprotected pattern also underlies `assocUnitsInWork` in `network.js`, where `handleJoint` sets `assocUnitsInWork[unit] = true` on entry and depends on every single validation/callback branch to explicitly `delete` it; several branches (e.g. defensive `throw Error("ifNeedHashTree() unsigned")`, `throw Error("ifOk() unsigned")`) can bypass that deletion on exception, permanently blocking any future handling of that specific unit: [5](#0-4) [6](#0-5) 

### Impact Explanation
Because `'aa_triggers'` is a single, global mutex key covering *all* AA trigger execution on the node, once it is stuck locked:
- `mutex.lock(['aa_triggers'], ...)` calls from any subsequent stabilization event queue up forever and are never executed (see `mutex.handleQueue`/`isAnyOfKeysLocked`): [7](#0-6) 
- No further AA triggers are ever processed by that node — funds sent to any AA become permanently unprocessed/frozen from that node's perspective, and the node's AA state permanently diverges from the rest of the network (a node-disagreement-on-validity/stability condition), since `writer.saveJoint` invokes `aa_composer.handleAATriggers()` after every stabilization that includes AA triggers: [8](#0-7) 

This satisfies "AA fund loss or freezing" and "node disagreement on validity or stability" from the validation criteria, and is reachable purely from posting an ordinary unit that becomes an AA trigger — no privileged/hub/peer role required.

### Likelihood Explanation
The exact reachability of one of the internal `throw` assertions from externally-supplied trigger data requires careful crafting (e.g., causing the AA's own response unit to be judged non-serial via racing/overlapping secondary triggers), so it is not trivially reproducible with a single simple transaction, but the structural defect — no exception safety around `mutex.exec`/`handleAATriggers` — is unconditional and any one throw anywhere in the long trigger-processing chain (which spans formula evaluation, DB writes, and secondary AA calls) is sufficient to trip it permanently.

### Recommendation
Wrap the protected callback execution in `mutex.js`'s `exec()` in a `try/finally` (or catch-and-rethrow-after-release) so that `release(arrKeys)` (and `handleQueue()`) always runs even if `proc` throws or an inner async step throws unexpectedly. Additionally, wrap `handleAATriggers`'s per-trigger processing (`handlePrimaryAATrigger`/`handleTrigger`) in defensive error handling so that a failure in one trigger cannot leave the `'aa_triggers'` lock (or `assocUnitsInWork[unit]` in `network.js`) permanently held; any unexpected error should still result in `unlock()` being called (optionally after logging/quarantining the offending trigger) rather than deadlocking the whole subsystem.

### Proof of Concept
Conceptual reproduction:
1. Deploy an AA whose secondary-trigger fan-out or response composition can be driven, via a crafted primary trigger unit, into the `"nonserial AA"` assertion path in `validateAndSaveUnit` (`aa_composer.js:1822-1836`) or the `"secondary triggers while bouncing"` path (`aa_composer.js:1717-1719`) — e.g. by arranging overlapping AA-to-AA secondary triggers that compete for the same AA balance/UTXOs within one `handleAATriggers()` pass.
2. Post the triggering unit; once it stabilizes, `writer.saveJoint` calls `aa_composer.handleAATriggers()`, which acquires the `'aa_triggers'` mutex and begins iterating triggers.
3. When processing the crafted trigger throws inside the `handleTrigger` call chain before reaching `unlock()`/`onDone()` in `handleAATriggers`, `mutex.exec`'s pushed lock entry for `['aa_triggers']` is never removed.
4. Post any subsequent unit that stabilizes and would normally trigger `handleAATriggers()` again — verify (e.g., via `mutex.getCountOfLocks()`/`isAnyOfKeysLocked(['aa_triggers'])`) that it is queued forever and never executes, confirming all future AA trigger processing on the node is permanently frozen.
