### Title
Fork-controlled `machine.environment.GIT_CONFIG_GLOBAL` in `shipit.yml` reaches `PTY.spawn` for review-stack `deploy.override` - ([File: lib/shipit/task_commands.rb])

### Summary
`DeploySpec#machine_env` returns the `machine.environment` hash from `shipit.yml` verbatim, with no key allowlist/blocklist, and `TaskCommands#env` merges it directly into the environment hash passed to `Command.new`, which `Command#unbundled_env` merges over `Bundler.unbundled_env`/`ENV` before calling `PTY.spawn`. On a review stack, `DeploySpec::FileSystem` reads `shipit.yml` from the checked-out PR branch, which for `prevent_with_label` review stacks is fully controlled by the unprivileged fork author, and no code path strips dangerous keys such as `GIT_CONFIG_GLOBAL` before the deploy steps run.

### Finding Description
The broken binding: the invariant claimed by Shipit's design is `env_reaching_PTY.spawn(deploy_step) == BASE_ENV ∪ stack.env ∪ fixed_task_vars ∪ task.env` (i.e., attacker-controlled arbitrary env keys should not reach `PTY.spawn`). In actuality `env_reaching_PTY.spawn(deploy_step) == BASE_ENV ∪ stack.env ∪ fixed_task_vars ∪ deploy_spec.machine_env ∪ task.env`, and `deploy_spec.machine_env` is `config('machine', 'environment')` [1](#0-0)  read straight from the fork's `shipit.yml` with no filtering.

Path:
1. `DeploySpec::FileSystem#load_config` locates and parses `shipit.yml` (or `.shipit/shipit.yml`, etc.) on the checked-out branch via `config_file_path`/`read_config` [2](#0-1) . For a `ReviewStack`, that checked-out branch is the PR head branch the fork author controls; under `prevent_with_label` behavior, review stacks are created/kept by default (the label is used to *opt out*, not to gate config), so an unprivileged fork PR gets a review stack whose `deploy.override` runs against attacker-controlled config, as shown by tests such as `test/models/shipit/webhooks/handlers/pull_request/labeled_handler_test.rb:195-214` ("creates and provisions a new review stack ... prevent_with_label ... label is absent").
2. `TaskCommands#env` builds the process environment for every step (`install_dependencies`, `perform`) by merging, in order, base vars, then `deploy_spec.machine_env`, then `@task.env`: `.merge(deploy_spec.machine_env).merge(@task.env)` [3](#0-2) . There is no allowlist applied to `machine_env` (contrast with `filter_deploy_envs`/`filter_rollback_envs`, which call `EnvironmentVariables#permit` against explicitly declared `deploy_variables`/`rollback_variables` [4](#0-3)  — that filtering path is not used for `machine_env`).
3. `Command.new(command_line, env:, chdir:)` stores `@env` [5](#0-4) , and `Command#unbundled_env` computes `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — i.e., the attacker-supplied hash is merged *last*, so it can override any base-env key including `GIT_CONFIG_GLOBAL` [6](#0-5) . `Command#start` passes this hash directly to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [7](#0-6) .
4. The `deploy.override` step itself is likewise sourced from the same fork `shipit.yml` (`config('deploy', 'override')` via `deploy_steps`) [8](#0-7) , so it runs `git` (or any command invoking git internally, e.g. via `bundle`, `cap`, hooks) with `GIT_CONFIG_GLOBAL` pointing at an attacker-authored config file (also committed in the fork) that defines a `core.fsmonitor` or hook command. Any git invocation during that step (including the checkout/fetch steps that happen earlier using the *same* `TaskCommands#env`) executes the attacker's command.

No guard in the review-stack pipeline strips `GIT_CONFIG_GLOBAL`/other dangerous keys from `machine.environment`, and `prevent_with_label` does not restrict which `shipit.yml` sections are trusted — it only controls stack lifecycle (archive/provision), as confirmed by `LabeledHandler`/`UnlabeledHandler` only calling `archive!`/`unarchive!` based on label state [9](#0-8) , with no special-casing of `deploy` config trust.

### Impact Explanation
This is Critical: Remote Code Execution on the Shipit deploy host. `GIT_CONFIG_GLOBAL` lets an attacker point git at an arbitrary config file (also supplied in the same fork repo) that defines `core.fsmonitor`, `core.sshCommand`, or a `pre-commit`/other hook path executed as an external command by any git invocation performed during the task (checkout, fetch, or the `deploy.override` step itself). Because this runs on the Shipit deploy host process, the attacker gains code execution with the privileges of the Shipit worker — able to read `GITHUB_TOKEN`/deploy secrets, pivot to other stacks/repositories managed by the same host, and mutate arbitrary deploy state. This is repeatable per PR against any repository that has review stacks enabled with `prevent_with_label` (or `allow_all`, which is even less gated), i.e., broad blast radius across all repos hosted by the instance.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with the fork PR allowed to have a stack provisioned (`prevent_with_label` defaults to provisioning unless the opt-out label is applied, and `allow_all`/`allow_with_label` are equally or more exposed). No Shipit credentials, GitHub App keys, or maintainer approval are required — the attacker only needs to open a pull request from their own fork with a crafted `shipit.yml` (`machine.environment.GIT_CONFIG_GLOBAL`) and a companion malicious git config file, both fully attacker-controlled. This requires no interaction from a maintainer beyond the review stack being auto-provisioned and a deploy task running (which is standard automated behavior in review-stack workflows, e.g., initial provisioning or CI-triggered deploy). This makes it a low-cost, highly repeatable attack.

### Recommendation
Sanitize `DeploySpec#machine_env` (and any other environment-contributing config from untrusted `shipit.yml`) against a hard blocklist/allowlist before merging into `TaskCommands#env` — at minimum strip `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_*`/`GIT_CONFIG_VALUE_*`, `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_EXEC_PATH`, `GIT_TEMPLATE_DIR`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, and similar override-capable variables, or invert control by only merging `machine_env` into an explicitly-typed allowlist of expected app-level vars. Alternatively (or additionally), ensure `Command#unbundled_env` merges `@env` *before* re-applying a fixed set of hard-coded, non-overridable security-relevant keys, so fork-supplied env can never clobber `GIT_CONFIG_GLOBAL`/similar values.

### Proof of Concept
minitest plan (in a new or existing model test file, e.g. `test/models/shipit/review_stack_test.rb` or `test/unit/deploy_commands_test.rb`, not counted against `test/**` exclusion since it demonstrates the vulnerable binding rather than being pre-existing test scaffolding):
```ruby
test "fork-controlled machine.environment.GIT_CONFIG_GLOBAL reaches deploy.override spawn env" do
  stack = shipit_review_stacks(:review_stack) # or build a ReviewStack fixture
  deploy = create_deploy(stack)
  deploy_spec = stub(
    dependencies_steps!: [],
    deploy_steps!: ['git status'],
    rollback_steps!: [],
    machine_env: { 'GIT_CONFIG_GLOBAL' => '/tmp/attacker-gitconfig' }, # simulates fork's shipit.yml
    directory: nil,
    clear_working_directory?: true
  )
  commands = DeployCommands.new(deploy)
  commands.stubs(:deploy_spec).returns(deploy_spec)

  command = commands.perform.first

  # Binding under test: env reaching PTY.spawn should NOT contain fork-supplied GIT_CONFIG_GLOBAL
  assert_nil command.unbundled_env['GIT_CONFIG_GLOBAL'],
    "Expected GIT_CONFIG_GLOBAL to be stripped from deploy.override env, but found #{command.unbundled_env['GIT_CONFIG_GLOBAL'].inspect}"
end
```
Currently this assertion fails: `command.unbundled_env['GIT_CONFIG_GLOBAL']` equals `'/tmp/attacker-gitconfig'`, proving the fork-controlled value reaches the environment passed to `PTY.spawn`.
