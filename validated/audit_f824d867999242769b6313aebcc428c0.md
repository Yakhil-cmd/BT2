### Title
Webhook Signature Verified Against Attacker-Chosen Organization While Handler Acts on a Different Repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the request signature against using a field taken directly from the unauthenticated JSON payload (`repository.owner.login`), while the event handlers that subsequently act on the payload (e.g. `PushHandler`) resolve the target `Repository`/`Stack` using a *different* field from the same payload (`repository.full_name`). Nothing binds these two fields together, so a caller who legitimately possesses the `webhook_secret` for one configured GitHub organization can forge a validly-signed request whose `repository.full_name` points at a repository belonging to a completely different organization configured on the same Shipit instance.

### Finding Description
`verify_signature` computes the organization used for HMAC verification straight from request body content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization config block (`webhook_secret`, `app_id`, etc.) documented for multi-org deployments: [3](#0-2) 

Each organization can have its own distinct `webhook_secret`, known to whoever created/administers that GitHub App for that org (it is entered by hand when creating the App, per `docs/setup.md`). This means a legitimate administrator of Org A's Shipit GitHub App knows Org A's `webhook_secret` and is fully able to compute a valid `X-Hub-Signature` for arbitrary payload bytes.

Once `verify_signature` passes, `WebhooksController#create` dispatches the same raw payload to handlers: [4](#0-3) 

Handlers such as `PushHandler` never re-derive or re-check the organization used to verify the signature. They resolve the target repository purely from `repository.full_name`: [5](#0-4) [6](#0-5) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository) are two independent, attacker-controlled JSON fields inside the same POST body, an attacker who legitimately controls Org A's webhook secret can sign a body where `repository.owner.login = "orgA"` but `repository.full_name = "orgB/victim-repo"`. The signature check passes (it only cares that the bytes match Org A's HMAC), and the `PushHandler` then acts on `orgB`'s stack — an organization the attacker has no relationship with. This breaks the intended binding: `organization that authenticated == repository that is written`.

### Impact Explanation
A successful forgery lets an entity that only administers one configured GitHub organization's App trigger `GithubSyncJob` (via `stack.sync_github`) against another organization's stacks, and equally reach every other webhook handler keyed off `repository.full_name`/`params.repository.full_name` (pull request opened/labeled/unlabeled/reopened/edited/assigned handlers, review-stack provisioning, PR archiving/unarchiving) for repositories belonging to a different, unrelated organization on the same instance. Where continuous deployment/review-stack provisioning is configured, this can result in an unauthorized sync that seeds an unintended deploy pipeline or provisions/archives review stacks for a repository the caller does not own — a cross-repository/cross-organization action performed without the victim organization's consent. This lands in the High/Critical impact classes defined for this scan (escalation across organization boundaries, unauthorized stack actions) because it is a boundary a Shipit operator explicitly relies on when hosting multiple organizations' repos on one instance.

### Likelihood Explanation
This requires an attacker who already legitimately controls a `webhook_secret` for at least one organization configured in `config/secrets.yml` — a realistic scenario for any Shipit deployment that follows the documented multi-organization setup (`docs/setup.md` "Using Multiple Github Applications"), since each org's GitHub App creator independently knows that org's secret and has no operational reason to trust other orgs on the same Shipit host. No GitHub-side webhook delivery is even required — the attacker can POST directly to Shipit's public `/webhooks` endpoint with a self-computed signature. Likelihood is therefore concrete/practical specifically for multi-org Shipit installations.

### Recommendation
Bind the verified organization to the repository actually acted upon: after `verify_signature` resolves `repository_owner`, `WebhooksController` should pass or expose the verified organization to `Shipit::Webhooks.for_event`, and each handler should validate that `Repository.from_github_repo_name(payload.dig('repository','full_name'))`'s owner matches the organization used to verify the signature before performing any operation, rejecting the request (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per the documented multi-org config).
2. As the administrator of `orgA`'s GitHub App (who knows `orgA`'s `webhook_secret`), craft a JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, body)` and POST it with `X-Github-Event: push` directly to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and validates successfully against the attacker-known secret.
5. `PushHandler` resolves `Repository.from_github_repo_name("orgB/victim-repo")` and enqueues `GithubSyncJob` for `orgB`'s stack, even though the attacker never authenticated as, nor was authorized by, `orgB`.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
