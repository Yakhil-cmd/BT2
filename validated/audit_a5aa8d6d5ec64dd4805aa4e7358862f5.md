### Title
`is_valid_signed_package()` verifies only the signer's address, not the network/chain the signed package was created for, enabling cross-network signature replay in AA logic - (File: formula/evaluation.js)

### Summary
The `onlyConnext` bug is a missing-domain-check pattern: a permissioned entry point authenticates the caller (`msg.sender == connext`) but never binds the check to the origin domain/chain it was intended for, so a message from any domain is accepted as if it came from the expected one. The analogous primitive in ocore is `is_valid_signed_package()`, used inside AA (Autonomous Agent) oscript logic to authenticate off-chain signed messages (e.g., payment-channel updates, order-book orders). It verifies the signature and the signer address, but the hash-to-sign construction (`object_hash.getSignedPackageHashToSign`) contains no network/chain identifier, so a validly signed package produced for one Obyte network (e.g. testnet) verifies successfully when replayed against another network (e.g. mainnet) sharing the same address/keys, or reused for a different purpose than originally intended if the AA doesn't independently bind extra context.

### Finding Description
`is_valid_signed_package` is evaluated in `formula/evaluation.js`: [1](#0-0) 

It only checks:
- the structural fields of the package (`signed_message`, `last_ball_unit`, `authors`, `version`),
- that `last_ball_unit` is a stable, on-MC unit,
- and delegates signature verification to `signed_message.validateSignedMessage`.

`validateSignedMessage` checks the author address, definition-to-address binding, and the authentifiers against the definition: [2](#0-1) [3](#0-2) 

The actual bytes that get signed are produced by `getSignedPackageHashToSign`, which hashes the package contents (`signed_message`, `authors` without authentifiers, `last_ball_unit`, `version`) with no domain separator identifying which ocore network (mainnet vs. testnet, or any future alternative network sharing the same codebase) the signature is valid for: [4](#0-3) 

Unlike full DAG units, which are network-bound indirectly through `witness_list_unit`/genesis-derived parent chains that differ per network, a signed package is a free-standing off-DAG object whose hash-to-sign has none of that context. The only fields tying it to a specific deployment are `channel`/`period`-like application fields that individual AA authors may *choose* to embed inside `signed_message` (as seen in the payment-channel and order-book samples), analogous to how a Connext-receiving contract could manually check `_origin` itself only if it remembers to. The primitive itself provides no enforced binding.

Sample AAs demonstrate the pattern of manually trying to scope a signed package to "this channel" via `signed_message.channel != this_address`: [5](#0-4) 

But this is an AA-author convention, not something `is_valid_signed_package` enforces. If an AA author (or a generic signing flow such as wallets that expose a general-purpose "sign message" feature) does not embed such a scoping field, or embeds only an address/period without a network id, then:
- A signature produced by a user for use in one context (one AA, one network) can be replayed by anyone against a different context that only checks the same address and a coarse condition (e.g., amount/price fields) as in `order_book_exchange.oscript`'s order matching, which checks address/asset/price fields inside `signed_message` but nothing globally unique to the deployment network.
- Because `signMessage()` in `signed_message.js` does not embed any network identifier into the signed content either: [6](#0-5) 

there is no core-level guarantee that a signature intended for testnet cannot be replayed on mainnet (or vice versa) for any AA that relies solely on `is_valid_signed_package(package, address)` plus attacker-influenced/coarse fields in `signed_message`, mirroring the missing-origin-domain check in the `onlyConnext` modifier.

### Impact Explanation
An AA that uses `is_valid_signed_package` to authorize a state change (fund release, order execution, channel closure) without independently embedding a network/domain-unique nonce in the signed content can have its off-chain signed authorizations reused in an unintended context. This can lead to unauthorized fund movement or double execution of an authorization if the AA's own scoping fields (e.g., `channel`, `period`) are insufficiently unique or omitted, causing AA fund loss.

### Likelihood Explanation
Exploitability depends entirely on each individual AA's oscript logic: AAs that faithfully bind `channel`, `period`, `order-id` (as shown in the two sample AAs) are not exploitable this way. However, since the vulnerability lives in the *primitive* (`is_valid_signed_package`/`getSignedPackageHashToSign`), any AA author who assumes the primitive already binds signatures to "this network" or "this specific purpose" (analogous to assuming `onlyConnext` already checks origin) can ship an exploitable AA. This is a design-level gap rather than a guaranteed live exploit in a specific shipped AA, so likelihood is best characterized as Medium — real, but conditional on how AA authors use the primitive.

### Recommendation
Include a network/domain separator (e.g., `constants.version`'s associated network genesis unit or an explicit `alt`/network id) in `getSignedPackageHashToSign`'s hashed content, or require `is_valid_signed_package` callers to pass and internally verify an expected `home_network`/context id field that is mandatory in every signed package, so that a signature cannot be verified successfully outside the network/context in which it was created — mirroring the recommended fix of checking `_origin` in `onlyConnext`.

### Proof of Concept
Conceptual PoC (cannot be fully executed without two live ocore networks sharing address-derivation compatible keys, but the code path is directly traceable):
1. A user signs a message with `signMessage()` on network A (e.g. testnet) authorizing "pay X to Y", intending it only for an AA on network A that calls `is_valid_signed_package(pkg, signer_address)`. [6](#0-5) 
2. Because `getSignedPackageHashToSign` never mixes in a network-specific value, the exact same `signedPackage` object verifies as `true` when evaluated by `is_valid_signed_package` inside an AA with the same design deployed on network B (e.g. mainnet), or inside an unrelated AA on the same network that also expects "X to Y" style content but doesn't independently constrain the package to itself. [1](#0-0) [4](#0-3) 
3. Any AA relying on this primitive without its own strict context binding (unlike the two audited sample AAs) authorizes an action the signer did not intend for that context, causing unauthorized fund movement from the AA.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
