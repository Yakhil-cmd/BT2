### Title
Fork-controlled `machine.environment` in `shipit.yml` overrides the hard-coded `BUNDLE_PATH`, letting a PR redirect bundler on the deploy host - ([File: lib/shipit/task_commands.rb])

### Summary
`TaskCommands#env` sets a safe, hard-coded `BUNDLE_PATH` and then unconditionally merges `deploy_spec.machine_env` on top of it, and `machine_env` is read verbatim from the repository's `shipit.yml` (`config('machine', 'environment')`). For a `ReviewStack` on a repository configured with `provisioning_behavior = allow_all`, that `shipit.yml` is read from the untrusted PR branch, so a fork PR author can set `BUNDLE_PATH` in `machine.environment` and have it override the safe default before it reaches `PTY.spawn`.

### Finding Description
Broken binding: the code assumes `command.env['BUNDLE_PATH'] == Rails.root.join('data', 'bundler').to_s` for every task/deploy command. In fact:

- `DeploySpec#machine_env` returns `config('machine', 'environment') || {}` with no filtering: [1](#0-0) 

- `TaskCommands#env` builds the hash used for all task commands (`install_dependencies`, `perform`, and by extension `DeployCommands#env`) by setting `BUNDLE_PATH` to the safe default and then merging `deploy_spec.machine_env` *after* it: [2](#0-1) 

  Because `.merge` on a `Hash` lets later keys win, any `BUNDLE_PATH` entry under `machine.environment` in the fork's `shipit.yml` silently replaces the hard-coded safe path.

- `DeployCommands#env` (used for the `deploy` steps derived from `deploy.override`/discovery) simply calls `super`, inheriting this same merge order: [3](#0-2) 

- The resulting hash is passed as `@env` to `Command.new(..., env:, ...)`, and ultimately reaches the process via `unbundled_env` merged into `PTY.spawn`: [4](#0-3) 

- For a review stack, `DeploySpec::FileSystem` builds this configuration by reading `shipit.yml` from `@task.working_directory`, i.e., the actual checkout of the PR branch's head commit — content fully controlled by the fork PR author. [5](#0-4) 

- The `deploy.variables` mechanism (`DeploySpec#deploy_variables`, `filter_deploy_envs`/`EnvironmentVariables#permit`) only allowlists which env keys a user can pass explicitly when *triggering* a deploy (`@task.env`); it never touches `machine_env`, so it provides no protection here. [6](#0-5) [7](#0-6) 

Existing tests already demonstrate that `machine_env` reaches `command.env` unfiltered: [8](#0-7) 

Attack flow: attacker opens a fork PR against a repository with `review_stacks_enabled = true` and `provisioning_behavior = allow_all`. The PR's `shipit.yml` contains `machine: { environment: { BUNDLE_PATH: <attacker path inside checkout> } }` plus a vendored gem tree at that path with a gem that executes code on `require`/native extension build. `OpenedHandler` creates the review stack for this untrusted branch without any maintainer approval (`allow_all` needs no label): [9](#0-8) 
When the stack's dependency-install/deploy task subsequently runs (`bundle install`, `bundle exec cap ... deploy`, etc.), it uses the attacker's `BUNDLE_PATH`, causing bundler to load/build gems from attacker-supplied code on the Shipit host.

### Impact Explanation
Any command in the review-stack task pipeline that shells out through bundler (`bundle install` in `install_dependencies`, `bundle exec ...` in discovered/overridden `deploy_steps`) executes with a fork-controlled `BUNDLE_PATH`, so bundler resolves and loads gems from an attacker-populated tree, which can execute arbitrary Ruby/native code at `require`/install time on the Shipit host process. This is repeatable on every PR/deploy cycle and confined to the fork PR author's own repository/stack (not cross-tenant), but it directly yields command execution on the deploy host — matching the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" category.

### Likelihood Explanation
Requires only: (1) the target repository has review stacks enabled with `provisioning_behavior = allow_all` (a documented, commonly recommended setting per `docs/review_stacks.md`), and (2) the attacker can open a PR from a fork — no privileged role, token, or secret needed. Cost is a single PR; the vulnerable code path (`TaskCommands#env` merge order) runs on every provisioned/deployed review stack, making it fully feasible and repeatable.

### Recommendation
In `lib/shipit/task_commands.rb`, do not allow `deploy_spec.machine_env` (or any fork-controllable source) to override security-sensitive keys such as `BUNDLE_PATH`, `PATH`, `GIT_ASKPASS`, `GITHUB_TOKEN`, etc. Merge `machine_env` first, then apply the hard-coded/safety-critical keys last (reverse the merge order), or explicitly strip disallowed keys from `machine_env` before merging (e.g., via an allowlist similar to `EnvironmentVariables#permit`, applied to `machine_env` too, not just to task-submitted `@task.env`).

### Proof of Concept
```ruby
# test/unit/deploy_commands_test.rb (new test)
test "machine_env from shipit.yml cannot override BUNDLE_PATH" do
  @deploy_spec.stubs(machine_env: { 'BUNDLE_PATH' => '/tmp/attacker-gems', 'GLOBAL' => '1' })

  command = @commands.install_dependencies.first

  # Binding under test: BUNDLE_PATH must remain the safe default regardless of
  # fork-controlled machine.environment.
  assert_equal Rails.root.join('data', 'bundler').to_s, command.env['BUNDLE_PATH']
end
```
Running this against current code fails: `command.env['BUNDLE_PATH']` equals `/tmp/attacker-gems` because `deploy_spec.machine_env` is merged after the hard-coded default in `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`), confirming the vulnerability.
