### Title
Stack-scoped ApiClient token can read CI status of any stack via `CCMenuController#stack` bypassing token scoping - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor that all other API controllers inherit from `Shipit::Api::BaseController`, replacing the scoped lookup with an unscoped one. This breaks the binding "stack a token authorizes == stack a token can touch": a `read:stack`-permissioned `ApiClient` that is deliberately restricted to a single stack (via `ApiClient#stack_id`) can nonetheless read the CI/deploy status of *any* stack in the Shipit instance simply by passing a different `stack_id` param.

### Finding Description
`BaseController` defines the intended scoping contract: [1](#0-0) 

`stacks` restricts the queryable set to the client's own stack when `ApiClient#stack_id?` is true, and `stack` resolves `params[:stack_id]` only within that restricted relation. Every other API controller (e.g. deploys, rollbacks, tasks) relies on this `stack`/`stacks` pair, so a client scoped to Stack A cannot address Stack B through `params[:stack_id]`.

`CCMenuController`, however, defines its own `stack` method that calls `Stack.from_param!` directly on the unscoped `Stack` model, ignoring `current_api_client.stack_id`: [2](#0-1) 

The controller's only authorization check is `require_permission :read, :stack`, which validates the `read:stack` *permission string* on the client, not which stack it is scoped to: [3](#0-2) 

`ApiClient#stack_id?` (via `stack_id.present?` semantics used elsewhere, e.g. `belongs_to :stack, optional: true`) is the only mechanism that limits a per-stack token to its stack; `CCMenuController` never consults it. As a result, any valid `ApiClient` credential with `read:stack` permission — even one explicitly created with `stack:` set to restrict it to one project (see fixture `here_come_the_walrus` in `test/fixtures/shipit/api_clients.yml`) — can enumerate and read the build/deploy status of every other stack in the instance by iterating `stack_id` values.

### Impact Explanation
This crosses the "stack a token authorizes vs. stack it touches" binding: a token intentionally minted with narrow scope (single stack, read-only) is silently promoted to read CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, `webUrl`) for every stack managed by the Shipit instance, including stacks belonging to other teams/repositories the token holder has no legitimate visibility into. This is an unauthorized read of deploy/task state across stack boundaries, matching the High-severity category "unauthenticated read of stack state, task streams or deploy output" in spirit — here the actor is authenticated as *some* client, but reads state entirely outside the scope it was authorized for, which is the core authorization escalation the class of bug targets. Note: `CCMenuController#show` exposes deploy status metadata only (not source code or secrets), so the blast radius is confined to that read.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token with `read:stack` permission (a routine, low-privilege credential many integrations hold, e.g. the CCMenu client auto-created in `CCMenuUrlController`) and knowledge/guessing of another stack's `to_param` (repo owner/name/environment), which is often predictable or discoverable via the (unscoped) `Stack.all` listing on other endpoints. No webhook secret, GitHub token, or elevated privilege is needed — only a token that was deliberately scoped down to one stack.

### Recommendation
Remove the `CCMenuController#stack` override and use the inherited scoped `stack`/`stacks` helpers from `BaseController` (or explicitly intersect `Stack.from_param!` results with `current_api_client.stack_id` when present) so that a stack-scoped client cannot address stacks outside its `stack_id`.

### Proof of Concept
1. Create two stacks, Stack A (`shopify/private-repo/production`) and Stack B (`shopify/other-repo/production`).
2. Create an `ApiClient` scoped to Stack A only: `ApiClient.create!(creator: user, name: 'ci-bot', stack: stack_a, permissions: ['read:stack'])`.
3. As that client, request:
   `GET /api/stack_a_owner/private-repo/production/ccmenu.xml` — succeeds (expected).
4. Using the same client's token, request:
   `GET /api/other_repo_owner/other-repo/production/ccmenu.xml` — with the current code this also succeeds (200 OK) and returns Stack B's `lastBuildStatus`/`lastBuildLabel`/`lastBuildTime`, even though the token was scoped only to Stack A. This is confirmed by tracing `CCMenuController#stack` (`Stack.from_param!`, unscoped) versus `BaseController#stack` (`stacks.from_param!`, scoped by `current_api_client.stack_id`).
