### Title
CCMenuController#stack bypasses ApiClient stack scoping, allowing a stack-scoped token to read any other stack's CCMenu XML - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController#stack` scopes stack lookups through `stacks`, which restricts resolution to `current_api_client.stack_id` when the client is scoped to a specific stack [1](#0-0) . `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, completely bypassing that scoping check [2](#0-1) . Combined with `require_permission :read, :stack`, which only checks the operation:scope permission string and never compares stack identity [3](#0-2) , a valid `ApiClient` token scoped (via `stack_id`) to stack A can be replayed unchanged against `.../stackB/ccmenu.xml?token=...` and will render stack B's data.

### Finding Description
The intended binding is: `current_api_client.stack_id == resolved_stack.id` whenever `current_api_client.stack_id?` is true (i.e., a token scoped to a specific stack must only be usable to read that stack). This binding is enforced in the generic base controller helper `stacks`/`stack` [1](#0-0) , which every other API controller (`DeploysController`, `LocksController`, `OutputsController`, `RollbacksController`, `StacksController`) relies on for its `stack`/`stacks` lookups.

`Api::CCMenuController`, however, defines its own private `stack` method:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 
This resolves the stack from `params[:stack_id]` against `Stack.all`, never consulting `current_api_client.stack_id`. `authenticate_api_client` is also overridden to accept the token from `params[:token]` (query string) instead of only Basic Auth headers [4](#0-3) , which is how CCMenu URLs (generated by `CCMenuUrlController#fetch`) are designed to work [5](#0-4) .

`require_permission :read, :stack` only calls `check_permissions!(operation, scope)`, which checks that the string `"read:stack"` is in `permissions`, with no reference to any stack at all [3](#0-2) . `ApiClient.authenticate` similarly just verifies the signature and loads the record by id — it does not touch `stack_id` [6](#0-5) .

Exploit flow: an attacker who has legitimately obtained (or been given) a CCMenu URL/token scoped to stack A — e.g., via `GET /ccmenu/*stackA` which creates/returns an `ApiClient` with `read:stack` permission [7](#0-6)  — can take that same `token` query parameter and issue `GET /api/*stackB/ccmenu.xml?token=<A's token>`. Because `CCMenuController#stack` ignores `current_api_client.stack_id`, `Stack.from_param!` resolves stack B unconditionally, and `require_permission :read, :stack` passes since the client still has `read:stack`. The response renders stack B's CCMenu XML instead of a 403.

Note: the current `ApiClient` write paths I could inspect (`ApiClientsController#create_params`, `CCMenuUrlController#client`) do not obviously expose an attacker-controlled way to set `stack_id` themselves via the web UI form (`create_params` only permits `:name` and `permissions`) [8](#0-7) , and `CCMenuUrlController#client` creates a client without an explicit `stack:` association, i.e., unscoped (`stack_id` nil) [7](#0-6) . I was not able to fully confirm every code path where an `ApiClient.stack_id` is populated (e.g., admin-created scoped clients via `belongs_to :stack, optional: true` on the model [9](#0-8) ) within the remaining tool budget. Given `ApiClient` explicitly supports a `stack_id`-scoped mode (as evidenced by `BaseController#stacks`), the code path exists and any client legitimately created/assigned a `stack_id` (e.g., by an operator through some admin flow not fully traced here) is subject to this bypass specifically in the CCMenu controller.

### Impact Explanation
An attacker holding a stack-scoped `read:stack` token can read another stack's CCMenu status/build XML (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) for arbitrary stacks by only changing the URL path, not the token [10](#0-9) . This is an unauthenticated-relative-to-target-stack read of stack state/build status across tenants, matching the "High - unauthorized read of stack state" category. The bug is confined to `CCMenuController`; other API controllers correctly use the scoped `stack`/`stacks` helper from `BaseController` and are not affected.

### Likelihood Explanation
Exploitation requires only possession of one valid `read:stack`-scoped token whose `stack_id` differs from the target — the exact CCMenu-URL model that Shipit itself provides for lightweight, low-privilege integrations (e.g., CI status widgets). No secrets, no GitHub credentials, and no elevated Shipit role are needed beyond having been issued (or having self-obtained, if the token-issuance path allows it) any stack-scoped token; the request itself is a single GET with a swapped path segment, fully repeatable against every stack.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup like the base controller, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so it respects `current_api_client.stack_id` scoping exactly as `BaseController#stack` does, instead of calling `Stack.from_param!` unscoped.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to stack A cannot read stack B's ccmenu xml" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar2"), branch: 'main')

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'Scoped Client',
    stack: stack_a,
    permissions: %w[read:stack],
  )

  assert_equal stack_a.id, scoped_client.stack_id # binding LHS: token authorizes stack A

  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  # binding RHS: request resolves/serves stack B despite token scoped to stack A
  assert_response :forbidden # EXPECTED after fix; currently returns :ok with stack B's XML
end
```
This demonstrates the divergence: `scoped_client.stack_id == stack_a.id` while the request is served for `stack_b`, which the current `CCMenuController#stack` implementation does not prevent.
