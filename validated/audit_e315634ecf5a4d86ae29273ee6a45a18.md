### Title
Unchecked `IERC721.transferFrom` Return in Bridge Allows Unauthorized Cross-Chain Minting and Permanent Asset Loss — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721` calls `IERC721(_tokenAddress).transferFrom(...)` at two critical points without verifying success. The ERC20 bridge path was hardened with `SafeERC20`, but the ERC721 path was not. A registered non-compliant ERC721 token that silently returns instead of reverting on a failed transfer allows: (1) any user to obtain a free cross-chain mint by depositing nothing, and (2) permanent loss of a user's bridged NFT on withdrawal.

---

### Finding Description

`BridgeTransferERC721.requestERC721Transfer` (line 129) and `BridgeTransferERC721.handleERC721Transfer` (line 69) both call `IERC721(_tokenAddress).transferFrom(...)` as a raw external call with no success check:

**Deposit path** (`requestERC721Transfer`, line 129):
```solidity
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
_requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
```
If `transferFrom` silently returns without reverting (non-compliant ERC721), the bridge never receives the token, yet `_requestERC721Transfer` proceeds to emit `RequestValueTransferEncoded` and increment `requestNonce`. The counterpart bridge operators observe the event and call `handleERC721Transfer` on the other chain, releasing or minting the NFT to the attacker.

**Withdrawal path** (`handleERC721Transfer`, line 69):
```solidity
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);

// ...
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
```
All state mutations (nonce advancement, request hash marking, event emission) occur **before** the transfer. If `transferFrom` silently fails, the nonce is consumed and the request is permanently marked handled, but the user never receives their NFT.

By contrast, the ERC20 bridge path explicitly uses `SafeERC20`:

```solidity
// BridgeTransferERC20.sol line 29
using SafeERC20 for IERC20;
// ...
IERC20(_tokenAddress).safeTransfer(_to, _value);       // line 71
IERC20(_tokenAddress).safeTransferFrom(...);            // line 133
```

No equivalent protection exists for ERC721.

---

### Impact Explanation

- **Deposit path**: Any user can call `requestERC721Transfer` with a registered non-compliant ERC721 token. If `transferFrom` silently fails, the bridge emits a valid `RequestValueTransferEncoded` event with a consumed `requestNonce`. Counterpart bridge operators relay this event and mint/unlock the NFT on the other chain. The attacker receives a bridged NFT without depositing anything — **unauthorized cross-chain mint of a bridged asset**.

- **Withdrawal path**: A user's legitimate cross-chain withdrawal is processed by operators via `handleERC721Transfer`. If the token's `transferFrom` silently fails, the bridge nonce is advanced and the request hash is permanently marked as handled, but the NFT is never delivered. The user's asset is permanently locked in the bridge with no recourse — **permanent loss of bridged asset**.

---

### Likelihood Explanation

The trigger requires a registered ERC721 token that does not revert on a failed `transferFrom`. Token registration is controlled by the bridge owner, providing a partial mitigation. However, the ERC721 standard only says `transferFrom` SHOULD throw; it does not mandate it. Non-standard or upgradeable ERC721 tokens (e.g., tokens with pausable transfers that return silently, or tokens with custom access control that silently no-ops) can satisfy this condition. The deposit-path attack is reachable by any unprivileged user once such a token is registered.

---

### Recommendation

Mirror the ERC20 bridge pattern and use `safeTransferFrom` (from OpenZeppelin's `SafeERC721` or equivalent) for all ERC721 transfers, or wrap the calls with a low-level check:

```solidity
// Option 1: use safeTransferFrom (checks onERC721Received and reverts on failure)
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);

// Option 2: low-level call with success check
(bool ok,) = _tokenAddress.call(
    abi.encodeWithSelector(IERC721.transferFrom.selector, address(this), _to, _tokenId)
);
require(ok, "ERC721 transferFrom failed");
```

Additionally, for `handleERC721Transfer`, move the state mutations (nonce update, hash marking) to **after** the transfer succeeds, following a checks-effects-interactions pattern.

---

### Proof of Concept

1. Bridge owner registers a non-compliant ERC721 token `MaliciousNFT` whose `transferFrom` silently returns without reverting and without changing ownership.
2. Attacker calls `bridge.requestERC721Transfer(maliciousNFT, attackerOnOtherChain, tokenId, "")`.
3. `IERC721(maliciousNFT).transferFrom(attacker, bridge, tokenId)` silently no-ops; bridge still owns nothing.
4. `_requestERC721Transfer` passes `onlyRegisteredToken` and `onlyUnlockedToken`, emits `RequestValueTransferEncoded`, increments `requestNonce`.
5. Counterpart bridge operators observe the event and call `handleERC721Transfer` on the other chain.
6. Counterpart bridge mints/unlocks the NFT to `attackerOnOtherChain`.
7. Attacker has received a bridged NFT without depositing the original.
