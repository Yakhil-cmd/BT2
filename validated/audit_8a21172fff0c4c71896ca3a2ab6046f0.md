### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets any repository's status webhook flip CI state on same-SHA commits belonging to other stacks/repositories - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` writes a GitHub status to every `Commit` row that matches the payload `sha`, with no filter on `repository`/`stack`, unlike the generic `Handler#stacks` helper which does scope by `repository.full_name`. Since `sha` is attacker-supplied content shared across repositories only by coincidence of git history/content addressing, and the webhook signature only authenticates that the request came from *some* repository owned by the attacker (via `Shipit.github(organization: repository_owner)`), an attacker who owns a repository can craft a `status` event whose SHA collides with a commit tracked in a victim's stack, causing `Status` records (and thus `deployable?`/merge eligibility) to be written for the victim's commit without any authentication from the victim's repository.

### Finding Description
The broken binding: the code should enforce `status.repository == commit.stack.repository` before writing, i.e. `Commit.where(sha: params.sha, stack: stacks)` — but instead it does `Commit.where(sha: params.sha)` with no stack scoping at all.

Path:
- `Shipit::WebhooksController#create` parses the raw body and dispatches to `Shipit::Webhooks.for_event('status')` → `Handlers::StatusHandler` [1](#0-0) .
- `verify_signature` only checks that the HMAC signature is valid for `Shipit.github(organization: repository_owner)`, i.e. it authenticates that the sender is a legitimate webhook source *for the attacker's own repository* named in the payload — it does not restrict which commits the payload may mutate [2](#0-1) .
- The base `Handler` class defines a `stacks` helper that correctly scopes lookups by `Repository.from_github_repo_name(repository_name)` [3](#0-2) , and other handlers (e.g. push, pull_request) use this repository-scoped lookup.
- `StatusHandler#process`, however, bypasses this scoping entirely and queries the global `Commit` table by `sha` alone: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) .
- `Commit#create_status_from_github!` then creates a `Status` row scoped to `commit.stack_id` (the victim's stack) via `add_status`/`statuses.replicate_from_github!` [5](#0-4) , and this mutates the commit's `status` (a `Status::Group`), which feeds `deployable?` (`success? && !blocked?`) [6](#0-5)  and triggers `stack.schedule_merges` / `deployable_status` hooks [7](#0-6) .

Exploit flow: the attacker registers a repository/webhook with Shipit (any repo Shipit tracks, or even one whose owner matches an org Shipit recognizes), engineers or discovers a commit whose SHA is identical to a commit already present in a victim stack that requires `ci/coverage` (SHA collisions across repos are trivial to produce deliberately — e.g., importing/cherry-picking the victim's exact commit into the attacker's own repo, since git SHAs are content-addressed and identical tree+metadata yields an identical SHA), and sends a `status` webhook with `context: ci/coverage`, `state: success`, `sha: <shared-sha>`. The signature check passes because it is validated against the attacker's own repository/org's webhook secret, not against ownership of that specific SHA or stack. `StatusHandler#process` then writes a `success` status for `ci/coverage` onto **every** `Commit` row with that SHA, including the victim's, altering the victim's `deployable?`/merge eligibility.

Existing guards do not catch this: `verify_signature` authenticates the sender-repo pair but is blind to which commits get mutated; `Handler#stacks`'s repository-scoping is simply not used by `StatusHandler`; there is no model-level validation tying `Status#stack_id`/`commit.stack_id` to the webhook's originating repository.

### Impact Explanation
An attacker-controlled webhook write mutates CI state (and hence deploy/merge eligibility) for a commit belonging to a repository/stack that never authenticated the event — this is a cross-repository/cross-tenant write matching the "payload for one repository mutating another's stack, commit, task or team" Critical impact category. Concretely, flipping a required context like `ci/coverage` to `success` can make an otherwise-blocked victim commit `deployable?`, enabling an unauthorized deploy, or unblock `stack.schedule_merges`, enabling an unauthorized merge. The attack is repeatable against any commit whose SHA the attacker can reproduce and is not limited to a single victim stack — any tracked stack sharing that SHA is affected simultaneously.

### Likelihood Explanation
Preconditions: the attacker needs a Shipit-tracked GitHub repository (or org) capable of emitting a validly-signed `status` webhook to the shared Shipit host, and needs the target SHA to also exist as a `Commit` row in a victim's stack. Producing a SHA collision is not cryptographic collision — it only requires the attacker to have (or fork/cherry-pick) the exact same commit content/metadata as the victim's tracked commit, which is achievable in ordinary workflows (shared upstream history, vendored commits, forks). Attacker cost is low: one HTTP POST to `/webhooks` with a legitimate signature for their own repo. This is fully repeatable and requires no privileged Shipit role, session, or secret beyond the attacker's own repo's webhook secret (which they control since it's their own repo).

### Recommendation
Scope `StatusHandler#process` to only touch commits belonging to stacks of the repository that authenticated the webhook, mirroring the pattern used by `Handler#stacks`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status webhook only affects commits in the authenticating repository's stacks" do
  victim_stack = shipit_stacks(:shipit) # requires ci/coverage in ci.require
  attacker_stack = shipit_stacks(:cyclimse) # unrelated repo/stack

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  before_status = victim_commit.status.state
  before_deployable = victim_commit.deployable?

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/coverage'
  }.merge(repository_params_for(attacker_stack)).to_json
  # signature stubbed/valid for attacker_stack's repo owner
  post :create, body: body, as: :json

  victim_commit.reload
  after_status = victim_commit.status.state
  after_deployable = victim_commit.deployable?

  # Binding under test: victim_commit's CI state should equal before_status/before_deployable
  # (unchanged by a webhook that only authenticated attacker_stack's repository)
  assert_equal before_status, after_status, "victim commit status must not change from an unrelated repo's webhook"
  assert_equal before_deployable, after_deployable, "victim commit deployable? must not change from an unrelated repo's webhook"
end
```
This test currently fails against `StatusHandler#process`'s unscoped `Commit.where(sha: params.sha)`, confirming the cross-repository write.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
