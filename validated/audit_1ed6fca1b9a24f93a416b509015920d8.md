Confirmed: the signature-selection organization and the repository the webhook acts on are two independently read fields from the same unsigned-until-verified JSON body, and the verification never binds them together.

### Title
Webhook signature verification binds only to `repository.owner.login`, not to `repository.full_name` acted upon by handlers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) pulled straight out of the untrusted, not-yet-verified JSON payload. [1](#0-0)  Once the signature checks out against that organization's own secret, the entire raw body — including a completely independent field, `repository.full_name` — is handed unmodified to the event handlers. [2](#0-1)  Every handler resolves the `Stack`/`Repository` to act on via `payload.dig('repository', 'full_name')`, not via `repository.owner.login`. [3](#0-2) [4](#0-3) 

### Finding Description
Shipit supports multiple GitHub organizations/Apps configured under `Shipit.github(organization: ...)`, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml`). Nothing prevents an operator of one onboarded GitHub organization ("org-A", for which they legitimately know or control the App/webhook secret) from crafting an arbitrary webhook POST where:
- `repository.owner.login` (or `organization.login`) = `"org-A"` — so `verify_signature` selects org-A's `GithubApp` and the HMAC(secret_A, raw_body) check passes, since the whole body (including the forged `repository.full_name`) is signed with a secret the attacker legitimately possesses. [5](#0-4) 
- `repository.full_name` = `"victim-org/victim-repo"` — an unrelated repository already onboarded onto the same Shipit instance under a *different* organization.

The equality that should hold is: `organization authenticated by verify_signature == organization owning the repository the handler mutates`. Instead, the code only checks `organization authenticated == repository.owner.login` (a value chosen by the attacker), while the actual repository state that is written (`Stack#sync_github`, `Commit#create_from_github!`, `Status` records, `PullRequest`/`ReviewStack` archive/unarchive, `Team`/`Membership` changes for `membership` events, etc.) is looked up purely from `repository.full_name`, a sibling field in the same unverified JSON that is never cross-checked against `repository.owner.login`. [6](#0-5) [3](#0-2) 

Because the HMAC covers the raw body as a whole (not a specific field), signing with org-A's own key legitimately produces a valid signature for a payload whose `repository.full_name` claims to be `victim-org/victim-repo`.

### Impact Explanation
This lets an attacker who controls (or is a member of, i.e. can trigger webhook deliveries for) any *one* org-A repository configured on the shared Shipit instance forge webhook events attributed to *any other* onboarded repository:
- `push` events trigger `Stack#sync_github(expected_head_sha:)`, which fetches commits from GitHub for the victim's stack, and can drive continuous-deployment triggers on the branch believed to be synced. [7](#0-6) 
- `status`/`check_suite` events write commit statuses (`commit.statuses.create`) for the victim commit, which feed directly into `commit.deployable?`, potentially marking an otherwise-unreviewed victim commit as "green" and unlocking automatic/continuous deploys.
- `pull_request` events (`opened`, `labeled`, `reopened`, `closed`) can force-provision, archive, or unarchive a victim ReviewStack.
- `membership` events create/delete `Team`/`Membership` records that feed into `Shipit.github_teams`-based authorization for the victim org.

This is a cross-repository/cross-organization write achievable without any Shipit session, API token, or `webhook_secret`/`api_clients_secret` compromise of the *victim* — only knowledge of one's own legitimately-configured org's webhook secret, satisfying the "cross-repository writes" and "escalation into `Shipit.github_teams` authorization" Impact criteria.

### Likelihood Explanation
Requires the attacker to control an organization/GitHub App that is itself already onboarded to the same shared Shipit instance (multi-tenant deployments configuring several `github:` orgs in `secrets.yml`, as shown by `config/secrets.development.shopify.yml`). This is a realistic deployment shape for Shipit (it is explicitly built to host multiple orgs), and the attacker needs no privileges on the victim org or repository at all — only the ability to deliver a webhook to Shipit's public webhook endpoint with their own org's valid signature.

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, after resolving the organization used to verify the signature, require that `repository.owner.login` (the field used to select the verification secret) match the owner segment of `repository.full_name` (the field used to resolve the `Stack`/`Repository`) before dispatching to any handler. Reject the webhook (422) on mismatch.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with a GitHub App and its own `webhook_secret` (`config/secrets.development.shopify.yml` pattern).
2. Attacker owns `org-a/some-repo` (already onboarded to this Shipit instance) and knows `org-a`'s webhook secret (legitimately, since they administer the App/webhook config for their own org).
3. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org_a_webhook_secret, raw_body)>` and POSTs to `/webhooks`.
5. `verify_signature` resolves `Shipit.github(organization: "org-a")`, verifies HMAC against `org-a`'s secret — passes, since the attacker legitimately holds it. [1](#0-0) 
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")`, entirely bypassing `org-a`, and triggers `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack. [3](#0-2) [7](#0-6)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
