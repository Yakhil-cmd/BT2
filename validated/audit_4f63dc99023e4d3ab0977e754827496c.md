### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status from one repository mutate commits belonging to any other stack sharing the SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table with no repository/stack scoping, unlike every other webhook handler (`PushHandler`, `CheckSuiteHandler`, `AssignedHandler`, `ClosedHandler`) which all filter through `stacks`/`Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`. Combined with `verify_signature` authenticating requests only at the GitHub *organization* level (not per-repository) and `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` auto-shipping newly green commits, this can let a status event legitimately signed for one repository flip CI state and trigger a ship/block on a different stack that happens to share the commit SHA.

### Finding Description
The broken binding: the code should enforce `status.repository == commit.stack.repository` (the authenticated repository must equal the repository owning the mutated commit), but `StatusHandler#process` never reads or checks `payload.dig('repository', 'full_name')` at all: [1](#0-0) 

Compare with the base `Handler#stacks` helper that every other handler uses to scope by repository: [2](#0-1) , and with `PushHandler#process`/`CheckSuiteHandler#process`, which both filter through `stacks`: [3](#0-2) [4](#0-3) 

Authentication is organization-scoped, not repository-scoped: `verify_signature` picks the `GithubApp` config purely from `repository.owner.login` and validates the raw body against that organization's single `webhook_secret`: [5](#0-4) . `verify_webhook_signature` uses one shared secret per organization: [6](#0-5) . Once verified, the raw parsed body — not the verified repository — is handed straight to the handler: [7](#0-6) .

Root cause: a webhook that is only cryptographically bound to "some repository within organization X" is allowed, by `StatusHandler`, to mutate a commit belonging to *any* stack in the datastore whose SHA matches, regardless of which repository that commit's stack tracks. If an attacker controls (or can register a webhook on) any repository sharing the same GitHub App/organization webhook secret as a victim stack, and can produce a commit with an identical SHA to one already present in the victim stack's commit table (e.g., by forking/cherry-picking so the SHA collides, which is common for repos with shared history), they can `POST /webhooks` with `X-Github-Event: status`, a `context` the victim stack requires (e.g. `buildkite/deploy`), `state: success`, and the shared `sha`. `StatusHandler#process` finds the victim's `Commit` row and calls `commit.create_status_from_github!`, creating a `Status` for the victim stack: [8](#0-7) . `Status#after_create`/`after_commit` callbacks then call `commit.stack.enable_ci!` and `commit.schedule_continuous_delivery`: [9](#0-8) , and `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob` if `stack.continuous_deployment?` and `stack.deployable?`: [10](#0-9) , which will `trigger_deploy` the now-green commit: [11](#0-10) .

Existing guards do not close this gap: `verify_signature` only proves the payload came from *an* authorized sender for *that organization*, not that the sender is authorized for the specific commit/stack being mutated; the `ExplicitParameters` schema in `StatusHandler` only validates types, not repository ownership; and there is no `stacks`/repository filter anywhere in `StatusHandler#process`, unlike its sibling handlers.

### Impact Explanation
A payload correctly authenticated for one repository can write a `Status` row and trigger a deploy for a stack belonging to a completely different repository — this is exactly the "payload for one repository mutating another's stack/commit" category, rated Critical (unauthorized deploy of attacker-influenced/premature code). The blast radius spans every stack in the same GitHub App/organization installation, since the webhook secret is shared per-organization rather than per-repository, and any of them with `continuous_deployment` enabled and a required status context is a target.

### Likelihood Explanation
Exploitation requires: (1) the attacker to be able to send a validly-signed webhook, which in practice requires access to a repository under the same organization/GitHub App installation as the victim (or the org's `webhook_secret` being unset, in which case `verify_webhook_signature` trivially returns `true`: [12](#0-11) ); and (2) a commit SHA that exists in both the attacker's controlled repository and the victim's tracked stack (achievable via forks/cherry-picks sharing history, or via the unset-secret path where the attacker can pick any SHA already present as a victim commit). Given these preconditions, the attack is cheap and repeatable against any stack with `continuous_deployment` enabled.

### Recommendation
Scope `StatusHandler#process` to the repository named in the webhook payload, mirroring `PushHandler`/`CheckSuiteHandler`: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and only create/update statuses for commits belonging to those stacks, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |c| c.create_status_from_github!(params) } }` instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/webhooks/status_handler_test.rb`):
1. Create two stacks: `victim_stack` (repository `victim/repo`, `continuous_deployment: true`, `required_statuses` including `buildkite/deploy`) and `attacker_stack` (repository `attacker/repo`).
2. Create a `Commit` on `victim_stack` with `sha: "deadbeef..."`, not yet deployed, currently CI-`pending`/absent (`victim_commit.state != 'success'`) — this is the binding to assert before: `assert_not_equal 'success', victim_commit.reload.state`.
3. Send `POST /webhooks` with `X-Github-Event: status`, body `{ "sha" => "deadbeef...", "state" => "success", "context" => "buildkite/deploy", "repository" => { "full_name" => "attacker/repo", "owner" => { "login" => "attacker-org" } } }`, stubbing `verify_signature`/`GithubHook` as in existing tests.
4. Assert after: `assert_equal 'success', victim_commit.reload.state` and `assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack])`, proving a payload naming `attacker/repo` mutated `victim_stack`'s commit and triggered continuous delivery — violating the invariant that a status only affects the repository that authenticated it.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
