### Title
Cross-organization commit status forgery via unscoped `StatusHandler` breaks the authenticated-organization/written-repository binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
In a multi-tenant Shipit deployment (multiple GitHub organizations configured under `Shipit.github`, each with its own `webhook_secret`), the webhook signature check authenticates a request against the organization named in the payload's `repository.owner.login` (or `organization.login`), but the `status` event handler never re-checks that the commit it writes actually belongs to that organization's repository. It blindly updates any commit in the entire Shipit database whose SHA matches the attacker-supplied value. This is the same class of bug as the Hats Protocol finding: a value that determines "who is authorized" (`repository_owner` used to pick the `webhook_secret`) is disconnected from the value that determines "what gets mutated" (`Commit.where(sha: params.sha)`, which has no organization/repository scope at all).

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App config used to validate `X-Hub-Signature` based solely on `repository_owner`, itself read straight out of the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

This design is explicitly meant to support multiple, independently-managed GitHub organizations sharing one Shipit instance, each with its own `webhook_secret`: [3](#0-2) 

Once the signature check passes for *some* organization, the payload is dispatched to every handler registered for the event with no further binding to that organization: [4](#0-3) [5](#0-4) 

Most handlers re-derive scope from `repository.full_name` via the base `Handler#stacks`/`#repository_name` helpers, which at least ties the mutated `Stack`/`Repository` back to a field inside the same request: [6](#0-5) 

But `StatusHandler` does not use this scoping at all — its params schema doesn't even require a `repository` key, and it queries commits globally by SHA: [7](#0-6) 

So the equality that should hold — *organization whose `webhook_secret` authenticated the request* == *organization owning the repository/commit being written* — is never enforced for `status` events. Any tenant configured in `Shipit.github` (i.e., anyone who legitimately administers their own onboarded GitHub App/organization on a shared Shipit instance) can sign a payload with their own `webhook_secret`, and use it to write a fabricated commit status onto a commit belonging to a **different** organization's stack, as long as they know that commit's SHA (trivially obtainable for any public repository, or any repo the attacker can see via their own limited access).

### Impact Explanation
Commit statuses gate deploy eligibility in Shipit — the changelog documents "blocking statuses" that must be present/passing before a deploy can proceed: [8](#0-7) 

By forging a `success` status for a required check context on a commit belonging to an org they don't control, a tenant on a shared multi-org Shipit instance can satisfy another organization's deploy-blocking status requirements and cause an unauthorized deploy to proceed for a stack/repository they have no legitimate authority over. This is a cross-repository, cross-tenant write achieved purely by holding credentials scoped to a different, unrelated repository — matching the report's "Critical: cross-repository writes / unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires only: (1) the attacker's own organization is one of the tenants configured under `Shipit.github` on a shared instance (a supported, documented deployment mode), (2) knowledge of a target commit SHA in another tenant's tracked repository (often public), and (3) the ability to compute an HMAC-SHA1 over an arbitrary body with their own `webhook_secret` and POST it to the public `/webhooks` endpoint. No Shipit session, API token, or the victim organization's secret is needed. Given multi-org configuration is a documented, encouraged feature, this is realistically reachable.

### Recommendation
In `StatusHandler` (and any other handler that doesn't rely on `Handler#stacks`), require and validate the `repository.full_name` field, resolve the owning `Repository`/`Stack`, and confirm it matches the organization that authenticated the request (`repository_owner` used in `WebhooksController#verify_signature`) before mutating any `Commit`. More generally, `WebhooksController` should pass the authenticated organization down to handlers so every handler can assert the field(s) it writes belong to that same organization, rather than trusting unrelated fields deeper in the same JSON body.

### Proof of Concept
1. Deploy Shipit with two organizations configured, e.g. `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-org config), each tracking their own stacks/commits.
2. As the (unprivileged w.r.t. Shipit, but legitimate) admin of `OrgA`'s GitHub App, compute `sha1=HMAC-SHA1(webhook_secret_A, body)` for a crafted body:
```json
{
  "sha": "<known commit sha belonging to an OrgB-tracked repository>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" } }
}
```
3. POST this body to `/webhooks` with `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, looks up `Shipit.github(organization: "OrgA")`, and successfully verifies the signature against `webhook_secret_A`. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no organization filter, finds the commit belonging to `OrgB`, and calls `commit.create_status_from_github!(params)`, marking it as passing — even though the request was only ever authenticated as `OrgA`. [9](#0-8)
