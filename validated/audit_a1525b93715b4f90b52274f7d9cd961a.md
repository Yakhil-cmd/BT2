### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while event handlers act on the independently-controlled `repository.full_name` field, allowing an unauthenticated forged webhook for any victim repository whenever any configured GitHub org has no `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) out of the **same attacker-supplied JSON body** it is trying to authenticate. Every downstream event handler, however, resolves the `Stack`/`Repository` to act on using a *different* field of that same body: `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`). These two fields are never checked for consistency. Because `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected org has no `webhook_secret` configured (`lib/shipit/github_app.rb:76-77`) — a supported, documented configuration, as shown by `config/secrets.development.shopify.yml:9,18` (`webhook_secret: # nil`) — an attacker can pick an org with no secret for the "authenticating" field while pointing `repository.full_name` at a victim repository/stack secured by a different org's secret.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally if the selected org's `webhook_secret` is blank:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

Meanwhile every `Shipit::Webhooks::Handlers::Handler` subclass (push, status, pull_request, check_suite, etc.) resolves the actual `Stack`/`Repository` it operates on from a completely separate JSON path:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`repository.owner.login` and `repository.full_name` normally describe the same repository when GitHub sends the payload, but nothing in this engine cryptographically or logically ties them together — they are just two independent keys inside one JSON body that an attacker fully controls when POSTing directly to `/webhooks`. The equality this code implicitly (and wrongly) assumes is:

`{organization whose secret authenticated the signature} == {repository the handler acts on}`

but the actual binding that is enforced is only:

`{organization named in repository.owner.login} == {org config selected for signature check}`, independent of `repository.full_name`.

### Impact Explanation
If the Shipit deployment configures multiple GitHub organizations (a documented, supported setup — see `config/secrets.development.shopify.yml:5-23`) and at least one of them has no `webhook_secret` set (also shown as a valid/documented value, `webhook_secret: # nil`), an attacker who knows this (e.g., because they administer that low-security org, or because it's a default/dev tenant) can send a raw, **unsigned** POST to `/webhooks` with:
- `repository.owner.login` = the no-secret org (makes `verify_webhook_signature` return `true` with no signature required), and
- `repository.full_name` = `victim_org/victim_repo`

The payload is then routed to real handlers for the victim's stack. For example, the `commit_status` handler creates `Status` rows for an arbitrary commit sha in the victim's repository. `MergeRequest#all_status_checks_passed?` / `#any_status_checks_missing?` consume these stored `Status` records directly (`app/models/shipit/merge_request.rb:193-206`) to gate the merge queue and continuous-deployment triggers, so forged "success" statuses can help an unauthorized commit clear CI gating and reach an unauthorized deploy/merge. The `push` handler similarly can be triggered against the victim stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), and `pull_request` handlers can archive/unarchive review stacks for a victim repo. This satisfies the Critical impact bucket ("unauthorized deploy, rollback or merge") because it is reachable with zero credentials, zero GitHub webhook secret, and zero Shipit session/API token — only knowledge that some tenant org in the shared installation has no webhook secret.

### Likelihood Explanation
The multi-org configuration format (`config/secrets.development.shopify.yml`) and the blank-secret fallback (`verify_webhook_signature` returning `true`) are both first-class, documented behaviors of this engine, not host-app misconfiguration. Any Shipit installation onboarding multiple orgs where even one org is left with `webhook_secret: nil` (an explicitly supported default) is exploitable by anyone able to reach the public `/webhooks` endpoint with no other requirement.

### Recommendation
Bind the signature-selection organization to the same repository identity the handlers act on: require that `repository.full_name`'s owner matches `repository_owner`/`organization.login` before dispatching to handlers, and reject (422) on mismatch. Additionally, do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank for events carrying a `repository`/`organization` payload — either require a secret for every configured org or scope the blank-secret bypass so it can never authorize actions against a different org's repository.

### Proof of Concept
1. Configure Shipit with two tenants in `secrets.yml`, mirroring `config/secrets.development.shopify.yml`: `victim_org` (has a strong `webhook_secret`) and `attacker_org` (no `webhook_secret`, `# nil`).
2. As the attacker (no GitHub access to `victim_org`, no Shipit API token), send:
```
POST /webhooks
X-Github-Event: status
Body:
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker_org" }, "full_name": "victim_org/victim_repo" }
}
```
No `X-Hub-Signature` header is required.
3. `repository_owner` resolves to `attacker_org`; `Shipit.github(organization: "attacker_org").verify_webhook_signature` returns `true` because that tenant's `webhook_secret` is blank.
4. The `status` handler resolves the target stack via `repository.full_name` = `victim_org/victim_repo` and writes a forged `Status` (`success`) against the victim commit, which can be consumed by `MergeRequest#all_status_checks_passed?` to permit an otherwise-blocked merge/deploy of that commit.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
