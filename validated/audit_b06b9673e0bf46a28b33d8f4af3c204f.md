### Title
Reentrant call through `signer-manager-trait` into other pox-5 state-mutating functions bypasses the reentrancy guard - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond`, `update-bond-registration`, and `stake` all read state (existing membership, allowances, per-cycle totals) *before* invoking an attacker-supplied contract via `contract-call? signer-manager validate-stake!`, and only write the resulting map updates *after* that external call returns. The contract has a purpose-built reentrancy guard (`signer-manager-call-active` / `ERR_REENTRANT_CALL`), but it only prevents a second *trait call* from being issued while one is in flight — it does not prevent the untrusted `signer-manager` contract from calling back into other pox-5 public functions that don't themselves invoke `signer-manager-validate-stake`.

### Finding Description
`pox-5.clar` defines a reentrancy guard specifically to defend against this bug class: [1](#0-0) 

`signer-manager-validate-stake` sets `signer-manager-call-active` to `true`, performs `(contract-call? signer-manager validate-stake! ...)` on a caller-supplied, untrusted `<signer-manager-trait>` implementation, then resets the flag to `false`. Public entry points such as `register-for-bond` call this helper in the *middle* of their logic: [2](#0-1) 

At the point `signer-manager-validate-stake` invokes the trait function, pox-5 has already:
- read `existing-membership`, `old-sbtc`, `existing-stake`, `allowance`, and `current-total-staked` (lines 679-708),
- passed the `bond-overlaps-new-position?` and balance checks based on that *stale* pre-write snapshot,

but has **not yet** performed any of the `map-set`/`map-insert` writes for `protocol-bond-memberships`, `protocol-bonds-total-staked`, `signer-shares-staked-for-cycle`, etc. (lines 786-815). Those writes only happen after the trait call returns.

The guard only blocks a *second* call to `signer-manager-validate-stake` (i.e., `ERR_REENTRANT_CALL` fires only if the nested call itself tries to call another signer-manager trait function). It is not checked at the top of `register-for-bond`, `update-bond-registration`, or `stake` themselves. Consequently, a malicious `signer-manager` contract's `validate-stake!` implementation can call back into any pox-5 public function that does **not** route through `signer-manager-validate-stake` (e.g. `unstake`, `stake-update`, reward-claim functions, or `register-for-bond` for a *different, non-overlapping* `bond-index` that requires a different, non-malicious signer so it skips its own trait call) while the outer call's state (`protocol-bond-memberships`, `signer-shares-staked-for-cycle`, `protocol-bonds-total-staked`, `ustx-delegated-per-cycle`) has not yet been committed.

Because the actual STX lock for the staker's `amount-ustx` is applied by the Rust-side pox-locking handler only once, based on the tx's final Clarity return value (not incrementally per nested call), a staker can be credited (in the Clarity-side bookkeeping maps) as staked/bonded shares in **two** cycles/bonds simultaneously off of a single underlying STX balance that is checked (`stx-account`) but never actually decremented mid-transaction. This breaks the equality between "STX actually locked" and "reward-eligible shares recorded," i.e., double-counting a commitment.

### Impact Explanation
This falls under the in-scope Critical impact category "double-counting a commitment or reward": a staker's shares can be recorded against `signer-shares-staked-for-cycle` / `protocol-bonds-total-staked` / `ustx-delegated-per-cycle` for more than one bond/cycle position while only a single amount of STX is ever locked to back it, inflating claimable sBTC rewards and signer voting weight beyond what is actually collateralized.

### Likelihood Explanation
Exploitation requires the attacker to control (or have their own bond/stake serviced by) a `signer-manager` contract implementing `signer-manager-trait`, which is exactly the contract-supplied, unprivileged, attacker-controlled principal that `register-for-bond`/`update-bond-registration`/`stake` accept as an argument. No admin, miner, or other-user key is required — the staker simply deploys their own signer-manager contract to register their own stake, satisfying the "unprivileged account" and "not requiring an admin key" constraints. The primary uncertainty is whether the full downstream Rust-side accounting (in `pox-locking/src/pox_5.rs`, which was only partially reviewed) fully re-derives locked amounts from a single canonical read at the very end of the transaction in a way that would still cap credited shares to what was actually locked; this could not be fully confirmed within the available context.

### Recommendation
Move the reentrancy check (`asserts! (not (var-get signer-manager-call-active)) ERR_REENTRANT_CALL`) to the very top of every public function that mutates `protocol-bond-memberships`, `staker-info`, or any per-cycle share/reward map — not just the ones that themselves call `signer-manager-validate-stake` — so that *no* pox-5 public entry point can be invoked while a trait callback to an untrusted `signer-manager` is in flight. Alternatively, apply strict check-effects-interactions ordering: perform all map reads used for authorization decisions, then all map writes, and only call the untrusted trait function last (after state has already been committed), or set the guard before *any* state is read and clear it only after all state for that call has been written.

### Proof of Concept
1. Attacker deploys `evil-signer-manager` implementing `signer-manager-trait`, whose `validate-stake!` function, on first invocation, calls back into pox-5's `register-for-bond` for a second, non-overlapping `bond-index` that uses a different (non-reentrant) legitimate signer-manager, passing the same `tx-sender`/staker and the same `amount-ustx` that is still fully present in the attacker's unlocked STX balance (because the outer, in-progress call hasn't caused any STX to move yet).
2. This nested `register-for-bond` call reads `existing-membership` as `none` (outer call's `map-set protocol-bond-memberships` has not executed yet), passes `bond-overlaps-new-position?`, passes `total-balance >= amount-ustx` (STX not yet locked), and completes normally, writing `protocol-bond-memberships`, incrementing `protocol-bonds-total-staked`, and crediting `signer-shares-staked-for-cycle`/`ustx-delegated-per-cycle` for bond B.
3. Control returns to `evil-signer-manager.validate-stake!`, which returns `(ok true)`.
4. The outer `register-for-bond` call for bond A resumes and completes, writing its own `protocol-bond-memberships` entry (bond A) and incrementing bond A's totals/shares for the same staker and the same `amount-ustx`.
5. Result: the staker now has committed shares recorded in both bond A and bond B's reward-accounting maps, while only one `amount-ustx` worth of STX will ultimately be locked by the node-level handler — a double-counted commitment inflating reward eligibility and signer weight beyond the actually-locked STX.

;; Reentrancy guard: prevents cross-function re-entry through signer-manager trait calls
(define-data-var signer-manager-call-active bool false)

(define-trait signer-manager-trait (
    (validate-stake!
        ;; staker, first-index, num-indexes, amount-ustx, amount-sats, is-bond, signer-calldata
        (principal uint uint uint uint bool (optional (buff 500)))
        (response bool uint)
    )
))

(define-private (validate-no-reentrancy)
    (ok (asserts! (not (var-get signer-manager-call-active)) ERR_REENTRANT_CALL))
)

;; A helper function to call the `validate-stake!` function on a given
;; signer-manager, wrapping the reentrancy guard logic around it. This should
;; be the only way that `validate-stake!` is called in the contract, since it
;; is critical to ensure that reentrancy attacks are prevented.
(define-private (signer-manager-validate-stake
        (signer-manager <signer-manager-trait>)
        (staker principal)
        (first-index uint)
        (num-indexes uint)
        (amount-ustx uint)
        (amount-sats uint)
        (is-bond bool)
        (signer-calldata (optional (buff 500)))
    )
    (begin
        (asserts! (not (var-get signer-manager-call-active)) ERR_REENTRANT_CALL)
        (var-set signer-manager-call-active true)
        (try! (contract-call? signer-manager validate-stake! staker first-index
            num-indexes amount-ustx amount-sats is-bond signer-calldata
        ))
        (var-set signer-manager-call-active false)
        (ok true)
    )
)
