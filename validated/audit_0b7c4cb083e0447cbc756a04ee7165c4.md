Based on my analysis, ocore contains a directly analogous pattern in its **AA `attestation` message app**, which is the on-chain identity/association mechanism most similar to OpenQ's `associateExternalIdToAddress`.

### Title
AA `attestation` messages let any unprivileged trigger sender overwrite the address→profile association that downstream AA logic relies on to identify a legitimate claimant - (File: `aa_validation.js`, `validation.js`, `formula/evaluation.js`, `writer.js`)

### Summary
An Autonomous Agent (AA) can emit an `attestation` message associating an arbitrary `address` with a `profile` (analogous to OpenQ's `associateExternalIdToAddress`, which associates an off-chain ID with an on-chain address). The `address` field of the attestation payload is validated as either a fixed address or an **arbitrary formula** [1](#0-0) , meaning an AA author can (and commonly would, e.g. in a registration/KYC-style AA) set it from trigger-controlled data such as `trigger.data.address` rather than being hard-locked to `trigger.address`. Any unprivileged party can post a trigger causing the AA to emit a new attestation for a target address that was previously legitimately claimed by someone else.

### Finding Description
Core-level validation of the `attestation` message imposes no ownership or uniqueness constraint on the attested address: it explicitly permits attesting any address, including ones "that have never been used yet" or that belong to someone else, with the comment confirming this is intentional design [2](#0-1) . Every attestation is persisted keyed by `(attestor_address, address, field)` in `attestations`/`attested_fields`, and the latest one always wins by default (`ifseveral='last'`) [3](#0-2) . When downstream oscript/AA logic queries an address's attested value via the `attestation`/`attested` formula, it selects the most recent matching row (unstable first, then stable) ordered by MCI/level, i.e. last-write-wins [4](#0-3) .

Because the `attestor_address` in this scenario is the AA itself (the AA is the unit author of its own response, so `attestor_address = AA address` [5](#0-4) ), and because the AA's own `attestation` payload can bind `address` to trigger-supplied data rather than `trigger.address`, **any unprivileged AA caller can trigger a new attestation for someone else's already-registered address**, exactly mirroring the OpenQ flaw where `associateExternalIdToAddress` let an attacker overwrite `addressToExternalUserId[winner_address]` with the attacker's own ID.

If a bounty/reward-style AA (structurally identical in intent to `test/samples/things_registry_and_marketplace.oscript`, but using `attestation` instead of a properly-guarded `var[...]` state variable) relies on `attestation[[attestors=this_address, address=$claimant, ifseveral='last']]` to look up a previously-registered identity/eligibility flag for a payout, a malicious unprivileged trigger sender can call the same AA with the victim's address as the target and overwrite the attested profile field, causing the legitimate claimant's lookup to resolve to attacker-supplied data instead of their own registration.

### Impact Explanation
A legitimate user who registered/claimed eligibility through an AA-emitted attestation can be prevented from completing their claim because a subsequent unprivileged trigger from any other address can silently overwrite the `ifseveral='last'` attestation record for their address. This is a High-severity denial-of-service against fund claims and, depending on how the consuming AA structures its logic, can also enable outright fund redirection/loss if the overwritten profile field feeds directly into payout addresses/amounts.

### Likelihood Explanation
This requires a specific (but plausible and previously-seen-in-the-wild) AA design pattern: using `attestation` with a trigger/attacker-controllable `address` field instead of hard-coding `trigger.address`, and relying on `ifseveral='last'` semantics for eligibility lookups without an explicit "already registered" guard (unlike the safe `var['owner_'||$id]` pattern used in `things_registry_and_marketplace.oscript`). Any AA author who uses this natural-looking pattern is exposed, and the trigger to exploit it is a single, ordinary posted unit from any address — no special privilege needed.

### Recommendation
- In `aa_validation.js`, discourage/flag `attestation` payloads whose `address` formula does not reference `trigger.address`/`trigger.initial_address`, or document prominently that AA authors must gate attestation targets with an explicit prior-ownership check (as done for `var[...]` state in registration-style AAs).
- For AA templates/documentation, recommend using a `var['owner_'||id]`-style guarded state variable (checked with `bounce` on conflict) rather than raw `attestation` when the semantics require an address to be bound exactly once to a claimant, since `attestation`/`attested` intentionally has last-write-wins, no-ownership-check semantics at the protocol level.

### Proof of Concept
1. Deploy AA `R` with logic: on `trigger.data.register` and `trigger.data.id`, if `!var['claimed_' || $id]`, set `var['claimed_' || $id] = 1` and emit `{app:'attestation', payload:{address: trigger.data.target, profile: {id: trigger.data.id}}}` (a realistic simplification of a "bind on-chain address to external id" registration AA), without checking whether `trigger.data.target` already has an attestation for a different id.
2. Legitimate winner `W` triggers `R` with `id=W_id`, `target=W_address` → AA emits `attestation(address=W_address, profile={id:W_id})`.
3. Bounty-paying AA `B` later determines the winner by `attestation[[attestors=R_address, address=$candidate, ifseveral='last']].id == expected_winner_id` to authorize payout to `$candidate`.
4. Attacker `A` triggers `R` again with `id=A_id`, `target=W_address` (no ownership check prevents this) → a new, more recent attestation is written for `W_address` with `id=A_id`.
5. When `W` now triggers `B`, the `ifseveral='last'` lookup for `W_address` returns `A_id` instead of `W_id`, and `B`'s eligibility check fails, blocking `W` from claiming the bounty — mirroring the OpenQ POC exactly.
