### Title
Cross-repository writes via webhook signature verification keyed on `repository.owner.login` while handlers act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's webhook secret to verify the HMAC signature with based solely on `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body itself. Every event handler, however, resolves the target `Repository`/`Stack` to write to using `repository.full_name` from that same body. In a multi-organization Shipit deployment (`config/secrets.*.yml` supports a `github: { org1: {...}, org2: {...} }` map, each with its own `webhook_secret`), these two fields are never checked for consistency, so a party who legitimately controls one configured organization's webhook secret can forge a payload whose `repository.owner.login` matches their own org (so their real secret verifies it) while `repository.full_name` names a repository belonging to a different, victim organization.

### Finding Description
`verify_signature` derives the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization app/secret from `Rails.application.credentials.github`, which explicitly supports one config block per GitHub organization each with an independent `webhook_secret`: [3](#0-2) [4](#0-3) 

The verification step only proves that "the sender knows the webhook secret for the organization named in `repository.owner.login`". It does not prove anything about `repository.full_name`, which is a sibling field in the very same untrusted body and is never cross-checked against `repository.owner.login`.

Every default handler, however, resolves which local `Repository`/`Stack` records to mutate using `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

The PR handlers do the same: [8](#0-7) 

Because the `organization` that authenticates (via `repository.owner.login`) and the `repository` that is written (via `repository.full_name`) are two different, independently attacker-controlled JSON fields under one HMAC over the whole body, an attacker who is a legitimate GitHub org admin/owner for **any one** organization configured in this Shipit instance (and therefore knows or can obtain that org's `webhook_secret` value configured for their own repositories) can compute a valid signature for a crafted body where `repository.owner.login` = their own org (so `verify_signature` picks their org's real secret and it matches), but `repository.full_name` = `"victim-org/victim-repo"`. This body will pass `verify_signature` and then be dispatched to handlers that act on the victim's repository/stack, e.g. triggering `stack.sync_github(expected_head_sha: ...)` on a push event for a stack that belongs to a completely different, uninvolved organization: [9](#0-8) 

This is exactly the "organization authenticated vs. repository written" binding break called out in the rules: the equality that should hold is `organization_that_signed(payload) == owner(repository_written_to(payload))`, and the codebase never asserts it.

### Impact Explanation
This breaks the binding between "who proved they control the signing secret" and "whose repository state gets mutated." Depending on which handler is exercised this permits an attacker who only controls a foreign/unrelated GitHub organization configured on the same Shipit instance to force a resync (`Stack#sync_github`) or otherwise write status/PR/team state (`MembershipHandler` creates/removes `Team`/`Membership` records; `StatusHandler` creates Commit statuses) attributed to a victim repository/stack they do not own, without ever holding the victim organization's webhook secret. This satisfies the "cross-repository writes" Critical-impact criterion in the rules, since it lets one organization's authenticated webhook traffic write to another organization's stack/repository records.

### Likelihood Explanation
Exploitability requires the target Shipit instance to be configured with more than one GitHub organization (the multi-org `github:` map schema shown in `config/secrets.development.shopify.yml`), and requires the attacker to have legitimate knowledge of the webhook secret for at least one of those configured organizations (e.g., they are an owner/admin of one of the multiple orgs onboarded to this Shipit instance, or they can read that org's webhook secret from their own GitHub App/webhook settings). This is a realistic multi-tenant scenario the codebase explicitly documents and supports, and no code path validates that `repository.owner.login` and the owner portion of `repository.full_name` agree.

### Recommendation
In `WebhooksController#verify_signature`, after establishing which org's secret validated the signature, also verify that `params.dig('repository','full_name')&.split('/')&.first` (case-insensitively) equals `repository_owner`, rejecting the request (HTTP 422) on mismatch before dispatching to any handler. Alternatively, have `Shipit::Webhooks::Handlers::Handler#repository_name` re-derive the repo name only from the already-verified `repository_owner`, or scope the handler's `Repository.from_github_repo_name` lookup to organizations matching the one whose secret validated the payload.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` schema).
2. As an admin of `attacker-org` (or anyone who knows `attacker-org`'s configured `webhook_secret`), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org webhook_secret, raw_body)>`.
4. POST to `/github/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`), verifies the signature against the attacker's own valid secret, and succeeds.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` and, if such a stack exists and is on the pushed branch, calls `stack.sync_github(expected_head_sha: ...)` — a write against `victim-org`'s stack triggered purely by `attacker-org`'s valid webhook secret.

Note: this analysis is based on static review of the routes/controllers/handlers found in the index; I was unable to execute the request end-to-end in this environment, so the exact HTTP response/side effects should be confirmed by a live test (e.g., extending `test/controllers/webhooks_controller_test.rb`) before treating this as fully proven.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks

            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
