### Title
Cross-organization status forgery via unbound webhook signature selection - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a delivery against using an attacker-controlled payload field (`repository.owner.login`, falling back to `organization.login`), but none of the event handlers scope their side effects to that same organization. In particular, `StatusHandler` looks up commits purely by SHA across the entire Shipit instance, with no repository/organization check at all. This breaks the binding "organization whose secret authenticated the request == repository/commit the request is allowed to act on."

### Finding Description
`verify_signature` derives the signing organization straight from the unauthenticated request body and only then checks the signature against that organization's configured secret: [1](#0-0) [2](#0-1) 

This is a legitimate, documented multi-tenant configuration: `Shipit.github(organization:)` looks up a per-organization `github` config block (with its own `webhook_secret`) keyed by the organization name found in `secrets.github`. [3](#0-2) 

The signature only proves "this body was HMAC-signed with organization X's secret" — it says nothing about which repository the payload's other fields describe. Handlers, however, use a *different* field (`repository.full_name`) to decide what gets acted upon, and in the `status` handler don't even use the repository at all: [4](#0-3) [5](#0-4) 

`StatusHandler#process` runs `Commit.where(sha: params.sha)` unscoped by stack/repository/organization, then calls `create_status_from_github!`, which persists a GitHub-style commit status and triggers deploy-gating logic: [6](#0-5) [7](#0-6) [8](#0-7) 

An attacker who legitimately administers a GitHub App for one organization onboarded into a shared Shipit instance (and thus knows that organization's own `webhook_secret`, exactly as intended by the multi-tenant design) can:
1. Craft a `status` webhook body with `repository.owner.login` = their own organization (so `verify_signature` selects their own known secret and the HMAC check passes).
2. Set `sha` to the head commit of a stack belonging to a **different** organization/repository they do not control (commit SHAs are public information, obtainable from the target's GitHub repo).
3. Set `state` to `success` (and matching `context`) for that foreign commit.

Because `Commit.where(sha:)` is global, Shipit will attach that forged status to the victim commit regardless of which organization's secret validated the request.

### Impact Explanation
This is a cross-repository/cross-organization forgery that breaks a deployment-trust binding: the organization that authenticated the webhook is not required to equal the repository/commit that gets written. If the victim stack's `shipit.yml`/`stack` relies on a required status context to gate `deployable?`/`schedule_continuous_delivery` (blocking or required statuses, continuous delivery), the attacker can synthesize a passing status for a commit they do not own, contributing to an unauthorized/continuous deploy being triggered on a stack outside their organization. This matches the in-scope "High" impact of escalation via forged authorization signals, and can reach "unauthorized deploy" territory in continuous-delivery configurations, since `create_status_from_github!` feeds directly into `deployable?` and `schedule_continuous_delivery`.

### Likelihood Explanation
Requires the attacker to control (or administer) at least one organization's Shipit GitHub App integration on a shared/multi-tenant Shipit instance — a documented, supported configuration (`secrets.github` keyed by multiple organizations) rather than a privileged Shipit account, session, or `ApiClient` token. No repository write access to the victim's repo is needed; only the victim commit's SHA, which is public GitHub information. `CheckSuiteHandler` also matches purely by `stacks.where(branch:)` derived from `params.repository.full_name`/`Repository.from_github_repo_name`, which is scoped correctly — `StatusHandler` is the outlier lacking any repository check.

### Recommendation
Bind webhook signature verification and payload processing to the *same* repository/organization identity: after selecting the app config to verify the signature, re-derive the organization/repository from the verified payload and require that every handler (especially `StatusHandler`) filters by `stack`/`repository` matching `repository.full_name`'s owner, not merely by an unscoped SHA lookup. Reject events whose `repository.owner.login` does not match the owner embedded in `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (multi-tenant setup as documented in `docs/setup.md`).
2. As the administrator of `org-a` (attacker), obtain `org-a`'s `webhook_secret` (they configured it) and the head commit SHA of a stack tracked under `org-b/victim-repo`.
3. POST to `/github/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "sha": "<victim-org-b-commit-sha>",
  "state": "success",
  "context": "<required-status-context>"
}
```
4. Sign the raw body with `org-a`'s known `webhook_secret` and send it as `X-Hub-Signature`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'org-a')` (from `repository.owner.login`), verifies successfully against `org-a`'s secret.
6. `StatusHandler#process` executes `Commit.where(sha: '<victim-org-b-commit-sha>')`, unscoped by repository, and creates a "success" status on the victim's commit — potentially satisfying a required/blocking status check and triggering `schedule_continuous_delivery` for `org-b`'s stack, despite the attacker having no access to `org-b`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
        def process
```
