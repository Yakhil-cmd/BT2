## Analysis

The GitLab bug is a case of **privilege chaining**: a user is granted a narrowly-scoped permission (`manage_group_access_tokens`) but the code that consumes that permission fails to bound the *resulting* privilege (token role) to the actor's own privilege level, letting a low-privilege action mint a high-privilege credential.

The closest reachable analog in `ocore` is in the `'seen'` spending-condition operator, where a definition author can specify amount constraints (`amount`, `amount_at_least`, `amount_at_most`) on a `filter.what === 'input'` clause, but those constraints are silently never enforced at evaluation time — only `filter.what === 'output'` filters apply the amount checks. This means a definition that was authored to require "a large-value proof of payment" from a given address can actually be satisfied by a trivial, unprivileged input of any amount, escalating a minimal action into full spending authority.

### Title
Unenforced amount constraints on `'seen'` input filters in address/asset conditions allow privilege escalation to unlock protected funds - (File: definition.js)

### Summary
`Definition.validateDefinition`'s `getFilterError` accepts `amount`, `amount_at_least`, and `amount_at_most` fields on `'seen'` filters regardless of whether `filter.what` is `'input'` or `'output'`, but `validateAuthentifiers`'s evaluation of the `'seen'` operator only applies those amount constraints when `filter.what === 'output'`. Any `'seen'` condition written against `input`s with an amount constraint is effectively evaluated as if the amount clause did not exist.

### Finding Description
`getFilterError` in `definition.js` validates the shape of a `'seen'` filter used inside address definitions and asset issue/transfer conditions, allowing `amount`/`amount_at_least`/`amount_at_most` on filters regardless of `what`: [1](#0-0) 

However, when the condition is actually evaluated during authentifier validation, the amount checks are gated behind `filter.what === 'output'`, and are never applied for `filter.what === 'input'`: [2](#0-1) 

Concretely, a definition can legally contain:
```
['seen', {what: 'input', asset: 'base', type: 'transfer', address: 'ADDR_X', amount_at_least: 1000000}]
```
intended to mean "release these funds only once `ADDR_X` has been observed spending (as input) at least 1,000,000 bytes, as economic proof". Because the `amount_at_least` clause is dropped for `what: 'input'`, the SQL query executed is simply "has `ADDR_X` ever had a `transfer` input at all" — satisfied trivially by a single 1-byte spend. Any unprivileged unit poster who controls `ADDR_X` (or who can induce/observe such a minimal transfer) can therefore satisfy a condition that was designed to require a much larger, costlier action, unlocking the associated spending or issuance rights.

This is directly analogous to the GitLab issue: a narrowly-scoped/low-cost capability (posting a tiny transfer) is silently accepted as fulfilling a higher-privilege gate (the definition author's intended large-value proof), because the enforcement code does not mirror the scope that validation nominally allowed.

### Impact Explanation
Any address or asset condition relying on `'seen'` with `what: 'input'` and an amount bound is not enforced as authored. This can lead to concrete unauthorized spending: funds or asset transfer/issue rights gated by "wait until a payment of at least N was made" can be released by a payment far below N, i.e., value can be extracted from a contract/shared address/asset condition that the definer believed was protected by an amount threshold. This is a fund-loss / unauthorized-spending class impact reachable purely from a single posted unit (the low-value input) by any unprivileged party, matching the Medium-severity privilege-chaining pattern in the source report.

### Likelihood Explanation
Reaching this requires only that some address definition or asset issue/transfer condition uses `'seen'` with `what: 'input'` combined with an amount constraint — a legitimate and plausible oscript/definition pattern for building payment-conditioned spending rules or escrow-like conditions. No special privileges, malicious peers, or node compromise are needed; the attacker only needs to be the party (or collude with the party) referenced by the `address` filter and post a minimal, otherwise valid transfer.

### Recommendation
In `definition.js`, move the amount/amount_at_least/amount_at_most application out of the `filter.what === 'output'` block so it applies uniformly to both `'input'` and `'output'` filters (inputs already carry an `amount` column in the `inputs` table for transfer/issue types), or alternatively have `getFilterError` reject amount-related fields when `filter.what === 'input'` if amount enforcement is not meant to be supported for inputs, so authors cannot construct conditions whose validated shape silently diverges from evaluated behavior.

### Proof of Concept
1. Definer creates address `SHARED` with definition:
```
['and', [
  ['sig', {pubkey: PUBKEY_DEFINER}],
  ['seen', {what: 'input', asset: 'base', type: 'transfer', address: 'ADDR_X', amount_at_least: 1000000}]
]]
```
intending funds at `SHARED` to be spendable by the definer only after `ADDR_X` has made a >=1,000,000-byte transfer somewhere on the DAG (proof of solvency/activity).
2. `ADDR_X`'s owner posts a normal, unrelated payment unit with a `transfer` input of 1 byte from `ADDR_X` (any ordinary spend qualifies, no special crafting needed).
3. Once that unit is stable, the definer (or anyone who can produce the `sig` component) posts a spending unit from `SHARED` referencing the `'seen'` condition; `validateAuthentifiers` evaluates the `case 'seen'` SQL without any `amount>=?` clause because `filter.what === 'input'`, and the trivial 1-byte transfer satisfies the query, releasing `SHARED`'s funds despite the intended 1,000,000-byte threshold never being met.
