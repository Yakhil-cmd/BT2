The code is real and the race is real. Let me trace it precisely.

## `RemoveVotesAfter` — Locking Analysis [1](#0-0) 

```go
func (h *headerGovModule) RemoveVotesAfter(blockNum uint64) {
    dirty := false
    for epochIdxIter, votes := range h.groupedVotes {   // ← NO LOCK
        for blockNumIter := range votes {               // ← NO LOCK
            if blockNumIter > blockNum {
                dirty = true
                h.mu.Lock()
                delete(h.groupedVotes[epochIdxIter], blockNumIter)
                if len(h.groupedVotes[epochIdxIter]) == 0 {
                    delete(h.groupedVotes, epochIdxIter)
                }
                h.mu.Unlock()   // ← lock released after EACH delete
            }
        }
    }
    ...
}
```

Two distinct problems:

**Problem 1 — Data race on map iteration**: The outer `range h.groupedVotes` and inner `range votes` loops read the maps without holding `h.mu`. `AddVote` writes to `h.groupedVotes` under `h.mu.Lock()`. Concurrent unlocked read + locked write on the same map is a Go data race (undefined behavior, can panic). [2](#0-1) 

**Problem 2 — Per-delete lock granularity**: The lock is acquired and released for each individual `delete`, not for the entire removal loop. Between two consecutive deletes, `h.mu` is unheld, so a concurrent `getVotesInEpoch` fast-path can acquire `h.mu.RLock()` and observe a partially-deleted `h.groupedVotes[epochIdx]`. [3](#0-2) 

## `getVotesInEpoch` fast path

```go
h.mu.RLock()
defer h.mu.RUnlock()
maps.Copy(votes, h.groupedVotes[epochIdx])   // sees partial state between deletes
return votes
``` [4](#0-3) 

The copy is atomic with respect to the mutex, but because `RemoveVotesAfter` releases the lock between deletes, the copy can execute in a window where some votes for the epoch have been deleted and others have not.

## Impact on `VerifyGov`

`getExpectedGovernance` calls `getVotesInEpoch`, aggregates the returned votes into a `PartialParamSet`, and returns a `GovData`. `VerifyGov` then does a `reflect.DeepEqual` between this locally-derived governance and the governance embedded in the block header. [5](#0-4) 

If `getVotesInEpoch` returns a partially-deleted vote set (missing some votes that were present when the block proposer ran `PrepareHeader`), the locally-derived governance will differ from the header's governance, causing `ErrGovVerification` on a valid block. Conversely, if the proposer ran `PrepareHeader` during the partial-deletion window, it embeds wrong governance, which honest verifiers (without the race) will reject. Either path produces consensus divergence between nodes that hit the race and those that do not.

## Trigger Path (Public/Permissionless)

`RewindDelete` → `RemoveVotesAfter` is called from `blockchain.go` during a chain reorganization. [6](#0-5)  Any peer can trigger a reorg by advertising a longer valid chain — no privileged access required. Concurrent `VerifyGov` calls happen naturally during block import/sync on the same node.

### Title
Unlocked map iteration and per-delete lock granularity in `RemoveVotesAfter` allow partial vote-set observation by concurrent `getExpectedGovernance`, causing `VerifyGov` consensus divergence — (`kaiax/gov/headergov/impl/rewind.go`)

### Summary
`RemoveVotesAfter` iterates `h.groupedVotes` without holding `h.mu` and acquires/releases the lock once per `delete`. A concurrent `getVotesInEpoch` fast-path call can observe a partially-deleted epoch vote set, causing `getExpectedGovernance` to derive governance that differs from what the block proposer embedded, making `VerifyGov` reject a valid block or accept an invalid one, splitting the chain.

### Finding Description
In `rewind.go`, `RemoveVotesAfter` ranges over `h.groupedVotes` and its inner maps without holding `h.mu`, then acquires and releases `h.mu.Lock()` for each individual `delete`. This creates two issues: (1) a Go data race between the unlocked range and concurrent `AddVote` writes; (2) a logical race where `getVotesInEpoch`'s `maps.Copy` (under `h.mu.RLock()`) executes between two consecutive deletes, copying a partially-deleted vote set. `getExpectedGovernance` then aggregates this incomplete set into a `GovData` that does not match the block header's governance, causing `VerifyGov` to return `ErrGovVerification`.

### Impact Explanation
Consensus divergence: nodes that hit the race window compute a different expected governance than nodes that do not, causing them to disagree on block validity. This is a chain split on honest nodes.

### Likelihood Explanation
Chain reorgs are a normal network event triggerable by any peer. The race window is small but non-zero and grows with the number of votes being removed. Under load or targeted reorg spam, the probability of hitting the window is non-negligible.

### Recommendation
Hold `h.mu.Lock()` for the entire duration of `RemoveVotesAfter` (and `RemoveGovAfter`), not per-delete:

```go
func (h *headerGovModule) RemoveVotesAfter(blockNum uint64) {
    h.mu.Lock()
    defer h.mu.Unlock()
    dirty := false
    for epochIdxIter, votes := range h.groupedVotes {
        for blockNumIter := range votes {
            if blockNumIter > blockNum {
                dirty = true
                delete(h.groupedVotes[epochIdxIter], blockNumIter)
                if len(h.groupedVotes[epochIdxIter]) == 0 {
                    delete(h.groupedVotes, epochIdxIter)
                }
            }
        }
    }
    // release lock before calling VoteBlockNums (which also takes RLock)
    h.mu.Unlock()
    if dirty {
        WriteVoteDataBlockNums(h.ChainKv, h.VoteBlockNums())
    }
}
```

The same fix applies to `RemoveGovAfter`. [7](#0-6)

func (h *headerGovModule) getVotesInEpoch(epochIdx uint64) map[uint64]headergov.VoteData {
	pBorder := ReadLowestVoteScannedEpochIdx(h.ChainKv)
	if pBorder == nil {
		panic("lowest vote scanned epoch index must exist")
	}
	border := *pBorder

	if border <= epochIdx {
		logger.Debug("Scanning votes fastpath")

		h.mu.RLock()
		defer h.mu.RUnlock()
