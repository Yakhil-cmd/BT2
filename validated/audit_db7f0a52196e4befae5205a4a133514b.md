This confirms the vulnerability: `verify_signature` in `Shipit::WebhooksController` and the `repository` resolution in `EditedHandler` derive their organization identity from two *independently attacker-controlled* JSON paths of the same unsigned POST body.

### Title
Cross-organization webhook signature bypass allows attacker to mutate another org's PullRequest record - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify against using `params.dig('repository','owner','login')` [1](#0-0) , while `EditedHandler#repository` (and `#pull_request`) resolves the target `Shipit::Repository`/`Shipit::PullRequest` using the separate `params.repository.full_name` field [2](#0-1) . Because these are two independent fields in the same attacker-supplied JSON body, an attacker can set `repository.owner.login` to an org with no `webhook_secret` (passing signature verification trivially) while setting `repository.full_name` to a *different, protected* org/repo, causing `EditedHandler#process` to write attacker-controlled PR data onto that unrelated repository's tracked PR.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never enforces:
`params.repository.owner.login == params.repository.full_name.split('/').first`

In real GitHub payloads this is always true, but nothing in this engine validates it, and the attacker fully controls the raw POST body.

Path:
1. `WebhooksController#verify_signature` (before_action) computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and looks up `Shipit.github(organization: repository_owner)` [3](#0-2) . If that org (`org-x`) has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` returns `true` unconditionally: `return true unless webhook_secret` [4](#0-3) .
2. The `EditedHandler`'s `ExplicitParameters` schema only requires `repository.full_name` [5](#0-4) , it never requires or cross-checks `repository.owner.login`.
3. `EditedHandler#repository` calls `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, which parses `full_name` independently (`repo_owner, repo_name = github_repo_name.downcase.split('/')` and does `find_by`) [6](#0-5) , resolving to `org-y/protected-repo`.
4. `EditedHandler#pull_request` joins `stack: :repository` filtering by that resolved `repository.id` and `params.number` [7](#0-6) .
5. `#process` calls `pull_request.update(github_pull_request: params.pull_request)` with the fully attacker-controlled `pull_request` hash (title, head sha/ref, additions/deletions, labels) [8](#0-7) .

None of the existing guards catch this: `verify_signature` only authenticates that the sender knows `org-x`'s secret (or that `org-x` has none), not that the payload's `full_name` belongs to `org-x`; `drop_unhandled_event` only checks the event type exists; the `ExplicitParameters` schema validates types/presence, not owner consistency; `Repository.from_github_repo_name` performs no ownership/organization cross-check against the verified signature's organization.

### Impact Explanation
An unprivileged attacker who controls a webhook-emitting repository under any organization with no (or a leaked/weak) `webhook_secret` can forge a `pull_request` "edited" webhook body whose `repository.owner.login` names their own unprotected org (to pass signature verification) but whose `repository.full_name` names an arbitrary victim org/repo tracked by Shipit. This lets them overwrite `github_pull_request` (title, `head.sha`, `head.ref`, additions/deletions, labels) on any `Shipit::PullRequest` in the victim's stack whose PR `number` they can guess or brute-force (PR numbers are small sequential integers, trivially enumerable). Since `head.sha`/`head.ref` are later consumed for merge-queue/merge decisions, this is a cross-repository/cross-tenant integrity break matching "a payload for one repository mutating another's stack" - Critical severity.

### Likelihood Explanation
Preconditions are modest and realistic in multi-tenant Shipit deployments: only one organization anywhere in the Shipit installation needs to have no `webhook_secret` configured (or the attacker needs any repo under an org with a weak/leaked secret) - the victim org can be fully secured. The attacker needs no Shipit credentials, no GitHub App access, and no relationship to the victim org; they only need the ability to POST arbitrary JSON to the public `POST /webhooks` endpoint (this is an unauthenticated HTTP endpoint by design) and knowledge/guess of a PR `number` in the victim stack. This is directly repeatable against any number of victim repositories/PRs from a single unprotected source org.

### Recommendation
In `WebhooksController#verify_signature` and/or `EditedHandler` (and all sibling PR handlers using the same pattern), enforce that the organization used to select the verifying `GitHubApp`/secret matches the organization embedded in `repository.full_name` used for record resolution — e.g., derive `repository_owner` consistently from `full_name.split('/').first` in one place, or explicitly assert `params.repository.full_name.split('/').first.casecmp?(repository_owner)` before processing, rejecting mismatches with `head(422)`.

### Proof of Concept
Minitest plan (no live GitHub):
1. Seed `org-x` with a `Shipit::GitHubApp`/config that has no `webhook_secret` (or stub `Shipit.github(organization: 'org-x')` to return an app with `webhook_secret: nil`).
2. Seed `org-y/protected-repo` `Shipit::Repository`, a `Shipit::Stack`, and a `Shipit::PullRequest` with `number: 42` and an initial `github_pull_request` hash (e.g., `title: "legit"`, `head: {sha: "aaa...", ref: "main"}`).
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or any value, since `org-x` has no secret), and JSON body:
   ```json
   {
     "action": "edited",
     "number": 42,
     "pull_request": { "...attacker-controlled fields, head.sha=evilsha..." },
     "repository": { "owner": {"login": "org-x"}, "full_name": "org-y/protected-repo" },
     "sender": {"login": "attacker"}
   }
   ```
4. Assert response is `200 OK` (not `422`).
5. Assert `pull_request.reload.github_pull_request['head']['sha'] == 'evilsha'` and `title` reflects attacker-supplied value — i.e., the equality `params.repository.owner.login ("org-x") == full_name.split('/').first ("org-y")` is false, yet the write against `org-y`'s row succeeded, proving the missing binding check.
