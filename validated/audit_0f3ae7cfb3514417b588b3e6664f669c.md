### Title
Webhook signature verification org (`repository.owner.login`) is not bound to the repository record (`repository.full_name`) mutated by handlers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`verify_signature` selects which GitHub App/org secret to verify the HMAC signature against using `repository_owner`, which is parsed from `params.dig('repository', 'owner', 'login')` in the same untrusted JSON body. Handlers (`Handler#stacks`, `Handler#repository_name`) separately read `payload.dig('repository', 'full_name')` from that same body to locate the `Repository`/`Stack` to mutate. Because these are two independent fields inside a body the attacker fully controls, an attacker who owns a real, registered organization (with a known `webhook_secret`) can craft a body where `repository.owner.login` matches their own org (so verification passes with their own secret) while `repository.full_name` names a victim's repository (so the handler mutates the victim's stack).

### Finding Description
The claimed binding is: `organization_that_verified_signature (repository.owner.login) == organization_owning_the_repository_mutated (repository.full_name's owner)`.

`verify_signature` computes:
```
github_app = Shipit.github(organization: repository_owner)   # repository_owner = params.dig('repository','owner','login')
verified = github_app.verify_webhook_signature(sig, request.raw_post)
``` [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves a per-org config only when the deployment is running in multi-org mode (`github_default_organization` non-nil); it uses `github_app_config(organization)`, i.e. it picks the secret keyed by the attacker-controlled `organization` string: [3](#0-2) 

Once verification succeeds, `create` dispatches the raw, unverified-for-consistency body to handlers:
```
params = JSON.parse(request.raw_post)
Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [4](#0-3) 

Handlers locate the target `Repository`/`Stack` using a *different* field of the same body, `repository.full_name`, never cross-checked against `repository.owner.login`:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler#process` then calls `stack.sync_github` for every matching stack: [6](#0-5) 

Exploit flow: attacker owns/configures an org `attacker` that is a legitimate, registered organization in Shipit's multi-org GitHub App config (so attacker knows/controls `attacker`'s `webhook_secret`). Attacker crafts a raw JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker" }, "full_name": "victim/repo" }
}
```
Attacker computes `X-Hub-Signature: sha1=HMAC(attacker_webhook_secret, raw_body)` themselves (no GitHub relay needed - this is a direct POST to `/webhooks`). `verify_signature` reads `repository.owner.login` = `attacker`, fetches `attacker`'s `GitHubApp`, and the HMAC matches because the attacker signed with their own known secret over the exact body they crafted — verification passes. The handler then reads `repository.full_name` = `victim/repo`, resolves `Repository.from_github_repo_name('victim/repo')`, and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stacks, causing GitHub sync/mutation against a repository the attacker never authenticated for.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type exists; `ExplicitParameters` schemas (e.g. `PushHandler.params`) only validate presence/type of `ref`/`after`, not repository identity; there is no code anywhere that asserts `repository.owner.login == repository.full_name.split('/').first`.

### Impact Explanation
A payload verified under one organization's secret mutates a repository/stack belonging to a different, unrelated tenant — this is squarely the "payload for one repository mutating another's stack/commit/task" Critical category. The attacker can trigger `sync_github` (and, for `status`/`check_suite` events, commit status writes and check-run refresh jobs) against any repository name they choose, as long as the attacker controls one registered org's webhook secret. This is repeatable for any target repository name and works across the whole multi-tenant fleet configured in `secrets.github`, since the org selection for verification is entirely decoupled from the repository actually acted upon.

### Likelihood Explanation
Requires: (1) the deployment to be running in multi-org GitHub App mode (`github_default_organization` non-nil, i.e. `secrets.github` keyed by org names) — in single-app mode `Shipit.github` ignores the `organization:` argument entirely and always uses the single global secret, so this path only matters in the multi-org configuration; (2) attacker legitimately controls at least one org/repo registered in Shipit with a known `webhook_secret` (a realistic bar for a "webhook-emitting repository owner" as specified in the threat model). Given that, the attack is a single crafted HTTP POST with no dependency on live GitHub relay, fully repeatable and low-cost.

### Recommendation
After successful signature verification, before dispatching to handlers, assert that the repository being acted upon actually belongs to the organization whose secret verified the payload, e.g. compare `repository.full_name.split('/').first.downcase == repository_owner.downcase` (or resolve the `Repository`'s persisted owner/organization and compare it to `repository_owner`), rejecting the request with 422 on mismatch. Do not let `repository.owner.login` and `repository.full_name` be trusted as independently-sourced facts within the same request.

### Proof of Concept
Minitest plan for `test/controllers/webhooks_controller_test.rb` (multi-org mode):
```ruby
test "signature valid for attacker org must not authorize mutating victim repo" do
  # Arrange: multi-org secrets config with orgs "attacker" and "victim", each with distinct webhook_secret
  # Repository/Stack fixtures exist for "victim/repo" but not for "attacker/repo"

  body = {
    ref: 'refs/heads/master',
    after: 'deadbeef',
    repository: { owner: { login: 'attacker' }, full_name: 'victim/repo' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_webhook_secret, body)}"

  @request.headers['X-Github-Event'] = 'push'
  @request.headers['X-Hub-Signature'] = signature

  victim_stack = shipit_stacks(:victim_repo_stack)

  assert_no_enqueued_jobs do
    post :create, body:, as: :json
  end
  assert_response :unprocessable_entity  # currently FAILS: response is :ok and GithubSyncJob is enqueued for victim_stack
end
```
Assertion on both sides of the binding: `repository_owner` (`attacker`, used to select the verifying secret) must equal the owner implied by `repository.full_name` (`victim`, the repository actually mutated) — the test demonstrates they diverge and the request is nonetheless accepted and dispatched to `PushHandler`, enqueuing `GithubSyncJob` against `victim_stack`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
