### Title
Cross-repository commit status forgery via unscoped `StatusHandler` webhook processing - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `status` webhook event is processed by `Shipit::Webhooks::Handlers::StatusHandler`, which updates commit statuses purely by matching `sha` against the entire `Commit` table, without ever checking that the `sha` belongs to a stack/repository owned by the GitHub organization whose webhook secret authenticated the request.

### Finding Description
`WebhooksController#verify_signature` selects the signing key by looking up `Shipit.github(organization: repository_owner)`, where `repository_owner` is derived from the payload's `repository.owner.login` (or `organization.login`) [1](#0-0) [2](#0-1) . This only proves that the request was validly signed by *some* configured GitHub organization's app — it never restricts *which repository's data* the event handler is allowed to mutate.

For most handlers this is safe because the base `Handler#stacks` method scopes lookups through `Repository.from_github_repo_name(repository_name)`, where `repository_name` comes from `payload.dig('repository', 'full_name')` [3](#0-2) , e.g. in `PushHandler#process` and `CheckSuiteHandler#process` [4](#0-3) [5](#0-4) .

`StatusHandler`, however, breaks this pattern entirely: it queries `Commit.where(sha: params.sha)` across the whole database, with no `repository_name`/`stacks` scoping at all, and calls `commit.create_status_from_github!(params)` on every match [6](#0-5) .

This breaks the binding: **organization authenticated (via `repository_owner` / webhook secret) ≠ repository whose commit status is written (any repository containing a commit with that `sha`)**. Any organization legitimately configured in `Shipit.github` (i.e., any customer/tenant onboarded onto a shared Shipit instance, or any org an unprivileged member can trigger a `status` event from) can send a validly-signed `status` webhook naming an arbitrary commit `sha` — including a `sha` that exists only in a completely different organization's/repository's stack — and have Shipit record an attacker-chosen CI state (`success`, `failure`, `pending`) for that foreign commit.

### Impact Explanation
Commit statuses drive Shipit's deployability checks (required statuses gating whether a commit can be deployed/merged). By forging a `success` status for a required CI check on a victim stack's commit that the attacker does not have write access to, an attacker can manipulate deploy-gating state for a repository/organization they do not control, since the webhook signature only proves "some tenant's org sent this," not "this org owns the target commit." This aligns with the "unauthorized deploy" / cross-tenant authorization escalation impact class in a multi-organization Shipit deployment.

### Likelihood Explanation
Exploitability requires only that the attacker control (or trigger CI activity in) any GitHub organization/repository that is configured as a tenant in the same Shipit instance's `Shipit.github` config (as documented for multi-org setups) [7](#0-6) , and that they can guess or learn the target commit `sha` (SHAs are not secret — they are visible in PRs, commit history, CI logs, etc.). No access to the victim repository, no `ApiClient` token, and no privileged Shipit account is needed — only a validly signed `status` webhook from any configured org.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: restrict the `Commit` lookup to commits belonging to `stacks` derived from `payload.dig('repository', 'full_name')`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` (or an equivalent join), so that a status update can only affect commits belonging to the repository that actually triggered the (correctly authenticated) webhook.

### Proof of Concept
1. Shipit is configured with two tenants, `victim-org` (tracking a stack whose commit `abc123` requires a `ci/tests` status to be deployable) and `attacker-org` (an org the attacker can trigger GitHub events in, with its own legitimate `webhook_secret` configured in `Shipit.github`).
2. Attacker triggers (or crafts, if they control the CI integration on their own repo) a `status` event from `attacker-org`'s repository with body:
   ```json
   {
     "sha": "abc123",
     "state": "success",
     "context": "ci/tests",
     "repository": {"full_name": "attacker-org/some-repo", "owner": {"login": "attacker-org"}}
   }
   ```
3. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s legitimate `webhook_secret`, and successfully verifies the (correctly signed by GitHub for that org's own repo) signature [1](#0-0) .
4. `StatusHandler#process` runs `Commit.where(sha: "abc123")`, finds the victim's commit (since `sha` values are global, unscoped lookup), and calls `create_status_from_github!`, recording a forged `success` status for `ci/tests` on the victim's commit [6](#0-5) , potentially marking it deployable despite the attacker having no access to `victim-org`.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
