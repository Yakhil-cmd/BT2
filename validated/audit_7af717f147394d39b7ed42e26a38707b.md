### Title
ERC20Transactor credits the requested amount to XCM holding instead of the amount actually received, breaking accounting for fee-on-transfer/deflationary ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` moves an ERC20 token from a user to the shared `ERC20TransfersCheckingAccount` by calling the token's `transfer()` function and only checking the boolean return value, not the actual balance delta. It then credits the XCM holding register with the full requested `amount` regardless of how much the checking account actually received.

### Finding Description
`withdraw_asset_with_surplus` performs the withdrawal by invoking the target ERC20 contract's `transfer(checking_address, amount)` via `pallet_revive::Pallet::<T>::bare_call` [1](#0-0) . Success is determined solely by decoding the boolean return value of `transfer()`, not by comparing the checking account's balance before and after the call: [2](#0-1) 

If `is_success` is `true`, the code unconditionally constructs `AssetsInHolding` with `Erc20Credit(amount)` — the amount requested by the XCM program, not the amount actually credited to the checking account. This is exactly the bug class in the reported Teller finding: code assumes the transferred amount equals the requested amount, when for fee-on-transfer/deflationary ERC20 tokens the recipient can receive strictly less.

The corresponding `deposit_asset_with_surplus` later moves `amount` back out of the checking account to a beneficiary using the same pattern (call `transfer()`, trust the boolean return) [3](#0-2) .

The `Erc20Credit` imbalance type is explicitly documented as not enforcing real balance constraints: "This type implements the necessary imbalance accounting traits but does not perform runtime-level balance enforcement... the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" [4](#0-3) .

This transactor is wired into Asset Hub Westend's `AssetTransactors` list, reachable from any `pallet_xcm::execute`/XCM program a signed user submits, matching ERC20 contracts by `AccountKey20` address with no allow-list [5](#0-4) . Both `pallet-revive` contract upload/instantiation are permissionless (`EnsureSigned`) on this runtime, and `AllowEVMBytecode` is enabled, so any signed user can deploy an arbitrary ERC20-style token (including a benign-looking fee-on-transfer/deflationary token, not necessarily a maliciously-crafted attacker contract) and interact with it through this transactor.

### Impact Explanation
When a real (non-adversarial) fee-on-transfer or deflationary ERC20 is used: the user's `WithdrawAsset` moves tokens out of their account with an actual on-chain deficit (the checking account receives less than `amount` due to the token's internal fee/burn logic), but the XCM holding register is credited with the full `amount`. If a subsequent instruction in the same XCM program (e.g. `DepositAsset`) then tries to move `amount` back out of the checking account, that transfer will attempt to move more than the checking account actually holds of that token. Depending on the token's semantics this either reverts (causing the whole deposit instruction to fail while the earlier, already-executed `WithdrawAsset` is *not* rolled back — since only individual instructions are wrapped in `transactional_process`, not the whole program) or, for tokens with more permissive internal accounting, could allow the checking account's tracked "virtual" balance across multiple ERC20 assets/users to permanently diverge from its real on-chain balance. In the revert case, the user's real tokens are consumed by the withdrawal but never delivered to the beneficiary, and the actually-transferred (fee-reduced) amount is stranded in `ERC20TransfersCheckingAccount` with no on-chain pallet-level accounting to recover or reconcile it — a permanent loss of user funds. This matches the Medium severity of the source finding: it's a fund-loss/accounting-integrity bug limited to interactions with a specific, non-standard token category, not a generic protocol break, and it does not enable unbacked issuance of first-class runtime assets (only of the externally-tracked ERC20 balance bookkeeping inside the XCM holding register, transient to a single XCM execution).

### Likelihood Explanation
Reaching this code path only requires a signed extrinsic (`pallet_xcm::execute` or equivalent dispatchable) executing a `WithdrawAsset`/`DepositAsset` program referencing an `AccountKey20` location that resolves to some ERC20 contract on Asset Hub — no governance, no privileged role, no malicious peer/validator is needed. Deploying an ERC20 contract with a fee-on-transfer/deflationary transfer function via `pallet-revive` is also permissionless on this runtime (`UploadOrigin`/`InstantiateOrigin` = `EnsureSigned`). The likelihood is moderate: it requires a user to actually use or be tricked into using a fee-on-transfer-style token through this specific transactor path, which is a narrower attack surface than a fully generic accounting bug, but it is fully reachable by an ordinary, unprivileged user with no code execution assumptions beyond deploying/calling a standard-looking ERC20.

### Recommendation
In `withdraw_asset_with_surplus`, read the checking account's ERC20 balance immediately before and after the `transfer()` call (via a `balanceOf` call or equivalent) and credit the XCM holding with the *actual* delta rather than the requested `amount`. Symmetrically, in `deposit_asset_with_surplus`, verify the beneficiary's balance delta matches expectations, or explicitly document/enforce that only tokens with standard, non-deflationary transfer semantics are supported (e.g., by comparing pre/post balances and erroring out on mismatch, similar to how "fee-on-transfer" is typically handled by measuring actual received amounts rather than trusting boolean return values or fixed input amounts).

### Proof of Concept
No local Rust/FRAME integration test was executed for this analog within this session (tool budget exhausted); the existing test suite in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs` (`withdraw_and_deposit_erc20s`, `smart_contract_does_not_return_bool_fails`, `expensive_erc20_runs_out_of_gas`) already demonstrates the harness pattern for exercising `ERC20Transactor` end-to-end via `PolkadotXcm::execute` with a compiled Solidity fixture and confirms the transactor trusts the contract's boolean return value without balance verification. A concrete reproduction would extend these fixtures with a `MyTokenFeeOnTransfer`-style contract (`transfer()` that moves `amount * (1 - fee_bps)` to `to` while returning `true`), execute the same `withdraw_asset`/`deposit_asset` XCM as in `withdraw_and_deposit_erc20s`, and assert that (a) the sender's ERC20 balance decreases by the full `amount`, (b) the `ERC20TransfersCheckingAccount` balance for that token does not match what the holding register believes it should be, and (c) the beneficiary either receives less than `amount` or the deposit instruction fails while the withdrawal is not rolled back. This was not run; the analysis is based on static code inspection of `erc20_transactor.rs` and its wiring, not on an executed test with observed pass/fail results.
