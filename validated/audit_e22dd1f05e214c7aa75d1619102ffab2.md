## Analysis

I found a concrete analog: the `spender_attested` asset feature lets the asset **definer** (an unprivileged asset issuer, one of the personas explicitly in scope) unilaterally revoke the ability of any existing token holder to move their coins, at any time, with a single `asset_attestors` message — exactly the "owner can freeze withdraws" pattern from the Tigris report, mapped onto ocore's asset/attestation mechanism.

### Title
Asset definer can freeze any existing holder's funds at will via `asset_attestors` message on `spender_attested` assets - (File: validation.js)

### Summary
Assets defined with `spender_attested: true` require every output/input address to currently be attested by one of the asset's attestors [1](#0-0) . The attestor list is not fixed at asset creation — the definer can publish a new `asset_attestors` unit at any time, and the latest such list (by DAG level) fully replaces the previous one [2](#0-1) . Validation of this update message only checks the shape of the attestor list and the asset reference, it never validates that previously-transacted holders remain attested or requires any timelock/notice [3](#0-2) [4](#0-3) .

### Finding Description
When an asset is created with `spender_attested: true`, the definer supplies an initial attestor list, and validation only enforces the list is well-formed [5](#0-4) . This list is not immutable: `readAsset` always re-reads the *most recent* `asset_attestors` unit for the asset (ordered by DAG `level`/`rowid`, i.e. the latest one wins) [2](#0-1) .

For every payment (issue or transfer) of a `spender_attested` asset, both the sender and the recipient addresses must currently appear in the `attestations` table under one of the attestor addresses from that latest list, checked via `filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors` [6](#0-5) , and enforced in `validatePayment`/`validatePaymentInputsAndOutputs` ("none of the authors is attested" / "some output addresses are not attested") [7](#0-6) [1](#0-0) .

Because the definer alone controls the attestor list (there is no separate governance, timelock, or cosigning requirement on `asset_attestors` messages beyond the definer being the single author), the definer can:
1. Sell/issue a `spender_attested` token that many holders acquire while attested.
2. Later publish a new `asset_attestors` unit removing all attestors (or replacing them with an attestor who will never re-attest existing holders), instantly invalidating every future transfer, issue, or output for those addresses — freezing all holders' balances of that asset permanently, with no way for holders to react beforehand since there is no delay between publication and effect (unlike a timelock, which the Tigris report argued should let users exit before a malicious change lands).
3. Combine this with `cosigned_by_definer: true` or `issued_by_definer_only` to make redemption/further movement additionally definer-gated [8](#0-7) , compounding the freeze.

This mirrors the Tigris finding precisely: a single "owner"/definer key holds unilateral, instantaneous power to prevent users from moving their already-owned funds, and this power is layered on top of a design that (per the external report's mitigation-target) is exactly the kind of centralization that undermines any downstream trust assumptions (e.g., an AA or DEX built to trade this asset, or LPs of this asset, cannot exit before the freeze takes effect).

### Impact Explanation
Any holder of a `spender_attested` asset can have their balance made permanently untransferable by the asset definer at any time after acquisition, with no warning period and no way for holders to preemptively withdraw. This is a direct "AA/asset fund freezing" impact matching the required "AA fund loss or freezing" outcome, reachable purely by a single asset-issuer-authored unit (`asset_attestors`) that any unprivileged issuer address can post. If the asset is used as backing/collateral inside an AA (e.g., a DEX, vault, or stablecoin-like AA built on ocore), the AA's funds denominated in that asset also freeze, since AA logic cannot bypass `validatePaymentInputsAndOutputs`'s attestation check.

### Likelihood Explanation
High for any asset explicitly built with `spender_attested: true` (a legitimate, documented feature, e.g. for compliance/KYC use-cases) — the freeze requires only one ordinary `asset_attestors` message from the definer, no special privileges beyond being the original asset definer, no consensus/timelock delay, and no on-chain restriction preventing an empty or hostile attestor list from being pushed. This is not a bug in unit/DAG validation logic itself but an inherent centralization property of the `spender_attested` asset type that is not disclosed/mitigated at the protocol layer (no minimum notice period, no restriction such as "cannot decrease attested set for already-transacted addresses").

### Recommendation
- Add a grace/notice period (e.g., minimum MCI delay) before a new `asset_attestors` list becomes enforceable for already-attested addresses, giving holders time to exit or convert before the freeze takes effect, mirroring the timelock-should-allow-exit principle from the report.
- Alternatively, allow (but do not require) addresses attested under any *previously* valid attestor list unit to remain valid for a bounded window, rather than only ever honoring the single latest list.
- Document prominently in wallet/UI tooling that `spender_attested` assets carry issuer-controlled freeze risk, and surface the current attestor list/definer address to users before they accept such an asset.
- Consider requiring `asset_attestors` updates to be co-signed by a quorum (e.g., existing attestors) rather than the definer alone, when the asset is intended to be trust-minimized.

### Proof of Concept
1. Attacker (or a "rug" issuer) defines asset `X` with `spender_attested: true`, `is_transferrable: true`, and an initial attestor list `[A]` [9](#0-8) .
2. Attestor `A` attests victim addresses `V1..Vn`; victims acquire asset `X` (issue/transfer succeeds because `filterAttestedAddresses` finds them attested) [10](#0-9) .
3. Definer posts an `asset_attestors` message for asset `X` with an empty/only-definer-controlled attestor list `[B]` (definer's own new address, which never attests `V1..Vn`) [11](#0-10) .
4. `readAsset` picks this new unit as the latest attestor list (ordered by level) for all subsequent reads of asset `X` [2](#0-1) .
5. Any subsequent payment attempt by `V1..Vn` fails validation with "none of the authors is attested" / "some output addresses are not attested" [7](#0-6) [12](#0-11) , permanently freezing their balances of asset `X` with no recourse.

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
