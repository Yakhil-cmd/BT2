### Title
Webhook signature is verified against a webhook secret selected from the payload's declared organization, but `StatusHandler` writes commit statuses matched purely by `sha` with no repository/organization scoping - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to HMAC-verify against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, attacker-suppliable JSON body: [1](#0-0) [2](#0-1) 

Once the signature check passes (using the secret belonging to the organization the attacker *chose to declare*), the dispatched `status` event handler ignores that organization/repository entirely and matches target `Commit` rows globally by `sha` alone: [3](#0-2) 

This is the same class of bug as the report's `settleAskMaker()`/`settleAskTaker()` issue: one part of the system verifies a narrow field (`stockInfo.authority`/here, the declared `repository.owner.login`), while a *different* part of the system acts on a broader, unchecked field (the maker's balances/here, any `Commit` matching `sha` regardless of which stack/repository owns it). The binding that should hold - "organization that authenticated == repository that is written" - is broken.

### Finding Description
Shipit supports multiple independent GitHub App configurations, one per organization, each with its own `webhook_secret`: [4](#0-3) 

The webhook endpoint is a single shared route (`POST /webhooks`) for all organizations: [5](#0-4) 

`verify_signature` resolves *which* app/secret to check the HMAC against by reading `repository_owner`, itself derived from the JSON body being verified: [6](#0-5) 

Anyone who legitimately administers **any one** GitHub organization/App connected to this Shipit instance knows that org's `webhook_secret` and can therefore produce a validly-signed request as long as `repository.owner.login` in the body names *their own* org. Nothing ties the rest of the payload's semantic content (the `sha`, `branch`, or `repository.full_name` actually acted upon by the handler) to that same organization.

The dispatched handler for the `status` event does not reuse `repository_owner`/`repository.full_name` at all - it queries `Commit` globally by `sha`: [7](#0-6) 

Other handlers correctly scope via the base `Handler#stacks`, which filters by `Repository.from_github_repo_name(repository_name)`: [8](#0-7) 
but `StatusHandler` bypasses that helper entirely, so the equality "organization that authenticated == repository the status is written to" is never enforced for this event type. Only the fields `sha`/`state`/etc. are covered by the handler's own param whitelist, but crucially the *repository ownership* of the target commit is not checked against the org whose secret validated the signature.

### Impact Explanation
A commit `sha` is frequently public information (visible on GitHub, in PR URLs, in CI logs, etc.), even for repositories the attacker has no write access to. Using only the `webhook_secret` of an organization/App the attacker legitimately controls (e.g., their own onboarded org in a shared Shipit instance), the attacker can forge a `status` webhook with:
- `repository.owner.login` = their own org (passes signature check)
- `sha` = the head commit of a target victim stack in a completely different organization
- `state` = `success`, `context` = whatever `ci.require` context that victim stack demands

This injects a fabricated passing CI status onto the victim's commit: [9](#0-8) 
which flips `Commit#deployable?` to `true`, which in turn can unblock `stack.trigger_deploy`/continuous deployment for the victim's stack: [10](#0-9) [11](#0-10) 

This satisfies the "unauthorized deploy" High-severity impact criterion: an attacker who never had any permission on the victim's stack/organization causes an unauthorized/CI-bypassed deploy to occur there, purely by forging status webhooks signed with their own, unrelated org's secret.

### Likelihood Explanation
Requires only: (1) the attacker legitimately administers at least one GitHub organization/App already connected to the shared Shipit instance (a low bar in any multi-tenant/multi-org Shipit deployment, and explicitly a supported configuration per `config/secrets.development.shopify.yml`), and (2) knowledge of a target commit `sha` in another onboarded stack, which is commonly public. No `ApiClient` token, `webhook_secret` of the *victim* org, GitHub App private key, or privileged Shipit account is required - only knowledge of one's own, legitimately-issued webhook secret for an unrelated org.

### Recommendation
`StatusHandler` (and any other handler that does not go through `Handler#stacks`) must scope its query by the `repository.full_name` from the same payload, and that `repository.full_name`'s owner must be checked to equal `repository_owner` used during signature verification - i.e., enforce that the organization whose secret validated the signature is the same organization that owns the repository being written to. More generally, `WebhooksController#verify_signature` should pass the resolved organization down to handlers (or handlers should independently re-derive and check it) so that every write is scoped to the authenticated organization, not merely the declared one.

### Proof of Concept
1. Attacker legitimately owns/administers organization `AttackerOrg`, onboarded into the shared Shipit instance with `webhook_secret = S`.
2. Attacker identifies a target Shipit stack belonging to `VictimOrg/victim-repo`, and a specific pending/unmerged commit `sha = X` on that stack (obtainable from GitHub's public commit history or the PR page).
3. Attacker crafts a `status` webhook body:
   ```json
   {
     "sha": "X",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "AttackerOrg" } }
   }
   ```
4. Attacker computes `X-Hub-Signature = sha1=HMAC(S, body)` using their own known secret `S`, sets `X-Github-Event: status`, and POSTs to the shared `/webhooks` endpoint.
5. `verify_signature` resolves `repository_owner = "AttackerOrg"`, fetches `AttackerOrg`'s `webhook_secret`, and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `StatusHandler#process` runs `Commit.where(sha: "X")`, finds the victim's commit (regardless of it belonging to `VictimOrg`), and calls `create_status_from_github!`, injecting a fake `success` status (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`).
7. If `VictimOrg`'s stack has `continuous_deployment` enabled or a deploy is manually triggered, the forged status makes `commit.deployable?` return `true`, permitting a deploy that should have been blocked by real CI.

Note: I was not able to fully verify from the available index whether any additional server-side check (outside the excerpted files) re-validates repository ownership before `create_status_from_github!` is invoked in production; the analysis above is based on the `StatusHandler` and `Handler` base class code shown, which contain no such check.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
