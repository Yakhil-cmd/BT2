### Title
Unhandled exception inside the global `handleJoint` mutex critical section can permanently freeze unit validation - ([File: network.js])

### Summary
The Xen CVE describes a bug class where the p2m lock is left held forever because an error path fails to release it, causing a host-wide hang. `ocore` has an analogous single global mutex, `handleJoint`, that every incoming/posted unit must acquire before validation, and the unlock is only invoked from specific named callbacks of `validation.validate()`. If any code reachable from within that critical section throws synchronously instead of routing through one of those callbacks, the `handleJoint` key is never released, and since it is a single global key (not per-unit or per-address), every future unit (peer-submitted or self-composed) queues forever behind it — the node can no longer confirm any new unit.

### Finding Description
`mutex.js` implements a simple non-timing-out lock: `exec()` pushes the requested key array into `arrLockedKeyArrays` and only calls `release()` when the caller explicitly invokes the returned `unlock` function [1](#0-0) . There is no timeout, no exception safety net, and no way to force-release a key once it is locked — exactly like Xen's p2m lock, which "remains unavailable indefinitely in certain error conditions."

`network.js`'s `handleJoint()` acquires this global `handleJoint` key before calling `validation.validate()`, and the corresponding `unlock()` is called only inside the specific result callbacks (`ifUnitError`, `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, `ifOk`, `ifOkUnsigned`) [2](#0-1) [3](#0-2) . The same global `handleJoint` key is also acquired by the composer save paths (`composer.js`, `divisible_asset.js`, `indivisible_asset.js` `getSavingCallbacks`) for self-posted units and by `joint_storage.js`'s `purgeUncoveredNonserialJointsUnderLock` [4](#0-3) [5](#0-4) , so any hang there stops both remote-unit processing and local wallet/AA/asset-payment posting.

Inside `validation.validate()`, `async.series` runs a chain of validators (`checkDuplicate`, `validateHeadersCommissionRecipients`, `validateHashTreeBall`, `validateParents`, `validateSkiplist`, `validateWitnesses`, `validateAATrigger`, `validateTpsFee`, `validateAuthors`, `validateMessages`) while holding a per-author-address mutex lock, and the final callback only calls `unlock()` after `commit_fn()` completes [6](#0-5) . Deep inside message/output validation (`validatePaymentInputsAndOutputs` → `checkInputDoubleSpend`), the double-spend "accept" path for private assets explicitly does `throw Error("spend proof didn't help: "+err)` in `onDone` [7](#0-6) . Because this throw happens synchronously inside the nested callback chain invoked from within `async.series`'s step function, it is not caught by `async.series`'s error-first convention (`cb(err)` was never called) — it instead propagates as an uncaught JS exception straight up through `validate()`'s `mutex.lock(arrAuthorAddresses, ...)` closure, and further up through the outer `handleJoint` mutex closure in `network.js`, without ever reaching the `unlock()` calls in either `validation.validate`'s error/success branches or `handleJoint`'s callback handlers. The result: both the per-author mutex key(s) and the global `handleJoint` key remain permanently locked in `arrLockedKeyArrays`, exactly mirroring the Xen p2m-lock-stuck-forever condition, since `mutex.js` has no exception guard or timeout to recover from a thrown error inside `exec`'s `proc`.

This throw is reachable by any private-asset issuer/holder or double-spender: crafting a private-asset unit whose divisible/indivisible payment message triggers the "accept doublespend, then fail spend-proof verification" branch (`err` truthy after `acceptDoublespends`'s private-write branch) causes `onDone` to throw while `!conf.bLight` (i.e., on any full/hub node validating this unit), permanently wedging that node's single `handleJoint` lock.

### Impact Explanation
Because `handleJoint` is a single, global, unqualified key used to serialize essentially all unit-validation on the node (remote joints via `network.js`, and self-composed base/divisible/indivisible-asset joints via composer/asset modules), a permanent lock leak here means the node can never again validate or save any unit — new units queue in `mutex.js`'s `arrQueuedJobs` indefinitely. This matches the "network unable to confirm new units" impact bucket: a single crafted private-asset unit causes a full/hub node to stop processing the entire DAG, a node-wide denial of service reachable by an ordinary, unprivileged private-payment counterparty/asset issuer — not a privileged operator, peer, or hub role.

### Likelihood Explanation
Reaching the throw requires: (1) a private asset (`objAsset.is_private`) with a double-spend input that the double-spend checker decides to "accept" (this is a legitimate, attacker-triggerable code path for handling conflicting private-payment spend proofs), and (2) the subsequent spend-proof verification path returning an error to `onDone` while the validating node is not light (`!conf.bLight`, i.e. a full/hub node, which is the node type actually enforcing consensus). Exploitation depends on the private-payment spend-proof/double-spend machinery producing a non-null `err` on this path — this is plausible given the code has an explicit, dedicated `throw` statement anticipating exactly this failure mode ("spend proof didn't help"), suggesting the authors considered it an "should never happen" edge case rather than fully hardened it, similar to how the Xen advisory bug arose from an under-tested error branch.

### Recommendation
- Never `throw` inside code paths reached from within `async.series` step callbacks or inside a mutex-lock closure; instead route the error through the standard `cb(err)` chain so `commit_fn`/`unlock()` are always reached.
- Wrap the body of `mutex.lock`'s `exec(arrKeys, proc, ...)` (or at least the top-level entry points like `handleJoint()`'s `validate` function and `validation.validate()`) in a try/catch (or `try { } finally { unlock(); }`) so any unexpected exception still releases the lock instead of leaking it forever.
- Add a lock-acquisition timeout / watchdog in `mutex.js` that force-releases (and logs/aborts safely) a key that has been held beyond a sane bound, instead of allowing indefinite starvation, mirroring the Xen fix approach of adding recovery from error conditions in lock handling.
- Specifically fix `validation.js`'s `onDone` in `checkInputDoubleSpend` (line ~2297) to call `cb2(err)`/report the error through the normal validation-error channel instead of throwing.

### Proof of Concept
1. As a private-asset holder, construct two conflicting units spending the same private-asset input (a classic double-spend), such that the second unit reaches the "accept doublespend" branch in `checkInputDoubleSpend` for a private, non-light-mode-validating node.
2. Ensure the accompanying private spend-proof fails verification so that `checkForDoublespends`'s final callback invokes `onDone(err)` with a truthy `err`.
3. Post/broadcast this unit to a full/hub node (`!conf.bLight`). `validation.js:2297-2299` executes `throw Error("spend proof didn't help: "+err)` inside the callback chain nested under `async.series` inside `mutex.lock(arrAuthorAddresses, ...)` inside `network.js`'s `mutex.lock(['handleJoint'], ...)`.
4. The thrown exception propagates past all `unlock()` call sites in `validation.validate()` and `handleJoint()`, leaving both the author-address mutex key and the global `handleJoint` key permanently in `arrLockedKeyArrays` (per `mutex.js`'s `release()`/`exec()` design, which has no exception-safety or timeout).
5. Observe that subsequent unit submissions (both from peers and from the node's own wallet/composer, which also lock `handleJoint`) queue indefinitely in `arrQueuedJobs` and are never processed — the node stops confirming new units until restarted.
