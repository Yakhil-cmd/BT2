### Title
Cross-Organization Webhook Forgery via Organization/Repository Binding Mismatch in `WebhooksController#verify_signature` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify a webhook against based on `repository.owner.login` (or `organization.login`) read from the **unauthenticated** request body itself, while every event handler that actually acts on data (syncing commits, unarchiving/labeling/closing PRs, refreshing check runs, creating commit statuses) resolves its target via `repository.full_name` from that same body. These two fields are never bound to each other by the signature, so in a multi-organization Shipit deployment an attacker can pick whichever `repository.owner.login` maps to a laxly-configured (or blank) `webhook_secret` while pointing `repository.full_name` at a completely different organization's tracked repository/stack.

### Finding Description
`verify_signature` computes the org used for verification purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

That org name is passed to `Shipit.github(organization: repository_owner)`, which in the multi-org schema looks up a *per-organization* app config (with its own `app_id`, `private_key`, and `webhook_secret`): [3](#0-2) 

`GitHubApp#verify_webhook_signature` explicitly short-circuits to `true` whenever the selected org's `webhook_secret` is blank/unset — which the docs present as a normal, optional configuration (`webhook_secret: # nil`): [4](#0-3) [5](#0-4) 

Meanwhile, every webhook handler resolves the actual `Repository`/`Stack` to mutate using `repository.full_name` from the very same payload, completely independent of whatever org was used for signature verification: [6](#0-5) [7](#0-6) 

This breaks the equality that should hold: `organization that authenticated the signature == organization owning the repository the handler writes to`. Concretely, if the Shipit instance is configured with two orgs (as `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml` show is supported) and one of them has no `webhook_secret` configured, an attacker can:

1. Craft a JSON body with `"organization": {"login": "<org-with-blank-secret>"}` (or `repository.owner.login` set to that org) and `"repository": {"full_name": "<victim-org>/<tracked-repo>"}`.
2. Send it to the public `/github/webhooks` endpoint (no CSRF protection, no other authentication) with any junk `X-Hub-Signature` header.
3. `verify_signature` resolves `github_app` for the blank-secret org, and `verify_webhook_signature` returns `true` unconditionally regardless of the header value.
4. The event is dispatched to a handler (e.g. `push` → `GithubSyncJob`, `pull_request` closed/opened/reopened/labeled handlers, `check_suite`/`status`) which resolves and mutates the *victim org's* stack/PR state via `repository.full_name`.

### Impact Explanation
This is an unauthenticated write into another organization's Shipit-tracked repository state: forged `push` events trigger `GithubSyncJob` to pull and append commits into the victim's stack (potentially advancing what auto-deploy pipelines consider deployable), and forged `pull_request` events can unarchive/label/close/merge-adjacent PR review stacks belonging to a repository the attacker has no access to. This satisfies the Critical bar of "cross-repository writes / an unauthorized deploy" because the attacker never needed the victim org's `webhook_secret`, GitHub App credentials, or a Shipit session — only knowledge that some other configured org in the same Shipit instance has no (or a guessable) webhook secret.

### Likelihood Explanation
Requires the target Shipit deployment to run in multi-organization mode with at least one configured organization lacking a `webhook_secret` (explicitly documented as an accepted, optional configuration) — a realistic and encouraged setup for organizations that don't need webhook verification for a "throwaway"/internal org. No credentials, session, or GitHub App private key are needed; only the ability to POST to the public webhook endpoint.

### Recommendation
Bind the signature-verification organization to the same identity used for repository resolution: derive the org to verify against from the resolved `Repository`/`Stack` record's own known owner (looked up first via `repository.full_name`), not from a client-supplied field, and reject the request if that owner doesn't match the org whose webhook_secret produced a valid signature. Additionally, disallow (or explicitly warn against) empty `webhook_secret` for any organization once multiple organizations are configured, since a blank secret in one org fully undermines the security of the whole shared endpoint.

### Proof of Concept
Given a `config/secrets.yml` with two GitHub orgs configured (as in `test/dummy/config/secrets_double_github_app.yml`), where `OrgOne.webhook_secret` is blank and `OrgTwo` is the real victim org with a strict secret and a tracked repository "OrgTwo/prod-repo":

```
POST /github/webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-that-exists-on-github>",
  "repository": {
    "full_name": "OrgTwo/prod-repo",
    "owner": { "login": "OrgOne" }
  }
}
```

`repository_owner` resolves to `"OrgOne"`; `Shipit.github(organization: "OrgOne")` loads OrgOne's config whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the bogus `X-Hub-Signature`. The request passes `verify_signature` and is dispatched; `PushHandler` then resolves `stacks` via `repository.full_name` = `"OrgTwo/prod-repo"` and calls `stack.sync_github(expected_head_sha: ...)` on the victim org's stack — a write action the attacker was never authorized to trigger.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
