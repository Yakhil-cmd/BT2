### Title
Unfiltered PR-label-derived environment variables reach `PTY.spawn` for review-stack Commands, bypassing the whitelist that protects task/deploy env — (File: `lib/shipit/task_commands.rb`, `app/models/shipit/review_stack.rb`, `lib/shipit/command.rb`)

### Summary
`Shipit::TaskCommands#env` (and the analogous `DeployCommands#env`) unconditionally merges `@stack.env` into the environment passed to `Command.new`, and for a `ReviewStack` that method injects one entry per PR label (`LABEL_NAME.upcase => "true"`) with no whitelist check. `Command#unbundled_env` forwards this hash verbatim to `PTY.spawn`, unlike task-supplied env which is explicitly filtered through `EnvironmentVariables#permit`/`VariableDefinition`. An attacker who can label their own PR therefore controls an arbitrary environment variable *name* (fixed value `"true"`) for every shell/interpreter process Shipit spawns for that review stack.

### Finding Description
Broken binding (expected but false): `Command#unbundled_env.keys ⊆ deploy_spec.machine_env.keys ∪ deploy_variables.map(&:name)`.

Trace:
- `ReviewStack#env` merges `super` with one entry per label, uppercased, value `"true"`: [1](#0-0) 
- `LabelCapturingHandler#capture_labels` writes attacker-controlled label names into `pull_request.labels` straight from the webhook payload, with no filtering beyond schema shape: [2](#0-1) 
- `TaskCommands#env` merges `@stack.env` directly (no `EnvironmentVariables.permit` call), then separately merges `deploy_spec.machine_env` and `@task.env` — only `@task.env`/deploy variables receive whitelist treatment elsewhere (`filter_deploy_envs`/`filter_rollback_envs`), `@stack.env` never does: [3](#0-2) [4](#0-3) 
- `Command#unbundled_env` merges this env with `BASE_ENV`/`PATH` and passes it straight to `PTY.spawn`: [5](#0-4) 
- `EnvironmentVariables#permit` is the only mechanism that enforces a whitelist, and it is never invoked on `@stack.env`: [6](#0-5) 

This label→env behavior is intentional and already asserted by existing tests (`test/lib/shipit/task_commands_test.rb`, `test/lib/shipit/deploy_commands_test.rb`, `test/models/shipit/review_stack_test.rb`), confirming it is a real, unguarded code path rather than a hypothetical one.

Correction to the question's stated precondition: `PypiDiscovery` only contributes to `discover_deploy_steps` (via `publish_egg`, producing `python setup.py register sdist` / `twine upload`), not to `dependencies_steps!`: [7](#0-6) . There is no auto-discovered `pip install` anywhere in the engine. However, the underlying environment-injection bug is not specific to `install_dependencies`: it applies identically to every `Command` produced by `TaskCommands#env`/`DeployCommands#env`, including `perform` (which does run `publish_egg`'s `python setup.py ...` for auto-discovered PyPI projects) and any `dependencies: override:` step a repo owner writes in `shipit.yml` (e.g. `pip install -r requirements.txt`), which is a common real-world configuration. So the "install_dependencies + PypiDiscovery" narrative in the question is not literally accurate, but the same `TaskCommands#env` unfiltered-merge flaw makes the described PYTHONPATH/`sitecustomize.py` RCE reachable through `install_dependencies` whenever a maintainer's `shipit.yml` invokes Python for dependency installation, and reachable unconditionally through `perform` for any repo with a `setup.py`.

Attacker request: open a PR against a review-stack-enabled repository, commit a `true/sitecustomize.py` (or similarly named) payload at repo root, and cause a `labeled` webhook with label `pythonpath` to be delivered (per this challenge's threat model, the attacker is assumed able to label their own PR).

### Impact Explanation
If exploitable, this is Critical: arbitrary command execution on the deploy host, since attacker-named environment variables (`PYTHONPATH`, `LD_PRELOAD`, `BASH_ENV`, `RUBYOPT`, `GIT_SSH_COMMAND`, `NODE_OPTIONS`, etc.) reach `PTY.spawn` for processes that run as part of the deploy pipeline. Impact is scoped to the attacker's own review-stack (their own PR/branch), not cross-tenant, but it does grant execution before any human code review of the PR contents, on the shared Shipit deploy host, which can affect other stacks sharing that host/cache.

### Likelihood Explanation
Requires: review stacks enabled for the repository, the attacker's PR able to receive a `labeled`/`opened`/`reopened` webhook processed by `LabelCapturingHandler`, and a python (or other env-var-sensitive interpreter) invocation actually occurring in `dependencies`/`deploy` steps for that stack (either via `shipit.yml` `dependencies.override`, or automatically for PyPI-style repos via `perform`). Attacker cost is low (open PR, add label, commit payload file) once these preconditions hold; it is repeatable for every review stack the attacker controls.

### Recommendation
Apply `EnvironmentVariables#permit` (or an equivalent explicit whitelist keyed off `deploy_spec.machine_env`/`VariableDefinition`, and/or a hardcoded deny-list of security-sensitive variable names like `PYTHONPATH`, `LD_PRELOAD`, `BASH_ENV`, `PERL5LIB`, `NODE_OPTIONS`, `GIT_SSH_COMMAND`) to `ReviewStack#env`/`@stack.env` before it is merged in `TaskCommands#env` and `DeployCommands#env`, so label-derived variables are constrained the same way task-triggered env is.

### Proof of Concept
Add to `test/lib/shipit/task_commands_test.rb`:
```ruby
test "#install_dependencies does not leak unwhitelisted PR labels like PYTHONPATH into the spawned env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["pythonpath"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  Shipit::TaskCommands.any_instance.stubs(:deploy_spec).returns(
    stub(dependencies_steps!: ["pip install -r requirements.txt"], machine_env: {})
  )

  command = Shipit::TaskCommands.new(task).install_dependencies.first

  # Broken binding: this currently passes with no whitelist check,
  # proving PYTHONPATH is not filtered against deploy_spec.machine_env/VariableDefinition.
  assert_equal "true", command.env["PYTHONPATH"]
end
```
This demonstrates that `command.env['PYTHONPATH']` is populated purely from the PR label with no whitelist enforcement, matching the broken binding traced above.
