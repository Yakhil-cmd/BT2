### Title
Api::CCMenuController bypasses ApiClient stack scoping, letting a stack-scoped token read the status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` scopes an authenticated `ApiClient` to a single stack when the client has a `stack_id` set, by resolving the requested stack through `stacks.from_param!` rather than `Stack.from_param!`. [1](#0-0)  `Api::CCMenuController` overrides this `stack` accessor and resolves the stack directly from `params[:stack_id]` against the full `Stack` table, discarding the scoping enforced by the base class. [2](#0-1)  This breaks the equality that should hold between "the stack a token authorizes" and "the stack the endpoint actually touches," analogous to the RandomnessCommit report's core issue of a privileged-looking commitment (here, a stack-scoped API token) being usable outside the scope it was meant to be bound to.

### Finding Description
`ApiClient` records can optionally `belongs_to :stack`, and `BaseController#stacks` restricts the visible stack set to that one stack when `current_api_client.stack_id?` is true:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

This is the intended enforcement mechanism for least-privilege, stack-scoped tokens (e.g. the fixture `here_come_the_walrus` client, which is scoped to the `shipit` stack and holds only `read:stack`) [3](#0-2) , and it is exercised/verified in `Api::StacksControllerTest` ("an api client scoped to a stack will only see that one stack"). [4](#0-3) 

However, `Api::CCMenuController` defines its own `stack` method that ignores this scoping:
```ruby
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end
``` [5](#0-4) 

`require_permission :read, :stack` only checks the string permission `"read:stack"` against `ApiClient#permissions`; it never validates that the token's `stack_id` matches the `stack_id` in the request:
```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [6](#0-5) 

So any client holding the generic `read:stack` permission — including one whose `stack_id` restricts it to a single specific stack — can supply an arbitrary `stack_id` in the URL and receive that other stack's CI/build status, name, last build label/time and web URL via the CCMenu XML response. [7](#0-6)  This is confirmed reachable via query-string token auth, which the controller also supports (`authenticate_api_client` overridden to accept `params[:token]`), so no session/cookie is required — only possession of the stack-scoped token. [8](#0-7) 

### Impact Explanation
This matches the "High" bucket defined for this scan: "unauthenticated read of stack state, task streams or deploy output" via a token whose authorized scope does not match what it can actually touch. A token that was deliberately minted to expose only one stack's CI status (e.g. handed to an external CI dashboard or third party integration) can be used to read the deploy/build status of every other stack in the Shipit instance, defeating the purpose of the `stack_id` scoping mechanism.

### Likelihood Explanation
Any holder of a `read:stack`-permissioned `ApiClient` token — regardless of whether it is stack-scoped — can trigger this by simply changing the `stack_id` in the CCMenu request URL/query string. No additional privilege, session, or GitHub credential is required beyond the token itself, and the token can be obtained through the ordinary, documented `CCMenuUrlController#fetch` flow or any other stack-scoped client provisioning path in the app.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the scoped `stacks` collection (i.e. reuse `BaseController#stack`/`#stacks`) instead of querying `Stack` directly, so that a stack-scoped `ApiClient` cannot resolve a `stack_id` outside its assigned stack.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack: A` with permission `read:stack` (as in the `here_come_the_walrus` fixture pattern, or via the normal `ApiClientsController#create` flow with a `stack` association).
2. Using that client's `authentication_token`, issue: `GET /api/stacks/B/ccmenu.xml?token=<token>` where `B` is any other stack in the instance.
3. Observe that the request succeeds (`require_permission :read, :stack` only checks the `read:stack` string permission) and returns stack `B`'s CCMenu XML (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`), even though the token's `stack_id` is `A`, because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped rather than `stacks.from_param!`. [2](#0-1) 

Note: I was not able to independently confirm the exact implementation of `Stack.from_param!` / `.from_param!` (the model method definitions were not found in the indexed code, likely defined via a `to_param`/`FriendlyId`-style concern not covered by the index), so the precise lookup semantics (e.g. whether it matches by numeric id or a composite `owner/name/environment` param) are inferred from usage context rather than verified directly. This does not affect the core finding, since the scoping bypass is in which relation (`Stack` vs `stacks`) the lookup is performed against, not in the lookup method itself.
