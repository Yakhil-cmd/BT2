### Title
`CCMenuController#stack` bypasses `ApiClient#stack_id` tenant scoping via unscoped `Stack.from_param!` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController#stack` resolves the stack through the tenant-scoped `stacks` helper (`stacks.from_param!(params[:stack_id])`), which restricts lookup to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped. `Shipit::Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, so any stack-scoped `ApiClient` token can be used to read CCMenu XML status for any stack in the system, not just the one it is scoped to.

### Finding Description
The binding that should hold for every `Api::BaseController` subclass is:
`stack == stacks.from_param!(params[:stack_id])` where `stacks == current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` (`app/controllers/shipit/api/base_controller.rb` lines 74-80).

`Api::LocksController` does not define `stack` at all, so it inherits the scoped version unmodified — confirmed by `grep` showing zero `def stack` occurrences in `locks_controller.rb`, and its `create`/`update`/`destroy` actions all call the inherited, scoped `stack` (`app/controllers/shipit/api/locks_controller.rb` lines 12-31).

`Api::CCMenuController`, however, redefines `stack` as:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
(`app/controllers/shipit/api/ccmenu_controller.rb` lines 29-31), which resolves against `Stack.from_param!` directly — bypassing the `current_api_client.stack_id` restriction entirely. This is the only controller in `app/controllers/shipit/api/` that overrides `stack` this way; `HooksController` calls the inherited scoped `stack` internally when computing `stack_id` (`app/controllers/shipit/api/hooks_controller.rb` lines 50-52), and `Api::StacksController` uses the scoped `stacks` collection for its own resolution.

Exploit flow: an attacker who holds (or is issued) a legitimate `ApiClient` token scoped to `stack_id: A` can call `GET /api/ccmenu/<stack_id_of_B>.xml` with basic-auth credentials for their own scoped client. `CCMenuController#authenticate_api_client` only authenticates the token (`ApiClient.authenticate(params[:token])`, line 34) — it does not re-check `stack_id` matching. `require_permission :read, :stack` calls `current_api_client.check_permissions!(:read, :stack)`, which validates operation/scope type, not that the target `stack.id` matches `current_api_client.stack_id`. The unscoped `Stack.from_param!` then happily resolves stack `B`, and `show` renders `stack.deploys_and_rollbacks.last` for stack B in the response XML.

### Impact Explanation
An attacker holding an `ApiClient` token scoped to one stack can read deploy/rollback status (id, timestamp, running/not-running) of any other stack in the Shipit instance via the CCMenu XML endpoint, which is designed for unauthenticated-looking polling. This is a cross-tenant unauthorized read of stack state — matching the High severity category ("escalation into ... unauthenticated read of stack state, task streams or deploy output"). It does not by itself achieve command execution or credential exfiltration (only deploy status metadata is exposed), so it is bounded to High, not Critical, unless a stack-scoped token is otherwise obtainable by an unprivileged party — which the scenario in this specific webhook-attacker profile (no `ApiClient` token) would not directly grant. This finding is a real, reproducible controller-level access-control defect, but the specific attacker model described (unprivileged GitHub user, no `ApiClient` token, no session) does not have a path to invoke this endpoint successfully, since `authenticate_api_client` still requires a valid `ApiClient` token.

### Likelihood Explanation
Exploitation requires possession of ANY valid, stack-scoped `ApiClient` credential (basic auth `token`/`token` pair, or `params[:token]` query auth as used by CCMenu). This is a real credential, typically issued to a specific team/repository integration, not something an anonymous internet user without such a token can obtain. Given the stated attacker model (no `ApiClient` token, no session, no secrets), this specific path is not reachable — it requires a precondition (a legitimate but narrowly-scoped API token) outside of the defined "unprivileged attacker" capabilities.

### Recommendation
Change `Api::CCMenuController#stack` to use the inherited scoped resolution:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the override entirely so it falls back to `BaseController#stack`, ensuring `current_api_client.stack_id` scoping applies uniformly across all `Api::BaseController` subclasses.
