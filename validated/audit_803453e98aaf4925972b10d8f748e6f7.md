### Title
Webhook signing organization is decoupled from the repository/commit actually mutated, enabling cross-repository status forgery and continuous-deployment triggering - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, a value taken directly from the untrusted JSON payload (`params.dig('repository', 'owner', 'login')`), [1](#0-0) . Once the signature validates against that organization's secret, the parsed payload is handed to event handlers, which determine what data is actually written using entirely different, unchecked fields of the same payload — e.g. `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [2](#0-1) , and `StatusHandler#process` doesn't even scope by repository at all, looking commits up globally by `sha` [3](#0-2) . Nothing binds the organization whose secret validated the signature to the repository/commit that the handler subsequently mutates.

### Finding Description
This mirrors the `LiquidityPenaltyHook` bug class: a "verified" credential is checked against one part of the state (the organization used to pick the HMAC key), while the actual state mutation acts on a different, unverified part of the same attacker-supplied payload (the repository `full_name` or a bare commit `sha`). The binding that should hold is:

`organization whose secret signed the request == organization/repository whose state is mutated`

but the code never enforces it:
- `verify_signature` picks the HMAC secret via `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [4](#0-3) .
- `create` then dispatches `params` (the full attacker-controlled JSON) unchanged to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) .
- The base `Handler` resolves the repository to act on from `payload.dig('repository', 'full_name')`, a field independent of `repository.owner.login` [6](#0-5) .
- `StatusHandler` is worse: it ignores `repository`/`stacks` entirely and updates any `Commit` in the entire installation matching the attacker-chosen `sha`: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) .

Since a Shipit instance can be configured with multiple organizations, each with its own `webhook_secret` (as shown in the sample config listing `somegithuborg`/`someothergithuborg` each with independent `webhook_secret`) [7](#0-6) , an entity that legitimately controls one configured organization's webhook secret (e.g., an org owner who set up their own GitHub App/webhook integration into the shared Shipit instance) can compute a valid `X-Hub-Signature` for **any** payload body, then set that body's `repository.full_name`/`sha` to reference a completely different organization's Stack/Commit. `verify_signature` only proves "this body was signed with org A's key" — it never proves "and this body only mutates org A's data."

### Impact Explanation
Via `StatusHandler`, an attacker who owns one configured organization can forge arbitrary commit statuses on any commit belonging to any other stack in the instance, by matching an existing `sha`. `Commit#create_status_from_github!` → `add_status` updates `status`, which feeds `Commit#deployable?` (`success? && !blocked?`) [8](#0-7)  and `schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` once a commit becomes deployable under continuous deployment [9](#0-8) . This can cause an unauthorized deploy to be triggered on a stack the attacker has no legitimate access to, satisfying the Critical "unauthorized deploy" impact bar. It also lets an attacker forge commit statuses cross-repository, corrupting CI state relied on for merges/deploys.

### Likelihood Explanation
Requires only that the attacker administers (or has legitimate webhook credentials for) any one organization configured on the shared Shipit instance — not privileged access to the victim organization, no Shipit session, no stolen secret. In any multi-tenant Shipit deployment (which the engine explicitly supports via per-organization `github:` config blocks), this is straightforward to exploit: craft a `status` (or other) webhook JSON body referencing a foreign `sha`/`full_name`, sign it with your own org's known `webhook_secret`, and POST it to `/webhooks`.

### Recommendation
Bind the verified signing organization to the object being mutated: after selecting `repository_owner` and successfully verifying the signature, re-derive/require the repository owner from the same trusted value the signature was checked against, and reject (or scope all handler lookups by) any `repository.full_name`/commit whose owner does not match the verified `repository_owner`/`organization`. Concretely, `Handler#repository_name`/`StatusHandler#process` should filter `Commit`/`Repository` lookups by `stack.repository.owner == verified_organization`, not merely by an unchecked `sha` or `full_name` pulled from the same unauthenticated JSON body that selected the key.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (multi-tenant setup as documented in `docs/setup.md`/`config/secrets.*.yml`).
2. Attacker owns `attacker-org` and therefore knows its `webhook_secret`.
3. Attacker crafts a `status` event JSON body: `{"sha": "<victim commit sha>", "state": "success", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/attacker-repo"}}`.
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over this exact body — `verify_signature` succeeds because `repository_owner` resolves to `attacker-org` and the signature matches that org's secret [10](#0-9) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` [3](#0-2) , which matches the victim's commit (belonging to `victim-org`) regardless of the `repository` field, and marks it successful.
6. If `victim-org`'s stack runs continuous deployment, `Commit#schedule_continuous_delivery` enqueues an unauthorized deploy for that forged-successful commit [9](#0-8) .

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
