### Title
Missing atomic locking around private-asset chain double-spend check allows racing spend of the same private output - (File: private_payment.js)

### Summary
`validateAndSavePrivatePaymentChain()` in `private_payment.js` opens a DB transaction, performs a "check if duplicate / is already spent" `SELECT`, and — only if the row is not already a matching duplicate — proceeds to insert the spending input and mark the source output spent. Unlike the mainline unit-saving path, this critical read-then-write sequence is not protected by the application's `mutex.lock('handleJoint')` serialization primitive that guards unit validation/saving elsewhere in the codebase.

### Finding Description
For public units, every validate-then-save operation is funneled through `mutex.lock('handleJoint')` before touching the DB (see the saving callbacks in `divisible_asset.js` and `indivisible_asset.js`, e.g. `divisible_asset.js:317-324` and `indivisible_asset.js:830-837`), ensuring the DB read (duplicate/double-spend check) and the DB write (insert + mark spent) happen as one atomic step relative to all other unit processing in the node.

`private_payment.js:validateAndSavePrivatePaymentChain` (lines 23-119), however, takes its own connection from the pool and wraps only a `BEGIN`/`COMMIT` transaction around the check-then-insert sequence — it never acquires `mutex.lock('handleJoint')` or any other cross-request lock: [1](#0-0) 

This function is reachable directly from network message handling. Critically, `handleSavedPrivatePayments()` in `network.js` explicitly processes multiple queued private-payment rows **in parallel** with `async.each`, invoking `privatePayment.validateAndSavePrivatePaymentChain` (via `network.js`) concurrently for different rows without any shared mutex: [2](#0-1) 

`handleOnlinePrivatePayment` similarly calls the same unguarded function directly for freshly-arrived private payments: [3](#0-2) 

Because the pad_usb-style pattern here is "no exclusivity guard on a critical read-modify-write of protected state," two private-payment chains addressing the same source output (e.g. two chains claiming to spend the same private output, sent by a colluding/duplicate device message or replayed slightly out of order) can both pass the "not yet spent / not duplicate" `SELECT` inside their own transactions before either commits the `UPDATE ... SET is_spent=1` / `INSERT`. Depending on the storage backend's isolation semantics and connection pooling behavior (the code explicitly supports non-SQLite backends — see `doubleSpendIndexMySQL` handling in `validation.js:2409`), this opens a window where both branches proceed to `indivisibleAsset.validateAndSavePrivatePaymentChain` / `divisibleAsset.validateAndSavePrivatePaymentChain`, exactly mirroring the pam_usb bug class: a non-atomic check-then-act on shared critical state, executed concurrently, where the loser's overwrite (or duplicate insert) is not properly rejected by the intended replay/double-spend guard.

### Impact Explanation
If exploited, this allows a private-asset output to be spent by two different chains that were queued/received concurrently, i.e., a double-spend of a private-asset unit that a receiving node could accept as valid twice before the conflict is detected at stabilization. This directly matches the "double-spend of a stable output" and "node disagreement on validity" impact classes called out in scope, since it corrupts the wallet's private-payment bookkeeping (`outputs`/`inputs` tables) and can allow value to be double-counted before eventual stabilization/consensus reconciliation.

### Likelihood Explanation
Exploitability requires an attacker (or a malfunctioning/malicious paired device or hub-relayed peer) sending two private-payment chains for the same output in close succession so they are processed in the same window — a realistic scenario given `handleSavedPrivatePayments` is explicitly designed to process multiple pending private payments "in parallel." No privileged access is needed; only the ability to send a normal `private_payment`/private-chain message that any correspondent device or hub already can send. Likelihood is Medium: the race window is narrow and backend-dependent (much harder under SQLite's single-writer model, more plausible under a MySQL-backed hub/full node), which is consistent with the CVSS of the analog (`AC:H`).

### Recommendation
Wrap the entire check-then-insert sequence in `private_payment.js:validateAndSavePrivatePaymentChain` with the same `mutex.lock('handleJoint')` (or a dedicated per-(unit,message_index,output_index) lock key) used by the public unit-saving path, so the duplicate/double-spend `SELECT` and the subsequent insert/`is_spent` update are serialized against all other private-chain processing for the same output, not just protected by an unenforced DB transaction boundary.

### Proof of Concept
1. Two private-payment chains, C1 and C2, are crafted (or arrive from two different peers/devices) both claiming to spend the same source output (same `src_unit`, `src_message_index`, `src_output_index`).
2. Both are queued into `unhandled_private_payments` and later picked up by `handleSavedPrivatePayments()`, which calls `async.each` over the pending rows, invoking `validateAndSavePrivatePaymentChain` for C1 and C2 concurrently on separate pooled connections. [4](#0-3) 
3. Each connection independently executes `BEGIN`, runs the duplicate-check `SELECT` in `private_payment.js:62-73` and sees the output as not yet claimed, then proceeds to `assetModule.validateAndSavePrivatePaymentChain(conn, ...)` before either transaction commits. [5](#0-4) 
4. Both transactions `COMMIT`, resulting in two distinct spends recorded against the same private output — a double-spend that the intended duplicate/is_spent guard failed to prevent due to lack of serialization.
