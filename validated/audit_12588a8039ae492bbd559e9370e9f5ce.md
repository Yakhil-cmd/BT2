### Title
Open Redirect via Unvalidated `origin` Parameter in OAuth Callback — ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` redirects the browser to `request.env['omniauth.origin']` after a successful GitHub OAuth login, with no validation that this value points back to the Shipit host. This mirrors the `EmailVerifyBegin` bug class from the report: an attacker-supplied "return" destination is trusted and used to redirect the client's browser after a sensitive operation (email verification there, GitHub sign-in here) without checking it against an allow-list of trusted domains.

### Finding Description
The route mounts the OmniAuth GitHub strategy at `/github/auth/github`, exposing `get '/'` (request phase) and `get/post :callback` [1](#0-0) . When a user is not authenticated, `Authentication#force_github_authentication` redirects them to `github_authentication_path(origin: request.original_url)` [2](#0-1) . The OmniAuth request phase persists this `origin` query parameter across the OAuth round-trip, and on callback it is surfaced as `request.env['omniauth.origin']`.

`GithubAuthenticationController#callback` consumes that value directly:
```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  ...
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
``` [3](#0-2) 

Because `origin` is an ordinary request parameter, an attacker can craft `GET /github/auth/github?origin=https://evil.example.com` (or `//evil.example.com`) and send that link to a victim. There is no allow-list, no `same-origin`/`same-host` check, and no use of a signed/opaque state value — the equality that should hold, "the redirect target after OAuth completion == a URL on the Shipit host", is never enforced. After the victim completes real GitHub authentication (their session cookie, `session[:user_id]`, and `session[:authenticated]` are all set on the legitimate Shipit host at this point), the final `redirect_to(return_url)` sends their browser to the attacker's page.

### Impact Explanation
This is a forced-OAuth-completion / open-redirect chain matching the explicit High-severity bucket "session fixation / forced OAuth completion." An attacker can weaponize the trusted Shipit OAuth flow to funnel a legitimately-authenticated victim to an attacker-controlled page immediately after login, enabling convincing phishing (e.g., a fake "session expired, re-enter your GitHub credentials" page) or token/parameter leakage via `Referer`/query strings from the attacker's landing page. It does not itself leak `github_access_token`, but it abuses the trust boundary of the engine's own authentication redirect, exactly analogous to the reported `domain` parameter flaw where an unfiltered destination is trusted post-verification.

### Likelihood Explanation
The attack requires only that a victim click a link crafted by the attacker (an unprivileged, unauthenticated party) — no repository access, API token, or webhook secret is needed. The vulnerable code path (`callback`) is reached on every successful login through the standard, documented OAuth flow described in `docs/setup.md`, making the trigger trivial to reach.

### Recommendation
Validate `return_url` before redirecting: parse it and confirm the host/scheme matches `Shipit.host` (or is a relative path with no scheme/host component) before calling `redirect_to`. Reject or fall back to `root_path` otherwise, e.g.:
```ruby
def callback
  return_url = safe_return_url(request.env['omniauth.origin'])
  ...
  redirect_to(return_url)
end

def safe_return_url(url)
  return root_path if url.blank?
  uri = URI.parse(url) rescue nil
  return root_path unless uri
  return url if uri.host.nil? # relative path
  return url if uri.host == Shipit.host
  root_path
end
```

### Proof of Concept
1. Attacker sends victim: `https://shipit.example.com/github/auth/github?origin=https://evil.example.com/phish`
2. Victim clicks, is redirected into GitHub's real OAuth consent screen, and approves (trusting the legitimate `shipit.example.com` origin).
3. GitHub redirects back to `.../github/auth/github/callback`; `GithubAuthenticationController#callback` sets `session[:user_id]`/`session[:authenticated]` on the Shipit host, then executes `redirect_to("https://evil.example.com/phish")`.
4. The victim's browser, now authenticated to Shipit, lands on the attacker's page, which can present a phishing UI or capture any leaked parameters.
