### Title
Webhook signature verification authenticates the payload's `organization`/`repository.owner.login`, but every event handler acts on the independent `repository.full_name` field, letting an attacker with one valid organization webhook secret write into unrelated repositories/stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature with by reading `repository.owner.login` (or `organization.login`) out of the untrusted JSON body, then checks the signature against that specific organization's secret. [1](#0-0) 
Once the signature passes, `WebhooksController#create` dispatches the *entire* raw payload to handlers such as `PushHandler` and `StatusHandler`, which independently resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — a completely different field from the one used to pick the verifying secret. [2](#0-1) [3](#0-2) 

### Finding Description
The equality the code implicitly assumes is:
`organization authenticated by verify_signature (repository.owner.login) == organization/repository actually written to by the handler (repository.full_name)`

This holds for genuine GitHub-generated payloads, but the controller verifies the signature over the *raw bytes* the caller submits, and nothing ties `repository.owner.login` to `repository.full_name` — both are attacker-controlled fields inside the same JSON body. An actor who legitimately possesses a valid webhook secret for *some* GitHub organization/App installation known to this Shipit instance (e.g., because they administer that org's GitHub App, or because the instance is shared across teams/orgs) can:

1. Set `repository.owner.login` (and/or `organization.login`) to their own organization, so `Shipit.github(organization: repository_owner)` resolves to the secret they control.
2. Sign the raw body with that secret so `verify_signature` passes.
3. Set `repository.full_name` inside the same payload to an arbitrary *other* repository tracked by Shipit.

Handlers never re-validate that `full_name` belongs to the organization that was authenticated:
- `PushHandler#process` looks up `stacks` (derived from `repository.full_name` via `Handler#stacks`/`#repository_name`) and calls `stack.sync_github(expected_head_sha: params.after)`, letting the attacker force a resync of an arbitrary tracked stack to an attacker-chosen SHA. [4](#0-3) 
- `StatusHandler#process` writes a GitHub commit status for any `sha` supplied, on any commit belonging to any tracked repository, regardless of which organization was authenticated. [5](#0-4) 
- The pull-request family of handlers (`OpenedHandler`, `LabeledHandler`, `LabelCapturingHandler`, etc.) similarly resolve their target repository/stack purely from `params.repository.full_name`, and can archive/unarchive review stacks or mutate pull-request/label state for repositories outside the authenticated organization. [6](#0-5) [7](#0-6) 

### Impact Explanation
This crosses the "cross-repository writes" boundary explicitly called out as a valid High/Critical impact: an actor authenticated only for organization A can inject webhook-driven state changes (sync triggers, commit statuses that gate merge-queue/deploy decisions, review-stack archive/unarchive, PR label capture) into repository/stack B, which belongs to an entirely different, unauthenticated organization. Because commit statuses influence `deployable_status`/merge-queue eligibility (see `Commit#create_status_from_github!` usage in tests), this can be leveraged to manipulate which commits appear deployable in a stack the attacker has no legitimate relationship with.

### Likelihood Explanation
Exploitability requires the attacker to control a valid webhook secret for at least one organization known to the Shipit instance — this is a materially weaker precondition than requiring a Shipit user session, `ApiClient` token, or the target repository's own secret, since Shipit is designed to be a multi-tenant/multi-organization deploy dashboard where many independent GitHub orgs/App installations are configured. The attacker never needs credentials tied to the victim organization or repository, only to any one organization onboarded to the same Shipit instance, and the request is a single unauthenticated HTTP POST to `/webhooks`.

### Recommendation
After `verify_signature` succeeds, re-derive `repository_owner`/organization strictly from the field(s) actually used by the handlers (`repository.full_name`'s owner segment), or, more robustly, verify that the resolved `Repository`/`Stack` (via `repository.full_name`) actually belongs to the same GitHub organization/App installation whose secret validated the signature before invoking any handler. Reject the request (422) if the two do not match, mirroring the `inactiveAuction`-style pattern from the analog report: gate all repository-mutating logic behind a check that ties the authenticated principal to the resource being mutated.

### Proof of Concept
1. Attacker administers (or has compromised) the GitHub App/organization "attacker-org", which is registered with this Shipit instance and has its own webhook secret.
2. Attacker crafts a JSON payload for the `status` event:
```json
{
  "sha": "<victim-repo-commit-sha>",
  "state": "success",
  "context": "ci/attacker",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature` using the "attacker-org" webhook secret over the raw body and sends it to `POST /webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` to `"attacker-org"`, fetches that org's app, and the signature validates.
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) finds commits by `sha` inside `victim-org/victim-repo` (an entirely different, unauthenticated org) and creates a forged `success`/`failure` status on them, unrelated to any check performed against "attacker-org".

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
