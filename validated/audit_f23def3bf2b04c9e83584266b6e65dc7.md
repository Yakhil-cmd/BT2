### Title
Unscoped signer-key grant lets any granted `signer-manager` perform arbitrary stacking actions on behalf of a stacker - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar`'s signer-key grant mechanism computes its authorization message hash over only `{topic: "grant-authorization", signer-manager, auth-id}`, deliberately omitting `pox-addr`, `reward-cycle`, `period`, and `max-amount` — the very fields that pox-4's `get-signer-key-message-hash` includes to scope a signature to one specific stacking action. [1](#0-0)  This is structurally the same bug class as the DiamondCut proposal-hash omission: a signature/authorization commitment leaves out the parameters that should have constrained what can later be executed, so anything holding the resulting authorization can act far outside the scope the signer actually agreed to.

### Finding Description
In pox-4, a signer's authorization for a specific stacking action is bound to `pox-addr`, `reward-cycle`, `topic`, `period`, `auth-id`, and `max-amount` via `get-signer-key-message-hash`, and `verify-signer-key-sig`/`consume-signer-key-authorization` check and consume that exact tuple, single-use, per action. [2](#0-1) [3](#0-2) 

In pox-5, `grant-signer-key` verifies a one-time signature over `get-signer-grant-message-hash(signer-manager, auth-id)` — a hash that intentionally excludes `max-amount`, `period`, `reward-cycle`, and `pox-addr`, as the contract's own comment states. [4](#0-3)  Once verified, the contract sets a durable, unscoped record `signer-key-grants {signer-key, signer-manager} -> true` with no amount, period, cycle, or pox-addr constraint. [5](#0-4)  Subsequent checks via `verify-signer-key-grant` only assert that this `{signer-key, signer-manager}` pair exists — they do not re-check any per-action scope (amount, cycle, period, pox-addr): [6](#0-5) 

The single signature the stacker produced (over just `signer-manager` + `auth-id`) is treated by the contract as blanket, indefinite consent for that `signer-manager` contract to represent the signer key in all future stacking-related calls that key the `signer-manager` trust relationship off `signer-key-grants`, since none of `pox-addr`, `reward-cycle`, `period`, or `max-amount` were ever committed to by the stacker's signature. This mirrors the Diamond bug: the "id" the user actually signs off on (the grant) is computed from a subset of the data that will later determine what code/action gets executed, so a party controlling the unconstrained side (here, the `signer-manager` contract or whoever controls it) can drive stacking actions — amounts, periods, and reward cycles — that the signer never explicitly authorized via signature.

### Impact Explanation
This breaks the "an unsigned stacking action" invariant: the signer's cryptographic authorization is supposed to gate what a delegate/manager contract can do with the signer key, but because the amount/period/cycle/pox-addr are not part of the signed message nor of the persisted grant record, a `signer-manager` contract (which the stacker trusted only for the initial registration event denoted by one `auth-id`) can subsequently invoke stacking operations gated by `verify-signer-key-grant` with arbitrary amounts, periods, reward cycles, and pox-addr values that were never presented to or signed by the signer key holder. This can result in signing weight, reward-slot commitments, or locked-fund parameters exceeding what the signer actually authorized — matching the High-severity criterion "signing weight or reward slots exceeding locked value, an unsigned stacking action."

### Likelihood Explanation
This requires only an unprivileged interaction: a stacker signs one grant message for a `signer-manager` contract (as designed, e.g. onboarding), and that manager contract (which could be malicious, compromised, or simply buggy) then calls other pox-5 entry points that rely on `verify-signer-key-grant` for authorization instead of a scoped per-action signature. No admin/miner/bond-pause privilege is needed — the `signer-manager` is by design an ordinary contract the stacker interacts with under `contract-caller` checks. The likelihood of exploitation depends on whether other pox-5 functions actually gate execution solely via `verify-signer-key-grant` without additional independent amount/period checks; this could not be fully confirmed within the available search budget (see below).

### Recommendation
Bind `get-signer-grant-message-hash` (and the persisted `signer-key-grants` record) to the same scoping fields used elsewhere in the contract for stacking authorizations — at minimum `pox-addr`, `reward-cycle`/valid-cycle range, `period`, and `max-amount` — or, if the grant is intended only to authorize the registration event (not open-ended stacking), ensure every downstream stacking function that can move funds independently re-verifies a freshly scoped, single-use signer authorization (as pox-4 does with `consume-signer-key-authorization`) rather than relying on the long-lived, unscoped `signer-key-grants` map alone.

### Proof of Concept
1. Stacker signs `get-signer-grant-message-hash(signer_manager, auth_id)` — a hash containing only `topic`, `signer-manager`, and `auth-id`. [7](#0-6) 
2. `signer_manager` contract calls `grant-signer-key`, which verifies the signature and permanently sets `signer-key-grants {signer-key, signer-manager} = true`. [8](#0-7) 
3. Any later pox-5 function that authorizes an action solely via `verify-signer-key-grant` will succeed for that `{signer-key, signer-manager}` pair regardless of the `pox-addr`, `reward-cycle`, `period`, or amount involved, because none of those values were part of the original signed commitment or the stored grant record. [6](#0-5) 
4. This lets `signer_manager` perform stacking actions with parameters (amount, cycle, period, pox-addr) the signer never reviewed or signed, until `revoke-signer-grant` is explicitly called by the signer-key holder. [9](#0-8) 

**Note on completeness:** I was unable to exhaustively confirm, within the remaining search budget, exactly which other pox-5 public functions (e.g. `register-signer`, `stake`, `stake-extend`, `update-bond-registration`) call `verify-signer-key-grant` as their *sole* authorization gate versus combining it with additional independent per-transaction checks — the grep for those function definitions did not complete before the iteration limit. This should be verified directly against `stackslib/src/chainstate/stacks/boot/pox-5.clar` before treating this as a confirmed exploit path rather than a design-pattern concern.

(define-public (grant-signer-key
        (signer-key (buff 33))
        (signer-manager principal)
        (auth-id uint)
        (signer-sig (buff 65))
    )
    (begin
        ;; ensure no reentrancy through signer-manager trait calls
        (try! (validate-no-reentrancy))

        ;; Only the signer contract itself can call this function to grant a signer key
        (asserts! (is-eq contract-caller signer-manager)
            ERR_UNAUTHORIZED_SIGNER_REGISTRATION
        )
        (asserts!
            (is-none (map-get? used-signer-key-grants {
                signer-key: signer-key,
                signer-manager: signer-manager,
                auth-id: auth-id,
            }))
            ERR_SIGNER_KEY_GRANT_USED
        )

        (asserts!
            (is-eq
                (unwrap!
                    (secp256k1-recover?
                        (get-signer-grant-message-hash signer-manager auth-id)
                        signer-sig
                    )
                    ERR_INVALID_SIGNATURE_RECOVER
                )
                signer-key
            )
            ERR_INVALID_SIGNATURE_PUBKEY
        )

        (asserts!
            (map-insert used-signer-key-grants {
                signer-key: signer-key,
                signer-manager: signer-manager,
                auth-id: auth-id,
            }
                true
            )
            ERR_SIGNER_KEY_GRANT_USED
        )

        (map-set signer-key-grants {
            signer-key: signer-key,
            signer-manager: signer-manager,
        }
            true
        )

        (print {
            topic: "grant-signer-key",
            signer-key: signer-key,
            signer-manager: signer-manager,
            auth-id: auth-id,
        })

            signer-manager: signer-manager,
            auth-id: auth-id,
        })

(define-public (revoke-signer-grant
        (signer-manager principal)
        (signer-key (buff 33))
    )
    (begin
        ;; ensure no reentrancy through signer-manager trait calls
        (try! (validate-no-reentrancy))

        ;; Validate that `contract-caller` has the same pubkey hash as `signer-key`
        (asserts!
            (is-eq
                (unwrap-panic (principal-construct?
                    (if is-in-mainnet
                        STACKS_ADDR_VERSION_MAINNET
                        STACKS_ADDR_VERSION_TESTNET
                    )
                    (hash160 signer-key)
                ))
                contract-caller
            )
            ERR_UNAUTHORIZED
        )
        (print {
            topic: "revoke-signer-grant",
            signer-key: signer-key,
            signer-manager: signer-manager,

            signer-key: signer-key,
            signer-manager: signer-manager,
            existed: (map-delete signer-key-grants {
                signer-key: signer-key,

;; Construct the message hash for validating a signer key grant. Unlike [get-signer-key-message-hash],
;; this message hash does not include `max-amount`, `period`, or `reward-cycle`. The topic is always `"grant-authorization"`.
;; The `pox-addr` field is optional. When `none`, it means the signer key can be used for any PoX address.
(define-read-only (get-signer-grant-message-hash
        (signer-manager principal)
        (auth-id uint)
    )
    (sha256 (concat SIP018_MSG_PREFIX
        (sha256 (unwrap-panic (to-consensus-buff? POX_5_SIGNER_DOMAIN)))
        (sha256 (unwrap-panic (to-consensus-buff? {
            topic: "grant-authorization",
            signer-manager: signer-manager,
            auth-id: auth-id,
        })))
    ))
)

(define-read-only (verify-signer-key-sig (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                         (reward-cycle uint)
                                         (topic (string-ascii 14))
                                         (period uint)
                                         (signer-sig-opt (optional (buff 65)))
                                         (signer-key (buff 33))
                                         (amount uint)
                                         (max-amount uint)
                                         (auth-id uint))
  (begin
    ;; Validate that amount is less than or equal to `max-amount`
    (asserts! (>= max-amount amount) (err ERR_SIGNER_AUTH_AMOUNT_TOO_HIGH))
    (asserts! (is-none (map-get? used-signer-key-authorizations { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount }))
              (err ERR_SIGNER_AUTH_USED))
    (match signer-sig-opt
      ;; `signer-sig` is present, verify the signature
      signer-sig (ok (asserts!
        (is-eq
          (unwrap! (secp256k1-recover?
            (get-signer-key-message-hash pox-addr reward-cycle topic period max-amount auth-id)
            signer-sig) (err ERR_INVALID_SIGNATURE_RECOVER))
          signer-key)
        (err ERR_INVALID_SIGNATURE_PUBKEY)))
      ;; `signer-sig` is not present, verify that an authorization was previously added for this key
      (ok (asserts! (default-to false (map-get? signer-key-authorizations
            { signer-key: signer-key, reward-cycle: reward-cycle, period: period, topic: topic, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount }))
          (err ERR_NOT_ALLOWED)))
    ))
  )
