### Title
Webhook `status` event handler is not scoped to the authenticating organization, allowing cross-repository CI status forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an incoming webhook using a `webhook_secret` that is selected based on an organization name taken from the payload itself, then hands the raw JSON to whichever handler matches the event type. Unlike `PushHandler` and `CheckSuiteHandler`, which scope their effect to the repository named in the payload, `StatusHandler` looks up commits globally by SHA with no repository/organization scoping at all. This breaks the binding "the organization whose secret signed the request" == "the repository being acted on," letting any org with a valid `webhook_secret` on a shared Shipit instance forge CI status for commits belonging to a completely different, unrelated repository.

### Finding Description
The signature check picks which GitHub App/organization secret to validate against using fields taken directly from the untrusted payload: [1](#0-0) [2](#0-1) 

Once the signature is verified against the org selected from `repository.owner.login` (or `organization.login`), the entire parsed payload is dispatched to the event handler: [3](#0-2) 

The base `Handler` class provides a `stacks` helper that scopes any handler to the repository named in `repository.full_name`: [4](#0-3) 

`PushHandler` and `CheckSuiteHandler` correctly use this scoping so their side effects are confined to the repository named in the payload: [5](#0-4) [6](#0-5) 

`StatusHandler`, however, does not use `stacks`/`repository_name` at all — it queries `Commit` globally by SHA across the entire instance and writes a status onto whatever commit matches, regardless of which repository/org owns it: [7](#0-6) 

Because commit SHAs are 40-character git hashes that are public (visible in Shipit's own UI, GitHub commit pages, PRs, etc.), an attacker does not need to guess them — they only need to know a target commit SHA that exists in another stack on the same Shipit instance.

The equality this breaks: `organization authenticated by verify_signature` should equal `organization owning the repository/commit the handler mutates`. Before the request: attacker's own org secret authenticates only requests describing attacker's own org's events. After the request: the `status` handler writes a fabricated CI status onto a commit belonging to an entirely different, unrelated stack, because `Commit.where(sha: ...)` performs no repository/organization check.

### Impact Explanation
`Commit#create_status_from_github!` populates the commit's CI status, which Shipit's deploy gating (branch protection / "detect broken CI" / required status checks feature) relies on to allow or block deploys. An attacker who legitimately controls (or has been granted) a low-privilege GitHub organization/app installation on a shared multi-org Shipit instance (a supported configuration per `docs/setup.md` and `config/secrets.development.example.yml`, which explicitly documents multiple orgs each with their own `webhook_secret`) can forge a `status` webhook with `state: "success"` for an arbitrary commit SHA belonging to a victim organization's stack. This can fake a green CI check and enable an unauthorized deploy of a repository the attacker has no access to — a cross-repository, unauthorized-deploy scenario.

### Likelihood Explanation
Any tenant configured with their own `webhook_secret` on a shared Shipit instance (the documented multi-org configuration) can trivially pass `verify_signature` for their own organization, then set an arbitrary `sha` in the `status` payload. No knowledge of the victim's `webhook_secret`, GitHub token, or Shipit session is required — only knowledge of a target commit SHA, which is generally public. This is directly reachable from the unauthenticated `/webhooks` endpoint.

### Recommendation
Scope `StatusHandler` (and any other handler that doesn't already use `stacks`) to the repository named in the payload, and cross-validate that the organization used for signature verification (`repository_owner`) matches the owner of `repository.full_name` before processing. Reject events where the signing organization does not own the repository referenced in the payload.

### Proof of Concept
1. Configure Shipit with two organizations, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org example): `attacker-org` and `victim-org`, both installed on the same Shipit instance.
2. Attacker obtains the `sha` of a commit belonging to a stack under `victim-org` (public information, e.g., from the Shipit UI or GitHub).
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
4. Attacker signs the payload with `attacker-org`'s `webhook_secret` and sends it to `POST /webhooks` with `X-Github-Event: status` and the corresponding `X-Hub-Signature`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully — [1](#0-0) .
6. `StatusHandler#process` matches the victim's commit purely by SHA and writes the forged "success" status onto it — [7](#0-6)  — enabling an unauthorized deploy of `victim-org`'s stack.
