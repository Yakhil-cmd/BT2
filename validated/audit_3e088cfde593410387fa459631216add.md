### Title
Commit status webhook writes are bound only to commit SHA, not to the repository that emitted the event, allowing cross-repository status forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb](app/models/shipit/webhooks/handlers/status_handler.rb))

### Summary
`StatusHandler`, invoked from `WebhooksController#create` after GitHub webhook signature verification, resolves the target of a `status` event purely by commit SHA, with no check that the SHA actually belongs to the repository that the verified signature says the event came from. This breaks the same trust binding described in the Fei `GenesisGroup` report: a check exists (webhook signature verifying "this organization/repository is legitimate"), but a value it does not cover (which repository a given commit SHA belongs to) is used to decide what state gets mutated.

### Finding Description
`WebhooksController#verify_signature` authenticates a webhook using the secret configured for the *organization* derived from the payload's `repository.owner.login` (or `organization.login`) field: [1](#0-0) 

Once the signature is verified, the raw payload is handed unmodified to the matching handler: [2](#0-1) 

For `status` events, `StatusHandler#process` looks up every `Commit` in the entire database whose `sha` matches the payload's `sha` — with no filter on `repository`/`stack` at all — and writes a status onto each one: [3](#0-2) 

Compare this to every other handler (`PushHandler`, pull-request handlers), which resolve the target scope through `Handler#stacks`, itself scoped by `repository.full_name` from the payload: [4](#0-3) [5](#0-4) 

`StatusHandler` is the outlier: it never consults `payload.dig('repository', 'full_name')` at all, so the signature-verified binding is "this status event legitimately originates from organization/repo X" while the actual write binding is "any `Commit` row anywhere in the Shipit install whose `sha` matches, regardless of which stack/repository it belongs to."

Git commit SHAs are content-addressed and not scoped to a single repository: any fork, mirror, or repository that shares history with a tracked stack's repository (including a repository the attacker creates and merely pushes the same tree/commit into, inside an org where the Shipit GitHub App is installed) will produce a webhook with an identical `sha` value. Because `StatusHandler` performs no ownership check, a `status` event that is entirely legitimate for the attacker's own unrelated repository can overwrite the recorded CI/build status of a completely different, unrelated stack's commit.

### Impact Explanation
Commit statuses are the basis of Shipit's safety checks that gate whether a commit is considered "deployable" (`Commit#create_status_from_github!` and the checks consumed by `Stack`/`Status::Group` to decide if a commit passes CI before it may be deployed). An attacker who can trigger a `status` webhook for a SHA that coincides with a commit tracked by a target stack (e.g., by forking or otherwise obtaining push access to any repository under the same GitHub organization where the app is installed, and creating a status via the ordinary GitHub Statuses API — no Shipit credentials or privileges on the target stack required) can inject a fabricated `success` status onto a commit belonging to a stack they have no authorization over, degrading the CI-gating safety check that Shipit's deploy pipeline relies on. This crosses the "unauthorized deploy" boundary in spirit: it lets an unprivileged actor manipulate the safety-check state that determines whether Shipit will allow a commit to ship, without ever touching an `ApiClient` token, a Shipit session, or repository write access on the target stack's repository itself.

### Likelihood Explanation
Reaching this requires only the ability to make GitHub deliver a `status` webhook for a colliding SHA — achievable by pushing a shared commit into any repository within the organization scope, without any privilege on the specific target stack/repository, and without breaking or forging the HMAC signature itself (the signature check passes legitimately because the event really is a valid GitHub webhook, just for the wrong logical target). This is a realistic, low-cost path since organizations commonly host many repositories/forks under the app's installation.

### Recommendation
Scope `StatusHandler#process` (and `Commit` status lookups generally) by repository, not solely by SHA — e.g., restrict the `Commit.where(sha: params.sha)` lookup to commits whose `stack.repository` matches `payload.dig('repository', 'full_name')`, mirroring the pattern already used by `Handler#stacks`/`PushHandler`.

### Proof of Concept
1. Attacker has push access to `attacker-org/random-repo`, where the Shipit GitHub App happens to also be installed (any repo in the org qualifies; no access to the target stack's repository is needed).
2. Attacker pushes a commit whose content/tree is identical to a commit `C` that Shipit already tracks for stack `target-org/target-repo` (e.g., by forking `target-repo` and repushing, or by cherry-picking the exact tree), yielding the same SHA.
3. Attacker calls GitHub's Statuses API (`POST /repos/attacker-org/random-repo/statuses/{sha}`) with `state: "success"`, `context: "ci/required-check"` — an action requiring only normal collaborator write access to their own repo.
4. GitHub delivers a `status` webhook, signed with the legitimate per-organization `webhook_secret`, which passes `WebhooksController#verify_signature`.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, matches commit `C` under `target-org/target-repo`, and calls `commit.create_status_from_github!(params)`, marking `C` as passing CI in the unrelated target stack — even though the target stack's actual CI never ran or failed.
