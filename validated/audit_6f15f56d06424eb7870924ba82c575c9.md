### Title
Reused EVM `create1` deployer nonce after account reaping lets a new contract collide with a not-yet-swept terminated contract's child-trie storage - ([File: substrate/frame/revive/src/exec.rs])

### Summary
`pallet-revive` derives a contract's address (`create1`) and, indirectly, its child-trie `trie_id` from the deployer's `frame_system` account nonce. Unlike `pallet-contracts`, which keeps a dedicated **monotonic** `Nonce` counter specifically because "the trie of a new contract is deleted lazily and there might be storage of the old instantiation still in it" (`substrate/frame/contracts/src/lib.rs:1333-1354`), `pallet-revive` uses the ordinary `frame_system` account nonce for both address (`create1`) and `trie_id` derivation. That nonce is not monotonic for a given account across its lifetime: `frame_system::Pallet::dec_providers`/`dec_sufficients` reap (kill) the account and reset its nonce to `0` (`substrate/frame/system/src/lib.rs:1690-1780`, confirmed by `substrate/frame/system/src/tests.rs:132-231` and `substrate/frame/balances/src/tests/currency_tests.rs:410-446`, e.g. `assert_eq!(System::account_nonce(&2), 0)` after reaping). A normal, unprivileged user can reap and later re-fund their own deployer account, causing the nonce to restart from a value it has already used, so a subsequent `instantiate` recomputes the **same** address and the **same** `trie_id` as an earlier, terminated contract whose child-trie storage has not yet been swept by the deferred `on_idle` deletion queue.

### Finding Description
Contract address derivation:
```
// substrate/frame/revive/src/exec.rs:1197-1219
let account_nonce = <System<T>>::account_nonce(&sender);
let address = if let Some(salt) = salt {
    address::create2(&deployer, executable.code(), input_data, salt)
} else {
    address::create1(&deployer, if origin_is_caller {
        account_nonce.saturating_sub(1u32.into()).saturated_into()
    } else {
        account_nonce.saturated_into()
    })
};
let contract = ContractInfo::new(&address, <System<T>>::account_nonce(&sender), *executable.code_hash())?;
```
and `trie_id` derivation:
```
// substrate/frame/revive/src/storage.rs:449-473
pub fn new(address: &H160, nonce: T::Nonce, code_hash: H256) -> Result<Self, DispatchError> {
    if <AccountInfo<T>>::is_contract(address) {
        return Err(Error::<T>::DuplicateContract.into());
    }
    let account_id = T::AddressMapper::to_fallback_account_id(address);
    if NativeDepositOf::<T>::iter_prefix(&account_id).next().is_some() {
        return Err(Error::<T>::PendingDepositCleanup.into());
    }
    let trie_id = ("bcontract_trie_v1", address, nonce).using_encoded(T::Hashing::hash) ...
```
`ContractInfo::new` only rejects reuse if (a) an active `ContractInfo` still exists at that address, or (b) leftover `NativeDepositOf` rows haven't been drained. It does **not** check whether the *child trie itself* (queued in `DeletionQueue`/`DeletionQueueItem` for lazy sweep, see `substrate/frame/revive/src/storage.rs:823-848` and `substrate/frame/revive/src/lib.rs:743-756`) is still pending removal. Because `address` and `nonce` are both reproducible (deployer nonce resets to `0` on reaping — `frame_system::Pallet::dec_providers`/`on_killed_account`), a second contract created with the same `(address, nonce)` pair gets the **identical `trie_id`** as a previously terminated contract whose storage is still sitting in the child trie awaiting `on_idle`'s lazy drain (`substrate/frame/revive/src/tests/pvm.rs:449-489`, `substrate/frame/revive/src/tests/deposit_payment.rs:529-596` show termination defers cleanup to `Contracts::on_idle`). The new contract therefore starts life sharing a child trie with stale key/value pairs left by the destroyed contract, and when `on_idle` eventually processes the deferred deletion entry it will wipe keys out of that same trie — potentially the live contract's freshly written storage — since the queue tracks trie_ids/entries, not "is this trie currently owned by a live contract".

Root cause chain:
1. Attacker (any signed account, no privilege) deploys contract A via `instantiate`/`eth_instantiate*` using nonce N (`create1(deployer, N)`).
2. Attacker calls `SELFDESTRUCT`/terminate on A. `do_terminate` removes `AccountInfoOf` immediately but queues the trie for lazy deletion (`ContractInfo::queue_for_deletion`, `substrate/frame/revive/src/exec.rs:1874-1930`).
3. Attacker drains all remaining balance/providers on their own deployer account so it is reaped by `frame_system` (`dec_providers`/`dec_sufficients` → `on_killed_account`), which resets `Account::<T>` and hence the account's nonce back toward `0`.
4. Attacker re-funds and re-uses the same deployer address (creating it fresh raises `IncRefStatus::Created`, nonce restarts at 0/low values matching prior usage).
5. Attacker calls `instantiate` again; `create1` recomputes the same address as A and `ContractInfo::new` computes the same `trie_id` because `(address, nonce)` repeats. The `is_contract` and `NativeDepositOf` guards pass (A's `ContractInfo` and native-deposit rows can already be gone), but the deletion queue for A's trie has not been drained yet (`on_idle` runs lazily, bounded by weight, `substrate/frame/revive/src/storage.rs` `DeletionQueueManager`/`process_deletion_queue_batch`).
6. The new contract B begins operating on the same child trie as A. Any storage A left behind (e.g., token balances, allowances, access-control flags) is visible/writable under B's `Key` space before `on_idle` runs; and once `on_idle` eventually runs for A's queued deletion entry, it will delete raw child-trie keys matching what it iterated for A — potentially destroying B's own live storage if B has written under colliding trie positions in the interim, or otherwise blending state between two logically distinct contracts.

This is the exact bug class identified in the external report: a "salt"/uniqueness counter (`positions[msg.sender]` there, the deployer account nonce here) is assumed monotonic by the id-derivation logic, but an orthogonal action (`updateOwner` decrementing `positions` there; account reaping resetting the nonce here) can move it backwards, breaking the uniqueness guarantee the derivation depends on.

### Impact Explanation
This is a state-integrity / storage-collision bug reachable purely through ordinary user-issued extrinsics (`instantiate`, self-destruct/terminate, plain balance transfers to drain and later re-fund an account) — no privileged role, no malicious validator/collator, no forged inherent. The consequence is that a contract's on-chain storage (balances, allowances, access flags, ownership records, etc., depending on what the destroyed predecessor stored) can leak into or be overwritten by an unrelated new contract sharing the same trie, and a subsequent lazy sweep can wipe a live contract's storage as collateral damage. Depending on what is stored (e.g. an ERC-20-style balance mapping), this could enable unbacked balances to appear in the new contract or cause deterministic loss of a live contract's state — a genuine integrity break, not merely a griefing/DoS as in the Solidity report (which was "only" a revert/DoS). This is comparable to, and more severe than, the underlying report's Medium-risk classification, though I could not execute a concrete end-to-end Rust/FRAME test harness run in this session to observe the exact numeric before/after storage read to fully confirm the collateral-deletion effect within the time/tooling available for this pass.

### Likelihood Explanation
Requires: (1) instantiate + terminate a contract from an account, (2) get that account reaped (trivial — transfer away all funds and lose provider/consumer refs, or simply never hold funds beyond the ED and let normal usage reap it), (3) re-fund and reinstantiate before `on_idle`'s bounded, deferred deletion queue drains that specific trie entry. Step 3's timing window depends on `DeletionQueue` backlog/weight budget, which is influenced by ambient network activity (more contract terminations happening chain-wide increase queue depth and widen the window) — this is not an attacker-controlled precondition and is not a resource-exhaustion/flooding claim, since the attacker does not need to flood anything; a busy chain naturally creates this window. Under lighter load the window may be small (single block), but it is not attacker-privileged and not reliant on any protocol/config assumption beyond default lazy-deletion behavior that already exists in shipped code.

### Recommendation
Mirror `pallet-contracts`'s approach: derive `trie_id` (and ideally CREATE1 addressing where not already fixed to EVM's raw nonce semantics) from a **dedicated monotonic counter that is never reset by account reaping**, or explicitly check the `DeletionQueue`/`DeletionQueueItem` entries for a pending trie_id before allowing a new `ContractInfo` to reuse it in `ContractInfo::new` (analogous to the existing `NativeDepositOf::iter_prefix` guard, but scanning/keying deletion-queue entries by trie_id, or maintaining an auxiliary "pending trie ids" set for O(1) lookup). At minimum, block instantiation whenever the target trie_id still has an outstanding `DeletionQueueItem`, exactly as is already done for `NativeDepositOf` rows in `substrate/frame/revive/src/storage.rs:458-465`.

### Proof of Concept
I was not able to execute an actual Rust/FRAME integration test in this session (no filesystem/terminal access in ask-only mode); the analysis above is based on directly reading the shipped source and existing tests that already demonstrate each individual mechanism used in the chain:
- `create1` nonce-based addressing: `substrate/frame/revive/src/exec.rs:1197-1219`, `substrate/frame/revive/src/address.rs:264-270`, verified against `substrate/frame/revive/src/tests/pvm.rs:308-348` (`create1_address_from_extrinsic`).
- Account nonce reset to `0` on reaping: `substrate/frame/system/src/lib.rs:1690-1731` (`dec_providers`/`dec_sufficients`), demonstrated by `substrate/frame/system/src/tests.rs:132-231` and `substrate/frame/balances/src/tests/currency_tests.rs:410-446` (`assert_eq!(System::account_nonce(&2), 0)` after reap).
- Deferred lazy trie deletion after termination: `substrate/frame/revive/src/exec.rs:1874-1930` (`do_terminate` → `queue_for_deletion`), and `substrate/frame/revive/src/tests/pvm.rs:449-489` / `substrate/frame/revive/src/tests/deposit_payment.rs:529-596`, which explicitly show the test suite calling `Contracts::on_idle` to drain the queue *before* re-instantiating at the same address — implying that without this explicit drain, the guard in `ContractInfo::new` (`substrate/frame/revive/src/storage.rs:449-473`, which only checks `is_contract` and `NativeDepositOf`, not the deletion queue) would not by itself prevent trie_id reuse while old data is still pending removal.

A concrete reproduction would require chaining these three already-independently-tested behaviors into one end-to-end scenario (instantiate → terminate → drain deployer account to reap it → re-fund → re-instantiate before `on_idle` fully drains) and asserting that the new contract's `trie_id` equals the old one and/or that stale child-trie keys are visible to it; I did not have execution access to run this scenario in this session, so I can confirm the code-level guard gap and the individually-tested building blocks, but not a live-observed storage collision.
