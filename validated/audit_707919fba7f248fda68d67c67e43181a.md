### Title
Controller can receive token transfers but has no entrypoint to withdraw or recover them, so any tokens held by the controller are permanently stuck - (File: contracts/controller/src/lib.rs)

### Summary
The Tokemak `SwapRouter` accepts ETH via `receive()` with no way to move it out. The same shape exists in XOXNO Lending's `Controller`: tokens can arrive at the controller address through several real paths (direct `token.transfer` by anyone, refund-delta windows, strategy leftovers), yet the controller exports no sweep/rescue/withdraw entrypoint for its own balance. The codebase itself acknowledges this twice: the borrow/withdraw recipient guard exists precisely because "the controller holds funds no balance-delta measurement can ever claim," and a regression test pins that a pre-existing controller token balance is "not used as refund or swept." [1](#0-0) [2](#0-1) 

### Finding Description
The controller's only outbound token movement is `refund_controller_balance_delta` in `contracts/controller/src/payments.rs`, which transfers strictly the positive delta measured since `balance_before` of the same call, explicitly "preserving the pre-existing balance." [3](#0-2) 

GH-17 added `InvalidFlashloanReceiver` rejection for `borrow`/`withdraw` recipients equal to the pool or controller, closing the protocol-created stranding path. [4](#0-3)  But nothing stops an unprivileged address from crediting the controller directly:

- `token.transfer(user -> controller, amount)` — a plain SAC/SEP-41 transfer requires only the sender's auth; the controller cannot refuse receipt.
- Tokens arriving at the controller outside a measured callback window (e.g., between a `balance_before` snapshot of another flow and completion of a prior operation, or contract-address transfers routed through Aquarius/Soroswap venues to the controller address) are never attributed.

Unlike the swap-aggregator, which exports an owner-only `sweep_balance` recovering any balance above reserved fees, the controller's endpoint surface contains no recovery function — its entrypoints are limited to position/payment flows (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `flash_position`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`, `claim_revenue`, `recapitalize`, `update_indexes`, `update_account_threshold`), all of which move funds only via measured deltas or pool calls, never touching the controller's standing balance. [5](#0-4) 

The test `test_migrate_refund_ignores_preexisting_controller_balance` is a direct proof: 0.25 ETH minted to the controller survives a full `migrate_from_blend` untouched, with the assertion "pre-existing controller ETH must remain (not used as refund or swept)." [6](#0-5) 

### Impact Explanation
Permanent freezing of funds. Any token balance held by the controller — whether sent by mistake, pushed by a venue, or left behind by a partial refund — has no exit path through any controller entrypoint, owner-gated or otherwise. This matches the original report's impact (funds stuck indefinitely), on a contract that is demonstrably reachable as a token recipient by unprivileged addresses.

### Likelihood Explanation
Medium likelihood, medium impact — consistent with the original Medium rating. SAC token transfers to a contract address require no contract cooperation, so accidental or griefing deposits are trivially possible. Additionally, flows that authorize token transfers *to* the controller for measured settlement (supply/repay/recapitalize prepayments, swap inputs) create windows where excess or misrouted tokens land on the controller and are deliberately preserved rather than recovered, per the delta-refund design. The loss is bounded to whatever accumulates on the controller address, which the design ensures is never claimed — but is also never zero in practice once the first stray transfer lands.

### Recommendation
Add an owner/governance-gated `sweep`-style entrypoint on the controller that transfers a specified token's full controller balance to a recipient (mirroring `sweep_balance` on the swap-aggregator), or route it through the existing governance execute path. A governance operation avoids adding privileged surface directly to the controller while still making stranded balances recoverable.

### Proof of Concept
1. Any user calls `token::Client::transfer(&user, &controller_address, &amount)` on any listed asset (e.g., USDC SAC). This requires only the user's auth and always succeeds.
2. The controller's USDC balance is now `amount`. Enumerate every controller entrypoint: none transfers a token out of the controller except `refund_controller_balance_delta`, which caps the transfer at the delta measured within the same invocation — the pre-existing `amount` is preserved by construction (`contracts/controller/src/payments.rs:48-51`).
3. Run any flow that could conceivably touch it — `repay` with overpayment, `migrate_from_blend` with refund-listed tokens: the existing test `test_migrate_refund_ignores_preexisting_controller_balance` proves the pre-existing balance is returned untouched (`tests/test-harness/tests/strategy/migrate_blend.rs:529-535`).
4. The `amount` is permanently locked: no borrower withdrawal, no revenue claim, no recapitalize, and no admin function can move it.

/// Refunds only the controller balance increase since `balance_before`,
/// preserving the pre-existing balance; no-op for a nonpositive delta.
pub(crate) fn refund_controller_balance_delta(
    env: &Env,
    asset: &Address,
    balance_before: i128,
    refund_to: &Address,
) {
    let controller = env.current_contract_address();
    let excess = balance_delta_since(env, asset, &controller, balance_before);
    if excess > 0 {
        token::Client::new(env, asset).transfer(&controller, refund_to, &excess);
    }
}

    /// Transfers each token's balance above its reserved fee total to `recipient`. Owner only.
    #[only_owner]
    fn sweep_balance(env: Env, recipient: Address, tokens: Vec<Address>) {
        renew_instance(&env);
        let router = env.current_contract_address();
        let n = tokens.len();
        for i in 0..n {
            // `i < n == tokens.len()`, so the index is in range by construction.
            let token = tokens.get_unchecked(i);
            let client = token::Client::new(&env, &token);
            let balance = client.balance(&router);
            let reserved = storage::reserved_fee_balance(&env, &token);
            if balance > reserved {
                client.transfer(&router, &recipient, &(balance - reserved));
            }
        }
    }
