### Title
Cross-organization webhook forgery due to mismatched fields used for signature-secret selection vs. repository targeting - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the incoming request using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). But the handlers that actually act on the payload (`Handler#stacks`) resolve the target `Stack` using a *different* field from the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')`. Because these are two independent fields inside a single JSON blob that the attacker fully controls, nothing enforces that `repository.owner.login` matches the owner encoded in `repository.full_name`. ### Finding Description
This is a direct analog of the reported bug class: two representations of "the same" quantity (here, "which organization/repository this webhook is for") are computed from different sub-fields, and only one of them is protected/consistency-checked, while the other drives the real effect.

- `verify_signature` builds `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature, request.raw_post)`. The webhook secret used for HMAC verification is chosen by the `repository.owner.login` (or `organization.login`) field of the *same body being verified*. [1](#0-0) 
- Once verification succeeds, the raw parsed params are dispatched unmodified to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [4](#0-3) 
- Every handler resolves which `Stack`(s) to mutate via `Handler#stacks`, which looks up `Repository.from_github_repo_name(repository_name)`, where `repository_name` is `payload.dig('repository', 'full_name')` — a *different* JSON field than the one used to pick the verifying secret. [3](#0-2) 

An attacker who administers their own GitHub organization/App integration inside this Shipit instance (and therefore legitimately knows the `webhook_secret` configured for that organization) can craft a webhook body where:
- `repository.owner.login` = `"attacker-org"` (used only to select the verifying secret — which the attacker knows), and
- `repository.full_name` = `"victim-org/victim-repo"` (used to resolve the actually-affected `Stack`).

They then compute a valid `X-Hub-Signature` over the full raw body using their own known `webhook_secret`, and POST it to the shared `/webhooks` endpoint. `verify_signature` succeeds (attacker-org's secret matches attacker-org's own HMAC), so the forged event is accepted and dispatched with the victim's `repository.full_name`, causing handlers to act against a stack the attacker does not control.

Concretely with `PushHandler`, this causes `stack.sync_github(expected_head_sha: params.after)` to run against the victim's stack with an attacker-chosen `ref`/`after` sha, and with `StatusHandler`, it lets the attacker inject a fabricated commit status (`commit.create_status_from_github!`) against any commit sha they choose, without needing write access to the victim repository at all. [5](#0-4) [6](#0-5) 

**Binding broken (as an equality):**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` ≠ `repository written by handlers (repository.full_name)` — the report's "organization that authenticated versus the repository that is written" analog exactly.

Before the attacker's request: signature verification and repository targeting are assumed (by GitHub's real webhook format) to always agree, since GitHub itself populates both fields consistently. After the attacker's crafted request: the two fields diverge, and the code path never checks that `repository.full_name`'s owner segment matches the `repository_owner` used to authenticate the request.

### Impact Explanation
This escalates an attacker who only administers their own organization's GitHub integration within this Shipit instance into being able to forge push/status/check_suite/pull_request events for a *different, unrelated organization's* repositories/stacks. Depending on stack configuration (e.g. `continuous_deployment: true` combined with required statuses), forged `status` and `push` events can influence or trigger deploys of a stack the attacker does not own, and can desynchronize `sync_github` state — this reaches the "cross-repository writes / unauthorized deploy" impact tier defined in scope, since it lets one tenant/organization write into another tenant's stack state using only credentials the attacker legitimately possesses for their own organization.

### Likelihood Explanation
Requires only that: (1) the Shipit instance is configured with more than one organization's GitHub App/webhook secret (multi-tenant setup, which `Shipit.github(organization:)` is explicitly designed to support), and (2) the attacker is a legitimate admin/webhook holder for at least one of those organizations. No repository write access, no `ApiClient` token, and no privileged Shipit account is required — only the ability to know one organization's own `webhook_secret`, which this rule set treats as an attacker-controllable credential boundary (not an excluded precondition like GitHub App private key or repository write access).

### Recommendation
Bind the field used to select/verify the signing secret to the same field used to resolve the target repository. Concretely, derive `repository_owner` from the same `repository.full_name` (or verify that `repository.full_name`'s owner segment equals `repository.owner.login`/`organization.login`) before dispatching, and reject the webhook if they disagree.

### Proof of Concept
1. Attacker configures/administers organization `attacker-org` in this Shipit instance and knows its `webhook_secret`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_of_attacker-org, raw_body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and verifies successfully against the attacker's own secret. [1](#0-0) 
6. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github(expected_head_sha: "deadbeef...")` on the victim's stack, despite the attacker having no legitimate relationship to `victim-org/victim-repo`. [3](#0-2) [5](#0-4)
