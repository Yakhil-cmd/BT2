### Title
Cross-repository status write via unscoped SHA lookup lets `ignore_ci` stacks be ship/blocked by foreign commit statuses - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming `status` webhook by a bare `sha` lookup across the entire `commits` table, with no repository scoping, unlike every other handler in the same package. Combined with `Commit#deployable?` short-circuiting on `stack.ignore_ci?`, a `failure` status delivered for a SHA that is shared between an attacker-controlled repository and a victim `ignore_ci: true` stack can flip that stack's merge/block/deploy state.

### Finding Description
The broken binding is: `commit.stack_id == webhook.repository.stack_id` is assumed by the system but never enforced by `StatusHandler#process`.

```ruby
# app/models/shipit/webhooks/handlers/status_handler.rb
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This differs from the base `Handler` pattern, which provides a repository-scoped `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) that other handlers (pull_request, push, check_suite) use to constrain writes to the repository that authenticated the webhook: [2](#0-1) 

`StatusHandler` ignores this and matches purely on `sha`, so any commit row in any stack sharing that SHA gets `commit.create_status_from_github!(params)` applied.

Signature verification only proves that the payload was signed for the *claimed* `repository.owner.login`, not that the `sha` inside it belongs to that repository:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
end
``` [3](#0-2) 

Since a git commit SHA is a deterministic hash of tree/parents/author/committer/message/timestamps and not of the hosting repository, the same SHA legitimately exists in multiple repositories (forks, mirrors, unmodified fast-forward merges). If a victim's Shipit stack tracks a repository that shares history with a repository the attacker controls (their own fork, or any repo under the same GitHub App/organization installation that Shipit trusts for signature verification), the attacker can push/land a commit and then emit (or have GitHub emit) a `status` event with `context: ci/lint`, `state: failure` for that SHA. `StatusHandler` writes this status onto every `Commit` row with that SHA, including the one belonging to the victim's stack.

`Commit#deployable?` then evaluates:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [4](#0-3) 

When `stack.ignore_ci?` is true, CI state is irrelevant to deployability — but the injected `failure` status still affects `blocked?`/`blocking_statuses` semantics and downstream hooks (`add_status` triggers `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`), which can flip merge/ship/block behavior driven by the forged status: [5](#0-4) 

None of the existing guards prevent this: `verify_signature` authenticates the claimed owner/org, not the SHA-to-repository binding; `drop_unhandled_event` only filters event types; there is no `ExplicitParameters` constraint tying `sha` to `repository.full_name`; and `StatusHandler` itself never calls the `stacks`/`repository_name` scoping helper that sibling handlers use.

### Impact Explanation
An attacker who controls (or can push to) any repository whose commits' SHAs coincide with a victim `ignore_ci: true` stack's commits (fork/mirror/shared-history scenario within GitHub's signature-verification boundary) can write arbitrary `Status` rows onto the victim stack's commits, altering `blocked?`/deployable state and triggering `stack.schedule_merges` or deploy/rollback decisions for a repository that never authenticated the payload. This is a cross-tenant write: a payload authenticated for one repository mutates state belonging to another stack/commit, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation requires: (1) a victim stack configured with `ignore_ci: true`, and (2) a commit SHA that is shared between the victim's tracked repository and a repository for which the attacker can obtain a validly-signed `status` webhook (their own repo/fork under a GitHub App installation trusted by the deployed Shipit instance, or any repo in the same GitHub organization if signatures are verified per-organization). SHA collision here is not brute-forced — it arises naturally from forks/mirrors with unmodified, fast-forwarded commits, which is a common real-world topology. Given those preconditions, the attack is fully repeatable and costs only a normal GitHub push/webhook delivery.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring other handlers' use of `stacks`/`repository_name`, e.g. restrict the `Commit.where(sha: ...)` query to `stack_id in stacks.select(:id)` (or join through `Repository.from_github_repo_name(repository_name)`), so a status can only be applied to commits belonging to stacks of the repository that signed the payload.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Repository`/`Stack` pairs: `victim_stack` (`ignore_ci: true`, required context `ci/lint`) and `attacker_stack`, both tracking a `Commit` with the identical `sha` (simulating shared history/fork).
2. Assert baseline: `victim_commit.deployable?` is `true` (since `ignore_ci?` short-circuits) and `victim_commit.blocked?` is `false`.
3. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` with `sha` set to the shared SHA, `context: 'ci/lint'`, `state: 'failure'`, and `repository.full_name` pointing at the attacker's repository only.
4. Assert the victim's `Commit` row now has a `Status` record for `ci/lint`/`failure` (`Commit.where(sha: sha, stack_id: victim_stack.id).first.statuses.exists?(context: 'ci/lint', state: 'failure')` is `true`) despite the payload never naming the victim's repository — proving the cross-repository write and demonstrating the equality `commit.stack_id == webhook.repository.stack_id` is violated.
