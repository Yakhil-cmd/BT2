### Title
`r of set` / `weighted and` definitions accept duplicate branches, letting one signer satisfy a multi-signer threshold - (File: definition.js)

### Summary
`ClearingHouse.whitelistAmm()` pushes an AMM address onto an array with no duplicate check, so the same AMM's `unrealizedPnl`/`notionalPosition` gets counted multiple times, silently weakening a threshold-style solvency calculation (`_calcMarginFraction`). The same "list-with-no-uniqueness-check feeding a threshold count" pattern exists in `ocore`'s address-definition evaluator: `validateDefinition()`'s `'r of set'` and `'weighted and'` operators never verify that the entries in `args.set` are distinct, and the authentifier evaluator (`validateAuthentifiers`) simply increments a `count`/`weight` for every branch that evaluates true, regardless of whether multiple branches represent the same underlying signer/key.

### Finding Description
In `definition.js`, `validateDefinition()` validates the `'r of set'` op only for structural correctness: [1](#0-0) 
There is no check that `args.set` contains distinct sub-conditions (e.g., distinct pubkeys/addresses). The same lack of uniqueness checking applies to `'weighted and'`: [2](#0-1) 

When the definition is actually evaluated against signatures in `validateAuthentifiers()`, `'r of set'` simply walks every element of `args.set`, evaluates it at path `path+'.'+index`, and increments a plain counter for every element that returns true, then requires `count >= args.required`: [3](#0-2) 

`'sig'` leaves are verified independently per-path against `assocAuthentifiers[path]`: [4](#0-3) 

Because ECDSA signing in this codebase is deterministic (same private key + same message hash → same signature, standard secp256k1/RFC6979 behavior used throughout the unit-signing flow), a definition such as:
```
['r of set', {required: 2, set: [
    ['sig', {pubkey: pubkeyA}],
    ['sig', {pubkey: pubkeyA}]   // duplicate branch, same key
]}]
```
is accepted by `validateDefinition` (both branches are individually well-formed, `required(2) <= set.length(2)`), yet it can be satisfied by a single private key: the holder of `pubkeyA` signs the unit once and copies the identical deterministic signature into both authentifier paths `r.0` and `r.1`. Both branches independently verify true, `count` reaches `2`, and the "2-of-N" threshold is satisfied by one signer. This is architecturally identical to Hubble's bug: a list intended to represent *distinct* contributing entities (AMMs in Hubble; signer branches here) is never checked for duplicates, so its aggregated count (`unrealizedPnl` sum vs. `count`/`weight` sum) silently double-counts one entity as if it were two.

The same weakness applies to `'weighted and'`, where duplicate `{value, weight}` entries let one signature contribute its `weight` twice toward `required`.

This is reachable by any unprivileged party who defines an address (a wallet author, a shared-address template proposer in `wallet_defined_by_addresses.js`, or an AA author defining a nested/parameterized address condition), since `validateDefinition`/`validateAuthentifiers` are the generic address-definition/authentifier evaluators used everywhere (author definitions, asset conditions, AA definition conditions).

### Impact Explanation
The practical impact is a false sense of multi-party security: a definition that reads as "N distinct signers required" (`r of set` with `required = k`) can, if it contains duplicate branches referencing the same key/address, be satisfied by fewer than `k` distinct signers — as few as one. In a shared/joint address scenario (e.g. a shared wallet template built via `wallet_defined_by_addresses.js`, or an AA-controlled address condition gating fund release), a party that controls the construction of the definition (or that can get a duplicate branch introduced, e.g. by re-using the same member's address at two different signing paths) can retain unilateral spending power over funds that other co-signers believe require joint approval. That is unauthorized/unintended spending of jointly-controlled funds — the counterpart of Hubble's "trade while insolvent" outcome, but here it is "spend while believed to require co-signature."

Unlike the Hubble case, the vulnerable list is not a governance-controlled global registry but a definition an individual party constructs; the severity therefore depends on whether counter-parties can detect the duplication by inspecting the definition/chash before trusting it. Because this requires deliberate/careless construction of a definition rather than an automatically reachable, unconditional double-count (as with Hubble's AMM list), and because the raw definition (containing the duplicate sub-condition) is visible on-chain/inspectable via its `chash`, the exploitability is lower than the original report but the underlying validation gap (no dedup in threshold-style set operators) is real and unaddressed.

### Likelihood Explanation
Medium. Exploiting this requires social/UX conditions: a counter-party must accept a shared/joint address definition without noticing that two branches of an `r of set`/`weighted and` reference the same underlying signer (e.g., because the definition is built from a template with variable substitution, as in `wallet_defined_by_addresses.js`'s `handleNewSharedAddress`/`validateAddressDefinitionTemplate`, where each participant is shown filled-in defaults rather than the full raw definition of every other member). No core validation code independently flags or rejects such duplication, so the protocol offers no defense-in-depth against it, unlike, e.g., the sorted/deduplicated `earned_headers_commission_recipients` or `checkAttestorList` lists elsewhere in `validation.js`, which do enforce sorted-and-unique semantics.

### Recommendation
In `definition.js`'s `validateDefinition()`, for the `'r of set'` and `'weighted and'` operators, compute a canonical hash/serialization of each branch in `args.set` and reject the definition if any two branches are structurally identical (or, at minimum, if two `'sig'` branches share the same `pubkey`, or two `'address'`/`'cosigned by'` branches reference the same address). This mirrors the recommended fix for the Hubble bug (reject duplicates before accepting the list) and would make the `required`/`weight` threshold semantics match user expectations that each set member represents a distinct signer.

### Proof of Concept
1. Build an address definition:
```
['r of set', {required: 2, set: [
    ['sig', {pubkey: PUBKEY_A}],
    ['sig', {pubkey: PUBKEY_A}]
]}]
```
2. This passes `validateDefinition()` in `definition.js` (lines 147-184) since each branch is a well-formed `sig` op and `required(2) <= set.length(2)`.
3. Compute `address = objectHash.getChash160(definition)` and fund it.
4. To spend, the holder of `PUBKEY_A`'s private key signs the unit once, producing signature `S` for `unit_hash_to_sign`.
5. Submit authentifiers `{ "r.0": S, "r.1": S }`.
6. In `validateAuthentifiers()`'s `'r of set'` handler (lines 692-711), both branches independently call `evaluate` on `['sig', {pubkey: PUBKEY_A}]` (lines 734-754), each verifying `S` against `PUBKEY_A` and `unit_hash_to_sign` — both succeed, `count` becomes `2`, and `count >= args.required` is true, authorizing the spend with only one distinct signer.
