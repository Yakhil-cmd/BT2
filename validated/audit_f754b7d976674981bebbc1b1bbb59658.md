### Title
Webhook signature verification and event handling use two different, independently-attacker-controlled repository fields, allowing a valid signature from one org to authorize actions against a different org's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` selects which GitHub App / `webhook_secret` to verify a delivery against using `repository.owner.login` (or `organization.login`), but the event handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`) key off the independent `repository.full_name` field. Nothing enforces `repository.full_name == "#{repository.owner.login}/#{repository.name}"`. This is the exact "pairs equal tokens" class of bug from the external report: two fields that are supposed to move together are validated/used separately, so a delivery can be signature-valid for org A while being processed as if it targeted org B's repository/stack.

### Finding Description
`before_action :verify_signature` computes `repository_owner` purely from the untrusted JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves the GitHub App/secret configuration keyed by that owner login, and the signature is checked against that org's `webhook_secret`: [3](#0-2) 

Once verification passes, `create` re-parses the same raw body and dispatches it to handlers unchanged: [4](#0-3) 

Handlers resolve the target stacks using a *different* field of the same payload — `repository.full_name` — with no cross-check against the `repository.owner.login` used for signing: [5](#0-4) 

In a multi-organization Shipit deployment (`config/secrets*.yml` supports a per-organization `github:` map, each with its own `webhook_secret`), an attacker who legitimately controls one organization's GitHub App installation (and therefore knows that org's `webhook_secret`, which is not a privileged Shipit credential) can craft a webhook payload where `repository.owner.login` is set to their own org (so `verify_signature` selects and validates against a secret they know) while `repository.full_name` is set to `"victim-org/victim-repo"`. The signature check passes, and the handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) then looks up and acts on stacks belonging to `victim-org/victim-repo` — a repository the attacker was never authenticated for.

This directly mirrors the reported bug class: `UniswapStyleLib`/`PriceAware` trusted that `path` and `tokens` were consistent without checking they actually paired up; here Shipit trusts that `repository.owner.login` (used for authentication) and `repository.full_name` (used for authorization/target selection) are consistent, without ever checking `full_name.split('/').first == owner.login`.

### Impact Explanation
This breaks the binding "organization authenticated == repository that is written," which the rules explicitly call out as in-scope. Depending on the handler triggered, the attacker can:
- Force a `GithubSyncJob` to run against a victim stack (`PushHandler`), causing Shipit to fetch/sync git state and potentially trigger continuous deployment for a repository/organization the attacker does not own.
- Inject forged commit `Status`/`CheckRun` records for a victim stack's commits (`StatusHandler`, `CheckSuiteHandler`), which the merge queue (`MergeRequest#all_status_checks_passed?` / `any_status_checks_failed?`) and continuous-delivery logic rely on to decide whether to merge or deploy — i.e. this can lead to an **unauthorized deploy or merge** by spoofing green CI status on someone else's stack.

This satisfies the Critical/High impact bar ("cross-repository writes... or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration — see `config/secrets.development.example.yml`'s multi-org example), and (b) the attacker to control at least one of those organizations' GitHub App installation/webhook secret, which is a normal, unprivileged position for a legitimate customer/org-admin in a multi-tenant Shipit deployment, not a privileged Shipit credential. Given that, exploitation is a single crafted HTTP POST with a valid HMAC computed from the attacker's own known secret — no Shipit session, API token, or GitHub write access to the victim repo is required.

### Recommendation
In `WebhooksController`/`Handler`, derive both the signing organization and the acted-upon repository from the same, single source of truth, and explicitly validate consistency, e.g.:
```ruby
def repository_full_name
  params.dig('repository', 'full_name')
end

def repository_owner
  repository_full_name&.split('/', 2)&.first || params.dig('organization', 'login')
end
```
and/or add an explicit check in `verify_signature`/`Handler#repository_name` that `full_name.split('/').first.casecmp(owner_login) == 0` before dispatching, rejecting (422) mismatched payloads.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `attacker-org` and `victim-org`, each with its own `github.webhook_secret` (a legitimate multi-tenant setup per `docs/setup.md`).
2. As the owner of `attacker-org`'s GitHub App, compute `sha1=HMAC(attacker_secret, body)` for a `push` payload where:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"`
3. POST this body with header `X-Github-Event: push` and the computed `X-Hub-Signature` to `/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully against the attacker's own secret.
5. `PushHandler#process` (via `Handler#stacks`) resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues a `GithubSyncJob` for the victim's stack, despite the request never being authenticated by `victim-org`'s GitHub App/secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
