### Title
Webhook authentication is bound to the wrong organization, allowing forged status/push events to be written against a different org's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to authenticate a webhook against using `repository_owner`, a field read straight out of the attacker-supplied, not-yet-verified JSON body. The event handlers, however, resolve *which* `Repository`/`Stack` to write to using a different field from the same payload, `repository.full_name`. These two lookups are never bound to each other, and if the organization selected for signature verification has no `webhook_secret` configured, verification is skipped entirely — letting an attacker author an unsigned payload whose `repository.owner.login` points at a secret-less org while `repository.full_name` points at a different, victim org's repository, causing Shipit to act on that victim repository with no valid signature at all.

### Finding Description
Signature selection and verification: [1](#0-0) [2](#0-1) 

`repository_owner` is taken directly from the unverified JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), and is used only to pick which `github_app`/secret to check the signature against.

The actual signature check trivially passes when no secret is configured for that organization: [3](#0-2) 

`return true unless webhook_secret` — this is the exact analog to the deposit/withdraw bug: a per-organization "trust counter" (here, "was this org's secret satisfied?") that is trivially reset to a passing state (blank secret ⇒ always verified) and then relied upon as if it constrained a *different* asset (the repository actually mutated).

Once past `verify_signature`, every handler ignores `repository_owner` entirely and resolves the target `Stack`/`Repository` from `repository.full_name`, a completely separate field of the same payload: [4](#0-3) 

So the binding actually enforced is:
`organization whose (possibly blank) webhook_secret satisfied verify_webhook_signature` — but the binding relied upon by downstream handlers is `organization that owns the repository being written to (repository.full_name)`. These are never asserted equal anywhere in `app/controllers/shipit/webhooks_controller.rb` or `app/models/shipit/webhooks/handlers/handler.rb`.

Concretely: if an operator configures an organization `OrgA` in `Shipit.github` without a `webhook_secret` (a config shape explicitly shown as valid in `config/secrets.development.shopify.yml:9,18` — `webhook_secret: # nil`), any unauthenticated caller can:
1. Set `X-Github-Event: status` (or `push`, `pull_request`, etc.).
2. Send a JSON body with `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")` is selected, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally) — see `app/models/shipit/hook.rb`/`lib/shipit/github_app.rb`.
3. Set `repository.full_name = "OrgB/victim-repo"` where `OrgB` is a real, secret-protected organization with active stacks.
4. The handler resolves the stack purely from `repository.full_name` (`Repository.from_github_repo_name`), completely bypassing `OrgB`'s actual `webhook_secret`.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding called out in the analog rules. Concretely reachable, unauthenticated write paths through this hole include:
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) creating a forged commit status (e.g. `success`) on a commit belonging to `OrgB`'s repository, which can satisfy CI/deploy-safety gates that other Shipit logic (deployable/merge status) depends on, leading to an **unauthorized deploy** of code that never actually passed CI.
- `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) enqueuing a `GithubSyncJob` for an arbitrary stack under `OrgB` using an attacker-chosen `after` SHA.
- Pull-request handlers under `app/models/shipit/webhooks/handlers/pull_request/` mutating merge/label state for `OrgB`'s pull requests.

This satisfies the Critical impact bar ("an unauthorized deploy, rollback or merge") because it lets an unprivileged, unauthenticated attacker forge signed-looking GitHub events against a repository whose real webhook secret was never checked.

### Likelihood Explanation
Requires only that at least one organization configured in the multi-tenant `Shipit.github` config has a blank/absent `webhook_secret` — a state the project's own sample config treats as normal/supported (`config/secrets.development.shopify.yml`), and which the code explicitly special-cases (`return true unless webhook_secret`). No GitHub credentials, session, or API token are needed; the attacker only needs network access to the public `/webhooks` endpoint and knowledge of a secret-less configured org name and a target repo's `full_name`.

### Recommendation
- Verify the webhook signature strictly per-repository, not per-organization-selected-from-payload: reject (422) when no `webhook_secret` is configured, instead of returning `true`.
- Bind the two lookups: after `verify_signature`, assert that the organization actually authenticated equals the owner segment of `repository.full_name` before dispatching to handlers, rejecting mismatches.
- Consider deriving the authenticating organization from a source not fully controlled by the JSON body prior to verification (e.g., requiring installation ID checks against GitHub's installation-scoped webhook delivery, if available).

### Proof of Concept
1. Configure Shipit with two orgs, e.g. in `config/secrets.yml`:
```yaml
github:
  OrgA:
    webhook_secret: # blank
  OrgB:
    webhook_secret: "real-secret"
```
2. `OrgB/victim-repo` exists as a tracked `Repository`/`Stack` in Shipit.
3. Send (no `X-Hub-Signature` needed, or any garbage value):
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo" },
  "sha": "<commit-sha-of-orgb-victim-repo>",
  "state": "success"
}
```
4. `verify_signature` looks up `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of header value.
5. `StatusHandler` resolves the commit purely from `sha`/`repository.full_name` = `OrgB/victim-repo`, creating a forged `success` status for that commit with no valid signature ever checked against `OrgB`'s real secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
