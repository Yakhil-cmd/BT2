### Title
`EnvironmentVariables#interpolate` falls back to the Shipit worker's own `ENV[variable]` for undeclared `$VAR` references in `shipit.yml` steps - ([File: lib/shipit/environment_variables.rb])

### Summary
`EnvironmentVariables#interpolate` resolves any `$VAR` token in a `Command`'s arguments by first checking the curated per-task env hash and, if the key is absent, falling back directly to `ENV[variable]` — the real, live environment of the Shipit Rails/worker process. Since `dependencies` (and other) steps in a repository's `shipit.yml` are attacker-influenced strings that get interpolated this way, a step referencing an undeclared variable such as `$RUBYOPT` or `$BUNDLE_GEMFILE` can pull the Shipit host's own process environment value into the command line, whose output is exposed via `Task#output`.

### Finding Description
The claimed safe binding — "undeclared `$VAR` resolves to empty/absent, never `ENV[variable]` from the Shipit host process" — does **not** hold. The actual code is: [1](#0-0) 

`interpolate` explicitly does `@env.fetch(variable) { ENV[variable] }`: if the curated `@env` hash (built per-task in `TaskCommands#env`) doesn't contain the referenced key, it silently substitutes the Shipit worker process's real `ENV[variable]`, not an empty string.

`Command#interpolate_environment_variables` calls this on every argument before spawning the process and using it in `start`: [2](#0-1) [3](#0-2) 

`TaskCommands#install_dependencies` builds these `Command` objects directly from `deploy_spec.dependencies_steps!`, which originates from the cached `shipit.yml` (`DeploySpec::FileSystem`, populated by `CacheDeploySpecJob#perform`): [4](#0-3) [5](#0-4) 

The env hash passed to each `Command` (`TaskCommands#env`) is a curated merge of `@stack.env`, hardcoded task metadata, `deploy_spec.machine_env`, and `@task.env` — it is **not** the full process `ENV`, and it is not restricted through `EnvironmentVariables#permit`/`variable_definitions` before being handed to `Command`. Because `interpolate` performs its own independent fallback to global `ENV` (not the sanitized hash), any repository-authored step string can reference an env var name that isn't in this curated hash and have it resolved from the Shipit process's real environment instead of being empty. `EnvironmentVariables#permit`/`sanitize_env_vars` restricts what *stack/task*-declared variables are allowed into the merged env, but it does nothing to stop `interpolate`'s independent `ENV[variable]` fallback for names not present in that hash at all — this is a distinct code path with no equivalent guard.

### Impact Explanation
If the Shipit host process has sensitive configuration exposed via environment variables (a common 12-factor pattern for secrets, credentials paths, or tokens), a repository-controlled `dependencies` step referencing that variable name by chance or by informed guess (e.g. `$RUBYOPT`, `$BUNDLE_GEMFILE`, or a more sensitive name) will have its value substituted into the literal shell command line, and since PTY output is streamed to `Task#output`, the value becomes visible in the task log to anyone who can view that stack's task output. This matches "exfiltration of deploy-time secrets" (Critical) or, at minimum, "unauthenticated/low-privilege read of task streams / deploy output" (High), depending on what is actually stored in the worker's `ENV` and who can view task output for the affected stack.

### Likelihood Explanation
Exploitability depends entirely on reachability: `dependencies_steps!` are sourced from `shipit.yml` cached by `CacheDeploySpecJob`, which is populated for commits associated with the stack. Whether a fully unprivileged PR author (no push/merge rights on the tracked branch) can get their own `shipit.yml`'s `dependencies` steps executed depends on whether commit-check/CI paths (e.g. `EphemeralCommitChecks`, which also references `dependencies` steps) run against PR-head commits rather than only the protected tracked branch. I was not able to fully trace `CacheDeploySpecJob`'s triggering conditions or `EphemeralCommitChecks`'s exact commit source within the available tool budget, so I cannot conclusively confirm whether this is reachable by a PR author with zero write access, or whether it requires a maintainer merging the PR (write access), which would fall outside the "unprivileged" attacker model given in the rules. This is the key open uncertainty.

Additionally, actual impact is capped by what secrets, if any, exist in the Shipit worker's environment under variable names an attacker can guess or that are already public conventions (`RUBYOPT`, `BUNDLE_GEMFILE`); this is speculative without knowledge of the deployment's specific env configuration.

### Recommendation
Change `EnvironmentVariables#interpolate` to never fall back to the real process `ENV`; undeclared variables should resolve to an empty string (or raise), e.g. `@env.fetch(variable, '')` instead of `@env.fetch(variable) { ENV[variable] }`, in `lib/shipit/environment_variables.rb`.

### Proof of Concept
Minitest plan (`test/unit/environment_variables_test.rb` or `test/unit/command_test.rb`):
```ruby
test "interpolate does not leak host process ENV for undeclared variables" do
  ENV['RUBYOPT'] = 'SENTINEL-SECRET-VALUE'
  command = Shipit::Command.new(['echo', '$RUBYOPT'], chdir: Dir.tmpdir, env: {})
  refute_includes command.interpolated_arguments.join(' '), 'SENTINEL-SECRET-VALUE'
ensure
  ENV.delete('RUBYOPT')
end
```
Binding to assert on both sides:
- Expected safe value: `Shipit::EnvironmentVariables.with({}).interpolate('$RUBYOPT') == ''` (or unchanged literal)
- Actual current value: `Shipit::EnvironmentVariables.with({}).interpolate('$RUBYOPT') == Shellwords.escape(ENV['RUBYOPT'])`

Given the current implementation at [6](#0-5)  the second assertion holds today, proving the binding is broken. What remains unverified is the exact unprivileged-attacker reachability of `dependencies_steps!` execution (via `CacheDeploySpecJob`/`EphemeralCommitChecks`), which I could not fully confirm within the available investigation — a full session with broader access to `app/models/shipit/ephemeral_commit_checks.rb` and the webhook/commit-check controller chain is needed to close that gap.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end

      end
