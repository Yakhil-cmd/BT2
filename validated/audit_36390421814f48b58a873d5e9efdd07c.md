### Title
ERC-721 Tokens Can Be Permanently Locked in the Kaia Service-Chain Bridge via the ERC-20 Transfer Path — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` uses `SafeERC20.safeTransferFrom` to pull tokens into the bridge. Because `safeTransferFrom` resolves to a low-level call to `transferFrom(address,address,uint256)` — a selector shared by both ERC-20 and ERC-721 — any registered ERC-721 token can be deposited through the ERC-20 path. On the counterpart chain, `handleERC20Transfer` attempts to release the token via `safeTransfer`, which calls `transfer(address,uint256)`. ERC-721 does not implement this function, so the call reverts and the ERC-721 token is permanently locked in the source bridge with no recovery path short of a contract upgrade.

---

### Finding Description

`BridgeTransferERC20.sol` and `BridgeTransferERC721.sol` both inherit `BridgeTokens`, which maintains a single untyped registry:

```solidity
mapping(address => address) public registeredTokens; // <token, counterpart token>
``` [1](#0-0) 

`registerToken` is `onlyOwner` and stores only the counterpart address — **no token-type field is recorded**:

```solidity
function registerToken(address _token, address _cToken)
    external
    onlyOwner
    onlyNotRegisteredToken(_token)
{
    registeredTokens[_token] = _cToken;
    ...
}
``` [2](#0-1) 

The bridge owner legitimately registers ERC-721 tokens for ERC-721 bridging using this same function. Once registered, the ERC-721 token address passes the `onlyRegisteredToken` guard in `_requestERC20Transfer`.

`requestERC20Transfer` (the public ERC-20 deposit entry point) pulls tokens with:

```solidity
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
``` [3](#0-2) 

`SafeERC20.safeTransferFrom` resolves to a low-level call to selector `transferFrom(address,address,uint256)`:

```solidity
function safeTransferFrom(IERC20 token, address from, address to, uint256 value) internal {
    callOptionalReturn(token, abi.encodeWithSelector(token.transferFrom.selector, from, to, value));
}
``` [4](#0-3) 

ERC-721 exposes the **identical** 4-byte selector `0x23b872dd` for `transferFrom(address,address,uint256)`:

```solidity
function transferFrom(address from, address to, uint256 tokenId) public {
    require(_isApprovedOrOwner(msg.sender, tokenId), ...);
    _transferFrom(from, to, tokenId);
}
``` [5](#0-4) 

So the deposit half succeeds: the ERC-721 token is transferred to the bridge. The bridge then emits `RequestValueTransfer` with `TokenType.ERC20`.

On the counterpart chain, `handleERC20Transfer` attempts to release the token:

```solidity
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [6](#0-5) 

`SafeERC20.safeTransfer` calls `transfer(address,uint256)`:

```solidity
function safeTransfer(IERC20 token, address to, uint256 value) internal {
    callOptionalReturn(token, abi.encodeWithSelector(token.transfer.selector, to, value));
}
``` [7](#0-6) 

ERC-721 does **not** implement `transfer(address,uint256)`. The low-level call returns no data or reverts, causing `callOptionalReturn` to revert with `"SafeERC20: low-level call failed"`. The ERC-721 token is now permanently locked in the source bridge.

---

### Impact Explanation

An ERC-721 token that is legitimately registered in the bridge for ERC-721 bridging can be deposited through the ERC-20 path by any token holder who approves the bridge. The token is irrecoverably locked in the source bridge contract because:

- The deposit (`requestERC20Transfer`) succeeds.
- The withdrawal (`handleERC20Transfer`) always reverts for ERC-721 tokens.
- No admin function exists to rescue arbitrary tokens from the bridge.

The corrupted state is: the bridge holds the ERC-721 token but the `requestNonce` has advanced and the event has been emitted, so the counterpart chain will repeatedly attempt and fail `handleERC20Transfer`. The token owner loses their asset permanently without a contract upgrade.

---

### Likelihood Explanation

- **Trigger**: Any holder of a registered ERC-721 token who approves the bridge can call `requestERC20Transfer` directly. No special role is required.
- **Precondition**: The ERC-721 token must be registered in the bridge — a normal operational state for any bridge supporting ERC-721 transfers.
- **Fee path**: With `_feeLimit = 0` and no ERC-20 fee configured for the ERC-721 token address, `_payERC20FeeAndRefundChange` returns 0 without any blocking token operations. [8](#0-7) 

- **`modeMintBurn = false`** (lock/unlock mode): the deposit path does not call `burn`, so the ERC-721 token is silently held by the bridge before the event is emitted. [9](#0-8) 

---

### Recommendation

Add a token-type field to the registry and enforce it at deposit time, or add an explicit check in `requestERC20Transfer` that the token address does not respond to ERC-721's `supportsInterface(0x80ac58cd)`. The simplest guard is to call `decimals()` on the token and revert if it is absent (ERC-721 contracts do not implement `decimals()`), mirroring the fix suggested in the Linea report.

Alternatively, maintain two separate registries — one for ERC-20 tokens and one for ERC-721 tokens — and enforce that `requestERC20Transfer` only accepts addresses from the ERC-20 registry.

---

### Proof of Concept

```solidity
// Assume:
// - bridge is deployed in lock/unlock mode (modeMintBurn = false)
// - erc721 is a standard ERC-721 token registered in the bridge
// - attacker owns tokenId 42

// Step 1: Attacker approves bridge
erc721.approve(address(bridge), 42);  // standard ERC-721 approval

// Step 2: Attacker calls the ERC-20 deposit path with the ERC-721 address
// _value = 42 (tokenId), _feeLimit = 0
bridge.requestERC20Transfer(address(erc721), attacker, 42, 0, "");
// SUCCESS: safeTransferFrom calls transferFrom(attacker, bridge, 42)
// ERC-721's transferFrom(from, to, tokenId) matches the selector 0x23b872dd
// Token is now held by bridge; RequestValueTransfer(ERC20, ...) is emitted

// Step 3: On counterpart chain, operator calls handleERC20Transfer
bridge_counterpart.handleERC20Transfer(txHash, attacker, attacker,
    address(erc721_counterpart), 42, nonce, blockNum, "");
// REVERTS: safeTransfer calls transfer(attacker, 42)
// ERC-721 has no transfer(address,uint256) → "SafeERC20: low-level call failed"

// Result: tokenId 42 is permanently locked in the source bridge.
``` [10](#0-9) [11](#0-10)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
