### Title
Membership webhook `MembershipHandler#process` grants `Shipit.github_teams` membership without validating that the authenticated organization owns the target team - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` only proves that a payload was signed by *some* organization already configured in Shipit (the one named in `params['organization']['login']`), never that this organization actually owns the `team.id` referenced in the payload. `MembershipHandler#find_or_create_team!` looks up the `Team` purely by `github_id` and only assigns `organization` on the create branch, so for a pre-existing `Team` row the organization is never re-checked, letting any org whose webhook secret the attacker controls add arbitrary users to any other org's team.

### Finding Description
The intended binding is: `team.organization == params.organization.login` for every membership event applied to that `team`, i.e. a `Membership` row created from a webhook must have been authenticated by the organization that actually owns that GitHub team.

Trace:
- `Shipit::WebhooksController#verify_signature` computes `repository_owner` via `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) . Membership webhooks have no `repository` key, so `repository_owner` is exactly `params['organization']['login']` — fully attacker-supplied.
- It then does `Shipit.github(organization: repository_owner)` and verifies the signature using **that** organization's configured `webhook_secret` [2](#0-1) . This only proves the request was signed by whichever org the attacker names (`attackers-own-org`); it says nothing about the `team` object also present in the same payload.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . The block that sets `organization` **only runs on record creation** (ActiveRecord `find_or_create_by!` semantics); if a `Team` row with that `github_id` already exists (created earlier by the real owning org), the organization mismatch between `team.organization` (real org) and `params.organization.login` (`attackers-own-org`) is silently ignored.
- `process` unconditionally calls `team.add_member(User.find_or_create_by_login!(params.member.login))` [4](#0-3)  and `Team#add_member` simply appends the member with no organization check [5](#0-4) .
- `User#authorized?` grants Shipit access to any user belonging to a team present in `Shipit.github_teams` [6](#0-5) , with no re-validation against GitHub.

No other guard intervenes: `drop_unhandled_event` only checks that a handler is registered for the `membership` event; `ExplicitParameters` schema only validates types/presence, not cross-field authorization [7](#0-6) ; there is no code anywhere in `MembershipHandler` or `Team` comparing `params.organization.login` to the pre-existing `team.organization`.

Attacker's exact request: `POST /webhooks` with `X-Github-Event: membership`, body `{"action":"added","team":{"id":<victim_team_github_id>,"slug":"...","name":"...","url":"..."},"organization":{"login":"attackers-own-org"},"member":{"login":"attacker_login"}}`, signed with `attackers-own-org`'s real `webhook_secret` (which the attacker legitimately possesses because Shipit has that org configured as a tenant). This passes `verify_signature`, finds the pre-existing `Team` row for the victim org's team by `github_id`, and adds `attacker_login` as a member — with no membership on GitHub ever occurring.

### Impact Explanation
The attacker gains membership in a `Shipit.github_teams`-listed team without GitHub ever reflecting that membership, which flips `User#authorized?` to `true` for the attacker, granting them full authenticated access to the Shipit UI/API for every stack gated by that team — including triggering deploys, rollbacks, and other privileged actions normally restricted to the victim organization's real team members. This is a cross-tenant authorization bypass ("escalation into `Shipit.github_teams` authorization" per the High severity bucket), and repeatable at will as long as the attacker knows/guesses a `team.id` value and controls a configured organization's webhook secret.

### Likelihood Explanation
Exploitation requires: (1) Shipit configured in a multi-organization mode where the attacker's own org has legitimate GitHub App credentials registered in Shipit (attacker therefore knows its real `webhook_secret`), and (2) at least one `Team` row for a different organization already exists in the `teams` table (created by that org's own prior legitimate webhook traffic) with a `github_id` the attacker can discover or guess (GitHub team IDs are sequential integers, often enumerable via the public API if team visibility permits, or observable in other webhook/API responses). Given those two realistic preconditions for a multi-tenant Shipit deployment, the attack is a single crafted HTTP request, fully repeatable, and requires no privileged Shipit role.

### Recommendation
In `MembershipHandler#find_or_create_team!`, always verify `team.organization == params.organization.login` for both the create and find branches, and reject/raise (or no-op) when they differ instead of silently reusing the existing row. Additionally, `Team.find_or_create_by!` should scope the lookup on `(github_id:, organization:)` rather than `github_id` alone, so that teams from different organizations can never collide on the same `github_id`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership webhook cannot grant team membership on behalf of a different organization" do
  victim_team = shipit_teams(:real_org_team) # organization: "real-org", github_id: 4242

  payload = {
    'action' => 'added',
    'team' => { 'id' => victim_team.github_id, 'name' => victim_team.name, 'slug' => victim_team.slug, 'url' => victim_team.api_url },
    'organization' => { 'login' => 'attackers-own-org' },
    'member' => { 'login' => 'attacker_login' }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

  refute_includes victim_team.reload.members.map(&:login), 'attacker_login',
    "Team##{victim_team.id} organization=#{victim_team.organization} must not gain a member " \
    "from a payload authenticated as organization=attackers-own-org"
end
```
Both sides of the binding to assert: `victim_team.organization` ("real-org") must equal the organization that authenticated the request ("attackers-own-org") before any `Membership` row is written — currently they diverge and the test fails against current code, confirming the bug.
