### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled`, letting an unreviewed fork branch auto-provision a Stack whose `shipit.yml` `dependencies` steps get executed via `TaskCommands#install_dependencies` - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` uses `&&`/`||` without parentheses so that `repository.review_stacks_enabled` only gates the `allow_all` branch; the `allow_with_label` and `prevent_with_label` branches are evaluated independently of that flag. As a result, a repository whose maintainer disabled dynamic review-stack provisioning can still have a `ReviewStack` auto-created and auto-provisioned for an attacker's pull request, whose branch head is then checked out and whose `shipit.yml` `dependencies` steps are executed unreviewed via `TaskCommands#install_dependencies`.

### Finding Description
Binding claimed to hold: `stack.branch used by install_dependencies == pull_request.head.ref of a branch an authorized user approved`. The code shows this binding is broken independent of `review_stacks_enabled`.

`provision?` is defined as: [1](#0-0) 

Due to Ruby operator precedence (`&&` binds tighter than `||`), this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only consulted in the first disjunct. If a repository has `review_stacks_enabled = false` but `provisioning_behavior` is `allow_with_label` (and the attacker's own PR carries the configured label, which the attacker controls on their own PR) or `prevent_with_label` (and the attacker simply omits the label), `provision?` returns `true` even though the maintainer explicitly disabled dynamic provisioning.

Once `provision?` is true, `OpenedHandler#process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which creates a `ReviewStack` with `branch: params.pull_request.head.ref` — the attacker's fork branch: [2](#0-1) 

That stack is queued for provisioning (`Shipit::ReviewStackProvisioningQueue.add(stack)`), which drives the standard deploy pipeline for the new stack. `TaskCommands#deploy_spec` builds `DeploySpec::FileSystem.new(@task.working_directory, @stack)` against the checked-out commit of that branch, and `TaskCommands#install_dependencies` maps `deploy_spec.dependencies_steps!` directly into `Command` objects with no approval gate: [3](#0-2) 

`dependencies_steps` is sourced straight from the checked-out `shipit.yml`'s `dependencies.override` key (or discovered installer commands), with no distinction between "reviewed" and "unreviewed" refs: [4](#0-3) 

Existing guards do not stop this: the correctly-written `respond_to_label_change?` in `LabeledHandler` explicitly `&&`s `repository.review_stacks_enabled` outside the OR: [5](#0-4) 

confirming that `OpenedHandler#provision?` is the outlier that fails to enforce the same invariant. No webhook forgery is required — this is triggered by a legitimate GitHub `pull_request.opened` webhook for a real PR the attacker opened against the target repository from their own fork, which passes normal signature verification since it is a genuine GitHub-originated event.

### Impact Explanation
An attacker who can open a pull request against any repository registered with Shipit (regardless of whether that repository's owner intentionally left `review_stacks_enabled` off) can force Shipit to auto-create and provision a `Stack` tracking their own fork branch, then have that stack's provisioning/deploy pipeline execute `dependencies` steps from their own `shipit.yml` — including arbitrary shell (e.g., `curl | sh`) — via `Command#start`/`PTY.spawn` on the Shipit deploy host. This is Critical: RCE on the deploy host, reachable by an unprivileged PR author, and repeatable against any repository configured with `provisioning_behavior` of `allow_with_label` or `prevent_with_label` regardless of the `review_stacks_enabled` toggle, i.e., a payload from one PR/repo achieving unauthorized deploy/execution the maintainer explicitly opted out of.

### Likelihood Explanation
Preconditions: target repository is registered in Shipit with `review_stacks_enabled = false` and `provisioning_behavior` set (or defaulted) to `allow_with_label` or `prevent_with_label`. Attacker cost is minimal: open a PR from a fork, optionally add/omit a label they control on their own PR, and include a `dependencies:` section in `shipit.yml`. No secrets, tokens, or privileged roles are needed, matching the stated attacker capability set. This is fully repeatable per-PR and per-repository sharing this configuration.

### Recommendation
Fix the operator precedence in `provision?` so `review_stacks_enabled` gates all branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Add a minitest under `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style (existing suite already has helpers `configure_provisioning_behavior`, `payload_parsed`):
```ruby
test "does NOT create stacks when review_stacks_enabled is false, even if allow_with_label label is present" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # review_stacks_enabled = false
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert both sides of the binding: `repository.review_stacks_enabled` (`false`) vs. whether a `Stack`/`ReviewStack` is created (`Shipit::Stack.count` unchanged). Running this against current code should FAIL (a stack IS created), proving the precedence bug allows bypassing the disabled flag; after the fix it should PASS.
