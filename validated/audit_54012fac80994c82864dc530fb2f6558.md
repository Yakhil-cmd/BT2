This is confirmed to require multi-organization Shipit deployments where webhook_secret is configured per-organization (as in `test/dummy/config/secrets_double_github_app.yml`), which requires admin-controlled configuration, not something an unprivileged attacker controls on their own. That said, the analog does hold structurally, so I'll present it.

### Title
Webhook organization used for signature verification is not bound to the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify the HMAC signature using `repository_owner`, which is read from the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once verified, the raw payload is handed unmodified to event handlers (e.g. `PushHandler`), which independently resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')`. Nothing ties the "owner" field used for cryptographic verification to the "full_name" field used to determine which repository/stack is written to.

### Finding Description
`verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(...)` using that organization's `webhook_secret` [1](#0-0) . `repository_owner` is derived purely from body content: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) .

After verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the same raw `params` hash to handlers [3](#0-2) . Handlers such as `PushHandler` and the base `Handler` class resolve the affected `Stack` via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [4](#0-3) , and `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for matching stacks [5](#0-4) .

The equality the code implicitly (and incorrectly) assumes is:
`organization_used_for_signature_verification (repository.owner.login) == organization_whose_repository_full_name_is_acted_upon (repository.full_name split)`

Because both fields live in the same attacker-suppliable JSON body, and only one field (`repository.owner.login`) is used to pick the secret, an attacker who legitimately controls a GitHub App/organization configured in `Shipit.secrets.github` (as in multi-org setups like `test/dummy/config/secrets_double_github_app.yml`, which shows two independently configured organizations `OrgOne`/`OrgTwo` each with their own `webhook_secret`) can sign a payload with their own valid `webhook_secret`, while setting `repository.full_name` to point at a stack belonging to a *different* organization/repository hosted on the same Shipit instance.

### Impact Explanation
If exploitable, this would let an attacker with legitimate webhook-signing capability for one onboarded organization forge webhook events (`push`, `status`, `check_suite`, `pull_request`, etc.) that are accepted as authentic for stacks belonging to an unrelated organization/repository on the same Shipit instance, triggering `GithubSyncJob`, review-stack archiving/unarchiving, or commit status changes cross-repository — a cross-repository-write class impact.

### Likelihood Explanation
Likelihood is low in practice: exploitation requires the attacker to already be an authorized configurer/owner of at least one organization/GitHub App entry present in `Shipit.secrets.github` on the target Shipit instance (i.e., they must know a valid `webhook_secret` for some org connected to that instance) — this is an admin-level trust relationship, not something any external GitHub user possesses. The rules explicitly exclude findings that require privileged configuration access or an existing trusted-organization relationship as the sole precondition; here that precondition is unavoidable, since single-organization deployments (the default, where `github_default_organization` returns `nil` and `Shipit.github(organization: nil)` uses `secrets.github` directly with no per-owner secret dispatch [6](#0-5) ) have no cross-organization boundary to break at all.

### Recommendation
When resolving the organization for signature verification, cross-check that the resolved `repository_owner` matches the owner implied by `repository.full_name` (or, more robustly, verify the signature against the specific `webhook_secret` scoped to the `Repository`/`Stack` record actually being targeted, not one derived independently from attacker-controlled JSON). Handlers should not trust `payload['repository']['full_name']` as authoritative for repository selection unless it has been confirmed to match the same organization used to verify the signature.

### Proof of Concept
Not reproducible without a live multi-organization Shipit deployment and control over one org's registered `webhook_secret`; conceptually:
1. Attacker is a configured Shipit organization (`OrgOne`) with known `webhook_secret`.
2. Attacker crafts a `push` payload with `repository.owner.login = "OrgOne"` (used only for signature verification) but `repository.full_name = "OrgTwo/victim-repo"`.
3. Attacker signs the raw body with `OrgOne`'s `webhook_secret`; `verify_signature` passes because it only checks `Shipit.github(organization: "OrgOne")`.
4. `PushHandler` resolves the stack via `repository.full_name = "OrgTwo/victim-repo"` and triggers `sync_github` on the victim org's stack.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
