### Title
Cross-organization CI-status forgery bypasses repository scoping and triggers unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a payload's HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, attacker-supplied JSON body. That field is never cross-checked against the field the event handlers actually use to decide *what gets written*. `Shipit::Webhooks::Handlers::StatusHandler` in particular does not scope its write to any repository at all — it looks up commits globally by `sha`. This breaks the binding "organization authenticated == repository written," letting an attacker who legitimately controls a webhook secret for one configured GitHub organization forge a signed payload that is applied to a *different* organization's stack.

### Finding Description
Signature verification only proves the payload was signed with the secret of the organization named in the payload itself: [1](#0-0) [2](#0-1) 

In multi-tenant configurations `Shipit.github(organization:)` resolves a distinct `webhook_secret` per organization key in `secrets.github`: [3](#0-2) 

Once the signature check passes, the same raw payload is dispatched to every handler for the event, with no re-validation that `repository.owner.login` matches the repository actually being mutated: [4](#0-3) 

Most handlers scope their side effects using `Repository.from_github_repo_name(repository_name)` where `repository_name` is read from `repository.full_name` in the same payload: [5](#0-4) 

`StatusHandler` (used for GitHub Status webhook events, i.e. CI results that drive deployability) does not use this scoping helper at all — it resolves target commits purely by `sha` across the entire installation: [6](#0-5) 

Because `repository.owner.login` (used to pick the HMAC secret) and `sha`/`repository.full_name` (used to pick the record mutated) are independent, unvalidated fields inside the same attacker-controlled JSON body, an attacker who is a legitimate admin of Organization A (and therefore knows or controls Org A's `webhook_secret`) can sign a payload with Org A's secret while setting `sha` to a commit that belongs to a stack owned by Organization B. The signature check passes (it only proves "signed by Org A"), yet `StatusHandler#process` blindly creates a CI status on Org B's commit: [6](#0-5) 

A forged `state: 'success'` status on a stack configured for continuous deployment satisfies the CI-passed precondition and causes `ContinuousDeliveryJob`/`trigger_continuous_delivery` to fire automatically for that commit, as demonstrated by existing test coverage of this code path: [7](#0-6) 

The equality the engine relies on is: `organization whose secret signed the request == repository/stack that gets mutated by the request`. Before the attack this holds because normal GitHub deliveries always set `repository.owner.login` and `repository.full_name`'s owner to the same value. After the attacker's crafted request, the two diverge: the signature is verified against Org A while the write lands on a commit belonging to Org B's stack, and `StatusHandler` never checks that the two match.

### Impact Explanation
This allows an attacker to inject arbitrary, forged CI status ("success"/"failure") onto any commit in *any* stack managed by the Shipit instance, regardless of which organization/repository they actually have push or webhook access to, as long as they can sign with some organization's configured `webhook_secret`. On a stack with `continuous_deployment` enabled, this can trigger an unauthorized automatic deploy of a commit the attacker doesn't control the review/approval of, and can also be used to make an otherwise-failing commit appear deployable to `require_ci`/deploy-eligibility checks elsewhere in the engine. This matches the High-severity criterion "an unauthorized deploy" caused by escalation across a repository/organization trust boundary.

### Likelihood Explanation
The prerequisite is limited to control of one organization's webhook signing secret (an organization the attacker is expected to be able to configure webhooks for, e.g. their own org tracked by the same Shipit instance) — no GitHub write access to the victim repository, no Shipit session, and no API token are required. Given multi-organization Shipit deployments are an explicitly supported configuration (`github_app_config`/`github_organizations`), and `StatusHandler` performs zero repository-scoping, this is directly reachable by any actor entrusted with one org's webhook secret.

### Recommendation
In `StatusHandler` (and any other handler that doesn't already scope via `Handler#repository_name`), restrict the lookup to commits belonging to stacks whose repository matches `payload.dig('repository', 'full_name')`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { ... })` matching the repository derived from the payload. Additionally, in `WebhooksController#verify_signature`, after verifying the signature, assert that `repository.owner.login`/`organization.login` matches the repository actually referenced by `repository.full_name` before dispatching to handlers, so a payload signed by Org A can never be applied to Org B's data.

### Proof of Concept
1. Attacker configures/knows the `webhook_secret` for `OrgA`, a GitHub organization tracked by the target Shipit instance (a legitimate capability for their own org).
2. Attacker crafts a GitHub `status` event JSON body:
```json
{
  "sha": "<sha-of-a-commit-in-OrgB/victim-repo-stack>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POSTs to `/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and confirms the signature — the request passes. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the OrgB commit regardless of the signing organization — and calls `create_status_from_github!`, marking it CI-successful. [6](#0-5) 
6. If OrgB's stack has `continuous_deployment: true`, this forged success status triggers an unauthorized deploy job for that commit. [7](#0-6)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
