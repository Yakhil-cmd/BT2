### Title
Stale owner votes are not purged from pending `MultisigTransaction`s on owner removal, allowing a re-added owner's pre-removal approval to be silently counted toward quorum - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`multisig_account::update_owner_schema` removes an address from the `MultisigAccount.owners` vector but never touches the `votes: SimpleMap<address, bool>` stored inside any still-pending `MultisigTransaction`. Vote weight is computed at execution/`can_be_executed` time purely by intersecting `owners` with `votes` [1](#0-0) . If an owner is removed and later re-added to the same multisig (same address), their old vote entry from *before* removal is still present in the `votes` map of any transaction that has not yet been executed/removed, and it is immediately counted again — with no new signature or `vote_transaction` call from that owner after re-admission.

### Finding Description
The vote-counting helper only checks whether the address is currently in `owners` and whether `votes` contains that key; it does not check when the vote was cast relative to owner-set membership changes: [1](#0-0) 

`update_owner_schema` mutates the `owners` vector on removal but performs no cleanup of `votes` in any `MultisigAccount.transactions` entry: [2](#0-1) 

The existing test suite even documents the intermediate state — that a removed owner's approval stops counting — but does not exercise the re-add path: [3](#0-2) 

Because votes are recorded per `(multisig_account, sequence_number, owner_addr)` with no epoch/generation binding to the owner set that was active at vote time, this is structurally the same admission defect as the referenced Ethos report: a piece of per-address authorization state (`isAddressCompromised` there, `votes[owner_addr]` here) is not cleared when the owner's relationship to the account changes, and it silently regains effect when the same address is restored to a privileged role — without a fresh authorization action.

Attack / accidental-trigger path:
1. Owners create a pending `MultisigTransaction` (e.g., a sensitive payload) via `create_transaction`.
2. Owner `X` approves it via `approve_transaction`/`vote_transaction`, recording `votes[X] = true`.
3. `X` is removed via `remove_owners` (wrapping `update_owner_schema`); the transaction now lacks enough approvals and cannot execute — consistent with `test_validate_transaction_should_not_consider_removed_owners`.
4. Later, `X` (the same address — could be a wallet/multisig resource-account signer whose control has changed hands, or is added back for unrelated reasons, e.g. after being mistakenly removed, or after a dispute) is re-added via `add_owners`.
5. The stale `votes[X] = true` entry from step 2 is still stored on the still-pending transaction and is now recounted by `num_approvals_and_rejections_internal`, potentially pushing the transaction over the required-signatures threshold and letting it execute — without `X` (or whoever now controls `X`) ever approving under the current owner set/context.

### Impact Explanation
This allows a transaction to reach and pass the multisig approval threshold using an approval that was never re-affirmed under the current owner membership, effectively causing unauthorized execution of arbitrary multisig payloads (fund transfers, owner/threshold changes, module calls) whenever an owner is removed and later re-added while a transaction created in between (or before removal and still pending) exists. In adversarial settings — e.g., an owner is removed for being compromised or malicious and is later re-instated after resolving the dispute, or the same on-chain address changes real-world control — this reproduces exactly the "restored address regains privileged action capability without a fresh check" pattern from the source report, but here it grants extra unearned approval weight rather than merely lifting a block.

### Likelihood Explanation
Owner rotation (remove + re-add of the same address) is a normal, permitted multisig-admin operation and requires no special privilege beyond what any owner-management multisig transaction already requires. It does not require any cryptographic weakness — only the timing coincidence of a pending transaction existing across an owner removal/re-addition cycle, which is plausible for any active multisig with a queue of pending transactions and periodic owner turnover.

### Recommendation
When removing an owner in `update_owner_schema`, purge that owner's `votes` entry from every transaction still in `multisig_account_ref_mut.transactions` (or otherwise bind votes to an owner-set generation/epoch counter that increments on every add/remove, and require the vote's stored generation to match the current generation before counting it in `num_approvals_and_rejections_internal`).

### Proof of Concept
Move test sketch (extends the existing `test_validate_transaction_should_not_consider_removed_owners`):
```move
create_with_owners(owner_1, vector[owner_2_addr, owner_3_addr], 2, vector[], vector[]);
create_transaction(owner_1, multisig_account, PAYLOAD); // auto-votes owner_1 = true
approve_transaction(owner_2, multisig_account, 1);       // votes: owner_1, owner_2 = true
assert!(can_be_executed(multisig_account, 1), 0);        // 2/3, executable

let multisig_signer = &create_signer(multisig_account);
remove_owners(multisig_signer, vector[owner_2_addr]);
assert!(!can_be_executed(multisig_account, 1), 1);       // owner_2's vote no longer counts

add_owners(multisig_signer, vector[owner_2_addr]);       // re-add same address, NO new vote cast
assert!(can_be_executed(multisig_account, 1), 2);        // BUG: stale owner_2 vote is recounted, tx executable again
```
This demonstrates the transaction regaining sufficient approvals purely from re-adding `owner_2`, with no new call to `vote_transaction`/`approve_transaction` from `owner_2` after re-admission.

    inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
        let num_approvals = 0;
        let num_rejections = 0;

        let votes = &transaction.votes;
        owners.for_each_ref(|owner| {
            if (simple_map::contains_key(votes, owner)) {
                if (*simple_map::borrow(votes, owner)) {
                    num_approvals += 1;
                } else {
                    num_rejections += 1;
                };
            }
        });

        (num_approvals, num_rejections)
    }
