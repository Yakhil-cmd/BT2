## Title
Contract acceptance signature is bound only to `title` text, not the full contract terms, allowing acceptance-signature replay across different contracts - ([File: wallet.js])

### Summary
In both `prosaic_contract` and `arbiter_contract` flows, a peer's cryptographic acceptance of a contract is verified with `signed_message.validateSignedMessage`, but the check only confirms that the signed text equals `objContract.title` and that the signer address matches `objContract.peer_address` [1](#0-0) . Nothing in the verification ties the signature to the full contract terms (`text`, `amount`, `asset`, `ttl`, `arbiter_address`, `creation_date`, etc.), which are exactly the fields that make up the true contract hash (`getHash`) [2](#0-1) . This mirrors the audited `confidentialApprove` bug: the "status/consent" being asserted (agreement to a specific contract) is not actually bound into what is signed.

### Finding Description
When a peer accepts a prosaic or arbiter contract, `respond()` sends a `signed_message` that signs only the contract `title` string, produced via `signMessage`/`signer.readDefinition` flow, and the acceptor's device sends `{hash, status, signed_message}` back to the offeror [3](#0-2) .

On receipt, `wallet.js` validates the signed message like this for prosaic contracts:
```
signed_message.validateSignedMessage(db, objSignedMessage, objContract.peer_address, function(err) {
    if (err || objSignedMessage.authors[0].address !== objContract.peer_address || objSignedMessage.signed_message != objContract.title)
        return callbacks.ifError("wrong contract signature");
    processResponse(objSignedMessage);
});
``` [4](#0-3) 

The identical pattern exists for arbiter contracts:
```
signed_message.validateSignedMessage(db, objSignedMessage, objContract.peer_address, function(err) {
    if (err || objSignedMessage.authors[0].address !== objContract.peer_address || objSignedMessage.signed_message != objContract.title)
        return callbacks.ifError("wrong contract signature");
    processResponse(objSignedMessage);
});
``` [5](#0-4) 

The actual contract identity/hash, however, is computed from the *entire* set of terms:
```
function getHash(contract) {
	return crypto.createHash("sha256").update(contract.title + contract.text + contract.creation_date, "utf8").digest("base64");
}
``` [2](#0-1) 

Because the acceptance-signature check only compares against `objContract.title` (not `objContract.hash`, and not `text`/`amount`/`asset`/`ttl`/`arbiter_address`), a signature that a peer produced when accepting one contract can be replayed to make it appear they accepted a *different* contract, as long as:
1. The attacker (the contract offeror — the party who controls contract creation and is *not* privileged/trusted) crafts a second contract with the same `title` string but different `text`, `amount`, `asset`, or `arbiter_address`.
2. The attacker resends the peer's previously captured `signed_message` (title-only signature) as the `signed_message` field of the (forged) `arbiter_contract_response`/`prosaic_contract_response` for the new contract.

`processResponse` will then set `objContract.status` to `"accepted"` for the new (unauthorized) contract terms and — for arbiter contracts — proceeds to build a shared/multisig address and share it with cosigners, treating the peer as a fully consenting cosigner of the new terms [6](#0-5) . This exactly parallels the audited vulnerability: the semantically important field (which specific contract/status is being approved) is detached from the signature, enabling a replay/substitution attack that flips the meaning of a previously issued authorization.

Additionally, the "accepted" vs "declined" `status` string itself is also never bound into the signature — it is simply an unsigned sibling field of the message (`body.status`) alongside the signed title text [7](#0-6) . This is the closest structural analog to the original report's core defect (`_status` not tied to the signature).

### Impact Explanation
An offeror-controlled attack can cause a peer's wallet to record consent/"acceptance" of contract terms (amount, counterparty role, arbiter, asset) that the peer never actually signed, purely by reusing a title-matching signature from an earlier, legitimately accepted contract. For arbiter contracts, this drives creation of a shared address and CHARGE_AMOUNT deposit flow and can misrepresent which terms a party is bound to in a dispute, causing potential fund loss/misallocation when the arbiter later resolves a dispute based on the (forged) accepted contract record. This satisfies the "AA/contract fund loss or freezing" and "wallet and contract message handling" impact categories in scope.

### Likelihood Explanation
Exploitability requires the attacker to be the contract offeror (an unprivileged wallet user), able to freely choose the `title` string of any contract they create, and to have previously received one valid signed acceptance from the target peer for some contract sharing that title. Because `title` is attacker-chosen and unconstrained, and `getHash`/uniqueness relies on `text + creation_date`, crafting a second contract with an identical title but different substantive terms is straightforward. The main constraint is that the peer must have accepted at least one prior contract with the reused title — a realistic scenario in recurring or templated business relationships (e.g., "Service Agreement", "Freelance Contract").

### Recommendation
Bind the full material identity of the contract (i.e., `objContract.hash`, or a hash/structure covering `title`, `text`, `amount`, `asset`, `arbiter_address`, `ttl`, `creation_date`) — and the `status` value itself — into the signed message, rather than signing only the `title` string. `validateSignedMessage` call sites in `wallet.js` for `prosaic_contract_response` and `arbiter_contract_response` should compare `objSignedMessage.signed_message` against `objContract.hash` (or a canonical serialization including status), not `objContract.title`. Additionally, maintain replay protection (e.g., reject reuse of the same signed-message payload across different contract hashes).

### Proof of Concept
1. Attacker (Alice) creates Contract A with `title: "Service Agreement"`, sends offer to Bob via `arbiter_contract.createAndSend`.
2. Bob accepts Contract A; his wallet calls `respond(hash, "accepted", ...)`, producing `signed_message` that signs `text_to_sign = "Service Agreement"` (the title) under Bob's key [3](#0-2) .
3. Alice's wallet receives and validates this in the `arbiter_contract_response`/`prosaic_contract_response` handler, storing the base64 `signed_message`.
4. Alice creates Contract B with the same `title: "Service Agreement"` but different `text`/`amount`/`arbiter_address` (a different, less favorable set of terms for Bob), and different `creation_date` (so `getHash` differs and it's a "new" contract).
5. Alice crafts an `arbiter_contract_response`/`prosaic_contract_response` message for Contract B's `hash`, with `status: "accepted"` and reuses Bob's previously captured `signed_message` from step 2.
6. On Alice's own wallet (or any node performing the same validation, e.g. a cosigner), the check `objSignedMessage.signed_message != objContract.title` passes because both contracts share the same title, and `objSignedMessage.authors[0].address === objContract.peer_address` also passes since it's the same peer address [8](#0-7) .
7. Contract B is marked `"accepted"` and the arbiter/shared-address flow proceeds as if Bob consented to Contract B's actual terms, which he never signed.

		cb = function(){};

		var response = {hash: objContract.hash, status: status, signed_message: signedMessageBase64};
		if (authors)
			response.authors = authors;
		device.sendMessageToDevice(objContract.peer_device_address, "prosaic_contract_response", response);

	if (status === "accepted") {

				return cb(err);
			send(authors);
		});
	} else
		send();
}
