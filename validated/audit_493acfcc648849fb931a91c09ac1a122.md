### Title
Cross-repository status forgery via unscoped `sha` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` across the **entire** commits table, without checking the webhook payload's `repository.full_name` against the commit's actual stack repository. Every other handler (`CheckSuiteHandler`, `PullRequest::*`) scopes lookups through `Handler#stacks`, which is derived from `Repository.from_github_repo_name(repository_name)`. `StatusHandler` alone skips that binding, so a status event that is validly signed for repository A can write a `Status` (and flip `deployable?`) on a commit that actually belongs to a completely different repository/stack B, as long as the SHA matches.

### Finding Description
The broken binding, stated explicitly: the question requires
`payload.dig('repository','full_name') == commit.stack.repository.full_name`
to hold before a status write from that payload is allowed to affect `commit`. This binding is enforced by `CheckSuiteHandler` (`stacks.where(branch: ...)` then `stack.commits.where(sha: ...)` [1](#0-0)  ) and by the generic `Handler#stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)` [2](#0-1) .

`StatusHandler#process`, however, never calls `stacks` at all: [3](#0-2) 
It looks up **every** `Commit` row in the database whose `sha` matches `params.sha`, regardless of which repository/stack it belongs to, and calls `commit.create_status_from_github!(params)` on each, which creates a `Status` scoped to `commit.stack_id` and can flip `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [4](#0-3)  and `create_status_from_github!`/`add_status` [5](#0-4) .

`WebhooksController#verify_signature` only proves that the payload was genuinely signed by the GitHub App/org identified by `repository.owner.login` in the payload [6](#0-5) ; it never checks that the `repository` in the payload matches the repository owning the `commit` the handler ends up mutating. The signature check and the mutation target are decoupled — that is the root cause.

Exploit flow: SHA1 is content-addressed, not repository-scoped. An attacker who forks (or otherwise obtains a copy of) a victim's public repository has byte-identical commit objects, hence identical SHAs, in their own repository. If the attacker's own repository/org has the Shipit GitHub App installed (or any mechanism causing GitHub to emit a genuinely-signed `status` webhook for events on the attacker's own repo, e.g. via the GitHub Status API on their own commit), GitHub will sign and deliver a `status` event with `repository.full_name = "attacker/fork"`, `sha = <shared sha>`, `state: "success"`. This payload passes `verify_signature` (it is legitimately signed for the attacker's own org) and is then dispatched to `StatusHandler`, which finds **all** `Commit` rows sharing that SHA — including the victim's commit that lives under an entirely different Stack/repository — and writes a `success` `Status` on it, flipping `deployable?` for the victim's stack.

### Impact Explanation
This is a payload for one repository mutating another repository's commit/stack state — explicitly one of the listed Critical categories. Concretely: `Commit#deployable?` becomes true for the victim's commit without any CI ever having run against the victim's actual repository/branch, which can unblock continuous deployment (`schedule_continuous_delivery`) or merge-queue validation for the victim stack, i.e. an unauthorized deploy/merge condition. This is repeatable against any stack whose commits' SHAs the attacker can reproduce (any commit reachable from a public fork, or any commit whose content the attacker can otherwise duplicate), and it works against arbitrary victim stacks in the same Shipit instance since the lookup is completely global (`Commit.where(sha: ...)`, no stack/repo scoping).

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository they control that shares at least one commit SHA with a targeted victim commit (trivial for public repos via forking) and (b) the ability to have GitHub emit a genuinely-signed `status` webhook for that commit in their own repository — achievable if the Shipit GitHub App/webhook is installable by the attacker on their own repo, or if the attacker's org already has the app installed for legitimate reasons. No Shipit secrets, sessions, or API tokens are required, matching the "unprivileged attacker" threat model in scope. This is easily repeatable and low-cost given normal Shipit/GitHub App configurations that allow installation on arbitrary user-owned repos.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: resolve the target repository from the payload via `Handler#stacks` (i.e. `Repository.from_github_repo_name(repository_name)`), then only look up commits within `stack.commits.where(sha: params.sha)` for each matching stack, instead of querying `Commit` globally by `sha`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook for repository A cannot alter deployable? of a commit belonging to repository B with the same sha" do
  victim_stack  = shipit_stacks(:shipit)             # repository: "shipit"
  attacker_repo_full_name = "attacker/unrelated-repo" # explicitly NOT victim_stack.repository.full_name

  victim_commit = shipit_commits(:first)
  victim_commit.statuses.destroy_all
  refute victim_commit.reload.success?
  refute victim_commit.deployable?

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker' } }
  }

  # Binding under test, stated before tracing:
  assert_not_equal attacker_repo_full_name, victim_stack.repository.full_name

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # If the equality attacker_repo_full_name == victim_stack.repository.full_name is false
  # (it is), deployable? must remain false. The bug makes it flip to true instead.
  assert victim_commit.reload.deployable?, "commit became deployable via a payload for a different repository"
end
```
This mirrors the described minitest proof: a victim commit starts non-`success?`, a `StatusHandler.call` invocation with an attacker-controlled payload sharing only the `sha` (never the victim stack's repository) is made, and `commit.reload.deployable?` becomes true — confirming the binding is broken in `app/models/shipit/webhooks/handlers/status_handler.rb`.
