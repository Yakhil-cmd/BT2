Based on my research, this is a legitimate cross-tenant authentication-bypass vulnerability rooted in the `Team.find_or_create_by!` lookup being keyed only on the global GitHub `github_id`, not scoped to the organization that owns it.

### Title
Membership webhook from an unrelated (but Shipit-registered) organization can add arbitrary members to another organization's privileged `Team` by github_id collision - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely via `Team.find_or_create_by!(github_id: params.team.id)`, with no check that `params.organization.login` matches the `team.organization` already stored for that `github_id`. Because webhook signature verification in `WebhooksController#verify_signature` only proves the payload was signed by *some* organization registered in Shipit (the one named in `params.organization.login`/`repository_owner`), an operator of a second, unrelated but Shipit-connected organization can forge a genuinely-signed `membership` event whose `team.id` collides with an existing `Team` row that belongs to a different, privileged organization, causing `team.add_member(member)` to insert a `Membership` for an arbitrary login into that privileged team.

### Finding Description
The binding the code should enforce is: `Membership.team_id`'s `Team#organization` == `params.organization.login` (the org that actually signed/verified this specific webhook request). The code never checks this.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')`. For a `membership` event there is no `repository` key, so `repository_owner` = `params['organization']['login']`, i.e., fully attacker-supplied but must match a real, Shipit-configured organization whose `webhook_secret` was actually used to sign the request. It then does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. This only proves "this org (B) really sent this payload" — it says nothing about the `team.id` field's true owner.
2. `MembershipHandler#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`) does:
   ```ruby
   Team.find_or_create_by!(github_id: params.team.id) do |team|
     team.github_team = params.team
     team.organization = params.organization.login
   end
   ```
   The block only runs when a *new* record is created. `github_id` has no per-organization scoping. If a `Team` row already exists with `github_id == params.team.id` (e.g., a team belonging to org A, previously loaded into `Shipit.github_teams` via `Shipit.github_teams ||= github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }`, see `lib/shipit.rb`), the lookup returns that pre-existing org-A team even though the webhook was verified for org B.
3. `MembershipHandler#process` then calls `team.add_member(member)` where `member = User.find_or_create_by_login!(params.member.login)` — an attacker-chosen GitHub login, entirely disjoint from org A's real membership. This writes a `Shipit::Membership` row linking the attacker's user to org A's team.
4. `User#authorized?` (`app/models/shipit/user.rb:80-82`) does `teams.where(id: Shipit.github_teams.map(&:id)).exists?`. Since the forged `Membership` now points at a `Team` whose id is in `Shipit.github_teams`, `authorized?` flips to `true` for the attacker's `User` row — an authentication/authorization bypass. If that user later authenticates via OAuth as that same GitHub login, or if `logged_in?`/session flows key off this `User` record, they gain full org-authorized status in Shipit.

No existing guard closes this gap: `verify_signature` authenticates the *sender org*, not the *team payload's* owning org; `find_or_create_team!`'s `ExplicitParameters` schema only validates types/presence, not ownership; there is no comparison anywhere between `team.organization` (already persisted) and `params.organization.login` (from the current request) on the found/existing branch.

### Impact Explanation
An attacker who controls any second GitHub organization that Shipit has been configured to talk to (i.e., has its own registered `webhook_secret`/GitHub App config in Shipit, a normal, low-privilege multi-tenant setup) can, for a `github_id` value that collides with a privileged team from a *different* org, grant "authorized" status (`Shipit.github_teams` membership) to an arbitrary GitHub login. This is a High/Critical escalation into `Shipit.github_teams` authorization as defined in scope: it lets an attacker-controlled identity satisfy the authorization check used to gate access across the whole Shipit instance, without ever being a real member of the legitimate organization/team. This is repeatable for every subsequent `added` membership event and reversible/toggleable via `removed` as well, and is not limited to a single stack — it affects the global authorization gate used across the app (`Authentication` concern references `Shipit.github_teams`).

### Likelihood Explanation
Preconditions: Shipit must be configured with at least two organizations (multi-org GitHub Apps/webhook_secrets), one of which is a privileged org whose team is in `Shipit.github_teams`. The attacker must control (or compromise) a second, distinct organization already registered with Shipit — this is a normal, low-privilege position (e.g., any org onboarded to a shared Shipit instance), not a fabricated secret. The attacker must also know or guess the target team's numeric GitHub `id` (team ids are visible via GitHub's public team/API pages or via `Shipit.github_teams`-derived URLs in some configurations), which is a modest but realistic reconnaissance cost. Given these fairly common multi-tenant deployment conditions, the attack is straightforward and fully repeatable with ordinary HTTP POSTs to `/webhooks`.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization`, and explicitly reject (or no-op) if a `Team` with the given `github_id` already exists under a *different* `organization` than `params.organization.login`:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  if team && team.organization != params.organization.login
    raise ArgumentError, "team id #{params.team.id} does not belong to organization #{params.organization.login}"
  end
  team || Team.create!(github_team: params.team, organization: params.organization.login)
end
```
Additionally, consider making `(github_id, organization)` a unique composite key at the DB level, or validating `organization` matches on every find in `Team`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb` and `test/models/users_test.rb` style):
```ruby
test "membership webhook from org B cannot hijack org A's privileged team" do
  privileged_team = shipit_teams(:shopify) # organization: 'org-a', github_id: 555
  Shipit.stubs(:github_teams).returns([privileged_team])

  # Simulate genuinely-signed webhook from a *different*, Shipit-registered org "org-b"
  payload = {
    action: 'added',
    team: { id: privileged_team.github_id, name: 'Whatever', slug: 'whatever', url: 'https://…' },
    organization: { login: 'org-b' },
    member: { login: 'attacker' }
  }

  assert_difference -> { Membership.count }, 1 do
    Shipit::Webhooks::Handlers::MembershipHandler.call(payload) # signature verified against org-b's real secret
  end

  attacker = Shipit::User.find_by!(login: 'attacker')
  # BEFORE: attacker.teams.where(id: privileged_team.id).exists? == false
  # AFTER:
  assert attacker.teams.where(id: privileged_team.id).exists?
  assert attacker.authorized?  # bypass confirmed: authorized? flips true without ever belonging to org-a
end
```
This demonstrates the equality `Membership.team_id == privileged_team.id` being satisfied for a webhook whose verified `organization.login` (`org-b`) differs from `privileged_team.organization` (`org-a`), and shows `User#authorized?` flipping to `true` as a result.
