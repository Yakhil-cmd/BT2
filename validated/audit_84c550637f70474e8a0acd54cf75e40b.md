## Title
Missing sender authentication in `handleNewSharedAddress` allows an unpaired network attacker to inject a bogus multisig/shared address that the wallet accepts as "its own" - (File: wallet_defined_by_addresses.js)

### Summary
`handleNewSharedAddress()` validates the *structure* of a `new_shared_address` device message (definition hashes to the claimed address, signer addresses match definition leaves) but never authenticates *who is allowed to send it*. Unlike the sibling handler `create_new_shared_address`, which requires `from_address` to be one of the device addresses embedded in the definition template [1](#0-0) , the final `new_shared_address` case in `wallet.js` calls `walletDefinedByAddresses.handleNewSharedAddress(body, …)` without passing or checking `from_address` at all [2](#0-1) . This is the same bug class as CVE-2026-60112: a privileged, trust-establishing action (registering a new address as "mine"/shared) is performed for any caller without verifying that caller is entitled to trigger it.

### Finding Description
`new_shared_address` is dispatched to any correspondent device that reaches `handleMessageFromHub` (this subject is not even required to be in the `arrSubjectsAllowedFromNoncorrespondents` whitelist gate in `device.js`, but any already-paired correspondent, or one that pairs first, can send it) [3](#0-2) .

`handleNewSharedAddress` only checks that:
1. `body.definition` hashes to `body.address` [4](#0-3) 
2. Each `signers[path].address` matches the address found at that leaf of the definition [5](#0-4) 
3. `determineIfIncludesMeAndRewriteDeviceAddress` confirms one of the leaf addresses is already one of the *local* `my_addresses` or `shared_addresses` [6](#0-5) 

It never confirms that the message actually originates from a device that is supposed to be a cosigner, nor that the recipient ever participated in the `create_new_shared_address` → `approve_new_shared_address` negotiation for this exact template. Compare this to `validateAddressDefinitionTemplate`, used for the *offer* stage, which explicitly requires `arrDeviceAddresses.indexOf(from_address) !== -1` (sender device address must be mentioned in the definition template) [7](#0-6) . That authentication step is silently skipped for the final `new_shared_address` message, which is the one that actually calls `addNewSharedAddress()` and persists the address into `shared_addresses` / `shared_address_signing_paths` [8](#0-7) .

Since the local device's own address (e.g. one already used to receive real funds) satisfies the "one of the leaf addresses is my address" check, any correspondent (or, given `bIndirectCorrespondent` propagation, any device the victim indirectly knows of) can send a `new_shared_address` message embedding the victim's own address plus arbitrary attacker-controlled addresses/definitions (e.g. `["or", [victim_address, attacker_address]]`), and the wallet will silently register this as a legitimate shared address it recognizes and will watch/display as belonging to the user - without any confirmation dialog and without verifying the sender was a party to any prior approval flow.

### Impact Explanation
Because the resulting shared address is an `"or"`-composed definition containing the attacker's own address as an alternative spending path, once the victim's wallet begins treating/displaying the shared address as one of "its" addresses (and possibly directs incoming payments there, or a counterparty is told this is a joint address), the attacker can unilaterally spend any funds sent to that address using their own signature via the `"or"` branch - a direct unauthorized-spending / fund-loss scenario. It also lets an attacker plant fabricated multisig relationships that corrupt local wallet state (`shared_addresses`, `shared_address_signing_paths`), potentially causing the wallet to solicit cosigning ("sign") requests for outputs the attacker controls, or confuse balance/ownership tracking.

### Likelihood Explanation
Exploitation only requires the attacker to be (or become) a paired correspondent device of the victim - device pairing itself is attacker-initiated and low-friction (`handlePairingMessage` accepts any device presenting a valid, non-expired pairing secret) [9](#0-8) . No special privilege beyond being a correspondent is required to send `new_shared_address`; the missing `from_address` check in `wallet.js`'s dispatcher [2](#0-1)  means the message is processed identically regardless of the true relationship between sender and the referenced addresses.

### Recommendation
In the `new_shared_address` case of `handleMessageFromHub` (`wallet.js`), pass `from_address` into `handleNewSharedAddress` and require that `from_address` matches the `device_address` of at least one signer entry in `body.signers` (mirroring the check already done in `validateAddressDefinitionTemplate`). Additionally, `handleNewSharedAddress`/`determineIfIncludesMeAndRewriteDeviceAddress` should verify that a corresponding `pending_shared_addresses`/`pending_shared_address_signing_paths` record exists (i.e., that this device actually initiated or approved this specific definition template) before silently calling `addNewSharedAddress`, rather than accepting any well-formed definition that happens to reference a locally-known address.

### Proof of Concept
1. Attacker pairs with victim device (or is already an existing correspondent).
2. Attacker learns one of victim's addresses `V` (payment addresses are often shared to receive/send funds).
3. Attacker crafts `arrDefinition = ["or", [["address", V], ["address", A]]]` where `A` is attacker's own address, computes `shared_address = chash160(arrDefinition)`, and builds `signers = {"r.0": {address: V, device_address: victim_device_address}, "r.1": {address: A, device_address: attacker_device_address}}`.
4. Attacker sends device message `{subject: "new_shared_address", body: {address: shared_address, definition: arrDefinition, signers: signers}}` directly to the victim.
5. `handleNewSharedAddress` passes all structural checks (chash matches, signer addresses match leaves, `V` is found in victim's `my_addresses`), and `addNewSharedAddress` persists `shared_address` into the victim's wallet without ever confirming attacker was authorized to propose this relationship.
6. If any counterparty (potentially the attacker themselves, via chat "shared address" flows) sends funds to `shared_address`, the attacker can immediately spend them alone via the `"or"` branch, while the victim's wallet incorrectly believes the funds are safely held under a relationship it "owns."

**Note:** I was not able to fully trace how the UI layer (outside indexed ocore core files) decides which "shared addresses" to display/accept for outgoing payments, so I cannot definitively confirm the exact user-facing trigger that causes funds to be sent to such an injected address; this analysis is based on the ocore-level authentication gap in `wallet_defined_by_addresses.js`/`wallet.js` only.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);

function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
}
