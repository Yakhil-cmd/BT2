### Title
Global commit-sha lookup in `StatusHandler#process` allows cross-repository/cross-stack status forgery - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no repository scoping, unlike other handlers which restrict processing to `stacks` derived from `payload.dig('repository', 'full_name')`. Any signed status webhook for a sha that happens to also exist as a `Commit` row under a different `Stack` (e.g. a fork sharing pre-divergence history) will write a `Status` row for that other, unrelated stack too.

### Finding Description
The binding that should hold is: `status.stack_id == Stack.find_by(id: payload_repository_full_name→stacks).id`, i.e. every `Status` created from a webhook must belong to the stack(s) of the repository actually named and authenticated in that webhook's payload. Instead, the code enforces: `status.stack_id == commit.stack_id for every Commit whose sha == params.sha, across the whole Commits table`.

`StatusHandler#process` [1](#0-0)  ignores the `stacks` helper defined on the base `Handler` class, which exists precisely to scope handler behavior to `Repository.from_github_repo_name(repository_name)&.stacks` [2](#0-1) . Instead it queries `Commit.where(sha: params.sha)` unscoped by repository, and for every match calls `commit.create_status_from_github!(params)`, which calls `statuses.replicate_from_github!(stack_id, github_status)` using that commit's own `stack_id` [3](#0-2) [4](#0-3) .

`WebhooksController#verify_signature` only authenticates that the payload was correctly signed for `repository_owner` (`payload.dig('repository','owner','login')`) via `Shipit.github(organization: repository_owner)` [5](#0-4) . It does not, and cannot by itself, restrict which `Commit`/`Stack` rows the handler subsequently mutates — that restriction is left entirely to each handler's own use of `stacks`/`repository_name`, and `StatusHandler` never invokes them.

Attacker flow: attacker owns/controls repo `attacker/fork`, which is tracked as Stack A in Shipit. Repo `victim/upstream` (or another fork) is tracked as Stack B and, due to shared git history prior to divergence, still has a `Commit` row with the same `sha` as a commit in Stack A. The attacker sends a legitimately GitHub-signed `status` webhook for `attacker/fork` (signed with `attacker/fork`'s own valid webhook secret/org) naming that shared `sha` with `state: success`. `verify_signature` passes because the signature is valid for the attacker's own org/repo. `StatusHandler#process` then finds both `Commit` rows (Stack A's and Stack B's) sharing that `sha` and creates a `Status` for both stacks, even though Stack B's repository/org never authenticated or emitted this event.

### Impact Explanation
A single legitimately-signed webhook from an attacker-controlled repository forges a CI status (`success`/`failure`/etc.) on a completely different, unrelated stack/tenant's commit, without that tenant's webhook secret ever being used. Since `deployable?`/`blocked?`/continuous delivery checks rely on `Status`/`state` [6](#0-5) , a forged `success` status can make a victim commit appear deployable and trigger `schedule_continuous_delivery` [7](#0-6) , which can lead to an unauthorized deploy of a commit the victim organization did not intend to ship — matching the Critical category "a payload for one repository mutating another's stack, commit, task ... or an unauthorized deploy". It is repeatable against any pair of stacks that happen to share a `Commit.sha` (most realistically via forks sharing pre-fork history, but the code path itself is unscoped for any sha collision).

### Likelihood Explanation
Requires: (1) attacker controls/owns a GitHub repo tracked by Shipit as a Stack, and can trigger a real GitHub `status` webhook for it (trivial — any CI integration or the GitHub API can post a status on a commit in a repo the attacker owns); (2) a second, victim Stack whose `commits` table contains a `Commit` row with the identical sha — realistic for forked repositories imported into Shipit before/around fork time, since Shipit imports commit history per stack including shared ancestor commits. No Shipit secrets, sessions, or privileged roles are needed; the attacker only needs a real, validly-signed webhook for their own repo. This is a low-cost, deterministic, and repeatable exploit given the precondition.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository/stacks derived from the verified payload (as other handlers do via `stacks`), e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each { |commit| commit.create_status_from_github!(params) }`, so a status is only ever applied to commits belonging to stacks of the repository that was actually authenticated in the webhook.

### Proof of Concept
Minitest plan (`test/models/status_test.rb` style, no live GitHub):
1. Create `repo_a = create(:repository, owner: 'attacker', name: 'fork')`, `stack_a = create(:stack, repository: repo_a)`.
2. Create `repo_b = create(:repository, owner: 'victim', name: 'upstream')`, `stack_b = create(:stack, repository: repo_b)`.
3. Create `commit_a = create(:commit, stack: stack_a, sha: 'deadbeef' * 5)` and `commit_b = create(:commit, stack: stack_b, sha: commit_a.sha)` (shared ancestor sha).
4. Build a payload with `repository.full_name = 'attacker/fork'`, `sha: commit_a.sha`, `state: 'success'`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller signature, since signature only proves authenticity for `attacker/fork`, not authorization scope).
6. Assert: `Status.where(stack_id: stack_a.id, ...).exists?` is true (expected), AND `Status.where(stack_id: stack_b.id, ...).exists?` is also true (unexpected) — proving a webhook authenticated only for `attacker/fork` wrote a `Status` row for `victim/upstream`'s stack.
7. Assert equality-check failure explicitly: `refute_equal [stack_a.id], Status.where(commit_id: [commit_a.id, commit_b.id]).pluck(:stack_id).uniq.sort - [stack_a.id]` i.e. `stack_b.id` is present in the written stack_ids despite the payload naming only `attacker/fork`.
