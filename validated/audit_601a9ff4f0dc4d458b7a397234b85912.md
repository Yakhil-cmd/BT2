### Title
Stack-scoped API token bypasses stack authorization scope in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor inherited from `Shipit::Api::BaseController` and resolves the requested stack with `Stack.from_param!(params[:stack_id])` directly, bypassing the `stacks` scoping method that restricts a stack-scoped `ApiClient` to only the stack it was authorized for. This breaks the binding "the stack a token authorizes == the stack it touches."

### Finding Description
`ApiClient` supports a `stack_id` column that is meant to restrict a token to a single stack [1](#0-0) . `BaseController` enforces this scoping centrally: `stacks` returns only the authorized stack when `current_api_client.stack_id?` is true, and every other API controller resolves the target stack through `stacks.from_param!`, which raises `ActiveRecord::RecordNotFound` for a stack the client isn't scoped to. [2](#0-1) 

`CCMenuController`, however, defines its own `stack` method that calls `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` model, entirely skipping the `stacks` scoping helper: [3](#0-2) 

The `require_permission :read, :stack` before_action only verifies the client's *permission string* (`read:stack` in its `permissions` array), never that the specific stack being requested matches the client's `stack_id`: [4](#0-3) [5](#0-4) 

So the "verified" property (the token carries `read:stack` permission, possibly scoped to stack A) is not the same as the "acted on" property (`show` renders whichever `stack_id` param is supplied), exactly analogous to the reported bug class where the wrong account/object is checked against the wrong one.

### Impact Explanation
Any `ApiClient` token that holds the `read:stack` permission — even one deliberately scoped to a single stack via `stack_id` for restricted CI-status polling — can be replayed against the CCMenu endpoint (`GET /api/stacks/:stack_id/ccmenu.xml`) with an arbitrary `stack_id` to read the build/deploy status, last build label, and lock state of any other stack in the installation, including stacks belonging to different repositories the token holder was never granted access to. This is an unauthorized cross-stack read of stack state, matching the "High" impact category ("unauthenticated read of stack state ... escalation into authorization scope").

### Likelihood Explanation
Exploitation requires possession of any valid `ApiClient` authentication token with `read:stack` permission (the same starting condition assumed for legitimate stack-scoped tokens, e.g. tokens minted by `CCMenuUrlController#client`/`api_clients_controller.rb` for restricted use-cases). No additional privilege, session, or write access is required — only substituting the `stack_id` route/query parameter. This is a straightforward, low-effort exploitation once any such scoped token is obtained (e.g. leaked from a CI status widget URL).

### Recommendation
Change `CCMenuController#stack` to resolve the stack through the same authorization-aware helper used elsewhere, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so a stack-scoped client can only ever resolve to its own stack, consistent with `BaseController`.

### Proof of Concept
1. An admin (or the `/stacks/:id/settings` "Fetch URL" flow) issues, or a stack-scoped integration mints, an `ApiClient` with `permissions: ["read:stack"]` and `stack_id` set to Stack A's id.
2. Using that client's `authentication_token`, request `GET /api/stacks/<Stack-B-id>/ccmenu.xml?token=<token>` (or via Basic auth), where Stack B is a different, unauthorized stack.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(params[:stack_id])`, the request succeeds and returns Stack B's latest deploy/rollback status and lock state, even though the token is only supposed to be authorized for Stack A per `ApiClient#stack_id` [6](#0-5) .
