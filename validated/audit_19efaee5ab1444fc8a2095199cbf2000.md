### Title
Signature/binding org mismatch via `repository.owner.login` vs `organization.login` in `MembershipHandler` - ([File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::WebhooksController#repository_owner` prefers `params.dig('repository','owner','login')` over `params.dig('organization','login')` when deciding which org's `webhook_secret` to verify the signature against, while `Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` always uses `params.organization.login` to set `Team#organization`, independent of any `repository` key. An attacker who controls a legitimate, configured GitHub App/org in Shipit (e.g. `attacker-org`) can inject an arbitrary `repository.owner.login` = `attacker-org` (so the signature is checked and passes against a secret they know) while setting the top-level `organization.login` to a victim org (e.g. `shopify`), causing the `MembershipHandler` to create/mutate a `Team` bound to `shopify` and add an attacker-chosen GitHub login as a member.

### Finding Description
The binding the code should preserve is: `organization used to verify the signature == organization whose Team/Membership rows get written`. Tracing the code:

- `verify_signature` calls `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. [1](#0-0) 
- `repository_owner` resolves as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — note `repository` takes precedence over `organization` when both are present. [2](#0-1) 
- `MembershipHandler#find_or_create_team!` independently reads `params.organization.login` (never `repository.owner.login`) to set `Team#organization` on creation, and `process` uses `params.member.login` to add/remove a membership. [3](#0-2) 
- The `membership` event's `ExplicitParameters` schema only declares `action`, `team`, `organization`, `member` as required/permitted fields — it does not declare or forbid a `repository` key, so injecting an extra top-level `repository` object in the JSON body does not fail parsing. [4](#0-3) 
- The handler base class (`Handler#initialize`) parses the full raw payload via `ExplicitParameters::Parameters.define`, so unpermitted extra keys like `repository` are simply ignored by the schema, not rejected. [5](#0-4) 

**Attacker request**: POST `/webhooks` with header `X-Github-Event: membership`, JSON body containing:
```
{
  "action": "added",
  "team": {"id": <attacker-chosen id>, "name": "x", "slug": "x", "url": "https://example.com"},
  "organization": {"login": "shopify"},
  "member": {"login": "<attacker-chosen-github-login>"},
  "repository": {"owner": {"login": "attacker-org"}}
}
```
signed with `X-Hub-Signature: sha1=<hmac using attacker-org's real webhook_secret>`.

**Exploit flow**: `repository_owner` returns `"attacker-org"` because `repository.owner.login` is present and takes precedence. `Shipit.github(organization: "attacker-org")` returns the app config the attacker legitimately owns/knows the secret for, so `verify_webhook_signature` succeeds. The request passes `drop_unhandled_event` (membership has a registered handler) and reaches `MembershipHandler#process`, which reads `params.organization.login == "shopify"` — a value never checked against the org that verified the signature — and calls `Team.find_or_create_by!(github_id: params.team.id)`, setting `team.organization = "shopify"` on creation, then adds the attacker-controlled `member` to that team via `team.add_member(member)`. `User.find_or_create_by_login!` will also fetch/create a `User` record for whatever login the attacker supplies.

**Why existing guards fail**: `verify_signature` only checks that *some* value returned by `repository_owner` matches a valid signature; it never asserts that this same value equals `params.organization.login` used later by the handler. `MembershipHandler` never re-validates `params.organization.login` against `repository_owner` or against any authenticated identity. `ExplicitParameters` schema for `MembershipHandler` doesn't declare/require `repository`, so it neither rejects nor is influenced by an extra `repository` object smuggled into the payload only to affect `repository_owner` in the controller.

### Impact Explanation
An attacker with a legitimate, self-registered org config in Shipit's multi-org secrets (a documented supported setup) can forge webhook membership events that are cryptographically valid (per Shipit's own logic) yet get attributed to and mutate `Team`/`Membership` state under an entirely different, victim organization (e.g., `shopify`) that the attacker does not control and has no secret for. This is a cross-tenant write: `Team#organization` is set to a value the attacker chooses, and arbitrary GitHub logins can be inserted as `Membership` rows under that team. Since `User#authorized?` in `Shipit.github_teams` gates access based on `teams.where(id: Shipit.github_teams.map(&:id))`, if the fabricated team's `github_id` happens to collide with (or if an operator later trusts) a team referenced in `Shipit.github_teams`, this could escalate into unauthorized access grants — matching the "escalation into `Shipit.github_teams` authorization" / cross-tenant mutation impact categories. The attack is repeatable against any org configured in Shipit's secrets, using only the attacker's own real, legitimately-issued secret.

### Likelihood Explanation
Preconditions: (1) Shipit is configured with multiple orgs' webhook secrets (multi-org setup as documented), (2) the attacker has legitimately registered/owns one of those orgs' GitHub App (so they know its `webhook_secret`) — a normal, unprivileged capability documented as a supported configuration path, not a stolen secret. No Shipit session, API token, or victim-org secret is needed. The attacker only needs to know the target org's login string (`shopify`), which is public. This is a single crafted HTTP POST, fully repeatable and scriptable, requiring no interaction with GitHub itself and no privileged role.

### Recommendation
In `Shipit::WebhooksController`, resolve `repository_owner` consistently for the entire request and make `verify_signature` bind explicitly to whichever organization the handler will actually act on — e.g., pass the *same* resolved `organization_login` value into both the signature-verification step and into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization: organization_login) }`, and have `MembershipHandler` (and any other handler using `params.organization.login`) assert `params.organization.login == verified_organization` before persisting, raising/aborting otherwise. Alternatively, disallow/ignore a top-level `repository` key for org-level events like `membership` (there is no repository in real GitHub `membership` payloads) so `repository_owner` cannot be diverted away from `organization.login` for these events.

### Proof of Concept
```ruby
test "membership event with mismatched repository.owner.login vs organization.login writes Team under attacker-chosen org, verified against a different org's secret" do
  @request.headers['X-Github-Event'] = 'membership'

  payload = {
    action: 'added',
    team: { id: 999_999, name: 'Fake', slug: 'fake', url: 'https://example.com' },
    organization: { login: 'shopify' }, # binding side B: org whose Team gets mutated
    member: { login: 'attacker_chosen_login' },
    repository: { owner: { login: 'attacker-org' } } # binding side A: org used for signature verification
  }.to_json

  # attacker-org's real, known secret is used to sign -- verification passes against 'attacker-org'
  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, payload)
  @request.headers['X-Hub-Signature'] = signature

  Shipit.github(organization: 'attacker-org').expects(:verify_webhook_signature)
        .with(signature, payload).returns(true) # side A: verified as attacker-org

  assert_difference -> { Shipit::Team.where(organization: 'shopify').count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  # side B: Team created is bound to 'shopify' though 'shopify' never verified this request
  team = Shipit::Team.find_by(github_id: 999_999)
  assert_equal 'shopify', team.organization
  refute_equal 'attacker-org', team.organization # binding A != binding B: provenance violated
end
```

          end
        end
