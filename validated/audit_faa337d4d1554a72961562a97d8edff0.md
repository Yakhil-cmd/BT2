### Title
Cross-repository Status forgery — `Commit` status written without repository binding check - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` purely by `sha`, with no comparison between the webhook payload's `repository.full_name` and the `Stack#repository.full_name` that owns the matched commit. Any correctly-signed `status` webhook whose `sha` collides with a commit that already exists in another stack's repository will flip that commit's `state`/`deployable?`, even though the payload never named that stack's repository.

### Finding Description
The claimed binding is: `Handler#repository_name` for the delivered payload == `Stack#repository.full_name` of the commit whose `deployable?` flips.

Tracing the code:
- `WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers [1](#0-0) .
- For the `status` event, `Shipit::Webhooks.default_handlers` registers `Handlers::StatusHandler` [2](#0-1) .
- `StatusHandler#process` looks commits up **only by `sha`**, with no filter on `stack_id`, `repository`, or `branches` matching the commit's own stack:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
- `create_status_from_github!` writes a `Status` row and recomputes `commit.state` via `add_status`, which can transition the commit to `success` [4](#0-3) .
- `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [5](#0-4) , and depends only on the commit's own `status`, not on which repository sent the webhook.

The `params` schema accepted by `StatusHandler` never includes or validates `repository` at all — it only requires `sha`/`state` and accepts `description`, `target_url`, `context`, `created_at`, `branches` [6](#0-5) . So `params.repository` (payload's repo) is simply discarded before `process` runs — there is no code path in this handler that reads `repository.full_name` and compares it to `Commit#stack.repository.full_name`.

**Root cause**: `Commit.sha` is not scoped/unique per repository at the application layer for this lookup — the `status` webhook handler trusts the `sha` field as sufficient identification of "the commit to update," ignoring which repository the event actually came from.

**Exploit path and guard failure**: `verify_signature` in `WebhooksController` validates the HMAC using `Shipit.github(organization: repository_owner)`, i.e., the webhook secret is bound to the **GitHub organization** derived from the payload's `repository.owner.login`/`organization.login`, not to the specific repository [7](#0-6) [8](#0-7) . This means any repository under the same GitHub App installation/organization shares the same webhook secret and produces a validly-signed delivery for its own events. If an attacker controls (or pushes to) a repository "B" in the same organization as target stack A's repository, and crafts (or naturally reproduces, e.g. by cherry-picking/copying) a commit whose `sha` equals a commit's `sha` already tracked in stack A, then sets any CI status ("success") on that commit in repo B via the normal GitHub API (which they can do because they own repo B), GitHub will deliver a genuinely, correctly-signed `status` webhook for repo B. `verify_signature` passes because the signature is valid for the shared org secret and `repository_owner` from the payload correctly identifies repo B's owner. `StatusHandler#process` then matches the commit in **stack A** purely by `sha` and writes the "success" status to it, flipping `commit.deployable?` to `true` for a commit that never received a legitimate green CI status from stack A's own repository/CI.

None of the listed guards prevent this: `verify_signature`/`GitHubApp#verify_webhook_signature` only proves the event came from *some* repo under the correct org — it does not bind the event to a specific repository; `drop_unhandled_event` only checks the event type exists; the `ExplicitParameters` schema for `StatusHandler` never requires/validates `repository`; `force_github_authentication`, `User#authorized?`, `require_permission!`, and the `stacks` scope are irrelevant to unauthenticated webhook delivery; model validations on `Repository`/`Stack` don't constrain cross-repository `sha` collisions.

### Impact Explanation
An attacker who controls any repository sharing the same GitHub App/organization webhook secret as a target stack can cause a `success` (or any) CI status to be written to an arbitrary commit in an unrelated stack, purely by matching `sha`. This flips `Commit#deployable?` to `true` [5](#0-4) , which is read by `Stack#next_expected_commit_to_deploy` [9](#0-8)  and can trigger continuous deployment via `Commit#schedule_continuous_delivery` [10](#0-9) , or make manual deploy of that commit (bypassing `require_ci`) succeed where it should have been rejected. This is "a payload for one repository mutating another's stack/commit" and can lead to an unauthorized deploy — matching the Critical impact category.

### Likelihood Explanation
Exploitability requires: (1) the attacker to control a repository within the same GitHub organization/App installation as the victim stack (a real precondition for multi-repo Shipit deployments configured under one org secret, per `docs/setup.md`'s single-organization config example), and (2) the attacker's commit `sha` to collide with a specific commit already present in the victim stack — trivially achievable if the victim repository is public (the attacker can literally copy the exact commit object, since git SHAs are reproducible for identical content/metadata) or if the attacker can predict/observe a sha (e.g., PR commits are visible). No Shipit secret, session, or API token is required; the attacker only needs push/API access to their own repo in the shared org, which GitHub grants to any of its members. This is fully repeatable against any tracked commit in any stack sharing the same org secret.

### Recommendation
In `StatusHandler#process` (and analogously in `create_status_from_github!`/`add_status`), scope the `Commit` lookup by both `sha` and the repository identified in the payload — e.g., resolve `Stack`s whose `repository.full_name` equals `params.repository.full_name` (or `payload.name`, already present in GitHub's `status` payload) and only update commits within those stacks: `Commit.joins(:stack).where(sha: params.sha, stack: { repository: matching_repo })`. Require/validate `repository` in the `StatusHandler` params schema so payloads without a matching repository are rejected outright.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status webhook from repository B flips deployable? for a commit belonging to stack A's repository" do
          stack_a = shipit_stacks(:shipit) # repository.full_name == "shopify/shipit-engine" (stack A)
          commit_a = stack_a.commits.create!(
            sha: "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
            message: "test",
            authored_at: Time.now,
            committed_at: Time.now
          )
          refute commit_a.deployable?

          # payload names repo B ("attacker/forked-repo"), never stack A's repository.full_name
          payload = {
            'sha' => commit_a.sha,
            'state' => 'success',
            'name' => 'attacker/forked-repo',
            'repository' => { 'full_name' => 'attacker/forked-repo', 'owner' => { 'login' => 'attacker' } },
            'branches' => [{ 'name' => stack_a.branch }]
          }

          # Binding under test, BEFORE:
          assert_not_equal payload['repository']['full_name'], stack_a.repository.full_name

          StatusHandler.new.call(payload)

          # Binding AFTER: still mismatched, yet commit's deployable? flipped -- proves the write
          # happened without honoring the binding.
          assert_not_equal payload['repository']['full_name'], stack_a.repository.full_name
          assert commit_a.reload.deployable?, "commit in stack A became deployable from a payload naming repo B"
        end
      end
    end
  end
end
```
This demonstrates that `Commit#deployable?` can become `true` for a commit in stack A purely from a `StatusHandler` invocation whose payload `repository.full_name` never equalled `Stack#repository.full_name` for that commit's stack, confirming the broken binding.
