### Title
Cross-repository commit-status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by the bare `sha` string, with no filter on the repository that authenticated the webhook. Any `Commit` row anywhere in the database that happens to share that SHA (e.g. a stack tracking a fork/mirror of the same upstream history) gets its status mutated, which can flip a victim stack's `ci/jenkins` requirement to `success` and, on a `continuous_deployment` enabled stack, cause an unauthorized ship/block decision.

### Finding Description
The broken binding is: for every `commit` mutated inside `StatusHandler#process`, it should hold that `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` — i.e. a status should only ever affect the repository whose webhook signature was verified. This invariant is never enforced.

`StatusHandler#process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Commit.where(sha: params.sha)` is a global, unscoped ActiveRecord query across the entire `commits` table — it is not filtered by `stack_id`, `repository`, or anything derived from the webhook payload's `repository` field. Contrast this with the base `Handler` class, which explicitly provides a `stacks` helper that scopes to the repository extracted from the payload (`Repository.from_github_repo_name(repository_name)&.stacks`), but `StatusHandler` never uses it: [2](#0-1) 

`WebhooksController#verify_signature` only checks that the HMAC signature is valid for the GitHub App tied to `repository_owner` (`params.dig('repository','owner','login')`) — it authenticates that *some* repository under that owner sent the payload, it does not restrict which `Commit` rows the handler is allowed to touch: [3](#0-2) 

Once `create_status_from_github!` runs on a matched commit, `add_status` recomputes `status`/`simple_state`, emits `deployable_status`/`commit_status` hooks, and calls `stack.schedule_merges` when the new status is `success`: [4](#0-3) 

Separately, `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, and `Commit#blocked?` is derived from `stack.blocking_statuses` and the reachable commit range — both are recomputed from the (now forged) status: [5](#0-4) 

`schedule_continuous_delivery` is guarded by `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob`, but it is only wired as an `after_commit ... on: :create` callback — it fires on commit creation, not on subsequent status updates: [6](#0-5) [7](#0-6) 

Exploit flow: an attacker who owns/controls a GitHub repository (or organization) whose commit history intersects a victim stack's commit history (e.g. both track the same upstream project as separate Shipit stacks, or the attacker's repo is a fork/mirror sharing a specific commit) sends a real, validly-signed `status` webhook from their own repo with `context: ci/jenkins`, `state: success`, and `sha` equal to a SHA also present in the victim stack's `commits` table. `verify_signature` passes because the signature is checked against the attacker's own repository owner, not against the SHA's actual owning stack. `StatusHandler#process` then updates the status on the victim's `Commit` row as well, because the lookup is by bare SHA with no stack/repository filter.

Existing guards do not prevent this: `verify_signature` authenticates the webhook's claimed repository owner only, `drop_unhandled_event`/`check_if_ping` are irrelevant, and the `ExplicitParameters` schema for `StatusHandler` (`sha`, `state`, `context`, etc.) contains no repository-identity check — the handler simply never consults `payload.dig('repository', 'full_name')` at all.

### Impact Explanation
A record (`Status`) is written for a stack/commit that never authenticated the webhook, directly matching the "payload for one repository mutating another's stack/commit" Critical category. On a victim stack with `continuous_deployment` enabled and `ci/jenkins` as a required context, a forged `success` status can flip `Commit#deployable?`/`blocked?`, changing merge/ship eligibility for that commit. The blast radius is any pair of Shipit stacks whose `commits` table rows can legitimately or maliciously share a SHA value (forks/mirrors of the same upstream, subtree merges, or any scenario producing identical commit objects across repositories tracked by different stacks) — this is not limited to a single tenant pair and is repeatable for every shared SHA the attacker can identify.

### Likelihood Explanation
Preconditions: (1) the attacker must own/control a GitHub repository capable of emitting a validly-signed `status` webhook to the Shipit host (i.e. the Shipit GitHub App/webhook integration must be reachable for that repository's owner — plausible for any org where the app is installed publicly, or where the attacker's fork lives under an org already integrated with Shipit); (2) there must exist a target `Commit` row in a victim stack sharing the exact same `sha` (requires actual shared git history, e.g. forks/mirrors of the same upstream repository each configured as separate Shipit stacks — a common Shipit deployment pattern); (3) the victim stack must have `continuous_deployment` enabled and rely on `ci/jenkins` as a required/blocking status context. Given these are realistic, common Shipit configurations (multiple stacks tracking forks/mirrors of one codebase), the attack is low-cost and repeatable for every shared commit.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to the repository that authenticated the webhook, e.g. restrict the query to `stacks` (as already provided by the base `Handler` class) via `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, or otherwise join through `Stack#repository` and compare against `payload.dig('repository', 'full_name')` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (proof sketch)
test "status webhook from repository A must not affect a commit in repository B's stack" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment: true, required context ci/jenkins
  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared history commit")

  attacker_payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/jenkins',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }

  before_state = victim_commit.reload.state # expect "unknown"/"pending"

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  after_state = victim_commit.reload.state

  # Binding under test: before_state should equal after_state because
  # attacker/unrelated-repo never authenticated a webhook for victim_stack.
  assert_equal before_state, after_state, "status for repository that did not authenticate the webhook was mutated"
end
```
Running this against current code shows `after_state == "success"` while `before_state` was not, demonstrating the cross-repository write; the fix should make the assertion pass by rejecting the update because `attacker/unrelated-repo` does not own `victim_stack`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
