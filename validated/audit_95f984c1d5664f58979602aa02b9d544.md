### Title
`OpenedHandler#provision?` operator-precedence bug lets attacker bypass `review_stacks_enabled` via PR label - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` (and identically `ReopenedHandler#unarchive?`) uses Ruby's `&&`/`||` precedence such that `review_stacks_enabled` only gates the `allow_all` disjunct, not the `allow_with_label` or `prevent_with_label` disjuncts. This lets an attacker who controls their own PR's labels force stack auto-provisioning even when the operator has `review_stacks_enabled: false`.

### Finding Description
The claimed binding is: `provision? == true` should require `repository.review_stacks_enabled == true` (operator's opt-in), i.e. `review_stacks_enabled && (allow_all? || (allow_with_label? && label) || (prevent_with_label? && !label))`.

The actual code at [1](#0-0)  is:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
In Ruby, `&&` binds tighter than `||`, so this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present) || (prevent_with_label? && !label_present)`. `review_stacks_enabled` is only ANDed into the first disjunct; the other two disjuncts are fully independent of it. The identical pattern exists in `ReopenedHandler#unarchive?` at [2](#0-1) .

Exploit flow: an attacker who owns a repository/fork configured on the Shipit host with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (set by the operator for some unrelated purpose, e.g. staged rollout intent that was never enabled) opens a pull request and applies the configured label (e.g. `run-me`) to their own PR. The `pull_request` webhook `opened` event reaches `OpenedHandler#process` at [3](#0-2) , `respond_to_pull_request_opened?` calls `provision?`, which evaluates true due to the second disjunct regardless of `review_stacks_enabled`, and `ReviewStackAdapter#find_or_create!` creates a stack for the attacker's branch/environment, queuing provisioning that will check out and run the attacker's `shipit.yml`.

Existing guards do not catch this: `LabeledHandler#respond_to_label_change?` correctly ANDs `review_stacks_enabled` across the whole `archive?`/`unarchive?` disjunction at [4](#0-3) , showing the intended binding — but `OpenedHandler` and `ReopenedHandler` do not replicate this correctly. `ExplicitParameters` schema validation and `drop_unhandled_event`/signature verification only govern payload shape/authenticity, not this authorization logic, so they don't prevent the divergence. Test coverage in [5](#0-4)  always sets `review_stacks_enabled` true when testing `allow_with_label`/`prevent_with_label` behaviors, and the one test with `review_stacks_enabled: false` only tests `behavior: :allow_all` [6](#0-5) , so this exact combination (`review_stacks_enabled: false` + `allow_with_label` + label present) is untested and the bug is unguarded.

### Impact Explanation
An unprivileged attacker (repository owner of their own repo on the Shipit host, or PR author with label permission on their fork) can force unauthorized `Shipit::Stack` creation and provisioning for a repository the operator explicitly disabled review-stack auto-provisioning for. Provisioning executes the attacker's `shipit.yml` from their branch, leading to command execution on the deploy host in the review-stack provisioning context. This is repeatable against any repository configured with `review_stacks_enabled: false` + `provisioning_behavior: allow_with_label`, matching Critical impact (RCE via provisioning of attacker-controlled `shipit.yml`) scoped to repositories with this specific configuration.

### Likelihood Explanation
Requires a repository on the Shipit instance configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (or `prevent_with_label`, in the negated case) — a plausible operator misconfiguration, since `provisioning_behavior` and `review_stacks_enabled` are separate fields and an operator could set the behavior in advance without yet enabling review stacks. Given that configuration, attacker cost is trivial: open a PR and add/omit a label they control, no secrets or privileged roles needed. Fully repeatable per PR/webhook delivery.

### Recommendation
Wrap the full disjunction in explicit parentheses so `review_stacks_enabled` gates all three provisioning-behavior branches, matching `LabeledHandler`'s pattern:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the identical fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks_enabled is false even if allow_with_label label matches" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "run-me"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "run-me" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Given the current code, this assertion fails (`Shipit::Stack.count` increases by 1) because `repository.review_stacks_enabled == false` yet `provision?` evaluates true via the `allow_with_label? && label` disjunct — demonstrating both sides of the claimed binding (`review_stacks_enabled == false` vs. actual `provision? == true`) diverge.
