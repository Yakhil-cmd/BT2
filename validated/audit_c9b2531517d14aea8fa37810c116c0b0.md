## Title
Cross-Stack CCMenu Token Scope Bypass via Unscoped `Stack.from_param!` Lookup - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` authenticates requests with a bearer `token` param resolved to an `ApiClient`, which can be scoped to a single `stack_id`. However, the controller's private `stack` method bypasses the stack-scoping enforced everywhere else in the API and looks up *any* stack by the `stack_id` URL param, letting a token issued for one stack read build/deploy status for every other stack.

### Finding Description
The CCCM bug class is: data is authorized/scoped for one entity, but the code that acts on it never re-checks that scope before using a different, attacker-supplied value. In shipit-engine the analogous binding is: `ApiClient#stack_id` (the stack a token authorizes) must equal the stack whose data the controller actually reads.

`Shipit::Api::BaseController` establishes this binding centrally: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` resolves `params[:stack_id]` only within that restricted set. Every other API controller (e.g. `Api::DeploysController`, `Api::TasksController`, `Api::RollbacksController`) inherits this `stack` method unchanged, so a stack-scoped `ApiClient` can never touch a stack outside its scope.

`Shipit::Api::CCMenuController` overrides this method and drops the scoping entirely: [2](#0-1) 
`stack` is redefined as `Stack.from_param!(params[:stack_id])` — a direct, unscoped lookup — instead of `stacks.from_param!(params[:stack_id])`. `require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which checks the string permission list, not the stack scope: [3](#0-2) 
So the only remaining check is "does this token have `read:stack`", not "does this token's stack match the requested stack." `Stack.from_param!` will happily resolve any repo/environment/branch identifier the caller supplies.

The token itself is legitimately generated by `CcmenuUrlController#fetch`, which creates a token via `ApiClient` scoped to the requesting stack and embeds it as a URL query parameter meant to be pasted into third-party CI dashboard widgets (CCTray clients): [4](#0-3) 
These are inherently low-trust, often publicly reachable, tokens (embedded in third-party desktop/CI tools) — precisely the kind of “permitted for stack X” credential the scoping mechanism exists to contain. Because `CCMenuController#stack` never consults `current_api_client.stack_id`, holding a token for stack `org/repo-a/production` is sufficient to query `GET /api/stacks/*org/repo-b/staging/ccmenu?token=...` and get back `org/repo-b/staging`'s build/deploy state.

### Impact Explanation
Before the request: the equality that should hold is `current_api_client.stack_id == requested_stack.id` (enforced by `stacks.from_param!` in every other controller). After the request through `CCMenuController#show`, that equality is never checked — `stack` resolves independently of `current_api_client.stack_id`. The response leaks `stack.merge_status`, latest deploy/rollback `id`, `running?`, and timestamps for any stack in the installation: [5](#0-4) 
This matches the "High" impact tier defined by the rules — unauthenticated (out-of-scope) read of stack state/deploy output using a token that was authorized for a different, narrower scope. It is a genuine boundary crossing: no privileged account, webhook secret, or session is required — only possession of any single stack-scoped CCMenu token (which by design is meant to be shared with low-trust external tooling).

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where CCMenu/CCTray integration is used: the token is explicitly designed to be embedded in third-party URLs/config files (CI dashboard widgets), so its exposure surface is inherently wider than an internal API token. Any holder of one such token can enumerate/guess other stacks' `stack_id` path segments (`owner/repo/environment`, which are often predictable or discoverable via the public web UI) and pull their status without needing elevated permissions or repository write access.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to use the scoped `stacks` relation from `BaseController`, i.e. `stacks.from_param!(params[:stack_id])`, exactly like every other API controller, so that a stack-scoped `ApiClient#stack_id` is enforced against the requested `stack_id` before rendering any deploy/build status.

### Proof of Concept
1. As an authenticated user, visit stack A's settings page and enable CCMenu; `CcmenuUrlController#fetch` creates an `ApiClient` with `stack_id = A.id` and returns a URL like `/api/stacks/org/repo-a/production/ccmenu?token=T`.
2. Using the same token `T`, request `/api/stacks/org/repo-b/staging/ccmenu?token=T` (a different stack B the token was never scoped to).
3. `CCMenuController#authenticate_api_client` succeeds (token `T` is valid), `require_permission :read, :stack` passes (`check_permissions!` only checks the permission list), and `stack` resolves via `Stack.from_param!(params[:stack_id])` to stack B regardless of `T.stack_id == A.id`.
4. The response renders stack B's `merge_status`, latest deploy id, and running state — data the token holder was never authorized to see. [2](#0-1) [1](#0-0)
