### Title
Membership webhook authenticates against one GitHub organization while acting on team/organization data taken from an unverified field of the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to verify a webhook against using `repository_owner`, which prefers `params.dig('repository','owner','login')` over `params.dig('organization','login')`. `Webhooks::Handlers::MembershipHandler`, however, attributes the resulting team/membership mutation using the payload's `organization.login` and `team.id` fields directly, without checking that they match the organization whose secret was used to authenticate the request. In a multi-org Shipit deployment (`config/secrets.*.yml` supports `github: { org1: {...}, org2: {...} }`), an attacker who legitimately administers one configured GitHub org (and therefore knows that org's `webhook_secret`) can forge a `membership` payload that is *signed* as their own org but *declares* an arbitrary `organization.login` / `team.id`, causing Shipit to add themselves to a `Team` record that maps to `Shipit.github_teams`.

### Finding Description
`repository_owner` in `WebhooksController` is computed purely from the JSON body, before/independently of whether that value is what the rest of the pipeline will use: [1](#0-0) 

For a `membership` event, GitHub's real payload only contains `organization`, not `repository`. Nothing in the controller enforces that constraint on attacker-supplied payloads. An attacker can inject a `repository.owner.login` key pointing at an org they control (`attacker-org`) so that `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and verifies the signature with `attacker-org`'s own `webhook_secret`, which the attacker knows because they are the one who configured/owns that org's webhook in this multi-tenant instance: [2](#0-1) 

Once the signature passes, `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler`, which ignores `repository_owner`/the verified org entirely and instead trusts the payload's own `organization.login` and `team.id` to find-or-create a `Team` and add/remove the named `member`: [3](#0-2) 

The binding that is broken: **the organization that authenticated the request (via HMAC secret lookup keyed off `repository_owner`) is not the organization the payload is written against** (`organization.login` used by `find_or_create_team!`, and `team.id` which can target an already-existing `Team` row belonging to a different org, e.g. one backing `Shipit.github_teams`). Membership/team objects created or modified by this handler feed directly into authorization: `User#authorized?` checks membership in `Shipit.github_teams`, and `Team#handle`/`Team.find_or_create_by_handle` ties `Team` rows to `Shipit.github_teams`: [4](#0-3) [5](#0-4) 

Before the attacker's request: attacker is a member of `attacker-org` only, `authorized? == false` for the Shipit instance whose access is gated by e.g. `shopify/developers`. After the crafted `membership` "added" webhook (correctly HMAC-signed under `attacker-org`'s secret, but declaring `organization.login = "shopify"` and the real `team.id` of `shopify/developers`): the attacker's `User` row becomes a member of the `shopify/developers` `Team`, and `authorized?` now returns `true`.

### Impact Explanation
This maps to the explicitly listed High-impact category "escalation into `Shipit.github_teams` authorization." The attack requires no `ApiClient` token, no Shipit session, no GitHub App private key, and no write access to the victim repository — only knowledge of one's own org's configured webhook secret in a multi-org deployment, which is exactly the kind of unprivileged-relative-to-the-victim-org attacker the scan targets.

### Likelihood Explanation
Requires the deployment to use the documented multi-organization `github:` secrets layout (`config/secrets.development.shopify.yml` shows this schema is a supported configuration, not a misconfiguration), and the attacker must know the real GitHub `team.id` of the target team (discoverable via GitHub's public/team APIs or leaked from a prior legitimate webhook/log). This narrows likelihood somewhat but does not require any secret belonging to the victim org.

### Recommendation
In `MembershipHandler#find_or_create_team!` and `#process`, verify that `params.organization.login` (and the org owning `params.team.id`) matches the organization actually used to authenticate the webhook (i.e., pass the verified `repository_owner`/organization down from the controller and compare it against `params.organization.login`, rejecting mismatches). More generally, `verify_signature` should not select the verification key from a field (`repository.owner.login`) that downstream handlers do not subsequently re-validate — the field used to pick the secret and the field(s) acted upon must be the same, verified value.

### Proof of Concept
1. Deploy Shipit configured for two GitHub orgs, `shopify` and `attacker-org`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` schema).
2. Attacker, who administers `attacker-org` in this Shipit instance, knows `attacker-org`'s `webhook_secret`.
3. Attacker discovers `shopify/developers`' real GitHub team id (e.g. via GitHub API) and its Shipit-side `github_id`.
4. Attacker POSTs to `/webhooks` with `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "repository": {"owner": {"login": "attacker-org"}},
  "organization": {"login": "shopify"},
  "team": {"id": <shopify_developers_github_id>, "name": "Developers", "slug": "developers", "url": "https://api.github.com/..."},
  "member": {"login": "attacker-github-login"}
}
```
   signed with `X-Hub-Signature: sha1=<HMAC using attacker-org's webhook_secret>`.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org`, verifies successfully with `attacker-org`'s secret.
6. `MembershipHandler#process` finds the existing `shopify/developers` `Team` by `github_id`, creates/finds `User` for `attacker-github-login`, and calls `team.add_member(member)`.
7. Attacker logs into Shipit as `attacker-github-login`; `User#authorized?` now returns `true` because the user is a member of a `Team` included in `Shipit.github_teams`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
