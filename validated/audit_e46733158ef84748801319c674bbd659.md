### Title
`ContainsEscapeSequence` only detects the ESC byte (0x1B) and misses 8-bit C1 control codes, allowing terminal-manipulating sequences to bypass the escape-sequence guard in `gh repo read-file`, `gh gist view`, and `gh pr diff` - ([File: pkg/iostreams/content.go])

### Summary
`ContainsEscapeSequence` in `pkg/iostreams/content.go` is the sole gate used by `gh repo read-file`, `gh gist view --raw`, and `gh pr diff` (non-color, piped/refusal path) to decide whether attacker-controlled text may reach the terminal. It only scans for the single byte `0x1B` and ignores 8-bit C1 control codes (`0x80`-`0x9F`, e.g. `0x9B` as CSI, `0x9D` as OSC, `0x90` as DCS), which some terminal emulators interpret as control sequences without a preceding ESC.

### Finding Description
`ContainsEscapeSequence` is defined as: [1](#0-0) 
It is used as the terminal-injection guard in three commands that print attacker-supplied bytes:
- `gh repo read-file`: after fetching file content from the Contents API, sanitization is explicitly turned off (`opts.IO.SetContentSanitization(false)`) unconditionally, before the guard runs, so once `ContainsEscapeSequence` returns false the bytes are written raw to `ContentOut` with no secondary sanitizer. [2](#0-1) 
- `gh gist view`: in the non-TTY raw-dump branch, the guard runs and then sanitization is likewise disabled for the actual write. [3](#0-2) 
- `gh pr diff`: same pattern in the non-color, non-TTY branch. [4](#0-3) 

Because the check is `bytes.IndexByte(b, 0x1B) >= 0`, a file/gist/diff whose "escape" bytes are encoded as raw 8-bit C1 controls (no `0x1B` present at all) passes the guard undetected, and — for `read-file` specifically — reaches the terminal with no fallback sanitizer at all, since `SetContentSanitization(false)` was already applied before the check. For `gist view` and `pr diff`, the TTY path keeps the `asciisanitizer`-based sanitization active (`newContentWriter` wraps `ContentOut` when `sanitizeContent` is true), which provides some backstop in interactive mode, but the piped/non-TTY branches disable sanitization outright once the (bypassable) guard passes, per the code cited above. [5](#0-4) 

### Impact Explanation
If a victim's terminal emulator honors raw 8-bit C1 control bytes (S8C1T-style behavior, still supported by some xterm-compatible/legacy terminal configurations), an attacker-controlled file (via `read-file`), gist file (via `gist view`), or PR diff content (via `pr diff`) could carry cursor-repositioning, screen-clearing, or prompt-spoofing sequences encoded purely with C1 bytes and slip past the "refuse escape sequences" protection intended to stop exactly this class of attack. This falls into GitHub's terminal/output-injection impact class (content manipulation of the victim's terminal display), not remote code execution or credential theft directly, but it undermines the guard's stated invariant ("a malicious file cannot manipulate a downstream terminal", per the code comment in `read_file.go` line 198).

### Likelihood Explanation
Exploitability is conditional on the victim's terminal actually interpreting standalone 8-bit C1 bytes as control functions. Most modern terminal emulators run in UTF-8 mode, where bytes `0x80`-`0x9F` are invalid as standalone UTF-8 code units and are typically replaced/dropped rather than executed as C1 controls; interpreting raw C1 requires an 8-bit/Latin-1 locale or explicit legacy compatibility mode, which is uncommon by default in current terminal emulators (iTerm2, GNOME Terminal, Windows Terminal, modern xterm defaults). This reduces the real-world likelihood substantially, but does not change that the code-level guard itself is objectively bypassable by design (single-byte 0x1B check, no C1 handling), and the attacker precondition (publish a file/gist/PR with the crafted bytes) is trivially met by an unprivileged attacker.

### Recommendation
Broaden `ContainsEscapeSequence` (or replace its use with the existing `asciisanitizer`-based sanitization path used elsewhere in the codebase, e.g. `iostreams.Untrusted`) to also detect/strip C1 control bytes (`0x80`-`0x9F`) in addition to `0x1B`, and ensure `SetContentSanitization(false)` is never applied before this broadened check in `read_file.go`, `view.go`, and `diff.go` — i.e., keep a sanitizing backstop even after the explicit guard passes, rather than relying solely on the single-byte scan.

// ContainsEscapeSequence reports whether b contains an ANSI escape byte (0x1B),
// which can manipulate a terminal when printed.
func ContainsEscapeSequence(b []byte) bool {
	return bytes.IndexByte(b, 0x1B) >= 0
}

// SetContentSanitization toggles ANSI escape sanitization on ContentOut.
// Commands should call this with false when an explicit opt-out flag (e.g.
// --allow-escape-sequences) is set, so subsequent writes of external content
// pass through unmodified.
func (s *IOStreams) SetContentSanitization(enabled bool) {
	s.sanitizeContent = enabled
	s.ContentOut = newContentWriter(s.Out, enabled)
}

// newContentWriter returns the writer to wire up as ContentOut. When
// sanitize is true it inserts an asciisanitizer in front of the underlying
// writer; otherwise it returns the underlying writer directly so writes
// reach stdout unchanged.
func newContentWriter(out io.Writer, sanitize bool) io.Writer {
	if !sanitize {
		return out
	}
	return transform.NewWriter(out, &asciisanitizer.Sanitizer{})
}
