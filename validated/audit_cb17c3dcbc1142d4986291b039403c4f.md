### Title
Missing depth-limit guard in `json_stringify` allows stack-overflow DoS via incrementally-grown state objects - (File: `formula/evaluation.js`)

### Summary
The oscript `json_stringify` operator serializes a formula-evaluated value using the custom recursive stringifier `string_utils.getJsonSourceString()`, but — unlike the sibling `json_parse` and `chash160` operators — it never calls `isTooBigObj()` to bound the depth/size of the object before serializing it [1](#0-0) . `json_parse` explicitly rejects oversized/too-deep results with `isTooBigObj(json)` [2](#0-1) , and `chash160` performs the same check before hashing an object [3](#0-2) . `json_stringify` skips this guard entirely, handing the value straight to the recursive `getJsonSourceString()` implementation, which has no depth limit of its own (only a `WeakMap` used to memoize repeated references, not to bound depth) [4](#0-3) .

### Finding Description
Object literals built directly inside a single oscript formula are bounded because the formula evaluator increments a depth counter on every `evaluate()` call and aborts once it exceeds 100 [5](#0-4) . This is the same order of magnitude as the `MAX_DEPTH = 100` AA-definition guard [6](#0-5)  and the unit-level `isTooDeeplyNestedOrHasTooManyNodes(objUnit)` check performed on every incoming unit [7](#0-6) .

However, AA state variables are **not** rebuilt as one large literal per trigger — they are read back as an already-evaluated `wrappedObject` and can be cheaply re-wrapped one level deeper per call, e.g. a formula such as `var['x'] = {a: var['x']}`. Each such trigger only evaluates a small, shallow AST (well under the 100-node evaluate-depth cap), yet it nests the *stored* object one additional level. Because state is persisted between AA triggers, an attacker can send a sequence of cheap trigger units that each add one level of nesting to a state variable, accumulating thousands of levels over time — far beyond the 100-level cap that protects any single unit or formula expression.

When the resulting deeply-nested state object is later passed to `json_stringify(var['x'])`, the value reaches `formula/evaluation.js`'s `json_stringify` case, which — unlike `json_parse`/`chash160` — omits the `isTooBigObj` guard and calls `string_utils.getJsonSourceString()` directly [8](#0-7) . `getJsonSourceString`'s internal `stringify()` recurses once per nesting level with no depth ceiling [9](#0-8) , so a sufficiently deep object triggers a native `RangeError: Maximum call stack size exceeded` synchronously inside AA response computation — exactly the same bug class as the Axios advisory, where a depth guard exists for the general recursive path but a specific serialization shortcut bypasses it.

### Impact Explanation
Every full node that executes the AA (to compute its response/bounce and update state) evaluates the same trigger and hits the same unguarded `json_stringify` call, so the crash is deterministic and reproducible across all nodes processing that trigger — not an isolated single-node fault. This can stall or crash AA execution for the affected autonomous agent across the network, leading to nodes being unable to finish processing/confirming the triggering unit's AA response (denial of service in a core, unprivileged-reachable execution path: any user can post a trigger to attacker-deployed AA logic). Depending on how the surrounding trigger-processing code handles an uncaught exception versus a graceful `setFatalError`, this can manifest as stuck/failed AA response generation, effectively freezing funds sent to that AA and/or causing nodes to diverge on whether the triggering unit's AA response was produced.

### Likelihood Explanation
The attacker only needs the ability to post ordinary triggers/data to an AA of their own design (fully attacker-controlled AA code) — no special privilege, hub, or peer position is required. Building the deep structure costs one small transaction per nesting level and is entirely feasible; only the final `json_stringify` call is needed to trigger the fault. This matches the "AA trigger sender / AA author" unprivileged actor category explicitly in scope.

### Recommendation
Add the same `isTooBigObj()` (or equivalent depth/size check) guard to the `json_stringify` case in `formula/evaluation.js` before calling `string_utils.getJsonSourceString()`, mirroring the checks already performed in the `json_parse` and `chash160` branches. Additionally, consider bounding the maximum nesting depth of persisted AA state variables at write time (not just at literal-construction time), so that objects cannot be grown incrementally across multiple triggers beyond the same 100-level ceiling enforced elsewhere.

### Proof of Concept
Conceptual PoC (illustrative oscript sequence against a custom AA):
```
// AA definition (simplified)
{
  messages: [{
    app: 'state',
    state: `{
      var['x'] = {a: var['x']};
      response['ok'] = 1;
    }`
  }]
}
```
1. Deploy the AA above.
2. Send ~5,000–10,000 cheap trigger units to the AA; each trigger evaluates a shallow formula (`{a: var['x']}`) but nests the persisted state object `var['x']` one level deeper per call — well under the per-formula 100-evaluate-depth cap each time.
3. Send a final trigger whose formula calls `json_stringify(var['x'])`.
4. On every node computing the AA response, `formula/evaluation.js`'s `json_stringify` handler passes the now deeply-nested object straight to `string_utils.getJsonSourceString()` without any `isTooBigObj` check, and the internal recursive `stringify()` overflows the call stack (`RangeError: Maximum call stack size exceeded`), analogous to the Axios `{}`-metatoken bypass of `maxDepth`.

Note: I was not able to fully verify, from the indexed code alone, whether some other layer (e.g., state-var storage size/complexity accounting in `aa_composer.js`) independently caps the depth of persisted state variables across multiple triggers; if such a check exists elsewhere, it would need to be confirmed to fully rule out or rule in this specific exploitation path. I recommend a Devin session with full repository access to trace `aa_composer.js`'s state-var write path end-to-end to confirm this gap conclusively.

**File:** string_utils.js (L220-257)
```javascript
function getJsonSourceString(obj, bAllowEmpty) {
	let cache = new WeakMap();  // object to stringified result
	function stringify(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				return toWellFormedJsonStringify(variable);
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
			case "boolean":
				return variable.toString();
			case "object":
				// return cached result if already processed
				if (cache.has(variable))
					return cache.get(variable);
				let result;
				if (Array.isArray(variable)){
					if (variable.length === 0 && !bAllowEmpty)
						throw Error("empty array in "+JSON.stringify(obj));
					result = '[' + variable.map(stringify).join(',') + ']';
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0 && !bAllowEmpty)
						throw Error("empty object in "+JSON.stringify(obj));
					result = '{' + keys.map(function(key){ return toWellFormedJsonStringify(key)+':'+stringify(variable[key]) }).join(',') + '}';
				}
				cache.set(variable, result);  // memoize for future references
				return result;
			default:
				throw Error("getJsonSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}
	}

	return stringify(obj);
}
```
