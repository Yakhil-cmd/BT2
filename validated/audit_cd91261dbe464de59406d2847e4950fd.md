## Title
Missing Balance-Overflow Check in `updateFinalAABalances` — (File: `aa_composer.js`)

## Summary
`aa_composer.js` enforces a `MAX_BALANCE` overflow guard only when the *initial* AA balance is updated with the trigger's incoming outputs, but the analogous guard is missing when the *final* AA balance is updated after the AA sends/receives payments to itself during response processing. This is the same class of bug as the reported GPToke issue: one code path (`stake`/`updateInitialAABalances`) enforces the invariant while a second, reachable path that mutates the same aggregate (`extend`/`updateFinalAABalances`) does not.

## Finding Description
In `aa_composer.js`, `handleTrigger` defines two functions that mutate `aa_balances`:

- `updateInitialAABalances` (lines 475-541) explicitly tracks overflow: for every asset whose balance is increased by the trigger's outputs, it checks `objValidationState.assocBalances[address][row.asset] > MAX_BALANCE` and sets `bOverflow`, ultimately returning `"balance overflow"` to `cb`, which causes the trigger to bounce. [1](#0-0) [2](#0-1) 

- `updateFinalAABalances` (lines 543-587) is called after the AA composes and validates its response unit, applying `assocDeltas` (computed from consumed outputs and any payment messages the AA sends to itself) directly to `objValidationState.assocBalances[address][asset]` and to the DB `aa_balances.balance` column — with **no** `MAX_BALANCE` (or any) bound check at all. [3](#0-2) 

`MAX_BALANCE` is deliberately defined to stay safely under the 64-bit signed integer range used by the `balance BIGINT` column: [4](#0-3) 

An AA can receive payments addressed to itself in the same response unit it composes (e.g., self-payment loops, asset issuance to self, "compounding" patterns common in AA templates such as market-maker/fundraising AAs). Each such execution goes through `updateFinalAABalances`, which adds unchecked deltas to the stored balance. Because there is no cap enforcement here (unlike in `updateInitialAABalances`), repeated invocations (over the AA's lifetime, or crafted single triggers that produce many self-directed outputs, bounded by `MAX_MESSAGES_PER_UNIT`) can push `aa_balances.balance` beyond `MAX_BALANCE`, and ultimately beyond the true 64-bit signed range that the underlying SQL engines (sqlite vs MySQL) can represent consistently.

## Impact Explanation
`aa_balances.balance` is a `BIGINT` used both to gate all future AA spending (via `balance[...]` reads in oscript formulas) and reconciled against `outputs` by the periodic `checkBalances()` consistency check. [5](#0-4) 
If the value silently overflows/wraps differently between database backends (sqlite's `INTEGER` arithmetic vs MySQL's `BIGINT` saturation/wraparound behavior), full nodes running different DB engines can compute different `balance` values for the same AA/asset, causing them to diverge on which future AA triggers succeed or bounce — a concrete network disagreement on AA validity/response outcome. It can also allow an AA's stored balance to end up larger (or smaller, if it wraps negative) than its real backing `outputs`, letting the AA later spend funds it does not actually hold (fund loss for other participants) or become permanently unable to spend a corrupted balance (fund freezing).

## Likelihood Explanation
Any AA author can design a template where the AA pays itself (self-referential payment output, or a newly issued asset credited to `this_address`) as part of normal, unprivileged AA logic — no special access or malicious node/peer is required. Because `handleTrigger` is invoked for every posted unit that triggers an AA, and self-payment/compounding patterns already exist in shipped sample AAs (e.g., market-maker templates), the overflow path is reachable purely from posting units/triggers, though it requires many repeated large self-transfers to approach `MAX_BALANCE` in practice, keeping likelihood moderate rather than trivial.

## Recommendation
Add the same overflow check used in `updateInitialAABalances` to `updateFinalAABalances`: after computing `objValidationState.assocBalances[address][asset] += assocDeltas[asset]`, verify the result does not exceed `MAX_BALANCE`, and if it does, bounce the response (consistent with how `updateInitialAABalances` bounces via `"balance overflow"`) rather than committing the update unconditionally to the DB.

## Proof of Concept
1. Deploy an AA whose response includes a `payment` message with an output back to `this_address` (self-payment), executed repeatedly (e.g., triggered many times, or an AA that issues a large asset amount to itself in `issueAsset`-style flows as seen in `aa_composer.js:1175-1213`).
2. Each execution passes through `handleTrigger` → `sendUnit` → `updateFinalAABalances(arrConsumedOutputs, objUnit, cb)`, which adds `assocDeltas[asset]` to `aa_balances.balance` without any bound check. [6](#0-5) 
3. Repeating this enough times drives `balance` past `MAX_BALANCE` (and eventually the true 64-bit signed limit), a state `updateInitialAABalances` would have prevented for trigger-output-driven increases but that `updateFinalAABalances` allows unchecked for self-payment-driven increases, leading to divergent/incorrect balance accounting across nodes.

			// this might happen if there is another pending invocation of our AA that created the outputs we are spending now
			if (!objValidationState.assocBalances[address][output.asset])

			if (message.app !== 'payment')

				if (output.address !== address)
