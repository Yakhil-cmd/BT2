### Title
Cross-organization CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound `status` webhook only against the GitHub organization named in the payload (`repository.owner.login`, falling back to `organization.login`), by fetching that organization's own `Shipit.github(organization: ...)` app/secret. [1](#0-0) [2](#0-1)  Once the signature check passes, the dispatched `Handlers::StatusHandler#process` never re-checks that field: it looks up commits purely by `sha` across the entire `Commit` table, with no scoping to the repository/organization whose signature was actually verified. [3](#0-2) 

### Finding Description
The binding that should hold is: `organization whose webhook signature was verified == organization/repository whose data is mutated`. In `StatusHandler`, this binding is broken:

- `verify_signature` computes `repository_owner` from the payload and asks `Shipit.github(organization: repository_owner)` for that specific org's app to validate `X-Hub-Signature`. [1](#0-0) 
- The `status` event is routed to `Shipit::Webhooks::Handlers::StatusHandler`. [4](#0-3) 
- Unlike other handlers (e.g. `PushHandler`, which scopes via `Repository.from_github_repo_name(repository_name)`), `StatusHandler#process` does not use `stacks`/`repository_name` at all. It runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global lookup across every stack/repository/organization tracked by this Shipit instance. [5](#0-4) [6](#0-5) 
- `create_status_from_github!` creates a `Status` record directly from the attacker-supplied `state`/`context`/etc., with no cross-check that the commit belongs to the organization that signed the request. [7](#0-6) 

Any commit sha is a 40-character hex value that is not secret — it appears in commit ranges, PR pages, deploy history pages, permalinks, etc. across any public or semi-public Shipit-tracked repo. Once an attacker has a sha for a commit belonging to a stack/organization they do not own, they can forge a `status` webhook signed with the secret of an organization they *do* legitimately control (their own GitHub org/App configured on the same shared Shipit instance), and inject an arbitrary `Status` (e.g. `state: "success"`, `context` matching a required/blocking check) onto that foreign commit.

### Impact Explanation
Commit "deployability" in Shipit is derived purely from stored `Status` rows: `deployable?` returns true when `success? && !blocked?` (or `ignore_ci?`), and `blocked?` inspects `blocking?` statuses on prior undeployed commits. [8](#0-7)  By forging a fake `success` status for a required/blocking CI context on a victim commit, an attacker (who controls only their own, unrelated org/App credentials, not the victim's) can:
- Flip a victim commit that never passed real CI into `deployable?`, allowing/queueing an unauthorized deploy of untested or malicious code.
- `Status#after_create` also calls `schedule_continuous_delivery`, so on stacks with `continuous_deployment: true` this can directly trigger an automatic, unauthorized deploy of the victim stack. [9](#0-8) [10](#0-9) 
- It also fires `Hook.emit(:commit_status/:deployable_status, ...)` outward, propagating the forged signal to external systems that trust Shipit. [11](#0-10) 

This matches the "unauthorized deploy" high/critical-tier impact: the write (`Status` creation on an arbitrary commit/stack) crosses the exact boundary that was supposed to be enforced by webhook signature verification (organization identity → data scope).

### Likelihood Explanation
The prerequisite is legitimate, low-privilege access to any single organization/App onboarded to the shared Shipit instance (i.e., being one tenant among many) — not privileged access to Shipit itself, not the victim's secret, and not a Shipit session or API token. Commit shas of other tracked stacks are routinely observable (public repos, PR links, deploy pages). The only "difficulty" is guessing/observing a target sha, which is not a secret value. Given `StatusHandler` performs zero repository-scoping (in contrast to every other handler that keys off `repository_name`), this is a straightforward, deterministic exploitation path once a target sha is known.

### Recommendation
Scope `StatusHandler#process` to the repository/organization that was actually authenticated, mirroring `Handler#stacks`/`repository_name`: only update commits whose `stack.repository` matches `payload.dig('repository','full_name')` (and, transitively, the org used in `verify_signature`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the global `Commit.where(sha: ...)`. More generally, every webhook handler should scope writes to the `Repository`/`Stack` derived from the same payload fields used for signature verification, so no handler can act on data for repositories/organizations other than the one whose signature was validated.

### Proof of Concept
1. Attacker legitimately controls (has installed) their own GitHub organization/App on the shared Shipit instance — say `attacker-org` — and thus knows a valid webhook secret for `attacker-org` (self-configured, not stolen from the victim).
2. Attacker learns the commit sha `V_SHA` of a commit belonging to `victim-org/victim-repo`, a stack tracked by the same Shipit instance (visible via Shipit's public commit/deploy pages, PRs, etc.).
3. Attacker crafts a GitHub `status` webhook payload:
```json
{
  "sha": "V_SHA",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
4. Attacker signs the raw body with `attacker-org`'s own webhook secret and sends it with header `X-Github-Event: status` to `POST /webhooks`.
5. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` (matching `repository.owner.login`), verifies successfully since the attacker used their own valid secret. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: "V_SHA")` — finds the victim's commit (unrelated to `attacker-org`) and creates a forged `success` `Status` on it. [3](#0-2) [7](#0-6) 
7. The victim commit becomes `deployable?` (or, if `continuous_deployment` is enabled on the victim stack, is auto-deployed), despite the attacker never having any access to `victim-org`.

**Note on uncertainty:** I could not fully confirm from the indexed code whether this Shipit deployment model is typically configured with multiple independent GitHub organizations/Apps sharing one Shipit instance (multi-tenant) versus a single-organization deployment (in which case the "authenticated org ≠ written repo" distinction would be moot, since there'd be only one org). The `Shipit.github(organization:)` lookup and `GithubOrganizationUnknown` handling in `WebhooksController` strongly suggest multi-organization support is a supported configuration, but the exact multi-tenancy semantics of `lib/shipit.rb`'s `github_apps` configuration were not fully retrievable within the indexed context. If the target deployment is confirmed single-organization only, this specific cross-org angle would not apply, though the missing repository-scoping in `StatusHandler` (compared to other handlers) remains a structural inconsistency worth fixing regardless.
