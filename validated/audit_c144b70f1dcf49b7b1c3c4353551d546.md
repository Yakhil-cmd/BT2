### Title
System-vote weighting uses instantaneous balance instead of a time-held balance, allowing flash-funded governance vote manipulation - (File: main_chain.js)

### Summary
The `countVotes` function in `main_chain.js` tallies votes for consensus-critical system parameters (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) by summing the *current* stable balance of each voting address at the moment the counting MCI stabilizes, exactly like the reported `compute_normal_bbro_reward` bug where a reward/weight is computed from a point-in-time balance rather than a balance that was actually held over the relevant period.

### Finding Description
`countVotes` first collects every address that has ever cast a `system_vote` for a subject [1](#0-0) , then computes each address's balance using only the current unspent, stable, good outputs at the time of counting [2](#0-1) . This balance snapshot is stored in a temporary `voter_balances` table and is later joined against `op_votes` / `numerical_votes` to compute `SUM(balance)` per candidate/value [3](#0-2) [4](#0-3) .

Crucially, the vote *record* (`system_votes`/`op_votes`/`numerical_votes` row with its `timestamp`) can be arbitrarily old — the only requirement is `timestamp >= since_timestamp`, a window that can stretch back a year or more [5](#0-4) . There is no requirement that the balance used for weighting was actually held by the address at the time the vote was cast, nor any check that the balance was held continuously since then. An address can therefore:
1. Cast a `system_vote` once, at any point in the past (even with a dust balance).
2. Wait until the vote-count MCI is about to stabilize (vote counting fires deterministically off-chain/via message triggers such as `applyEmergencyOpListChange` or the periodic yearly window logic).
3. Transfer a large sum of bytes into that voting address just before/at the stabilization point.
4. As soon as that MCI is marked stable and `countVotes` runs, the full transferred balance counts toward that address's already-registered vote.
5. Immediately move the funds back out afterward.

This is the same "flash stake" class of bug as the bBRO exploit: the weight calculation depends on a balance value read at a single instant (`last_distribution_block`-style snapshot) rather than integrating balance held over the voting period, letting a briefly-held large balance masquerade as a long-term stake.

### Impact Explanation
`op_list` votes directly determine the list of witnesses/order providers used for majority-witness-based stability and DAG ordering [6](#0-5) ; `threshold_size`, `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` are consensus-relevant network parameters that affect fee validation and TPS accounting used throughout unit validation [7](#0-6) . Because all full nodes independently execute `countVotes` deterministically over the same stable DAG state, this does not create node disagreement, but it does let an economically well-resourced but low-commitment attacker (or someone who can borrow/move large sums briefly, e.g. via exchange-custodied funds) disproportionately swing governance of the witness list or fee/TPS parameters without genuinely holding stake, undermining the "balance-weighted, held-over-time" security assumption behind the voting mechanism. A captured or manipulated `op_list`/parameter set can degrade network liveness/finality guarantees and enables follow-on attacks (e.g., pushing a witness set that colludes to stall stabilization or manipulate TPS fee economics).

### Likelihood Explanation
The attack requires only: (a) a previously cast (even trivial) vote from a controlled address, and (b) the ability to move a large balance into that address for a brief window around a predictable/triggerable vote-count event (`applyEmergencyOpListChange` shows count-triggering is even externally invocable under specific conditions) [8](#0-7) . No special privileges are needed — any unit poster can register the initial vote and later fund the address, making this reachable by an ordinary, unprivileged actor.

### Recommendation
Change vote weighting from an instantaneous balance snapshot to a time-weighted (or minimum-holding-period) balance — e.g., require the balance to have existed continuously since the vote was cast (or since some minimum lock time before the counting MCI), analogous to how the bBRO fix recommends avoiding reward calculations based on a naive time-delta multiplied by an end-of-period balance. Concretely, disallow counting balance increases that occurred within a short window (e.g., last N blocks/MCIs) before the counting MCI, or require votes to be re-affirmed/re-signed after any balance increase to prevent "flash-fund" vote injection.

### Proof of Concept
1. Address `V` sends a `system_vote` message for `op_list` (or a numerical subject) with a negligible balance, establishing a `system_votes`/`op_votes` row with an old `timestamp` that will satisfy `timestamp >= since_timestamp` at the next count [5](#0-4) .
2. Attacker waits until a vote-counting MCI is about to become stable (predictable from network timing, or forced via the emergency op-list-change path) [8](#0-7) .
3. Attacker transfers a large amount of bytes into `V` right before that MCI stabilizes.
4. When `countVotes` runs, the query at [2](#0-1)  picks up the newly received, now-stable, unspent balance for `V`, and it is summed into the vote tally for whatever `op_list`/parameter value `V` voted for [3](#0-2) .
5. Attacker moves the funds out of `V` immediately after, having paid no cost beyond transaction fees and a brief transfer, while having swung the vote tally as if the stake had been held for the full window.

async function applyEmergencyOpListChange(conn, emergency_count_command_timestamp, cb) {
	// last stable unit
	const [{ timestamp, main_chain_index }] = await conn.query("SELECT timestamp, main_chain_index FROM units WHERE is_stable=1 AND is_on_main_chain=1 ORDER BY main_chain_index DESC LIMIT 1");
	if (emergency_count_command_timestamp < timestamp + constants.EMERGENCY_OP_LIST_CHANGE_TIMEOUT) {
		console.log(`too early to apply emergency OP list change yet`);
		return cb();
	}
	console.log(`applying emergency vote count after being stuck at mci ${main_chain_index}`);
	await countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp);
	cb();
}
