### Title
Unvalidated swap routes can execute attacker-controlled code and steal unrelated wallet assets - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategies forward an opaque `swap` payload to the configured router, which can invoke arbitrary route-selected contracts beneath the caller’s authorization. A malicious route can therefore append a token transfer from the caller to the transaction’s authorization tree and steal unrelated wallet assets, analogous to executing an attacker-supplied resource rather than merely accepting bad swap pricing. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_tokens` snapshots input and output balances, authorizes one exact controller-to-router token transfer, and then invokes `router.execute_strategy` with caller-controlled `swap` bytes. [1](#0-0)  The granted controller authorization only covers the controller’s own transfer and does not itself constrain which contracts the router invokes while interpreting the opaque route payload. [3](#0-2) 

This affects every strategy using the shared router boundary, including `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. [4](#0-3) [5](#0-4) [6](#0-5)  Soroban simulation records calls requiring caller authentication as children of the strategy’s root authorization; if the user signs the returned tree without decoding every child, route-selected code can execute a wallet-token transfer that is economically unrelated to the swap. [7](#0-6) 

### Impact Explanation
A malicious route can steal unrelated tokens held by the strategy caller, not merely provide poor execution for the routed amount. [2](#0-1)  The repository’s adversarial test demonstrates a route-selected contract transferring the caller’s entire unlisted wallet-token balance to an attacker while the strategy still receives fair output and succeeds. [8](#0-7)  This is theft of user funds through execution of attacker-selected on-chain code.

### Likelihood Explanation
Exploitation requires the victim to submit or sign a malicious route and its simulated authorization tree, but ordinary users commonly rely on opaque route generation and may not decode nested Soroban authorizations. The host rejects an unlisted child transfer under an honest root-only tree, so the failure is not unauthorized host execution; it is the protocol’s acceptance of unconstrained route code that causes simulation to expose the poisoned child authorization. [9](#0-8)  A direct victim signature remains required, so this is more conditional than a fully permissionless pool drain, but the reachable consequence is complete loss of arbitrary signed wallet assets.

### Recommendation
Do not pass arbitrary executable route payloads beneath the caller’s strategy authorization without an enforced venue boundary. Add a protocol-controlled allowlist or otherwise constrain every route hop to known safe venue contracts, and reject payloads that can introduce unrelated token calls under the caller’s authorization tree. At minimum, transaction-building clients should display and enforce an exact expected authorization tree for each strategy, but contract-level venue restrictions are the robust mitigation because controller-side output measurement cannot bound losses outside the routed assets. [10](#0-9) 

### Proof of Concept
1. Alice owns a funded lending account and an unrelated wallet token.
2. An attacker deploys a contract whose route hop calls `token.transfer(alice, attacker, wallet_balance)`.
3. Alice submits `swap_collateral(account_id, USDC, amount, ETH, malicious_route)`, or another router-backed strategy.
4. The controller authorizes the exact controller input transfer and invokes `router.execute_strategy`. [11](#0-10) 
5. The router invokes the attacker-selected hop contract, whose call requests Alice’s authorization for the unrelated token transfer. [12](#0-11) [13](#0-12) 
6. Simulation records that transfer as a child of Alice’s `swap_collateral` authorization; signing the returned tree executes the theft while preserving fair swap output. [14](#0-13) 
7. The adversarial test confirms Alice’s unrelated wallet balance falls to zero and the attacker receives `WALLET_BALANCE`. [15](#0-14)

            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
