### Title
Attestor list revocation on a `spender_attested` asset can permanently freeze a holder's already-received funds - (File: validation.js)

### Summary
For assets defined with `spender_attested: true`, the asset definer alone controls the whitelist of addresses allowed to spend the asset via `asset_attestors` messages. Every subsequent payment involving that asset re-checks, at the moment of spending, whether the current author (the address that already owns the coins) is present in the *current* attestor list. Because the check is evaluated against the latest list rather than the list in force when the coins were received, a definer can post an `asset_attestors` update after a user has already received (and stably owns) units of the asset, permanently locking that user out of spending them — with no bounce, refund, or exit path, mirroring the "config changed after funds already committed" pattern from the reported IMA bug.

### Finding Description
When validating a payment of a `spender_attested` asset, `validatePayment()` loads the asset together with the *current* set of attested authors via `storage.loadAssetWithListOfAttestedAuthors()` and immediately rejects the unit if none of the authors (i.e., the address trying to spend) is attested: [1](#0-0) 

For divisible/private fixed-denomination inputs the same "spender must currently be attested" re-check is repeated directly against `objAsset.arrAttestedAddresses`: [2](#0-1) 

The attestor list itself is fully mutable after the asset is defined: `asset_attestors` messages let the definer push a brand-new list at any later main chain index, and validation only requires that the message be authored by `objAsset.definer_address`: [3](#0-2) 

`storage.readAsset()` always resolves to the *latest stable* attestor list unit for the asset when it fills `objAsset.arrAttestorAddresses`, i.e. there is no snapshot/versioning tied to when a particular holder received their coins: [4](#0-3) 

So the sequence is:
1. Definer creates asset with `spender_attested: true` and an initial attestor list (address A included).
2. Holder receives a payment output of the asset while A is on the list — the receive-time check only validates that *output* addresses are attested (via `filterAttestedAddresses`), which A satisfies: [5](#0-4) 
3. Later, the definer posts a new `asset_attestors` message removing A from the list.
4. Holder A now owns a stable, previously-valid output but can never again spend it: any future payment authored by A for this asset will be rejected with `"none of the authors is attested"` (or `"owner address is not attested"` for private fixed-denomination inputs), because the check is always evaluated against the *current* list, not the list at receipt time.

This exactly parallels the audited bug: an action that succeeds and irrevocably commits value based on state at time T (accepting/holding the asset while attested) can later be invalidated by an independently-mutable configuration change controlled by a privileged party (the schain owner disabling `automaticDeploy`; here, the asset definer editing the attestor list), permanently trapping the unprivileged holder's already-owned funds with no compensating refund/exit mechanism.

### Impact Explanation
An asset holder's legitimately received, stable balance of a `spender_attested` asset can become permanently unspendable purely due to a later, unrelated configuration change by the asset definer, with no on-protocol remedy (no bounce, no grace period, no way to move the funds even to a definer-controlled sink in the general divisible/public case). This is a direct "asset transfer condition" fund-freezing issue reachable by a normal asset issuer action against ordinary unprivileged holders, matching the accepted "AA fund loss or freezing" / node-disagreement-adjacent impact class from the rules (loss of usable funds for the holder).

### Likelihood Explanation
Any asset issuer choosing `spender_attested: true` can trigger this by simply publishing an updated `asset_attestors` list omitting a previously-attested address — no attacker collusion, no race condition, and no special privilege beyond being the asset's own definer (a role the protocol explicitly allows to control the attestor list at will, at any main-chain index, with no timelock). Because there is no notice period or grandfathering of previously-attested holders, this can happen at any time, intentionally or accidentally, making the likelihood of hitting this condition moderate-to-high for any asset using this feature.

### Recommendation
- Snapshot the "attested-at-receipt" status for each output, or otherwise allow holders whose address was attested when the funds were received a bounded grace period (e.g., analogous to the report's suggested 24h timelock before an `automaticDeploy`-like flag change takes effect) to move/exit their funds after removal from the attestor list.
- Alternatively, only enforce the "current spender attested" check for freshly issued/received outputs, and consider adding an explicit unattested-holder exit path (e.g., allow transfer back to the definer's address regardless of current attestation) so funds are never fully stranded.
- Document/require that `asset_attestors` updates cannot silently strand existing balances, and add validation-time or governance-level warnings when a removal would immediately freeze outstanding stable outputs.

### Proof of Concept
1. Definer creates an asset with `is_private: false`, `is_transferrable: true`, `spender_attested: true`, `attestors: [A]` (`asset` message; validated by `validateAssetDefinition`, `validateAttestorListUpdate` machinery — see [6](#0-5) ).
2. Definer sends a payment output of this asset to address `A`. Receive-time validation only checks that the *output* address `A` is attested via `filterAttestedAddresses` ( [5](#0-4) ), which passes; the unit becomes stable — `A` now legitimately and irrevocably owns the coins.
3. Definer posts a new `asset_attestors` message for the same asset with a list that no longer contains `A` (allowed per [3](#0-2) ; `storage.readAsset` will resolve to this newest list, per [4](#0-3) ).
4. `A` attempts to spend the previously-received output (e.g., send it back to the definer or to a third party). `validatePayment` recomputes `arrAttestedAddresses` for the current author set, finds it empty (A no longer attested), and rejects with `"none of the authors is attested"` ( [1](#0-0) ) — for private/fixed-denomination transfers the analogous rejection is `"owner address is not attested"` ( [2](#0-1) ).
5. `A`'s balance of this asset is now permanently frozen: no valid unit authored by `A` moving these coins can ever validate again, with no bounce or refund mechanism recovering the value.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
