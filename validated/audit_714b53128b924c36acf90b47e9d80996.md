## Title
Webhook signature is verified per-organization, but `StatusHandler` writes commit statuses to *any* repository — cross-repository status forgery enabling unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The reported bug class is "a value the system trusts (future-epoch balance) is checked against the wrong scope (only next epoch) instead of the scope that's actually mutated." The equivalent binding in Shipit is: **the organization whose webhook secret authenticated the request** vs. **the repository/commit that the handler actually mutates**. `WebhooksController` verifies the HMAC signature using the organization named in the payload's `repository.owner.login`, but several handlers — most concretely `StatusHandler` — never re-check that the object being written (a `Commit`) actually belongs to that authenticated organization/repository. `StatusHandler` looks the commit up **globally by SHA** across the whole Shipit instance.

### Finding Description
`WebhooksController#verify_signature` derives the org used to select the webhook secret purely from the request body itself: [1](#0-0) [2](#0-1) 

Once the signature check passes (using the secret configured for that *organization*, per `Shipit.github(organization: repository_owner)`), the raw JSON `params` are handed unmodified to every registered handler: [3](#0-2) 

Most handlers re-derive the target repository from `payload.dig('repository', 'full_name')` via the shared base class: [4](#0-3) 

But `StatusHandler` does not use `repository_name`/`stacks` scoping at all — it resolves the target purely from the attacker-supplied commit `sha`, searched across the **entire** `Commit` table (i.e. every repository/stack tracked by this Shipit instance): [5](#0-4) 

The binding that should hold — `organization authenticated by verify_signature == organization owning the repository whose Commit gets a status written` — is never enforced. The signature only proves "this body was HMAC-signed with organization X's webhook secret" (per `GitHubApp#verify_webhook_signature`): [6](#0-5) 

In a multi-tenant Shipit deployment (explicitly a supported configuration — `config/secrets.development.shopify.yml` shows multiple orgs each with their own `webhook_secret`): [7](#0-6) 

any account that legitimately owns a repository/App-installation in **one** configured organization (org A) can send a `status` webhook whose signature is valid (signed with org A's secret) but whose payload's `sha` names a commit that belongs to a completely different tracked repository (org B). `StatusHandler` will happily create a `Status` on org B's commit: [5](#0-4) 

### Impact Explanation
Commit CI statuses gate Shipit's deploy pipeline (`ci.require` checks required status contexts before allowing/auto-triggering a deploy, per the documented `ci.require` config). By forging a `success` status for a required CI context on a victim commit whose SHA the attacker can discover (commit SHAs are public via the GitHub API), an attacker in org A can satisfy org B's deploy gating checks and cause an **unauthorized deploy** of org B's stack — without ever holding an `ApiClient` token, session, or write access to org B's repository. This matches the in-scope Critical impact "an unauthorized deploy."

### Likelihood Explanation
Exploitability requires only: (1) legitimate access to a GitHub App/webhook configured for *any* organization tracked by the same multi-tenant Shipit instance, and (2) knowledge of a target commit SHA in another org's tracked repository (trivially obtainable via the public GitHub API). No secrets, sessions, or repository write access to the victim repo are needed — only the ability to author a valid webhook body signed with one's *own* org's secret. This is a realistic scenario for any shared/multi-tenant Shipit deployment, which the codebase explicitly documents as a supported configuration.

### Recommendation
In `Handler#process` (or a shared before-filter in `WebhooksController`), enforce that the organization/repository that authenticated the signature (`repository_owner` used in `verify_signature`) matches the repository actually mutated by the handler. Concretely, `StatusHandler` should scope its `Commit` lookup through `stacks`/`Repository.from_github_repo_name(repository_name)` (like `PushHandler` already does) rather than a global `Commit.where(sha:)`, and any handler resolving objects by cross-cutting identifiers (SHA, PR number, etc.) must additionally filter by the repository named in the authenticated payload.

### Proof of Concept
1. Configure two orgs in Shipit, `org-a` and `org-b`, each with its own `webhook_secret`, each with a stack/repository tracked.
2. Discover a commit SHA `S` belonging to `org-b/victim-repo` that Shipit is tracking (e.g., via GitHub's public commits API), and note a required CI context configured in `org-b/victim-repo`'s `shipit.yml` `ci.require`.
3. As an attacker who legitimately controls `org-a`'s webhook secret (e.g. as an admin of their own GitHub App/org configured within the same shared Shipit instance), craft a `status` event payload:
```json
{
  "sha": "S",
  "state": "success",
  "context": "<required-ci-context-of-org-b>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/attacker-repo" }
}
```
4. Sign it with `org-a`'s `webhook_secret` and POST it to `/github/webhooks` with `X-Github-Event: status`. `verify_signature` succeeds because it resolves `Shipit.github(organization: "org-a")` and validates against `org-a`'s secret.
5. `StatusHandler#process` executes `Commit.where(sha: "S").each { |commit| commit.create_status_from_github!(params) }` — since `S` belongs to `org-b/victim-repo`, that commit now has a forged `success` status for a status Shipit's continuous-delivery / deploy gating logic depends on.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
