### Title
Cross-organization commit-status forgery via global SHA lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` binds webhook authentication to the *organization* derived from the untrusted payload (`repository.owner.login`), but `Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit purely by a global `sha` lookup, with no re-check that the commit's owning repository/organization matches the organization whose secret validated the request. This breaks the equality: `organization that authenticated == repository that is written`.

### Finding Description
In a multi-organization Shipit deployment (explicitly documented in `docs/setup.md:181-209`, "Using Multiple Github Applications"), each GitHub organization has its own `webhook_secret`. The webhook signature is checked against the secret for the organization named in the payload: [1](#0-0) [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
  ...
end
```
where `repository_owner` is `params.dig('repository', 'owner', 'login')` [2](#0-1) .

Signature validation only proves the request came from *some* organization's real GitHub App installation (the one named in the payload's own `repository.owner.login`) — it says nothing about which commit/stack the event is allowed to affect.

The `status` event handler, however, ignores `repository.full_name` entirely and updates **any** commit in the whole Shipit database matching the SHA, regardless of which stack/repository/organization owns it: [3](#0-2) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Note the base `Handler` class *does* provide a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)` [4](#0-3) , and `PushHandler`/`CheckSuiteHandler` use it (`stacks.not_archived.where(branch:)` / `stacks.where(branch:)`), but `StatusHandler` does not use `stacks` at all — it queries `Commit` globally by `sha`.

`create_status_from_github!` then persists attacker-supplied `state`, `description`, `target_url`, and `context` directly onto that commit, which feeds `Commit#status`, `deployable?`, CI-gating for deploys, and merge-queue checks (`MergeRequest::StatusChecker`) [5](#0-4) [6](#0-5) .

**Attack path**: An attacker who owns/administers *their own* GitHub organization (Org A) — a normal, unprivileged capability having nothing to do with Shipit credentials — has the Shipit GitHub App installed there and knows nothing about Shipit's secrets. GitHub's Commit Status API historically allows setting a status for an arbitrary SHA on a repository you can write to, even if that SHA doesn't belong to that repository's history. The attacker sets a commit status on their own Org A repo for a SHA that they know belongs to a victim commit in Org B's stack (SHAs are public and frequently exposed via PR URLs, Shipit UI, etc.). GitHub sends the resulting `status` webhook, correctly HMAC-signed by Org A's real `webhook_secret`. `WebhooksController#verify_signature` legitimately validates it (using Org A's secret, matching the payload's own `repository.owner.login == OrgA`). `StatusHandler` then finds Org B's commit purely by SHA and writes attacker-controlled state/description/target_url onto it — with no verification that the commit belongs to Org A.

### Impact Explanation
This lets an attacker who only controls their own GitHub organization (not any Shipit credential) forge a passing (or failing) CI status on an arbitrary commit belonging to a different organization's stack in the same multi-tenant Shipit instance. Since `deployable?` and merge-queue merge gating depend on commit status state, this can be used to make an otherwise-blocked commit appear "green," enabling an unauthorized deploy or an unauthorized automatic merge via the merge queue — matching the "unauthorized deploy...or merge" Critical impact criterion.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with multiple GitHub organizations sharing one install (a documented, supported configuration), (2) the attacker controlling any one of those organizations (a routine, unprivileged capability — e.g. any of the app's other tenants), and (3) knowledge of a target SHA in a victim stack (SHAs are not secrets and are widely observable). No Shipit session, API token, or webhook secret needs to be obtained by the attacker — GitHub itself produces the valid signature for their own org's traffic. This is realistic wherever the multi-org feature is used.

### Recommendation
In `StatusHandler` (and any other handler bypassing the `stacks` helper), scope commit lookups to the repository named in the payload, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or otherwise verify `payload.dig('repository','full_name')` corresponds to the commit's `stack.repository` before applying the status update. More generally, every handler should authorize on `repository_name`-derived `stacks`, not on a raw, database-wide lookup.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with distinct `webhook_secret`s (per `docs/setup.md`'s multi-org example).
2. Attacker controls `orgA`'s GitHub org and has the Shipit GitHub App installed there.
3. Victim stack lives under `orgB/victim-repo`, with an undeployed commit `abc123...` pending required CI checks.
4. Attacker calls GitHub's Status API on their own `orgA/attacker-repo` targeting sha `abc123...` (the victim's SHA) with `state: success`.
5. GitHub sends a `status` webhook to Shipit's `/webhooks` endpoint, `repository.owner.login = "orgA"`, signed with `orgA`'s real secret.
6. `WebhooksController#verify_signature` validates successfully against `Shipit.github(organization: "orgA")`.
7. `StatusHandler#process` executes `Commit.where(sha: "abc123...")` — matching the victim's commit under `orgB` — and calls `create_status_from_github!`, marking it "success" regardless of real CI state.
8. The victim's commit now reports as deployable/mergeable, potentially triggering an unauthorized deploy or merge-queue merge.
