## Title
Front-runnable AA-defined-AA addresses lead to silently dropped balance initialization and frozen funds - (File: `storage.js`)

### Summary
The AA→AA "definition" message flow assigns a new AA a fully deterministic address `chash160(definition)`, exactly like the `LMPVaultFactory.createVault()` CREATE2 pattern in the source report. Because the resulting address depends only on the definition content, an unprivileged attacker who can predict (or copy) the definition a legitimate factory AA is about to emit can pre-register the identical address first with a throw-away AA of their own. When the legitimate factory's response later re-emits the same `app: 'definition'` message, `storage.insertAADefinitions()` treats it as an "already exists" duplicate and returns early **without ever running the balance back-fill query**, so the newly-born AA's balance table is never initialized even though the factory immediately pays funds into it.

### Finding Description
An AA can programmatically spawn a child AA at address `objectHash.getChash160(definition)` by including an `app: 'definition'` message in its response, as shown in the "AA with generated definition of new AA" test: [1](#0-0) 

The address is computed purely from the definition JSON, and is fixed and completed with `message.payload.address = objectHash.getChash160(message.payload.definition)`: [2](#0-1) 

Validation of the message only checks that `payload.address === getChash160(payload.definition)`; it never checks who defines the address first: [3](#0-2) 

After an AA-defining unit stabilizes, `writer.js` calls `storage.insertAADefinitions()` with `bForAAsOnly = true` for every `app: 'definition'` payload found in the unit: [4](#0-3) 

Inside `insertAADefinitions()`, the address row is inserted with `INSERT IGNORE`. If a row for that address **already exists** (i.e., someone else defined the identical AA earlier) and `bForAAsOnly` is true, the function logs "ignoring repeated definition" and returns immediately — **before** reaching the code that back-fills `aa_balances` for the new address from pre-existing outputs: [5](#0-4) 

Because the address is purely content-derived, any unprivileged party can deploy a trivial one-message AA whose sole `app: 'definition'` message contains the exact same definition JSON that a target factory AA is known (or expected) to emit for a child AA, and trigger it first. If that attacker's throw-away AA fires before the legitimate factory AA's trigger, the child address gets defined by the attacker's unit/mci. When the legitimate factory later emits the identical `definition` message (deterministically, same bytes → same address), `insertAADefinitions()` hits the `bForAAsOnly` early-return branch and skips the `aa_balances` INSERT/REPLACE entirely — even though the factory's very next message in the same response is a `payment` sending funds to that address.

This is the direct analog of the reported `LMPVaultFactory.createVault()` CREATE2 front-running bug: a deterministic, content-addressed creation path lets an unprivileged third party pre-empt the address, and the "real" creator's transaction is not reverted outright but is silently short-circuited, leaving the created entity in an inconsistent state (in ocore's case, an AA with an address and definition but no correctly-initialized balance record for out-of-band or pre-birth outputs).

### Impact Explanation
The pre-empted child AA can end up with an `aa_balances` table that never reflects outputs that should have been credited to it (any non-AA-response outputs sent to that address prior to its "official" birth mci recorded by the factory, or accounting inconsistencies from using the attacker's earlier mci as the baseline). Since AA responses use `aa_balances` to decide how much they can spend, this can cause **AA fund freezing** (funds appear unspendable/unaccounted by the AA) or divergent balance accounting between nodes depending on transaction propagation/inclusion order, which is a node-disagreement-on-validity/stability class issue. This matches the accepted impact categories (AA fund loss/freezing, node disagreement on validity or stability).

### Likelihood Explanation
Any unprivileged user can deploy AAs and send them triggers at will — no special privilege is required (`validateAADefinition`/`aa_composer` triggers are open to anyone). Predicting/copying a factory AA's static child definition is trivial when the factory template does not depend on trigger data (a common and even recommended pattern, as shown directly in the codebase's own test suite). Front-running only requires getting a unit included before the legitimate factory's response unit, which is achievable via standard fee/priority manipulation, making this a realistically reachable Medium-severity issue rather than a purely theoretical one.

### Recommendation
- In `storage.js` `insertAADefinitions()`, do not skip the balance back-fill step purely because a row for the address already exists; instead verify whether the *existing* definer is the same defining AA/trigger chain that was expected, and if a different unit defined it, still perform the balance-catch-up query for the address using the correct combined mci baseline.
- Alternatively, disallow "squatting": when validating the `definition` inline payload (`validation.js`), reject definitions whose `chash160` collides with an address that was defined by a *different* AA/unit lineage than the one now defining it, so the second definer's response bounces cleanly instead of silently succeeding without side effects.
- At minimum, emit a hard validation error (bounce) rather than a silent "ignoring repeated definition" log when `bForAAsOnly` collides with a pre-existing address, so factory AAs and their operators are aware the child was not correctly initialized.

### Proof of Concept
1. Deploy `attacker_aa`, a one-message AA whose response is `{app: 'definition', payload: {definition: CHILD_AA_JSON}}` where `CHILD_AA_JSON` is copied verbatim from a known/public `factory_aa`'s static child template (as in `test/aa_composer.test.js:944-977`).
2. Trigger `attacker_aa` so its response lands and stabilizes first, defining `child_aa_address = chash160(CHILD_AA_JSON)` with `unit = attacker's unit`, `mci = attacker's mci`. No `aa_balances` catch-up is skipped here (attacker is first, `bForAAsOnly` still true but insert succeeds normally).
3. Trigger `factory_aa` as normal; its response also emits the identical `{app:'definition', payload:{definition: CHILD_AA_JSON}}` message followed by a `payment` message sending funds to `child_aa_address`.
4. In `storage.insertAADefinitions()`, the `INSERT IGNORE` for `child_aa_address` returns `affectedRows === 0` (already exists from step 2); since `bForAAsOnly === true`, the function logs "ignoring repeated definition of AA ... in AA unit ..." and calls `cb()` immediately, **never executing** the `aa_balances` INSERT/REPLACE query that would normally credit `child_aa_address` with any pre-existing outputs.
5. `child_aa_address`'s balance bookkeeping is now inconsistent with what the factory intended, demonstrating the fund-freezing/accounting-divergence impact from the front-run.
