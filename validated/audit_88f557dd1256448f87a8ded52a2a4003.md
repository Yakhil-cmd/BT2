This confirms the binding break: `WebhooksController#verify_signature` selects which GitHub App/secret to authenticate against using `repository_owner`, derived from the same unverified JSON body being authenticated [1](#0-0) , and falls back to `organization.login` if `repository` is absent [2](#0-1) . But `Shipit::Webhooks::Handlers::Handler#stacks` looks up the affected `Repository` via a separate field of that same payload, `repository.full_name` [3](#0-2) , and `Repository.from_github_repo_name` splits that string on `/` to get owner and name independently [4](#0-3) . Nothing cross-checks that `repository.owner.login` (used to pick the authenticating secret) matches the owner segment embedded in `repository.full_name` (used to pick the repository actually written to).

### Title
Webhook authentication org selection is decoupled from the repository actually mutated - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App configuration (and therefore the HMAC secret) to validate a webhook against using `repository_owner`, itself read out of the unauthenticated JSON body via `params.dig('repository', 'owner', 'login')` (or `organization.login`) [5](#0-4) . Handlers that subsequently act on the payload (e.g. `PushHandler`, `StatusHandler`) resolve the target `Stack`/`Repository` from a different field of the same body, `repository.full_name` [3](#0-2) , [6](#0-5) . The "authenticating owner" and "written repository owner" are never asserted equal.

### Finding Description
The equality that should hold is:
`organization authenticated by verify_webhook_signature == owner(repository.full_name) acted on by the handler`

Before the fix: an attacker who knows (or controls) the `webhook_secret` for *any* organization configured in this Shipit instance (e.g. their own low-trust org, or an org whose `webhook_secret` is unset — in which case `Hook::DeliverySigner`/`verify_webhook_signature` short-circuits to `true` when `webhook_secret` is blank, see `lib/shipit/github_app.rb:76-83`) can post a crafted body where:
- `repository.owner.login` = `attacker_org` (used only to select the signing secret at `webhooks_controller.rb:25,59-61`)
- `repository.full_name` = `victim_org/victim_repo` (used by every handler to find the real `Repository`/`Stack` to mutate)

Because the HMAC is computed over the raw POST body with the secret chosen from the attacker-controlled `repository.owner.login` field, the signature check in `lib/shipit/github_app.rb:76-83` passes as long as the attacker signs with the secret of the org they nominate — there is no requirement that this org match the owner segment of `repository.full_name` that the handlers subsequently trust.

### Impact Explanation
Handlers keyed off `repository.full_name` (via `Handler#stacks`, `Repository.from_github_repo_name`) can be driven against any existing `Repository`/`Stack` in the instance regardless of which organization's secret validated the request. Concretely: `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` [6](#0-5)  — this forces a Git sync/re-fetch cycle for a target stack the attacker does not own, using attacker-chosen `after` SHA claims, and `StatusHandler#process` writes commit `Status` rows for any `sha` matching an existing `Commit` across the whole instance regardless of which organization's secret authenticated it [7](#0-6) . This constitutes a cross-repository write/state-manipulation crossing the intended per-organization trust boundary of the webhook subsystem, satisfying "cross-repository writes" in the impact rubric.

### Likelihood Explanation
Requires only that the attacker control (or have configured) the `webhook_secret` for *some* organization onboarded to this Shipit instance — no GitHub App private key, no repository write access to the victim repo, and no Shipit session/API token is needed, satisfying the "unprivileged attacker" constraint. Multi-tenant Shipit deployments hosting several organizations are the most exposed.

### Recommendation
After `verify_signature` resolves `repository_owner` and validates the HMAC, re-derive the repository/stack lookup key strictly from the same authenticated organization scope — e.g. assert that the owner segment of `repository.full_name` equals `repository_owner`, or scope `Handler#stacks`/`Repository.from_github_repo_name` lookups by the authenticated organization rather than trusting `full_name` in isolation.

### Proof of Concept
1. Configure two orgs in `Shipit.github`, `attacker-org` (secret `S1`, known to attacker) and `victim-org` (secret `S2`, unknown to attacker), both with existing repositories/stacks.
2. POST to `/github/webhooks` with `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" }
}
```
3. Set `X-Hub-Signature: sha1=<hmac(S1, raw_body)>`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and validates successfully with `S1` [1](#0-0) .
5. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github` on the victim's stacks [3](#0-2) , [6](#0-5) , despite the request never being validated against `victim-org`'s secret.
