## Title
Malicious counterparty can register their address as a bouncing AA to force full rollback of a protocol AA's payout logic (e.g. liquidation/closure/redemption) - (File: aa_composer.js)

### Summary
In ocore's Autonomous Agent (AA) execution engine, whenever an AA response sends a payment to an address that is itself a registered AA, the engine automatically fires a secondary trigger on that recipient AA. If the secondary AA bounces, the **entire primary trigger's state changes and response are unconditionally rolled back**. A user who is due to receive funds (e.g., collateral being returned during a forced liquidation, closure, or refund) can pre-register their own receiving address as an AA definition that always bounces on any incoming trigger, thereby permanently blocking the protocol AA from completing that critical operation - the same class of "recipient callback denial-of-service" as the `onERC721Received` reversion issue in the external report.

### Finding Description
When an AA response includes payment outputs, `sendUnit`/`sendDummyUnit` collect the output addresses and call `handleSecondaryTriggers`, which looks up whether any output address is a registered AA and, if so, recursively invokes `handleTrigger` on it as a secondary trigger: [1](#0-0) 

If any of those secondary AA calls ends up bouncing (returns a non-empty `bounce_message`), the `async.eachSeries` error handler is invoked, and — critically — for a **primary** trigger this causes a full `revert()` of the whole call chain, not just the failing branch: [2](#0-1) 

`revert()` rolls back all state variable updates and cached responses accumulated across the entire trigger chain (including changes made by the protocol AA itself before it tried to pay the malicious counterparty), then converts the whole primary trigger into a bounce: [3](#0-2) 

This mirrors the Revert Lend bug exactly: a protocol contract (there, `V3Vault._cleanupLoan` calling `safeTransferFrom`; here, any lending/vault-style AA sending a payment message back to `trigger.address` or `trigger.initial_address` as part of `liquidate`/`close`/`redeem`-style logic) performs a "push" transfer to a user-controlled recipient. If that recipient is a contract (here: an AA) whose callback (here: its trigger-handling logic) is designed to always fail/bounce, the sender's entire critical state transition (marking debt repaid, deleting the loan, updating collateral) never gets committed — it's rolled back along with the payment. Because AA addresses are cheap to compute/publish and definitions can be pre-registered by any unprivileged user before ever taking on a loan/position, an attacker fully controls whether their own address will always reject incoming triggers, deterministically blocking the protocol's cleanup path.

### Impact Explanation
Any oscript-based protocol relying on the AA-to-AA callback model to force a payout as part of a debt-closure/liquidation/insolvency-resolution routine can be indefinitely blocked from completing that routine by a counterparty who registers their receiving address as a perpetually-bouncing AA. Because the protocol's own state changes (e.g., zeroing out debt, deleting collateral records) are bundled in the same atomic chain and get rolled back together with the failed payout, this leads to the same category of harm as the referenced finding: positions that should be closed/liquidated cannot be, so bad debt or undercollateralized positions persist and accumulate, ultimately threatening protocol insolvency for any lending/vault AA built on ocore.

### Likelihood Explanation
Any user can trivially compute and publish an AA definition whose `messages`/`bounce_fees` logic causes it to always `bounce()` on trigger (e.g., an `init` formula that unconditionally calls `bounce('no')`), and can pre-select that AA's address as the account they use to interact with a lending/vault protocol before ever opening a position. No special privilege or race condition is needed — this is fully within the reach of an ordinary AA author/trigger sender acting as a borrower.

### Recommendation
Protocol AAs built on ocore should not couple mandatory funds-return logic to state cleanup atomically when the recipient could be an AA. Where possible: (1) perform the state cleanup (marking debt/position closed) unconditionally before or independently of the payout message, so a downstream bounce of a secondary AA does not roll back the accounting change, or (2) use a "pull" pattern — record a claimable balance for the counterparty in AA state instead of pushing a payment message directly to an address that might be an adversarial AA, letting the counterparty withdraw separately. At the engine level, documentation/guidance for AA developers should clearly flag that payments to arbitrary addresses can silently become secondary triggers that can revert the entire response chain, per `handleSecondaryTriggers`/`revert` in `aa_composer.js`.

### Proof of Concept
1. Attacker defines and publishes an AA at address `M`:
```
{
  init: "{ bounce('always reject'); }",
  messages: [{ app: 'state', state: "{ }" }]
}
```
2. Attacker uses address `M` as their identity to open a leveraged position/loan on a lending-style protocol AA `V` (i.e., `trigger.address == M`).
3. When `V`'s liquidation/closure logic later needs to run and includes a `payment` message sending remaining collateral back to `trigger.address` (`M`), `sendUnit`/`sendDummyUnit` detects that `M` is a registered AA and calls `handleSecondaryTriggers` on it, per [1](#0-0) .
4. `M`'s `init` immediately calls `bounce()`, causing its `handleTrigger` to invoke `onDone` with a bounce message.
5. Back in `V`'s `handleSecondaryTriggers`, the `async.eachSeries` error handler treats this as a chain failure and, since `V`'s trigger was primary, calls `revert({message: "one of secondary AAs bounced with error: ...})`, per [4](#0-3) .
6. `revert()` rolls back all of `V`'s state changes (e.g., loan deletion, debt zeroing) and converts the whole operation into a bounce, per [3](#0-2) , meaning `V` never actually closes/liquidates the position for `M`.
