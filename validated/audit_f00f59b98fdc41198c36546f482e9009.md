### Title
AA response atomicity: a single asset with an unmet transfer/issue condition, non-transferable status, or private/fixed-denomination mismatch causes the entire multi-message AA response to bounce, discarding all other valid payments and state changes - ([File: aa_composer.js])

### Summary
When an Autonomous Agent (AA) trigger produces a response with multiple `payment` messages (e.g., paying bytes to one address and an asset to another, or several assets to several recipients in the same response), the whole unit is composed and validated as a single atomic object. If any single asset-payment message in that response cannot be satisfied — because the asset is private, is not transferable to the target address, fails its `transfer_condition`/`issue_condition`, or fails the `spender_attested` check — the composer aborts the *entire* response via `bounce()`, not just the failing message. This mirrors the reported pattern where a single "bad" asset in an all-or-nothing sweep/transfer loop causes an otherwise legitimate operation to permanently fail.

### Finding Description
In `sendUnit()` inside `handleTrigger`, all payment messages for a response are processed with `async.eachSeries`: [1](#0-0) 

If `storage.loadAssetWithListOfAttestedAuthors` finds the asset `is_private`, the series callback immediately errors out with `"sending private asset from AA"`, and the series-completion handler calls `bounce(err)` for the *whole* unit: [2](#0-1) 

Even when all per-message pre-checks pass, the fully composed `objUnit` (which may bundle several unrelated payment messages plus a state-update message) is validated as one indivisible unit via `validateAndSaveUnit`, and any failure there also triggers a full `bounce`: [3](#0-2) 

The actual asset-level restrictions that can fail at this stage — `is_transferrable`, `transfer_condition`/`issue_condition`, and `spender_attested` — are enforced deep inside unit validation, independently per asset, but a failure on any one of them fails the entire unit: [4](#0-3) 

`bounce()` then discards `objStateUpdate`, restores balances, and — if any bounce fee has been received — sends back only a refund unit, dropping every other message in the original response (payments to other addresses, other assets, and any state-variable updates): [5](#0-4) 

This is the ocore analog of `sweepTo`'s all-or-nothing loop: one "frozen"/restricted asset embedded among otherwise-valid outputs is enough to sink the complete operation.

### Impact Explanation
An AA author that legitimately wants to pay out multiple assets/addresses in one response (a very common pattern for exchanges, escrow contracts, DEXes, etc.) can be permanently prevented from doing so as soon as one target asset's condition becomes unsatisfiable at the destination — e.g. the destination address loses/never had the required attestation, a `transfer_condition` formula referencing external state stops evaluating to true, or the asset is or becomes `is_private`/non-transferable relative to the AA's balance holder. Every subsequent trigger that would produce that same batched response now bounces: the trigger sender only gets back `trigger.outputs - bounce_fees`, the other (perfectly valid) legs of the payment never execute, and any state changes intended alongside the payment are lost. If the failing condition is permanent, the AA is effectively frozen for that class of triggers, and funds sent by ordinary users keep being consumed as bounce fees.

### Likelihood Explanation
This is triggerable by any ordinary, unprivileged unit poster who sends a trigger to a public AA — no privileged role is required. It only requires an AA definition (which is public and reusable by anyone) that emits payments touching more than one asset/address in a single response, and one of those assets having (or later acquiring) a transfer/issue condition or attestation requirement that isn't met for the given trigger. Given how common multi-output/multi-asset AA responses are (e.g., paying out principal in one asset and fee/reward in another), this is a realistic, repeatable condition rather than a contrived edge case.

### Recommendation
Avoid coupling unrelated payment legs into a single atomic AA response when their success is not correlated: allow the AA formula/composer to either (a) validate transfer/issue conditions and attestation eligibility for each asset message *before* committing to bundling it with other unrelated legs, so an AA author can react to per-message failure instead of bouncing everything, or (b) provide an explicit mechanism (e.g., a "best effort" payment message type) that allows individual asset-payment failures to be dropped from the response without forcing a full bounce of otherwise-valid messages and state updates.

### Proof of Concept
1. Deploy an AA whose response (for a given trigger) sends: (a) bytes to `trigger.address`, and (b) some `asset X` (with a `transfer_condition` gated on e.g. a data feed or an `attested` check) to the same or a different address, in the same set of `messages`.
2. Post a trigger unit; while the `transfer_condition`/attestation for asset X is unmet at that moment (or the destination has never been attested), `sendUnit` proceeds through `completePaymentPayload` for asset X (this stage doesn't check transfer condition), builds `objUnit`, then `validateAndSaveUnit` fails inside `validatePaymentInputsAndOutputs` (`"transfer or issue condition not satisfied"` / `"some output addresses are not attested"`).
3. Observe in `aa_composer.js` that this causes `bounce(err)` for the whole unit: the bytes payment to `trigger.address` that would otherwise have succeeded is never sent, all state changes are rolled back, and only `trigger.outputs.base - bounce_fees.base` is refunded to the trigger sender.
4. Because the failing condition (e.g., missing attestation, permanently false transfer condition) can persist indefinitely, every future identical trigger produces the same full bounce, permanently blocking the AA's intended multi-asset payout logic.
