## Analog Found: Multisig Timelock-Override Threshold Inflated by a Non-Genuine "Implicit Execution Vote"

### Title
Multisig timelock override-threshold check counts an unvoted executor's implicit approval, letting the timelock be bypassed with one fewer genuine approval than configured - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
This is the Aptos-native analog of the `LibOverride._purchaseOverride` bug: the report's root cause is that a decision-critical counter (`loss`) was incremented using an inflated value (`_msgValue()`, which includes a refundable excess) instead of the true "spent" amount. In `multisig_account.move`, the timelock-override decision is gated on `num_approvals`, but that count is inflated with a "phantom" approval from the executing owner even when that owner never actually voted — inflating the value fed into a security check (`override_threshold`) that is supposed to represent genuine recorded approvals.

### Finding Description
`can_execute_with_timelock` allows immediate execution, bypassing the timelock wait, if `num_approvals >= override_threshold`: [1](#0-0) 

The `num_approvals` value passed into this check is computed by `can_execute`, which unconditionally adds +1 for the calling owner if that owner has not explicitly voted yet ("implicit" approval-by-execution): [2](#0-1) 

The same phantom-vote inflation is repeated inside the VM-invoked prologue function `validate_multisig_transaction`, which recomputes `num_approvals` and again adds +1 for the executor if they haven't voted, then feeds that inflated count into both the quorum check and the `can_execute_with_timelock` override check: [3](#0-2) 

Because the +1 is added regardless of whether the account actually has `override_threshold` genuine on-chain votes, an owner who has never approved the pending transaction can trigger execution and have their own act of calling `validate_multisig_transaction` counted as the missing vote needed to satisfy `override_threshold`. This lets the timelock be bypassed with only `override_threshold - 1` real approvals plus one non-genuine "approval" contributed solely by the act of executing — exactly analogous to the Solidity bug where a refundable, non-spent value (`_msgValue()`) was credited as if it were the real cost (`_spend`).

### Impact Explanation
`MultisigAccountTimeLock.override_threshold` is documented as "the number of approvals required to bypass the timelock" and is enforced to be strictly greater than `num_signatures_required` (per the doc's requirement table, `EINVALID_TIMELOCK_OVERRIDE_THRESHOLD` check), i.e., it is meant to represent a higher, stricter bar of *genuine* approvals than ordinary execution. Because the executor's own call inflates the approval count used for this stricter check, the timelock's core security guarantee — that only a real super-majority of owners can skip the waiting period — is broken by one vote. This is a wrong-state-transition/authorization-bypass at the multisig transaction admission boundary: a transaction that should be forced to wait out `timelock_period` is instead admitted and executed immediately, based on an approval set that does not actually exist on-chain.

### Likelihood Explanation
Likelihood is high in any deployment that uses the `MultisigAccountTimeLock` override-threshold feature: any owner (even one who never approved the transaction) can trigger this by simply calling execution once `num_signatures_required` (the lower, ordinary bar) is met, without needing to coordinate an actual `override_threshold`-sized approval set.

### Recommendation
Do not feed the implicit "vote by executing" count into `can_execute_with_timelock`/override-threshold logic. Instead, pass the genuine on-chain approval count (`num_approvals_and_rejections` result, without the executor's ad hoc +1) into the override-threshold comparison, reserving the implicit-vote addition only for the ordinary `num_signatures_required` quorum check where it is intended to apply.

### Proof of Concept
1. Configure a multisig account with `num_signatures_required = 3`, `timelock_period = T`, `override_threshold = 4`, and 4+ owners.
2. Create a transaction; 3 distinct owners approve it (satisfying `num_signatures_required` but not `override_threshold`).
3. Before `T` elapses, have a 4th owner (who has cast no vote at all) call the multisig execution entry point.
4. In `validate_multisig_transaction`, `has_voted_for_approval` is false for this 4th owner, so `num_approvals` is bumped from 3 to 4 [4](#0-3) , which now satisfies `override_threshold` in `can_execute_with_timelock` [5](#0-4)  — the transaction executes immediately, bypassing the timelock wait using only 3 genuine approvals instead of the configured 4.

        assert_valid_sequence_number(multisig_account, sequence_number);

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );
