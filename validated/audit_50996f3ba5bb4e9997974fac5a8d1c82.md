## Confirmed multi-org config
Shipit explicitly supports one GitHub App (and one `webhook_secret`) *per organization* in a single instance: `config/secrets.development.example.yml` shows the `github: { somegithuborg: {...}, someothergithuborg: {...} }` schema, and `Shipit.github(organization:)` picks the app/secret keyed by organization name. ### Title
Webhook signature is bound to `repository.owner.login`, not to the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the inbound HMAC against using `repository_owner`, a value read from the *same untrusted JSON body* it is about to verify (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The signature check only proves "the sender knows organization X's secret"; it never establishes that organization X actually owns the repository/commit that the event handlers subsequently act on. Handlers instead key off a different, independent field of the same body — `repository.full_name` (`Handler#repository_name`) — or, in the `status` event, off no repository field at all (`Commit.where(sha: params.sha)`). This is the same bug class as the audited `SophonFarming.add()`/`set()` finding: one signal is used to authorize the trust decision while a *different* signal in the same request determines what state gets mutated, and nothing binds the two together.

### Finding Description
`verify_signature` computes:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [3](#0-2) 
`repository_owner` is taken from `repository.owner.login` (fallback `organization.login`) inside the attacker-supplied JSON body itself: [4](#0-3) 

`GitHubApp#verify_webhook_signature` only checks that the raw body's HMAC matches the secret configured for that organization: [5](#0-4) 

Once verified, the actual repository/stack targeted by handlers is derived from a *separate* field, `repository.full_name`: [6](#0-5) 

Nothing forces `repository.owner.login` (used to pick the secret) to equal the owner encoded in `repository.full_name` (used to pick the target stack). Because both fields are attacker-controlled fields inside a single request that the attacker crafts and signs themselves, an operator/administrator of *any one* organization already registered with this Shipit instance (i.e., someone who legitimately knows their own org's `webhook_secret`, which is normal for a GitHub App owner/installer of that org) can:
1. Set `repository.owner.login` (or `organization.login`) to their own org — so `Shipit.github(organization: repository_owner)` resolves to the secret they know.
2. Sign the raw body with that known secret — passing `verify_signature`.
3. Set `repository.full_name` (and, for `status` events, just the `sha`) to point at a completely different organization/repository/commit tracked by the same Shipit instance.

The `status` handler is the most severe instance because it doesn't even use `repository_name`/`full_name` to scope the update — it matches purely on `sha` across the entire `commits` table: [7](#0-6) 
So a forged, self-signed `status` webhook (signed with the attacker's own org secret) can create/alter a CI status (`state`, `context`, `description`, `target_url`) on any commit belonging to any other stack in the instance, as long as the attacker knows or predicts its SHA (e.g., visible via any public repo/PR page, Shipit UI, or their own fork sharing history with the victim's default branch).

### Impact Explanation
Commit statuses drive Shipit's safety/authorization gates: `Commit#deployable?`/blocking-status checks, `required_statuses`, and continuous delivery/merge scheduling (`stack.schedule_merges if new_status.pending? || new_status.success?`) are all evaluated from `Status` records written by this handler. [8](#0-7) 
An attacker who controls a legitimately-registered but unrelated organization in the same multi-tenant Shipit instance can forge a "success" status on a victim commit they don't have any GitHub write access to, satisfying `required_statuses`/CI checks and triggering `schedule_merges` / continuous deployment for that victim stack — an unauthorized deploy or merge, which is explicitly in the Critical impact bucket. `PushHandler`/`CheckSuiteHandler` are less directly exploitable (they only re-trigger fetches from GitHub via Shipit's own credentials), but `StatusHandler` alone is sufficient to break the authorization binding.

### Likelihood Explanation
Requires only: (a) being an owner/admin of *one* organization already connected to the target multi-tenant Shipit instance (knowing that org's own `webhook_secret`, which such an owner legitimately possesses — no privileged Shipit account, `ApiClient` token, or GitHub App private key is needed), and (b) knowing/guessing the target commit SHA of a different, victim stack tracked by the same instance. Both preconditions are realistic in any Shipit deployment serving more than one GitHub organization, which is an explicitly documented and supported configuration.

### Recommendation
Bind the field used for signature/secret selection to the field used for target resolution: after selecting the app/secret via `repository_owner`, re-derive `repository_owner` from the *same* `repository.full_name` (or `organization.login`) that handlers use to resolve the stack, and reject the request if they disagree. Additionally, scope `StatusHandler#process` (and any other handler) to commits belonging to a stack whose `Repository` matches `repository.full_name`, instead of a bare `Commit.where(sha:)` lookup across the whole instance.

### Proof of Concept
1. Attacker registers/owns GitHub org `attacker-org`, added to the Shipit instance's multi-org `secrets.yml` (`github.attacker-org.webhook_secret = S`).
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha, from a different org's stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` using their own known secret `S`.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against `S`.
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — finds the victim commit (unrelated org/stack) and calls `create_status_from_github!`, marking it as `success`, which can satisfy `required_statuses` and trigger `schedule_merges`/continuous deployment for the victim's stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
