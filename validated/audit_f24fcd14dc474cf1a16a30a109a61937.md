### Title
Api::CCMenuController bypasses stack-scoped ApiClient authorization, allowing a token issued for one stack to read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The precision-loss bug class in the report is a mismatch between the value that is *checked* (`amount`) and the value that is actually *applied* (`bias`), letting the applied effect diverge from what the guard verified. In this engine, the same class of bug appears in the API `ApiClient` stack-scoping mechanism: `Api::BaseController` defines a scoped stack lookup (`stacks.from_param!`) that all other API resource controllers rely on to enforce `ApiClient#stack_id`, but `Api::CCMenuController` silently overrides `stack` to resolve against the unscoped `Stack` relation, so the permission check passes while the record actually touched is never validated against the token's stack binding.

### Finding Description
`Api::BaseController#stacks` implements the scoping contract for stack-bound API tokens: [1](#0-0) [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

`ApiClient` supports being scoped to a single stack via `belongs_to :stack, optional: true` and `stack_id`, and permission enforcement is a separate, purely name-based check (`check_permissions!` just verifies `"#{operation}:#{scope}"` is in the client's `permissions` array, with no relation to which stack record is loaded): [2](#0-1) [3](#0-2) 

`Api::StacksController`, which is the reference implementation, correctly reuses the scoped lookup: [4](#0-3) 

But `Api::CCMenuController` overrides `stack` and resolves it against the global `Stack` relation instead of the client-scoped `stacks` relation, while still declaring only the generic `require_permission :read, :stack`: [5](#0-4) [6](#0-5) 

Because `require_permission!` only checks that `"read:stack"` is present in the token's permission list (true for any token with that permission, including stack-scoped ones — see the `here_come_the_walrus` fixture which is scoped to a single stack yet holds `read:stack`), and `stack` here never consults `current_api_client.stack_id`, any authenticated API client holding `read:stack` — even one deliberately restricted to a single stack — can pass `params[:stack_id]` for a *different* stack and successfully load and render that other stack's CCMenu XML (deploy/rollback history, status, last build info).

This is the same binding violation as the report: the guard (`require_permission!`, and the `stacks` scoping contract elsewhere) verifies one thing ("this token has read:stack and is scoped to stack A"), while the code path that actually executes (`stack` in this controller) acts on a different, unchecked value (any `stack_id` param), exactly mirroring "check on `amount`, effect based on `bias`" — here it's "authorization scoped to stack A, effect touches stack B."

### Impact Explanation
This crosses the "stack a token authorises versus a stack it touches" boundary called out in scope, and it is a concrete unauthorized read of stack state (deploy/rollback status and metadata) via a token that was deliberately restricted to a different stack — matching the High-severity category "unauthenticated/under-scoped read of stack state" listed in scope. No repository write access, GitHub credentials, or privileged account are required beyond possessing any valid stack-scoped `ApiClient` token (e.g., one created via `CCMenuUrlController`, which itself mints a `read:stack`-scoped-to-one-stack token: see `app/controllers/shipit/ccmenu_url_controller.rb`).

### Likelihood Explanation
High. Any legitimate holder of a scoped `read:stack` API token (the exact kind `CCMenuUrlController` generates for embedding in CI dashboards) can trivially exploit this by changing the `stack_id` segment of the request URL — no special crafting, timing, or race condition needed.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup, matching `Api::StacksController` and `Api::BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the local override entirely (or deleting it so the inherited `BaseController#stack` is used, since the route param name matches).

### Proof of Concept
1. Create (or obtain) a stack-scoped `ApiClient` restricted to `Stack A`, with `permissions: ['read:stack']` (this is exactly what `CCMenuUrlController#client` creates, scoped via `stack:` in `find_or_create_by!`).
2. Using that client's `authentication_token`, send `GET /api/stacks/OwnerB/repoB/environmentB/ccmenu` (i.e., substitute `stack_id` for `Stack B`, which the token was never scoped to).
3. `authenticate_api_client` succeeds (valid token), `require_permission!(:read, :stack)` succeeds (token has `read:stack`), and `stack` resolves via `Stack.from_param!(params[:stack_id])` against all stacks — returning `Stack B`'s data even though the token's `stack_id` is `Stack A`.
4. Compare against `Api::StacksController#show` with the same token and `Stack B`'s id, which correctly returns `404`/empty because `stacks` is scoped to `Stack A` only — demonstrating the inconsistency is specific to `CCMenuController`.
