### Title
Webhook signature verification uses an unverified organization selector, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` selects which GitHub App / webhook secret to verify a webhook against based on a value read out of the *unverified* JSON payload (`repository.owner.login` or `organization.login`), rather than from anything cryptographically tied to a fixed installation. In a multi-organization Shipit deployment (a configuration this engine explicitly supports and documents), an attacker who controls a webhook secret for one configured organization can forge a signature that is valid for that organization while the remainder of the payload (e.g. `repository.full_name`, commit SHAs, statuses) targets a repository belonging to a completely different, victim organization. Downstream handlers trust the payload's `repository.full_name` to resolve the target `Stack`/`Repository` without ever checking that this matches the organization used to verify the signature.

### Finding Description
The engine supports multiple independent GitHub Apps/organizations, each with its own `webhook_secret`, configured under `config/secrets.yml` as documented in `docs/setup.md` ("Using Multiple Github Applications") and exercised by `test/dummy/config/secrets_double_github_app.yml`. `Shipit.github(organization:)` looks up the correct `GitHubApp` (and therefore the correct `webhook_secret`) for a given organization name [1](#0-0) .

In `WebhooksController#verify_signature`, the organization used to select which secret to verify against is derived directly from the untrusted, not-yet-verified request body:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The HMAC check itself (`verify_webhook_signature`) does correctly validate the raw body against `webhook_secret`, but only for whichever organization's secret was selected using this attacker-controlled field [3](#0-2) .

After signature verification, `create` re-parses the same raw body and dispatches it to event handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Handlers (e.g. `Shipit::Webhooks::Handlers::Handler#stacks`) resolve the target repository purely from `payload.dig('repository', 'full_name')`, with no cross-check against `repository_owner`/the organization whose secret validated the signature:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

The binding that should hold is: **organization whose webhook secret authenticated the request == owner of the repository the payload's events are applied to**. Because `repository_owner` (used to pick the secret) and `repository.full_name` (used to pick the target stack) are two independently attacker-controlled fields inside the same unauthenticated JSON body, an attacker can set them inconsistently: sign the payload with the secret of an organization they legitimately control (e.g. by installing the Shipit-configured GitHub App on their own org and triggering a real event, or simply computing HMAC-SHA1 knowing that org's `webhook_secret`), while pointing `repository.full_name` at a `Repository`/`Stack` belonging to a different, victim organization also configured on the same Shipit instance.

### Impact Explanation
This breaks the trust boundary between "which organization's credentials were used to authenticate this request" and "which repository/stack the webhook is allowed to act upon." Depending on the event type dispatched (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.), an attacker can:
- Enqueue `GithubSyncJob` for a victim stack with an attacker-chosen `expected_head_sha`, potentially causing Shipit to treat an attacker-influenced commit as the head of a victim's protected branch, which can feed into deploy/merge automation.
- Inject fabricated commit `status`/`check_suite` results for a victim's commits, which several installations use as gating conditions for autodeploys or the merge queue — i.e., unauthorized manipulation of deploy/merge decisioning for a repository the attacker does not own.
- Create/alter `Team`/`Membership` records via the `membership` event handler using data attributed to an organization they don't administer.

This matches the "organization that authenticated versus the repository that is written" trust-binding break called out as in-scope, and can lead to unauthorized deploy/merge decisions being influenced for repositories outside the attacker's control — a High-severity outcome (escalation of webhook-derived authority across organizational/repository boundaries) under this engine's own multi-org support, without requiring a Shipit session, API token, or any other privileged credential.

### Likelihood Explanation
Exploitation requires: (1) the Shipit instance being configured with more than one GitHub organization (a first-class, documented configuration — see `docs/setup.md` "Using Multiple Github Applications"), and (2) the attacker knowing/controlling the `webhook_secret` for at least one of the configured organizations (e.g., because they administer that org's GitHub App settings, which is plausible for federated/self-service multi-tenant Shipit deployments). Given that condition, the rest of the attack is a single crafted HTTP POST to the shared `/webhooks` endpoint with mismatched `repository.owner.login` and `repository.full_name` fields — no additional access is needed. Likelihood is moderate: it depends on the multi-org deployment model, but that model is explicitly supported and documented by the engine itself, so it is not an out-of-scope "host misconfiguration."

### Recommendation
Do not use an unauthenticated field from the payload to select the verification secret and then trust a different unauthenticated field from the same payload to select the write target without cross-validation. Options:
- After a successful signature match, re-derive the organization strictly from the already-verified body and enforce that `repository.full_name`'s owner segment matches `repository_owner` (the same field used for verification) before dispatching to handlers, rejecting mismatches with 422.
- Alternatively, iterate over all configured organizations' secrets and verify successfully only if the same organization that validates the signature also owns the acted-upon repository, rather than trusting a single attacker-supplied `repository_owner` lookup key.

### Proof of Concept
Preconditions: Shipit configured with two organizations, `AttackerOrg` (attacker knows/controls `webhook_secret_A`) and `VictimOrg` (hosts a tracked `Repository`/`Stack`), per `docs/setup.md`'s multi-org schema.

1. Attacker builds a JSON push payload:
```json
{
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, raw_body)>` using the known secret for `AttackerOrg`.
3. POST to `/webhooks` with `X-Github-Event: push` and the signature header.
4. `verify_signature` computes `repository_owner == "AttackerOrg"`, loads `Shipit.github(organization: "AttackerOrg")`, and the HMAC check passes (it's the attacker's own secret) [6](#0-5) .
5. `create` re-parses the body and dispatches to the push handler, which resolves the target stack via `repository.full_name == "VictimOrg/victim-repo"` [5](#0-4) , causing Shipit to act on the victim repository's stack using a payload never authenticated by `VictimOrg`'s secret.

Note: I was unable to open `app/models/shipit/webhooks/handlers/push_handler.rb`, `status_handler.rb`, and `app/models/shipit/repository.rb` directly in this session due to a tool error on the final iteration, so the exact downstream job/attribute effects for each event type are inferred from `Handler#stacks`/`#repository_name` and the `GithubSyncJob` enqueue behavior visible in `test/controllers/webhooks_controller_test.rb`; a full review of each handler's side effects is recommended to enumerate the complete blast radius.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
