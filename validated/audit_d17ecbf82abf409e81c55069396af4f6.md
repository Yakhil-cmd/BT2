### Title
Webhook signature is verified against `repository.owner.login` while handlers act on `repository.full_name`, allowing cross-repository status/event forgery — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multiple GitHub organizations, each with its own `webhook_secret` [1](#0-0) . The `WebhooksController#verify_signature` selects which organization's secret to check the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) [2](#0-1) . Once the signature is accepted, event handlers resolve *which repository/stack to act on* using a **different** field of the same payload: `payload.dig('repository', 'full_name')` [3](#0-2) , or in `StatusHandler`'s case, no repository scoping at all — it matches purely by commit `sha` across the entire installation [4](#0-3) .

### Finding Description
The equality the system implicitly (and incorrectly) assumes is:

`organization authenticated (repository.owner.login used to pick webhook_secret)` == `repository/stack acted upon (repository.full_name / commit.sha used by handlers)`

These two values are never cross-checked. `GithubApp#verify_webhook_signature` only proves that *some* configured organization's secret produced a valid HMAC over the raw body [5](#0-4) ; it says nothing about which repository the payload's other fields describe. An operator running Shipit with multiple GitHub Apps (one per customer/org, as documented) trusts that a validly-signed webhook for org A cannot forge state for org B's stacks.

But because the two lookups (`repository_owner` for signing org vs. `repository.full_name`/`sha` for target) are independent JSON paths inside the *same, attacker-controlled* JSON body, an unprivileged attacker who legitimately owns/administers *their own* installed GitHub App (org A) can:
1. Send an HTTP POST to `/webhooks` with `repository.owner.login = "org-a"` (so `verify_signature` picks org A's `webhook_secret`, which the attacker knows because they installed the app and can also just trigger a real event from their own repo to get a validly signed body/secret pair).
2. Set `repository.full_name = "victim-org/victim-repo"` (or, for `status`/`push` events, arbitrary `sha`/`ref` values) in the same payload.
3. Since the HMAC covers the raw bytes and org A's secret is the one used to sign it, the signature check in `WebhooksController#verify_signature` passes even though the payload's `full_name`/`sha` refer to victim-org's resources [6](#0-5) .
4. `Shipit::Webhooks.for_event(event)` dispatches to handlers that trust `payload.dig('repository', 'full_name')` to locate `Stack`s [3](#0-2) , e.g. `PushHandler` enqueues a `sync_github` for any stack matching that full name and branch [7](#0-6) , or `StatusHandler` creates a commit status for **any** commit with matching `sha` anywhere in the Shipit instance, with no repository check whatsoever [4](#0-3) .

This is the direct analog of the reported bug class: just as `ShareModule.handleReport` used an "authorized" quantity (`totalShares()`) that silently included un-vetted prior state (already-taken fees), Shipit's webhook pipeline uses an "authorized" identity (the org whose secret matched) as if it also vetted an unrelated payload field (`repository.full_name`/`sha`) that the signature never actually bound.

### Impact Explanation
An attacker who controls one legitimate, low-privilege GitHub App installation (their own org) can forge events attributed to a repository/commit they do not own or have push access to:
- Forge commit statuses (`StatusHandler`) for arbitrary commits across the whole Shipit instance, independent of repository, since lookup is only by `sha` — this can flip CI/merge-gating status used elsewhere in the deploy/merge pipeline (`Shipit::Commit#create_status_from_github!`, referenced from `commit_checks.rb`), potentially allowing an unauthorized merge or deploy to proceed by spoofing a passing status.
- Trigger `sync_github`/push processing for victim stacks via `PushHandler`, causing Shipit to fetch and register victim commits out of band.
- Forge pull-request/team/membership events for organizations the attacker does not administer, subject to whatever the specific handler does with `organization`/`repository` fields.

This crosses a real trust boundary (org A's credential should never let you write to org B's repository state) and can plausibly enable an unauthorized deploy/merge (matches the "High"/"Critical" impact bar: escalation of authorization, unauthorized deploy).

### Likelihood Explanation
Requires the deployment to be configured with multiple GitHub organizations (a documented, supported configuration) and requires the attacker to control (or install) at least one GitHub App on some organization pointed at the same Shipit instance — no repository write access to the victim org, no Shipit session, and no privileged Shipit account is needed, satisfying the "unprivileged attacker" constraint.

### Recommendation
After signature verification, re-derive the organization from the same field used for repository/stack resolution (e.g., require `payload.dig('repository', 'owner', 'login')` used in signature selection to equal the owner/org portion of `payload.dig('repository', 'full_name')`, and reject events where they diverge). Additionally, `StatusHandler` should scope `Commit` lookups by the verified repository, not by `sha` alone.

### Proof of Concept
Conceptual PoC (cannot be executed here — no test/script access permitted in scope, and `test/**` is out of scope for this engine per the rules, so this is illustrative only):
1. Attacker installs a Shipit-connected GitHub App on `attacker-org`, obtaining a valid `webhook_secret`.
2. Attacker crafts a `status` event payload:
```json
{ "sha": "<victim-commit-sha>", "state": "success", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"} }
```
3. Attacker signs it with `attacker-org`'s `webhook_secret` and POSTs to `/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and accepts the signature [6](#0-5) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's real commit regardless of which repository it belongs to — and creates a forged success status on it [4](#0-3) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
