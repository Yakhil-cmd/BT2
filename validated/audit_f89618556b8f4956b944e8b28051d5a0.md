## Title
Unit hash-to-sign omits `oversize_fee`, allowing fee-amount tampering after cosigner signatures are collected — ([File: object_hash.js])

## Summary
`getUnitHashToSign` (used to compute the bytes actually signed by every author/cosigner) is built from `getNakedUnit`, which explicitly strips `oversize_fee` (along with `headers_commission`/`payload_commission`/`main_chain_index`) before hashing. Unlike `headers_commission`/`payload_commission`, which are fully re-derived from the unit's own content and independently re-verified in `validation.js`, `oversize_fee` is a fee value computed from unit size *and* the current network `threshold_size` system variable at composition time, and it directly enters the payment-balance equation checked during validation. Because it is excluded from the signed content, a party controlling the "naked" unit (e.g., the initiating device in multi-device/multisig signing) can request cosigner signatures over a unit, then change `oversize_fee` afterward without invalidating any authentifier — exactly the same root cause pattern as the referenced "fee rate not hashed" finding (a fee-relevant field is left out of the hash that authorizers rely on).

## Finding Description
- `object_hash.js` `getNakedUnit()` deletes `unit`, `headers_commission`, `payload_commission`, `oversize_fee`, `actual_tps_fee`, `main_chain_index` before any hashing. [1](#0-0) 
- `getUnitHashToSign()` calls `getNakedUnit()` and additionally strips `authentifiers`, then hashes the remaining naked object — this is the value every author (including cosigners in a shared/multisig address) actually signs. [2](#0-1) 
- `headers_commission` and `payload_commission`, though excluded from the hash, are safe because validation re-derives and enforces them purely from the unit's own content (`objectLength.getHeadersSize`/`getTotalPayloadSize`), so they cannot be tampered with independently of content that *is* hashed. [3](#0-2) 
- `oversize_fee`, however, is not re-derivable from unit content alone: it depends on the network's `threshold_size` system variable (`storage.getOversizeFee`), and validation only checks that it is a positive integer, not that it equals a specific expected recomputed value tied into the signed content. [4](#0-3) 
- `oversize_fee` is nevertheless load-bearing for the funds balance check: `total_input` must equal `total_output + headers_commission + payload_commission + oversize_fee + tps_fee + burn_fee + vote_count_fee`. [5](#0-4) 
- In multi-device/multisig signing flow (`wallet.js` "sign" case), a proposing device sends an `unsigned_unit` (which already carries whatever `oversize_fee` the proposer chose) to a cosigner device; the cosigner computes `text_to_sign = objectHash.getUnitHashToSign(body.unsigned_unit)` and signs that value — never seeing or committing to the `oversize_fee` figure because it's excluded from the hash. [6](#0-5) 
- The composer itself sets `oversize_fee` from `storage.getOversizeFee(objUnit, last_ball_mci)` right before signing, confirming this field is meant to be a fee determined at composition time, not baked into the content that's cryptographically committed via the signature. [7](#0-6) 

Because the signature (produced under `getUnitHashToSign`) never covers `oversize_fee`, any party who controls the unsigned unit object between the time cosigners sign and the time it is finalized/broadcast (or a hub/proxy forwarding the "sign" request, or a colluding co-author on a shared multisig address) can increase `oversize_fee` after collecting valid signatures from other cosigners, without invalidating those signatures. The unit still passes `hasValidHashes`/signature checks, and the funds balance equation simply requires that the (now-inflated) `oversize_fee` be paid out of the shared address's inputs — spending more of the cosigners' shared funds than they actually approved when they signed.

## Impact Explanation
This allows unauthorized spending from a multisig/shared address: cosigners approve a transaction by signing a specific naked-unit hash, but the actual amount deducted from the shared balance for `oversize_fee` can be silently increased post-signature by whichever party assembles/forwards the final unit. This is a fund-loss/unauthorized-spending impact for legitimate cosigners on a shared address, matching the High severity bar of the referenced report (fee amount not bound by the signature the payer approved).

## Likelihood Explanation
Exploitability requires a scenario where multiple authors/cosigners rely on `getUnitHashToSign` to approve a transaction body without independently re-verifying the numeric `oversize_fee` value bound into the final broadcast unit (e.g., the proposing device or a message-forwarding hub is untrusted/compromised relative to the other cosigners). Since `oversize_fee` is only non-zero for large units above `threshold_size`, and multisig composition flows explicitly separate "propose" and "sign" steps across devices (`wallet.js` sign handler), this is a realistic path for any wallet implementation that trusts `getUnitHashToSign` as the sole integrity guarantee for a to-be-signed unit's numeric fee fields.

## Recommendation
Include `oversize_fee` (and any other content-independent, network-state-derived fee field intended to be paid by the signer) within the hash committed to by `getUnitHashToSign` (and consequently `getUnitHash`), or alternatively bind it cryptographically by re-deriving and strictly enforcing its exact expected value from `last_ball_mci`/content the same way `headers_commission`/`payload_commission` are enforced, so that it cannot be altered post-signature without invalidating existing authentifiers.

## Proof of Concept
1. Compose a large multi-authored (shared-address) unit whose size exceeds `threshold_size`, so `storage.getOversizeFee` returns a non-zero `oversize_fee`, and set that initial (small) `oversize_fee` on `objUnit`.
2. Send this `unsigned_unit` to a cosigner device via the `wallet.js` "sign" flow; the cosigner computes `objectHash.getUnitHashToSign(unsigned_unit)` (which strips `oversize_fee`) and returns a valid signature for that hash. [6](#0-5) 
3. Before broadcasting, the proposer (or an intermediary forwarding the message) modifies `objUnit.oversize_fee` to a larger value.
4. Recompute `objUnit.unit = objectHash.getUnitHash(objUnit)` — this value also excludes `oversize_fee` via `getNakedUnit`, so the unit hash and existing authentifiers remain valid. [8](#0-7) 
5. Submit the unit; `validation.js` only checks `oversize_fee` is a positive integer and folds it into the required `total_input`, accepting the higher fee deduction from the shared address's inputs without any indication that the cosigner never approved this specific figure. [5](#0-4)

function getUnitHashToSign(objUnit) {
	var objNakedUnit = getNakedUnit(objUnit);
	for (var i=0; i<objNakedUnit.authors.length; i++)
		delete objNakedUnit.authors[i].authentifiers;
	var sourceString = (typeof objUnit.version === 'undefined' || objUnit.version === constants.versionWithoutTimestamp) ? getSourceString(objNakedUnit) : getJsonSourceString(objNakedUnit);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
