### Title
`has_only` oscript operator builds a raw regex character class from unsanitized `sub` input, allowing negation/escaping and confusing the "sanitizer" - ([File: formula/evaluation.js])

### Summary
The `has_only` oscript function (used in AA formulas and address/asset definition `formula` conditions) builds a JavaScript `RegExp` character class directly from a user/AA-controlled string (`sub`), applying only a partial escaping (`]` and trailing `\`) before embedding it inside `"^[" + sub + "]*$"`. This is structurally the same bug class as CVE-2020-26973: a "sanitizer" (here, the code that is supposed to neutralize `sub` before using it to build a character-matching pattern) is confused by certain crafted input, so components that should be blocked/escaped slip through unmodified, changing the matching semantics in unexpected ways.

### Finding Description
`has_only` is implemented in `formula/evaluation.js`: [1](#0-0) 

The intent is: "does `str` consist only of characters found in `sub`?" To build this check, `sub` is dropped verbatim into a regex character class `[sub]`. The only defensive filtering is:
1. Reject if `sub` contains a backslash followed by `]` (`/\\]/`) or ends in a single trailing backslash.
2. Escape literal `]` characters to `\]`.

This escaping is incomplete/confused with respect to regex character-class semantics:
- A leading `^` in `sub` is not stripped or escaped. Since the class is built as `"[" + sub + "]"`, a `sub` value starting with `^` turns the intended "characters allowed" class into a **negated class** `[^...]`, completely flipping the semantics of the check (`has_only` becomes "has none of").
- Character ranges (`a-z`, `0-9`, etc.) inside `sub` are not neutralized, so `sub` values can introduce unintended ranges that match far more (or fewer) characters than the AA/definition author intended when constructing `sub` from concatenated or computed string parts.
- Because the escaping only special-cases `]`, other class metacharacters that a naive author assumes are "just characters" (e.g., `^`, `-`) behave specially, which is exactly the "confused sanitizer" pattern in the CVE: certain crafted input causes the wrong components (here, unintended matching ranges/negation) to be treated as literal/removed vs. active.

The same construction issue is validated as reachable (not filtered at validation time) in `formula/validation.js`'s `has_only` case, which only checks activation MCI and evaluates sub-expressions, performing no character-level restriction on `sub`: [2](#0-1) 

This operator is reachable by any AA author writing `has_only` into an AA's base/response formulas, and — more importantly — by any AA trigger sender or unit poster whenever an AA formula computes `sub` (or `str`) from trigger data, params, or state variables, since oscript strings are frequently concatenations of untrusted trigger fields.

### Impact Explanation
If an AA's logic uses `has_only` to validate that some attacker-influenced string (e.g., a memo, a computed identifier, or a whitelist assembled from data-feed/state values) contains only "safe" characters before using it in fund-moving or state-changing logic, an attacker who can influence the operand used as `sub` (directly or indirectly, e.g. by controlling one of several concatenated components) can cause the character class to be negated (via leading `^`) or extended (via unintended ranges), causing `has_only` to return an incorrect boolean. This can bypass an AA's input-validation gate, leading to unauthorized state transitions, incorrect branching in AA logic, or acceptance of otherwise-rejected data — potentially resulting in fund loss/misdirection from the AA if the validation was guarding a spending or issuance decision. This matches the "AA fund loss or freezing" / "node disagreement on validity" impact categories, since all full nodes execute the same formula deterministically but the incorrect matching means the AA's own guarantees can be silently violated.

### Likelihood Explanation
Exploitability depends on a specific pattern: an AA author using `has_only` with an operand that is (even partially) influenced by trigger data or other attacker-controllable inputs, and relying on its result for a security-relevant decision. This is a real, reachable pattern for AA formulas (oscript is Turing-complete-ish and widely used for validation gates), but it is not automatically present in every AA — it requires a specific programming pattern by the AA author. Given the operator's escaping is object­ively incomplete (handles only `]`, ignores `^` negation and ranges), any AA relying on this operator for character allow-listing of attacker-influenced strings is at risk. Likelihood is Medium-High for this specific misuse pattern, though it is conditioned on AA-author code, similar to how the original CVE was conditioned on sanitizer misuse by consumers of Firefox's sanitizer API.

### Recommendation
- In `formula/evaluation.js` (and mirrored logic in `formula/validation.js`), fully sanitize `sub` before embedding it in a regex character class: escape all regex metacharacters that have special meaning inside `[...]` (`]`, `\`, `^`, `-`, and ideally use a whitelist-diff approach instead of building a regex).
- Reject/escape a leading `^` in `sub` explicitly, or better, avoid `RegExp` construction entirely and instead implement `has_only` via a `Set` of the individual characters in `sub`, checking that every character in `str` is a member of that set — this avoids all regex-metacharacter confusion.
- Add unit tests covering `sub` values starting with `^`, containing `-` ranges, and other regex-special sequences to lock in the corrected semantics.

### Proof of Concept
Given the current implementation:
```js
// formula/evaluation.js has_only handler
sub = "^abc";          // attacker-influenced substring, e.g. from trigger.data.allowed
str = "xyz";           // attacker-influenced string being checked
// sub has no trailing backslash and no "\]" sequence, so it passes the guard
// sub.replace(/]/g,'\\]') leaves "^abc" unchanged
// resulting regex: new RegExp("^[^abc]*$").test("xyz")  -> true (str has "only characters NOT in abc")
```
An AA formula such as:
```
if (trigger.data.tag has_only "abcdef") { ... allow ... }
```
was intended by the AA author to allow only tags built from the letters `a-f`. If the AA computes the allow-list dynamically (e.g., `trigger.data.charset` concatenated with a fixed suffix) and an attacker can make that computed string begin with `^`, the check silently inverts, letting through values it was designed to reject. Because this executes identically on every full node, this is a deterministic AA-logic bypass rather than a node-disagreement bug, but it directly undermines whatever spending/state-transition guard the AA author built around `has_only`.
