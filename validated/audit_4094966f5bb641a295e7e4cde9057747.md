### Title
Permanent Loss of Staking Rewards due to Address Collision in Reward Allocation Map - ([File: kaiax/reward/impl/getter.go])

### Summary
A vulnerability exists in the Kaia reward distribution logic where staking rewards can be permanently lost due to overwriting entries in a reward allocation map. When the Prague hardfork is active, rewards are split between a validator's reward address and their consensus liquidity (CL) pool address. However, the implementation uses direct assignment to a local map, which causes rewards to be overwritten and lost if multiple reward destinations share the same address.

### Finding Description
In `kaiax/reward/impl/getter.go`, the functions `assignStakingRewards` [1](#0-0)  and `assignStakingRewardsFlex` [2](#0-1)  calculate the distribution of staking rewards. Since the Prague hardfork, rewards for validators with consensus liquidity are split into a validator portion (`cnAmount`) and a CL pool portion (`clAmount`) using the `cn.Split` function [3](#0-2) .

The calculated amounts are stored in a local `alloc` map using direct assignment:
```go
alloc[cn.RewardAddr] = cnAmount
alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
``` [4](#0-3) 

Because this map is populated via direct assignment rather than accumulation, several collision scenarios result in permanent loss of KAIA tokens:
1. **Self-Collision**: If a validator configures their `CLPoolAddr` to be the same as their `RewardAddr`, the `cnAmount` is overwritten by `clAmount`, and the `cnAmount` portion is never distributed [4](#0-3) .
2. **Cross-Validator Collision**: If multiple validators share the same `CLPoolAddr`, the `clAmount` of earlier validators in the loop is overwritten by subsequent ones [5](#0-4) .
3. **Reward/CL Collision**: If one validator's `RewardAddr` is the same as another's `CLPoolAddr`, an overwrite occurs.

The `remaining` budget is correctly reduced by the full reward amount [6](#0-5) , but the overwritten portions are never added to any account balance in `FinalizeState` [7](#0-6) . Additionally, a related bug in `consolidateNodes` causes all but the last `CLStakingInfo` to be ignored if multiple nodes share a `RewardAddr` [8](#0-7) .

### Impact Explanation
This vulnerability leads to the permanent loss (unintended burning) of KAIA tokens that were architecturally intended to be distributed as staking rewards. Furthermore, the block proposer receives a smaller reward than intended because the remainder of the reward budget (which is granted to the proposer) is calculated by subtracting the full, correct reward amounts from the budget, even though those amounts are subsequently lost [9](#0-8) .

### Likelihood Explanation
The likelihood is high as it is a standard and expected configuration for a validator to direct all their rewards (both regular and CL-based) to a single management address. The protocol does not prevent or warn against setting `RewardAddr` and `CLPoolAddr` to the same value, making this a silent and persistent failure mode for such validators.

### Recommendation
Modify `assignStakingRewards` and `assignStakingRewardsFlex` to accumulate rewards in the `alloc` map instead of using direct assignment. A helper function similar to `IncRecipient` [10](#0-9)  (which uses `Add` to accumulate balances) should be used to ensure that all portions of the reward are preserved regardless of address collisions.

### Proof of Concept
1. Enable the Prague hardfork on a test network.
2. Register a validator with a `RewardAddr` (e.g., `0x123...`) and a `CLPoolAddr` set to the same address (`0x123...`).
3. Ensure the validator has sufficient stake to be eligible for rewards.
4. Mine a block and observe the reward distribution for that validator.
5. The `cn.Split` function will correctly calculate two non-zero amounts (e.g., `cnAmount = 70`, `clAmount = 30`).
6. The `alloc` map will be updated: `alloc[0x123...] = 70`, then `alloc[0x123...] = 30`.
7. The validator receives only 30 tokens. The 70 tokens from `cnAmount` are lost from the system supply.
8. The total balance of the proposer will also be lower than expected because the full 100 tokens were subtracted from the budget when calculating the proposer's remainder.
