## Analog Found: Full plaintext device messages (including private payment blinding factors) written to console logs

### Title
Sensitive private-payment and signing data is written in plaintext to node logs before encryption/after decryption - (File: device.js)

### Summary
`ocore`'s device-messaging layer (`device.js`) unconditionally `console.log`s the complete JSON body of every device message it sends and every message it decrypts from a paired device. This mirrors CVE-2025-46808's bug class: sensitive application data is inserted into log output that is not meant to hold it.

### Finding Description
When a device prepares a message for a correspondent (peer or hub), the full plaintext `json` payload is logged before it is even encrypted: [1](#0-0) 

Symmetrically, when a device receives and decrypts an incoming package from a paired device, the fully decrypted message content is logged as well: [2](#0-1) 

These log lines are unconditional (no debug flag, no redaction) and fire for every device message type routed through `device.js`, including:
- Private payment chains sent via the `"private_payments"`/`"chain"` device-message types, which carry `blinding` factors, `output_hash`, `amount`, and `address` fields used to spend hidden indivisible/divisible-asset outputs (see how these fields are validated/consumed in `indivisible_asset.js`): [3](#0-2) 
- Multi-signature `"sign"` requests, which include `private_payloads` (blinding factors, outputs, and unsigned unit contents) exchanged between correspondent devices for co-signing: [4](#0-3) 

Because `deriveSharedSecret`/`decryptPackage` and `reliablySendPreparedMessageToHub` sit on the single code path used by every device-to-device exchange (pairing, chat, shared-address setup, AA-related contract messages, and private-payment forwarding), any correspondent device that a wallet is paired with can trigger these log statements simply by exchanging a routine encrypted message — no special privilege is required beyond being an accepted correspondent.

### Impact Explanation
Blinding factors and hidden output data are the confidentiality/soundness anchor of ocore's private (indivisible/divisible) assets: possession of the correct `blinding` value for an output is what lets a party later construct a valid `spend_proof` and reveal/spend that output (see `spend_proof` computation in `validatePrivatePayment`): [5](#0-4) . Persisting these values in plaintext application logs (which are frequently rotated, shipped to centralized logging/monitoring systems, attached to bug reports, or otherwise handled with weaker access control than the wallet's encrypted database) creates a durable side channel through which someone with log access — not just the paired counterparty — can learn private-payment secrets, enabling them to independently reconstruct and potentially race/double-spend a private output, or learn co-signing payloads for multisig transactions ahead of intended finalization.

### Likelihood Explanation
Any device paired with the victim wallet (a routine, low-privilege relationship intentionally supported by ocore's design) can send or receive an ordinary message that flows through this code, causing the sensitive content to be logged on every exchange — this happens automatically and continuously in normal operation, not only in an attack scenario, making exposure highly likely wherever logs are retained or exported.

### Recommendation
Remove or gate the plaintext logging in `reliablySendPreparedMessageToHub` (device.js:572) and `decryptPackage` (device.js:466) behind an explicit, opt-in debug flag, and redact/omit fields known to carry secret material (`blinding`, `private_payloads`, `outputs[].blinding`, unsigned-unit private payment data) even when such debug logging is enabled.

### Proof of Concept
1. Pair two wallets (device A and device B) as ordinary correspondents.
2. From device A, send a private (indivisible or divisible) asset payment to device B using the standard private-payment chain flow.
3. On device A's node, observe stdout/log output from `reliablySendPreparedMessageToHub` showing the full unencrypted JSON message, including the `blinding` and `output_hash` values of the private outputs, at device.js:572.
4. On device B's node, observe the `"decrypted: "+decrypted_message` log line at device.js:466 containing the same secret payload after decryption.
5. Anyone with read access to either node's logs (log aggregation service, crash dump, shared hosting logs, support ticket) now possesses the blinding factors needed to construct valid spend proofs for the private outputs, independent of the intended recipient's cooperation.
