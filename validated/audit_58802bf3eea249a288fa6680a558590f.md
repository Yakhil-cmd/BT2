### Title
Webhook signature verifies the sender's organization but never binds it to the repository whose data is mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate an incoming webhook's HMAC against by reading `repository_owner`, but every downstream `Webhooks::Handlers::Handler` subclass resolves the target `Repository`/`Stack` from a *different, independently-read* payload field (`repository.full_name`). Nothing ties these two values together, so a party who legitimately controls one GitHub organization's webhook secret in a multi-tenant Shipit deployment can forge a validly-signed webhook that mutates state belonging to an unrelated, victim organization's repository.

### Finding Description
`verify_signature` derives `repository_owner` from the payload and uses it purely to select which org's secret verifies the HMAC signature: [1](#0-0) [2](#0-1) 

That check only proves "this request was signed by whoever holds the `webhook_secret` for the organization named in `repository.owner.login`." It says nothing about which repository's data the request is allowed to affect.

Separately, `Shipit::Webhooks::Handlers::Handler` resolves the actual target repository/stacks from a different payload field, read independently of `repository_owner`: [3](#0-2) 

`PushHandler#process` then uses that unrelated-to-signing `stacks` scope to act on a stack chosen by branch name and to trigger a sync with an attacker-supplied `expected_head_sha`: [4](#0-3) 

`StatusHandler#process` is even less scoped — it looks up commits globally by `sha` with no repository/stack filter at all, and writes a GitHub-reported CI status onto whatever `Commit` row matches: [5](#0-4) [6](#0-5) 

Shipit explicitly supports multiple GitHub organizations configured with independent `webhook_secret`s in the same instance, as shown in the reference secrets template: [7](#0-6) 

The binding that should hold is: `organization authenticated by verify_signature via repository_owner == organization that owns the Repository whose Stack/Commit rows the handler mutates`. Because both sides are read from the same untrusted, single HMAC-signed JSON body but never cross-checked against each other, an attacker who legitimately owns one organization's `webhook_secret` (e.g., they run their own GitHub App installation registered on this Shipit instance, a normal unprivileged tenant capability) can set `repository.owner.login` to their own org (so `verify_signature` validates against their own secret) while setting `repository.full_name` to a victim organization's tracked repository (so the handler resolves and mutates the victim's `Stack`/`Commit` rows).

This is the multi-tenant analog of the reported "check happens on the wrong value" root cause: the check is performed against `repository.owner.login`, but the mutating effect is driven by `repository.full_name`/`sha`, and no code enforces they refer to the same repository/organization.

### Impact Explanation
The most damaging concrete path is `StatusHandler`: `Commit.where(sha: params.sha)` has no scoping by repository or stack at all, so a request that is validly signed under the attacker's own org's secret can flip the CI status of a victim commit (identified purely by its 40-hex SHA) to `success`, via `Commit#create_status_from_github!` / `Status.replicate_from_github!`. Commit deployability is gated by `Commit#deployable?`, which is satisfied once `success? && !blocked?`: [8](#0-7) 

Forging a passing status for a victim commit that never actually passed CI removes a required gate that legitimate deploy operators rely on before shipping a `sha` — i.e., it manufactures a false "deployable" signal for a repository/organization the attacker has no relationship to, feeding directly into an eventual unauthorized deploy decision. This satisfies the "authenticated org differs from repository written" trust-boundary break called out in scope, and the effect (poisoning the CI-status precondition that gates deploys) lands in the reward tier for "escalation ... an unauthorized deploy."

### Likelihood Explanation
Requires only: (1) this Shipit instance be configured for more than one GitHub organization (a documented, supported deployment mode, evidenced by the multi-org secrets template), and (2) the attacker legitimately controls the `webhook_secret` of any one of those configured organizations (their own tenant/org, not privileged Shipit credentials, no `ApiClient` token, no `GITHUB_TOKEN`). No signature bypass, no cryptographic weakness, and no interaction with any authenticated Shipit user is required — only crafting a JSON body whose `repository.owner.login` differs from `repository.full_name`, signed with a secret the attacker already legitimately possesses. This is a realistic, low-effort scenario for any multi-org Shipit deployment.

### Recommendation
After computing `repository_owner` in `verify_signature`, or before dispatching to handlers in `WebhooksController#create`, validate that the organization implied by `repository.full_name` (its owner segment) matches the `repository_owner` that was used to select the signing secret; reject the webhook otherwise. Additionally, scope `StatusHandler` (and any other handler that looks up records by `sha` alone) to the resolved `stacks`/`repository` instead of querying `Commit` globally, mirroring the scoping already used by `PushHandler` and the `PullRequest` handlers.

### Proof of Concept
1. Configure/observe a Shipit instance with two organizations, e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` layout). The attacker only needs to legitimately control `attacker-org`'s webhook secret (e.g. they administer their own GitHub App installed against Shipit for their own org).
2. Attacker crafts a raw JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-controlled commit sha>"
}
```
   or, to hit `StatusHandler`:
```json
{
  "repository": { "owner": { "login": "attacker-org" } },
  "sha": "<victim commit sha, known/public>",
  "state": "success"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_of_attacker-org, raw_body)>` themselves, since they legitimately hold `attacker-org`'s secret.
4. POST to `/webhooks` with header `X-Github-Event: push` (or `status`).
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the signature validates successfully — `app/controllers/shipit/webhooks_controller.rb:24-30`.
6. The dispatched handler ignores `repository.owner.login` entirely: `PushHandler` resolves stacks via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack; or `StatusHandler` writes a forged `success` status onto `Commit.where(sha: params.sha)` for the victim's commit (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), with no repository/organization cross-check ever performed.

This confirms the check (`verify_signature`/`repository_owner`) and the effect (`Repository`/`Commit` selected via `full_name`/`sha`) operate on unrelated payload fields, breaking the intended "authenticated organization == repository written" binding.
