### Title
Missing `return` after exception in `getBase64Hash` causes double invocation of the private-payment completion callback - ([File: network.js])

### Summary
`getBase64Hash()`/`getSourceString()` in `object_hash.js` can throw when handed a malformed `payload` object [1](#0-0) . In `network.js`, `handleSavedPrivatePayments()`'s inner `validateAndSave` catches this exception but fails to `return` from the `catch` block, so execution falls through into the normal validation path and the per-row completion callback `cb` ends up invoked twice for the same row — an analog of curl's CVE-2022-42915 pattern where a failed/erroring path does not properly abort before the normal cleanup/completion path also runs, leading to a double "free"/double-completion of the same resource.

### Finding Description
In `handleSavedPrivatePayments()`, each row from `unhandled_private_payments` is processed inside `async.each`, with `cb` being the per-item completion callback that `async.each` uses to track progress toward the final callback (which calls `unlock()` on the `"saved_private"` mutex) [2](#0-1) .

Inside `validateAndSave`, the code does:
```
try {
    var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
}
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ifOk: ..., ifError: ..., ifWaitingForChain: ... });
``` [3](#0-2) 

There is no `return` statement at the end of the `catch` block. `deleteHandledPrivateChain` is asynchronous — it schedules a DB `DELETE` and calls `cb()` only once that completes [4](#0-3) . Because the `catch` block does not return, execution *synchronously* continues past it to compute `key` (using the now-`undefined` `json_payload_hash`, since the assignment failed) and then calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, callbacks)`. That call eventually invokes one of `ifOk`, `ifError`, or `ifWaitingForChain`, every one of which itself calls `cb()` (directly, or via `deleteHandledPrivateChain(..., cb)`) [5](#0-4) .

The net effect: for a row whose head payload throws during hashing, `cb` for that `async.each` item gets scheduled to fire **twice** — once from the catch block's `deleteHandledPrivateChain`, and again from whichever outcome branch of `validateAndSavePrivatePaymentChain` fires. This is the "double free"/double-completion class of bug: an error path fails to short-circuit before falling into the same completion/cleanup routine that the success path also triggers.

### Impact Explanation
`async.each`'s internal completion counter is decremented once per `cb()` call it expects per item; a duplicate `cb()` call for the same item causes the aggregate completion callback (which calls `unlock()` on the `"saved_private"` mutex and emits `new_my_transactions`) to fire prematurely, before all other private-payment rows in the batch have actually finished being validated/cleaned up [6](#0-5) . Because the mutex is released early, `handleSavedPrivatePayments` can be re-entered concurrently (it is called repeatedly on `saved_unit`/other triggers) while the first pass's DB operations (including inserts of private outputs performed inside `validateAndSavePrivatePaymentChain` → `divisibleAsset`/`indivisibleAsset` `validateAndSavePrivatePaymentChain`) are still pending on other rows. This creates a race window where the same private-payment row can be processed by two overlapping invocations, risking duplicate insertion of the same private outputs (double-crediting a private payment to the wallet) or corrupting the `unhandled_private_payments` cleanup bookkeeping, since one caller's cleanup can race with another's still-in-flight validation of the identical row.

This also silently proceeds to run full-blown chain validation/saving (`validateAndSavePrivatePaymentChain`) with a payload that already threw during hashing — an unexpected/undefined-hash object being pushed further into the persistence pipeline instead of being cleanly rejected.

### Likelihood Explanation
Reaching this path only requires a private-payment counterparty (a paired device or peer) to send a private-payment chain whose head element's `payload` is structured in a way that makes `getSourceString`/`getJsonSourceString` throw (e.g. payload containing values `getSourceString` does not support, such as `undefined`, functions, or other JSON-source-string-incompatible types) [1](#0-0) . Any wallet or hub that stores such a chain in `unhandled_private_payments` and later calls `handleSavedPrivatePayments()` will trigger the double-callback path. This does not require malicious network/hub compromise — a private-payment counterparty (in scope) crafting a malformed private-payment payload is sufficient to trigger it.

### Recommendation
Add a `return` statement at the end of the `catch` block in `validateAndSave` (network.js) so that after `deleteHandledPrivateChain(..., cb)` is scheduled, execution does not continue into computing `key` and calling `privatePayment.validateAndSavePrivatePaymentChain`. This ensures the completion callback for that row is invoked exactly once, matching the single-invocation contract expected by `async.each`.

### Proof of Concept
1. As a paired device / private-payment counterparty, send (or have stored via the hub-relay device-message flow) a private-payment chain whose head element's `payload` is well-formed enough to pass earlier structural checks but contains a value that makes `getSourceString`/`getJsonSourceString` throw when computing its hash (e.g., a payload field containing `undefined` or another type unsupported by the source-string serializer used in `getBase64Hash`).
2. Ensure this row lands in the `unhandled_private_payments` table together with at least one other pending, valid private-payment row for the same wallet.
3. Trigger `handleSavedPrivatePayments()` (called automatically on relevant events, e.g. `saved_unit`).
4. Observe: the malformed row's `cb()` is scheduled twice (once via the `catch` block's `deleteHandledPrivateChain`, once via whichever `ifOk`/`ifError`/`ifWaitingForChain` branch fires from the fallthrough call to `validateAndSavePrivatePaymentChain`), causing `async.each`'s final callback (and `unlock(["saved_private"])`) to run before the other pending row(s) have finished being validated/cleaned up — creating a window for concurrent re-entrant processing of the same still-pending private-payment row.

*Note:* I could not fully trace the exact downstream SQL insert path within `divisible_asset.js`/`indivisible_asset.js`'s `validateAndSavePrivatePaymentChain` to confirm whether the race concretely permits a duplicate-output insert versus being caught by unique constraints; this would benefit from a live/dynamic trace to confirm the exact severity of the resulting duplication.
