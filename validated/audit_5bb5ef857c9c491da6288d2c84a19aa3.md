### Title
`review_stacks_enabled` is only enforced in the first disjunct of `OpenedHandler#provision?`, allowing review-stack provisioning while the feature is disabled - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Repository#review_stacks_enabled` is intended to be the master switch for the review-stack feature, but `OpenedHandler#provision?` (and the sibling `LabeledHandler`/`ReopenedHandler`/`UnlabeledHandler`) only ANDs it with the first disjunct (`provisioning_behavior_allow_all?`). The two remaining disjuncts (`allow_with_label`/`prevent_with_label`) never check `review_stacks_enabled` at all, so with `review_stacks_enabled == false` a repository left on `allow_with_label` (with a known/guessed label) or `prevent_with_label` (trivially, by omitting the label) will still provision a `ReviewStack` for any opened PR.

### Finding Description
Broken binding as claimed: `review_stacks_enabled` == the authoritative gate for all provisioning, but the code only implements:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Due to Ruby operator precedence (`&&` binds tighter than `||`), this parses exactly as written with implicit parens: `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. So the first disjunct is correctly gated by `review_stacks_enabled`, confirming that particular branch is not vulnerable in isolation — but disjuncts two and three are entirely independent of `review_stacks_enabled`.

`provisioning_behavior` is a plain enum with three values and defaults from a migration/schema value, not derived from `review_stacks_enabled`: [2](#0-1) 

Exploit flow: An attacker who can open a pull request against a repository configured with `review_stacks_enabled = false` and `provisioning_behavior = allow_with_label` (or `prevent_with_label`) can:
- For `allow_with_label`: add the label matching `repository.provisioning_label_name` (visible/discoverable via the repository settings UI at `app/views/shipit/repositories/settings.html.erb`, not a secret) to their own PR.
- For `prevent_with_label`: simply open the PR without any label at all — the default state.

`respond_to_pull_request_opened?` then returns true and `process` calls `ReviewStackAdapter#find_or_create!`, which creates a real `Shipit::ReviewStack` (a `Stack` subtype) with attacker-controlled `branch` (the PR's head ref) and `environment` derived from the PR number: [3](#0-2) 

No other guard intervenes: `respond_to_pull_request_opened?` only checks `params.action == "opened"` before calling `provision?`; there's no additional `review_stacks_enabled` check elsewhere in the handler chain, so once GitHub's real signed webhook for a genuine "opened" PR event arrives, the flawed OR-chain alone decides provisioning.

### Impact Explanation
This creates unauthorized `ReviewStack`/`Stack` records (and queues them for provisioning) for a repository whose administrator explicitly disabled review stacks (`review_stacks_enabled = false`), believing that flag to be authoritative. Once queued via `Shipit::ReviewStackProvisioningQueue.add`, downstream provisioning jobs will act on attacker-controlled branch/environment data. This is scoped as Critical per the impact matrix: a record (stack) is written for a repository based on attacker input that should have been blocked by the repository's own disabled-feature configuration, potentially leading into deploy/provisioning of attacker-controlled branches.

### Likelihood Explanation
Preconditions: a repository must exist with `review_stacks_enabled = false` and `provisioning_behavior` left at its default/residual value of `allow_with_label` or `prevent_with_label` rather than being reset alongside disabling the feature. This is a plausible, low-cost misconfiguration since `review_stacks_enabled` and `provisioning_behavior` are independent fields with no validation coupling them (no callback/validation found tying `provisioning_behavior` to `allow_all` when `review_stacks_enabled` is false). Given that precondition, exploitation costs the attacker nothing beyond opening a PR (and optionally adding a label they can see in the repo settings page) — no secrets, tokens, or elevated roles are required, and it is fully repeatable across any repository in this misconfigured state.

### Recommendation
Change `provision?` to require `repository.review_stacks_enabled` as a top-level AND across the entire disjunction, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to the equivalent logic in `LabeledHandler`, `UnlabeledHandler`, and `ReopenedHandler` if they share this pattern.

### Proof of Concept
minitest matrix in a handler test (e.g. `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
```ruby
[:allow_all, :allow_with_label, :prevent_with_label].each do |behavior|
  test "does not provision when review_stacks_enabled=false and provisioning_behavior=#{behavior}" do
    repository = shipit_repositories(:shipit).tap do |r|
      r.update!(review_stacks_enabled: false, provisioning_behavior: behavior)
    end
    payload = pull_request_opened_payload(repository: repository, labels: behavior == :allow_with_label ? [repository.provisioning_label_name] : [])

    assert_no_difference -> { Shipit::ReviewStack.count } do
      Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(payload).process
    end
  end
end
```
Before the fix, this assertion fails for `allow_with_label` and `prevent_with_label` (a `ReviewStack` is created), while it correctly passes for `allow_all`, confirming the binding is only honored on the first disjunct.
