Based on my research, I found a concrete analog of the reported bug class in `Shipit::WebhooksController`.

### Title
Webhook signature verification is scoped by an unverified organization derived from the payload, allowing cross-repository forged events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The external report describes a bug where a value used to drive a critical operation (shares minted / assets redeemed) is taken from unverified, attacker-influenced storage rather than being derived from the verified input. In Shipit, `WebhooksController#verify_signature` selects which GitHub App/secret to check the request signature against using `repository_owner`, a value pulled directly out of the *unverified* JSON body, before the signature has been validated at all.

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) 

`repository_owner` is read straight from the untrusted payload: [2](#0-1) 

`Shipit.github(organization:)` looks up the app config purely by this attacker-supplied string: [3](#0-2) 

Because the org used to select the verification secret is untrusted, and downstream handlers such as `PushHandler` only scope by branch name (not by verified repository identity): [4](#0-3) 

an attacker who legitimately controls a repository/webhook secret in *one* configured GitHub organization can submit a request whose `repository.owner.login` field matches their own org (so their real secret validates it), while the JSON body's actual `repository.full_name`/branch fields are crafted to reference a different stack. Since the equality the code should enforce is:

`organization used to verify signature == organization owning the repository actually acted upon`

the code instead only enforces "the attacker knows *a* valid secret for *some* configured org," and lets the payload body — including branch and repo fields consumed by handlers — go unchecked against that org.

### Impact Explanation
This can let a holder of one organization's legitimate webhook secret trigger sync/push jobs (`GithubSyncJob`) for a stack belonging to a different repository/org whose branch name happens to match, potentially causing unintended deploy-triggering sync activity, membership creation (`MembershipHandler`), or status writes (`StatusHandler`) not scoped to the org that was actually cryptographically verified. This falls into the "cross-repository writes" / "unauthorized deploy" impact category since it can affect stacks outside the actor's own repository scope, provided the target stack shares a tracked branch name.

### Likelihood Explanation
Exploitation requires the attacker to already control a legitimate webhook secret for at least one configured GitHub organization in a multi-org Shipit deployment (as documented in `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`). This is a real, supported and documented configuration, but requires the specific multi-org setup and a coincidental/targeted branch-name match, making this a moderate-likelihood, configuration-dependent issue rather than a universally exploitable one.

### Recommendation
After signature verification succeeds, verify that the `repository.owner.login` (or `organization.login`) actually used to select the webhook secret matches the repository/stack that handlers subsequently act upon, rather than trusting the payload-derived org purely as a secret-selection key with no post-verification binding check.

### Proof of Concept
Conceptual, requires a live multi-org deployment to fully validate:
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct webhook secrets (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who owns a webhook endpoint for `OrgA`, craft a JSON push payload where `repository.owner.login = "OrgA"` (to pass verification with the known `OrgA` secret) but `repository.full_name` and `ref` are set to reference a stack that actually belongs to `OrgB`.
3. Sign the payload with the `OrgA` secret and send it to `/webhooks` with `X-Github-Event: push`.
4. Because `PushHandler#process` filters stacks only by branch name derived from the payload (not the verified org), a stack under `OrgB` sharing that branch name will have `sync_github` invoked. [5](#0-4) 

I was not able to directly view `app/models/shipit/webhooks/handler.rb` (base class) or the `status_handler.rb`/`check_suite_handler.rb` files in this final pass due to tool errors, so I cannot fully confirm whether the base `Handler` class independently re-derives and checks the repository/organization binding elsewhere before dispatching to individual handlers. This is a gap in verification — a Devin session with full file access would be needed to confirm whether any such binding check exists in `Handler` itself, which could mitigate or entirely negate this finding.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
