## Analysis Summary

Reducing the external report to its core invariant: **a value/commitment that is supposed to gate admission must actually be checked at the point where the transaction is accepted for execution** — not merely computed and left dangling. I traced this pattern through Aptos's newer `EncryptedPayload` transaction flow (mempool/consensus/VM), since it is the closest local analog to an "oracle-style" value that must be verified before being trusted.

### Candidates considered
1. WebAuthn / `PartialAuthenticatorAssertionResponse::verify` — public key / challenge binding is checked correctly; rejected.
2. `TransactionAuthenticator::FeePayer::verify` zero-address vs real-address dual-message logic — intentional documented behavior, not a bug; rejected.
3. `transaction_validation.move` sequence/chain-id/expiration/nonce checks — all enforced consistently; rejected.
4. **`EncryptedPayload` sender/signer binding (`PayloadAssociatedData`) never checked during decryption/admission** — kept as strongest candidate, with local proof below.

### Title
Sender/signer binding committed at encryption time is never verified during decryption, breaking the encrypted-transaction admission invariant - (File: `consensus/src/pipeline/decryption_pipeline_builder.rs`)

### Summary
Encrypted transactions bind `(sender, signer_auth_keys)` into the ciphertext's associated data at build time via `TransactionBuilder::encrypt_payload`, and `EncryptedPayload::verify` exists specifically to re-check that binding. However, the decryption pipeline that transitions a payload from `Encrypted` to `Decrypted` (and thus admits it for execution) never calls this verification — it only checks a payload hash of the plaintext executable, not the sender/signer identity that was cryptographically committed.

### Finding Description
At encryption time, the SDK binds the transaction's sender and every signer's `(address, auth_key)` pair into the ciphertext's associated data: [1](#0-0) 

`EncryptedPayload` exposes an explicit `verify` method whose stated purpose is to re-derive this associated data from the current transaction context and check it against the ciphertext: [2](#0-1) 

Decryption is performed with no associated-data argument at all — `do_final_decryption` calls `FPTXWeighted::decrypt(decryption_key, &prepared_ciphertext_or_error)`, and the only post-decryption admission check is `try_into_decrypted`, which validates solely the `payload_hash` (a hash of the decrypted executable + nonce) and, optionally, `claimed_entry_fun`: [3](#0-2) [4](#0-3) 

Neither `payload_hash` nor `claimed_entry_fun` says anything about which account is the intended sender or which set of signers were supposed to authorize the transaction. The one function designed to check that (`EncryptedPayload::verify`, taking `sender: AccountAddress, signer_auth_keys: Vec<(AccountAddress, AuthenticationKey)>`) has no caller anywhere in the decryption pipeline or in the AptosVM prologue path — a repo-wide search for its invocation only turns up its own definition and unrelated references, with no call site wiring the current `raw_txn.sender()` / `TransactionAuthenticator::all_signer_auth_keys()` into it before or during admission.

`TransactionAuthenticator::all_signer_auth_keys` exists precisely to reconstruct the `(address, auth_key)` list needed for this check: [5](#0-4) 

but it is likewise not invoked to feed `EncryptedPayload::verify` at any admission point I could find.

Signature verification itself (`TransactionAuthenticator::verify` / `as_encrypted_variant`) only covers `sender`, `sequence_number`, `max_gas_amount`, `gas_unit_price`, `expiration_timestamp_secs`, `chain_id`, and the *encrypted* payload wrapper (ciphertext + payload_hash + epoch) — never the plaintext executable or the AAD-committed signer set: [6](#0-5) 

So the only cryptographic tie between "who is allowed to submit/execute this decrypted payload" and "what the ciphertext was actually encrypted for" is the AAD check in `EncryptedPayload::verify` — and that function is dead code with respect to the admission path.

### Impact Explanation
If the underlying `FPTXWeighted` scheme's `decrypt` does not itself authenticate against the associated data (its signature, `decrypt(decryption_key, ciphertext)`, takes no AAD parameter, consistent with this), an encrypted payload can be decrypted and admitted for execution without any check that the *current* `RawTransaction.sender` and its authenticator's signer set match what was committed to at encryption time. Since `sender`, `sequence_number`, `gas`, `expiration`, and `chain_id` all live outside the ciphertext and are independently signed, an attacker with knowledge of a ciphertext/`payload_hash` pair (e.g., observed on the network before decryption) could in principle wrap it in a new `RawTransaction` with a different `sender`/`fee_payer`/secondary-signer set, sign it themselves, and have it decrypt and execute successfully as long as `payload_hash` still matches — since nothing at admission time checks that the ciphertext was ever bound to *that* sender/signer combination. This is a broken sender/signer binding invariant at the transaction-admission boundary and can result in a transaction executing/committing under a signer set the encrypting party never authorized.

### Likelihood Explanation
This requires the encrypted-transactions feature to be enabled (`FeatureFlag::ENCRYPTED_TRANSACTIONS`) and depends on whether `FPTXWeighted::decrypt` performs any implicit AAD authentication internal to `aptos-batch-encryption` that isn't visible from the caller's signature. I could not fully inspect the internals of `crates/aptos-batch-encryption/src/shared/ciphertext/mod.rs`'s cryptographic guarantees within the scope of this review, so I cannot be fully certain whether the missing call to `EncryptedPayload::verify` is fully exploitable or merely a defense-in-depth check that's redundant with scheme-level AAD authentication baked into the ciphertext format itself. Given that `verify()` exists as a distinct, purpose-built method taking exactly the encryption-time AAD inputs, and is never called at the one place (`try_into_decrypted`) where the state transition to "admitted/decrypted" happens, this looks like an intended check that was not wired up.

### Recommendation
Call `EncryptedPayload::verify(sender, signer_auth_keys)` — using `raw_txn.sender()` and `TransactionAuthenticator::all_signer_auth_keys()` computed from the *currently admitted* `SignedTransaction` — before or as part of `try_into_decrypted`, and reject with a new `DecryptionFailureReason` (e.g., `AssociatedDataMismatch`) on failure, mirroring how `PayloadHashMismatch` and `ClaimedEntryFunctionMismatch` are already handled.

### Proof of Concept
Not fully constructible without access to `aptos-batch-encryption`'s internal AEAD/authentication guarantees, which were outside what I could verify via the indexed code. The code-level gap is demonstrable by inspection:
1. `sdk/src/transaction_builder.rs` binds `(sender, signer_auth_keys)` into the ciphertext AAD at encryption (`EncryptedPayload::verify` is the intended check-back function).
2. `consensus/src/pipeline/decryption_pipeline_builder.rs::do_final_decryption` → `try_into_decrypted` never calls `EncryptedPayload::verify`, nor does any other file in the indexed codebase.
3. `TransactionAuthenticator::verify` never touches the plaintext executable or signer-AAD binding either.

A background Devin agent with full repo/build access should confirm whether `FPTXWeighted::decrypt` itself authenticates against AAD before treating this as exploitable versus a missing defense-in-depth check.

    /// Encrypts a transaction payload using the provided encryption key.
    /// This is a helper method used internally by `with_encrypted_payload` and `payload`.
    fn encrypt_payload(
        payload: TransactionPayload,
        sender: AccountAddress,
        signer_auth_keys: Vec<(AccountAddress, AuthenticationKey)>,
        encryption_key: &EncryptionKey,
        encryption_epoch: u64,
    ) -> Result<EncryptedPayload> {
        // Convert payload to executable
        let executable = payload.executable()?;
        let extra_config = payload.extra_config();

        // Generate decryption nonce
        let decryption_nonce: DecryptionNonce = rand::random();

        // Create DecryptedPayload for encryption
        let decrypted_payload = DecryptedPlaintext::new(executable, decryption_nonce);

        let associated_data = PayloadAssociatedData::new(sender, signer_auth_keys);

        // Encrypt the payload
        // Note: FPTXWeighted::encrypt requires CryptoRng from ark_std::rand, so we use StdRng
        let mut rng = StdRng::from_entropy();
        let ciphertext = FPTXWeighted::encrypt(
            encryption_key,
            &mut rng,
            &decrypted_payload,
            &associated_data,
        )?;

        // Compute payload hash from the executable
        // We need to compute hash before encryption, so we use the executable directly
        let payload_hash = CryptoHash::hash(&decrypted_payload);

        // Create encrypted payload
        Ok(EncryptedPayload::Encrypted(EncryptedInner {
            ciphertext,
            extra_config,
            payload_hash,
            encryption_epoch,
            claimed_entry_fun: None,
        }))
    }

    /// Verify the decrypted plaintext against the stored commitments and, on success,
    /// transition `self` to `Decrypted`. On mismatch, `self` is left as `Encrypted` and the
    /// failure reason is returned so the caller can mark the payload failed.
    pub fn try_into_decrypted(
        &mut self,
        eval_proof: EvalProof,
        plaintext: DecryptedPlaintext,
    ) -> Result<(), DecryptionFailureReason> {
        let Self::Encrypted(original) = self else {
            panic!("try_into_decrypted called on non-Encrypted state");
        };

        if original.payload_hash != CryptoHash::hash(&plaintext) {
            return Err(DecryptionFailureReason::PayloadHashMismatch);
        }

        if let Some(claim) = &original.claimed_entry_fun {
            let TransactionExecutable::EntryFunction(entry_fun) = plaintext.executable() else {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            };
            if *entry_fun.module() != claim.module {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
            if let Some(claimed_function_id) = &claim.function
                && entry_fun.function() != claimed_function_id.as_ident_str()
            {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
        }

        *self = Self::Decrypted {
            original: original.clone(),
            eval_proof,
            decrypted: plaintext,
        };
        Ok(())
    }

    /// Collect `(address, auth_key)` pairs for every signer in the transaction,
    /// in deterministic order: sender, then secondary signers, then fee payer.
    /// Returns `None` if any signer uses an authenticator incompatible with
    /// encrypted transactions (keyless, abstract auth, etc.).
    pub fn all_signer_auth_keys(
        &self,
        sender_address: AccountAddress,
    ) -> Option<Vec<(AccountAddress, AuthenticationKey)>> {
        let mut result = Vec::new();

        let sender_auth = self.sender();
        if !sender_auth.supports_encrypted_txn() {
            return None;
        }
        result.push((sender_address, sender_auth.authentication_key()?));

        let secondary_addresses = self.secondary_signer_addresses();
        let secondary_auths = self.secondary_signers();
        if secondary_addresses.len() != secondary_auths.len() {
            return None;
        }
        for (addr, auth) in secondary_addresses.into_iter().zip(secondary_auths.iter()) {
            if !auth.supports_encrypted_txn() {
                return None;
            }
            result.push((addr, auth.authentication_key()?));
        }

        if let (Some(fee_payer_addr), Some(fee_payer_auth)) =
            (self.fee_payer_address(), self.fee_payer_signer())
        {
            if !fee_payer_auth.supports_encrypted_txn() {
                return None;
            }
            result.push((fee_payer_addr, fee_payer_auth.authentication_key()?));
        }

        Some(result)
    }

    /// This is needed because signatures are verified over the executable, not the encrypted ciphertext.
    pub fn as_encrypted_variant(&self) -> Cow<'_, Self> {
        match &self.payload {
            TransactionPayload::EncryptedPayload(EncryptedPayload::Decrypted {
                original, ..
            })
            | TransactionPayload::EncryptedPayload(EncryptedPayload::FailedDecryption {
                original,
                ..
            }) => Cow::Owned(RawTransaction {
                sender: self.sender,
                sequence_number: self.sequence_number,
                payload: TransactionPayload::EncryptedPayload(EncryptedPayload::Encrypted(
                    original.clone(),

                gas_unit_price: self.gas_unit_price,
                expiration_timestamp_secs: self.expiration_timestamp_secs,
                chain_id: self.chain_id,
            }),
