### Title
Missing cosigner verification allows any correspondent device to request signing on shared/multisig addresses - (File: wallet.js)

### Summary
CVE-2019-20145 describes an "Incorrect Access Control" flaw in GitLab. The analogous weakness in ocore is in the device-message handler for the `"sign"` subject in `handleMessageFromHub`, where the check that the requesting device is actually an authorized cosigner of the target address has been explicitly commented out, leaving any known correspondent device free to trigger signing prompts for addresses it does not control.

### Finding Description
In `wallet.js`, the `"sign"` case of `handleMessageFromHub`/`doHandle` processes device messages of the form `{address, signing_path, unsigned_unit}` sent from another paired device, intended for multisig/multilateral signing flows. [1](#0-0) 

After validating the shape of the unsigned unit and (optionally) private payloads, the code resolves the address via `findAddress(body.address, body.signing_path, {...})`. In the `ifLocal` branch, the verification that the sender device is actually a legitimate cosigner of `body.address` (via `extended_pubkeys`/`my_addresses` for the given wallet) is explicitly commented out: [2](#0-1) 

Instead, `callbacks.ifOk()` is called and a `"signing_request"` event is emitted directly, exposing the unsigned unit (and any embedded private payment payloads) to the front end/UI for the user to sign, without server-side confirmation that the requesting device is actually one of the addresses' registered signers. The only real gating is that the *address itself* resolves locally (`findAddress` -> `ifLocal`), which is a property of the recipient's wallet database, not of the sender's authorization to request a signature from that particular address's cosigner set.

This differs from the correct model used elsewhere in the codebase (e.g. `wallet_defined_by_keys.js`'s `readDeviceAddressesControllingPaymentAddresses`, which explicitly queries `my_addresses JOIN extended_pubkeys` to establish which devices legitimately control a payment address before forwarding private payment chains) — that pattern is present for private-payment forwarding but is missing/disabled for the interactive `"sign"` request path. [3](#0-2) 

### Impact Explanation
Because any correspondent (paired) device — including one added via a normal pairing flow, not necessarily a true cosigner — can send arbitrary `"sign"` requests naming any locally-hosted shared/multisig address and any `signing_path`, it can:
- Spam the victim's wallet UI with attacker-crafted signing prompts for units the attacker fully controls (including outputs/amounts), potentially tricking a careless or automated (headless) signer into approving a payment that benefits the attacker, causing unauthorized spending from the shared address.
- Exfiltrate/probe wallet-internal state indirectly, since the flow proceeds to emit `"signing_request"` with the full unsigned unit and any private payloads embedded in the request, even though the requester was never confirmed to be part of that address's cosigner set.
This maps to the "concrete unauthorized spending" / "AA-adjacent fund loss" impact class required by the validation rubric, since a shared address's spending policy relies on genuine multi-party consent, and the missing check erodes the access boundary between "any correspondent" and "actual cosigner."

### Likelihood Explanation
Reachability requires only that the attacker's device be an already-known correspondent of the victim (a normal, low-friction pairing interaction, not requiring any special trust), then send a crafted `hub/message` with `subject: "sign"` referencing the victim's shared address, which the attacker can learn from any prior interaction (e.g., appearing as a member of a shared/multisig address, or being told the address for legitimate reasons unrelated to being a signer). No cryptographic keys or hub/node compromise are needed — this is reachable purely as an unprivileged device sending a device message, matching the "paired device" reachable-actor class in scope.

### Recommendation
Re-enable (or reimplement) the cosigner-authorization check before proceeding with an `ifLocal` `"sign"` request: query `my_addresses`/`extended_pubkeys` (or the shared-address signing-paths table) to confirm `from_address` is actually a device authorized to co-sign `body.address` for the given `signing_path`, and reject the request (`callbacks.ifError("sender is not cosigner of this address")`) otherwise, mirroring the authorization pattern already used in `wallet_defined_by_keys.readDeviceAddressesControllingPaymentAddresses`.

### Proof of Concept
1. Attacker pairs with victim's device as a normal correspondent (standard pairing flow, no special privilege).
2. Attacker learns (or guesses/observes) one of victim's shared/multisig addresses `A` and a valid `signing_path` for it (addresses and paths are not secret and can be observed from any shared chat/contract context).
3. Attacker crafts an `unsigned_unit` with attacker-favorable payment outputs and sends a `hub/message` with `subject: "sign"`, `body: {address: A, signing_path, unsigned_unit}` to the victim's device.
4. On the victim's node, `handleMessageFromHub` processes this in the `"sign"` case; `findAddress(A, signing_path, {...})` resolves `ifLocal` because `A` is hosted locally; the disabled cosigner check at wallet.js:335-338 means `callbacks.ifOk()` is called and `"signing_request"` is emitted immediately, presenting the attacker's crafted unit to the victim's signing UI as if it were a legitimate cosigning request — with no verification that the attacker device is actually part of `A`'s cosigner set. [4](#0-3)
