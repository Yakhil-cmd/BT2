### Title
`NonTransfer` proxy on Polkadot/Westend/Rococo (and staking-async `rc`) relay-chain runtimes falsely declares itself a superset of `Auction`, letting a limited-scope proxy escalate to the unrestricted `Registrar::swap` call it explicitly denies - ([File: polkadot/runtime/westend/src/lib.rs])

### Summary
The Keystone CVE's invariant is "a credential created within a limited scope must not be able to acquire permissions broader than that scope." The FRAME analog is `pallet_proxy`'s `InstanceFilter::is_superset`, which `do_proxy` uses to gate `add_proxy`/`remove_proxy` calls made *through* an existing proxy relationship [1](#0-0) . This exact bug class — a proxy type claiming `is_superset` over another type whose `filter` admits calls the claiming type's own `filter` denies — was already found and fixed for `asset-hub-westend`'s `NonTransfer`/`Governance` pair in PR #12769 [2](#0-1) , with a regression test and a lattice-wide invariant test added afterward [3](#0-2) .

The same pattern is still present, unfixed, in the Polkadot/Westend/Rococo relay-chain runtimes and `staking-async/rc`: `NonTransfer.is_superset` returns `true` for every other `ProxyType` except `Any` [4](#0-3) , while `NonTransfer.filter` explicitly and deliberately excludes `Registrar::swap` ("Specifically omitting Registrar `swap`") [5](#0-4) . Yet `ProxyType::Auction.filter` admits the *entire, unrestricted* `Registrar` call family, including `swap` [6](#0-5) . The identical pattern exists in Rococo [7](#0-6)  and in `substrate/frame/staking-async/runtimes/rc/src/lib.rs` [8](#0-7) .

### Finding Description
`pallet_proxy::do_proxy` only blocks a delegate from adding/removing a proxy of a *broader* type by checking `def.proxy_type.is_superset(proxy_type)` [1](#0-0) . This check is purely declarative (a hand-written lattice) and is not derived from, nor cross-checked against, the `filter` predicate that actually enforces per-call permissions. When a `ProxyType` variant's `is_superset` implementation over-claims (declares itself a superset of a type whose `filter` admits a call the claimer's own `filter` denies), a delegate holding only the narrower type can:
1. Call `Proxy::add_proxy(real, delegate_or_self, ProxyType::Auction, 0)` on behalf of `real` — permitted because `NonTransfer.is_superset(Auction) == true`.
2. Then call `Proxy::proxy(real, None, RuntimeCall::Registrar(paras_registrar::Call::swap { .. }))` using the newly created `Auction` proxy relationship — permitted because `Auction.filter` admits unrestricted `RuntimeCall::Registrar(..)`.

This reaches exactly the call (`Registrar::swap`) that `real`'s original `NonTransfer` grant intentionally withheld from the delegate, as shown by the explicit comment denying it in the `NonTransfer` arm [5](#0-4) . This mirrors the already-acknowledged root cause in `asset-hub-westend`'s prior bug: `is_superset` claims containment that `filter` does not actually provide [9](#0-8) .

### Impact Explanation
`Registrar::swap` is treated by the runtime authors as sensitive enough to be deliberately excluded from `NonTransfer` even though other Registrar operations (`register`, `deregister`, `reserve`) are allowed — this signals that `swap` carries risk the delegator did not intend to expose to a limited proxy (e.g., silently exchanging para IDs/deposits/lease positions between parachains a manager controls). A limited-scope delegate escalating to it violates the confused-deputy/least-privilege guarantee `pallet_proxy` is supposed to provide, comparable in class (though narrower in blast radius, since it needs `real` to already be a parachain manager) to the Keystone issue where a limited-scope credential could mint one with admin-equivalent power.

### Likelihood Explanation
Reachable by any account that has granted (or been granted) a `NonTransfer` proxy — a completely ordinary, unprivileged, user-controlled configuration; no governance, sudo, or stolen keys are required. The two calls (`add_proxy` then `proxy`) are both standard signed extrinsics with normal fees. The only precondition is that `real` is a registered parachain manager, which is a legitimate scenario `paras_registrar` and the `Auction`/`ParaRegistration` proxy types are explicitly designed to support.

### Recommendation
Apply the same fix pattern used in PR #12769 to `polkadot/runtime/westend`, `polkadot/runtime/rococo`, and `substrate/frame/staking-async/runtimes/rc`: either (a) remove `Auction` (and any other over-claimed subset) from `NonTransfer.is_superset`'s wildcard arm, or (b) restrict `ProxyType::Auction`'s filter to the same `Registrar` subset (`register`/`deregister`/`reserve`) that `NonTransfer` itself allows, denying `swap`. Longer term, add the lattice-wide invariant test (`superset` implies `filter` containment) that was added for `asset-hub-westend` [3](#0-2)  to these relay-chain runtimes as well, so this bug class cannot silently reappear.

### Proof of Concept
Not executed. Conceptual repro path for a background agent/researcher using the existing `pallet_proxy`/`paras_registrar` test harnesses in `polkadot/runtime/westend` (or Rococo):
1. Fund account `A` (manager of registered para `P`) and account `B`.
2. `Proxy::add_proxy(origin=A, delegate=B, proxy_type=ProxyType::NonTransfer, delay=0)`.
3. As `B`: `Proxy::proxy(origin=B, real=A, force_proxy_type=Some(NonTransfer), call=Proxy::add_proxy{delegate: B, proxy_type: ProxyType::Auction, delay:0})` — expect `Ok`, confirming escalation add succeeds (should fail if fixed).
4. As `B`: `Proxy::proxy(origin=B, real=A, force_proxy_type=Some(Auction), call=Registrar::swap{ id: P, other: P2, .. })` — expect the call to dispatch (not `CallFiltered`), demonstrating `B` executed `swap` on `A`'s behalf despite `NonTransfer` explicitly denying it.

I could not fully verify within the available tool budget the exact internal origin/authorization check performed inside `paras_registrar::Pallet::swap` (i.e., whether it requires `A` to already be the para's manager, or has additional root/paired-swap requirements) — this should be confirmed by reading `polkadot/runtime/common/src/paras_registrar/mod.rs` before finalizing severity, since it determines the real-world precondition (para-manager status) and blast radius of the escalation.
