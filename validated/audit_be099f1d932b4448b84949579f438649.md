### Title
Off-chain signed messages (`is_valid_signed_package`, contract/device signatures) lack any chain/network-binding field, enabling cross-network signature replay - ([File: signed_message.js])

### Summary
Obyte's `signed_message` format — used by `signMessage()`/`validateSignedMessage()` in `signed_message.js` and exposed to oscript via `is_valid_signed_package()` — has no mandatory field that binds a signature to a specific network/chain instance (mainnet, testnet, devnet, or any other ocore-based fork). Unlike full DAG units, whose hash-to-sign implicitly includes network-specific data through `constants.alt`/`constants.version` embedded in the unit object, a `signed_message` package can validly omit `version` and `last_ball_unit` entirely, leaving the signed content and its hash identical across every ocore deployment that shares the same address-derivation scheme. This is the same class of bug as the reported ERC20Permit chain-ID issue: the signature scheme has no domain separator distinguishing one chain instance from another, so a signature legitimately produced on one network can be replayed on another.

### Finding Description
`signMessage()` builds an unsigned package containing only `version`, `signed_message`, `authors`, and optionally `last_ball_unit` (only when `bNetworkAware` is requested): [1](#0-0) 

`validateSignedMessage()` accepts a much smaller whitelist of fields and treats `version` and `last_ball_unit` as fully optional: [2](#0-1) [3](#0-2) 

When `last_ball_unit` is absent, `bNetworkAware` is `false` and the code falls back to validating the embedded `definition` with no reference at all to this chain's ledger state: [4](#0-3) 

The hash that is actually signed, `getSignedPackageHashToSign()`, only strips `authentifiers`; it does not add any per-network salt, genesis-unit id, or chain identifier: [5](#0-4) 

Compare this with full DAG units, where `constants.version`/`constants.alt` are mandatory unit fields and differ per network (mainnet `"4.0"`/`"1"`, testnet `"4.0t"`/`"2"`, devnet `"4.0dev"`/`"3"`), and `constants.supported_versions` differs per network too: [6](#0-5) [7](#0-6) 

For a full unit, an alien-network unit would fail version/alt checks. For a `signed_message`, however, `version` is optional (`"version" in objSignedMessage` check is skipped entirely if absent), and there is no `alt`/network field in the whitelist at all, so nothing prevents a package with the exact same `signed_message` content and `authors`/`authentifiers` from validating identically on any ocore-based network that shares the address's definition.

This signed-message primitive is directly reachable by an unprivileged AA trigger sender through the oscript function `is_valid_signed_package`, which forwards straight to `signed_message.validateSignedMessage`: [8](#0-7) 
It is also used for device-level authentication flows such as prosaic-contract acceptance: [9](#0-8) 

### Impact Explanation
Any AA that gates state changes or fund transfers on `is_valid_signed_package(trigger.data.signed_package, oracle_or_counterparty_address)` — e.g., price/data attestations, KYC confirmations, arbitration or prosaic-contract sign-offs — can be manipulated if the signing address (whose address is derived purely from its `definition`, independent of network) produces the same message on more than one ocore-based network (mainnet/testnet/devnet, or any other fork/side-chain running the same codebase). An attacker who has observed such a signed package on one network can submit it verbatim as AA trigger data on another network. Because the signature checks in `Definition.validateAuthentifiers` only verify the ECDSA signature against `unit_hash_to_sign`, which is agnostic to network identity when `version`/`last_ball_unit` are omitted, the replayed package is accepted as freshly authorized, potentially causing the AA to release funds, update balances, or otherwise act on stale/foreign-network authorization it should not honor.

### Likelihood Explanation
Exploitation requires only that: (1) an attestor/oracle/counterparty address reuses the same key/definition across two ocore-based networks or contexts (a realistic and even encouraged pattern, since Obyte addresses are portable and identical bytes work on mainnet/testnet), and (2) at least one legitimately produced `signed_message` for that address becomes observable (it is often published as AA trigger data, which is public). No privileged access, hub compromise, or node collusion is needed — any unit poster/AA trigger sender can copy and resubmit the package. This is a Medium-likelihood, Medium/High-impact bug: it depends on key reuse across networks/environments, which is common practice but not universal.

### Recommendation
- Add a mandatory chain/network-binding field to the signed-message schema (e.g., embed `constants.alt` or `constants.GENESIS_UNIT` into the object that `getSignedPackageHashToSign()` hashes), and reject packages missing it, mirroring the domain-separator fix recommended for EIP-2612.
- Make `version`/`last_ball_unit` mandatory rather than optional in `validateSignedMessage()`, and verify `last_ball_unit` actually belongs to the chain being validated against (already partly done when present) so the anchor can't simply be omitted.
- Document that oracle/attestor implementations must not reuse the same address/key to sign the same message content across different ocore-based networks, or must include an explicit network tag inside `signed_message` payloads consumed by AAs.

### Proof of Concept
1. Oracle O runs identical software on `network A` (e.g. a private/dev ocore deployment) and later the same key/definition is used to sign a `signed_message` package `P = {signed_message: {...}, authors:[{address:O, authentifiers:{...}}]}` with no `version` and no `last_ball_unit` field (a valid, minimal `signMessage(msg, O, signer, false, cb)` call, see `signed_message.js:28-41`).
2. This package `P` is published as AA trigger data on network A to satisfy some AA logic gated by `is_valid_signed_package(trigger.data.signed_package, O)`.
3. An attacker copies `P` verbatim and submits it as `trigger.data.signed_package` in a unit sent to an unrelated AA on network B (mainnet or another fork) that also expects attestations from address `O` (same definition/address, portable across networks).
4. `formula/evaluation.js`'s `is_valid_signed_package` handler calls `signed_message.validateSignedMessage(conn, signedPackage, evaluated_address, mci, ...)`, which finds `bNetworkAware = false` (no `last_ball_unit`), verifies only the embedded `definition` hash and the ECDSA signature over `getSignedPackageHashToSign(objSignedMessage)` — a hash with no network-specific input — and returns success, exactly as it did on network A.
5. The AA on network B treats `P` as freshly authorized data/consent from `O` and proceeds with its logic (fund release, state update), even though `O` never intended this signature to apply to network B.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
