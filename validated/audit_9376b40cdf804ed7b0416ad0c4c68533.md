### Title
Malicious secondary AA can permanently freeze a shared multi-party payout by force-reverting the primary trigger's entire response - (File: aa_composer.js)

### Summary
Augur's `disavowCrowdsourcers` bug allowed a malicious ERC777-like recipient to revert an unavoidable transfer, freezing shared bond funds and blocking a mandatory unlock function for all other honest participants. In ocore's AA engine, an analogous atomicity hazard exists: when a primary AA trigger sends payments to multiple output addresses in a single response unit, and one of those addresses is a secondary AA, that secondary AA's mandatory execution (its own "hook", automatically invoked upon receiving funds) can unconditionally `bounce()`. This causes the *entire* primary trigger — including payments and state updates intended for all other, unrelated recipients bundled in the same unit — to be rolled back via `revert()`.

### Finding Description
In `handleSecondaryTriggers()`, after a primary AA's response unit sends outputs to one or more AA addresses, each output AA address is invoked as a secondary trigger: [1](#0-0) 

If any secondary AA in that set bounces (which any AA fully controls unconditionally, e.g., by calling `bounce(...)` in its own bytecode regardless of amount received), the error propagates up through `async.eachSeries`, and because the top-level call is not itself secondary (`bSecondary` is false for the primary), the code calls `revert()` rather than simply failing that one branch: [2](#0-1) 

`revert()` unconditionally rolls back *all* state changes and *all* queued payments from the primary trigger — not just the failed branch to the malicious AA: [3](#0-2) 

This is architecturally similar to the Augur bug: a single malicious counterparty, simply by unconditionally reverting upon receipt of funds (its mandatory "hook"), can force an entire shared operation — including transfers due to completely unrelated, honest parties bundled in the same message set — to fail. Because AA execution is deterministic based on persisted state variables (which are also rolled back), retrying the same trigger logic (e.g., a "settle"/"distribute" call on a lending pool, auction, or dispute-resolution AA) will deterministically reproduce the same computation, include the same payment to the malicious AA address, and bounce again — indefinitely. This can strand funds inside the paying AA's balance, unable to ever be distributed to the honest co-beneficiaries, exactly as in Augur where bond funds became frozen because the disavowal transfer to a malicious `repBondOwner` could never succeed.

### Impact Explanation
Any AA design pattern that pays out multiple parties from a shared pool in one message set (e.g., multi-party escrow, auction settlement, staking/dispute payout, revenue-sharing AAs) is vulnerable: an attacker who controls (or registers) one of the payee addresses as a malicious AA that always bounces can indefinitely block the payout to every other party in that batch, freezing shared AA funds and denying other reporting participants/depositors their funds — matching the "AA fund loss or freezing" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be one of several intended payees of a shared AA's payout logic and that they deploy a trivial malicious AA (any AA whose code unconditionally calls `bounce()`), something fully within reach of an unprivileged AA author. No special privileges, race conditions, or network-level assumptions are needed — it is a deterministic consequence of `handleSecondaryTriggers`'s all-or-nothing `revert()` semantics documented at `aa_composer.js:1743-1750`.

### Recommendation
Do not let a bounce in one secondary AA branch roll back payments/state changes destined for unrelated addresses in the same primary response. Options: (1) isolate each secondary-AA branch's execution so failures there only fail that branch (already partially attempted via savepoints, but currently `revert()` unwinds the whole primary trigger rather than only the failing branch); (2) require AA developers who pay out to potentially-untrusted AA addresses to use a withdrawal/pull pattern (store a claimable balance and let the payee separately trigger their own withdrawal) instead of push-paying multiple recipients atomically in one unit, and document this risk prominently in AA authoring guidance.

### Proof of Concept
1. Deploy AA `M` ("malicious") whose entire logic is a single `bounce("nope")` regardless of inputs.
2. Deploy AA `P` ("payout pool") that, per trigger, pays out from its balance to two addresses in one response unit: an honest user address `H` and `M`'s address, and additionally updates a state variable marking the round as settled.
3. Fund `P` and trigger it once. Because `P`'s response includes an output to `M`, `handleSecondaryTriggers` invokes `M` as a secondary trigger; `M` bounces.
4. Per `aa_composer.js:1743-1750`, since the top-level call is primary (`bSecondary` false), `revert()` is invoked, rolling back the entire response unit from `P`, including the payment to honest party `H` and the "settled" state variable update.
5. Any subsequent trigger of `P` reproduces the exact same deterministic computation (same state, same balances), again includes the payment to `M`, and again reverts — `H` can never receive their share and `P`'s pooled funds remain permanently stuck, mirroring the Augur `disavowCrowdsourcers`/`repBondOwner` freeze scenario.
