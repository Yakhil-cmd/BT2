### Title
Unvalidated P2P Staking Info Delivery Allows Malicious Sync Peer to Corrupt Staking DB — (`datasync/downloader/queue.go`)

### Summary

During fast-sync or snap-sync, a malicious P2P peer can supply a fabricated `P2PStakingInfo` payload that is accepted without any content validation, persisting attacker-controlled `CouncilStakingAmounts` and `CouncilRewardAddrs` into the staking DB. Subsequent reward distribution and WeightedRandom proposer selection consume these corrupted values.

### Finding Description

`DeliverStakingInfos` in `datasync/downloader/queue.go` contains a `validate` closure that unconditionally returns `nil`:

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
``` [1](#0-0) 

The `reconstruct` closure then directly assigns the peer-supplied payload into the `fetchResult`:

```go
reconstruct := func(index int, result *fetchResult) {
    result.StakingInfo = stakingInfoList[index]
    result.SetStakingInfoDone()
}
``` [2](#0-1) 

Compare this to `DeliverBodies` and `DeliverReceipts`, which both validate against a cryptographic commitment in the block header (`header.TxHash` and `header.ReceiptHash` respectively):

```go
// DeliverBodies
if types.DeriveTransactionsRoot(types.Transactions(txLists[index]), header.Number) != header.TxHash {
    return errInvalidBody
}
``` [3](#0-2) 

```go
// DeliverReceipts
if types.DeriveReceiptsRoot(types.Receipts(receiptList[index]), header.Number) != header.ReceiptHash {
    return errInvalidReceipt
}
``` [4](#0-3) 

No equivalent hash field for staking info exists in the block header, and no on-chain AddressBook re-derivation is performed. The `ToStakingInfo` conversion is a direct field copy with zero verification:

```go
func ToStakingInfo(si *P2PStakingInfo) *StakingInfo {
    return &StakingInfo{
        SourceBlockNum:   si.BlockNum,
        NodeIds:          si.CouncilNodeAddrs,
        StakingContracts: si.CouncilStakingAddrs,
        RewardAddrs:      si.CouncilRewardAddrs,
        ...
        StakingAmounts:   si.CouncilStakingAmounts,
    }
}
``` [5](#0-4) 

The `P2PStakingInfo` struct carries all fields that drive reward distribution and proposer selection: [6](#0-5) 

Staking info is only scheduled for fast/snap sync under `WeightedRandom` proposer policy, at `stakingUpdateInterval` boundaries, and only before the Kaia fork: [7](#0-6) 

The `deliver` generic function does enforce that delivery is only accepted from a peer that was explicitly requested (via `pendPool[id]` check): [8](#0-7) 

This means the attacker must be a connected peer that the syncing node actually requests staking info from — not a completely unsolicited injection. However, any peer the node connects to during sync qualifies, and Kaia's P2P layer does not restrict which peers can serve staking info responses.

### Impact Explanation

- **Corrupted staking DB**: Attacker-controlled `CouncilStakingAmounts` and `CouncilRewardAddrs` are persisted for historical staking update blocks.
- **Invalid reward distribution**: The reward module reads these amounts to split block rewards among validators. Fabricated amounts redirect rewards to attacker-controlled addresses.
- **Corrupted WeightedRandom proposer selection**: Proposer weights are derived from `CouncilStakingAmounts`; inflating one validator's amount biases proposer selection, enabling targeted censorship or double-spend facilitation.
- **Chain split potential**: Honest fully-synced nodes derive staking info from on-chain AddressBook state; a fast/snap-synced node using corrupted staking info will diverge in proposer selection and reward accounting.

### Likelihood Explanation

- Exploitable by any peer the syncing node connects to during fast/snap sync — no privileged access required.
- The attacker only needs to run a standard Kaia P2P node and respond to `StakingInfoMsg` requests with fabricated data.
- Fast/snap sync is the default mode for new nodes joining the network, making this a realistic attack surface.
- The `// TODO-Kaia-Snapsync update validation logic` comment confirms this is a known gap, not an intentional design choice.

### Recommendation

1. Add a cryptographic commitment to staking info in the block header (e.g., a `StakingInfoHash` field), and validate the delivered payload against it in the `validate` closure — mirroring the pattern used for receipts and bodies.
2. As an interim measure, re-derive staking info from the on-chain AddressBook contract state after fast/snap sync completes, overwriting any peer-supplied values.
3. Alternatively, fetch staking info from multiple independent peers and require consensus before persisting.

### Proof of Concept

1. Run a malicious Kaia node that intercepts `StakingInfoMsg` requests and responds with a `P2PStakingInfo` where `CouncilStakingAmounts[0]` is set to `math.MaxUint64` and `CouncilRewardAddrs[0]` is set to an attacker-controlled address.
2. Connect a victim node in fast-sync mode to the malicious peer.
3. After sync completes, call `GetStakingInfo` for a staking-update block number.
4. Observe that the returned `StakingAmounts` match the injected values rather than the on-chain AddressBook state.
5. Observe that subsequent block reward distribution sends funds to the attacker-controlled reward address.
