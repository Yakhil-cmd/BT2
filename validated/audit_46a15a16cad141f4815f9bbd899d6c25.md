### Title
Stack-scoped API token can read CCMenu build status for any stack, bypassing its stack authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
This is an analog of the "H-3 proportional fee" bug class: a binding that should tie an authorized scope to the exact resource acted upon is broken. In shipit-engine, `Shipit::ApiClient` tokens can be scoped to a single stack via `stack_id`, and `Api::BaseController#stack` enforces that scoping. `Api::CCMenuController`, however, overrides `#stack` and looks up the stack directly from the URL param, never consulting `current_api_client.stack_id`, breaking the "stack a token authorizes" vs "stack it touches" binding.

### Finding Description
`Shipit::ApiClient` supports being scoped to a specific stack: [1](#0-0) 

The base API controller correctly enforces this scoping when resolving the target stack for a request: [2](#0-1) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the authenticated client is stack-scoped, and `stack` resolves `params[:stack_id]` only within that restricted set. This is the binding: **stack authorized by token == stack acted upon**.

`Api::CCMenuController` authenticates using a `params[:token]` (rather than HTTP Basic auth) and overrides `#stack` to bypass the scoped lookup entirely: [3](#0-2) 
`Stack.from_param!(params[:stack_id])` is called on the unscoped `Stack` class, not on `stacks` (the api_client-scoped relation) that `BaseController` provides. `require_permission :read, :stack` only checks that the token *has* the `read:stack` permission bit — it does not check *which* stack the permission applies to.

Consequently, holding a valid token for stack A (`api_client.stack_id == A.id`, permissions `["read:stack"]`), an attacker can request:
```
GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<token-for-stack-A>
```
and `Stack.from_param!` will happily resolve stack B, which is rendered via `project.xml.builder`, exposing stack B's `merge_status`, latest deploy `id`, `running?` state, and build timestamps — cross-stack leakage of stack state that the token was never authorized to read.

### Impact Explanation
This crosses the "unauthenticated (here: unauthorized-scope) read of stack state" impact bucket. A token scoped to one stack (e.g., handed to a low-trust integration such as a CI status badge/build-monitor widget) can read build/deploy status of every other stack in the installation, including private/internal deployment pipelines, purely by supplying a different `stack_id` in the URL — no additional credential or repository access required.

### Likelihood Explanation
High. Any legitimate holder of a stack-scoped, `read:stack`-permissioned API token — which is the standard credential type used for exposing this exact CCMenu status feed to external consumers/build monitors — can trivially enumerate other `stack_id` values (which are just `owner/repo/environment` strings, often predictable/public via the repository name) and substitute them in the URL. No signature/collision/race is required; it's a straight authorization-scope check that is simply missing on this one controller while present on the shared base controller for every other resource.

### Recommendation
In `Api::CCMenuController#stack`, resolve the stack through the scoped `stacks` relation from `BaseController` instead of the raw `Stack` class:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the "stack the token is scoped to" == "stack rendered" invariant enforced everywhere else in the API.

### Proof of Concept
1. Create two stacks, `org/repo-a/production` (id A) and `org/repo-b/production` (id B).
2. Create an `ApiClient` with `stack_id = A.id` and `permissions = ["read:stack"]`; obtain its `authentication_token`.
3. Request `GET /api/stacks/org/repo-b/production/ccmenu?token=<token>`.
4. `authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` passes (client has `read:stack`), and `stack` returns `Stack.from_param!('org/repo-b/production')` — stack B — even though the client is scoped only to stack A.
5. The response renders `project.xml.builder` with stack B's `merge_status`, latest deploy id, and running/build state, none of which the token should have been able to read.
