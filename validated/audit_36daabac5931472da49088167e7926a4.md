### Title
Unbounded in-memory scan of `storage.assocUnstableMessages` in `dataFeedExists` allows AA callers to cause quadratic-blowup DoS during AA trigger evaluation - (File: data_feeds.js)

### Summary
`dataFeedExists()` in `data_feeds.js` contains an unbounded `for...in` loop over `storage.assocUnstableMessages` — an in-memory map that holds **every currently-unstable unit's messages** — whenever it is called with `bAA=true` (i.e. from an AA's `in_data_feed` oscript evaluation). This mirrors the reported Carapace bug: an attacker-influenced, unbounded array/collection is scanned inside a "critical path" function (here, AA trigger/response evaluation, analogous to `lockCapital`), and the size of that collection can be driven up by ordinary, unprivileged actors simply by keeping many units unstable, degrading or stalling AA response computation for every node.

### Finding Description
`dataFeedExists` is invoked from `definition.js` (`in data feed` address-definition condition) and from `formula/evaluation.js` (`in_data_feed` oscript function used inside Autonomous Agents) with `bAA=true`. [1](#0-0) [2](#0-1) 

When `bAA` is true, instead of querying an indexed key-value store, the function iterates over **all keys of `storage.assocUnstableMessages`** (one entry per currently-unstable unit in the whole node's memory cache), and for each matching unit it iterates over **all of that unit's messages**: [3](#0-2) 

`storage.assocUnstableMessages` is populated for every unit that becomes unstable (i.e., every newly-posted, not-yet-stabilized unit network-wide) and only cleared when the unit stabilizes: [4](#0-3) 

This loop has no size cap, no early termination heuristic besides "found," and no complexity charge tied to the size of `assocUnstableMessages` (unlike `array`/`dictionary` literals in the same formula evaluator, which explicitly enforce `isTooBigObj`/100-element caps — see `formula/evaluation.js` lines 1132, 1171). Because any unprivileged unit poster can increase the number of simultaneously unstable units on the DAG (e.g., by posting many low-value units/AA triggers faster than they stabilize, or simply during periods of high organic throughput), the cost of this loop scales with global, attacker-influenceable state rather than with any per-call bounded input — directly analogous to `ProtectionPool#lockCapital` looping over an attacker-inflatable `activeProtectionIndexes` array.

### Impact Explanation
Every node executing an AA that calls `in_data_feed` (or the `data_feed` reader through the related unstable-scan path in `readDataFeedValue`, lines 205–274, which performs the same unbounded scan) must perform this O(N) scan deterministically as part of consensus-critical AA trigger/response computation. Because AA execution must be identical and deterministic across all full nodes to agree on the resulting response unit, a sustained increase in the count of unstable units (which any user can cause simply by posting many units, without needing privileged access) inflates the cost of *every* AA that uses `in_data_feed`/`data_feed` with unstable-data lookups, network-wide, at the same time. This can materially slow down or stall AA trigger handling (`handleTrigger`/`handlePrimaryAATrigger` in `aa_composer.js`), which runs synchronously while holding the unit's validation/db state, ultimately threatening the network's ability to timely confirm AA-driven units — the same class of impact as the referenced report ("pool won't be able to be locked"/here, "AAs cannot be reliably triggered/confirmed").

### Likelihood Explanation
Likelihood is moderate: the loop is not attacker-controlled in isolation (it depends on the global count of unstable units, not a value the attacker fully owns like a contract-scoped array), but any user can cheaply increase the unstable-unit count by posting units, and any AA author can trivially write an AA that calls `in_data_feed`/`data_feed` on every trigger, so a coordinated flood of low-cost units combined with mass-triggering of such AAs is a straightforward, cheap attack requiring no special privileges — consistent with the "unprivileged AA trigger sender / asset issuer" reachability constraint in scope.

### Recommendation
Replace the in-memory linear scan over `storage.assocUnstableMessages` with an indexed lookup structure keyed by `(oracle address, feed_name)` for unstable AA-authored data feeds (mirroring the stable-path key-value index already used in `dataFeedByAddressExists`/`readDataFeedByAddress`), or cap/charge oscript complexity proportional to the current size of `assocUnstableMessages` so the cost is bounded and paid for by the caller, consistent with the existing `isTooBigObj`/100-element caps enforced elsewhere in `formula/evaluation.js`.

### Proof of Concept
1. An attacker (or a period of ordinary high load) causes a large number of units to remain unstable simultaneously (this is possible because unit posting is cheap and stabilization requires witness quorum and time).
2. Any AA definition that uses `in_data_feed` or `data_feed` with `unstable_opts` set (common in real-time price-feed AAs) is triggered by a normal user payment.
3. On every trigger, `dataFeedExists`/`readDataFeedValue` iterates the full `storage.assocUnstableMessages` map (line 34/213 of `data_feeds.js`) and every message of every matching unit, with cost growing linearly in the number of currently unstable units, network-wide, for every node independently computing the same deterministic AA response — producing a compounding slowdown as unstable-unit count grows.
