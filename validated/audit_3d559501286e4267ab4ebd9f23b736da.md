Confirmed the root cause: `is_supported_mint` (programs/cp-swap/src/utils/token.rs:335-360) returns `Ok(true)` immediately whenever the mint's owner is the legacy SPL `Token` program, without ever inspecting the mint's `freeze_authority` field. Both `initialize` and `initialize_with_permission` rely solely on this check before creating pool vaults and pulling in creator liquidity.

### Title
Permissionless pool creation accepts freezable (freeze-authority) SPL token mints, letting a malicious pool creator permanently lock LP funds - (File: programs/cp-swap/src/utils/token.rs, programs/cp-swap/src/instructions/initialize.rs, programs/cp-swap/src/instructions/withdraw.rs)

### Summary
Pool creation via `initialize`/`initialize_with_permission` only rejects unsupported Token-2022 extensions; for legacy SPL Token mints it accepts *any* mint, including one with an active `freeze_authority`. A malicious actor can create a pool pairing a legitimate token with a token they control the freeze authority for, attract other LPs to `deposit`, then freeze the pool's vault token account for the malicious mint. Because `withdraw` atomically transfers both `token_0` and `token_1` out of the vaults, freezing either vault account permanently blocks withdrawal of both tokens for every LP in the pool.

### Finding Description
`is_supported_mint` at [1](#0-0)  returns `true` unconditionally for any mint owned by the legacy `Token` program:

```rust
pub fn is_supported_mint(...) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    ...
}
```

This check is the only gate applied in both permissionless pool creation paths, `initialize` [2](#0-1)  and `initialize_with_permission` [3](#0-2) . Neither creator identity nor freeze authority of the SPL mint is validated anywhere in pool creation or in `deposit` [4](#0-3) .

Once other LPs deposit token_0/token_1 into the pool vaults (created via `create_token_account` at [5](#0-4) ), the mint's freeze authority (held by the malicious pool creator) can freeze the vault token account off-chain via the standard SPL Token `FreezeAccount` instruction — no privileged program logic is required, this is a base SPL Token feature usable by anyone who created the mint.

`withdraw` then unconditionally attempts both transfers before returning success:
```rust
transfer_from_pool_vault_to_user(... token_0_vault ...)?;
transfer_from_pool_vault_to_user(... token_1_vault ...)?;
``` [6](#0-5) 

If either vault's token account is frozen, the corresponding `transfer_checked` CPI at [7](#0-6)  fails with the SPL Token program's `AccountFrozen` error, reverting the entire `withdraw` transaction — including the LP burn. This locks out withdrawal of both tokens for every LP holding shares of that pool, not just the malicious creator.

### Impact Explanation
This is a permanent freezing of legitimate LP funds. Innocent LPs who deposit the "good" counter-asset (e.g., a wrapped stablecoin) into a pool that also holds a malicious, freeze-authority-controlled mint lose access to both their good and bad tokens once the vault is frozen — the atomic nature of `withdraw` means the healthy token is trapped too. Swaps into/out of the frozen vault also fail, and creator/protocol fee collection instructions (`collect_creator_fee`, `collect_protocol_fee`) that transfer from the same vaults would likewise revert, compounding the freeze across all pool participants.

### Likelihood Explanation
Pool creation is fully permissionless — any user can call `initialize` with a self-minted SPL Token mint that retains freeze authority, at negligible cost (a single mint creation and pool initialization transaction). No whitelist or freeze-authority check currently blocks this. The only requirement is that an unsuspecting LP subsequently deposits into the pool, which is likely for newly created pools advertised with attractive-looking pairs.

### Recommendation
In `is_supported_mint`, reject legacy SPL Token mints (and Token-2022 mints) that have a non-null `freeze_authority` set, or require it to be revoked (`None`) before allowing pool creation. Alternatively, disallow freezing to affect vault accounts by checking account state before/after in every transfer-dependent instruction, though rejecting freezable mints at pool-creation time is the more robust fix.

### Proof of Concept
1. Attacker creates SPL Token mint `M` via the legacy Token program, retaining `freeze_authority = attacker`.
2. Attacker calls `initialize` pairing `M` with a legitimate mint `USDC`, seeding minimal initial liquidity; `is_supported_mint` passes for both mints (`M` because `mint_info.owner == Token::id()`).
3. Victim LP calls `deposit`, transferring `USDC` and `M` into the pool vaults [8](#0-7) .
4. Attacker calls the standard SPL Token `FreezeAccount` instruction against the pool's `token_M_vault` account (allowed since attacker holds `M`'s freeze authority).
5. Victim LP calls `withdraw`; the CPI transferring frozen `M` out of the vault reverts, reverting the whole transaction and permanently trapping the victim's `USDC` share alongside the frozen `M`.
