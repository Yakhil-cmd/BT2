### Title
Cross-repository commit-status and push forgery via mismatched webhook trust binding - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The webhook signature check in `WebhooksController` authenticates a request only against the GitHub organization named in `repository.owner.login` (or `organization.login`), but the handlers that actually act on the payload (`Handlers::Handler#repository_name`, `Handlers::StatusHandler#process`) select the target repository/commit using a *different* field of the same payload (`repository.full_name`, or a global `sha` lookup with no repository scoping at all). Because both fields live in the same attacker-controlled JSON body, an attacker who legitimately controls any one organization configured in `Shipit.secrets.github` (i.e., can produce a validly-signed webhook for their own org) can set `repository.owner.login` to their own org while pointing `repository.full_name` / `sha` at a completely different, victim stack.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`: [1](#0-0) [2](#0-1) 

Once verified, `create` dispatches the *entire raw payload* to every registered handler for the event, unchanged: [3](#0-2) 

Handlers derive the repository they act on from a **different** JSON key, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

`PushHandler` uses this to trigger `stack.sync_github`, forcing a resync to an attacker-chosen `after` SHA: [5](#0-4) 

`StatusHandler` is worse: it doesn't even use `repository_name` — it looks up commits **globally by SHA across the entire installation**, with no repository or organization scoping whatsoever, and writes a GitHub-reported CI status directly onto them: [6](#0-5) 

There is no code path anywhere in `verify_signature`, `Handler`, `PushHandler`, or `StatusHandler` that asserts `repository.owner.login` (the value the signature was actually checked against) matches `repository.full_name`'s owner or the org owning the commit's stack. The trust binding that should hold is:

`organization whose webhook_secret validated the HMAC == organization/repository the handler writes state for`

This binding is never enforced, so it can be broken by anyone who legitimately controls one org's webhook secret in a multi-org Shipit deployment (a normal, unprivileged relationship relative to any *other* org/stack tracked by the same Shipit instance) — they can forge signed payloads whose "content" fields target a foreign stack.

### Impact Explanation
Using a validly-signed webhook for their own organization, an attacker can:
- Force `commit.create_status_from_github!` to record a fabricated `success` (or any) status for an arbitrary commit SHA in a victim stack they do not control, via `StatusHandler`, since the lookup is a bare `Commit.where(sha: params.sha)` with no ownership check. If that stack's `shipit.yml` `ci.require` gates continuous deployment on that status context, this can make an otherwise CI-unverified commit appear deployable, contributing to an unauthorized deploy.
- Force `stack.sync_github(expected_head_sha: ...)` on a victim stack via `PushHandler`, influencing which commit the stack treats as its head for deploy purposes.

This crosses the "cross-repository writes / unauthorized deploy" impact bar defined for this analog class, since it lets an org boundary that was authenticated stand in for a repository boundary that was never checked.

### Likelihood Explanation
Exploitability requires the attacker to control (or have webhook-secret knowledge for) at least one organization entry configured under `Shipit.secrets.github` on the target Shipit instance — a realistic scenario for any multi-tenant/multi-org Shipit deployment where organizations self-register their GitHub App/webhook. Relative to any *other* tracked org/stack, this is an unprivileged attacker. The `StatusHandler` path requires no knowledge of internal state beyond a target commit SHA that is likely public (visible on GitHub); the `PushHandler` path requires knowing a branch name and SHA, both public GitHub information.

### Recommendation
Bind the two identities used during webhook processing:
1. In `Handler#repository_name` (and any handler using it), assert that the resolved repository's owner matches `repository_owner`/the organization whose secret validated the signature, rejecting the event otherwise.
2. In `StatusHandler#process`, scope the `Commit` lookup by the repository/stack derived from the payload's `repository.full_name`, not just by bare `sha`, and again cross-check that repository's owner against the verified `repository_owner`.
3. More generally, have `verify_signature` store the verified organization on the request/params and have every handler explicitly re-derive its target repository/org from that verified value rather than re-reading an unrelated field from the same untrusted JSON body.

### Proof of Concept
1. Attacker legitimately owns GitHub org `attacker-org`, which is configured in `Shipit.secrets.github` with a webhook secret they know (e.g. because they self-installed the Shipit GitHub App on their own org, a supported, low-privilege setup path per `docs/setup.md`).
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<victim commit sha, e.g. from a public PR on victim/repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s own known `webhook_secret` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, verifies successfully against `attacker-org`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of which org it actually belongs to — and calls `create_status_from_github!`, injecting a forged `success` status that can satisfy `ci.require` on the victim's stack and unblock an automatic/continuous deploy. # frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
