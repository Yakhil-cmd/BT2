### Title
Malicious "always-bounce" AA at a payout address can force revert of an entire AA response chain, blocking protocol actions such as liquidation - ([File: aa_composer.js])

### Summary
The Autonomous Agent (AA) engine builds each primary trigger's response as an atomic chain: the primary unit's outputs are inspected, and any output address that is itself a registered AA is invoked as a "secondary trigger" via `handleSecondaryTriggers`. If that secondary AA bounces, the **entire** primary response — including all state variable updates already computed by the primary (and any other) AA in the chain — is unwound via `revert()`, which rolls back to the savepoint and re-bounces the primary trigger. This is functionally identical to the ERC777-callback pattern in the referenced report: an untrusted recipient can execute code ("hook") during a value transfer, and that code's failure propagates back and blocks/reverts the caller's critical state transition (e.g., liquidation).

### Finding Description
`handleSecondaryTriggers` in `aa_composer.js` looks up every output address of the just-composed response unit that is itself an AA and recursively calls `handleTrigger` on it as a secondary trigger: [1](#0-0) 

If any of those secondary AAs bounces, `async.eachSeries`'s completion handler treats this as a hard failure of the *whole* primary chain and calls `revert()`, not merely `bounce()` of the one recipient: [2](#0-1) 

`revert()` then discards all state variable changes accumulated by every AA in the chain, rolls the database back to `SAVEPOINT initial_balances`, clears the batch, and finally calls `bounce()` on the primary trigger, so the primary AA's action never takes effect: [3](#0-2) 

Because AA addresses are permissionless (`chash160` of any arbitrary definition JSON) and no design restriction prevents payout addresses from being attacker-chosen AAs, any protocol AA that must, as part of a single state-changing action, send an output to a party-supplied or otherwise attacker-influenced address (e.g., returning excess collateral to the position owner during liquidation, paying a referrer, or forwarding funds to a "next hop" contract) is exposed: if that recipient address is defined as an AA whose `state`/`messages` formula deterministically throws (e.g., references an undefined variable, divides by zero, or fails a `bounce_fees` check), the recipient will bounce every time it is triggered, forcing `revert()` and undoing the calling AA's intended action.

This mirrors the reported ERC777 issue precisely: a token/callback recipient controlled by an attacker can make the recipient-side execution fail on demand, and this failure is used to block a legitimate operation (liquidation) that the attacker wants to prevent, purely by choosing to receive value at a "hostile" address.

### Impact Explanation
An attacker who is a borrower/position owner in a lending/DeFi-style AA can pre-register (or have the protocol accept) an "always-bounce" AA address as the destination for their share of funds during a critical multi-step action such as liquidation, rebalancing, or an oracle-triggered settlement that spans a secondary AA hop. Every attempt by the protocol to execute that action against the attacker's position reverts entirely — the protocol's balances, debt/collateral state variables, and any bookkeeping updates are rolled back as if nothing happened, while bytes/fees paid in the trigger are still consumed. This can permanently block liquidation of an undercollateralized position (freezing protocol funds / enabling bad debt), or more generally let any counterparty veto any AA-chain action that pays them, causing AA fund loss or freezing for the protocol.

### Likelihood Explanation
Exploitation only requires an unprivileged user to define one on-chain AA whose formula deterministically fails (trivial to construct, e.g. referencing a nonexistent asset/data feed or an arithmetic error) and to ensure the protocol AA under attack routes any output to that address as part of a chained/secondary-trigger flow. No special privileges, race conditions, or network assumptions are needed — it is fully deterministic and reproducible by any unit poster who can trigger the vulnerable AA.

### Recommendation
Do not allow a single hostile secondary-AA failure deep in a response chain to unconditionally revert the entire primary chain's already-computed state changes for AAs unrelated to the failing branch. Options: (1) treat a secondary AA's bounce as a local failure that only discards that AA's own attempted state changes/balance while allowing the rest of the chain (and the primary AA's already-emitted state updates) to stand, unless the primary AA's own logic explicitly depends on the secondary succeeding; (2) document prominently and enforce in guidelines that AA authors implementing fund-critical operations (like liquidation) must not condition irreversible protocol bookkeeping on payments sent to addresses that can be freely chosen/controlled by counterparties, and provide/encourage a "fire-and-forget"/isolated-failure payment primitive for such payouts.

### Proof of Concept
1. Deploy AA `Victim` that, on a "liquidate" trigger, updates state vars marking a position as liquidated and, in the same response unit, sends the borrower's leftover collateral to `trigger.data.recipient` (an address supplied/controlled by the borrower being liquidated).
2. As the borrower, register `Attacker` AA whose `messages`/`state` formula unconditionally throws (e.g. `state: "{ var['x'] = 1/0; }"` or reference to an undefined asset causing an evaluation error), and set `trigger.data.recipient = Attacker_address` in the liquidation trigger (or have it stored from a prior deposit).
3. Post a unit triggering `Victim`'s liquidation logic. `Victim`'s primary response computes state updates and includes a payment output to `Attacker`.
4. `handleSecondaryTriggers` invokes `Attacker` as a secondary trigger; `Attacker` bounces (per `bounce_fees` check or formula error) as shown by the reachable code path at [2](#0-1) .
5. `revert()` unwinds `Victim`'s liquidation state changes entirely ( [3](#0-2) ), so the position remains un-liquidated even though liquidation conditions were met — repeatable indefinitely by the attacker.
