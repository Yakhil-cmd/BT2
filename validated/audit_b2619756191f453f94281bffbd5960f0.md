### Title
Shared, unwrapped address/AA definition object returned from `readDefinitionByAddress`/`readAADefinition` is exposed to oscript mutation via `definition[...]` and can corrupt the cached definition used by later validations - (File: formula/evaluation.js)

### Summary
The `CollateralInfo.collateralAddresses` bug is a public/unrestricted reference to internal state that lets any caller mutate data that should be read-only. The analogous pattern in ocore is the `definition` oscript operator: it calls `storage.readAADefinition`/`storage.readDefinitionByAddress` and hands the *raw* returned `arrDefinition` array/object directly into `new wrappedObject(arrDefinition)` without cloning it first.

### Finding Description
In `evaluate()`, case `'definition'`, the code does:
```
storage.readAADefinition(conn, addr, mci, function (arrDefinition, definition_unit) {
    if (arrDefinition) {
        if (bAA)
            return cb(new wrappedObject(arrDefinition));
        ...
        cb(new wrappedObject(arrDefinition));
    }
    storage.readDefinitionByAddress(conn, addr, mci, {
        ifFound: function (arrDefinition) {
            cb(new wrappedObject(arrDefinition));
        }
    });
});
``` [1](#0-0) 

Everywhere else in the interpreter, values retrieved from validation state/caches that are exposed as `wrappedObject` are defensively deep-cloned before being wrapped, e.g. `previous_aa_responses`, `trigger.data`, `trigger.outputs`, and the `unit[]` operator all call `string_utils.cloneDeep(...)` before constructing the `wrappedObject`: [2](#0-1) [3](#0-2) 

The `definition` operator is the outlier: it wraps `arrDefinition` (the object returned from `storage.readAADefinition`/`storage.readDefinitionByAddress`) directly. If those storage functions return a cached object by reference (rather than a fresh copy per call), an AA's oscript formula can then mutate the resulting `wrappedObject` (e.g. `$d = definition[$addr]; $d[1].amount = 999999999;` — mutation of nested wrappedObject fields is a normal, supported oscript feature, as shown by the mutation tests) and this mutation would propagate back into the shared cached definition object used by the address-definition/authentication cache for subsequent validations of that same address in later units.

### Impact Explanation
If the definition cache is a shared, non-cloned reference, corrupting it via oscript AA execution could alter the authentication rules (e.g. thresholds in an `and`/`or`/`r_of_set` definition, `sig` pubkeys, `address` sub-definitions) that later unit/authentifier validation logic reads for that address, causing the node to disagree about which signatures/definitions are valid — enabling unauthorized spending from that address or a validity/stability disagreement across nodes (since not all nodes execute the same AA in the same order/cache state), which matches the required "unauthorized spending" / "node disagreement on validity" impact bar.

### Likelihood Explanation
Reachable by any unprivileged AA author: simply write a getter/state formula that calls `definition[address]` and mutates the returned object. No privileged access is required — this is directly reachable from a posted AA trigger, matching the reachable-actor requirement (AA author / AA trigger sender).

### Recommendation
Deep-clone `arrDefinition` before wrapping, mirroring the pattern used for `trigger.data`, `trigger.outputs`, and `previous_aa_responses`:
```js
cb(new wrappedObject(string_utils.cloneDeep(arrDefinition)));
```
at all three call sites in the `'definition'` case in `formula/evaluation.js` (lines 1632, 1637, 1646), so oscript-level mutation of the returned wrappedObject can never affect the underlying cached definition object.

### Proof of Concept
1. An address `A` has a definition cached by `storage.readDefinitionByAddress`/`readAADefinition` (returned as `arrDefinition`, potentially the same in-memory object across calls if cached).
2. An AA formula executes:
```
$d = definition[A];
$d[1].pubkey = 'ATTACKER_PUBKEY';
```
3. Because `arrDefinition` was not cloned before being wrapped, mutating `$d` mutates the same object instance held in the definition cache.
4. Any subsequent validation of a unit signed by address `A` that reads the (now-corrupted) cached definition may accept a signature under the attacker-controlled pubkey/threshold, or nodes with differing cache states diverge on whether the unit is valid — unauthorized spending / consensus disagreement.

Note: this depends on confirming that `storage.readAADefinition`/`storage.readDefinitionByAddress` return the *same cached object instance* on repeated calls (vs. a fresh row parse each time); I was not able to fully verify the caching internals of these storage functions within the available search budget, so this should be validated against `storage.js`/`definition.js` before treating it as fully confirmed.
