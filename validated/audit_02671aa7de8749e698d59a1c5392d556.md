### Title
Webhook signature is verified against the organization derived from `repository.owner.login`/`organization.login`, but downstream handlers act on the unrelated `repository.full_name` field of the same payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports multi-organization GitHub App configuration, where each organization has its own `webhook_secret`. `WebhooksController#verify_signature` selects *which* secret to verify the inbound HMAC-SHA1 signature against by reading `repository.owner.login` (falling back to `organization.login`) out of the untrusted JSON body itself, then calls `Shipit.github(organization: repository_owner)` to fetch that organization's app/secret and verifies the signature with it. Once the signature check passes, the event is dispatched to handlers (e.g. `PushHandler`, `StatusHandler`) which determine the *actual* stack/repository to act on using a different field of the same payload: `repository.full_name`, via `Repository.from_github_repo_name`. Nothing ties `repository.owner.login` back to `repository.full_name`'s owner segment.

### Finding Description
`verify_signature` computes the organization used for secret lookup from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves per-organization app config/secret from `secrets.github`: [3](#0-2) 

Once verification succeeds, `Handler#stacks`/`Handler#repository_name` resolve the target repository from a *different* field, `repository.full_name`, and hand the payload to model/job code that mutates state (sync commits, create/update `PullRequest`s, archive/unarchive review stacks, create statuses): [4](#0-3) [5](#0-4) [6](#0-5) 

This is structurally the same class of bug as the Notional report: one field is checked (primary debt / `repository.owner.login`) while a sibling field that drives the actually consequential operation (secondary debts / `repository.full_name`) is left unchecked against the same invariant. Here, the "equality" that should hold but is never enforced is:

`repository.owner.login` (or `organization.login`) used to pick the verifying secret == owner segment of `repository.full_name` used to pick the mutated `Repository`/`Stack`.

If an attacker/operator controls (or has been issued) a valid `webhook_secret` for organization `B` (e.g., they administer a Shipit-connected GitHub App/org `B`, or the secret for `B` has weaker operational controls), they can send a webhook whose body sets `repository.owner.login = "B"` while `repository.full_name = "A/some-repo"`. `verify_signature` authenticates the request using `B`'s webhook secret (which the attacker controls, since it's their own org's HMAC secret and they craft the exact `raw_post` used to compute it) and the check passes. `PushHandler`/`StatusHandler`/`CheckSuiteHandler` etc. then act on `Repository.from_github_repo_name("A/some-repo")`, which belongs to a different, uninvolved organization `A`. This lets a party who only owns credentials for org `B` inject writes (trigger `sync_github`, forge commit `status`, forge `check_suite` results affecting deployability, mutate `PullRequest`/review-stack state) against stacks/repositories that belong to org `A`, entirely bypassing the intended per-organization trust boundary that `webhook_secret` is meant to enforce.

### Impact Explanation
This breaks the organization-authenticated vs. repository-written binding at the heart of Shipit's multi-tenant webhook trust model. An attacker who legitimately controls one organization's webhook secret can forge events attributed to a repository owned by a different organization, causing cross-repository state changes (fake commit statuses feeding into deployability checks, fake `check_suite` results, forced sync of arbitrary branches/SHAs, review-stack archive/unarchive, `PullRequest` record tampering) without ever holding credentials for the victim organization. This matches the "cross-repository writes" Critical impact bucket, since the write target (repository/stack) is decoupled from the authenticated credential's scope.

### Likelihood Explanation
Requires only that: (1) the deployment configures more than one GitHub organization/app in `secrets.github` (a documented, supported configuration per `Shipit.github_organizations`/`TOP_LEVEL_GH_KEYS`), and (2) the attacker possesses (or can obtain) a legitimate `webhook_secret` for *any one* of those configured organizations — which is a much lower bar than needing write access to the target organization/repository itself, and does not require a Shipit session, API token, or GitHub write access to the victim repo. No other validation ties the two payload fields together anywhere in the request path.

### Recommendation
After `verify_signature` succeeds, cross-check that the organization used to select the webhook secret (`repository.owner.login`/`organization.login`) matches the owner segment of `repository.full_name` (and any other repository identifiers used later by handlers) before dispatching to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `WebhooksController#create`. Reject (422) any payload where these disagree.

### Proof of Concept
1. Shipit is configured with two GitHub organizations in `secrets.github`: `orgA` (victim, with stacks for `orgA/service`) and `orgB` (attacker-controlled, `webhook_secret` known to the attacker because they administer the corresponding GitHub App/org integration).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "orgA/service", "owner": { "login": "orgB" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orgB_webhook_secret, raw_body)` and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgB")` (from `repository.owner.login`) and successfully verifies the signature using `orgB`'s secret — request passes.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgA/service")` (from `repository.full_name`) and calls `stack.sync_github(expected_head_sha: params.after)` on `orgA`'s stack, even though the request was never signed by `orgA`.

Note: full exploitability depends on operational deployment specifics (whether the target Shipit instance is actually configured with multiple organizations and whether the attacker can obtain a secret for any one of them) that could not be fully verified from the indexed code alone; a Devin session with access to the full test suite and any multi-org deployment configuration would be needed to construct and run an end-to-end reproduction.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
