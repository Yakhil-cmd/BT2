### Title
Referenda decision/confirmation/timeout periods keep elapsing purely by block-number while voting/deposit calls can be paused by `pallet-tx-pause`/`pallet-safe-mode`, unfairly flipping "would-pass" referenda to Rejected/TimedOut - ([File: substrate/frame/referenda/src/lib.rs])

### Summary
The Goldfinch report's violated invariant is: *a state-machine that transitions a financial position toward a punitive terminal state (default) based purely on elapsed time, while an external/administrative pause prevents the affected party from taking the very action (`pay`) that would keep the position healthy.* The Polkadot SDK analog is `pallet-referenda`'s `service_referendum`/`nudge_referendum` logic, which advances a referendum toward `Rejected`/`TimedOut` purely based on block-number arithmetic (`decision.since`, `track.decision_period`, `track.confirm_period`, `T::UndecidingTimeout`), with no allowance for the fact that `pallet-tx-pause` (or `pallet-safe-mode`) can filter out the very calls voters/depositors need (`vote`, `place_decision_deposit`) to keep a referendum passing.

### Finding Description
`Pallet::service_referendum` in `substrate/frame/referenda/src/lib.rs` computes referendum outcomes strictly from block numbers: [1](#0-0) 
- While `deciding.is_some()`, if `now >= deciding.since.saturating_add(track.decision_period)` and the tally is not passing, the referendum is unconditionally marked `Rejected`.
- If it is passing but the confirmation window (`deciding.confirming`) elapses (`now >= t`), it becomes `Approved`; if confirmation is interrupted and the decision period runs out, it can end up rejected instead.
- Before deciding even begins, if `now >= timeout` (`status.submitted + T::UndecidingTimeout::get()`) the referendum is unconditionally marked `TimedOut`: [2](#0-1) 

None of these transitions check whether voters were actually able to cast votes (`pallet-conviction-voting::vote`) or place/refresh the decision deposit (`Referenda::place_decision_deposit`) during that window.

Separately, `pallet-tx-pause` provides a `Contains<RuntimeCall>` implementation wired into `frame_system::Config::BaseCallFilter` that can filter out (pause) any named call, including `vote` or `place_decision_deposit`, while leaving unrelated pallets/timers (like `pallet-referenda`'s own on-chain alarms serviced via `pallet-scheduler`) running normally: [3](#0-2) [4](#0-3) 

This is configured in the reference node runtime: [5](#0-4) 

Exactly as with Goldfinch's `TranchedPool.pay()` being `whenNotPaused` while `_assess()` still measures elapsed time, `pallet-referenda`'s alarm/timer mechanics (`ensure_alarm_at`, `note_one_fewer_deciding`, scheduled `nudge_referendum` calls) continue to fire via `pallet-scheduler` and evaluate strictly against `now` regardless of whether the calls that let a voter/depositor "keep the referendum healthy" are currently pausable/paused.

### Impact Explanation
If `TxPause::pause` (or `SafeMode::enter`/`force_enter`) is used to pause `ConvictionVoting::vote` or `Referenda::place_decision_deposit` — e.g., during an incident response, a chain-wide safe-mode activation, or any period where these calls are filtered — any referendum that is inside its `decision_period`/`confirm_period` or waiting on its `UndecidingTimeout` continues to count down unaffected. A referendum that would otherwise have gathered enough votes to pass, or would have had its decision deposit placed/topped up in time, can be irreversibly finalized as `Rejected` or `TimedOut` purely because voters/depositors were denied the ability to act during the pause — with no mechanism to extend the decision clock by the paused duration. This can incorrectly kill governance proposals (loss of intended on-chain action) analogous to Goldfinch protection sellers/borrowers being unfairly marked in default state due to an externally imposed pause that the state-machine's timers do not account for.

### Likelihood Explanation
`pallet-tx-pause` and `pallet-safe-mode` are both wired into the reference Substrate node runtime's `BaseCallFilter`, and pausing individual calls (`vote`, `place_decision_deposit`) is an explicitly supported, low-friction operation (`TxPause::pause` requires only `PauseOrigin`, e.g. root/governance — analogous to the Goldfinch multisig, not an attacker). Any runtime that composes `pallet-referenda`/`pallet-conviction-voting` together with `pallet-tx-pause` or `pallet-safe-mode` (a common defensive combination for incident response) is exposed. The referendum lifecycle code has no coupling to the pause state at all, so this is a deterministic, always-reachable timing/fairness gap rather than a probabilistic race.

### Recommendation
When `pallet-tx-pause`/`pallet-safe-mode` filters out calls relevant to a referendum's health (`vote`, `place_decision_deposit`), `pallet-referenda` should either:
- Extend `decision_period`/`confirm_period`/`UndecidingTimeout` by the duration those calls were paused (mirroring the report's recommendation to not count elapsed pause time toward default/rejection), or
- Provide a governance-controlled mechanism to pause/extend a referendum's own alarm (already partially exposed via `Root`-only `nudge_referendum`/`kill`/`cancel`) whenever a chain-wide pause affecting voting calls is active, and document this operational dependency clearly for runtime integrators combining these pallets.

### Proof of Concept
This finding is a structural/design-gap analog rather than a directly reproducible single-transaction exploit, and no local Rust/FRAME integration test was executed to confirm the end-to-end sequence (pausing `vote` via `TxPause::pause`, then advancing blocks through `pallet-referenda`'s `service_referendum` to observe an unwanted `Rejected`/`TimedOut` transition) due to tool/time constraints in this session. The code paths cited above (`service_referendum`'s unconditional block-number comparisons at `substrate/frame/referenda/src/lib.rs:1167-1237`, and `TxPause`'s `Contains` filter at `substrate/frame/tx-pause/src/lib.rs:279-288`) are present and wired together in the shipped reference runtime (`substrate/bin/node/runtime/src/lib.rs:311-345`), so the mechanical reachability (pause call → referendum timers unaffected) is verifiable by static code reading, but the deterministic negative outcome (an otherwise-passing referendum being rejected solely due to the pause window) has not been confirmed by an executed test in this session — status: **not run / unverified by execution**.
