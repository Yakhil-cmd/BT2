### Title
Stack-Scoped API Client Token Bypasses Stack Authorization in CCMenu Endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports optional per-stack scoping via `belongs_to :stack, optional: true` [1](#0-0) , and the base API controller enforces this scoping by restricting the resolvable stack set to only the client's assigned stack when one is present: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) . `Api::CCMenuController`, however, overrides `#stack` to resolve directly from the raw request parameter, completely bypassing that scoping: `@stack ||= Stack.from_param!(params[:stack_id])` [3](#0-2) .

### Finding Description
The trust binding that should hold is: **stack a token authorizes == stack the code touches**. `Api::BaseController#stacks`/`#stack` is the canonical enforcement point for that binding — any endpoint using it can only ever resolve a stack that the presented `ApiClient` is scoped to [2](#0-1) .

`Api::CCMenuController` inherits from `BaseController` and authenticates the same way (`ApiClient.authenticate(params[:token])`, falling back to `super` for Basic Auth) [4](#0-3) , and it still declares `require_permission :read, :stack` [5](#0-4) , which only checks that the string `"read:stack"` is present in `current_api_client.permissions` [6](#0-5)  — it performs no per-stack check. The actual per-stack restriction is supposed to come exclusively from the `stacks`/`stack` scoping helper in `BaseController`, but `CCMenuController` redefines `#stack` to skip it entirely, resolving any `params[:stack_id]` value against the global `Stack` table [3](#0-2) .

Before the attacker's request: an `ApiClient` scoped to stack A (`stack_id = A`, `permissions = ["read:stack"]`) can only enumerate/read stack A through any endpoint using `BaseController#stack` (e.g. `Api::StacksController#show`), because `stacks` is filtered to `Stack.where(id: A)` [2](#0-1) .

After: the same token, presented to `GET /api/stacks/:stack_id/ccmenu.xml`, resolves `stack_id` directly via `Stack.from_param!` with no scoping filter [7](#0-6) , letting it read CI/build status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) for any stack B ≠ A in the deployment, via the `shipit/ccmenu/project` template [8](#0-7) .

This is the direct analog of the reported bug class: an accounting/authorization key that is supposed to scope an actor's permitted resource (bond token index / stack_id) is silently ignored by one code path that acts on a caller-supplied value instead, breaking the equality `token.stack_id == stack_acted_upon`.

### Impact Explanation
This is a High-severity finding: it is an "unauthenticated read of stack state" in the sense defined by the rules — a token deliberately restricted to one stack's read access escalates to read build/deploy status of every stack on the Shipit instance, bypassing the very authorization boundary (`ApiClient#stack_id`) the application relies on for multi-tenant stack isolation.

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped `read:stack` API token (a routine, low-privilege credential intentionally handed out for narrow purposes such as CI dashboards) can trivially trigger this by changing the `stack_id` path segment in the CCMenu XML request — no additional privilege, session, or secret is required beyond the token they already legitimately hold.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, permission-scoped resolution (`stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so the `current_api_client.stack_id` restriction from `BaseController#stacks` is enforced consistently across all API endpoints.

### Proof of Concept
1. As an authorized user, issue a stack-scoped API client for Stack A with only `read:stack` permission (`ApiClient.create!(creator: user, name: 'ci', permissions: ['read:stack'], stack: stack_a)`), yielding token `T`.
2. Confirm `T` is properly scoped: `GET /api/stacks/{stack_b.id}` with Basic Auth `T` returns 200 for Stack A but the equivalent request scoped elsewhere in the normal API is restricted to Stack A only, per `Api::BaseController#stacks` [2](#0-1) .
3. Issue `GET /api/stacks/{stack_b.to_param}/ccmenu.xml?token=T` where `stack_b` is a different, unrelated stack.
4. Observe the response returns Stack B's build status XML (`name`, `activity`, `lastBuildStatus`, etc.) despite `T` being scoped only to Stack A, because `Api::CCMenuController#stack` bypasses the `current_api_client.stack_id` filter [3](#0-2) .
