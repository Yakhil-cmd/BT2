### Title
ERC721 `transferFrom` Used Instead of `safeTransferFrom` in Bridge Handle Path — Permanent Lock of Bridged ERC721 Assets - (File: `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer` uses the bare `IERC721.transferFrom` to deliver a bridged NFT to the user-specified destination address. If that destination is a contract that does not implement `IERC721Receiver.onERC721Received`, the token is silently transferred into the contract and permanently locked there. Using `safeTransferFrom` would instead revert the transaction, preserving the bridge's custody and allowing recovery.

---

### Finding Description

In `contracts/service_chain/bridge/BridgeTransferERC721.sol`, the non-mintBurn branch of `handleERC721Transfer` (line 69) calls:

```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
```

The ERC-721 standard defines two transfer variants:
- `transferFrom` — moves the token with no check on whether the recipient can handle ERC-721 tokens.
- `safeTransferFrom` — additionally calls `onERC721Received` on the recipient if it is a contract, reverting if the callback is absent or returns the wrong selector.

By using the unsafe variant, the bridge will successfully transfer the NFT into any contract address `_to`, even one that has no mechanism to move or recover the token. The transaction completes, the `HandleValueTransfer` event is emitted, the bridge nonce advances, and the token is gone.

The ERC-20 path in the same codebase already applies the correct pattern: `BridgeTransferERC20.sol` and `BridgeFee.sol` both import and use `SafeERC20` (`safeTransfer` / `safeTransferFrom`). The ERC-721 path has no equivalent safeguard. [1](#0-0) [2](#0-1) [3](#0-2) 

---

### Impact Explanation

When `handleERC721Transfer` is called with a `_to` address that is a contract without `onERC721Received`:

1. The bridge's internal state is fully updated: `_setHandledRequestTxHash`, `_updateHandleNonce`, and the `HandleValueTransfer` event are all committed before the transfer call.
2. `IERC721.transferFrom` succeeds (it does not check the recipient).
3. The NFT is now owned by `_to` but `_to` cannot move it — permanent loss.
4. The bridge nonce has advanced; the request is marked handled; there is no on-chain recovery path.

The corrupted value is the ERC-721 token balance of the destination contract: it receives a token it can never spend, and the rightful owner loses it permanently. This falls under **unauthorized burn / permanent loss of bridged assets**. [4](#0-3) 

---

### Likelihood Explanation

- Any user who initiates a cross-chain ERC-721 transfer and specifies a contract address as `_to` (e.g., a multisig wallet, a DeFi vault, or a smart-contract account that does not implement `IERC721Receiver`) triggers this path.
- The bridge operators relay the request faithfully; they have no way to detect or block the bad destination.
- Contract-to-contract NFT transfers are a common and legitimate use case, making accidental triggering realistic.

---

### Recommendation

Replace `transferFrom` with `safeTransferFrom` in `handleERC721Transfer`:

```solidity
// Before (line 69)
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

`safeTransferFrom` will revert if `_to` is a contract that cannot handle ERC-721 tokens, keeping the NFT in the bridge's custody and allowing the operator to retry with a corrected destination.

Note: `requestERC721Transfer` (line 129) pulls the token *into* the bridge contract using `transferFrom`. Since the bridge itself does not implement `onERC721Received`, changing that call to `safeTransferFrom` would break deposits. That line should remain as-is. [5](#0-4) 

---

### Proof of Concept

1. Deploy a minimal contract `NoReceiver` that does **not** implement `IERC721Receiver`.
2. On the child chain, call `requestERC721Transfer(tokenAddr, noReceiverAddr, tokenId, "")`.
3. Bridge operators observe the `RequestValueTransfer` event and call `handleERC721Transfer(txHash, from, noReceiverAddr, tokenAddr, tokenId, nonce, blockNum, "")` on the parent chain.
4. The call succeeds: `HandleValueTransfer` is emitted, `lowerHandleNonce` advances.
5. `IERC721(tokenAddr).ownerOf(tokenId)` returns `noReceiverAddr`.
6. `NoReceiver` has no function to call `transferFrom` or `safeTransferFrom`, so the token is permanently locked.
7. The bridge has no mechanism to re-issue or recover the token.
