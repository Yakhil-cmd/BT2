### Title
Cross-Organization Webhook Forgery via Mismatched Signature-Verification Identity and Handler-Trusted Repository Identity - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
The external report's core lesson is that a value the protocol *acts on* must actually be the value that was *verified/secured* — an oracle's TWAP price must correspond to the price the protocol trusts, or attackers can drive protocol behavior with data that was never properly authenticated. The equivalent trust binding in Shipit is: `verified organization == acted-upon repository`. `WebhooksController#verify_signature` selects which GitHub App/HMAC secret to check against using `repository_owner`, derived from the same attacker-controlled JSON body [1](#0-0) , while the actual event handlers act on a completely independent field of that same body, `repository.full_name`, without re-checking it belongs to the verified organization [2](#0-1) .

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration to validate the signature against by reading `repository_owner` straight out of the unauthenticated JSON payload: [3](#0-2) [1](#0-0) 

The signature is verified as HMAC over the *entire* raw body using the secret belonging to whichever organization's login string appears in `repository.owner.login` (or `organization.login`) [4](#0-3) . Shipit supports multiple independently configured GitHub Apps/organizations, each with its own `webhook_secret` [5](#0-4) .

Once the signature check passes, `create` hands the *entire* parsed body to the event handler, unfiltered: [6](#0-5) 

Every handler resolves the affected `Repository`/`Stack` from a *different* field of the same body — `repository.full_name` — via `Handler#repository_name`/`#stacks`, with no cross-check that this repository belongs to the organization that was used to verify the signature: [2](#0-1) 

This is exactly the "organization that authenticated versus the repository that is written" binding: the signature only proves the request was signed with organization A's secret; it does not prove anything about `repository.full_name`, which the handler blindly trusts. Concretely, `PushHandler#process` uses `repository.full_name` (via `stacks`) to look up any stack tracked under that name and force a resync to an attacker-chosen `after` SHA: [7](#0-6) . `CheckSuiteHandler` and `StatusHandler` similarly act on whatever repository/commit identifiers appear in the body without validating them against the verified organization: [8](#0-7) [9](#0-8) .

An attacker who controls (or is an admin of) any single GitHub organization/repository that has its own Shipit-configured GitHub App — and therefore can legitimately obtain a validly-signed webhook delivery for that org — can submit a raw HTTP POST directly to `/webhooks` with a body where `repository.owner.login` is set to *their own* org (satisfying `verify_signature`, since they know/control that org's `webhook_secret`) while `repository.full_name` is set to an arbitrary *other* tracked repository (`victim-org/victim-repo`) that they do not control. Because `verify_signature` and the handler each read a different, uncorrelated field of the same JSON, the forged cross-repository payload passes verification and is then acted upon as if it legitimately originated from the victim repository.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding required by scope, and results in cross-repository writes/actions without authorization: an attacker with legitimate but unprivileged control of one Shipit-tracked GitHub App/organization can force sync, status, and check-run state changes on a completely unrelated stack belonging to another organization/repository they have no access to. Depending on downstream handler logic (`stack.sync_github`, `commit.create_status_from_github!`, `schedule_refresh_check_runs!`), this can trigger unwanted syncs, poison commit status data used for deploy/merge gating, and refresh check-run states for repositories the attacker does not own — a cross-tenant integrity violation reachable purely from the public, unauthenticated `/webhooks` endpoint.

### Likelihood Explanation
Likelihood is moderate-to-high for any multi-organization Shipit deployment (explicitly documented and supported, see `docs/setup.md`): the attacker needs only to be an admin/owner of one org configured in Shipit — which is a routine, "unprivileged" position relative to any *other* tracked organization — and the ability to send a raw HTTP request with a body they fully control and a correctly computed HMAC using a secret they know for their own org. No GitHub App private key, no Shipit session, and no privileged Shipit account are required.

### Recommendation
`Handler#repository_name`/`#stacks` (and all callers) should validate that the repository resolved from the payload actually belongs to the same GitHub organization that was used to select the webhook secret in `verify_signature`, e.g., by passing the verified `repository_owner`/organization identity down into the handler and asserting `repository.full_name.split('/').first == verified_organization` (or equivalent) before acting, rather than trusting `repository.full_name` independently of the identity used for signature verification.

### Proof of Concept
1. Attacker is an org owner/admin for `attacker-org`, which has its own Shipit GitHub App entry with `webhook_secret = S` (per `docs/setup.md`'s multi-org config).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, body)>` themselves (they know `S`), and sets `X-Github-Event: push`.
4. `POST /webhooks` with this body/headers. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates the signature against `S`, which succeeds [3](#0-2) .
5. `create` invokes `PushHandler.call(params)`, which resolves `stacks` via `repository.full_name = "victim-org/victim-repo"` [2](#0-1)  and forces `stack.sync_github(expected_head_sha: "deadbeef...")` on the victim's stack [7](#0-6)  — despite the request never being authenticated as originating from `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
