## Title
Session fixation on GitHub OAuth login — session ID is never rotated after authentication (`app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`GithubAuthenticationController#callback` binds a freshly authenticated GitHub identity to the current session by writing `session[:user_id]` directly, without first calling `reset_session` (or otherwise rotating the session identifier). This mirrors the report's root-cause pattern of "changing state without first re-validating/re-establishing the trust boundary that other checks rely on": here, the *session identity* (GitHub login) changes, but the *session container* (cookie/session ID) that `Authentication#current_user` trusts is left untouched, breaking the binding `session_id == pre-authentication anonymous session_id == post-authentication authenticated session_id`.

### Finding Description
The OAuth callback action is: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true

  redirect_to(return_url)
end
```

`sign_in_github` resolves/creates a `User` from GitHub and stores the resulting `user.id` directly into the pre-existing session hash: [2](#0-1) 

There is no `reset_session` call anywhere in this controller before the privilege elevation (`session[:user_id]` transitioning from unset/anonymous to a concrete authenticated user id). Compare this to `logout`, which does call `reset_session`: [3](#0-2) 

Downstream, `Authentication#current_user` trusts whatever `session[:user_id]` currently resolves to, and grants access to any `Shipit.github_teams`-authorized functionality (stacks, deploys, rollbacks, API client management) purely based on that session: [4](#0-3) 

Because the session identifier (cookie value) is never rotated at the moment `session[:user_id]` changes from anonymous to authenticated, an attacker who can fix/know a victim's session identifier before login (e.g., by planting a cookie value the attacker also possesses, a classic session-fixation setup) will, once the victim completes the OAuth dance, share a session that is now bound to the victim's `User` record — while the attacker has never needed to know the victim's GitHub credentials, `github_access_token`, or `api_clients_secret`.

### Impact Explanation
This directly maps to the explicitly allowed High-severity category "session fixation / forced OAuth completion." A successful fixation grants the attacker the victim's authenticated Shipit session, i.e., escalation into whatever `Shipit.github_teams` authorization the victim holds — enabling unauthorized stack visibility, and depending on team membership, unauthorized deploys/rollbacks/task triggers, without ever needing a Shipit `ApiClient` token, webhook secret, or the victim's real GitHub token.

### Likelihood Explanation
The only precondition is the general web session-fixation setup (attacker able to set/know a value that will be used as the victim's session cookie, e.g. via a subdomain, cookie-planting header, or a scenario where the session cookie is not scoped/regenerated) plus getting the victim to complete the existing GitHub OAuth login flow. No repository write access, no privileged account, no TLS interception, and no possession of any Shipit secret is required — matching the rules' unprivileged-attacker constraint. This is a plausible, code-verifiable gap since `reset_session` is present for `logout` but conspicuously absent for `callback`.

### Recommendation
Call `reset_session` (or otherwise regenerate the session ID) in `GithubAuthenticationController#callback` immediately before assigning `session[:user_id]`, preserving only the `omniauth.origin`-derived `return_url` across the reset, mirroring the pattern already used in `logout`.

### Proof of Concept
1. Attacker obtains/fixes a session identifier `S` that will be used by the victim's browser for `Shipit.host` (via any session-fixation vector applicable to the deployment, e.g. a shared subdomain cookie or a client that accepts an externally supplied session id).
2. Victim, using session `S`, visits `/github/auth/github`, completes the real GitHub OAuth handshake.
3. `GithubAuthenticationController#callback` executes `session[:user_id] = sign_in_github(auth)` on session `S` — without rotating `S`.
4. Attacker, already in possession of session id `S`, now has a browser session where `current_user` resolves to the victim's `User` record, per `Authentication#find_current_user` / `#current_user`.
5. Attacker performs actions (viewing stacks, triggering deploys/rollbacks if the victim is on an authorized team) as the victim. [5](#0-4) [6](#0-5)

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end

    def logout
      reset_session
      redirect_to(root_path)
    end

    private

    def sign_in_github(auth)
      user = User.find_or_create_from_github(auth.extra.raw_info)
      user.update(github_access_token: auth.credentials.token)
      user.id
    end
```
