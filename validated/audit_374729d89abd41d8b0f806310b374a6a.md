### Title
Webhook signature verified against `repository.owner.login`'s GitHub App while the actual write target is looked up from `repository.full_name` in the same untrusted payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit installation, `WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the raw, attacker-controlled JSON body, but every event `Handler` subsequently resolves the repository/stack to act on using a *different* field of the same payload, `repository.full_name`, without ever checking that it belongs to the organization that was actually authenticated.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the untrusted payload and fetches the matching `GitHub App` config/secret for that org: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves the app config purely by the string passed in, with no relationship enforced beyond dictionary lookup: [3](#0-2) 

Once the signature check passes, `create` hands the *entire* raw JSON body to every handler for the event, unfiltered: [4](#0-3) 

Handlers resolve the target repository/stack independently, from `params.repository.full_name` (or `payload.dig('repository','full_name')`), a *different* key of the same JSON object used for signature-org selection: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` and `Repository#github_app` independently re-derive the owner from `full_name`/`owner` column, again with no cross check against the org used to verify the signature: [7](#0-6) [8](#0-7) 

The binding that should hold is: **organization that authenticated the request == organization/repository that is written to**. Because `repository_owner` (used for `verify_signature`) and `repository.full_name` (used for `from_github_repo_name`) are two independently-controlled fields inside one JSON document that is never re-signed field-by-field, an org whose own webhook secret is legitimately known to it (it is that org's own credential, configured by that org's own GitHub App, not a secret belonging to anyone else) can produce a validly-signed request body whose `repository.owner.login`/`organization.login` matches its own org (so `verify_signature` succeeds) while `repository.full_name` names a repository belonging to a *different* tenant/org hosted on the same Shipit instance. The push/pull_request handlers (`GithubSyncJob`, `ReviewStackAdapter`, label/close/reopen handlers) will then act on that other org's stack — queuing syncs, archiving/unarchiving review stacks, or updating pull-request state for a repository the requester never authenticated for.

### Impact Explanation
This breaks the "GitHub organization authenticated" vs "repository/stack written" binding described in the rules. A tenant that legitimately owns one GitHub App integration on a multi-org Shipit instance can cause writes (unarchive/archive review stacks, trigger `GithubSyncJob` commit ingestion, mutate pull-request state) against another tenant's repository/stack, which the attacker has no authorization for. This is a cross-repository/cross-tenant write achieved purely by crafting the JSON body fields inconsistently, which the controller never cross-validates. It does not require the victim's webhook secret, GitHub App private key, or any Shipit session/API token — only the attacker's own legitimately-issued webhook secret for their own org.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (`secrets.github` keyed by multiple orgs, i.e. `github_default_organization` non-nil), and (2) the attacker controlling (as a legitimate customer/tenant) at least one configured GitHub App/organization with a known webhook secret. Given those preconditions — which are exactly the conditions the multi-tenant feature is built for — crafting the divergent payload is trivial (HMAC-SHA1 over a JSON body they fully control). Likelihood is moderate: it depends on this deployment mode being used, but when it is, the exploit path requires no other privilege escalation.

### Recommendation
After `verify_signature` succeeds, re-derive `repository_owner` and cross-check it against every repository reference used downstream (`repository.full_name`, `organization.login`) before dispatching to handlers; reject (422) the webhook if they disagree. Alternatively, have `Handler#stacks`/`#repository` resolution take the authenticated organization as an explicit, required parameter instead of re-parsing it from the payload, so the org that verified the signature is structurally the only org whose repositories can be mutated.

### Proof of Concept
1. Deploy Shipit configured with two GitHub App organizations, `org-a` (attacker's own tenant, webhook secret known to attacker) and `org-b` (victim tenant, hosts `org-b/private-repo` with a Shipit stack).
2. Attacker crafts a `pull_request` webhook JSON body where:
   - `repository.owner.login` = `"org-a"` (or `organization.login` = `"org-a"`), so `repository_owner` resolves to `org-a`.
   - `repository.full_name` = `"org-b/private-repo"`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-webhook-secret, raw_body)` using their own known secret for `org-a`.
4. POST to `/webhooks`. `verify_signature` calls `Shipit.github(organization: "org-a")` and the HMAC check passes because the attacker used `org-a`'s real secret.
5. `PullRequest::OpenedHandler#repository` resolves `Repository.from_github_repo_name("org-b/private-repo")`, finds the victim's repository, and `ReviewStackAdapter#find_or_create!` provisions/mutates a review stack under `org-b`'s repository — a write the attacker was never authorized to perform, driven entirely by the mismatch between the org used for signature verification and the repository field used for the actual write.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```
