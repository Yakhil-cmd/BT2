Now I have the exact binding: `verify_signature` selects the GitHub App configuration (and thus the HMAC secret) using `repository_owner`, which is read directly from the untrusted JSON payload (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), while the handler that actually acts on the payload (`Handler#stacks`, used by `PushHandler`, etc.) resolves the target repository from a *different* payload field, `payload.dig('repository', 'full_name')`. Both fields are attacker-controlled and never cross-checked against each other, and only the "owner" field's chosen organization's secret is used to validate the signature.

### Title
Webhook signature is validated against an attacker-chosen organization while the acted-upon repository is read from an unrelated payload field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization config (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (with a fallback to `params.dig('organization', 'login')`) [1](#0-0) [2](#0-1) . That same raw HTTP body is later dispatched to handlers such as `PushHandler`, which independently determines the repository to act on via `payload.dig('repository', 'full_name')` in `Handler#repository_name` [3](#0-2) . Nothing binds the "owner" value used to select the verifying secret to the "full_name" value used to select the acted-upon repository/stack.

### Finding Description
This mirrors the report's root cause: a value that is supposed to bind cryptographic verification to the acted-upon data is instead derived independently, breaking the intended equality `organization authenticated == repository written`.

`verify_signature` fetches `Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature_header, request.raw_post)` [1](#0-0) . `GithubApp#verify_webhook_signature` explicitly states `return true unless webhook_secret` [4](#0-3) , and the setup docs mark the webhook secret as "(optional)" [5](#0-4) , with the shipped example config leaving `webhook_secret:` blank/nil for each org [6](#0-5) .

Consequently, in a multi-organization Shipit deployment where at least one configured organization has no `webhook_secret` set (an explicitly supported, documented configuration, not a misconfiguration outside the documented deployment model), an unauthenticated attacker can:
1. Send an unsigned/arbitrarily-signed POST to `/webhooks` with `repository.owner.login` set to that unprotected organization (satisfying `verify_signature`, since `webhook_secret` is blank there and the check short-circuits to `true`).
2. Set `repository.full_name` to any other organization/repository actually configured in Shipit (e.g., a fully-protected, high-value org/repo).
3. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name(repository_name)`, using `full_name` — a completely different field from the one that gated signature verification — and triggers `stack.sync_github(expected_head_sha: params.after)` for that unrelated repository/stack [7](#0-6) [3](#0-2) .

This is precisely the "organization authenticated versus repository written" binding named in scope: the code authenticates one identity (`repository.owner.login`) but writes/acts on another (`repository.full_name`), and these are never checked for consistency.

### Impact Explanation
This allows an unauthenticated attacker to forge GitHub webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) targeting any stack/repository configured under a *different*, fully-signature-protected GitHub organization, as long as any single organization in the same Shipit instance has no webhook secret configured. Effects include forcing `GithubSyncJob`, injecting fabricated commit statuses, or manipulating team/membership state tied to unrelated organizations — undermining the deploy-trust boundary between organizations hosted by the same Shipit instance, and enabling unauthorized triggering of stack synchronization/deploy-adjacent state changes without any valid credential for the targeted organization.

### Likelihood Explanation
Requires only that the deployment operate multiple GitHub organizations under one Shipit instance and that at least one configured organization omit `webhook_secret` — an explicitly documented, optional setting [5](#0-4) . No GitHub App private key, session, or `ApiClient` token is required; the attacker only needs to send a crafted, unsigned HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Bind signature verification to the same identity that handlers use for dispatch: derive `repository_owner` from `payload.dig('repository', 'full_name')` (splitting on `/`) rather than from `repository.owner.login`/`organization.login`, or better, verify the signature per-organization and additionally assert that `repository.owner.login` matches the owner segment of `repository.full_name` before invoking any handler. Additionally, consider requiring `webhook_secret` to be present for every configured organization (fail closed) rather than defaulting to `true` when absent.

### Proof of Concept
1. Configure Shipit with two organizations: `org-a` (no `webhook_secret`) and `org-b` (has `webhook_secret` and a protected stack `org-b/secret-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/secret-repo"
  }
}
```
No `X-Hub-Signature` header is required to pass, since `Shipit.github(organization: "org-a")` has no `webhook_secret`, causing `verify_webhook_signature` to return `true` unconditionally [8](#0-7) .
3. `WebhooksController#create` dispatches the parsed payload to `PushHandler`, which resolves the target stack from `full_name` = `org-b/secret-repo` [9](#0-8) [3](#0-2) , triggering `sync_github` for `org-b`'s stack despite the request never being authenticated against `org-b`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
