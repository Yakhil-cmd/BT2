### Title
Cross-organization team hijack via unscoped `github_id` lookup in `MembershipHandler` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by the numeric `params.team.id` (GitHub's globally-unique team id), with no check that the webhook's signing organization (`params.organization.login`, which is what `verify_signature` binds the HMAC to) actually owns that team. In a multi-org Shipit deployment, any org configured with its own GitHub App/`webhook_secret` can forge a `membership` `action:'added'` event that names a *different* org's team id, and the handler will happily append arbitrary `member.login` users into it.

### Finding Description
Binding claimed: `orgs whose secret can write to a Shipit.github_teams team == 1 (its real owner)`.

Trace:
- `WebhooksController#verify_signature` picks the HMAC secret via `Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) [2](#0-1) . This only proves the payload was signed with the secret belonging to the org *named in the payload*.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` — matching purely on the GitHub-global team id, never comparing it against `params.organization.login` or the existing `team.organization` column [3](#0-2) .
- For an *existing* `Team` row (e.g. one already enumerated in `Shipit.github_teams`, built from the primary org's `oauth.teams` config via `github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }` [4](#0-3) ), `find_or_create_by!` finds it by `github_id` and skips the creation block entirely — `team.organization` is never re-validated. `team.add_member(member)` is then invoked with the attacker-supplied `member.login` [5](#0-4) .
- `Shipit.github` supports a documented multi-org configuration schema where distinct orgs each have their own `app_id`/`private_key`/`webhook_secret` (see `test/dummy/config/secrets_double_github_app.yml` with `OrgOne`/`OrgTwo`, and `docs/setup.md`'s "multiple Github applications for different Github organizations" section). An org that legitimately owns one of these separate App configurations knows its own `webhook_secret` and can compute a valid `X-Hub-Signature` for any payload body it wants, as long as `organization.login`/`repository.owner.login` in that payload matches its own org key.
- `User#authorized?` trusts team membership directly: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , so any login injected into that `Team` record becomes authorized.

Exploit flow: an admin of "OrgTwo" (a legitimately configured, but non-privileged-team-owning org in the same multi-org Shipit instance) sends `POST /webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with OrgTwo's own `webhook_secret`, and body:
```json
{"action":"added","team":{"id":<victim_team_github_id>,"name":"...","slug":"...","url":"..."},
 "organization":{"login":"OrgTwo"},"member":{"login":"attacker-controlled-login"},
 "repository":{"owner":{"login":"OrgTwo"}}}
```
`verify_signature` passes (OrgTwo's own secret matches). `find_or_create_team!` finds the pre-existing victim team by `github_id` (a value that is not secret — GitHub team ids are visible via the `org_teams`/`GET /orgs/{org}/teams` API and elsewhere) and adds the named member to it. Repeating this with different `member.login` values for the same `team.id` enrolls an arbitrary list of logins into that privileged team, purely from OrgTwo's own secret.

None of the existing guards catch this: `verify_signature` only authenticates *which org sent the request*, not which team the payload is allowed to mutate; the `ExplicitParameters` schema in `MembershipHandler` validates types/presence only, not cross-field organizational consistency; and there is no `require_permission!`/ownership check inside `MembershipHandler#process`.

### Impact Explanation
An attacker who controls any org configured in a multi-org Shipit deployment can enroll arbitrary GitHub logins into any `Shipit.github_teams` team (including ones exclusively belonging to a different, unrelated org), granting those logins `User#authorized?` access to the whole Shipit instance. This is a High-severity escalation into `Shipit.github_teams` authorization, matching the rubric's "escalation into `Shipit.github_teams` authorization" impact category. It is fully repeatable — one webhook per injected login, and also reversible/abusable via `action:'removed'` to deauthorize legitimate members of the victim team.

### Likelihood Explanation
Requires a multi-org Shipit deployment where more than one organization has its own independently-configured GitHub App/`webhook_secret` (a documented, supported configuration per `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`). The attacker must control (own/administer) at least one such configured org — a materially lower privilege bar than controlling the org that actually owns the target `Shipit.github_teams` team. The target team's numeric `github_id` is not a secret (discoverable via GitHub's team API) and the `Team` row typically already exists once the corresponding team has ever synced/webhooked once. Attack cost is a single crafted HTTP POST per injected login, fully scriptable and repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/update by both `github_id` and `organization` (`Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and explicitly reject/raise when an existing `Team` with that `github_id` has an `organization` different from `params.organization.login`, rather than silently reusing the record.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":membership from a different org cannot add members to another org's team" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify'

  @request.headers['X-Github-Event'] = 'membership'
  # signature stubbed to succeed for org 'attacker-org' regardless of secret used
  Shipit.expects(:github).with(organization: 'attacker-org').returns(stub(verify_webhook_signature: true))

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'injected-attacker-login' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  assert_no_difference -> { Team.count } do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  victim_team.reload
  # BROKEN BINDING (current code): assert victim_team.members.exists?(login: 'injected-attacker-login') # true, attacker succeeded
  # EXPECTED (fixed code):
  refute victim_team.members.exists?(login: 'injected-attacker-login')
end
```
Both sides of the binding — "orgs whose secret can write to a `Shipit.github_teams` team" — should equal `{ 'shopify' }` (1, the real owner); the current code allows `{ 'shopify', 'attacker-org', ... }` (every configured org), confirming the vulnerability.

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)

          end
        end

        end
