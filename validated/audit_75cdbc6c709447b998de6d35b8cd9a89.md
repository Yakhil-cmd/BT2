### Title
Cross-organization webhook forgery via mismatched signing-organization and target-repository fields - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against using `repository_owner`, an attacker-controlled field read from the still-unverified JSON body [1](#0-0) , while the actual repository/stack acted upon by the event handlers is taken from a *different* field of the same body, `repository.full_name`, via `Handler#repository_name` [2](#0-1) . Nothing binds these two fields together, so a signature that is valid for one organization's secret can be used to authorize a payload whose `repository.full_name` names a stack belonging to a completely different, unrelated organization/repository.

### Finding Description
`repository_owner` is computed purely from the JSON body, before any cryptographic check has occurred: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [3](#0-2) . This value is used to fetch the corresponding `GitHubApp` config and verify the HMAC signature against *that organization's* `webhook_secret` [1](#0-0) , and `verify_webhook_signature` even short-circuits to `true` when no `webhook_secret` is configured for that organization [4](#0-3) .

Once the signature check passes, `create` hands the **entire raw payload** to every registered handler for the event, unfiltered by `repository_owner` [5](#0-4) . Handlers such as `PushHandler` resolve the target `Stack`/`Repository` using `payload.dig('repository', 'full_name')` [2](#0-1) [6](#0-5) , a field that is never checked for consistency with `repository.owner.login`/`organization.login` used for signing.

Shipit explicitly documents and supports a multi-organization configuration where each organization has its own `github.<org>.webhook_secret` [7](#0-6)  (see also `config/secrets.development.shopify.yml`). In that supported topology, an attacker who legitimately controls (or knows the webhook secret / has no-secret access for) one configured organization can craft a webhook body where:
- `repository.owner.login` = the attacker's own configured organization (used only to select/pass the signature check, e.g. an org with `webhook_secret` unset, which trivially passes per the `return true unless webhook_secret` bypass), and
- `repository.full_name` = `"victim-org/victim-repo"`, a stack tracked under a completely different, protected organization.

The signature check binds "the organization that authenticated" (via `repository_owner`) but the handler logic acts on "the repository that is written" (via `repository.full_name`) — exactly the trust boundary the engine intends to enforce (per-organization/per-repo webhook authenticity) but fails to bind together.

### Impact Explanation
This breaks the equality the engine relies on: `organization authenticated == organization owning the acted-upon repository`. By exploiting the mismatch, an unprivileged actor who only controls one configured (low/no-secret) organization can forge `push`, `status`, `check_suite`, or `membership` events that are processed as if they came from a different organization's repository. For `push`, this triggers `stack.sync_github(expected_head_sha:)` for stacks belonging to a repository the attacker does not own [6](#0-5) , causing GitHub state to be resynced/deploy-eligible state changed based on a forged, cross-organization trigger — an unauthorized action against a stack outside the attacker's control, meeting the "unauthorized deploy/rollback trigger" bar for High severity in multi-tenant Shipit deployments.

### Likelihood Explanation
Requires: (1) the Shipit instance configured for multiple GitHub organizations (a documented, supported setup), and (2) the attacker controlling or having signing capability (or a secret-less config) for at least one of those organizations while targeting a stack under another. This is a realistic scenario for shared/multi-tenant Shipit installs serving several orgs, but not applicable to single-organization deployments, so likelihood is moderate and configuration-dependent.

### Recommendation
After verifying the HMAC signature, additionally assert that `repository.owner.login` (or `organization.login`) equals the owner segment of `repository.full_name` for every event before dispatching to handlers, rejecting mismatches with `422`. Alternatively, scope handler processing/`Repository.from_github_repo_name` lookups to only repositories owned by the same organization that was cryptographically verified in `verify_signature`.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (webhook secret unset/known to attacker) and `victim-org` (protected, unknown secret), both tracked per `docs/setup.md`'s multi-org example.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes/omits the `X-Hub-Signature` appropriate for `attacker-org`'s (absent) secret, which `verify_webhook_signature` accepts (`return true unless webhook_secret`) [4](#0-3) .
4. `WebhooksController#verify_signature` passes because it only checked `attacker-org` [1](#0-0) .
5. `PushHandler#process` resolves stacks via `repository.full_name` = `victim-org/victim-repo` and calls `stack.sync_github(expected_head_sha:)` on the victim's stack [6](#0-5) , an action never authenticated for `victim-org`.

```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```markdown
## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
```
