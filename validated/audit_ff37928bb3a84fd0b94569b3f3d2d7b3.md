### Title
Missing `return` after malformed-payload catch block causes double-handling of a private payment chain in `handleSavedPrivatePayments` - ([File: network.js])

### Summary
`network.js`'s `handleSavedPrivatePayments()` demuxes/parses locally-queued private payment chains (`unhandled_private_payments`) sent by a payment counterparty. When hashing a malformed private-element payload throws, the error branch handles the error and deletes/finalizes the row via `deleteHandledPrivateChain(..., cb)`, but execution falls through to the rest of the function instead of returning, so the same (already "freed"/finalized) chain state is used again to call `privatePayment.validateAndSavePrivatePaymentChain(...)`. This mirrors the CVE-2021-3497 bug class: on the error path of parsing a malformed structure, code continues to operate on state that should have been considered already disposed of.

### Finding Description
In `handleSavedPrivatePayments`, for every queued row, `validateAndSave` is defined as: [1](#0-0) 

The `try` computes `json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true)`. A wallet counterparty fully controls the JSON content of `arrPrivateElements[0].payload` (it is delivered via `private_payment_chains`/`handlePrivatePaymentChains` and stored verbatim as `row.json` in `unhandled_private_payments`), so a crafted payload can be malformed enough to make `getBase64Hash` throw (analogous to a malformed Matroska/media structure triggering an error path in a demuxer).

On throw, the `catch` block:
- logs the error,
- optionally sends an error result to the peer,
- calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — this **deletes the DB row and invokes `cb` (the `async.each` iteratee callback)**, effectively finishing/"freeing" this queue item for the surrounding `async.each` control flow.

There is **no `return`** after this `catch` block. Execution continues to: [2](#0-1) 

This means:
1. `key` is built using `json_payload_hash`, which is `undefined` because the `try` never completed (var-hoisted, still initializes to `undefined`).
2. `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` is invoked a second time on the very data whose processing was just declared done via `deleteHandledPrivateChain`/`cb()`.
3. Depending on the outcome of this second validation attempt, `ifOk` or `ifError` will call `deleteHandledPrivateChain(...)` **again**, invoking `cb` a **second time** for the same `async.each` item, and emitting `'private_payment_validated-...undefined-...'` events that no code is listening for (since the queued listener key in `wallet.js`/`handlePrivatePaymentChains` is built from the correctly-computed hash, not `undefined`).

Double-invoking the `async.each` iteratee callback is a classic "use of already-completed/freed continuation" bug: `async.each`'s completion handler can fire prematurely or be invoked twice, corrupting the accounting of `assocNewUnits`/`arrNewUnits` and the `unlock()` call for the `"saved_private"` mutex, and it also means a chain that already threw on hash computation is nevertheless pushed through `validateAndSavePrivatePaymentChain`, which begins a real DB transaction (`BEGIN`) in `private_payment.js`: [3](#0-2) 

### Impact Explanation
An attacker who can post a private payment chain with a payload that is well-formed enough to pass `handlePrivatePaymentChains`'s shallow validation in `wallet.js` (which only checks presence of fields, not that hashing succeeds) but fails at `objectHash.getBase64Hash`, can:
- Cause a private payment chain to be processed twice against the same row, with an extra un-keyed database transaction (`BEGIN`/`COMMIT`/`ROLLBACK`) launched over the same malformed data.
- Corrupt the `async.each` completion bookkeeping (double `cb()` calls), which can cause the mutex `unlock()` for `["saved_private"]` to fire out of turn or `assocNewUnits` handling to run in an inconsistent state, leading to a node getting stuck processing/serving private payments or missing notifications for legitimately accepted chains that were queued in the same batch — a denial of the wallet's ability to confirm/relay new private payment chains reliably.
- Trigger the second `validateAndSavePrivatePaymentChain` call to attempt a real commit against un-vetted malformed data via `writer.saveJoint`-adjacent code paths, increasing the attack surface for downstream state corruption.

This does not, by itself, directly cause unauthorized spending or supply inflation, but it does create node disagreement on request completion / stuck processing of private-payment queues, an availability impact analogous to the CVE's use-after-free-on-error-path root cause.

### Likelihood Explanation
Reaching this path only requires a counterparty (a normal, unprivileged wallet peer engaging in a private payment) to send a `private_payment_chains` message whose head element's `payload` is valid enough to satisfy `handlePrivatePaymentChains`'s structural checks in `wallet.js` (non-empty object, valid asset string, non-empty `inputs`/`outputs` arrays of non-empty objects) but is not stably hashable by `objectHash.getBase64Hash` (e.g., containing values that make hashing throw, such as unsupported/cyclical or otherwise adversarial JSON substructures accepted by the initial checks). Since the code is reached from message handling that any correspondent device can trigger, likelihood is moderate-to-high for a targeted attacker; it does not require special privileges.

### Recommendation
Add an explicit `return` (or restructure with `return cb(...)`/`if/else`) after the `catch` block in `validateAndSave` inside `handleSavedPrivatePayments`, so that once `deleteHandledPrivateChain` has been invoked for a malformed payload, execution does not fall through to compute `key` from an `undefined` hash and re-invoke `validateAndSavePrivatePaymentChain`. E.g.:
```js
try {
    var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
}
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```

### Proof of Concept
1. A device/peer sends a `private_payment_chains` message whose `arrChains[0][0].payload` satisfies the shallow checks in `wallet.js`'s `handlePrivatePaymentChains` (`isNonemptyObject`, non-empty `outputs`/`inputs` arrays of non-empty objects, string `asset`) but is crafted so `objectHash.getBase64Hash(payload, true)` throws (e.g., a value type/structure not supported by the hashing routine, or a self-referential/edge-case object that the initial structural check does not catch).
2. This gets queued into `unhandled_private_payments` and, when `handleSavedPrivatePayments` runs, hits the `catch` in `validateAndSave`.
3. Because of the missing `return`, `deleteHandledPrivateChain` runs and invokes `cb()`, and immediately afterward `privatePayment.validateAndSavePrivatePaymentChain` is invoked a second time on the same `arrPrivateElements`, eventually invoking `cb()` again from within its `ifOk`/`ifError` handler — resulting in `cb` being called twice for one `async.each` item, which async libraries treat as an error/undefined-behavior condition affecting the batch's completion callback and the `["saved_private"]` mutex unlock timing. [4](#0-3)
