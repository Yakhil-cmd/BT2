## Analysis

This confirms the vulnerability. `Handler#stacks` resolves the *target* repository/stack using `payload.dig('repository', 'full_name')` [1](#0-0) , while `WebhooksController#verify_signature` resolves the *signing* organization used to select the `webhook_secret` using `params.dig('repository', 'owner', 'login')` [2](#0-1) . These two fields are read independently from the same untrusted, attacker-supplied JSON body and are never cross-checked against each other, exactly mirroring the reported bug class: a field that is acted upon (`full_name`, used to select the stack that gets synced/mutated) is never covered by the check that is actually performed (the signature verification keyed on `owner.login`).

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization [3](#0-2) . In any multi-org install (`lib/shipit.rb`'s `github_app_config`/`github_organizations` support multiple orgs under `secrets.github` [4](#0-3) ), it is common/plausible to have at least one org with `webhook_secret: nil` (as shown even in the shipped sample config [5](#0-4) ). An attacker who knows of, or controls, such a zero-secret (or otherwise-known-secret) org can forge `repository.owner.login` to name that org while setting `repository.full_name` to `victim-org/victim-repo`. `verify_signature` authenticates against the attacker's org's secret (trivially satisfied or forgeable) and passes [6](#0-5) , but `PushHandler#process` then acts on the victim stack looked up by `full_name` [7](#0-6) , enqueuing `stack.sync_github(expected_head_sha: ...)` → `GithubSyncJob`, which fetches commits from GitHub for that stack using the stack's own `github_api`/repository and appends them, potentially fast-forwarding CI/deploy state for a repository the attacker doesn't own [8](#0-7) .

### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but events are dispatched against the repository named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the `X-Hub-Signature` against using `params.dig('repository', 'owner', 'login')`, but the actual side effects of the webhook (which stack/repository gets synced) are determined by the unrelated `payload.dig('repository', 'full_name')` field read later in `Handler#stacks`. Because both fields come from the same unauthenticated JSON body and are never cross-validated, an attacker can pick which org's secret authenticates the request while still targeting an arbitrary victim repository/stack.

### Finding Description
`verify_signature` computes `repository_owner` from the raw, unverified payload and uses it to look up the `GitHubApp` (and thus the `webhook_secret`) to check the signature against [9](#0-8) . Once the signature check "passes" for that chosen organization, `create` dispatches the full, still-attacker-controlled `params` hash to the registered handlers [10](#0-9) . `Handler#stacks`/`#repository_name`, however, resolve the target stack via `payload.dig('repository', 'full_name')`, a completely separate field of the same payload [1](#0-0) . There is no requirement that `owner.login` and the owner encoded in `full_name` refer to the same repository/org.

If the resolved organization has no `webhook_secret` configured, `verify_webhook_signature` returns `true` unconditionally regardless of the signature header [3](#0-2) , so no secret at all is needed for that branch. Multi-organization Shipit installs are explicitly supported (`Shipit.github_organizations`, `github_app_config`) [4](#0-3) , and it is a supported/likely configuration state to have an org onboarded without a webhook secret set yet (as illustrated by the shipped sample config with `webhook_secret: # nil` for both orgs) [11](#0-10) .

This is the direct analog of the reported bug: `deposit_for()` checked `_locked.end` while the caller (`claim()`) had already determined the lock state via `perpetuallyLocked`, so the verified condition didn't match the condition actually governing the state being mutated. Here, the verified field (`owner.login`) does not match the field actually used to select the mutated resource (`full_name`).

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written." An attacker with knowledge of (or control over) any single organization configured in a multi-tenant Shipit instance — particularly one with no `webhook_secret` set — can forge push/status/pull_request/check_suite/membership webhook payloads that pass signature verification under that org's identity while acting on an arbitrary victim stack's data (triggering `GithubSyncJob` commit ingestion, `Status` creation, pull-request-driven review-stack provisioning, or `Membership`/`Team` mutations for `membership` events) for repositories/orgs the attacker has no legitimate relationship with. This is an authentication-bypass-class issue: the request is treated as an authenticated GitHub webhook for the victim repository despite never being signed by the victim's/GitHub's own secret for that repository.

### Likelihood Explanation
Likelihood is high in any deployment with more than one configured GitHub org/app, or any org lacking a `webhook_secret`, since exploitation requires only crafting an HTTP POST with a mismatched `repository.owner.login` vs `repository.full_name` — no privileged Shipit session, API token, or webhook secret for the victim org is required.

### Recommendation
Derive the organization used for signature verification from the same repository identity that handlers act on (e.g., parse `owner` from `repository.full_name` itself, or require that `repository.owner.login` matches the owner segment of `repository.full_name`/`organization.login` before proceeding), and reject the webhook if they disagree. Additionally, avoid the silent "verified = true when webhook_secret is blank" fallback in `verify_webhook_signature`, or gate it behind an explicit, documented opt-in, so an unconfigured org can't be used to bypass signature checks for another org's traffic.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `attacker-org` (no `webhook_secret` set) and `victim-org` (has a stack tracking `victim-org/victim-repo`).
2. POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
No valid `X-Hub-Signature` is required, since `attacker-org` has no configured secret, so `verify_webhook_signature` returns `true` [12](#0-11) .
3. `verify_signature` passes because it resolved `Shipit.github(organization: 'attacker-org')` [6](#0-5) .
4. `PushHandler#process` resolves `stacks` via `full_name` = `victim-org/victim-repo` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack [7](#0-6) , enqueuing `GithubSyncJob` against the victim repository despite the webhook never having been authenticated for `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
