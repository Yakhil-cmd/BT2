### Title
Cross-Organization Forged Commit Status Enables Unauthorized CI Bypass and Merge - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an incoming webhook's HMAC signature against by reading `repository.owner.login`/`organization.login` out of the **same untrusted, unverified JSON body** it is about to authenticate. The field used for org selection (used to pick the signing key) is never bound to the field the `status` event handler actually acts on (`Commit.where(sha: params.sha)`, which is *not scoped to any repository at all*). This breaks the equality that should hold: `organization whose secret authenticated the request == repository/commit the request is allowed to mutate`.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
```
and [2](#0-1) 
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`repository_owner` is parsed from the raw, attacker-controlled request body *before* the signature is validated, and only used to pick which org's secret to HMAC-check the whole body against.

Once verified, the body is dispatched to handlers with no further binding to that same organization. `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb`) does: [3](#0-2) 
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
It looks up `Commit` purely by `sha` — it does **not** consult `repository.full_name`/`owner.login` at all (unlike `PushHandler`/PR handlers, which at least route through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`). Even for those other handlers, the repository field used for routing (`repository.full_name`) is a completely different JSON field from the one used for signature-org selection (`repository.owner.login`), so nothing enforces that they agree.

This means: an attacker who legitimately controls one organization's GitHub App webhook secret in a multi-org Shipit deployment (`config/secrets.yml` `github: <org>: webhook_secret:`) can POST a forged `X-Github-Event: status` webhook, signed with *their own org's* secret, but naming an arbitrary commit `sha` belonging to a totally different organization/repository tracked by the same Shipit instance. Because commit SHAs are public (visible via GitHub UI/API for any repo the attacker can view), this is trivial to obtain for a target repo.

`Commit#create_status_from_github!` → `add_status` then calls `stack.schedule_merges` when the injected status is `success`/`pending`: [4](#0-3) 
```
if previous_status.simple_state != new_status.simple_state
  ...
  stack.schedule_merges if new_status.pending? || new_status.success?
end
```
and marks the commit deployable via `deployable?`: [5](#0-4) 
```
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
```
`schedule_continuous_delivery` is also driven by `deployable?` and `stack.continuous_deployment?`, so injecting a fabricated "success" status for a commit belonging to a *different* organization's stack can trigger Shipit's own automatic merge queue processing and/or continuous deployment for that stack, using Shipit's own `GITHUB_TOKEN` for that target org.

### Impact Explanation
This breaks the binding "organization whose signature authenticated the webhook == repository/stack the webhook payload is permitted to mutate." An attacker who only controls one org's webhook secret can forge CI/commit-status state for commits belonging to an entirely unrelated organization managed by the same Shipit instance, causing Shipit to treat unreviewed/failing commits as CI-passed and schedule an unauthorized merge or an unauthorized automatic deploy via `stack.schedule_merges` / `schedule_continuous_delivery`, using the target organization's real `GITHUB_TOKEN`. This matches the "unauthorized deploy, rollback or merge" and "cross-repository writes" Critical impact criteria.

### Likelihood Explanation
Requires the attacker to be a legitimate (if unprivileged relative to the *target* org) party that knows a webhook secret for at least one organization configured on the shared Shipit instance — a realistic scenario for any multi-tenant/multi-org Shipit deployment as documented (`docs/setup.md`, `config/secrets.development.shopify.yml`). No access to the target org's secret, Shipit session, or `ApiClient` token is required, and target commit SHAs are typically public. The `status` handler path requires no additional per-repo checks, making this the most direct exploitation route.

### Recommendation
Bind webhook-signature verification and event routing to the same, single source of truth: after verifying the signature with the organization's secret, re-derive/require that `repository.owner.login` (or `organization.login`) used for secret selection matches the `repository.full_name`'s owner that handlers subsequently act upon, and reject mismatches. Additionally, `StatusHandler#process` should filter `Commit` by `stack.repository` (derived from the verified organization/repository) rather than a bare, repository-agnostic `sha` lookup, so a forged event cannot touch commits outside the authenticated organization's repositories.

### Proof of Concept
1. Shipit instance configured with two GitHub Apps/orgs in `secrets.yml`: `org-attacker` (secret known to the attacker, e.g. because they administer that org's GitHub App) and `org-victim` (tracks stack `org-victim/target-repo`, `continuous_deployment: true`, with branch protection requiring a `ci/build` status).
2. Attacker fetches the SHA of an unreviewed/malicious commit pushed to `org-victim/target-repo` (public info).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "<victim-repo-target-sha>",
  "state": "success",
  "context": "ci/build",
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-attacker/some-repo" }
}
```
signed (`X-Hub-Signature`) with `org-attacker`'s `webhook_secret`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-attacker")` (from `repository.owner.login`), verifies successfully with the attacker's own known secret.
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which ignores `repository` entirely and finds `Commit.where(sha: "<victim-repo-target-sha>")` — the actual commit belonging to `org-victim`'s stack — and calls `commit.create_status_from_github!(params)`, recording a fabricated "success" CI status.
6. `Commit#add_status` sees the state transition to success and calls `stack.schedule_merges`, and `schedule_continuous_delivery` fires because `deployable?` now returns true, causing Shipit to merge/deploy the victim commit using `org-victim`'s real GitHub credentials — without ever knowing `org-victim`'s webhook secret.
