### Title
Webhook signature verification binds the wrong organization field, allowing cross-repository writes via a mismatched `repository.full_name` payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a signature against using `repository_owner`, parsed from `repository.owner.login` (or `organization.login`), but every webhook `Handler` subclass resolves the target `Stack`/`Repository` using a *different* payload field, `repository.full_name`. Because the HMAC signature only proves the raw request body was signed with *some* organization's configured `webhook_secret` — and Shipit supports multiple organizations, each with its own independently configured secret — an operator/attacker who legitimately controls the webhook secret for organization A can forge a payload whose `repository.owner.login` is `A` (so signature verification passes and picks A's secret) while `repository.full_name` points at a repository belonging to organization B. This breaks the intended binding "organization authenticated by signature == repository that gets written to," letting an attacker act on stacks belonging to a repository/organization they do not control.

### Finding Description
`verify_signature` in [1](#0-0)  resolves `repository_owner` via: [2](#0-1) 

and uses it purely to pick which `Shipit.github(organization:)` instance/secret to verify the `X-Hub-Signature` against. It does not otherwise constrain which repository the event content is allowed to reference.

Every handler that ultimately mutates state (push, status, check_suite, membership, pull_request, etc.) inherits from `Handler` and resolves the affected stacks by a *different* field: [3](#0-2) 

`PushHandler#process`, for example, uses `stacks` (derived from `repository.full_name`) to sync any matching, non-archived stack for the pushed branch: [4](#0-3) 

Because Shipit is explicitly designed to be configured with per-organization GitHub Apps/secrets (`Shipit.github(organization: ...)`, documented in `docs/setup.md`), a party who is an authorized member/admin of one connected GitHub organization (and therefore knows or can generate a validly-signed payload for that organization's app/webhook secret) can send a webhook whose `repository.owner.login` matches their own organization (satisfying `verify_signature`) but whose `repository.full_name` is set to `victim-org/victim-repo`. The signature check passes because it is only proving "this body was HMAC-signed with organization A's secret" — it never asserts that the `repository` object inside the payload actually belongs to organization A.

This breaks the equality that should hold: `organization authenticated by signature == organization/repository whose stacks are written`. The webhook signature authenticates a payload body against organization A's secret, but the code that acts on the payload trusts a repository field that can name organization B.

### Impact Explanation
This allows cross-repository writes: an attacker who is a legitimate collaborator of one Shipit-connected organization can trigger `Stack#sync_github` (`GithubSyncJob`), create bogus commit statuses via `StatusHandler`, or invoke other handler side effects (`CheckSuiteHandler`, `MembershipHandler`, `PullRequestHandler` family) against stacks/repositories belonging to a completely different organization that they have no legitimate access or write permission to. This meets the Critical bar of "cross-repository writes" defined in scope, since it crosses the deployment-trust boundary between "organization that authenticated the request" and "repository whose stacks are affected."

### Likelihood Explanation
Exploitability requires the attacker to control (or be able to produce validly-signed payloads for) at least one organization onboarded to the same multi-tenant Shipit instance — a realistic scenario for any Shipit deployment serving more than one GitHub organization, since each organization's webhook secret is independent and none of them are meant to authorize actions on another organization's repositories. No repository write access, GITHUB_TOKEN, or API client credentials are required — only the ability to deliver an HTTP POST with a valid signature for one configured organization, which is the exact channel `WebhooksController#create` exposes unauthenticated to the public internet.

### Recommendation
After signature verification succeeds for `repository_owner`, additionally verify that the resolved organization/owner matches the owner embedded in `repository.full_name` (and in any other identifying field used by the handlers) before invoking any handler. Concretely, `Handler#stacks`/`Handler#repository_name` should validate that `payload.dig('repository', 'full_name')` starts with `"#{repository_owner}/"`, or `verify_signature` should derive its lookup key from the same field the handlers use (`repository.full_name`'s owner segment) so the same identifier is both signed-over and trusted.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own `github.webhook_secret` (per `docs/setup.md`), and both have stacks configured (e.g. `org-a/repo-a`, `org-b/repo-b`).
2. Attacker is a legitimate GitHub org owner/admin of `org-a` and therefore can obtain (or self-generate, since they administer the webhook delivery for their own org) a validly HMAC-signed push payload using `org-a`'s `webhook_secret`.
3. Attacker crafts the JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "org-a" },
       "full_name": "org-b/repo-b"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-webhook-secret, body)` and POSTs to `/github/webhooks`.
5. `verify_signature` resolves `repository_owner == "org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature validates successfully [5](#0-4) .
6. `PushHandler.call(params)` runs, and `Handler#repository_name` resolves `"org-b/repo-b"` from `repository.full_name`, matching `org-b`'s stack and triggering `stack.sync_github(expected_head_sha: ...)` on a repository the attacker does not control [3](#0-2) [4](#0-3) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
