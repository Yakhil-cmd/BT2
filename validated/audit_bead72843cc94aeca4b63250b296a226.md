## Title
Missing authorization when validating a new address definition with an unresolved nested `address` reference - (File: definition.js)

### Summary
`validateDefinition()` in `definition.js` decides whether a candidate address/asset-condition definition structurally contains a signature ("each branch must have a signature") before that definition is ever allowed to be registered as an address's spending condition. For the `['address', <other_address>]` operator, when the referenced address's definition cannot yet be resolved (neither stored on-chain nor supplied by a co-author in the same unit), the code is hard-coded to treat this branch as if it satisfies the signature requirement, unconditionally: [1](#0-0) 

```
ifDefinitionNotFound: function(definition_chash){
//	if (objValidationState.bAllowUnresolvedInnerDefinitions)
//		return cb(null, true);
var bAllowUnresolvedInnerDefinitions = true;
...
if (arrDefiningAuthors.length === 0) // no address definition in the current unit
    return bAllowUnresolvedInnerDefinitions ? cb(null, true) : cb("definition of inner address "+other_address+" not found");
```

### Finding Description
The original design intent (visible from the commented-out lines) was that `bAllowUnresolvedInnerDefinitions` should be a flag set explicitly by trusted internal callers only — e.g. wallet code that pre-validates address definition templates against fake/incomplete data before a real unit exists [2](#0-1)  and [3](#0-2) , neither of which populate `objValidationState.bAllowUnresolvedInnerDefinitions` in this build, meaning the flag effectively never gets set through the intended, restricted path anyway. Instead, the actual runtime behavior now unconditionally treats any unresolved `['address', X]` reference as "has signature" (`bHasSig = true`) — this is exactly the "insecure default" pattern from GHSA-7rq6-7gv8-c37h: a security-relevant gate that used to require an explicit opt-in condition now defaults to the permissive behavior for every caller, including real, unprivileged unit posters submitting brand-new address definitions via `validateAuthor()` → `Definition.validateAuthentifiers()` → `validateDefinition()`. [4](#0-3) 

This bypasses the structural safety check at the end of `validateDefinition`: [5](#0-4)  An attacker can register a completely new address whose definition is literally just `['address', 'SOME_ADDRESS_NEVER_DEFINED_HERE']` (or as one branch of an `'or'`/`'and'` composition) and have it accepted as valid, since `bHasSig` is forced to `true` for that branch without any actual authentifier being present or checked.

### Impact Explanation
Because `validateDefinition` is the gate that decides whether a definition is legal *at all* (used both when defining a brand-new address in `objAuthor.definition` and when validating asset issue/transfer conditions via `Definition.validateDefinition` called from `validateAssetDefinition`), an attacker-controlled definition can pass this "signature required" sanity check without embedding any real, currently-verifiable authentication. This weakens a core invariant of the DAG's authorization model (every spending path must be gated by a signature) and can be leveraged to register definitions/asset conditions that different validating nodes may end up treating inconsistently once the referenced address is (or is not) later defined by different co-authoring units — a node-disagreement-on-validity vector, and in the address-definition case, funds sent to an address whose top-level definition itself relies purely on this unresolved bypass can become permanently unspendable/frozen once no cosigner ever legitimately defines the referenced inner address, since `validateAuthentifiers` (the actual signature-checking pass, at [6](#0-5) ) does not share this bypass and always returns `false` when the inner definition is unresolved. This is a Medium/High severity authorization-boundary defect: it lets a single unit poster register spending conditions/asset conditions that were meant to require the referenced address's definition, without that check actually being enforced.

### Likelihood Explanation
This is trivially reachable by any unprivileged unit poster: simply define/register a new address (author.definition) or an asset issue/transfer condition containing an `['address', X]` clause where `X`'s definition does not resolve at validation time (X unused or intentionally not resolvable by any co-author in the unit) — see the `case 'address'` op inside `validateDefinition`. No special privileges, mining, or hub/witness cooperation is required.

### Recommendation
Restore the intended gating: only allow `cb(null, true)` for an unresolved inner `address` reference when `objValidationState.bAllowUnresolvedInnerDefinitions` is explicitly set by trusted internal callers (as the commented-out code originally did), and make production/unit validation paths (`validateAuthor`, `validateAssetDefinition`) never set this flag. For all real unit validation, an unresolved inner address reference should cause `validateDefinition` to fail (`cb("definition of inner address "+other_address+" not found")`), matching the strict behavior already used in `validateAuthentifiers`.

### Proof of Concept
1. Craft a unit whose author defines a brand-new address with `definition = ['address', 'SOME_ADDRESS_X']`, where `SOME_ADDRESS_X` has no prior on-chain definition and is not supplied as a co-author's definition in the same unit.
2. Submit the unit; `validateAuthor` → `Definition.validateAuthentifiers` → `validateDefinition` evaluates the `'address'` op, hits `ifDefinitionNotFound`, and because `bAllowUnresolvedInnerDefinitions` is hard-coded `true` at [7](#0-6) , returns `cb(null, true)`.
3. The overall `evaluate()` result reports `bHasSig = true`, satisfying the `"each branch must have a signature"` check at [8](#0-7) , so the definition is accepted as a valid new address definition even though it contains no verifiable signature requirement at registration time.
