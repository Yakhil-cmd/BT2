### Title
Membership webhook trusts `team.id` without binding the verified organization, allowing cross-tenant team escalation - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify the HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner` for membership events falls back to `params.dig('organization', 'login')` — fully attacker-controlled and used only to pick the *verification key*, not to constrain the payload's effect. `MembershipHandler#find_or_create_team!` then does `Team.find_or_create_by!(github_id: params.team.id)`, which if a Team row with that `github_id` already exists (created for a different, victim organization) is looked up and mutated without ever checking that its `organization` column matches the organization that actually signed the request. This lets an attacker who owns any org configured in Shipit's multi-tenant `secrets.github` config forge a membership webhook naming an arbitrary existing `Team.github_id` belonging to a different org and add themselves as a member.

### Finding Description
The broken binding, stated as an equality that the code fails to enforce:
`Shipit.github(organization: repository_owner).webhook_secret_org == Team.find_by(github_id: params.team.id).organization`

These are never checked against each other.

Code path:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `github_app = Shipit.github(organization: repository_owner)` and verifies the signature against that org's `webhook_secret`. For a `membership` event there is no `repository` key in the payload, so `repository_owner` (line 61) falls back to `params.dig('organization', 'login')` — a value the attacker fully controls in their own signed payload.
2. Provided the attacker owns/configures an org in Shipit (`Shipit.github(organization:)` at lib/shipit.rb:170-181 supports multiple tenants via `secrets.github`), they can sign the payload with *their own* org's `webhook_secret` and it will pass verification, since verification only checks "was this signed by the secret for the org named in the payload," not "is this org allowed to touch the referenced team."
3. `MembershipHandler#process` (app/models/shipit/webhooks/handlers/membership_handler.rb:22-34) calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` (lines 38-43). The block that sets `organization` only runs on **creation**. If a `Team` row with that `github_id` already exists (e.g., a privileged team belonging to `victim-org`, present because it's listed in `Shipit.github_teams`, see lib/shipit.rb:256-258), `find_or_create_by!` returns the existing record untouched — the attacker's claimed `organization.login` is silently discarded, and no comparison is made between the existing `team.organization` and the org that authenticated the request.
4. `team.add_member(member)` (app/models/shipit/team.rb:41-43) then inserts a `Membership` linking the attacker's `User` (created via `User.find_or_create_by_login!(params.member.login)`) to the victim's team.
5. `User#authorized?` (app/models/shipit/user.rb:80-82) checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` — since the attacker is now a member of a team in `Shipit.github_teams`, this becomes `true`, and `Authentication#force_github_authentication` no longer blocks them.

No existing guard prevents this: `verify_signature` only authenticates "a payload signed by org X's secret," it does not scope which `Team` rows that org may touch; `find_or_create_by!`'s block is a create-only callback, not a validation; the `ExplicitParameters` schema for `MembershipHandler` only checks types/presence of `action`, `team.id/name/slug/url`, `organization.login`, `member.login` — it does not cross-check `organization.login` against `Team#organization`.

### Impact Explanation
A successful forged webhook grants the attacker's GitHub identity membership in an arbitrary privileged Shipit `Team` (by guessing/observing `github_id`), which flips `User#authorized?` to `true` for that user, bypassing `force_github_authentication`'s intended organization-membership gate. This is repeatable against any Team whose `github_id` is known or guessable (`github_id` is a small sequential GitHub team ID, easily brute-forced), and works across tenants — any org configured as a Shipit tenant can be abused to attack any other tenant's teams. This matches the High severity category: "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Preconditions: Shipit must be configured with at least two GitHub organizations/tenants in `secrets.github` (multi-tenant mode, `github_default_organization` non-nil), one of which the attacker controls and can configure a `membership` webhook with a known `webhook_secret`; a `Team` row for the victim org's privileged team must already exist (created via prior sync or `github_teams` config lookup) with a `github_id` the attacker can discover or guess. Attacker cost is low: create/own a GitHub org, register it as a Shipit GitHub App tenant (a normal onboarding action, not a Shipit secret), and send one crafted, self-signed HTTP POST to `/webhooks`. No Shipit session, token, or private key is required. Feasibility depends entirely on the deployment actually running Shipit in multi-tenant mode with attacker-controlled org onboarding permitted — a real but non-universal configuration.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the resolved `Team#organization` matches the organization that authenticated the current webhook request (e.g., pass the verified `repository_owner`/organization through the handler and raise/reject if `team.organization != verified_organization`) instead of trusting `find_or_create_by!`'s block only on creation. Additionally, `WebhooksController#verify_signature` should reject events where the claimed `organization.login`/`repository.owner.login` does not match the org actually configured for the resolved `github_app`, and handlers should never let cross-tenant payloads mutate `Team`/`Membership` rows belonging to a different `organization`.

test "membership webhook cannot let another org's signed payload join a team it doesn't own" do
  victim_team = Shipit::Team.create!(organization: 'victim-org', github_id: 555, name: 'core', slug: 'core', api_url: 'https://api.github.com/teams/555')
  Shipit.stubs(:github_teams).returns([victim_team])

  attacker_login = 'attacker'
  payload = {
    'action' => 'added',
    'team' => { 'id' => 555, 'name' => 'core', 'slug' => 'core', 'url' => 'https://api.github.com/teams/555' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => attacker_login },
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

  attacker = Shipit::User.find_by(login: attacker_login)
  # Binding under test: the team's organization must equal the org that authenticated the request
  assert_equal 'victim-org', victim_team.reload.organization
  refute_equal 'attacker-org', victim_team.organization
  # This assertion should fail before the fix (attacker becomes authorized despite belonging to attacker-org, not victim-org)
  refute attacker.authorized?, "attacker should not gain authorization via a different org's signed membership webhook"
end

      github_app = Shipit.github(organization: repository_owner)

    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
