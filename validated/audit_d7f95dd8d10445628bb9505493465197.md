Unauthenticated user-impersonation via unchecked `X-Shipit-User` header in `identify_user` allows unauthorized deploy/rollback attribution - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
`Api::BaseController#identify_user` resolves `current_user` purely from the client-supplied `X-Shipit-User` HTTP header, looking up any `User` by login with no verification that the login corresponds to `current_api_client.creator`. Any caller holding a valid but low-privilege `ApiClient` token can set this header to an arbitrary victim login and have deploys, rollbacks, or task triggers/aborts attributed to that victim.

### Finding Description
The broken binding is: `current_user_identity == authenticated_identity_of_the_request`, i.e. the identity acted upon should equal `current_api_client.creator`. Instead: [1](#0-0) 

`identify_user` takes `request.headers['X-Shipit-User']` verbatim and does `User.where('lower(login) = ?', user_login.downcase).first`, with no comparison to `current_api_client.creator`. `current_user` memoizes this result: [2](#0-1) .

Authentication only validates the `ApiClient` bearer token via `BasicAuth`/`ApiClient.authenticate`, which is independent of the `creator` association: [3](#0-2)  and [4](#0-3) . Permission checks (`require_permission!`/`check_permissions!`) only validate the operation/scope permission list of the `ApiClient`, not the identity of the acting user: [5](#0-4) .

This `current_user` is then passed directly as the acting user to sensitive state-changing operations:
- `DeploysController#create` → `stack.trigger_deploy(commit, current_user, ...)`: [6](#0-5) 
- `RollbacksController#create` → `deploy.trigger_rollback(current_user, ...)` / `active_task.abort!(aborted_by: current_user, ...)`: [7](#0-6) 
- `TasksController#trigger`/`#abort` → `stack.trigger_task(params[:task_name], current_user, ...)` / `task.abort!(aborted_by: current_user)`: [8](#0-7) 

Exploit flow: attacker obtains (or is issued) any valid `ApiClient` token with minimal permissions (e.g. only `deploy:stack` on their own stack, or any token they legitimately hold), then sends `POST /stacks/:owner/:repo/:env/deploys` (or `rollbacks`, `tasks`) with `Authorization: Basic <valid-token-encoded>` and header `X-Shipit-User: <victim-login>`. The resulting `Deploy`/`Rollback`/`Task` record is created with `user_id` pointing to the victim, not the actual API-client creator — spoofing the audit trail and misattributing the deploy/rollback action.

Existing guards fail because `authenticate_api_client` only checks the bearer token validity/permissions of the `ApiClient` record, not any relationship between the client and the header-supplied user; `require_permission!` checks operation scope, not identity; and `identify_user` has zero authorization logic tying the header value to `current_api_client.creator`.

### Impact Explanation
Any holder of a valid `ApiClient` token (even one scoped to a single stack with a single low-privilege permission such as `deploy:stack`) can attribute deploys, rollbacks, and task aborts to an arbitrary Shipit user of their choosing. This constitutes an unauthorized action with spoofed audit-trail identity (falls under "unauthorized deploy, rollback" impact and audit trail forgery), and it is repeatable against any stack the token has access to, for any victim login present in the `users` table. The blast radius is per-stack/tenant scoped to whatever the token's `stack_id`/permissions allow, but the identity forgery itself is unbounded — any known login can be impersonated in the resulting records.

### Likelihood Explanation
Preconditions: attacker needs a valid `ApiClient` token (not a Shipit secret, but a legitimately-provisioned low-privilege token — e.g. a CI integration token) and knowledge of a victim's login (logins are generally public/discoverable via GitHub). No GitHub App secrets, session, or `api_clients_secret` needed beyond possessing one working token. Cost is trivial: a single crafted HTTP header on an already-permitted request. This is fully repeatable per request.

### Recommendation
In `identify_user`, only trust `X-Shipit-User` when it matches `current_api_client.creator&.login` (case-insensitively), or restrict header-based identity substitution to trusted/unlimited API clients (e.g. `UnlimitedApiClient` or clients explicitly flagged as allowed to act on behalf of others). Otherwise, always bind `current_user` to `current_api_client.creator`.

### Proof of Concept
Minitest plan (`test/controllers/shipit/api/deploys_controller_test.rb` style, ActionDispatch::IntegrationTest):
1. Create `victim = shipit_users(:walrus)` (or any distinct user) and `actor = create(:user)`.
2. Create `api_client = ApiClient.create!(creator: actor, name: 'ci', permissions: ['deploy:stack'], stack: stack)`.
3. POST to `api_deploys_path(stack)` with `Authorization: Basic <api_client.authentication_token base64>`—no login/password segments needed since `ApiClient.authenticate` verifies token only—plus header `'X-Shipit-User' => victim.login`, body `{ sha: commit.sha }`.
4. Assert response status `:accepted`.
5. Assert `Deploy.last.user_id == victim.id` (equality that should NOT hold) versus the expected binding `Deploy.last.user_id == api_client.creator_id` (equality that SHOULD hold but doesn't) — demonstrating the divergence: `assert_equal victim.id, Deploy.last.user_id` succeeds while `assert_equal actor.id, Deploy.last.user_id` fails, proving `current_user` was spoofed via the header rather than bound to `current_api_client.creator`.
