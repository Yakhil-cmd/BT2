### Title
Cross-stack authorization bypass in `Api::CCMenuController#stack` — token's stack scope is not enforced ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The engine binds an `ApiClient`'s authorization to a specific stack via `ApiClient#stack_id`, enforced centrally in `Api::BaseController#stacks`/`#stack`. `Api::Ccmenucontroller` overrides `#stack` and bypasses that scoping, so a token that is only supposed to authorize reads of one stack can be replayed to read the build/deploy status of any stack on the instance.

### Finding Description
`Api::BaseController` is designed to bind every API client's authorization to the stack(s) it was granted: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

`require_permission!` only checks that the permission string (e.g. `read:stack`) is present in the client's `permissions` array — it never checks which record the permission applies to: [2](#0-1) 

The actual restriction to "this token may only see stack X" is enforced solely by the `stacks`/`stack` helper filtering on `current_api_client.stack_id`. This is exactly the binding pattern described in the report's bug class: a token *authorizes* one stack, but the code that resolves *which* stack is *touched* can diverge from that authorization.

`Api::CCMenuController`, however, overrides `stack` and completely skips the scoped `stacks` helper: [3](#0-2) 

```ruby
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`Stack.from_param!(params[:stack_id])` resolves against **all** stacks, not `current_api_client`'s scoped set. `require_permission :read, :stack` on this controller only asserts the token has the `read:stack` permission string — it does not assert the token's `stack_id` matches the requested `stack_id`.

The token itself is trivially obtainable by any authenticated Shipit user (not necessarily an admin) via `CCMenuUrlController#fetch`, which mints an `ApiClient` scoped to a single stack with only `read:stack` permission, and returns the token embedded in a URL: [4](#0-3) 

Because `Api::CCMenuController#show` uses the unscoped `stack` override, that single-stack token can be replayed against `GET /api/stacks/*stack_id/ccmenu?token=...` for **any** other `stack_id` on the instance and will succeed, since the only check performed is `check_permissions!(:read, :stack)`, which is satisfied by any `read:stack`-scoped token regardless of which stack it was minted for: [5](#0-4) 

Equality that should hold but doesn't:
`stack the token authorizes (current_api_client.stack_id)` == `stack the controller acts on (params[:stack_id] resolved via Stack.from_param!)`

Before the attacker's request: the token minted by `CCMenuUrlController` is scoped to stack A only (`current_api_client.stack_id == A.id`).
After the attacker's request: `Api::CCMenuController#show` renders build status for stack B (`params[:stack_id] == B.to_param`), with no re-check that `A == B`.

### Impact Explanation
This grants any user who can reach `CCMenuUrlController#fetch` for a stack they can view (or who otherwise obtains any `read:stack`-scoped token, e.g. the low-privilege `here_come_the_walrus` fixture pattern) the ability to read the last deploy/build status (`lastBuildStatus`, `lastBuildLabel`, lock state, etc., rendered by `app/views/shipit/ccmenu/project`) of **every** stack in the Shipit instance, including stacks the user has no authorization to view. This matches the report's Impact category of unauthorized read of stack state through a broken authorization binding, reached purely with a token any authenticated user can self-issue for one stack and then reuse against arbitrary other stacks — no privileged account, GitHub App key, `webhook_secret`, or `api_clients_secret` is required.

### Likelihood Explanation
High. Any authenticated user with view access to at least one stack can call `CCMenuUrlController#fetch` to mint a `read:stack`-scoped `ApiClient` and its token, then directly call the CCMenu API endpoint with a different `stack_id` in the URL/path while keeping the same `token` query parameter. No race condition, no timing, no cryptographic secret needed — the flaw is a pure logic/scoping bypass in `Api::CCMenuController#stack`.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` helper from `Api::BaseController` instead of querying `Stack.from_param!` directly, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This restores the invariant that `current_api_client.stack_id` (when present) always constrains which stack a request can resolve to, consistent with every other controller inheriting from `Api::BaseController`.

### Proof of Concept
1. As any authenticated Shipit user with access to Stack A, visit `GET /ccmenu/*stack_id=A` (`CCMenuUrlController#fetch`). This creates an `ApiClient` with `permissions: ['read:stack']`, `stack_id: A.id`, and returns a URL containing `token=<A-scoped-token>`.
2. Take that `token` and issue `GET /api/stacks/*stack_id=B/ccmenu?token=<A-scoped-token>` for an arbitrary Stack B that the user is not authorized to view.
3. `Api::BaseController#authenticate_api_client`'s `BasicAuth` path is bypassed by `CCMenuController#authenticate_api_client`, which authenticates via `params[:token]` directly; `require_permission :read, :stack` passes because the token has `read:stack`; `Api::CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` = Stack B, ignoring that the token's `stack_id` is A.
4. The response renders Stack B's CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, lock status, etc.), disclosing build/deploy state of a stack the attacker's token was never authorized for.
