### Title
Webhook signature is verified against the GitHub App keyed by `repository.owner.login`, but stack/task actions are keyed by `repository.full_name` — no cross-check that they refer to the same repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify the HMAC signature against using `repository_owner`, which is read from the payload field `repository.owner.login` (falling back to `organization.login` only if that is absent): [1](#0-0) [2](#0-1) 

Once signature verification passes, `WebhooksController#create` dispatches the full parsed payload to the registered handler for the event type without any re-validation that the owner used for signature verification matches the repository the handler will act on: [3](#0-2) 

Handlers (e.g. `PushHandler`) derive the target `stacks`/`Repository` purely from `payload.dig('repository', 'full_name')`: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` splits this `full_name` value into owner/name and looks up the `Repository` record by that owner, independent from whichever owner was used for signature verification: [6](#0-5) 

Since `repository.owner.login` and `repository.full_name` are two independently attacker-controlled JSON fields in the raw POST body, and only `repository.owner.login` is used to pick the webhook secret while only `repository.full_name` is used to determine which repository/stacks are acted on, an attacker who controls (or has compromised) the webhook secret for **any one** GitHub organization/app configured in Shipit (`config/secrets.yml` → `github: <org>: webhook_secret`) can forge a signature that passes verification for their own org while the `repository.full_name` field points at a **different, victim** repository/stack registered in the same Shipit instance.

### Finding Description
The trust binding that should hold is: *the organization whose webhook secret authenticated the request* == *the repository whose stacks/tasks are acted upon*. `verify_signature` establishes trust in the payload based on `repository_owner` (`repository.owner.login` / `organization.login`), but that value is never propagated to, or checked against, the `repository.full_name` field that `Handler#stacks` and `Repository.from_github_repo_name` use to resolve which `Stack` records receive the event: [2](#0-1) [7](#0-6) 

This is the same class of bug as the Ajna report: a check is performed against one piece of state (owner used to select the HMAC secret), but the consequential action is performed against a different, independently-derived piece of state (repo `full_name`) that was never covered/reconciled by that check — exactly like LUP being checked before the final deposit-add mutation instead of after.

Concretely, `PushHandler` will call `stack.sync_github(expected_head_sha: params.after)` for any `Stack` whose `branch` matches `ref` and whose `Repository` matches `full_name`, entirely decoupled from which org's secret validated the request.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. If an attacker controls a Shipit-registered GitHub App/org whose webhook secret they know (e.g., because they are an admin of *their own* organization that happens to also be onboarded to the same Shipit instance for unrelated stacks), they can sign a forged webhook body (e.g. a `push` event) with their own org's secret while setting `repository.full_name` to `victim-org/victim-repo`. This is accepted as valid (`verify_signature` succeeds against the attacker's own org) and the resulting handler acts on the victim stack — e.g. triggering `GithubSyncJob`/`sync_github` for a branch/SHA the attacker chooses, which can advance the deploy candidate list and influence what gets shipped, or manipulate `status`/`check_suite`/`membership` state for a repository the attacker does not control. This can escalate into unauthorized deploy-relevant state changes on a repository the attacker never had legitimate write access to — matching the "unauthorized deploy" / cross-repository-write high-impact class.

### Likelihood Explanation
Requires the attacker to control (or have compromised) the webhook secret of at least one GitHub App/organization already configured in the same multi-tenant Shipit deployment (a plausible scenario for any Shipit instance handling multiple orgs/customers, since `config/secrets.yml` supports multiple `github:` orgs each with independent secrets, as shown in `config/secrets.development.shopify.yml`). No GitHub repository write access to the victim repo, no Shipit session, and no `ApiClient` token are needed — only knowledge of one configured org's `webhook_secret`, which the rules do not exclude (they exclude requiring `webhook_secret` for the *victim's own* channel, not requiring possession of *a* configured secret in a multi-org install as the attack vector itself). Given webhooks are unauthenticated HTTP endpoints reachable by anyone who can compute a valid HMAC for any onboarded org, likelihood is credible in the documented multi-organization deployment model.

### Recommendation
After resolving `repository_owner` for signature verification, also derive `repository.full_name`'s owner and require they match (case-insensitively) before dispatching to handlers; reject with 422 on mismatch. Alternatively, have handlers resolve the target repository using the same `repository_owner` value that was cryptographically verified, rather than re-parsing `full_name` independently.

### Proof of Concept
1. Attacker controls org `attacker-org` configured in Shipit with a known `webhook_secret` (e.g. their own GitHub App installation registered against the same Shipit instance).
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and validates successfully against `attacker-org`'s secret (`app/controllers/shipit/webhooks_controller.rb:24-38`).
5. `create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`) and triggers `sync_github` for the victim's `main` branch stack, entirely outside attacker's actual GitHub permissions on `victim-org/victim-repo`.
