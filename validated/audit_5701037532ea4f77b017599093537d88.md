### Title
Webhook `organization.login` is not bound to the signature-verifying `repository.owner.login`, allowing an attacker with one org's webhook secret to attribute `Team`/`Membership` writes to another org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret using `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`), but `MembershipHandler#process`/`#find_or_create_team!` reads a *separate* field, `params.organization.login`, to create/select the `Team` and to add members. Because nothing enforces `repository.owner.login == organization.login`, an attacker who legitimately controls the webhook secret for one configured GitHub organization can sign a request whose body claims a different `organization.login`, causing Shipit to create or mutate a `Team` for that other organization and add an attacker-chosen member to it.

### Finding Description
The binding the code implicitly assumes is: `signing_org == params.organization.login` (the org whose secret verified the request equals the org whose `Team`/`Membership` state is mutated). This is never enforced.

- `verify_signature` computes `repository_owner` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . `repository_owner` prefers `repository.owner.login`, falling back to `organization.login` only if `repository` is absent [3](#0-2) . Since the raw JSON body is fully attacker-controlled, an attacker can include *both* keys with different values.
- `MembershipHandler` never reads `repository.owner.login`; its `ExplicitParameters` schema only requires `organization.login`, `team`, and `member` [4](#0-3) , and `find_or_create_team!` sets `team.organization = params.organization.login` on create, or looks up an existing team by `github_id` (whose `organization` is then left as-is) on update [5](#0-4) .
- Each configured organization has its own webhook secret via `Shipit.github(organization:)` / `github_app_config(organization)`, read from server credentials, one entry per onboarded org in a multi-tenant Shipit instance [6](#0-5) . In practice, the administrator of a given onboarded org configures that org's webhook (and therefore knows/controls that org's `webhook_secret`) when wiring it up in GitHub - this is the only "privilege" required, and it is scoped to their own org, not to any other tenant.

Exploit flow: an attacker who administers "attacker-org" (one org onboarded into this shared Shipit instance) POSTs directly to `/webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with attacker-org's own webhook secret over the raw body, and a JSON body:
```json
{
  "action": "added",
  "team": {"id": 1, "name": "Developers", "slug": "developers", "url": "https://example.com"},
  "organization": {"login": "shopify"},
  "member": {"login": "attacker"},
  "repository": {"owner": {"login": "attacker-org"}}
}
```
`verify_signature` looks up `attacker-org`'s `GitHubApp`, verifies the signature against attacker-org's own known secret, and succeeds. `MembershipHandler#process` then reads `organization.login == "shopify"`, finds (or creates) the `Team` for `shopify` with `github_id: 1`, and adds `attacker` as a member of it via `team.add_member(member)` [7](#0-6) . No code path cross-checks `repository_owner`/signing org against `params.organization.login`.

Existing guards do not stop this: `drop_unhandled_event` only checks the event name is registered [8](#0-7) ; the `ExplicitParameters` schema validates presence/type of `organization.login` but not its relationship to `repository`; `verify_signature`'s `rescue Shipit::GithubOrganizationUnknown` only guards against unconfigured orgs, not mismatched ones.

### Impact Explanation
An attacker who legitimately controls the webhook secret of any one org onboarded to a shared/multi-tenant Shipit instance can add an arbitrary GitHub login (including their own) as a member of a `Team` belonging to a *different, victim* organization, or create a spoofed `Team` record attributed to that victim org. Since `User#authorized?` grants app-wide login/authorization to any user who is a member of a team listed in `Shipit.github_teams` [1](#0-0) , this is a cross-tenant privilege escalation: an attacker outside the victim org's real GitHub team can gain Shipit-level authorization tied to that team. This matches "High - escalation into `Shipit.github_teams` authorization" (and, if the targeted team maps to deploy permission checks elsewhere, could escalate toward unauthorized deploy actions). It is repeatable against any `team.id`/`github_id` and any target `organization.login` string, is not scoped to the attacker's own tenant, and works cross-tenant on any shared Shipit deployment.

### Likelihood Explanation
Requires: (1) the Shipit instance is configured for more than one GitHub organization (multi-tenant `secrets.github` keyed by org) — a documented, supported configuration; (2) the attacker legitimately controls the webhook secret of at least one onboarded, low-privilege org. Given that, the attack is a single crafted HTTP POST with no other secrets needed — cheap, deterministic, and repeatable. On a single-organization Shipit instance (the common case, "backward compatibility" top-level `secrets.github` schema) the fallback logic still exists in code but there's only one org/secret so the divergence has no cross-tenant blast radius; the vulnerability is real specifically for multi-org configurations.

### Recommendation
Bind the signature-verifying identity to the mutation target: after computing `repository_owner`, require that `params.dig('organization','login')`, if present, equals `repository_owner` (or, for org-only events like `membership`, always source the signing org purely from `organization.login` and never let a `repository` field override it for those events). Reject the request (422) on mismatch. More robust: pass the verified `repository_owner`/signing org explicitly into each handler and have `MembershipHandler` use that verified value instead of re-reading `params.organization.login` independently.

### Proof of Concept
```ruby
test ":membership payload with mismatched repository.owner and organization is bound to the signing org" do
  @request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: { id: 999, name: 'Spoofed', slug: 'spoofed', url: 'https://example.com' },
    organization: { login: 'shopify' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  Shipit.github(organization: 'attacker-org').expects(:verify_webhook_signature).returns(true)

  assert_difference -> { Team.count }, 1 do
    post :create, body:, as: :json
    assert_response :ok
  end

  team = Team.find_by(github_id: 999)
  # Signature only proved control of 'attacker-org', yet the mutated Team is attributed to 'shopify'
  assert_equal 'shopify', team.organization
  assert team.members.exists?(login: 'attacker')
end
```
This demonstrates: signing org (`attacker-org`, verified) != mutated org (`shopify`, written), breaking the intended `verified-org == mutated-org` binding.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
