## Title
Cross-organization commit-status spoofing via webhook signature/scope mismatch - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit supports multi-tenant GitHub App configuration, where each GitHub organization can have its own `webhook_secret` [1](#0-0) . Incoming webhooks are authenticated by looking up the signing secret for the organization named in the payload's `repository.owner.login` (or `organization.login`) field, and verifying the `X-Hub-Signature` against that org's secret [2](#0-1) . However, once the signature is accepted, the `status` event handler processes the payload's `sha`/`state` fields and applies them to **any** `Commit` record in the entire database matching that SHA, with no re-check that the commit belongs to a stack/repository under the authenticated organization [3](#0-2) .

### Finding Description
The binding that should hold is: **organization that authenticated == repository (and its commits) that get written**. In `WebhooksController#verify_signature`, `repository_owner` is read straight from the JSON payload and used to select which organization's `webhook_secret` verifies the signature [4](#0-3) [5](#0-4) . This only proves that the request was signed by *some* organization configured in Shipit — it does not confine what the handler is allowed to mutate to that organization's data.

`StatusHandler#process` ignores repository scoping entirely:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
`Commit.where(sha: params.sha)` is a global lookup across all stacks/repositories tracked by the Shipit instance, not scoped by `payload.dig('repository','full_name')` the way the base `Handler#stacks` helper is for other handlers [6](#0-5) . This mirrors the reported analog bug class: a value used for authorization (`self.quantity`/here, the authenticating organization) is not the same value actually consumed for the effect (`quantity`/here, the commit being written), so the "remaining"/actual scope silently diverges from the authorized scope.

Any organization that has its own GitHub App/webhook secret configured in this Shipit instance (a legitimate but unprivileged tenant of the instance) can sign an arbitrary webhook body. By setting `repository.owner.login` to their own org (so the HMAC check passes) while setting the top-level `sha`/`state`/`context` fields to reference a commit SHA that happens to exist in a completely different organization's repository/stack, they can force a fabricated commit status (e.g., `state: "success"`, arbitrary `context`) onto that unrelated commit.

### Impact Explanation
Commit statuses gate CI-required merges and deploy eligibility in Shipit (`commit.deployable?`, `require_ci` checks referenced in `test/controllers/api/deploys_controller_test.rb`). Forging a "success" status for a commit belonging to a repository/org the attacker does not control can make an otherwise CI-failing or unreviewed commit appear deployable, enabling an unauthorized deploy of that target repository. This satisfies the "unauthorized deploy" Critical-impact criterion, since it lets a party with only their own org's webhook credentials influence deploy-gating state for a repository they have no write access to.

### Likelihood Explanation
Requires the attacker to control (or configure) at least one organization/app entry with a valid `webhook_secret` in the Shipit instance — a low bar in multi-tenant deployments where several orgs' GitHub Apps are registered on a shared instance, and where any org admin can independently know their own `webhook_secret` and craft raw HTTP POSTs to the shared `/webhooks` endpoint (not through GitHub itself, since payload fields are attacker-controlled JSON, only the signature must match). The attacker also needs to know or discover a target commit SHA (SHAs are not secret; they're visible in Shipit's own web UI, GitHub, PR links, etc.).

### Recommendation
Scope every webhook handler's writes to the organization that authenticated the request, not just to matching SHAs/refs. Concretely, in `StatusHandler#process` (and any other handler using unscoped lookups), verify that `payload.dig('repository','owner','login')` (or `organization.login`) matches the owner of the repository associated with each `Commit`/`Stack` being mutated, e.g. filtering `Commit.where(sha: params.sha)` by `stack.repository.owner == repository_owner` before calling `create_status_from_github!`. More generally, thread the verified `repository_owner` through to `Handler#stacks`/`repository_name` derivation so no handler can act on records belonging to a different organization than the one that produced a valid signature.

### Proof of Concept
1. Shipit instance configured with two tenants: `org-attacker` (attacker's own GitHub org/App, `webhook_secret_attacker`) and `org-victim` (unrelated org with a deployable stack and commit `sha=abcd1234`).
2. Attacker computes `sha256`/`sha1=HMAC(webhook_secret_attacker, body)` over a crafted body:
```json
{
  "sha": "abcd1234",
  "state": "success",
  "context": "ci/attacker-forged",
  "branches": [{"name": "master"}],
  "repository": {"owner": {"login": "org-attacker"}}
}
```
3. POST to `/webhooks` with header `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `org-attacker`, fetches `org-attacker`'s webhook secret, and successfully verifies the signature [4](#0-3) .
5. `StatusHandler#process` finds the `Commit` with `sha == "abcd1234"` — which actually belongs to `org-victim` — and applies the forged `success` status to it [3](#0-2) , with no check that the commit belongs to `org-attacker`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
