### Title
Cross-Organization Webhook Spoofing via Unbound `repository.owner.login` vs `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-GitHub-App deployments, `Shipit::WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body, while every webhook `Handler` resolves the *stack to mutate* using an entirely different field of that same unverified body: `repository.full_name`. Because these two fields are never checked for consistency, and because `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as "always valid," an attacker can pick an organization with no configured secret to trivially pass verification, then point `repository.full_name` at a stack belonging to a *different*, properly-secured organization.

### Finding Description
`WebhooksController#verify_signature` computes the organization used for signature verification purely from body content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the app config keyed by that attacker-supplied organization name: [3](#0-2) 

`GitHubApp#verify_webhook_signature` unconditionally returns `true` when the resolved organization's config has no `webhook_secret`: [4](#0-3) 

This "no secret configured" case is a first-class supported configuration in this engine — the multi-org secrets fixture ships an org with `webhook_secret: # nil` right next to a properly-secured org: [5](#0-4) 

Meanwhile, every `Handler` resolves the *actual stack to act on* using a completely different field of the same unverified JSON body — `repository.full_name` — with no cross-check against `repository.owner.login`: [6](#0-5) [7](#0-6) 

**Binding broken:** `organization used to select the verifying secret` == `organization that owns the repository actually written`. Before the attack, the two are only equal for legitimate GitHub-originated payloads (GitHub always sends a consistent `repository` object). After the attack, an attacker submits a single JSON body where `repository.owner.login` names an org with no `webhook_secret` (verification trivially passes) but `repository.full_name` names a stack under a different, secret-protected org — the handler acts on that unrelated stack.

`PushHandler`, for example, will re-sync a targeted stack's commits from GitHub using an attacker-chosen `after` SHA and branch, using only `full_name` to pick the stack: [8](#0-7) 

If the targeted stack has `continuous_deployment` enabled, the forced `sync_github` (which discovers new commits/refreshes state) can feed the continuous-delivery pipeline, producing deploys the attacker did not have credentials to trigger directly.

### Impact Explanation
This crosses a credential/authentication boundary documented in scope: the webhook signature is meant to bind "this event is authentically from GitHub for organization X" to "this event's payload describes/affects resources of organization X." By decoupling the field used for authentication (`owner.login`) from the field used for authorization/routing (`full_name`), an attacker who knows (a) that a low-value org is configured without a `webhook_secret` and (b) the `owner/name` of a target repository/stack under a different, properly-secured org, can forge unauthenticated `push`/`status`/`pull_request`/etc. events against that target stack. This can cause unauthorized state changes (commit sync, status creation, PR/review-stack lifecycle changes) and, where continuous deployment is enabled, an unauthorized deploy — matching the Critical "unauthorized deploy" and High "unauthenticated write to stack state" impact classes.

### Likelihood Explanation
Requires: (1) the host application to configure more than one GitHub App/organization (a documented, explicitly-tested configuration shape — see `secrets_double_github_app.yml`), and (2) at least one of those orgs to have no `webhook_secret` set (also an explicitly supported/tested configuration value, `webhook_secret: nil`). No credentials, tokens, or prior access are required — the webhook endpoint is unauthenticated by design and CSRF protection is explicitly skipped. Given multi-org shipit-engine deployments are a real, documented use case, and that leaving one org's `webhook_secret` unset is a plausible operator mistake (or default), likelihood is moderate-to-high wherever multi-org configuration is used.

### Recommendation
- After signature verification, re-derive the organization strictly from the config used to verify (not from body fields), and require that `repository.owner.login`/`organization.login` used for handler routing (`Handler#repository_name`) matches the organization whose secret validated the request.
- Do not allow `verify_webhook_signature` to silently succeed for organizations with no configured secret in multi-org mode; require an explicit opt-in (e.g., raise/log loudly, or require `Shipit.github_default_organization` semantics) instead of treating missing secret as valid.
- Add a guard in `Handler#stacks`/`#repository_name` to reject events whose resolved repository's owner does not match the organization used to authenticate the webhook.

### Proof of Concept
Given a shipit-engine deployment configured like `secrets_double_github_app.yml` (`OrgOne` has a `webhook_secret`, `OrgTwo` does not), an attacker (no credentials needed) sends:

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # irrelevant, ignored

{
  "ref": "refs/heads/main",
  "after": "deadbeefcafefeed0000000000000000000dead",
  "repository": {
    "owner": { "login": "OrgTwo" },      // used only to pick verifying app -> no secret -> auto-pass
    "full_name": "OrgOne/victim-repo"     // used by PushHandler to pick the actual stack
  }
}
```

`verify_signature` resolves `Shipit.github(organization: "OrgTwo")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret), so the request is accepted (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`). `PushHandler#process` then calls `Repository.from_github_repo_name("orgone/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`) and enqueues `sync_github` for that stack — despite the attacker never having a valid signature for `OrgOne`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
