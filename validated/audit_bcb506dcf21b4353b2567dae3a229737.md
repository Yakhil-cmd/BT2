### Title
ERC20Transactor credits the full nominal `amount` to the XCM holding register without verifying the actual balance delta on fee-on-transfer / deflationary ERC20 tokens - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor` (wired into `AssetHubWestend`'s XCM config, confirmed by its use in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`) bridges XCM `TransactAsset` withdraw/deposit calls into `pallet_revive` ERC20 `transferCall`s. Both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` treat a successful (non-reverted, `true`-returning) ERC20 `transfer` call as proof that exactly `amount` moved, and build the XCM holding-register credit (`Erc20Credit(amount)`) or report success purely from the requested `amount`, never from an actual `balanceOf` measurement before/after the call. This is exactly the bug class from the report: code assumes `order.amount_in`/`amount` was fully transferred, when fee-on-transfer (deflationary) ERC20 tokens deliver less than requested. [1](#0-0) [2](#0-1) 

### Finding Description
`withdraw_asset_with_surplus` withdraws `amount` of an ERC20 token from `who` by calling `IERC20::transferCall{ to: checking_address, value: amount }` via `pallet_revive::Pallet::<T>::bare_call`. It only inspects whether the call reverted and whether the ABI-decoded boolean return value is `true`: [3](#0-2) 
If the call succeeds, it unconditionally constructs `Erc20Credit(amount)` — the *nominal requested amount*, not the actual increase of the checking account's ERC20 balance: [4](#0-3) 

`Erc20Credit` is a bespoke imbalance type explicitly documented as *not* enforcing runtime-level balance constraints ("the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime") [5](#0-4)  — i.e., the XCM holding register's accounting for this asset is *purely nominal* and disconnected from the real on-chain ERC20 balance of the checking account.

For a fee-on-transfer / deflationary ERC20 token (a standard, permissionless ERC20 that any user can deploy and register as a trusted asset for XCM, exactly the scenario the referenced audit targets), `transfer(to, amount)` returns `true` while depositing less than `amount` into `to`. The withdraw path therefore mints an XCM holding credit for `amount` while the checking account's real balance only increased by `amount - fee`. Symmetrically, `deposit_asset_with_surplus` calls `transferCall{ to: beneficiary, value: amount }` from the checking account and, on `Ok(true)`, reports full success without checking that the beneficiary actually received `amount`: [6](#0-5) 

The violated invariant is the same as in the report: **the XCM asset-holding accounting (analogous to the DEX's internal accounting of `order.amount_in`) must reflect the real token balance delta, not the nominal transfer amount, for any ERC20-like token that can apply a fee/deduction on transfer.** No `balanceOf` snapshot is taken before/after either `transferCall`, so this holds for any deflationary token registered through `Matcher::matches_fungibles`, which is attacker/asset-issuer controlled (any ERC20 contract deployed via `pallet_revive` and permitted by the runtime's asset/location matcher).

Concretely, once the withdrawn amount is over-credited into the holding register on `withdraw_asset_with_surplus`, subsequent XCM instructions in the same program (e.g. `DepositAsset`, `InitiateTransfer`/reserve-forwarding to a remote chain) operate on a holding register that says `amount` is available when the checking account's real ERC20 balance is only `amount - fee`. Any onward `deposit_asset_with_surplus` attempting to move the full nominal `amount` out of the checking account will fail (revert due to insufficient real ERC20 balance) — but if the program's earlier stages already emitted state to a remote chain claiming `amount` was reserved/received (e.g. via a `ReserveAssetDeposited`/derivative-mint instruction on the destination based on the message content produced before the failing deposit), a backing mismatch between the checking-account reserve and remote-side claims can occur. Even absent multi-chain effects, a purely local `TransferAsset` (withdraw+deposit in one program) will attempt to move `amount` in the deposit leg while the checking account only holds `amount - fee`, causing a revert of the deposit's inner call, an unrecoverable inconsistency between the recorded holding credit and reality, and a stuck/failed XCM execution path that a user cannot work around (same "swap execution can halt/fail mid-way, locking assumptions on false amounts" outcome flagged in the source report).

### Impact Explanation
This breaks the core XCM invariant that the value represented in the holding register during instruction execution must be backed 1:1 by actual on-chain token balances. For any fee-on-transfer ERC20 asset admitted to this transactor's `Matcher`, every withdraw operation systematically over-states the amount actually escrowed in the `TransfersCheckingAccount`, and every deposit assumes the beneficiary received the full nominal amount. This can manifest as: (a) deterministic failure/reversion of otherwise-valid XCM programs moving such tokens (denial of service for that asset class), and (b) an accounting mismatch between the checking account's real balance and the amount the XCM executor believes it "owns," which is the same root-cause class flagged Medium in the source report (assumed full transfer amount vs actual balance delta for fee-on-transfer tokens). I could not, within the available tooling, trace a concrete cross-chain path from this checking-account discrepancy through to unbacked issuance on a remote chain (that would require confirming exactly which XCM instructions/programs invoke `withdraw_asset_with_surplus` followed by a remote-forwarding step before any local `deposit_asset_with_surplus` reconciliation, and whether `pallet_revive`'s contract-call storage changes are rolled back transactionally on a later XCM instruction failure). Given that uncertainty, I present this as the direct structural analog to the reported Medium-severity bug class rather than an escalated Critical/High cross-chain theft finding.

### Likelihood Explanation
Reachability requires: (1) the runtime registers `ERC20Transactor` in its XCM config (confirmed for `asset-hub-westend`), and (2) an ERC20 contract implementing a transfer fee/deflation mechanism is deployed via `pallet_revive` and made matchable by the configured `Matcher: MatchesFungibles<H160, u128>` (a standard, permissionless action available to any user deploying a `revive` contract and, depending on runtime asset-registration policy, registering/using it in an XCM program). No privileged role, governance action, or malicious node is required — this matches the report's attacker model of an unprivileged user supplying/using an adversarial-but-standard-interface ERC20 token.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `balanceOf` (or equivalent) for the relevant account before and after the `transferCall`, and use the measured delta — not the requested `amount` — to construct `Erc20Credit`/determine success:
```rust
let balance_before = balance_of(checking_address);
// ... perform transferCall(amount) ...
let balance_after = balance_of(checking_address);
let actual = balance_after.saturating_sub(balance_before);
Erc20Credit(actual)
```
Apply the analogous check on the deposit side using the beneficiary's balance delta, and propagate the actual/adjusted amount to `AssetsInHolding` accordingly rather than assuming the requested `amount` was fully honored.

### Proof of Concept
I was not able to execute a runtime/integration test within this session (read-only investigation). No PoC was run; no test-run results are being claimed. The finding is derived purely from static analysis of the guarded code path: `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` unconditionally use the requested `amount` param to build `Erc20Credit`/report success once the ERC20 `transfer` call succeeds and decodes to `true`, with no `balanceOf` check before/after, confirmed by direct reading of `erc20_transactor.rs` lines 150-306 and its wiring in `asset-hub-westend/src/xcm_config.rs`. A concrete reproduction would require: deploying a `pallet_revive` ERC20 contract with a transfer fee via a `bare_call`/`instantiate`, registering it as a `MatchesFungibles` asset in a test runtime using `ERC20Transactor`, and executing an XCM `WithdrawAsset`/`DepositAsset` program to observe the checking account's real ERC20 balance diverge from the `Erc20Credit` amount recorded in the holding register — this last step was not performed in this session due to tool limitations (no code execution/terminal access).

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}
