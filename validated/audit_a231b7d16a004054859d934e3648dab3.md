### Title
Webhook signature verification is skipped when a configured GitHub organization has no `webhook_secret`, allowing forged push/status/check_suite events against arbitrary tracked repositories - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which HMAC secret to validate a webhook against by reading `repository.owner.login` (or `organization.login`) directly out of the **unverified** JSON body, before any cryptographic check has occurred. `GitHubApp#verify_webhook_signature` then unconditionally returns `true` if that organization's `webhook_secret` is blank. Because Shipit supports a multi-organization config (`Shipit.github(organization:)` / `github_app_config`), and `webhook_secret` is documented as optional per-organization, an attacker can craft a payload that claims to be from any configured organization that has no secret set, bypass signature verification entirely, and then have the full, attacker-controlled `params` body dispatched to the real event handlers (`push`, `status`, `check_suite`, `membership`, etc.) which act on whatever `repository.full_name` / `sha` / `state` values are in that same body - regardless of the organization used to pass the check.

### Finding Description
The binding that should hold is:
`organization used to authenticate the webhook == organization whose repository/stack state is mutated by the handler`

`verify_signature` breaks this binding:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read from the raw, unauthenticated request body before `verified` is computed - it is not itself covered by any prior check. `Shipit.github(organization:)` resolves per-organization config from `secrets.github`: [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats a blank secret as automatically verified:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

The setup docs explicitly mark the webhook secret as **optional**: [4](#0-3) 

Once `verify_signature` passes (trivially, because the chosen organization has no secret configured), `create` dispatches the **entire** JSON body - unscoped to that organization - to the registered handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [5](#0-4) 

Handlers such as `PushHandler` and `StatusHandler` act on `repository.full_name`, `sha`, `state`, etc. taken from that same body: [6](#0-5) 

The existing test suite demonstrates that status payloads directly create `Status` records from webhook input once signature checking is stubbed/passed: [7](#0-6) 

and that signature verification is performed per-organization, keyed on a value taken straight from the payload: [8](#0-7) 

Nothing in `create`, `PushHandler`, or `StatusHandler` re-validates that `repository.full_name`'s owner matches the `repository_owner`/organization that was actually used to pass signature verification. The multi-org config schema (`github_app_config`) means a large Shipit installation can have several organizations configured, and if even one of them is left with a blank `webhook_secret` (an easy misconfiguration given it's documented as optional), any event claiming that organization bypasses signature checking while still being free to reference any other tracked repository's `full_name`/branch/sha in the same JSON body.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" binding required by the rules. A successful forgery lets an unauthenticated attacker:
- Inject fabricated `status` events that mark an arbitrary commit's CI context as `success`, which can defeat `ci.require` checks that gate deploys, leading to an **unauthorized deploy** of code that never actually passed CI, or
- Inject fabricated `push`/`check_suite` events to force `sync_github`/check-run refresh on arbitrary tracked stacks, manipulating deploy state.

Both outcomes fall within the in-scope Critical impact category ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability depends entirely on configuration: the attacker needs to know (or guess) the login of at least one organization configured in Shipit's multi-org `secrets.github` block that has no `webhook_secret` set. Since the secret is documented as optional and organizations/login names are often public knowledge (e.g. visible in the target's GitHub App installation or the repositories Shipit already tracks), this is a plausible operator misconfiguration rather than a purely theoretical scenario, and the code contains no secondary check to prevent it once it occurs. No `ApiClient` token, session, or GitHub write access is required — only network access to the `/webhooks` endpoint.

### Recommendation
- Do not resolve the verification secret from an unauthenticated field of the same payload being verified. Require a `webhook_secret` for every configured organization (fail closed instead of "return true unless webhook_secret").
- After signature verification succeeds, cross-check that the organization used to select the secret matches the owner segment of `repository.full_name` (or `organization.login`) actually acted upon by the handler, rejecting mismatches.
- Consider making `webhook_secret` mandatory in the config schema validation at boot time so an organization cannot silently opt out of verification.

### Proof of Concept
1. Shipit is deployed with a multi-org config containing at least two organizations: `victim-org` (has a `webhook_secret`) and `unsecured-org` (misconfigured with a blank/absent `webhook_secret`), both able to be resolved via `Shipit.github(organization:)`.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: status` and a body:
```json
{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<real sha of victim commit>",
  "state": "success",
  "context": "ci/required-check",
  "branches": [{ "name": "master" }]
}
```
3. `verify_signature` computes `repository_owner = "unsecured-org"`, resolves that org's `GitHubApp`, and `verify_webhook_signature` returns `true` immediately because `webhook_secret` is blank for `unsecured-org` - regardless of the (attacker-arbitrary) `X-Hub-Signature` header value, as shown by the code path in `lib/shipit/github_app.rb:76-77`.
4. `create` then dispatches the full body to `Handlers::StatusHandler`, which creates/updates a `Status` on the real commit belonging to `victim-org/victim-repo`, as demonstrated by the equivalent flow in `test/controllers/webhooks_controller_test.rb:42-59`.
5. If `victim-org/victim-repo`'s stack has `ci.require: ["ci/required-check"]`, this forged status satisfies the CI gate and the commit becomes eligible to deploy/merge without having actually passed CI.

**Uncertainty / unverified aspects:** I was not able to retrieve the `Shipit::Webhooks::Handlers::Handler` base class (which defines the `stacks` helper used by `PushHandler`/`StatusHandler`) within the available tool calls, so I could not directly confirm whether stack/repository lookup in every handler is strictly keyed off `repository.full_name` with no additional scoping to the verified organization. The `status` handler's behavior is confirmed via the existing test (`test/controllers/webhooks_controller_test.rb:42-59`), which is sufficient to demonstrate the forged-status impact; the push/check_suite cross-repository claim is inferred from `PushHandler`'s reliance on `params` fields not covered by the per-organization signature check and should be double-checked against `Handler#stacks` in a full session.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
