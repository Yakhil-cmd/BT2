### Title
Webhook signature verification is keyed off an attacker-controlled organization field, letting an unsigned/mis-signed payload act on a repository belonging to a different, properly-secured organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App config (and therefore which `webhook_secret`) to validate the request against by reading `repository_owner`/`organization.login` straight out of the still-unauthenticated JSON body, before any signature check occurs. The actual repository that gets mutated by the event handlers is looked up from a *different* field of the same unauthenticated body (`repository.full_name`). These two lookups are never bound to each other, so the identity used to choose the verification secret can diverge from the identity of the resource actually written to.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [1](#0-0) 

`repository_owner` is derived from the unverified request body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization `GitHubApp` instance from `config/secrets.yml`, and if that organization's config has no `webhook_secret` configured, verification is unconditionally granted:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

The multi-organization configuration schema is a documented, supported deployment (`docs/setup.md`, "Using Multiple Github Applications"), where each org has its own independent `webhook_secret` entry, and a blank/`nil` `webhook_secret` per org is an explicitly supported value shown in the sample configs (`webhook_secret: # nil`). [4](#0-3) [5](#0-4) 

After `verify_signature` passes (for whatever reason), `create` re-parses the *same* raw body and dispatches it to event handlers using a completely separate field:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [6](#0-5) 

Handlers resolve the target `Repository`/`Stack` purely from `repository.full_name` in that body, with no re-check against `repository_owner`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 

Pull-request handlers similarly resolve the repository from `params.repository.full_name` and then archive/unarchive review stacks, update pull request records, capture labels, etc. [8](#0-7) [9](#0-8) 

**The broken binding, stated as an equality that should hold but doesn't:**
`organization used to select webhook_secret (verification identity)` == `organization/repository whose Shipit resources are mutated (write identity)`.

Before the attacker's request: for a legitimate GitHub webhook, both fields come from the same trusted GitHub payload for the same repository/org, so they always match.

After an attacker's forged request: the attacker fully controls both `repository.owner.login`/`organization.login` (verification identity) and `repository.full_name` (write identity) independently in the raw JSON body, since neither is checked before the other is used. If *any* organization configured on the Shipit instance has no `webhook_secret` set (an explicitly documented/supported configuration, and the project's own dummy/test configs ship with it blank), the attacker sets `repository.owner.login` to that unsecured organization to make `verify_webhook_signature` return `true` unconditionally (no valid `X-Hub-Signature` needed), while setting `repository.full_name` to any repository actually tracked by Shipit — including ones that belong to a different, properly secured organization.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary called out in the analog rules. Depending on the event type dispatched, an unauthenticated attacker can:
- Enqueue `GithubSyncJob` for an arbitrary tracked stack via forged `push` events, forcing Shipit to sync/deploy against attacker-chosen refs.
- Create fake commit `status` entries influencing deploy gating for a targeted stack.
- Archive/unarchive review stacks, or mutate `PullRequest` records, for a targeted stack via forged `pull_request` events.

This is a cross-repository/cross-organization write achieved purely by controlling unauthenticated request content — no `ApiClient` token, webhook secret, or GitHub credential is required for the target org, satisfying the "unauthorized deploy" / "cross-repository writes" Critical/High impact bar, provided a Shipit deployment configures at least one organization without a `webhook_secret` (a state the codebase's own sample configs, docs, and default templates treat as normal/supported, not as "the host not mounting the engine as documented").

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (documented, supported feature) where at least one configured organization has no `webhook_secret` set — shown as the default/example value in this engine's own config templates and dummy configs — and (2) the target repository/stack to be tracked under a different organization in the same instance. Given that a blank `webhook_secret` is the literal example value shipped in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`, and there is no engine-level warning/validation preventing this configuration, the precondition is plausible in real deployments that mix a "public"/test GitHub App with no secret alongside a production one, or that simply forget to set `webhook_secret` for one org while relying on defaults.

### Recommendation
- Verify the signature using the *same* organization ultimately used to resolve the acted-upon repository (i.e., re-derive/re-validate `repository.full_name`'s owning organization against `repository_owner` before dispatch, or perform the repository/stack lookup and reconcile the two).
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; require an explicit "unauthenticated" opt-in per organization, and refuse to dispatch cross-organization-affecting events when signature verification was skipped.
- Ensure the JSON `params` used in `verify_signature` and the JSON re-parsed in `create` are the exact same parsed object and that authorization decisions (which secret governs the request) are made using a field that binds 1:1 to the resource the handlers subsequently mutate.

### Proof of Concept
Preconditions: Shipit configured with two GitHub orgs, e.g. `SecureOrg` (real `webhook_secret` set, tracks `SecureOrg/prod-repo`) and `OpenOrg` (no `webhook_secret`, i.e. blank as shown in `test/dummy/config/secrets_double_github_app.yml`).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json
(no valid X-Hub-Signature required)

{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha already present in target repo>",
  "repository": {
    "full_name": "SecureOrg/prod-repo",
    "owner": { "login": "OpenOrg" }
  }
}
```
1. `repository_owner` returns `"OpenOrg"`.
2. `Shipit.github(organization: "OpenOrg")` returns a `GitHubApp` with `webhook_secret` blank.
3. `verify_webhook_signature` returns `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb` calling `lib/shipit/github_app.rb` line 77), so `verify_signature` passes without a valid `X-Hub-Signature`.
4. `create` re-parses the same body and dispatches the `push` handler, which resolves the stack via `repository.full_name = "SecureOrg/prod-repo"` and enqueues a sync/deploy job for that stack — despite the request never being authenticated against `SecureOrg`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
