### Title
Arbiter-contract dispute resolution leaves the contract permanently in `dispute_resolved` state, blocking fund withdrawal via `complete()` - ([File: arbiter_contract.js])

### Summary
This is the direct analog of the reported "rejected auction is always in default state" bug. In the reported system, an auction that is rejected transitions into a status that no closing function recognizes, so the pool can never be closed. In `ocore`'s arbiter-contract subsystem, once an arbiter resolves a dispute, the local contract status is flipped to `dispute_resolved`, but the only function that actually spends the shared-address funds, `complete()`, only accepts contracts whose status is `paid` or `in_dispute`. `dispute_resolved` (and `in_appeal`) are excluded, so the contract is stuck in a state from which the wallet-level API can never release the escrowed funds.

### Finding Description
When a dispute is opened, `openDispute()` sets the contract status to `in_dispute` [1](#0-0) 

When the arbiter later posts its resolution as a `data_feed` unit, the `new_my_transactions` listener immediately overwrites the status to `dispute_resolved`, regardless of whether the winner has withdrawn anything yet: [2](#0-1) 

The only function capable of actually sending the payment that unlocks the shared address (based on the on-chain `["in data feed", ...]` spending branch derived in `deriveSharedAddress()`) is `complete()`. Its guard clause explicitly rejects any status other than `paid` or `in_dispute`: [3](#0-2) 

Because the status listener at line 894 always transitions the contract to `dispute_resolved` as soon as the arbiter's unit is seen (even before it is stable), and no other function in this file transitions the contract back to `paid`/`in_dispute` or otherwise permits `complete()` to run, calling `complete()` after a dispute resolution will always fail with `"contract can't be completed"`. The `appeal()` path suffers the same fate: it moves status to `in_appeal` [4](#0-3) 
but nothing in this file ever transitions a contract out of `in_appeal` back into a state that `complete()` accepts (the `appeal_approved`/`appeal_declined` statuses exist only in the DB schema, e.g. in the sqlite migration/init scripts, but are never set anywhere in the wallet-side JS logic that was inspected).

Note: `wallet.js` also references these status strings and I was unable to fully confirm within this session whether it contains an alternate code path that transitions the contract out of `dispute_resolved`/`in_appeal` back into a `complete()`-eligible state, or drives the actual completion through a different route. This should be verified before finalizing severity.

### Impact Explanation
The shared address escrow definition is designed so the arbiter's winner decision (`in data feed` condition) is the on-chain trigger that authorizes payout. However, the wallet's `complete()` gate means the intended API surface for actually building/signing/broadcasting that payout transaction is unreachable once the local status becomes `dispute_resolved` (or `in_appeal`). Any counterparty relying on the wallet library (and any GUI/headless wallet built on it that calls `arbiter_contract.complete()`) has no way to withdraw the arbiter-awarded funds through the normal flow — the funds are effectively frozen in the shared address unless the user manually crafts a raw multisig transaction outside the library's supported API. This matches the "AA fund loss or freezing" class from the validation criteria: funds legitimately unlocked on-chain become practically unrecoverable through the intended contract/wallet message handling logic.

### Likelihood Explanation
This triggers deterministically and unconditionally on every dispute that reaches resolution — there is no attacker action required beyond normal use of the dispute/appeal flow (which is reachable by either counterparty to an arbiter contract, an unprivileged wallet user). Any contract that goes through `openDispute()` → arbiter resolves → status becomes `dispute_resolved` will hit this block 100% of the time when the winner tries to `complete()`.

### Recommendation
Update the guard in `complete()` (and any equivalent completion logic) to also accept `dispute_resolved` (and, if applicable, `appeal_declined`/`appeal_approved` once appeal handling is implemented) as valid statuses for payout, mirroring the on-chain spending conditions already encoded in `deriveSharedAddress()`. Ensure that every status the state machine can reach has a corresponding exit path in `complete()`/`revoke()` so no contract can become permanently un-completable.

### Proof of Concept
1. Two parties create and sign an arbiter contract, pay into the shared address (status `paid`).
2. Payer calls `openDispute()` → status becomes `in_dispute`.
3. Arbiter posts a `data_feed` unit naming a winner; the `new_my_transactions` listener fires and sets status to `dispute_resolved` (`arbiter_contract.js:894`).
4. Winner calls `complete(hash, walletInstance, [], cb)`.
5. `complete()` checks `objContract.status !== "paid" && objContract.status !== "in_dispute"` — true, since status is `dispute_resolved` — and returns `cb("contract can't be completed")`.
6. No other function in `arbiter_contract.js` transitions the contract out of `dispute_resolved`, so the funds in the shared address remain inaccessible through the library's supported API indefinitely.
