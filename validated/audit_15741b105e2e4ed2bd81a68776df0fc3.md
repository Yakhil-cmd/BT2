### Title
Fail-open exception handling in hookify's PreToolUse hook allows configured "block" rules to be silently bypassed on any rule-evaluation error - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
The GMX-Synthetics report describes a bug class where an incomplete enumeration of "special" error conditions (`isEmptyPriceError()` missing `EmptyFeedPrice`) causes the code to fall through to the wrong branch (cancel instead of revert), with real financial impact. The `hookify` plugin in this repository exhibits the same bug class in its security-decision logic: its `PreToolUse` hook enumerates only a narrow set of expected failure modes and, for anything outside that set, silently defaults to the "allow" branch instead of the safe "deny" branch, defeating user-configured `block` rules.

### Finding Description
`plugins/hookify/hooks/pretooluse.py` is the script Claude Code invokes before every tool call to decide whether to allow, deny, or warn about an operation [1](#0-0) . Its `main()` function wraps the entire rule-loading/evaluation flow in a single broad `try/except Exception`, and in the `finally` block it unconditionally calls `sys.exit(0)`: [2](#0-1) 

Per the plugin's own documented hook-output contract, a `PreToolUse` hook only denies an operation when it returns `hookSpecificOutput.permissionDecision: "deny"`; any other output (including a bare `systemMessage`) is treated as an allow [3](#0-2) . The rule engine's own success path only emits `permissionDecision: "deny"` when a `block`-action rule matches [4](#0-3) . Consequently, whenever an exception escapes `load_rules()`/`RuleEngine.evaluate_rules()` and is caught by the outer handler in `pretooluse.py`, the hook emits only `{"systemMessage": ...}` and exits 0 — which the Claude Code hook framework interprets as "allow" — even if the user configured a `block` rule (e.g., to stop `rm -rf`, writes to `.env`/credentials files, etc.) that should have denied the very operation that triggered the crash [5](#0-4) .

This mirrors the GMX report's bug class precisely: the code enumerates specific "safe-to-continue" cases (I/O errors, regex errors, YAML parse errors, all individually caught and gracefully degraded within `config_loader.py`/`rule_engine.py`) but does not guarantee that *every* possible failure inside rule evaluation is classified correctly — any exception not anticipated by the inner handlers (e.g., an `AttributeError`/`KeyError` from a rule whose `conditions` list contains malformed dict entries that pass frontmatter parsing but break `_check_condition`, or a `TypeError` from a non-string field value reaching `.startswith()`/`.endswith()` in `_check_condition`) is caught generically and results in an "allow" default rather than a "deny" default for a security control [6](#0-5) .

### Impact Explanation
An unprivileged user (or an untrusted `.claude/hookify.*.local.md` rule file, since these are project-local config that can also come from an untrusted repo/worktree) that trips any unhandled edge case in rule evaluation causes the hook to fail open, letting a dangerous `Bash`/`Write`/`Edit` operation that was supposed to be blocked (e.g. `rm -rf`, writing secrets, destructive commands) execute anyway. This is a direct hook-bypass / unauthorized-tool-action outcome, matching the "hook bypass" trust boundary and "unauthorized shell/file action" impact category.

### Likelihood Explanation
The failure requires triggering an exception in the rule-matching path that isn't already caught by the narrower, purpose-built handlers in `config_loader.py`/`rule_engine.py` (which already catch `IOError`, `ValueError`, `KeyError`, `AttributeError`, `TypeError`, `re.error`, `UnicodeDecodeError` at multiple layers). This narrows realistic likelihood, but the top-level `except Exception: ... finally: sys.exit(0)` design in `pretooluse.py` guarantees that *any* residual bug in the evaluation pipeline degrades to "allow" rather than "deny," which is the wrong default for a security-relevant hook.

### Recommendation
Change the fail-open default in `plugins/hookify/hooks/pretooluse.py` to fail closed (or at least fail neutral without discarding configured `block` intent) when an unexpected exception occurs during rule evaluation — for example, by tracking whether any loaded rule for the current event is a `block` rule and, on unexpected error, emitting `permissionDecision: "ask"` (or `"deny"`) instead of only a `systemMessage`, analogous to how the GMX fix added the missing `EmptyFeedPrice` case to `isEmptyPriceError()` so the correct (safe) branch is always taken.

### Proof of Concept
1. Create `.claude/hookify.block-rm.local.md` with `action: block`, `event: bash`, and a condition list.
2. Craft the rule file so that after successful frontmatter parsing, `Rule.conditions` contains an entry causing `_check_condition` to raise (e.g. an `AttributeError` from a non-string field or a `KeyError` from a `Condition` missing an expected attribute due to a version mismatch).
3. Trigger a `Bash` tool call with `rm -rf /important/path`.
4. Observe that `RuleEngine.evaluate_rules()` raises, `pretooluse.py`'s outer `except Exception` catches it, prints only a `systemMessage`, and `sys.exit(0)` runs — the hook framework treats this as "allow," and the destructive command executes despite the configured `block` rule. [5](#0-4)

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```

```python
    def _check_condition(self, condition: Condition, tool_name: str,
                        tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> bool:
        """Check if a single condition matches.

        Args:
            condition: Condition to check
            tool_name: Tool being used
            tool_input: Tool input dict
            input_data: Full hook input data (for Stop events, etc.)

        Returns:
            True if condition matches
        """
        # Extract the field value to check
        field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
        if field_value is None:
            return False

        # Apply operator
        operator = condition.operator
        pattern = condition.pattern

        if operator == 'regex_match':
            return self._regex_match(pattern, field_value)
        elif operator == 'contains':
            return pattern in field_value
        elif operator == 'equals':
            return pattern == field_value
        elif operator == 'not_contains':
            return pattern not in field_value
        elif operator == 'starts_with':
            return field_value.startswith(pattern)
        elif operator == 'ends_with':
            return field_value.endswith(pattern)
        else:
            # Unknown operator
            return False
```
