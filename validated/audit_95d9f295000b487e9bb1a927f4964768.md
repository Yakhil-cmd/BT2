### Title
API-scoped ApiClient tokens can read CI status (CCMenu) for any stack, bypassing `stack_id` scoping - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` restricted to a single stack (`ApiClient#stack_id`) can only ever see that stack, by routing all lookups through `stacks` → `stacks.from_param!`. `Shipit::Api::CCMenuController` breaks this invariant by defining its own `#stack` method that queries `Stack.from_param!(params[:stack_id])` directly against the unscoped `Stack` relation, never checking `current_api_client.stack_id`.

### Finding Description
`BaseController` defines the trust binding "stack a token authorizes == stack the endpoint touches" as: [1](#0-0) 

`stacks` is scoped to `current_api_client.stack_id` when present; `stack` resolves `params[:stack_id]` only within that scope. Every other API controller inherits this and is therefore correctly bound.

`CCMenuController`, however, overrides `stack` to bypass the scope entirely: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

This calls `Stack.from_param!` (the unscoped class method), not `stacks.from_param!` (the client-scoped instance method used by `BaseController`). The only authorization check present is `require_permission :read, :stack`, which validates that the client's `permissions` array includes `read:stack` — it does not check *which* stack the permission applies to. `ApiClient#check_permissions!` only checks the permission string, never the `stack_id` binding: [3](#0-2) 

The route confirms `stack_id` is attacker-supplied per request, independent of which stack the token was scoped to: [4](#0-3) 

Before the fix (i.e., as coded): a token with `stack_id = A` and `read:stack` permission satisfies `require_permission :read, :stack` for *any* `params[:stack_id]` value, and `CCMenuController#stack` resolves whatever stack ID is in the URL, not just `A`. After the equivalent fix (mirroring `BaseController#stack`, i.e. `stacks.from_param!(params[:stack_id])`), a request for stack `B` with a token scoped to `A` would raise `ActiveRecord::RecordNotFound` because `B` is not in the scoped `stacks` relation.

### Impact Explanation
This is an authorization-scope bypass: a caller holding only a narrowly-scoped `ApiClient` token (scoped to stack A, e.g., a CCMenu client created via `CCMenuUrlController`) can read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, activity) for any other stack in the installation by simply changing the `stack_id` in the URL, and the request is served without complaint. This matches the "unauthorized read of stack state / deploy output" category (High) called out in scope, since it is disclosure of deploy state for a stack the token was never authorized to touch, achieved purely by an unprivileged/limited-scope credential.

### Likelihood Explanation
High for any deployment that uses stack-scoped `ApiClient` tokens: the request requires only knowledge of a valid, narrowly-scoped `read:stack` token (which the application itself hands out via `CCMenuUrlController` for the CCMenu integration) and the target stack's `repo_owner/repo_name/environment` path (which is often predictable/enumerable). No privilege escalation, additional secrets, or write access is needed — only the existing scoped read token.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped resolver, exactly like `BaseController#stack`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the direct `Stack.from_param!` call so the `current_api_client.stack_id` scoping is enforced consistently across all API controllers.

### Proof of Concept
1. Create (or use the existing CCMenu flow) an `ApiClient` scoped to stack A: `ApiClient.create!(creator: user, name: 'CCMenu Client', permissions: %w[read:stack], stack_id: stack_a.id)`.
2. Using that client's `authentication_token`, issue: `GET /api/stacks/<owner_b>/<repo_b>/<env_b>/ccmenu` (stack B, unrelated to the token's `stack_id`).
3. `require_permission :read, :stack` passes because the client has `read:stack` in `permissions`.
4. `CCMenuController#stack` executes `Stack.from_param!(params[:stack_id])` — unscoped — resolving stack B despite the token being scoped only to stack A.
5. The response renders stack B's CI/deploy status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`), which the token was never authorized to see.
