### Title
CCMenu API bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides `BaseController#stack` with a version that does not honor the `ApiClient`'s `stack_id` scoping, so a token that is only authorized (`read:stack`) for one specific stack can be used to read the build/deploy status of any other stack via the CCMenu endpoint.

### Finding Description
`Shipit::Api::BaseController` enforces stack scoping for API tokens through two cooperating methods: `stacks`, which restricts the visible `Stack` set to `current_api_client.stack_id` when the client is scoped, and `stack`, which resolves the requested stack from that restricted set: [1](#0-0) 

Every other API controller (deploys, tasks, hooks, merge_requests, etc.) relies on this inherited `stack` method, so a token created with `stack_id` set to Stack A cannot resolve or act on Stack B — `stacks.from_param!` raises `RecordNotFound` for stacks outside the scope.

`CCMenuController`, however, defines its own `stack` private method that calls `Stack.from_param!(params[:stack_id])` directly, completely bypassing `current_api_client.stack_id` scoping: [2](#0-1) 

`require_permission :read, :stack` only checks that the string permission `"read:stack"` is present on the token via `ApiClient#check_permissions!`; it never checks which specific stack the token is bound to: [3](#0-2) 

The binding broken is: `ApiClient.stack_id` (the stack a token authorizes) `== stack_id` (the stack the request actually touches). This holds for every API controller that uses the inherited `BaseController#stack`, but is broken specifically in `CCMenuController`, which re-defines `stack` to ignore the scoping.

This is reachable with an unprivileged, minimally-scoped token: `CCMenuUrlController#client` creates (or reuses) a per-user `ApiClient` with only `read:stack` permission, generated on demand for any user who can view a stack page: [4](#0-3) 
An operator can also explicitly scope an `ApiClient` to a single stack via the `stack` association exposed on the model, intending that token to be usable only for that stack: [5](#0-4) 

Because `CCMenuController#show` calls the overridden `stack` method to build the response, any valid `read:stack` token — regardless of the stack it was scoped to when created — can be replayed against `/api/*/ccmenu/*stack_id` for an arbitrary `stack_id` and will render that other stack's data: [6](#0-5) 

### Impact Explanation
This crosses the "unauthenticated/unauthorized read of stack state" boundary called out as a High-severity impact: a token that a Shipit operator scoped to one stack (or an ambient CCMenu token issued for stack A) discloses build status, last build label/time, lock state, and web URL for any other stack in the installation, without the token ever being authorized for that stack. This is a genuine authorization-boundary bypass — the credential's authorized scope (`ApiClient.stack_id`) and the resource it actually operates on diverge, exactly the class of binding violation the report highlights (an authorized scope not enforced on the acted-upon resource).

### Likelihood Explanation
Exploitation only requires possession of any valid `read:stack`-scoped `ApiClient` token — no elevated Shipit session, GitHub credentials, or admin access is needed beyond what is already necessary to obtain such a token for one's own stack (e.g., visiting `/ccmenu/*stack_id` as any authenticated Shipit user, which mints a token automatically). The overridden `stack` method requires no additional exploitation technique; it's a direct method call with attacker-controlled `params[:stack_id]`.

### Recommendation
Remove the private `stack` override in `Shipit::Api::CCMenuController` (and the analogous override in `Shipit::CCMenuUrlController` if scoping is desired there too) so it inherits `BaseController#stack`/`#stacks`, ensuring `current_api_client.stack_id` scoping is enforced consistently across all API endpoints, including CCMenu.

### Proof of Concept
1. As Shipit user A, visit a page that triggers `CCMenuUrlController#fetch` for Stack A (e.g., via the CCMenu URL feature), obtaining a token scoped to `read:stack` for the user (or have an operator create an `ApiClient` with `stack: stack_a`, `permissions: ['read:stack']`).
2. Using that token, issue `GET /api/<anything>/ccmenu/<stack_b-owner>/<stack_b-name>/<stack_b-environment>?token=<token>` where Stack B is a stack the token was never scoped to.
3. Observe that `CCMenuController#show` returns Stack B's build/deploy XML successfully (HTTP 200), even though the token's `stack_id` (if set) points only to Stack A — demonstrating the scoping bypass, in contrast to any other API endpoint (e.g., `/api/*/stacks/<stack_b_id>`) which would 404 for the same token due to `BaseController#stacks` filtering.
