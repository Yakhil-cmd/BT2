### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but every event handler resolves its target Stack/Commit from the independent `repository.full_name` field, allowing a webhook validly signed by one organization's secret to write data into any other organization's repository hosted on the same Shipit instance - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
In the multi-organization GitHub App configuration, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using an attacker-supplied field (`repository.owner.login`), while every `Webhooks::Handlers::Handler` subclass resolves the actual `Repository`/`Stack` to mutate using a *different*, independently-controlled field in the same JSON body (`repository.full_name`). Because the HMAC only covers the raw body and not a specific binding between these two fields, a webhook payload signed with Org A's secret can declare `repository.owner.login = "OrgA"` (to pass signature verification) while setting `repository.full_name = "OrgB/some-repo"` (to target a different organization's repository), breaking the trust binding: `organization authenticated == repository written`.

### Finding Description
The webhook signature check is: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`repository_owner` is read from the unauthenticated JSON body itself, and it is used only to pick which `GitHubApp` (and thus which `webhook_secret`) to validate against, via `Shipit.github(organization:)`, which does per-organization lookups in the multi-app config: [2](#0-1) 

Once the signature is confirmed valid for the *claimed* organization, `create` dispatches the same raw JSON `params` to every registered handler for the event, without ever re-checking that the target repository actually belongs to that organization: [3](#0-2) 

Every handler resolves its target `Stack`/`Repository` using `repository.full_name`, a field wholly independent from `repository.owner.login`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

For example, `StatusHandler` looks up commits purely by `sha` (global, not scoped to org) and writes a `Status` on them: [5](#0-4) 

and `PushHandler` triggers a sync of any stack matching `branch` for the repo resolved from `full_name`: [6](#0-5) 

`docs/setup.md` documents this multi-organization deployment as a first-class, supported configuration where a single Shipit instance hosts several GitHub Apps (and their distinct `webhook_secret`s) for different organizations, each with its own set of repositories/stacks in the same database: [7](#0-6) 

Before vs. after the attack:
- Before: signature verification for organization `X` should imply that only data belonging to `X`'s repositories can be legitimately mutated by that request.
- After: an attacker who knows (or controls) Org A's `webhook_secret` (e.g., they are an admin of Org A's own GitHub App settings, which is normal for a "trusted" org onboarded to this shared Shipit instance) can forge a payload that is verified using Org A's secret but whose `repository.full_name` names a repository belonging to Org B — a repository this attacker has no access or authorization for — and have Shipit act on it (creating commit statuses, triggering github syncs/deploys eligibility signals, processing pull_request/merge events, etc., for Org B's stacks).

### Impact Explanation
This breaks the binding "organization authenticated == repository written," resulting in cross-organization/cross-repository writes on a shared Shipit instance: an actor who only controls one tenant's webhook secret can inject fabricated GitHub events (commit statuses, pushes, pull request/label events, check-suite results) that get applied to another tenant's Stack/Repository data. Depending on which event types are abused, this can influence CI status used for merge/deploy safety checks (`Commit#create_status_from_github!`) or trigger `GithubSyncJob` against another org's repository, i.e. cross-repository writes / unauthorized-state manipulation on data the attacker's own organization signature should not be able to touch.

### Likelihood Explanation
This requires the deployment to use the documented multi-organization GitHub App configuration (multiple orgs sharing one Shipit instance and database) and requires the attacker to know one organization's `webhook_secret` (typically obtainable by any org admin who is legitimately onboarded to configure their own GitHub App webhook on the shared instance — not a Shipit `ApiClient` token, GitHub App private key, or session compromise). No other privilege is required: the attacker crafts a raw JSON body with mismatched `repository.owner.login` vs `repository.full_name` and computes the HMAC with their own known secret. This is a plausible, realistic scenario for the explicitly-supported multi-tenant deployment mode.

### Recommendation
When verifying the webhook signature for a given organization, the handler dispatch should also enforce that every field referencing a repository/organization in the payload (`repository.full_name`'s owner, `organization.login`, etc.) is consistent with `repository_owner`/the organization whose secret validated the signature, rejecting (422) any payload where they diverge. Alternatively, resolve the `Repository`/`Stack` only from the verified organization, and reject events for repositories not owned by that organization before handing the payload to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`.

### Proof of Concept
1. Deploy Shipit configured with the multi-organization GitHub App schema (as in `docs/setup.md`), with Org A and Org B both onboarded (each with its own `app_id`/`webhook_secret`), and Org B has an existing Stack/Repository with tracked commits.
2. As an admin of Org A's own GitHub App (legitimate access to Org A's `webhook_secret`, e.g. because Org A itself administers/configures its webhook settings), craft a `status` event JSON body:
   ```json
   {
     "sha": "<sha of a commit belonging to Org B's repo>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/some-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac>` using Org A's `webhook_secret` over the raw body.
4. `POST /webhooks` with `X-Github-Event: status` and the header above.
5. `verify_signature` resolves `repository_owner = "OrgA"`, fetches Org A's `GitHubApp`, and validates the signature successfully (attacker knows Org A's secret).
6. `StatusHandler#process` runs unmodified against `Commit.where(sha: params.sha)`, which matches Org B's commit (since lookup is global by sha, not scoped to the authenticated org), and creates a forged `Status` record on Org B's commit — a write the attacker was never authorized to make, achieved purely by holding Org A's webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
