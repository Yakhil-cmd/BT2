### Title
Attestations granted via the `attested` authentifier can never be revoked by the attestor - ([File: definition.js])

### Summary
The `attested` address-definition primitive and `spender_attested` asset condition let an attestor address vouch for another address. Once an attestation unit is posted, the `attestations` table only ever receives `INSERT`s — there is no message type, opcode, or storage mechanism that lets the attestor revoke, expire, or supersede-to-false a previously issued attestation. Consequently, any privilege that was granted to an address through `attested`/`spender_attested` becomes permanent, exactly mirroring the "strategist can't be removed" bug class: a role/permission can be granted but never revoked by the party that granted it.

### Finding Description
The `attested` definition operator lets an address's spending condition be satisfied if a listed attestor has ever attested that address: [1](#0-0) 

The same trust model backs `spender_attested` assets, where payment validation requires the payer/issuer to be an "attested" address before a transfer or issuance is allowed: [2](#0-1) 

Attestation records are written via the `attestation` app message and inserted into the `attestations` table with no delete, expiry, or “revoked” flag: [3](#0-2) 

The `attestations` table schema itself has no field capturing a validity window, sequence number that could be overridden, or revocation status — it is a pure append-only ledger of `(unit, message_index, attestor_address, address)`: [4](#0-3) 

This is architecturally distinct from the `asset_attestors` mechanism (a different, unrelated feature), where the *asset definer* can fully replace the attestor list for an asset at any time — that path already supports revocation: [5](#0-4) [6](#0-5) 

But individual address attestations (the `attestation`/`attested` primitive used in address definitions and in `spender_attested` eligibility checks) have no analogous "clear list" or "latest wins" semantics — an attestation, once issued, is a permanent grant that the attestor cannot walk back.

### Impact Explanation
Any address definition using `['attested', address, [attestor,...]]` as an authorization branch, or any asset relying on `spender_attested`, permanently authorizes every address that was ever attested by the specified attestor(s) — even if the attestor later determines the attestation was made in error, the attested party's KYC/compliance status changed, the attested address was compromised, or the attestor wants to revoke trust for any legitimate reason. Since attested-based conditions are commonly used to gate spending rights or asset transfer/issuance eligibility, this can result in indefinite unauthorized spending/issuance rights for an address the attestor no longer trusts — a concrete case of privilege that cannot be revoked by its issuer, directly mapping to the "asset issuance and transfer conditions" and "address definitions and authentifiers" categories.

### Likelihood Explanation
Any wallet owner, asset issuer, or AA definer can construct an address definition or asset (`spender_attested: true`) that depends on `attested`, and any attestor address can attest another address via a standard `attestation` message — these are all ordinary, unprivileged operations reachable by a single posted unit. Once mistakenly or maliciously attested (e.g., attestor's key compromised and used to attest an attacker-controlled address, or business relationship terminated), there is no on-chain remedy; the condition remains permanently satisfiable.

### Recommendation
Introduce a revocation mechanism for attestations, e.g.:
- Support a "latest wins" semantic per `(attestor_address, address)` pair (similar to `asset_attestors`), where a new attestation message from the attestor with an explicit `revoked: true` flag (or empty profile) supersedes prior attestations.
- Modify the `attested` definition-evaluation query to only consider the most recent attestation from each attestor for the address, rather than any historical record, and require the attestation payload to carry an active/inactive status field.

### Proof of Concept
1. Attestor A posts `{app: 'attestation', payload: {address: B, profile: {...}}}`, satisfying a definition `['attested', B, [A]]` used to gate B's spending on a shared/multisig address, or satisfying `spender_attested` for an asset that B wants to receive/issue.
2. B's key is later compromised, or A's relationship with B is terminated.
3. A has no on-chain message type to remove/invalidate the earlier attestation.
4. The `attested` condition for B continues to evaluate true forever (per `definition.js` case `'attested'`, and `validation.js` `spender_attested` check), permanently retaining B's authorization despite A's intent to revoke it.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
