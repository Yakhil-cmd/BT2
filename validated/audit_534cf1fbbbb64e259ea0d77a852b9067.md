This confirms the vulnerability chain. `Stack#env` (base class) is overridden by `ReviewStack#env` at [1](#0-0)  which merges pull request label names (uppercased, value `"true"`) into the env hash with **no allowlist**. `TaskCommands#env` merges `@stack.env` directly at [2](#0-1)  and `TaskCommands#perform`/`#install_dependencies` build `Command.new(command_line, env:, chdir:)` at [3](#0-2) . `Command#start` then runs `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` where `unbundled_env` merges `@env` verbatim into the child process environment at [4](#0-3) . Labels are captured verbatim from the webhook body by `LabelCapturingHandler#capture_labels` at [5](#0-4) , with no restriction on the label name's characters (only a `String` type check in the schema) at [6](#0-5) .

Critically, note the allowlisting mechanism `EnvironmentVariables#permit` at [7](#0-6)  IS used for user-supplied env params via `filter_deploy_envs`/`filter_rollback_envs`/`TaskDefinition#filter_envs` at [8](#0-7)  and [9](#0-8) , and controller tests confirm this filtering rejects unlisted variables like `DANGEROUS_VARIABLE` [10](#0-9) . **However, this filtering is only applied to explicit user/API-supplied `env` params — it is never applied to `ReviewStack#env`'s label-derived hash**, which flows unfiltered through `TaskCommands#env`/`DeployCommands#env` straight into `Command`'s `PTY.spawn`. Tests explicitly confirm labels reach the process env unfiltered: [11](#0-10)  and [12](#0-11)  both assert `env["WIP"]` and `env["BUG"]` are `"true"` directly from `pull_request.labels`, with no whitelist check anywhere in this path.

Since `PTY.spawn` interprets a joined string through a shell and `Command#parse_arguments` at [13](#0-12)  keeps a `shipit.yml` step (e.g. `bundle install`, `bundle exec rake`) as a single string argument to the shell, any environment variable name is a candidate for consultation by that shell-interpreted step — including `GEM_PATH`, which is consulted by RubyGems/`Bundler` `require`/`bundle` machinery. An attacker who opens a PR against a repository configured with `provisioning_behavior: allow_with_label` and applies a label literally named `gem_path` (case-insensitive, since it's upcased) causes `ReviewStack#env["GEM_PATH"] = "true"` to be injected into every task/deploy `Command`'s environment for that review stack, on every run of a shell-interpreted `shipit.yml` step for that PR's review stack.

### Title
Unfiltered pull-request label names become process environment variables (e.g. `GEM_PATH`) in shell-interpreted `shipit.yml` steps - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) as an environment variable set to `"true"`, with no allowlist, unlike the `EnvironmentVariables#permit` allowlist enforced for user/API-supplied env params. This unfiltered hash is merged into `TaskCommands#env`/`DeployCommands#env` and passed straight to `PTY.spawn` when executing `shipit.yml` steps, letting an unprivileged PR author who can apply a label (`allow_with_label`) inject arbitrary environment variable names — such as `GEM_PATH` — into the deploy host's process environment for that review stack's tasks/deploys.

### Finding Description
The broken binding is: the set of environment variable names reaching `PTY.spawn` for a review stack's shell-interpreted steps should equal `Shipit.env keys ∪ fixed keys set by TaskCommands/DeployCommands ∪ allowlisted deploy/task/rollback variable names` (per `EnvironmentVariables#permit`). In practice it equals that set **∪ the set of the PR's label names (uppercased)**, because `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" }` with no filtering, and this merged hash flows unmodified through `Commands#env` → `TaskCommands#env`/`DeployCommands#env` (`lib/shipit/task_commands.rb:33-48`) into `Command.new(command_line, env:, chdir:)` (`lib/shipit/task_commands.rb:17-27`), and ultimately `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` (`lib/shipit/command.rb:92`), where `unbundled_env` merges `@env` verbatim (`lib/shipit/command.rb:103-105`).

The label names themselves are attacker-controlled and unsanitized: `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) persists `params.pull_request.labels.map(&:name)` directly from the webhook JSON body, and the `ExplicitParameters` schema only requires `name` to be a `String` — no format/character restriction. Any GitHub user can create a label named e.g. `gem_path` on their own repository/fork PR and apply it.

Exploit flow: attacker owns/controls a repository with Shipit's `provisioning_behavior` set to `allow_with_label` (a maintainer/operator-chosen mode, but the *label name itself* is attacker-defined text, not restricted to the configured `provisioning_label_name`). Attacker opens a PR, creates and applies a label literally named `gem_path`. GitHub sends a `pull_request` `labeled` webhook; `LabelCapturingHandler` persists `"gem_path"` into `pull_request.labels`. When any task or deploy runs for that review stack (including CI-triggered continuous delivery or a manually triggered restart task), `ReviewStack#env` includes `"GEM_PATH" => "true"`, which reaches every shell-interpreted `shipit.yml` step's process environment via `PTY.spawn`.

Existing guards fail here because: `verify_signature`/webhook signature checks only ensure the webhook truly came from GitHub for that repository — they do not restrict label *names*, which are already user-controlled content on GitHub itself. `EnvironmentVariables#permit`, which correctly allowlists explicit user-submitted deploy/task/rollback `env` params (verified in `test/controllers/api/tasks_controller_test.rb:48-53`), is simply never invoked on `ReviewStack#env`'s label-derived hash — there is no call to `.permit` anywhere in `ReviewStack#env`, `TaskCommands#env`, or `DeployCommands#env`.

### Impact Explanation
An attacker who can open a PR and apply a label on any repository configured for review-stack provisioning (`allow_with_label`/`prevent_with_label`/`allow_all`, since `capture_labels` runs regardless of provisioning behavior as long as a stack is present and not archived) can inject arbitrary environment variable names into every subsequent task/deploy `Command`'s process environment for that PR's review stack. Setting `GEM_PATH="true"` is unlikely by itself to achieve full RCE since RubyGems interprets `GEM_PATH` as a `:`-delimited path list rather than accepting arbitrary shell content, and the value is fixed to `"true"` rather than attacker-chosen (the attacker only controls the *variable name*, not the value) — this significantly limits the practical exploitability of this specific vector for RCE, since there is no mechanism shown here for the attacker to set the *value* of `GEM_PATH` to a malicious path. The demonstrated impact is unauthorized environment variable injection into the shell-interpreted step's process env for that review stack, matching a lower-severity "unintended write/behavior for a repository via unauthenticated/attacker-controlled input" class rather than a demonstrated Critical RCE, because a full exploit requires also controlling the *value*, which this path does not provide (value is hardcoded to `"true"`).

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`review_stacks_enabled`) with some provisioning behavior configured by a maintainer, and a PR from any GitHub user (including from a fork) with label-creation ability on their own PR (GitHub allows repo collaborators to create/apply labels; on a public repo without protections this may be limited to collaborators, but on the attacker's own repository they control this fully). Attacker cost is minimal — a single label application. It is repeatable against any repository with review stacks enabled where the attacker can label PRs.

### Recommendation
Apply an explicit allowlist to `ReviewStack#env`'s label-derived environment variables, analogous to `EnvironmentVariables#permit` for deploy/task/rollback variables — e.g., only forward labels matching a configured pattern/allowlist, or prefix label-derived env keys (e.g., `LABEL_<NAME>`) to avoid colliding with well-known environment variable names like `GEM_PATH`, `BUNDLE_*`, `LD_PRELOAD`, `RUBYOPT`, etc. Additionally, reject or filter label names against a denylist of sensitive/reserved environment variable names before merging into `env`.
