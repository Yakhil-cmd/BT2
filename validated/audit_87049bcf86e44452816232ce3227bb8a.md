### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in StatusHandler#process - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone, with no filtering by the repository named in the same verified webhook payload, unlike its sibling `CheckSuiteHandler` which correctly scopes through `stacks`. Since `sha` values can collide across unrelated repositories/forks and are not GitHub-secret, an attacker who owns any Shipit-registered repository/org can send a validly-signed `status` webhook for their own repo but with a victim's commit `sha`, causing the forged status to be written onto the victim's `Commit` row in another Stack.

### Finding Description
The broken binding: for a webhook payload `P`, every `Commit` mutated by `P` must satisfy `commit.stack.repository.full_name == P.dig('repository','full_name')`. In `StatusHandler#process`: [1](#0-0) 

`Commit.where(sha: params.sha)` queries across **all** stacks/repositories, with no join to `repository_name` or `stacks`. Compare this to `CheckSuiteHandler`, which does scope correctly: [2](#0-1) 

The base `Handler` class even provides the scoped helper `stacks`, derived from `repository_name` in the payload, but `StatusHandler` never uses it: [3](#0-2) 

Signature verification (`WebhooksController#verify_signature`) only proves the payload was HMAC-signed by the GitHub App belonging to the *organization* named in `repository.owner.login`: [4](#0-3) 

It does not prove or check that the `sha` in the payload actually belongs to a commit in that same organization's/repository's history. An attacker who owns `attacker/repo` (registered as a Shipit Stack) has legitimate possession of the webhook secret for their own org, so they can craft and correctly sign an arbitrary JSON body naming their own repository but any `sha` string (e.g., copied from a public victim repo commit) and `state: 'success'`. `WebhooksController#create` dispatches this straight to `StatusHandler.call(params)`, which then finds and mutates **any** `Commit` row across the entire installation matching that `sha`, calling `commit.create_status_from_github!(params)`: [5](#0-4) 

This writes a `Status` record via `statuses.replicate_from_github!` onto the victim commit, which affects `commit.state`/`status` used for deploy-gating logic elsewhere in the app. No existing guard (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema in `StatusHandler.params`) checks repository ownership of the `sha`; they only validate signature and payload shape.

### Impact Explanation
A forged `success` (or any) CI status is written onto a victim Stack's `Commit` that the attacker does not own or control, potentially satisfying `required_statuses`/`blocking_statuses` checks and unblocking or influencing an unauthorized deploy decision on the victim's stack — a cross-repository/cross-tenant write matching the "Critical: payload for one repository mutating another's stack/commit" category. The attack is fully repeatable against any known `sha` (e.g., commits shared across public forks, or any sha the attacker can observe from a victim's public commit history) and requires only that the attacker control one registered Stack to obtain a valid webhook secret.

### Likelihood Explanation
Preconditions are minimal and attacker-controlled: register/own a Shipit Stack for `attacker/repo` (a normal, unprivileged onboarding action), know or copy a target `sha` string, and send one signed POST to `/webhooks`. No GitHub App private key, `secret_key_base`, or victim credentials are needed — only the attacker's own legitimately-issued webhook secret for their own org. This is trivially repeatable and requires no interaction from the victim.

### Recommendation
Scope `StatusHandler#process` to only commits in stacks belonging to the repository named in the verified payload, mirroring `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This uses the inherited `stacks` helper (derived from `repository_name`) so a status can only ever be applied to commits belonging to the repository that was cryptographically verified as the payload sender.

### Proof of Concept
1. Create two `Stack`s, A (`attacker/repo`) and B (`victim/repo`), each with a `Commit` having the identical `sha = "deadbeefcafe..."` (simulate a shared/forked sha).
2. Stub/set `Shipit.github(organization: 'attacker')` webhook secret so a locally-computed HMAC signature is valid (as in `test/controllers/webhooks_controller_test.rb`'s pattern of stubbing `verify_signature`/`verify_webhook_signature`).
3. POST to `/webhooks` with `X-Github-Event: status`, body `{"sha": "<shared sha>", "state": "success", "repository": {"full_name": "attacker/repo", "owner": {"login": "attacker"}}}`, signed correctly for org `attacker`.
4. Assert: `commit_b.statuses.count` increased by 1 and `commit_b.reload.state == 'success'` (victim's commit was mutated) — i.e., assert `commit_b.stack.repository.full_name != payload['repository']['full_name']` yet `commit_b.statuses.last.present?`, proving the repository-scope binding is violated. Also assert `commit_a` was unaffected/duplicated as expected, isolating that the write landed on B's commit despite the payload naming A.
