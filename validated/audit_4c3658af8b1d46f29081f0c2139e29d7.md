Found it: `Shipit::Api::CCMenuController#stack` bypasses the stack-scoping that every other API controller enforces.

### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's deploy state - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` tokens can be scoped to a single stack via `ApiClient#stack_id`, and every other API controller enforces this scope by resolving stacks through the `stacks` helper (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`) before calling `.from_param!`. `Shipit::Api::CCMenuController` instead defines its own `stack` method that calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, breaking the "stack a token authorises" vs "stack it touches" binding.

### Finding Description
`Shipit::Api::BaseController` centralizes the token-to-stack authorization binding in the `stacks`/`stack` helpers: [1](#0-0) 

`Shipit::Api::StacksController` (and other API controllers) correctly use `stacks.from_param!(params[:id])`, ensuring a stack-scoped client can only resolve the one stack it was authorized for: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to call `Stack.from_param!` directly on the `Stack` class rather than the caller's authorized `stacks` scope: [3](#0-2) 

The controller only enforces `require_permission :read, :stack` (a permission-string check via `ApiClient#check_permissions!`), which never inspects `current_api_client.stack_id`: [4](#0-3) 

The equality that should hold — "stack a token authorizes" == "stack it touches" — is broken here: `current_api_client.stack_id` is never consulted, so `stack_id` == authorized stack, but `params[:stack_id]` (attacker-controlled) == the stack actually touched, and these can differ.

Note that `CCMenuController` also overrides `authenticate_api_client` to authenticate via `params[:token]` (a query-string token, as intentionally generated by `CCMenuUrlController`), which is a deliberate, documented design (tokens embedded in CCMenu URLs). That part is in scope/by design; the vulnerability is that the resulting client's `stack_id` scope is not honored for stack resolution.

### Impact Explanation
Any holder of a stack-scoped `ApiClient` token with `read:stack` permission (e.g., a CCMenu integration token intentionally created and scoped to one stack, as shown in `Shipit::CCMenuUrlController`) can supply an arbitrary `stack_id` to `GET /api/stacks/:stack_id/ccmenu.xml` and read deploy/rollback status (`deploys_and_rollbacks.last`) for any other stack in the installation, not just the one it was authorized for. This is an unauthorized read of stack/task state across stacks (High severity per the rules: "unauthenticated/unauthorized read of stack state, task streams or deploy output"), even though the token was deliberately scoped to a single stack. [5](#0-4) 

### Likelihood Explanation
Likelihood is meaningful but bounded: exploitation requires possession of a valid, stack-scoped `ApiClient` token (which is by design distributed to users/tools integrating CCMenu for one stack) with `read:stack` permission, and knowledge/guessing of another stack's `to_param` (its numeric id or environment slug). No secret guessing or privilege escalation beyond parameter substitution is required once such a token is held — this is a straightforward IDOR caused by the missing scoping check, distinguishing it from the every-other-controller pattern that does enforce scoping correctly.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the caller's authorized scope, mirroring the rest of the API controllers, e.g. `stacks.from_param!(params[:stack_id])`, where `stacks` is inherited from `BaseController` and already accounts for `current_api_client.stack_id`.

### Proof of Concept
1. Create (or otherwise obtain) an `ApiClient` scoped to `stack_id: A` with `read:stack` permission (this is exactly what `Shipit::CCMenuUrlController#client` does for any user who can view stack A's page: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`).
2. Use the resulting `authentication_token` (embedded as `?token=` in the CCMenu URL for stack A) against a different stack B's endpoint:
   `GET /api/stacks/<stack_B_id_or_env>/ccmenu.xml?token=<token_for_stack_A>`
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(...)`, the request succeeds and returns stack B's deploy/rollback status, even though the token's `stack_id` is A.
