### Title
Bridge ERC20 Transfer Permanently Stuck When Recipient Is Blacklisted by Token — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`handleERC20Transfer` in the Kaia service-chain bridge performs the actual ERC20 token transfer **after** updating nonce-tracking state, but within the same atomic transaction. If the token transfer reverts (e.g., because the recipient is blacklisted by a token such as USDC), the entire transaction reverts, rolling back all nonce state. Because `closedValueTransferVotes` is also rolled back, operators can re-vote — but the transfer will always revert again. `lowerHandleNonce` and `recoveryBlockNumber` are permanently stuck, and in `modeMintBurn` mode the bridged tokens are burned on the source chain but never minted on the destination chain, causing permanent asset loss.

---

### Finding Description

In `contracts/service_chain/bridge/BridgeTransferERC20.sol`, `handleERC20Transfer` executes in this order: [1](#0-0) 

1. `_lowerHandleNonceCheck` — validates nonce is ≥ `lowerHandleNonce`
2. `_voteValueTransfer` — when threshold is reached, sets `closedValueTransferVotes[nonce] = true` and returns `true`
3. `_setHandledRequestTxHash` — marks the request tx hash as handled
4. `handleNoncesToBlockNums[nonce] = blockNum` — records the block number
5. `_updateHandleNonce` — advances `lowerHandleNonce` and `recoveryBlockNumber`
6. Emits `HandleValueTransfer`
7. **Performs the actual token transfer**: `IERC20(_tokenAddress).safeTransfer(_to, _value)` (or `mint`)

If step 7 reverts (e.g., `_to` is blacklisted by the ERC20 token), the entire Solidity transaction reverts, undoing **all** state changes from steps 2–5:

- `closedValueTransferVotes[nonce]` is reset to `false`
- `handleNoncesToBlockNums[nonce]` is never set
- `lowerHandleNonce` does not advance
- `recoveryBlockNumber` does not advance

`_updateHandleNonce` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive nonces starting from `lowerHandleNonce`: [2](#0-1) 

Since `handleNoncesToBlockNums[stuck_nonce]` is never set, `lowerHandleNonce` is permanently stuck. The `_voteValueTransfer` check: [3](#0-2) 

Because `closedValueTransferVotes` is rolled back on revert, operators can re-vote indefinitely — but every attempt to execute the transfer will revert again, creating an infinite retry loop.

The off-chain bridge manager (`node/sc/bridge_manager.go`) submits `handleERC20Transfer` transactions driven by the `recoveryBlockNumber`: [4](#0-3) 

Since `recoveryBlockNumber` never advances past the stuck block, the recovery system perpetually re-scans and re-submits the failing nonce.

---

### Impact Explanation

**In `modeMintBurn = true` mode** (child-chain bridge): tokens are burned on the source chain when `requestERC20Transfer` is called. If `handleERC20Transfer` permanently reverts on the destination chain, those tokens are burned and never minted — **permanent, irrecoverable loss of bridged assets**.

**In `modeMintBurn = false` mode** (parent-chain bridge): tokens are locked in the source bridge contract. The recipient can never receive them, and there is no mechanism to refund the sender.

Additionally, `lowerHandleNonce` being stuck means `recoveryBlockNumber` never advances, causing the bridge recovery system to waste operator gas indefinitely on failed transactions.

There is no `skipNonce` or emergency-skip function in the bridge contract to bypass the stuck nonce.

---

### Likelihood Explanation

Low-to-medium. Requires:
1. An ERC20 token with a blacklist feature (e.g., USDC, USDT) to be registered in the bridge.
2. The recipient address (`_to`) to be blacklisted by that token — either before or after the bridge request is made.

USDC blacklisting is an operational reality (Tether/Circle have blacklisted hundreds of addresses). Any user who initiates a bridge transfer to an address that subsequently gets blacklisted triggers this condition without any privileged access.

---

### Recommendation

Separate the nonce-state commit from the token transfer. Two approaches:

1. **Commit-then-try pattern**: Commit all nonce state first, then attempt the transfer. If the transfer fails, emit a `TransferFailed` event and allow the recipient to claim via a separate `claimFailed` function, rather than reverting the entire transaction.

2. **Pull pattern**: Instead of pushing tokens to `_to` in `handleERC20Transfer`, record the pending balance in a mapping (`pendingBalances[_to][token] += value`) and let the recipient pull via a separate `claim()` function. This decouples nonce advancement from token delivery.

Example for approach 2:
```solidity
mapping(address => mapping(address => uint256)) public pendingBalances;

function handleERC20Transfer(...) public onlyOperators {
    // ... vote and nonce logic ...
    pendingBalances[_to][_tokenAddress] += _value;
}

function claimERC20(address _token) external {
    uint256 amount = pendingBalances[msg.sender][_token];
    require(amount > 0, "nothing to claim");
    pendingBalances[msg.sender][_token] = 0;
    IERC20(_token).safeTransfer(msg.sender, amount);
}
```

The same fix applies to `handleKLAYTransfer` in `BridgeTransferKLAY.sol`: [5](#0-4) 

where a contract recipient that reverts on `receive()` causes the same permanent nonce-stuck condition.

---

### Proof of Concept

1. Deploy the bridge in `modeMintBurn = true` mode with a USDC-like token (with blacklist) registered.
2. User A calls `requestERC20Transfer(token, recipientAddr, 100, 0, "")` on the source chain. Tokens are burned. `requestNonce` becomes 1.
3. Token issuer blacklists `recipientAddr`.
4. Bridge operators call `handleERC20Transfer(txHash, A, recipientAddr, token, 100, 0, blockNum, "")` on the destination chain.
5. Voting threshold is reached; `closedValueTransferVotes[0] = true`; `handleNoncesToBlockNums[0] = blockNum`; `_updateHandleNonce` runs; then `IERC20(token).safeTransfer(recipientAddr, 100)` reverts due to blacklist.
6. Entire transaction reverts. `closedValueTransferVotes[0]` is reset to `false`. `handleNoncesToBlockNums[0]` is `0`. `lowerHandleNonce` remains `0`.
7. Operators retry — same result. `lowerHandleNonce` is permanently `0`.
8. 100 tokens are permanently burned on the source chain and never minted on the destination chain. [6](#0-5) [7](#0-6)

    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }
