## Title
Cross-organization webhook forgery via `organization.login` fallback in signature verification vs `repository.full_name` used for stack lookup - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on a value it reads from the *unverified* JSON body, and that value can come from a different field than the one the event handlers use to resolve which repository/stack the event applies to.

### Finding Description
`verify_signature` picks the app used to check the signature via: [1](#0-0) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This value is looked up *before* the signature is verified, and it is only used to choose `Shipit.github(organization: repository_owner)` for HMAC comparison: [2](#0-1) 

Once verification passes, the full raw payload is handed unmodified to the registered handler, and the handler resolves the target stack using an entirely different field — `repository.full_name`: [3](#0-2) 

In a multi-organization deployment (`config/secrets*.yml` supporting a `github: { OrgOne: {...}, OrgTwo: {...} }` map, as documented in `test/dummy/config/secrets_double_github_app.yml`), each tenant organization has its **own** GitHub App installation and its **own** `webhook_secret`. Because `repository_owner` falls back to the top-level `organization.login` key when `repository.owner.login` is absent, an attacker who administers their own tenant org ("OrgOne", with a known/derivable webhook secret they control) can craft a payload where:
- `organization.login = "OrgOne"` (so `repository_owner` resolves to their own org, letting them compute a valid `X-Hub-Signature` with their own webhook secret), while
- `repository.full_name = "OrgTwo/victim-repo"` (a repository/stack belonging to a different tenant they do not control).

The signature check only validates that *some* organization's secret matches; it never confirms that the organization whose secret validated the signature is the same organization that owns the `repository` object the handlers subsequently act on. This breaks the trust binding: `{organization authenticated} == {repository written}`.

### Impact Explanation
Handlers such as `PushHandler` (`stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }`), `StatusHandler` (creates commit statuses used in deploy safety checks), and `MembershipHandler` (creates/updates `Team` membership, which feeds into `Shipit.github_teams` authorization) all key off `repository.full_name` or `organization.login` taken from the same attacker-controlled JSON body, independent of which org's secret validated the request. An attacker abusing this could inject forged GitHub statuses, forged pushes, or forged team membership changes into another tenant's stack — this reaches the High-impact bucket ("escalation into `Shipit.github_teams` authorization" via `MembershipHandler`, and "unauthenticated read/write of stack state" via forged push/status events for a repository the attacker does not own).

### Likelihood Explanation
Exploitability is realistic only in **multi-tenant Shipit deployments** where multiple GitHub organizations are configured (a documented, supported configuration — see `config/secrets.development.example.yml` and `test/dummy/config/secrets_double_github_app.yml`). The attacker needs to control at least one legitimate tenant organization's webhook secret (obtainable simply by being an admin of their own org's GitHub App installation, which is the normal, unprivileged self-service capability every tenant already has) and craft a raw HTTP POST directly to the shared `/github/webhooks` endpoint with a custom JSON body and a matching `X-Hub-Signature`. This does not require compromising the target org, stealing `GITHUB_TOKEN`, or obtaining an `ApiClient` token — only administrative access to one's own onboarded organization in the shared instance.

### Recommendation
Verify the signature against the same organization value that will actually be used by the handlers (`repository.full_name`'s owner), not an independently-resolved `organization.login` fallback. At minimum, after choosing the app/secret for verification, re-derive `repository_owner` strictly from `repository.owner.login` (never falling back to a separate top-level `organization` object when a `repository` key is present), and reject the webhook if `repository.owner.login` and top-level `organization.login` disagree.

### Proof of Concept
1. Deploy Shipit configured with two tenant orgs, `OrgOne` and `OrgTwo`, each with their own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an administrator of `OrgOne` (attacker-controlled), craft a JSON body:
```json
{
  "organization": { "login": "OrgOne" },
  "repository": { "full_name": "OrgTwo/victim-repo" },
  "team": { "id": 1, "name": "evil", "slug": "evil", "url": "https://example.com" },
  "member": { "login": "attacker" },
  "action": "added"
}
```
3. Compute `X-Hub-Signature: sha1=<hmac>` using `OrgOne`'s known `webhook_secret` over the raw body.
4. POST to the shared `webhooks#create` endpoint with `X-Github-Event: membership`.
5. `verify_signature` resolves `repository_owner` to `"OrgOne"` (via the `organization.login` fallback, since `repository.owner.login` is absent) and verifies successfully against `OrgOne`'s secret.
6. `MembershipHandler#process` runs using `params.organization.login == "OrgOne"` for the `Team#organization` field but the underlying `Repository.from_github_repo_name` lookups elsewhere in other handlers (e.g. `PushHandler`, `StatusHandler`) use `repository.full_name`, letting the same crafted body target `OrgTwo/victim-repo` for push/status handlers while using a signature validated only against `OrgOne`.
