### Title
Webhook signature verification selects the GitHub App/organization from a different payload field than the one used to pick the target repository/stack, allowing cross-tenant status/sync forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* `GitHubApp` (and therefore which `webhook_secret`) to validate an inbound webhook against using `repository_owner`, a value read straight out of the untrusted JSON body. Separately, every event `Handler` (e.g. `PushHandler`, `StatusHandler`) resolves *which* `Repository`/`Stack` to act on using a different field of the same untrusted body, `repository.full_name`. Nothing enforces that these two independently-attacker-controlled fields describe the same repository/organization, so a valid HMAC computed with one tenant's webhook secret can be replayed against an arbitrary other tenant's stack.

### Finding Description
`verify_signature` derives the organization used to select the verifying `GitHubApp` purely from the JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the app config keyed by that organization name and calls `verify_webhook_signature`, which is only correct if that organization's `webhook_secret` is the one the attacker used to sign the body: [3](#0-2) 

Multiple, independently configured organizations are an explicitly documented, supported topology, each with its own `webhook_secret`: [4](#0-3) 

Once the signature check passes, `create` dispatches the *whole* raw payload (including `repository.full_name`) to the handler, without re-checking that `repository.full_name`'s owner matches `repository_owner`: [5](#0-4) 

Every handler then determines the actual `Stack`/`Repository` to act on from `repository.full_name`, a field that was never compared to the field used for signature-org selection: [6](#0-5) 

This is precisely the required binding break: the equality `organization(payload) == organization(signature-verified-app)` is checked, but the code silently assumes it also equals `owner(repository.full_name)` used for the actual write. These two JSON fields are populated independently by whoever crafts the raw POST body, so an attacker who legitimately controls (and thus legitimately knows the `webhook_secret` of) *one* onboarded organization on a shared Shipit instance can set `repository.owner.login`/`organization.login` to their own org (so the HMAC check passes against their own secret) while setting `repository.full_name` to `victim-org/victim-repo` (so the handler acts on a completely unrelated tenant's stack).

### Impact Explanation
Handlers act directly on attacker-supplied payload data once dispatched, scoped only by the (attacker-controlled, unverified-against-signing-org) `repository.full_name`:
- `PushHandler` triggers `GithubSyncJob` for any stack matching the forged `full_name`/branch, using `params.after` as the expected head SHA: [7](#0-6) 
- The webhook test suite demonstrates that `status` events write `state`, `description`, `target_url`, and `context` directly from the payload onto a `Commit` looked up only by `sha`, without any additional cross-check to the app/org that authenticated the request — this is the field that Shipit's deploy/merge gating (required checks, merge queue) relies on: [8](#0-7) 

Because a forged, cross-tenant `status` webhook can inject a fabricated "success" status (or resync a foreign stack), this crosses into unauthorized-deploy/merge territory in a multi-organization Shipit installation — the highest-severity bucket defined by the rules (cross-repository writes / unauthorized deploy or merge), reached without ever needing the victim organization's own webhook secret, private key, or session — only the attacker's own, legitimately-possessed org's secret.

### Likelihood Explanation
This requires a multi-tenant Shipit deployment (documented and supported: `github:` keyed by multiple organizations, each with a distinct `webhook_secret`). Any party who legitimately administers one of the onboarded GitHub organizations — a normal, unprivileged relationship to *other* tenants on the same Shipit instance — can exploit this purely by crafting an arbitrary JSON body and signing it with their own webhook secret; no code execution, social engineering, or victim credentials are required. Likelihood is moderate-to-high in any shared/multi-org Shipit installation.

### Recommendation
In `WebhooksController`, after `verify_signature` succeeds, assert that the organization used to select the verifying `GitHubApp` (`repository_owner`) is identical to the owner segment of `repository.full_name` (and of `organization.login` where present) before dispatching to handlers; reject the request with `422` on mismatch. Alternatively, make every handler resolve the target `Repository`/`Stack` using the same `repository_owner` value that was authenticated, rather than trusting `full_name` independently.

### Proof of Concept
Preconditions: a Shipit instance configured with two organizations, `OrgAttacker` (attacker administers this org's GitHub App/webhook and thus legitimately knows `webhook_secret_A`) and `OrgVictim` (unrelated tenant, stack `OrgVictim/victim-repo` exists on the same Shipit instance).

1. Attacker crafts a `status` (or `push`) webhook body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "description": "forged",
  "target_url": "https://attacker.example/fake",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgAttacker" }, "full_name": "OrgVictim/victim-repo" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, body)>` using their own `webhook_secret_A`.
3. POST to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` computes `repository_owner = "OrgAttacker"`, loads `Shipit.github(organization: "OrgAttacker")`, and the signature validates successfully against `webhook_secret_A`.
5. `create` dispatches the full payload to `Shipit::Webhooks.for_event('status')`, whose handler resolves the target repository/commit via `repository.full_name = "OrgVictim/victim-repo"` and the given `sha`, writing the forged status onto the victim's real commit — with no check that `OrgAttacker` and `OrgVictim` are the same.

Note: I was unable to load `app/models/shipit/webhooks/handlers/status_handler.rb` directly within the tool budget; the behavior above (status fields written verbatim from payload, keyed by `full_name`+`sha`) is inferred from `app/models/shipit/webhooks/handlers/handler.rb` (confirmed) plus the observed assertions in `test/controllers/webhooks_controller_test.rb`. This should be verified directly against `status_handler.rb` before remediation.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
