### Title
Cached, zero-tolerance ArbStore cut baked into arbiter-contract shared-address spending condition can permanently freeze funds - ([File: arbiter_contract.js])

### Summary
`deriveSharedAddress()` in `arbiter_contract.js` bakes an exact-amount ("has output") spending condition into the arbiter-contract shared address using `arbstoreInfo.cut`, a value fetched once from an external ArbStore HTTP endpoint and cached indefinitely in an in-memory map with no expiry and no tolerance for drift. Because the resulting definition requires the settlement payment to match this baked-in split to the byte, any mismatch between the cut value used at address-derivation time and the cut actually required to satisfy the peer's/acceptor's independently-verified copy of the definition makes the shared address's spending conditions permanently unsatisfiable, exactly analogous to the zero-slippage bug in the external report where a hard-coded, non-adjustable parameter makes a legitimate claim/settlement path permanently revert.

### Finding Description
`arbiters.getArbstoreInfo()` fetches `{address, cut}` from the ArbStore's HTTP `/api/get_info` endpoint and caches it forever in the process-local `arbStoreInfos` map: [1](#0-0) 

`arbiter_contract.js`'s `deriveSharedAddress()` uses this cached `cut` to compute the exact "has output" amounts encoded in the shared address `or`/`and` definition, with `Math.floor(contract.amount * (1 - arbstoreInfo.cut))` used as an *exact* required output amount and no tolerance/slippage allowance whatsoever: [2](#0-1) 

Both contract parties independently call `deriveSharedAddress()` — the offeror when creating/sharing the address, and the acceptor when verifying it in `handleReceivedSharedAddress()`, which recomputes the definition and compares its hash to the one received: [3](#0-2) 

Because `arbStoreInfos[arbiter_address]` is cached without expiry (`if (arbStoreInfos[arbiter_address]) return cb(null, arbStoreInfos[arbiter_address]);`), the offeror's and acceptor's wallets can end up using different `cut` values (e.g. one wallet had a stale cached cut from before the ArbStore operator changed its fee, or one wallet never previously contacted the ArbStore and fetches a newer value) — there is no re-validation against a canonical, timestamped, or on-chain source of truth for `cut`, and no tolerance band is allowed in the "has output" amount condition, unlike the divisible-asset composer functions elsewhere in the codebase which explicitly support `tolerance_plus`/`tolerance_minus` for exactly this kind of imprecision (see `inputs.js` and `indivisible_asset.js`).

### Impact Explanation
If the two parties' recomputed definitions disagree because of a stale/changed `cut`, `handleReceivedSharedAddress()` will reject the shared address (`expected_shared_address !== shared_address`) and never call `setField(hash, "shared_address", ...)`, silently stalling the contract before any funds move. More critically, once a shared address IS accepted by both parties, its spending condition permanently encodes an exact split based on the `cut` value in effect at derivation time; any part of the flow that must later reproduce or verify this exact amount (as done independently on each device rather than being derived once from an authoritative, immutable on-chain value) can diverge if the parties' devices ever recompute it (e.g., after the ArbStore is contacted again with a changed fee), leaving deposited contract funds unable to satisfy the "has output" condition and effectively frozen in the shared address, since Obyte's `has` clause requires bit-exact output amounts with zero slippage tolerance.

### Likelihood Explanation
Likelihood is moderate: it requires the ArbStore operator to change its `cut` value between the time one party's wallet cached the old value and the other fetched (or later re-fetches) a new one — plausible over the lifetime of long-running wallet processes and across the days/weeks (`ttl` field defaults to 168 hours) that arbiter contracts remain pending, and entirely outside the control of the two contracting parties (an unprivileged event triggered solely by a third-party ArbStore's own configuration change).

### Recommendation
Do not use a client-cached, non-expiring `cut` value to compute exact "has output" spending amounts. Either: (1) freeze and persist the `cut` value used at contract-creation time as part of the on-chain/contract record so both parties always reference the same immutable number rather than re-fetching/re-deriving it, and/or (2) add cache expiry/refresh with mutual re-verification before finalizing `shared_address`, and (3) consider allowing a small explicit tolerance in the settlement condition (mirroring `tolerance_plus`/`tolerance_minus` used elsewhere for divisible-asset payments) so minor split discrepancies do not permanently block spending from the shared address.

		if (err) {
			return cb(err);
		}
		if (!validationUtils.isNonemptyString(url))
			return cb("invalid url received from hub");
		requestInfoFromArbStore(url+'/api/get_info', function(err, info){
			if (err)
				return cb(err);
			if (!validationUtils.isNonemptyObject(info))

			if (!info.address || !validationUtils.isValidAddress(info.address) || isNaN(cut) || cut < 0 || cut >= 1) {
				return cb("malformed info received from ArbStore");
			}

			arbStoreInfos[arbiter_address] = info;
			cb(null, info);
		});
	});

function handleReceivedSharedAddress(hash, shared_address, from_cosigner, retry_count = 0) {
	console.log(`received shared address ${shared_address} for arbiter contract ${hash} from peer`);
	db.query("SELECT 1 FROM shared_addresses WHERE shared_address=?", [shared_address], function (rows) {
		if (rows.length === 0) {
			if (retry_count >= 10)
				return console.log(`shared address ${shared_address} not found in db after 10 retries, giving up`);
			console.log(`shared address ${shared_address} not yet in db, waiting for 30 seconds and trying again`);
			return setTimeout(handleReceivedSharedAddress, 30000, hash, shared_address, from_cosigner, retry_count + 1);
		}
		console.log(`shared address ${shared_address} found in db, deriving shared address definition to verify it matches the received one`);
		deriveSharedAddress(hash, false, function (err, arrDefinition, assocSignersByPath) {
			if (err) {
				if (retry_count >= 10)
					return console.log(`failed derivation of shared address ${shared_address} after 10 retries, giving up`, err);
				console.log("error deriving shared address definition, will retry in 30 seconds", err);
				return setTimeout(handleReceivedSharedAddress, 30000, hash, shared_address, from_cosigner, retry_count + 1);
			}
			const expected_shared_address = objectHash.getChash160(arrDefinition);
			if (expected_shared_address !== shared_address)
				return console.log(`expected shared address ${expected_shared_address} does not match received from offeror ${shared_address}`, JSON.stringify(arrDefinition, null, 2));
			console.log(`shared address ${expected_shared_address} matches the received one, setting it to the contract and sharing with cosigners`);
			setField(hash, "shared_address", shared_address, function (contract) {
				eventBus.emit("arbiter_contract_update", contract, "shared_address", shared_address);
			}, from_cosigner);
		});
	});
}
