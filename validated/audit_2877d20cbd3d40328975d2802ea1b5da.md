### Title
One malicious `system_vote_count` subject can permanently block MCI stabilization and all other votes/AA triggers - ([File: main_chain.js])

### Summary
`markMcIndexStable()` collects every distinct `system_vote_count` subject seen in the units of the MCI being stabilized into `voteCountSubjects`, then processes them serially with a plain `for...of` loop and no error isolation. If `countVotes()` throws for any one subject, the exception aborts the loop before the remaining subjects are counted and before `updateRetrievable()` (and everything chained after it, including `handleAATriggers()`) ever runs — exactly the "one bad item blocks all others in the same batch" pattern described in the report, but here the blocked batch is the entire MCI-stabilization pipeline rather than an independent set of markets.

### Finding Description
In `main_chain.js`, while stabilizing an MCI, each unstable unit's messages are scanned and any `system_vote_count` payload is collected into a shared array: [1](#0-0) 

After all units of the MCI are processed, the subjects are counted one by one with no try/catch: [2](#0-1) 

`countVotes()` throws in several reachable situations, e.g. when fewer than `COUNT_WITNESSES` addresses have accumulated `op_list` votes: [3](#0-2) 
or when no numeric-vote median can be found: [4](#0-3) 
or when there are no votes yet for the requested subject in the emergency path: [5](#0-4) 

Any unprivileged unit poster can include a `system_vote` / `system_vote_count` message pair (`validation.js` only checks the subject is one of the five known names and that it's a single such message per unit): [6](#0-5) 
By crafting the vote state so that one of the five subjects (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) ends up with an edge-case vote distribution (e.g. too few distinct OP candidates, or a distribution that lands exactly on an unreachable median condition), the poster forces `countVotes()` to throw for that subject at MCI-stabilization time. Because the subjects are iterated with a bare `for...of` and `await`, this single throwing subject:
1. prevents any subsequent subject in `voteCountSubjects` from being counted for that MCI (blocking updates to unrelated system parameters, analogous to one perpetual market blocking others' funding-rate updates), and
2. prevents `updateRetrievable()` → `calcCommissions()` → `handleAATriggers()` from ever executing for that MCI, since the uncaught exception unwinds the `async function` before those calls are reached.

### Impact Explanation
Because `markMcIndexStable` is on the critical path invoked from `stabilizeMci()`/`advanceMcStability()` inside an open DB transaction, an uncaught exception here does not just skip a vote count — it aborts the stabilization step for the MCI while inside `conn.query("BEGIN")`/before `COMMIT`, and blocks `handleAATriggers()` and `updateTpsFees()` for that MCI. Since MCI stabilization is sequential and each subsequent MCI's stabilization builds on the previous one being finalized, a permanently-throwing subject (a vote configuration that will always fail the same way, e.g., persistently fewer than 12 distinct OP candidates) can repeatedly break stabilization every time that subject reappears in `voteCountSubjects`, i.e., every unit that includes another `system_vote_count` for that subject reintroduces the fault. This matches the "network unable to confirm new units" impact bar: node operators would see stabilization exceptions/crashes rather than silent skips, but the net effect is denial of forward progress for stabilization-dependent state (AA triggers, TPS fee updates, and other system votes) triggered by an ordinary, unprivileged unit author.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to control/accumulate a vote distribution that reaches one of the `throw Error(...)` branches in `countVotes` at the moment a `system_vote_count` for that subject stabilizes. This is fully achievable by an unprivileged actor without any special access — voting itself only requires posting ordinary `system_vote` / `system_vote_count` units, and vote weight is based on the poster's own stable balance, so a well-funded or well-timed attacker (e.g., voting for `op_list` with an intentionally too-small OP set, or manipulating the timing so the numeric-vote median search yields `undefined`) can reliably reproduce the throw.

### Recommendation
Wrap each `countVotes()` call in the loop with its own error handling so a failure processing one subject does not prevent processing the rest or block `updateRetrievable()`/`handleAATriggers()`:
```js
for (let subject of voteCountSubjects) {
    try {
        await countVotes(conn, mci, subject);
    } catch (e) {
        console.log(`countVotes failed for subject ${subject}: ${e}`);
        // log/alert, but continue with other subjects and finish stabilization
    }
}
updateRetrievable();
```
Additionally, harden `countVotes()` itself so genuinely reachable edge cases (too few OP candidates, no median found, no votes yet for an emergency subject) are handled as no-ops/log-and-skip rather than thrown exceptions, since they are driven by attacker-influenced input, not internal invariants.

### Proof of Concept
1. As an ordinary user, accumulate stable balance and post `system_vote` units voting `op_list` for a set of addresses such that, across all historical votes, strictly fewer than `constants.COUNT_WITNESSES` (12) distinct OP addresses have ever been voted for.
2. Post a `system_vote_count` unit with `payload: "op_list"`.
3. When this unit's MCI stabilizes, `saveUnstablePayloads()` adds `"op_list"` to `voteCountSubjects` [1](#0-0) , and the post-loop code calls `countVotes(conn, mci, "op_list")` [2](#0-1) .
4. Inside `countVotes`, `op_rows.length !== constants.COUNT_WITNESSES` is true, so it throws `"wrong number of voted OPs: " + ops.length` [3](#0-2) , aborting the `for` loop before any other queued `voteCountSubjects` are processed and before `updateRetrievable()`/`handleAATriggers()` run for that MCI — blocking stabilization-dependent processing network-wide until the underlying vote state is fixed.
