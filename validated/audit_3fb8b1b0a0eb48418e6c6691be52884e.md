### Title
Cross-organization webhook signature confusion allows attacker to trigger unauthorized `sync_github` on a victim org's stack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` derives the signing organization solely from `repository.owner.login` (or `organization.login`) in the JSON body, and verifies the HMAC signature against that organization's `webhook_secret`. `Handler#repository_name`/`#stacks` independently re-read `repository.full_name` from the same body to select which `Repository`/`Stack` to act on, with no check that the resolved repository's owner matches the organization whose secret verified the signature.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `repository_owner` (used in `verify_signature` to pick `Shipit.github(organization: repository_owner)`) must equal `Repository.from_github_repo_name(repository_name).owner` (used in `Handler#stacks` to pick the target stack). In this code, both values are read from attacker-controlled JSON fields in the *same* webhook body — `repository.owner.login` for the former [1](#0-0)  and `repository.full_name` for the latter [2](#0-1)  — and nothing forces them to be consistent.

Exploit flow: `WebhooksController#create` parses the raw POST body and, after `verify_signature` passes, dispatches to handlers with the *same* parsed params [3](#0-2) . `verify_signature` fetches `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature, raw_post)`, which computes `OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message)` using organization A's `webhook_secret` [4](#0-3) . An attacker who owns org A can compute a valid signature over an arbitrary body, because they control A's `webhook_secret` (their own org's webhook config) and the entire raw body, including `repository.full_name`, which they set to `'B-org/private-repo'`. `PushHandler#process` then calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` where `stacks` resolves via `Repository.from_github_repo_name(repository_name)` — i.e., B's repository — using the attacker-chosen `after` SHA [5](#0-4) . `Repository.from_github_repo_name` does a plain `find_by(owner:, name:)` lookup with no ownership/tenant check against the verifying organization [6](#0-5) .

No existing guard prevents this: `verify_signature` only checks that *some* organization's secret matches the raw body; it never re-derives or pins the "owning organization" implied by `repository.full_name` used later by the handler. `drop_unhandled_event` and `ExplicitParameters` schemas (`requires :ref`, `requires :after`) validate shape, not ownership. There is no cross-check anywhere in the controller or `Handler` base class comparing `repository_owner` to the owner embedded in `repository.full_name`.

### Impact Explanation
This is a payload for one repository/organization mutating another organization's stack — matches the Critical category "a payload for one repository mutating another's stack" and "unauthorized deploy" trigger. Concretely, an attacker who controls only their own org A's webhook secret can force `GithubSyncJob`-driving `sync_github(expected_head_sha:)` calls against B's stack with an attacker-chosen SHA, potentially causing Shipit to treat an arbitrary/malicious commit as the expected head for B's stack, affecting sync/deploy state. The attack is repeatable against any stack in the Shipit instance whose `full_name` the attacker can guess/know, regardless of tenant boundaries, as long as the attacker owns any single onboarded GitHub organization in this Shipit instance.

### Likelihood Explanation
Preconditions are modest: the attacker must own/control at least one GitHub organization (A) that is configured in this Shipit instance with a `webhook_secret` they know (trivial if it's their own org and they set up the webhook, or already satisfied for any org they legitimately manage), and B's repository/stack must already exist in Shipit. No Shipit session, API token, or GitHub App private key is required — only knowledge of A's `webhook_secret`, which an org owner naturally possesses. The attacker crafts one raw HTTP POST to `/webhooks` with a forged `X-Hub-Signature` computed from their own secret, requiring no interaction with GitHub's real webhook delivery system. This is fully repeatable and low-cost per request.

### Recommendation
In `Handler#stacks`/`#repository_name` (or in `WebhooksController#create`), require that the organization used to verify the signature (`repository_owner`) matches the owner embedded in the target `repository.full_name` before resolving/acting on any `Repository`/`Stack`; reject the webhook (422) if they diverge. Alternatively, pass the verified `repository_owner` down to handlers and have `Repository.from_github_repo_name` (or a new scoped lookup) filter by that verified owner rather than trusting the unauthenticated `full_name` owner segment in isolation.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "push webhook signed by org A cannot mutate org B's stack via mismatched repository.full_name" do
  stack = shipit_stacks(:shipit) # belongs to org B, e.g. "B-org/private-repo"
  body = {
    ref: 'refs/heads/master',
    after: 'attacker-controlled-sha',
    repository: {
      full_name: stack.repository.github_repo_name, # "B-org/private-repo"
      owner: { login: 'A-org' } # attacker's own org, used only for signature verification
    }
  }.to_json

  github_app_a = mock('github_app_a')
  github_app_a.stubs(:verify_webhook_signature).returns(true)
  Shipit.stubs(:github).with(organization: 'A-org').returns(github_app_a)

  stack.expects(:sync_github).with(expected_head_sha: 'attacker-controlled-sha')

  post :create, body: body,
       headers: { 'X-Github-Event' => 'push', 'X-Hub-Signature' => 'sha1=whatever' }

  assert_response :ok
end
```
This demonstrates that `repository_owner` ("A-org", used for signature verification) and the owner embedded in `repository.full_name` ("B-org", used to resolve the target stack) diverge, yet `sync_github` still fires against B's stack — confirming the broken binding.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
