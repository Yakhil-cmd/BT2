Confirmed. The `Handler` base class provides a `stacks` helper that scopes to the repository named in the payload via `Repository.from_github_repo_name(repository_name)&.stacks`, but `StatusHandler#process` does not use it — it queries `Commit.where(sha: params.sha)` directly, unscoped by repository or stack.

### Title
`StatusHandler#process` mutates commit status across repositories via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, ignoring the `repository.full_name` in the verified webhook payload, and calls `commit.create_status_from_github!(params)` on every matching row. Because `sha` is not unique across stacks/repositories in the schema, a webhook signed by attacker-org's own valid `webhook_secret` can write a `Status` (and trigger CI-gated side effects) on a commit belonging to an unrelated victim-org stack, provided both stacks happen to contain a commit with the same SHA.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't: `repository_owner_that_signed_the_webhook == repository_owner_of_the_commit_being_mutated`. The engine enforces `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` in `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`), which only guarantees the payload was signed by whichever organization's `webhook_secret` matches `repository_owner` from the JSON body — it says nothing about which commit rows get touched downstream.

`StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This never consults `payload.dig('repository', 'full_name')`, unlike the base `Handler` class which defines a `stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) that does scope by `Repository.from_github_repo_name(repository_name)&.stacks`. `StatusHandler` doesn't use that helper at all. `Commit` has only a non-unique index on `(stack_id, sha)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not a global uniqueness constraint on `sha`, so multiple stacks (different repositories/orgs) can legitimately have `Commit` rows sharing the same `sha` (e.g., shared git history, forks, cherry-picks, imported history).

Exploit flow: attacker owns `attacker-org` and its `webhook_secret`. They craft/import a repo history sharing a commit SHA with `victim-org/victim-repo` (e.g. by forking or importing shared history) so a `Commit` row exists in both stacks with identical `sha`. They then `POST /webhooks` with `X-Github-Event: status`, a body `{"sha": "<shared-sha>", "state": "success", "repository": {"full_name": "attacker-org/attacker-repo", "owner": {"login": "attacker-org"}}, ...}`, signed with `attacker-org`'s own `webhook_secret`. `verify_signature` passes because it correctly validates against `attacker-org`. `StatusHandler#process` then finds and mutates **all** `Commit` rows with that `sha`, including the one in `victim-org`'s stack, calling `create_status_from_github!` on it — which creates a `Status`, can flip `deployable_status`, enable CI on the victim's stack (`Status#enable_ci_on_stack`), and schedule `ProcessMergeRequestsJob`/continuous delivery for the victim's stack.

Existing guards do not prevent this: `verify_signature` only authenticates the org, not the target row; `ExplicitParameters` (the `params do ... end` schema) validates payload shape, not scope; there is no `stacks`/repository filter in `StatusHandler`; no model validation ties `Commit#sha` uniquely to one stack.

### Impact Explanation
An attacker-controlled webhook payload for a repository the attacker fully controls mutates commit-status state belonging to a different tenant's stack (`victim-org/victim-repo`), which can enable CI on the victim stack, unblock/merge-gate decisions via `deployable?`/`blocked?` (`app/models/shipit/commit.rb:227-237`), and enqueue `ProcessMergeRequestsJob` — i.e., a payload for one repository mutating another's commit/stack, matching the "Critical" category ("a payload for one repository mutating another's stack, commit, task or team"). It's repeatable per shared SHA and generalizes to any pair of stacks with overlapping commit history (forks, imports, shared upstream repos), which is a plausible real-world occurrence in engineering organizations that mirror/import repositories into Shipit.

### Likelihood Explanation
Preconditions: attacker needs a valid webhook signed with their own org's `webhook_secret` (which they own, per the rules) and needs a commit SHA that collides between their own tracked stack and the victim's tracked stack — realistic when repos are forked/imported/mirrored with shared history, which is common. No victim secrets or privileges are required. Attacker cost is low: one crafted, self-signed HTTP POST.

### Recommendation
Scope the lookup in `StatusHandler#process` to the repository named in the verified payload, mirroring `Handler#stacks`: replace `Commit.where(sha: params.sha)` with a query restricted to `stacks` (e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`), so only commits belonging to the repository that produced the verified signature are mutated.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create `attacker_stack` under `Repository` `attacker-org/attacker-repo`, and `victim_stack` under `Repository` `victim-org/victim-repo`.
2. Create `Commit.create!(stack: attacker_stack, sha: 'deadbeef...')` and `Commit.create!(stack: victim_stack, sha: 'deadbeef...')` (same sha, different stacks).
3. POST a `status` webhook body with `repository.full_name = 'attacker-org/attacker-repo'`, `sha = 'deadbeef...'`, signed/stubbed as valid for `attacker-org`.
4. Assert: `attacker_commit.reload.statuses.count == 1` (mutated, expected) AND `victim_commit.reload.statuses.count == 0` (must NOT be mutated). Current code fails this because `victim_commit.statuses.count` will also be `1`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
