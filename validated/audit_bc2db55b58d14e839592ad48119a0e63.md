### Title
Case-sensitivity mismatch in address validation allows bypass of canonical-address checks in pre-timestamp-upgrade payment outputs - (File: `validation.js`, function `validatePaymentInputsAndOutputs`)

### Summary
`validation.js` selects between two address-validity checkers depending on `last_ball_mci`:
```js
const isValidAddressWithCase = objValidationState.last_ball_mci >= constants.timestampUpgradeMci
    ? ValidationUtils.isValidAddress
    : ValidationUtils.isValidAddressAnyCase;
``` [1](#0-0) 

`isValidAddress` requires the strict canonical uppercase Base32 form (`/^[A-Z2-7]{32}$/`) plus a valid checksum, while `isValidAddressAnyCase` only validates the checksum (`isValidChash`) regardless of letter case: [2](#0-1) 

This is directly analogous to the Monstra CMS bug class in CVE-2018-17418: a security-relevant string (a file extension there, an address here) is validated by one code path with a case-sensitive/canonical check while a parallel, more permissive path accepts case-mangled variants that are nonetheless treated as semantically valid by the rest of the system.

### Finding Description
Every other part of the system — author addresses, `arrAuthorAddresses`, "this address"/"other address" definitions, sorting/duplicate-detection logic across `validation.js` (e.g. `prev_address > output.address`, `arrOutputAddresses.indexOf(...)`) — treats addresses as opaque, case-sensitive strings and assumes the canonical uppercase representation produced by `chash.getChash160`. `isValidAddressAnyCase` breaks that invariant: it accepts any letter-case permutation of a checksum-valid Base32 string (e.g. lowercase or mixed case), which passes the checksum algorithm in `chash.js` (`isChashValid`) purely on bit-level content, independent of case.

Because output-address validation in the pre-`timestampUpgradeMci` branch uses this lenient checker, a poster of a payment unit could submit outputs whose `address` field is a case-variant of a genuine, already-used address. Since string equality, string sorting, and de-duplication elsewhere in the codebase (`arrOutputAddresses.indexOf`, `prev_address` sort checks, wallet-side balance/UI aggregation keyed by address string) are case-sensitive, such an address is treated as a *different* address from its canonical uppercase counterpart even though it decodes to the identical checksum-valid chash. This can defeat address-based invariants such as "outputs must be sorted, duplicates merged, and consolidated per address" and can confuse downstream consumers (wallets, AAs, block explorers) that index balances/authorization by the literal address string, since two textually distinct strings can represent what a human/other component assumes is "the same address."

### Impact Explanation
If reachable, this allows a poster to craft payment outputs that are individually valid (checksum-valid) but not canonically normalized, splitting/duplicating what should be a single logical destination address into multiple string keys. Any downstream logic (wallet balance tracking, AA state, private-payment linking, address-based authorization/spending conditions) that indexes by the literal address string rather than by canonical/normalized chash could disagree about balances or apply spending/definition-matching logic incorrectly — a form of node/wallet disagreement about the correct interpretation of ownership, which maps to the "node disagreement on validity" impact category.

### Likelihood Explanation
The bypass is gated by `objValidationState.last_ball_mci >= constants.timestampUpgradeMci`. This is a historical upgrade point (the flag existed to support units before the wallet/network moved to strict uppercase addresses only) and `timestampUpgradeMci` on both mainnet and testnet has long since passed the current chain height, so the lenient (`isValidAddressAnyCase`) branch is not exercised by any unit that can be included today. This significantly limits practical exploitability under current network conditions — the vulnerable branch is dead code in production but remains present and could regain relevance in unusual reorg/replay/light-client-catchup scenarios that revalidate old units, or if `last_ball_mci` bookkeeping is manipulated.

### Recommendation
- Remove or tightly scope the `isValidAddressAnyCase` fallback so it can never validate output addresses on any currently reachable `last_ball_mci` value, or normalize (canonicalize to uppercase) any address accepted via the lenient path before it is used in comparisons, sorting, deduplication, or storage.
- Audit all other call sites and any wallet/AA code that indexes balances or definitions by raw address strings to ensure they always operate on canonicalized (uppercase) addresses, never on whatever case variant appeared in a historical unit.
- Add regression tests that submit case-permuted but checksum-valid addresses for units at/above and below `timestampUpgradeMci` to confirm consistent rejection/canonicalization.

### Proof of Concept
Not independently verified against the live network because `timestampUpgradeMci` has already passed on both networks, so this could not be demonstrated as an unauthenticated, currently-exploitable path; it is documented here as a residual/legacy weakness rather than a proven live exploit. A concrete PoC would require either (a) validating an old, pre-upgrade unit via light-client catchup/proof replay, or (b) a test harness that sets `objValidationState.last_ball_mci` below `constants.timestampUpgradeMci` and submits a payment message whose output `address` is a lowercase/mixed-case permutation of a valid Base32 chash (e.g. `mxmekgn37h5qo2awht7xrg6lhjvvtawu` instead of `MXMEKGN37H5QO2AWHT7XRG6LHJVVTAWU`), then checks whether it is accepted by `validatePaymentInputsAndOutputs` and how it is subsequently treated by balance/dedup logic that assumes case-sensitive canonical strings.

function isValidChash(str, len){
	return (isStringOfLength(str, len) && chash.isChashValid(str));
}

function isValidAddressAnyCase(address){
	return isValidChash(address, 32);
}

function isValidAddress(address){
	return (typeof address === "string" && /^[A-Z2-7]{32}$/.test(address) && isValidChash(address, 32));
}
