The reported bug class — an unconditional token push to a fixed, non-caller-controlled address that can be frozen/blacklisted, with no escrow fallback, causing entire instructions to permanently revert — has a direct analog in this repo's creator-fee collection flow.

### Title
Permanently frozen creator fees due to unconditional token push with no escrow fallback - (File: `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
`collect_creator_fee_permissionless` and `collect_creator_fee` both transfer the pool's accumulated `creator_fees_token_0`/`creator_fees_token_1` directly from the pool vaults to a fixed destination — the pool creator's associated token account — via `transfer_from_pool_vault_to_user`, with no fallback if that transfer fails.

### Finding Description
Both fee-collection instructions unconditionally push tokens to the creator's ATA: [1](#0-0) 

`collect_creator_fee_permissionless` is explicitly designed to be callable by *any* unprivileged account (`payer: Signer`), while the recipient (`creator_token_0`/`creator_token_1`) is fixed by the `pool_creator` field constraint and cannot be redirected: [2](#0-1) [3](#0-2) 

The token program used for the pool's mints is Token-2022 or legacy SPL Token, both of which support account freezing via the mint's `freeze_authority` (this is a base `Mint` field, not an `ExtensionType`). The pool's own mint-support allow-list (`is_supported_mint`) only inspects `ExtensionType`s (`TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, `ScaledUiAmount`) and does not check or restrict `freeze_authority`: [4](#0-3) 

Thus a pool can legitimately be created for tokens like USDC/USDT that carry a live freeze authority. If the pool creator's associated token account for `vault_0_mint`/`vault_1_mint` is ever frozen (compliance action, sanctions, or malicious front-run freeze), `transfer_checked` from the vault to that account will revert every time, and there is no escrow or alternate claim path — mirroring exactly the root cause described in the referenced report (direct push to a potentially blacklisted/frozen party, no try/catch, no escrow).

### Impact Explanation
Once the creator's destination ATA is frozen, both `collect_creator_fee` and `collect_creator_fee_permissionless` become permanently uncallable for that pool (the destination is fixed and cannot be substituted). The accrued `creator_fees_token_0`/`creator_fees_token_1` balances remain locked inside the pool vaults indefinitely — a permanent freeze of the creator's legitimately earned fee funds, satisfying the "permanent freezing of user funds" impact bar. It does not, however, block swaps, deposits, or withdrawals (those use caller-controlled accounts), so the blast radius is confined to the creator-fee bucket rather than the whole pool, in line with a Medium severity assessment.

### Likelihood Explanation
Any pool creator using a token with an active freeze authority (e.g., USDC/USDT) is exposed the moment their fee-receiving ATA is frozen by the token issuer for any reason (compliance/sanctions, mistaken action, or third-party manipulation of an as-yet-uncreated ATA’s eventual freeze). Since `collect_creator_fee_permissionless` is callable by anyone and creates the account via `init_if_needed`, an attacker cannot force a freeze themselves (freezing requires the mint's freeze authority), but real-world stablecoin freezes are a realistic, externally-triggerable event, making this a credible, non-privileged-signer-triggered scenario once such a freeze occurs.

### Recommendation
Do not let a failed transfer to the creator revert the whole instruction and permanently lock the fee amounts. Wrap the vault-to-creator transfer so that on failure, the amount is instead credited to a per-creator escrow/claimable balance in `pool_state` (or a dedicated PDA) that the creator (or admin) can withdraw once their account is un-frozen or to an alternate address, analogous to the escrow fallback recommended for the referenced Wagmi Leverage fix.

### Proof of Concept
1. A pool is initialized with `vault_0_mint` = a Token-2022/SPL token whose mint has a `freeze_authority` (e.g., a USDC/USDT-style token); `is_supported_mint` does not reject this since freeze authority isn't an inspected `ExtensionType`.
2. Trading occurs and `pool_state.creator_fees_token_0` accumulates value in the vault.
3. The token issuer (freeze authority holder) freezes the pool creator's associated token account for `vault_0_mint` (a normal compliance action against that specific holder).
4. Any subsequent call to `collect_creator_fee` (by the creator) or `collect_creator_fee_permissionless` (by anyone) executes `transfer_from_pool_vault_to_user` targeting the frozen `creator_token_0` account, which reverts inside `token_2022::transfer_checked`.
5. Because the destination account is fixed by the `address = pool_state.load()?.pool_creator` / `associated_token::authority = creator` constraints and there is no fallback path, the accrued `creator_fees_token_0` is permanently unclaimable while the vault continues to hold those tokens.

```rust
pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
```
