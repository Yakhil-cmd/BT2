### Title
Webhook signature verification keyed off attacker-controlled `repository.owner.login` allows cross-organization forgery of push/status/check-suite/PR events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization `webhook_secret` to validate the HMAC signature against using `repository_owner`, a value read directly from the untrusted JSON payload (`repository.owner.login` or `organization.login`). The handler that actually processes the event and writes state, however, resolves the target `Repository`/`Stack` from a *different* field of the same payload: `repository.full_name` [1](#0-0) . Nothing enforces that the organization used to select the verification secret is the same organization whose repository is ultimately acted upon. This is the same class of bug as the reported Omnipool issue: a value used to authorize/validate an operation (`bptIndex`/here, `repository_owner`) is not actually kept in lockstep with the value that determines what gets written (`assetIndex`/here, `repository.full_name`), so the "verified" scope and the "acted upon" scope can diverge.

### Finding Description
- `verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) .
- `GithubApp#verify_webhook_signature` explicitly short-circuits to `true` when no `webhook_secret` is configured for that organization: `return true unless webhook_secret` [3](#0-2) .
- After the signature check passes, `create` re-parses the *same raw body* and dispatches it to handlers keyed by event type: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
- Every handler resolves the actual `Repository`/`Stack` scope from `payload.dig('repository', 'full_name')`, a field independent of the one used to pick the verification secret: `Repository.from_github_repo_name(repository_name)&.stacks` [5](#0-4) . `PushHandler`, `StatusHandler`, and `CheckSuiteHandler` all consume this same `stacks`/`repository_name` resolution and mutate real Shipit state (triggering GitHub syncs, writing commit statuses, scheduling check-run refreshes) [6](#0-5) [7](#0-6) [8](#0-7) .

Binding broken (equality that should hold but doesn't):
`organization used to select verification secret (repository.owner.login)` **≠** `organization/repository whose Stack state is written (repository.full_name)`.

### Impact Explanation
Shipit deployments commonly onboard multiple GitHub organizations, each with its own entry (and its own, possibly-absent `webhook_secret`) under `Shipit.github` — the shipped example config even ships with `webhook_secret: # nil` for sample orgs [9](#0-8) . If any onboarded organization has no `webhook_secret` configured (a documented, supported configuration state, not a misconfiguration the engine rejects), a completely unauthenticated attacker can:
1. Craft a JSON payload with `repository.owner.login` (or `organization.login`) set to that no-secret organization, so `verify_webhook_signature` passes unconditionally.
2. Set `repository.full_name` inside the same payload to `victim-org/victim-repo`, a repository actually tracked by Shipit under a properly-secured organization.
3. Send it to `/webhooks` with any `X-Github-Event` header (`push`, `status`, `check_suite`, etc.).

The handler dispatch never re-checks that the verified organization matches the acted-upon repository, so the forged event is processed against the victim's `Stack`: e.g. `PushHandler` forces a `sync_github` for an attacker-chosen SHA [6](#0-5) , `StatusHandler` writes arbitrary commit statuses on real commits [7](#0-6) , and `CheckSuiteHandler` triggers check-run refresh logic for the victim's commits [8](#0-7) . Because commit statuses and check-run state gate deployability (`Deployable`/merge/deploy checks depend on status/check-run state), an attacker able to write fake "success" statuses for a victim commit can unlock or influence deploy/merge decisions without ever holding a Shipit session, `ApiClient` token, or the victim organization's actual `webhook_secret`. This crosses the "unauthorized deploy" and "cross-repository writes" bar without any privileged credential, satisfying the Critical impact criteria.

### Likelihood Explanation
This requires no privileged access: the attacker needs only (a) knowledge that some organization onboarded to the target Shipit instance has no `webhook_secret` set — a realistic, unenforced configuration (the shipped sample config demonstrates this exact state) — or (b) control of any org with a Shipit-registered GitHub App whose secret they legitimately know (e.g., their own sandbox org added for testing/staging), and simply mismatching `repository.owner.login` against `repository.full_name` in the forged payload. No signature secret for the victim org is ever needed. This is a straightforward, reliably reproducible HTTP request; the only precondition is multi-organization support, which is a first-class documented Shipit feature (`config.github` is keyed by organization, and `Shipit.github(organization:)` is the standard lookup) [10](#0-9) .

### Recommendation
After determining `event`/`repository_owner` for signature verification, re-validate that the organization derived from `repository.full_name` (and/or `organization.login`) used by the dispatched `Handler` matches the organization whose secret validated the signature, rejecting the request (422) on mismatch. Concretely, in `Handler#repository_name`/`stacks`, or centrally in `WebhooksController#verify_signature`, compare the owner segment of `full_name` against `repository_owner` before dispatch, mirroring how `_withdrawFromAuraPool` in the referenced report enforces index consistency before acting.

### Proof of Concept
1. Configure Shipit with two organizations: `attacker-org` (no `webhook_secret`, or one known to the attacker) and `victim-org` (properly secured, tracked stack e.g. `victim-org/victim-repo`).
2. Send:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything
Body:
{
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/attacker-forged"
}
```
3. `verify_signature` resolves `repository_owner = "attacker-org"`, looks up `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the bogus `X-Hub-Signature` [3](#0-2) .
4. `StatusHandler.call(params)` then resolves the target via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` and writes a forged `success` status on the victim's real commit [7](#0-6) , with no credential belonging to `victim-org` ever presented.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
