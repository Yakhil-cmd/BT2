## Analysis Result

### Title
Function-call access key `allowance` cap is silently bypassed for delegate/meta-transactions - (File: `runtime/runtime/src/actions.rs`)

### Summary
`FunctionCallPermission.allowance` is meant to bound the total NEAR that a given function-call access key can spend on gas/deposits on behalf of its owning account. When a transaction is submitted directly (non-meta), the allowance is checked and decremented in the verifier as gas is purchased. However, when the same key is used to sign a `DelegateAction` (meta transaction, NEP-366), `validate_delegate_action_key` validates only the nonce, receiver, method name, and zero-deposit constraints of the `FunctionCallPermission` — it never inspects or updates `allowance`, because in this path the relayer (not the key's owner account) prepays all gas and deposit costs.

### Finding Description
`validate_delegate_action_key` in `runtime/runtime/src/actions.rs` performs the following checks for a function-call-permissioned key when unwrapping a `DelegateAction`: nonce validity, that exactly one `FunctionCall` action is present, that its `deposit == 0`, that the receiver matches `function_call_permission.receiver_id`, and that the method name is allowed [1](#0-0) .
Nowhere in this function, nor in `apply_delegate_action` which invokes it, is `function_call_permission.allowance` read or decremented [2](#0-1) .
This is corroborated by the integration test explicitly asserting that a key with only 1 yoctoNEAR allowance (less than the cost of a single gas unit) still succeeds when routed through a relayer/meta-transaction, and that the allowance value on-chain is left completely unchanged afterward [3](#0-2) .
The project's own architecture documentation independently confirms and names this exact gap: "For allowance, however, there is no check ... even if the allowance of the key is insufficient to make the call directly, indirectly through meta transaction it will still work" [4](#0-3) .

This is structurally identical to the reported bug class: a protective limit (`allowance`, analogous to IL protection) is enforced on one call path (direct transaction / `Router.removeLiquidity()`) but is completely skippable via an alternate, permissionless entry point (delegate action / `Pools.removeLiquidity()` called directly) that any unprivileged account (the relayer) can construct.

### Impact Explanation
Function-call access keys with a small `allowance` are commonly issued as limited-blast-radius session/app keys — the allowance is the *only* mechanism restricting how much value a given key can cause to be spent from/via the owning account over its lifetime, since `receiver_id`/`method_names` only restrict *what* can be called, not how many times or at what gas cost. Via the delegate-action path, any holder of such a key (including an attacker who has captured only this narrowly-scoped key, expecting it to be usable at most a handful of times before the allowance is exhausted) can act as, or collude with, a relayer and invoke the permitted method an unlimited number of times with arbitrarily large prepaid gas, entirely bypassing the allowance cap that was the key's core safety constraint. This produces unauthorized use of the account's identity/predecessor authority beyond what the key issuer intended to permit, which the codebase's own docs acknowledge as a real, if "accepted", consequence.

### Likelihood Explanation
The path is trivially reachable by any account: sign a `DelegateAction` with a restricted function-call key and have any account (including one controlled by the same actor) wrap it as the relayer, exactly as exercised by the existing test `meta_tx_fn_call_access_key_insufficient_allowance` [3](#0-2) . No validator or network-layer privilege is required — it is fully reachable from ordinary submitted transactions.

### Recommendation
Either (a) enforce and account for `allowance` consumption against the relayer-covered cost when a `FunctionCallPermission` key signs a `DelegateAction` (deducting from the key's allowance the same way as in the direct-transaction verifier path), or (b) explicitly document in user-facing NEP-366/access-key documentation that `allowance` provides no protection whatsoever for keys used via meta transactions, and that key issuers must not rely on `allowance` to bound usage if delegate actions are possible for that key. Given this is already documented as intentional in `docs/architecture/how/meta-tx.md`, at minimum the discrepancy should be surfaced prominently in the wallet/access-key-issuance developer documentation, not buried in an internal architecture doc.

### Proof of Concept
1. Create account `bob` with a `FunctionCallPermission` access key with `allowance = 1 yoctoNEAR`, restricted to method `test_method` on receiver `carol`.
2. Have `bob` sign a `DelegateAction` invoking `test_method` on `carol`.
3. Have any relayer account (e.g. `alice`, potentially attacker-controlled) wrap it in a transaction and submit it.
4. Observe the call succeeds and `bob`'s access key allowance is unchanged — reproduced directly by the existing test `meta_tx_fn_call_access_key_insufficient_allowance` [3](#0-2) .
