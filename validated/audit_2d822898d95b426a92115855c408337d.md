### Title
Cross-tenant webhook forgery lets an attacker-controlled GitHub organization grant itself Shipit team membership used for `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
The engine's webhook signature check authenticates only the *organization key* used to pick a secret (`repository_owner`, dug from the untrusted body itself), while every event `Handler` acts on entirely separate fields of the same body (`repository.full_name`, `organization.login`, `team.*`, `member.login`) without re-validating that those fields agree with the organization whose secret actually signed the request.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) to validate against using a value pulled straight out of the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` is looked up per-organization when the engine is configured for multiple GitHub organizations (a documented, supported configuration): [3](#0-2) 

Each organization can have its own independent `webhook_secret`: [4](#0-3) 

The HMAC check only proves "this body was signed with organization X's secret" - it says nothing about which *records* the body's other fields will cause the engine to mutate. Every `Handler` subclass reads unrelated fields from the same body to decide what to write, completely independent of which organization's secret validated it, e.g.:
- `Handler#repository_name` uses `payload.dig('repository', 'full_name')` to find the `Repository`/`Stack` to act on: [5](#0-4) 
- `MembershipHandler#process` uses `params.team` / `params.organization.login` / `params.member.login` to create/update a `Team` and add/remove `Membership` rows: [6](#0-5) 

These `Membership`/`Team` rows are exactly what gate application access: `User#authorized?` grants access if the user belongs to any `Team` in `Shipit.github_teams`: [7](#0-6) 

The binding that should hold is:
`organization whose secret validated the signature == organization/repository/team referenced by the fields the handler acts on`

Instead the engine only enforces "some registered organization's secret signed *some* body", and lets the body's own `organization.login` / `team.id` / `repository.full_name` fields - fully attacker-chosen when the attacker legitimately controls (and knows the `webhook_secret` of) *any* organization onboarded to the same multi-tenant Shipit instance - name a *different* victim organization's team or repository.

Concretely: an attacker who is an administrator of "attacker-org" (one of several organizations configured under `secrets.yml`'s `github:` multi-org schema, per `docs/setup.md`) knows `attacker-org`'s `webhook_secret`. They can POST directly to the (public, unauthenticated) `/github/webhooks` endpoint a `membership` event body where:
- `X-Github-Event: membership`
- body's `organization.login` = `"victim-org"` (a team-restricted org referenced in `Shipit.github_teams`)
- body's `team.id`/`slug` = the real GitHub team ID of a privileged `victim-org` team
- body's `member.login` = the attacker's own Shipit `User#login`
- `action` = `"added"`

There is no `organization`/`repository` field the controller inspects for this event type (`repository_owner` falls back to `params.dig('organization', 'login')`, which the attacker also freely controls), so the controller will look up `Shipit.github(organization: "victim-org")`'s webhook secret to verify... but since the attacker also controls that field, they could just as easily set `organization.login` to their own `attacker-org` (whose secret they know) while the `team.organization` field assigned inside `find_or_create_team!` is taken from that *same* attacker-controlled field. However, `Team.find_or_create_by!(github_id: params.team.id)` matches by the **real GitHub team id**, which the attacker can look up publicly for the target org/team, and once a `Team` row with that `github_id` already exists (created previously via legitimate `victim-org` team-sync), `find_or_create_by!` returns the existing record and the forged event simply calls `team.add_member(member)` on the *real, privileged* `victim-org` team - with the org field in the payload never re-checked against the team actually being mutated.

### Impact Explanation
This lets an attacker escalate into `Shipit.github_teams` authorization - the exact "High" severity category defined in scope - by forging their own Shipit `User` into an arbitrary existing `Team` (including access-gating teams for other tenants/organizations), bypassing GitHub's real team-membership requirement entirely. The same missing binding also lets forged `push`/`pull_request` events name an arbitrary victim `repository.full_name`, triggering `stack.sync_github`, review-stack archival/unarchival, or provisioning on stacks belonging to organizations the attacker's signed secret was never meant to authorize.

### Likelihood Explanation
Requires the deployment to use the documented multi-organization `github:` configuration and requires the attacker to be a legitimate administrator (or leak recipient) of at least one onboarded organization's `webhook_secret` - not a privileged Shipit account, GitHub write access to the victim repo, or any Shipit session/API token. Team `github_id` values are discoverable via GitHub's public API for many orgs, making the membership-escalation path realistic once any single tenant's webhook secret is known to the attacker.

### Recommendation
In `WebhooksController#verify_signature` and in every `Handler`, cross-validate that the organization/repository fields the handler acts on (`repository.full_name`, `organization.login`, `team.organization`) match the organization identity that was actually used to select and validate the webhook secret, rejecting the event otherwise. For `MembershipHandler#find_or_create_team!`, additionally verify `params.organization.login` matches the existing `Team#organization` before mutating membership.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret known to attacker) and `victim-org` (has an existing `Team` row, e.g. `github_id: 12345`, used in `Shipit.github_teams`).
2. Attacker crafts:
```json
{
  "action": "added",
  "team": {"id": 12345, "name": "Ops", "slug": "ops", "url": "https://api.github.com/teams/12345"},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker-github-login"}
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org_webhook_secret, body)>` and POSTs it to `/github/webhooks` with `X-Github-Event: membership`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` (from `repository_owner` fallback) and validates successfully since the attacker knows that secret.
5. `MembershipHandler#process` runs `Team.find_or_create_by!(github_id: 12345)` - matches the pre-existing `victim-org` "Ops" team by `github_id` - and calls `team.add_member(attacker_user)`, granting the attacker's Shipit user membership in `victim-org`'s authorization-gating team, satisfying `User#authorized?` for that tenant without ever authenticating to `victim-org`.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
