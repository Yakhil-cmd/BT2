### Title
Asset attestor list ("`asset_attestors`") can be changed by the asset definer at any time, and light vs. full nodes pick the "latest" list using inconsistent ordering, causing validation disagreement for `spender_attested` assets - ([File: storage.js])

### Summary
The reported bug class is about a privileged actor changing a critical distribution parameter (`rewardToken`) mid-stream without any consistency guarantee, letting different observers compute incompatible results. The `ocore` analog is `readAsset()`'s resolution of the "latest" attestor list for a `spender_attested` asset: full nodes and light clients use two different, non-equivalent ordering criteria to decide which of several competing `asset_attestors` updates is authoritative.

### Finding Description
An asset can be created with `spender_attested: true`, requiring the definer to publish and subsequently update the trusted attestor list via `asset_attestors` messages [1](#0-0) . The definer is free to post a new `asset_attestors` update at any time — validation only checks that the sender is the asset's definer and that the list is well-formed; it places no restriction on frequency or on maintaining consistency with prior updates [2](#0-1) .

When resolving which attestor list currently applies, `readAsset()` in `storage.js` queries all `asset_attestors` units for the asset and picks the "latest" one, but the ordering criterion differs between full nodes and light clients: [3](#0-2) 

Full nodes order by `level` (a deterministic, DAG-derived causal-order value), while light clients order by `units.rowid`, which merely reflects the local insertion order of units into the light client's own SQLite database — an order that depends on when/how the light client happened to request or receive those units from a hub, not on the units' actual DAG position. If a definer posts two (non-double-spending) `asset_attestors` updates that are both stable, `sequence='good'`, and dated before the same `last_ball_mci`, a full node deterministically picks the one with the higher `level`, but a light client can pick a different one depending purely on local retrieval order. This mirrors the report's core issue: a single mutable "current configuration" (the reward token / here, the trusted attestor set) is read by different consumers at different times/via different code paths without a canonical, consistently-derived answer.

### Impact Explanation
This directly determines `objAsset.arrAttestorAddresses`, which feeds into `filterAttestedAddresses()` and ultimately into `validatePayment()`'s check of whether the payer/issuer is attested for a `spender_attested` asset [4](#0-3) . Because light clients rely on this local, non-deterministic resolution instead of the DAG-canonical one used by full nodes/hubs, a light wallet can accept a payment as valid (spender attested) for a payment that a full node would reject, or vice versa. This is a node-disagreement-on-validity condition for private-payment counterparties and light wallet holders of `spender_attested` assets — the exact "different observers end up with inconsistent state due to a changed configuration" bug class described in the source report, but here reachable by any asset issuer without special privileges over the protocol.

### Likelihood Explanation
Any asset definer can trivially post multiple `asset_attestors` updates for their own `spender_attested` asset; no cost/rate-limit prevents this beyond normal fees, and the "one update per unit" rule only limits how many updates fit in a single unit, not how many can be issued over time [5](#0-4) . The divergence is triggered purely by the definer choosing to post competing `asset_attestors` units, something entirely within the reach of an ordinary asset issuer/spender_attested-asset holder.

### Recommendation
Make the "latest attestor list" resolution deterministic and identical for both full and light nodes — e.g., always resolve by DAG level (or another canonical, hash-based tie-break) rather than falling back to `units.rowid` for light clients, or explicitly disallow ambiguous concurrent `asset_attestors` updates so at most one canonical list can exist before a given `last_ball_mci`.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and attestor list `[X]`.
2. `D` posts `asset_attestors {asset: A, attestors: [X]}` (unit `U1`).
3. Later, `D` posts a second `asset_attestors {asset: A, attestors: [Y]}` (unit `U2`), positioned in the DAG so it is not a double-spend but has ambiguous causal ordering relative to some other stable unit(s) at the same MCI window.
4. Once both `U1` and `U2` are stable and `sequence='good'`, a full node computes the "latest" list via `level DESC`; a light client computes it via `units.rowid DESC`, which reflects only the order the light client happened to fetch/store `U1`/`U2` locally — e.g., a light wallet that requested `U2` before `U1` while a hub/full node's DAG level ordering ranks `U1` as later.
5. A payment from address attested for `[X]` but not `[Y]` (or vice versa) is then judged valid by the light client and invalid by the full node (or vice versa), demonstrating the consensus-relevant discrepancy stemming from `storage.js` lines 1921-1930.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
