### Title
Unauthenticated `membership` webhook grants team authorization when `webhook_secret` is unset - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` whenever `webhook_secret` is blank, which is the default/shipped configuration in this repo. Combined with `MembershipHandler#process`, an unauthenticated attacker can add any user (including one they control) to any `Shipit::Team` referenced by `id` in the config's `oauth.teams`, flipping `User#authorized?` to true and unlocking the entire web UI.

### Finding Description
The broken binding is: `request signature verified by webhook_secret of organization O` == `organization O owning the Team record being mutated`. This never holds when `webhook_secret` is nil, because no signature check occurs at all.

Code path:
- `Shipit::WebhooksController#verify_signature` fetches `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)` [1](#0-0) .
- `GitHubApp#verify_webhook_signature` short-circuits `return true unless webhook_secret` [2](#0-1) , and `@webhook_secret = @config[:webhook_secret].presence` [3](#0-2) .
- The default/example configs ship with `webhook_secret` unset: `config/secrets.development.example.yml` line 11, `test/dummy/config/secrets.test.json` line 12, `test/dummy/config/secrets.yml` line 13 all show `webhook_secret: # nil` [4](#0-3) [5](#0-4) .
- With signature check bypassed, `Shipit::Webhooks.for_event('membership')` dispatches to `Handlers::MembershipHandler` [6](#0-5) .
- `MembershipHandler#process` calls `find_or_create_team!` (which does `Team.find_or_create_by!(github_id: params.team.id)`, trusting attacker-supplied `team.id`/`name`/`slug`/`url`/`organization.login`) and then `team.add_member(User.find_or_create_by_login!(params.member.login))` for `action == 'added'` [7](#0-6) .
- `Team#add_member` appends the member unconditionally [8](#0-7) .
- `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [9](#0-8) , and `force_github_authentication` gates the entire authenticated UI on this predicate [10](#0-9) .

No other guard intervenes: `drop_unhandled_event` only checks that a handler is registered for the event name, not provenance [11](#0-10) ; the `ExplicitParameters` schema on `MembershipHandler` only validates shape/types, not the organization/team ownership [12](#0-11) .

Attacker request: `POST /webhooks` with header `X-Github-Event: membership`, no `X-Hub-Signature`, body `{"action":"added","team":{"id":<id of an existing Shipit::Team whose id is in Shipit.github_teams.map(&:id)>,"name":"x","slug":"x","url":"http://x"},"organization":{"login":"shopify"},"member":{"login":"attacker"}}`.

### Impact Explanation
An unauthenticated internet request creates a `Membership` row binding an attacker-chosen (or newly created) `User` login to a privileged `Team`, which is checked by `User#authorized?` on every controller action gated by `force_github_authentication`. This is repeatable for any team id and any login, is not tied to any tenant boundary, and results in full authenticated access to the Shipit web UI (deploy, rollback, merge, task creation) — matching the "Critical: authentication bypass (forged webhook ... accepted)" category.

### Likelihood Explanation
The only precondition is that the deployed instance's `secrets....github.webhook_secret` is unset — which is exactly the value in every shipped example/default config in this repo (`config/secrets.development.example.yml`, `test/dummy/config/secrets.test.json`, `test/dummy/config/secrets.yml`, `test/dummy/config/secrets_double_github_app.yml`). Any operator who deploys without explicitly setting a webhook secret is exposed. Attacker cost is a single unauthenticated HTTP POST with no secrets, tokens, or GitHub App keys required, and the attack is fully repeatable and scriptable.

### Recommendation
Fail closed instead of open in `GitHubApp#verify_webhook_signature` (i.e., treat a blank `webhook_secret` as a misconfiguration that rejects all webhooks, or require signature verification unconditionally and refuse to boot/serve `/webhooks` without a configured secret), and additionally bind `MembershipHandler#find_or_create_team!` to reject/refuse creating or mutating a `Team` whose `organization` does not match the `repository_owner`/verified webhook organization.

### Proof of Concept
In an `ActionDispatch::IntegrationTest` (or existing `WebhooksControllerTest` style using `ActionController::TestCase`):
1. Stub `Shipit.github(organization: 'shopify')` to return a `GitHubApp` built with `webhook_secret: nil` (matches `test/dummy/config/secrets.test.json`, no stubbing needed even, as it's already nil in test config).
2. Set `Shipit.github_teams` (or rely on `test/fixtures/shipit/*teams.yml`) to include a team, e.g. `shipit_teams(:shopify_developers)`.
3. POST to `/webhooks` (via `webhooks_controller#create`) with `X-Github-Event: membership`, no `X-Hub-Signature` header, and body `{action: 'added', team: {id: shipit_teams(:shopify_developers).id, name: 'x', slug: 'x', url: 'http://x'}, organization: {login: 'shopify'}, member: {login: 'attacker'}}.to_json`.
4. Assert `response` is `:ok` (200), then assert `User.find_by(login: 'attacker').authorized?` is `true`, and `Team.find_by(id: shipit_teams(:shopify_developers).id).members.map(&:login)` includes `'attacker'`.
5. Both sides of the binding — "verified organization" (none, since no secret checked) vs. "organization owning mutated team" (`shopify`) — diverge, confirming the vulnerability. This mirrors the existing test `":membership can append an user membership"` in `test/controllers/webhooks_controller_test.rb:159-165`, which already demonstrates unsigned membership webhooks succeed against the shipped test config.
