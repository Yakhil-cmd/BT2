### Title
Stack-scoped ApiClient token discloses build/deploy status of unauthorized stacks via CCMenu API - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup used by `Shipit::Api::BaseController` in a way that discards the stack-scoping enforced for `ApiClient` tokens, breaking the binding: "stack a token authorises" == "stack it touches".

### Finding Description
`Shipit::Api::BaseController` establishes a binding between an authenticated `ApiClient` and the stacks it may see: `stacks` restricts to the client's own `stack_id` when the client is stack-scoped, and `stack` is looked up through that scoped relation: [1](#0-0) 

`Shipit::ApiClient` supports being bound to a single stack (`belongs_to :stack, optional: true`), and `check_permissions!` only checks the operation/scope string (e.g. `read:stack`), never the stack binding itself: [2](#0-1) 

`Shipit::Api::CCMenuController` inherits from `BaseController` and declares `require_permission :read, :stack`, but it overrides `stack` to bypass the scoped `stacks` relation entirely and instead resolves any stack directly from the request parameter: [3](#0-2) 

It also overrides `authenticate_api_client` to accept the token via a query parameter instead of Basic Auth, which is otherwise consistent with how the base controller resolves an `ApiClient`: [4](#0-3) 

Because `require_permission!` only calls `current_api_client.check_permissions!(operation, scope)` (a permission-string check, not a stack-identity check), and because `stack` no longer routes through `stacks`, any `ApiClient` holding `read:stack` permission — including one that is supposed to be restricted to a single stack via `stack_id` — can be used with an arbitrary `stack_id` request parameter to reach any stack in the installation.

The test suite demonstrates that this scoping is expected to matter elsewhere (e.g. `StacksController#index`), confirming stack-bound `ApiClient`s are a real, relied-upon security boundary in this engine: [5](#0-4) 

### Impact Explanation
This crosses the "unauthenticated/unauthorized read of stack state, task streams or deploy output" High-severity bucket: an `ApiClient` token that was deliberately scoped to a single stack (so that leaking that token only exposes one stack's build status) can instead be used to read the CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, etc., rendered by `shipit/ccmenu/project`) of every stack in the Shipit instance, defeating the purpose of stack scoping.

### Likelihood Explanation
Any holder of a stack-scoped `read:stack` token (a credential explicitly meant to be narrowly scoped, e.g. distributed to a CI dashboard/CCMenu client for one project) can trivially exploit this by simply changing the `stack_id` request parameter — no additional privilege or session is required beyond possessing that one legitimately-scoped token.

### Recommendation
Have `Shipit::Api::CCMenuController#stack` resolve through the same scoped `stacks` relation used by `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of unscoped `Stack.from_param!(params[:stack_id])`, so stack-bound `ApiClient` tokens cannot be used to query stacks outside their `stack_id` binding.

### Proof of Concept
1. Create an `ApiClient` bound to `stack_id: <stack A>.id` with permission `read:stack` (mirrors the `here_come_the_walrus` fixture pattern used in tests: [6](#0-5) ).
2. Obtain that client's `authentication_token`.
3. Send `GET /api/stacks/:stack_id/ccmenu.xml?token=<token>` where `:stack_id` refers to stack B (a different stack the client is not bound to).
4. `authenticate_api_client` in `CCMenuController` successfully resolves the same `ApiClient` from the token. `require_permission :read, :stack` passes because the client has `read:stack` permission (permission check is scope-string only, not stack-identity). `stack` resolves stack B directly via `Stack.from_param!`, bypassing the `stacks` scoping that would have raised a not-found error for `BaseController#stack`. The response renders stack B's build status, disclosing information the token was never authorized to see.
