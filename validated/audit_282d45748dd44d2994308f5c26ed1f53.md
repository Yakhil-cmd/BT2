### Title
Unauthenticated crash via NULL/undefined `dh.recipient_ephemeral_pubkey` mismatch in `decryptPackage()` triggers an unhandled exception on the device-message decrypt path - (File: device.js)

### Summary
`device.decryptPackage()` decrypts device messages received via a hub. When the `recipient_ephemeral_pubkey` in a crafted encrypted package does not match any of the recipient's known keys (temp, prev-temp, permanent), the function does not simply return an error to the caller. Instead, at [1](#0-0) , it schedules a `setTimeout` callback that unconditionally `throw`s an `Error`. Because this throw happens inside an asynchronous `setTimeout` callback, it executes outside of any surrounding `try/catch` (the call sites at [2](#0-1)  and [3](#0-2)  only guard the synchronous call, not the deferred timer callback), making it an unhandled exception in the Node.js event loop.

### Finding Description
This mirrors the LZWDecode-class bug: attacker-supplied, malformed/unexpected input (here, a `recipient_ephemeral_pubkey` value that doesn't match a valid key) is not defensively rejected before reaching a path that dereferences/executes unchecked logic, and instead of a controlled error return, the code path leads to an unrecoverable runtime fault (a thrown, uncaught exception) that terminates the process.

Reachability: any correspondent device (or even a non-paired device, since `pairing`, `my_xpubkey`, and `wallet_fully_approved` subjects are explicitly allowed from unknown correspondents per [4](#0-3) ) can send a `hub/message` whose `encrypted_package.dh.recipient_ephemeral_pubkey` is a garbage/expired/rotated value. The hub-side field presence checks at [5](#0-4)  only validate that the fields exist and are strings — they never validate that the `recipient_ephemeral_pubkey` actually equals a key the recipient currently holds. Message signature/hash verification (lines 163-172) does not protect this field's semantic correctness. The message is then decrypted via `decryptPackage` at [2](#0-1) , which hits the "unknown key" branch and schedules the crash.

### Impact Explanation
The thrown error inside `setTimeout` is not caught by any wrapping `try/catch` in the JS event loop; unless the host process has a global `process.on('uncaughtException', ...)` handler that swallows all errors (not confirmed present for this particular throw path), the Node.js process will terminate. For a full/witness/hub-serving node, this is a remote, unauthenticated (or minimally-privileged, "any correspondent") denial of service: the affected node stops processing and validating units/messages until restarted, i.e., "a network unable to confirm new units" if this affects witness or serving nodes broadly, matching the Medium severity/DoS class of the original LZWDecode NULL-pointer-dereference report.

### Likelihood Explanation
Likelihood is limited by the note that: (1) the throw only fires when the local key cannot be matched, which normally happens due to legitimate key rotation edge cases, but can be deliberately forced by any device sending a message with a bogus `recipient_ephemeral_pubkey`; and (2) I could not fully verify within the available context whether `network.js`'s `uncaughtException` handlers (referenced but not fully inspected) intercept and neutralize this specific throw before process termination. This is the main uncertainty in this analog — I was not able to read the full contents of the `uncaughtException` handler in `network.js` before the investigation budget ran out, so the actual crash-vs-swallowed outcome is unconfirmed.

### Recommendation
- Replace the `setTimeout(() => { throw ... })` pattern in `decryptPackage()` (device.js line 431-433) with a safe, caught error path: emit a `nonfatal_error` event (the code already has a commented-out `eventBus.emit('nonfatal_error', ...)` alternative) instead of throwing, or wrap the deferred throw in code that funnels into existing error-handling/telemetry rather than raising an uncaught exception.
- Confirm and, if necessary, harden the global `uncaughtException` handler in `network.js` so that isolated per-message decrypt failures cannot crash the whole node process.

### Proof of Concept
1. Attacker (any correspondent device, or non-correspondent using an allowed subject like `pairing`) sends a `hub/message` justsaying to the hub, addressed to victim's device, with a well-formed `encrypted_package` whose `dh.recipient_ephemeral_pubkey` is any base64 string that is not the victim's current temp, previous temp, or permanent device pubkey (e.g., a random freshly-generated ephemeral pubkey), and a valid signature over the fields the hub checks.
2. Hub forwards this message; victim's `handleJustsaying('hub/message', ...)` validates hash/signature (which don't cover key-matching), then calls `decryptPackage()`.
3. `decryptPackage()` falls into the `else` branch at device.js:429, logs "message encrypted to unknown key", and schedules the `setTimeout` throw.
4. 100ms later, the scheduled callback throws, uncaught by any `try/catch`, potentially crashing the victim's node process (subject to the unverified global handler behavior noted above).
