## Title
Webhook signature is verified against the organization inferred from `repository.owner.login`, but handlers act on `repository.full_name` — allowing a party who owns a webhook secret for one configured GitHub organization to forge events that mutate stacks belonging to a different organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
When Shipit is configured with the multi-organization GitHub App schema (`Shipit.github(organization:)`), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC signature against using an **unverified** field from the JSON body: `repository.owner.login` (or `organization.login`). Once that check passes, the event is dispatched to handlers (`PushHandler`, `StatusHandler`, PR handlers, etc.) which resolve the actual `Repository`/`Stack` to mutate using a **different** field of the same unverified body: `repository.full_name`. Because the field used to choose the verifying secret is not cryptographically bound to the field used to select the target repository, an attacker who legitimately knows the webhook secret for *any* one configured organization can craft a payload whose signature validates under their own org's secret while `repository.full_name` points at a stack belonging to a *different* organization onboarded to the same Shipit instance.

### Finding Description
`verify_signature` computes the signing organization from attacker-controlled JSON before the signature is checked: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up the per-organization config (and thus the `webhook_secret` used to verify) purely from this untrusted body field: [3](#0-2) 

Once verification passes, the event handlers never re-check `repository.owner.login`; instead they resolve the target repository/stack from a *different* payload field, `repository.full_name`: [4](#0-3) [5](#0-4) [6](#0-5) 

This is documented as an intended multi-tenant deployment mode, where each organization owns and configures its own GitHub App and therefore its own `webhook_secret` in `config/secrets.yml`: [7](#0-6) 

The binding that should hold is:
`organization whose webhook_secret authenticated the request == organization that owns the repository being written to`

But nothing enforces this equality: `repository_owner` (used only to pick the verifying secret) and `repository.full_name` (used to pick the mutated `Repository`/`Stack`) are independent, sibling fields inside the same unverified JSON body. An attacker who is an admin of `OrgA` (and thus legitimately knows `OrgA`'s `webhook_secret`, since GitHub App owners set/see this secret themselves) can:
1. Set `repository.owner.login` = `OrgA` (so `Shipit.github(organization: "OrgA")` is used).
2. Sign the raw body with `OrgA`'s known `webhook_secret`, so `verify_webhook_signature` passes.
3. Set `repository.full_name` = `OrgB/some-repo` (a repository belonging to a different organization, `OrgB`, tracked by the same Shipit instance).

The signature passes, then a handler such as `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgB/some-repo")` and calls `stack.sync_github(expected_head_sha: params.after)`, which enqueues `GithubSyncJob` for `OrgB`'s stack with an attacker-chosen `expected_head_sha`: [8](#0-7) 

The job itself re-fetches commits through GitHub's API using the credentials of the actual repository owner (`stack.github_api` → `Shipit.github(organization: repository.owner)`), so it cannot be used to inject fake commit content — but the attacker still gets an unauthorized, cross-organization write: they can trigger sync/status/PR-state changes and job enqueuing (`GithubSyncJob`, `CacheDeploySpecJob`, PR create/archive/unarchive via `ReviewStackAdapter`, commit `Status` creation via `StatusHandler`) against a stack/repository they have no legitimate relationship to, purely because they hold a secret for an unrelated organization onboarded to the same instance.

### Impact Explanation
This crosses the "cross-repository writes" bar explicitly called out as acceptable High/Critical impact: an unprivileged-with-respect-to-`OrgB` attacker (who is only an admin/owner of `OrgA`'s GitHub App) can cause writes against `OrgB`'s `Stack`/`Repository`/`PullRequest`/`Commit` records — enqueuing sync jobs, creating/archiving review stacks, and injecting bogus commit statuses — despite the webhook signature check nominally protecting the endpoint. The root cause is that the field trusted to select the verifying secret (`repository.owner.login`) is never bound to the field trusted to select the mutated resource (`repository.full_name`).

### Likelihood Explanation
This requires the deployment to use the documented multi-organization GitHub App configuration (multiple orgs sharing one Shipit instance) and for the attacker to be a legitimate owner/admin of at least one of those onboarded GitHub Apps — a realistic scenario for any Shipit instance shared across multiple business units/orgs, which is the explicit purpose of the "Using Multiple Github Applications" feature. No GitHub App private key, Shipit session, or `ApiClient` token is required — only a webhook secret the attacker is entitled to know for their own org.

### Recommendation
Bind signature verification to the same identity used for resource resolution. Concretely:
- After selecting `github_app` from `repository_owner` and verifying the signature, re-derive the organization from `repository.full_name` (or `organization.login`) and require it to match `repository_owner` before dispatching to handlers; reject (422) on mismatch.
- Alternatively, verify the payload against *every* configured organization's `webhook_secret` and only proceed if the one that verifies also matches the owner encoded in `repository.full_name`.
- Handlers should never trust `repository.full_name` in isolation for cross-tenant deployments without confirming it is consistent with the verified organization.

### Proof of Concept
1. Configure Shipit in multi-org mode with `OrgA` and `OrgB`, each with their own `webhook_secret` (per `docs/setup.md`, "Using Multiple Github Applications").
2. As the legitimate owner of `OrgA`'s GitHub App, know `OrgA`'s `webhook_secret`.
3. Craft a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>`.
5. `POST /webhooks` with header `X-Github-Event: push`.
6. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, verifies successfully against `OrgA`'s secret.
7. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, and if that stack exists and its branch matches, calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, enqueuing `GithubSyncJob` against `OrgB`'s stack — a cross-organization write triggered solely with `OrgA`'s credentials.

(Note: full end-to-end confirmation of downstream effects of `GithubSyncJob`/`CacheDeploySpecJob` on deploy triggering was not exhaustively traced beyond what is cited above; the core cross-tenant signature/resource binding break is confirmed directly from `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, and `lib/shipit.rb`.)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
