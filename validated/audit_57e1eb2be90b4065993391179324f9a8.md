### Title
Cross-organization webhook forgery via signature/payload owner-field mismatch enabling forged commit statuses and unauthorized push syncs on stacks belonging to a different GitHub organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). However, none of the actual event handlers (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`) resolve the target `Repository`/`Stack` using that same `owner.login` field — they instead resolve it from `repository.full_name` (`Shipit::Repository.from_github_repo_name`) or, for `StatusHandler`, from a bare `sha` lookup with no repository/owner check at all. In a Shipit instance configured for multiple GitHub organizations (an explicitly documented and tested configuration), an attacker who legitimately administers one onboarded organization (and thus knows that organization's real `webhook_secret`) can craft an arbitrary HMAC-valid POST to `/webhooks` whose `repository.owner.login` names their own org (so the correct/known secret is selected and signature verification passes) while `repository.full_name` (or simply the commit `sha`) references a stack/commit belonging to a different, victim organization also hosted on the same instance.

### Finding Description
The equality that should hold is:
`organization whose secret validated the signature == organization that owns the repository/stack the handler subsequently writes to`.

- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` comes directly from the untrusted JSON body (`repository.owner.login` or `organization.login`), then verifies `X-Hub-Signature` against that specific org's `webhook_secret`. [1](#0-0) [2](#0-1) 

- Multiple independent GitHub-App configurations (one webhook secret per org) sharing a single Shipit instance is an explicitly supported and tested configuration. [3](#0-2) [4](#0-3) 

- After signature verification passes, `create` re-parses the *same* raw body and dispatches it to handlers unchanged — the `owner.login` value used for the security decision is never re-checked against anything the handler later trusts. [5](#0-4) 

- `PushHandler` resolves the stacks to sync purely from `repository.full_name`, with no cross-check against the `owner.login` used to pick the signing secret: [6](#0-5) [7](#0-6) 

- `StatusHandler` is worse: it doesn't even use `repository` — it looks up **any** `Commit` in the entire database matching the given `sha` and attaches an attacker-supplied status/state to it, regardless of which repository/org that commit belongs to: [8](#0-7) 

Because HMAC-SHA1 signs the raw bytes of the body but the code never verifies that the `owner.login` field used to select the secret is *consistent* with the `full_name`/`sha` fields the handlers act on, an org that is a legitimate but unprivileged tenant of the shared Shipit instance can forge events that mutate/observe state belonging to a completely different tenant.

### Impact Explanation
An attacker who administers Org A (onboarded, with a real, known `webhook_secret`) on a shared multi-org Shipit deployment can:
- Post a forged `status` event, signed with Org A's own secret, targeting a commit `sha` that belongs to Org B's private repository/stack, injecting a fabricated "success" CI status via `Commit#create_status_from_github!`. If Org B's `shipit.yml` gates deploys on required CI contexts (`ci.require`), this can be used to make an otherwise-failing/unreviewed commit appear deployable, contributing to an **unauthorized deploy** of Org B's stack — one of the explicitly listed Critical/High impacts.
- Post a forged `push` event, signed with Org A's secret but naming Org B's `repository.full_name`, forcing `GithubSyncJob`/`stack.sync_github(expected_head_sha:)` to run against Org B's stacks, which can trigger continuous-deployment pipelines outside Org B's control.

This breaks the intended trust boundary between independently onboarded organizations sharing one Shipit instance, which the engine explicitly supports (`Shipit.github_organizations`, `test/dummy/config/secrets_double_github_app.yml`).

### Likelihood Explanation
Requires only that: (1) the operator hosts more than one GitHub organization's apps on a single Shipit instance (a documented, tested, first-class configuration), and (2) the attacker legitimately administers at least one of those organizations (able to see/rotate its own `webhook_secret` — no privileged Shipit access, no `ApiClient` token, and no access to the victim org is required). Crafting the forged JSON body and computing the HMAC with a known secret is trivial. No social engineering, TLS interception, or host misconfiguration beyond "multi-tenant deployment" (which the engine markets/documents as supported) is needed.

### Recommendation
After selecting the GitHub App/secret via `repository_owner` and verifying the signature, re-validate that every repository/commit the handler subsequently touches actually belongs to that same, signature-verified organization (e.g., compare `repository.full_name.split('/').first` against `repository_owner`, and have `StatusHandler` scope its `Commit` lookup by the stack's repository owner) before performing any handler side effects.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately administers `OrgA` and knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a JSON body:
```json
{
  "sha": "<victim-commit-sha-belonging-to-OrgB>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and sends `POST /webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature using `OrgA`'s real secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, applying the forged `success` status to the victim commit belonging to `OrgB`, with no check that `OrgA` has any relationship to that commit/repository.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
